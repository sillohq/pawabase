Pawabase's configuration is entirely environment-variable-driven. Every service reads its settings from the `.env` file that `docker-compose.yml` loads into every container. There is no configuration file on disk, no JSON config blobs in a database, and no command-line flags to pass at runtime. This keeps configuration simple and auditable — you can diff `.env` across environments, review it in version control (minus the secrets), and know exactly what every process is doing.

This page catalogs every variable Pawabase reads, organized by category: secrets, URLs and ports, security, infrastructure, and development-only flags.

## Required secrets

These six variables **must** be set before `docker compose up` will succeed. The `docker-compose.yml` validates `POSTGRES_PASSWORD` explicitly, but the remaining secrets are required at runtime — the API, Akountz, and Angula will fail to start if they are missing or empty.

<AccordionGroup>
  <Accordion title="PAWABASE_INTERNAL_SECRET">
    A 32-byte hex string. Signs service-to-service tokens. Every internal call between services carries a JWT signed with this secret, and the receiving service verifies it before processing the request. It must be identical in every container (it is loaded from `.env`, which all services share). Generate with `openssl rand -hex 32`. Never expose it to any client-side code.
  </Accordion>
  <Accordion title="PAWABASE_JWT_MASTER_SECRET">
    A 32-byte hex string. The master key from which every per-environment user token signing key is derived: `HMAC(master_key, "<project>:<env>")`. This means a token minted for `acme/development` cannot be used against `acme/production` — the derived key is different, and the signature will fail verification. Compromising this key invalidates every token in every project and every environment. Rotate it only as a break-glass operation — see [Upgrades](/self-hosting/upgrades). Generate with `openssl rand -hex 32`.
  </Accordion>
  <Accordion title="PAWABASE_MASTER_KEY">
    A 32-byte hex string. Encrypts environment secrets (`secret://NAME` values) and webhook signing keys at rest in the database. If this key is lost, all stored secrets are unrecoverable — you would need to re-create every secret for every environment manually. Generate with `openssl rand -hex 32`. Store a backup somewhere safe (a password manager, a sealed envelope in a safe).
  </Accordion>
  <Accordion title="POSTGRES_PASSWORD">
    The password for the `pawabase` database superuser on the bundled Postgres. The `docker-compose.yml` enforces it with `${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}`, which causes Compose to abort with a clear error if unset. Used in the `PAWABASE_DATABASE_URL` connection string inside the API and Akountz containers. Generate with `openssl rand -hex 32`.
  </Accordion>
</AccordionGroup>

<Warning>
All three master secrets (`INTERNAL_SECRET`, `JWT_MASTER_SECRET`, `MASTER_KEY`) are generated once and never change unless you deliberately rotate them. They are the root of trust for the entire platform. If any is compromised, the blast radius is the entire installation — every project, every environment, every user. Generate them with `openssl rand -hex 32` and store them in a secrets manager.
</Warning>

## Required admin credentials

<AccordionGroup>
  <Accordion title="PAWABASE_ADMIN_EMAIL">
    The email address of the first platform operator. On startup, if no operator exists for the reserved `_platform` project, Akountz creates one with this email, sets the password from `PAWABASE_ADMIN_PASSWORD`, and grants the built-in `admin` role with `permissions=["*"]`. This is the account you use to sign into Studio for the first time. The email must be unique — if an operator with that address already exists, it is not recreated.
  </Accordion>
  <Accordion title="PAWABASE_ADMIN_PASSWORD">
    The password for the initial operator account. Must contain upper- and lower-case letters, a digit, and a symbol. After the first login, change this password through Studio's account settings. Do not leave the initial credentials in `.env` on a production host — rotate them immediately after the first admin login.
  </Accordion>
</AccordionGroup>

## URL and port configuration

These variables control how clients and other services reach Pawabase.

<AccordionGroup>
  <Accordion title="PAWABASE_PUBLIC_URL">
    The origin that clients, browsers, and email links use. Every URL in a password reset email, every OAuth callback URL, every signed storage URL, and every CORS origin check is built relative to this value. In development, set it to `http://localhost:8080`. In production, set it to your actual domain, e.g., `https://api.your-app.example.com`.

    <Warning>
    This must match the actual URL users access. If `PAWABASE_PUBLIC_URL` says `http://localhost:8080` but users reach Pawabase at `https://api.example.com`, signed storage URLs will point to localhost (and fail), OAuth callbacks will redirect to localhost (and break), and CORS will reject requests from the real origin. This is the single most common configuration error in self-hosted deployments.
    </Warning>
  </Accordion>
  <Accordion title="PAWABASE_PUBLIC_GATEWAY_URL">
    Separate from `PAWABASE_PUBLIC_URL` for cases where the gateway sits behind a different URL than the public API origin. In most deployments, these are the same. The gateway uses this for constructing URLs it returns to clients.
  </Accordion>
  <Accordion title="PAWABASE_GATEWAY_PORT">
    The host port the gateway exposes. Defaults to `8080`. Change this if port 8080 is already in use, but remember to update your reverse proxy configuration accordingly.
  </Accordion>
  <Accordion title="PAWABASE_STUDIO_PORT">
    The host port Studio exposes. Defaults to `8090`. Change this if port 8090 is occupied.
  </Accordion>
</AccordionGroup>

## Security configuration

<AccordionGroup>
  <Accordion title="PAWABASE_COOKIE_SECURE">
    Controls whether Studio's session cookie carries the `Secure` flag. When `true`, the cookie is only sent over HTTPS connections. This must be `true` in production — if you are behind a reverse proxy that terminates TLS, set this to `true` and ensure the proxy forwards the `X-Forwarded-Proto` header so Studio can detect that the original request was HTTPS.

    Setting this to `false` in production means the session cookie is transmitted in plaintext over HTTP, which makes session hijacking trivial on any network an attacker can observe.
  </Accordion>
  <Accordion title="PAWABASE_APP_ENV">
    The application environment name. Defaults to `production`. This affects logging verbosity, error detail in responses (production hides stack traces; development shows them), and certain feature flags. Set to `local` or `development` when running `scripts/dev.sh`. Never set this to `production` on a developer's laptop unless you intend for every error to be silently swallowed in logs.
  </Accordion>
  <Accordion title="PAWABASE_DB_GENERATE_SCHEMAS">
    Controls whether the API automatically creates database schemas for new projects on startup. Defaults to `true` when running `scripts/dev.sh` and is not set in the production `.env.example`. In production, schemas should be managed by the API's migration system rather than auto-generated.
  </Accordion>
</AccordionGroup>

## Infrastructure defaults

<AccordionGroup>
  <Accordion title="PAWABASE_DEFAULT_DATA_URL">
    The fallback database connection string for environments that have not configured their own `infra.database_url` in Studio. Defaults to `sqlite:///data/envs/{project}__{env}.db`, which creates a SQLite file per `(project, environment)` pair inside the `api-data` volume. The `{project}` and `{env}` placeholders are substituted at runtime.

    In production, you should configure each environment with an explicit Postgres URL through Studio's Infrastructure settings (`Settings → Infrastructure`). The SQLite fallback is intended for development, demo projects, and testing — it does not support concurrent connections, which means two requests arriving simultaneously on the same SQLite-backed environment will queue.
  </Accordion>
  <Accordion title="PAWABASE_STORAGE_* (file storage)">
    Where uploaded files go for every environment that has not configured its own storage in Studio. The Docker install runs a bundled **MinIO** and points these settings at it, so file storage works with nothing to set up: Pawabase creates its bucket on first start and keeps each project environment's files under its own prefix.

    To use your own S3-compatible service (AWS S3, Cloudflare R2, Backblaze B2, DigitalOcean Spaces, Wasabi, Ceph), set the endpoint and credentials in `.env` and run `docker compose up -d --scale minio=0`:

    ```bash
    PAWABASE_STORAGE_ENDPOINT=https://<account>.r2.cloudflarestorage.com
    PAWABASE_STORAGE_BUCKET=pawabase
    PAWABASE_STORAGE_REGION=auto
    PAWABASE_STORAGE_ACCESS_KEY=...
    PAWABASE_STORAGE_SECRET_KEY=...
    ```

    `PAWABASE_STORAGE_PUBLIC_ENDPOINT` is the address browsers use for presigned upload and download URLs. It defaults to the endpoint you set, or `http://localhost:9000` for the bundled MinIO; behind a domain, set it to that domain. `PAWABASE_STORAGE_PATH_STYLE` defaults to `true` (`host/bucket/key`); set it to `false` for virtual-hosted addressing (`bucket.host/key`) as AWS S3 prefers. An environment that sets `infra.storage` in Studio overrides all of this for itself.
  </Accordion>
  <Accordion title="PAWABASE_STORAGE_ROOT">
    The directory inside the API container used when file storage runs on the local disk, that is, when no `PAWABASE_STORAGE_ENDPOINT` is set (running the API outside Docker, for example). Defaults to `/data/objects`, inside the `api-data` volume.
  </Accordion>
  <Accordion title="PAWABASE_CODE_PATH">
    The directory where example code projects are mounted for the API to access. Defaults to `/code`, mapped to `./examples/code` on the host. This is used by the code examples that ship with the platform and by the function compiler when it needs to resolve imports.
  </Accordion>
</AccordionGroup>

## Inline worker and scheduler flags

<AccordionGroup>
  <Accordion title="PAWABASE_INLINE_WORKER">
    Defaults to `"false"` in the production compose configuration. When set to `"true"`, the API process also runs the worker as an inline component, consuming jobs from Redis without a separate container. This is useful for development (fewer containers to manage) and for minimal deployments with low job volume. In production, run the worker as a separate service for isolation and independent scaling.

    <Warning>
    An inline worker has no heartbeat row in `WorkerHeartbeat`. Studio's status page treats workers without a heartbeat row as alive only while the parent process reports `worker.get("alive")` as true. This means Studio cannot independently detect that an inline worker has crashed — it can only tell that the API process is running, which does not guarantee the worker is consuming jobs.
    </Warning>
  </Accordion>
  <Accordion title="PAWABASE_INLINE_SCHEDULER">
    Defaults to `"false"` in the production compose configuration. When set to `"true"`, the API process also runs the scheduler. See [Scaling](/self-hosting/scaling) for the critical rule: run exactly one scheduler, ever. An inline scheduler is safe only when you have exactly one API replica.
  </Accordion>
</AccordionGroup>

## Development configuration

When using `scripts/dev.sh`, the script sets several environment variables that override the production defaults. These are not in `.env.example` because they are the script's responsibility:

```bash
# scripts/dev.sh sets these internally:
export PAWABASE_APP_ENV="${PAWABASE_APP_ENV:-local}"
export PAWABASE_INTERNAL_SECRET="${PAWABASE_INTERNAL_SECRET:-dev-internal-secret-change-me-please}"
export PAWABASE_JWT_MASTER_SECRET="${PAWABASE_JWT_MASTER_SECRET:-dev-jwt-master-secret-change-me-please}"
export PAWABASE_MASTER_KEY="${PAWABASE_MASTER_KEY:-dev-master-key-change-me-please-0000}"
export PAWABASE_DB_GENERATE_SCHEMAS=true
export PAWABASE_PUBLIC_URL="http://127.0.0.1:8080"
export PAWABASE_PUBLIC_GATEWAY_URL="http://127.0.0.1:8080"
export PAWABASE_ADMIN_EMAIL="${PAWABASE_ADMIN_EMAIL:-admin@pawabase.local}"
export PAWABASE_ADMIN_PASSWORD="${PAWABASE_ADMIN_PASSWORD:-Pawabase!admin1}"
export PAWABASE_INLINE_SCHEDULER=true
```

<Warning>
The development defaults use placeholder secrets (`dev-internal-secret-change-me-please`, etc.) that are printed in the script itself. If you run `scripts/dev.sh` on a host accessible to other people, change these immediately — the default secrets are the same on every developer's machine, which means a developer on the same network can forge internal service tokens. For any shared development environment, set `PAWABASE_INTERNAL_SECRET`, `PAWABASE_JWT_MASTER_SECRET`, and `PAWABASE_MASTER_KEY` before running the script.
</Warning>
