The `docker-compose.yml` is the entire deployment surface for a single-host Pawabase installation. It defines seven services, three named volumes, and a shared configuration layer (`x-pawabase`) that ensures every container starts from the same build with the same environment variables, differentiated only by the `command` each service receives. Understanding this file is the difference between "it works on my machine" and "I can explain exactly what is running and why."

## The shared configuration layer

The file opens with two YAML anchor blocks — `x-pawabase` and `x-api-env` — that every service extends. This is not decoration; it is the mechanism that keeps seven processes running from a single `Dockerfile`.

<CardGroup cols={2}>
  <Card title="x-pawabase" icon="layer-group">
    The base configuration every Pawabase service inherits: the build context, the image name (falling back to `pawabase:local`), `restart: unless-stopped`, the `.env` file, and the core environment variables (`PAWABASE_APP_ENV`, `PAWABASE_REDIS_URL`, `PAWABASE_API_URL`, `PAWABASE_AKOUNTZ_URL`, `PAWABASE_ANGULA_URL`, `PAWABASE_GATEWAY_URL`, `PAWABASE_STUDIO_URL`). These URLs are how each service discovers its peers on the internal Docker network — the gateway knows to call `http://api:8001`, and Studio knows to call `http://akountz:8002`.
  </Card>
  <Card title="x-api-env" icon="gear">
    Extends `x-pawabase` with the API-specific environment variables: `PAWABASE_DATABASE_URL` (Postgres connection string), `PAWABASE_DEFAULT_DATA_URL` (the fallback database for environments that have not configured their own), `PAWABASE_STORAGE_ROOT`, `PAWABASE_CODE_PATH`, and the `inline_worker` / `inline_scheduler` flags set to `"false"`. This is the difference between the API running as a standalone service and the API folding worker/scheduler into itself for development convenience.
  </Card>
</CardGroup>

```yaml
# The shared base — every Pawabase service inherits this
x-pawabase: &pawabase
  build: .
  image: ${PAWABASE_IMAGE:-pawabase:local}
  restart: unless-stopped
  env_file: .env
  environment: &env
    PAWABASE_APP_ENV: ${PAWABASE_APP_ENV:-production}
    PAWABASE_REDIS_URL: redis://redis:6379/0
    PAWABASE_API_URL: http://api:8001
    PAWABASE_AKOUNTZ_URL: http://akountz:8002
    PAWABASE_ANGULA_URL: http://angula:8003
    PAWABASE_GATEWAY_URL: http://gateway:8080
    PAWABASE_STUDIO_URL: http://studio:8090
```

The `<<: *env` merge syntax is used extensively: `api`, `worker`, and `scheduler` all inherit `x-api-env` (which itself merges `x-pawabase`'s `env`), while `akountz`, `angula`, `gateway`, and `studio` inherit `x-pawabase`'s `env` directly and override `PORT` and, in Akountz's case, `PAWABASE_DATABASE_URL`.

## Service-by-service breakdown

<AccordionGroup>
  <Accordion title="postgres — the platform database">
    Uses the official `postgres:16-alpine` image. It hosts the platform's entire state: projects, environments, definitions, keys, secrets, audit entries, and Akountz's identity tables (in a separate `akountz` database created by the init script). Two volumes are mounted: the named `postgres` volume for durable data and `./docker/postgres/init.sql` as an initialization script that runs once on first startup, creating the `akountz` database.

    ```yaml
    postgres:
      image: postgres:16-alpine
      environment:
        POSTGRES_USER: pawabase
        POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}
        POSTGRES_DB: pawabase
      volumes:
        - postgres:/var/lib/postgresql/data
        - ./docker/postgres/init.sql:/docker-entrypoint-initdb.d/10-databases.sql:ro
      healthcheck:
        test: ["CMD-SHELL", "pg_isready -U pawabase -d pawabase"]
        interval: 5s
        timeout: 5s
        retries: 20
    ```

    The health check uses `pg_isready` with 20 retries at 5-second intervals, meaning Compose will not start dependent services until Postgres is accepting connections — roughly up to 100 seconds of startup tolerance. The init script (`docker/postgres/init.sql`) is marked `:ro` (read-only) and lands in `/docker-entrypoint-initdb.d/`, where Docker Postgres executes it only on the first initialization of a fresh data directory. On subsequent restarts, it is ignored.
  </Accordion>

  <Accordion title="redis — the queue, event, and cache backbone">
    Uses `redis:7-alpine` with AOF (Append Only File) persistence enabled (`--appendonly yes`). Redis is not optional — it is the backing store for Sillo's event bus, the job queues that the worker consumes, the scheduler's internal job registry, and the pub/sub channel that lets multiple Angula instances share realtime publications. Without Redis, Angula works for a single instance but loses presence and history on restart, and the worker has nowhere to pull jobs from.

    ```yaml
    redis:
      image: redis:7-alpine
      command: ["redis-server", "--appendonly", "yes"]
      volumes: [redis:/data]
      healthcheck:
        test: ["CMD", "redis-cli", "ping"]
        interval: 5s
        timeout: 3s
        retries: 20
    ```

    The named `redis` volume ensures that AOF data survives container restarts. The health check is the simplest possible: `redis-cli ping` must return `PONG`. Three retries with a 3-second timeout means Redis must be ready within 9 seconds, which is always the case unless the host is out of memory.
  </Accordion>

  <Accordion title="api — the configuration authority and data plane">
    The most important service. It extends `x-api-env`, mounts the `api-data` volume at `/data`, and mounts `./examples/code:/code:ro` for the code examples that ship with the platform. It depends on both Postgres and Redis being healthy before starting, and its health check runs a Python one-liner that opens an HTTP connection to the API's own health endpoint on port 8001.

    ```yaml
    api:
      <<: *api-env
      command: ["api"]
      volumes: [api-data:/data, ./examples/code:/code:ro]
      depends_on:
        postgres: { condition: service_healthy }
        redis: { condition: service_healthy }
      healthcheck: &health
        test: ["CMD", "python", "-c", "import os,urllib.request; urllib.request.urlopen('http://127.0.0.1:%s/health' % os.environ.get('PORT', '8001'), timeout=3)"]
        interval: 10s
        timeout: 5s
        retries: 12
        start_period: 20s
    ```

    The `start_period: 20s` in the health check is significant: the API compiles environments and loads job classes on startup, which can take 15-30 seconds depending on the number of definitions. Compose will not count health check failures during the first 20 seconds, giving the API time to finish initialization. The `api-data` volume stores compiled app caches, object storage objects, and the SQLite fallback databases used when no Postgres is configured for an environment.
  </Accordion>

  <Accordion title="worker — asynchronous job execution">
    Extends `pawabase` with the `worker` command. It has no exposed port — it never accepts an HTTP connection. It consumes jobs from Redis-backed queues (`events`, `webhooks`, `flows`, `functions`, `mail`, `default`) and executes them. It depends on the API being healthy because it reuses the API's `Platform` object and job class registry.

    ```yaml
    worker:
      <<: *pawabase
      command: ["worker"]
      environment: *api-env
      volumes: [api-data:/data, ./examples/code:/code:ro]
      depends_on:
        api: { condition: service_healthy }
    ```

    Multiple worker replicas can run simultaneously — each is an independent consumer of the same queues, and Sillo's queue semantics handle concurrent consumption safely. Scale it horizontally without configuration changes.
  </Accordion>

  <Accordion title="scheduler — time-based job triggering">
    Extends `pawabase` with the `scheduler` command. Like the worker, it has no exposed port and depends on the API. It reconciles schedule definitions from Postgres every 15 seconds and emits jobs or events when the time comes.

    <Warning>
    Run exactly one scheduler. Sillo's scheduler keeps its registered jobs in memory — it is not a distributed lock or a leader-elected singleton. Two scheduler processes will each independently decide "it is time" and each independently queue or emit the same job. For a `trigger.schedule` flow that sends a daily digest email, that means two identical emails. For a schedule that charges a subscription, that means two identical charges. This is the one process in the topology that must never be scaled horizontally.
    </Warning>
  </Accordion>

  <Accordion title="akountz — identity and authentication">
    Extends `pawabase` with the `akountz` command and its own database (`akountz` instead of `pawabase`). It owns accounts, sessions, tokens, MFA, organizations, teams, and the per-environment token signing keys. It depends on Postgres, Redis, and the API being healthy.

    ```yaml
    akountz:
      <<: *pawabase
      command: ["akountz"]
      environment:
        <<: *env
        PORT: "8002"
        PAWABASE_DATABASE_URL: postgres://pawabase:${POSTGRES_PASSWORD}@postgres:5432/akountz
      depends_on:
        postgres: { condition: service_healthy }
        redis: { condition: service_healthy }
        api: { condition: service_healthy }
    ```

    Akountz has its own database because its identity tables (users, sessions, MFA secrets, organizations) are logically separate from the API's project and definition tables. They share the same physical Postgres instance in a typical install but live in different databases — never mixed in the same schema. On first startup, if `admin_email` and `admin_password` are set and no operator exists for the `_platform` project, Akountz creates the first platform operator automatically.
  </Accordion>

  <Accordion title="angula — realtime">
    Extends `pawabase` with the `angula` command on port 8003. It depends only on Redis being healthy — it does not need Postgres at all because its channel state, presence, and replay history live in Redis via `sillo-wire`. This is intentional: Angula is stateless with respect to the platform database, so it can start and serve realtime connections even if the API or Akountz are temporarily down.

    ```yaml
    angula:
      <<: *pawabase
      command: ["angula"]
      environment:
        <<: *env
        PORT: "8003"
      depends_on:
        redis: { condition: service_healthy }
    ```

    Multiple Angula instances share publications over Redis pub/sub. Without Redis, realtime works within a single instance but disconnected clients lose presence and replay history on reconnect.
  </Accordion>

  <Accordion title="gateway — the only public door">
    The gateway exposes port 8080 on the host and depends on the API, Akountz, and Angula being healthy. It is the single public entry point: every request a browser, mobile app, or server integration makes flows through it. It resolves API keys, enforces rate limits and CORS, strips impersonation headers, and signs the internal `X-Pawabase-Context` header before forwarding to the appropriate upstream service.

    ```yaml
    gateway:
      <<: *pawabase
      command: ["gateway"]
      environment:
        <<: *env
        PORT: "8080"
      ports: ["${PAWABASE_GATEWAY_PORT:-8080}:8080"]
      depends_on:
        api: { condition: service_healthy }
        akountz: { condition: service_healthy }
        angula: { condition: service_healthy }
    ```

    The host port is configurable via `PAWABASE_GATEWAY_PORT` in `.env`. By default it is 8080. The gateway has no exposed port for anything else — the internal services are only reachable on the Docker network.
  </Accordion>

  <Accordion title="studio — the control plane">
    The Studio control plane exposes port 8090 and depends on the API and Akountz being healthy. It is a Sillo + Inertia + React application that provides the operator interface for designing projects, managing users, and configuring everything else. It never touches a database directly — every action goes through Studio's bridge to the management API.

    ```yaml
    studio:
      <<: *pawabase
      command: ["studio"]
      environment:
        <<: *env
        PORT: "8090"
      ports: ["${PAWABASE_STUDIO_PORT:-8090}:8090"]
      depends_on:
        api: { condition: service_healthy }
        akountz: { condition: service_healthy }
    ```

    Like the gateway, the host port is configurable via `PAWABASE_STUDIO_PORT`. Studio is reachable from the operator's browser only; it never handles requests from project users or clients — that is the gateway's job.
  </Accordion>
</AccordionGroup>

## Volumes

Three named volumes are declared at the bottom of the file:

```yaml
volumes:
  postgres:
  redis:
  api-data:
```

- **`postgres`** — durable storage for the platform database. Includes both the `pawabase` database (projects, definitions, keys, secrets, audit log) and the `akountz` database (identity tables).
- **`redis`** — persistent storage for Redis AOF data. Queues, event history, and realtime state survive container restarts.
- **`api-data`** — mounted at `/data` inside the API, worker, and scheduler containers. Stores compiled app caches, object storage objects, and SQLite fallback databases for environments that do not have a dedicated Postgres configured.

<Tip>
You can mount a host directory instead of a named volume for `api-data` if you want to inspect or back up the data directly from the host: `api-data: /path/on/host:/data`. Named volumes are simpler and get cleaned up by `docker compose down -v`; host directories give you filesystem-level access for backups and restores.
</Tip>

## The .env file and variable substitution

Every `${VAR}` or `${VAR:-default}` reference in `docker-compose.yml` is resolved from the `.env` file in the same directory. Compose loads `.env` automatically — you do not need to pass `--env-file`. The `.env.example` file provides the template; copy it to `.env` and fill in the secrets.

The `${POSTGRES_PASSWORD:?...}` syntax is a Compose feature that aborts with an error message if the variable is unset. This is why the platform will not start with a missing Postgres password — it fails loudly instead of starting with a blank password. Other variables use `:-` defaults: `PAWABASE_APP_ENV` defaults to `production`, `PAWABASE_GATEWAY_PORT` defaults to `8080`, `PAWABASE_STUDIO_PORT` defaults to `8090`.

<Warning>
The `.env` file is loaded by Compose for *variable substitution* in `docker-compose.yml`, but it is **not** automatically available inside containers unless explicitly referenced. Each service that needs environment variables either inherits them via `env_file: .env` (which the `x-pawabase` anchor handles) or defines them explicitly. The `api`, `worker`, and `scheduler` services use `environment: *api-env`, which merges the base env — but the `POSTGRES_PASSWORD` variable is consumed at Compose's variable-substitution layer (in the `PAWABASE_DATABASE_URL` string) and is never passed as `POSTGRES_PASSWORD` inside the container. Inside the container, the connection string already has the password interpolated.
</Warning>

## Starting the stack

```bash
# Copy the template and set your secrets
cp .env.example .env
# Edit .env — fill in every secret and the admin credentials

# Start everything in detached mode
docker compose up -d

# Watch the startup logs
docker compose logs -f

# Stop everything
docker compose down

# Stop and remove all data volumes (starts completely fresh)
docker compose down -v
```

The `docker compose up -d` command builds the image (if not already built) and starts all seven services in dependency order. Because of the `depends_on` conditions with `service_healthy`, Compose will not start the gateway until the API, Akountz, and Angula are healthy; it will not start the API until Postgres and Redis are healthy. The entire stack typically comes up in 30-60 seconds on a warm host, longer on a cold host where Postgres needs to initialize its data directory.

After startup, verify every service is running:

```bash
docker compose ps
```

Every service should show `Up` with a healthy status. If any service shows `Restarting` or `unhealthy`, check its logs: `docker compose logs <service-name>`.

## Customizing the compose file

You can override any aspect of the compose configuration without editing the original file. Create a `docker-compose.override.yml` in the same directory, and Compose merges it automatically:

```yaml
# docker-compose.override.yml
services:
  gateway:
    ports:
      - "443:8080"  # expose on 443 instead of 8080
  postgres:
    environment:
      POSTGRES_SHARED_BUFFERS: "512MB"
```

You can also pass a different compose file with `-f`:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

This pattern is how the [production checklist](/self-hosting/production-checklist) recommends layering production-specific configuration on top of the development default.

## Resource limits per service

The base `docker-compose.yml` does not set CPU or memory limits on any service — every container can use as much of the host's resources as the kernel allows. This is appropriate for a single-service-per-host default, but once several services share a host (which is the default single-host topology), an unbounded worker consuming a burst of CPU-heavy jobs can starve the gateway of CPU it needs to keep serving requests. Add limits via an override file once you have observed real resource usage with `docker stats`:

```yaml
# docker-compose.override.yml
services:
  api:
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 2g
        reservations:
          cpus: "0.5"
          memory: 512m
  worker:
    deploy:
      resources:
        limits:
          cpus: "1.5"
          memory: 1g
  gateway:
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512m
```

<Note>
Under plain `docker compose up` (not `docker stack deploy`), the `deploy.resources` block is honored for CPU and memory limits as of Compose v2 — you do not need Swarm mode for this to take effect. Verify with `docker inspect <container> --format='{{.HostConfig.Memory}}'` after starting the stack; a nonzero value confirms the limit applied.
</Note>

Start without limits, observe steady-state and peak resource usage for a week under real traffic, then set limits with headroom above the observed peak — tight limits that trigger OOM kills under normal load are worse than no limits at all.

## Environment variable precedence

Compose resolves environment variables for a container from several layers, and the order matters when values conflict:

1. Variables set directly in the `environment:` block of the service (including anything merged in via a YAML anchor like `<<: *env`) — highest precedence.
2. Variables loaded from the file referenced by `env_file:` (`.env` in Pawabase's case) — lower precedence than `environment:`.
3. Variables used only for **substitution** inside `docker-compose.yml` itself (the `${VAR}` syntax) are resolved from the shell environment or the `.env` file in the project directory, which Compose loads automatically for this purpose specifically — this is a separate mechanism from `env_file:` and happens before the compose file is even parsed into service definitions.

This is why `POSTGRES_PASSWORD` behaves the way the Warning above describes: it is consumed at substitution time (layer 3) to build `PAWABASE_DATABASE_URL`, but it is never itself injected into a container's process environment via `environment:` or `env_file:` — nothing in `docker-compose.yml` lists `POSTGRES_PASSWORD` in an `environment:` block for the `api` or `akountz` services (only the `postgres` service receives it directly, to configure the database engine itself).

## Single-server deployment (complete walkthrough)

This is the default topology every other section on this page describes: one host runs every service via `docker compose up -d`. Here is the complete sequence from a bare Docker install to a running platform:

```bash
# 1. Verify Docker and Compose
docker --version
docker compose version

# 2. Clone or copy the Pawabase project directory
cd /opt/pawabase

# 3. Create and populate .env
cp .env.example .env
openssl rand -hex 32   # run four times, once per secret, paste into .env
nano .env

# 4. Build the image
docker compose build

# 5. Start the stack
docker compose up -d

# 6. Watch startup order: postgres and redis become healthy first,
#    then api, then akountz/angula, then gateway/studio
docker compose logs -f

# 7. Confirm everything is healthy
docker compose ps
```

This is appropriate for development, staging, demos, and production deployments that fit comfortably within a single host's resources (see [Requirements](/self-hosting/requirements) for sizing guidance). Its main limitation is a single point of failure: if the host goes down, every Pawabase service goes down with it, including Postgres and Redis.

## Single-server with an external managed Postgres

A common middle ground before moving to a full multi-server topology: keep every application service on one host, but point at a managed Postgres instance instead of the bundled container. This removes Postgres's resource footprint and operational burden from the host while keeping everything else simple.

```yaml
# docker-compose.override.yml
services:
  postgres:
    # Disable the bundled Postgres entirely by scaling it to zero replicas,
    # or remove the service block altogether if you never need it locally.
    deploy:
      replicas: 0

  api:
    environment:
      PAWABASE_DATABASE_URL: postgres://pawabase:${MANAGED_PG_PASSWORD}@managed-db.example.com:5432/pawabase?sslmode=require
    depends_on: {}   # remove the postgres dependency since it no longer runs here

  akountz:
    environment:
      PAWABASE_DATABASE_URL: postgres://pawabase:${MANAGED_PG_PASSWORD}@managed-db.example.com:5432/akountz?sslmode=require
    depends_on:
      redis: { condition: service_healthy }
```

<Warning>
Overriding `environment:` on a service that uses a YAML anchor merge (`<<: *api-env` or `<<: *env`) in the base file does not merge at the key level in Compose's override semantics for the `environment` mapping form used here — Compose merges override `environment` entries on top of the base service's resolved environment map, so individual keys like `PAWABASE_DATABASE_URL` are replaced while the rest of the inherited environment (`PAWABASE_REDIS_URL`, `PAWABASE_API_URL`, and so on) is preserved. Verify the final resolved configuration with `docker compose config` before starting the stack, since silently losing an inherited variable is a common override mistake.
</Warning>

You still need to create the `akountz` database yourself on the managed instance (the `docker/postgres/init.sql` script only runs against the bundled container's first-boot initialization), and you need network connectivity from the host to the managed database (a VPC peering connection, a VPN, or an allow-listed IP with `sslmode=require`, never a database open to the public internet without TLS).

## Multi-server deployment behind a load balancer

For a topology where multiple hosts each run a full application tier behind a load balancer (see [Requirements](/self-hosting/requirements) and [Scaling](/self-hosting/scaling) for when this becomes necessary), the compose file itself does not change much — what changes is that the Docker Compose internal DNS names (`api`, `akountz`, `angula`, `gateway`, `studio`) only resolve *within a single Compose project's network on a single host*. Across hosts, you must replace these with real, reachable addresses.

```yaml
# docker-compose.override.yml on each application host
services:
  api:
    environment:
      PAWABASE_REDIS_URL: redis://redis.internal.example.com:6379/0
      PAWABASE_DATABASE_URL: postgres://pawabase:${POSTGRES_PASSWORD}@postgres.internal.example.com:5432/pawabase
  akountz:
    environment:
      PAWABASE_REDIS_URL: redis://redis.internal.example.com:6379/0
      PAWABASE_DATABASE_URL: postgres://pawabase:${POSTGRES_PASSWORD}@postgres.internal.example.com:5432/akountz
  gateway:
    environment:
      PAWABASE_API_URL: http://api.internal.example.com:8001
      PAWABASE_AKOUNTZ_URL: http://akountz.internal.example.com:8002
      PAWABASE_ANGULA_URL: http://angula.internal.example.com:8003
```

Each application host still runs its own local `postgres` service definition disabled (replicas: 0, as above) or removed, since the data tier now lives on dedicated hosts reachable over the internal network. The load balancer in front sits above all application hosts and only needs to reach each host's gateway port (`PAWABASE_GATEWAY_PORT`, default 8080) and, if Studio should be reachable through the same balancer, the Studio port (`PAWABASE_STUDIO_PORT`, default 8090).

<Note>
This pattern requires a private network that spans your hosts — a cloud VPC, a WireGuard mesh, or a data-center private network. Never expose `PAWABASE_REDIS_URL` or `PAWABASE_DATABASE_URL` targets over the public internet without a VPN or TLS, since Redis has no authentication configured by default in the bundled setup and Postgres's password alone is not a substitute for network isolation.
</Note>

## Command reference

A working set of `docker compose` commands for day-to-day operation of the stack:

```bash
# Start everything in the background
docker compose up -d

# Start only specific services (and their dependencies)
docker compose up -d gateway studio

# Stop everything without removing containers
docker compose stop

# Stop and remove containers (keeps volumes)
docker compose down

# Stop and remove containers and volumes (destroys data — see Backups first)
docker compose down -v

# Tail logs for every service
docker compose logs -f

# Tail logs for one service
docker compose logs -f worker

# Show the last 100 lines without following
docker compose logs --tail=100 api

# Open a shell inside a running container
docker compose exec api sh

# Run a one-off command in a new container (does not affect the running one)
docker compose run --rm api migrate

# Live resource usage per container
docker stats

# Container status and health
docker compose ps

# Scale a stateless service to multiple replicas
docker compose up -d --scale worker=3

# Rebuild the image after a source change, then recreate affected containers
docker compose build && docker compose up -d

# Print the fully resolved configuration (all anchors, overrides, and
# variable substitutions expanded) — invaluable for debugging override files
docker compose config
```

## Troubleshooting the compose stack

<AccordionGroup>
  <Accordion title="A service is stuck in a restart loop">
    Check its logs first: `docker compose logs <service>`. The most common causes are a missing or malformed environment variable (check `docker compose config` to see the fully resolved environment), a database connection failure (Postgres not yet healthy, or a typo in the connection string), or a migration failure on startup (`PAWABASE_MIGRATE=true` by default, and `entrypoint.sh` runs `python -m database.migrate` for `api` and `akountz` before serving — a failing migration prevents the service from ever reaching its health check).
  </Accordion>
  <Accordion title="A dependent service never starts because its dependency shows unhealthy">
    `depends_on` with `condition: service_healthy` blocks startup until the health check passes. If `postgres` never reports healthy, check `docker compose logs postgres` for a crash-looping database (often caused by a permissions problem on the mounted volume, or a corrupted data directory from an interrupted previous run). If `api` never reports healthy, check whether it is still running its migration (large migrations can exceed the `start_period: 20s` grace window and cause early health check failures that Compose ignores until `start_period` elapses, but if the migration itself is genuinely stuck, the container will keep failing checks indefinitely).
  </Accordion>
  <Accordion title="Permission denied errors writing to /data or /code">
    The image runs as a non-root user (`useradd --create-home --uid 10001 pawabase` in the Dockerfile, and the container drops to `USER pawabase` before running). If you bind-mount a host directory in place of a named volume (for `api-data`, for example) and that host directory is owned by `root` or another UID, the `pawabase` user (UID 10001) will not have write access. Fix ownership on the host: `sudo chown -R 10001:10001 /path/on/host`.
  </Accordion>
  <Accordion title="Changes to .env do not take effect">
    `docker compose up -d` alone does not always recreate a container whose only change is an environment variable value it already had a value for — Compose detects configuration drift and recreates containers automatically in most cases, but if you suspect a stale value, force it: `docker compose up -d --force-recreate`. Also double check you edited `.env` in the same directory as `docker-compose.yml` — Compose only auto-loads the `.env` colocated with the compose file being run.
  </Accordion>
  <Accordion title="Port already in use">
    If `PAWABASE_GATEWAY_PORT` (default 8080) or `PAWABASE_STUDIO_PORT` (default 8090) collides with another process on the host, either stop the conflicting process or change the port in `.env` before starting. `docker compose up -d` will fail with a clear "port is already allocated" error rather than silently picking another port.
  </Accordion>
  <Accordion title="docker compose config reports an unknown anchor or merge error">
    This almost always means the Compose version is too old to understand the YAML anchor and merge-key syntax (`&pawabase`, `<<: *env`) used throughout `docker-compose.yml`. Upgrade to Compose v2 as described in [Requirements](/self-hosting/requirements).
  </Accordion>
</AccordionGroup>

## Build process details

The Dockerfile that `build: .` in `x-pawabase` refers to is a two-stage build:

1. **`studio-assets` stage** (`node:22-slim`): installs the Studio frontend's npm dependencies with `npm ci`, then runs `npm run build`, producing a compiled Vite bundle.
2. **`runtime` stage** (`python:3.11-slim`): installs `uv` as the Python package manager, copies each service's `pyproject.toml` first (so dependency layers cache independently of source changes), runs `uv sync --frozen --no-dev --all-packages`, then copies `pawabase_kit/`, each service directory (`api/`, `akountz/`, `angula/`, `gateway/`, `studio/`), and `examples/` source, copies `docker/entrypoint.sh` to `/usr/local/bin/pawabase`, creates the non-root `pawabase` user, and finally copies the compiled Studio frontend bundle from the first stage into `studio/frontend/dist`.

Because dependency installation happens before source code is copied, changing application code and re-running `docker compose build` reuses the cached dependency-installation layers and only rebuilds from the `COPY packages packages` step onward — this makes iterative rebuilds meaningfully faster than a from-scratch build. A full `docker compose build --no-cache` (as recommended for the very first production build, and for upgrades in [Upgrades](/self-hosting/upgrades)) discards all layer caching and rebuilds everything, which is slower but eliminates any risk of a stale cached layer.

The final image's `ENTRYPOINT` is `["pawabase"]` (the `entrypoint.sh` script), and its default `CMD` is `["help"]`, which prints the usage line if you run the image without a `command:` override — this is exactly what each service's `command: ["api"]`, `command: ["worker"]`, and so on supplies in `docker-compose.yml`.
