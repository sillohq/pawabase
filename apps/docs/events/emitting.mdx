Events in Pawabase are emitted automatically from several sources. You don't call a special function to emit most of them — they fire as a natural consequence of platform operations.

This page explains **what** emits events, **when** they fire, and **how to emit your own** from a flow.

## Sources of events

| Source | Events emitted | When it fires |
| --- | --- | --- |
| Resource writes | `<resource>.created`, `<resource>.updated`, `<resource>.deleted` | After the write is committed to the database |
| `event.emit` block (in a flow) | Any event name you specify | When the block runs and the flow reaches that step |
| Schedule triggers | `scheduler.fired.<schedule>` | According to the cron schedule you configured |
| Authentication actions | `user.signed_up`, `user.signed_in`, `user.email_verified` | In the Akountz service, after the action succeeds |
| Mail delivery | `mail.sent`, `mail.failed` | After an email is dispatched to the SMTP provider |
| Webhook delivery | `webhook.delivered`, `webhook.failed` | After an outbound webhook attempt completes |
| Inbound webhooks | `<slug>:<action>` | When an external service POSTs to your webhook endpoint |

## Resource events

Every resource automatically emits three events:

```text
<resource>.created   →  after a record is inserted
<resource>.updated   →  after a record is modified
<resource>.deleted   →  after a record is deleted
```

The `<resource>` is the resource name you defined in Studio. For a resource named `orders`:

- `orders.created` — fires after every `POST /rest/v1/orders` that succeeds
- `orders.updated` — fires after every `PATCH /rest/v1/orders/{id}` that succeeds
- `orders.deleted` — fires after every `DELETE /rest/v1/orders/{id}` that succeeds

The event payload is the **full record** — all fields, including `id`, `created_at`, and `updated_at`.

<Note>
Resource events fire **inside the same database transaction** as the write. If the write is rolled back (e.g., due to a constraint violation), the event is not emitted. If the write commits, the event is guaranteed to fire.
</Note>

### Transaction safety

When a flow uses a `db_transaction` block that performs multiple resource writes, each successful write within the transaction emits its own event. All events fire only if the entire transaction commits — if the transaction rolls back, none of the events fire.

This means you can rely on events for consistency: if you see an `orders.created` event in your flow, the order record is guaranteed to exist in the database.

### Event ordering within a resource

Events for a single resource are ordered: if you create then update record A, `orders.created` fires before `orders.updated`. However, events for **different** resources or records may arrive in any order.

## Emitting events from flows

You can publish custom events from any flow using the **`event.emit`** block:

1. Add a **Platform → Emit event** block to your flow.
2. Configure the fields:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| **Event** | string | yes | The event name (e.g., `order.paid`) |
| **Payload** | JSON object | no | The data to carry with the event |

<Info>
The event name must follow the `domain.action` convention (`order.paid`, not `Order Paid`). See [Event names](/events/catalog) for conventions.
</Info>

### Using template expressions

The payload field accepts `{{ }}` expressions that resolve against earlier flow steps:

```json
{
  "order_id": "{{ steps.create_order.output.id }}",
  "total": "{{ input.total }}",
  "items": "{{ steps.lookup.items }}"
}
```

If a referenced step hasn't run or produced no output, the expression evaluates to `null`. See [Expressions](/concepts/expressions) for the full template syntax.

### What happens when you emit

```text
event.emit block runs
      ↓
Event published to the durable queue
      ↓
Flow continues (does not wait for consumers)
      ↓
Subscribers react asynchronously:
  • Matching flows are queued as jobs
  • Webhook endpoints receive HTTP POSTs
  • Realtime channels broadcast to connected clients
```

The emit is **fire-and-forget** — your flow doesn't wait for consumers to finish. The event is queued and processed in the background.

## How the event queue works

Events are published to a **durable, Redis-backed queue**. This means:

- **Events survive crashes** — if Pawabase restarts, queued events are still there.
- **Slow consumers don't block** — a flow that takes 10 seconds to process doesn't slow down the emitter.
- **Backlog grows during traffic spikes** — events accumulate and are processed as workers become available.

The queue retains events per `(project, environment)` pair. Events from one environment never reach subscribers in another.

## The event envelope

Every event, when received by a subscriber, has this shape:

```json
{
  "event": "orders.created",
  "payload": { "id": "ord_42", "total": 2999, "status": "pending" },
  "id": "evt_abc123def456",
  "published_at": "2026-09-28T10:00:00.123456+00:00",
  "actor": "usr_001",
  "project": "acme",
  "env": "production",
  "source": "api"
}
```

| Field | What it is |
| --- | --- |
| `event` | The event name |
| `payload` | The event data |
| `id` | Unique event identifier (for deduplication) |
| `published_at` | When the event was emitted |
| `actor` | Who or what caused the event (`"system"`, a user ID, or `"scheduler"`) |
| `project` / `env` | Which project/environment this event belongs to |
| `source` | Which service emitted it (`"api"`, `"scheduler"`, etc.) |

## Event backpressure

When events are produced faster than they can be consumed, they accumulate in the Redis backlog. This is **natural backpressure** — the emitter never slows down, but consumers fall behind.

If the event volume is sustained and Redis reaches its memory limit, older events may be trimmed from the backlog. However, every processed event is permanently recorded in the **Event log** (visible in Studio under Observability → Events), so you can always audit what happened.

For sustained high-volume event processing:
- Scale up your worker pool (increase `PAWABASE_WORKER_CONCURRENCY`)
- Monitor the Event log for consumer failures
- Consider batching events within a flow if individual processing is fast

## Debugging events

### Seeing what events fired

In Studio, go to **Observability → Events** to browse all events by:

- Event name (e.g., `orders.created`)
- Project and environment
- Time range
- Actor (user or system)

Click any event to see its full payload and which consumers processed it.

### Checking consumer outcomes

Each event log entry shows which subscribers processed the event and whether each succeeded or failed. A failed consumer shows the error message and the number of retry attempts.

### Testing event emission

You can emit a test event from a flow:

1. Create a flow with a `event.emit` block.
2. Run the flow manually from Studio (using the **Run** button).
3. Check the Events dashboard to see the emitted event.

### Verifying delivery to subscribers

If a flow triggered by an event doesn't run:
1. Check that the event name matches exactly (case-sensitive).
2. Check that the subscriber flow is **enabled** (draft flows don't receive events).
3. Check the Events dashboard for consumer failures.

## Common patterns

### Emit and forget

The simplest pattern: emit an event and continue. The event triggers downstream processing that runs independently:

```text
Resource write
   ↓
orders.created emitted
   ↓
Flow returns response to client
   ↓
(Background) Matching flow runs: validate order, emit order.validated
```

### Chaining events through flows

A flow triggered by an event can emit another event, creating a chain:

```text
orders.created
   ↓
flow: validate-order
   ↓
order.validated (emitted)
   ↓
flow: fulfill-order
   ↓
order.fulfilled (emitted)
```

Each flow is decoupled from the others — if the fulfillment flow is down, `order.validated` events queue up until it recovers.

### Emitting from resource hooks

You don't need to manually emit resource events — they fire automatically. But you can combine them with custom events in the same flow:

```text
trigger: orders.created (automatic)
   ↓
resource.create: inventory.reservation
   ↓
event.emit: inventory.reserved (custom)
   → triggers: flow: send-receipt
```
