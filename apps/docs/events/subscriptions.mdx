A **subscription** is the link between an event and a consumer. Every event in Pawabase can have any number of subscriptions. When the event fires, each subscription runs independently as a background job — none of them block each other, and none of them block the emitter.

This page covers how to configure each subscription type, how event names are matched, delivery guarantees, and how to debug failures.

## Subscribing from a flow

The primary way to react to events is a flow's **`trigger.event`** node. Configure it in the flow editor:

1. Add a **Trigger → Event** node.
2. Enter the event name or pattern — e.g. `orders.created` or `order.*`.
3. Optionally add a **condition** to restrict which matching events actually start the run.

See [Triggers → `trigger.event`](/flows/triggers#trigger-event---platform-events) for the full field reference and input shape.

### What the flow receives

A flow triggered by an event receives the full event envelope as `input.event`:

```text
$input.event.name           → "orders.created"
$input.event.payload        → { "id": "ord_42", "total_cents": 4900, ... }
$input.event.payload.id     → "ord_42"
$input.event.id             → "evt_abc123"   (use this for idempotency)
$input.event.occurred_at    → "2026-09-28T10:00:00.123Z"
$input.event.actor          → "usr_001" or null
```

The timestamp field is `occurred_at`, not `published_at` or `timestamp`.

### Trigger condition

A condition on a `trigger.event` node restricts which matching events actually start a run. The condition is evaluated against the event envelope before the flow is queued — if the condition is false, the flow is never started for that event:

```json
{ "gt": ["$input.event.payload.total_cents", 10000] }
```

Use the same condition language as policies and `control.if`: `$path` operands, operators like `eq`/`ne`/`gt`, and combinators `all`/`any`/`not`. See [Conditions](/policies/conditions) for the full reference.

## Subscribing from a function

Python functions can be registered as event subscribers in Studio under **Code → Functions → Edit → Triggers**. When the event fires, the function runs as a background job on the `functions` queue.

The function receives the event envelope. See [Functions](/code/functions) for how to write and deploy functions.

## Subscribing from an outbound webhook

An outbound webhook subscription delivers the event envelope to an external HTTP endpoint. Configure outbound webhooks in **Studio → Automate → Webhooks → Outbound**. See [Outbound webhooks](/webhooks/outbound) for configuration and signature verification.

## Subscribing from a realtime channel

A realtime channel subscription publishes the event as a message to a channel when the event fires, pushing it immediately to all connected clients. Configure channel rules in **Studio → Realtime → Channel rules**. See [Realtime](/realtime/overview) for how channel rules work.

## Event name matching

Pawabase uses `fnmatch.fnmatchcase` for event pattern matching. The `*` wildcard matches any sequence of characters, **including dots**:

| Pattern | Matches | Does not match |
| --- | --- | --- |
| `orders.created` | `orders.created` | Everything else — exact match |
| `orders.*` | `orders.created`, `orders.updated`, `orders.line_item.added` | `users.created` — `*` crosses dots |
| `*.created` | `orders.created`, `users.created`, `invoice.line.created` | `orders.updated` |
| `order.*` | `order.created`, `order.paid`, `order.line.added` | — `*` crosses all dots |
| `*` | Every event | — |

Matching is case-sensitive. `Orders.Created` does not match `orders.created`.

If you need to match only a single-level wildcard (e.g., `orders.something` but not `orders.something.else`), there is no single-segment wildcard syntax. Use an exact name, or check `input.event.name` inside the flow with a `control.if` block to filter on the specific pattern you need.

## Delivery guarantees

| Property | Behavior |
| --- | --- |
| **At-least-once** | Every event reaches every matching subscriber at least once. A consumer failure causes the event to be redelivered. Design consumers to be idempotent using the event `id`. |
| **Per-name ordering** | Events with the same name are delivered in the order they were published. Different event names may arrive out of order relative to each other. |
| **Environment isolation** | Events from `acme/production` never reach subscribers in `acme/development`. |
| **Asynchronous** | Subscribers run as background jobs. The emitter never waits. A slow subscriber doesn't delay the emitter or other subscribers. |

## Retry behavior

When a subscriber job fails, it is retried. The number of attempts and the backoff behavior are configured per subscriber:

| Subscriber type | Default attempts | Backoff strategy | Queue |
| --- | --- | --- | --- |
| Flow (`trigger.event`) | 1 (no automatic retries by default) | — | `flows` |
| Function | Configured per function | Exponential with jitter | `functions` |
| Outbound webhook | Configured per webhook | Exponential with jitter | `webhooks` |
| Realtime channel | 0 — fire and forget | — | (in-process) |

<Warning>
Flow jobs dispatched from events have `tries=1` by default — no automatic retry. If you need a flow to retry on failure, add a `control.retry` block inside the flow around the steps that can fail, or configure retries on the job that dispatches the flow.
</Warning>

After all retries are exhausted, the failed job moves to the dead-letter queue (DLQ). Inspect failed jobs in **Studio → Operate → Failed jobs**, where you can re-run them with the original input.

## Idempotency

Because delivery is at-least-once, a consumer may receive the same event more than once. Always design subscribers to handle duplicates:

```json
{
  "id": "dedup_check",
  "data": {
    "block": "cache.get",
    "config": { "key": "evt:{{ input.event.id }}" }
  }
}
```

Check for the event id in a cache or a dedicated idempotency table before acting. Mark it as processed only after the work is safely committed.

## Inspecting subscriptions in Studio

**Observability → Events** in Studio:

- Shows all events by name, time, project, and environment.
- Clicking an event shows its full payload and every consumer: which ran, which succeeded, which failed, and how many retries each took.
- Links to the flow run, function job, or webhook delivery for each consumer.

**Operate → Failed jobs** shows jobs that exhausted all retries, with the full error trace and the ability to re-run.

## Troubleshooting

<AccordionGroup>
  <Accordion title="A flow never starts even though the event fires">
    Check: (1) the event name matches exactly — case-sensitive; (2) the flow is enabled, not in draft; (3) the trigger condition, if set, is not filtering out the event — open the event in the Events dashboard and compare its payload against the condition.
  </Accordion>
  <Accordion title="A consumer processes the same event twice">
    Expected with at-least-once delivery. Check whether the consumer is idempotent and is correctly using the event id to detect duplicates. If the event appears twice in the Events dashboard with different `id` values, those are genuinely two separate events; if the same `id` appears, that's a redelivery.
  </Accordion>
  <Accordion title="A wildcard like order.* isn't matching order.line_item.added">
    It should — `*` in Pawabase's event patterns crosses dot boundaries, so `order.*` matches `order.line_item.added`. If it isn't matching, check the exact event name in the Events dashboard against the pattern you configured.
  </Accordion>
  <Accordion title="A flow subscription is missing from the consumer list">
    The flow may have been in draft at the time the event fired. Only enabled flows receive events. Publishing the flow and waiting for the next occurrence is the resolution; there is no way to replay an event to a flow that wasn't enabled when it fired, beyond manually re-running the flow or re-triggering the source action.
  </Accordion>
</AccordionGroup>
