A **subscription** is a rule that says: "When event X fires, do Y." Every event in Pawabase can have multiple subscribers — a flow, a function, a webhook endpoint, or a realtime channel. Subscribers never block the event; they receive work asynchronously as queued jobs.

This page covers how to configure each subscriber type, how events are matched, what delivery guarantees you get, and how to debug subscription failures.

## Subscribing from a flow

The most common way to react to events is the **Event trigger** in a flow:

1. Open a flow in Studio.
2. Add or edit the trigger block.
3. Choose **Event** as the trigger type.
4. Enter the event name or pattern (e.g., `orders.created` or `orders.*`).
5. Optionally add a **condition** to filter which events trigger the flow.

<Steps>
  <Step title="Choose an event">
    Enter the event name or pattern. The `*` wildcard matches one dot-separated segment: `orders.*` matches `orders.created` but not `orders.us.shipped`. See the [Event catalog](/events/catalog) for all available event names.
  </Step>
  <Step title="Add a condition (optional)">
    Conditions use the same expression language as [Policies](/policies/overview) and [Flow conditions](/flows/overview#conditions). The condition has access to the full event envelope via `input.event`.
  </Step>
</Steps>

### What the flow receives

When the event fires, the flow starts with `input.event` containing the full event envelope:

```text
$input.event.name           → "orders.created"
$input.event.payload        → { "id": "ord_42", "total": 2999, ... }
$input.event.payload.total  → 2999
$input.event.id             → "evt_abc123" (for deduplication)
$input.event.published_at   → "2026-09-28T10:00:00+00:00"
$input.event.actor          → "usr_001" or "system"
```

From any subsequent step, you can reference these with expressions like `{{ input.event.payload.total }}` or `{{ input.event.id }}`.

### Filtering with conditions

A condition on the trigger restricts when the flow runs. Only events where the condition is truthy will trigger the flow.

Example: only process orders over $100 (10,000 cents):

```json
{ "gt": ["{{ input.event.payload.total_minor }}", 10000] }
```

Example: only for a specific user:

```json
{ "eq": ["{{ input.event.actor }}", "usr_001"] }
```

See [Expressions → Conditions](/concepts/expressions#conditions) for the full operator reference.

<Info>
Conditions on event triggers are evaluated **synchronously** when the event is published. If the condition fails, the flow is never queued — it's cheaper than starting the flow and failing inside a step.
</Info>

## Subscribing from a function

Functions can subscribe to events by registering as event handlers. In your function code:

```python
from pawabase_kit import function

@function("handle_order_created")
async def handle_order_created(event, ctx):
    order = event.payload
    await ctx.runtime.resource.create("order_notifications", {
        "order_id": order["id"],
        "status": "queued"
    })
    return {"processed": True}
```

The function receives the full event envelope as the `event` parameter. Configure which events trigger the function in Studio:

1. Go to **Code → Functions**.
2. Edit your function.
3. Under **Triggers**, add an event subscription: `orders.created`.
4. Optionally add a **condition** (same expression language as flows).

Functions run as **queued jobs** on the worker queue. If a function fails, it's retried according to the function's configured `tries` and `backoff` settings (defaults: 3 attempts, 2x backoff).

## Subscribing from a webhook

Outbound webhooks are subscriptions that deliver events to external HTTP endpoints. When an event matching the webhook's subscribed events fires, Pawabase sends an HTTP POST to the configured URL.

Configure outbound webhooks in **Studio → Automate → Webhooks → Outbound**. The webhook receives the full event envelope in the request body, signed with HMAC-SHA256. See [Outbound webhooks](/webhooks/outbound) for complete configuration.

## Subscribing from realtime

Realtime channels can subscribe to events and broadcast them to connected clients. When an event fires, Pawbasse publishes a message to the channel, which is immediately pushed to all subscribed WebSocket clients.

Configure realtime channel rules in **Studio → Realtime → Channel rules**. See [Realtime overview](/realtime/overview) for details.

## Event name matching

Events are matched using the `*` wildcard, which matches exactly one dot-separated segment:

| Pattern | Matches | Does not match |
| --- | --- | --- |
| `orders.created` | Only `orders.created` | `orders.updated`, `users.created` |
| `orders.*` | `orders.created`, `orders.updated` | `orders.us.shipped`, `users.created` |
| `*.created` | `orders.created`, `users.created` | `orders.updated` |
| `*` | Every event | (nothing — matches all) |

Matching is **case-sensitive** and uses glob-style patterns (not regex).

## Delivery guarantees

| Guarantee | What it means |
| --- | --- |
| **At-least-once** | Every event is delivered at least once. If a consumer fails, the event may be redelivered. Consumers must be idempotent. |
| **Per-event-name ordering** | For a single event name (e.g., `orders.created`), events are delivered in the order they were published. |
| **Isolation** | Events from `acme/production` never reach subscribers in `acme/development`. |
| **Async delivery** | Subscribers receive work as queued jobs. A slow subscriber never delays the emitter or other subscribers. |
| **No cross-event ordering** | Events with different names (`orders.created` and `users.created`) may be delivered in any order relative to each other. |

<Warning>
If you need exactly-once processing (e.g., financial transactions), design your consumer to be idempotent. Use `input.event.id` to detect and skip duplicates.
</Warning>

## Retry behavior by subscriber type

| Subscriber type | Default retries | Default backoff | Queue |
| --- | --- | --- | --- |
| Flow | 5 | 2x exponential | `flows` |
| Function | 3 | 2x exponential | `functions` |
| Webhook | 5 | 2x exponential | `webhooks` |
| Realtime | 0 (no retry) | — | (in-process) |

Retry settings are configurable per flow, function, and webhook in Studio. The maximum backoff delay caps at 60 seconds regardless of settings.

### Dead letter queue

After all retries are exhausted, the failed job is moved to a dead-letter queue (DLQ). Failed jobs appear in **Studio → Operate → Failed jobs**, where you can:

- Inspect the full error trace
- See all retry attempts and their error messages
- Re-run the job with the original input
- Export the error for debugging

## Monitoring subscriptions

Studio provides several tools for subscription observability:

1. **Events dashboard** (Observability → Events) — Browse all events, filter by name, project, environment, and time range. Each event shows its consumers and their outcomes (queued, succeeded, failed).

2. **Flow execution traces** (Build → Flows → Executions) — When an event triggers a flow, the execution trace shows the event as the trigger input. Expand any step to see the available data.

3. **Failed jobs** (Operate → Failed jobs) — See all jobs that exhausted their retries, with error details and the ability to re-run.

4. **Webhook deliveries** (Automate → Webhooks → Deliveries) — Track every webhook delivery: status, HTTP response code, response body, and retry history.

## Common mistakes

<AccordionGroup>
  <Accordion title="Event name doesn't match">
    Event names are case-sensitive. `Orders.Created` does not match `orders.created`. Copy the exact name from the [Event catalog](/events/catalog).
  </Accordion>
  <Accordion title="Draft flow doesn't trigger">
    Flows must be **enabled** (has at least one version published) to receive event triggers. A draft flow won't fire.
  </Accordion>
  <Accordion title="Condition always fails">
    Conditions are evaluated synchronously when the event is published. If your condition references data that isn't in the event payload, it will always fail. Use the Events dashboard to inspect the actual payload.
  </Accordion>
  <Accordion title="Function doesn't fire">
    Verify the function is deployed (has an enabled version) and that the trigger configuration includes the event name.
  </Accordion>
  <Accordion title="Not handling duplicates">
    At-least-once delivery means events may be redelivered. Use `input.event.id` to deduplicate in your consumer logic.
  </Accordion>
</AccordionGroup>
