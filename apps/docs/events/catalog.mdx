This page catalogues every event Pawabase emits automatically, what triggers each one, and the payload shape a subscriber receives. You can subscribe to any of these events from a flow's `trigger.event` node, a function subscription, an outbound webhook, or a realtime channel.

For custom events you emit yourself, see [Emitting](/events/emitting). For wildcard pattern matching, see [Events overview → wildcard matching](/events/overview#event-names-and-wildcard-matching).

<Note>
Platform lifecycle events for flows (`flow.started`, `flow.completed`, `flow.failed`) are **not** emitted by Pawabase — those names do not exist. If you need to react to a flow's completion, have the flow emit a custom event at its end with `event.emit`.
</Note>

## Resource events

Every resource with `events: true` (the default) emits three events. The resource name is the value of the resource's `name` field — the same name in the URL `/rest/v1/<name>`.

| Event name | Triggered by |
| --- | --- |
| `<resource>.created` | A record is successfully created |
| `<resource>.updated` | A record is successfully updated |
| `<resource>.deleted` | A record is successfully deleted |

These events fire after the write commits to the database. If the write fails or is rolled back, no event is emitted.

### Payload shape

The payload is the full record after the write (for `created` and `updated`), or the record as it existed before deletion (for `deleted`). It contains every field in the resource's read model — the same fields a `GET /rest/v1/<name>/{id}` would return.

The event arrives in a subscribing flow as `input.event`, with the record at `input.event.payload.record`:

```json
{
  "event": {
    "name": "orders.created",
    "payload": {
      "resource": "orders",
      "change": "created",
      "record": {
        "id": "ord_9f2",
        "customer_id": "cus_abc",
        "status": "pending",
        "total_cents": 4900,
        "created_at": "2026-09-30T14:02:11Z",
        "updated_at": "2026-09-30T14:02:11Z"
      }
    },
    "id": "evt_3b8f1c2a",
    "source": "resources",
    "actor": "usr_abc",
    "occurred_at": "2026-09-30T14:02:11.342Z",
    "request_id": "req_7e9a1c"
  }
}
```

To access the record in a flow: `$input.event.payload.record.id`, `{{ input.event.payload.record.status }}`, etc.

### Disabling resource events

Set `events: false` on a resource definition to stop emitting all three events for that resource:

```json
{ "name": "audit_logs", "events": false }
```

This is primarily useful for high-write resources where event overhead matters, or for purely internal resources you never want driving automation.

## Auth events

Akountz emits these events after identity actions complete:

| Event name | Triggered by | Payload |
| --- | --- | --- |
| `user.signed_up` | A new account is created | `{ user_id, email, email_verified }` |
| `user.signed_in` | A user successfully authenticates | `{ user_id, email, method, ip }` |
| `user.signed_out` | A session is terminated | `{ user_id }` |
| `user.email_verified` | Email verification completes | `{ user_id, email }` |
| `user.password_changed` | A user changes their password | `{ user_id }` |
| `user.mfa_enabled` | A user confirms TOTP enrollment | `{ user_id }` |
| `user.mfa_reset` | An administrator resets a user's MFA | `{ user_id }` |

### `user.signed_in` payload

```json
{
  "event": {
    "name": "user.signed_in",
    "payload": {
      "user_id": "usr_abc",
      "email": "chioma@example.com",
      "method": "password",
      "ip": "203.0.113.4"
    },
    "id": "evt_5c4d3e2f",
    "source": "akountz",
    "actor": "usr_abc",
    "occurred_at": "2026-09-30T14:00:00Z",
    "request_id": "req_9a8b7c"
  }
}
```

The `method` field distinguishes how the user authenticated:

| Value | Meaning |
| --- | --- |
| `password` | Email and password grant |
| `magic_link` | Magic link click-through |
| `oauth:<provider>` | OAuth/OIDC provider — e.g. `oauth:google`, `oauth:github` |
| `mfa` | MFA challenge completion |

### `user.signed_up` payload

```json
{
  "payload": {
    "user_id": "usr_new",
    "email": "new.user@example.com",
    "email_verified": false
  }
}
```

The `user.signed_up` event is a common trigger for welcome emails, onboarding flows, and default data creation. An unverified email has `email_verified: false`; `user.email_verified` fires separately once the user clicks the verification link.

## Wildcard subscriptions for auth events

To react to any sign-in regardless of method:

```json
{ "event": "user.signed_in" }
```

To react to any user lifecycle event:

```json
{ "event": "user.*" }
```

Since `*` crosses dots in Pawabase's pattern matching, `user.*` matches `user.signed_in`, `user.signed_up`, `user.email_verified`, and all others. Check `input.event.name` inside the flow to branch on which event fired.

## The complete platform event list

| Event name | Emitted by |
| --- | --- |
| `<resource>.created` | Resource layer — every resource write |
| `<resource>.updated` | Resource layer — every resource write |
| `<resource>.deleted` | Resource layer — every resource write |
| `user.signed_up` | Akountz — new account creation |
| `user.signed_in` | Akountz — successful authentication |
| `user.signed_out` | Akountz — session termination |
| `user.email_verified` | Akountz — email verification |
| `user.password_changed` | Akountz — password change |
| `user.mfa_enabled` | Akountz — TOTP enrollment confirmation |
| `user.mfa_reset` | Akountz — administrator MFA reset |

There is no separate catalog of flow or scheduler events. Flows emit whatever you configure with `event.emit`; the scheduler triggers flows directly without emitting a separate platform event.

## Custom event names

You can emit any event name from a flow's `event.emit` block. Custom events follow the same at-least-once, environment-isolated delivery guarantees as platform events.

Follow the `domain.action` naming convention and use lowercase with dots: `order.paid`, `invoice.overdue`, `cart.abandoned`. This keeps event names consistent and makes wildcard subscriptions predictable.

Avoid names that could collide with current or future platform events: don't use `user.*`, `<resource>.*`, as top-level prefixes for custom events if you have resources or auth-adjacent logic that might shadow them.

```json
{
  "id": "announce_payment",
  "data": {
    "block": "event.emit",
    "config": {
      "event": "payment.captured",
      "payload": {
        "order_id": "{{ steps.load_order.output.id }}",
        "amount_cents": "{{ steps.load_order.output.total_cents }}"
      }
    }
  }
}
```
