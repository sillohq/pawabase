A session lets a user make authenticated requests after sign-in. Pawabase returns a short-lived access token and a rotating refresh token.

The access token authorizes application API requests. The refresh token obtains a replacement pair. Keep the two roles separate: a refresh token is not a bearer credential for resource requests.

## Configure lifetimes in Studio

Open **Users & auth → Configuration → Passwords** for the selected environment.

| Setting | Default | Meaning |
| --- | --- | --- |
| Access token lifetime | 900 seconds | How long a newly issued access token remains valid |
| Refresh token lifetime | 2,592,000 seconds | Lifetime configured for issuing refresh credentials |

Changing a lifetime affects subsequent token issuance. It does not rewrite expiration timestamps inside existing tokens.

A shorter access lifetime reduces the time that stale permissions can remain in a previously issued token. It requires a reliable refresh implementation.

## Session response

Password sign-in, successful email-link verification, MFA completion, and refresh return session information. OAuth redirects deliver a subset in a fragment.

A JSON session response has this shape:

~~~json
{
  "access_token": "<access-token>",
  "refresh_token": "<refresh-token>",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1790850000,
  "session_id": "<session-id>",
  "org": null,
  "org_role": null,
  "user": {
    "id": "482",
    "email": "amina@example.com"
  }
}
~~~

The user object above is abbreviated. `expires_at` is an illustrative Unix timestamp in seconds.

| Field | Application use |
| --- | --- |
| `access_token` | Authorization header on protected API requests |
| `refresh_token` | Next refresh request; replace after every successful refresh |
| `token_type` | Bearer-token scheme |
| `expires_in` | Access lifetime in seconds |
| `expires_at` | Absolute access expiration |
| `session_id` | Identifies this session across token rotations |
| `org` / `org_role` | Active application organization and membership role |
| `user` | Profile information for the signed-in person |

An MFA challenge or verification-pending sign-up response is not a session. Check the response shape before saving credentials.

## Use the access token

~~~bash
curl "$PAWABASE_URL/auth/v1/user" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
~~~

Use the same pair of headers for protected resource requests. The API key and token must belong to the same environment.

Do not send tokens in ordinary query strings. URLs commonly appear in history, logs, analytics, and copied links.

## Claims on the access token

Claims describe the authenticated user at the time the token was issued.

| Claim | Meaning |
| --- | --- |
| `sub` | User identity |
| `project`, `env` | Project and environment scope |
| `roles` | Environment role names |
| `perms` | Effective permission names |
| `org`, `org_role` | Active application organization and membership role |
| `aal` | Authentication assurance level |
| `sid` | Session ID |
| `jti` | Individual token ID |
| `iat`, `exp` | Issuance and expiration timestamps |
| `meta` | User metadata, when present |
| `app` | Application-managed metadata, when present |

Decoding a token for display is not verification. Let Pawabase verify it when making API requests. Do not authorize a backend action using unverified decoded claims.

Policies expose these values through [the authentication context](/auth/auth-in-policies), including `$auth.roles`, `$auth.permissions`, and `$auth.org`.

## Refresh a session

~~~bash
curl -X POST "$PAWABASE_URL/auth/v1/token" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "grant_type": "refresh_token",
    "refresh_token": "<current-refresh-token>"
  }'
~~~

A successful response contains a new access token and a new refresh token. Replace the entire stored pair together.

Do not keep using the previous refresh token. It has been consumed.

### Serialize refresh requests

Several requests may discover an expired access token simultaneously. Coordinate them through one refresh operation.

~~~javascript
let session = null;
let refreshInFlight = null;

function setSession(next) {
  session = next;
}

async function refreshSession() {
  if (refreshInFlight) return refreshInFlight;
  if (!session?.refresh_token) throw new Error("Sign in again");

  const refreshToken = session.refresh_token;
  refreshInFlight = (async () => {
    const response = await fetch(PAWABASE_URL + "/auth/v1/token", {
      method: "POST",
      headers: {
        apikey: PAWABASE_PUBLISHABLE_KEY,
        "Content-Type": "application/json",
      },
      body: JSON.stringify({
        grant_type: "refresh_token",
        refresh_token: refreshToken,
      }),
    });
    const result = await response.json();
    if (!response.ok) {
      session = null;
      throw new Error("Your session could not be renewed");
    }
    session = result;
    return result;
  })();

  try {
    return await refreshInFlight;
  } finally {
    refreshInFlight = null;
  }
}
~~~

This example coordinates refreshes within one JavaScript runtime. Multiple tabs need shared coordination, and a server handling concurrent requests needs a lock or equivalent session-store operation.

If the server accepted a refresh but the response was lost, blindly retrying the old refresh token can trigger reuse detection. End the local session and ask for a fresh sign-in when you cannot safely recover the replacement.

### Reuse detection

Reusing an already-consumed refresh token can revoke the session's refresh chain. This protects against reuse of a copied credential, but a buggy client with parallel refreshes can cause the same result.

Investigate repeated sign-outs by checking for duplicate refresh calls, stale browser tabs, and retries after network failures. Never log the token values while doing so.

## Change the active organization

Use the refresh endpoint with `org`:

~~~json
{
  "grant_type": "refresh_token",
  "refresh_token": "<current-refresh-token>",
  "org": "northstar"
}
~~~

The user must belong to the requested organization.

| Request | Result |
| --- | --- |
| Omit `org` | Retain the current organization if membership remains valid |
| Set an organization slug | Switch to that organization after membership validation |
| Set `org: null` | Clear the active organization |

A switch also rotates the token pair. Replace it and clear cached data or subscriptions for the previous organization.

## List active sessions

~~~bash
curl "$PAWABASE_URL/auth/v1/sessions" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
~~~

The response contains a `data` array. Each entry includes `id`, `method`, `aal`, `ip`, `user_agent`, `created_at`, `last_refreshed_at`, and `current`.

Use `current` to label “This session.” Browser and IP information help a person recognize activity, but are not proof of device ownership.

Only sessions with an active refresh credential appear. An expired session should not be presented as still resumable.

Operators can inspect user sessions in **Users & auth → Users**, then open a user.

## Sign out

~~~bash
curl -X POST "$PAWABASE_URL/auth/v1/logout" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"scope":"local"}'
~~~

| Scope | Effect |
| --- | --- |
| `local` | Revoke the current session |
| `global` | Revoke all sessions for the user |
| `others` | Revoke the user's other sessions and retain this one |

The response contains `signed_out: true` and the selected scope.

For local or global logout, remove local credentials, user-specific caches, and subscriptions. If the network request fails, clearing local state still signs the person out of that browser, but does not prove remote revocation succeeded.

### Revoke a selected session

~~~bash
curl -X DELETE "$PAWABASE_URL/auth/v1/sessions/$SESSION_ID" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
~~~

A successful deletion returns 204 with no response body. Use session IDs returned for the signed-in user; do not build an interface that accepts arbitrary IDs.

## What revocation does and doesn't do immediately

Revocation prevents further refresh. An already-issued access token can remain usable until its expiry on services that validate the token without checking live session state.

Do not promise instant invalidation of every API request after logout or a role change. Access-token lifetime is part of that boundary.

Current-user endpoints may additionally check live account availability. That does not mean every resource request performs the same account lookup.

## Roles, membership, and MFA changes

Roles and permissions are refreshed when new access tokens are issued. Organization membership is also reconsidered during issuance.

After enrollment confirmation elevates an existing session to `aal2`, refresh to obtain an access token reflecting the new assurance level. A token already stored in memory does not change itself.

Use [MFA](/auth/mfa) for enrollment and challenge handling.

## Store credentials according to your application

A browser-only client can keep a session in memory, accepting that a reload loses it unless another persistence strategy is added. JavaScript-readable persistent storage increases exposure to injected scripts.

A backend-for-frontend can hold Pawabase tokens on the server and use its own Secure, HttpOnly session cookie. The backend must implement its cookie, CSRF protection, session store, and refresh coordination; Pawabase's JSON token response does not set up that architecture automatically.

Native applications should use the platform's protected credential storage.

Never put refresh tokens in application logs, error reporting payloads, or analytics properties.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Immediate 401 after sign-in | Matching gateway, API key, environment, and bearer header |
| Intermittent refresh failures | Concurrent refresh calls or reused stored tokens |
| Permissions stay unchanged | Whether the client actually installed the newest token pair |
| Session disappears from the device list | Refresh expiry or revocation |
| Logout completed but a copied access token still works | Its remaining access lifetime |
| Organization switch is denied | Membership and exact organization slug |
| MFA enrollment succeeded but policy still denies | Refresh and inspect the newly issued assurance level |
