A Pawabase session is the pairing of two things: Sillo's own generic token-family mechanism (rotation, reuse detection, revocation — the same primitive every Pawabase service's users ride on) and `SessionInfo`, a small Akountz table that remembers what Sillo's tokens don't: which device, which sign-in method, and what assurance level. This page documents both halves, plus the exact shape of the claims a client actually receives.

## The three kinds of token

`pawabase_kit.tokens` defines three token shapes, all JWTs, but only one of them — the user access token — is ever handed to a client application:

| Kind | Issued by / for | Signing key | Typical lifetime |
| --- | --- | --- | --- |
| **Service token** | One Pawabase service calling another. | The installation's internal secret, per `(issuer, audience)`. | Short (default 60s) — re-minted per call. |
| **Context token** | The gateway telling a service which project/environment/credential a request carries. | The internal secret. | 60s. |
| **User token** | Akountz, for a project's end users. | Derived per `(project, env)` from the platform's JWT master secret. | `access_ttl` (default 900s) for access; `refresh_ttl` (default 2,592,000s / 30 days) for refresh. |

This page is about the third kind. The first two are internal plumbing — worth knowing exist (so a `typ` claim of `"service"` or `"context"` on a token you happen to inspect doesn't surprise you), but never something a client integration issues or verifies directly.

### Per-environment signing keys

```python
def derive_env_secret(master: str, project: str, env: str) -> str:
    message = f"pawabase:user-token:{project}:{env}".encode()
    return hmac.new(master.encode(), message, hashlib.sha256).hexdigest()
```

Every environment's user-token signing key is deterministically derived from one platform-wide master secret plus the `(project, env)` pair. Nobody needs to generate or store a separate key per environment, and — critically — a token successfully verified against `acme/development`'s derived key cannot be re-verified against `acme/production`'s, because they're different derived secrets. `verify_user_token` additionally checks the `prj`/`env` claims inside the token match the environment being verified against, as a second, redundant guard against a token being replayed at the wrong environment.

## `issue_user_token`: the real claim shape

Access tokens are minted by `issue_user_token` in `pawabase_kit/tokens.py` — not by a hand-rolled `build_token_payload()` or any function inside Akountz itself. Akountz calls it once per session start and once per refresh, from `app/sessions.py`'s `_access_token`:

```python
def issue_user_token(
    master: str, *,
    project: str, env: str, user_id: str, jti: str, session_id: str,
    ttl: int = 900,
    email: str | None = None,
    roles: list[str] | None = None,
    permissions: list[str] | None = None,
    org: str | None = None,
    org_role: str | None = None,
    aal: str = "aal1",
    extra: dict[str, Any] | None = None,
    app: dict[str, Any] | None = None,
) -> str:
```

The resulting JWT payload:

```json
{
  "sub": "482",
  "aud": "authenticated",
  "iss": "pawabase:akountz:acme",
  "prj": "acme",
  "env": "production",
  "sid": "f3f0c2f8a91b4d5e",
  "jti": "8a2e1c...",
  "iat": 1735660800,
  "exp": 1735661700,
  "typ": "access",
  "aal": "aal1",
  "email": "chioma@example.com",
  "roles": ["editor"],
  "perms": ["reports.publish"],
  "org": "acme-hq",
  "org_role": "admin",
  "meta": { "tier": "starter" },
  "app": { "customer_id": "cus_9f21" }
}
```

| Claim | Meaning |
| --- | --- |
| `sub` | The user's id, as a string. |
| `aud` | Always `"authenticated"` for a user token. |
| `iss` | `pawabase:akountz:<project>`. |
| `prj`, `env` | The environment this token is valid for — re-checked on every verification, on top of the signing key already being environment-specific. |
| `sid` | The **session id** — Sillo's token family id. Every access token minted from the same session shares this value across every refresh. |
| `jti` | This specific token's id. Reused from Sillo's own tracked token-family JTI, so revocation and rotation stay aligned with Sillo's `JWTToken` rows. |
| `typ` | `"access"` — `verify_user_token` rejects anything else. |
| `aal` | `"aal1"` or `"aal2"` — see [MFA → assurance levels](/auth/mfa#assurance-levels-aal1-and-aal2). |
| `roles`, `perms` | Resolved fresh at mint time from [`rbac.roles_of`/`rbac.permissions_of`](/auth/roles-and-permissions#listing-assigning-and-revoking). |
| `org`, `org_role` | The active organization (if any) and the caller's role in it — see [Organizations → organizations and sessions](/auth/organizations#organizations-and-sessions). |
| `meta` | `user_metadata` — present only if non-empty. **User-editable; never trust it in a policy.** |
| `app` | `app_metadata` — present only if non-empty. Only an administrator or a service key can set it; safe to gate access on. |

<Warning>
There is no `build_token_payload()` function anywhere in this codebase, and there is no `Principal.__init__(self, token, secret)` signature that parses claims out of a raw JWT at construction time. The real `Principal` (`pawabase_kit.principal.Principal`) takes already-verified `(kind, claims)` and does no decoding itself — token verification happens once, earlier in the request pipeline, via `verify_user_token`. See [Overview → the `Principal`](/auth/overview#the-principal-what-a-request-actually-carries).
</Warning>

## Starting a session

`start_session` is the single function behind every "sign the user in" path — password, magic link, email verification, social login, and MFA completion all call it with a different `method` string:

```python
async def start_session(
    akountz: Akountz, config: AuthConfig, user: AuthUser, *,
    method: str, ctx: Any = None, aal: str = "aal1", org: str | None = None,
) -> dict[str, Any]:
```

It does five things, in order: validates `org` membership (if one was requested), asks Sillo's `JWTUserMixin.issue_token_pair` for a fresh access/refresh pair, records a `SessionInfo` row for the family, resets the account's failure/lockout counters via `record_success`, and logs a `sign_in` event plus a `user.signed_in` platform event.

```json
{
  "access_token": "eyJhbGciOi...",
  "refresh_token": "rft_8f2c...",
  "token_type": "bearer",
  "expires_in": 900,
  "expires_at": 1735661700,
  "session_id": "f3f0c2f8a91b4d5e",
  "org": null,
  "org_role": null,
  "user": { "id": "482", "email": "...", "..." : "..." }
}
```

`expires_in` is `config.access_ttl` (seconds remaining); `expires_at` is a Unix timestamp computed at response time — both describe the **access** token only. The refresh token's own, much longer, lifetime (`config.refresh_ttl`) is never surfaced as a field in this response; a client tracks refresh-token validity implicitly by whether the next refresh call succeeds.

## Refreshing: rotation and theft detection

Every refresh call **consumes** the refresh token it's given and issues a brand-new one — this is Sillo's rotating-refresh-token model, and Akountz adds nothing to the mechanism itself beyond re-minting the richer access token claims on top of it:

```python
pair = await user.refresh_token_pair(refresh_token, akountz.refresh_secret(config.project, config.env))
```

A successful refresh always returns a **new** `refresh_token` in the response — clients must persist it and discard the one they sent, exactly the same as the initial sign-in response. Presenting the same refresh token twice is precisely what theft detection watches for:

```python
except ValueError as exc:
    if "theft" in str(exc):
        row = await JWTToken.filter(token_jti=claims.get("jti") or "").first()
        if row is not None:
            await SessionInfo.filter(family=row.token_family).update(revoked_at=datetime.now(UTC))
        await akountz.emit(config.project, config.env, "session.reuse_detected", {"user_id": str(user.id)}, actor=str(user.id))
    raise HTTPException(status_code=401, detail="invalid refresh token") from exc
```

If a refresh token that's already been consumed is presented again — the signature of either a stolen token being used after the legitimate client already refreshed, or a client bug that retried a request with a stale token — Sillo raises a "theft" error, and Akountz responds by revoking the **entire session family**, not just the one token, and emitting `session.reuse_detected`. Every access token from that session stops being useful the moment it naturally expires (revocation doesn't retroactively invalidate an unexpired access token — see [immediate revocation](#what-revocation-does-and-doesnt-do-immediately) below), and the refresh chain is dead; the user must sign in again.

<Warning>
Refresh-token rotation means a client must never keep using an old refresh token "just in case." If two requests race and both try to refresh with the same token, one wins and the other is treated as reuse — revoking the session for both. A correct client refreshes proactively, serially, and always overwrites its stored refresh token with the one from the latest successful response before making another request that needs it.
</Warning>

### What changes at refresh, not immediately

Several things about a session are deliberately **not** re-evaluated until the next refresh, because the access token is a self-contained, signed artifact valid for its whole `access_ttl` window regardless of what changes server-side in the meantime:

- Role and permission changes ([Roles and permissions](/auth/roles-and-permissions#how-roles-and-permissions-reach-a-policy)).
- Organization membership-role changes ([Organizations](/auth/organizations#the-membership-role-is-re-read-at-issue-time)).
- `app_metadata` changes made by an administrator.
- The assurance level, *unless* `elevate()` is called explicitly on the live session (see [MFA → assurance levels](/auth/mfa#assurance-levels-aal1-and-aal2)).

If your application needs a change to take effect immediately rather than on next refresh, the only mechanism is revoking the affected session(s) so the client is forced to re-authenticate.

## Switching organization context mid-session

A refresh can name `org` to move the session to a different organization (or clear it), independent of anything else about the refresh. See [Organizations → switching or clearing the organization on refresh](/auth/organizations#switching-or-clearing-the-organization-on-refresh) for the full three-way distinction between omitting the field, naming a new organization, and explicitly clearing it with `null`/`""`.

## The `SessionInfo` model

Sillo's own `JWTToken` rows track the rotation/revocation state of a token family; `SessionInfo` is what Akountz adds on top, one row per family:

```python
class SessionInfo(Model):
    family = fields.CharField(max_length=64, primary_key=True)
    user = fields.ForeignKeyField("models.AuthUser", related_name="sessions")
    project = fields.CharField(max_length=63, db_index=True)
    env = fields.CharField(max_length=63)
    method = fields.CharField(max_length=32)
    aal = fields.CharField(max_length=8, default="aal1")
    org = fields.CharField(max_length=63, null=True)
    ip = fields.CharField(max_length=64, null=True)
    user_agent = fields.CharField(max_length=512, null=True)
    last_refreshed_at = fields.DatetimeField(null=True)
    revoked_at = fields.DatetimeField(null=True)
```

`family` **is** the session id (`sid` claim) — the primary key of this table is literally the string that shows up on every access token minted from it. `method` records how the session began (`"password"`, `"magic_link"`, `"oauth:google"`, `"recovery"`, `"email_verification"`, …) and never changes after creation, even across refreshes.

### Listing sessions

```bash
curl "$GW/auth/v1/sessions" -H "Authorization: Bearer $ACCESS_TOKEN" -H "apikey: $KEY"
```

```json
{ "data": [
  { "id": "f3f0c2f8...", "method": "password", "aal": "aal1", "ip": "203.0.113.4",
    "user_agent": "Mozilla/5.0 ...", "created_at": "2026-09-28T09:00:00Z",
    "last_refreshed_at": "2026-09-30T08:12:00Z", "current": true },
  { "id": "9b1e4a02...", "method": "oauth:google", "aal": "aal1", "ip": "198.51.100.9",
    "user_agent": "...", "created_at": "2026-09-15T14:22:00Z",
    "last_refreshed_at": null, "current": false }
] }
```

The list only includes families that are **both** un-revoked in `SessionInfo` **and** currently have an active, non-consumed, non-expired refresh token in Sillo's own `JWTToken` table — a `SessionInfo` row whose refresh token has simply expired from age (never revoked, just aged out past `refresh_ttl`) is filtered out rather than shown as a stale, misleadingly "active" entry.

## Revocation: every path

| Action | Effect | Who can trigger it |
| --- | --- | --- |
| `POST /auth/v1/logout` with `{"scope": "local"}` (default) | Revokes only the current session. | The user. |
| `POST /auth/v1/logout` with `{"scope": "others"}` | Revokes every session except the current one. | The user. |
| `POST /auth/v1/logout` with `{"scope": "global"}` | Revokes every session, including the current one. | The user. |
| `DELETE /auth/v1/sessions/{session_id}` | Revokes one specific session by id. | The user, for their own sessions. |
| `POST /projects/.../users/{user_id}/sessions/revoke` | Revokes every session for that user. | An administrator / service key. |
| `DELETE /projects/.../users/{user_id}/sessions/{session_id}` | Revokes one specific session. | An administrator / service key. |
| A refresh-token reuse ("theft") is detected | Revokes the entire family automatically. | The system, never a person. |
| An administrator disables the account | Calls `revoke_all` as part of disabling. | An administrator. |

`revoke_session` and `revoke_all` both do two things together — revoke the underlying Sillo `JWTToken` family **and** stamp `SessionInfo.revoked_at` — so the two records of "is this session alive" never drift out of sync:

```python
async def revoke_session(user: AuthUser, family: str) -> bool:
    revoked = await JWTToken.revoke_family(family)
    updated = await SessionInfo.filter(user=user, family=family, revoked_at=None).update(revoked_at=datetime.now(UTC))
    return bool(revoked or updated)
```

### What revocation does and doesn't do, immediately

Revoking a session invalidates its **refresh token** immediately — the next refresh attempt with it fails with `401 invalid refresh token`. It does **not** retroactively invalidate an access token that's already been issued and hasn't expired yet; that token remains verifiable (its signature and claims are still valid) until its own `exp` passes, which is at most `access_ttl` seconds away — 15 minutes by default. This is the same trade-off documented for [password changes](/auth/passwords#password-change-security-model): a short `access_ttl` is what bounds the actual window of exposure after a revocation, not the revocation call itself.

<Warning>
If you need truly immediate termination of access (not just "can't refresh anymore"), the only real lever is `access_ttl` — a shorter access-token lifetime means a shorter worst-case window between "we revoked this" and "the token stopped working." There is no separate access-token blocklist check on every request.
</Warning>

## One-time tokens

Every single-use link or code flow in Akountz — email verification, password recovery, magic links, invitations, and MFA challenges — is backed by one shared mechanism: a `OneTimeToken` row plus a signed, time-limited wrapper around its id.

```python
LIFETIMES = {
    "verify": 24 * 3600,      # 24 hours
    "recovery": 3600,          # 1 hour
    "magic": 900,              # 15 minutes
    "invite": 7 * 24 * 3600,  # 7 days
    "mfa": 300,                # 5 minutes
    "email_change": 24 * 3600,
    "link": 600,               # identity-linking tickets, 10 minutes
}
```

The token string itself is Sillo's `URLSafeTimedSerializer` signature over `{"id": row.id}`, keyed per `(project, env, purpose)` — not a JWT, and unrelated to the access/refresh token signing scheme above. `consume()` checks the signature and its embedded age (`max_age=LIFETIMES[purpose]`), then separately checks the database row hasn't already been used or expired, and marks it used with a conditional update (`WHERE used_at IS NULL`) so two concurrent redemptions of the same link can't both succeed. Every failure mode — bad signature, expired signature, missing row, already-used row, database-level expiry — collapses to the identical `400 the link is invalid or has expired`, deliberately, so a client (or an attacker probing links) can't distinguish "this link is old" from "this link was already used" from "this link was forged."

`peek=True` verifies and looks up the row **without** consuming it — used by the recovery flow's "is this link still valid" check before showing a password form, and by the invitation-accept flow's initial lookup before the final consuming call.

## Real scenarios

### Session refresh in a mobile app

A mobile client typically stores the refresh token in secure device storage and refreshes proactively — a few minutes before the access token's `expires_at` — rather than waiting for a `401` from an API call. Because refresh rotates the token every time, the client's storage write (new refresh token in, old one discarded) must complete before the token is used again; a client that refreshes from two code paths concurrently (a background sync and a foreground request both waking up at once) risks one of them presenting an already-consumed token and triggering theft detection, which revokes the whole session. Serializing refresh calls behind a single in-flight request (a mutex or a shared promise/future around the refresh call) avoids this entirely.

### Detecting a compromised session after a password reset

Resetting a password (via the recovery flow) calls `revoke_all` automatically — every session dies, everywhere, the moment a new password is set. A plain in-account password *change* (via `PATCH /auth/v1/user`) does **not** do this by design (see [Passwords → password change security model](/auth/passwords#password-change-security-model)); if a user suspects compromise and changes their password proactively rather than through the forgot-password flow, your client should also offer an explicit "sign out everywhere" action, which maps to `POST /auth/v1/logout` with `{"scope": "global"}`.

### Building a "you're signed in on 3 devices" settings page

`GET /auth/v1/sessions` gives you everything needed: `method` for an icon/label ("Signed in with Google" vs. "Password"), `ip`/`user_agent` for a human-readable device description, `created_at`/`last_refreshed_at` for recency, and `current: true` to visually distinguish the session making the request itself (usually rendered without a "sign out" button, or with a different one that also ends the local app session).

## Common mistakes

<AccordionGroup>
  <Accordion title="Looking for build_token_payload() or a Principal(token, secret) constructor">
    Neither exists. Token minting is `issue_user_token` in `pawabase_kit/tokens.py`; `Principal` takes already-verified `(kind, claims)` and does no verification itself.
  </Accordion>
  <Accordion title="Reusing a refresh token after a successful refresh">
    The refresh token you sent is consumed the instant the refresh succeeds. Always store and use the **new** `refresh_token` from the response; presenting the old one again triggers theft detection and kills the whole session.
  </Accordion>
  <Accordion title="Expecting a role or org_role change to appear on the current access token">
    It won't, until the next refresh or sign-in. See [what changes at refresh, not immediately](#what-changes-at-refresh-not-immediately).
  </Accordion>
  <Accordion title="Expecting revocation to instantly invalidate an unexpired access token">
    It doesn't — only the refresh token is immediately dead. The access token remains valid until its own `exp`. Shorten `access_ttl` if your threat model needs a tighter worst-case window.
  </Accordion>
  <Accordion title="Treating a magic-link, invite, or recovery token as a JWT">
    They're all `URLSafeTimedSerializer` signatures over a database row id, a completely different mechanism from the JWT access/refresh pair, with their own per-purpose lifetimes.
  </Accordion>
</AccordionGroup>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `401 invalid refresh token` right after a refresh that appeared to succeed | Two concurrent refresh calls raced; the second presented an already-consumed token. | Serialize refresh calls behind one in-flight request. |
| `session.reuse_detected` events appearing in production | Either a genuine stolen refresh token, or a client bug retrying with a stale token. | Audit client refresh logic for concurrency bugs before assuming compromise. |
| A user's new role doesn't show up in `$auth.roles` right away | The client is using an access token minted before the change. | Wait for the next refresh, or revoke the session to force re-authentication. |
| `GET /auth/v1/sessions` is missing a session the user swears is active | Its refresh token aged out past `refresh_ttl` without ever being revoked. | Expected — an aged-out, non-revoked session is filtered from the active list. |
| Access token still "works" for a few minutes after the user signed out on another device | Expected — revocation kills the refresh token immediately, not the still-valid access token. | Lower `access_ttl` if this window is unacceptable for your threat model. |
