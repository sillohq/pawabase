Password recovery allows a user to reset their password when they've forgotten it — or when a compromised password needs to be rotated immediately. The flow is designed to be **keyless**: the user never needs to answer security questions or enter a verification code before receiving the reset link. Security comes from the single-use, time-limited link sent to the verified email address.

<CardGroup cols={3}>
  <Card title="Single-use, 1-hour TTL" icon="timer">Every recovery link works exactly once and expires in 1 hour.</Card>
  <Card title="No enumeration" icon="eye">The `/recover` endpoint returns the same response whether the email exists or not.</Card>
  <Card title="Full sign-out on reset" icon="shield-check">After a successful reset, all other sessions are revoked immediately.</Card>
</CardGroup>

## The recovery flow

### Step 1: Request a reset link

**Request**: `POST /auth/v1/recover`

```bash
curl -X POST "$GW/auth/v1/recover" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{ "email": "chioma@example.com" }'
```

The response is always `{"sent": true, "message": "If the address has an account, a message is on its way."}` — regardless of whether the email is registered. This prevents account enumeration, which is the primary security property of the request endpoint.

Behind the scenes:

```python
async def recover(ctx: HttpContext, body: EmailRequest):
    config = await config_for(akountz, ctx)
    user = await find_by_email(config.project, config.env, normalise_email(body.email))
    if user is not None and not user.is_disabled:
        token = await links.issue(akountz, config, "recovery", user=user)
        await emails.send(...)
        await log_event(config.project, config.env, "recovery_requested", user=user, ctx=ctx)
    return SENT
```

The token is a `OneTimeToken` row with:

| Property | Value |
| --- | --- |
| Purpose | `"recovery"` |
| Lifetime | **3600 seconds** (1 hour) |
| Single-use | Yes |
| Rate limit | 10 requests per 60 seconds per IP |

If the user is disabled (`is_disabled == true`), no email is sent — a disabled account cannot recover its password through this flow. An administrator must re-enable the account first.

The `redirect_to` parameter is supported and validated against the environment's `site_url` and `redirect_urls`. If `redirect_to` points to an allowed URL, the completion page redirects there with the tokens in the URL fragment after a successful reset.

### Step 2: Open the recovery page

When the user clicks the link in their email, two paths are possible:

1. **With `site_url` configured**: The link points to `{site_url}/auth/callback?token=…&type=recovery`, and the application's frontend handles the completion.
2. **Without `site_url`**: The link points to Akountz's own recovery page at `/auth/v1/links/{project}/{env}/recovery?token=…`.

The recovery page is rendered as a self-contained HTML form by `_recovery_page()`:

```html
<!doctype html>
<html>
<head><title>Choose a new password</title></head>
<body>
<h1>Choose a new password</h1>
<form id=f>
  <input id=p type=password required minlength=8 autocomplete=new-password>
  <p><button>Save</button></p>
</form>
<p id=m></p>
<script>
document.getElementById('f').onsubmit = async e => {
  e.preventDefault();
  const r = await fetch('/auth/v1/links/{project}/{env}/recovery', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ token: "{token}", password: document.getElementById('p').value })
  });
  const b = await r.json();
  document.getElementById('m').textContent = r.ok
    ? 'Your password was changed. You can sign in now.'
    : (b.detail?.problems || [b.detail]).join(' ');
};
</script>
</body>
</html>
```

This page is served from Akountz directly — no API key is needed. The environment and project are in the URL path, not in a header. The form posts to `/auth/v1/links/{project}/{env}/recovery` (the `register_keyless_recovery` endpoint), which is the same endpoint used when `site_url` is configured and the application forwards the request.

### Step 3: Confirm the new password

**Request**: `POST /auth/v1/recover/confirm`

```bash
curl -X POST "$GW/auth/v1/recover/confirm" \
  -H "content-type: application/json" \
  -d '{ "token": "a1b2c3d4e5f6…", "password": "new-correct-horse-battery-staple" }'
```

The `complete` handler processes the token:

```python
if kind == "recovery":
    if password is None:
        await links.consume(akountz, config, "recovery", token, peek=True)
        return {"valid": True}
    check_password_policy(config, password)
    row = await links.consume(akountz, config, "recovery", token)
    user = row.user
    user.set_password(password)
    user.failed_logins = 0
    user.locked_until = None
    await user.save(update_fields=["password", "failed_logins", "locked_until"])
    await revoke_all(user)
    await log_event(config.project, config.env, "password_reset", user=user, method="recovery", ctx=ctx)
    await akountz.emit(config.project, config.env, "user.password_reset", {"user_id": str(user.id)}, actor=str(user.id))
    return await start_session(akountz, config, user, method="recovery", ctx=ctx)
```

Seven things happen, in order:

1. **Password policy check**: The new password is validated against the environment's `password_policy`. If it fails, `422` is returned with a `problems` array before any state change occurs.
2. **Token consumption**: The one-time token is marked as used. If it was already used or expired, `400 the link is invalid or has expired`.
3. **Password set**: `set_password` hashes and stores the new password.
4. **Lockout cleared**: `failed_logins` resets to 0 and `locked_until` is cleared to `None`. This means a user who was locked out due to too many failed attempts can reset their password and immediately sign in without waiting for the lockout to expire.
5. **All sessions revoked**: `revoke_all` terminates every other session — every device the user was signed in on.
6. **Event emitted**: `user.password_reset` is emitted, and a login event with `kind: "password_reset"` is recorded.
7. **New session issued**: A fresh access/refresh token pair is returned.

<Warning>
A password reset **signs out every device** the user has signed in on. This is deliberate — if an attacker knows the current password, every active session is a potential entry point. After resetting, the user needs to sign in again on every device.
</Warning>

## The keyless recovery page

When `site_url` is not configured, Akountz serves the recovery form directly at `/auth/v1/links/{project}/{env}/recovery`. This page:

- Requires only the `token` query parameter — no API key, no cookies.
- Validates the token server-side on form submission.
- Returns JSON on success (`{"changed": true, "user": ...}`) or an HTML error page on failure.
- Is the same endpoint registered by `register_keyless_recovery` at `POST /links/{project}/{env}/recovery`.

The `register_keyless_recovery` function is called separately from the main routes registration, because it has `exclude_from_schema=True` — it's not part of the OpenAPI schema, and it's intended to be called only from the link page itself.

```python
def register_keyless_recovery(r: Router, akountz: Akountz) -> None:
    @r.post("/links/{project}/{env}/recovery", request_model=ResetBody, exclude_from_schema=True)
    async def recovery_submit(ctx: HttpContext, project: str, env: str, body: ResetBody):
        config = await load_config(akountz, project, env)
        result = await complete(akountz, config, "recovery", body.token, ctx=ctx, password=body.password)
        return {"changed": True, "user": result.get("user")}
```

## Recovery and account lockout

Recovery has a specific interaction with the brute-force lockout mechanism:

- **Lockout does not block recovery**: A locked-out user can still request a recovery link and reset their password. The `find_by_email` lookup in `/recover` does not check `is_locked` — only the `/token` (sign-in) endpoint does.
- **Lockout is cleared on reset**: After a successful password reset, `failed_logins` and `locked_until` are reset. The user can sign in immediately.
- **Recovery does not count as a failed attempt**: Requesting a recovery link (`/recover`) is rate-limited separately (`"akz:links"` middleware, 10 per 60 seconds) but does not increment `failed_logins`. Only password verification attempts in `/token` affect the lockout counter.

## Security considerations

### The reset link is a credential

A recovery link is equivalent to a password — anyone who has it can change the password and sign in. The security model is:

1. **Single-use**: Once consumed, the link cannot be used again.
2. **Time-limited**: 1 hour from issuance.
3. **Email-bound**: The link is sent to the email address on the account. The token's `email` field matches the account's email.
4. **Not a bearer token**: The link cannot be used as an `Authorization` header. It can only be submitted to the recovery endpoint.

### What happens if the email is also compromised

If an attacker has access to both the user's email inbox *and* knows (or has guessed) the current password, they can sign in and change the password before the legitimate user can reset it. In this case, the legitimate user's recovery link would be sent to the attacker's inbox. This is why:

- **Account disablement** is available to administrators (`PATCH /auth/v1/user` with `disabled: true`), which immediately revokes all sessions and prevents sign-in.
- **MFA** adds a second factor that the attacker would also need to bypass, even with the password and email access.
- **Session revocation** via the admin API can kill all active sessions immediately.

### Recovery codes and MFA

If MFA is enabled, a password reset via the recovery flow **does not require the MFA codes**. The recovery link is the single factor — possession of the email inbox. After the reset, the new session is issued at `aal1` (no MFA), even if the user previously had `aal2`. The user must then complete MFA re-enrollment if they want to restore the `aal2` assurance level.

<Note>
This is a deliberate trade-off: if the email inbox is compromised, requiring MFA codes would make recovery impossible for the legitimate user (who also lost their email access). The recovery flow prioritizes recoverability over assurance. After resetting, the user should re-enroll MFA immediately.
</Note>

## Recovery link lifetime and limits

| Property | Value |
| --- | --- |
| Token lifetime | **1 hour** (`LIFETIMES["recovery"] = 3600`) |
| Single-use | Yes — consumed on first use |
| Rate limit | 10 requests per 60 seconds per IP |
| Redirect support | Yes — `redirect_to` to an allowed URL |
| Password policy enforced | Yes — the new password must satisfy `password_policy` |
| Sessions revoked | Yes — all other sessions are terminated |
| Lockout cleared | Yes — `failed_logins` and `locked_until` reset |

## Admin-initiated password resets

An administrator can reset a user's password through the Platform API:

```bash
curl -X PATCH "$STUDIO/studio/api/platform/projects/acme/envs/production/users/8" \
  -H "content-type: application/json" -H "X-XSRF-TOKEN: $XSRF" -b cookies.txt \
  -d '{ "password": "temp-password-123", "password_policy": "strict" }'
```

Wait — actually, the admin API uses `PATCH` on the user resource with a `password` field, which calls `check_password_policy` and `set_password` directly. This does **not** send a recovery email and does **not** revoke existing sessions (unlike the user-initiated recovery flow). An admin resetting a password should also call `POST /projects/{project}/envs/{env}/users/{user_id}/sessions/revoke` if they want to sign the user out.

Admin-initiated resets also don't emit the `user.password_reset` event in the same way — they emit `user.updated` instead. The admin can force a password reset and then revoke all sessions to achieve the same security outcome as the user-initiated flow.

## Recovery event logging

Every step of the recovery flow is logged:

| Event | `kind` | When |
| --- | --- | --- |
| Recovery requested | `recovery_requested` | `POST /auth/v1/recover` is called (even if the email doesn't exist). |
| Password reset | `password_reset` | After a successful reset, in `complete`. |
| Sign-in after reset | `sign_in` | After `start_session` completes the reset flow. |
| Session reuse detected | `session.reuse_detected` | If the refresh token from the post-reset session is reused. |

These events appear in the admin events API and the audit log.
