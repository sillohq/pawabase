Password recovery allows users to reset their password when they have forgotten it. The flow involves requesting a recovery code, receiving it via email, and then using that code to set a new password. Throughout the process, Pawabase enforces rate limiting, validates the recovery token, and ensures that only the legitimate user can reset their password.

Password recovery is distinct from email verification and magic links — it is specifically designed for users who already have an account but cannot remember their password. The recovery flow uses a different token type (`OneTimeToken` with `kind: "recover"`) than verification (`OTP` with `kind: "verify"`).

## How password recovery works

The password recovery flow consists of three main steps: requesting a recovery token, receiving the email, and completing the password reset.

<Steps>
  <Step title="User requests recovery">
    The user submits their email address to the `/recover` endpoint. Pawabase validates the email format and checks if the user exists.
  </Step>
  <Step title="Recovery token is created and sent">
    Pawabase creates a `OneTimeToken` record with `kind: "recover"` and sends an email containing a recovery link with the token.
  </Step>
  <Step title="User submits new password">
    The user clicks the recovery link and submits a new password through the `complete` handler. Pawabase validates the token and updates the password hash.
  </Step>
  <Step title="All sessions are revoked">
    After the password is changed, all existing sessions for the user are revoked. The user must sign in again with their new password.
  </Step>
</Steps>

### The `/recover` endpoint

The `/recover` endpoint initiates the recovery process:

```bash
curl -X POST "$GW/auth/v1/recover" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "email": "user@example.com"
  }'
```

The endpoint:

1. Validates the email format.
2. Checks if a user with that email exists. If not, returns `404 user not found`.
3. Checks rate limits (per-IP, per-user, and per-email).
4. Creates a `OneTimeToken` with `kind: "recover"`.
5. Sends a recovery email containing the recovery URL.
6. Returns `200 recovery email sent` (regardless of whether the user exists — this is a security measure to prevent email enumeration).

<Warning>
The `/recover` endpoint always returns a success response, even if the email does not exist. This prevents attackers from discovering valid email addresses by observing different responses. The endpoint only creates a token and sends an email if the user exists — but the response is always the same.
</Warning>

### Rate limiting on `/recover`

The `/recover` endpoint is heavily rate-limited to prevent abuse:

- **Per-IP rate limiting**: Maximum 5 recovery requests per 60 seconds from a single IP address.
- **Per-user rate limiting**: Maximum 3 recovery requests per hour for the same user.
- **Per-email rate limiting**: Minimum 60 seconds between consecutive recovery requests for the same email.

If any limit is exceeded, the endpoint returns `429 rate limit exceeded`. The rate limits are enforced by the rate limiting middleware which checks the IP address, user ID, and email address against the rate limit counters.

### The `recovery_token_ttl`

Recovery tokens have a configurable time-to-live. The default is 15 minutes, but this can be changed in the environment configuration through `recovery_token_ttl`. The `ttl` is set when the `OneTimeToken` is created and the token expires at `created_at + recovery_token_ttl`.

If a recovery token expires before the user completes the reset, the token is invalid and the user must request a new one. The expired token remains in the database as a record (but with `used = True` or `expired = True`).

## The `OneTimeToken` model

Recovery tokens are stored in the `OneTimeToken` table:

```python
class OneTimeToken(BaseModel):
    id: UUID = Field(default_factory=uuid4, primary_key=True)
    email: str = Field(index=True)
    kind: str  # "recover", "verify", or "magic_link"
    token: str  # The one-time token string (random, unguessable)
    token_hash: str  # SHA-256 hash of the token for secure storage
    ttl: datetime  # When the token expires
    used: bool = False
    created_at: datetime = Field(default_factory=datetime.now(UTC))
    expires_at: datetime = Field(default_factory=datetime.now(UTC))
```

The `OneTimeToken` model is shared across verification, recovery, and magic link flows. The `kind` field distinguishes the purpose:

- **`"recover"`**: Password recovery token. Used with the `/recover/complete` endpoint.
- **`"verify"`**: Email verification token. Used with the `/verify/complete` endpoint.
- **`"magic_link"`**: Magic link token. Used with the `/magic-link/complete` endpoint.

The `token` field contains the raw token string (e.g., a random alphanumeric string). The `token_hash` field contains the SHA-256 hash of the token. When validating a token, the server hashes the submitted token and compares it against `token_hash`. The raw token is never stored persistently — only the hash is stored.

### Why hash the token?

Storing only the hash of the token (not the raw token) is a critical security measure:

1. **Database compromise**: If the database is compromised, the attacker only gets hashes — not the actual tokens. They cannot use the hashes to validate tokens without knowing the original values.
2. **Brute-force protection**: Even if an attacker gets the hash, they cannot reverse it to get the original token (assuming a strong hash function like SHA-256 and a sufficiently random token).
3. **Token reuse prevention**: The hash allows the server to check if a token has been used without exposing the raw token.

## The `complete` handler

The `complete` handler validates the recovery token and allows the user to set a new password:

```bash
curl -X POST "$GW/auth/v1/recover/complete" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "token": "rft_recover_abc123...",
    "new_password": "NewSecurePassword123!"
  }'
```

The `complete` handler:

1. Hashes the submitted token and looks up the matching `OneTimeToken` record.
2. Checks if the token exists. If not, returns `400 invalid recovery token`.
3. Checks if the token has expired (`ttl` passed). If so, returns `400 recovery token expired`.
4. Checks if the token has already been used (`used == True`). If so, returns `400 recovery token already used`.
5. Validates the new password against the password policy (minimum length, complexity requirements, etc.).
6. Updates the user's password hash.
7. Marks the `OneTimeToken` as `used = True`.
8. Resets `failed_logins` to `0` on the `AuthUser` record.
9. Revokes all existing sessions for the user (see [Session revocation →](#session-revocation)).
10. Emits a `user.password_changed` event.
11. Returns the new access token and refresh token.

<Note>
After a successful password recovery, the user's `failed_logins` counter is reset to `0`. This is important because the password recovery flow is often triggered after multiple failed login attempts, and the failed login counter should not persist after the password is changed.
</Note>

### Session revocation after password change

When a user changes their password (through recovery or through the normal password change flow), **all existing sessions are revoked**. This is a security measure to prevent an attacker who may have obtained the user's password from continuing to access the account.

The session revocation is handled by the `revoke_all` function:

```python
async def revoke_all(config: AuthConfig, user_id: UUID, env_id: UUID) -> None:
    sessions = await SessionInfo.filter(user_id=user_id, env_id=env_id, revoked=False)
    for session in sessions:
        session.revoked = True
        session.revoked_at = datetime.now(UTC)
        await session.save()
```

Every `SessionInfo` row for the user is marked as `revoked = True` and `revoked_at = now()`. After revocation, any refresh token associated with these sessions will be rejected with `401 session revoked`. The user must sign in again with their new password to create new sessions.

### The `new_password` endpoint

The `new_password` endpoint allows users to change their password directly without going through the recovery flow:

```bash
curl -X POST "$GW/auth/v1/new-password" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "current_password": "OldPassword123!",
    "new_password": "NewSecurePassword123!"
  }'
```

The `new_password` endpoint:

1. Validates the current password against the stored hash.
2. Validates the new password against the password policy.
3. Updates the password hash.
4. Resets `failed_logins` to `0`.
5. Revokes all existing sessions.
6. Emits a `user.password_changed` event.
7. Returns the new access token and refresh token.

The `new_password` endpoint requires the user to provide their current password. This is different from the recovery flow, which only requires the recovery token. The `new_password` endpoint is for users who know their current password and want to change it — not for users who have forgotten it.

<Warning>
The `new_password` endpoint does not accept a `current_password` of `null` or empty string. The current password must match the stored hash. If the current password is incorrect, the endpoint returns `401 invalid password`.
</Warning>

## Rate limiting throughout the recovery flow

Rate limiting protects every step of the recovery process:

<CardGroup cols={2}>
  <Card title="`/recover` rate limits" icon="clock">5 requests per 60 seconds per IP, 3 per hour per user.</Card>
  <Card title="`/recover/complete` rate limits" icon="shield">10 attempts per 60 seconds per token, 3 per email per hour.</Card>
</CardGroup>

### `/recover/complete` rate limiting

The `complete` handler has its own rate limiting to prevent brute-force attacks on recovery tokens:

- **Per-token**: Maximum 10 attempts per 60 seconds for the same token.
- **Per-email**: Maximum 3 recovery completions per hour for the same email.
- **Per-IP**: Maximum 20 recovery completions per 60 seconds from a single IP.

If any limit is exceeded, the `complete` handler returns `429 rate limit exceeded`.

### Why rate limit the complete endpoint?

Recovery tokens are long, random strings that are theoretically unguessable. However, rate limiting is still important because:

1. **Token leakage**: If a recovery token is leaked (e.g., through browser history, email forwarding, or a compromised email account), an attacker could attempt to use it. Rate limiting limits how many times they can try.
2. **Brute-force protection**: Even with strong random tokens, rate limiting provides an additional layer of protection against systematic attacks.
3. **Email bombing prevention**: Without rate limiting, an attacker could use the recovery flow to send recovery emails to many addresses, causing email bombing.

## The `recovery_token_ttl` configuration

The `recovery_token_ttl` is configured at the environment level. It determines how long a recovery token is valid:

```python
# Environment configuration:
recovery_token_ttl = timedelta(minutes=15)  # Default
```

The TTL affects the flow as follows:

- When a recovery token is created, `expires_at` is set to `now() + recovery_token_ttl`.
- When the `complete` handler validates the token, it checks `expires_at > now()`.
- If the token has expired, the `complete` handler returns `400 recovery token expired`.
- The user must then request a new recovery token through `/recover`.

### Choosing the right TTL

The TTL is a trade-off between security and usability:

| TTL | Security | Usability |
| --- | --- | --- |
| Short (5-10 minutes) | More secure — less time for an attacker to use a leaked token. | Less convenient — the user must request a new token more often. |
| Long (30-60 minutes) | Less secure — more time for an attacker to use a leaked token. | More convenient — the user has more time to complete the reset. |
| Indefinite | Insecure — tokens never expire, increasing the attack window. | Most convenient — but should never be used. |

The recommended TTL is 15 minutes. This provides a reasonable balance between security and usability.

## Security model

Password recovery has a well-defined security model that protects against common attacks:

### Credential stuffing

The recovery flow is protected against credential stuffing through rate limiting and the one-time token mechanism. Even if an attacker has a list of email/password pairs, they cannot use the recovery flow to change passwords without first obtaining the recovery token (which is sent to the email).

### Brute-force protection

Recovery tokens are cryptographically random strings (typically 32+ characters). Brute-forcing a recovery token is computationally infeasible. Additionally, rate limiting on both `/recover` and `/recover/complete` provides further protection.

### Account enumeration

The `/recover` endpoint always returns a success response regardless of whether the email exists. This prevents attackers from discovering valid email addresses by observing different responses.

### Token leakage

Recovery tokens are sent via email, which introduces the risk of token leakage through email forwarding, compromised email accounts, or email logging. The one-time use nature of recovery tokens mitigates this risk — even if a token is leaked, it can only be used once before being invalidated.

### Session revocation

After a password change, all existing sessions are revoked. This prevents an attacker who may have obtained the old password from continuing to access the account with existing sessions.

## Common mistakes

<AccordionGroup>
  <Accordion title="Returning different responses for existing vs non-existing emails">
    If `/recover` returns `404` for non-existing emails, attackers can enumerate valid email addresses. Always return the same success response regardless of whether the email exists.
  </Accordion>
  <Accordion title="Not revoking sessions after password change">
    If existing sessions are not revoked after a password change, an attacker who obtained the old password can continue to access the account. Always revoke all sessions after a password change.
  </Accordion>
  <Accordion title="Not resetting `failed_logins`">
    If `failed_logins` is not reset after a password change, the user may still be locked out even after successfully changing their password. Always reset `failed_logins` to `0`.
  </Accordion>
  <Accordion title="Storing raw recovery tokens in the database">
    Only store the hash of the recovery token. Storing the raw token creates a vulnerability — if the database is compromised, all recovery tokens are exposed.
  </Accordion>
  <Accordion title="Not checking the `used` flag">
    If the `complete` handler doesn't check `used == True`, a recovery token could be used multiple times. Always mark the token as used after a successful recovery.
  </Accordion>
  <Accordion title="Ignoring the `ttl` check">
    If the `complete` handler doesn't check if the token has expired, old recovery tokens could still be accepted. Always check `expires_at`.
  </Accordion>
</AccordionGroup>
