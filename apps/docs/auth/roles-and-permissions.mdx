Pawabase's role-based access control is not a bespoke Akountz feature — it's Sillo's own generic permission system (`Permission`, `Group`, `UserGroup`), which Akountz scopes so that many project environments can share one database without their roles colliding. There is no `Role` or `RoleAssignment` model, and no separate policy-expression syntax for permissions: a "role" in this documentation is simply a named `Group` of `Permission`s.

## The real models

Sillo's permission system lives outside Akountz entirely (`sillo.permissions`); Akountz's own contribution is `app/rbac.py`, a thin scoping layer over three of Sillo's models:

| Model | What it is |
| --- | --- |
| `Permission` | A named permission string, e.g. `reports.publish`. Globally unique across the whole Sillo database. |
| `Group` | A named collection of permissions — what this documentation calls a **role**. Also globally unique by name. |
| `UserGroup` | The join row: one user belongs to one group. |

Because `Permission` and `Group` names are unique across the *entire* database — and Akountz serves every project's every environment out of one database — a role literally named `editor` cannot exist twice. Akountz solves this by storing every name with its environment baked in as a prefix:

```python
def scoped(project: str, env: str, name: str) -> str:
    return f"{project}/{env}/{name}"
```

So the role you create as `editor` in Studio for `acme/production` is stored as `Group(name="acme/production/editor")`, and the permission `reports.publish` becomes `Permission(name="acme/production/reports.publish")`. Every function in `app/rbac.py` strips the prefix back off before returning anything to a caller:

```python
def _strip(project: str, env: str, names: list[str]) -> list[str]:
    prefix = f"{project}/{env}/"
    return sorted({name[len(prefix):] for name in names if name.startswith(prefix)})
```

<Warning>
There is no `Role` model and no `RoleAssignment` model anywhere in this codebase. "Role" is purely a documentation term for a `Group` — Sillo's own generic grouping primitive, which Akountz happens to use for authorization roles but which carries no role-specific fields of its own beyond `name`, `description`, and its members.
</Warning>

## Defining a role

```python
async def define_role(
    project: str, env: str, name: str, *,
    description: str = "",
    permissions: list[str] | None = None,
) -> Group:
```

`define_role` is idempotent — calling it again with a different `permissions` list *reconciles* the group's permissions to match exactly what you passed, adding what's missing and removing what's no longer listed:

```python
group = await Group.get_or_create(scoped(project, env, name), description)
if permissions is not None:
    current = set(await group.get_permissions())
    wanted = {scoped(project, env, p) for p in permissions}
    for perm in wanted - current:
        await Permission.define(perm)
    if wanted - current:
        await group.add_permissions(*(wanted - current))
    if current - wanted:
        await group.remove_permissions(*(current - wanted))
```

Any permission named in `permissions` that doesn't exist yet is defined automatically (`Permission.define(perm)`) — you don't need a separate "create this permission" step before referencing it in a role. Passing `permissions=None` (the default when calling `define_role` without that argument) leaves the group's existing permissions untouched; passing `permissions=[]` explicitly clears them all.

Through the admin API, this is exposed as an idempotent `PUT`:

```bash
curl -X PUT "$STUDIO/internal/v1/projects/acme/envs/production/roles" \
  -H "Authorization: Bearer $SERVICE_TOKEN" -H "content-type: application/json" \
  -d '{
    "name": "editor",
    "description": "Can create and publish content",
    "permissions": ["posts.create", "posts.edit", "posts.publish"]
  }'
```

```json
{
  "name": "editor",
  "description": "Can create and publish content",
  "permissions": ["posts.create", "posts.edit", "posts.publish"],
  "members": 0
}
```

Role names are validated against `^[a-z][a-z0-9_:-]{0,62}$` at the admin API layer — lowercase, starting with a letter, up to 63 characters, allowing digits, underscores, colons, and hyphens. Permission strings themselves have no format constraint in Akountz beyond being non-empty; the convention used throughout this documentation and the built-in `admin` role is dotted-path style (`reports.publish`, `users.disable`), but nothing enforces that shape.

## Listing, assigning, and revoking

```python
async def list_roles(project: str, env: str) -> list[dict]:
    ...  # [{"name": ..., "description": ..., "permissions": [...], "members": int}, ...]

async def assign_role(user: AuthUser, name: str) -> None:
    """Creates the role (with no permissions) if it doesn't exist yet, then adds the user."""

async def revoke_role(user: AuthUser, name: str) -> None:
    """A no-op if the user isn't in the role, or the role doesn't exist."""

async def roles_of(user: AuthUser) -> list[str]:
    """The names of every group this user belongs to, unprefixed."""

async def delete_role(project: str, env: str, name: str) -> bool:
    """Deletes the group and every UserGroup membership row for it. Returns False if it didn't exist."""
```

Notice that `assign_role` silently creates the role if it doesn't already exist, with no permissions attached — a convenient default for `default_roles` in the auth configuration (see [below](#default-roles-on-sign-up)), but worth knowing so a typo in a role name doesn't raise an error; it just quietly creates an empty role.

```bash
# Admin API
curl -X PATCH "$STUDIO/internal/v1/projects/acme/envs/production/users/482" \
  -H "Authorization: Bearer $SERVICE_TOKEN" -H "content-type: application/json" \
  -d '{"roles": ["editor", "billing_viewer"]}'
```

The admin user-update endpoint reconciles a user's full role set the same way `define_role` reconciles a group's permissions — it diffs the requested `roles` list against `rbac.roles_of(user)` and assigns/revokes the difference, rather than requiring one call per role.

## Direct permission grants

Separately from roles, a user can hold permissions directly, bypassing any group:

```python
async def grant(user: AuthUser, *permissions: str) -> None:
    for perm in permissions:
        await Permission.define(scoped(user.project, user.env, perm))
    await Permission.assign(user, *(scoped(user.project, user.env, p) for p in permissions))

async def revoke(user: AuthUser, *permissions: str) -> None:
    await Permission.revoke(user, *(scoped(user.project, user.env, p) for p in permissions))
```

```bash
curl -X POST "$STUDIO/internal/v1/projects/acme/envs/production/users/482/permissions" \
  -H "Authorization: Bearer $SERVICE_TOKEN" -H "content-type: application/json" \
  -d '{"permissions": ["reports.export"]}'
```

A user's *effective* permissions are the union of their direct grants and every permission held by every group they belong to:

```python
async def permissions_of(user: AuthUser) -> list[str]:
    direct = await Permission.of(user)
    via_groups: list[str] = []
    for group in await Group.of_user(user):
        via_groups.extend(await group.get_permissions())
    return _strip(user.project, user.env, [*direct, *via_groups])
```

This is the exact list that ends up as the `perms` claim on an access token (see [Tokens and sessions](/auth/tokens-and-sessions#claims-on-the-access-token)) — resolved fresh at every sign-in and every refresh, never cached on the user row.

## No built-in hierarchy, and what `"*"` means

Roles are flat: there is no concept of one role inheriting another's permissions. If your product needs "admin implies editor implies viewer," you either list every underlying permission explicitly in the `admin` role, or check multiple roles in a policy condition (`{"role": ["admin", "editor"]}` matches either).

The one built-in exception is a **wildcard permission**, `"*"`, checked explicitly wherever `Permission.assign`/`Permission.of` results are consulted — for example, the platform's bootstrap-created `admin` role (see [Overview → bootstrapping the first operator](/auth/overview#bootstrapping-the-first-operator)) is defined with `permissions=["*"]`, and `Principal.has_permission` treats it as matching any permission string:

```python
def has_permission(self, permission: str) -> bool:
    if self.kind in ("service", "operator") and "admin" in self.roles:
        return True
    perms = self.permissions
    return permission in perms or "*" in perms
```

Use `"*"` sparingly — it's meant for a small number of fully trusted operator/admin roles, not as a general-purpose "give this role everything" shortcut for project-level roles.

## How roles and permissions reach a policy

Neither `roles_of` nor `permissions_of` is called from inside a policy condition directly — they're resolved once, at token-issuance time, and baked onto the access token as `roles` and `perms` claims (see [`issue_user_token`](/auth/tokens-and-sessions#issue_user_token)). `Principal.as_policy_context()` then exposes them under `$auth`:

```python
def as_policy_context(self) -> dict[str, Any]:
    return {
        "authenticated": True,
        "kind": self.kind,
        "roles": self.roles,
        "permissions": self.permissions,
        ...
    }
```

From there, the real [condition language](/policies/conditions) — plain JSON, no expression syntax, no `has_permission()` function call — has two purpose-built shorthands:

```json
{ "role": "admin" }
{ "role": ["admin", "editor"] }        // any of these
{ "permission": "reports.publish" }
{ "permission": ["reports.publish", "reports.export"] }   // all of these
```

`role` expands to an `any` of `contains($auth.roles, "<name>")` checks; `permission` expands to an `all` of `contains($auth.permissions, "<name>")` checks (a single-element list behaves the same as a bare string). Both are synchronous, in-memory checks against the token's own claims — there is no database round trip and no async `has_permission()` call happening at policy-evaluation time, because the roles and permissions were already resolved once, when the token was minted.

```json
{ "any": [
  { "role": "admin" },
  { "all": [ { "role": "editor" }, { "owner": "author_id" } ] }
] }
```

"Admins may do this to anything; editors only to content they own." See [the condition language](/policies/conditions#shorthands) and [shorthands reference](/policies/shorthands) for the complete shorthand catalog, and [recipes](/policies/recipes) for more role-and-ownership patterns.

<Warning>
There is no `has_permission()` function inside a policy condition, and conditions are never written in TOML — the entire condition language is plain JSON with the five forms (boolean, group, comparison, check, shorthand) documented on [the condition language](/policies/conditions) page. Anything describing a `has_permission(...)` call or a `[policy] expression = "..."` TOML block does not match how Pawabase policies actually work.
</Warning>

## Default roles on sign-up

The environment's `default_roles` configuration field (see [Configuration → `default_roles`](/auth/configuration#default_roles)) is a list of role names every newly created account is automatically assigned to, via exactly `rbac.assign_role`:

```python
for role in config.default_roles:
    await rbac.assign_role(user, role)
```

Because `assign_role` creates the role if it's missing (with no permissions), a typo in `default_roles` doesn't raise a sign-up error — it silently creates an empty, useless role and assigns everyone to it. Verify `default_roles` entries against `GET /projects/{project}/envs/{env}/roles` after changing them.

## Real scenarios

### Feature gating by role

A SaaS with `free`, `pro`, and `enterprise` tiers modeled as roles, each carrying the permissions for the features that tier unlocks:

```bash
curl -X PUT ".../roles" -d '{"name": "pro", "permissions": ["exports.csv", "exports.pdf", "api.access"]}'
curl -X PUT ".../roles" -d '{"name": "enterprise", "permissions": ["exports.csv", "exports.pdf", "api.access", "sso.configure", "audit.export"]}'
```

Because there's no inheritance, `enterprise` has to restate every permission `pro` has plus its own — there's no shorthand for "everything `pro` has, plus." Keeping the permission lists for related tiers generated from one place in your own provisioning script (rather than hand-maintained in two separate `PUT` bodies) avoids drift between them.

### Combining role and ownership checks

"Editors may edit anything; authors may only edit their own drafts":

```json
{ "any": [
  { "role": "editor" },
  { "all": [
    { "role": "author" },
    { "owner": "author_id" },
    { "eq": ["$record.status", "draft"] }
  ] }
] }
```

### Scoped service access

A background service that only needs read access to reports, using a permission rather than a role, combined with the `service` shorthand so an ordinary staff member with the same permission string doesn't unintentionally satisfy a rule meant for machine callers:

```json
{ "all": [ { "service": true }, { "permission": "reports.read" } ] }
```

## Common mistakes

<AccordionGroup>
  <Accordion title="Looking for a Role or RoleAssignment model">
    They don't exist. RBAC is `Permission`/`Group`/`UserGroup` — Sillo's generic primitives — with every name prefixed by `project/env/` so one database can serve every environment without collisions.
  </Accordion>
  <Accordion title="Passing an unprefixed name straight to Sillo's Group/Permission APIs">
    Always go through `app/rbac.py`'s functions (`define_role`, `assign_role`, `grant`, …), which apply and strip the `project/env/` prefix consistently. Calling Sillo's `Group`/`Permission` models directly bypasses environment scoping and risks colliding with another project's role of the same name.
  </Accordion>
  <Accordion title="Expecting role inheritance">
    There is none. `enterprise` does not automatically include everything `pro` has — list every permission explicitly, or check multiple roles with `{"role": ["pro", "enterprise"]}` in policies that should apply to both tiers.
  </Accordion>
  <Accordion title="Expecting a role assignment to update an already-issued token">
    Roles and permissions are baked onto the access token at issuance and only re-read on the next refresh (see [Tokens and sessions → what changes at refresh, not immediately](/auth/tokens-and-sessions#what-changes-at-refresh-not-immediately)). Revoking a role doesn't invalidate tokens already handed out; it changes what the *next* refresh or sign-in produces.
  </Accordion>
  <Accordion title="Writing a permission check as a TOML expression or calling has_permission(...)">
    Neither exists in this system. Every condition, including role and permission checks, is JSON using the shorthands `{"role": ...}` and `{"permission": ...}` — see [the condition language](/policies/conditions).
  </Accordion>
</AccordionGroup>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| A role assigned through the admin API doesn't show up on the user's next request | The user's current access token was issued before the assignment. | Have the client refresh; roles are re-resolved on every refresh, not mid-token. |
| `default_roles` created a role with no permissions | A typo in the role name in the environment's auth config. | Check `GET .../roles` for an unexpectedly empty role and fix the spelling. |
| A permission check always fails even though the role clearly has it | The permission or role name wasn't scoped consistently (mixed casing, extra whitespace, wrong environment). | Compare the exact string in `GET .../roles` against what the policy condition or `grant()` call uses. |
| Deleting a role doesn't revoke access immediately | Same as above — claims already on an issued token stay valid until it expires or is refreshed. | Revoke sessions explicitly (`POST .../users/{id}/sessions/revoke`) if immediate effect is required. |
