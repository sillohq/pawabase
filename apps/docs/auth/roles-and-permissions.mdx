Roles and permissions form the access control layer of Pawabase's authentication system. Roles group permissions together, and permissions define what actions a user can perform. Pawabase provides a flexible role-based access control (RBAC) system with global and organization-scoped roles.

The RBAC system is built on three models: `Role`, `RoleAssignment`, and the `Permissions` array. Roles are assigned to users through `RoleAssignment` records, and the resulting permissions are included in the user's access token claims. The `has_permission` function in the policy engine resolves permissions from roles in real-time.

## The `Role` model

The `Role` model defines a set of permissions that can be assigned to users:

```python
class Role(BaseModel):
    id: UUID = Field(default_factory=uuid4, primary_key=True)
    name: str = Field(unique=True)  # e.g., "admin", "editor", "member"
    permissions: list[str] = Field(default_factory=list)  # e.g., ["user:read", "user:write"]
    scope: str = "global"  # "global" or "org"
    description: str | None = None
    created_at: datetime = Field(default_factory=datetime.now(UTC))
    updated_at: datetime = Field(default_factory=datetime.now(UTC))
```

The `Role` model stores:

- **`name`**: The unique name of the role (e.g., `"admin"`, `"editor"`, `"member"`). Role names are unique across the environment.
- **`permissions`**: An array of permission strings. Each permission string follows the format `resource:action` (e.g., `"user:read"`, `"user:write"`, `"org:delete"`).
- **`scope`**: The scope of the role — `"global"` or `"org"`. Global roles apply to all organizations. Organization-scoped roles apply only within a specific organization.
- **`description`**: Optional description of the role's purpose.

### Permission format

Permissions follow a consistent `resource:action` format:

| Permission | Description |
| --- | --- |
| `user:read` | Read user information. |
| `user:write` | Modify user information. |
| `user:delete` | Delete a user account. |
| `org:read` | Read organization information. |
| `org:write` | Modify organization information. |
| `org:delete` | Delete an organization. |
| `session:revoke` | Revoke user sessions. |
| `mfa:reset` | Reset MFA for a user. |
| `role:assign` | Assign roles to users. |
| `role:revoke` | Revoke roles from users. |

The permission strings are defined by the application developer. Pawabase does not impose a fixed set of permissions — the `permissions` array is arbitrary and defined by the application.

### Role scope: `global` vs `org`

Roles have two scopes:

1. **`global`**: Global roles apply to the user across all organizations and the personal context. A user with a global `"admin"` role is an admin everywhere.
2. **`org`**: Organization-scoped roles apply only within a specific organization. A user with an org-scoped `"admin"` role is only an admin in that organization.

```python
# Global role — applies everywhere
Role(name="admin", permissions=["user:read", "user:write"], scope="global")

# Org-scoped role — applies only within the organization
Role(name="org_admin", permissions=["org:read", "org:write"], scope="org")
```

### Default roles

The `default_roles` configuration defines which roles are automatically assigned to new users:

```toml
[auth]
default_roles = ["member"]
```

When a new user signs up, they are automatically assigned all roles listed in `default_roles`. This is configured at the environment level.

## The `RoleAssignment` model

Role assignments link users to roles:

```python
class RoleAssignment(BaseModel):
    id: UUID = Field(default_factory=uuid4, primary_key=True)
    user_id: UUID = Field(foreign_key="auth_user.id")
    role_id: UUID = Field(foreign_key="role.id")
    scope: str = "global"  # "global" or "org"
    org_id: UUID | None = None  # Only set when scope is "org"
    assigned_by: UUID | None = None  # The user who assigned the role
    assigned_at: datetime = Field(default_factory=datetime.now(UTC))
    revoked_at: datetime | None = None
```

The `RoleAssignment` model tracks:

- **`user_id`**: The user who has been assigned the role.
- **`role_id`**: The role that was assigned.
- **`scope`**: The scope of the assignment (`"global"` or `"org"`).
- **`org_id`**: The organization ID if the assignment is org-scoped. `null` for global assignments.
- **`assigned_by`**: The user ID of the administrator who assigned the role. `null` for system-assigned roles (like `default_roles`).
- **`assigned_at`**: When the role was assigned.
- **`revoked_at`**: When the role was revoked. If `null`, the role is still active.

### Multiple assignments per user

A user can have multiple `RoleAssignment` records — one for each role assigned to them. This allows a user to have multiple roles simultaneously. For example, a user could be both an `"admin"` (global) and an `"org_admin"` (org-scoped for `acme-hq`).

The `has_permission` function aggregates permissions from all active role assignments:

```python
async def has_permission(principal: Principal, permission: str) -> bool:
    # Check all active role assignments
    for assignment in await RoleAssignment.filter(
        user_id=principal.user_id,
        revoked_at=None
    ):
        role = await Role.get(id=assignment.role_id)
        if permission in role.permissions:
            return True
    return False
```

## `assign_role` and `revoke_role`

Roles are assigned and revoked through the `assign_role` and `revoke_role` functions:

### `assign_role`

```python
async def assign_role(
    config: AuthConfig,
    *,
    user_id: UUID,
    role_name: str,
    scope: str = "global",
    org_id: UUID | None = None,
    assigned_by: UUID | None = None,
) -> RoleAssignment:
    role = await Role.get(name=role_name)
    assignment = RoleAssignment.create(
        user_id=user_id,
        role_id=role.id,
        scope=scope,
        org_id=org_id,
        assigned_by=assigned_by,
    )
    # Emit role.assigned event
    await log_event(...)
    return assignment
```

The `assign_role` function:

1. Looks up the `Role` by name.
2. Creates a new `RoleAssignment` record.
3. Sets `assigned_by` if provided.
4. Emits a `role.assigned` event.
5. Returns the `RoleAssignment` record.

### `revoke_role`

```python
async def revoke_role(
    config: AuthConfig,
    *,
    user_id: UUID,
    role_name: str,
    scope: str = "global",
    org_id: UUID | None = None,
) -> None:
    assignment = await RoleAssignment.filter(
        user_id=user_id,
        role_name=role_name,
        scope=scope,
        org_id=org_id,
        revoked_at=None
    ).first()
    if assignment:
        assignment.revoked_at = datetime.now(UTC)
        await assignment.save()
        # Emit role.revoked event
        await log_event(...)
```

The `revoke_role` function:

1. Looks up the active `RoleAssignment` for the user, role, scope, and org.
2. Sets `revoked_at = now()` to mark the assignment as revoked.
3. Emits a `role.revoked` event.

### Admin API for role management

Administrators can assign and revoke roles through the admin API:

```bash
# Assign a role
curl -X POST "$GW/projects/my-project/envs/prod/users/{user_id}/roles" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "role": "admin",
    "scope": "global"
  }'

# Revoke a role
curl -X DELETE "$GW/projects/my-project/envs/prod/users/{user_id}/roles" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "role": "admin",
    "scope": "global"
  }'
```

The admin API delegates to `assign_role` and `revoke_role` internally. The service key must have the `role_manage` permission.

## How roles appear in access tokens

The `roles` claim in the access token is constructed from the user's active role assignments:

```python
def build_role_names(config: AuthConfig, user_id: UUID) -> list[str]:
    roles = []
    assignments = await RoleAssignment.filter(
        user_id=user_id,
        revoked_at=None
    )
    for assignment in assignments:
        role = await Role.get(id=assignment.role_id)
        roles.append(role.name)
    return roles
```

The `build_role_names` function queries all active `RoleAssignment` records for the user, looks up each `Role`, and collects the role names. These names are stored in the `roles` claim of the access token.

### Role names in the `Principal`

The `Principal` constructor sets `self.roles` and adds it to `self.claims`:

```python
self.roles = token.get("roles", [])
self.claims["roles"] = self.roles
```

So `Principal.roles` and `$auth.claims.roles` are the same array of role names. The `roles` claim is what `$auth.claims.roles` resolves to in policies.

### Role names on refresh

When a token is refreshed, the `roles` claim is re-read from the database. This means:

1. If a role is revoked, it will no longer appear in the `roles` claim on the next refresh.
2. If a new role is assigned, it will appear in the `roles` claim on the next refresh.
3. The current access token continues to carry the old `roles` claim until it expires and is refreshed.

<Note>
Role changes are reflected on the next refresh — not immediately. The current access token continues to carry the old roles until it expires. This is by design — refreshing the token database on every request would be prohibitively expensive.
</Note>

## The `has_permission` function

The `has_permission` function checks whether a user has a specific permission:

```python
async def has_permission(principal: Principal, permission: str) -> bool:
    # Check all active role assignments
    assignments = await RoleAssignment.filter(
        user_id=principal.user_id,
        revoked_at=None
    )
    for assignment in assignments:
        role = await Role.get(id=assignment.role_id)
        if permission in role.permissions:
            return True
    return False
```

The function iterates through all active `RoleAssignment` records for the user, looks up each `Role`, and checks whether the requested permission is in the `Role.permissions` array.

### Using `has_permission` in policies

In policy expressions, `has_permission` is called like this:

```toml
expression = "has_permission($auth, 'user:delete')"
```

The `has_permission` function receives the `Principal` object and the permission string. It returns `true` if the user has the permission, `false` otherwise.

### How `has_permission` is evaluated

The policy engine evaluates `has_permission` at request time:

1. The policy expression references `has_permission($auth, 'permission')`.
2. The policy engine extracts the `Principal` from the request's access token.
3. The `has_permission` function queries the database for the user's active role assignments.
4. For each assignment, the `Role` is looked up and the permissions are checked.
5. If any matching permission is found, `true` is returned. Otherwise, `false`.

<Warning>
`has_permission` performs a database query on every call. For high-traffic endpoints, this can create a performance bottleneck. Consider caching permission results or using role-based checks (`$auth.claims.roles contains ...`) instead.
</Warning>

### Performance optimization

For performance-critical endpoints, consider these optimization strategies:

1. **Cache role assignments**: Cache the result of `has_permission` for a short duration (e.g., 60 seconds).
2. **Use role checks instead**: `$auth.claims.roles contains 'admin'` is faster than `has_permission($auth, 'user:delete')` because it doesn't require a database query.
3. **Pre-compute permissions**: At sign-in time, pre-compute the user's permissions and store them in the token claims (in `app_metadata`). This avoids database lookups on every request.
4. **Batch permission checks**: If multiple permissions need to be checked, batch them into a single query instead of multiple `has_permission` calls.

## Permission checking performance

Permission checking performance is a critical consideration for production applications:

### Database query cost

Each call to `has_permission` performs at least one database query to fetch the user's role assignments and another query to fetch each role. For a user with many roles, this can result in multiple queries per request.

| Number of roles | Queries per `has_permission` call |
| --- | --- |
| 1 | 2 (assignment + role) |
| 5 | 6 (1 + 5) |
| 10 | 11 (1 + 10) |

### Caching strategies

1. **In-memory cache**: Cache the result of `has_permission` for the duration of the request. All calls within the same request can share the cached result.
2. **Redis cache**: Use Redis to cache permission results across requests. Cache TTL of 60-120 seconds.
3. **Token claims cache**: Store pre-computed permissions in the `app_metadata` claim of the access token. The token is refreshed periodically (every 15 minutes), so permissions are up-to-date within that window.

### When to use `has_permission` vs role checks

| Method | Speed | Use Case |
| --- | --- | --- |
| `$auth.claims.roles contains 'admin'` | Fast (no DB query) | Simple role-based checks. Best for high-traffic endpoints. |
| `has_permission($auth, 'user:delete')` | Slow (DB query) | Granular permission checks. Best for low-traffic or admin endpoints. |

<Note>
For most applications, role-based checks are sufficient and more performant. Use `has_permission` only when you need granular permission checks that can't be expressed as role names.
</Note>

## Common mistakes

<AccordionGroup>
  <Accordion title="Assuming role hierarchy exists">
    Pawabase roles are flat — there is no inheritance between roles. If you need an admin role to inherit editor permissions, you must explicitly assign the same permissions to the admin role or implement it in the policy expression.
  </Accordion>
  <Accordion title="Putting too many permissions in a single role">
    Over-granular roles lead to role explosion (too many roles). Keep roles focused — a role should represent a job function, not a single permission.
  </Accordion>
  <Accordion title="Not revoking roles properly">
    Use `revoke_role` (which sets `revoked_at`) instead of deleting `RoleAssignment` records. Deleting records breaks the audit trail. Always use `revoke_role`.
  </Accordion>
  <Accordion title="Using `has_permission` on every request">
    `has_permission` performs database queries. Using it on every request for high-traffic endpoints will create a performance bottleneck. Cache results or use role-based checks instead.
  </Accordion>
  <Accordion title="Not checking `revoked_at`">
    When checking permissions, always filter by `revoked_at == None`. If you don't, revoked roles will still grant permissions.
  </Accordion>
  <Accordion title="Confusing `scope` in role assignments">
    A global role assignment has `org_id = null`. An org-scoped role assignment has `org_id` set. Mixing these up leads to incorrect permission checks. Always check the scope when assigning or revoking roles.
  </Accordion>
</AccordionGroup>
