Roles group the permissions people need to do their work. Permissions describe individual capabilities, such as `leave.review`, `expenses.approve`, or `reports.export`.

In a PeopleOps application, an employee can submit requests, a manager can review team requests, and a payroll administrator can export approved expenses. Model these as explicit capabilities, then attach policies to the relevant resource operations and routes.

Roles belong to one application environment. They are separate from Studio organization roles and from roles within an application organization.

## Design the permission set

Start with actions your product exposes:

| Role | Example permissions | Intended audience |
| --- | --- | --- |
| employee | `leave.submit`, `expenses.submit` | All employees |
| manager | `leave.review` | Approved managers |
| payroll | `expenses.approve`, `reports.export` | Payroll staff |
| auditor | `reports.read` | Read-only reviewers |

A permission string is a name you choose. Use a consistent naming convention and the same exact value in role definitions and policy conditions.

Roles are flat. A manager does not automatically inherit the employee role or its permissions. Assign both roles, or include the employee permissions in the manager role.

Do not assume a role named `admin` bypasses application policies. A policy must explicitly allow its role or permissions. Service credentials have different access semantics.

## Create a role in Studio

1. Open the project and select the environment.
2. Open **Users & auth → Roles**.
3. Select **New role**.
4. Enter a name such as `payroll`.
5. Add a description explaining who should receive it.
6. Enter comma-separated permissions: `expenses.approve, reports.export`.
7. Save.

Role names start with a lowercase letter and can contain lowercase letters, digits, underscores, colons, and hyphens, up to 63 characters.

The role list shows descriptions, permissions, and member counts. Open a role to change its permissions. Saving an edited permission list makes that list the role's permission set; omitting an old entry removes it from the role.

## Assign roles to a user

1. Open **Users & auth → Users**.
2. Search for and open the user.
3. In **Roles**, enter the complete comma-separated list the user should have.
4. Select **Save roles**.
5. Refresh the user's session or sign in again before verifying the new access.

Treat the Roles field as the desired full set. To add `payroll` to a user who should remain an employee, retain `employee` in the field.

Define the role first and check its spelling. An unintended empty role does not grant the permissions you expected.

### Remove a role

Open the user, remove the role from their list, and save. Review direct grants and other roles before assuming the user has lost a permission: another assignment may still provide it.

### Delete a role

Open the role under **Roles** and select **Delete**. Before deleting, inspect policies that check the role name and users who rely on its permissions. Deleting a role does not rewrite those policy references.

Already-issued access tokens may continue to carry previous roles or permissions until they expire. See [Tokens and sessions](/auth/tokens-and-sessions).

## Grant a permission directly

A user can also receive a direct permission without joining a role.

In the user detail view, enter the permission under the permissions controls and select **Grant**. Remove a direct grant using its remove action.

Direct grants are useful for a specific exception, such as giving a temporary reviewer `reports.export`. Roles are easier to review when a capability belongs to a recurring job function.

Effective permissions combine direct grants and permissions from every assigned role. Removing a direct grant will not remove the same permission if a role still provides it.

## Default roles for registration

Under **Users & auth → Configuration**, add limited roles to **Default roles**.

For example, a public customer portal might assign `customer`. An employee portal could use `employee` when registration is otherwise controlled.

Default roles apply when accounts are created. They do not replace role assignments for all existing users. Never add privileged approval or export permissions to a public registration default.

## Enforce a permission

Creating a role does not protect an endpoint by itself. Create a policy and attach it to an enabled operation or custom route.

In Studio's policy editor, create `can_export_reports` with this condition:

~~~json
{
  "all": [
    { "authenticated": true },
    { "permission": "reports.export" }
  ]
}
~~~

Assign the policy to the report-export route. Then call the public route with the caller's publishable key and access token.

The policy evaluates the permissions in the authenticated session. A request body containing `"permissions": ["reports.export"]` does not grant that permission.

### Check a role directly

For a feature intended for a named job function:

~~~json
{
  "role": ["payroll", "auditor"]
}
~~~

The list means either role is sufficient. Use separate conditions inside `all` when both roles are required.

Permission-based policies usually survive role reorganizations more easily. You can create a new role with `reports.export` without editing every export policy.

### Combine a permission with organization isolation

A reviewer permission should not grant access to every customer organization's records.

For an individual-record operation:

~~~json
{
  "all": [
    { "authenticated": true },
    { "permission": "leave.review" },
    { "exists": "$auth.org" },
    { "eq": ["$record.organization_slug", "$auth.org"] }
  ]
}
~~~

The user needs both the capability and the correct active organization. Ensure the record's organization identifier uses the same representation as the session's organization claim.

Create operations have no existing record. Use the validated input and a workflow that prevents users from selecting an unauthorized organization. See [Policy context](/policies/context).

## Wildcard permissions

The permission `*` grants broad permission access. It should be reserved for accounts that intentionally need that breadth.

A wildcard permission does not make ownership and organization checks disappear. A combined policy can still require a matching record owner or organization.

Avoid placing `*` in a default role. Prefer explicit permissions for routine support, reporting, and operations work.

## Read the current user's access information

Use the public profile endpoint:

~~~bash
curl "$PAWABASE_URL/auth/v1/user" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
~~~

The user profile includes roles and permissions. Use them to explain available actions and adjust the interface.

The policy decision for another API request uses that request's access token. A fresh profile response can therefore show an assignment newer than an older token. Refresh the session before testing a recent role change.

Do not put a service key in the browser to assign roles. Application users cannot elevate their access by editing their own profile metadata.

## User metadata is not a grant

A person may be able to edit their own profile data. A profile field such as `department` can support display or preferences, but a user-editable `is_admin` or `role` value must not become an authorization shortcut.

Keep privilege assignments in managed roles, permissions, or appropriately controlled application metadata. Use the policy context's verified role and permission fields.

## Test the complete workflow

For an expense approval feature:

1. Create `expenses.approve` in the payroll role.
2. Assign payroll to the reviewer.
3. Attach a permission policy to the approval route.
4. Sign in as an ordinary employee and confirm approval is denied.
5. Sign in as the reviewer and confirm approval is allowed.
6. Try approving another organization's expense and confirm isolation.
7. Remove the role, renew the session, and confirm approval is denied.
8. Check whether a direct grant or another role still provides the permission.

Use publishable keys and real user sessions for these tests. Service credentials can bypass policies and produce misleading results.

## Troubleshooting

### The user has the role but the action is denied

Check the permission spelling, the assigned policy, and any additional organization, ownership, or assurance conditions. Then refresh the session.

### The user still has access after a role was removed

Check for another role, a direct grant, a wildcard permission, or an unexpired token containing the previous claims.

### The role exists in development but not production

Roles and assignments are environment-scoped. Review the target environment's Roles tab and provision the intended assignments there.

### Hiding a button did not prevent the request

Client-side visibility is not enforcement. Attach the policy to the public operation or route, then test that API directly.

### Removing a direct permission did not change effective access

Inspect role permissions. Effective access combines all grants; removing one source does not override another.
