Authentication configuration defines how people join and sign in to one application environment. Configure it before building login screens so the client can handle the actual registration, verification, and MFA requirements.

A production environment typically needs different application URLs, provider credentials, and registration rules from development. Always check the environment selector before saving.

## Open the configuration

In Studio, open your project, select the environment, then open **Users & auth → Configuration**. The form contains Sign-up, Passwords, Sign-in methods, URLs, OAuth providers, and email settings.

Change the controls you need and select **Save**. Authentication settings may take a short time to propagate. Verify the observable result with the public settings endpoint and a fresh sign-in before investigating a failed change.

## Registration

| Studio setting | Default | Effect |
| --- | --- | --- |
| Sign-up enabled | On | Allows public registration |
| Require email verification | Off | Password sign-up requires email confirmation before a normal password sign-in |
| Default roles | Empty | Assigns the listed environment roles when an account is created |

For an employee-only PeopleOps application, disable public sign-up and provision approved accounts through Studio. Existing accounts can still use enabled sign-in methods.

For a public marketplace, enable sign-up and decide whether users must verify their email before using the product. When verification is required, the sign-up response contains the user, `session: null`, and `verification_required: true`. Display a confirmation screen instead of sending the person into the signed-in application.

### Default roles

Define roles under **Users & auth → Roles** before adding their names to **Default roles**. A default role is a privilege assigned to new accounts, so choose a limited role such as `customer` or `employee`.

Do not use a privileged reviewer or administrator role as a public registration default. Default role changes are not a bulk reassignment of existing users; update existing assignments separately.

## Passwords

| Studio setting | Default | Purpose |
| --- | --- | --- |
| Policy | Basic | Choose Basic or Strict password validation |
| Minimum length | 8 characters | Minimum accepted password length |
| Access token lifetime | 900 seconds | Lifetime of an issued access token |
| Refresh token lifetime | 2,592,000 seconds | Configured lifetime used when issuing refresh credentials |

Basic validates password length. Strict adds password-strength requirements. Both use the configured minimum length.

The server enforces password validation when a password is created or changed. Your client may display requirements and provide immediate feedback, but it must also handle the server's validation response. A later policy change does not rewrite users' existing passwords.

### Choose token lifetimes deliberately

An access token is attached to application requests. A refresh token obtains a replacement token pair without asking for the password again.

Shorter access-token lifetimes reduce how long an already-issued token can carry stale permissions after a role change or session revocation. They also increase how often the client refreshes.

A refresh lifetime is not a substitute for a reliable refresh implementation. Save replacement refresh tokens, coordinate concurrent refreshes, and send the user back to sign-in when the refresh chain is no longer usable. See [Tokens and sessions](/auth/tokens-and-sessions).

Both controls use seconds. Fifteen minutes is `900`; one day is `86400`; thirty days is `2592000`.

## Sign-in methods

### Magic links

Enable **Magic links** to let users request a passwordless email sign-in link.

Account creation also depends on **Sign-up enabled** and the request's `create_user` field. Disabling sign-up prevents the magic-link request from registering unknown addresses even if the request asks to create an account.

There is no separate `magic_link_create_account` Studio setting. See [Magic links](/auth/magic-links) for the supported request fields and callback flow.

### MFA

Enable **MFA (TOTP)** to allow users to enroll an authenticator app and complete MFA challenges.

This setting enables the capability; it does not require every account to enroll. Use a policy such as `{"aal": "aal2"}` on sensitive actions when the action must require a two-factor session.

Disabling MFA changes the authentication experience for enrolled accounts. Test that change in staging and review policies that require `aal2` before applying it to production.

## Application and redirect URLs

### Site URL

Set **Site URL** to the application's base URL:

~~~text
https://people.example.com
~~~

When Site URL is configured, authentication emails direct the browser to:

~~~text
https://people.example.com/auth/callback?token=<one-time-token>&type=<purpose>
~~~

Your application must implement `/auth/callback`. It reads the purpose and token, calls the corresponding public verification endpoint, and handles the response.

The token in an email link is not an access token. Exchange it using the appropriate endpoint before making authenticated resource requests.

If Site URL is empty, email links use Pawabase's hosted link pages. For an application that needs to capture sessions and handle MFA itself, configure Site URL and own the callback.

### Additional allowed redirect URLs

Use this field for other trusted destinations, such as a staging frontend or a specific application route.

Pawabase accepts an exact configured URL, a path below it, or a query appended to it. It is not an arbitrary wildcard list. For example, allowing `https://people.example.com` allows paths on that origin; it does not allow `https://people.example.com.attacker.invalid`.

Choose the narrowest practical destinations. A trusted destination must not itself forward users to an arbitrary URL supplied in a query parameter.

### Redirect validation and CORS differ

Redirect URLs control where authentication flows may direct a browser. CORS controls whether browser JavaScript may call the gateway from an origin.

If the callback loads but its API request fails in the browser, check [CORS configuration](/operate/rate-limits-and-cors). Adding a redirect URL does not automatically configure CORS.

## OAuth providers

Under **OAuth providers**, add a supported provider or a custom provider.

The built-in provider choices are Google, GitHub, Discord, and Microsoft. Each needs its provider-issued client ID and client secret. Use environment secrets for sensitive credentials, referenced as `secret://NAME`.

For a custom provider, the form also exposes:

| Field | What to supply |
| --- | --- |
| Authorize endpoint | Provider URL that starts user authorization |
| Token endpoint | Provider URL used to exchange the authorization code |
| Userinfo endpoint | Provider URL that returns the authenticated profile |
| Scopes | Provider-specific permissions requested during sign-in |
| Enabled | Whether the provider is available for sign-in |

Configure the provider application's callback URL using the [Social login](/auth/social-login) guide. Your application's post-login destination and the provider callback are different URLs.

Keep production provider credentials separate from development credentials. Confirm that referenced secrets exist in the target environment before testing.

## Authentication email templates

Authentication email settings cover verification, password recovery, magic links, organization invitations, and email changes.

Each template has a subject and text body. Use these placeholders:

| Placeholder | Meaning |
| --- | --- |
| `{project}` | Project display name |
| `{email}` | Recipient address |
| `{link}` | Generated action link |
| `{organization}` | Organization name for an invitation |
| `{role}` | Invited organization role |

Use single braces. For example:

~~~text
Subject: Sign in to {project}

Hello,

Open this link to sign in:
{link}

The link works once and expires in 15 minutes.
If you did not request it, you can ignore this email.
~~~

Preserve `{link}` in every action email. A readable email without its action URL cannot complete the workflow.

Templates customize the message; they do not configure the mail transport. Have the installation operator configure delivery, then test with a real mailbox. See [Mail](/mail/overview).

## Verify what the application sees

The public settings endpoint returns safe capability information:

~~~bash
curl "$PAWABASE_URL/auth/v1/settings" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY"
~~~

It exposes registration, verification, magic-link, MFA, provider, and password-policy information. It does not expose OAuth secrets or all administrative settings.

Use this response to decide which login controls to render. A hidden button is not enforcement: the server evaluates the current configuration when the request arrives.

## Prepare a development environment

1. Set Site URL to the local frontend origin.
2. Configure the frontend's gateway URL and development publishable key.
3. Enable the sign-in methods needed for the feature under development.
4. Define a limited default role if registration should assign one.
5. Configure email delivery before testing verification or recovery.
6. Implement the callback route and the MFA response branch.
7. Create two ordinary test users with different ownership or organization membership.
8. Verify their access through public APIs.

Use test accounts whose roles resemble production accounts. Testing only as an operator or with a service key does not establish that user policies work.

## Prepare production

Review registration rules, default roles, application URLs, provider secrets, and email delivery in the production environment itself. Verify a fresh registration, an existing-user sign-in, recovery, refresh, and logout using the production frontend.

Changing authentication configuration does not migrate development users into production. Promotion also does not provision the target environment's secrets.

For a sensitive workflow, test the policy requiring `aal2` with both a normal session and a session that completed MFA.

## Troubleshooting

| Symptom | What to inspect |
| --- | --- |
| Registration returns 403 | Sign-up enabled in the environment selected by the API key |
| Registration succeeds but no session appears | Require email verification and the response's verification flag |
| Magic links do not register a new address | Sign-up enabled and the request's `create_user` value |
| Redirect is rejected | Site URL, additional URLs, scheme, port, and path |
| Provider is absent from settings | Enabled state and client ID |
| Callback page is missing | Application routing for `/auth/callback` |
| Email contains a literal placeholder | Placeholder spelling and single-brace syntax |
| Role change is not reflected | Refresh the user session and inspect the newly issued claims |
| A saved change is not visible immediately | Allow brief propagation, then recheck with the same environment's key |

Continue with [Passwords](/auth/passwords), [Magic links](/auth/magic-links), or [Social login](/auth/social-login) to implement a complete sign-in path.
