This page is the complete reference for how to integrate Pawabase auth into any client type, covering SDK initialization, sign-up and sign-in flows, token storage and refresh, CORS configuration, service key authentication, mobile-specific considerations, and the complete error handling patterns you'll encounter across every client type.

## The frontend SDK

The Pawabase frontend SDK provides a complete authentication flow for web and mobile applications. It handles every aspect of the authentication lifecycle: sign-up, sign-in, token management, session management, MFA, and error handling.

<Steps>
  <Step title="Initialize the SDK">
    Create a `PawabaseClient` instance with your publishable key, project ID, and environment ID. The SDK validates the key format and loads the environment configuration.
  </Step>
  <Step title="Sign up or sign in">
    Call the appropriate sign-up or sign-in method. The SDK validates inputs, makes the API request, and handles the response.
  </Step>
  <Step title="Store tokens securely">
    The SDK stores the access token and refresh token using the configured storage mechanism (memory, cookie, or platform-specific secure storage).
  </Step>
  <Step title="Automatically refresh tokens">
    Before the access token expires, the SDK silently refreshes using the refresh token. If refresh fails, the SDK clears stored tokens and emits events for the application to handle.
  </Step>
  <Step title="Handle session events">
    The SDK emits events for sign-in, sign-out, token refresh, theft detection, and errors. Subscribe to these events to update the application state.
  </Step>
</Steps>

### SDK initialization

Initialize the SDK with your publishable key and project configuration:

```typescript
import { createClient } from '@pawabase/sdk'

const client = createClient({
  publishableKey: 'pk_abc123...',
  projectId: 'acme',
  envId: 'production',
  autoRefresh: true,
  tokenStorage: 'cookie',
  refreshThreshold: 60,
})
```

The SDK configuration accepts the following options:

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `publishableKey` | string | Required | The publishable key (`pk_...` prefix). Identifies the project and environment. |
| `projectId` | string | Required | The project identifier. |
| `envId` | string | Required | The environment identifier (`development`, `staging`, `production`). |
| `autoRefresh` | boolean | `true` | Whether to automatically refresh tokens before expiration. |
| `tokenStorage` | string | `'memory'` | Token storage mechanism: `'memory'`, `'cookie'`, or `'secure'`. |
| `refreshThreshold` | number | `60` | Number of seconds before token expiration to trigger a refresh. |
| `gatewayUrl` | string | Platform default | The URL of the Pawabase gateway. |
| `retryConfig` | object | Default retry settings | Configuration for retry logic on transient failures. |

The publishable key is safe to use in client-side code because it only grants access to the self-service API. It cannot perform administrative operations — those require a service key. The publishable key identifies the project and environment, and the gateway resolves it to determine which tenant's user directory to use.

### SDK initialization details

When the SDK is initialized, it performs several setup operations:

1. **Key validation**: The SDK validates the publishable key format. If the key doesn't match the expected format (`pk_` prefix), initialization fails with a configuration error.
2. **Configuration loading**: The SDK fetches the environment's auth configuration (`GET /auth/v1/settings`) to determine which sign-in methods are available.
3. **Session restoration**: If stored tokens exist, the SDK attempts to restore the session by validating the access token. If the token is valid, the user is considered signed in.
4. **Auto-refresh setup**: If `autoRefresh` is `true`, the SDK sets up a timer to refresh the token `refreshThreshold` seconds before expiration.
5. **Event listener registration**: The SDK registers internal event listeners for token refresh, sign-out, and theft detection.

```typescript
class PawabaseClient {
  private config: ClientConfig
  private tokens: TokenStore | null = null
  private refreshTimer: ReturnType<typeof setTimeout> | null = null

  constructor(config: ClientConfig) {
    this.config = config
    this.validateKey(config.publishableKey)
    this.loadConfiguration()
    this.restoreSession()
    if (config.autoRefresh) {
      this.setupAutoRefresh()
    }
  }
}
```

### Sign-up with the SDK

```typescript
const { data, error } = await client.auth.signUp({
  email: 'chioma@example.com',
  password: 'correct-horse-battery-staple',
  name: 'Chioma Nwosu',
  data: { tier: 'starter' },
  redirectTo: 'https://app.example.com/auth/callback',
})
```

The SDK handles the complete sign-up flow:

1. **Input validation**: The SDK validates the email format, password length, and password policy requirements before sending the request. If the password doesn't meet the policy, the SDK returns a client-side error with specific details about which rules were violated.
2. **API request**: The SDK sends a `POST /auth/v1/signup` request with the user's information. The request includes the `apikey` header (the publishable key) and the request body containing `email`, `password`, `name`, `data`, and `redirectTo`.
3. **Response handling**: The SDK processes the response. If sign-up succeeds, the response includes the user object and, if `require_email_verification` is `false`, the session tokens.
4. **Verification handling**: If `require_email_verification` is `true`, the SDK stores the `redirect_to` URL and the user's email. The application should display a verification prompt and redirect the user after verification is complete.
5. **Error mapping**: The SDK maps server errors to user-friendly error objects. Each error includes a `statusCode`, `message`, and optional `details` field with structured information about the error.

```typescript
interface SignUpResponse {
  user: User
  session: Session | null
  verificationRequired: boolean
}
```

### Sign-in with the SDK

The SDK supports multiple sign-in methods:

```typescript
// Password sign-in
const { data, error } = await client.auth.signIn({
  email: 'chioma@example.com',
  password: 'correct-horse-battery-staple',
})

// Magic link sign-in
const { data, error } = await client.auth.signInWithMagicLink({
  email: 'chioma@example.com',
})

// Social login
const { data, error } = await client.auth.signInWithOAuth({
  provider: 'google',
  options: {
    redirectTo: 'https://app.example.com/auth/callback',
    scopes: ['openid', 'email', 'profile'],
  },
})

// MFA completion
const { data, error } = await client.auth.signInWithMFA({
  mfaToken: 'mfa_token_abc123...',
  code: '123456',
})
```

Each sign-in method follows the same pattern but has different requirements and response shapes. The SDK handles method-specific logic:

- **Password sign-in**: Validates email and password format, sends the request, handles the response including MFA challenges if required.
- **Magic link**: Sends the magic link request, stores the email for later verification, handles the callback when the user clicks the link.
- **Social login**: Initiates the OAuth2 flow, handles the redirect, exchanges the authorization code for tokens.
- **MFA completion**: Sends the TOTP code to the MFA endpoint, handles the response including the new session tokens.

### MFA handling in the SDK

When MFA is enabled and the user signs in with a password, the SDK automatically handles the MFA challenge flow:

```typescript
// The sign-in response may include an MFA challenge
const { data, error } = await client.auth.signIn({
  email: 'chioma@example.com',
  password: 'correct-horse-battery-staple',
})

if (data.mfaRequired) {
  // The SDK detected an MFA challenge
  // Display the MFA input field to the user
  const mfaCode = await showMFAInput()
  
  // Complete the MFA challenge
  const { data: mfaData, error: mfaError } = await client.auth.completeMFA({
    mfaToken: data.mfaToken,
    code: mfaCode,
  })
  
  // Now the user is signed in with aal2 session
}
```

The SDK automatically detects MFA requirements and provides methods for completing the challenge. The `mfaToken` is a one-time token that identifies the MFA challenge session. It must be used within the challenge window and cannot be reused.

### Token storage

The SDK stores tokens using a secure mechanism appropriate for the client type:

#### Browser storage options

The SDK provides three storage mechanisms for browser environments:

1. **Memory storage (default)**: Tokens are stored in JavaScript variables within the SDK instance. This is the most secure option against XSS attacks because tokens are not accessible through `localStorage` or `sessionStorage`. However, tokens are lost when the page is refreshed.
2. **Cookie storage**: Tokens are stored in httpOnly cookies. This provides persistence across page refreshes and is not accessible to JavaScript. Requires proper CORS and cookie configuration.
3. **Secure storage**: Tokens are stored using the platform's secure storage mechanism (e.g., Web Crypto API with a derived key).

```typescript
// Memory storage (default) — most secure against XSS
const client = createClient({
  publishableKey: 'pk_abc123...',
  tokenStorage: 'memory',
})

// Cookie storage — persists across refreshes
const client = createClient({
  publishableKey: 'pk_abc123...',
  tokenStorage: 'cookie',
  cookieOptions: {
    domain: '.example.com',
    path: '/',
    sameSite: 'strict',
    secure: true,
  },
})
```

<Warning>
Never store tokens in `localStorage` or `sessionStorage`. These are accessible to any JavaScript running on the page, making them vulnerable to XSS attacks. The SDK should never store tokens in `localStorage` — this is a fundamental security requirement.
</Warning>

#### Mobile storage

On mobile platforms, the SDK uses the platform's secure storage:

- **iOS**: Tokens are stored in the iOS Keychain, which is encrypted and protected by the device's biometric authentication. The Keychain persists across app updates and is backed up to iCloud (if enabled).
- **Android**: Tokens are stored in the Android Keystore, which is hardware-backed on supported devices. The Keystore provides strong encryption and is protected by the device's lock screen.

```typescript
// On iOS, the SDK automatically uses the Keychain
const iosClient = createClient({
  publishableKey: 'pk_abc123...',
  tokenStorage: 'secure', // Uses Keychain on iOS
})

// On Android, the SDK automatically uses the Keystore
const androidClient = createClient({
  publishableKey: 'pk_abc123...',
  tokenStorage: 'secure', // Uses Keystore on Android
})
```

#### Server-side storage

Backend clients should not use the SDK's built-in token storage. Instead, backend clients should use service keys for authentication and store refresh tokens in a secure server-side session store or database.

```python
# Backend storage example
import redis
from pawabase import PawabaseClient

redis_client = redis.Redis(host='localhost', port=6379, db=0)
client = PawabaseClient(service_key='sk_abc123...')

# Store refresh token in Redis with TTL
await redis_client.setex(
    f"refresh:{user_id}",
    timeout=config.refresh_ttl,
    value=refresh_token,
)
```

### Automatic token refresh

The SDK automatically refreshes tokens before they expire:

```typescript
class TokenRefresher {
  private timer: ReturnType<typeof setTimeout> | null = null
  
  setupAutoRefresh() {
    const token = this.getAccessToken()
    if (!token) return
    
    const expiresIn = this.getTokenExpiration(token)
    const refreshIn = Math.max(0, expiresIn - this.config.refreshThreshold)
    
    this.timer = setTimeout(async () => {
      await this.refresh()
    }, refreshIn * 1000)
  }
  
  async refresh() {
    try {
      const refreshToken = this.getRefreshToken()
      const { data, error } = await client.auth.refresh(refreshToken)
      
      if (error) {
        throw error
      }
      
      this.storeTokens(data.access_token, data.refresh_token)
      this.setupAutoRefresh() // Schedule next refresh
    } catch (err) {
      this.handleRefreshFailure(err)
    }
  }
}
```

The refresh flow is:

1. The SDK tracks the `expires_in` value from the token response.
2. Before the access token expires, the SDK sends a refresh request with the refresh token.
3. If the refresh succeeds, the SDK updates the stored tokens.
4. If the refresh fails, the SDK clears the stored tokens and emits a `signedOut` event.

```typescript
client.on('signedOut', () => {
  // Clear application state
  store.clearAuth()
  router.navigate('/auth/sign-in')
  showNotification('Your session has expired. Please sign in again.')
})
```

The `refreshThreshold` (default: 60 seconds) determines how many seconds before token expiration the SDK initiates a refresh. A shorter threshold means more frequent refresh requests but less risk of the token expiring mid-request. A longer threshold means fewer refresh requests but a higher chance of the token expiring before the refresh completes.

### Refresh token rotation handling

When the SDK refreshes a token, the old refresh token is rotated (replaced by a new one). The SDK handles this transparently:

1. The SDK sends the old refresh token to `POST /auth/v1/token` with `grant_type: "refresh_token"`.
2. The server validates the refresh token, issues new tokens, and rotates the refresh token.
3. The SDK stores the new refresh token and uses it for subsequent refresh requests.

If the refresh fails because the old token was already rotated (theft detection), the SDK emits a `theftDetected` event:

```typescript
client.on('theftDetected', async () => {
  // The refresh token was used by someone else
  // Both the legitimate user and the attacker now have valid tokens
  // The legitimate user should be alerted and asked to sign out all sessions
  
  await showTheftWarning()
  await client.auth.signOut() // Sign out all sessions
  router.navigate('/auth/sign-in')
})
```

The `theftDetected` event is the signal that someone else used the refresh token. The SDK should:

1. Alert the user that their account may have been compromised.
2. Clear all stored tokens.
3. Redirect the user to the sign-in page.
4. Optionally, call `client.auth.signOut()` to revoke all sessions.

<Warning>
The `theftDetected` event does NOT automatically revoke the attacker's session. Both the legitimate user and the attacker have valid tokens after the theft. The legitimate user must sign out all sessions to revoke the attacker's token.
</Warning>

### Session restoration

When the application starts, the SDK attempts to restore the user's session:

```typescript
async function restoreSession() {
  const accessToken = await client.getAccessToken()
  if (!accessToken) {
    // No stored tokens — user is not signed in
    return { authenticated: false }
  }
  
  // Validate the access token
  const isValid = await client.auth.validateToken(accessToken)
  if (!isValid) {
    // Access token is invalid — try to refresh
    const refreshToken = await client.getRefreshToken()
    if (refreshToken) {
      const { data, error } = await client.auth.refresh(refreshToken)
      if (error) {
        // Refresh failed — user must sign in
        await client.auth.signOut()
        return { authenticated: false }
      }
      // Refresh succeeded — session restored
      return { authenticated: true, user: data.user }
    }
    // No refresh token — user must sign in
    await client.auth.signOut()
    return { authenticated: false }
  }
  
  // Access token is valid — session restored
  return { authenticated: true, user: await client.auth.getUser() }
}
```

Session restoration happens automatically during SDK initialization if `autoRefresh` is `true`. The SDK checks for stored tokens, validates the access token, and if invalid, attempts to refresh using the stored refresh token.

### Error handling in the SDK

The SDK provides a structured error handling system:

```typescript
try {
  const { data, error } = await client.auth.signIn({
    email: 'chioma@example.com',
    password: 'correct-horse-battery-staple',
  })
  
  if (error) {
    handleError(error)
    return
  }
  
  // Success — use data.user and data.session
} catch (err) {
  // Network errors or unexpected failures
  handleUnexpectedError(err)
}
```

The SDK error object has the following structure:

```typescript
interface SDKError {
  statusCode: number
  message: string
  code: string
  details?: Record<string, any>
  retryAfter?: number
}
```

Common error codes include:

| Code | Status | Description |
| --- | --- | --- |
| `invalid_credentials` | 400 | Email or password is incorrect. |
| `account_disabled` | 403 | The account has been disabled by an administrator. |
| `email_not_verified` | 403 | Email verification is required. |
| `mfa_required` | 403 | MFA verification is required. |
| `aal_required` | 403 | Minimum AAL level not met. |
| `account_locked` | 429 | Account is temporarily locked due to too many failed attempts. |
| `rate_limit_exceeded` | 429 | Too many requests. |
| `session_revoked` | 401 | The session has been revoked. |
| `theft_detected` | 401 | Refresh token was already rotated. |
| `token_expired` | 401 | The access token has expired. |

## CORS configuration

Cross-Origin Resource Sharing (CORS) controls which origins can make requests to the Pawabase API. CORS is configured per environment and is essential for browser-based applications.

### Configuring CORS

```json
{
  "auth": {
    "cors_origins": [
      "https://app.example.com",
      "https://staging.example.com",
      "http://localhost:3000"
    ]
  }
}
```

The `cors_origins` array specifies the allowed origins. Each origin must match exactly (scheme, host, and port). Wildcards are not supported — each origin must be explicitly listed.

### How CORS works in Pawabase

When the frontend SDK makes a request to the Pawabase API:

1. **Simple requests**: For `GET` requests or `POST` requests with `Content-Type: application/x-www-form-urlencoded`, the browser sends the request directly with the `Origin` header. The server checks if the `Origin` matches any of the configured `cors_origins`. If it matches, the server responds with `Access-Control-Allow-Origin` set to the matching origin.
2. **Preflight requests**: For `POST` requests with `Content-Type: application/json` or other non-simple requests, the browser sends a preflight `OPTIONS` request first. The server responds with CORS headers indicating the allowed methods, headers, and credentials.

```
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: apikey, content-type, authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400
```

### Preflight request handling

The preflight `OPTIONS` request is handled by the gateway before the request reaches the API:

```
Browser → OPTIONS /auth/v1/token (Origin: https://app.example.com)
Gateway → Checks Origin against cors_origins
Gateway → If match, returns CORS headers
Browser → Sends actual POST /auth/v1/token with CORS headers
```

The gateway handles preflight requests without calling the API. The CORS headers are cached by the browser for `Access-Control-Max-Age` seconds (default: 86400 / 24 hours).

### CORS and the token endpoint

The `/auth/v1/token` endpoint has special CORS handling because it is used by the frontend SDK:

```
POST /auth/v1/token
Origin: https://app.example.com
apikey: pk_abc123...
Content-Type: application/json
```

The gateway validates the `Origin` header against `cors_origins`. If the origin is allowed, the response includes the appropriate `Access-Control-Allow-Origin` header. If the origin is not allowed, the gateway returns a CORS error and the request fails.

<Important>
If `cors_origins` is empty or not configured, the server accepts requests from any origin. This is convenient for development but should never be used in production. Always configure `cors_origins` to restrict access to known origins.
</Important>

### CORS configuration per environment

Each environment can have its own CORS configuration:

| Environment | Typical `cors_origins` |
| --- | --- |
| Development | `["http://localhost:3000", "http://localhost:5173"]` |
| Staging | `["https://staging.example.com"]` |
| Production | `["https://app.example.com", "https://www.example.com"]` |

Development should have relaxed CORS to facilitate local development. Production should have an explicit allow-list to prevent unauthorized origins from making requests.

## Backend integration

Backend services interact with Pawabase using service keys rather than the frontend SDK. Service keys provide full administrative access and are used for server-to-server communication.

### Service keys

Service keys are of two types:

| Type | Prefix | Permissions |
| --- | --- | --- |
| Publishable key | `pk_` | Read-only access to self-service API. Safe for client-side code. |
| Secret key | `sk_` | Full admin access. Never expose in client-side code. |

Service keys are issued by the Pawabase platform and are associated with a specific project and environment. They should be stored in a secret manager (AWS Secrets Manager, HashiCorp Vault, etc.) and never in source code or configuration files.

### Service key authentication

Service keys are passed in the `apikey` or `authorization` header:

```bash
# Using the apikey header
curl -X GET "$GW/projects/acme/envs/production/users" \
  -H "apikey: sk_abc123..."

# Using the authorization header
curl -X GET "$GW/projects/acme/envs/production/users" \
  -H "authorization: Bearer sk_abc123..."
```

Both headers serve the same purpose. The `apikey` header is a convenience header, while `authorization: Bearer` is the standard HTTP authentication header. The choice depends on the API gateway's configuration.

### Server-to-server token management

Backend services can manage tokens programmatically:

```python
from pawabase import PawabaseClient

client = PawabaseClient(
    service_key="sk_abc123...",
    project_id="acme",
    env_id="production",
)

# Create a user
user = await client.auth.create_user(
    email="new@example.com",
    name="New User",
    data={"department": "Engineering"},
)

# Sign in a user (creates a session)
session = await client.auth.sign_in(
    email="chioma@example.com",
    password="correct-horse-battery-staple",
)

# Revoke all sessions for a user
await client.auth.revoke_all_sessions(user_id=user.id)

# List all sessions for a user
sessions = await client.auth.list_sessions(user_id=user.id)
```

The backend client handles all the same operations as the frontend SDK but with full administrative privileges. The backend client does not need to handle token storage or refresh — it uses the service key for each request.

### Backend error handling

Backend clients should handle errors differently from frontend clients because they don't have user interaction:

```python
import asyncio
from pawabase import PawabaseError

async def get_valid_access_token(client: PawabaseClient, refresh_token: str) -> str:
    max_retries = 3
    for attempt in range(max_retries):
        try:
            data = await client.auth.refresh(refresh_token=refresh_token)
            return data['access_token']
        except PawabaseError as e:
            if e.status_code == 401:
                # Need to re-authenticate
                data = await client.auth.sign_in(...)
                return data['access_token']
            elif e.status_code == 429:
                # Rate limited — wait and retry
                await asyncio.sleep(e.retry_after * (2 ** attempt))  # Exponential backoff
                continue
            elif e.status_code >= 500:
                # Server error — retry with exponential backoff
                await asyncio.sleep(2 ** attempt)
                continue
            else:
                raise
    
    raise PawabaseError("Failed to get valid access token after retries")
```

Backend error handling patterns:

1. **Exponential backoff**: For transient errors (429, 500, 502, 503), use exponential backoff with jitter. Double the wait time with each retry, and add a random jitter to avoid thundering herd problems.
2. **Retry limits**: Set a maximum number of retries (typically 3-5) to prevent infinite retry loops.
3. **Circuit breaker**: After repeated failures, stop trying for a configurable period. This prevents overwhelming a failing service.
4. **Logging**: Log all errors with sufficient context (project, environment, user ID, error code) for debugging and auditing.

## Mobile client integration

Mobile clients use the same SDK architecture as web clients but with platform-specific storage and deep linking capabilities.

### iOS integration

On iOS, the SDK stores tokens in the Keychain:

```swift
import PawabaseSDK

let client = PawabaseClient(
    publishableKey: "pk_abc123...",
    projectId: "acme",
    envId: "production"
)

// The SDK automatically stores tokens in the Keychain
let session = await client.auth.signIn(
    email: "chioma@example.com",
    password: "correct-horse-battery-staple"
)

// Access the current user
let user = await client.auth.getUser()
```

The iOS SDK uses the Keychain for token storage with these properties:

- **Accessibility**: `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` — tokens are only accessible when the device is unlocked and are not backed up to iCloud by default.
- **Security**: The Keychain is encrypted using the device's hardware security module.
- **Biometric protection**: Tokens can be protected by biometric authentication (Face ID, Touch ID) using the `kSecAccessControlBiometryCurrentSet` attribute.

### Android integration

On Android, the SDK stores tokens in the Keystore:

```kotlin
import com.pawabase.sdk.PawabaseClient

val client = PawabaseClient(
    publishableKey = "pk_abc123...",
    projectId = "acme",
    envId = "production"
)

// The SDK automatically stores tokens in the Keystore
val session = client.auth.signIn(
    email = "chioma@example.com",
    password = "correct-horse-battery-staple"
)

// Access the current user
val user = client.auth.getUser()
```

The Android SDK uses the Keystore for token storage with these properties:

- **Hardware-backed**: On devices with a hardware Keystore, tokens are stored in hardware-backed secure storage.
- **Encrypted**: The Keystore uses AES-256 encryption with keys stored in the hardware security module.
- **Biometric authentication**: Tokens can be protected by biometric authentication using `setUserAuthenticationRequired`.

### Deep linking

Mobile clients handle redirect URLs through deep links. Deep links allow the application to intercept URLs that would otherwise be handled by the browser:

```
myapp://auth/callback?token=otp_abc123...
myapp://auth/callback?code=auth_code_abc123...
myapp://auth/callback?error=access_denied
```

Deep links are used for:

1. **Social login**: The provider redirects to the deep link URL, which the app intercepts to extract the authorization code.
2. **Magic link**: The email contains the deep link URL, which the app intercepts to extract the token.
3. **Verification**: The verification link redirects to the deep link URL, which the app processes to verify the email.
4. **Redirect after sign-in**: After a successful sign-in, the app redirects to the deep link URL to complete the authentication flow.

#### Registering deep link URL schemes

**iOS**: Add URL schemes to `Info.plist`:

```xml
<key>CFBundleURLTypes</key>
<array>
  <dict>
    <key>CFBundleURLSchemes</key>
    <array>
      <string>myapp</string>
    </array>
  </dict>
</array>
```

**Android**: Add intent filters to `AndroidManifest.xml`:

```xml
<activity android:name=".auth.AuthCallbackActivity">
  <intent-filter>
    <action android:name="android.intent.action.VIEW" />
    <category android:name="android.intent.category.DEFAULT" />
    <category android:name="android.intent.category.BROWSABLE" />
    <data android:scheme="myapp" android:host="auth" android:path="/callback" />
  </intent-filter>
</activity>
```

#### Universal Links and App Links

For iOS, Universal Links provide a more secure alternative to custom URL schemes:

```json
// /Users/admin/sillo.build/apple-app-site-association
{
  "applinks": {
    "details": [
      {
        "appID": "TEAMID.com.example.myapp",
        "paths": ["/auth/callback/*"]
      }
    ]
  }
}
```

For Android, App Links provide similar functionality with domain verification.

### Mobile-specific considerations

1. **Network reliability**: Mobile networks are less reliable than Wi-Fi. The SDK should implement retry logic for network failures and handle intermittent connectivity gracefully.
2. **Background app state**: When the app is in the background, token refresh requests may be delayed. The SDK should handle this by refreshing tokens when the app returns to the foreground.
3. **Secure storage**: Always use the platform's secure storage (Keychain/Keystore). Never store tokens in `AsyncStorage`, `UserDefaults`, or similar insecure storage.
4. **Biometric authentication**: The SDK can optionally require biometric authentication before accessing stored tokens. This provides an additional layer of security on mobile devices.
5. **Deep link handling**: The SDK must correctly intercept and parse deep link URLs. Malformed or unexpected deep links should be handled gracefully.

## Token refresh patterns

### Frontend pattern

The frontend SDK handles token refresh automatically:

```typescript
// Automatic refresh (default behavior)
const client = createClient({
  publishableKey: 'pk_abc123...',
  autoRefresh: true,
  refreshThreshold: 60, // Refresh 60 seconds before expiration
})

// Manual refresh
const { data, error } = await client.auth.refresh()
```

The automatic refresh mechanism:

1. The SDK tracks the `expires_at` timestamp from the token response.
2. `refreshThreshold` seconds before `expires_at`, the SDK initiates a refresh.
3. The refresh request includes the stored refresh token.
4. If successful, the SDK updates stored tokens and schedules the next refresh.
5. If the refresh fails, the SDK emits a `signedOut` event and clears stored tokens.

### Backend pattern

Backend clients should implement their own refresh logic:

```python
async def get_valid_access_token(client: PawabaseClient, refresh_token: str) -> str:
    max_retries = 3
    for attempt in range(max_retries):
        try:
            data = await client.auth.refresh(refresh_token=refresh_token)
            return data['access_token']
        except PawabaseError as e:
            if e.status_code == 401:
                # Refresh token is invalid — need to re-authenticate
                session = await client.auth.sign_in(
                    email=stored_email,
                    password=stored_password,
                )
                return session['access_token']
            elif e.status_code == 429:
                # Rate limited
                await asyncio.sleep(e.retry_after * (2 ** attempt))
                continue
            elif e.status_code >= 500:
                # Server error
                await asyncio.sleep(2 ** attempt)
                continue
            else:
                raise
    raise PawabaseError("Failed to get valid access token")
```

Backend clients should also implement:

1. **Token caching**: Cache the access token in memory or a short-lived cache to avoid unnecessary refresh requests.
2. **Refresh token rotation**: Track the current refresh token and update it after each successful refresh.
3. **Graceful degradation**: If the refresh token expires, fall back to service key authentication for admin operations or prompt the user to re-authenticate.

### Handling refresh failures

When a refresh fails, the client must re-authenticate:

1. **Token expired**: The access token has expired and the refresh token is also expired. Re-authenticate with credentials.
2. **Session revoked**: The session has been explicitly revoked. Re-authenticate with credentials.
3. **Theft detected**: The refresh token was already rotated by an attacker. Sign out all sessions and re-authenticate.
4. **Rate limited**: Too many refresh requests. Wait and retry with exponential backoff.
5. **Network failure**: The request failed due to a network issue. Retry with exponential backoff.

```typescript
async function ensureValidToken(client: PawabaseClient): Promise<string> {
  const accessToken = client.getAccessToken()
  if (accessToken && !client.isTokenExpired(accessToken)) {
    return accessToken
  }
  
  const refreshToken = client.getRefreshToken()
  if (!refreshToken) {
    throw new Error('No refresh token available')
  }
  
  try {
    const { data, error } = await client.auth.refresh(refreshToken)
    if (error) {
      throw error
    }
    return data.access_token
  } catch (err) {
    if (err.statusCode === 401) {
      // Session revoked or theft detected
      await client.auth.signOut()
      throw new Error('Session expired. Please sign in again.')
    }
    throw err
  }
}
```

## Platform-specific integration patterns

### Server-side rendering (SSR)

For SSR applications, the SDK must be configured differently:

```typescript
// Server-side SDK initialization
const serverClient = createClient({
  publishableKey: 'pk_abc123...',
  tokenStorage: 'memory', // Use memory on the server
  autoRefresh: false, // Disable auto-refresh on the server
})

// On each request, restore the session from cookies
app.use(async (req, res, next) => {
  const cookie = req.cookies['pawabase_token']
  if (cookie) {
    await serverClient.auth.restoreSession(cookie)
  }
  next()
})
```

SSR considerations:

1. **Token storage**: Use memory storage on the server. Do not use cookie storage on the server-side — cookies are a client-side mechanism.
2. **Session restoration**: Restore the session from cookies on each request. The cookie contains the refresh token.
3. **Auto-refresh**: Disable auto-refresh on the server-side. The server should refresh tokens on-demand, not on a timer.
4. **CSRF protection**: Ensure CSRF protection is in place for all state-changing operations.

### Real-time applications

For real-time applications (WebSockets, Server-Sent Events), tokens must be refreshed independently of the SDK's HTTP client:

```typescript
class RealTimeClient {
  private ws: WebSocket
  private refreshInterval: ReturnType<typeof setInterval>
  
  constructor(private client: PawabaseClient, private wsUrl: string) {
    this.connect()
    this.setupTokenRefresh()
  }
  
  private async connect() {
    const token = await this.ensureValidToken()
    this.ws = new WebSocket(`${this.wsUrl}?token=${token}`)
  }
  
  private setupTokenRefresh() {
    this.refreshInterval = setInterval(async () => {
      const token = await this.ensureValidToken()
      // Send the new token to the WebSocket server
      this.ws.send(JSON.stringify({ type: 'token_refresh', token }))
    }, 60000) // Refresh every 60 seconds
  }
}
```

Real-time applications need to handle token refresh separately from the HTTP client because the WebSocket connection is long-lived and cannot be easily refreshed.

### Microservices architecture

In a microservices architecture, each service should have its own service key:

```
Frontend → Gateway → Auth Service (public key)
Gateway → User Service (service key)
Gateway → Order Service (service key)
```

Each service should have a service key with only the permissions it needs:

```python
# User service key — read-only access to user data
user_client = PawabaseClient(
    service_key="sk_user_readonly_...",
    permissions=["user:read"],
)

# Order service key — read and write access to orders
order_client = PawabaseClient(
    service_key="sk_order_full_...",
    permissions=["order:read", "order:write"],
)
```

Service keys should be rotated regularly and stored in a centralized secret manager.

## Error patterns across client types

### Browser client errors

| Error | Status | Cause | SDK handling |
| --- | --- | --- | --- |
| `401 invalid refresh token` | 401 | Token expired or revoked | SDK clears tokens and emits `signedOut` |
| `401 session revoked` | 401 | Session was explicitly revoked | SDK clears tokens and emits `signedOut` |
| `401 theft detected` | 401 | Refresh token was already rotated | SDK emits `theftDetected` event |
| `403 confirm your email address first` | 403 | `require_email_verification` is `true` | SDK shows verification prompt |
| `403 mfa token and code are required` | 403 | MFA is required | SDK shows MFA input field |
| `403 aal2 authentication required` | 403 | `require_aal` check failed on refresh | SDK shows MFA prompt |
| `429 too many failed attempts` | 429 | Account locked | SDK shows lockout message |
| `409 an account with this email already exists` | 409 | Duplicate email on sign-up | SDK shows error message |
| `429 rate limit exceeded` | 429 | Too many requests | SDK shows rate limit message |
| `400 redirect_to is not an allowed URL` | 400 | Redirect URL not in `redirect_urls` | SDK shows error message |

### Mobile client errors

Mobile clients handle errors similarly to browser clients but with additional considerations:

- **Deep link failures**: If the deep link URL is not intercepted correctly, the OAuth2 flow fails. Ensure the app's URL scheme is registered in the platform's configuration.
- **Network errors**: Mobile apps may have intermittent connectivity. The SDK should implement retry logic for transient network errors.
- **Secure storage failures**: If the secure storage is compromised, tokens must be revoked immediately. The SDK should detect secure storage failures and clear stored tokens.
- **Biometric authentication failures**: If biometric authentication fails, the SDK should fall back to password authentication or session restoration.
- **Background state**: When the app returns from the background, the SDK should check if the token has expired and refresh if necessary.

### Backend client errors

| Error | Status | Cause | Handling |
| --- | --- | --- | --- |
| `401 invalid refresh token` | 401 | Token expired or revoked | Log the error and re-authenticate |
| `401 session revoked` | 401 | Session was explicitly revoked | Log the error and re-authenticate |
| `401 theft detected` | 401 | Refresh token was already rotated | Log the error, sign out all sessions |
| `403 forbidden` | 403 | Service key lacks permissions | Check the service key's permissions |
| `409 an account with this email already exists` | 409 | Duplicate email on creation | Handle gracefully (update existing user) |
| `429 rate limit exceeded` | 429 | Too many requests | Implement exponential backoff |
| `500 internal server error` | 500 | Server-side error | Retry with exponential backoff |
| `502 bad gateway` | 502 | Gateway error | Retry with exponential backoff |
| `503 service unavailable` | 503 | Service unavailable | Retry with exponential backoff |
| `504 gateway timeout` | 504 | Gateway timeout | Retry with exponential backoff |

### Error classification and handling

Errors can be classified into four categories:

1. **Client errors (4xx)**: The request is invalid. The client should not retry without fixing the request. Examples: `400`, `401`, `403`, `404`, `409`, `422`.
2. **Rate limit errors (429)**: Too many requests. The client should wait and retry after the `retry_after` period.
3. **Server errors (5xx)**: The server encountered an error. The client should retry with exponential backoff.
4. **Network errors**: The request failed due to a network issue. The client should retry with exponential backoff.

## Common mistakes

<AccordionGroup>
  <Accordion title="Storing tokens in localStorage">
    This is vulnerable to XSS attacks. The SDK should use httpOnly cookies or secure storage. Never store tokens in localStorage or sessionStorage. If the SDK stores tokens in localStorage, any XSS vulnerability in the application can steal all authenticated sessions.
  </Accordion>
  <Accordion title="Exposing service keys in client-side code">
    Service keys have full admin access — exposing them in client-side code gives anyone who can inspect the page full control over all user accounts. Always use service keys from backend servers. Service keys should never appear in browser DevTools, mobile app binaries, or any client-side artifact.
  </Accordion>
  <Accordion title="Not configuring CORS in production">
    Without CORS configuration, the server accepts requests from any origin. This allows any website to make authenticated requests to the Pawabase API. Always configure `cors_origins` in production with an explicit allow-list.
  </Accordion>
  <Accordion title="Not handling the `signedOut` event">
    When the SDK emits `signedOut`, the client must redirect the user to the sign-in page. Ignoring this event leads to users making API calls with expired tokens, resulting in confusing error messages and a poor user experience.
  </Accordion>
  <Accordion title="Assuming refresh tokens never expire">
    They do — refresh tokens have a configurable lifetime (`refresh_token_ttl`, default 30 days). After that, the user must sign in again. The SDK should handle the case where the refresh token has expired by redirecting the user to the sign-in page.
  </Accordion>
  <Accordion title="Not implementing retry logic for backend clients">
    Backend clients should implement exponential backoff for rate-limited errors (429) and server errors (500). Without retry logic, transient failures cause permanent errors. The retry logic should include exponential backoff with jitter and a maximum retry count.
  </Accordion>
  <Accordion title="Ignoring theft detection">
    If the `theftDetected` event fires, the SDK should alert the user and sign out all sessions. Ignoring this signal leaves the attacker's session active and the legitimate user vulnerable to further unauthorized access.
  </Accordion>
  <Accordion title="Using the same service key across multiple environments">
    If a key is compromised in `development`, it's also compromised in `production`. Use separate service keys for each environment. Each environment should have its own service key with appropriate permissions.
  </Accordion>
  <Accordion title="Not setting `refreshThreshold` appropriately">
    A `refreshThreshold` that is too high causes unnecessary refresh requests. A threshold that is too low causes tokens to expire before the refresh completes. The default of 60 seconds is a good starting point for most applications.
  </Accordion>
  <Accordion title="Not validating redirect URLs in production">
    Without proper `site_url` and `redirect_urls` configuration, an attacker can redirect users to malicious URLs after sign-in. Always configure `site_url` and an explicit `redirect_urls` allow-list in production.
  </Accordion>
</AccordionGroup>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `401 invalid refresh token` in SDK | Token expired or was rotated | SDK handles automatically — check if `signedOut` event was emitted |
| `CORS error` in browser | Origin not in `cors_origins` | Configure `cors_origins` to include the app's origin |
| `403 forbidden` with service key | Service key lacks the required permission | Check the service key's permissions in the admin dashboard |
| `400 email and password are required` | Missing email or password in sign-in request | Ensure both fields are provided |
| `403 magic links are disabled` | `magic_link_enabled` is `false` | Enable magic links in the configuration or use a different sign-in method |
| Deep link not intercepted on mobile | URL scheme not registered | Register the URL scheme in the platform's configuration |
| `theftDetected` event fires unexpectedly | Another device used the refresh token | Alert the user, sign out all sessions, and re-authenticate |
| Tokens not persisting across page refresh | Using `memory` storage | Switch to `cookie` storage or `localStorage` (with security warnings) |
| `403 aal2 authentication required` on refresh | `require_aal` check failed | User needs to complete MFA to elevate their session |
| `409 an account with this email already exists` | User already exists | Use sign-in instead of sign-up, or use a different email |

## FAQ

<AccordionGroup>
  <Accordion title="Can I use multiple SDK instances?">
    Yes — you can create multiple `createClient` instances with different publishable keys for different projects or environments. Each instance manages its own tokens and sessions independently. This is useful for multi-tenant applications where the same user might have accounts in different projects.
  </Accordion>
  <Accordion title="Can I use the SDK with a custom API gateway?">
    The SDK is configured to use the Pawabase gateway URL. If you're using a custom gateway, configure the `gatewayUrl` option in the SDK initialization. All API calls will be directed to the custom gateway.
  </Accordion>
  <Accordion title="Does the SDK support SSR?">
    Yes — the SDK can be used in server-side rendering contexts. Token storage should be configured to use server-side sessions (e.g., HTTP-only cookies) rather than client-side storage. The `tokenStorage: 'memory'` option is recommended for SSR.
  </Accordion>
  <Accordion title="Can I use the SDK without auto-refresh?">
    Yes — set `autoRefresh: false` in the SDK configuration. You'll need to manually call `client.auth.refresh()` before each API call that requires an access token. This is useful for applications that need precise control over when tokens are refreshed.
  </Accordion>
  <Accordion title="How do I handle token expiration in a polling app?">
    For polling apps (e.g., background workers), use a service key instead of the SDK. Service keys authenticate directly with the API and don't need token refresh handling. The SDK is designed for interactive applications, not long-running background processes.
  </Accordion>
  <Accordion title="What is the maximum number of concurrent sessions?">
    Pawabase does not limit the number of concurrent sessions per user. Each sign-in creates a new `SessionInfo` row. All sessions remain valid until explicitly revoked or until the refresh token TTL expires.
  </Accordion>
  <Accordion title="How does the SDK handle token rotation transparently?">
    When the SDK refreshes a token, it automatically updates the stored refresh token. The application does not need to handle the rotation manually — the SDK stores the new refresh token and uses it for subsequent refresh requests. Only if the refresh fails does the SDK emit events for the application to handle.
  </Accordion>
  <Accordion title="Can I use the SDK with a WebSocket connection?">
    Yes — the SDK provides `client.auth.getAccessToken()` to retrieve the current access token for WebSocket authentication. The token should be sent as a query parameter or in the `Authorization` header when establishing the WebSocket connection. The token should be refreshed independently of the SDK's HTTP client.
  </Accordion>
</AccordionGroup>
