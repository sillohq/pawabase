Social login allows users to sign in using their existing accounts on third-party providers such as Google, GitHub, Apple, Microsoft, Facebook, or LinkedIn. Pawabase implements OAuth2/OIDC flows for each provider, handling the redirect to the provider, the callback, and the creation or linking of user accounts.

Social login is configured through the `providers` object in the environment configuration. Each provider has its own client ID, client secret, and configuration. Pawabase supports built-in providers (pre-configured for popular services) and generic providers (for any OAuth2/OIDC-compliant service).

## How social login works

The social login flow follows the OAuth2/OIDC protocol:

<Steps>
  <Step title="User initiates social login">
    The user clicks the "Sign in with [Provider]" button. The client redirects the user to Pawabase's authorization endpoint.
  </Step>
  <Step title="Redirect to provider">
    Pawabase redirects the user to the provider's authorization URL with the appropriate scope and state parameter.
  </Step>
  <Step title="User authenticates with provider">
    The user signs in to the provider's website and authorizes the requested scopes.
  </Step>
  <Step title="Provider redirects back">
    The provider redirects back to Pawabase with an authorization code.
  </Step>
  <Step title="Pawabase exchanges code for tokens">
    Pawabase exchanges the authorization code for access and ID tokens from the provider.
  </Step>
  <Step title="Claims are extracted and mapped">
    Pawabase extracts the user's identity from the ID token and maps the provider's claims to Pawabase's user model.
  </Step>
  <Step title="Session is created">
    Pawabase creates or links the user account and creates a session with `method: "social"`.
  </Step>
</Steps>

### The OAuth2/OIDC flow

The flow is implemented using the standard OAuth2 authorization code flow with PKCE (Proof Key for Code Exchange) for additional security:

1. **Authorization request**: Pawabase constructs the authorization URL with the provider's client ID, redirect URI, scope (typically `openid email profile`), state parameter (for CSRF protection), and PKCE code challenge.
2. **User authentication**: The user authenticates with the provider and grants the requested scopes.
3. **Authorization code**: The provider redirects back to Pawabase's callback URL with an authorization code.
4. **Token exchange**: Pawabase exchanges the authorization code for tokens using the provider's token endpoint. The PKCE code verifier is included to complete the PKCE flow.
5. **ID token validation**: Pawabase validates the ID token signature, issuer, audience, and expiration.
6. **Claims extraction**: Pawabase extracts the user's identity claims from the ID token.

<Warning>
Always use PKCE in the OAuth2 flow. PKCE prevents authorization code interception attacks where an attacker steals the authorization code and tries to exchange it for tokens. Without PKCE, the authorization code is vulnerable to interception.
</Warning>

## Provider configuration

Providers are configured through the `providers` object in the environment settings:

```python
providers = {
    "google": {
        "client_id": "your-google-client-id",
        "client_secret": "your-google-client-secret",
        "redirect_uri": "https://yourapp.com/auth/callback/google",
        "scope": "openid email profile",
        "enabled": True,
    },
    "github": {
        "client_id": "your-github-client-id",
        "client_secret": "your-github-client-secret",
        "redirect_uri": "https://yourapp.com/auth/callback/github",
        "scope": "read:user user:email",
        "enabled": True,
    },
    "apple": {
        "client_id": "your-apple-client-id",
        "client_secret": "your-apple-client-secret",
        "redirect_uri": "https://yourapp.com/auth/callback/apple",
        "scope": "name email",
        "enabled": True,
    },
}
```

### Built-in providers

Pawabase includes pre-configured settings for the following providers:

- **Google**: Uses Google's OAuth2/OIDC endpoint. Scopes: `openid email profile`. The Google ID token includes the `sub`, `email`, `name`, and `picture` claims.
- **GitHub**: Uses GitHub's OAuth2 endpoint. Scopes: `read:user user:email`. GitHub does not have a standard OIDC endpoint; Pawabase uses the GitHub API to fetch user profile data.
- **Apple**: Uses Apple's Sign in with Apple flow. Scopes: `name email`. Apple provides a `sub` claim, `email`, and `name`. Apple may provide a private relay email (`privaterelay.appleid.com`) that forwards to the user's real email.
- **Microsoft**: Uses Microsoft's Azure AD/OIDC endpoint. Scopes: `openid email profile`. The Microsoft ID token includes standard OIDC claims.
- **Facebook**: Uses Facebook's OAuth2 flow. Scopes: `email public_profile`. Facebook requires additional API calls to fetch email and profile data.
- **LinkedIn**: Uses LinkedIn's OAuth2/OIDC endpoint. Scopes: `openid profile email`.

### Generic providers

Any OAuth2/OIDC-compliant provider can be added as a generic provider:

```python
providers = {
    "my-custom-provider": {
        "client_id": "your-client-id",
        "client_secret": "your-client-secret",
        "redirect_uri": "https://yourapp.com/auth/callback/my-custom-provider",
        "scope": "openid email profile",
        "authorization_url": "https://provider.com/oauth/authorize",
        "token_url": "https://provider.com/oauth/token",
        "userinfo_url": "https://provider.com/oauth/userinfo",
        "enabled": True,
    },
}
```

The generic provider configuration requires:

- **`authorization_url`**: The provider's authorization endpoint.
- **`token_url`**: The provider's token endpoint.
- **`userinfo_url`**: The provider's userinfo endpoint (optional if the ID token contains all required claims).
- **`scope`**: The OAuth2 scopes to request.
- **`client_id` and `client_secret`**: The provider's credentials.
- **`enabled`**: Whether the provider is active.

## Claims mapping

Each provider returns different claims in their ID token or userinfo response. Pawabase maps provider claims to the Pawabase user model:

<CardGroup cols={2}>
  <Card title="Standard claims" icon="check-circle">`sub`, `email`, `name`, and `picture` are mapped from standard OIDC claims.</Card>
  <Card title="Provider-specific claims" icon="gear">Provider-specific claims (e.g., `login` from GitHub) are stored in `auth_providers` and `metadata`.</Card>
</CardGroup>

### Standard claim mapping

| OIDC Claim | Pawabase Field | Description |
| --- | --- | --- |
| `sub` | `auth_providers[provider].id` | The provider's user ID. Used as the unique identifier for the provider account. |
| `email` | `AuthUser.email` | The user's email address. Used for login and communication. |
| `name` | `AuthUser.name` or `metadata.full_name` | The user's display name. |
| `picture` | `metadata.avatar_url` | The URL of the user's profile picture. |
| `email_verified` | `AuthUser.email_verified` | Whether the provider has verified the email address. |

### Provider-specific claims

Providers may include additional claims that are not part of the standard OIDC specification. These claims are stored in the `auth_providers` field of the `AuthUser` record:

```json
{
    "google": {
        "id": "1234567890",
        "locale": "en",
        "verified_email": true
    },
    "github": {
        "id": "987654321",
        "login": "johndoe",
        "company": "Example Corp"
    }
}
```

The `auth_providers` field is a JSON object where each key is the provider name and the value is an object containing all claims from that provider. This allows you to access provider-specific data without modifying the core user model.

## Account linking and unlinking

Users can link multiple social accounts to a single Pawabase account. The account linking logic works as follows:

### Linking accounts

1. When a user signs in with a social provider for the first time, Pawabase creates a new `AuthUser` record with the provider's claims.
2. If the user's email already matches an existing `AuthUser` record, Pawabase links the new provider to the existing account (instead of creating a new one).
3. The provider's `sub` (user ID) and claims are stored in the `auth_providers` field of the existing account.
4. The `auth_providers` array is updated to include the new provider.

### Unlinking accounts

Users can unlink social accounts through the self-service API:

```bash
curl -X DELETE "$GW/auth/v1/social/link/{provider}" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json"
```

When a provider is unlinked:

1. The provider's `sub` and claims are removed from `auth_providers`.
2. The user can still sign in using other linked providers or their password.
3. If all social providers are unlinked and the user has no password, the account is locked — the user must set a password to regain access.

<Warning>
Unlinking the last social provider for an account that has no password will lock the account. The user will be unable to sign in until they set a password through the password recovery flow.
</Warning>

### Email matching for linking

When a user signs in with a social provider, Pawabase checks if the provider's email matches an existing `AuthUser` record:

1. The provider's `email` claim is extracted.
2. Pawabase looks up `AuthUser` records with a matching email.
3. If a match is found, the provider is linked to the existing account.
4. If no match is found and `magic_link_create_account` is `true`, a new account is created.
5. If no match is found and `magic_link_create_account` is `false`, the sign-in fails with `404 user not found`.

<Note>
Email matching is case-insensitive. `User@example.com` and `user@example.com` are treated as the same email for account linking purposes.
</Note>

## Social login and MFA

Social login interacts with MFA (Multi-Factor Authentication) in the following ways:

1. **MFA is optional for social login**: By default, social login sign-in produces an `aal1` session even if the user has MFA enabled. The MFA challenge is not automatically triggered.
2. **MFA can be required**: If the environment or organization has `require_mfa` enabled, the user will be prompted for their TOTP code after the social login callback.
3. **MFA state is preserved**: If the user has MFA enabled and completes the MFA challenge, the session's AAL is elevated to `aal2`.

```
Social login → aal1 → (MFA prompt if required) → aal2 session
```

### MFA enforcement with social login

When `require_mfa` is enabled at the environment or organization level:

1. After the social login callback, Pawabase checks if the user has MFA enabled.
2. If MFA is enabled and the session AAL is below `min_aal`, the user is prompted for their TOTP code.
3. The TOTP code is validated against the stored `mfa_secret`.
4. If valid, the session AAL is elevated to `aal2`.
5. If invalid, the sign-in fails with `401 invalid MFA code`.

### MFA recovery and social login

If the user has lost access to their TOTP device, they can use their MFA recovery codes to sign in. MFA recovery codes work with social login just as they do with password sign-in:

1. After the social login callback, the user is prompted for an MFA code or recovery code.
2. If a recovery code is entered, it is validated against the stored `MFARecoveryCode` records.
3. If valid, the session AAL is elevated to `aal2` and the recovery code is marked as used.

## Security considerations

Social login introduces several security considerations that must be addressed:

### CSRF protection

The OAuth2 flow is vulnerable to CSRF attacks where an attacker tricks a user into authorizing an application they didn't intend to. Pawabase protects against CSRF through:

1. **State parameter**: A random `state` parameter is included in the authorization request and verified in the callback. If the state doesn't match, the callback is rejected.
2. **PKCE**: The PKCE code challenge and verifier prevent authorization code interception attacks.
3. **Redirect URI validation**: The redirect URI must exactly match a registered URI. Pawabase validates the redirect URI against the configured list.

### Token storage

The provider's access token (which Pawabase receives) is stored securely:

1. **Access tokens**: Not stored persistently — they are used to fetch user profile data and then discarded. Pawabase only needs the ID token to authenticate the user.
2. **ID tokens**: Validated and then discarded — the claims are extracted and used to create or update the user account.
3. **Provider credentials**: The `client_id` and `client_secret` are stored in the environment configuration, encrypted at rest. They should never be exposed in client-side code.

### Account takeover prevention

An attacker could potentially take over an account by signing in with a different provider that has the same email. Pawabase prevents this through:

1. **Email verification**: The provider's `email_verified` claim is checked. If the provider hasn't verified the email, the sign-in is more carefully evaluated.
2. **Provider linking**: If a new provider's email matches an existing account, the provider is linked to that account rather than creating a new one.
3. **Password requirement**: If an account has a password, the password must be verified before linking a new social provider (to prevent an attacker from linking a provider to an account they don't own).

### Redirect URI validation

The redirect URI must be validated to prevent open redirect vulnerabilities:

1. Only pre-registered redirect URIs are accepted.
2. Wildcard redirect URIs are not allowed.
3. The redirect URI must match exactly (scheme, host, port, path).

<Warning>
Never allow dynamic redirect URIs in production. An attacker could register a redirect URI pointing to their own server and intercept the authorization code or tokens.
</Warning>

## Common mistakes

<AccordionGroup>
  <Accordion title="Not using PKCE">
    Without PKCE, the authorization code can be intercepted and exchanged for tokens by an attacker. Always use PKCE in the OAuth2 flow.
  </Accordion>
  <Accordion title="Not validating the state parameter">
    The state parameter prevents CSRF attacks. If the state is not validated, an attacker could trick a user into authorizing an unintended application.
  </Accordion>
  <Accordion title="Allowing unverified emails for account linking">
    If a provider hasn't verified the email, linking it to an existing account could allow an attacker to take over that account. Always check `email_verified` before linking.
  </Accordion>
  <Accordion title="Storing provider access tokens persistently">
    Pawabase doesn't need to store provider access tokens persistently. They are used briefly to fetch profile data and then discarded. Storing them creates an unnecessary security risk.
  </Accordion>
  <Accordion title="Not configuring MFA for social login">
    If your application requires MFA, social login alone (aal1) is insufficient. Always enforce `require_mfa` for sensitive applications.
  </Accordion>
</AccordionGroup>
