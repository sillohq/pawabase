Social sign-in in Pawabase is built on `sillo-oauth`, a standalone OAuth 2.0/OIDC client library. Akountz configures providers per environment, drives the redirect and callback, and decides what a verified external identity means for an account — `sillo-oauth` itself never touches Akountz's database or knows what a user is.

<CardGroup cols={3}>
  <Card title="Four shipped providers" icon="check-circle">Google, GitHub, Discord and Microsoft ship with sensible defaults. Anything else is a generic OAuth 2.0/OIDC provider.</Card>
  <Card title="The redirect URI is computed, not configured" icon="lock">`redirect_uri` is built server-side from the environment; it is never a field you set in provider configuration.</Card>
  <Card title="One identity, many providers" icon="link">A single account can link Google, GitHub, Discord and Microsoft simultaneously through the `Identity` table.</Card>
</CardGroup>

## The shipped providers

`app/oauth.py` maps four provider names to `sillo-oauth` classes:

```python
SHIPPED = {
    "google": GoogleOAuthProvider,
    "github": GithubOAuthProvider,
    "discord": DiscordOAuthProvider,
    "microsoft": MicrosoftOAuthProvider,
}
```

<Warning>
The shipped list is **Google, GitHub, Discord, and Microsoft** — not Apple, Facebook, or LinkedIn. Documentation or examples naming those three do not match the current implementation. If you need a provider outside this list (including Apple, Facebook, LinkedIn, GitLab, or an internal OIDC identity provider), configure it as a [generic provider](#generic-providers) with its own endpoints.
</Warning>

Each shipped provider has built-in defaults for its endpoints and default scopes, defined in `sillo-oauth`:

| Provider | Default scopes | Notable behavior |
| --- | --- | --- |
| `google` | `openid`, `email`, `profile` | OIDC; `email_verified` is meaningful — Google states it, so it's safe to auto-match an existing account by email. |
| `github` | `read:user`, `user:email` | Not OIDC. PKCE is off (GitHub's OAuth app flow doesn't support it). If `/user` withholds the email (a private-email setting), a second call to `/user/emails` finds the primary verified address. `email_verified` is only ever `true` when the address came from that emails endpoint. |
| `discord` | `identify`, `email` | Not OIDC. Discord returns an avatar *hash*, not a URL — the provider builds the CDN link itself (`https://cdn.discordapp.com/avatars/{id}/{hash}.png`). `verified` in Discord's payload is about the email address, not the whole account. |
| `microsoft` | `openid`, `email`, `profile` | OIDC (Entra ID / Microsoft identity platform). Endpoints are tenant-scoped — `tenant` defaults to `"common"` (personal and work accounts both accepted). Microsoft's userinfo endpoint does not return `email_verified`, so it's always reported as `false` (meaning "not stated," not "unverified"). |

### Configuring a shipped provider

Each provider is configured under `providers` in the environment's `auth` block, keyed by name:

```json
{
  "providers": {
    "google": {
      "client_id": "1234567890-abc.apps.googleusercontent.com",
      "client_secret": "secret://GOOGLE_CLIENT_SECRET",
      "enabled": true
    },
    "github": {
      "client_id": "Iv1.a1b2c3d4e5f6",
      "client_secret": "secret://GITHUB_CLIENT_SECRET"
    },
    "discord": {
      "client_id": "1122334455667788",
      "client_secret": "secret://DISCORD_CLIENT_SECRET"
    },
    "microsoft": {
      "client_id": "11111111-2222-3333-4444-555555555555",
      "client_secret": "secret://MICROSOFT_CLIENT_SECRET",
      "tenant": "common"
    }
  }
}
```

| Field | Applies to | Meaning |
| --- | --- | --- |
| `client_id` | every provider | The OAuth application's public client id. Required — a provider with no `client_id` is treated as not configured. |
| `client_secret` | every provider | The application's secret. `secret://NAME` resolves it from the project's secret store rather than storing it in plain JSON. |
| `enabled` | every provider | Defaults to `true`. Set `false` to configure credentials without exposing the provider yet. |
| `tenant` | `microsoft` only | Directory to authenticate against: a tenant id, `"common"`, `"organizations"`, or `"consumers"`. |
| `scopes` | every provider | A **list of strings**, overriding the provider's default scopes. |
| `authorize_params` | every provider | An object of extra query parameters merged into every authorize URL, e.g. `{"access_type": "offline", "prompt": "consent"}` to request a Google refresh token. |

A provider only counts as enabled for `GET /auth/v1/settings` and for the authorize endpoint when it has `enabled: true` (or the field is absent) **and** a non-empty `client_id`:

```python
def enabled_providers(self) -> list[str]:
    return sorted(
        name for name, conf in self.providers.items()
        if conf.get("enabled", True) and conf.get("client_id")
    )
```

<Warning>
The field is `scopes` (a JSON array), never `scope` as a single space-delimited string. Passing `"scope": "openid email"` as a string is silently ignored — `build_provider` only reads `settings.get("scopes")` as a list.
</Warning>

## Generic providers

Any provider name that isn't one of the four shipped ones is built as a plain `OAuthProvider` — Pawabase's baseline OAuth 2.0/OIDC client — as long as three endpoints are supplied:

```json
{
  "providers": {
    "gitlab": {
      "client_id": "abcdef1234567890",
      "client_secret": "secret://GITLAB_CLIENT_SECRET",
      "authorize_endpoint": "https://gitlab.com/oauth/authorize",
      "token_endpoint": "https://gitlab.com/oauth/token",
      "userinfo_endpoint": "https://gitlab.com/api/v4/user",
      "scopes": ["read_user"]
    }
  }
}
```

The three endpoint fields are the **real** field names for a generic provider:

| Field | Required | Meaning |
| --- | --- | --- |
| `authorize_endpoint` | Yes | Where the browser is redirected to start the flow. |
| `token_endpoint` | Yes | Where the authorization code is exchanged for tokens. |
| `userinfo_endpoint` | Yes | Where the verified profile is fetched with the access token. |

Missing any of the three raises `500 provider '<name>' needs authorize, token and userinfo endpoints` the first time that provider is used, from `build_provider`:

```python
if not all(settings.get(key) for key in GENERIC_KEYS):
    raise HTTPException(
        status_code=500,
        detail=f"provider {name!r} needs authorize, token and userinfo endpoints",
    )
return OAuthProvider(name=name, **options, **{key: settings[key] for key in GENERIC_KEYS})
```

If the provider speaks OIDC, adding `"openid"` to `scopes` is what triggers OIDC-aware behavior in `sillo-oauth`; the field names themselves (`authorize_endpoint`/`token_endpoint`/`userinfo_endpoint`) don't change between OAuth 2.0 and OIDC providers.

A generic provider maps its userinfo response onto a profile with a best-effort default: it looks for a subject under `sub`, `id`, `user_id` or `uid` in that order, and picks up `email`/`name`/`username`/`avatar_url` under their most common key names (`preferred_username`, `picture`). If your provider uses non-standard field names, you'll need a provider-specific integration rather than the generic client — the generic mapping has no per-field override in the JSON configuration.

<Note>
The same three-field shape (`authorize_endpoint`, `token_endpoint`, `userinfo_endpoint`) can also *override* one of the four shipped providers' defaults — useful for a self-hosted GitLab-compatible GitHub Enterprise instance, or a Google Workspace domain with custom endpoints. `build_provider` applies any of these three keys on top of the shipped class's built-in defaults when they're present.
</Note>

## The redirect URI is never user-configured

Unlike the old assumption that `redirect_uri` is something you set per provider, it is **always computed server-side** by Akountz, from the environment identity, never read from provider configuration:

```python
def callback_url(akountz: Akountz, config: AuthConfig, provider: str) -> str:
    base = (config.public_url or akountz.settings.public_url).rstrip("/")
    return f"{base}/auth/v1/callback/{config.project}/{config.env}/{provider}"
```

This means the URL you register with each OAuth provider's developer console is deterministic and always has the shape:

```
https://<your-public-url>/auth/v1/callback/{project}/{env}/{provider}
```

For example, `https://api.pawabase.com/auth/v1/callback/acme/production/google`. There is no field in the `providers` object that changes this — supplying a `redirect_uri` in provider configuration has no effect; `build_provider` always overrides it with `callback_url(...)`.

<Warning>
Register exactly this computed URL — one per `(project, env, provider)` combination — in each provider's developer console. A mismatch here is the single most common cause of OAuth sign-in failures, and it always surfaces as the provider's own generic "redirect URI mismatch" error, before Akountz is even involved.
</Warning>

## The authorize → callback flow

<Steps>
  <Step title="GET /auth/v1/authorize/{project}/{env}/{provider}">
    A browser navigation (not an API call — there's no API key header on this request; the environment comes from the path). Optionally takes `?redirect_to=` (where the client wants to land afterward — validated against the environment's `site_url`/`redirect_urls`) and, for account linking, `?link_token=`.

    Akountz builds the provider object from configuration, asks `sillo-oauth` for an authorize URL, and redirects the browser there with a signed state cookie:

    ```python
    authorize = authorize_url(provider_obj, return_to=json.dumps(state))
    return redirect(authorize.url).set_cookie(**authorize.cookie_kwargs(secure=secure))
    ```

    The state cookie is `httponly`, `samesite=lax`, and (in production, where `public_url` starts with `https://`) `secure`. It's namespaced per provider so two sign-in attempts started in two tabs don't clobber each other, and it's signed with a per-`(project, env)` derived secret (`akountz.state_secret(project, env)`) so a callback can't be replayed against a different environment.
  </Step>
  <Step title="The user authenticates with the provider">
    Entirely outside Pawabase — the provider's own consent screen.
  </Step>
  <Step title="GET /auth/v1/callback/{project}/{env}/{provider}">
    The provider redirects back here. `sillo_oauth.exchange(provider_obj, ctx)` verifies the state cookie against the callback's `state` parameter, trades the authorization code for tokens, and fetches the profile — returning an `OAuthProfile` or raising `OAuthError`.
  </Step>
</Steps>

### What's inside an `OAuthProfile`

```python
@dataclass(frozen=True)
class OAuthProfile:
    provider: str
    subject: str
    email: str | None = None
    email_verified: bool = False
    name: str | None = None
    username: str | None = None
    avatar_url: str | None = None
    raw: dict[str, Any] = field(default_factory=dict)
    tokens: OAuthTokens | None = None
    return_to: str | None = None
```

`subject` is the only field ever safe to key a local account on — it's the provider's own stable identifier, unlike an email address (which can be reassigned) or a username (which can be renamed). Akountz looks up `Identity` rows by `(project, env, provider, subject)`, never by email alone, for an *existing* linked identity.

## What happens with the verified profile

The callback handler follows this decision order:

<Steps>
  <Step title="Already linked?">
    Look up `Identity` by `(project, env, provider, subject)`. If found, this is the account — no other checks needed, and this is also the path a second sign-in from the same provider always takes.
  </Step>
  <Step title="Explicit link in progress?">
    If the authorize request carried a `link_token` (see [Linking a provider to an existing account](#linking-a-provider-to-an-existing-account)), the token is consumed and its user becomes the target — but only if no *other* account already has this exact provider identity linked (`identity_already_linked` otherwise).
  </Step>
  <Step title="Match by verified email?">
    If the provider reports `email_verified: true`, Akountz looks for an existing account with that email in this environment and attaches the new identity to it. **An unverified email never triggers this match** — only a provider-asserted verified address can attach to an existing account, closing the door on an attacker registering an unverified address that happens to match a victim's account.
  </Step>
  <Step title="Otherwise, create a new account">
    Only if `signup_enabled` is `true` (`signup_disabled` error otherwise) and the profile has an email (`email_required` otherwise — a provider that returns no email at all cannot create an account through this path). If an account with that email already exists but the provider's email wasn't verified, the callback refuses with `email_unverified_conflict` rather than silently attaching to (or shadowing) an existing account.
  </Step>
</Steps>

A newly created account gets `create_account(..., password=None, username=profile.username, name=profile.name or "", verified=profile.email_verified)` — password sign-in is unusable until the user sets one — and its `avatar_url` is set from the profile immediately after creation.

### Errors, as redirect fragments or JSON

Every failure in the callback maps to a short error code. If the flow has a `redirect_to` target, the code comes back as `#error=<code>` on that URL; otherwise it's a `400` with `"sign-in failed: <code>"`.

| Code | Meaning |
| --- | --- |
| `denied` | The user declined consent at the provider. Not a fault — treat as "back to login." |
| `state_mismatch` | No state cookie, a forged/tampered cookie, or a cookie from a different provider. |
| `state_expired` | The state cookie's `max_age` passed — the user took too long at the provider's screen. |
| `provider_error` | The provider redirected back with its own `error` parameter (invalid scope, misconfigured client, etc.). |
| `exchange_failed` | The authorization code could not be traded for tokens (stale/replayed code, redirect URI mismatch, bad client credentials). |
| `profile_failed` | A token was obtained but the userinfo call failed, returned non-JSON, or had no usable subject. |
| `signup_disabled` | No account matched, `signup_enabled` is `false`. |
| `email_required` | No account matched, and the provider returned no email to create one with. |
| `email_unverified_conflict` | An account with this email exists, but the provider's email is unverified, so it can't be trusted to attach. |
| `account_disabled` | The matched or linked account has been disabled by an administrator. |
| `identity_already_linked` | A link was requested, but this exact provider identity is already attached to a different account. |

Every failed callback also logs a `sign_in` event with `method="oauth:<provider>"`, `success=False`, and `reason` set to the error code — visible through `GET /auth/v1/history` for the affected user (when one can be identified) and through the admin events API.

## MFA and social login

If the resolved account has `mfa_enabled` and the environment allows MFA, the callback issues an MFA challenge instead of a session — exactly the same challenge shape used by the password grant:

```python
if user.mfa_enabled and config.mfa_enabled:
    challenge = await links.issue(akountz, config, "mfa", user=user, data={"method": f"oauth:{provider}"})
    payload = {"mfa_required": "true", "mfa_token": challenge}
```

The client completes it the same way as any other MFA challenge — `POST /auth/v1/token` with `grant_type: "mfa"`. See [MFA → MFA during sign-in](/auth/mfa#mfa-during-sign-in).

## Linking and unlinking identities

A signed-in user can attach an additional provider to their existing account, or detach one they no longer use.

### Linking a provider to an existing account

```bash
curl -X POST "$GW/auth/v1/identities/link?provider=github" \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "apikey: $PAWABASE_PUBLISHABLE_KEY"
```

```json
{ "url": "https://api.pawabase.com/auth/v1/authorize/acme/production/github?link_token=..." }
```

This mints a short-lived (10-minute) one-time `link` token bound to the signed-in user and the target provider, and returns a URL the client should navigate to. That URL is the *same* authorize endpoint used for ordinary sign-in, just carrying `link_token` in the query string — the authorize handler threads it through the OAuth state, and the callback consumes it to attach the new identity to the already-known user instead of running the sign-in matching logic.

### Unlinking an identity

```bash
curl -X DELETE "$GW/auth/v1/identities/42" \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "apikey: $PAWABASE_PUBLISHABLE_KEY"
```

Blocked with `409 set a password before removing your only sign-in method` if this is the user's *last* identity and they have no usable password — otherwise removing it would lock them out entirely, since the account would have neither a password nor any linked provider left to sign in with.

```python
if not user.has_usable_password() and await Identity.filter(user=user).count() <= 1:
    raise HTTPException(status_code=409, detail="set a password before removing your only sign-in method")
```

## The `Identity` model

```python
class Identity(Model):
    id = fields.IntField(primary_key=True)
    user = fields.ForeignKeyField("models.AuthUser", related_name="identities", on_delete=fields.CASCADE)
    project = fields.CharField(max_length=63)
    env = fields.CharField(max_length=63)
    provider = fields.CharField(max_length=64)
    subject = fields.CharField(max_length=255)
    email = fields.CharField(max_length=255, null=True)
    email_verified = fields.BooleanField(default=False)
    data = AnyJSONField(default=dict)
    last_sign_in_at = fields.DatetimeField(null=True)

    class Meta:
        unique_together = (("project", "env", "provider", "subject"),)
```

`data` holds the provider's raw userinfo payload (`profile.raw`) verbatim, refreshed on every sign-in through that identity — useful if your application needs a field the standard `OAuthProfile` mapping doesn't surface (a GitHub organization membership list, for instance). `GET /auth/v1/user` surfaces a stripped view of every linked identity: `id`, `provider`, `email`, and `last_sign_in_at`.

## Real scenarios

### Social-login-only signup

To offer a product where users only ever sign up through Google or GitHub, with no password form at all: leave `signup_enabled: true`, configure only the providers you want, and simply never build a password sign-up form in your client. Accounts created this way have `has_usable_password() == false` until the user explicitly sets one later, which is fine — nothing about Akountz requires a usable password to exist.

### Requiring a corporate Microsoft tenant

Restrict sign-in to one organization's directory by setting `tenant` to that organization's tenant id instead of `"common"`:

```json
{ "providers": { "microsoft": { "client_id": "...", "client_secret": "secret://MS_SECRET", "tenant": "8f14e...-tenant-id" } } }
```

A personal Microsoft account, or an account from a different organization's tenant, will fail at Microsoft's own consent screen before ever reaching Akountz's callback.

### Migrating a user from password to social-only

A user who wants to drop their password and rely solely on, say, Google: they link Google first (`POST /identities/link`), confirm it succeeded, and only then would an application choose to let them clear their password — Akountz itself has no "remove my password" endpoint; `PATCH /auth/v1/user` only ever *sets* a new password, it cannot unset one back to "unusable." In practice, most products simply leave the password set (unused) rather than trying to remove it.

## Common mistakes

<AccordionGroup>
  <Accordion title="Listing Apple, Facebook or LinkedIn as shipped providers">
    They aren't. The `SHIPPED` map in `app/oauth.py` has exactly four entries: `google`, `github`, `discord`, `microsoft`. Any other provider name must be configured as a generic OAuth 2.0/OIDC provider with its own three endpoints.
  </Accordion>
  <Accordion title="Setting redirect_uri in provider configuration">
    It has no effect. `callback_url()` always computes it from `public_url`/`site_url` and the `(project, env, provider)` path — register that computed URL with the provider instead.
  </Accordion>
  <Accordion title="Using scope (singular, a string) instead of scopes (a list)">
    `build_provider` only reads `settings.get("scopes")` as a list. A `"scope": "openid email"` string field is ignored entirely, silently falling back to the provider's default scopes.
  </Accordion>
  <Accordion title="Forgetting Discord in a provider list">
    Discord is a fully shipped, first-class provider (`DiscordOAuthProvider`) — it is easy to omit by mistake when writing a provider list from memory rather than from `app/oauth.py`.
  </Accordion>
  <Accordion title="Assuming an unverified email can match an existing account">
    It can't, deliberately. Only `email_verified: true` from the provider triggers a match-by-email against an existing account; an unverified address either creates a new account (if no conflicting account exists) or fails with `email_unverified_conflict`.
  </Accordion>
</AccordionGroup>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `404 the '<name>' provider is not enabled` | Missing `client_id`, or `enabled: false`. | Add the credentials or flip `enabled: true`. |
| Provider's own "redirect URI mismatch" error | The registered callback URL doesn't match `callback_url()`'s computed value. | Recompute `https://<public_url>/auth/v1/callback/{project}/{env}/{provider}` and register exactly that. |
| `500 provider '<name>' needs authorize, token and userinfo endpoints` | A generic provider is missing one of the three required endpoint fields. | Supply `authorize_endpoint`, `token_endpoint`, and `userinfo_endpoint`. |
| `email_unverified_conflict` on sign-in | An account with this email exists, and the provider didn't assert `email_verified: true`. | The user should sign in with their original method and link the provider from within the account instead. |
| `409 identity_already_linked` when linking | This exact provider identity is already attached to a different account. | Unlink it from the other account first, or sign in with that account instead. |
