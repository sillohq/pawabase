Pawabase is designed with security as a first-class concern. Every component of the authentication system — from credential storage to token issuance to session management — follows strict security principles. Understanding the threat model and the security properties of each authentication method is essential for building secure applications with Pawabase.

This page covers the complete security model: the threat model, credential hygiene practices, token rotation security, security properties by authentication method, the production validation checklist, and common security vulnerabilities to avoid.

## Threat model

Pawabase identifies and mitigates the following threat vectors:

### Credential stuffing

Credential stuffing attacks use lists of known username/password pairs to gain unauthorized access. Pawabase mitigates this through:

1. **Password hashing**: All passwords are hashed with bcrypt (cost factor 12). Bcrypt is designed to be computationally expensive, making brute-force attacks impractical.
2. **Rate limiting**: The `/auth/v1/token` endpoint limits sign-in attempts to 5 per 60 seconds per IP address. After 5 failed attempts, the endpoint returns `429 rate limit exceeded`.
3. **Account lockout**: After `mfa_failed_attempts_lockout` (default: 5) failed attempts, the account is locked for a configurable period.
4. **Failed login tracking**: The `failed_logins` counter tracks failed sign-in attempts. The counter resets on successful sign-in or password change.

### Brute-force attacks

Brute-force attacks systematically try every possible password or token. Pawabase mitigates this through:

1. **Rate limiting**: Per-IP and per-user rate limits on all authentication endpoints (`/auth/v1/token`, `/auth/v1/recover`, `/auth/v1/magic-link`).
2. **Account lockout**: Temporary lockout after too many failed attempts.
3. **Token entropy**: Recovery tokens, magic link tokens, and verification codes are cryptographically random (32+ characters), making brute-forcing computationally infeasible.
4. **Password complexity requirements**: Pawabase enforces minimum password length and complexity.

### Token theft

Token theft occurs when an attacker obtains a valid access token or refresh token. Pawabase mitigates this through:

1. **Short-lived access tokens**: Access tokens expire in 900 seconds (15 minutes). Even if stolen, the token is only valid for a short window.
2. **Refresh token rotation**: When `refresh_token_rotation` is enabled, refresh tokens are rotated on every use. A stolen refresh token can only be used once before it is invalidated.
3. **Theft detection**: The `theft_detected` flag on `SessionInfo` indicates that a token was used unexpectedly, signaling possible compromise.
4. **Revocation**: Stolen tokens can be revoked through the admin `POST .../sessions/revoke` endpoint.

<Warning>
Refresh token theft is the most dangerous form of token compromise because refresh tokens are long-lived. Even with rotation, there is a window where the attacker's token is valid. Monitor for unexpected token rotation events.
</Warning>

### Session hijacking

Session hijacking occurs when an attacker takes over a user's active session by obtaining their session ID or refresh token. Pawabase mitigates this through:

1. **Session binding**: Refresh tokens are cryptographically bound to the session through the `refresh_jti` field. A token cannot be used with a different session.
2. **IP address tracking**: The `SessionInfo` row stores the `ip_address` of the device that created the session. Unusual IP changes can signal session hijacking.
3. **User agent tracking**: The `SessionInfo` row stores the `user_agent` string. Changes in user agent can signal session hijacking.
4. **Device info tracking**: The `SessionInfo` row stores `device_info` for additional fingerprinting.

### Account enumeration

Account enumeration occurs when an attacker discovers valid email addresses by observing different responses from authentication endpoints. Pawabase mitigates this through:

1. **Uniform responses**: The `/recover`, `/magic-link`, and `/verify` endpoints always return the same success response regardless of whether the email exists. This prevents attackers from discovering valid email addresses.
2. **No timing differences**: All endpoints return responses in approximately the same time regardless of whether the email exists, preventing timing-based enumeration.
3. **Rate limiting**: Per-IP and per-email rate limits prevent bulk enumeration attacks.

### CSRF attacks

Cross-site request forgery (CSRF) attacks trick a user into submitting unintended requests to the application. Pawabase mitigates this through:

1. **State parameter**: The OAuth2 flow includes a random `state` parameter that is validated in the callback. This prevents CSRF in social login flows.
2. **PKCE**: The Proof Key for Code Exchange (PKCE) mechanism prevents authorization code interception attacks.
3. **CORS validation**: The `cors_origins` configuration restricts which origins can make requests to the API. Requests from unauthorized origins are rejected.
4. **Token-based authentication**: All requests require an access token or service key in the `Authorization` header, making CSRF attacks impractical.

### Man-in-the-middle (MITM) attacks

MITM attacks intercept communication between the client and server. Pawabase mitigates this through:

1. **HTTPS enforcement**: All authentication endpoints require HTTPS. Pawabase enforces TLS on all connections.
2. **Token signing**: Access tokens are signed with the environment's secret key. Even if intercepted, tokens cannot be forged.
3. **Token expiration**: Short-lived access tokens (15 minutes) limit the window of exposure for intercepted tokens.
4. **Refresh token binding**: Refresh tokens are bound to the session through cryptographic signatures, preventing token substitution.

<Warning>
Never disable HTTPS in production. All authentication traffic must be encrypted. Pawabase enforces HTTPS at the gateway level — if you're behind a reverse proxy, ensure TLS is terminated at the proxy and the connection between the proxy and Pawabase is also encrypted.
</Warning>

## Credential hygiene

Credential hygiene refers to how credentials (passwords, tokens, service keys) are stored, transmitted, and handled:

### Password storage

Passwords are stored as bcrypt hashes in the `AuthUser` table:

```python
password_hash = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))
```

- **Bcrypt cost factor**: 12 rounds. This makes bcrypt computationally expensive — each hash takes approximately 250ms to compute on modern hardware.
- **Salt**: Bcrypt automatically generates a unique salt for each password. The salt is embedded in the hash string.
- **No plaintext storage**: Passwords are never stored in plaintext. The `password_hash` field contains only the bcrypt hash.
- **Verification**: Passwords are verified by comparing the hash of the submitted password against the stored hash using `bcrypt.checkpw()`.

<Warning>
Never log passwords, password hashes, or password reset tokens. Never include passwords in error messages, audit logs, or debugging output. Always treat passwords as sensitive data that must never leave the authentication flow.
</Warning>

### Password transmission

Passwords must be transmitted securely:

1. **HTTPS only**: Passwords are sent over HTTPS connections only. Never send passwords over plain HTTP.
2. **Request body only**: Passwords are sent in the request body (`-d` in curl), never in URL parameters or query strings.
3. **No cookies**: Passwords are never stored in cookies — they are transmitted only during the sign-in request.
4. **Client-side handling**: Frontend applications should never store passwords in localStorage, sessionStorage, or JavaScript variables. Passwords should be sent directly to the backend and immediately cleared from memory.

### Memory handling

After password verification, the password must be cleared from memory:

```python
# Verify the password
if not bcrypt.checkpw(password.encode(), stored_hash):
    raise PrincipalException("invalid password")
# Clear the password from memory
del password
```

In Python, `del` removes the reference to the string, but the string may still exist in memory until garbage collection. For higher security, use `secrets.token_bytes` or overwrite the string buffer before deletion.

### Token storage on clients

Where tokens are stored on clients depends on the client type:

| Client Type | Recommended Storage | Risk |
| --- | --- | --- |
| **Browser (web app)** | httpOnly cookies | localStorage is vulnerable to XSS. httpOnly cookies are not accessible to JavaScript. |
| **Mobile (iOS)** | iOS Keychain | Keychain is encrypted and protected by the device's biometric authentication. |
| **Mobile (Android)** | Android Keystore | Keystore is hardware-backed and encrypted. |
| **Backend service** | Environment variables or secret manager | Never hardcode tokens in source code. Use a secret manager (AWS Secrets Manager, HashiCorp Vault, etc.). |

### Service key hygiene

Service keys (publishable and secret keys) are the most sensitive credentials in Pawabase:

1. **Never expose service keys in client-side code**: Publishable keys are meant for client-side use, but secret keys must always be kept on the backend.
2. **Rotate service keys regularly**: Service keys should be rotated periodically (e.g., every 90 days) to limit the exposure window.
3. **Use the principle of least privilege**: Each service key should have only the permissions needed for its task.
4. **Store in a secret manager**: Service keys should be stored in a secret manager (AWS Secrets Manager, HashiCorp Vault, etc.), not in environment variables or configuration files.
5. **Audit service key usage**: Monitor which service keys are being used, from which IPs, and for which operations.

<Warning>
A leaked secret key gives the attacker full administrative access to the environment — they can create, update, and delete any user, manage all sessions, and modify roles and permissions. Treat secret keys with the same security as root passwords.
</Warning>

## Token rotation and security

Token rotation is a core security feature of Pawabase's authentication system:

### The `RevokedToken` table

The `RevokedToken` table provides an additional revocation mechanism:

```sql
CREATE TABLE auth_revoked_token (
    id UUID PRIMARY KEY,
    session_id UUID NOT NULL REFERENCES auth_session(id),
    jti VARCHAR(255) NOT NULL,
    revoked_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

Every time a session is revoked, the `jti` of the refresh token is recorded in the `RevokedToken` table. On every refresh attempt, the server checks whether the refresh token's `jti` appears in the `RevokedToken` table. If it does, the token is rejected even if the session hasn't been explicitly marked as revoked.

### How token rotation prevents replay attacks

Token rotation prevents replay attacks by ensuring that each refresh token can only be used once:

1. **User A** has refresh token `rft_A` for session `S1`.
2. **Attacker** steals `rft_A` and sends it to `/auth/v1/token`.
3. **Server** validates `rft_A`, issues new tokens, and rotates — `rft_A` is now invalid.
4. **User A** later sends `rft_A` to `/auth/v1/token`.
5. **Server** rejects `rft_A` because it was already used (it was rotated in step 3).
6. **Attacker** also sent `rft_A` in step 3, so the attacker's token is also now invalid.
7. Both User A and the attacker have new valid tokens — but the legitimate user can detect the theft because their token was unexpectedly rotated.

### Token expiration vs session expiration

Access tokens and sessions have independent expiration:

- **Access token**: Expires after `access_token_ttl` (default: 900 seconds). The `exp` claim determines this.
- **Session**: May have an `expires_at` timestamp. If set, the session expires at this time regardless of the token TTL.
- **Refresh token**: May have a `refresh_token_ttl`. If `null`, the refresh token does not expire based on time.

When an access token expires, the client uses the refresh token to get a new one. If the session's `expires_at` has passed, the refresh is rejected even if the refresh token is still valid.

## Security properties by authentication method

Each sign-in method has different security properties:

### Password sign-in

| Property | Value |
| --- | --- |
| **AAL** | `aal1` (without MFA), `aal2` (with MFA) |
| **Factor count** | 1 (password), 2 (password + TOTP) |
| **Phishing resistance** | Low — users can be tricked into entering their password on a fake site. |
| **Brute-force resistance** | Medium — bcrypt hashing makes offline brute-force impractical, but online brute-force is possible without rate limiting. |
| **Credential stuffing resistance** | Medium — rate limiting and account lockout mitigate credential stuffing. |
| **Session security** | Medium — access tokens are short-lived, but refresh tokens are long-lived and can be stolen. |

### Magic link sign-in

| Property | Value |
| --- | --- |
| **AAL** | `aal1` |
| **Factor count** | 1 (email access) |
| **Phishing resistance** | Low — clicking a link is susceptible to phishing. |
| **Brute-force resistance** | High — tokens are cryptographically random and single-use. |
| **Credential stuffing resistance** | High — no password to stuff. |
| **Session security** | Medium — same token rotation and revocation as password sign-in. |

### Social login

| Property | Value |
| --- | --- |
| **AAL** | `aal1` (without MFA), `aal2` (with MFA) |
| **Factor count** | 1 (provider authentication), 2 (provider + TOTP) |
| **Phishing resistance** | Medium — depends on the provider's phishing resistance. |
| **Brute-force resistance** | High — tokens are issued by the provider, not guessable. |
| **Credential stuffing resistance** | High — no password to stuff. |
| **Session security** | Medium — same token rotation and revocation as other methods. |

### MFA sign-in

| Property | Value |
| --- | --- |
| **AAL** | `aal2` (TOTP), future `aal3` (hardware keys) |
| **Factor count** | 2 (password + TOTP, magic link + TOTP, social + TOTP) |
| **Phishing resistance** | Medium — TOTP codes can be phished. Hardware keys (future) are phishing-resistant. |
| **Brute-force resistance** | High — TOTP codes change every 30 seconds and are 6 digits (1,000,000 combinations). |
| **Credential stuffing resistance** | High — even with the password, the attacker needs the TOTP code. |
| **Session security** | High — `aal2` sessions are more secure and can be enforced through `require_aal`. |

### Recovery sign-in

| Property | Value |
| --- | --- |
| **AAL** | `aal2` |
| **Factor count** | 2 (email + recovery code) |
| **Phishing resistance** | Low — recovery codes can be phished if the user is tricked into revealing them. |
| **Brute-force resistance** | High — recovery codes are 8-character hex strings (16^8 = 4.3 billion combinations). |
| **Credential stuffing resistance** | High — no password to stuff. |
| **Session security** | High — recovery sign-in revokes all existing sessions and requires re-enrollment of MFA. |

## Production validation checklist

Before deploying to production, validate the following security configurations:

<AccordionGroup>
  <Accordion title="Environment configuration">
    1. `require_email_verification` is `true` — all users must verify their email before accessing the application.
    2. `min_aal` is set appropriately — at least `"aal2"` for applications handling sensitive data.
    3. `refresh_token_rotation` is `true` — refresh tokens are rotated on every use.
    4. `recovery_token_ttl` is 15 minutes or less — recovery tokens expire quickly.
    5. `magic_link_ttl` is 15 minutes or less — magic link tokens expire quickly.
  </Accordion>
  <Accordion title="Rate limiting">
    1. Per-IP rate limiting is enabled on `/auth/v1/token` (30 requests per 60 seconds).
    2. Per-IP rate limiting is enabled on `/auth/v1/recover` (5 requests per 60 seconds).
    3. Per-IP rate limiting is enabled on `/auth/v1/magic-link` (5 requests per 60 seconds).
    4. Per-IP rate limiting is enabled on `/auth/v1/verify` (30 requests per 60 seconds).
    5. Per-user rate limiting is enabled on all authentication endpoints.
  </Accordion>
  <Accordion title="Token security">
    1. Access token TTL is 900 seconds (15 minutes) or less.
    2. Refresh token TTL is configured and appropriate for the application.
    3. `refresh_token_rotation` is `true`.
    4. The `RevokedToken` table is configured and maintained.
    5. Session expiration is configured through `expires_at` if needed.
  </Accordion>
  <Accordion title="Password security">
    1. Password complexity requirements are enforced (minimum length, character variety).
    2. Bcrypt cost factor is 12 or higher.
    3. Account lockout threshold (`mfa_failed_attempts_lockout`) is configured.
    4. `failed_logins` is reset on successful sign-in and password change.
    5. Password reset (recovery) is properly rate-limited.
  </Accordion>
  <Accordion title="CORS and CSRF">
    1. `cors_origins` is configured with only the allowed origins.
    2. The OAuth2 flow uses PKCE.
    3. The OAuth2 flow uses the `state` parameter.
    4. Redirect URIs are validated against a pre-registered list.
    5. No wildcard redirect URIs are allowed.
  </Accordion>
  <Accordion title="Service key hygiene">
    1. Secret keys are stored in a secret manager, not in environment variables or configuration files.
    2. Service keys have the minimum permissions needed.
    3. Publishable keys are the only keys exposed to client-side code.
    4. Service key rotation is scheduled (every 90 days).
    5. Service key usage is monitored and audited.
  </Accordion>
  <Accordion title="MFA">
    1. `require_mfa` is enabled if the application handles sensitive data.
    2. `min_aal` is `"aal2"` or higher.
    3. MFA recovery codes are generated (10 per user) and securely distributed.
    4. Admin MFA reset is available for locked-out users.
    5. Failed MFA attempts are tracked and lockout is configured.
  </Accordion>
  <Accordion title="HTTPS and encryption">
    1. HTTPS is enforced on all authentication endpoints.
    2. TLS certificates are valid and not self-signed.
    3. TLS 1.2 or higher is enforced.
    4. HSTS headers are set.
    5. Token signing keys are rotated periodically.
  </Accordion>
  <Accordion title="Monitoring and logging">
    1. Audit logging is enabled for all authentication events.
    2. Failed sign-in attempts are logged and monitored.
    3. Token rotation events are monitored for theft detection.
    4. Policy overrides (`force`) are logged for audit purposes.
    5. Rate limit violations are logged and monitored.
  </Accordion>
  <Accordion title="Session management">
    1. All sessions are stored in the `SessionInfo` table.
    2. `revoked` and `revoked_at` are properly set on revoked sessions.
    3. The `RevokedToken` table is maintained.
    4. Session enumeration is available through the admin API.
    5. Session revocation (`POST .../sessions/revoke`) is tested and working.
  </Accordion>
  <Accordion title="Email verification">
    1. `require_email_verification` is `true` for production applications.
    2. The verification email template uses `{{verify_url}}` correctly.
    3. The `verify` endpoint is rate-limited.
    4. The `complete` handler properly validates `ttl`, `used`, and `code_hash`.
    5. Admin-initiated verification is available for edge cases.
  </Accordion>
</AccordionGroup>

## Common security vulnerabilities

### LocalStorage token storage

**Vulnerability**: Storing refresh tokens in localStorage makes them accessible to JavaScript running in the browser. Any XSS vulnerability in the application can steal the tokens.

**Mitigation**: Use httpOnly cookies for token storage. httpOnly cookies are not accessible to JavaScript and are protected against XSS attacks.

### Exposed service keys

**Vulnerability**: Service keys embedded in client-side code or configuration files are visible to anyone who can access the codebase or browser developer tools.

**Mitigation**: Keep service keys on the backend only. Use a secret manager for storage. Rotate keys regularly.

### No CORS configuration

**Vulnerability**: Without CORS configuration, any origin can make requests to the API. This allows cross-site request forgery (CSRF) and data exfiltration.

**Mitigation**: Configure `cors_origins` with only the allowed origins. Reject requests from unauthorized origins.

### Weak password policies

**Vulnerability**: Allowing weak passwords (e.g., "123456", "password") makes brute-force attacks easy.

**Mitigation**: Enforce minimum password length (at least 8 characters), character variety (uppercase, lowercase, numbers, symbols), and common password blacklists.

### Missing rate limiting

**Vulnerability**: Without rate limiting, an attacker can make unlimited sign-in attempts, recovery requests, or verification requests.

**Mitigation**: Implement rate limiting on all authentication endpoints. Use per-IP, per-user, and per-email rate limits.

### Not revoking sessions after password change

**Vulnerability**: If existing sessions are not revoked after a password change, an attacker who obtained the old password can continue to access the account.

**Mitigation**: Always revoke all sessions after a password change using `revoke_all`.

<Warning>
The most common security vulnerability is storing refresh tokens in localStorage. This single mistake can expose all authenticated users to XSS attacks. Always use httpOnly cookies or a secure token store.
</Warning>

## Security audit trail

All security-relevant events are logged in the audit trail:

- **`user.signed_in`**: User signed in (method, AAL, IP address).
- **`user.signed_out`**: User signed out.
- **`token.issued`**: Access and refresh tokens were issued.
- **`token.refreshed`**: Tokens were refreshed.
- **`token.revoked`**: Tokens were revoked.
- **`user.password_changed`**: User changed their password.
- **`user.email_verified`**: User verified their email.
- **`user.mfa_reset`**: MFA was reset.
- **`role.assigned`**: A role was assigned to a user.
- **`role.revoked`**: A role was revoked from a user.
- **`org.member_added`**: A member was added to an organization.
- **`policy.override`**: A policy was overridden with `force`.
- **`rate_limit_exceeded`**: A rate limit was exceeded.

The audit trail provides a complete record of all security-relevant events, enabling administrators to detect, investigate, and respond to security incidents.
