Magic links let a person sign in by opening a single-use link sent to their email address. They work well for customer portals and applications where people sign in infrequently.

The complete integration includes a request form, email delivery, an application callback, token verification, and session handling. A successful link request alone does not mean the person is signed in.

## Enable magic links in Studio

1. Open your project and select the environment.
2. Open **Users & auth → Configuration**.
3. Enable **Magic links** under **Sign-in methods**.
4. Decide whether **Sign-up enabled** should allow new accounts.
5. Set **Site URL**, for example `https://portal.example.com`.
6. Add any other trusted redirect destinations.
7. Review the **Magic link** email subject and text.
8. Save and test delivery to a mailbox you control.

The application must serve `/auth/callback` below Site URL. That page receives the one-time token and exchanges it through the public API.

Mail transport must be configured for the installation. Template customization and mail delivery are separate tasks.

## Request a sign-in link

Send a publishable key for the target environment. No bearer token is required.

~~~bash
curl -X POST "$PAWABASE_URL/auth/v1/magic-link" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "amina@example.com",
    "create_user": false,
    "redirect_to": "https://portal.example.com/requests"
  }'
~~~

| Field | Required | Behavior |
| --- | --- | --- |
| `email` | Yes | Address receiving the link |
| `create_user` | No | Defaults to true; permits account creation only when sign-up is enabled |
| `redirect_to` | No | Requested destination; must pass the environment's redirect rules |

The response is deliberately generic:

~~~json
{
  "sent": true,
  "message": "If the address has an account, a message is on its way."
}
~~~

Show this as a request acknowledgment. Do not display “Account found” or claim that the email has arrived.

### Existing users and new users

For an unknown address, a user is created only when both `create_user` and the environment's sign-up setting allow it. Creation occurs when the link is requested; verification occurs when the link is redeemed.

When creation is not allowed, the request still returns the generic response. Disabled accounts also do not receive a usable new sign-in link through this request.

For an invite-only application, disable sign-up in Studio. Setting `create_user: false` in your own frontend is useful behavior, but a caller can change their request. The environment setting enforces the registration boundary.

## Receive the callback

With Site URL configured, the email link looks like:

~~~text
https://portal.example.com/auth/callback?token=<one-time-token>&type=magic
~~~

If the request supplied `redirect_to`, it is also carried in the callback query. Your application should independently restrict the destination before navigating.

Read the token, remove it from the visible URL, and verify it once. Avoid loading analytics or third-party scripts while the token remains in the URL.

~~~javascript
const callback = new URL(window.location.href);
const token = callback.searchParams.get("token");
const purpose = callback.searchParams.get("type");

window.history.replaceState(
  {},
  "",
  callback.pathname
);

if (purpose !== "magic" || !token) {
  throw new Error("This is not a valid magic-link callback");
}
~~~

In a framework that reruns effects, guard the exchange so a render does not redeem the same token twice.

## Exchange the token

The supported completion endpoint is `POST /auth/v1/magic-link/verify`:

~~~bash
curl -X POST "$PAWABASE_URL/auth/v1/magic-link/verify" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"token":"<one-time-token-from-the-email>"}'
~~~

The token is single-use and expires after 15 minutes. There is no magic-link lifetime control in the current Studio configuration.

A successful exchange verifies the user's email and normally returns the session fields described in [Tokens and sessions](/auth/tokens-and-sessions). A disabled account is refused.

### Handle MFA before entering the application

If the account has MFA enabled and the environment permits MFA, verification returns:

~~~json
{
  "mfa_required": true,
  "mfa_token": "<challenge-token>"
}
~~~

Collect an authenticator or recovery code, then complete the challenge:

~~~bash
curl -X POST "$PAWABASE_URL/auth/v1/token" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "grant_type": "mfa",
    "mfa_token": "<challenge-token>",
    "code": "<authenticator-or-recovery-code>"
  }'
~~~

Keep the challenge out of persistent logs and URLs. Only the completed session's access token belongs in an Authorization header.

A magic-link session without MFA has assurance level `aal1`. Completing MFA produces `aal2`. Enforce the required level on sensitive routes through policies.

## A callback integration

This helper returns explicit application states. The caller is responsible for storing a returned session or showing the MFA form.

~~~javascript
async function verifyMagicLink(token) {
  const response = await fetch(
    PAWABASE_URL + "/auth/v1/magic-link/verify",
    {
      method: "POST",
      headers: {
        apikey: PAWABASE_PUBLISHABLE_KEY,
        "Content-Type": "application/json",
      },
      body: JSON.stringify({ token }),
    }
  );

  const result = await response.json();
  if (!response.ok) {
    return {
      state: "failed",
      status: response.status,
      message: typeof result.detail === "string"
        ? result.detail
        : "The link could not be verified",
    };
  }
  if (result.mfa_required) {
    return { state: "mfa", challenge: result.mfa_token };
  }
  if (!result.access_token || !result.refresh_token) {
    return { state: "failed", message: "No session was returned" };
  }
  return { state: "signed-in", session: result };
}
~~~

After storing a session, call `GET /auth/v1/user` or load a protected resource to establish the signed-in screen. Clear any previous user's resource caches before navigation.

## Hosted link behavior

If Site URL is empty, the email uses Pawabase's hosted link handler. It can redeem the link and display a completion page. When it has both an allowed redirect destination and a session result, it can redirect with tokens in the URL fragment.

The hosted page does not provide your application's full MFA interaction. Configure Site URL and handle the JSON verification response in your application when MFA is part of the sign-in experience.

Do not assume that a “You're all set” hosted page has stored a session in your frontend.

## Customize the email

In **Users & auth → Configuration**, edit the Magic link email. Supported placeholders include `{project}`, `{email}`, and `{link}`.

~~~text
Sign in to {project}

Use this link to access your customer portal:
{link}

This link works once and expires in 15 minutes.
If you did not request it, you can ignore this email.
~~~

Use the generated `{link}` rather than constructing a URL with a token yourself.

## Failure handling

| Result | Likely cause | Application action |
| --- | --- | --- |
| 400 on request | Redirect URL is not allowed | Correct the configured destination |
| 403 on request | Magic links are disabled | Offer another enabled sign-in method |
| 429 on request | Request rate limit reached | Delay another request and show a retry message |
| 400 on verification | Invalid, expired, already-used, or wrong-environment token | Offer to request a new link |
| 403 on verification | Account disabled | Direct the user to support |
| Successful MFA challenge | Another factor is required | Show the MFA form |
| Network failure during verification | Exchange outcome is uncertain | Do not repeatedly redeem the token; check local session state and offer a fresh sign-in |

Invalid-token responses intentionally do not distinguish forged, expired, and already-used links.

## Production considerations

Treat control of the mailbox as control of the first sign-in factor. Use MFA policies for higher-risk actions.

Email security scanners may open links before a person does. An application callback can present an explicit “Continue signing in” action before redeeming the token. This reduces accidental redemption but must be tested with the mail systems your users actually use.

Magic-link sign-in does not revoke other sessions. Provide a sessions screen if people need to review or terminate other devices.

Do not count every requested link as a completed sign-in. Measure successful session establishment separately from email requests.

## Test the complete path

Test an existing account, an unknown address with sign-up enabled, an unknown address with sign-up disabled, an expired link, a reused link, and an MFA-enrolled account. Verify the API key, callback URL, and mail configuration separately in staging and production.
