Magic links provide a passwordless sign-in experience. The user enters their email address, receives a link via email, and clicks it to sign in — no password required. Magic links are ideal for applications where convenience is paramount and the security boundary of email access is acceptable.

Magic links differ from password sign-in in that they don't require a password at all. They differ from email verification in that they directly sign the user in (creating a session) rather than just verifying the email. The `magic_link_enabled` flag controls whether magic links are available, and `magic_link_create_account` determines whether new accounts are automatically created or only existing users can sign in.

## How magic links work

When a user enters their email address and requests a magic link, Pawabase:

1. Checks if `magic_link_enabled` is `true`. If not, returns `403 magic links are not enabled`.
2. Checks if the email belongs to an existing user. If the user does not exist and `magic_link_create_account` is `false`, returns `404 user not found`.
3. If the user does not exist and `magic_link_create_account` is `true`, creates a new `AuthUser` record with `email_verified = True` (since the magic link confirms email ownership).
4. Creates a `OneTimeToken` with `kind: "magic_link"`.
5. Sends a magic link email to the user's address.
6. Returns `200 magic link sent` (regardless of whether the user exists — this is a security measure).

<Steps>
  <Step title="User requests a magic link">
    The user submits their email address to the `/magic-link` endpoint. Pawabase validates the email format and checks the configuration flags.
  </Step>
  <Step title="Account is created or found">
    If `magic_link_create_account` is `true` and the email doesn't belong to an existing user, a new account is created with `email_verified = True`. If the user exists, the existing account is used.
  </Step>
  <Step title="Magic link token is created">
    A `OneTimeToken` with `kind: "magic_link"` is created with a random token and a configurable TTL.
  </Step>
  <Step title="Email is sent">
    The magic link email is sent to the user's address. The email contains a link with the token embedded.
  </Step>
  <Step title="User clicks the link">
    The user clicks the link in their email, which directs them to the `/magic-link/complete` handler.
  </Step>
  <Step title="Session is created">
    The `complete` handler validates the token, creates a session, and returns the access and refresh tokens.
  </Step>
</Steps>

### The `/magic-link` endpoint

The `/magic-link` endpoint initiates the magic link sign-in flow:

```bash
curl -X POST "$GW/auth/v1/magic-link" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "email": "user@example.com"
  }'
```

The endpoint validates the email format, checks the configuration flags, and either creates a new account (if `magic_link_create_account` is `true`) or looks up the existing user. It then creates a `OneTimeToken` and sends the magic link email.

### `magic_link_enabled`

The `magic_link_enabled` flag controls whether magic links are available for sign-in:

- When `true`, users can sign in using magic links.
- When `false`, the `/magic-link` endpoint returns `403 magic links are not enabled`.
- This flag is set at the environment level and can be changed without deploying new code.

<Warning>
If `magic_link_enabled` is `true` and `magic_link_create_account` is also `true`, any email address can be used to create an account. This is convenient for open applications but may not be appropriate for applications that require user registration approval or invite-only access.
</Warning>

### `magic_link_create_account`

The `magic_link_create_account` flag controls whether new accounts are automatically created:

| `magic_link_create_account` | Behavior |
| --- | --- |
| `true` | New users are automatically created when they click a magic link. Their account is created with `email_verified = True`. |
| `false` | Only existing users can sign in with a magic link. If the email doesn't belong to an existing user, the endpoint returns `404 user not found`. |

This flag allows you to control whether your application allows self-registration through magic links or requires an invitation or manual account creation.

## The magic link token

The magic link token is stored in the `OneTimeToken` table with `kind: "magic_link"`:

```python
class OneTimeToken(BaseModel):
    id: UUID = Field(default_factory=uuid4, primary_key=True)
    email: str = Field(index=True)
    kind: str  # "magic_link"
    token: str  # The one-time token string
    token_hash: str  # SHA-256 hash of the token
    ttl: datetime  # When the token expires
    used: bool = False
    created_at: datetime = Field(default_factory=datetime.now(UTC))
    expires_at: datetime = Field(default_factory=datetime.now(UTC))
```

The token has the same structure as recovery and verification tokens — it is a random string, stored as a hash, with a configurable TTL. The token is single-use: after it is successfully used to sign in, it is marked as `used = True` and cannot be used again.

### Token TTL

The magic link token TTL is configured through `magic_link_ttl`. The default is typically 15 minutes, but this can be customized. If the token expires before the user clicks the link, the token is invalid and the user must request a new magic link.

### Token security

The magic link token is a cryptographically random string (typically 32+ characters). It is hashed using SHA-256 before being stored in the database. When the user submits the token, the server hashes the submitted token and compares it against the stored hash. The raw token is never stored persistently.

## The `complete` handler

The `/magic-link/complete` handler validates the magic link token and creates a session:

```bash
curl -X POST "$GW/auth/v1/magic-link/complete" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "token": "rft_magic_abc123..."
  }'
```

The `complete` handler:

1. Hashes the submitted token and looks up the matching `OneTimeToken` record.
2. Checks if the token exists. If not, returns `400 invalid magic link token`.
3. Checks if the token has expired (`ttl` passed). If so, returns `400 magic link token expired`.
4. Checks if the token has already been used (`used == True`). If so, returns `400 magic link token already used`.
5. Finds or creates the user account. If `magic_link_create_account` is `true` and the user doesn't exist, a new account is created.
6. Marks the user as `email_verified = True`.
7. Creates a new session using `start_session` with `method: "magic_link"` and `aal: "aal1"`.
8. Marks the `OneTimeToken` as `used = True`.
9. Emits a `user.signed_in` event with `method: "magic_link"`.
10. Returns the access token and refresh token.

### AAL implications

Magic link sign-in produces an `aal1` session — single-factor authentication. The user's email is the only factor they need to prove ownership of. No password or TOTP is required.

If the environment requires `min_aal: "aal2"` (e.g., for compliance or sensitive operations), magic link sign-in alone is insufficient. The user would need to complete an additional MFA challenge to reach `aal2`. This can be done through:

1. **TOTP after magic link**: The user signs in with the magic link (aal1) and is then prompted to enter their TOTP code to reach aal2.
2. **MFA policy enforcement**: If the organization has `require_mfa` enabled, the magic link session would be denied access to protected resources until MFA is completed.

<Note>
The AAL for magic link sessions is always `"aal1"`. There is no way to obtain a higher AAL through magic link alone — the user would need to sign in with a method that includes MFA (such as password + TOTP).
</Note>

### `email_verified` is set automatically

When a user signs in through a magic link, their `email_verified` flag is automatically set to `True`. This is because clicking a magic link demonstrates email ownership — the user must have access to the email address to receive the link. Therefore, email verification is not required separately for magic link users.

## Email templates

The magic link email uses a template that includes a magic link URL. The template variable `{{magic_link_url}}` is replaced with the actual URL that includes the one-time token:

```
Sign in with a magic link

Click the link below to sign in:
{{magic_link_url}}

This link expires in 15 minutes. If you didn't request a sign-in link, you can safely ignore this email.
```

The `{{magic_link_url}}` template variable is generated by Pawabase and includes the token as a query parameter. The URL format is:

```
https://yourapp.com/magic-link?token=rft_magic_abc123...
```

## Security considerations

Magic links trade some security for convenience. Understanding the security implications is important before enabling them:

### Email access as the security boundary

With magic links, the security boundary is the user's email account. If an attacker gains access to the user's email, they can sign in as the user — there is no password to steal. This is fundamentally different from password-based sign-in, where the attacker needs both the email and the password.

The following measures mitigate this risk:

1. **Rate limiting**: Both `/magic-link` and `/magic-link/complete` are rate-limited to prevent brute-force and enumeration attacks.
2. **One-time tokens**: Each magic link token can only be used once. Even if a token is intercepted, it cannot be reused after the legitimate user clicks it.
3. **Token expiration**: Magic link tokens expire after a configurable TTL, limiting the window of exposure.
4. **Session revocation**: After a magic link is used, any existing sessions for the user remain valid (unlike password recovery, which revokes all sessions). This is because magic link sign-in is a legitimate sign-in method, not a security compromise.

### Comparison with password sign-in

| Aspect | Magic Link | Password |
| --- | --- | --- |
| **Security boundary** | Email access | Email + password |
| **AAL** | `aal1` | `aal1` (or `aal2` with MFA) |
| **Convenience** | Very high — no password to remember | Medium — password must be remembered |
| **Phishing resistance** | Low — clicking a link is susceptible to phishing | Medium — password can be entered on a real site |
| **Account recovery** | Not needed — magic link works regardless | Requires password recovery flow |
| **Email verification** | Automatic (`email_verified = True`) | Requires separate verification flow |

### When to use magic links

Magic links are appropriate when:

- Convenience is a top priority (e.g., internal tools, low-risk applications).
- The application has a strong email security model (e.g., organization-controlled email).
- Users have verified their email through a separate process before using magic links.
- The application is not a high-security target (e.g., not banking or healthcare).

Magic links are **not** appropriate when:

- High security is required (e.g., financial applications, healthcare records).
- Users may not have access to their email (e.g., shared email accounts).
- The application is subject to compliance requirements that mandate multi-factor authentication.

<Warning>
Never use magic links as the sole sign-in method for high-security applications. Always require MFA (TOTP, hardware keys, etc.) as a second factor for applications that handle sensitive data.
</Warning>

### Rate limiting

The `/magic-link` endpoint is rate-limited:

- **Per-IP**: Maximum 5 magic link requests per 60 seconds.
- **Per-user**: Maximum 3 magic link requests per hour.
- **Per-email**: Minimum 60 seconds between consecutive requests.

The `/magic-link/complete` endpoint is also rate-limited:

- **Per-token**: Maximum 10 attempts per 60 seconds.
- **Per-email**: Maximum 3 completions per hour.

Rate limiting prevents email bombing, brute-force attacks on tokens, and enumeration attacks.

## Common mistakes

<AccordionGroup>
  <Accordion title="Not rate-limiting the magic link endpoint">
    Without rate limiting, an attacker can send thousands of magic link emails to a single address or domain, causing email bombing and potential blacklisting of your sending domain.
  </Accordion>
  <Accordion title="Allowing magic link sign-in without email verification">
    Magic links automatically set `email_verified = True`. This is correct behavior — clicking the link proves email ownership. Do not require separate email verification after magic link sign-in.
  </Accordion>
  <Accordion title="Using magic links for high-security applications">
    Magic links have a single security boundary (email access). They should not be the sole sign-in method for high-security applications. Always add MFA as a second factor.
  </Accordion>
  <Accordion title="Not checking the `used` flag on the complete handler">
    If the `complete` handler doesn't check `used == True`, a magic link token could be used multiple times. Always mark the token as used after a successful sign-in.
  </Accordion>
  <Accordion title="Setting `magic_link_create_account = true` without restrictions">
    If `magic_link_create_account` is `true`, any email address can create an account. This may lead to spam accounts. Consider using invite-only registration or email domain restrictions.
  </Accordion>
</AccordionGroup>
