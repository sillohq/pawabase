Every Pawabase project gets an identity service for free: sign-up, sign-in, sessions, MFA, social login, roles, and multi-tenant organizations. That service is **Akountz**, one of Pawabase's platform services, and this section of the documentation is its complete user-facing reference. This page is the map — what Akountz is responsible for, the shape of a user account, how a request becomes an authenticated caller, and where to go next for each capability.

## What Akountz owns

Akountz is a standalone service inside the Pawabase platform. It owns identity and nothing else — project configuration, outbound mail and the platform event log all belong to the Platform API, and Akountz reaches them through an internal service client rather than owning them directly. Concretely, Akountz is responsible for:

- **Accounts**: creating, finding, updating, disabling and soft-deleting users, scoped to a project environment.
- **Credentials**: password hashing and verification, magic links, and the four supported OAuth/OIDC providers.
- **Sessions**: issuing and rotating access/refresh token pairs, tracking devices, and revocation.
- **MFA**: TOTP enrollment, verification, and single-use recovery codes.
- **RBAC**: named permission groups (what this documentation calls "roles") and directly granted permissions.
- **Organizations**: multi-tenant grouping of users within one environment, with role-based membership, teams, and email invitations.

Everything else about a request — what a given role or permission is *allowed to do* against your data — is decided by Pawabase's [policy engine](/policies/overview), not by Akountz. Akountz's job ends at producing a token with the right claims on it; the policy engine reads those claims.

## The `AuthUser` model

Every account is a row in Akountz's own database, in the `AuthUser` model (table `akz_users`). It combines Sillo's generic user base (password hashing, verification timestamps) with Sillo's JWT session mixin (token families, rotation, theft detection), and Pawabase adds the fields that make one user pool serve many projects and environments:

| Field | Type | Notes |
| --- | --- | --- |
| `project` | string | The project slug. **A plain string, not a foreign key or a UUID.** |
| `env` | string | The environment name (`development`, `production`, …), also a plain string. |
| `email` | string | Lowercased on write. Unique per `(project, env)`, not globally unique. |
| `username` | string | Unique per `(project, env)`. Auto-generated from the email if not supplied at sign-up. |
| `name` | string | Display name. Defaults to `""`. |
| `avatar_url` | string, nullable | Set by the user, or by a social provider on first sign-in. |
| `phone` | string, nullable | Not used by any sign-in flow today; a plain profile field. |
| `user_metadata` | JSON | Data the user can edit themselves, through `PATCH /auth/v1/user`. |
| `app_metadata` | JSON | Data only an administrator or a service key can set. |
| `disabled_at` | timestamp, nullable | Set when an administrator disables the account. |
| `failed_logins`, `locked_until` | int, timestamp | Brute-force lockout bookkeeping — see [Passwords → brute-force protection](/auth/passwords#brute-force-protection). |
| `mfa_enabled` | boolean | Whether the account currently has a confirmed second factor. |
| `last_sign_in_ip` | string, nullable | The IP address of the most recent successful sign-in. |

The table also carries the fields Sillo's own base classes add: a password hash column, `email_verified_at`, `is_active`, `deleted_at`, and the timestamps every Sillo model gets. `(project, env, email)` and `(project, env, username)` are both declared as unique constraints at the database level, which is what makes "one account per environment" a guarantee rather than a convention.

<Warning>
`project` and `env` are plain `CharField`s, not foreign keys and not UUIDs. There is no `Project` or `Environment` row that `AuthUser.project` points at — Akountz trusts whatever project/environment slug the calling context supplies (resolved from the request's API key upstream of Akountz) and scopes every query to it. Code or documentation that treats `project` as a UUID column is wrong; it has always been a string.
</Warning>

## Creating an account: `create_account`

Every path that produces a new user — the sign-up endpoint, magic links, social login, and the admin API — funnels through one function, `create_account` in `app/accounts.py`:

```python
async def create_account(
    config: AuthConfig,
    *,
    email: str,
    password: str | None,
    username: str | None = None,
    name: str = "",
    user_metadata: dict[str, Any] | None = None,
    app_metadata: dict[str, Any] | None = None,
    verified: bool = False,
) -> AuthUser:
    ...
```

What it does, in order:

1. Normalizes and validates the email (`normalise_email` — lowercased, checked against a simple `local@domain.tld` pattern, rejected past 255 characters).
2. Rejects a duplicate `(project, env, email)`.
3. If a `username` was supplied, rejects a duplicate `(project, env, username)`; otherwise generates one from the email's local part, appending a random numeric suffix until it's unique.
4. Builds the `AuthUser` row with `user_metadata`/`app_metadata` defaulting to `{}`, and `email_verified_at` set only if `verified=True`.
5. Sets a real password (after running it through [password policy](/auth/passwords#password-policy-enforcement)) if one was given, or calls `set_unusable_password()` if `password=None` — the path social login and magic-link signups take.
6. Saves the row, then assigns every role named in the environment's `default_roles` configuration.

`create_account` never issues a session and never sends an email — those are the caller's job (the signup route starts a session or sends a verification link depending on `require_email_verification`; the social login callback route decides based on whether MFA is required).

<Note>
There is no separate `register()` or `signup()` function in the account layer — `create_account` is the single account-creation primitive, called from four different places (`routes/auth.py`, `routes/recovery.py` for magic links, `routes/security.py` for social login, and `routes/admin.py` for the admin API), each supplying different arguments for the same function.
</Note>

## The `Principal`: what a request actually carries

An access token, once verified, becomes a `Principal` object (`pawabase_kit.principal.Principal`) that every Pawabase service places on the request as `ctx.user`. It is deliberately small — two attributes:

```python
class Principal(UserProtocol):
    def __init__(self, kind: str, claims: dict[str, Any]) -> None:
        self.kind = kind      # "user", "operator", or "service"
        self.claims = claims  # the verified token's claims, already trusted
```

Nothing is fetched from the database to build a `Principal` — the claims *are* the source of truth for the lifetime of the token. `Principal` exposes convenience properties over those claims: `identity` (the `sub` claim), `email`, `roles`, `permissions`, `org`, `has_permission(...)`, `has_role(...)`, and `as_policy_context()`, which is what feeds `$auth` inside a [policy condition](/policies/conditions). See [Tokens and sessions](/auth/tokens-and-sessions) for the exact claim names the access token carries, and [the condition language](/policies/conditions) for how `$auth.*` paths resolve against `as_policy_context()`'s output.

`kind` distinguishes three callers:

| `kind` | Who | Typical token |
| --- | --- | --- |
| `"user"` | An end user of your project. | A user access token from Akountz. |
| `"operator"` | A Studio operator (someone signed into Pawabase Studio itself). | Issued against the reserved `_platform` environment. |
| `"service"` | Another Pawabase service, or a caller using a secret key. | A short-lived service token, re-minted per call. |

## The reserved `_platform` environment

Studio itself is a Pawabase application, and its operators sign in through the exact same Akountz — but against a reserved environment, `_platform`/`_platform`, that isn't backed by the project API and isn't editable through the normal auth configuration. It has its own hard-coded, deliberately stricter defaults (`signup_enabled: false`, `password_policy: "strict"`, no magic links, a one-hour access token) — see [Configuration → the `_platform` environment](/auth/configuration#the-_platform-environment) for the full settings.

### Bootstrapping the first operator

On a fresh Akountz deployment, no operator exists to sign into Studio yet. At startup, `ensure_operator()` checks two environment variables, `PAWABASE_ADMIN_EMAIL` and `PAWABASE_ADMIN_PASSWORD`:

- If either is unset, nothing happens — startup continues with no operator.
- If both are set and **no** user already exists in `_platform`/`_platform`, Akountz creates one verified account with `create_account`, defines an `admin` role scoped to `_platform`/`_platform` with the single permission `"*"`, and assigns that role to the new account.
- If an operator already exists, this step is a no-op — it only ever runs once per installation.

This is the only place a wildcard `"*"` permission is created automatically; it exists purely to give the very first operator full control before any other role has been defined. See [Roles and permissions](/auth/roles-and-permissions) for what a `"*"` permission actually matches.

Each of those pages is self-contained, but they share vocabulary that's worth fixing here:

- **Environment**: a `(project, env)` pair, e.g. `acme`/`production`. Every user, session, role, permission and organization belongs to exactly one environment. Nothing is shared across environments — not even a lockout counter.
- **Session** and **token family** are the same thing: one `SessionInfo` row, one Sillo `JWTToken` family, one refresh token that rotates as it's used.
- **AAL** (Authentication Assurance Level) is `aal1` for a normal sign-in and `aal2` once a session has completed MFA. It lives on the session and is re-minted onto every access token issued from that session.
- **Role**, in this documentation, means a named `Group` of permissions (Sillo's RBAC), not a special first-class model — see [Roles and permissions](/auth/roles-and-permissions) for why that distinction matters.

## Common mistakes

<AccordionGroup>
  <Accordion title="Treating `project` as a foreign key or UUID">
    `AuthUser.project` and `AuthUser.env` are plain strings, populated from the request's resolved API key context. There is no join to a `Project` table inside Akountz — the project registry lives entirely in the Platform API, and Akountz only ever sees the slug.
  </Accordion>
  <Accordion title="Expecting one global user pool">
    An email address can hold a separate account in every environment of every project. A user signed up in `acme/development` does not exist in `acme/production` unless they sign up there too. This is deliberate: it keeps test data and production data from ever mixing.
  </Accordion>
  <Accordion title="Calling `create_account` expecting it to log the user in">
    It only builds and saves the row. Starting a session, sending a verification email, and deciding whether MFA applies are the caller's responsibility — look at how `routes/auth.py`'s signup handler and `routes/security.py`'s OAuth callback each use it differently.
  </Accordion>
  <Accordion title="Assuming roles live directly on the user model">
    `AuthUser` has no `roles` column. Roles are Sillo's `Group`/`UserGroup` membership rows, resolved at read time through `rbac.roles_of(user)`. See [Roles and permissions](/auth/roles-and-permissions).
  </Accordion>
</AccordionGroup>
