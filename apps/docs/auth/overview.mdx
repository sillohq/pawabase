Authentication gives your application a verified user identity. Pawabase supports email and password, emailed sign-in links, OAuth providers, authenticator apps, rotating sessions, and application organizations. The resulting identity is available to resource policies, storage rules, realtime channels, and custom routes.

For example, a PeopleOps application can let employees sign in, read their own leave requests, submit expenses, and join an employer's organization. Authentication establishes who the employee is. Policies decide which records and actions that employee can access.

## Choose the correct account boundary

Pawabase has two separate audiences:

| Audience | Where accounts are managed | What access means |
| --- | --- | --- |
| Your development and operations team | Studio organization and team settings | Permission to configure projects and environments |
| People using your application | A project's environment, under **Users & auth** | An identity that your application's policies can authorize |

A Studio operator account is not an application user account. Signing into Studio does not test your application's sign-in or access rules.

Application accounts belong to a project and environment. A development account does not automatically exist in production. Use an API key and user token from the same environment for every request.

### Authentication and authorization

A successful sign-in does not grant access to every resource. Each enabled operation still needs the appropriate policy.

For a leave-request resource, you might allow authenticated employees to create records, owners to read their requests, and HR reviewers to approve them. A frontend that hides the approval button improves usability, but the update operation or approval route must also enforce the reviewer policy.

Start with [Policies](/policies/overview) once sign-in works.

## Configure authentication in Studio

1. Open your project and select **development**.
2. Open **Users & auth**.
3. Select **Configuration**.
4. Decide whether people may create accounts using **Sign-up enabled**.
5. Choose whether email verification is required.
6. Set the password policy and token lifetimes.
7. Enable the sign-in methods your application will expose.
8. Set **Site URL** to your application's origin, such as `http://localhost:5173`.
9. Add any additional trusted redirect URLs.
10. Save the configuration.

The configuration page includes OAuth provider credentials and authentication email templates. Mail delivery also requires the installation's mail service to be configured; editing an email template alone does not provide delivery.

Settings apply to the selected environment. Repeat the review in staging and production, using their URLs and credentials. See [Authentication configuration](/auth/configuration) for every setting.

## Choose a sign-in method

| Method | Application experience | What to implement |
| --- | --- | --- |
| [Email and password](/auth/passwords) | Registration and a conventional sign-in form | Sign-up, token exchange, verification, recovery |
| [Magic links](/auth/magic-links) | Email address followed by a single-use link | Link request, callback, token verification, MFA branch |
| [Social login](/auth/social-login) | Redirect to a configured identity provider | Provider configuration, redirect, callback, session handling |
| [MFA](/auth/mfa) | Authenticator code or recovery code after a first factor | Enrollment, confirmation, challenge handling, protected actions |

You can offer more than one method. Keep account recovery and session management accessible regardless of the method chosen.

Enabling MFA allows enrollment. It does not automatically require every application operation to use a two-factor session. Protect sensitive actions with an assurance-level policy.

## Discover available methods from the application

Use the environment's publishable key when loading public authentication settings:

~~~bash
curl "$PAWABASE_URL/auth/v1/settings" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY"
~~~

A default response includes:

~~~json
{
  "signup_enabled": true,
  "email_verification_required": false,
  "magic_link_enabled": true,
  "mfa_enabled": true,
  "providers": [],
  "password_policy": {
    "kind": "basic",
    "min_length": 8
  }
}
~~~

This endpoint does not require an existing user session. Use the response to show available sign-in choices and password requirements. The server still enforces its configuration even if the browser has an older copy.

Never put a secret or service key into a login page. A publishable key selects the environment; it does not identify an end user.

## Build a password sign-in

Send the email address and password to the public token endpoint:

~~~bash
curl -X POST "$PAWABASE_URL/auth/v1/token" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "grant_type": "password",
    "email": "amina@example.com",
    "password": "<password-entered-by-the-user>"
  }'
~~~

A successful sign-in returns access and refresh tokens, expiration information, the session ID, and the user. If the account requires MFA, the result contains an MFA challenge instead. Do not treat every successful HTTP response as a completed sign-in.

~~~javascript
async function signIn(email, password) {
  const response = await fetch(PAWABASE_URL + "/auth/v1/token", {
    method: "POST",
    headers: {
      apikey: PAWABASE_PUBLISHABLE_KEY,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ grant_type: "password", email, password }),
  });
  const result = await response.json();

  if (!response.ok) {
    throw new Error(
      typeof result.detail === "string" ? result.detail : "Sign-in failed"
    );
  }
  if (result.mfa_required) {
    return { state: "mfa", challenge: result.mfa_token };
  }
  if (!result.access_token || !result.refresh_token) {
    throw new Error("Sign-in did not return a session");
  }
  return { state: "signed-in", session: result };
}
~~~

`PAWABASE_URL` and `PAWABASE_PUBLISHABLE_KEY` are application configuration values in these examples. Supply them through your application's configuration mechanism.

The [password guide](/auth/passwords) covers sign-up responses, verification requirements, account lockout, and password changes.

## Make an authenticated application request

Send both the publishable key and the user's access token:

~~~bash
curl "$PAWABASE_URL/rest/v1/leave_requests" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
~~~

The key determines the target environment. The bearer token identifies the user and carries the claims policies evaluate. Resource access depends on the resource's enabled operation and assigned policy.

Use `GET /auth/v1/user` with the same headers to load the signed-in user's profile. It is useful after a callback or when restoring an application session.

## Treat sessions as application state

A session is more than a boolean `loggedIn` flag. Your application should distinguish:

- Signed out: show sign-in and recovery options.
- Verification pending: show instructions for confirming the email address.
- MFA pending: collect the next factor without treating the challenge as an access token.
- Signed in: attach the current access token to requests.
- Refreshing: coordinate requests while replacing the token pair.
- Session ended: clear cached user data and return to sign-in.

Refresh tokens rotate. Persist the returned replacement and prevent simultaneous refreshes from reusing the same token. See [Tokens and sessions](/auth/tokens-and-sessions).

When a different person signs in on the same device, clear resource caches and subscriptions associated with the previous user.

## Manage users in Studio

The **Users** tab lets operators search accounts by name or email and filter disabled or unverified users. Opening a user exposes account details, roles, permissions, sessions, and history.

Use **New user** when an operator needs to provision an account. If no password is supplied, the user can set one through password recovery after mail delivery is available.

Use the **Roles** tab to define reusable permission sets. Assign them in the user's detail view. Use **Sign-in activity** to investigate authentication failures without asking users to share passwords or tokens.

Application organization membership is separate from environment-wide roles. See [Application organizations](/auth/organizations) when building a product that serves multiple customer teams.

## Connect authentication to a real workflow

For an employee leave-request feature:

1. Create an employee account in development and complete sign-in.
2. Create a resource with an owner field that stores the authenticated employee's identity.
3. Assign an authenticated policy to create.
4. Assign an owner policy to list and get.
5. Give HR reviewers a permission for the approval action.
6. Enforce that permission on the approval route.
7. Test with two employees and a reviewer.
8. Repeat using production-equivalent settings in staging.

Test denied requests as well as allowed requests. In particular, employee A must not read employee B's records by guessing a record ID or adding a filter.

## Troubleshooting

### Sign-in works in development but not production

Check the gateway URL and publishable key together. Accounts, provider credentials, redirects, and configuration are environment-specific. Promotion of definitions does not create production users.

### The API returns an MFA challenge

The user has enrolled MFA and the environment enables it. Complete the challenge using the MFA grant documented in [MFA](/auth/mfa). A challenge token cannot authorize resource requests.

### The user is signed in but resource requests fail

Inspect the resource operation and its policy. A signed-in identity satisfies authentication, but may lack a role, permission, ownership match, organization, or required assurance level.

### Email links never arrive

Verify mail delivery, the destination address, and the selected environment. A generic successful email-request response intentionally does not prove an account exists or that an email reached the inbox.

### Changes to roles do not appear immediately

Roles and permissions are included in issued access tokens. Refresh or sign in again after changing assignments. Existing access tokens may retain their previous claims until expiry.
