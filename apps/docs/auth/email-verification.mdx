Email verification is the process of confirming that a user owns the email address they provided during sign-up. Pawabase sends a verification email containing a one-time link that the user clicks to verify their address. Once verified, the user can access all features that require email confirmation.

Email verification is controlled by the `require_email_verification` configuration flag. When enabled, new sign-ups must complete verification before they can access the application. The verification flow consists of two endpoints: the verification request endpoint (`verify`) and the completion handler (`complete`).

## How email verification works

When a new user signs up (through `POST /auth/v1/token` with `grant_type: "password"` or `grant_type: "magic_link"`), Pawabase creates the `AuthUser` record and checks the `require_email_verification` flag:

<Steps>
  <Step title="User signs up">
    The user provides an email and password (or clicks a magic link). Pawabase creates the `AuthUser` record with `email_verified = False`. If `require_email_verification` is `true`, the user cannot access the application until they verify their email.
  </Step>
  <Step title="Verification request">
    The client calls `POST /auth/v1/verify` with the user's email. Pawabase creates a new `OTP` record with `kind: "verify"` and generates a one-time code.
  </Step>
  <Step title="Email is sent">
    Pawabase sends an email to the user's address containing a verification link with the one-time code embedded. The email template uses `{{verify_url}}` which is replaced with the actual verification URL.
  </Step>
  <Step title="User clicks the link">
    The user clicks the verification link in their email. The link directs them to the `complete` handler, which validates the one-time code.
  </Step>
  <Step title="Verification is complete">
    The `complete` handler validates the code against the `OTP` table, marks the user as `email_verified = True`, and deletes the used `OTP` record. The user can now access the application.
  </Step>
</Steps>

### The `OTP` model

Verification codes are stored in the `OTP` table:

```python
class OTP(BaseModel):
    id: UUID = Field(default_factory=uuid4, primary_key=True)
    email: str = Field(index=True)
    kind: str  # "verify", "recovery", or "magic_link"
    code: str  # The one-time code
    code_hash: str  # Hashed version of the code for secure storage
    ttl: datetime  # When the code expires
    used: bool = False
    created_at: datetime = Field(default_factory=datetime.now(UTC))
    expires_at: datetime = Field(default_factory=datetime.now(UTC))
```

The `OTP` model has the following fields:

- **`email`**: The email address the verification code was sent to. Indexed for fast lookups.
- **`kind`**: The type of OTP — `"verify"` for email verification, `"recovery"` for password recovery, or `"magic_link"` for magic link sign-in.
- **`code`**: The raw one-time code (stored temporarily for verification).
- **`code_hash`**: The hashed version of the code, stored securely in the database. The raw code is not stored persistently after verification.
- **`ttl`**: The expiration timestamp. The code is only valid until this time.
- **`used`**: `True` if the code has been used. Once used, the code cannot be verified again.
- **`expires_at`**: The expiration timestamp. Codes that have expired are rejected automatically.

## The `verify` endpoint

The `verify` endpoint initiates the verification process. The client sends the user's email address, and Pawabase creates an `OTP` record and sends the verification email:

```bash
curl -X POST "$GW/auth/v1/verify" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "email": "user@example.com"
  }'
```

The `verify` endpoint validates the email format, checks if the user exists, and if `require_email_verification` is enabled, creates an `OTP` record and sends the email. If the user does not exist, the endpoint returns `404 user not found`. If the email is already verified, it returns `400 email already verified`.

### Rate limiting on the `verify` endpoint

The `verify` endpoint is protected by rate limiting to prevent abuse:

- **Per-IP rate limiting**: Each IP address is limited to a certain number of verification requests per time window (default: 30 requests per 60 seconds).
- **Per-user rate limiting**: Each user is limited in how many verification emails they can request within a short period (default: 5 requests per hour).
- **Per-email rate limiting**: Each email address has a cooldown period between verification requests (default: 60 seconds between requests for the same email).

If any rate limit is exceeded, the endpoint returns `429 rate limit exceeded` with details on when the limit resets.

### What happens if the user already has an `OTP` record

If the user already has an unexpired, unused `OTP` record for verification, the `verify` endpoint either:

1. Returns the existing `OTP` record (no new one is created), or
2. Creates a new `OTP` record and invalidates the old one.

This depends on the configuration. The default behavior is to create a new `OTP` record, which invalidates the old one by setting its `used` flag to `True`. This prevents an attacker from using an old verification code that they might have intercepted.

## The `complete` handler

The `complete` handler validates the verification code and marks the user as verified. The client receives the verification link from the email and passes the code to this handler:

```bash
curl -X POST "$GW/auth/v1/complete" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "code": "abcdef123456"
  }'
```

The `complete` handler:

1. Looks up the `OTP` record by the code. If the code is not found, returns `400 invalid verification code`.
2. Checks if the code has expired. If the `ttl` has passed, returns `400 verification code expired`.
3. Checks if the code has already been used (`used == True`). If so, returns `400 verification code already used`.
4. Marks the `AuthUser` as `email_verified = True`.
5. Marks the `OTP` record as `used = True`.
6. Emits a `user.email_verified` event.
7. Returns the access token and refresh token for the verified session.

### After verification completes

Once the user is verified, they can access all features that require email verification. If `require_email_verification` was blocking their access, the restriction is lifted immediately. The user's `Principal` will now have `email_verified = true` in their claims.

## Resend verification email

If the user doesn't receive the verification email, they can request a new one through the resend flow:

```bash
curl -X POST "$GW/auth/v1/verify/resend" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "email": "user@example.com"
  }'
```

The resend endpoint:

1. Validates the email format.
2. Checks if the user exists.
3. Checks if the user is already verified (if so, returns `400 email already verified`).
4. Checks rate limits (per-IP and per-email cooldown).
5. Invalidates any existing unexpired `OTP` record for the user.
6. Creates a new `OTP` record.
7. Sends a new verification email.

### Rate limiting on resend

The resend endpoint has stricter rate limiting than the initial `verify` endpoint:

- **Per-IP**: Maximum 5 resend requests per 60 seconds.
- **Per-email**: Minimum 60 seconds between consecutive requests for the same email.
- **Per-user**: Maximum 10 resend requests per hour.

These limits prevent email bombing and abuse of the verification system.

## Email templates

The verification email uses a template that includes a verification link. The template variable `{{verify_url}}` is replaced with the actual URL that includes the one-time code:

```
Verify your email address

Click the link below to verify your email:
{{verify_url}}

This link expires in 15 minutes. If you didn't create an account, you can safely ignore this email.
```

The `{{verify_url}}` template variable is generated by Pawabase and includes the verification code as a query parameter. The URL format is:

```
https://yourapp.com/verify?code=abcdef123456
```

### Customizing email templates

Email templates can be customized in the environment configuration. The default templates include:

- **Verification email**: The template used for email verification. Contains `{{verify_url}}`.
- **Recovery email**: The template used for password recovery. Contains `{{recovery_url}}`.
- **Magic link email**: The template used for magic link sign-in. Contains `{{magic_link_url}}`.

Each template can be configured with custom subject lines, HTML content, and plain-text alternatives.

## Unverified user restrictions

When `require_email_verification` is enabled, unverified users face several restrictions:

1. **Cannot access protected routes**: Any route that requires authentication will reject unverified users with `403 email not verified`.
2. **Cannot change password**: The password change endpoint requires email verification.
3. **Cannot initiate recovery**: Password recovery endpoints require email verification.
4. **Cannot sign out other sessions**: Session management endpoints require verification.
5. **Cannot access admin API**: Admin API endpoints require verified email addresses.

The restrictions are enforced by the `require_email_verification` gate in the authentication middleware. Every authenticated request checks the user's `email_verified` status before processing the request.

### How the restriction is enforced

The enforcement happens at the middleware level:

```python
async def verify_email_middleware(request: Request, call_next):
    principal = get_principal(request)
    if principal and require_email_verification:
        if not principal.email_verified:
            return Response(status_code=403, content="email not verified")
    return await call_next(request)
```

This means the restriction applies to every route that requires authentication, including the token refresh endpoint. An unverified user cannot refresh their tokens — they must verify their email first.

## Admin-initiated verification

Administrators can force-verify a user's email through the admin API:

```bash
POST /projects/{project}/envs/{env}/users/{user_id}/verify-email
```

This endpoint sets `email_verified = True` for the specified user without sending a verification email. It is useful for:

1. **Onboarding**: Administrators can pre-verify emails for known users during onboarding.
2. **Recovery**: If a user loses access to their email, an admin can verify it on their behalf.
3. **Testing**: Administrators can verify test users without sending actual emails.

The admin-initiated verification emits the same `user.email_verified` event as the self-service flow, so audit logs are consistent.

### Admin verification and session creation

When an administrator verifies a user's email, a verification session is not automatically created. The user still needs to sign in to get access tokens. The verification is recorded in the user's profile (`email_verified = True`), but no tokens are issued until the user signs in.

## Verification and social login

When a user signs in with a social provider (Google, GitHub, etc.), the email verification behavior depends on the provider:

1. **Providers that verify email**: Google and GitHub verify email addresses before providing them to Pawabase. When Pawabase receives an email from these providers, the email is considered verified (`email_verified = True`).
2. **Providers that do not verify email**: Some providers may not guarantee email verification. In this case, Pawabase may still set `email_verified = False` and require verification through the standard flow.
3. **`require_email_verification` still applies**: Even if the social provider verifies the email, if `require_email_verification` is enabled, Pawabase may still require the user to verify through the standard flow. This behavior is configurable.

<Warning>
Never trust the email verification status from a social provider without validating it. Always check the `email_verified` claim from the provider's token, and set `email_verified = True` only if the provider confirms it. Some providers may not include an `email_verified` claim at all.
</Warning>

## Verification and organizations

Email verification interacts with organization membership in the following ways:

1. **Organization invitations**: When a user is invited to an organization, the invitation email must be verified. The invitation is only accepted after the user verifies their email through the verification flow.
2. **Organization creation**: A user must verify their email before they can create an organization. This prevents anonymous organization creation.
3. **Organization membership**: Organization membership records are tied to the user's verified email. If a user changes their email, they must re-verify the new email address before it can be used for organization membership.

## Common mistakes

<AccordionGroup>
  <Accordion title="Not configuring `require_email_verification`">
    If you don't set `require_email_verification = true`, new users can access your application without verifying their email. This means anyone can sign up with a fake email and use your application. Always enable this for production applications.
  </Accordion>
  <Accordion title="Not rate-limiting the verify endpoint">
    Without rate limiting, an attacker can send thousands of verification emails to a single address or domain, causing email bombing and potential blacklisting of your sending domain.
  </Accordion>
  <Accordion title="Storing the raw verification code">
    The raw verification code should never be stored in the database. Only the hashed version (`code_hash`) should be persisted. Storing the raw code creates a security vulnerability — if the database is compromised, all verification codes are exposed.
  </Accordion>
  <Accordion title="Not handling expired codes">
    If the `complete` handler doesn't check `expires_at`, expired verification codes could still be accepted. This creates a security vulnerability — an attacker who intercepts an old verification link could still verify the email after the intended expiration time.
  </Accordion>
  <Accordion title="Ignoring the `used` flag">
    If the `complete` handler doesn't check `used == True`, a verification code could be used multiple times. This means an attacker who intercepts the verification link could verify the email multiple times.
  </Accordion>
  <Accordion title="Not sending the correct email template">
    Using the wrong template variable (e.g., `{{recovery_url}}` instead of `{{verify_url}}`) breaks the verification flow. The template must use the correct variable for the specific verification type.
  </Accordion>
</AccordionGroup>
