<Note>This page is about organizations *inside a project*, for your application's users. The organizations that own projects and hold your own team are a different feature: see [Organizations and teams](/concepts/organizations).</Note>

Organizations are Akountz's multi-tenancy primitive: a way to group users *within one environment* into separate tenants, each with its own membership, its own teams, and its own invitation flow — all backed by plain integer-keyed tables, not UUIDs, and with no per-organization auth configuration.

<CardGroup cols={3}>
  <Card title="Five real tables" icon="database">`Organization`, `Membership`, `Team`, `TeamMember`, `Invitation` — integer primary keys throughout, all scoped to one `(project, env)`.</Card>
  <Card title="Four roles, enforced" icon="users">`owner`, `admin`, `member`, `viewer` — validated against a real `ORG_ROLES` tuple, not a free-form string.</Card>
  <Card title="Invitations are tokens" icon="mail">An invitation is a one-time token plus a database row for listing and revocation — not a bare database flag.</Card>
</CardGroup>

## The five models

All defined in `database/models/orgs.py`:

```python
ORG_ROLES = ("owner", "admin", "member", "viewer")

class Organization(Model):
    id = fields.IntField(primary_key=True)
    project = fields.CharField(max_length=63, db_index=True)
    env = fields.CharField(max_length=63)
    slug = fields.CharField(max_length=63)
    name = fields.CharField(max_length=200)
    metadata = AnyJSONField(default=dict)
    created_by = fields.IntField(null=True)
    # unique_together: (project, env, slug)

class Membership(Model):
    id = fields.IntField(primary_key=True)
    organization = fields.ForeignKeyField("models.Organization", related_name="memberships")
    user = fields.ForeignKeyField("models.AuthUser", related_name="memberships")
    role = fields.CharField(max_length=32, default="member")
    # unique_together: (organization, user)

class Team(Model):
    id = fields.IntField(primary_key=True)
    organization = fields.ForeignKeyField("models.Organization", related_name="teams")
    slug = fields.CharField(max_length=63)
    name = fields.CharField(max_length=200)
    # unique_together: (organization, slug)

class TeamMember(Model):
    id = fields.IntField(primary_key=True)
    team = fields.ForeignKeyField("models.Team", related_name="members")
    user = fields.ForeignKeyField("models.AuthUser", related_name="team_memberships")
    # unique_together: (team, user)

class Invitation(Model):
    id = fields.IntField(primary_key=True)
    organization = fields.ForeignKeyField("models.Organization", related_name="invitations")
    email = fields.CharField(max_length=255)
    role = fields.CharField(max_length=32, default="member")
    token_id = fields.CharField(max_length=32)
    invited_by = fields.IntField(null=True)
    accepted_at = fields.DatetimeField(null=True)
    revoked_at = fields.DatetimeField(null=True)
    expires_at = fields.DatetimeField()
```

<Warning>
There is no `Org` model, no `OrgMember` model, no `CommerceOrg` "commerce blueprint," no `invite_only` flag, and no `left_at` timestamp anywhere in this schema. The real models are `Organization` and `Membership` — an organization has exactly one membership row per user, deleted outright (not soft-deleted with a `left_at`) when someone leaves or is removed.
</Warning>

An organization is scoped to a `(project, env)` pair like everything else in Akountz, and its `slug` is unique only within that pair — `acme-hq` can exist as a slug in both `acme/development` and `acme/production` independently, because they're `unique_together` on `(project, env, slug)`, not on `slug` alone.

## Roles within an organization

`Membership.role` is a plain string, but every endpoint that accepts one validates it against the real, closed set:

```python
ORG_ROLES = ("owner", "admin", "member", "viewer")

def _check_role(role: str) -> None:
    if role not in ORG_ROLES:
        raise HTTPException(status_code=422, detail=f"role is one of {', '.join(ORG_ROLES)}")
```

| Role | Can manage members/invitations/teams? | Can delete the organization? |
| --- | --- | --- |
| `owner` | Yes | Yes (and grant/revoke ownership) |
| `admin` | Yes | No |
| `member` | No | No |
| `viewer` | No | No |

"Managers" — the set allowed to invite, change roles, create teams, and remove other members — are `owner` and `admin`:

```python
MANAGERS = ("owner", "admin")
```

Beyond that four-value distinction, `member` and `viewer` carry no different behavior inside Akountz itself — Akountz enforces only the manager/non-manager split at the organization-management endpoints. If your application needs `member` and `viewer` to behave differently against *your own* data (say, viewers can read but not create records), that distinction belongs in your [policy conditions](/policies/conditions), read off `$auth.org_role`, not inside Akountz.

### An organization always keeps at least one owner

Two separate checks enforce this invariant:

```python
if (body.role == "owner" or target.role == "owner") and me.role != "owner":
    raise HTTPException(status_code=403, detail="only owners can grant or remove ownership")
if (target.role == "owner" and body.role != "owner"
        and await Membership.filter(organization=org, role="owner").count() <= 1):
    raise HTTPException(status_code=409, detail="an organization keeps at least one owner")
```

The same "last owner" guard applies to removing a member outright, not just demoting one — you cannot remove the sole remaining owner, and you cannot demote them, without first promoting someone else to `owner`.

## Creating an organization

```bash
curl -X POST "$GW/orgs" \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"slug": "acme-hq", "name": "Acme Corp", "metadata": {"plan": "growth"}}'
```

```json
{
  "id": 7,
  "slug": "acme-hq",
  "name": "Acme Corp",
  "metadata": { "plan": "growth" },
  "role": "owner",
  "created_at": "2026-09-30T10:00:00Z"
}
```

`slug` must match `^[a-z0-9][a-z0-9-]{1,62}$` (lowercase, starts with an alphanumeric, 2–63 characters, hyphens allowed thereafter) and must be unique within the environment — `409 that slug is taken` otherwise. The caller is automatically added as `Membership(role="owner")` — there's no separate step to become a member of an organization you just created. `metadata` is an open JSON object with no schema; use it for whatever organization-level settings your application needs (a plan tier, a billing customer id, feature flags), keeping in mind it's readable and writable by any `owner`/`admin` through `PATCH /orgs/{slug}`.

## Membership and team management

<Tabs>
  <Tab title="Members">
    | Endpoint | Who | Effect |
    | --- | --- | --- |
    | `GET /orgs/{slug}/members` | any member | List every member with role. |
    | `PUT /orgs/{slug}/members/{user_id}` | manager | Change a member's role (subject to the owner-count and ownership-transfer rules above). |
    | `DELETE /orgs/{slug}/members/{user_id}` | manager, or the member themself (leaving) | Remove a member. Also deletes their `TeamMember` rows across every team in the org. |
  </Tab>
  <Tab title="Teams">
    | Endpoint | Who | Effect |
    | --- | --- | --- |
    | `GET /orgs/{slug}/teams` | any member | List teams with member counts. |
    | `POST /orgs/{slug}/teams` | manager | Create a team (`slug` + `name`, same slug pattern as organizations). |
    | `PUT /orgs/{slug}/teams/{team}/members/{user_id}` | manager | Add an existing org member to a team. `404` if the team doesn't exist or the target isn't already an org member. |
    | `DELETE /orgs/{slug}/teams/{team}/members/{user_id}` | manager | Remove someone from a team (they remain an org member). |
  </Tab>
</Tabs>

<Note>
Teams are a flat grouping within an organization — there is no team-level role, no nested teams, and no team-scoped permission set. `TeamMember` is just a join row between `Team` and `AuthUser`. If your application needs team-level authorization, model it in your own data and reference `$auth.org` plus a team lookup in your policies, or keep team membership entirely inside your own schema rather than Akountz's.
</Note>

A user leaving voluntarily and a manager removing them go through the exact same `DELETE /orgs/{slug}/members/{user_id}` endpoint — the only difference is who's allowed to call it for which target (`user_id != caller.id` requires the caller to be a manager; leaving yourself never does). There is no `left_at` timestamp recording *when* someone left; the `Membership` row is deleted outright, so "when did they leave" is only ever recoverable from `LoginEvent`/platform event history (the `organization.deleted`, `invitation.accepted` style events emitted alongside these operations), not from the membership table itself.

## Invitations

Inviting someone by email is a two-part mechanism: a signed, single-use [one-time token](/auth/tokens-and-sessions#one-time-tokens) (purpose `"invite"`, 7-day lifetime) plus an `Invitation` row that lets the organization list, and revoke, pending invitations — the token alone can't do either of those, which is why both exist together.

```bash
curl -X POST "$GW/orgs/acme-hq/invitations" \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{"email": "new.hire@example.com", "role": "member", "redirect_to": "https://app.example.com/invite"}'
```

```json
{
  "id": 3,
  "email": "new.hire@example.com",
  "role": "member",
  "expires_at": "2026-10-07T10:00:00Z"
}
```

Requires manager privileges, rejects an invite to someone who's already a member (`409 already a member`), and sends an email using the `invite` message template (see [Configuration → `emails`](/auth/configuration#emails-customizing-message-templates), which has placeholders `{organization}`, `{project}`, `{role}`, `{link}`).

### Accepting an invitation

```bash
curl -X POST "$GW/invitations/accept" \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" -d '{"token": "eyJ..."}'
```

The signed-in user must already have (or create) an account with **exactly the email the invitation was sent to** — `403 this invitation was sent to another address` otherwise. This means a common real flow is: the invited person clicks the emailed link, which is not yet signed in; your client should route them through sign-up/sign-in with that same address first, and only then submit the accept call with a valid access token.

Acceptance is an *upsert*, not a plain insert — if the invited email already somehow holds a stale, pre-existing membership row (e.g. they were removed and re-invited), accepting replaces its role rather than conflicting:

```python
await upsert(Membership, organization=invitation.organization, user=user, defaults={"role": invitation.role})
```

### Listing and revoking pending invitations

```bash
curl "$GW/orgs/acme-hq/invitations" -H "Authorization: Bearer $ACCESS_TOKEN" -H "apikey: $KEY"
curl -X DELETE "$GW/orgs/acme-hq/invitations/3" -H "Authorization: Bearer $ACCESS_TOKEN" -H "apikey: $KEY"
```

The list only ever shows invitations that are still pending: not accepted, not revoked, and not past `expires_at`. Revoking sets `revoked_at`; the underlying one-time token becomes unusable the moment `accept` is attempted against a row that's no longer `accepted_at=None, revoked_at=None`, even though the signed token itself would otherwise still verify until its 7-day expiry.

## Organizations and sessions

An organization is not just a grouping of users — it can be woven into the *session* itself, so that an access token carries which organization the caller is currently acting within.

### Signing in scoped to an organization

Adding `"org": "acme-hq"` to a `POST /auth/v1/token` request (password, magic-link, or MFA-completion grant) scopes the resulting session:

```json
{ "grant_type": "password", "email": "...", "password": "...", "org": "acme-hq" }
```

If the user is a member, the response carries `org` and `org_role`; if not, the request fails outright with `403 you are not a member of that organization` — Akountz never silently drops an organization the caller explicitly asked for and issues an unscoped token instead.

```python
async def require_membership(config: AuthConfig, user: AuthUser, slug: str | None) -> str | None:
    if not slug:
        return None
    if await membership_role(config, user, slug) is None:
        raise HTTPException(status_code=403, detail="you are not a member of that organization")
    return slug
```

### Switching or clearing the organization on refresh

A refresh (`grant_type: "refresh_token"`) can carry `org` to switch which organization the *new* access token is scoped to, or omit it entirely to keep the session's current organization unchanged:

```python
KEEP: Any = object()

async def refresh_session(..., org: Any = KEEP) -> dict[str, Any]:
    ...
    active = info.org if info else None
    if org is not KEEP:
        active = await require_membership(config, user, org or None)
```

| Request body | Effect |
| --- | --- |
| `org` field omitted entirely | The session's current organization is kept unchanged. |
| `"org": "another-org"` | Switches to that organization (must be a member; `403` otherwise). |
| `"org": null` or `"org": ""` | Clears the organization — the next access token has `org: null`, `org_role: null`. |

The route layer distinguishes "omitted" from "explicitly null" using Pydantic's `model_fields_set`, which is why omitting the field and sending `null` behave differently — this is a real, load-bearing distinction, not an accident:

```python
org=body.org if "org" in body.model_fields_set else KEEP,
```

### The membership role is re-read at issue time

```python
org_role = await membership_role(config, user, org)
if org_role is None:
    org = None
```

Every time an access token is minted — sign-in or refresh — the caller's role in the requested organization is looked up fresh from the `Membership` table. If the role was just changed by an admin, or the membership was just removed, **the currently-live access token still carries the old `org_role` until the session refreshes**; only the *next* refresh picks up the change. This mirrors the same "claims are fixed at mint time" behavior [roles have](/auth/roles-and-permissions#common-mistakes) and [tokens have generally](/auth/tokens-and-sessions#what-changes-at-refresh-not-immediately).

## One auth configuration per environment

There is exactly one `AuthConfig` per `(project, env)` — password policy, `mfa_enabled`, token lifetimes, everything in [Configuration](/auth/configuration) applies uniformly to every organization inside that environment. There is no per-organization override of any of those settings, and no `min_aal` (or any other) field scoped to an individual organization.

<Warning>
If your product needs "organization Acme requires MFA but organization Globex doesn't," that distinction does not exist inside Akountz's configuration model. You would need to enforce it yourself — for example, a policy condition that checks both `$auth.org` and `$auth.claims.aal` together, or an application-level gate that reads a flag from your own database before allowing certain operations for a specific organization's members.
</Warning>

## Real scenarios

### Multi-tenant SaaS with team invitations

A typical B2B SaaS onboarding: a founder signs up, creates an organization (becoming its `owner` automatically), invites teammates by email at `member` or `admin`, and each invitee accepts once they've created or signed into their own account with the matching email. Session tokens are issued with `org` set once a user picks (or is defaulted into) a workspace in your client, and `$auth.org`/`$auth.org_role` drive every organization-scoped policy from there.

### Downgrading a departing admin

An `admin` who's leaving the company should be demoted or removed. If they happen to be the organization's only `owner`, the API refuses both the demotion and the removal until someone else is promoted to `owner` first — this is enforced server-side, not something your client needs to check beforehand, though surfacing a clear error ("promote another owner first") in your UI avoids a confusing raw `409`.

### Re-inviting after a revoked invitation

If an invitation is revoked before being accepted, sending a *new* invitation to the same email is a completely independent `POST /orgs/{slug}/invitations` call — it creates a new token and a new `Invitation` row; the revoked one has no bearing on whether a new one can be issued (the only duplicate check is against *current membership*, not against past invitation history).

## Common mistakes

<AccordionGroup>
  <Accordion title="Looking for an Org or OrgMember model">
    They're `Organization` and `Membership`. Both use plain auto-incrementing integer primary keys, not UUIDs.
  </Accordion>
  <Accordion title="Expecting an invite_only flag">
    There isn't one. Whether an organization accepts self-service joins or only invited members is an application-level decision — Akountz gives you organization creation, membership, and invitations as primitives; it doesn't have an "open vs. closed" organization setting.
  </Accordion>
  <Accordion title="Expecting a left_at timestamp on Membership">
    There isn't one — leaving or being removed deletes the `Membership` row outright. If you need an audit trail of departures, consume the platform event stream (`invitation.accepted`, `organization.created`, `organization.deleted`, and friends emitted via `akountz.emit`) rather than looking for a soft-delete column.
  </Accordion>
  <Accordion title="Assuming a CommerceOrg or any organization 'blueprint' exists">
    It doesn't. There is exactly one organization shape — `Organization` plus `Membership`/`Team`/`Invitation` — with no specialized subtype for commerce or any other vertical.
  </Accordion>
  <Accordion title="Expecting per-organization auth settings like a min_aal">
    Auth configuration (`password_policy`, `mfa_enabled`, token lifetimes, everything in Configuration) is environment-wide. There is no organization-scoped override for any of it.
  </Accordion>
  <Accordion title="Forgetting that org_role only updates on refresh">
    A role change made through `PUT /orgs/{slug}/members/{user_id}` doesn't retroactively change an already-issued access token's `org_role` claim — only the next sign-in or refresh reflects it.
  </Accordion>
</AccordionGroup>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `403 you are not a member of that organization` at sign-in | The `org` slug in the request doesn't have a `Membership` row for this user. | Confirm membership with `GET /orgs`, or have them accept a pending invitation first. |
| `409 an organization keeps at least one owner` | Trying to demote or remove the sole `owner`. | Promote another member to `owner` first. |
| `403 only owners can grant or remove ownership` | An `admin` (not `owner`) tried to change someone to/from `owner`. | Only an `owner` can touch the `owner` role. |
| `403 this invitation was sent to another address` | The signed-in account's email doesn't match the invited email exactly. | Sign in with the exact address the invitation was sent to. |
| An accepted role change to `org_role` isn't visible on the client | The client is using a stale access token. | Refresh the session; `org_role` is re-read at issue time on every refresh. |
