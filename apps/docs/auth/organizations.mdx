Organizations provide multi-tenant architecture for Pawabase applications. An organization is a logical grouping of users that share roles, permissions, and configuration. Organizations allow you to build applications that serve multiple tenants — each tenant has its own set of users, roles, and data isolation.

Organizations are deeply integrated into Pawabase's authentication system. The `$auth.org` object is available in policy expressions, allowing you to write organization-scoped access control. Users can belong to multiple organizations and switch between them seamlessly.

## The `Org` model

The `Org` model represents an organization:

```python
class Org(BaseModel):
    id: UUID = Field(default_factory=uuid4, primary_key=True)
    name: str
    slug: str = Field(unique=True)
    logo_url: str | None = None
    invite_only: bool = False
    created_at: datetime = Field(default_factory=datetime.now(UTC))
    updated_at: datetime = Field(default_factory=datetime.now(UTC))
    deleted_at: datetime | None = None
```

The `Org` model stores the organization's identity and configuration:

- **`name`**: The display name of the organization (e.g., "Acme Corporation").
- **`slug`**: A URL-friendly identifier for the organization (e.g., "acme-corp"). Slugs are unique and used in URLs and references.
- **`logo_url`**: Optional URL to the organization's logo.
- **`invite_only`**: If `True`, new members can only join through an invitation. If `False`, anyone with a valid invite link can join.
- **`deleted_at`**: If set, the organization is soft-deleted. Organization-scoped sessions become invalid when the organization is deleted.

### Organization creation

Organizations are created through the admin API or by the first user (who becomes the organization owner). When an organization is created:

1. A new `Org` record is inserted.
2. The creator is added as the first member via `OrgMember`.
3. The creator is assigned the `owner` role (or a configurable default role).
4. An organization-scoped authentication context is created.

<Note>
The `invite_only` flag controls whether new members can join without an explicit invitation. When `invite_only` is `True`, the organization requires an invitation link or admin approval for new members. When `False`, any user can join using a join link.
</Note>

### Soft delete

Organizations support soft delete through the `deleted_at` field:

1. When an organization is deleted, `deleted_at` is set to the current timestamp.
2. All organization-scoped sessions are invalidated.
3. All `OrgMember` records for the organization remain in the database (for audit purposes).
4. The organization name and slug are preserved.
5. Users who were members of the deleted organization are no longer associated with it — `$auth.org` is `null` for those users.

<Warning>
When an organization is deleted, all sessions for users scoped to that organization become invalid. Users attempting to refresh their tokens with that organization will receive `401 session revoked`. The organization must be restored from the soft delete or the user must create a new session.
</Warning>

## The `OrgMember` model

The `OrgMember` model represents a user's membership in an organization:

```python
class OrgMember(BaseModel):
    id: UUID = Field(default_factory=uuid4, primary_key=True)
    org_id: UUID = Field(foreign_key="org.id")
    user_id: UUID = Field(foreign_key="auth_user.id")
    role: str  # The user's role within the organization
    joined_at: datetime = Field(default_factory=datetime.now(UTC))
    left_at: datetime | None = None
```

The `OrgMember` model tracks:

- **`org_id`**: The organization the user belongs to.
- **`user_id`**: The user who is a member.
- **`role`**: The user's role within this specific organization. This is different from global roles — a user can have the role `"admin"` in one organization and `"member"` in another.
- **`joined_at`**: When the user joined the organization.
- **`left_at`**: When the user left the organization (if applicable). If `null`, the user is still a member.

### Membership states

A user can have the following membership states:

1. **Active**: `left_at` is `null`. The user is a current member.
2. **Left**: `left_at` is set to a timestamp. The user was once a member but has left.
3. **Pending**: The user has been invited but has not yet accepted the invitation.

### Multiple memberships

A user can be a member of multiple organizations. Each membership is a separate `OrgMember` record with its own `org_id`, `role`, and `joined_at`. This allows a user to have different roles in different organizations.

## Organization-scoped authentication

When a user signs in with an organization parameter, their session becomes organization-scoped:

```bash
curl -X POST "$GW/auth/v1/token" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "grant_type": "password",
    "email": "user@example.com",
    "password": "password123",
    "org": "acme-hq"
  }'
```

### The `org` parameter on sign-in

The `org` parameter is accepted on all sign-in endpoints (`password`, `refresh_token`, `magic_link`, social login). It specifies the organization for the session:

1. The server validates that the user is a member of the specified organization.
2. If the user is not a member, the sign-in fails with `403 you are not a member of that organization`.
3. If the user is a member, the `SessionInfo` row is created with `org` set to the organization ID and `org_role` set to the user's role in that organization.
4. The access token includes the `org` claim and the `roles` claim includes the organization role.

### `$auth.org` in policies

The `$auth.org` object is available in policy expressions:

```toml
# Policy example: only allow members of the "acme-hq" organization
[policy]
expression = "$auth.org.slug == 'acme-hq'"
```

The `$auth.org` object contains:

- **`id`**: The organization UUID.
- **`slug`**: The organization slug.
- **`name`**: The organization name.

### `org_role` claim

The `org_role` is the user's role within the organization. It is stored in the `SessionInfo.org_role` field and included in the access token claims. The `org_role` is different from global roles — it is specific to the organization.

```python
# The org_role is included in the token payload:
"org_role": "admin"  # The user's role within the organization
```

The `org_role` is used in policy expressions like `$auth.org_role` to determine what actions the user can perform within the organization.

## Membership management

Administrators can manage organization memberships through the admin API:

### Adding a member

```bash
curl -X POST "$GW/projects/my-project/envs/prod/orgs/{org_id}/members" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "user_id": "user-uuid",
    "role": "member"
  }'
```

Adding a member creates a new `OrgMember` record and emits a `org.member_added` event. If the organization has `invite_only = True`, the member must accept an invitation before the membership is active.

### Removing a member

```bash
curl -X DELETE "$GW/projects/my-project/envs/prod/orgs/{org_id}/members/{user_id}" \
  -H "apikey: $PAWABASE_SECRET_KEY"
```

Removing a member sets `left_at = now()` on the `OrgMember` record. The user's `org` and `org_role` in their active sessions are cleared. The user can still sign in without an organization.

### Updating a member's role

```bash
curl -X PATCH "$GW/projects/my-project/envs/prod/orgs/{org_id}/members/{user_id}" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "role": "admin"
  }'
```

Updating a member's role changes the `role` field on the `OrgMember` record. The new role takes effect on the next refresh — the current access token continues to carry the old role until it expires.

## Switching organizations

Users can switch between organizations they belong to through the refresh flow:

```bash
curl -X POST "$GW/auth/v1/token" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "grant_type": "refresh_token",
    "refresh_token": "rft_8f2c...",
    "org": "acme-hq"
  }'
```

The switch process:

1. The server validates that the user is a member of the target organization.
2. The `SessionInfo` row is updated with the new `org` and `org_role`.
3. New tokens are issued with the updated `org` and `org_role` claims.
4. The `last_active_at` is updated.
5. A `session.org_switched` event is emitted.

### The `KEEP` sentinel

The `KEEP` sentinel is used to preserve the current organization during a refresh:

```bash
curl -X POST "$GW/auth/v1/token" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "grant_type": "refresh_token",
    "refresh_token": "rft_8f2c...",
    "org": "KEEP"
  }'
```

When `org: "KEEP"` is sent, the server preserves the current organization from the existing session. This is useful when the client doesn't know which organization the user is currently scoped to. The `KEEP` sentinel ensures the user doesn't accidentally switch organizations during a refresh.

<Note>
If the `org` parameter is omitted from a refresh request, the current organization is preserved (the default behavior). The `KEEP` sentinel is an explicit way to say "keep the current organization" and is useful when the client is explicitly setting the `org` parameter.
</Note>

## Clearing the organization

To return to a non-organization-scoped session:

```bash
curl -X POST "$GW/auth/v1/token" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "grant_type": "refresh_token",
    "refresh_token": "rft_8f2c...",
    "org": null
  }'
```

Clearing the organization:

1. The `SessionInfo` row's `org` and `org_role` are set to `null`.
2. New tokens are issued with `org: null` and `org_role: null`.
3. The user is now in a "personal" context where `$auth.org` is `null`.

### What clearing affects

1. **`$auth.org`** becomes `null` in policies.
2. **`$auth.org_role`** becomes `null`.
3. **Organization-scoped policies** no longer apply to the user.
4. **Organization resources** (if any) are no longer accessible.
5. **The user can still sign in** — they just don't have an organization context.

## Session management for organizations

Each session has an `org` and `org_role` stored in the `SessionInfo` row. This means:

1. **Multiple sessions per user**: A user can have sessions scoped to different organizations simultaneously.
2. **Session isolation**: Tokens for one organization cannot be used to access resources scoped to a different organization.
3. **Organization switching**: Switching organizations through refresh creates new tokens while preserving the session row.
4. **Organization deletion**: When an organization is deleted, all sessions scoped to that organization are invalidated.

### Listing organization sessions

The admin API can list sessions for a specific organization:

```bash
curl -X GET "$GW/projects/my-project/envs/prod/orgs/{org_id}/sessions" \
  -H "apikey: $PAWABASE_SECRET_KEY"
```

This returns all active sessions for members of the specified organization. Each session includes the member's `user_id`, `org_role`, `method`, `aal`, `ip_address`, and `user_agent`.

## The `min_aal` per organization

Organizations can set their own `min_aal` requirement:

```toml
[org.acme-hq.auth]
min_aal = "aal2"
```

When `min_aal` is set for an organization:

1. Members of the organization must have at least `aal2` to access protected resources within that organization.
2. Refresh requests from sessions with AAL below `min_aal` are denied for that organization.
3. The organization-level `min_aal` overrides the environment-level setting for members of that organization.

### How `min_aal` is enforced per organization

The `min_aal` check happens during the refresh flow:

```python
async def refresh(config, session, refresh_token):
    # ... validate refresh token ...
    # Check min_aal for the session's organization
    if session.org:
        org_min_aal = await get_org_min_aal(session.org)
        if org_min_aal and session.aal < org_min_aal:
            raise PrincipalException("aal2 authentication required")
```

If the session's organization has `min_aal = "aal2"` and the session's AAL is `"aal1"`, the refresh is denied. The user must complete MFA to elevate their AAL before they can refresh.

## Organization metadata

The `Org` model has a `metadata` field for storing arbitrary organization-specific data:

```python
class Org(BaseModel):
    ...
    metadata: dict = Field(default_factory=dict)
```

The `metadata` field is a JSON object that can store any organization-specific configuration:

```json
{
    "billing_plan": "enterprise",
    "feature_flags": {
        "beta_features": true,
        "custom_domains": false
    },
    "settings": {
        "default_role": "member",
        "max_members": 100
    }
}
```

The `metadata` field is not accessible through `$auth.org` in policies. It is stored in the database and accessed through the admin API.

## Commerce blueprint

The commerce blueprint extends organizations with e-commerce capabilities:

```python
class CommerceOrg(Org):
    store_name: str
    currency: str = "USD"
    default_tax_rate: float = 0.0
    payment_settings: dict = Field(default_factory=dict)
    product_catalog: list = Field(default_factory=list)
```

The commerce blueprint adds:

- **Store identity**: `store_name`, `currency`, `default_tax_rate`.
- **Payment configuration**: `payment_settings` for processing payments.
- **Product catalog**: `product_catalog` for managing products.
- **Order management**: Orders are scoped to the organization.

<Note>
The commerce blueprint is an optional extension for organizations that need e-commerce capabilities. It is not part of the core Pawabase authentication system — it extends the `Org` model with commerce-specific fields. See the commerce documentation for more details.
</Note>

## Common mistakes

<AccordionGroup>
  <Accordion title="Not handling organization deletion">
    When an organization is deleted, all sessions scoped to it are invalidated. If you're not handling this case, users may suddenly find themselves unable to refresh their tokens. Always check if the organization still exists on refresh.
  </Accordion>
  <Accordion title="Confusing global roles with `org_role`">
    Global roles are stored in the `Role` table and applied to all organizations. `org_role` is specific to a single organization. A user can have the global role `"admin"` but the `org_role` `"member"` in a specific organization.
  </Accordion>
  <Accordion title="Not setting `invite_only` correctly">
    If `invite_only` is `False` and you're using organization invitations, anyone with the invite link can join. If `invite_only` is `True`, new members must have an explicit invitation. Choose the right setting for your use case.
  </Accordion>
  <Accordion title="Not using `KEEP` when switching organizations">
    Omitting `org` from a refresh preserves the current organization. But if the client explicitly sets `org`, it switches. Use `KEEP` to preserve the current organization when you're not sure which one the user is currently scoped to.
  </Accordion>
  <Accordion title="Storing sensitive data in `Org.metadata`">
    The `metadata` field is a JSON object stored in the database. It's not accessible through `$auth.org` in policies. Don't store data you need to gate access on in `metadata` — use roles and `org_role` instead.
  </Accordion>
</AccordionGroup>
