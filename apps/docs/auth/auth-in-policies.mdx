Pawabase uses a policy engine to enforce access control on protected routes and operations. Policies are written in a simple expression language that evaluates the `$auth` object — which contains all the information about the authenticated user. Policies determine whether a request is allowed or denied based on the user's identity, roles, organization, and authentication level.

The `$auth` object is available in every policy expression. It is constructed from the access token claims and provides a structured way to access the user's identity, roles, organization, and metadata within policy expressions.

## The `$auth` object structure

The `$auth` object is constructed from the access token claims. Every authenticated request has a `Principal` object that provides access to all claims:

```python
class Principal:
    def __init__(self, token: dict, secret: str):
        self.claims = token
        self.org = token.get("org")
        self.user_id = token.get("sub")
        self.session_id = token.get("session_id")
        self.roles = token.get("roles", [])
        self.claims["roles"] = self.roles
        self.claims["org"] = self.org
        self.claims["aal"] = token.get("aal", "aal1")
```

The `$auth` object exposes the following fields:

| Expression | Type | Description |
| --- | --- | --- |
| `$auth.claims` | object | All token claims. Contains `roles`, `org`, `aal`, `user`, `app`, `sub`, `session_id`, etc. |
| `$auth.org` | object or null | The organization context. `null` if the session is not organization-scoped. |
| `$auth.org_role` | string or null | The user's role within the organization. `null` if not scoped to an org. |
| `$auth.user_id` | string | The user's unique ID (`sub` claim). |
| `$auth.session_id` | string | The session UUID. |
| `$auth.operator` | boolean | `true` if the request came from a service key, `false` otherwise. |
| `$auth.claims.roles` | array of strings | The role names assigned to the user. |
| `$auth.claims.aal` | string | The Authenticator Assurance Level. |
| `$auth.claims.user` | object | The `user_metadata` object. **Not safe for policies.** |
| `$auth.claims.app` | object | The `app_metadata` object. **Safe for policies.** |

### `$auth.org` structure

When the session is organization-scoped, `$auth.org` is an object:

```json
{
    "id": "uuid-here",
    "slug": "acme-hq",
    "name": "Acme Corporation"
}
```

When the session is not organization-scoped, `$auth.org` is `null`. Policies that reference `$auth.org` must handle the `null` case:

```toml
# Policy example: only allow if the user is in an organization
expression = "$auth.org != null && $auth.org.slug == 'acme-hq'"
```

### `$auth.operator` flag

The `operator` flag indicates whether the request was authenticated using a service key:

- **`$auth.operator == false`**: The request was authenticated by a user (password, magic link, social login, or refresh). The user's identity, roles, and organization are available.
- **`$auth.operator == true`**: The request was authenticated by a service key. The service key's claims are available, but user-specific fields like `roles`, `org`, and `org_role` may be empty or set by the service key configuration.

The `operator` flag is critical for distinguishing between user-initiated requests and service-initiated requests. Backend services, cron jobs, and server-to-server communication use service keys, while frontend applications use user authentication.

<Warning>
Never trust `$auth.operator` alone for access control. A service key may have broad permissions, but the policy should still verify that the specific operation is allowed. Always combine `$auth.operator` checks with other policy conditions.
</Warning>

## Meta vs app claims

The distinction between `meta` (user_metadata) and `app` (app_metadata) is critical for policy design:

### `user` (meta) claims

The `user` claim contains `user_metadata` — data that the user themselves can modify:

- **Profile information**: Name, avatar, preferences.
- **Custom fields**: Any user-editable data.
- **Public information**: Data that should not gate access.

Because users can modify `user_metadata` themselves, **it must never be used for access decisions**. A malicious user could simply change their own metadata to gain access to protected resources.

### `app` claims

The `app` claim contains `app_metadata` — data that only administrators or service keys can modify:

- **Role assignments**: Tiers, plans, access levels.
- **Permissions**: Feature flags, access controls.
- **Administrative data**: Internal metadata that should not be user-editable.

Because only administrators can modify `app_metadata`, **it is safe to use for access decisions**. Users cannot change their own `app_metadata` to gain unauthorized access.

### Policy examples using meta vs app

```toml
# ❌ BAD — user can modify this themselves
expression = "$auth.claims.user.tier == 'premium'"

# ✅ GOOD — only admins can modify this
expression = "$auth.claims.app.tier == 'premium'"
```

```toml
# ❌ BAD — user could change their own role
expression = "$auth.claims.user.role == 'admin'"

# ✅ GOOD — only admins can assign roles
expression = "$auth.claims.app.role == 'admin'"
```

```toml
# ✅ Correctly checking both meta and app
expression = "$auth.claims.app.verified == true && $auth.claims.user.status == 'active'"
```

## Policy expression language

Policy expressions are written in a simple expression language that evaluates to a boolean. The expression can reference any field of the `$auth` object using dot notation.

### Basic operators

| Operator | Description | Example |
| --- | --- | --- |
| `==` | Equal to | `$auth.claims.app.tier == 'premium'` |
| `!=` | Not equal to | `$auth.claims.aal == 'aal2'` |
| `&&` | Logical AND | `$auth.claims.app.tier == 'premium' && $auth.claims.aal == 'aal2'` |
| `||` | Logical OR | `$auth.claims.roles contains 'admin' || $auth.claims.app.bypass == true` |
| `!` | Logical NOT | `$auth.claims.app.disabled != true` |
| `contains` | Array membership | `$auth.claims.roles contains 'editor'` |
| `in` | List membership | `$auth.claims.app.tier in ['free', 'premium']` |

### String comparison

String comparisons are case-sensitive. If you need case-insensitive comparison, use the `lower()` function:

```toml
expression = "lower($auth.claims.user.department) == 'engineering'"
```

### Array operations

Array operations allow checking whether a value exists in an array:

```toml
# Check if the user has a specific role
expression = "$auth.claims.roles contains 'admin'"

# Check if the user's tier is in a list of allowed tiers
expression = "$auth.claims.app.tier in ['free', 'premium', 'enterprise']"
```

### Complex expressions

Complex expressions combine multiple conditions:

```toml
# Premium user in the acme-hq organization with at least aal2
expression = "$auth.claims.app.tier == 'premium' && $auth.org.slug == 'acme-hq' && $auth.claims.aal == 'aal2'"

# Admin or user with verified email and active status
expression = "$auth.claims.roles contains 'admin' || ($auth.claims.app.email_verified == true && $auth.claims.app.active == true)"
```

## Role-based policy examples

### Simple role check

```toml
# Only users with the 'admin' role can access this route
[policy]
expression = "$auth.claims.roles contains 'admin'"
```

### Multiple roles

```toml
# Users with 'admin' or 'editor' role can access
[policy]
expression = "$auth.claims.roles contains 'admin' || $auth.claims.roles contains 'editor'"
```

### Role check with organization

```toml
# Admin in the acme-hq organization
[policy]
expression = "$auth.org.slug == 'acme-hq' && $auth.org_role == 'admin'"
```

### Role hierarchy (none — flat)

Pawabase does not have a built-in role hierarchy. Roles are flat — there is no inheritance between roles. If you need a role hierarchy, implement it in the policy expression:

```toml
# Manual role hierarchy: admin > editor > member
expression = "$auth.claims.roles contains 'admin' || ($auth.claims.roles contains 'editor' && $auth.claims.app.access_level >= 2)"
```

<Warning>
Pawabase roles are flat. There is no implicit inheritance between roles. If you need a hierarchy (e.g., admin > editor > member), you must implement it yourself in the policy expression or through `app_metadata`.
</Warning>

## Organization-based policy examples

### Organization scope

```toml
# Only users in the acme-hq organization
[policy]
expression = "$auth.org != null && $auth.org.slug == 'acme-hq'"
```

### Organization and role

```toml
# Users who are admins in their organization
[policy]
expression = "$auth.org_role == 'admin'"
```

### Multiple organizations

```toml
# Users in either acme-hq or globex-inc
[policy]
expression = "$auth.org.slug == 'acme-hq' || $auth.org.slug == 'globex-inc'"
```

### Organization-level `min_aal`

```toml
# Only aal2 sessions in the acme-hq organization
[policy]
expression = "$auth.org.slug == 'acme-hq' && $auth.claims.aal == 'aal2'"
```

## Combined role and organization policies

The most common use case is combining role-based and organization-based policies:

```toml
# Admins can access everything, editors can access the acme-hq org
[policy]
expression = "$auth.claims.roles contains 'admin' || ($auth.org.slug == 'acme-hq' && $auth.claims.roles contains 'editor')"
```

```toml
# Users in acme-hq with at least aal2 can access premium features
[policy]
expression = "$auth.org.slug == 'acme-hq' && $auth.claims.aal == 'aal2' && $auth.claims.app.premium == true"
```

```toml
# Only org admins can manage members, and only in their own org
[policy]
expression = "$auth.org_role == 'admin' && $auth.claims.app.action == 'manage_members'"
```

## The `require_aal` directive

The `require_aal` directive is a special policy configuration that enforces a minimum Authenticator Assurance Level:

```toml
[auth]
require_aal = "aal2"
```

When `require_aal` is set, every request is checked against the minimum AAL. If the session's AAL is below the minimum, the request is denied with `403 aal2 authentication required`.

### Environment-level `require_aal`

Set at the environment level:

```toml
[auth]
require_aal = "aal2"
```

This applies to all requests in this environment. All sessions must have at least `aal2` to access any protected resource.

### Organization-level `require_aal`

Set at the organization level:

```toml
[org.acme-hq.auth]
require_aal = "aal2"
```

This applies only to members of the `acme-hq` organization. Members of other organizations are not affected.

### `require_aal` vs policy expressions

`require_aal` is a hard requirement — it is enforced before the policy expression is evaluated. The policy expression is evaluated only if the `require_aal` check passes. This means:

1. If `require_aal = "aal2"`, all sessions must have `aal2` or higher.
2. The policy expression can still further restrict access (e.g., only admins can access a specific route).
3. `require_aal` is not a substitute for policy expressions — it is an additional enforcement layer.

## The `has_permission` function

The `has_permission` function checks whether the user has a specific permission:

```toml
expression = "has_permission($auth, 'user:delete')"
```

The `has_permission` function checks the user's roles and permissions against a permission string. It returns `true` if the user has the permission, `false` otherwise.

The function uses the `Role.permissions` array and the `RoleAssignment` records to determine whether the user has the specified permission. See [Roles and permissions →](/auth/roles-and-permissions) for the complete reference.

### Performance considerations

The `has_permission` function performs database lookups to resolve the user's permissions. For performance-critical endpoints, consider caching the permission result or using role-based checks instead of permission-based checks:

```toml
# ✅ Fast — simple role check
expression = "$auth.claims.roles contains 'admin'"

# ⚠️ Slower — permission check with database lookups
expression = "has_permission($auth, 'user:delete')"
```

For high-traffic endpoints, prefer role-based checks (`$auth.claims.roles contains ...`) over permission-based checks (`has_permission(...)`).

## Admin override of policy decisions

Administrators can override policy decisions through the `force` flag:

### The `force` flag

The `force` flag bypasses policy evaluation for a specific request. When `force = true`, the request is allowed regardless of the policy expression:

```toml
[auth]
force = true  # All requests bypass policy evaluation
```

The `force` flag is intended for administrative operations and should be used sparingly:

1. **Emergency access**: When a policy is incorrectly denying access to a legitimate user.
2. **Administrative operations**: When an administrator needs to perform an operation that would normally be denied by policy.
3. **Testing**: During policy testing, to verify that the request would be allowed without policy enforcement.

<Warning>
The `force` flag bypasses ALL policy evaluation. Never use `force = true` in production for regular user requests. It should only be used by administrators for specific operations. All `force` overrides are logged in the audit trail.
</Warning>

### Audit logging for overrides

Every policy override is logged:

```json
{
    "event": "policy.override",
    "user_id": "uuid-here",
    "session_id": "uuid-here",
    "resource": "/projects/my-project/envs/prod/users/{user_id}",
    "policy_expression": "$auth.claims.roles contains 'admin'",
    "force": true,
    "operator": true,
    "timestamp": "2025-09-28T10:00:00Z",
    "reason": "emergency_access"
}
```

Audit logs include the policy expression, whether `force` was used, the operator status, the timestamp, and the reason for the override. This provides a complete audit trail of all policy decisions and overrides.

## Policy evaluation order

Policies are evaluated in a specific order:

1. **`require_aal` check**: If `require_aal` is configured, the AAL is checked first. If the AAL is below the minimum, the request is denied immediately.
2. **`force` check**: If `force` is `true`, the policy expression is bypassed and the request is allowed.
3. **Policy expression evaluation**: The policy expression is evaluated against the `$auth` object.
4. **`has_permission` check**: If the policy expression passes, the `has_permission` function is evaluated (if referenced).
5. **Decision**: The final decision is `allow` if all checks pass, or `deny` if any check fails.

The evaluation order ensures that hard requirements (`require_aal`) are checked before soft requirements (policy expressions), and that `force` overrides are the last resort.

## Common mistakes

<AccordionGroup>
  <Accordion title="Using `user` claims for access decisions">
    Never gate access on `$auth.claims.user` fields — users can modify their own `user_metadata`. Use `$auth.claims.app` instead, which only administrators can modify.
  </Accordion>
  <Accordion title="Not handling `$auth.org == null`">
    Policies that reference `$auth.org` must handle the `null` case. A missing `org` will throw an error when accessing `$auth.org.slug`. Always check `$auth.org != null` first.
  </Accordion>
  <Accordion title="Confusing `$auth.operator` with `force`">
    `$auth.operator` indicates whether a service key was used. `force` bypasses policy evaluation. They are unrelated — a service key request still goes through policy evaluation unless `force` is set.
  </Accordion>
  <Accordion title="Using `force` for regular requests">
    The `force` flag is for emergency administrative overrides only. Using it for regular requests bypasses all policy enforcement and creates a security vulnerability.
  </Accordion>
  <Accordion title="Ignoring `require_aal` in policy design">
    `require_aal` is checked before policy expressions. If `require_aal = "aal2"` and a user has `aal1`, the policy expression is never evaluated. Always design policies with `require_aal` in mind.
  </Accordion>
  <Accordion title="Not logging policy overrides">
    All `force` overrides should be logged for audit purposes. If you're not logging overrides, you can't track when and why policies were bypassed.
  </Accordion>
</AccordionGroup>
