Multi-factor authentication (MFA) adds a second factor of authentication beyond the password or email link. Pawabase supports TOTP (Time-Based One-Time Password) as the primary MFA method, with 10 recovery codes for account recovery when the TOTP device is lost. MFA is enforced through the `require_mfa` configuration flag and the `require_aal` policy directive.

MFA is deeply integrated into Pawabase's authentication system. Every sign-in method (password, magic link, social login) can optionally require MFA. The AAL (Authenticator Assurance Level) system tracks the strength of authentication, and the `require_aal` policy directive enforces minimum AAL requirements for sensitive operations.

## How MFA works

MFA in Pawabase is implemented through TOTP:

<Steps>
  <Step title="MFA is enabled for the environment">
    The `require_mfa` flag is set to `true` in the environment configuration. This requires all users to complete MFA before accessing protected resources.
  </Step>
  <Step title="User enrolls in MFA">
    The user generates a TOTP secret (`mfa_secret`) and scans a QR code with an authenticator app. The secret is stored securely in the `AuthUser` record.
  </Step>
  <Step title="TOTP codes are generated">
    The authenticator app generates 6-digit codes that change every 30 seconds based on the TOTP secret and the current time.
  </Step>
  <Step title="User provides the code">
    During sign-in, the user enters the TOTP code from their authenticator app. Pawabase validates the code against the stored secret.
  </Step>
  <Step title="AAL is elevated to `aal2`">
    If the TOTP code is valid, the session's AAL is elevated from `aal1` to `aal2`. The user now has multi-factor authentication.
  </Step>
</Steps>

### TOTP algorithm

Pawabase uses the standard TOTP algorithm (RFC 6238):

1. **Secret generation**: A 160-bit (20-byte) random secret is generated using `secrets.token_bytes(20)`. The secret is base32-encoded for display.
2. **QR code generation**: The secret is encoded as a URI (`otpauth://totp/...`) that can be scanned by authenticator apps.
3. **Code generation**: Every 30 seconds, the authenticator app computes `HMAC-SHA1(secret, current_time_slot)` and truncates the result to a 6-digit code.
4. **Code validation**: Pawabase computes the expected code using the same algorithm and compares it against the user's submitted code. A window of ±1 time slot is allowed to account for clock drift.

<Note>
The TOTP secret is stored in the `AuthUser.mfa_secret` field. It is stored as a base32-encoded string. The secret should never be exposed to the user after enrollment — it is only displayed once during the QR code generation step.
</Note>

### TOTP enrollment flow

1. The user initiates MFA enrollment through the self-service API or admin API.
2. Pawabase generates a new `mfa_secret` and stores it in the `AuthUser` record with `mfa_enabled = True`.
3. Pawabase generates a QR code URI that the user can scan with their authenticator app.
4. The user scans the QR code and enters a verification code to confirm the setup.
5. Pawabase validates the verification code against the stored secret.
6. If valid, the enrollment is complete and the user is now MFA-protected.

### `mfa_secret` field

The `AuthUser.mfa_secret` field stores the TOTP secret:

```python
class AuthUser(BaseModel):
    id: UUID = Field(default_factory=uuid4, primary_key=True)
    email: str = Field(unique=True)
    password_hash: str | None = None
    mfa_secret: str | None = None  # Base32-encoded TOTP secret
    mfa_enabled: bool = False
    failed_logins: int = 0
    ...
```

- **`mfa_secret`**: The base32-encoded TOTP secret. `null` if MFA is not enabled or has not been enrolled.
- **`mfa_enabled`**: `True` if the user has enrolled in MFA and the secret is set. `False` otherwise.

When `mfa_enabled` is `True`, the `mfa_secret` must be a valid base32 string. If `mfa_enabled` is `True` but `mfa_secret` is `null`, the user cannot complete MFA challenges.

## Recovery codes

Recovery codes are single-use codes that allow the user to sign in when they have lost access to their TOTP device. Each user receives 10 recovery codes upon MFA enrollment.

### The `MFARecoveryCode` model

Recovery codes are stored in the `MFARecoveryCode` table:

```python
class MFARecoveryCode(BaseModel):
    id: UUID = Field(default_factory=uuid4, primary_key=True)
    user_id: UUID = Field(foreign_key="auth_user.id")
    code: str  # The raw recovery code
    code_hash: str  # SHA-256 hash of the code
    used: bool = False
    created_at: datetime = Field(default_factory=datetime.now(UTC))
    used_at: datetime | None = None
```

The `MFARecoveryCode` model stores:

- **`user_id`**: The user who owns this recovery code.
- **`code`**: The raw recovery code (used temporarily during validation).
- **`code_hash`**: The SHA-256 hash of the code. Only the hash is stored persistently.
- **`used`**: `True` if the code has been used. Recovery codes are single-use.
- **`used_at`**: The timestamp when the code was used.

### Recovery code generation

When MFA is enrolled, 10 recovery codes are generated:

```python
def generate_recovery_codes(user_id: UUID) -> list[str]:
    codes = []
    for _ in range(10):
        code = secrets.token_hex(4)  # 8-character hex string
        code_hash = hashlib.sha256(code.encode()).hexdigest()
        MFARecoveryCode.create(user_id=user_id, code=code, code_hash=code_hash)
        codes.append(code)
    return codes
```

Each code is an 8-character hexadecimal string. The codes are displayed to the user once during enrollment and should be saved securely. Pawabase never stores the raw codes — only their hashes.

### Recovery code usage

When a user enters a recovery code during sign-in:

1. The code is hashed using SHA-256.
2. The hash is compared against the `MFARecoveryCode` table.
3. If a matching record is found and `used == False`:
   - The code is marked as `used = True`.
   - The `used_at` timestamp is set.
   - The user is signed in with an `aal2` session.
4. If a matching record is found and `used == True`:
   - The code has already been used. The sign-in fails with `400 recovery code already used`.
5. If no matching record is found:
   - The code is invalid. The sign-in fails with `400 invalid recovery code`.

### Recovery code security

Recovery codes are designed to be used only as a last resort:

1. **Single-use**: Each code can only be used once. After use, it is permanently marked as `used = True`.
2. **Hashed storage**: Only the SHA-256 hash is stored. The raw codes are never persisted.
3. **Limited supply**: Only 10 codes per user. Once all 10 are used, the user cannot recover through codes and must use a different method (e.g., admin MFA reset or password recovery).
4. **Admin monitoring**: Administrators can see how many recovery codes remain unused through the admin API.

## Admin MFA reset

Administrators can reset a user's MFA settings through the admin API:

```bash
POST /projects/{project}/envs/{env}/users/{user_id}/reset-mfa
```

The admin MFA reset:

1. Clears the user's `mfa_secret` (sets it to `null`).
2. Sets `mfa_enabled = False`.
3. Invalidates all recovery codes (sets `used = True` for all `MFARecoveryCode` records).
4. Revokes all existing sessions for the user.
5. Emits a `user.mfa_reset` event.

After an admin MFA reset, the user must re-enroll in MFA to regain MFA protection. The user can sign in without MFA (aal1) until they re-enroll.

### Why admin MFA reset is important

Admin MFA reset is a critical safety valve:

1. **Lost TOTP device**: If the user loses their phone or authenticator app, they cannot generate TOTP codes. The admin can reset MFA so the user can sign in and re-enroll.
2. **Compromised TOTP**: If the user suspects their TOTP secret has been compromised, the admin can reset MFA to invalidate all existing codes.
3. **Employee offboarding**: When an employee leaves the organization, admin MFA reset is part of the offboarding process.

<Warning>
Admin MFA reset revokes all sessions for the user. The user will need to sign in again from scratch. This is a security measure — if an admin resets MFA, any existing sessions could be from a compromised account.
</Warning>

### Who can perform admin MFA reset

Only administrators with the appropriate permissions can perform MFA resets. The service key must have the `user_mfa_reset` permission. The admin API is protected by the service key authentication mechanism.

## AAL levels

Pawabase defines three levels of Authenticator Assurance Level:

<CardGroup cols={3}>
  <Card title="`aal1`" icon="circle" subtitle="Single-factor">Password, magic link, or social login without MFA.</Card>
  <Card title="`aal2`" icon="shield-check" subtitle="Multi-factor">Password + TOTP, magic link + TOTP, or social login + TOTP.</Card>
  <Card title="`aal3`" icon="key-round" subtitle="Phishing-resistant">Reserved for future hardware security keys.</Card>
</CardGroup>

### `aal1` — Single-factor authentication

`aal1` is the default AAL for all sign-in methods that do not include MFA:

- Password sign-in without MFA
- Magic link sign-in (without MFA)
- Social login without MFA
- Recovery sign-in (without MFA)

`aal1` sessions are created when the user completes the primary authentication factor (password, magic link, or social login) without completing an MFA challenge.

### `aal2` — Multi-factor authentication

`aal2` is the AAL for sessions that include MFA:

- Password sign-in + TOTP
- Magic link sign-in + TOTP
- Social login sign-in + TOTP
- Recovery sign-in + TOTP or recovery code

`aal2` sessions are created when the user completes the primary authentication factor and then completes an MFA challenge (TOTP code or recovery code).

### `aal3` — Phishing-resistant authentication

`aal3` is reserved for future use. It will support phishing-resistant authentication methods such as hardware security keys (FIDO2/WebAuthn). Currently, `aal3` is not implemented and any attempt to use it returns `403 aal3 not yet supported`.

### AAL in the `Principal`

The AAL is stored in the `Principal` object and the access token:

```python
class Principal:
    def __init__(self, token: dict, secret: str):
        self.claims = token
        self.claims["aal"] = token.get("aal", "aal1")
```

The AAL is accessible through `Principal.claims["aal"]` and `$auth.claims.aal` in policies. The `require_aal` policy directive uses this value to enforce minimum AAL requirements.

## Policy enforcement with `require_aal`

The `require_aal` policy directive enforces a minimum AAL for specific operations:

```toml
[auth]
require_aal = "aal2"
```

When `require_aal` is set:

1. Every authenticated request is checked against the minimum AAL.
2. If the session's AAL is below the minimum, the request is denied with `403 aal2 authentication required`.
3. The client must prompt the user to complete an MFA challenge to elevate the AAL.
4. Once the user completes the MFA challenge, a new session with `aal2` is created and the request is allowed.

### `require_aal` with organization scope

`require_aal` can be set at the organization level in addition to the environment level:

```toml
# Environment-level (applies to all users)
require_aal = "aal2"

# Organization-level (applies only to members of this org)
[org.my-org.auth]
require_aal = "aal2"
```

Organization-level `require_aal` overrides the environment-level setting for members of that organization. If a user is a member of multiple organizations with different `require_aal` settings, the highest requirement applies.

### `require_aal` vs `require_mfa`

The `require_aal` and `require_mfa` configurations are related but distinct:

| Configuration | Scope | Effect |
| --- | --- | --- |
| `require_mfa` | Environment-level | All users must complete MFA before accessing the application. |
| `require_aal` | Environment and organization-level | Specifies the minimum AAL for the application or organization. |
| `require_email_verification` | Environment-level | All users must verify their email before accessing the application. |

If `require_mfa` is `true`, all sessions are `aal2` or higher. If `require_aal` is `"aal2"` but `require_mfa` is `false`, users can still sign in with `aal1` but cannot access resources that require `aal2`. The `require_aal` directive is more granular than `require_mfa`.

<Warning>
`require_mfa` and `require_aal` work together. Setting `require_mfa = true` automatically enforces `aal2` for all users. Setting `require_aal = "aal2"` without `require_mfa` requires users to complete MFA on their first request to a protected resource.
</Warning>

## Failed MFA attempts and lockout

Pawabase tracks failed MFA attempts and enforces lockout after a threshold is reached:

### Failed attempt tracking

Every failed MFA attempt is recorded on the `AuthUser` record:

```python
class AuthUser(BaseModel):
    ...
    failed_logins: int = 0  # Track of failed login attempts (including MFA failures)
    ...
```

The `failed_logins` counter is incremented on every failed sign-in attempt (including failed MFA validation). The counter is reset to `0` when:

1. The user successfully signs in (including successful MFA validation).
2. The user changes their password (through recovery or `new_password`).
3. An administrator resets the user's account.

### Lockout threshold

The lockout threshold is configured at the environment level:

```python
# Environment configuration:
mfa_failed_attempts_lockout = 5  # Maximum failed MFA attempts before lockout
```

When `failed_logins` exceeds the threshold:

1. The user's account is locked.
2. Subsequent sign-in attempts are rejected with `403 account locked`.
3. The user cannot sign in until the lockout is cleared by an administrator or until the lockout period expires.
4. The lockout period is configurable (default: 15 minutes).

### Lockout bypass

Administrators can bypass the lockout through the admin API:

```bash
POST /projects/{project}/envs/{env}/users/{user_id}/unlock
```

The unlock endpoint:

1. Resets `failed_logins` to `0`.
2. Clears any lockout flag.
3. Emits a `user.unlocked` event.
4. Allows the user to sign in again.

The lockout bypass is an administrative tool and should only be used when the legitimate user is locked out and needs to regain access.

### `failed_logins` and password recovery

When a user completes password recovery (through `/recover/complete`), the `failed_logins` counter is reset to `0`. This is intentional — the password recovery flow requires a recovery token, which is a strong form of authentication. If the user has recovered their password, they should not be locked out from signing in with their new password.

## MFA interaction with each sign-in method

MFA interacts with each sign-in method differently:

### Password sign-in + MFA

The standard flow is:

1. User enters email and password.
2. Pawabase validates the password against the stored hash.
3. If `mfa_enabled` is `True` for the user, Pawabase prompts for a TOTP code.
4. The user enters the TOTP code.
5. Pawabase validates the TOTP code against `mfa_secret`.
6. If valid, a session with `aal2` is created.
7. If invalid, `failed_logins` is incremented.

### Magic link sign-in + MFA

The flow is similar but starts with the magic link:

1. User requests a magic link via email.
2. User clicks the magic link and submits it to the `complete` handler.
3. Pawabase validates the token and creates a session with `aal1`.
4. If `mfa_enabled` is `True`, Pawabase prompts for a TOTP code.
5. The user enters the TOTP code.
6. Pawabase validates the TOTP code and elevates the session to `aal2`.

<Note>
With magic link sign-in, the initial session is `aal1` (because the magic link alone doesn't prove MFA). The user must complete the MFA challenge to reach `aal2`. Some applications may allow limited access with `aal1` and require `aal2` for sensitive operations.
</Note>

### Social login + MFA

The flow for social login with MFA:

1. User signs in with a social provider.
2. Pawabase validates the social provider's token and creates a session with `aal1`.
3. If `mfa_enabled` is `True`, Pawabase prompts for a TOTP code.
4. The user enters the TOTP code.
5. Pawabase validates the TOTP code and elevates the session to `aal2`.

Social login with MFA has a subtle difference: the social provider may have already verified the user's email (indicated by `email_verified` in the ID token). However, email verification is not MFA — it is a single factor (ownership of the email). MFA requires a second factor (TOTP, hardware key, etc.).

### Recovery sign-in + MFA

When a user signs in with a recovery code:

1. User enters their email and recovery code.
2. Pawabase validates the recovery code against the `MFARecoveryCode` table.
3. If valid, a session with `aal2` is created (recovery codes are considered a valid second factor).
4. The recovery code is marked as `used = True`.
5. The user is signed in and must re-enroll in MFA (a new `mfa_secret` and recovery codes are generated).

## MFA and email verification

MFA and email verification are independent but complementary:

1. **Email verification** confirms that the user owns the email address they provided.
2. **MFA** confirms that the user has the TOTP device associated with their account.
3. A user can be email-verified but not have MFA enabled (aal1).
4. A user can have MFA enabled but not be email-verified (unlikely in practice but technically possible).
5. `require_email_verification` and `require_mfa` can both be enabled simultaneously. In this case, a user must both verify their email and complete MFA to access protected resources.

### `require_email_verification` + `require_mfa`

When both are enabled:

1. New sign-ups must verify their email before accessing the application.
2. After email verification, the user must also enroll in MFA.
3. Sign-in requires both email verification and MFA.
4. The session AAL is `aal2` after both checks pass.

The `require_email_verification` flag does not automatically enable MFA. They are separate configuration flags that can be used independently or together.

## Common mistakes

<AccordionGroup>
  <Accordion title="Storing `mfa_secret` in plaintext">
    The TOTP secret should be stored as a base32-encoded string, not as plaintext. If the database is compromised, an attacker could use the secret to generate valid TOTP codes. Always store the secret securely.
  </Accordion>
  <Accordion title="Not invalidating recovery codes after admin reset">
    When an admin resets MFA, all recovery codes must be invalidated. If they are not, an attacker could use an old recovery code to bypass the new MFA setup.
  </Accordion>
  <Accordion title="Not resetting `failed_logins` after password recovery">
    If `failed_logins` is not reset after password recovery, the user may still be locked out even after successfully recovering their password.
  </Accordion>
  <Accordion title="Confusing `require_mfa` with `require_aal`">
    `require_mfa` mandates MFA for all users. `require_aal` specifies a minimum AAL. Setting `require_aal = "aal2"` without `require_mfa` means users can still sign in with `aal1` — they just can't access protected resources until they complete MFA.
  </Accordion>
  <Accordion title="Allowing `aal1` access when `require_aal = "aal2"`">
    If `require_aal = "aal2"` is set, all `aal1` sessions should be denied access to protected resources. Failing to enforce this undermines the entire MFA policy.
  </Accordion>
  <Accordion title="Not limiting recovery code usage">
    Recovery codes are single-use. If a recovery code can be used multiple times, an attacker who intercepts a recovery code could sign in repeatedly.
  </Accordion>
</AccordionGroup>
