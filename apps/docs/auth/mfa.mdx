Pawabase's second factor is TOTP (RFC 6238) — the six-digit, time-based codes produced by an authenticator app like Google Authenticator, Authy, or a password manager's built-in generator. Sillo has no one-time-password primitive of its own, so this comes from `pyotp`. This page documents the whole lifecycle: enrollment, confirmation, verification during sign-in, recovery codes, and how MFA interacts with sessions through the assurance level.

<CardGroup cols={3}>
  <Card title="One factor at a time" icon="smartphone">An account has at most one confirmed `MfaFactor`. Re-enrolling replaces it.</Card>
  <Card title="Secrets are encrypted, never plain" icon="lock">The TOTP secret is stored as `secret_ciphertext`, sealed with the platform's secret box — never as plain base32.</Card>
  <Card title="Recovery codes are hashed" icon="key">Ten single-use codes are issued on confirmation. Only their SHA-256 hash is ever stored.</Card>
</CardGroup>

## The two real models

MFA state lives in two tables, both in `database/models/users.py`. Neither resembles a `mfa_secret` column on the user row, and neither is named `MFARecoveryCode`.

### `MfaFactor`

```python
class MfaFactor(Model):
    """A second factor. TOTP secrets are encrypted at rest."""
    id = fields.IntField(primary_key=True)
    user = fields.ForeignKeyField("models.AuthUser", related_name="factors", on_delete=fields.CASCADE)
    kind = fields.CharField(max_length=16, default="totp")
    secret_ciphertext = fields.TextField()
    confirmed_at = fields.DatetimeField(null=True)
    last_used_step = fields.BigIntField(default=0)
    friendly_name = fields.CharField(max_length=100, default="Authenticator app")
```

| Field | Meaning |
| --- | --- |
| `kind` | Always `"totp"` today — the only factor kind Akountz implements. |
| `secret_ciphertext` | The TOTP secret, **encrypted**, not the raw base32 string. Sealed with `akountz.box.seal(secret)` on write, opened with `akountz.box.open(...)` only at verification time. |
| `confirmed_at` | `null` until the user proves possession with a first valid code. An unconfirmed factor is not usable for sign-in and is cleaned up the next time enrollment starts. |
| `last_used_step` | The last 30-second TOTP time step that was accepted. This is the replay guard — see [Replay protection](#replay-protection) below. |
| `friendly_name` | A label; not currently surfaced by any endpoint, but present for future multi-factor UI. |

<Warning>
The TOTP secret is never stored or transmitted as plain base32 after enrollment. It exists in plaintext only for the brief moment between generation and the response to `POST /auth/v1/mfa/totp/enroll` (so it can be shown to the user or embedded in a QR code), and again in memory during verification, after being decrypted from `secret_ciphertext`. If you were told the secret lives on `AuthUser.mfa_secret`, that is not how the current implementation works.
</Warning>

### `RecoveryCode`

```python
class RecoveryCode(Model):
    """A single-use MFA recovery code, stored as a SHA-256 hash."""
    id = fields.IntField(primary_key=True)
    user = fields.ForeignKeyField("models.AuthUser", related_name="recovery_codes", on_delete=fields.CASCADE)
    code_hash = fields.CharField(max_length=128, db_index=True)
    used_at = fields.DatetimeField(null=True)
```

That's the entire row: a hash and a used-at timestamp. There is no `code` column holding the raw value — once the ten codes are generated and returned to the client at confirmation time, Akountz has no way to display them again. If a user loses them, the only path forward is `POST /auth/v1/mfa/recovery-codes`, which invalidates every existing code and issues ten new ones.

## The enrollment lifecycle

MFA enrollment is a three-step flow: start it, confirm it with a real code, then it's live.

<Steps>
  <Step title="POST /auth/v1/mfa/totp/enroll">
    Requires a signed-in user and `mfa_enabled: true` on the environment (`403 MFA is disabled for this project` otherwise). This calls `mfa.enroll(akountz, user, issuer)`:

    ```python
    async def enroll(akountz: Akountz, user: AuthUser, issuer: str) -> dict[str, str]:
        await MfaFactor.filter(user=user, confirmed_at=None).delete()
        secret = pyotp.random_base32()
        factor = await MfaFactor.create(
            user=user, kind="totp", secret_ciphertext=akountz.box.seal(secret)
        )
        uri = pyotp.TOTP(secret).provisioning_uri(name=user.email, issuer_name=issuer)
        return {"factor_id": str(factor.id), "secret": secret, "otpauth_uri": uri}
    ```

    Any *unconfirmed* factor from a previous, abandoned enrollment attempt is deleted first — calling enroll again always starts clean. A fresh random base32 secret is generated, sealed, and stored. The response carries the **plaintext** secret (for manual entry) and an `otpauth://` provisioning URI (to render as a QR code), issued with `issuer` set to the project's display name.

    <Note>
    Calling enroll again while a factor is *already confirmed* does not touch the confirmed factor — it only clears unconfirmed ones. The old confirmed factor keeps working for sign-in until a new one is confirmed, at which point `confirm()` deletes every other factor the user has.
    </Note>
  </Step>
  <Step title="Scan or enter the secret">
    The client renders `otpauth_uri` as a QR code (most authenticator apps scan it directly) or shows `secret` for manual entry. This step happens entirely on the client; Akountz is not involved.
  </Step>
  <Step title="POST /auth/v1/mfa/totp/verify with the first code">
    Confirms the enrollment:

    ```python
    async def confirm(akountz: Akountz, user: AuthUser, code: str) -> list[str] | None:
        factor = await MfaFactor.filter(user=user, confirmed_at=None).order_by("-id").first()
        if factor is None or not await _check(akountz, factor, code):
            return None
        await MfaFactor.filter(user=user).exclude(id=factor.id).delete()
        factor.confirmed_at = datetime.now(UTC)
        await factor.save(update_fields=["confirmed_at"])
        user.mfa_enabled = True
        await user.save(update_fields=["mfa_enabled"])
        return await regenerate_recovery_codes(user)
    ```

    If the code checks out, every *other* factor the user has is deleted (enforcing "at most one factor"), the new one is marked confirmed, `AuthUser.mfa_enabled` flips to `true`, and ten fresh recovery codes are generated and returned — **this is the only response that ever contains raw recovery codes**. A wrong code returns `400 the code is not valid` and leaves the factor unconfirmed. If the current session came from a token, the route also calls `elevate()` to mark it `aal2` immediately, so the user doesn't have to sign in again right after turning MFA on.
  </Step>
</Steps>

```bash
curl -X POST "$GW/auth/v1/mfa/totp/enroll" \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "apikey: $PAWABASE_PUBLISHABLE_KEY"
```

```json
{
  "factor_id": "14",
  "secret": "JBSWY3DPEHPK3PXP",
  "otpauth_uri": "otpauth://totp/Acme:chioma@example.com?secret=JBSWY3DPEHPK3PXP&issuer=Acme"
}
```

```bash
curl -X POST "$GW/auth/v1/mfa/totp/verify" \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" -d '{"code": "482913"}'
```

```json
{
  "enabled": true,
  "recovery_codes": [
    "9f31c-a02de",
    "7b4e1-c9a03",
    "..."
  ]
}
```

<Warning>
Recovery codes appear exactly once, in this response. Instruct users to store them immediately — a password manager, a printed sheet, anywhere durable. There is no "show my recovery codes" endpoint, because Akountz never has the raw codes to show; only `code_hash` is on disk.
</Warning>

## Recovery code format

```python
RECOVERY_CODE_COUNT = 10

async def regenerate_recovery_codes(user: AuthUser) -> list[str]:
    await RecoveryCode.filter(user=user).delete()
    codes = []
    for _ in range(RECOVERY_CODE_COUNT):
        raw = secrets.token_hex(5)
        code = f"{raw[:5]}-{raw[5:]}"
        codes.append(code)
        await RecoveryCode.create(user=user, code_hash=_hash(code))
    return codes
```

Each code is `secrets.token_hex(5)` — **10 hex characters** drawn from 5 cryptographically random bytes — split evenly and joined with a hyphen, e.g. `9f31c-a02de`. Ten such codes are generated per batch, and generating a new batch always deletes every code from the previous batch first — codes are never additive.

The hash function normalizes before hashing so formatting doesn't matter at verification time:

```python
def _hash(code: str) -> str:
    return hashlib.sha256(code.replace("-", "").strip().lower().encode()).hexdigest()
```

A user can type `A1B2C3D4E5`, `a1b2c-3d4e5`, or `a1b2c 3d4e5` and all three hash identically — hyphens are stripped, whitespace trimmed, case lowered, before hashing. This makes recovery codes forgiving of how a user transcribes them from a printed sheet.

<Note>
Recovery codes are 10 lowercase hex characters (40 bits of entropy), not the shorter 8-character `token_hex(4)` format described in older material. Do not build a client-side regex validator narrower than "10 hex characters, optionally hyphenated" or it will reject valid codes.
</Note>

## Verifying a code

`mfa.verify(akountz, user, code)` is the single entry point used both by the sign-in MFA challenge and by the "confirm with a current code" gate on disabling MFA or regenerating recovery codes. It tries TOTP first, then falls back to recovery codes:

```python
async def verify(akountz: Akountz, user: AuthUser, code: str) -> str | None:
    factor = await MfaFactor.filter(user=user).exclude(confirmed_at=None).first()
    if factor is not None and await _check(akountz, factor, code):
        return "totp"
    recovery = await RecoveryCode.filter(user=user, code_hash=_hash(code), used_at=None).first()
    if recovery is not None:
        updated = await RecoveryCode.filter(id=recovery.id, used_at=None).update(used_at=datetime.now(UTC))
        if updated:
            return "recovery_code"
    return None
```

It returns `"totp"`, `"recovery_code"`, or `None` — never raises. The recovery-code consumption is a conditional `UPDATE ... WHERE used_at IS NULL`, so two concurrent requests racing to use the same recovery code can't both succeed; only one `UPDATE` affects a row.

### Replay protection

A TOTP code is checked against a ±1 step window (90 seconds total, accounting for clock drift), but each accepted step is remembered:

```python
async def _check(akountz: Akountz, factor: MfaFactor, code: str) -> bool:
    totp = pyotp.TOTP(akountz.box.open(factor.secret_ciphertext))
    ...
    for drift in (-1, 0, 1):
        step = int(now // 30) + drift
        if step <= factor.last_used_step:
            continue
        if secrets.compare_digest(totp.at(step * 30), code):
            factor.last_used_step = step
            await factor.save(update_fields=["last_used_step"])
            return True
    return False
```

`last_used_step` only ever moves forward. Once step `N` has been accepted, steps `≤ N` are rejected outright, even if the six digits are correct — this is what stops someone who observed a code over a shoulder (or intercepted it) from replaying it within its 30-second validity window. The comparison itself uses `secrets.compare_digest`, a constant-time comparison, so verification timing doesn't leak which digit differed.

## Disabling MFA and resetting recovery codes

| Endpoint | What it needs | What it does |
| --- | --- | --- |
| `POST /auth/v1/mfa/disable` | A current, valid code (TOTP or recovery). | Deletes every `MfaFactor` and every `RecoveryCode` for the user, sets `mfa_enabled = false`. |
| `POST /auth/v1/mfa/recovery-codes` | A current **TOTP** code specifically — a recovery code will not satisfy this check. | Deletes and reissues all ten recovery codes. |
| `GET /auth/v1/mfa` | A signed-in session. | Returns the `enabled`, `aal`, and `recovery_codes_remaining` fields. |

```python
async def disable(user: AuthUser) -> None:
    await MfaFactor.filter(user=user).delete()
    await RecoveryCode.filter(user=user).delete()
    user.mfa_enabled = False
    await user.save(update_fields=["mfa_enabled"])
```

`recovery-codes` deliberately requires a TOTP code (`await mfa.verify(...) != "totp"` is the rejection condition) rather than accepting a recovery code — otherwise a recovery code could be used to mint itself a fresh batch, defeating the "single use" property.

An administrator can also force-clear a user's MFA through the admin API: `POST /projects/{project}/envs/{env}/users/{user_id}/mfa/reset` calls the same `mfa.disable(user)` and emits `user.mfa_reset`. This is the recovery path for a user who has lost both their authenticator and every recovery code — support must verify identity out-of-band before calling it, since it removes the second factor entirely.

## MFA during sign-in

MFA does not gate the credential check itself — a wrong password still fails before MFA is ever considered. Once the password (or magic link, or social login) succeeds, Akountz checks whether the account has MFA enabled *and* the environment allows it:

```python
if user.mfa_enabled and config.mfa_enabled:
    challenge = await links.issue(akountz, config, "mfa", user=user, data={"method": "password", "org": body.org})
    return {"mfa_required": True, "mfa_token": challenge, "factors": ["totp", "recovery_code"]}
```

Instead of a session, the client gets an `mfa_token` — a short-lived (5-minute) [one-time token](/auth/tokens-and-sessions#one-time-tokens) that remembers which sign-in method was in progress and which organization (if any) was requested. The client then completes the grant:

```bash
curl -X POST "$GW/auth/v1/token" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" -H "content-type: application/json" \
  -d '{"grant_type": "mfa", "mfa_token": "eyJ...", "code": "482913"}'
```

On success, a session is started with `aal="aal2"` directly — the resulting access token's `aal` claim is `aal2` from the very first token, not upgraded on a later refresh. The response also includes `"mfa_method": "totp"` or `"mfa_method": "recovery_code"` so the client can prompt "you're running low on recovery codes" when appropriate (combine with `GET /auth/v1/mfa`'s `recovery_codes_remaining`).

A wrong code during this step calls the same `record_failure` lockout mechanism as a wrong password — repeated bad MFA attempts count toward the account's lockout threshold, they are not a separate, unlimited-attempts surface. `POST /auth/v1/mfa/totp/verify`, `/mfa/disable` and `/mfa/recovery-codes` are additionally rate-limited to 10 requests per 60 seconds per caller.

## Assurance levels: `aal1` and `aal2`

Every session (`SessionInfo` row) carries an `aal` field, either `"aal1"` (password/magic-link/social login alone) or `"aal2"` (MFA completed). This value is re-read and re-minted onto the access token on every refresh, so a session that reached `aal2` stays `aal2` across its whole lifetime unless something explicitly resets it:

```python
async def elevate(akountz: Akountz, config: AuthConfig, user: AuthUser, family: str) -> None:
    """Mark a session as having passed MFA (aal2)."""
    await SessionInfo.filter(family=family, user=user).update(aal="aal2")
```

`elevate()` is called from exactly one place today: right after a user confirms TOTP enrollment on an already-open session, so they don't have to sign out and back in to get an `aal2` token. A brand-new sign-in through the MFA challenge flow reaches `aal2` directly via `start_session(..., aal="aal2", ...)`.

### Using `aal` in a policy

The assurance level is on the token as `$auth.claims.aal`, and the condition language ships a dedicated shorthand for it:

```json
{ "aal": "aal2" }
```

which expands to `{"eq": ["$auth.claims.aal", "aal2"]}`. A typical use is gating a sensitive action behind MFA regardless of role:

```json
{ "all": [
  { "role": "bursar" },
  { "aal": "aal2" }
] }
```

See [the condition language](/policies/conditions#shorthands) for the full shorthand reference.

<Warning>
There is no per-organization or per-route "minimum AAL" configuration field anywhere in Akountz — `aal` is only ever an attribute of a session, read and compared inside policy conditions like the one above. If you need "this route always requires `aal2`," write that as part of the route's policy, not as a separate configuration block. Akountz's `AuthConfig` has a single environment-wide `mfa_enabled` toggle (whether MFA is available/enforced at all when a user has enrolled one) — it has no config field named `require_aal`, and no per-organization auth settings of any kind. See [Organizations → one auth configuration per environment](/auth/organizations#one-auth-configuration-per-environment).
</Warning>

## Real scenarios

### Enforcing MFA for a specific role

Akountz has no "require MFA for role X" configuration switch — `mfa_enabled` is an environment-wide flag, not scoped to a role or organization. To require MFA specifically for, say, every `bursar`, enforce it at the policy layer on the operations that matter:

```json
{ "any": [
  { "not": { "role": "bursar" } },
  { "all": [ { "role": "bursar" }, { "aal": "aal2" } ] }
] }
```

This reads as "anyone who isn't a bursar is unaffected by this rule; a bursar must additionally have completed MFA." Combine it with the rest of the resource's access policy in an `all`.

### Customer onboarding with optional MFA

A common SaaS pattern: MFA is available but not mandatory, and users are nudged to enroll after their first sign-in. Since `user_metadata` is client-editable, a safe way to track "has been nudged" without letting the user fake it is to store the flag in `app_metadata` from a server-side flow, and read `mfa_enabled` directly from `GET /auth/v1/user` to decide whether to show the enrollment prompt.

### Recovering a locked-out user (support flow)

A user who has lost their phone and their recovery codes cannot self-service — there is no "email me a new secret" flow, by design, since that would defeat the purpose of a second factor. The only path is an administrator calling the admin reset endpoint after verifying identity out-of-band:

```bash
curl -X POST "$STUDIO/internal/v1/projects/acme/envs/production/users/482/mfa/reset" \
  -H "Authorization: Bearer $SERVICE_TOKEN"
```

This clears `mfa_enabled` and deletes all factors and recovery codes. The user can then sign in with just their password and re-enroll MFA from scratch.

## Common mistakes

<AccordionGroup>
  <Accordion title="Expecting the secret to be retrievable after enrollment">
    `secret_ciphertext` is opaque outside Akountz's own decryption. If a user closes the enrollment screen before scanning the QR code, the only fix is to call `enroll` again — it clears the unconfirmed factor and issues a fresh secret. There's no "show me my in-progress secret again" endpoint.
  </Accordion>
  <Accordion title="Treating recovery codes as reusable">
    Each code works exactly once — `used_at` is set on first successful use and the code is rejected on every subsequent attempt, even if it's typed correctly. This is enforced with a conditional update, not a delete, so used codes remain visible for audit (though no endpoint currently exposes them).
  </Accordion>
  <Accordion title="Assuming MFA is configured per-organization or per-role">
    It's a single environment-wide toggle (`mfa_enabled`) plus a per-account flag (`AuthUser.mfa_enabled`). There is no config surface for "require MFA only for admins" — build that as a policy condition on the operations that need it, as shown above.
  </Accordion>
  <Accordion title="Confusing `mfa_enabled` on the environment with `mfa_enabled` on the user">
    Both must be true for a challenge to be issued at sign-in (`if user.mfa_enabled and config.mfa_enabled`). Turning off the environment's `mfa_enabled` doesn't delete anyone's factors — it just stops the challenge from being issued, effectively letting MFA-enrolled users sign in with just a password until it's turned back on.
  </Accordion>
</AccordionGroup>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `403 MFA is disabled for this project` on enroll | The environment's `mfa_enabled` is `false`. | Enable it in the environment's auth configuration. |
| `400 the code is not valid` on confirm | Clock drift beyond ±30s, or the wrong secret was scanned. | Confirm the device clock is correct; retry `enroll` for a fresh secret if in doubt. |
| A previously accepted code is rejected on retry | Expected — `last_used_step` blocks replay of an already-used step. | Wait for the next 30-second window and enter the new code. |
| `400 a current authenticator code is required` on `/mfa/recovery-codes` | A recovery code (not a TOTP code) was submitted. | Regenerating codes requires the authenticator app specifically. |
| User locked out with no recovery codes and no phone | Both factors of MFA lost. | An administrator must call the admin MFA-reset endpoint after verifying identity. |
