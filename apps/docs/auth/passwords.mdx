Passwords are the foundational sign-in method in Pawabase's Akountz identity service. Every other method — magic links, social login, refresh — ultimately produces the same access/refresh token pair and the same `Principal`, so the password grant is the reference case that everything else is built on. This page covers the full lifecycle: how accounts are created, how sign-in works, what password policy is enforced, how passwords are hashed and stored, and how to update a profile including changing a password.

<CardGroup cols={3}>
  <Card title="One grant shape" icon="key-round">Every grant type ends at the same `{access_token, refresh_token, session_id, user}` response shape.</Card>
  <Card title="Hashing is explicit" icon="fingerprint">`passlib`-backed (bcrypt by default, `pbkdf2_sha256` fallback). You can inspect the algorithm in `services/akountz`.</Card>
  <Card title="Lockout is automatic" icon="shield">After `lockout_threshold` failed attempts (default 10) within `lockout_minutes` (default 15), the account is temporarily locked.</Card>
</CardGroup>

## Sign-up

Creating a new account sends a `POST` to `POST /auth/v1/signup`. The request body is a `SignUp` model:

```json
{
  "email": "chioma@example.com",
  "password": "correct-horse-battery-staple",
  "username": "chioma",
  "name": "Chioma Nwosu",
  "data": { "tier": "starter" }
}
```

| Field | Required | Max length | Description |
| --- | --- | --- | --- |
| `email` | Yes | 255 | Must be a valid email format. Normalized to lowercase. Unique per project environment. |
| `password` | Yes | 1024 | Checked against the environment's `password_policy` before the account is created. |
| `username` | No | 150 | If provided, must be unique per environment. If omitted, a username is auto-generated from the email prefix. |
| `name` | No | 200 | Display name, defaults to `""`. |
| `data` | No | — | Initial `user_metadata`. Merged into the account's profile data. |
| `redirect_to` | No | — | URL to redirect to after sign-in. Must be allowed by the environment's `site_url` or `redirect_urls`. |

The sign-up endpoint enforces several checks in sequence:

1. **`signup_enabled`**: If `false`, returns `403 sign-up is disabled`.
2. **`redirect_to` validation**: If provided and not in the allowed list, returns `400 redirect_to is not an allowed URL`.
3. **Duplicate email**: If an account with this email already exists in the project environment, returns `409 an account with this email already exists`.
4. **Duplicate username**: If a username is provided and already taken, returns `409 that username is taken`.
5. **Password policy**: Checked before the password is hashed and stored.
6. **Account creation**: The `create_account` function creates the `AuthUser` row, sets the password (or an unusable password for accounts created without a password, such as social login), assigns `default_roles`, and emits a `user.created` event.

```python
user = await create_account(
    config,
    email=body.email,
    password=body.password,
    username=body.username,
    name=body.name,
    user_metadata=body.data,
)
```

If `require_email_verification` is `true`, the response includes `"verification_required": true` and no session. The user must verify their email before a session is issued. Otherwise, a session is started immediately.

### Username generation

If no `username` is provided, one is auto-generated from the email's local part:

```python
base = re.sub(r"[^a-z0-9_.-]", "", (wanted or email.split("@", 1)[0]).lower())[:40] or "user"
```

If that base is already taken, a random suffix is appended until a unique one is found. This means `ada@example.com` might become `ada` or `ada4821` — the client should not assume a specific username without reading the response.

## The password grant: `POST /auth/v1/token`

Signing in with a password sends `grant_type: "password"` to the token endpoint:

```bash
curl -X POST "$GW/auth/v1/token" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "grant_type": "password",
    "email": "chioma.nwosu@example.com",
    "password": "correct-horse-battery-staple"
  }'
```

```json
{
  "access_token": "eyJhbGciOi…",
  "refresh_token": "rft_8f2c…",
  "token_type": "bearer",
  "expires_in": 900,
  "session_id": "f3f0c2f8…",
  "org": null,
  "org_role": null,
  "user": {
    "id": "8",
    "email": "chioma.nwosu@example.com",
    "username": "chioma",
    "name": "Chioma Nwosu",
    "roles": ["guardian"]
  }
}
```

The endpoint enforces a series of checks, in order, before issuing a session:

<Steps>
  <Step title="Rate limiting">
    The endpoint is wrapped with `rate_limit_middleware` (30 requests per 60 seconds per IP). A client that exceeds this sees a `429` response.
  </Step>
  <Step title="Missing credentials">
    If `email` or `password` is absent, returns `400 email and password are required`.
  </Step>
  <Step title="Email lookup">
    `normalise_email` is applied, then the account is looked up by `(project, env, email)`. If not found, a synthetic failure is logged and `400 invalid email or password` is returned — the response is identical whether the email or the password is wrong, to prevent enumeration.
  </Step>
  <Step title="Lockout check">
    If `is_locked(user)` is `true` (the `locked_until` timestamp is in the future), returns `429 too many failed attempts; try again later`.
  </Step>
  <Step title="Password verification">
    `user.check_password(body.password)` uses `passlib` to verify against the stored hash. On failure, `record_failure` increments `failed_logins`; at the `lockout_threshold` (default 10), the account is locked for `lockout_minutes` (default 15) minutes.
  </Step>
  <Step title="Disabled check">
    If `user.is_disabled` is `true`, returns `403 this account is disabled`. A disabled account is one an administrator has deactivated — it is not the same as a locked account.
  </Step>
  <Step title="Email verification">
    If `require_email_verification` is `true` and `user.email_verified_at` is `None`, returns `403 confirm your email address first`.
  </Step>
  <Step title="MFA challenge">
    If the user has `mfa_enabled` and the environment has `mfa_enabled`, a TOTP or recovery-code challenge is issued instead of a session. See [MFA →](/auth/mfa).
  </Step>
  <Step title="Organization membership">
    If an `org` is provided, the user must be a member of that organization; otherwise `403 you are not a member of that organization`.
  </Step>
  <Step title="Session issuance">
    `start_session` mints the access/refresh token pair, records the session, logs the sign-in event, and returns the response.
  </Step>
</Steps>

<Warning>
The error responses for an unknown email and a wrong password are intentionally identical (`400 invalid email or password`). Never distinguish "account exists" from "account doesn't exist" from the error message alone.
</Warning>

### The `org` parameter on sign-in

Adding `"org": "acme-hq"` to the sign-in request scopes the session to that organization. If the user is a member, `org` and `org_role` appear in the response. If they are not a member, `403 you are not a member of that organization`. On refresh, the organization is kept by default unless explicitly switched or cleared — see [Tokens and sessions → switching or clearing the organization on refresh](/auth/tokens-and-sessions#switching-or-clearing-the-organization-on-refresh).

<Note>
Naming an `org` the user isn't a member of doesn't silently issue a token without it — it returns `403`. This is deliberate: the endpoint should never silently drop an organization the caller requested.
</Note>

## Password policy enforcement

Password policy is enforced at two boundaries: sign-up and password change. The `check_password_policy` function in `app/accounts.py` handles both:

```python
def check_password_policy(config: AuthConfig, password: str) -> None:
    if config.password_policy == "strict":
        problems = validate_password(password, min_length=config.password_min_length)
    else:
        problems = (
            [f"Password must be at least {config.password_min_length} characters."]
            if len(password or "") < config.password_min_length
            else []
        )
    if len(password or "") > 1024:
        problems.append("Password is too long.")
    if problems:
        raise HTTPException(
            status_code=422,
            detail={"message": "the password does not meet the policy", "problems": problems},
        )
```

### `basic` policy

The `basic` policy (the default) only checks the length:

| Condition | Result |
| --- | --- |
| `len(password) >= password_min_length` | Passes |
| `len(password) < password_min_length` | Fails with `"Password must be at least {N} characters."` |

This is suitable for internal tools or when the application's front-end adds additional strength checks.

### `strict` policy

The `strict` policy runs Sillo's `validate_password`, which enforces a mix of character classes (uppercase, lowercase, digits, symbols) beyond the length minimum. The exact rules are defined in Sillo's password validation module; the result is a `problems` array describing every rule the password fails.

Both policies reject passwords longer than 1024 characters. The policy is checked on the environment's `password_policy` setting at the time of the request — changing it does not retroactively invalidate existing passwords, but any password change going forward must satisfy the new policy.

## Password hashing

Passwords are never stored in plaintext. `AuthUser` inherits `UserBaseModel` from Sillo, which provides `set_password` and `check_password` using `passlib`:

```python
user.set_password(password)    # Hashes and stores the password
user.check_password(password)  # Verifies against the stored hash
```

By default, `passlib` uses **bcrypt** as the hashing algorithm. If bcrypt is not available in the deployment environment, it falls back to **PBKDF2-SHA256** with a configurable number of rounds. The algorithm identifier is stored in the hash string itself, so future algorithm changes are transparent — an account hashed with bcrypt can be verified even after the server is reconfigured to use a different default.

<Note>
There is no way to re-hash an account's password on the fly without knowing the plaintext. If you need to migrate hashing algorithms across a fleet, the standard approach is to re-hash on the next successful sign-in (when the user enters their password), checking the current algorithm and upgrading if it's outdated. Sillo's `UserBaseModel` supports this pattern through the `needs_rehash` mechanism.
</Note>

The `set_unusable_password` method is called when an account is created without a password (social login, magic link). This sets a marker that `has_usable_password()` returns `false` for — the account cannot sign in with a password until one is set.

```python
# Social login creates an account with no password:
user = await create_account(config, email=profile.email, password=None, ...)
user.set_unusable_password()
```

## Updating a profile

`PATCH /auth/v1/user` accepts a `UserUpdate` model. Any combination of fields can be updated in a single request:

```json
{
  "name": "Chioma Nwosu",
  "avatar_url": "https://cdn.example.com/avatars/8.png",
  "data": { "tier": "professional", "preferences": { "theme": "dark" } },
  "password": "new-correct-horse-battery-staple",
  "current_password": "old-correct-horse-battery-staple",
  "email": "chioma.new@example.com"
}
```

### Changing the password

Changing a password requires the current password — even if the account was created through social login and has `has_usable_password() == false`, the `current_password` check is skipped in that case (there is no existing password to check against). The new password is validated against the environment's `password_policy` before being stored.

```python
if body.password is not None:
    if user.has_usable_password() and not user.check_password(body.current_password or ""):
        raise HTTPException(status_code=400, detail="current_password is wrong")
    check_password_policy(config, body.password)
    user.set_password(body.password)
    changed.append("password")
```

After a password change, a `user.password_changed` event is emitted and the user's `last_sign_in_ip` and `last_login` are updated — but notably, existing sessions are **not** automatically revoked. A password change does not invalidate tokens already issued; the access token continues to work until it expires naturally. If you need immediate revocation on password change, you must call `revoke_all` explicitly (available through the admin API).

<Warning>
Changing a password does not sign out other devices. If a session was compromised and the user changes their password, the attacker's session remains valid until it expires. Use the admin `POST /projects/{project}/envs/{env}/users/{user_id}/sessions/revoke` endpoint to sign everyone out immediately after a suspected compromise.
</Warning>

### Changing the email

Changing the email is a two-step process to prevent account takeover:

1. The new email is checked for duplicates (returns `409 that email is in use` if taken).
2. Instead of immediately updating, a **verification link** is issued and sent to the *new* email address. The response includes `"changed": ["email (pending confirmation)"]`.
3. The user clicks the link in the new inbox and confirms. Only then is the email updated and marked verified.

This prevents an attacker who gains access to an account from immediately changing the email and locking the legitimate owner out.

### Updating user metadata

The `data` field is merged (not replaced) into `user_metadata`:

```python
user.user_metadata = {**(user.user_metadata or {}), **body.data}
```

This means a `PATCH` with `{"data": {"theme": "dark"}}` updates only the `theme` key without touching other keys in `user_metadata`.

## Error responses

Every possible error from the password endpoints:

| Status | Detail | When |
| --- | --- | --- |
| `400` | `email and password are required` | Sign-in with missing email or password. |
| `400` | `invalid email or password` | Email not found, or wrong password. Identical to prevent enumeration. |
| `400` | `the password does not meet the policy` | Password fails policy check. Body includes a `problems` array. |
| `400` | `the code is not valid` | MFA TOTP or recovery code fails verification. |
| `400` | `mfa_token and code are required` | MFA completion request missing required fields. |
| `400` | `the link is invalid or has expired` | Any one-time token (verify, recovery, magic, invite) is expired, already used, or tampered with. |
| `400` | `redirect_to is not an allowed URL` | `redirect_to` doesn't match `site_url` or `redirect_urls`. |
| `403` | `sign-up is disabled` | `signup_enabled` is `false` in the environment config. |
| `403` | `confirm your email address first` | `require_email_verification` is `true` and the account is unverified. |
| `403` | `this account is disabled` | The account has been disabled by an administrator. |
| `403` | `you are not a member of that organization` | An `org` was specified that the user is not a member of. |
| `403` | `magic links are disabled` | `magic_link_enabled` is `false`. |
| `409` | `an account with this email already exists` | Sign-up with a duplicate email. |
| `409` | `that username is taken` | Sign-up with a duplicate username. |
| `409` | `that email is in use` | Profile update to an email already registered. |
| `422` | `a valid email address is required` | Email doesn't pass the format check. |
| `422` | `{ "message": "the password does not meet the policy", "problems": [...] }` | Password policy violation with specific failed rules. |
| `429` | `too many failed attempts; try again later` | Account is locked due to too many failed sign-in attempts. |

<Tip>
The `422` with a `problems` array is the only error response that provides structured, machine-readable detail about *which* rules failed. Frontends can use it to render targeted inline validation rather than a generic "password doesn't meet requirements" message.
</Tip>

## Brute-force protection

Two layers of brute-force protection are in place:

1. **Per-IP rate limiting**: The `/auth/v1/token` endpoint is wrapped with `rate_limit_middleware` (30 requests per 60 seconds). Exceeding this returns `429` before any password check runs.
2. **Per-account lockout**: After `lockout_threshold` (default 10) failed password attempts within `lockout_minutes` (default 15) minutes, the account is locked until `locked_until` passes. The `failed_logins` counter resets to 0 and `locked_until` is set. A successful sign-in resets both counters to 0.

```python
async def record_failure(user: AuthUser, threshold: int, minutes: int) -> None:
    user.failed_logins += 1
    if user.failed_logins >= threshold:
        user.locked_until = datetime.now(UTC) + timedelta(minutes=minutes)
        user.failed_logins = 0
    await user.save(update_fields=["failed_logins", "locked_until"])
```

Lockout is per-environment — a user who is locked out in `acme/development` is not locked in `acme/production`, because the `AuthUser` row is scoped to `(project, env, email)`.

<Note>
Recovery codes bypass the lockout check — if a user is locked out but has MFA recovery codes, they can still sign in by using a recovery code as the TOTP code. This ensures that a brute-force lockout never becomes a denial of service against the legitimate user.
</Note>
