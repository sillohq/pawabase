Passwords are the foundational sign-in method in Pawabase's Akountz identity service. Every other method — magic links, social login, refresh — ultimately produces the same access/refresh token pair and the same `Principal`, so the password grant is the reference case that everything else is built on. This page covers the full lifecycle: how accounts are created, how sign-in works, what password policy is enforced, how passwords are hashed and stored, and how to update a profile including changing a password.

<CardGroup cols={3}>
  <Card title="One grant shape" icon="key-round">Every grant type ends at the same `{access_token, refresh_token, session_id, user}` response shape.</Card>
  <Card title="Hashing is explicit" icon="fingerprint">`passlib`-backed (bcrypt by default, `pbkdf2_sha256` fallback). You can inspect the algorithm in `services/akountz`.</Card>
  <Card title="Lockout is automatic" icon="shield">After `lockout_threshold` failed attempts (default 10) within `lockout_minutes` (default 15), the account is temporarily locked.</Card>
</CardGroup>

## Sign-up

Creating a new account sends a `POST` to `POST /auth/v1/signup`. The request body is a `SignUp` model:

```json
{
  "email": "chioma@example.com",
  "password": "correct-horse-battery-staple",
  "username": "chioma",
  "name": "Chioma Nwosu",
  "data": { "tier": "starter" }
}
```

| Field | Required | Max length | Description |
| --- | --- | --- | --- |
| `email` | Yes | 255 | Must be a valid email format. Normalized to lowercase. Unique per project environment. |
| `password` | Yes | 1024 | Checked against the environment's `password_policy` before the account is created. |
| `username` | No | 150 | If provided, must be unique per environment. If omitted, a username is auto-generated from the email prefix. |
| `name` | No | 200 | Display name, defaults to `""`. |
| `data` | No | — | Initial `user_metadata`. Merged into the account's profile data. |
| `redirect_to` | No | — | URL to redirect to after sign-in. Must be allowed by the environment's `site_url` or `redirect_urls`. |

The sign-up endpoint enforces several checks in sequence:

1. **`signup_enabled`**: If `false`, returns `403 sign-up is disabled`.
2. **`redirect_to` validation**: If provided and not in the allowed list, returns `400 redirect_to is not an allowed URL`.
3. **Duplicate email**: If an account with this email already exists in the project environment, returns `409 an account with this email already exists`.
4. **Duplicate username**: If a username is provided and already taken, returns `409 that username is taken`.
5. **Password policy**: Checked before the password is hashed and stored.
6. **Account creation**: The `create_account` function creates the `AuthUser` row, sets the password (or an unusable password for accounts created without a password, such as social login), assigns `default_roles`, and emits a `user.created` event.

```python
user = await create_account(
    config,
    email=body.email,
    password=body.password,
    username=body.username,
    name=body.name,
    user_metadata=body.data,
)
```

If `require_email_verification` is `true`, the response includes `"verification_required": true` and no session. The user must verify their email before a session is issued. Otherwise, a session is started immediately.

### Username generation

If no `username` is provided, one is auto-generated from the email's local part:

```python
base = re.sub(r"[^a-z0-9_.-]", "", (wanted or email.split("@", 1)[0]).lower())[:40] or "user"
```

If that base is already taken, a random suffix is appended until a unique one is found. This means `ada@example.com` might become `ada` or `ada4821` — the client should not assume a specific username without reading the response.

### What happens to the password

The password is immediately passed through `check_password_policy` (which validates against `password_policy` and `password_min_length`) and then through `user.set_password(password)` which calls `passlib`'s hashing. The `AuthUser` model inherits from Sillo's `UserBaseModel`, which provides the `set_password` and `check_password` methods. The password is never stored in plaintext — not even temporarily — and the raw password value from the request body is not logged anywhere in the sign-up flow.

After account creation, if `default_roles` is configured in the environment, `create_account` iterates through them and assigns each one to the new user via `rbac.assign_role(user, role)`. These roles are stored in the database and are not yet on any token — they appear on the token only at sign-in time.

A `user.created` event is emitted with `{"user_id": str(user.id), "email": user.email, "method": "password"}`. This event is consumed by platform event subscribers and recorded in the audit log.

### Account creation without a password

When an account is created through social login or magic link (not through the password sign-up endpoint), `create_account` is called with `password=None`. This results in `set_unusable_password()` being called — the account has `has_usable_password() == false` and cannot sign in with a password until one is set. The account is still created with a unique `(project, env, email)` identity, and the user can later add a password through `PATCH /auth/v1/user` with a `password` field.

### The `data` field and user metadata

The `data` field in the sign-up request is merged into `user_metadata`. This is the same field that can be updated later through `PATCH /auth/v1/user`. The `data` is stored as JSON in the `user_metadata` column of the `AuthUser` row. There is no validation of the `data` shape — it accepts any JSON object. The `data` field is also where `app_metadata` goes when set by an administrator.

<Note>
The distinction between `user_metadata` (set by the user themselves through `data`) and `app_metadata` (set only by administrators or service keys) is critical for policy design. User-editable metadata appears in `$auth.claims.meta` and must never be trusted for access decisions. Administrator-controlled metadata appears in `$auth.claims.app` and is safe to gate access on. See [auth in policies →](/auth/auth-in-policies#authclaimsapp--administrator-controlled-safe-for-policies).
</Note>

## The password grant: `POST /auth/v1/token`

Signing in with a password sends `grant_type: "password"` to the token endpoint:

```bash
curl -X POST "$GW/auth/v1/token" \
  -H "apikey: $PAWABASE_PUBLISHABLE_KEY" \
  -H "content-type: application/json" \
  -d '{
    "grant_type": "password",
    "email": "chioma.nwosu@example.com",
    "password": "correct-horse-battery-staple"
  }'
```

```json
{
  "access_token": "eyJhbGciOi…",
  "refresh_token": "rft_8f2c…",
  "token_type": "bearer",
  "expires_in": 900,
  "session_id": "f3f0c2f8…",
  "org": null,
  "org_role": null,
  "user": {
    "id": "8",
    "email": "chioma.nwosu@example.com",
    "username": "chioma",
    "name": "Chioma Nwosu",
    "roles": ["guardian"]
  }
}
```

The endpoint enforces a series of checks, in order, before issuing a session:

<Steps>
  <Step title="Rate limiting">
    The endpoint is wrapped with `rate_limit_middleware` (30 requests per 60 seconds per IP). A client that exceeds this sees a `429` response. This middleware is initialized in `register()` with `{"limit": 30, "window": 60}` and the `"akz:auth"` key.
  </Step>
  <Step title="Missing credentials">
    If `email` or `password` is absent, returns `400 email and password are required`. Both fields must be present and non-empty (the `SignUp` model enforces `password` has `min_length=1`, and the token endpoint checks both fields explicitly).
  </Step>
  <Step title="Email lookup">
    `normalise_email` is applied, then the account is looked up by `(project, env, email)`. If not found, a synthetic failure is logged and `400 invalid email or password` is returned — the response is identical whether the email or the password is wrong, to prevent enumeration.
  </Step>
  <Step title="Lockout check">
    If `is_locked(user)` is `true` (the `locked_until` timestamp is in the future), returns `429 too many failed attempts; try again later`. The `is_locked` property checks whether `locked_until` is set and in the future.
  </Step>
  <Step title="Password verification">
    `user.check_password(body.password)` uses `passlib` to verify against the stored hash. On failure, `record_failure` increments `failed_logins`; at the `lockout_threshold` (default 10), the account is locked for `lockout_minutes` (default 15) minutes.
  </Step>
  <Step title="Disabled check">
    If `user.is_disabled` is `true`, returns `403 this account is disabled`. A disabled account is one an administrator has deactivated — it is not the same as a locked account.
  </Step>
  <Step title="Email verification">
    If `require_email_verification` is `true` and `user.email_verified_at` is `None`, returns `403 confirm your email address first`. This check happens after the password is verified (so an attacker who knows a valid email and password still gets the "confirm your email" response rather than a different error — the endpoint does not reveal whether the account exists).
  </Step>
  <Step title="MFA challenge">
    If the user has `mfa_enabled` and the environment has `mfa_enabled`, a TOTP or recovery-code challenge is issued instead of a session. See [MFA →](/auth/mfa).
  </Step>
  <Step title="Organization membership">
    If an `org` is provided, the user must be a member of that organization; otherwise `403 you are not a member of that organization`.
  </Step>
  <Step title="Session issuance">
    `start_session` mints the access/refresh token pair, records the session, logs the sign-in event, and returns the response. The session is stored in `SessionInfo` with the method `"password"`, the current AAL (or `"aal2"` if MFA was just completed), and the organization if one was specified.
  </Step>
</Steps>

<Warning>
The error responses for an unknown email and a wrong password are intentionally identical (`400 invalid email or password`). Never distinguish "account exists" from "account doesn't exist" from the error message alone.
</Warning>

### The `org` parameter on sign-in

Adding `"org": "acme-hq"` to the sign-in request scopes the session to that organization. If the user is a member, `org` and `org_role` appear in the response. If they are not a member, `403 you are not a member of that organization`. On refresh, the organization is kept by default unless explicitly switched or cleared — see [Tokens and sessions → switching or clearing the organization on refresh](/auth/tokens-and-sessions#switching-or-clearing-the-organization-on-refresh).

<Note>
Naming an `org` the user isn't a member of doesn't silently issue a token without it — it returns `403`. This is deliberate: the endpoint should never silently drop an organization the caller requested.
</Note>

### The `redirect_to` parameter on sign-up

The `redirect_to` field in the `SignUp` request body is validated against the environment's `site_url` and `redirect_urls` configuration. If the URL is not allowed, the endpoint returns `400 redirect_to is not an allowed URL` before any account creation occurs. The `redirect_to` is stored in the one-time token (if verification is required) or used in the redirect fragment of the session response.

## Password policy enforcement

Password policy is enforced at two boundaries: sign-up and password change. The `check_password_policy` function in `app/accounts.py` handles both:

```python
def check_password_policy(config: AuthConfig, password: str) -> None:
    if config.password_policy == "strict":
        problems = validate_password(password, min_length=config.password_min_length)
    else:
        problems = (
            [f"Password must be at least {config.password_min_length} characters."]
            if len(password or "") < config.password_min_length
            else []
        )
    if len(password or "") > 1024:
        problems.append("Password is too long.")
    if problems:
        raise HTTPException(
            status_code=422,
            detail={"message": "the password does not meet the policy", "problems": problems},
        )
```

### `basic` policy

The `basic` policy (the default) only checks the length:

| Condition | Result |
| --- | --- |
| `len(password) >= password_min_length` | Passes |
| `len(password) < password_min_length` | Fails with `"Password must be at least {N} characters."` |

This is suitable for internal tools or when the application's front-end adds additional strength checks. The `password_min_length` applies here too — even with `"basic"`, you can enforce a minimum of 12 characters if you set `password_min_length: 12`.

### `strict` policy

The `strict` policy runs Sillo's `validate_password`, which enforces a mix of character classes (uppercase, lowercase, digits, symbols) beyond the length minimum. The exact rules are defined in Sillo's password validation module; the result is a `problems` array describing every rule the password fails.

Both policies reject passwords longer than 1024 characters. The policy is checked on the environment's `password_policy` setting at the time of the request — changing it does not retroactively invalidate existing passwords, but any password change going forward must satisfy the new policy.

### The 1024-character ceiling

The 1024-character maximum is enforced in both `check_password_policy` and in the `SignUp` model's `password` field constraint (`Field(max_length=1024)`). This serves two purposes: it prevents denial-of-service attacks where an extremely long password could cause excessive hashing time, and it aligns with typical password input field limits in browsers and mobile frameworks.

### Policy violations in detail

When `check_password_policy` raises a `422`, the `problems` array contains human-readable descriptions of every failed rule. A frontend can render each problem as an inline error message:

```json
{
  "message": "the password does not meet the policy",
  "problems": [
    "Password must contain an uppercase letter.",
    "Password must contain a digit.",
    "Password must contain a symbol.",
    "Password must be at least 12 characters."
  ]
}
```

The exact wording of each problem string comes from Sillo's `validate_password` implementation and should not be relied upon as a stable API — the field names and descriptions may evolve. The `problems` array is always a list of strings, and the `message` field is always `"the password does not meet the policy"`.

## Password hashing

Passwords are never stored in plaintext. `AuthUser` inherits `UserBaseModel` from Sillo, which provides `set_password` and `check_password` using `passlib`:

```python
user.set_password(password)    # Hashes and stores the password
user.check_password(password)  # Verifies against the stored hash
```

By default, `passlib` uses **bcrypt** as the hashing algorithm. If bcrypt is not available in the deployment environment, it falls back to **PBKDF2-SHA256** with a configurable number of rounds. The algorithm identifier is stored in the hash string itself, so future algorithm changes are transparent — an account hashed with bcrypt can be verified even after the server is reconfigured to use a different default.

<Note>
There is no way to re-hash an account's password on the fly without knowing the plaintext. If you need to migrate hashing algorithms across a fleet, the standard approach is to re-hash on the next successful sign-in (when the user enters their password), checking the current algorithm and upgrading if it's outdated. Sillo's `UserBaseModel` supports this pattern through the `needs_rehash` mechanism.
</Note>

### How `set_password` works

When `set_password` is called, `passlib` generates a random salt, applies the hashing algorithm (bcrypt or PBKDF2-SHA256), and stores the result as a single string that encodes the algorithm, the salt, and the hash. This means the hash string itself is self-describing:

```
$2b$12$LJ3m4xF8z1K2p9vR6nQq.eJxYzWq1N2B3C4D5E6F7G8H9I0J1K2L3M4
```

The `$2b$` prefix identifies bcrypt with a cost factor of 12. If the same account were hashed with PBKDF2-SHA256, the prefix would be different. When `check_password` is called, `passlib` reads the prefix, extracts the algorithm and salt, and verifies accordingly.

### `set_unusable_password`

The `set_unusable_password` method is called when an account is created without a password (social login, magic link). This sets a marker that `has_usable_password()` returns `false` for — the account cannot sign in with a password until one is set. The stored value is not a hash but a sentinel that `check_password` will always reject.

```python
# Social login creates an account with no password:
user = await create_account(config, email=profile.email, password=None, ...)
user.set_unusable_password()
```

### The `has_usable_password` gate

The `has_usable_password()` method is checked in two important places:

1. **Password change**: When a user changes their password through `PATCH /auth/v1/user`, the `current_password` check is skipped if `has_usable_password()` is `false`. This is because an account created through social login has no password to check against.
2. **Unlinking protection**: When a user tries to unlink their last identity and they have no usable password, the unlink is blocked (`409 set a password before removing your only sign-in method`). This prevents a user from locking themselves out by removing their last identity without setting a password first.

### The `passlib` dependency

`passlib` is a Python library that provides a uniform interface to over 30 password hashing algorithms. In the Pawabase codebase, only bcrypt and PBKDF2-SHA256 are used. The library handles all the complexity of salt generation, algorithm selection, and constant-time comparison. The `verify` method in `passlib` uses a constant-time comparison internally, which prevents timing attacks against the hash.

## Updating a profile

`PATCH /auth/v1/user` accepts a `UserUpdate` model. Any combination of fields can be updated in a single request:

```json
{
  "name": "Chioma Nwosu",
  "avatar_url": "https://cdn.example.com/avatars/8.png",
  "data": { "tier": "professional", "preferences": { "theme": "dark" } },
  "password": "new-correct-horse-battery-staple",
  "current_password": "old-correct-horse-battery-staple",
  "email": "chioma.new@example.com"
}
```

### Changing the password

Changing a password requires the current password — even if the account was created through social login and has `has_usable_password() == false`, the `current_password` check is skipped in that case (there is no existing password to check against). The new password is validated against the environment's `password_policy` before being stored.

```python
if body.password is not None:
    if user.has_usable_password() and not user.check_password(body.current_password or ""):
        raise HTTPException(status_code=400, detail="current_password is wrong")
    check_password_policy(config, body.password)
    user.set_password(body.password)
    changed.append("password")
```

After a password change, a `user.password_changed` event is emitted and the user's `last_sign_in_ip` and `last_login` are updated — but notably, existing sessions are **not** automatically revoked. A password change does not invalidate tokens already issued; the access token continues to work until it expires naturally. If you need immediate revocation on password change, you must call `revoke_all` explicitly (available through the admin API).

<Warning>
Changing a password does not sign out other devices. If a session was compromised and the user changes their password, the attacker's session remains valid until it expires. Use the admin `POST /projects/{project}/envs/{env}/users/{user_id}/sessions/revoke` endpoint to sign everyone out immediately after a suspected compromise.
</Warning>

### Changing the email

Changing the email is a two-step process to prevent account takeover:

1. The new email is checked for duplicates (returns `409 that email is in use` if taken).
2. Instead of immediately updating, a **verification link** is issued and sent to the *new* email address. The response includes `"changed": ["email (pending confirmation)"]`.
3. The user clicks the link in the new inbox and confirms. Only then is the email updated and marked verified.

This prevents an attacker who gains access to an account from immediately changing the email and locking the legitimate owner out.

The verification link for email changes uses the `kind: "email_change"` one-time token. The `complete` handler (`kind == "email_change"`) checks that the new email isn't already taken by another account, updates the email, marks it verified, and emits a `user.email_changed` event. The old email is preserved in the event payload for audit purposes.

### Updating user metadata

The `data` field is merged (not replaced) into `user_metadata`:

```python
user.user_metadata = {**(user.user_metadata or {}), **body.data}
```

This means a `PATCH` with `{"data": {"theme": "dark"}}` updates only the `theme` key without touching other keys in `user_metadata`. This merge semantics is specific to the self-service `PATCH /auth/v1/user` — the admin `PATCH .../users/{user_id}` endpoint **replaces** both `user_metadata` and `app_metadata` wholesale.

### Updating `app_metadata`

End users cannot modify `app_metadata` through the self-service `PATCH /auth/v1/user`. Only administrators (through the admin API) or service keys can set `app_metadata`. This distinction is enforced at the code level — the self-service `UserUpdate` model does not include an `app_metadata` field, and the admin `AdminUserUpdate` model does. The `app_metadata` is what appears in `$auth.claims.app` and is safe for policies to rely on.

### Updating `avatar_url`, `name`, and `phone`

These profile fields are updated directly on the `AuthUser` row:

- `name` replaces the display name (max 200 characters).
- `avatar_url` replaces the avatar URL (max 2048 characters). If `null`, no avatar is shown.
- `phone` replaces the phone number (max 32 characters). Optional.

These fields are returned in the `user` object of the sign-in response and in the `GET /auth/v1/user` response. They are also surfaced in the `user_view` response used throughout the admin API.

## Error responses

Every possible error from the password endpoints:

| Status | Detail | When |
| --- | --- | --- |
| `400` | `email and password are required` | Sign-in with missing email or password. |
| `400` | `invalid email or password` | Email not found, or wrong password. Identical to prevent enumeration. |
| `400` | `the password does not meet the policy` | Password fails policy check. Body includes a `problems` array. |
| `400` | `the code is not valid` | MFA TOTP or recovery code fails verification. |
| `400` | `mfa_token and code are required` | MFA completion request missing required fields. |
| `400` | `the link is invalid or has expired` | Any one-time token (verify, recovery, magic, invite) is expired, already used, or tampered with. |
| `400` | `redirect_to is not an allowed URL` | `redirect_to` doesn't match `site_url` or `redirect_urls`. |
| `403` | `sign-up is disabled` | `signup_enabled` is `false` in the environment config. |
| `403` | `confirm your email address first` | `require_email_verification` is `true` and the account is unverified. |
| `403` | `this account is disabled` | The account has been disabled by an administrator. |
| `403` | `you are not a member of that organization` | An `org` was specified that the user is not a member of. |
| `403` | `magic links are disabled` | `magic_link_enabled` is `false`. |
| `409` | `an account with this email already exists` | Sign-up with a duplicate email. |
| `409` | `that username is taken` | Sign-up with a duplicate username. |
| `409` | `that email is in use` | Profile update to an email already registered. |
| `422` | `a valid email address is required` | Email doesn't pass the format check. |
| `422` | `{ "message": "the password does not meet the policy", "problems": [...] }` | Password policy violation with specific failed rules. |
| `429` | `too many failed attempts; try again later` | Account is locked due to too many failed sign-in attempts. |

<Tip>
The `422` with a `problems` array is the only error response that provides structured, machine-readable detail about *which* rules failed. Frontends can use it to render targeted inline validation rather than a generic "password doesn't meet requirements" message.
</Tip>

## Brute-force protection

Two layers of brute-force protection are in place:

1. **Per-IP rate limiting**: The `/auth/v1/token` endpoint is wrapped with `rate_limit_middleware` (30 requests per 60 seconds). Exceeding this returns `429` before any password check runs. The middleware uses a Redis-backed sliding window, so the rate limit is enforced consistently across multiple application instances.
2. **Per-account lockout**: After `lockout_threshold` (default 10) failed password attempts within `lockout_minutes` (default 15) minutes, the account is locked until `locked_until` passes. The `failed_logins` counter resets to 0 and `locked_until` is set. A successful sign-in resets both counters to 0.

```python
async def record_failure(user: AuthUser, threshold: int, minutes: int) -> None:
    user.failed_logins += 1
    if user.failed_logins >= threshold:
        user.locked_until = datetime.now(UTC) + timedelta(minutes=minutes)
        user.failed_logins = 0
    await user.save(update_fields=["failed_logins", "locked_until"])
```

Lockout is per-environment — a user who is locked out in `acme/development` is not locked in `acme/production`, because the `AuthUser` row is scoped to `(project, env, email)`.

<Note>
Recovery codes bypass the lockout check — if a user is locked out but has MFA recovery codes, they can still sign in by using a recovery code as the TOTP code. This ensures that a brute-force lockout never becomes a denial of service against the legitimate user.
</Note>

### Lockout mechanics in detail

The lockout mechanism has several important properties:

- **Reset on success**: A successful sign-in (whether password, magic link, or social) resets `failed_logins` to 0 and clears `locked_until`. This means a user who has been locked out can sign in again once the lockout period expires.
- **Reset on password reset**: When a password is reset through the recovery flow, `failed_logins` and `locked_until` are both reset. This is deliberate — a user who was locked out due to too many failed attempts should be able to reset their password and sign in immediately.
- **Lockout is per-environment**: A user locked in `development` is not locked in `production`. Each environment maintains its own `failed_logins` counter.
- **Failed MFA attempts count**: A failed MFA verification also calls `record_failure`, so repeated MFA failures contribute to the lockout count.
- **Lockout does not block recovery**: The `/recover` endpoint does not check `is_locked`. A locked-out user can still request a recovery link and reset their password.

### Rate limiting interaction with lockout

The per-IP rate limit (30 requests per 60 seconds on `/auth/v1/token`) acts as the first line of defense. It catches bulk automated attacks before they reach the per-account lockout. The per-account lockout acts as the second line, catching targeted attacks against a specific account. Together, they provide protection at both the network level and the account level.

If an attacker makes 31 requests in 60 seconds (one per second), the 31st request gets a `429` from rate limiting before the password is ever checked. If the attacker spaces their attempts to stay under the rate limit (say, one every 3 seconds), they'll hit the per-account lockout after 10 failed attempts on that specific account.

## Password change security model

When a user changes their password, several security properties are maintained:

1. **The old password is required** (for accounts with a usable password). This ensures someone who has temporarily access to the account (e.g., through a compromised session) cannot change the password without knowing the current one.
2. **The new password is validated** against the current `password_policy`. This prevents a user from weakening their password after a policy tightening.
3. **Sessions are not automatically revoked**. This is a deliberate trade-off: if a user changes their password because they suspect a session was compromised, they might want to revoke all sessions immediately. But revoking all sessions on every password change would be disruptive (the user would be signed out of their own other devices). The admin API provides `POST .../sessions/revoke` for users who need immediate revocation.
4. **A `user.password_changed` event is emitted**. This allows external systems to react to password changes — sending notifications, triggering re-authentication for sensitive operations, or updating audit logs.
5. **The `last_sign_in_ip` and `last_login` are updated**. This provides an audit trail of when and where the password change occurred (relative to sign-in activity).

## Email change security model

The email change flow is designed around the principle that the email address is the primary identity verification mechanism. Key properties:

1. **The new email must not already be in use**: This prevents an attacker from changing the email to one they control, even if they can't access the account directly (they'd need the current password).
2. **The new email is verified before the change takes effect**: The old email remains unchanged until the verification link is clicked. This means the account owner continues to receive notifications at the old email during the verification window.
3. **The old email is preserved in the audit event**: When the change completes, `user.email_changed` is emitted with `from` and `to` fields, so an administrator can see what the email was before the change.
4. **The verification link is a one-time token**: It uses the `kind: "email_change"` token mechanism, with a configurable lifetime (typically 1 hour). After consumption, the link cannot be reused.

## Account disablement and its effect on passwords

When an administrator disables an account (sets `disabled_at`), the following happens:

- `is_disabled` returns `true` (the property checks `disabled_at is not None or not is_active`).
- All sessions are immediately revoked via `revoke_all`.
- Sign-in attempts return `403 this account is disabled`.
- The account's `AuthUser` row is preserved (soft delete is separate — disabling is reversible).
- Re-enabling clears `disabled_at` and emits `user.enabled`, but does not restore any sessions — the user must sign in again.

The password hash remains stored during disablement and re-enablement. The password is not affected by the disabled state — it can be used for sign-in as soon as the account is re-enabled.

## Common mistakes

<AccordionGroup>
  <Accordion title="Assuming the password policy applies retroactively">
    Changing `password_policy` from `"basic"` to `"strict"` does not require existing users to change their passwords immediately. The new policy only applies to `check_password_policy` calls — during sign-up and password change. Existing passwords remain valid until the user changes them.
  </Accordion>
  <Accordion title="Expecting a password change to sign out other sessions">
    It doesn't. A password change updates the hash but does not revoke existing access tokens. If a user suspects a session was compromised, they should use the admin `POST .../sessions/revoke` endpoint or call `revoke_all` explicitly.
  </Accordion>
  <Accordion title="Treating lockout as permanent">
    Lockout is temporary — it lasts `lockout_minutes` (default 15) minutes by default. After that window expires, the user can sign in again. The lockout counter is also reset on any successful sign-in.
  </Accordion>
  <Accordion title="Thinking that the lockout threshold is configurable per user">
    It's not. `lockout_threshold` and `lockout_minutes` are environment-level configuration values set through the `auth` block. They apply uniformly to all users in that environment. Adjust them through the configuration API, not on a per-user basis.
  </Accordion>
  <Accordion title="Confusing lockout with disablement">
    Lockout is automatic and temporary (triggered by failed attempts). Disablement is manual and permanent until re-enabled (performed by an administrator). A disabled account returns `403 this account is disabled`, while a locked account returns `429 too many failed attempts; try again later`.
  </Accordion>
  <Accordion title="Sending the raw password in logs">
    Never. The `check_password_policy` and `record_failure` functions operate on the password in memory. The raw password value from the request body is never written to any log, database column, or audit event. The `log_event` function records the method and success/failure, never the password itself.
  </Accordion>
</AccordionGroup>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `422` with password problems even though the password looks strong | `password_policy` is `"strict"` and the password fails a character-class check | Check the `problems` array for specific failed rules |
| `409 an account with this email already exists` on sign-up | The email is already registered in this project environment | Try signing in instead, or use a different email |
| `403 confirm your email address first` after entering correct credentials | `require_email_verification` is `true` and the account hasn't been verified | Complete the verification flow before signing in |
| `403 sign-up is disabled` | The environment administrator has turned off sign-ups | Contact the administrator or wait for sign-ups to be re-enabled |
| `429 too many failed attempts; try again later` | Account is locked due to too many failed attempts | Wait for the lockout period (default 15 min) to expire, or use a recovery code if MFA is enabled |
| Password change succeeds but the user is still signed in on other devices | Password change doesn't revoke sessions by design | This is expected; call `POST .../sessions/revoke` if immediate revocation is needed |
| `400 current_password is wrong` when changing password | The account has a usable password and the old password is incorrect | Enter the current password correctly, or set `has_usable_password() == false` first |
| `409 that email is in use` when changing email | The new email is already registered | Choose a different email address |

## FAQ

<AccordionGroup>
  <Accordion title="Can I use any Unicode character in a password?">
    Yes — the `password` field accepts any string up to 1024 characters. The `validate_password` function from Sillo operates on the raw string, so Unicode characters are valid password components. However, some authenticator apps and hardware keys may not handle unusual characters well.
  </Accordion>
  <Accordion title="What happens to the password hash when the environment config changes?">
    Nothing. The password hash is stored in the `AuthUser` row and is completely independent of the `password_policy` configuration. Changing the policy does not invalidate existing hashes or require rehashing.
  </Accordion>
  <Accordion title="Does bcrypt's cost factor change when the environment is upgraded?">
    Not automatically. The cost factor is baked into the stored hash string. If you want to increase the cost factor for new accounts, you would need to configure it in `passlib`'s defaults or migrate accounts on their next sign-in. Consult the Sillo documentation for configuring the bcrypt cost factor.
  </Accordion>
  <Accordion title="Can I disable password sign-in entirely?">
    Not directly — you can set `signup_enabled: false` to prevent new accounts from being created with passwords, and you can set `require_email_verification: true` to add friction, but existing password accounts can still sign in. To fully disable password sign-in, you'd need to build an application-level check or use a custom route handler.
  </Accordion>
  <Accordion title="How does the password grant handle `null` or empty string passwords?">
    The `SignUp` model enforces `password` has `min_length=1`, so an empty string cannot be submitted through the sign-up endpoint. For the token endpoint, if `password` is `null` or empty, the check `not body.email or not body.password` catches it and returns `400 email and password are required`.
  </Accordion>
  <Accordion title="Can I store passwords longer than 1024 characters?">
    No. The 1024-character limit is enforced both in the `SignUp` model field constraint and in `check_password_policy`. This prevents denial-of-service through excessively long passwords that would cause unreasonable hashing times.
  </Accordion>
</AccordionGroup>
