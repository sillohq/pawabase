The admin API provides a comprehensive set of endpoints for managing users in Pawabase. Administrators can list all users, create new users, update existing users, disable or delete accounts, manage sessions, change passwords, and assign roles — all through service key-authenticated endpoints.

The admin API is distinguished from the self-service API by its authentication mechanism (service keys), its broader scope of operations (all users in an environment), and its permission model (service key permissions). Every admin endpoint requires a valid service key with the appropriate permissions.

## Admin API base URL

All admin API endpoints are prefixed with the project and environment path:

```
/projects/{project}/envs/{env}/users/{user_id}/...
```

Where:
- `{project}` is the project identifier.
- `{env}` is the environment identifier (`dev`, `staging`, `prod`, etc.).
- `{user_id}` is the UUID of the user to manage.

The base URL is typically:

```
https://yourapi.com/projects/my-project/envs/prod/users/{user_id}/...
```

Every request to the admin API must include the `apikey` header with a valid service key:

```bash
curl -X GET "$GW/projects/my-project/envs/prod/users/{user_id}" \
  -H "apikey: $PAWABASE_SECRET_KEY"
```

## Service key permissions

Service keys have permissions that determine which admin endpoints can be called. The key permissions are:

- **`user_view`**: Can read user information. Required for `GET /users/{user_id}` and `GET /users`.
- **`user_create`**: Can create new users. Required for `POST /users`.
- **`user_update`**: Can update user information. Required for `PATCH /users/{user_id}`.
- **`user_delete`**: Can delete users. Required for `DELETE /users/{user_id}`.
- **`user_mfa_reset`**: Can reset MFA for users. Required for `POST /users/{user_id}/reset-mfa`.
- **`user_password_change`**: Can change user passwords. Required for `POST /users/{user_id}/password`.
- **`user_disable`**: Can disable and re-enable user accounts. Required for `POST /users/{user_id}/disable`.
- **`session_view`**: Can view user sessions. Required for `GET /users/{user_id}/sessions`.
- **`session_revoke`**: Can revoke user sessions. Required for `POST /users/{user_id}/sessions/revoke`.
- **`role_manage`**: Can assign and revoke roles. Required for `POST /users/{user_id}/roles` and `DELETE /users/{user_id}/roles`.

A service key with all permissions (`admin` scope) can perform all operations. A restricted service key can only perform operations for which it has the specific permission.

<Warning>
Service keys with broad permissions are a security risk. Always use the principle of least privilege — grant only the permissions needed for the task. A read-only service key should have `user_view` only, not `user_update` or `user_delete`.
</Warning>

## Listing users

Administrators can list all users in an environment:

```bash
curl -X GET "$GW/projects/my-project/envs/prod/users" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json"
```

The response includes a paginated list of all users in the environment. Each user object is a `user_view` response:

```json
{
    "id": "uuid-here",
    "email": "user@example.com",
    "name": "John Doe",
    "email_verified": true,
    "mfa_enabled": false,
    "disabled_at": null,
    "created_at": "2025-01-15T10:30:00Z",
    "last_active_at": "2025-09-20T14:22:00Z"
}
```

### Query parameters

The `GET /users` endpoint supports query parameters for filtering and pagination:

| Parameter | Type | Description |
| --- | --- | --- |
| `email` | string | Filter users by email address. |
| `name` | string | Filter users by name. |
| `email_verified` | boolean | Filter by email verification status. |
| `mfa_enabled` | boolean | Filter by MFA status. |
| `disabled` | boolean | Filter by disabled status. |
| `page` | integer | Page number for pagination. Default: `1`. |
| `page_size` | integer | Number of users per page. Default: `50`, maximum: `100`. |
| `sort` | string | Sort field. Options: `created_at`, `name`, `email`. Default: `created_at`. |
| `order` | string | Sort order: `asc` or `desc`. Default: `desc`. |

### Response structure

The response includes metadata for pagination:

```json
{
    "users": [...],
    "total": 1250,
    "page": 1,
    "page_size": 50,
    "total_pages": 25
}
```

## Creating users

Administrators can create users programmatically through the admin API:

```bash
curl -X POST "$GW/projects/my-project/envs/prod/users" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "email": "newuser@example.com",
    "name": "New User",
    "password": "SecurePassword123!",
    "email_verified": true,
    "mfa_enabled": false,
    "data": {
        "department": "Engineering",
        "role": "developer"
    },
    "app_metadata": {
        "tier": "premium",
        "plan": "enterprise"
    }
  }'
```

The `AdminUserCreate` object supports the following fields:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `email` | string | Yes | The user's email address. Must be unique. |
| `name` | string | No | The user's display name. |
| `password` | string | No | The user's password. If not provided, the user must sign in through a passwordless method. |
| `email_verified` | boolean | No | Whether the email is verified. Default: `false`. |
| `mfa_enabled` | boolean | No | Whether MFA is enabled. Default: `false`. |
| `data` | object | No | The `user_metadata` object. Merged with existing data if the user already exists. |
| `app_metadata` | object | No | The `app_metadata` object. Replaces existing metadata on update. |

### `data` vs `app_metadata`

When creating or updating a user, the `data` and `app_metadata` fields behave differently:

1. **`data` (user_metadata)**: The `data` field is **merged** with the existing `user_metadata` on update. If you update `data` with `{department: "Engineering"}`, it is merged with any existing `user_metadata` fields. This means you can update specific metadata fields without overwriting others.
2. **`app_metadata`**: The `app_metadata` field **replaces** the entire `app_metadata` object on update. If you update `app_metadata` with `{tier: "premium"}`, it replaces all existing `app_metadata` fields. This ensures administrators have full control over app metadata.

<Warning>
Never put sensitive data in `user_metadata` (`data`) because users can modify it themselves through the self-service API. Use `app_metadata` for data that should only be modified by administrators or service keys.
</Warning>

## Updating users

Administrators can update user information:

```bash
curl -X PATCH "$GW/projects/my-project/envs/prod/users/{user_id}" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "name": "Updated Name",
    "data": {
        "department": "Marketing"
    },
    "app_metadata": {
        "tier": "enterprise"
    }
  }'
```

The `AdminUserUpdate` object supports the same fields as `AdminUserCreate`, with the addition of:

| Field | Type | Description |
| --- | --- | --- |
| `disabled_at` | datetime or null | If set, disables the user's account. If `null`, re-enables the account. |
| `email` | string | Updates the email address. Must be unique. |
| `mfa_enabled` | boolean | Enables or disables MFA. |

### Update behavior

1. **Partial updates**: The `PATCH` method allows partial updates — only the fields provided in the request are updated. Fields not provided remain unchanged.
2. **`data` merge**: As noted above, `data` is merged with existing `user_metadata`.
3. **`app_metadata` replace**: `app_metadata` replaces the entire existing object.
4. **`email` change**: Changing the email address generates a new verification requirement if `require_email_verification` is enabled.

## Changing passwords

Administrators can change a user's password:

```bash
curl -X POST "$GW/projects/my-project/envs/prod/users/{user_id}/password" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "new_password": "NewSecurePassword123!"
  }'
```

The admin password change:

1. Validates the new password against the password policy.
2. Updates the password hash.
3. Resets `failed_logins` to `0`.
4. Revokes all existing sessions for the user.
5. Emits a `user.password_changed` event.
6. Returns the new access token and refresh token.

### Admin vs self-service password change

| Aspect | Admin Password Change | Self-Service Password Change |
| --- | --- | --- |
| **Endpoint** | `POST /users/{user_id}/password` | `POST /auth/v1/new-password` |
| **Authentication** | Service key | User's current password |
| **Requires current password** | No | Yes |
| **Session revocation** | Yes (all sessions revoked) | Yes (all sessions revoked) |
| **`failed_logins` reset** | Yes | Yes |

The admin password change does not require the current password because the administrator is authorized to change any user's password. The self-service password change requires the current password to verify the user's identity.

<Warning>
After an admin password change, all existing sessions are revoked. The user must sign in again with their new password. This is a security measure — if the admin changed the password due to a compromise, existing sessions must be invalidated.
</Warning>

## Disabling and re-enabling accounts

Administrators can disable user accounts:

```bash
curl -X POST "$GW/projects/my-project/envs/prod/users/{user_id}/disable" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "disabled_at": "2025-09-28T10:00:00Z"
  }'
```

The disable endpoint:

1. Sets `disabled_at` to the specified timestamp.
2. Revokes all existing sessions via `revoke_all`.
3. Marks all refresh tokens as invalid.
4. Emits a `user.disabled` event.
5. Returns `200 account disabled`.

To re-enable an account:

```bash
curl -X POST "$GW/projects/my-project/envs/prod/users/{user_id}/disable" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "disabled_at": null
  }'
```

Setting `disabled_at` to `null` re-enables the account. The user can sign in again and their refresh tokens are valid (if they haven't expired).

### `disabled_at` behavior

- When `disabled_at` is set, the account is immediately locked. All sessions are revoked.
- When `disabled_at` is `null`, the account is active. The user can sign in.
- `disabled_at` is a soft disable — the user record is not deleted, only marked as disabled.
- Disabled users cannot access any protected resources. Any request to a protected route returns `403 account disabled`.

## Deleting users

Administrators can delete user accounts:

```bash
curl -X DELETE "$GW/projects/my-project/envs/prod/users/{user_id}" \
  -H "apikey: $PAWABASE_SECRET_KEY"
```

The delete endpoint performs a **soft delete**:

1. The `AuthUser` record is marked as deleted (`deleted_at = now()`).
2. The user's data is anonymized (email and name are replaced with `[deleted]`).
3. All sessions are revoked via `revoke_all`.
4. All refresh tokens are invalidated.
5. The `OTP`, `MFARecoveryCode`, and `SessionInfo` records are preserved for audit purposes.
6. The `RevokedToken` records are preserved.
7. A `user.deleted` event is emitted.

### Soft delete vs hard delete

Pawabase uses soft delete for user accounts. This means:

- The `AuthUser` record is not physically deleted from the database.
- The `deleted_at` timestamp marks when the deletion occurred.
- The user's personal data is anonymized but the audit trail is preserved.
- Soft delete allows for data recovery in case of accidental deletion.
- Soft delete is required for compliance with data retention regulations.

### What happens after deletion

After a user is soft-deleted:

- The user cannot sign in (`403 account deleted`).
- All refresh tokens are invalid (`401 session revoked`).
- The user's email can be reused for a new account (after a configurable grace period).
- The `auth_providers` linking is preserved for audit purposes.
- The `RoleAssignment` records remain for audit purposes.

## Session management

Administrators can view and manage user sessions:

### Listing sessions

```bash
curl -X GET "$GW/projects/my-project/envs/prod/users/{user_id}/sessions" \
  -H "apikey: $PAWABASE_SECRET_KEY"
```

The response includes all active sessions for the user:

```json
{
    "sessions": [
        {
            "id": "session-uuid",
            "method": "password",
            "aal": "aal2",
            "org": null,
            "ip_address": "192.168.1.1",
            "user_agent": "Mozilla/5.0...",
            "created_at": "2025-09-20T10:00:00Z",
            "last_active_at": "2025-09-20T14:22:00Z",
            "revoked": false
        }
    ]
}
```

### Revoking a specific session

```bash
curl -X POST "$GW/projects/my-project/envs/prod/users/{user_id}/sessions/{session_id}/revoke" \
  -H "apikey: $PAWABASE_SECRET_KEY"
```

### Revoking all sessions

```bash
curl -X POST "$GW/projects/my-project/envs/prod/users/{user_id}/sessions/revoke" \
  -H "apikey: $PAWABASE_SECRET_KEY"
```

Both endpoints set `revoked = True` and `revoked_at = now()` on the `SessionInfo` row. Any subsequent refresh attempt with the session's refresh token returns `401 session revoked`.

### Session information

Each session returned by the admin API includes:

- **`id`**: The session UUID (same as the `SessionInfo.id`).
- **`method`**: How the session was created (`"password"`, `"magic_link"`, `"social"`, `"refresh"`, `"recovery"`).
- **`aal`**: The Authenticator Assurance Level.
- **`org`**: The organization ID (if scoped).
- **`ip_address`**: The IP address of the device.
- **`user_agent`**: The user agent string.
- **`created_at`**: When the session was created.
- **`last_active_at`**: When the session was last active.
- **`revoked`**: Whether the session has been revoked.

## Role assignments

Administrators can assign and revoke roles for users:

### Assigning a role

```bash
curl -X POST "$GW/projects/my-project/envs/prod/users/{user_id}/roles" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "role": "admin",
    "scope": "global"
  }'
```

### Revoking a role

```bash
curl -X DELETE "$GW/projects/my-project/envs/prod/users/{user_id}/roles" \
  -H "apikey: $PAWABASE_SECRET_KEY" \
  -H "content-type: application/json" \
  -d '{
    "role": "admin",
    "scope": "global"
  }'
```

Role assignments are managed through the `RoleAssignment` model. The `assign_role` and `revoke_role` functions handle the database operations. See [Roles and permissions →](/auth/roles-and-permissions) for the complete reference.

## Admin API vs self-service API

The admin API and self-service API are distinct interfaces for different use cases:

| Aspect | Admin API | Self-Service API |
| --- | --- | --- |
| **Authentication** | Service key | User credentials or access token |
| **Scope** | All users in an environment | The authenticated user only |
| **Permissions** | Service key permissions | User's own permissions |
| **User creation** | `POST /users` | Not available (users create themselves) |
| **User updates** | `PATCH /users/{id}` | `PATCH /auth/v1/user` (own data) |
| **Password change** | `POST /users/{id}/password` | `POST /auth/v1/new-password` |
| **Session management** | All sessions for any user | Own sessions only |
| **Role management** | `POST/DELETE /users/{id}/roles` | Not available |
| **Account disable/delete** | Available | Not available |
| **MFA reset** | Available | Not available |

The admin API is for backend administrators and service integrations. The self-service API is for frontend applications that need to interact with the authenticated user's account.

<Warning>
Never expose service keys in client-side code. Service keys have broad permissions and can perform any admin operation. Always keep service keys on the backend and expose only the self-service API to client-side applications.
</Warning>

## Common mistakes

<AccordionGroup>
  <Accordion title="Using a publishable key for admin operations">
    Publishable keys are designed for client-side use. They have limited permissions. Administrative operations require a secret key. Using a publishable key for admin operations will fail with `403 insufficient permissions`.
  </Accordion>
  <Accordion title="Not resetting `failed_logins` after admin password change">
    If `failed_logins` is not reset after an admin password change, the user may still be locked out from signing in with their new password. Always reset `failed_logins` to `0`.
  </Accordion>
  <Accordion title="Not revoking sessions after disabling an account">
    If sessions are not revoked when an account is disabled, the user could still access the application with existing sessions. Always use `revoke_all` when disabling an account.
  </Accordion>
  <Accordion title="Hard-deleting users instead of soft-deleting">
    Pawabase uses soft delete for compliance and audit trail purposes. Never physically delete user records. Always soft-delete by setting `deleted_at`.
  </Accordion>
  <Accordion title="Putting sensitive data in `user_metadata`">
    `user_metadata` (`data`) can be modified by the user themselves. Never put sensitive information (roles, permissions, tier) in `user_metadata`. Use `app_metadata` instead.
  </Accordion>
  <Accordion title="Granting all permissions to a service key">
    Service keys with all permissions are a security risk. Use the principle of least privilege — grant only the permissions needed for the specific task.
  </Accordion>
</AccordionGroup>
