title: "Managing users"
description: "The complete operator toolkit for one environment's users: search, create, update, disable, delete, sessions, MFA reset and history, all behind a service credential."
icon: "users-cog"
---

Everything an end user can do to their own account through `/auth/v1/user` has a mirror image for **operators** — a service credential acting from Studio or a backend script — under `/admin/v1/projects/{project}/envs/{env}/...` in Akountz's `routes/admin.py`. This is the surface Studio's **Auth → Users** screen is built on, and it's the page to reach for whenever you need to manage users programmatically: bulk-importing accounts, building a support tool, writing an onboarding script, or responding to an account-recovery request that a self-service flow can't handle (a lost MFA device with no recovery codes left, say).

<Note>
Every route on this page requires a **service credential** — `auth=SERVICE_ONLY` on each one. That means a **secret key**, or the operator token Studio mints for a signed-in operator. Never expose these routes to an end user's own browser session; see [security model →](/auth/security-model) for exactly what a service credential can do and why it must never leave your own servers.
</Note>

<CardGroup cols={3}>
  <Card title="One environment at a time" icon="layers">Every route takes `{project}` and `{env}` in its path — there's no cross-environment listing.</Card>
  <Card title="Soft delete" icon="trash-2">Deleting a user keeps the row (and its history) for attribution, releasing only the email and username for re-use.</Card>
  <Card title="Immediate where it matters" icon="zap">Disabling a user also revokes every session — it doesn't wait for their tokens to expire.</Card>
</CardGroup>

## Searching and listing users

```bash
curl "$STUDIO/admin/v1/projects/acme/envs/production/users?search=ada&limit=20" \
  -H "Authorization: Bearer $SERVICE_TOKEN"
```

```json
{
  "data": [
    {
      "id": "8", "email": "ada@example.com", "username": "ada", "name": "Ada Okafor",
      "email_verified": true, "disabled": false, "mfa_enabled": true,
      "user_metadata": { "locale": "en-NG" }, "app_metadata": { "plan": "pro" },
      "created_at": "2026-08-01T10:02:11.000Z"
    }
  ],
  "total": 1
}
```

| Query parameter | Meaning |
| --- | --- |
| `search` | Case-insensitive substring match against `email`, `username` **or** `name` |
| `status=disabled` | Only accounts with `disabled_at` set |
| `status=unverified` | Only accounts with no `email_verified_at` |
| `limit` | 1–200, default 50 |
| `offset` | Pagination offset, default 0 |

```bash
# Every disabled account, second page of 50
curl "$STUDIO/admin/v1/projects/acme/envs/production/users?status=disabled&limit=50&offset=50" \
  -H "Authorization: Bearer $SERVICE_TOKEN"
```

Each row in `data` is the **admin view** of a user (`user_view(u, admin=True)`) — it includes `app_metadata`, which the ordinary self-service `/auth/v1/user` response never exposes to the user themself in write form (they see it, but can't set it — see [auth in policies: claims.app](/auth/auth-in-policies#authclaimsapp--administrator-controlled-safe-for-policies)).

## Creating a user

```bash
curl -X POST "$STUDIO/admin/v1/projects/acme/envs/production/users" \
  -H "Authorization: Bearer $SERVICE_TOKEN" \
  -H "content-type: application/json" \
  -d '{
    "email": "femi@acme.example",
    "password": "a-temporary-password-1",
    "name": "Femi Adeyemi",
    "user_metadata": { "invited_by": "ada" },
    "app_metadata": { "department_id": 4 },
    "email_verified": true,
    "roles": ["bursar"]
  }'
```

```json
{
  "id": "12", "email": "femi@acme.example", "username": null, "name": "Femi Adeyemi",
  "email_verified": true, "disabled": false, "mfa_enabled": false,
  "user_metadata": { "invited_by": "ada" }, "app_metadata": { "department_id": 4 },
  "created_at": "2026-09-28T09:31:00.221Z"
}
```

| Field | Notes |
| --- | --- |
| `email` | Required, unique per environment |
| `password` | Optional — omit it to create a password-less account (the person signs in via [magic link](/auth/magic-links) or [social login](/auth/social-login) instead) |
| `username`, `name` | Optional profile fields |
| `user_metadata` | Same field the user could set themself via `PATCH /auth/v1/user`'s `data` |
| `app_metadata` | **Only** settable here or via `PATCH .../users/{id}` — never by the user |
| `email_verified` | Defaults `true` for operator-created accounts, skipping the verification email a self-service sign-up would send |
| `roles` | Assigned immediately, same as calling [roles and permissions](/auth/roles-and-permissions#assigning-and-revoking-roles-on-a-user) separately |

This is the right path for bulk-importing an existing user base (a CSV import script that calls this once per row), or for any "invite a teammate directly" admin feature that shouldn't wait on an email round-trip.

<Warning>
An email address that was previously used by a **deleted** account can be reused immediately — deletion releases it (see [deleting a user](#deleting-a-user) below). If a new signup with a recently-freed address fails unexpectedly, check whether an old, non-deleted account still holds it.
</Warning>

## Getting one user

```bash
curl "$STUDIO/admin/v1/projects/acme/envs/production/users/8" -H "Authorization: Bearer $SERVICE_TOKEN"
```

```json
{
  "id": "8", "email": "ada@example.com", "…": "…",
  "sessions": [
    { "id": "f3d9c2a1e8b74d0f", "method": "password", "aal": "aal2", "ip": "102.89.3.17",
      "user_agent": "Mozilla/5.0 …", "created_at": "2026-09-27T08:00:00Z",
      "last_refreshed_at": "2026-09-28T08:55:00Z", "current": false }
  ]
}
```

Unlike the list endpoint, getting **one** user also returns their `sessions` inline — the same shape `GET /auth/v1/sessions` returns for the user themself, minus which one is "current" (there's no meaningful "current session" from an operator's point of view). `404 no such user` for an id that doesn't exist, is soft-deleted, or belongs to a different environment.

You can also look a user up by **your own service's context** rather than by explicit project/env in the path — useful from inside a flow or another service that already has a `PlatformContext` bound:

```bash
curl "$STUDIO/admin/v1/users/8" -H "X-Pawabase-Context: $SIGNED_CONTEXT"
```

This is `GET /users/{user_id}` in `routes/admin.py`, documented as *"One user of the calling context's environment"* — it resolves project/env from `require_context(ctx)` instead of the path, which is how another internal service (a flow, a custom route in a different project's own backend) looks a user up without needing to know or pass the environment explicitly.

## Updating a user

```bash
curl -X PATCH "$STUDIO/admin/v1/projects/acme/envs/production/users/8" \
  -H "Authorization: Bearer $SERVICE_TOKEN" \
  -H "content-type: application/json" \
  -d '{
    "name": "Ada N. Okafor",
    "app_metadata": { "plan": "enterprise" },
    "roles": ["editor", "bursar"]
  }'
```

Every field is optional and independent — send only what's changing:

| Field | Effect |
| --- | --- |
| `name` | Replaces the display name |
| `email_verified` | `true` sets `email_verified_at` to now; `false` clears it |
| `disabled` | See [disabling a user](#disabling-a-user) |
| `password` | Sets a new password, run through the environment's [password policy](/auth/passwords#password-policy) first |
| `user_metadata` | **Replaces** the whole object (not merged — unlike the self-service `PATCH /auth/v1/user`, which merges) |
| `app_metadata` | Same: replaces, not merges |
| `roles` | **Replaces** the whole role set — see [roles and permissions](/auth/roles-and-permissions#assigning-and-revoking-roles-on-a-user) |
| `unlock` | `true` clears any brute-force lockout (`failed_logins = 0, locked_until = None`) |

<Warning>
`user_metadata` and `app_metadata` here **replace** rather than merge, unlike the end-user-facing `PATCH /auth/v1/user`, which merges `data` into the existing `user_metadata`. Sending `{"app_metadata": {"plan": "enterprise"}}` for a user whose `app_metadata` was previously `{"department_id": 4, "plan": "pro"}` **drops** `department_id` entirely. Fetch the current value first if you only mean to change one key.
</Warning>

## Disabling a user

```bash
curl -X PATCH "$STUDIO/admin/v1/projects/acme/envs/production/users/8" \
  -H "Authorization: Bearer $SERVICE_TOKEN" \
  -H "content-type: application/json" -d '{"disabled": true}'
```

Disabling does three things in one call, none of them optional or deferred:

1. Sets `disabled_at` to now.
2. **Immediately revokes every session** the user holds (`await revoke_all(user)`) — their existing access tokens still verify until they naturally expire (a JWT can't be un-signed), but every refresh token is invalidated, so they can't obtain a new one, and any [session-aware check](/auth/security-model#what-a-compromised-token-cant-do) stops trusting them the moment their current access token expires.
3. Emits `user.disabled`.

```bash
curl -X POST "$GW/auth/v1/token" -H "apikey: $PK" -H "content-type: application/json" \
  -d '{"email": "ada@example.com", "password": "correct-horse-1"}'
```
```json
// 403
{ "detail": "this account is disabled" }
```

A disabled user simply can't sign in at all — the check happens before password verification even completes in the sign-in flow. Re-enable with `{"disabled": false}`; this does **not** automatically re-establish any of their old sessions — they need to sign in again.

<Note>
Disabling is the right tool for "this account should stop working right now" — an offboarded employee, a suspected compromise, a policy violation under investigation. It's reversible and keeps the account and its history intact. Use [deleting](#deleting-a-user) only when the account should actually cease to exist.
</Note>

## Deleting a user

```bash
curl -X DELETE "$STUDIO/admin/v1/projects/acme/envs/production/users/8" \
  -H "Authorization: Bearer $SERVICE_TOKEN"
```

`204 No Content`. This is a **soft delete**, and it's worth knowing exactly what it does, since it's not simply "remove the row":

```python services/akountz/routes/admin.py (excerpt)
await revoke_all(user)
await Identity.filter(user=user).delete()
await mfa.disable(user)
# Soft delete keeps history attributable; the address is released for re-use.
user.deleted_at = datetime.now(UTC)
user.email = f"deleted+{user.id}@{project}.invalid"
user.username = f"deleted-{user.id}"
user.is_active = False
await user.save()
```

| What happens | Why |
| --- | --- |
| Every session revoked | The account can no longer authenticate at all |
| OAuth identities deleted | So a re-signup under the same email/provider doesn't collide with a stale link |
| MFA factors and recovery codes deleted | Nothing left to verify against a gone account |
| `deleted_at` set | The row is excluded from every ordinary query (`AuthUser.filter(..., deleted_at=None)` is the default everywhere in the codebase) |
| Email rewritten to `deleted+<id>@<project>.invalid` | **Releases the real address for immediate re-use** — a new sign-up with the same email succeeds right away |
| `is_active = False` | Belt-and-braces: `is_disabled` is also true via Sillo's base `is_active` flag |

The row itself, and anything in **your own** resources that references the user's id (an `author_id`, a `created_by`), still exists — deletion only touches Akountz's own tables. This is deliberate: history stays attributable (a post's `author_id` still resolves to a real, if inert, row) without the deleted person's identity being reachable, sign-in-able, or holding onto their real email address forever.

```bash
# Confirm the address is free again
curl -X POST "$GW/auth/v1/signup" -H "apikey: $PK" -H "content-type: application/json" \
  -d '{"email": "ada@example.com", "password": "a-brand-new-password-1"}'
# → 201, a genuinely new account
```

<Warning>
There is no "undelete." Once `deleted_at` is set and the email rewritten, the operation cannot be reversed through the API — the original email is gone from that row permanently (though a new signup can claim it again, as a **new**, unrelated account). If your product needs a recoverable "deactivate," build that as your own state (a flag in `app_metadata`, checked by your own policies) on top of [disabling](#disabling-a-user), and reserve deletion for genuinely final removal — a GDPR erasure request, for instance.
</Warning>

## Ending sessions

Two granularities: end everything, or end one specific session.

```bash
# Sign a user out everywhere — every refresh token invalidated
curl -X POST "$STUDIO/admin/v1/projects/acme/envs/production/users/8/sessions/revoke" \
  -H "Authorization: Bearer $SERVICE_TOKEN"
```
```json
{ "revoked": 3 }
```

```bash
# End one specific session by its id (the "family"/session_id from a token response)
curl -X DELETE "$STUDIO/admin/v1/projects/acme/envs/production/users/8/sessions/f3d9c2a1e8b74d0f" \
  -H "Authorization: Bearer $SERVICE_TOKEN"
```

`404 no such session` if the id doesn't match an active session for that user. Both routes are the operator-side mirror of the user's own [`GET /auth/v1/sessions`](/auth/tokens-and-sessions#listing-and-revoking-sessions) and `DELETE /auth/v1/sessions/{id}` — the difference is purely who's allowed to call them without needing the user's own token. Reach for `sessions/revoke` after disabling an account, resetting a compromised password, or any incident where "this specific device looked suspicious" isn't precise enough and you want a clean slate.

## Resetting a user's MFA

For the case self-service can't cover: a lost device **and** no remaining recovery codes.

```bash
curl -X POST "$STUDIO/admin/v1/projects/acme/envs/production/users/8/mfa/reset" \
  -H "Authorization: Bearer $SERVICE_TOKEN"
```

```json
{ "mfa_enabled": false }
```

This is identical in effect to the user's own `POST /auth/v1/mfa/disable` (deletes every `MfaFactor` and `RecoveryCode` row, sets `mfa_enabled = false`) with one crucial difference: **it needs no code**, because the entire point is recovering an account that can't produce one. Emits `user.mfa_reset`. See [MFA: administrator MFA reset →](/auth/mfa#administrator-mfa-reset) for the full mechanics.

<Warning>
Because this route bypasses the "prove you still control a factor" check by design, treat it as a genuine support action with the same care as a password reset for a suspicious request — verify the requester's identity out of band (a support ticket tied to a known account, a callback, whatever your process requires) before resetting someone's second factor. An attacker who can get an operator to call this endpoint on their behalf has effectively defeated MFA for that account.
</Warning>

## Sign-in history

```bash
curl "$STUDIO/admin/v1/projects/acme/envs/production/users/8/history" \
  -H "Authorization: Bearer $SERVICE_TOKEN"
```

```json
{
  "data": [
    { "id": 991, "user_id": "8", "email": "ada@example.com", "kind": "sign_in", "method": "password",
      "success": true, "reason": null, "ip": "102.89.3.17", "user_agent": "Mozilla/5.0 …", "at": "2026-09-28T08:00:00Z" },
    { "id": 988, "user_id": "8", "email": "ada@example.com", "kind": "sign_in", "method": "password",
      "success": false, "reason": "wrong password", "ip": "102.89.3.17", "user_agent": "…", "at": "2026-09-27T21:14:02Z" }
  ]
}
```

The last **100** `LoginEvent` rows for this one user, newest first — `sign_in`, `refresh`, `sign_out`, `mfa_challenge`, `mfa_verify`, `mfa_enrolled` events, each carrying success/failure and, for failures, a `reason` (`"unknown email"`, `"wrong password"`, `"locked"`, `"disabled"`, `"wrong code"`). This is the per-user drill-down; for an environment-wide feed (every user's events, filterable), see [environment-wide activity](#environment-wide-activity-and-statistics) below.

## Environment-wide activity and statistics

Two routes give an operational overview without picking a specific user first.

```bash
curl "$STUDIO/admin/v1/projects/acme/envs/production/events?kind=sign_in&failed=true&limit=50" \
  -H "Authorization: Bearer $SERVICE_TOKEN"
```

```json
{
  "data": [
    { "id": 988, "user_id": "8", "email": "ada@example.com", "kind": "sign_in", "method": "password",
      "success": false, "reason": "wrong password", "ip": "102.89.3.17", "user_agent": "…", "at": "…" }
  ]
}
```

`kind` filters by event kind, `failed=true` restricts to failures, `limit` caps at 500 (default 100).

```bash
curl "$STUDIO/admin/v1/projects/acme/envs/production/stats" -H "Authorization: Bearer $SERVICE_TOKEN"
```

```json
{
  "users": 412, "verified": 398, "mfa": 61, "disabled": 3,
  "signups_24h": 7, "sign_ins_24h": 189, "failures_24h": 4,
  "organizations": 12,
  "providers": [ { "provider": "google", "n": 240 } ]
}
```

This is the summary card set Studio's Auth dashboard shows: total users, how many verified/MFA-enrolled/disabled, sign-up and sign-in volume for the last day, organization count, and a breakdown of linked OAuth identities by provider. Useful for a health-check script or an internal ops dashboard beyond Studio itself.

## Organizations, from the operator side

Operators can see (but not directly modify membership of) every organization in an environment, without needing to be a member themselves — useful for support and for platform-wide oversight roles like `platform_admin` in the [commerce blueprint](/auth/organizations#the-commerce-blueprints-pattern-in-short).

```bash
curl "$STUDIO/admin/v1/projects/acme/envs/production/orgs" -H "Authorization: Bearer $SERVICE_TOKEN"
```

```json
{
  "data": [
    { "id": 14, "slug": "acme-inc", "name": "Acme Inc", "members": 3, "created_at": "…" },
    { "id": 15, "slug": "globex", "name": "Globex", "members": 1, "created_at": "…" }
  ]
}
```

```bash
curl "$STUDIO/admin/v1/projects/acme/envs/production/orgs/acme-inc" -H "Authorization: Bearer $SERVICE_TOKEN"
```

```json
{
  "slug": "acme-inc", "name": "Acme Inc", "metadata": { "plan": "trial" },
  "members": [ { "user_id": "8", "email": "ada@example.com", "role": "owner" } ],
  "teams": [ { "slug": "core", "name": "Core" } ]
}
```

There's no operator route to **change** a membership role or delete an organization directly — those actions go through the normal member-facing routes under `/auth/v1/orgs/{slug}`, called with a token belonging to an actual `owner`/`admin` of that organization (or, in a support situation, by an operator signing in through Studio's own tooling as needed, following whatever process your team uses for acting on a customer's behalf). This split is intentional: organization membership is customer-owned data, and Akountz's admin surface for it is read-only, matching the principle that operators observe and unblock, rather than silently reshaping a tenant's own structure.

## Studio's Auth screen

Everything on this page has a UI counterpart in Studio:

<Steps>
  <Step title="Open Build → Auth → Users">
    Search, filter by status, and open any user for the full detail view (profile, roles, sessions, sign-in history).
  </Step>
  <Step title="Edit roles and metadata inline">
    The role picker lists every role defined in the environment (from `GET .../roles`); `app_metadata` has its own editable JSON panel, separate from the read-only `user_metadata` view (which Studio shows but doesn't offer to edit on the user's behalf, since it's the user's own data).
  </Step>
  <Step title="Act on sessions and MFA">
    "Sign out everywhere" and "Reset MFA" buttons call exactly the routes documented above.
  </Step>
  <Step title="Auth → Organizations">
    A read-only roster mirroring `GET .../orgs`, useful for support without needing raw API calls.
  </Step>
</Steps>

<Tip>
Studio itself authenticates to Akountz's admin API the same way any other operator script would — with a short-lived **service token**, minted for the signed-in Studio operator, carrying their own roles as claims. There's no separate "Studio-only" backdoor; if you can call these routes with a valid service credential, you have exactly the same power Studio's UI does. See [security model →](/auth/security-model) for how operator tokens are scoped and verified.
</Tip>

## Common mistakes

<AccordionGroup>
  <Accordion title="Calling admin routes with a user's own access token">
    Every route in this section is `auth=SERVICE_ONLY`. A user's bearer token gets `401` — these routes exist for your own backend or Studio, never for a signed-in end user's browser.
  </Accordion>
  <Accordion title="Sending a partial user_metadata or app_metadata patch expecting a merge">
    The admin update **replaces** both fields wholesale, unlike the self-service endpoint. Fetch-then-merge in your own script if you only mean to change one key.
  </Accordion>
  <Accordion title="Assuming deletion removes the row and everything it touched">
    It's a soft delete that anonymises and deactivates — see [deleting a user](#deleting-a-user). Rows in your own resources that reference the user's id are untouched.
  </Accordion>
  <Accordion title="Forgetting that disabling revokes sessions but re-enabling doesn't restore them">
    Re-enabling clears `disabled_at`; it does not un-revoke anything. The user must sign in again.
  </Accordion>
  <Accordion title="Using MFA reset as a routine support action instead of a last resort">
    It skips the "prove you still have a factor" check by design. Reserve it for genuine lockouts and verify identity out of band first — see the warning under [resetting a user's MFA](#resetting-a-users-mfa).
  </Accordion>
</AccordionGroup>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `401` on any `/admin/v1/...` route | Called with a user token, or no token at all | Use a secret key or a Studio operator's service token |
| `404` from `GET .../users/{id}` for a user you know exists | Wrong `project`/`env` in the path, or the account is soft-deleted | Double-check the path; soft-deleted accounts are excluded from every admin lookup too |
| `PATCH` with `app_metadata` unexpectedly wipes other keys | Replace, not merge, semantics | Read-modify-write: `GET` first, merge client-side, then `PATCH` the full object |
| A disabled user can still make requests with an old access token | The access token hasn't expired yet — a JWT can't be revoked mid-flight | Expected within the token's TTL; see [security model](/auth/security-model#what-a-compromised-token-cant-do) |
| `POST .../signup` for a freshly-deleted address still fails | The deletion didn't actually complete, or you're testing against a different environment | Confirm the `DELETE` returned `204`, and that signup is aimed at the same project/env |
| `sessions/revoke` returns `{"revoked": 0}` | The user had no active sessions to begin with | Not an error — nothing to revoke |

## FAQ

<AccordionGroup>
  <Accordion title="Can an operator impersonate a user (get a token as them) directly?">
    Not through any route documented here — there's no "mint me a token for user X" endpoint. Support flows that need to act as a user go through your own product's support tooling, built on top of these read/manage primitives, not a built-in impersonation grant.
  </Accordion>
  <Accordion title="Is there a bulk-update endpoint?">
    No — each of these routes acts on one user. Bulk operations (a CSV import, a mass role change) are scripted by calling the single-user routes in a loop from your own tooling.
  </Accordion>
  <Accordion title="Does deleting a user emit an event I can react to?">
    Yes — `user.deleted` (also `user.disabled`/`user.enabled`, `user.mfa_reset`, and the ordinary `user.updated`/`user.created` events). Subscribe a flow to clean up related data in your own resources, send a notification, or sync to an external system. See [events →](/events/overview).
  </Accordion>
  <Accordion title="Can I search users across every environment of a project at once?">
    No — every route takes one `{env}` in its path. If you need a cross-environment view, call the listing route once per environment and combine the results client-side.
  </Accordion>
  <Accordion title="What's the difference between the admin 'roles' field on update and the dedicated roles endpoints described on the roles and permissions page?">
    They're two ways to reach the same underlying assignment logic — `PATCH .../users/{id} {"roles": [...]}` diffs and applies role membership exactly as described in [roles and permissions](/auth/roles-and-permissions#assigning-and-revoking-roles-on-a-user); there's no separate "roles" sub-resource to call instead. Use whichever is more convenient for the update you're making (a full user edit vs. a role-focused script).
  </Accordion>
</AccordionGroup>
