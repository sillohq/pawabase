## Roles and permissions

Roles live in Akountz, per environment (**Users & auth → Roles**, or `PUT /admin/v1/…/roles`):

| Role | Permissions |
| --- | --- |
| `admin` | `*` |
| `principal` | `students.*`, `staff.read`, `grades.read`, `reports.publish`, `finance.read`, `discipline.*`, `announcements.publish` |
| `teacher` | `students.read`, `attendance.write`, `grades.write`, `assessments.write`, `announcements.publish`, `discipline.report` |
| `bursar` | `students.read`, `finance.*` |
| `librarian` | `students.read`, `library.*` |
| `guardian` | `family.read` |
| `student` | `self.read` |

Roles and permissions are copied into every access token, so policies read them without a lookup.

## Named policies

Instead of repeating conditions on every operation, define them once:

<CodeGroup>
```json staff
{ "role": ["admin", "principal", "teacher", "bursar", "librarian"] }
```
```json school_admin
{ "role": ["admin", "principal"] }
```
```json family_access
{ "any": [
  { "role": ["admin", "principal", "teacher", "bursar", "librarian"] },
  { "owner": "user_id" },
  { "contains": ["$record.guardian_user_ids", "$auth.user_id"] }
] }
```
```json report_access
{ "any": [
  { "role": ["admin", "principal", "teacher", "bursar", "librarian"] },
  { "all": [
    { "eq": ["$record.published", true] },
    { "any": [ { "owner": "user_id" }, { "contains": ["$record.guardian_user_ids", "$auth.user_id"] } ] }
  ] }
] }
```
```json announcement_audience
{ "any": [
  { "role": ["admin", "principal", "teacher", "bursar", "librarian"] },
  { "all": [
    { "authenticated": true },
    { "eq": ["$record.published", true] },
    { "any": [ { "eq": ["$record.audience", "all"] }, { "contains": ["$auth.roles", "$record.audience"] } ] }
  ] }
] }
```
```json report_publisher
{ "all": [ { "authenticated": true }, { "permission": "reports.publish" } ] }
```
</CodeGroup>

In Studio these are built with the rule builder: *Any of* → *Has role* … → *Owns the record* … → *Compare values* `$record.guardian_user_ids` *contains* `$auth.user_id`.

## How the database sees it

When a **teacher** lists students, the engine **plans** `family_access` before querying: the role branch is already true, so the whole `any` is true and the query runs with no extra conditions.

When Chioma (a guardian) lists students:

- the role branch is decided immediately: she has no staff role, so it's false and drops out;
- what remains is `any(owner: user_id, contains guardian_user_ids)`, an **OR** of two record conditions. Only AND-ed equalities can become SQL, so this stays a **residual** checked on each row the query returns, and `total` is `null`.

That's correct and fine at a school's scale. For very large tables, restructure the rule so an AND-ed equality carries the weight, for example a `family_id` column on students and `{"eq": ["$record.family_id", "$auth.claims.app.family_id"]}`, which becomes `WHERE family_id = …`. ## Verified behaviour

These all hold in the finished system, and each is a line in its test script:

<Check>A guardian lists only their own children.</Check>
<Check>A guardian can't open another family's child (`404`).</Check>
<Check>A guardian can't see an unpublished report card, and sees it once published, with `pdf_url` added and `guardian_user_ids` removed by the `report_card_view` transformer.</Check>
<Check>A teacher can't publish report cards (`403`, lacks `reports.publish`).</Check>
<Check>A teacher can't record payments; a bursar can't take registers.</Check>
<Check>Guardians see guardian-audience and all-audience announcements, never drafts.</Check>
<Check>Students see only their own library loans.</Check>

<Warning>
When a field holds a user id that the **office** sets (like `guardians.user_id`), don't make it the owner field. Owner fields are overwritten with whoever writes the row.
</Warning>
