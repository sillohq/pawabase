The backend decides who sees what, so the front end can be simple: sign in, call REST, render. This page shows the patterns the Brightfield portal uses. They apply to any framework.

## Configuration from the environment

Never hard-code connection details. The portal reads them from `.env`:

```bash .env.example
VITE_PAWABASE_URL=http://localhost:8080
VITE_PAWABASE_PUBLISHABLE_KEY=
VITE_SCHOOL_NAME=Brightfield Academy
VITE_CURRENCY=NGN
VITE_LOCALE=en-NG
```

On start it validates them and shows a setup screen instead of failing, including a guard against pasting a **secret** key into a browser app:

```js
if (/(^|_)sk_|secret/i.test(config.key))
  problems.push(["VITE_PAWABASE_PUBLISHABLE_KEY", "this looks like a secret key; use the publishable one"]);
```

## Sign-in and refresh

```js
async function signIn(email, password) {
  const r = await fetch(`${url}/auth/v1/token?grant_type=password`, {
    method: "POST",
    headers: { apikey: key, "Content-Type": "application/json" },
    body: JSON.stringify({ email, password }),
  });
  if (!r.ok) throw await r.json();
  return r.json(); // { access_token, refresh_token, expires_at, user: { roles, ... } }
}
```

Access tokens last 15 minutes by default. Refresh a minute early, and share one in-flight refresh between concurrent requests:

```js
let refreshing = null;
async function freshToken() {
  if (session.expires_at - 60 > Date.now() / 1000) return session.access_token;
  refreshing ||= tokenRequest("refresh_token", { refresh_token: session.refresh_token })
    .then(store).finally(() => (refreshing = null));
  await refreshing;
  return session.access_token;
}
```

## Role-aware navigation, policy-enforced data

The token's `user.roles` decides which screens to show. That's a convenience only: a guardian who types `/finance` gets redirected, and the API would refuse the data anyway.

```js
const isStaff = has("admin", "principal", "teacher", "bursar", "librarian");
const isFinance = has("admin", "principal", "bursar");
```

## Filters use `filter[…]`

List filters are always `filter[field]=value`. A plain `?class_id=7` is **ignored**, a classic bug. A small helper makes it impossible to get wrong:

```js
const RESERVED = new Set(["page", "per_page", "sort", "select", "expand"]);
function rest(path, params) {
  const q = new URLSearchParams();
  for (const [k, v] of Object.entries(params || {}))
    if (v !== undefined && v !== null && v !== "")
      q.set(RESERVED.has(k) ? k : `filter[${k}]`, String(v));
  return `/rest/v1${path}?${q}`;
}
// rest("/invoices", { student_id: 12, status: "in.issued,overdue", sort: "-created_at" })
```

## Calling custom routes

Workflows are just endpoints:

```js
await post("/attendance/register", { class_id: 7, date: "2026-09-28",
  marks: [{ student_id: 12, status: "absent", note: "Unwell" }] });
await post("/finance/payments", { invoice_id: 44, amount: 50000, method: "bank_transfer", reference: "TRX-88121" });
await post(`/report-cards/${id}/publish`, { principal_comment: "A focused term." });
```

Errors come back as JSON with a status the UI can map: `422` (show field errors or the flow's message), `403` (hide the action), `409` (already done).

## What families see

Guardians call the same endpoints as staff: `GET /rest/v1/students` returns only their children, `GET /rest/v1/report_cards` only published cards, `GET /rest/v1/invoices` only their invoices. The portal has no "guardian API". [Client patterns in depth →](/clients/javascript)
