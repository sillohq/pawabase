Files are uploaded to Pawabase storage using `POST /storage/v1/<bucket>/<key>`. The gateway checks the bucket's write policy before forwarding the file to the configured driver.

There are two upload patterns:

1. **Direct upload** — your server or a trusted backend calls the storage API directly.
2. **Signed URL** — your server generates a time-limited URL, and the client uploads directly to storage without routing through your server.

There is no multipart upload protocol, and there is no separate Python storage SDK — uploads go through the same HTTP gateway all other requests use.

## Direct upload

Send the file as the request body with the appropriate `Content-Type`:

```bash
curl -X POST "$GW/storage/v1/avatars/usr_abc/photo.jpg" \
  -H "apikey: $SK" \
  -H "Content-Type: image/jpeg" \
  --data-binary @photo.jpg
```

Using a secret key (`$SK`) bypasses the bucket's write policy entirely. Use a publishable key plus a user token when you want the policy applied:

```bash
curl -X POST "$GW/storage/v1/documents/reports/q3-2026.pdf" \
  -H "apikey: $PK" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/pdf" \
  --data-binary @q3-2026.pdf
```

On success the API returns `200 OK` with the object key:

```json
{ "key": "reports/q3-2026.pdf", "bucket": "documents" }
```

### Upload limits

- The global maximum upload size is `PAWABASE_MAX_UPLOAD_BYTES` (default: 50 MB).
- A bucket's `max_size` provides a per-bucket ceiling below the global limit.
- A bucket's `allowed_types` checks the `Content-Type` header. A mismatched type returns `415 Unsupported Media Type`.

## Signed URL uploads (client-side)

When a browser or mobile app needs to upload a file, the recommended pattern is:

1. The client asks your backend (or a flow) for a signed upload URL.
2. The backend generates the URL with the `storage.signed_url` flow block.
3. The client uploads the file directly to the returned URL.
4. The client notifies your backend that the upload is complete (typically a resource update).

This keeps credentials off the client while letting the client upload without proxying through your server.

### Generating a signed upload URL from a flow

```json
{
  "id": "get_upload_url",
  "data": {
    "block": "storage.signed_url",
    "config": {
      "bucket": "avatars",
      "key": "{{ auth.user_id }}/avatar.jpg",
      "method": "PUT",
      "expires_in": 300
    }
  }
}
```

| Field | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `bucket` | string | Yes | — | The bucket name |
| `key` | string | Yes | — | The object key (path within the bucket) |
| `method` | `"GET"` or `"PUT"` | No | `"GET"` | `"PUT"` for an upload URL |
| `expires_in` | integer (seconds) | No | `3600` | How long before the URL expires |

The block output is `{ "url": "<signed_url>", "expires_at": "<timestamp>" }`.

### Client-side upload using the signed URL

```javascript
// 1. Request a signed upload URL from your backend
const { url } = await fetch('/api/upload-url', {
  method: 'POST',
  body: JSON.stringify({ filename: 'photo.jpg', content_type: 'image/jpeg' })
}).then(r => r.json());

// 2. Upload the file directly to storage
await fetch(url, {
  method: 'PUT',
  headers: { 'Content-Type': 'image/jpeg' },
  body: file
});

// 3. Notify your backend
await fetch('/api/update-avatar', {
  method: 'POST',
  body: JSON.stringify({ key: 'usr_abc/avatar.jpg' })
});
```

The signed URL is pre-authorized for one specific key with one specific method. It cannot be used for a different key, and it expires after `expires_in` seconds.

## Upload from a flow

The `storage.put` block writes content directly to storage from within a flow:

```json
{
  "id": "save_export",
  "data": {
    "block": "storage.put",
    "config": {
      "bucket": "exports",
      "key": "reports/{{ input.event.payload.month }}.csv",
      "content": "{{ steps.generate_csv.output.data }}",
      "content_type": "text/csv"
    }
  }
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `bucket` | string | Yes | The bucket name |
| `key` | string | Yes | The object key |
| `content` | string or bytes | Yes | The content to store |
| `content_type` | string | No | MIME type |

`storage.put` runs with service rights — it bypasses the bucket's write policy. If you need the policy applied inside a flow, add an explicit `policy.check` block before it.

## Object keys

Object keys are the full path within a bucket, separated by `/`. Keys are arbitrary strings — there are no "directories," just key prefixes:

- `avatars/usr_abc/photo.jpg`
- `exports/2026/10/report.csv`
- `documents/contract-001.pdf`

Keys are case-sensitive. Uploading to the same key overwrites the existing object — there is no versioning.
