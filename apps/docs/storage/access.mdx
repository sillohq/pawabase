Every storage operation is checked against the bucket's `read_policy` (for downloads) or `write_policy` (for uploads) before anything reaches the driver. The policy language is the same JSON condition language used for resource operations — the same operators, shorthands, and context.

## Policy context for storage

In addition to `$auth`, `$credential`, and `$request`, storage policies have access to `$object`:

| Path | Contents |
| --- | --- |
| `$object.key` | The full object key, e.g. `avatars/usr_abc/photo.jpg` |
| `$object.segments` | Array of key path segments, split on `/` — e.g. `["avatars", "usr_abc", "photo.jpg"]` |
| `$object.action` | `"read"` or `"write"` |

The `$object` context is only available in storage policies, not in resource policies.

## Correct condition operators

Storage policies use the same operators as all other policies in Pawabase:

| Operator | Meaning |
| --- | --- |
| `eq` | Equal |
| `ne` | Not equal |
| `in` | Value is in a list |
| `not_in` | Value is not in a list |
| `truthy` | Value is non-empty and non-null |
| `exists` | Value is not null |
| `all` | All sub-conditions true (logical AND) |
| `any` | At least one sub-condition true (logical OR) |
| `not` | Negates a condition |

<Warning>
The correct combinator names are `all` and `any` — **not** `and` or `or`. The correct inequality operator is `ne` — **not** `neq`. Using the wrong names causes a `422 Unprocessable Entity` when saving the policy.
</Warning>

## Common access patterns

### Public read, authenticated write

Suitable for product images, public assets:

```json
{
  "read_policy": "public",
  "write_policy": "authenticated"
}
```

### Authenticated read and write

Suitable for shared documents within a signed-in user pool:

```json
{
  "read_policy": "authenticated",
  "write_policy": "authenticated"
}
```

### Owner-scoped write

Each user can write only to keys that start with their own user id. This is the standard pattern for user-uploaded files:

```json
{
  "write_policy": {
    "all": [
      { "truthy": "$auth.user_id" },
      { "eq": ["$object.segments.0", "$auth.user_id"] }
    ]
  }
}
```

With keys structured as `<user_id>/<filename>` (e.g. `usr_abc/avatar.jpg`), `$object.segments.0` is the user id portion. This ensures a signed-in user can only write to their own prefix.

For owner-scoped read:

```json
{
  "read_policy": {
    "all": [
      { "truthy": "$auth.user_id" },
      { "eq": ["$object.segments.0", "$auth.user_id"] }
    ]
  }
}
```

### Role-restricted bucket

Only users with a specific role can access the bucket:

```json
{
  "read_policy": { "role": ["finance", "admin"] },
  "write_policy": { "role": "admin" }
}
```

### Service-only write

Only flows or server-side callers with a secret key can write. Authenticated users can read:

```json
{
  "read_policy": "authenticated",
  "write_policy": { "service": true }
}
```

This is the right pattern for system-generated exports, backups, and reports that users should be able to download but never upload to.

### Organization-scoped bucket

Within a multi-tenant app where `$auth.org` is the organization id, objects are scoped per org by key prefix:

```json
{
  "write_policy": {
    "all": [
      { "truthy": "$auth.org" },
      { "eq": ["$object.segments.0", "$auth.org"] }
    ]
  },
  "read_policy": {
    "all": [
      { "truthy": "$auth.org" },
      { "eq": ["$object.segments.0", "$auth.org"] }
    ]
  }
}
```

Objects are keyed `<org_id>/<filename>`. Users in `org_abc` can read and write `org_abc/<filename>` but not `org_xyz/<filename>`.

## Policy references

The same policy-reference forms that resources accept are also valid for bucket policies:

```json
"read_policy": "authenticated"           // named shorthand
"read_policy": "public"                  // named shorthand
"read_policy": "service"                 // named shorthand
"read_policy": { "role": "admin" }       // inline condition
"read_policy": ["mfa", "role:admin"]     // list (AND-ed)
"read_policy": null                      // defaults to authenticated
```

See [Policies → shorthands](/policies/shorthands) for the full list of named references.

## How a storage policy refusal looks

A read policy refusal returns `404 Not Found` — the same as a missing object — to avoid revealing whether the key exists. A write policy refusal returns `403 Forbidden`.

## Debugging access policies

If a download returns `404` and the object definitely exists:

1. Try the request with a secret key (`apikey: <secret key>`) — if it succeeds, the issue is the policy.
2. In Studio's **Observability → Requests**, find the failed request and check the `notes.pawabase.policy` field.
3. Compare `$object.key`, `$object.segments`, and `$auth` against the condition in the policy.
