**Access** in Pawabase storage is governed by per-bucket `read_policy` and `write_policy` JSON conditions. Every operation on a bucket — read, list, upload, delete, and signed URL generation — is evaluated against the relevant policy. The policy engine uses the same condition language that guards resources, routes, and realtime channels.

## Policy structure

Every bucket has two policies:

```json
{
  "name": "receipts",
  "read_policy": {
    "all": [
      {"authenticated": true},
      {"eq": ["$object.segments.0", "user"]}
    ]
  },
  "write_policy": {
    "all": [
      {"authenticated": true},
      {"in": ["$auth.roles", ["admin", "finance_staff"]]}
    ]
  }
}
```

The policy language supports the full set of conditions from the [Policy engine](/policies/conditions): `all`, `any`, `not`, `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `not_in`, `contains`, `starts_with`, `ends_with`, `matches`, `authenticated`, `role`, `permission`, `owner`, `service`, `kind`, `scope`, `aal`, and more.

## The $object variable

Storage policies have access to a special `$object` variable that provides information about the object being accessed:

```json
{
  "object": {
    "key": "user/8/receipts/inv-04.pdf",
    "segments": ["user", "8", "receipts", "inv-04.pdf"],
    "action": "read"
  }
}
```

This means you can write path-based access policies. For example, to restrict users to their own directory:

```json
{
  "read_policy": {
    "all": [
      {"authenticated": true},
      {"eq": ["$object.segments.0", "user"]},
      {"eq": ["$object.segments.1", "$auth.user_id"]}
    ]
  }
}
```

This policy requires that the user's ID matches the second segment of the object key, so user `8` can only access `user/8/...`.

## Policy evaluation

The `PolicyStorage` adapter evaluates the policy against an `PolicyEngine`. The evaluation context includes `auth`, `credential`, `project`, `env`, `object`, and `input`:

```python
context = {
    "auth": policy_auth(user),
    "credential": self.credential,
    "project": self.project,
    "env": self.env,
    "object": {"key": key, "segments": key.split("/"), "action": name},
    "input": input,
}
return evaluate(policy.condition, context)
```

Service credentials (`is_service: true`) always pass the policy check. This is how flows, scheduled jobs, and server-side code can write to any bucket regardless of the bucket's own `write_policy`.

```python
def allows(self, action, key, user=None) -> bool:
    if self.credential.get("is_service"):
        return True
    ...
```

## Scopes

API keys can carry scopes that further restrict what operations they can perform. Scopes are checked by the `PolicyGate` before the policy is even evaluated:

```python
if self.scope_required and platform is not None:
    if not platform.allows_scope(self.scope_required):
        raise PermissionDenied(f"This API key lacks the {self.scope_required!r} scope")
```

Common scopes for storage include `storage:read`, `storage:write`, and `storage:delete`. A key without the required scope is rejected before any policy evaluation occurs.

## Signed URL access

Signed URLs bypass the bucket's policies through a separate mechanism. When you create a signed URL with `storage.signed_url`, the URL itself carries the authorization. The recipient doesn't need a Pawabase API key — the signature is the credential.

```json
{
  "signed_url": "https://<api host>/storage/v1/signed/<bucket>/<key>?sig=..."
}
```

Whether signed URLs grant reads or writes is controlled by the bucket's `signed_reads` and `signed_writes` flags in `PolicyStorage`. Both default to `true`.

<Warning>
Signed URLs are time-limited (default 300 seconds). Always generate a fresh signed URL for each operation. Don't embed long-lived signed URLs in client-side code or shared documents.
</Warning>
