A **bucket** is a named container within an environment's storage. Each bucket has its own access policies and upload constraints, all sharing the same underlying storage driver configured at the environment level.

## Creating a bucket in Studio

1. Open your project and environment in Studio.
2. Navigate to **Build → Storage**.
3. Click **New bucket**.
4. Configure the fields below.
5. Save.

The bucket is immediately available for use.

## Bucket schema

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `name` | string | Yes | Bucket identifier. Lowercase, alphanumeric, hyphens. Unique within the environment. |
| `read_policy` | policy reference | No | Who can read (download) objects. Defaults to `authenticated`. |
| `write_policy` | policy reference | No | Who can upload objects. Defaults to `authenticated`. |
| `max_size` | integer | No | Maximum object size in bytes. No limit if omitted. |
| `allowed_types` | array of strings | No | Accepted MIME types. All types accepted if omitted. |

<Warning>
There is no `driver` field on a bucket. The storage driver (local, s3, or memory) is configured at the **environment** level under **Settings → Infrastructure → Storage** — all buckets in an environment share one driver. A per-bucket `driver` field does not exist and is not accepted.
</Warning>

## Access policies

`read_policy` and `write_policy` accept the same policy references that resources accept: a named policy, a policy shorthand, or an inline condition:

```json
"read_policy": "authenticated"
"write_policy": { "owner": "user_id" }
"read_policy": { "role": ["admin", "support"] }
```

The full policy context available to storage policies includes `$auth`, `$credential`, `$request`, and `$object`. The `$object` key provides:

| Path | Contents |
| --- | --- |
| `$object.key` | The full object key (e.g. `avatars/usr_abc/photo.jpg`) |
| `$object.segments` | Array of the key split on `/` (e.g. `["avatars", "usr_abc", "photo.jpg"]`) |
| `$object.action` | `"read"` or `"write"` |

This lets you write ownership-scoped policies like:

```json
{
  "all": [
    { "truthy": "$auth.user_id" },
    { "eq": ["$object.segments.1", "$auth.user_id"] }
  ]
}
```

…which requires the second path segment (index `1`) of the key to match the caller's user id — enforcing that `avatars/usr_abc/photo.jpg` is only writable by `usr_abc`.

See [Access](/storage/access) for the full policy context and more examples.

## Upload constraints

`max_size` and `allowed_types` are enforced at the gateway before the object reaches the driver:

```json
{
  "name": "documents",
  "max_size": 10485760,
  "allowed_types": ["application/pdf", "application/msword", "application/vnd.openxmlformats-officedocument.wordprocessingml.document"]
}
```

`max_size` is in bytes. `allowed_types` is a list of exact MIME type strings — the gateway checks the `Content-Type` header on upload. If the content type doesn't match, the request is rejected with `415 Unsupported Media Type`.

## Example bucket definitions

### Public read, authenticated write

```json
{
  "name": "product-images",
  "read_policy": "public",
  "write_policy": { "role": "staff" }
}
```

### Owner-scoped avatars

```json
{
  "name": "avatars",
  "read_policy": "public",
  "write_policy": {
    "all": [
      { "truthy": "$auth.user_id" },
      { "eq": ["$object.segments.0", "$auth.user_id"] }
    ]
  },
  "max_size": 2097152,
  "allowed_types": ["image/jpeg", "image/png", "image/webp"]
}
```

Objects are stored at keys like `<user_id>/avatar.jpg`. The write policy ensures a user can only write to keys starting with their own id.

### Admin-only private documents

```json
{
  "name": "invoices",
  "read_policy": { "role": ["finance", "admin"] },
  "write_policy": { "role": ["finance", "admin"] }
}
```

### Large file exports

```json
{
  "name": "exports",
  "read_policy": "authenticated",
  "write_policy": { "service": true },
  "max_size": 104857600
}
```

`"service": true` means only service credentials (flows running with service rights, or a secret key) can write. Authenticated users can read. This is the standard pattern for system-generated exports.

## Managing buckets via the Platform API

```bash
# Create a bucket
curl -X POST "$STUDIO/studio/api/platform/projects/acme/envs/production/storage/buckets" \
  -H "content-type: application/json" -H "X-XSRF-TOKEN: $XSRF" -b cookies.txt \
  -d '{
    "name": "avatars",
    "read_policy": "public",
    "write_policy": { "truthy": "$auth.user_id" },
    "max_size": 2097152,
    "allowed_types": ["image/jpeg", "image/png", "image/webp"]
  }'

# List buckets
curl "$STUDIO/studio/api/platform/projects/acme/envs/production/storage/buckets" \
  -H "X-XSRF-TOKEN: $XSRF" -b cookies.txt

# Delete a bucket (does not delete existing objects)
curl -X DELETE "$STUDIO/studio/api/platform/projects/acme/envs/production/storage/buckets/avatars" \
  -H "X-XSRF-TOKEN: $XSRF" -b cookies.txt
```

Deleting a bucket definition removes the bucket's configuration but does not delete the objects already stored in it. Objects must be deleted separately through the storage API or directly in the driver.

## Bucket names

Bucket names must be lowercase alphanumeric with hyphens, and unique within the environment. A bucket named `user-uploads` in `development` is independent from `user-uploads` in `production` — they share no objects and can have different policies.
