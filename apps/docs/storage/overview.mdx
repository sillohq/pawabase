**Storage** in Pawabase holds files — images, PDFs, exports, documents, and any other binary content your application needs. It is organized into **buckets**: named containers, each with its own access policy and configured on the environment's storage driver.

## How storage works

Storage in Pawabase sits behind the same gateway as the REST API. All storage requests go through `POST /storage/v1/<bucket>/<key>` (uploads) and `GET /storage/v1/<bucket>/<key>` (downloads). The gateway:

1. Resolves the API key to identify the environment.
2. Checks authentication: who is calling.
3. Evaluates the bucket's read or write policy.
4. Forwards the request to the configured storage driver.

The policy evaluation uses the same engine as resource policies — the same operators, shorthands, and `$auth` context. A storage bucket is not automatically public: you configure access explicitly.

## The storage driver is environment-level

The storage driver — where files physically live — is configured on the environment's `infra` settings, not on individual buckets. All buckets in an environment share the same underlying driver and its configuration (endpoint URL, region, credentials). What differs per bucket is the **access policy**: who can read and write each bucket's objects.

Three drivers are supported:

| Driver | Description |
| --- | --- |
| `local` | Files stored on the local filesystem. For development and single-server deployments. |
| `s3` | Any S3-compatible storage: AWS S3, MinIO, Tigris, Cloudflare R2, DigitalOcean Spaces. |
| `memory` | In-process, non-persistent. For tests only. |

There is no Google Cloud Storage or Azure Blob driver. See [Drivers](/storage/drivers) for configuration.

## Buckets

A bucket is a named container. You create buckets in Studio under **Build → Storage → New bucket** or through the Platform API. Each bucket has:

- A unique name within the environment.
- A `read_policy` — who can read (download) objects.
- A `write_policy` — who can write (upload) objects.
- Optional `max_size` — maximum object size in bytes.
- Optional `allowed_types` — list of accepted MIME types.

The driver, endpoint, and credentials are shared across all buckets in the environment. See [Buckets](/storage/buckets) for the full schema and configuration reference.

## Access control

Every storage operation is checked against the bucket's policy before reaching the driver. The policy language is the same JSON condition language used for resources:

```json
{ "truthy": "$auth.user_id" }
```

```json
{ "owner": "user_id" }
```

```json
{ "role": "admin" }
```

The `$object` context is also available in storage policies — it contains the key, key segments (the slash-separated parts of the object path), and the action (`read` or `write`). This lets you write policies like "a user can only read their own objects" by checking `$object.segments.0` against `$auth.user_id`.

See [Access](/storage/access) for the complete storage policy context and examples.

## Signed URLs

For client-side uploads and downloads, use signed URLs rather than exposing credentials in the browser. A signed URL is a time-limited URL that grants access to one specific object without requiring an API key or user token.

Generate signed URLs from a flow using the `storage.signed_url` block, or through the storage API. See [Downloads](/storage/downloads) and [Uploads](/storage/uploads) for the client-facing patterns.

## Flow integration

Four blocks give flows direct access to storage:

| Block | Purpose |
| --- | --- |
| `storage.put` | Write an object (store a file, save an export) |
| `storage.read` | Read an object's contents |
| `storage.signed_url` | Generate a time-limited signed URL for read or write |
| `storage.delete` | Delete an object |

Storage blocks run with service rights — they bypass the bucket's access policy. If a flow should respect the caller's access rights, add an explicit `policy.check` before the storage block.

## Common patterns

**User avatar upload:** A client requests a signed upload URL from a flow. The flow generates a URL scoped to `avatars/<user_id>/avatar.jpg` and returns it. The client uploads directly to storage using the URL. A resource update records the object key.

**Report export:** A scheduled flow generates a report, `storage.put`s it to a `reports` bucket, then `storage.signed_url` creates a download link sent by email.

**Document processing:** A flow triggered by a resource event reads a document from storage with `storage.read`, processes it, and stores the result.
