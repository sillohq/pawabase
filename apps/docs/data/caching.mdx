Reads that are hot and change rarely (a catalogue, a timetable, a calendar) can be cached with one setting.

## Turning it on

```json
{ "name": "calendar_events", "cache_ttl": 300 }
```

`cache_ttl` is in seconds, from 0 (off) to 86400. It applies to `list` and `get`. Custom routes have the same setting.

## How it's keyed

The cache key includes the **caller's identity**, the **key role**, the operation and the full query (filters, sort, page, select, expand). Two users never share a cached response, so caching can't leak rows across policies.

## Invalidation

Every write to a resource (through the API, Studio, flows or functions) invalidates everything tagged with that resource. Entries otherwise expire after `cache_ttl`.

<Note>
An `expand`ed response is tagged with the **parent** resource. If you cache a list that expands a frequently changing relation, keep the TTL short or don't cache it.
</Note>

## Where it's stored

The API uses Sillo's cache: Redis when `PAWABASE_REDIS_URL` is set (shared by every API instance), in-memory otherwise. Studio's **Observability → Cache** shows hit rates; `POST /platform/v1/projects/{ref}/envs/{env}/cache/invalidate` with `{"tags": ["calendar_events"]}` clears by tag.

## Caching in flows

Flows have explicit cache blocks for expensive lookups:

```text
cache.get key="rates:{{ input.body.currency }}"
  miss → http.request … → cache.set key=… value={{ steps.fetch.output }} ttl=3600 tags=["rates"]
```

and `cache.invalidate` to clear tags when source data changes. [Platform blocks →](/flows/platform-blocks)

## When not to cache

- Personal, fast-changing data (a user's own todo list): the per-caller key gives few hits.
- Anything whose correctness depends on seeing the latest write from another user immediately.
