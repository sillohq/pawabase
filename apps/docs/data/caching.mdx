Every `list` and `get` response on a resource is cached to reduce database load and improve latency. Caching is automatic and transparent to your application, but the cache key includes the caller's identity and policy scope, so different users see their own cached results.

## How caching works

The platform caches responses at the API layer, keyed by:

```text
resource name + operation + filters + sort + pagination + caller's auth context
```

This means:
- Two users with different policies get **different cache entries** — a user can never see another user's cached data.
- The same authenticated user requesting the same `list` with the same filters gets the cached response.
- Changes to the query parameters (different page, different sort, additional filter) produce a cache miss.

<Card title="Cache scope">
The cache is **per API instance**. If you run multiple API replicas, each has its own cache. Cache invalidation (described below) is broadcast through the event bus so all instances invalidate together.
</Card>

## When the cache is invalidated

The cache is automatically invalidated whenever a write operation succeeds on the same resource:

| Write operation | Invalidates |
| --- | --- |
| `resource.create` on `todos` | All `list` cache entries for `todos` |
| `resource.update` on `todos` (id=42) | All `list` and `get` cache entries for `todos` |
| `resource.delete` on `todos` (id=42) | All `list` and `get` cache entries for `todos` |

<Note>
Invalidation is **per resource**, not per record. Updating one todo invalidates the cache for the entire `todos` resource, including all other users' cached list results. This is deliberate: policies can join across records, so a change to one record might affect another user's policy results.
</Note>

## Configuring caching per resource

You can configure caching in Studio:

1. Open the resource in Studio (Data → Resources → *resource name*).
2. Go to the **Caching** tab.

| Setting | Default | What it controls |
| --- | --- | --- |
| `enabled` | On | Whether `list` and `get` responses are cached. |
| `ttl` | 60 seconds | How long a cached response is considered fresh before the platform checks the database for changes. |
| `max_entries` | 1000 | Maximum number of cache entries per resource. When exceeded, the oldest entries are evicted. |

<Warning>
The `list` operation's `total` field is cached alongside the data. If a policy uses row-by-row evaluation (non-pushdown), the cache can't guarantee an exact count — see [Policies → Pushdown](/policies/pushdown) for details on when counts are cached vs. computed fresh.
</Warning>

## Bypassing the cache

In certain situations you need fresh data:

### Query parameter (on individual requests)

Append `?cache=false` to any `list` or `get` request:

```bash
curl "https://api.your-app.pawabase.io/rest/v1/invoices?cache=false" \
  -H "apikey: $PK" -H "Authorization: Bearer $TOKEN"
```

### Resource configuration (always bypass)

Set `caching.enabled = false` in the resource's Caching tab to disable caching for that resource permanently. This is useful for resources with highly volatile data where the cache invalidation overhead outweighs the benefit.

<Info>
The cache does **not** apply to `create`, `update`, or `delete` operations — those always hit the database directly. Only read operations (`list` and `get`) are cached.
</Info>

## Cache and policies

The cache key includes the caller's resolved auth context. This means:

- An authenticated user and an anonymous user get **separate cache entries** for the same resource.
- Two users with different roles get **separate cache entries**.
- If a user's roles change (e.g., via the refresh flow), their old cache entries are automatically invalidated.

However, if a policy condition reads from an **external source** (like a function call or HTTP request), the cache cannot detect changes to that source. Cache invalidation only fires on writes to the same resource. If your policy depends on external data that changes outside Pawabase, use `?cache=false` or set a short TTL.

## Performance considerations

| Scenario | Recommendation |
| --- | --- |
| Frequently read, rarely written | Enable caching with a long TTL (300s or more). |
| Frequently written | Keep TTL short (10–30s) — cache invalidation on every write can cause thundering herd. |
| Highly personalized data (per-user) | Caching helps less — each user has their own cache entry. Use it mainly for reducing database load on repeated reads. |
| Count queries with row-by-row policies | Consider whether you need exact counts. If not, caching saves repeated expensive evaluation. |
