A **custom route** is an HTTP endpoint under `/rest/v1/<path>` that you define yourself, rather than one of the five standard resource CRUD routes. Custom routes let you expose actions, composite operations, or shaped responses that don't map cleanly to `list`/`get`/`create`/`update`/`delete`.

Like everything else in Pawabase, custom routes are definitions stored per environment — you create and edit them in Studio, promote them between environments, and they compile into your running API instantly.

## When to use a custom route

| Use case | Example |
| --- | --- |
| **Non-CRUD actions** | `POST /rest/v1/orders/{id}/refund` — refund an order, which touches multiple tables |
| **Batch operations** | `POST /rest/v1/users/bulk-import` — accept a CSV, validate, and create many records |
| **Composite endpoints** | `GET /rest/v1/dashboard/summary` — aggregate data from 3+ resources into one response |
| **External integrations** | `POST /rest/v1/webhooks/stripe` — receive a Stripe webhook, validate it, and emit an event |
| **Shaped responses** | `GET /rest/v1/reports/daily` — return data in a format optimized for a specific chart |

<Note>
For simple single-resource operations, prefer the standard resource routes. Custom routes are for when the standard five operations don't fit. See [Extension routes](/code/extension-routes) for full Python handler routes when you need complete control.
</Note>

## How to create a custom route in Studio

1. Open your project in Studio.
2. Go to **Data → Custom routes**.
3. Click **New route**.

| Field | What it controls |
| --- | --- |
| **Path** | The URL segment after `/rest/v1/`. E.g., `orders` makes the route `POST /rest/v1/orders`. Use `{param}` for path parameters. |
| **Method** | The HTTP verb: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`. |
| **Handler type** | What handles the request: a **Flow**, a **Function**, or **Schema-only** (for documentation-only routes). |
| **Input schema** | (Optional) A schema to validate the request body against. Required for `POST`/`PUT`/`PATCH`. |
| **Output schema** | (Optional) A schema the response is validated against. |
| **Policy** | The condition that decides whether the caller may access this route. |

### Path parameters

Routes support path parameters in the format `{param}`:

```
POST /rest/v1/orders/{order_id}/refund
```

Path parameters are available in the route's input as `params.order_id`.

## Route execution model

When a request hits a custom route, the platform:

1. **Validates** the request body against the input schema (if configured).
2. **Resolves the context** — the caller's identity, API key, and scopes.
3. **Evaluates the policy** — the same JSON condition language used everywhere else in Pawabase.
4. **Dispatches** — to the configured handler (flow or function).
5. **Returns** the response, validated against the output schema (if configured).

```text
Request
   ↓
Validate input (schema)
   ↓
Resolve auth context
   ↓
Policy check (condition)
   ↙              ↘
false               true
 ↓                  ↓
403               Handler (flow or function)
                        ↓
                  Validate output (schema)
                        ↓
                  Response
```

## Policies on custom routes

Every custom route requires a policy. The policy uses the same condition syntax as resource policies — see [Expressions](/concepts/expressions) for the full reference.

Example: only authenticated users can call a route:

```json
{ "truthy": "$auth.user_id" }
```

Example: only finance staff can access a route:

```json
{ "in": ["finance", "$auth.roles"] }
```

The condition has access to:
- `$auth` — the caller's identity and claims
- `$input` — the request body, query parameters, and path parameters
- `$env` — environment variables

## Handler types

### Flow handler

A flow handler runs a named flow when the route receives a request. The flow receives the request data as `$input` and returns whatever the flow's last step produces.

To configure: select the route in Studio, set **Handler type** to **Flow**, and choose the flow from the dropdown.

**Input shape** passed to the flow:
```json
{
  "method": "POST",
  "path": "/rest/v1/orders/{id}/refund",
  "params": { "id": "ord_123" },
  "query": {},
  "headers": { "content-type": "application/json" },
  "body": { "reason": "customer cancelled" }
}
```

In the flow, you can access these with expressions like `$input.body.reason` or `$input.params.id`.

### Function handler

A function handler calls a Python function registered via `@function`. The function receives a `FunctionContext` with the request data.

To configure: select the route in Studio, set **Handler type** to **Function**, and enter the function name.

### Schema-only handler

A schema-only route declares the input/output schemas but doesn't run any handler. This is useful for documenting endpoints that are handled by an external service (for example, a route handled by a CDN in front of Pawabase).

## Testing custom routes

You can test a route directly with `curl`:

```bash
curl -X POST http://localhost:8080/rest/v1/orders/ord_123/refund \
  -H "apikey: $PROJECT_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason": "customer cancelled"}'
```

Or from the **Routes** tab in Studio, where you can see the compiled OpenAPI definition, try the endpoint interactively, and inspect the execution trace.

## Custom routes vs. extension routes

| Feature | Custom route | Extension route |
| --- | --- | --- |
| Configured in Studio | Yes | No |
| Promotable between environments | Yes | No (it's code) |
| Handler language | Flow or any registered function | Python only |
| Full framework access | No | Yes |
| Best for | API endpoints, integrations | Complex request handling, streaming, middleware |

For most use cases, custom routes are the right choice. See [Extension routes](/code/extension-routes) for when you need full Python/Sillo router access.
