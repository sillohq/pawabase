## The mental model: an endpoint you define, run by a flow or a function

A [resource](/data/resources) gives you five operations on one table. A **custom route** is any other endpoint: refund an order, assemble a dashboard from three resources, accept a third party's callback, run a calculation. You choose the method and the path, say who may call it, and name what runs: a **flow** (built in Studio) or a **function** (Python in your project's code).

```text
request ──► rate limit ──► body validation ──► scope and plan-time policy ──► cache ──► full policy ──► handler ──► transformer ──► response
```

A route is a definition stored per environment, like everything else in Pawabase. It compiles into a live endpoint when the environment's definitions change, with no separate deploy for the route itself. The flow it names is also a definition, so a flow-backed route can be built, changed and promoted entirely in Studio.

| | Resource operations | Custom route |
| --- | --- | --- |
| **Shape** | Fixed: list, get, create, update, delete | Any method and path |
| **What answers** | The platform's data layer | A flow or a function |
| **Validation** | The resource's fields | `input_fields` or `input_schema` you choose |
| **Policy** | Per operation | One policy per route |
| **Caching** | `list` and `get` | `GET` routes |
| **Documentation** | Generated from the fields | Generated from the route's own settings |

Everything on this page was run against a real Pawabase API: flows were created and called, functions were loaded from a code directory, and the responses below are what came back. Where the behavior is read from code and not run, it says so.

## Where a route lives in Studio

Open **Build → Routes**. The page is described as *Custom endpoints under /rest/v1, handled by a flow or a Python function.* and lists each route with its **method**, **path**, **handler type** and **handler**. Create one with the new-route button; the sheet is titled **New route**.

| Section | Field | What it means |
| --- | --- | --- |
| **Endpoint** | **Method and path** | A method select (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`), the fixed prefix `/rest/v1`, and the path, with the placeholder `/checkout`. Hint: *Served under /rest/v1. Use* `{param}` *for path parameters.* |
| | **Name** (optional) | Hint: *The operation id in OpenAPI.* It is the summary in the generated documentation |
| | **Description** (optional) | Shown in the documentation |
| | **Enabled** | Hint: *Disabled routes answer 404.* |
| **Handler** | **Type** | **Flow** or **Function**. Description: *What runs when the endpoint is called.* |
| | **Flow** / **Function** | A select of the flows (or a text box for a function name). With no flows it says *No flows yet; type a name.* |
| **Access** | The policy picker | Who may call it |
| **Request & response** | **Request body** | Three choices: **Anything**, **Define fields**, **Use a schema** |
| | **Response schema** (optional) | A stored schema, documentation only (see below) |
| | **Transformer** (optional) | A stored transformer applied to the result |
| **Limits** | **Rate limit** | A switch. Hint: *Per caller, counted across all gateway instances.* |
| | **Cache responses** | 0 to 86,400 seconds |
| | **Tags** (optional) | Groups the endpoint in the API docs |

The footer has **Delete**, **Cancel** and a primary button (**Create route** or **Save changes**), and the hint beside them names what is missing, such as *Choose a handler.*

## The shape of a route definition

Through the platform API, a route is one JSON object:

```http
POST /platform/v1/projects/acme/envs/production/routes
```

```json
{
  "method": "POST",
  "path": "/orders/{id}/refund",
  "name": "Refund an order",
  "description": "Reverses a payment and restores stock.",
  "handler_type": "flow",
  "handler": "refund_order",
  "policy": { "in": ["finance", "$auth.roles"] },
  "input_fields": [
    { "name": "reason", "type": "string", "required": true, "max_length": 200 }
  ],
  "rate_limit": { "limit": 30, "window": 60 },
  "cache_ttl": 0,
  "tags": ["orders"],
  "enabled": true
}
```

| Field | Value | Default | Notes |
| --- | --- | --- | --- |
| `method` | `GET`, `POST`, `PUT`, `PATCH`, `DELETE` | `POST` | Anything else is a `422` |
| `path` | A path starting with `/` | | See [paths](#paths) |
| `handler_type` | `flow` or `function` | `flow` | Anything else is a `422` |
| `handler` | The flow's or function's name | | Not checked when you save |
| `policy` | A stored policy name, an inline condition, or `null` | `authenticated` | `null` means **authenticated**, so a route is never public by accident |
| `input_fields` | A field list | none | Validates the body, with required fields enforced |
| `input_schema` | A stored schema name | none | Validates the body, with `required` **not** enforced |
| `response_schema` | A stored schema name | none | Documentation only |
| `transformer` | A stored transformer name, or an inline definition | none | Reshapes the result |
| `rate_limit` | `{"limit": n, "window": seconds}` | none | Per caller |
| `cache_ttl` | 0 to 86,400 | `0` | `GET` routes only |
| `name`, `description`, `tags` | Text | empty | OpenAPI only |
| `enabled` | `true` or `false` | `true` | |

A route is unique by **method and path** within an environment, so `GET /count` and `POST /count` can both exist, and creating a second `GET /count` is refused with a `409` and `route already exists`.

The saved route comes back with the same fields, an `id`, timestamps and its environment, which is also what the list endpoint returns for each route.

## Paths

A route is served at `/rest/v1` followed by its path, so a route with the path `/orders/{id}/refund` answers at `/rest/v1/orders/{id}/refund`.

### What a path may look like

The path is checked when you save, and an invalid one is a `422` with the message `path must look like /orders/{id}/pay`. These were all run:

| Path | Accepted? |
| --- | --- |
| `/echo/{id}` | Yes |
| `/V1.2/Items-x_y` | Yes. Letters of either case, digits, dots, dashes and underscores are fine |
| `/files/{rest:path}` | Yes. `:path` lets one trailing parameter capture the rest of the path, slashes included |
| `/things/{id}/restock` | Yes |
| `x3` | No. It must start with `/` |
| `/bad path` | No. No spaces |
| `/x4/` | No. No trailing slash |

A segment in braces is a **path parameter**. Its name must be a valid identifier (a letter or underscore, then letters, digits or underscores).

### Paths that would shadow a resource

A route may not sit where a resource's own endpoints are. With a `things` resource, all of these are refused with `the path would shadow a resource's own routes (/<resource> or /<resource>/{id})`, whatever the method:

| Path | Result |
| --- | --- |
| `/things` | Refused |
| `/things/{id}` | Refused |
| `/things/{id}/restock` | **Accepted.** It is a different path |
| `/things/summary` | Accepted, and a request to it reached the route in a run. Still, `summary` is a value an id could take, so avoid a fixed segment where a record id could be |

The check is against the **resources that exist when you save the route**. If a resource is created **afterwards** at the same path, the save is not refused, and the **resource wins**: a `GET /later` route and then a `later` resource gave a `200` list from the resource, and the Overview listed `route GET /later: shadows a resource route` under definitions with problems. The route is silently unreachable until you rename one of them. Create resources first, and check the Overview after adding either.

### What the generated documentation shows

Each route becomes an operation in the environment's OpenAPI document. For a route named `Pretty name` with the description `d` and tags `["a", "b"]`, the operation had `summary` `Pretty name`, `description` `d`, `tags` `["a", "b"]` and an operation id built from the method and path (`get__rest_v1_x12`). A path with `{rest:path}` appears as `/rest/v1/files/{rest}`.

A route's documented responses are `200`, `401`, `403` and `422`. A route with a request body also documents the body's schema.

## What the handler receives

Whatever the handler type, the platform builds one request payload with five keys:

```json
{
  "params": { "id": "7" },
  "query": { "x": "1", "y": "two" },
  "body": { "reason": "because" },
  "headers": { "user-agent": "curl/8.7", "x-thing": "yes" },
  "client_ip": "203.0.113.9"
}
```

| Key | Content |
| --- | --- |
| `params` | Every path parameter, as **text**. `/echo/{id}` called with `/echo/7` gives `"7"`, never the number 7 |
| `query` | The whole query string, as text values. `?x=1&y=two` gives `{"x": "1", "y": "two"}` |
| `body` | The validated JSON body (see below), or `null` when there is none |
| `headers` | The request's headers, lower-cased. The platform's own credentials are removed: `apikey`, `x-api-key`, `cookie`, `proxy-authorization` and every `x-pawabase-*` header. `authorization` is passed through, because a function is trusted code |
| `client_ip` | The caller's address. `X-Forwarded-For` is a list that each proxy appends to, so what the caller wrote is on the left and is ignored: the address is the entry the gateway appended. With a load balancer in front of the gateway set `PAWABASE_TRUSTED_PROXY_HOPS=1` (one more hop from the right per proxy). `null` when unknown |

This is what a flow called through a route echoed back in a run:

```http
POST /rest/v1/echo/7?x=1&y=two
{ "reason": "because" }
```

```json
{
  "params": { "id": "7" },
  "query": { "x": "1", "y": "two" },
  "body": { "reason": "because" }
}
```

A `GET` route has no request body, so its `body` is `null`, even if the client sends one. A body sent with a `GET` was ignored in a run.

## A flow as the handler

`handler_type: "flow"` names a flow. The flow receives the payload above as its **trigger input**, so its blocks read the values with templates:

| In the flow | Value |
| --- | --- |
| `{{ input.params.id }}` | The path parameter |
| `{{ input.query.x }}` | A query value |
| `{{ input.body.reason }}` | A body field |

A flow used by a route needs a **`trigger.http`** node. If it has several, the one whose configured method and path match this route is used. A flow whose HTTP trigger has **no path** is also reachable directly at `/flows/v1/<name>`, which is a different door with its own policy (see [direct invocation](#the-other-doors-direct-flows-and-functions)).

### The flow's answer becomes the response

| The flow ends with | The route answers |
| --- | --- |
| A **`response.return`** block | That block's status, headers and body |
| An **`error.raise`** block | The status and message that block set, as `{"error": code, "message": message}` |
| Neither (it just finishes) | `200` with the flow's final result as JSON |

All three were run. A `response.return` with `status: 202` and a header `x-custom: yes` made the route answer:

```http
HTTP/1.1 202 Accepted
x-custom: yes

{ "queued": true }
```

An `error.raise` with `status: 404`, `code: "thing_missing"` and `message: "no such thing"` made it answer:

```http
HTTP/1.1 404 Not Found

{ "error": "thing_missing", "message": "no such thing" }
```

A flow with no `response.return`, ending in a `transform.map` block, answered with that block's output as the body:

```json
{ "b": "5", "alpha": 1 }
```

So a flow chooses the status, the headers and the body of its route. Use `response.return` when the status is not `200`, and `error.raise` for failures a client should be able to tell apart by `code`.

### A flow that does not exist

A route can be saved naming a flow that does not exist: the name is not checked. The first call answers:

```http
HTTP/1.1 500

{ "error": "missing_flow", "message": "route handler flow 'nope-flow' does not exist" }
```

Create the flow **before** the route, or check the Overview after saving. The same is true when you rename a flow: the route keeps the old name.

### An example: a flow that pays an order

A flow, `pay-order`, behind `POST /orders/{id}/pay`:

```json
{
  "name": "pay-order",
  "definition": {
    "nodes": [
      { "id": "start", "data": { "block": "trigger.http", "config": { "method": "POST", "path": "/orders/{id}/pay" } } },
      { "id": "load", "data": { "block": "resource.get", "config": { "resource": "orders", "id": "{{ input.params.id }}" } } },
      { "id": "paid", "data": { "block": "resource.update", "config": { "resource": "orders", "id": "{{ input.params.id }}", "data": { "status": "paid" } } } },
      { "id": "reply", "data": { "block": "response.return", "config": { "status": 200, "body": { "paid": true, "order": "{{ steps.paid.output }}" } } } },
      { "id": "missing", "data": { "block": "error.raise", "config": { "status": 404, "message": "no such order", "code": "order_not_found" } } }
    ],
    "edges": [
      { "id": "e1", "source": "start", "target": "load" },
      { "id": "e2", "source": "load", "target": "paid" },
      { "id": "e3", "source": "load", "target": "missing", "sourceHandle": "missing" },
      { "id": "e4", "source": "paid", "target": "reply" }
    ]
  }
}
```

and the route:

```json
{ "method": "POST", "path": "/orders/{id}/pay", "handler": "pay-order", "policy": "authenticated", "name": "Pay order" }
```

Called for an existing order, it answered `200` with `{"paid": true, "order": {...}}`, and for an id that does not exist, `404` with `{"error": "order_not_found", "message": "no such order"}`. Called without a credential, `401`, before the flow ran at all.

## A function as the handler

`handler_type: "function"` names a Python function that your project registers. Functions live in your project's code directory, which the API loads:

```text
code/
  acme/
    functions/
      billing.py       # @function("charge-order") ...
```

A function takes **one argument**, a context, and returns anything that can be written as JSON:

```python
from pawabase_core.functions import function


@function(
    "refund-order",
    description="Refund an order",
    policy="authenticated",
    input_fields=[
        {"name": "id", "type": "string", "required": True},
        {"name": "reason", "type": "string", "required": True, "max_length": 200},
    ],
    timeout=30,
)
async def refund_order(ctx):
    order_id = ctx.input["id"]
    reason = ctx.input["reason"]
    order = await ctx.runtime.resource_get("orders", order_id)
    ...
    return {"refunded": True, "order": order_id}
```

<Warning>
An earlier version of this page showed `async def refund_order(ctx, input)`. A function takes **only `ctx`**, and the payload is `ctx.input`. A two-argument function is called with one and fails.
</Warning>

### What the context holds

| Attribute | Meaning |
| --- | --- |
| `ctx.input` | The payload (see the next section) |
| `ctx.auth` | The caller's policy context: `authenticated`, `user_id`, `email`, `roles` and so on |
| `ctx.project`, `ctx.env` | Where the function is running |
| `ctx.trigger` | `http` for a route |
| `ctx.request` | For a route, `{"params", "query", "body", "headers", "client_ip"}`. For a direct call to the function, `None` |
| `ctx.runtime` | The platform's capabilities (resources, and the rest that flow blocks use) |
| `ctx.log(message, **data)` | Adds a log line to the invocation |

### What `ctx.input` is for a route

For a route, `input` is built from the payload, not passed as is:

| The request | `ctx.input` |
| --- | --- |
| `POST /plain/5?q=1` with body `{"a": 1}` | `{"id": "5", "a": 1}`. The path parameters and the body's keys, merged, and **the body wins** on a clash |
| `POST /plain/5` with body `[1, 2]` | `[1, 2]`. A body that is not an object **replaces** the input |
| `POST /plain/5` with no body | `{"id": "5"}`. The path parameters |
| `GET /plain/5?q=1` | `{"id": "5"}`. The query is **not** in `input` |

The query string is available only through `ctx.request["query"]`:

```json
{ "params": { "id": "5" }, "query": { "q": "1" }, "body": null }
```

### Validation of the input

A function can declare `input_fields`, and the merged input is validated against them in create mode, so required fields are enforced. This was run with `n` required and `id` declared:

| Request | Answer |
| --- | --- |
| `POST /fn/7` with `{"n": 3}` | `200`, the function runs with `{"n": 3, "id": "7"}` |
| `POST /fn/7` with `{}` | `422`, `{"error": "invalid", "message": "invalid function input", "details": [{"type": "missing", "loc": ["n"], ...}]}` |
| `POST /fn/7` with `{"n": "x"}` | `422`, the same shape, with an `int_parsing` detail |

Note that this `422` has a different shape from a bad **body**, which is a bare list. Two validations can apply to one request: the route's `input_fields` or `input_schema` first (the body), and the function's own `input_fields` (the merged input). See [what a bad request looks like](#errors-and-what-they-look-like).

### What a function's failures look like

| In the function | The route answers |
| --- | --- |
| It returns a value | `200` with the value as the body, **not** wrapped |
| It raises an exception | A plain `500`, `Internal Server Error`. The message is not returned |
| It runs longer than its `timeout` | `504`, `{"error": "timeout", "message": "function 'slow' exceeded 0.2s"}` |
| It is not registered | `404`, `{"error": "not_found", "message": "no function 'not_registered'"}`, on the first call. The route saved without complaint |

A function cannot choose its status or headers. If a route needs a `202` or a custom header, use a flow with `response.return`. If the logic must be Python, call the function from a flow, and let the flow answer.

### The function's own policy does not apply through a route

A function has a `policy` of its own (default `authenticated`). It is applied when the function is called **directly** at `/functions/v1/<name>`. When a **route** calls it, the route's policy decides, and the function's is not checked. This was run with a function whose policy is `deny`:

| Call | Answer |
| --- | --- |
| `POST /functions/v1/admin-only` as a signed-in user | `403`, `policy 'deny' refused` |
| `POST /rest/v1/adm`, a route with policy `public` that calls the same function | `200`, `"secret"` |

So **a route is a way around a function's policy**, deliberately or not. When a function is meant to be restricted, put the restriction on every route that calls it, and treat the route's policy as the real one.

## When to choose which

| | Flow | Function |
| --- | --- | --- |
| Edited in | Studio | Your code repository |
| Promoted with | **Promote** | Your deployment |
| Sets status and headers | Yes, with `response.return` | No |
| Errors with a code | Yes, with `error.raise` | A plain `500`, or a typed `FlowError` raised by your code |
| Needs a deploy to change | No | Yes |
| Can use any Python library | No | Yes |
| Best for | Orchestrating resources, mail, queues, webhooks | Real computation, a specific library, careful control of a transaction |

Start with a flow. Reach for a function when a flow cannot express the logic, and let a thin flow call it when you also need a status code or a header.

## The other doors: direct flows and functions

Routes are not the only way to run a flow or a function over HTTP. Two more endpoints exist, with different rules:

| Door | Path | Policy | Response |
| --- | --- | --- | --- |
| A function | `POST /functions/v1/<name>` | **The function's** `policy`, and the key's `functions:invoke` scope | `{"data": <result>}` |
| A flow | `POST /flows/v1/<name>` | The flow's `trigger.http` node's policy, default `authenticated` | The flow's `response.return`, or `{"data": <result>}` |

A flow is directly invocable only if it has a `trigger.http` node with **no path**. A flow with a path is served by a route instead. An unknown or path-bound flow answers `404`, `no directly invocable flow '<name>'`. A function that does not exist answers `404`, `no function '<name>'`.

The result of a direct function call is wrapped in `data`:

```json
{ "data": { "input": { "n": 1, "id": null }, "user": null, "trigger": "http", "request": null } }
```

and its `ctx.request` is `None`, because there was no route. Note `"id": null`: a declared field that the caller did not send arrives as `null`.

Both doors are part of the surface you expose. A flow or function that was written to be called by a route is **also** callable here, under its own policy, if it qualifies. Check the policy on each.

## The request body

How the body is read depends on the **method** and on whether the route declares an **input model**.

| Route | The body the handler sees |
| --- | --- |
| `GET`, `DELETE` | **Always `null`.** A body the client sends is ignored |
| `POST`, `PUT`, `PATCH` with `input_fields` or `input_schema` | The **validated** body, as an object |
| `POST`, `PUT`, `PATCH` **without** an input model | The parsed JSON, **unvalidated**. An object, a list or a string all pass through. Invalid JSON becomes `null` and the request still succeeds |

The last row was run. Without an input model, a body of `{"a": 1}`, `[1, 2]` and `"text"` reached the flow as sent, and the bytes `not json` reached it as `null`, with a `200`. A route with no model therefore accepts **anything** for its body. If the handler needs a shape, declare one.

### Declaring a shape: three choices

Studio's **Request body** control offers three:

| Choice | Stored as | Validates |
| --- | --- | --- |
| **Anything** | Nothing | Nothing |
| **Define fields** | `input_fields` | The body, with the rules of a resource `create` |
| **Use a schema** | `input_schema` | The body, against a stored schema, with one important difference below |

### `input_fields`: the strict one

The fields are compiled the way a resource's `create` body is, in create mode, and an unknown key is **refused**. All of this was run on a route with one required string `reason` with `max_length` 10:

| Body | Answer |
| --- | --- |
| `{"reason": "because"}` | Accepted |
| `{"reason": "way too long reason"}` | `422`, `String should have at most 10 characters` |
| `{}` | `422`, `Field required` for `reason` |
| `{"reason": "ok", "bonus": 1}` | `422`, `Extra inputs are not permitted` for `bonus` |
| No body at all | `422`, `Request body is not valid JSON` |

The `422` body is a bare list, one entry per problem:

```json
[
  {
    "type": "string_too_long",
    "loc": ["reason"],
    "msg": "String should have at most 10 characters",
    "input": "way too long reason",
    "ctx": { "max_length": 10 },
    "url": "https://errors.pydantic.dev/2.13/v/string_too_long"
  }
]
```

and a missing body is:

```json
[{ "loc": ["body"], "msg": "Request body is not valid JSON", "type": "json_invalid" }]
```

The field rules available are those of [Field types](/data/field-types) and [Validation](/data/validation): `required`, `max_length`, `minimum`, `enum`, `pattern`, nested objects and the rest.

### `input_schema`: documented strictly, enforced loosely

A stored schema can validate the body instead. It is the right choice when several routes, flows and resources share a shape. It does **not** behave like `input_fields` for `required`:

A route with `input_schema: "QuoteIn"`, where `QuoteIn` declares `items` as an integer that is required with a minimum of 1:

| Body | Answer |
| --- | --- |
| `{"items": 3}` | `200` |
| `{"items": 0}` | `422`, `Input should be greater than or equal to 1` |
| `{}` | **`200`**, the handler ran with `items` missing |

The minimum was enforced and the **required** flag was not. The generated documentation agrees with the behavior: `items` is shown as an integer **or null**, so the schema compiles with every field optional. Unknown keys are refused (`additionalProperties: false` in the document).

So with a schema, **check required values in the flow** (a `validate.schema` block, or a condition), or use `input_fields` where required fields matter. See [Schemas](/data/schemas) for the full list of what a referenced schema does and does not enforce.

### Both kinds of `422` are bare lists

A bad body is a bare list, as for a resource create. A bad **function input** is an object with an `error` and `details`, because it comes from a different check. A bad **flow validation** (`validate.schema` inside a flow) is yet another shape. A client that talks to several routes should handle all three. See [what a bad request looks like](#errors-and-what-they-look-like).

### The body is validated before the policy

On a route with an input model, validation runs **before** the policy. A caller who is not signed in and sends an invalid body gets the `422`, with the field names; sent a valid body they get the `401`:

| Caller | Body | Answer |
| --- | --- | --- |
| Signed out | invalid | `422` with the details |
| Signed out | valid | `401`, `Authentication required` |
| Signed in | invalid | `422` |

This means the **field names and rules** of a protected route are visible to anyone who can reach it. They are not secret on a well-documented API, but if the shape itself is sensitive, do not rely on the policy to hide it.

## Who may call a route

Every route has a **policy**, and every request passes through several checks. In the order they happen:

| Step | Refusal |
| --- | --- |
| 1. **Rate limit**, if the route has one | `429` |
| 2. **Body validation**, if there is an input model | `422` |
| 3. **The key's scope** | `403`, `This API key lacks the 'routes:invoke' scope` |
| 4. **The plan-time policy**: the part of the policy that does not depend on the body | `401` or `403` |
| 5. **Cache lookup**, for a cached `GET` route | (a hit returns here) |
| 6. **The full policy**, with the body available as `$input` | `401` or `403` |
| 7. The handler | |

### The default is `authenticated`

A route saved with no policy gets `authenticated`: a signed-in caller or a service credential. An anonymous caller gets `401`, `Authentication required`. To make a route public you must say so, with the built-in `public`.

### What a refusal looks like

| Caller | Policy | Answer |
| --- | --- | --- |
| Signed out | `authenticated` | `401`, `Authentication required` |
| Signed in, role `finance` | `{"in": ["finance", "$auth.roles"]}` | `200` |
| Signed in, another role | the same | `403`, `policy 'inline' refused` |
| Signed out | the same | `401` |
| Signed out, `n` = 50 | A stored policy `small`: `{"lte": ["$input.n", 10]}` | `401` |
| Signed in, `n` = 50 | the same | `403`, `policy 'small' refused` |

Note two things. A refusal of a **signed-out** caller is always a `401`, even when the real reason is the condition, so a client cannot tell "not signed in" from "signed in but not allowed" unless it knows it is signed in. And an **inline** condition is reported as `policy 'inline'`, while a stored policy is reported by its name, so stored policies give clearer messages.

### Policies that read the body

A condition can use `$input`, the validated body, such as `{"lte": ["$input.n", 10]}`. The route is checked in two phases: the parts that do not use `$input` are decided at step 4, before the body is trusted, and the full condition at step 6. A route whose policy **only** looks at `$input` is therefore decided after the body is read.

A `GET` route has no body, so `$input` is empty for it, and a comparison with a missing value is false. This was run: the stored policy `small` (`$input.n <= 10`) on a `GET` route refused a signed-in caller with `403`, `policy 'small' refused`. A condition on `$input` therefore makes a `GET` route **unreachable**. The same happens on a `POST` whose body omits the field: `{}` was refused too.

### API keys and scopes

A publishable or secret key carries **scopes**, and a route needs `routes:invoke`:

| Credential | Answer |
| --- | --- |
| A key with only `resource:read` | `403`, `This API key lacks the 'routes:invoke' scope` |
| A key with `routes:invoke` | The policy decides |
| A service credential | The policy decides |

Create keys with the scopes they need and no more. A browser key that should read data but never trigger a flow must not carry `routes:invoke`. See [API keys](/operate/api-keys).

### Rate limiting a route

A route has its own rate limit, per caller, counted across all gateway instances. It is separate from any resource's limit, and it is checked **first**, before the body is read, so invalid requests and refused requests count against the allowance too. With a limit of 2 per 60 seconds, the third request was refused:

```http
HTTP/1.1 429 Too Many Requests
retry-after: 30
x-ratelimit-remaining: 0

{
  "error": "rate_limit_exceeded",
  "message": "Too many requests. Slow down and retry later.",
  "retry_after": 30
}
```

Failed requests count: two `500` responses used up the allowance of a route in the same run. Choose a limit that tolerates your own clients' retries. For a route that costs money (sending mail, calling a payment provider), a limit is not optional.

## Disabling and removing a route

| Action | Effect |
| --- | --- |
| Turn **Enabled** off | The route is not registered. Requests answer `404` with the router's own body, `{"status": 404, "error": "Not Found", "message": "The page you are looking for does not exist."}` |
| Delete the route | The same, and the definition is gone |
| Delete the **flow** it uses | The route stays and every call answers `500`, `missing_flow` |
| Delete the **function's code** | The route stays and every call answers `404`, `no function '<name>'` |

The `404` of a disabled route differs from a resource's `404` (`Not found`, a plain string), which is useful when debugging: the long body means "no such route", and the short one means "no such record".

## Responses

### What a route returns

| The handler is | The response |
| --- | --- |
| A flow with `response.return` | Its status, its headers and its body |
| A flow that ends with `error.raise` | Its status and `{"error": code, "message": message}` |
| A flow that just finishes | `200` and the flow's final result |
| A function that returns | `200` and the returned value, **not** wrapped |
| A function that raises | `500`, `Internal Server Error` |

Every body is JSON. A route that returns a bare string returns it as a JSON string.

### The transformer

A route can name a [transformer](/data/transformers), stored or inline, and it is applied to the handler's result before the response is built. This was run on a flow that returned `{"b": "5", "alpha": 1}`, with a transformer that renames `alpha` to `first_value` and sets the case to camel:

```json
{ "b": "5", "firstValue": 1 }
```

The same five steps, in the same order, as on a resource: omit, pick, set, rename, case. For a list result, each item is shaped. Two details differ from a resource's transformer:

- The record the templates see is **whatever the handler returned**, not a database row.
- A route's transformer removes the route's **response schema** from the generated documentation, as it does for a resource.

Apply the transformer to the error paths with care. It runs on the result of the handler, so if your flow answers an error with a body, check that an `omit` or a `case` does not reshape the error your clients parse.

### `response_schema` is documentation

A route can name a stored schema as its `response_schema`. It appears as the `200` response in the generated OpenAPI document, and it is **not enforced**. In a run, a flow returned `{"total": 3, "internal": "leak"}` for a route whose response schema declared `total` and `currency`. The response had the extra key and no `currency`: nothing was stripped, nothing was added, nothing was refused.

So a response schema:

- **Documents** the shape for people and generated clients.
- Does **not** remove fields the flow added. A route that returns a whole record is not made safer by naming a schema.
- Does **not** apply defaults.
- Is dropped from the document when the route has a transformer.

To control what leaves, build the response in the flow, or use a transformer with `pick`.

## Errors, and what they look like

A route can fail in several ways, and each has its own body. A client of a route should handle all of them.

| Cause | Status | Body |
| --- | --- | --- |
| Over the rate limit | `429` | `{"error": "rate_limit_exceeded", "message": "...", "retry_after": 30}` |
| Invalid body (`input_fields`, `input_schema`) | `422` | A **bare list** of problems |
| Unparseable body, with an input model | `422` | `[{"loc": ["body"], "msg": "Request body is not valid JSON", "type": "json_invalid"}]` |
| Key lacks `routes:invoke` | `403` | `This API key lacks the 'routes:invoke' scope` (a plain string) |
| Not signed in | `401` | `Authentication required` (a plain string) |
| Policy refused | `403` | `policy '<name>' refused` (a plain string) |
| The flow raised with `error.raise` | the flow's status | `{"error": code, "message": message}` |
| The flow validates and fails | `422` | `{"error": "invalid", "details": [...]}` |
| Function input invalid | `422` | `{"error": "invalid", "message": "invalid function input", "details": [...]}` |
| Function timed out | `504` | `{"error": "timeout", "message": "..."}` |
| Function raised | `500` | `Internal Server Error` (plain) |
| Flow does not exist | `500` | `{"error": "missing_flow", "message": "route handler flow '...' does not exist"}` |
| Function not registered | `404` | `{"error": "not_found", "message": "no function '...'"}` |
| A transformer problem | `500` | `{"error": "transformer_error", ...}`, or a plain `500` |
| Route disabled or missing | `404` | `{"status": 404, "error": "Not Found", "message": "The page you are looking for does not exist."}` |

Three groups, by shape:

- **Plain strings**: `401`, `403` and the unhandled `500`. The text is the whole body.
- **Objects with `error` and `message`**: everything the platform or a flow raised on purpose.
- **A bare list**: body validation.

A client that parses every error as an object will fail on the `401`, the `403` and the validation list. Branch on the **status** first, then on the body's type.

### A pattern for a client

```ts
async function call(path: string, body?: unknown) {
  const response = await fetch(`/rest/v1${path}`, {
    method: "POST",
    headers: { apikey: KEY, Authorization: `Bearer ${token}`, "Content-Type": "application/json" },
    body: body === undefined ? undefined : JSON.stringify(body),
  })
  if (response.ok) return response.json()

  const text = await response.text()
  let parsed: unknown = text
  try { parsed = JSON.parse(text) } catch { /* a plain string body */ }

  if (response.status === 422 && Array.isArray(parsed)) {
    throw new ValidationError(parsed)                 // body validation
  }
  if (response.status === 422 && (parsed as any)?.error === "invalid") {
    throw new ValidationError((parsed as any).details) // function or flow validation
  }
  if (response.status === 429) {
    throw new RateLimited((parsed as any).retry_after)
  }
  if (response.status === 401) throw new NotSignedIn()
  if (response.status === 403) throw new Forbidden(String(parsed))
  const code = (parsed as any)?.error
  throw new ApiError(response.status, code ?? "error", (parsed as any)?.message ?? text)
}
```

The one function turns every shape into a typed error, so screens deal with `ValidationError` and `Forbidden`, not with HTTP details.

## Caching a route

A `GET` route can have a `cache_ttl`. The full account is on [Caching](/data/caching#caching-for-custom-routes). The facts that matter when you design a route:

- Only `GET` routes are cached. A time on any other method is accepted and does nothing.
- Entries are per caller and per full request: path parameters, query and body.
- A write to a resource does **not** clear a route's entries. A route is as fresh as its time.
- Only successes (status below 400) are stored, and the entry includes the **status and headers**.
- The lookup comes **before** the full policy check, so a policy that depends on the body or on outside state is not re-evaluated on a hit.

This was run with a `GET /count` route that listed a resource: after a record was added through the API, the same caller's same query still returned the old count. A different query, or a different caller, returned the new one.

The practical rules: keep the time short for a route that summarises changing data, keep its policy to conditions on the caller, and accept that a cached route can show data a moment old.

## Calling a route from the browser

A route is under `/rest/v1`, behind the same gateway as the resources. A browser needs the project's **publishable key** in the `apikey` header, the user's token in `Authorization` when the policy needs a user, and the site's origin in the environment's CORS list. See [Rate limits and CORS](/operate/rate-limits-and-cors).

```bash
curl -X POST "$GATEWAY/rest/v1/orders/ord_123/refund" \
  -H "apikey: $PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason": "customer cancelled"}'
```

The key must carry `routes:invoke`. A key limited to `resource:read` is refused with a `403` before the policy is looked at.

### Which key for which route

| Route is for | Key and policy |
| --- | --- |
| Anyone on the web | A publishable key with `routes:invoke`, policy `public`, a rate limit |
| Signed-in users | A publishable key and the user's token, policy `authenticated` or a role |
| Your servers only | A **secret** key, and a policy of `service`, so no browser can call it |
| A third party (a callback) | See [inbound hooks](#a-webhook-receiver) |

A secret key must never reach a browser. If a route must be callable only by your own backend, give it the `service` policy: a signed-in user's token is then refused.

## Recipes

The first three recipes below (the summary, the parameterised lookup and the validated write) were built and called, and the answers shown are what came back. The rest are patterns assembled from blocks that were run separately, so test them in your environment. The flows are shown as the nodes and edges Studio stores, which you can paste into a flow's **JSON** tab.

### A summary endpoint with SQL

A resource's API cannot group or total. A route backed by a flow with a **SQL query** can.

The flow, `summary`:

```json
{
  "nodes": [
    { "id": "start", "data": { "block": "trigger.http", "config": { "method": "GET", "path": "/summary" } } },
    { "id": "q", "data": { "block": "db.query", "config": {
        "sql": "SELECT status, COUNT(*) AS n, SUM(total) AS revenue FROM orders GROUP BY status ORDER BY status",
        "params": []
    } } },
    { "id": "r", "data": { "block": "response.return", "config": { "status": 200, "body": { "by_status": "{{ steps.q.output }}" } } } }
  ],
  "edges": [
    { "id": "e1", "source": "start", "target": "q" },
    { "id": "e2", "source": "q", "target": "r" }
  ]
}
```

The route:

```json
{ "method": "GET", "path": "/orders/summary", "handler": "summary", "policy": "public" }
```

Called with `GET /rest/v1/orders/summary`, it answered:

```json
{
  "by_status": [
    { "status": "new", "n": 1, "revenue": 5.0 },
    { "status": "paid", "n": 2, "revenue": 30.0 }
  ]
}
```

Three points. The query block returns a **list of row objects**, which the template passes through unchanged. The path `/orders/summary` sits next to the `orders` resource and was accepted, because a fixed segment is not the resource's own path, and a request to it reached the route. And the query reads the **raw table**, so it ignores the resource's policy: give the route the policy the data deserves. See [the SQL block's limits](#sql-in-a-flow-is-a-read-with-the-consoles-guard).

### A parameterised lookup

Never build SQL by joining text. Pass values as parameters:

```json
{ "id": "q", "data": { "block": "db.query", "config": {
    "sql": "SELECT COUNT(*) AS n, SUM(total) AS revenue FROM orders WHERE customer = ?",
    "params": ["{{ input.params.customer }}"]
} } }
```

With the route `GET /customers/{customer}/total`, a call for `a` returned `[{"n": 2, "revenue": 15.0}]`. A call whose path value was `a' OR '1'='1` returned `[{"n": 0, "revenue": null}]`: the value was treated as data, and matched no customer. The placeholder style is the database's (`?` on SQLite, `$1` on PostgreSQL, `%s` on MySQL), so write the query for the dialect the environment uses.

### A validated write

A route with no input model accepts any body, so validate inside the flow when the shape matters:

```json
{
  "nodes": [
    { "id": "start", "data": { "block": "trigger.http", "config": { "method": "POST", "path": "/place" } } },
    { "id": "v", "data": { "block": "validate.schema", "config": {
        "value": "{{ input.body }}",
        "fields": [
          { "name": "customer", "type": "string", "required": true },
          { "name": "total", "type": "number", "required": true, "minimum": 1 }
        ]
    } } },
    { "id": "c", "data": { "block": "resource.create", "config": {
        "resource": "orders",
        "data": { "customer": "{{ steps.v.output.customer }}", "status": "new", "total": "{{ steps.v.output.total }}" }
    } } },
    { "id": "r", "data": { "block": "response.return", "config": { "status": 201, "body": { "order": "{{ steps.c.output }}" } } } }
  ],
  "edges": [
    { "id": "e1", "source": "start", "target": "v" },
    { "id": "e2", "source": "v", "target": "c" },
    { "id": "e3", "source": "c", "target": "r" }
  ]
}
```

With a route of `POST /place` and the policy `authenticated`:

| Body | Answer |
| --- | --- |
| `{"customer": "c", "total": 7}` | `201`, `{"order": {"id": 4, "customer": "c", "status": "new", "total": 7.0, ...}}` |
| `{"customer": "c", "total": 0}` | `422`, the validation object below |
| `{}` | `422`, one detail per missing field |

```json
{
  "error": "invalid",
  "message": "validation failed",
  "details": [
    { "type": "greater_than_equal", "loc": ["total"], "msg": "Input should be greater than or equal to 1", "input": 0, "ctx": { "ge": 1.0 } }
  ]
}
```

This `422` is an **object**, unlike the bare list that `input_fields` produces. It is the shape of a flow's own validation. If you prefer one shape, put the fields in the route's `input_fields` and keep the flow for the work.

The `validate.schema` block cannot resolve a `ref` to a stored schema, so nested referenced objects are not checked there. See [Schemas](/data/schemas).

### A webhook receiver

A third party calls your system with a callback. A custom route can receive it:

```json
{ "method": "POST", "path": "/hooks/payments", "handler": "payment-callback", "policy": "public", "rate_limit": { "limit": 60, "window": 60 } }
```

Because the route is public, the flow must **verify the caller itself**: a shared secret in a header, or a signature. A route's flow receives the payload `params`, `query` and `body`, but not the request **headers**, so a header-based check cannot be done in a route's flow. For callbacks that must be authenticated by a signature, use an **inbound hook** instead, which verifies signatures before running anything. See [Inbound webhooks](/webhooks/inbound).

Use a route for a callback only when it carries its own secret in the body or the query, and compare it in the flow against a stored [secret](/operate/secrets).

### An endpoint your servers call

A route that only your backend should call has the `service` policy and is called with a **secret key**:

```json
{ "method": "POST", "path": "/internal/recalculate", "handler": "recalculate", "policy": "service" }
```

A signed-in user's token is refused with `403`, and a publishable key cannot satisfy `service`. The secret key must stay on the server.

### A queued job that answers at once

A slow job should not hold the request open. A flow can start the work and answer `202` immediately with `response.return`:

```json
{ "id": "r", "data": { "block": "response.return", "config": {
    "status": 202,
    "headers": { "x-custom": "yes" },
    "body": { "queued": true }
} } }
```

The route answered `202` with that body and header in a run. Place the block after the step that **starts** the work, and give the client somewhere to poll (a `jobs` resource it can read, or a status route) so it can learn the outcome.

### A search with many optional filters

A resource filter has a fixed set of operators. A route can combine several optional filters in SQL and answer a list the resource could not:

```json
{ "id": "q", "data": { "block": "db.query", "config": {
    "sql": "SELECT id, title FROM articles WHERE (? IS NULL OR status = ?) AND (? IS NULL OR title LIKE ?) ORDER BY id DESC LIMIT 50",
    "params": [
      "{{ input.query.status }}", "{{ input.query.status }}",
      "{{ input.query.q | default:\"\" }}", "%{{ input.query.q }}%"
    ]
} } }
```

Keep a `LIMIT`, parameterise every value, and remember that an uncached search with free text is the kind of route to put behind a rate limit.

## SQL in a flow is a read, with the console's guard

The SQL block runs through the **same read-only check** as the Database console. It accepts a statement the check calls a read, and refuses one it calls a write. Two things follow:

- It is for **reads**. A flow that must change data uses the resource blocks (`resource.create`, `resource.update`, `resource.delete`), or `db.transaction` for several writes that must succeed together.
- The check looks for forbidden words only when they have **spaces on both sides**, so it is a safeguard against mistakes and not a guarantee against a hostile statement. Flow authors are trusted with the database; treat the permission to edit flows accordingly. See [Database console](/data/database-console#reads-and-writes-how-the-console-decides).

A route's SQL also **skips the resource's policy and transformer**. Whatever the query selects is what the route can return, so select only the columns the caller may see.

## Versions: the same path in different environments

A route is part of the definitions, so it moves with the rest:

| Action | What happens to routes |
| --- | --- |
| **Promote** with `routes` (or with no `include`) | Each route is copied to the target by **method and path**. A route that exists there is overwritten, a new one is created |
| **Promote** | Never deletes. A route removed in the source stays in the target |
| A **release** | Includes the routes of the revision. A pinned `/rest/v2` serves the routes of its release |
| A flow or function the route names | Promoted separately. The route's definition only holds the **name** |

This was run: promoting `development` to `staging` with `include: ["routes"]` answered `{"from": "development", "to": "staging", "copied": {"routes": 2}}`, and staging then listed both routes, each pointing at its flow's name.

The consequence is the usual one for names: promote the **flows** with the routes, or the target has routes whose handler does not exist, and every call answers `500`, `missing_flow`. Promote everything (omit `include`) unless you are certain. For functions, deploy the code to the target environment's service before the route is called, or it answers `404`, `no function '<name>'`.

## Choosing between a route and its neighbours

Several features can answer an HTTP request, and they are not interchangeable.

| You want | Use | Why |
| --- | --- | --- |
| Create, read, update or delete one kind of record | A **resource** | Validation, policy, pagination, filtering, events and caching are already there |
| A different view of one resource's data | A resource with a **transformer**, or a second route | A transformer shapes; a route can query |
| An action that touches several records or services | A **route** with a flow | One endpoint, one policy, and the flow does the steps |
| A calculation, totals, a report | A **route** with a SQL or function handler | The resource API cannot aggregate |
| A callback from a third party that signs its requests | An **inbound hook** | It verifies the signature before running anything |
| A callback that carries its own token | A **route** with a public policy and a check in the flow | Headers are not available, so the token must be in the body or query |
| Work on a timetable | A **schedule** | No request is involved |
| A reaction to a record changing | An **event subscription** or a flow with a resource trigger | No client is waiting |
| An endpoint that must be callable only by your servers | A **route** with the `service` policy | A secret key, never in a browser |
| A public file or page | Storage or your own web server | A route returns JSON |

Two questions settle most choices. **Is a client waiting?** If not, it is not a route. **Is it one table with the usual operations?** If so, it is a resource.

## A worked design: refunding an order

A shop wants a **refund** action that only finance staff may take, that validates the amount, that records the refund, and that tells the client clearly what happened.

**The pieces.**

| Piece | Choice |
| --- | --- |
| Endpoint | `POST /orders/{id}/refund` |
| Who | A stored policy `finance_only`: `{"in": ["finance", "$auth.roles"]}` |
| Body | `input_fields`: `amount_cents` (integer, required, minimum 1) and `reason` (string, required, max 200) |
| Handler | A flow, `refund_order` |
| Limits | A rate limit of 20 per minute |
| Cache | None. A `POST` is never cached |

**The route.**

```json
{
  "method": "POST",
  "path": "/orders/{id}/refund",
  "name": "Refund an order",
  "handler_type": "flow",
  "handler": "refund_order",
  "policy": "finance_only",
  "input_fields": [
    { "name": "amount_cents", "type": "integer", "required": true, "minimum": 1 },
    { "name": "reason", "type": "string", "required": true, "max_length": 200 }
  ],
  "rate_limit": { "limit": 20, "window": 60 }
}
```

**The flow, in outline.**

1. `trigger.http`, `POST`, `/orders/{id}/refund`.
2. `resource.get` the order by `{{ input.params.id }}`. If it does not exist, an `error.raise` with status `404` and code `order_not_found`.
3. A condition that the amount does not exceed what is left to refund. If it does, an `error.raise` with status `409` and code `refund_exceeds_total`.
4. `resource.create` a `refunds` record with the order id, the amount, the reason and the caller (`{{ auth.user_id }}` is available to flows through the run's auth).
5. `resource.update` the order's `status`.
6. `response.return` with status `201` and the refund as the body.

**What each part guarantees.**

| Concern | Handled by | Outcome |
| --- | --- | --- |
| A customer calls it | The policy | `403`, `policy 'finance_only' refused`. Signed out, `401` |
| A bad amount | `input_fields` | `422`, a bare list naming `amount_cents` |
| A missing field | `input_fields` | `422`, `Field required` |
| An unknown extra field | `input_fields` | `422`, `Extra inputs are not permitted` |
| An order that does not exist | The flow | `404`, `{"error": "order_not_found", ...}` |
| A refund over the balance | The flow | `409`, `{"error": "refund_exceeds_total", ...}` |
| A burst of calls | The rate limit | `429` with `retry-after` |
| Who refunded what, and when | The `refunds` record and the audit trail of the resource | Recorded |

**What it does not guarantee.**

- **Atomicity.** Creating the refund and updating the order are two steps. If the second fails, the first stands. Use `db.transaction` for steps that must succeed together.
- **Idempotency.** Calling it twice refunds twice. Add an idempotency key to the body, store it, and refuse a repeat.
- **Hidden fields.** The flow returns whatever it puts in `response.return`. Build the body from the fields the client may see.

## Designing a route well

| Principle | In practice |
| --- | --- |
| **Name routes for what they do** | `POST /orders/{id}/refund`, not `POST /doRefund`. Resource-like nouns and a verb at the end |
| **Use the right method** | `GET` for reads (and caching), `POST` for actions, `PUT` and `PATCH` for replacement and change, `DELETE` for removal |
| **Declare the body** | `input_fields` for strict shapes. Without a model the route accepts anything |
| **Make the policy explicit** | The default is `authenticated`, which may be broader than you intend. Name a policy |
| **Rate-limit anything that costs** | Mail, payments, exports, SQL searches |
| **Return a clear status** | `201` for creation, `202` for accepted work, `409` for a conflict, with an `error` code clients can switch on |
| **Keep handlers small** | A flow that calls a function for the hard part, a function that does not know about HTTP |
| **Version by path** | `/v2/orders/{id}/refund` for a breaking change, with the old one left in place |
| **Keep routes out of resource space** | Use a sub-path (`/orders/{id}/refund`), never the resource's own path |

## Testing a route

A route is an HTTP endpoint, so a test is a request. Cover the three outcomes for each route: **who may**, **what is accepted**, and **what happens**.

```python
def test_refund_requires_finance(api, customer, finance):
    path = "/rest/v1/orders/7/refund"
    body = {"amount_cents": 500, "reason": "damaged"}

    assert api.post(path, json=body).status_code == 401                         # signed out
    assert api.post(path, json=body, auth=customer).status_code == 403           # wrong role
    assert api.post(path, json=body, auth=finance).status_code in (200, 201)     # allowed


def test_refund_validates_the_body(api, finance):
    path = "/rest/v1/orders/7/refund"
    for body in ({}, {"amount_cents": 0, "reason": "x"}, {"amount_cents": 5, "reason": "x", "extra": 1}):

        assert response.status_code == 422
        assert isinstance(response.json(), list)        # a bare list, from input_fields


def test_refund_reports_a_missing_order(api, finance):

    assert response.json()["error"] == "order_not_found"


def test_refund_is_rate_limited(api, finance):

```

Add to it:

- **A signed-out request with an invalid body.** It answers `422`, not `401`, because validation runs first. Decide whether that matters for the route.
- **A key without `routes:invoke`.** It must answer `403`.
- **The disabled route.** After turning **Enabled** off, the router's `404`.
- **The flow's absence.** Delete the flow in a scratch environment and confirm the route answers `500`, `missing_flow`, so you know what that looks like.

Test against a **development** environment, and promote only when the suite passes.

## What a function can do: the runtime

A function's `ctx.runtime` is the same set of capabilities that flow blocks use. It is what makes a function more than "Python in a request": it can reach the platform without any client or credential of its own.

| Area | Methods |
| --- | --- |
| **Resources** | `resource_list(resource, filters=, sort=, limit=, offset=)`, `resource_get(resource, id)`, `resource_create(resource, data)`, `resource_update(resource, id, data)`, `resource_delete(resource, id)` |
| **SQL** | `db_query(sql, params)` for reads, `db_transaction(operations)` for several writes that succeed or fail together |
| **Cache** | `cache_get`, `cache_set`, `cache_delete`, `cache_invalidate(tags)` |
| **Events and queues** | `emit(name, payload)`, `dispatch_flow(flow, input, delay=, queue=)`, `call_flow(flow, input)`, `dispatch_function(function, input, delay=, queue=)`, `call_function(name, input)` |
| **Realtime** | `publish(channel, event, payload)` |
| **Storage** | `storage_put`, `storage_read`, `storage_signed_url`, `storage_delete` |
| **Mail** | `send_mail(to, subject, text=, html=, template=, data=)` |
| **Outbound HTTP** | `http_request(method, url, headers=, json=, params=, timeout=, retries=)`, `webhook_send(event, payload)` |
| **Platform** | `secret(name)`, `identity_user(user_id)`, `check_policy(ref, context)`, `log(level, message, data)`, `metric(name, value, tags)` |

A resource write through the runtime is a **trusted** write: it skips the resource's policy, and it runs the after-write step, so the resource's cache is cleared and its events and realtime updates are published. It does not run a transformer.

### A function, run

A bulk import of people, behind `POST /people/bulk-import`. The function was loaded from `code/acme/functions/imp.py`, the route was `handler_type: "function"`, and the `people` resource had a unique `email` and a cache time of 60.

```python
from pawabase_core.functions import function


@function(
    "bulk-import",
    policy="public",
    input_fields=[
        {"name": "rows", "type": "array", "items": {"type": "object", "fields": [
            {"name": "name", "type": "string", "required": True},
            {"name": "email", "type": "email", "required": True},
        ]}}
    ],
)
async def bulk_import(ctx):
    created, failed = [], []
    for index, row in enumerate(ctx.input["rows"]):
        try:
            record = await ctx.runtime.resource_create("people", row)
            created.append(record["id"])
        except Exception as exc:
            failed.append({"index": index, "error": f"{type(exc).__name__}: {exc}"})
    total = await ctx.runtime.db_query("SELECT COUNT(*) AS n FROM people")
    ctx.log("imported", count=len(created))
    return {"created": created, "failed": failed, "total": total[0]["n"]}
```

Called with three rows, the third repeating the second row's email:

```json
{
  "created": [1, 2],
  "failed": [{ "index": 2, "error": "IntegrityError: UNIQUE constraint failed: people.email" }],
  "total": 2
}
```

The answer is the function's return value, **unwrapped**. Three properties of this design are the reason to use a function here:

| Property | Why it matters |
| --- | --- |
| **The unique violation is catchable.** Through the REST API it is a plain `500`. Through the runtime it is an exception your code can catch and report per row | One bad row does not stop the import, and the client learns which row failed and why |
| **Nested input validation** | A row missing its email answers `422` with `loc: ["rows", 0, "email"]`, before the function runs |
| **The cache was handled for you** | A list cached before the import showed both new people straight after, because each create cleared the resource's entries. An explicit `cache_invalidate` after the loop removed nothing, since there was nothing left |

The input validation, for the same function:

| Body | Answer |
| --- | --- |
| `{"rows": [{"name": "A"}]}` | `422`, `{"error": "invalid", "message": "invalid function input", "details": [{"type": "missing", "loc": ["rows", 0, "email"], "msg": "Field required", ...}]}` |
| `{"rows": "x"}` | `422`, the same shape, with a `list_type` detail: `Input should be a valid list` |

### Reading a secret

`await ctx.runtime.secret("MY_SECRET")` returns the secret's value, and `None` if it does not exist. In the run, a secret of twelve characters came back as twelve. Use it for provider keys and shared tokens, and never put a secret in the function's source.

### Logging

`ctx.log("imported", count=3)` adds a line to the invocation, and `runtime.log(level, message, data)` writes a user log, which appears under **User logs** in the request trace. Log what happened, not what was sent: bodies often contain personal data.

## Calling work that should not block the request

A route that has to answer quickly can hand work to a queue:

| Need | Method |
| --- | --- |
| Run a flow later, or in the background | `dispatch_flow(flow, input, delay=60, queue="mail")` |
| Run another function in the background | `dispatch_function(function, input, delay=0)` |
| Run a flow now and use its result | `call_flow(flow, input)` |
| Run another function now and use its result | `call_function(name, input)` |

Both `dispatch_*` methods return a job id. A function that dispatches and returns `{"queued": true}` answers fast, while the work runs in a worker. In a development install with the inline worker the work may run in the same process, so test queue behavior against a real worker before relying on it. See [Jobs and failures](/operate/jobs-and-failures).

A function that dispatches work and answers `200` cannot answer `202`. If the route must say `202`, use a flow with `response.return`, which can start the same background work and set the status.

## Idempotency: making a POST safe to repeat

Networks retry. A route that creates something, or moves money, should give the same answer when it is called twice with the same intent.

A pattern with a flow or function and one extra resource:

1. The client sends an **idempotency key** in the body (`"key": "order-7-refund-1"`).
2. A resource `idempotency_keys` holds `key` (unique) and `response` (json).
3. The handler first looks up the key. If it exists, it **returns the stored response**.
4. Otherwise it does the work, stores the key and the response, and returns it.

In a function:

```python
@function("refund", policy="authenticated")
async def refund(ctx):
    key = ctx.input["key"]
    found = await ctx.runtime.resource_list("idempotency_keys", filters={"key": key}, limit=1)
    if found["data"]:
        return found["data"][0]["response"]

    result = await do_the_refund(ctx)             # your logic
    try:
        await ctx.runtime.resource_create("idempotency_keys", {"key": key, "response": result})
    except Exception:
        # two requests raced: the unique index let one win. Return what it stored
        found = await ctx.runtime.resource_list("idempotency_keys", filters={"key": key}, limit=1)
        return found["data"][0]["response"]
    return result
```

The unique constraint on `key` is what makes it safe: two simultaneous requests cannot both store the key, and the loser returns the winner's answer. It is a pattern, not a platform feature, and the `do_the_refund` work still needs to be safe to have started twice, because both racers may reach it before either stores the key. Where that matters, store the key **first**, in a transaction with the work.

## Extension routers

Besides routes defined as data, a project can mount a **plain Sillo router** from code, in `code/<project>/routes.py`:

```python
from sillo import Router

router = Router(prefix="/billing")

@router.get("/ping")
async def ping(ctx):
    return {"pong": True}
```

It is loaded with the project's other code, and it is the way to write an endpoint that needs everything a web framework offers: streaming, file responses, custom middleware. It is **not** a stored definition: it is not shown in Studio's Routes page, it is not promoted, it has no policy, rate limit or cache setting from Pawabase, and you are responsible for authentication in it. Reach for it only when a route backed by a flow or a function cannot do the job. This section follows the description on the [Code](/code/overview) page and was not exercised in the runs above, so test an extension router in a development environment before you rely on it.

## Creating a route in Studio, start to finish

The whole job for a flow-backed route, in the order the screens appear.

<Steps>
  <Step title="Create the flow">
    Open **Flows** and create a flow whose first block is **HTTP trigger** (`trigger.http`). Set its method and path to the ones the route will use, for example `POST` and `/orders/{id}/refund`. Add the blocks that do the work, and end with a **Return response** block (`response.return`) when the status or headers matter. Save it.
  </Step>
  <Step title="Open Routes and create the route">
    In **Build → Routes**, create a new route. The sheet is titled **New route**.
  </Step>
  <Step title="Fill in the endpoint">
    Choose the **method**, type the **path** after the fixed `/rest/v1` prefix (placeholder `/checkout`), and optionally a **Name** and **Description** for the documentation. Leave **Enabled** on.
  </Step>
  <Step title="Choose the handler">
    Under **Handler**, leave **Type** on **Flow** and pick your flow from the select. If there are no flows yet, the field says *No flows yet; type a name.* and you can type the name of one you are about to create.
  </Step>
  <Step title="Set who may call it">
    Under **Access**, choose a policy. Leaving it empty means **authenticated**, which is not public. Pick `public` only when you mean it.
  </Step>
  <Step title="Describe the request">
    Under **Request & response**, set **Request body** to **Define fields** and add the fields with their rules, or **Use a schema** and choose one (remembering that required fields are not enforced that way). **Anything** accepts any body.
  </Step>
  <Step title="Add the limits">

## Route definitions by archetype

Concrete definitions to compare with your own. Each is the body you would send to the routes endpoint.

### An action on one record

```json
{
  "method": "POST",
  "path": "/orders/{id}/cancel",
  "name": "Cancel an order",
  "handler_type": "flow",
  "handler": "cancel_order",
  "policy": "own_orders",
  "input_fields": [{ "name": "reason", "type": "string", "max_length": 200 }],
  "rate_limit": { "limit": 10, "window": 60 }
}
```

A fixed verb at the end of an id path, an owner-scoped policy, an optional reason, and a limit that tolerates a retry or two.

### A read-only report

```json
{
  "method": "GET",
  "path": "/reports/revenue",
  "name": "Revenue by status",
  "handler_type": "flow",
  "handler": "revenue_report",
  "policy": "finance_only",
  "cache_ttl": 30,
  "tags": ["reports"]
}
```

`GET`, so it can be cached, with a short time because a report built from other resources is not cleared by writes.

### A public, rate-limited lookup

```json
{
  "method": "GET",
  "path": "/stock/{sku}",
  "name": "Stock level",
  "handler_type": "flow",
  "handler": "stock_level",
  "policy": "public",
  "rate_limit": { "limit": 120, "window": 60 },
  "cache_ttl": 10
}
```

A public endpoint with a rate limit and a short cache. The cache key includes the `sku`, so each product has its own entry.

### A server-to-server endpoint

```json
{
  "method": "POST",
  "path": "/internal/sync",
  "name": "Sync from the ERP",
  "handler_type": "function",
  "handler": "erp-sync",
  "policy": "service",
  "input_fields": [{ "name": "since", "type": "datetime", "required": true }]
}
```

Only a service credential passes the policy, so a browser key or a user token is refused. The function runs a long job, so it has a generous `timeout` in its own definition.

### A route kept off while it is built

```json
{
  "method": "POST",
  "path": "/beta/export",
  "handler": "export_everything",
  "policy": "deny",
  "enabled": false
}
```

A route can be saved disabled, with a policy that refuses everyone, so that nothing reaches it while the flow is finished. Both settings guard it: **Enabled** off answers `404`, and if someone enables it early, `deny` still refuses.

## A security review of a route

A route runs code on behalf of a caller. Before one goes public, walk the same checklist every time. Each item below comes from something that was run.

| Question | What was observed | What to do |
| --- | --- | --- |
| **Is the policy what I meant?** | Omitting the policy gives `authenticated`. `public` has to be written | Name the policy explicitly. Read it back in the route's sheet |
| **Does the policy fail closed?** | A condition on `$input` for a `GET` refused everyone. A comparison with a missing value is false | Test with the field present, missing and wrong |
| **Who can learn the body's shape?** | Validation runs **before** the policy, so a signed-out caller gets a `422` naming the fields | Accept it for documented APIs. Otherwise keep the route behind a gateway rule |
| **Does the function have a policy that routes bypass?** | A function with policy `deny` returned its result through a `public` route | Put the restriction on the **route**. Treat the function's policy as the policy of its direct door only |
| **Does a flow also have a direct door?** | A flow with a `trigger.http` that has no path is callable at `/flows/v1/<name>` | Give that trigger a policy, or give it a path |
| **Does `response_schema` limit the response?** | No. Extra keys were returned, defaults were not applied | Build the body in the flow, or use a transformer with `pick` |
| **Does `input_schema` require fields?** | No. `required` was not enforced, only constraints like `minimum` | Use `input_fields`, or check in the flow |
| **Does an unvalidated route accept anything?** | Any JSON, including lists and strings, and invalid JSON as `null` | Declare a model |
| **Can the query be injected?** | A SQL block with a parameter treated `a' OR '1'='1` as data | Always use parameters. Never join text |
| **Does the SQL respect policies?** | No. A flow's SQL reads the raw table | Select only what the caller may see, and set the route's policy to match |
| **Can a cached answer outlive the policy?** | The route's cache lookup is before the full policy check, and the key has identity and role only | Cache only routes whose policy is about the caller |
| **Does the rate limit cover failures?** | Failed requests counted, and the limit is per caller | Choose a limit above your clients' retries |
| **Can a key reach it?** | A key without `routes:invoke` was refused with `403` | Issue keys with the scopes they need |
| **Is it reachable by the wrong key type?** | A `service` policy refuses user tokens and publishable keys | Use it for server-to-server endpoints |
| **What do errors reveal?** | A function that raises returns a plain `500`, with no message | Good. Do not add messages that leak internals |

### The doors a route opens

A route is one door. The things it calls may have others:

```text
route  ─────► flow  ◄───── /flows/v1/<name>      (only if the trigger has no path)
route  ─────► function ◄── /functions/v1/<name>  (its own policy)
route  ─────► resource blocks ─── no policy, trusted
route  ─────► SQL block ───────── no policy, raw table
```

Review them as a set. A flow behind a locked route that is also open at `/flows/v1` is open.

## Troubleshooting

| What you see | Cause | Fix |
| --- | --- | --- |
| `404` with `{"status": 404, "error": "Not Found", ...}` | The route is disabled, deleted, or its method or path is different | Check **Enabled**, the method and the exact path |
| `404` with the plain text `Not found` | The path reached a **resource**, and the record does not exist | A route may be shadowed by a resource. Check the Overview |
| `401` on a route you thought was public | The policy is `authenticated` (the default) | Set `public` explicitly |
| `403`, `This API key lacks the 'routes:invoke' scope` | The key was created without that scope | Issue a key with it |
| `403`, `policy '<name>' refused` | The policy refused a signed-in caller | Check the condition against the caller and the body |
| `403` on a `GET` route whose policy mentions `$input` | A `GET` has no body, so the comparison is false | Move the check to the query, or use a `POST` |
| `422` with a list | Body validation. Read the `loc` and `msg` | Fix the body |
| `422` with `invalid function input` | The merged input failed the function's own `input_fields` | Check path parameters and body together |
| `422` with `validation failed` | A `validate.schema` block in the flow | Fix the body for that schema |
| `200` with `total: null` for a missing required field | The route uses `input_schema`, which does not enforce `required` | Use `input_fields` or check in the flow |
| `500`, `missing_flow` | The route names a flow that does not exist | Create the flow, or fix the name |
| `404`, `no function '<name>'` | The function is not registered (not deployed, wrong name, import error) | Check the project's code directory and the API's logs |
| `500`, `Internal Server Error` from a function route | The function raised | Read the function's logs. The message is not returned |
| `504`, `timeout` | The function ran past its `timeout` | Do less, or raise the timeout |
| `429` | Over the route's limit | Wait for `retry-after`, or raise the limit |
| An answer that does not reflect a write | A cached `GET` route | Shorten `cache_ttl`, or accept the staleness |
| A route's body is `null` | A `GET` or `DELETE` route, or an unparseable JSON body with no input model | Use `POST`, or fix the JSON |
| The `id` is text where you expected a number | Path parameters are always text | Convert in the flow or function |
| The response has fields it should not | The flow returns more than it should, and `response_schema` does not trim | Build the body, or use a transformer with `pick` |
| Changes to a function do not appear | The code is loaded once per project when it is first used | Restart the API, or reload the project's code |

## Questions that come up

<AccordionGroup>
  <Accordion title="Is a custom route public by default?">
    No. With no policy it is `authenticated`. To make it public, set the `public` policy.
  </Accordion>
  <Accordion title="Can a route return a status other than 200?">
    From a flow, yes: `response.return` sets the status and headers, and `error.raise` sets an error status. From a function, no: it returns `200`, unless it fails.
  </Accordion>
  <Accordion title="Are path parameters numbers?">
    No. They are always text. A flow or function converts them.
  </Accordion>
  <Accordion title="Why did my `GET` route ignore the body?">
    `GET` and `DELETE` routes never read a body. Use `POST`, or put the data in the query string.
  </Accordion>
  <Accordion title="Why does my route accept any JSON?">
    Without `input_fields` or `input_schema` the body is unvalidated. Declare a shape.
  </Accordion>
  <Accordion title="Why is `required` ignored with `input_schema`?">
    A referenced schema compiles with every field optional, so constraints are enforced and required is not. Use `input_fields` for required fields.
  </Accordion>
  <Accordion title="Can I see request headers in a flow?">
    No. A route's flow gets `params`, `query` and `body`. For header-based authentication of callbacks, use an inbound hook.
  </Accordion>
  <Accordion title="Can a route call another route?">
    A flow can call another flow, and a function can call flows, functions and resources through its runtime. Routing a call back out through HTTP to the same environment is not something to build on: call the flow or function directly.
  </Accordion>
  <Accordion title="Does a route have its own events?">
    No. A route runs a flow, and the resource blocks inside it publish the resource events they normally do. See [Resource events](/data/resource-events).
  </Accordion>
  <Accordion title="Can two routes share a path?">
    Yes, with different methods. The same method and path is refused with a `409`.
  </Accordion>
  <Accordion title="Can I use a route to replace a resource operation?">
    Not at the resource's own path. Disable the operation on the resource, and serve your own behavior at a sub-path.
  </Accordion>
  <Accordion title="What happens to a route when I delete its resource?">
    Nothing. The route is independent. If it used the resource's table through SQL, it will fail at run time.
  </Accordion>
  <Accordion title="How do I change a route without downtime?">
    Save it. It takes effect on the next request. For a breaking change, add a new path and migrate clients.
  </Accordion>
</AccordionGroup>

## Before you publish a route

1. **Is the path outside resource space,** and does the Overview report no problems?
2. **Is the policy named,** and does it fail closed?
3. **Is the body declared** with `input_fields` (or checked in the flow)?
4. **Does the handler exist** in this environment: the flow promoted, or the function deployed?
5. **Does the response contain only what the caller may see?**
6. **Does every error have a status and a code** a client can switch on?
7. **Is there a rate limit** where the route costs something?
8. **Is the cache time, if any, short,** and the policy about the caller only?
9. **Do keys have `routes:invoke`** only where they should?
10. **Do the other doors** (`/flows/v1`, `/functions/v1`) have the policies you intend?
11. **Is there a test** for who may, what is accepted and what happens?

## What to remember

- **A route is an endpoint under `/rest/v1`, answered by a flow or a function.**
- **No policy means `authenticated`.** Public must be written.
- **Validation runs before the policy.**
- **Path parameters and query values are text.**
- **Without an input model, the body is unvalidated.** `GET` and `DELETE` bodies are ignored.
- **`input_fields` enforce required. `input_schema` does not.**
- **`response_schema` is documentation.** It does not trim or default.
- **A flow chooses its status and headers. A function cannot.**
- **A function's own policy is not applied through a route.**
- **A route's cache is not cleared by writes.**
- **A route cannot sit at a resource's path.** One created later is silently shadowed, and the Overview says so.
- **A route names its handler without checking it.** Promote flows with routes.

## Terms

| Term | Meaning |
| --- | --- |
| **Route** | A stored endpoint under `/rest/v1` with a method, a path, a policy and a handler |
| **Handler** | The flow or function a route runs |
| **Payload** | The `params`, `query` and `body` handed to the handler |
| **Input model** | `input_fields` or `input_schema`, which validate the body |
| **Plan-time policy** | The part of a policy decided before the body is read |
| **`$input`** | The validated body, as a policy condition sees it |
| **`routes:invoke`** | The API key scope a route needs |
| **Direct door** | `/flows/v1/<name>` and `/functions/v1/<name>`, which run a flow or function without a route |
| **Shadowed** | A route that a resource's own path hides |
| **Function** | A registered Python function that takes a context and returns JSON |
