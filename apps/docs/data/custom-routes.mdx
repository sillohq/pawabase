Resources cover CRUD. **Custom routes** cover everything else: *admit a student*, *record a payment*, *generate report cards*, *dashboard numbers*.

## Defining a route

```json
{
  "method": "POST",
  "path": "/finance/payments",
  "name": "record_payment",
  "description": "Record a fee payment and settle the invoice.",
  "policy": "finance_staff",
  "input_schema": "PaymentInput",
  "response_schema": null,
  "transformer": null,
  "handler_type": "flow",
  "handler": "record_payment",
  "rate_limit": { "limit": 60, "window": 60 },
  "cache_ttl": 0,
  "tags": ["Finance"],
  "enabled": true
}
```

<ParamField path="method" type="GET | POST | PUT | PATCH | DELETE" default="POST" />
<ParamField path="path" type="string" required>
  Served under `/rest/v1`. May contain `{params}`: `/report-cards/{id}/publish`. Can't shadow a resource's own routes (`/<resource>` or `/<resource>/{id}`).
</ParamField>
<ParamField path="policy" type="policy reference">
  Who may call it. `null` means the default (signed-in users).
</ParamField>
<ParamField path="input_fields | input_schema" type="fields | schema name">
  Validate the body with inline fields or a named [schema](/data/schemas). Omit both to accept any body.
</ParamField>
<ParamField path="handler_type, handler" type="'flow' | 'function', name" required>
  What runs. Flows receive `{params, query, body}` as `input`; functions receive the params merged with the body.
</ParamField>

## What the handler receives

<Tabs>
  <Tab title="Flow">
    ```json
    { "params": { "id": "42" }, "query": { "dry_run": "true" }, "body": { "...validated...": true } }
    ```
    Read it with templates: `{{ input.params.id }}`, `{{ input.body.amount }}`. The flow answers with a `response.return` block (status, body, headers). If it ends without one, the last step's output is returned with `200`.
  </Tab>
  <Tab title="Function">
    `ctx.input` is `{**params, **body}` (or the body itself if it isn't an object). `ctx.request` holds the original `{params, query, body}`. The return value is the JSON response.
  </Tab>
</Tabs>

## Errors

Flows fail requests deliberately with `error.raise`:

```json
{ "status": 409, "code": "invoice_closed", "message": "This invoice is closed" }
```

The client receives that status and `{"error": "invoice_closed", "message": "This invoice is closed"}`. An unexpected failure in a block returns `500` with `block_failed` and the run's trace is kept for inspection.

## Routes vs direct invocation

| | Custom route | `POST /flows/v1/<name>` | `POST /functions/v1/<name>` |
| --- | --- | --- | --- |
| URL | Your own path with params | Flow name | Function name |
| Input validation | Fields or schema | none | Function's `input_fields` |
| Policy | Route's | `trigger.http`'s `policy` | Function's `policy` |
| In OpenAPI | Yes, with your description | No | No |
| Rate limit, cache, transformer | Yes | No | No |

Use custom routes for your public API; direct invocation is handy for internal tools and tests.

## Idempotency

Workflows called from clients get retried: by users double-clicking, by mobile networks. Make them safe:

- check for an existing record first (like `issue_term_invoice` does per student and term);
- accept a client-supplied `reference` and refuse duplicates;
- return `409` with a clear `code` when the action already happened.
