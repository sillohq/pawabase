## Overview

A **Resource** is an application entity — `customers`, `orders`, `products` — that Pawabase turns into a REST collection under `/rest/v1/<name>`. You define it once, in Studio's visual editor (or through the platform API, which is what Studio itself calls), and Pawabase compiles it into real routes: a Pydantic request model per write operation, a policy check per operation, and the OpenAPI document that describes all of it.

A Resource definition is stored as data — a row in the environment's control-plane database, not code — so editing it in Studio takes effect the next time the environment's compiled state is rebuilt, with no deploy step. Everything on this page is what that stored definition contains and what each part controls.

This walkthrough builds `orders` for a small e-commerce backend, alongside `customers` and `products`, to show a realistic set of fields, relations, and operation policies rather than a toy example.

## Step 1 — Name the resource

The name becomes the URL segment: `/rest/v1/<name>`. It must match `^[a-z][a-z0-9_]{0,62}$` — lowercase letters, digits, and underscores, starting with a letter. Uppercase, hyphens, and leading digits are all rejected at save time.

```json
{"name": "orders", "description": "Customer purchase orders."}
```

### Reserved names

A small set of names are reserved because Pawabase's own routes live at the top level of `/rest/v1`, and a Resource sharing one of those names would collide with them:

```
docs, openapi.json, x, rpc, health, internal, platform
```

Trying to save a Resource named `health` or `platform` is rejected with `'<name>' is reserved`. Nothing else is reserved — `users`, `resources`, and `spaces` are ordinary, unreserved names you're free to use for your own Resources.

### The table name

By default, the Resource's table is the same as its name. You can point it at a different table with `table` (matching `^[A-Za-z_][A-Za-z0-9_]{0,62}$`) — useful when exposing a table that predates the Resource, or when the Resource name you want in the API doesn't match an existing table you don't control.

```json
{"name": "orders", "table": "customer_orders"}
```

### The primary key

`primary_key` (default `"id"`) names the identifying column. `id_type` is either `"integer"` (the default — an auto-incrementing integer assigned by the database) or `"uuid"` (generated in Python with `uuid.uuid4()` at create time; see [Field types](/data/field-types)). Both `primary_key` and `id_type` should be set before the first migration — changing `id_type` after the table exists is a manual operation, not something migrate does for you (see [Migrations](/data/migrations)).

```json
{"name": "orders", "primary_key": "id", "id_type": "uuid"}
```

## Step 2 — Add fields

`fields` is a list of field definitions — the same shape documented in full on [Field types](/data/field-types). Every field you declare becomes: a property in the compiled request models, a property in the response, a `filter[<field>]=`/`sort=` target on `list`, and — once you run a migration — a column in the table.

```json
{
  "fields": [
    {"name": "customer_id", "type": "integer", "required": true, "indexed": true},
    {"name": "status", "type": "string", "enum": ["pending", "paid", "fulfilled", "cancelled"], "default": "pending"},
    {"name": "total_cents", "type": "integer", "required": true, "minimum": 0},
    {"name": "notes", "type": "text"},
    {"name": "internal_cost_cents", "type": "integer", "write_only": true},
    {"name": "placed_at", "type": "datetime", "read_only": true}
  ]
}
```

### Field property reference

This is the complete set of keys a field definition accepts. Every one of these is read by the compiler (`pawabase_kit.schemas.compile_model`), the SQL layer, or both — nothing here is aspirational.

| Property | Type | Meaning |
| --- | --- | --- |
| `name` | string | The field identifier. Must match `^[A-Za-z_][A-Za-z0-9_]{0,62}$` and be unique within the Resource. |
| `type` | string enum | One of the fourteen [field types](/data/field-types). Defaults to `string` if omitted. |
| `required` | boolean | Enforced only on **create**; a create request that omits the field fails with a 422 — unless `default` is set, which makes it effectively optional. |
| `default` | any | Substituted when the field is absent from a create request. |
| `nullable` | boolean | Whether `null` is an accepted value. Defaults to `true` unless the field is `required`, and is forced `true` on update and read regardless of this setting. |
| `enum` | array | Restricts the field to a fixed set of values; overrides `type` entirely with those literal values. |
| `pattern` | string | A regex the value must match (string-like types). |
| `min_length` / `max_length` | integer | Character-count bounds (string-like types). |
| `minimum` / `maximum` | number | Inclusive value bounds (`integer`, `number`, `date`, `datetime`). |
| `items` | object | Field spec for each element, on `array` fields. |
| `fields` | array | Nested field list, on `object` fields. |
| `schema` | string | The name of a reusable [Schema](/data/schemas), on `ref` fields — required for that type. |
| `description` | string | Shown in the generated OpenAPI document. |
| `example` | any | Shown in the OpenAPI document as a sample value. |
| `read_only` | boolean | Excluded entirely from the create and update request models — a client can never set it. Still returned in reads. Use it for server-computed or server-stamped values. |
| `write_only` | boolean | Accepted in create/update request bodies but excluded from the read model — never returned. Use it for values you accept but don't want to echo back (an internal cost, a one-time token). |
| `indexed` | boolean | An index is created for this column the next time you run a migration. |
| `unique` | boolean | A unique index is created for this column the next time you run a migration (see the note on `unique` in [Migrations](/data/migrations) about when this is a column constraint versus an index). |

<Info>
`read_only` and `write_only` are opposite halves of the same idea and are easy to swap by mistake. `read_only` means "the server decides this, the client never sends it" (a computed timestamp, a status the platform manages). `write_only` means "the client sends this, the server never echoes it back" (a secret, a field you accept purely as input). See [Schemas](/data/schemas) for exactly which compiled model each is skipped from.
</Info>

The primary key is always implicitly `read_only` and `integer`-or-`uuid` typed in the compiled read model — you never declare it yourself in `fields`.

## Step 3 — Configure operations

`operations` controls which of the five REST verbs exist for this Resource, and what policy gates each one. **Every operation is disabled until you explicitly enable it** — an undeclared or `enabled: false` operation doesn't return a 403; the route doesn't exist at all, and requests to it 404.

```json
{
  "operations": {
    "list":   {"enabled": true, "policy": "authenticated"},
    "get":    {"enabled": true, "policy": "authenticated"},
    "create": {"enabled": true, "policy": "authenticated"},
    "update": {"enabled": true, "policy": "owns_order"},
    "delete": {"enabled": true, "policy": "admin_only"}
  }
}
```

The five keys are exactly `list`, `get`, `create`, `update`, `delete` — nothing else is recognized. Each operation's settings are just `enabled` (boolean, default `false`) and `policy` (a reference resolved against the environment's policy engine — see the policies documentation). If you enable an operation without a valid `policy` reference, the definition is rejected at save time; Pawabase does not let you publish an operation with no gate.

<Warning>
Enabling `create`, `update`, or `delete` with a policy of `"public"` genuinely means anonymous, unauthenticated internet traffic can write to this table. Pick policies deliberately per operation — `list`/`get` are frequently public, `create`/`update`/`delete` rarely are.
</Warning>

## Step 4 — Add relations

`relations` lets `?expand=<name>` on `list` and `get` attach related records, and documents the foreign-key semantics between Resources.

```json
{
  "relations": [
    {"name": "customer", "type": "belongs_to", "resource": "customers", "field": "customer_id"},
    {"name": "line_items", "type": "has_many", "resource": "order_items", "field": "order_id"}
  ]
}
```

Each relation needs `name`, `resource`, and `field`; `type` defaults to `belongs_to` if omitted.

| Relation type | Meaning | The foreign-key column `field` lives on | What `?expand=` returns |
| --- | --- | --- | --- |
| `belongs_to` | This record references one record of another Resource | This Resource's own table (e.g. `orders.customer_id`) | The single related record |
| `has_many` | Another Resource's records reference this one | The *related* Resource's table (e.g. `order_items.order_id`) | An array of related records |

Expansion is a read of the related Resource, not a raw join: it's filtered through that Resource's own `get`-or-`list` policy and shaped by its own transformer, so `orders?expand=customer` can never leak a customer field the `customers` Resource's own read policy wouldn't otherwise let this caller see. If the related Resource has no readable operation enabled at all, expansion silently returns nothing for non-service callers.

## Step 5 — Configure behavior

| Flag | Default | Effect |
| --- | --- | --- |
| `timestamps` | `true` | Maintains `created_at`/`updated_at` datetime columns automatically; set on create, `updated_at` refreshed on update. |
| `owner_field` | `null` | On create, stamps the authenticated caller's identity into this column and rejects unauthenticated non-service requests; on update, strips any client-sent value for this column so a caller can't reassign ownership. |
| `events` | `true` | Publishes `<name>.created` / `<name>.updated` / `<name>.deleted` events after each write. |
| `realtime` | `false` | Publishes changes to the `resource:<name>` channel for realtime subscribers. |
| `transformer` | `null` | A transformer (Pawabase's declarative response-reshaping mechanism) applied to reads and writes before the response is sent. |
| `cache_ttl` | `0` (off) | Seconds to cache `list`/`get` responses; `0`–`86400` (24h). Writes to the Resource invalidate the cache. |
| `rate_limit` | `{}` (off) | `{"limit": 100, "window": 60}`-style cap per caller. If you set `rate_limit`, it must include `limit`. |
| `tags` | `[]` | Free-text labels shown in Studio and in the OpenAPI document's tag grouping. |

```json
{
  "owner_field": "customer_id",
  "timestamps": true,
  "events": true,
  "realtime": false,
  "cache_ttl": 30,
  "rate_limit": {"limit": 60, "window": 60}
}
```

## Step 6 — Save, migrate, and test

Saving a Resource definition validates it and stores it — it does **not** touch the database. No table exists and no column is added until you explicitly run a migration for that Resource (see [Migrations](/data/migrations)); a Resource can be fully defined, saved, and even have live traffic hitting other operations, while its table still doesn't exist, in which case reads and writes fail until you migrate.

Saving does bump the environment's version counter, which invalidates the compiled application (routes, models, OpenAPI) — the next request after a save recompiles against the new definition, with no restart or deploy required.

Once you've migrated, test directly against the compiled routes:

```bash
curl -X POST https://<your-gateway>/rest/v1/orders \
  -H "apikey: <project-key>" \
  -H "Content-Type: application/json" \
  -d '{"customer_id": 42, "total_cents": 4999}'
```

## Common mistakes

- **Forgetting to enable an operation.** Every operation defaults to disabled; without `enabled: true` the route simply doesn't exist and every request to it 404s — this is easy to mistake for a policy problem when it's actually a missing `enabled` flag.
- **Enabling an operation with no policy.** Pawabase refuses to save an enabled operation with an unresolvable policy reference.
- **Forgetting to migrate after saving.** The definition can be perfectly valid and the table can still not exist. See [Migrations](/data/migrations).
- **Mixing up `read_only` and `write_only`.** `read_only` fields are things the server decides; `write_only` fields are things the client sends but never sees echoed back. Getting these backwards either silently drops client input or silently exposes something you meant to hide.
- **Confusing `belongs_to` and `has_many`.** `belongs_to` means the foreign key lives on *this* Resource's table; `has_many` means it lives on the *related* Resource's table. Getting the direction wrong produces an expansion that always returns empty (or errors on a column that doesn't exist).
- **Relying on `unique` alone to prevent duplicate inserts under concurrency.** `unique` creates a database-level unique index the next time you migrate — it does enforce uniqueness at the database, but only from the moment you've migrated it; declaring `unique: true` on a field with no migration yet run does not protect existing rows.

## Adding a field to a resource already in production

Because saving a definition and running a migration are separate steps, the safe sequence for a live Resource is:

1. Add the field in Studio (or via the platform API) and save. This is non-destructive by itself — nothing in the database changes yet, and existing traffic against the Resource's other fields is unaffected.
2. If the field is `required`, decide whether existing records need a value — a `required` field with no `default` means new creates must supply it, but it says nothing about rows that already exist, since `required` is enforced only on create, never on existing rows or on update.
3. Run the migration for that Resource. Pawabase adds the new column with `ALTER TABLE ... ADD COLUMN`; existing rows get the column with a `NULL` value (or the database's handling of a default, if the column has one) — no existing data is rewritten or dropped.
4. If you also set `indexed` or `unique` on the new field, the same migration run creates the corresponding index.

The reverse — removing a field from the definition — never drops the underlying column. Pawabase only ever adds columns; the field simply stops being exposed through the API. See [Migrations](/data/migrations) for exactly what does and doesn't happen, and why.

## Versioning and promotion

Every save bumps the environment's version counter, which the platform uses to invalidate and recompile the environment's application, decide what's cached, and track state between environments. `POST .../promote` copies definitions — Resources, Schemas, policies, and the rest — from one environment to another (e.g. `staging` → `production`) and bumps the target environment's version. Promotion copies the *definition*; it does not run migrations on the target. Run the migration on the target environment yourself after promoting, the same way you would on the source.

## FAQ

**Can I create a Resource with zero fields?** Yes — a Resource always has an implicit primary key (and, unless `timestamps: false`, `created_at`/`updated_at`), so an "empty" Resource still has a real table shape once migrated.

**Can I rename a Resource?** Not in place. Create a new Resource with the desired name, optionally pointing `table` at the existing underlying table so no data moves.

**Can I copy a Resource from one environment to another?** Yes, through environment promotion.

**What happens to existing data when I edit a field's constraints (say, add `minimum`)?** Nothing, immediately — constraints are enforced by the compiled validation model on the *next* request, not retroactively against rows already in the table. Existing rows that would now fail validation stay exactly as they are in the database; they just can't be written back through the API without first satisfying the new constraint.
