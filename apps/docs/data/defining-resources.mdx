## Overview

This page walks through creating a resource definition step by step, from the first name field to the final save. Each step is self-contained and can be read independently.

A resource definition is stored as JSON data in the platform's control-plane database. You can create it using Studio's visual editor, the platform API, or by importing a JSON file. The platform validates the definition at save time and rejects invalid configurations with specific error messages.

## Step 1 — Create a resource

Every resource starts with a name. This is the URL segment: it becomes /rest/v1/<name>. It must be a lowercase string matching ^[a-z][a-z0-9_]{0,62}$ and cannot be one of the platform's internal names (health, openapi, resources, spaces, user, users, or anything starting with _).

The description is optional but strongly recommended. It appears in the OpenAPI document and in Studio's resource list, helping every consumer of the API understand what a resource represents without reading its field definitions.

```json
{"name": "invoices", "description": "Fee invoices per student per term."}
```

## Step 2 — Add fields

Fields define the shape of your resource. Each field has a name, a type, and optional constraints. The fields array is the core of the resource definition. Every field you declare becomes a validated column in the response, a searchable/filterable parameter in list, and a column in the database when you run migrate.

| Field property | Type | Meaning | Required? |
| --- | --- | --- | --- |
| `name` | string | The field identifier | Yes |
| `type` | string enum | One of the platform's field types | Yes |
| `required` | boolean | Whether the field must be present on create | Default false |
| `default` | any | Default value when omitted | Type must match type |
| `enum` | array | Allowed values for string fields | Mutually exclusive with type enum |
| `pattern` | string | Regex for string fields | Applies to string type only |
| `maximum`/`minimum` | number | Bounds for number fields | Applies to number type only |
| `max_length` | integer | Max string length | Applies to string type only |
| `write_only` | boolean | Accept input, never return | Default false |
| `items` | object | Type of array elements | Applies to array type only |

## Field types reference

| Type | Validates as | Database column | Use case |
| --- | --- | --- | --- |
| `string` | String | VARCHAR(n) | Names, identifiers, text |
| `number` | Number | DECIMAL/NUMERIC | Amounts, scores, measurements |
| `integer` | Integer | INTEGER/BIGINT | Counts, ids, quantities |
| `boolean` | Boolean | BOOLEAN | Flags, toggles, status indicators |
| `date` | Date string | DATE | Birthdays, due dates, deadlines |
| `datetime` | Datetime string | TIMESTAMP | Event timestamps, deadlines |
| `array` | Array of items | TEXT[] or JSONB | Tags, lists, multiple selections |

## Step 3 — Configure operations

The operations object controls which HTTP verbs are enabled for this resource and what policy governs each one. Every operation defaults to disabled. You must explicitly set enabled: true and provide a policy identifier for each operation you want to expose.

```json
"operations": {"list": {"enabled": true, "policy": "family_access"}, "get": {"enabled": true, "policy": "family_access"}, "create": {"enabled": true, "policy": "finance_staff"}, "update": {"enabled": true, "policy": "finance_staff"}, "delete": {"enabled": true, "policy": "school_admin"}}
```

## Step 4 — Add relations

Relations define how this resource connects to other resources. They enable ?expand=<relation> on list and get, and they establish the foreign-key semantics between resources.

```json
"relations": [{"name": "student", "type": "belongs_to", "resource": "students", "field": "student_id"}, {"name": "payments", "type": "has_many", "resource": "payments", "field": "invoice_id"}]
```

| Relation type | Meaning | Foreign key lives on | Expand direction |
| --- | --- | --- | --- |
| `belongs_to` | This record references one of another resource | On this resource's table | Returns the related record |
| `has_many` | Another resource references this one | On the other resource's table | Returns a collection of related records |

## Step 5 — Configure behaviour

Behaviour flags control side effects and performance characteristics:

| Flag | Default | Effect |
| --- | --- | --- |
| `owner_field` | null | Stamp caller identity on create and prevent client override |
| `timestamps` | true | Maintain created_at and updated_at automatically |
| `events` | true | Emit <name>.created|updated|deleted events on writes |
| `realtime` | false | Publish to resource:<name> channel on writes |
| `transformer` | null | A Python function that rewrites the response |
| `cache_ttl` | 0 | Cache responses per-caller for N seconds |
| `rate_limit` | {} | Cap requests per caller per time window |
| `tags` | [] | Free-text labels for organizing resources |

## Step 6 — Save and test

After saving, the platform bumps the environment's version counter and caches the compiled state. The next request after a save triggers recompilation. You can test immediately with curl or Postman against the resource's endpoints.

## Common mistakes to avoid

- **Forgetting to enable operations**: Every operation defaults to disabled. Without enabled: true, the route does not exist and requests return 404.

- **Missing policy identifiers**: Every enabled operation requires a policy. The platform will refuse to save without one.

- **Using table as a field name**: Reserved words and internal names cannot be used as field names.

- **Setting required: true without a default**: Required fields must be provided on every create request.

- **Confusing belongs_to and has_many**: belongs_to means this record has a foreign key to the other resource. has_many means the other resource has a foreign key to this one.

## Versioning and promotion

Every save to a resource definition bumps the environment's version counter. This version number is used for cache invalidation, compilation tracking, and promotion workflows.

When you promote a resource definition from one environment to another, the platform copies the definition and bumps the target environment's version counter. This ensures that each environment has its own compiled state and that changes are tracked across environments.

## Troubleshooting

- The platform refuses to save the definition: check that all required fields are present and all values match the expected types.

- The API does not behave as expected after saving: compiled state may be cached. Retry with a fresh request.

- Relations do not work as expected: verify that the field name matches the actual foreign key column name and that the target resource exists.

- Operations return 404: check that the operation is enabled: true and that the policy identifier exists in the environment.

## FAQ

- Can I create a resource without any fields? No — every resource must have at least one field to define its shape.

- Can I change the name of an existing resource? Not in place. Create a new resource with the desired name and table pointing at the old table.

- Can I copy a resource definition from one environment to another? Yes — use environment promotion.

- Can I import an existing resource definition? Yes — you can import a JSON definition file using the platform API or Studio.

- What happens to existing data when I change a field definition? Existing data is preserved. New fields are added as columns. Removed fields are no longer exposed through the API.
