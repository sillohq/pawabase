Validation happens in the compiled app **before** policies and SQL, using the Pydantic models generated from your fields. Invalid input never reaches your database or your flows.

## Constraints

| Constraint | Types | Example |
| --- | --- | --- |
| `min_length`, `max_length` | string, text, email, url | `"max_length": 200` |
| `minimum`, `maximum` | integer, number | `"minimum": 0, "maximum": 100` |
| `pattern` | string | `"pattern": "^[A-Z]{3}\\d{3}$"` |
| `enum` | string, integer, number | `"enum": ["draft", "live"]` |
| `required` | all | present on create |
| `nullable` | all | `null` accepted |

Patterns are regular expressions; remember to escape backslashes in JSON (`\\d`).

## Three models per resource

For each resource the compiler builds:

- a **create** model: `required` applies, `read_only` fields are rejected, defaults fill gaps;
- an **update** model: every field optional (partial `PATCH`), `read_only` rejected;
- a **read** model: everything returned except `write_only`, lenient so legacy rows still serialise.

Unknown fields in a body are **rejected** (`extra="forbid"`), which catches typos like `titel`.

## Error format

```http
HTTP/1.1 422 Unprocessable Entity
```

```json
{
  "detail": [
    { "loc": ["body", "title"], "msg": "Field required", "type": "missing" },
    { "loc": ["body", "score"], "msg": "Input should be greater than or equal to 0", "type": "greater_than_equal" },
    { "loc": ["body", "status"], "msg": "Input should be 'draft' or 'live'", "type": "literal_error" }
  ]
}
```

`loc` points at the field, including nested paths (`["body", "guardian", "email"]`), which is easy to map onto form fields in a UI.

## Validation beyond fields

Some rules depend on other data: *a score can't exceed the assessment's maximum*, *a payment can't exceed the balance*. Express them where the data is:

- in a **policy**, when it's about who may do it (`{"lte": ["$input.amount", 1000]}` for a spending limit);
- in a **flow**, for rules that need lookups, using `control.if` + `error.raise` with a clear `code` and status:

```json
{ "block": "error.raise", "config": { "status": 422, "code": "score_above_max",
  "message": "A score is above the assessment's maximum" } }
```

Clients then receive `{"error": "score_above_max", "message": "…"}` with status 422.
