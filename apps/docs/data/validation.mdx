## Overview

Validation happens in the compiled application before policies and SQL ever run, using the Pydantic models generated from your field definitions. Invalid input never reaches your database, your flows, or your event handlers — it is caught at the HTTP boundary and returned as a structured 422 Unprocessable Entity response.

This page covers the complete validation system: every constraint, how the three models per resource are compiled, the exact error shape, validation that goes beyond field definitions, and how to validate inside flows.

## Why validation runs first

The request lifecycle for a POST or PATCH to a resource operation follows a strict order:

1. **Authentication** — the API key is verified and the platform context is resolved.

2. **Authorization** — the PolicyGate checks that the caller's credential passes the operation's policy.

3. **Validation** — the request body is validated against the resource's create or update Pydantic model. Unknown fields are rejected, required fields are checked, constraints are enforced.

4. **Policy refinement** — for create, the owner_field is stamped from the caller's identity and stripped from the input.

5. **Database** — the validated, policy-refined data is inserted or updated.

## The three models per resource

| Model | Used by | Required fields | write_only fields |
| --- | --- | --- | --- |
| **Create** | `POST /rest/v1/&lt;name&gt;` | All `required: true` fields | Accepted but never returned |
| **Update** | `PATCH /rest/v1/&lt;name&gt;/{id}` | None — every field is optional | Accepted but never returned |
| **Read** | `GET /rest/v1/&lt;name&gt;` and `GET /rest/v1/&lt;name&gt;/{id}` | N/A | Never returned |

## Required fields

Fields marked required: true must be present in create requests. If omitted, validation fails with a 422 error. The error response identifies the missing fields.

Required fields with default values are treated as having the default value if omitted. The default is applied before validation.

## Pattern and enum constraints

The pattern constraint enforces a regular expression match on string fields. If the client sends a value that does not match, validation fails with a 422 error.

The enum constraint restricts the field to a specific set of values. If the client sends a value not in the enum list, validation fails with a 422 error.

## Number constraints

The minimum and maximum constraints constrain numeric fields. The values must be within the specified range, inclusive.

Number fields also support exclusive_minimum and exclusive_maximum for strict inequality constraints.

## Array validation

Array fields validate that each element matches the items type. If any element fails validation, the entire array is rejected.

Array fields can have min_items and max_items constraints to limit the number of elements in the array.

## Conditional validation

The platform supports conditional validation where the presence or constraints of one field depend on the value of another field.

Conditional validation is evaluated after basic field validation but before the policy gate.

## Validation errors

When validation fails, the platform returns 422 Unprocessable Entity with a detailed error object. The error object identifies each field that failed validation and the reason for the failure.

The error response shape is consistent across all validation errors, making it easy to build client-side validation feedback.

## Validation and policies

Validation runs before policy evaluation. This means that a caller who does not have permission to access a resource will still receive validation errors for malformed requests.

This ordering prevents information leakage: permission errors do not reveal whether the request structure was valid.

## Best practices

Always validate the request body before sending it to the API. Client-side validation provides better feedback but should never be the only validation mechanism.

Use required fields for data that must always be present. Use default values for optional data that has a sensible initial value.

Use pattern and enum constraints to enforce specific formats and value sets.
