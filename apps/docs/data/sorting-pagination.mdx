## Overview

Sorting and pagination control how resource lists are ordered and divided into pages. They work together to provide efficient, navigable collections of records.

## Sorting

The sort query parameter accepts comma-separated field names. An optional `-` prefix sorts in descending order. Without a prefix, sorting is ascending.

The sort field must reference a declared field in the resource definition. Sorting by an undeclared field returns 400 Bad Request.

Multiple sort fields create a multi-level sort. For example, sort=-due_on,amount sorts by due_on descending first, then by amount ascending for records with the same due_on.

## Pagination

Pagination is controlled by the page and per_page query parameters. page defaults to 1 and per_page defaults to 20 with a maximum of 200.

The response always includes page, per_page, and total fields. page indicates the current page number. per_page indicates the page size. total indicates the total number of matching records.

| Parameter | Default | Range | Meaning |
| --- | --- | --- | --- |
| `page` | 1 | >= 1 | 1-indexed page number |
| `per_page` | 20 | 1-200 | Rows per page |

## Total count

The total field counts rows matching both filters and the caller's policy. It comes back null only when a residual policy prevents exact database-level counting.

When pushdown succeeds, total is exact because the database can compute it efficiently. When pushdown falls back to row-by-row filtering, total may be null.

## Select and expand with pagination

The select parameter allows column projection, returning only the specified fields. The primary key is always added back to the response.

The expand parameter embeds related records. When combined with pagination, the pagination applies to the parent resource's records. Each parent record includes its related records as a nested collection.

## Cursor-based pagination

For very large datasets, cursor-based pagination provides better performance than offset-based pagination. The platform supports cursor-based pagination through the after parameter.

Cursor-based pagination uses a stable cursor (the primary key of the last record on the current page) to fetch the next page. This avoids the performance degradation of large offsets.

## Sorting performance

Sorting is efficient when the sort field is indexed. The platform automatically creates indexes on frequently sorted fields.

Sorting by multiple fields or by unindexed fields may be slower. Consider using select to limit the fields returned and reduce the sort overhead.

## Best practices

Always specify per_page to avoid fetching too many records. The default of 20 is reasonable for most use cases.

Use sort to order results meaningfully. Default sort order is by primary key ascending.

Use cursor-based pagination for datasets with more than 10,000 records.
