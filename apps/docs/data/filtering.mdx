List endpoints accept any number of filters as query parameters:

```text
?filter[<field>]=<operator>.<value>
```

A bare value means `eq`: `?filter[status]=active` equals `?filter[status]=eq.active`.

<Warning>
Filters **must** use the `filter[…]` form. A plain `?status=active` is ignored and returns every row you may see, a common bug in clients. Wrap your calls in a helper that always emits `filter[…]` (see [JavaScript](/clients/javascript)).
</Warning>

## Operators

| Operator | Meaning | Example |
| --- | --- | --- |
| `eq` | equals | `filter[status]=eq.paid` |
| `neq` | not equal | `filter[status]=neq.void` |
| `gt`, `gte` | greater than (or equal) | `filter[score]=gte.50` |
| `lt`, `lte` | less than (or equal) | `filter[due_on]=lt.2026-10-01` |
| `like` | case-sensitive match, `*` wildcard | `filter[title]=like.Math*` |
| `ilike` | case-insensitive match, `*` wildcard | `filter[email]=ilike.*@example.com` |
| `in` | one of, comma-separated | `filter[status]=in.issued,overdue` |
| `nin` | none of | `filter[grade]=nin.E8,F9` |
| `is` | `null`, `true` or `false` | `filter[returned_on]=is.null` |
| `isnot` | the opposite | `filter[middle_name]=isnot.null` |

Filters combine with **AND**. For OR logic across fields, use a [custom route](/data/custom-routes) backed by a flow with `db.query`.

## Types

Values are converted using the field's type before they reach SQL: `filter[published]=true` on a boolean field compares with a real boolean, dates compare as dates, integers as integers. Filtering on a field that isn't declared on the resource returns `400 cannot filter on unknown field 'x'`, so undeclared columns stay invisible.

## Examples

```bash
# overdue invoices for one student, newest first
GET /rest/v1/invoices?filter[student_id]=12&filter[status]=overdue&sort=-due_on

# books whose title contains "sun", any case
GET /rest/v1/library_books?filter[title]=ilike.*sun*

# loans not yet returned and due before today
GET /rest/v1/library_loans?filter[returned_on]=is.null&filter[due_on]=lt.2026-09-28

# a class's register for a day
GET /rest/v1/attendance_records?filter[class_id]=7&filter[date]=2026-09-28
```

## Filters and policies

Your filters and the policy's SQL conditions are **AND**-ed together. You can never filter your way into rows a policy hides; you can only narrow what you're allowed to see. The `total` in the response counts rows matching both, so pagination stays exact.
