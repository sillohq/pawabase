## Overview

`list` accepts any number of `filter[<field>]` query parameters, ANDed together, translated into a SQL `WHERE` clause before pagination and sorting run. There is no OR between filter parameters and no bracket-nested operator syntax — the operator lives inside the value, separated by a dot: `filter[<field>]=<operator>.<value>`.

```bash
curl "$GW/rest/v1/orders?filter[status]=eq.live&filter[total]=gte.10000" \
  -H "apikey: $PK" -H "Authorization: Bearer $TOKEN"
```

That request returns orders where `status` equals `"live"` **and** `total` is greater than or equal to `10000`. Every `filter[...]` parameter you add narrows the result set further; there is no way to express "status is live OR status is pending" as two `filter[status]` parameters — see [Filters can't express OR](#filters-cant-express-or) below for the workaround.

## The syntax, precisely

```
filter[<field>]=<operator>.<value>
```

- `<field>` must be a field declared on the resource (or the primary key, or a timestamp column, or the owner field — anything in the resource's field map). Filtering on an undeclared name returns `400 Bad Request`.
- `<operator>` is one of the twelve operators below, followed by a literal dot.
- `<value>` is everything after the first dot — including any further dots, which matters for values like `2026-09-30T10:00:00.000Z`.

**A bare value with no operator prefix defaults to `eq`.** `filter[status]=live` and `filter[status]=eq.live` are exactly equivalent. This also covers the case where your value happens to contain a dot but isn't meant as an operator: if what comes before the first dot isn't a recognized operator, the whole raw string is treated as the value under `eq` rather than raising an error. `filter[email]=jane.doe@example.com` is filtered as `eq` on the literal string `jane.doe@example.com` — `jane` is not a recognized operator, so the parser falls back to treating the entire value as an equality match rather than failing.

## The operator set

These twelve are the complete, exact set the platform recognizes — there is no `contains`, `starts`, `ends`, `icontains`, or `neq`-as-a-typo-for-`ne`:

| Operator | SQL equivalent | Meaning |
| --- | --- | --- |
| `eq` | `=` | Equals (also the default with no operator prefix) |
| `neq` | `<>` | Not equal |
| `gt` | `>` | Greater than |
| `gte` | `>=` | Greater than or equal |
| `lt` | `<` | Less than |
| `lte` | `<=` | Less than or equal |
| `like` | `LIKE` | Pattern match, case-sensitive (dialect-dependent) |
| `ilike` | `ILIKE` on Postgres, `LIKE` elsewhere | Pattern match, case-insensitive |
| `in` | `IN (...)` | Value is one of a comma-separated list |
| `nin` | `NOT IN (...)` | Value is none of a comma-separated list |
| `is` | `IS NULL` / `IS (NOT) <bool>` | Null or boolean identity check |
| `isnot` | `IS NOT NULL` / `IS NOT <bool>` | Negated null or boolean identity check |

An operator string that isn't one of these twelve is **not** an error by itself — because of the fallback described above, `filter[status]=foo.bar` is parsed as `eq` on the literal value `"foo.bar"`, not as an attempt to use an operator named `foo`. The only way to get a `400` from an operator problem is to use `is` or `isnot` with something other than `null`, `true`, or `false` (see below) — every other combination either matches one of the twelve operators or silently becomes an `eq` on the raw string.

## Equality and inequality

```bash
filter[status]=eq.published        # status = 'published'
filter[status]=published           # identical — bare value defaults to eq
filter[status]=neq.draft           # status <> 'draft'
```

## Numeric and date comparisons

`gt`, `gte`, `lt`, and `lte` work on any field whose stored type supports ordering — integers, numbers, dates, and datetimes.

```bash
# Orders placed on or after 1 Sept 2026
filter[created_at]=gte.2026-09-01T00:00:00Z

# Orders under $50 (price_cents is an integer column storing cents)
filter[price_cents]=lt.5000

# A closed range: total between 10,000 and 50,000 inclusive
filter[total]=gte.10000&filter[total]=lte.50000
```

Note the last example: a *range* on one field is expressed as two separate `filter[total]` parameters with different operators — `gte` and `lte` — not as a single parameter. Query-string parsing allows repeating a key, and the platform collects every `filter[total]=...` occurrence into its own `Filter` and ANDs them all, so this works exactly as shown.

## `like` and `ilike`: the wildcard is `*`, not automatic substrings

This is the operator most commonly implemented differently elsewhere, so it deserves its own section. `like` and `ilike` do **not** perform automatic substring matching — passing a bare word does not mean "contains this word." Instead, the platform takes whatever you pass as the value and substitutes every literal `*` character for SQL's `%` wildcard, then passes the result straight to the database's `LIKE` (or `ILIKE` on Postgres).

```bash
# Titles containing "invoice" anywhere
filter[title]=like.*invoice*

# Titles starting with "Draft"
filter[title]=like.Draft*

# Titles ending in ".pdf"
filter[title]=like.*.pdf

# A literal value with NO wildcard at all behaves like an exact match under LIKE
filter[title]=like.Invoice
```

If you send `filter[title]=like.invoice` (no `*` anywhere), you get a `LIKE` with no wildcard — which matches only rows where the column is exactly `"invoice"`, the same as `eq` would (modulo any `%`/`_` already present in the underlying data). Forgetting the `*` characters is the single most common filtering mistake against this operator; if a `like`/`ilike` filter is "returning nothing," check that you actually included the `*` wildcards you intended.

`ilike` is case-insensitive on Postgres (native `ILIKE`). On dialects without a native case-insensitive `LIKE`, `ilike` is downgraded to the same case-sensitive `LIKE` as the `like` operator — plan your data (e.g. a normalized lowercase column) if case-insensitive matching must be guaranteed across every database backend you might deploy to.

```bash
# Case-insensitive search for "widget" anywhere in the name, on Postgres
filter[name]=ilike.*widget*
```

SQL's other special character, the underscore `_` (matches exactly one character in `LIKE`), is **not** escaped or substituted by the platform — if your data or search term contains literal underscores, they behave as single-character wildcards in the resulting SQL, which is worth knowing if a `like` filter matches more than you expect on columns containing underscores.

## `in` and `nin`: membership

```bash
# status is one of pending, overdue
filter[status]=in.pending,overdue

# status is none of these
filter[status]=nin.draft,archived
```

The value is split on commas into a list; each element is encoded according to the field's declared type before being compared. There's no way to escape a literal comma inside one of the list elements — if a field's legitimate values could contain commas, `in`/`nin` isn't a safe operator to filter it with; use repeated `eq` filters combined client-side instead, or a custom route.

## `is` and `isnot`: null and boolean identity

`is`/`isnot` are narrower than the name suggests — they accept **exactly** `null`, `true`, or `false` as the value (case-insensitively: `Is.NULL` and `is.null` behave the same). Anything else is rejected outright with `400 Bad Request`, which is the one true syntax error `parse_filters` can raise from an operator body (as opposed to the `eq`-fallback behavior every other malformed operator gets):

```bash
filter[deleted_at]=is.null          # deleted_at IS NULL
filter[deleted_at]=isnot.null       # deleted_at IS NOT NULL
filter[featured]=is.true            # featured IS TRUE (or = true, dialect-dependent)
filter[archived]=is.false           # archived IS FALSE
```

```bash
# This raises 400 — "id/isnot take null, true or false"
filter[featured]=is.yes
```

```json
{"error": "bad_request", "message": "is/isnot take null, true or false"}
```

Do not use `eq.null` to check for null — `eq` encodes its value according to the field's type and compares with `=`, which in SQL never matches `NULL` regardless of what string you pass. Always use `is.null` / `isnot.null` for null checks.

## Filtering by field type

| Field type | Sensible operators | Example |
| --- | --- | --- |
| `string` / `text` | `eq`, `neq`, `like`, `ilike`, `in`, `nin`, `is`/`isnot` (null) | `filter[status]=eq.live` |
| `integer` / `number` | `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `in`, `nin` | `filter[amount]=gt.10000` |
| `boolean` | `is`, `isnot`, `eq` | `filter[active]=is.true` |
| `date` / `datetime` | `eq`, `gt`, `gte`, `lt`, `lte` | `filter[due_on]=gte.2026-01-01` |
| `uuid` | `eq`, `neq`, `in`, `nin` | `filter[id]=in.<uuid>,<uuid>` |

Dates and datetimes must be sent in a form the encoder for that column can parse — ISO 8601 (`2026-09-30` for `date`, `2026-09-30T10:00:00Z` for `datetime`) is the safe, well-supported form. An unparseable date value fails at the encoding stage with a database error, not a friendly `400` — validate date-shaped filter values client-side before sending them.

## Combining filters (AND only)

Every distinct `filter[...]` parameter — whether on the same field or different fields — is combined with `AND`. There is no `OR` in the filter query-string language.

```bash
# status = 'overdue' AND balance > 0 AND due_on < today
curl "$GW/rest/v1/invoices?filter[status]=eq.overdue&filter[balance]=gt.0&filter[due_on]=lt.2026-09-30" \
  -H "apikey: $PK" -H "Authorization: Bearer $TOKEN"
```

### Filters can't express OR

If your use case genuinely needs "status is `overdue` OR status is `cancelled`," the `in` operator covers the common case where the OR is over the *same field*:

```bash
filter[status]=in.overdue,cancelled
```

For an OR across *different fields* (e.g. "either `priority` is `high` OR `assignee_id` is null"), there is no query-string way to express it. Reach for a custom route backed by a flow or function, where you have full control over the query, or fetch a broader page with fewer filters and finish the OR client-side (acceptable only for small result sets, since it bypasses the database's own filtering efficiency and page-level pagination no longer means what you'd expect).

## Filter pushdown and policies

Filters you send are combined, at the SQL level, with whatever the caller's policy contributes — a policy can add its own equality conditions (for example, "only rows where `tenant_id` matches the caller's tenant") that are ANDed in alongside your `filter[...]` parameters, invisibly to the client. A filter and a policy narrowing the same field don't conflict; they simply both apply. See [Resources → total is null](/data/resources#what-residual-means-for-total) for what happens when a policy's row-level condition can't be pushed into SQL at all.

## Realistic business scenarios

**An orders list scoped to a date range and a status:**

```bash
curl "$GW/rest/v1/orders?filter[status]=in.paid,fulfilled&filter[created_at]=gte.2026-09-01T00:00:00Z&filter[created_at]=lt.2026-10-01T00:00:00Z&sort=-created_at" \
  -H "apikey: $PK" -H "Authorization: Bearer $TOKEN"
```

**Products under a price threshold that are still active:**

```bash
curl "$GW/rest/v1/products?filter[active]=is.true&filter[price_cents]=lte.5000" \
  -H "apikey: $PK" -H "Authorization: Bearer $TOKEN"
```

**A support-ticket search box translated to a `like` filter:**

```bash
curl "$GW/rest/v1/tickets?filter[subject]=ilike.*payment+failed*" \
  -H "apikey: $PK" -H "Authorization: Bearer $TOKEN"
```

(Remember to URL-encode the space and any other reserved characters in the actual request; the `*` wildcards themselves don't need encoding.)

**Excluding soft-deleted rows modeled with a nullable `deleted_at` column:**

```bash
curl "$GW/rest/v1/customers?filter[deleted_at]=is.null" \
  -H "apikey: $PK" -H "Authorization: Bearer $TOKEN"
```

## Errors

| Situation | Status | Body |
| --- | --- | --- |
| `filter[<field>]` names an undeclared field | `400` | `{"error": "bad_request", "message": "cannot filter on unknown field '<field>'"}` |
| `is`/`isnot` with a value other than `null`/`true`/`false` | `400` | `{"error": "bad_request", "message": "is/isnot take null, true or false"}` |
| An unrecognized operator prefix | *No error* — treated as `eq` on the full raw string | — |
| A filter value that can't be encoded for the field's type (e.g. non-numeric value for an integer column) | Database-level error, surfaced as an unhandled error | — |

## Troubleshooting

<AccordionGroup>
<Accordion title="My filter[name][contains]=... isn't working">
That bracket-operator syntax has never been how filtering works here. The operator goes inside the value with a dot, not in a second bracket: `filter[name]=like.*value*`.
</Accordion>
<Accordion title="filter[title]=like.invoice matches nothing, even though rows contain 'invoice' as part of a longer title">
like/ilike don't do automatic substring matching. Add the wildcard yourself: `filter[title]=like.*invoice*`.
</Accordion>
<Accordion title="filter[status]=neq.draft doesn't seem to be recognized">
Double-check you used neq, not ne — ne is not a valid operator here and would silently fall back to an eq match on the literal string "ne.draft" is not how it works either; the value after the first dot must follow a real operator token exactly as spelled: eq, neq, gt, gte, lt, lte, like, ilike, in, nin, is, isnot.
</Accordion>
<Accordion title="A date filter is returning a raw database error instead of a clean 400">
Unparseable date/datetime values fail at column encoding, not at the friendly filter-parsing stage. Validate the value is well-formed ISO 8601 before sending it.
</Accordion>
<Accordion title="I need OR between two different fields and filter[] can't do it">
Correct — filter[] is AND-only across every parameter. Use in.a,b for an OR over one field's values, or move the logic into a custom route.
</Accordion>
</AccordionGroup>

## FAQ

<AccordionGroup>
<Accordion title="Can I filter on a relation's fields, like filter[student.class_name]=Math?">
No. Filters only resolve against the resource's own fields — there is no cross-resource JOIN in the filter language. See Relations → the expand/filter boundary for the real boundary and the workaround.
</Accordion>
<Accordion title="Is filtering case-sensitive?">
eq, neq, and the comparison operators are exact-match against the database's own collation, which is typically case-sensitive on Postgres. like is case-sensitive; ilike is case-insensitive on Postgres and falls back to case-sensitive like elsewhere.
</Accordion>
<Accordion title="What happens if I send the same filter[field] twice with the same operator?">
Both are kept and ANDed — filter[status]=eq.a&filter[status]=eq.b is equivalent to status = 'a' AND status = 'b', which matches nothing unless a and b are the same value. This is rarely what you want; use in for an OR over one field.
</Accordion>
</AccordionGroup>
