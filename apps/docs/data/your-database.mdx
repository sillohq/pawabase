## Overview

Every environment in a Pawabase project has its own database for Resource data — completely separate from the platform's own control-plane database (which stores your project's definitions, audit log, and sessions). Pawabase supports three dialects for an environment's database: **SQLite**, **PostgreSQL**, and **MySQL**. If you don't configure one, the environment defaults to a SQLite file — SQLite is the platform's actual default, not an afterthought, and it's a genuinely fine choice through early development. This page covers configuring each dialect, what Pawabase does and doesn't manage in your database, and how to choose between them.

## One database per environment

```text
Project: shop
├── development  →  sqlite file, managed automatically
├── staging      →  PostgreSQL at db.staging.example.com
└── production   →  PostgreSQL at db.prod.example.com
```

Each environment's database is completely independent: a table created in `development` doesn't exist in `staging` or `production` until you define the same Resource there and migrate it, and data inserted in one environment is invisible to every other. This is what makes it safe to experiment freely in `development` without any risk to `production` data.

## The default: SQLite

If you don't set a database connection for an environment, Pawabase uses a SQLite file, one per project/environment pair, created automatically the first time the environment's database is touched. There's no setup step — no connection string, no server to run — which is why it's the default: it's the fastest path to a working environment, and it's a real, fully-supported dialect, not a stand-in that gets swapped out later. It just runs against a file rather than a server, so it's naturally suited to development and small deployments rather than a database several processes need to share concurrently.

You don't need to do anything to use it — it's simply what an environment gets until you configure something else in Studio under **Settings → Infrastructure → Database**.

## Configuring PostgreSQL or MySQL

For staging and production, or for development if you'd rather match production's dialect from the start, set a connection string per environment:

1. Open your project in Studio.
2. Go to **Settings → Infrastructure**.
3. Under **Database**, enter the connection URL for this environment.

```text
postgresql://user:password@host:5432/database_name
```

```text
mysql://user:password@host:3306/database_name
```

Pawabase detects the dialect from the connection URL itself — there's no separate "dialect" dropdown to also get right. Each environment's connection is independent: `staging` and `production` are two different URLs, typically two different database instances, configured separately in each environment's own Infrastructure settings.

<Warning>
The database user needs `CREATE`, `ALTER`, and `DROP TABLE` privileges (Pawabase never issues `DROP TABLE` itself today, but the permission set your provider offers usually bundles `CREATE`/`ALTER`/`DROP` together) on the schema it uses, since migrations run real DDL against this connection. It does not need superuser or database-admin privileges — scope it to the one database and schema this environment uses.
</Warning>

## What Pawabase creates — and when

Nothing is created automatically on first write. **A table only exists after you explicitly run a migration for that Resource** (`POST .../resources/{name}/migrate`, or Studio's "Migrate" action) — see [Migrations](/data/migrations) for the full mechanics. Before that, the Resource can be fully defined and even have some operations enabled, but reads and writes against it fail because the underlying table doesn't exist yet.

Once migrated, here's what a typical generated table looks like on PostgreSQL, for a Resource `orders` with a `uuid` primary key:

```sql
CREATE TABLE IF NOT EXISTS "orders" (
    "id" UUID PRIMARY KEY,
    "customer_id" BIGINT,
    "status" VARCHAR(255),
    "total_cents" BIGINT,
    "created_at" TIMESTAMPTZ,
    "updated_at" TIMESTAMPTZ
);

CREATE UNIQUE INDEX IF NOT EXISTS "ix_orders_customer_id" ON "orders" ("customer_id");
```

Notice there's no `DEFAULT gen_random_uuid()` on `id`, and no `NOT NULL` anywhere. Both are deliberate:

- **UUID primary keys are generated in Python, not by the database.** Pawabase calls `uuid.uuid4()` at the moment a record is created and inserts the value explicitly, rather than relying on a database-side default. This is why it works identically across all three dialects — SQLite and MySQL have no built-in random-UUID generator, so a database-side default wouldn't be portable across them, but a Python-side one is.
- **`required` is never turned into a column-level `NOT NULL`.** It's enforced only on create requests, at the validation layer — see [Migrations](/data/migrations) for what this means for existing rows when you add a required field later.

For an `integer` primary key, the generated column uses each dialect's own auto-increment mechanism: `INTEGER PRIMARY KEY AUTOINCREMENT` on SQLite, `BIGSERIAL PRIMARY KEY` on PostgreSQL, `BIGINT AUTO_INCREMENT PRIMARY KEY` on MySQL.

## What Pawabase never creates or manages

Pawabase does not manage:

- Tables you create yourself outside a Resource definition — they're left entirely alone.
- Columns you add manually to a Resource's table — migrations never remove a column, whether you added it yourself or it was ever declared in the definition (see [Migrations](/data/migrations)).
- Database users, roles, or grants.
- Extensions — if your data needs one (`pgcrypto`, `postgis`, etc.), install it yourself against the database directly; Pawabase never issues `CREATE EXTENSION`.
- Triggers, stored procedures, views, or foreign-key constraints — relations between Resources (`belongs_to`/`has_many`) are enforced at the application layer through policies and expansion, not as database foreign keys.

## Connecting to your database directly

For imports, backups, or debugging beyond what the [Database console](/data/database-console) offers, connect with your dialect's own client, using the connection string from **Settings → Infrastructure → Database**:

```bash
psql "postgresql://user:password@host:5432/database_name"
```

```bash
mysql -h host -u user -p database_name
```

```bash
sqlite3 storage/data/<project>__<env>.db
```

<Warning>
Direct access bypasses every Resource-level policy, validation rule, transformer, and event. Changes you make this way are not reflected in audit logs or event subscriptions — nothing about Pawabase's application layer knows they happened. Prefer the resource API for anything routine, and the [Database console](/data/database-console) (which is at least audited and cache-invalidation-aware for writes) for anything ad hoc; reserve a fully direct connection for migration, backup, and recovery scenarios the console doesn't cover.
</Warning>

## Choosing a dialect for a new project

**SQLite** is the right choice for early development: zero setup, a single file you can inspect, back up, or throw away trivially, and it's the platform default so there's nothing to configure. Its limits show up around concurrent write throughput and multi-process access to the same file — it's not the dialect to reach for once several people or processes need to write to the same database at once under real load.

**PostgreSQL** is the platform's most complete production option: it's the dialect the DDL generator and value codecs were clearly built with the most headroom for (native `UUID`, `JSONB`, `TIMESTAMPTZ`, `BIGSERIAL`), and it's a reasonable default choice for a production environment unless you have a specific reason to prefer MySQL.

**MySQL** is fully supported — the same migrate/query/console machinery works against it — with a few dialect-specific realities worth knowing going in: `datetime` values are stored timezone-naive (Pawabase normalizes to UTC before writing, but the column itself carries no offset, so all values in it are UTC by convention rather than by the database enforcing it), and its `JSON` column type is what every structured field (`json`, `array`, `object`, `ref`) uses in place of PostgreSQL's `JSONB`. Choose MySQL when it's already what your team runs and operates, rather than switching dialects specifically for Pawabase's sake.

Whichever you choose for production, it's worth developing against the same dialect locally when your application depends on dialect-specific SQL through the [Database console](/data/database-console) — a query using PostgreSQL's `jsonb_array_elements` won't run against a SQLite development database, for instance.

## Database requirements

Pawabase itself has no hard version floor for any of the three dialects beyond what its dependencies (Tortoise's database drivers, PyPika) require — verify current driver compatibility for your target database version rather than assuming a specific minimum. Connection pool sizing, disk space, and backup cadence are entirely your responsibility to plan for your own data volume and traffic; Pawabase doesn't impose or enforce sizing defaults on a database you've configured yourself.

## Backups and recovery

You are responsible for backing up an environment's database — Pawabase manages schema migrations (additive DDL, on your request) but performs no backups of its own. For a self-hosted installation, see [Backups](/self-hosting/backups). For a managed database (RDS, Cloud SQL, a managed Postgres provider), use that provider's backup tooling.

<Info>
The platform's own control-plane database (project and environment definitions, audit log, sessions — configured separately from any environment's data database) is distinct from every environment's Resource database covered on this page. Back up both, but understand they're separate systems: losing the platform database loses your definitions and audit history; losing an environment's data database loses that environment's records.
</Info>

## Database console

For inspecting data, running ad hoc queries, or one-off fixes without setting up a separate direct connection, use Studio's [Database console](/data/database-console) — it runs against whichever database you've configured for the environment, SQLite, PostgreSQL, or MySQL alike, with the same interface either way.
