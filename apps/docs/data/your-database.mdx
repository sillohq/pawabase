Every Pawabase environment has its own **database** — the database where your resource tables, schemas, and data live. The platform connects to it automatically based on configuration in Studio, and manages schema migrations as you define resources.

## One database per environment

```text
Project: school
├── development  →  PostgreSQL at db.dev.example.com
├── staging      →  PostgreSQL at db.staging.example.com
└── production   →  PostgreSQL at db.prod.example.com
```

Each environment's database is completely independent. Tables created in `development` don't exist in `production` until you create the same resource there. Data inserted in one environment is invisible to all others.

You configure the database connection per environment in Studio:

1. Open your project in Studio.
2. Go to **Settings → Infrastructure**.
3. Under **Database**, enter the connection string for this environment.

The connection string follows standard PostgreSQL format:

```text
postgresql://username:password@hostname:5432/database_name
```

<Warning>
The database user must have `CREATE`, `ALTER`, and `DROP` privileges on the target database, plus full access to all schemas it uses. Pawabase manages tables and indexes automatically; restricting DDL permissions will cause resource compilation to fail.
</Warning>

## What Pawabase creates

When you create a resource in Studio and it receives its first write, Pawabase creates the table and columns automatically:

```sql
-- Resource: invoices
CREATE TABLE "invoices" (
    "id" uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    "title" text NOT NULL,
    "amount_cents" integer NOT NULL,
    "status" text DEFAULT 'pending' NOT NULL,
    "due_on" date,
    "created_at" timestamptz NOT NULL DEFAULT now(),
    "updated_at" timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX "invoices_status_idx" ON "invoices" ("status");
```

- Tables use the `public` schema by default (configurable per resource).
- The `id` column is a UUID with a default of `gen_random_uuid()`.
- `created_at` and `updated_at` are managed automatically.
- Indexes are created automatically for fields used in filters and relations.

## What Pawabase does not create

Pawabase does **not** manage:
- Tables you create manually (they're left alone unless you delete the resource)
- Columns you add manually (they survive resource changes)
- Database users, roles, or grants
- Extensions (you must install these yourself: `CREATE EXTENSION IF NOT EXISTS ...`)
- Triggers or stored procedures

If you need database-level extensions (like `pgcrypto`, `postgis`, etc.), create them directly:

```sql
CREATE EXTISION IF NOT EXISTS "uuid-ossp";
```

<Info>
Pawabase uses `gen_random_uuid()` (from `pgcrypto`) for default IDs, not `uuid_generate_v4()`. The `pgcrypto` extension is pre-installed on most managed PostgreSQL services.
</Info>

## Connecting to your database directly

Sometimes you need to connect to the database directly — for data imports, backups, or debugging:

1. **Find the connection string** in Studio under Settings → Infrastructure → Database.
2. **Use any PostgreSQL client** — psql, your IDE, or a connection pooler.

```bash
psql postgresql://pawabase:secret@your-db.example.com:5432/pawabase_prod
```

<Warning>
Direct database access bypasses all resource policies, validation, and events. Changes you make directly to the database are not reflected in resource definitions, transformers, or audit logs. Use the API or database console for normal operations; direct access is for migration, backup, and emergency recovery only.
</Warning>

## Schema management

### Changing a resource maps to ALTER TABLE

When you add, remove, or change a field in Studio:

| Change | Database effect |
| --- | --- |
| Add a field | `ALTER TABLE ADD COLUMN` |
| Remove a field | Column is **not** dropped (data is preserved; the field is just hidden from the API) |
| Change type | `ALTER TABLE ALTER COLUMN TYPE` (may fail if data can't be cast) |
| Make required | `ALTER TABLE ALTER COLUMN SET NOT NULL` (fails if existing rows have NULL) |

<Warning>
Removing a field from a resource does **not** drop the database column. To permanently remove a column, use the database console or connect directly. This prevents accidental data loss from a resource edit.
</Warning>

## Database requirements

| Requirement | Minimum version | Notes |
| --- | --- | --- |
| PostgreSQL | 16 | Required for `gen_random_uuid()`, RLS, and window functions. |
| Disk space | 10 GB minimum | Pawabase doesn't enforce a minimum; plan for your data volume. |
| Connection pool | 20 per API instance | Set `max_connections` on your database accordingly. |
| Extensions | `pgcrypto` | Needed for UUID generation. Pre-installed on most managed services. |

## Backups and recovery

You are responsible for backing up your database. The platform doesn't automatically back up your data — it only manages schema migrations.

For a self-hosted installation, see [Backups](/self-hosting/backups). For managed databases (e.g., AWS RDS, Supabase), use your provider's backup features.

<Info>
The platform database (at `PAWABASE_PLATFORM_DB`) stores project definitions, audit log, and user sessions. This is **separate** from your per-environment databases. Back up both.
</Info>

## Database console

For inspecting data, running ad-hoc queries, or doing one-off fixes, use Studio's built-in [Database console](/data/database-console). It runs SQL directly against your environment's database, with no need to set up a separate connection.
