## Two databases, two jobs

A Pawabase installation touches two kinds of database, and confusing them is the root of most questions on this page.

| | Control-plane database | Environment database (this page) |
| --- | --- | --- |
| **Holds** | Projects, environments, every definition (resources, schemas, flows, policies, routes), keys, secrets (encrypted), the audit log | The **rows** your resources store: the tables created by [migrations](/data/migrations) |
| **Configured by** | `PAWABASE_DATABASE_URL` in the installation's environment file | `PAWABASE_DEFAULT_DATA_URL` in the same file |
| **Count** | One | One per environment, which may be the same server |
| **You read it through** | Studio | `/rest/v1`, the Records tab, and the **Database** page |
| **Lose it and you lose** | Your definitions and history | That environment's records |

Everything below is about the second column. A migration, a `GET /rest/v1/tickets`, the Records tab and the Database console all run against the **environment database** of the environment you are in.

<Note>
Database configuration lives in **one place: the environment file** (`.env`, or the variables your deployment injects). It is not configured in Studio, and it is not something you set through the platform's HTTP routes. Studio says so itself: the **Settings** page reads *Infrastructure (database, storage, mail) is configured once for the whole installation via .env, not per environment here.*
</Note>

## How Pawabase picks the database

Every environment's database comes from one setting, **`PAWABASE_DEFAULT_DATA_URL`**, a URL **template**. For each request that touches data, Pawabase replaces `{project}` with the project's ref and `{env}` with the environment's name, and connects to the result.

That is the entire rule. There is no per-resource database, no per-request choice, and no fallback chain: one environment, one URL, and the URL is derived from the template.

```text
PAWABASE_DEFAULT_DATA_URL=postgres://pawabase_app:<password>@db.internal:5432/{project}_{env}

shop / development  →  postgres://…@db.internal:5432/shop_development
shop / staging      →  postgres://…@db.internal:5432/shop_staging
shop / production   →  postgres://…@db.internal:5432/shop_production
```

So the template decides **how environments are separated**: by database name (as above), by SQLite file name, or, when the template has no placeholders, not at all (they share tables, and on PostgreSQL the `pb_<hash>_` prefix keeps them apart).

Three consequences:

- **One template means one server and one set of credentials.** Every environment of every project in an installation connects to the same host as the same role. To give production its own server, run production in its own installation, with its own environment file.
- **Pawabase never creates databases.** The template names databases, and you create them (and the role that owns them) before the first migration.
- **The dialect comes from the URL scheme.** `sqlite://` is SQLite, `postgres://` or `postgresql://` is PostgreSQL, and `mysql://` is MySQL, so there is no dialect setting to keep in step.

## What the default is

The default is a setting of your installation, so what it is depends on how you run Pawabase.

| How you run it | `PAWABASE_DEFAULT_DATA_URL` | Result |
| --- | --- | --- |
| `docker-compose.yml` (production layout) | `postgres://pawabase:<POSTGRES_PASSWORD>@postgres:5432/pawabase` unless you set it | **One shared PostgreSQL database** for every project and environment, with prefixed table names |
| `docker-compose.dev.yml` | `sqlite:///data/envs/{project}__{env}.db` | **One SQLite file per environment**, created on first use |
| API run directly with no setting | `postgres://pawabase:pawabase@127.0.0.1:5432/pawabase` (the setting's built-in default) | A local PostgreSQL that must exist |

<Warning>
Several other pages in this documentation describe SQLite as the platform default. That is true of the development compose file only. The built-in default and the production compose file both use PostgreSQL. Check `PAWABASE_DEFAULT_DATA_URL` in your own installation, and the **Database** page in Studio, which shows the dialect actually in use.
</Warning>

### Shared PostgreSQL and prefixed table names

When the template resolves to PostgreSQL, tables get a prefix, so that environments (and projects) that share a database never collide on a table name. To keep two environments' `tickets` tables from colliding, Pawabase gives the physical table a prefix:

```text
pb_<first 12 hex characters of sha256("<project>:<environment>")>_<table>      (cut to 63 characters)
```

So `tickets` in `acme/production` is a table called something like `pb_9c41e0d27a1b_tickets`. The resource is still `tickets`, `/rest/v1/tickets` still works, and the prefix only matters when you connect with another tool. To find a physical name, read the `table` in the response of **Create / migrate table**, or compute the hash yourself:

```python
import hashlib
print("pb_" + hashlib.sha256(b"acme:production").hexdigest()[:12] + "_tickets")
```

The prefix applies whenever the data URL is PostgreSQL, whether or not the template separates environments by database name. With a SQLite or MySQL URL, tables keep the exact name you declared.

### SQLite files

With the SQLite default, the file for `shop/development` is created at the path in the URL with `{project}` and `{env}` filled in, for example `/data/envs/shop__development.db`. Missing parent directories are created. The connection uses WAL journaling, which lets readers continue while a write happens.

SQLite URLs have a trap in how many slashes they have:

| URL | File |
| --- | --- |
| `sqlite:///data/envs/a__b.db` | **`/data/envs/a__b.db`**, an absolute path (three slashes) |
| `sqlite://data/envs/a__b.db` | `data/envs/a__b.db`, relative to the API's working directory (two slashes) |
| `sqlite://:memory:` | An in-memory database that disappears when the process stops |

Inside a container, the three-slash form puts the file at the container's `/data`, which should be a mounted volume. A relative path written into a container with no volume loses its data when the container is replaced.

## Where you see which database an environment uses

Studio shows it in three places.

**Overview.** The infrastructure panel lists the database as `platform default` or `configured`. Because the database comes from the environment file, expect `platform default` here, and read it as "the installation's database", not "a built-in one". The panel also lists storage, mail, cache, queue and events, so one glance tells you which pieces are real:

```json
{
  "database": "platform default",
  "storage": "local",
  "mail": "suppressed (not configured)",
  "cache": "MemoryCache",
  "queue": "SyncConnection",
  "events": "memory"
}
```

**Build → Database.** The page header reads *Browse the environment's database. Bring your own with a database URL in Settings.* (the URL is set in the environment file, as described below, and not on that page) and the **Tables** card lists every table, with a green badge naming the resource when the table's name equals the resource's declared `table`. A table with no badge is either not managed by a resource, or, on a PostgreSQL template without per-environment databases, carries the `pb_<hash>_` prefix, which the badge lookup does not account for (this is read from the code, not run against PostgreSQL). It also shows the dialect and `your database` or `platform default` above the list. The platform API behind it returns the dialect and whether the database is the configured one:

```json
{
  "dialect": "sqlite",
  "configured": false,
  "tables": [{ "name": "things", "resource": "things" }]
}
```

**The platform overview.** `GET /platform/v1/overview` lists every open connection the API process holds:

```json
[
  { "alias": "acme:development", "dialect": "sqlite", "connected": true },
  { "alias": "acme:development", "dialect": "sqlite", "connected": false }
]
```

Each entry is a connection **to a URL**. The alias is the environment that opened it first. After a URL is switched, the old connection stays in the list, still open, and an environment whose connection failed shows up with `connected: false`. See [the connection pool](#the-connection-pool).

## Configuring the database in the environment file

Everything is set with two variables. Where you set them depends on how you run Pawabase:

| How you run it | Where the variables go |
| --- | --- |
| Docker Compose | The `.env` file next to `docker-compose.yml`, which the compose file reads (`PAWABASE_DEFAULT_DATA_URL: ${PAWABASE_DEFAULT_DATA_URL:-...}`) |
| Another container platform | The service's environment, from your platform's secret or config store |
| The API run directly | The shell environment, or the `.env` the API loads from its working directory |

```bash
# the control plane: projects, definitions, keys, the audit log
PAWABASE_DATABASE_URL=postgres://pawabase:<password>@postgres:5432/pawabase

# the environment databases: one per project and environment, from this template
PAWABASE_DEFAULT_DATA_URL=postgres://pawabase_app:<password>@postgres:5432/{project}_{env}
```

### The steps

<Steps>
  <Step title="Create the databases and the role">
    On the server, create a role and one database per project and environment the template will produce (`shop_development`, `shop_staging`, `shop_production`). See [a role for Pawabase](#a-role-for-pawabase). Confirm the role can connect from the API's host with your database's own client. If that fails, nothing Pawabase does will fix it.
  </Step>
  <Step title="Set the template">
    Put `PAWABASE_DEFAULT_DATA_URL` in the environment file, with `{project}` and `{env}` where the names belong. Percent-encode special characters in the password (`p@ss` is `p%40ss`).
  </Step>
  <Step title="Restart the API">
    The variable is read when the API starts, so a change needs a restart (`docker compose up -d api`, or your platform's equivalent). Open connections to the old URLs are closed by it.
  </Step>
  <Step title="Migrate each resource">
    The new databases have no tables. Until you press **Create / migrate table** for each resource, reads of it answer `500`. See [Migrations](/data/migrations).
  </Step>
  <Step title="Confirm">
    Open **Build → Database**. The line above the table list names the dialect, the tables are listed with their resources, and a read through `/rest/v1` answers `200`.
  </Step>
</Steps>

### Templates for the common layouts

| You want | `PAWABASE_DEFAULT_DATA_URL` |
| --- | --- |
| One PostgreSQL database per project and environment | `postgres://app:<password>@db:5432/{project}_{env}` |
| One database per project, environments kept apart by table prefix | `postgres://app:<password>@db:5432/{project}` |
| One database for everything (the compose default), kept apart by table prefix | `postgres://app:<password>@db:5432/pawabase` |
| A SQLite file per environment | `sqlite:///data/envs/{project}__{env}.db` |
| MySQL, one database per project and environment | `mysql://app:<password>@db:3306/{project}_{env}?charset=utf8mb4` |
| TLS to a managed PostgreSQL | `postgres://app:<password>@host:5432/{project}_{env}?ssl=require` |

Database names are plain text, so choose project refs and environment names that are valid in them (lowercase letters, digits and underscores are always safe).

### Which one it is, in practice

The Overview's infrastructure panel and the **Database** page's dialect line show what is in use. They report the installation's database, so after you set the variable, the line should show your dialect (`postgres`, `mysql` or `sqlite`).

### Where the Secrets page fits

Studio's **Secrets** page is for values your flows and functions read (provider keys, shared tokens), and the connection URL does not go there. The data plane reads its database URL from the environment file, not from a stored secret.

## Connection URL syntax

The URL is parsed by the database layer under Pawabase (Tortoise), and these results were produced by running the parser on each form.

| URL | Meaning |
| --- | --- |
| `postgres://user:pass@host:5432/dbname` | PostgreSQL, through asyncpg |
| `postgresql://user:pass@host/dbname` | The same. Port defaults to 5432 |
| `asyncpg://user:pass@host/dbname` | Also accepted, the same driver |
| `postgres://user:pass@host/dbname?ssl=require` | PostgreSQL over TLS. `ssl=require` and `ssl=true` both turn it on |
| `postgres://user:pass@host/dbname?minsize=2&maxsize=10` | Pool size hints are read from the query string, as text values |
| `mysql://user:pass@host:3306/dbname` | MySQL. Port defaults to 3306 |
| `mysql://user:pass@host/dbname?charset=utf8mb4` | MySQL with an explicit character set |
| `sqlite:///data/envs/shop.db` | SQLite, absolute path `/data/envs/shop.db` |
| `sqlite://relative/path.db` | SQLite, relative path |
| `mariadb://...` | **Not recognised.** Use `mysql://` for MariaDB |
| anything else | Refused with `invalid database URL: Unknown DB scheme: ...` |

Special characters in a password must be percent-encoded: `p@ss` is `p%40ss`. The parser decodes `%40` back to `@` and the connection then authenticates correctly.

<Note>
`minsize` and `maxsize` come through the URL as strings. They are the driver's pool settings, and how a given driver version treats them is its own business, so test a value in a non-production environment before relying on it.
</Note>

### What an invalid or missing URL does

| Situation | Data plane answers |
| --- | --- |
| A URL with an unknown scheme | **503** with `invalid database URL: Unknown DB scheme: ...` |
| A template that leaves `{env}` or `{project}` in a place that makes an invalid URL | **503**, with the driver's error in the message |
| A well-formed URL whose server refuses the connection | **503** with `could not connect to the environment database: ConnectionRefusedError: ...` |
| A server that is up but rejects the login | **503**, with the driver's error in the message |
| A database that is up and has no tables yet | **500**, a plain `Internal Server Error` on reads |

A 503 from `/rest/v1` means Pawabase could not reach the database at all, and the body says so:

```json
{
  "error": "database_unavailable",
  "message": "could not connect to the environment database: ConnectionRefusedError: [Errno 61] Connect call failed ('127.0.0.1', 1)"
}
```

That is the useful distinction in the table: **503 means the connection**, **500 on a read means the table or column**. A client can treat 503 as "retry later" and 500 as "something is wrong with the data".

<Warning>
Studio's **Database** page is less graceful than the data plane. When the environment's database is unreachable, the overview request fails with a plain 500 instead of the 503 body, so Studio shows an error rather than an explanation. Use the data plane's 503 message, or the platform overview's `connected: false`, to diagnose.
</Warning>

## The connection pool

Pawabase keeps one connection object per **URL** in each API process.

- **Keyed by the resolved URL.** Two environments that resolve to the same URL share one connection. Two environments with different URLs do not.
- **Opened lazily.** The first request that needs the database connects. There is no connection at startup.
- **Closed on restart.** A change to the template takes effect when the API restarts, which closes every pooled connection. Until then, connections to the old URLs stay open. A project that rotates its database several times in a day accumulates open connections to the old ones.
- **Per process.** Each API replica has its own pool. Three replicas against one PostgreSQL means three sets of connections, so a server's connection limit is something to budget for.
- **Retried.** A connection that failed is recorded as not connected, and the next request tries again, so a database that was down comes back without restarting anything.

The consequences for operations:

| You do | Effect |
| --- | --- |
| Rotate a password by writing a new value to the same secret | The resolved URL changes, so a **new connection** opens with the new password. Nothing uses the old URL any more, but its connection stays open until the process restarts, so restart the API before you revoke the old password |
| Switch two environments to the same URL | They share one connection |
| Scale to more replicas | Connections to the database multiply by the replica count |
| Restart the API | All pooled connections are closed |

<Tip>
Plan database `max_connections` as: (replicas) × (environments on that server) × (pool size per connection) plus whatever else connects. A small managed database with a low connection limit is the most common reason a scaled-out Pawabase starts failing with 503.
</Tip>

## Switching the database

Changing `PAWABASE_DEFAULT_DATA_URL` moves **every environment of every project** at the next restart. What changes the moment the API restarts with the new value:

| Before | After |
| --- | --- |
| Reads and writes go to the old databases | They go to the **new** databases, on the very next request |
| Tables exist | **No tables exist** in the new databases |
| Rows are present | **No rows are present**, because nothing was copied |

A migration always runs against the database the API is currently connected to, so you cannot migrate into the new databases while the API still points at the old ones. That decides the order of a safe switch: prepare, schedule a short window, switch, migrate, copy, verify.

<Steps>
  <Step title="Create the new databases and the role">
    One database per project and environment, owned by the role in the new URL. See [a role for Pawabase](#a-role-for-pawabase).
  </Step>
  <Step title="Rehearse on a copy">
    Start a **second installation** (a staging copy of your compose project, with its own environment file) pointed at the new databases. Restore a backup of the old data into them, run the migrations, and test your application against it. This is where problems with sizes, types and grants appear, with no risk to production.
  </Step>
  <Step title="Announce a window and pause writes">
    Stop clients writing, or accept a short read-only period. Writes made after your final copy would otherwise be lost.
  </Step>
  <Step title="Copy the data">
    Dump from the old databases and load into the new ones, table by table, keeping the key columns as they are. See [moving existing data](#moving-existing-data-to-a-new-database).
  </Step>
  <Step title="Switch and restart">
    Change `PAWABASE_DEFAULT_DATA_URL` and restart the API. If the new databases already hold the migrated tables and the copied data (because you prepared them with the database's own tools, or by migrating during the window), requests succeed at once.
  </Step>
  <Step title="Verify">
    Compare row counts and a checksum, read records in the **Records** tab, and run your tests.
  </Step>
</Steps>

### Going back

Restore the previous value of `PAWABASE_DEFAULT_DATA_URL` and restart. The old databases were never touched, so the old data is visible again. Anything written to the new databases while the switch was live is **not** in the old ones, so switch back only before writes resume, or copy them back.

## Moving existing data to a new database

Pawabase has no export or import for row data. Use the database's own tools, and remember that the **physical table names** differ between the platform default and your own database: a table that is `pb_9c41e0d27a1b_tickets` in the shared default is `tickets` in yours.

### From the shared PostgreSQL default to your own PostgreSQL

```bash
# 1. Find the physical table name: the `table` in a migrate response, or compute the hash.
# 2. Dump only the data of that table from the shared database.
pg_dump "$SHARED_URL" --data-only --table=pb_9c41e0d27a1b_tickets > tickets.sql

# 3. Rename the table in the dump, then load into the new database,
#    after the new tables have been created by migrating there.
sed -i.bak 's/pb_9c41e0d27a1b_tickets/tickets/g' tickets.sql
psql "$NEW_URL" < tickets.sql
```

Then reset the key sequence, because a data-only load does not advance it:

```sql
SELECT setval(pg_get_serial_sequence('tickets', 'id'), COALESCE(MAX(id), 1)) FROM tickets;
```

Without that, the next create reuses an existing id and fails with a plain 500 on the primary key.

### From SQLite to PostgreSQL

SQLite stores booleans as `0` and `1`, datetimes as text with offsets, and JSON as text, so a straight dump does not load. Use a tool that converts types (`pgloader` is the usual one), or export each table as CSV and load it with explicit casts:

```sql
\copy tickets (id, subject, status, created_at) FROM 'tickets.csv' WITH (FORMAT csv, HEADER)
```

Load into the columns Pawabase created, so the types are PostgreSQL's. Check boolean and datetime columns afterwards, and reset sequences as above.

### What does not move by itself

| Item | Where it lives |
| --- | --- |
| Definitions (resources, schemas, flows, policies) | Control-plane database. Unaffected by a data switch |
| Records of every resource | **Moved by you** |
| Uploaded files | Storage, not the database |
| Secrets, keys, users | Control plane, and the auth service |
| Cached lists | The cache. Entries from before the switch may show old data until they expire or a write invalidates them. See [Caching](/data/caching) |

## A role for Pawabase

Give Pawabase a role of its own, scoped to one database, and no more.

### What the role needs

Pawabase issues exactly these kinds of statement against an environment database:

| Statement | When |
| --- | --- |
| `SELECT`, `INSERT`, `UPDATE`, `DELETE` | Every API request and the Records tab |
| `CREATE TABLE IF NOT EXISTS` | A migration, for a new resource |
| `ALTER TABLE ... ADD COLUMN` | A migration, for a new field |
| `CREATE [UNIQUE] INDEX` | A migration, for indexed, unique and owner fields |
| Table and column listing | Studio's Database page and every migration (it reads the catalog) |
| Whatever you type in the console | Subject to the console's read-only default |

It never issues `DROP`, `TRUNCATE`, `CREATE EXTENSION`, `GRANT`, or anything that changes roles. So the role does **not** need `DROP` or superuser rights, and an earlier version of this page was wrong to say it does.

### PostgreSQL

```sql
CREATE ROLE pawabase_app LOGIN PASSWORD '<password>';
CREATE DATABASE shop OWNER pawabase_app;
```

Owning the database is the simplest grant: the role can create tables and indexes in it and nothing outside it. If the database already exists and has other tables, grant narrowly instead:

```sql
GRANT CONNECT ON DATABASE shop TO pawabase_app;
GRANT USAGE, CREATE ON SCHEMA public TO pawabase_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO pawabase_app;
```

Tables the role creates are owned by it, which gives it every privilege on them. Tables that already exist (a legacy table you map a resource onto) need an explicit grant:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON legacy_customers TO pawabase_app;
GRANT USAGE, SELECT ON SEQUENCE legacy_customers_id_seq TO pawabase_app;
```

The sequence grant is the one that is forgotten. Without it, inserts fail with a permission error on the sequence.

### MySQL

```sql
CREATE DATABASE shop CHARACTER SET utf8mb4;
CREATE USER 'pawabase_app'@'%' IDENTIFIED BY '<password>';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX ON shop.* TO 'pawabase_app'@'%';
```

Restrict the `'%'` host to your API's address range where you can.

### SQLite

There are no roles. The API process needs read and write access to the file and to its directory, because WAL mode creates `-wal` and `-shm` files next to the database.

### A read-only role for people

For analysts and reporting tools, create a separate role that can read only:

```sql
CREATE ROLE reporting LOGIN PASSWORD '<password>';
GRANT CONNECT ON DATABASE shop TO reporting;
GRANT USAGE ON SCHEMA public TO reporting;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO reporting;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO reporting;
```

This is the safe way to give someone a SQL connection. It bypasses policies and transformers like any direct connection, so it should still be limited to people allowed to see everything in those tables.

## The environment file, in practice

A few habits make the file reliable.

### Which file the stack reads

With Docker Compose, the `.env` next to `docker-compose.yml` supplies variables that the compose file passes into the API container. A variable in the file but not mentioned in the compose file's `environment:` block does not reach the container, so confirm the compose file names `PAWABASE_DEFAULT_DATA_URL` (the shipped one does, with a default). To see what the API actually received, inspect the running container's environment rather than the file:

```bash
docker compose exec api printenv | grep PAWABASE_DEFAULT_DATA_URL
```

That one command settles most "I changed it and nothing happened" questions: either the value is not the one you set, or the API was not restarted.

### Quoting and special characters

| Situation | Write |
| --- | --- |
| A password with `@`, `:`, `/`, `?` or `#` | Percent-encode it: `p@ss/word` is `p%40ss%2Fword` |
| A value with `$` | Double it in a compose `.env` (`$$`), or the file's own interpolation will eat it |
| A value with spaces | There should not be any in a URL |
| A template with braces | Leave `{project}` and `{env}` exactly as written. Do not let your shell or a templating tool expand them |

### One file per installation

Each installation has its own file, and the file is the record of how that installation is wired. Keep a **template of the file** (with the secrets blanked) in source control, so a new installation starts from the same shape, and keep the real values in your secret store.

### Changing it safely

1. Edit the value in the file (or the secret store).
2. Read the new value back from the running container after the restart, as above.
3. Make one read through `/rest/v1` and look at the platform overview: the entry for the new URL should say `connected: true`.
4. Check **Build → Database** for the dialect and tables.

If step 3 shows `connected: false`, the data plane answers `503` with the driver's error, and the message is the quickest diagnosis there is.

### What does not take effect

| You changed | Takes effect |
| --- | --- |
| The environment file only | Not until the API restarts |
| A Studio setting | Never, for the database. Studio has no setting for it |
| A definition (resource, route, flow) | Immediately, but it does not touch the database URL |
| The database itself (a password, a host) | When the API next opens a connection. A password change on the server breaks open connections, so restart the API |

## Complete examples

### A small team on one server

```bash
# control plane
PAWABASE_DATABASE_URL=postgres://pawabase:<password>@postgres:5432/pawabase

# one database per project and environment, on the same server
PAWABASE_DEFAULT_DATA_URL=postgres://pawabase_app:<password>@postgres:5432/{project}_{env}
```

The server holds `pawabase` (the control plane) and one database per project and environment. Backups are one dump per database.

### A managed PostgreSQL with TLS

```bash
PAWABASE_DATABASE_URL=postgres://pawabase:<password>@pg.example.com:5432/pawabase?ssl=require
PAWABASE_DEFAULT_DATA_URL=postgres://pawabase_app:<password>@pg.example.com:5432/{project}_{env}?ssl=require
```

### Development on SQLite

```bash
PAWABASE_DEFAULT_DATA_URL=sqlite:///data/envs/{project}__{env}.db
```

One file per environment under the mounted `/data` volume, which is what `docker-compose.dev.yml` does.

### Production and staging as two installations

```bash
# staging installation's .env
PAWABASE_DEFAULT_DATA_URL=postgres://stg_app:<password>@db-staging:5432/{project}_{env}

# production installation's .env
PAWABASE_DEFAULT_DATA_URL=postgres://prod_app:<password>@db-prod:5432/{project}_{env}
```

Different hosts, different roles, different files. Neither installation can reach the other's data, which is the strongest separation the template model offers.

## Choosing a dialect

All three dialects run the same resources, the same API and the same console. What differs is what the database underneath is good at.

| | SQLite | PostgreSQL | MySQL |
| --- | --- | --- | --- |
| **Setup** | None. A file | A server, a role, a database | A server, a user, a database |
| **Concurrent writers** | One writer at a time (WAL lets readers continue) | Many | Many |
| **Several API replicas** | **No.** A file on one disk | Yes | Yes |
| **Native types** | Text, integer, real | `UUID`, `JSONB`, `TIMESTAMPTZ`, `BOOLEAN`, `BIGSERIAL` | `JSON`, `DATETIME(6)`, `BOOLEAN`, `CHAR(36)` for UUIDs |
| **Column length limits** | None | `VARCHAR(n)` from `max_length`, default 255 | Same |
| **Datetime storage** | ISO text, offset kept | Instant with time zone | Naive UTC |
| **Unique text comparison** | Case-sensitive | Case-sensitive | **Case-insensitive** by default |
| **Idempotent migrations** | Yes | Yes | **No** for indexes |
| **Best for** | Development, small single-process deployments | Production | Production where MySQL is already what you run |

### A recommendation

- **Develop on the dialect you will run in production.** A resource that works on SQLite can fail on PostgreSQL in ways the API cannot warn you about: a string longer than 255 characters, a uuid column that rejects a malformed value, a unique check that behaves differently, a type that stores a value SQLite accepts and PostgreSQL does not. Running the same dialect in development finds these before production does.
- **Use PostgreSQL for production** unless you already operate MySQL. It is the production layout of the compose file, every column type maps to a native type, and migrations are fully idempotent.
- **Use SQLite for a first afternoon**, for tests that must start instantly, and for single-user tools. Move off it before you add a second API replica, because a SQLite file cannot be shared safely between processes on different machines, and two replicas on one machine each hold their own connection to the same file.

### The environment can mix dialects

Because each environment picks its own database, you can run SQLite in `development` and PostgreSQL in `production`. It works, and the cost is the class of surprises above. A common middle path is PostgreSQL everywhere, with `development` on a small local container.

## SQLite in detail

| Topic | What to know |
| --- | --- |
| **Where the file is** | Wherever the URL says, with `{project}` and `{env}` filled in. Absolute with three slashes, relative with two |
| **Directories** | Created for you if missing |
| **Journal** | WAL, with a small size limit. You will see `<file>-wal` and `<file>-shm` beside the database while it is open |
| **Writes** | Serialized. One writer at a time, so a long write blocks other writes |
| **Types** | Loosely typed. A column keeps whatever you store, which hides type errors that other dialects raise |
| **Strings** | No length limit, so `max_length` is only an API check |
| **Datetimes** | ISO text with the offset you sent. Sorting is by text |
| **Booleans** | `0` and `1` |
| **`ALTER TABLE`** | Can add columns, and drop them from 3.35. Cannot change a type, so a rebuild is needed |
| **Replicas** | One only |

### Backing up a SQLite environment

Copy the file with the `.backup` command, not with `cp`, while the API is running, because a plain copy can miss data that is still in the `-wal` file:

```bash
sqlite3 /data/envs/shop__production.db ".backup '/backups/shop__production.db'"
```

Or stop the API, copy the file and the `-wal` and `-shm` files together, and start it again. Restoring is replacing the file while the API is stopped.

### The limits of a single file

A SQLite environment is bounded by one disk and one writer. Signs it is time to move: write latency that grows with traffic, a `database is locked` error in the logs, the need for a second API replica, or a database large enough that backups take noticeable time. Moving is a switch to PostgreSQL with a data copy, as described under [switching](#switching-the-database).

## PostgreSQL in detail

| Topic | What to know |
| --- | --- |
| **Driver** | asyncpg. The URL schemes `postgres://`, `postgresql://` and `asyncpg://` are all accepted |
| **TLS** | Add `?ssl=require` (or `ssl=true`) to the URL. Managed providers usually require it |
| **Schema** | Pawabase uses the role's default schema, normally `public`. There is no schema setting |
| **Tables** | On the shared default, prefixed `pb_<hash>_`. On your own database, as declared |
| **Keys** | `BIGSERIAL` for integer keys, `UUID` for uuid keys. UUIDs are generated by Pawabase, not the database |
| **JSON** | `JSONB` for `json`, `array`, `object` and `ref` fields |
| **Time** | `TIMESTAMPTZ`, so values are instants and are returned with an offset |
| **Migrations** | Fully idempotent: `IF NOT EXISTS` on every statement |
| **Extensions** | Never created by Pawabase. Install what you need yourself |

### Connection poolers

Managed providers often put a pooler (PgBouncer or a vendor equivalent) in front of the database. Pawabase holds a connection per URL per process and issues ordinary statements, with transactions used for multi-step writes. A pooler in **transaction** mode works with that, provided the driver is not relying on server-side prepared statements across transactions, so test one write path and one transaction (a flow with `db.transaction`) against your pooler in a non-production environment before relying on it. A pooler in **session** mode is the safest.

### Useful statements

```sql
-- Which tables belong to which environment on the shared default?
SELECT tablename FROM pg_tables WHERE tablename LIKE 'pb\_%' ORDER BY tablename;

-- How big is each table?
SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS size
FROM pg_catalog.pg_statio_user_tables ORDER BY pg_total_relation_size(relid) DESC;

-- Who is connected?
SELECT usename, application_name, state, count(*) FROM pg_stat_activity GROUP BY 1, 2, 3;
```

The first lists the shared default's prefixed tables. Match one to an environment by computing the hash for `<project>:<environment>`.

## MySQL in detail

| Topic | What to know |
| --- | --- |
| **URL** | `mysql://user:pass@host:3306/db`. `mariadb://` is not a recognised scheme. Use `mysql://` for MariaDB |
| **Character set** | Set `?charset=utf8mb4` so emoji and every script store correctly |
| **SQL mode** | The connection runs in `STRICT_TRANS_TABLES`, so an oversize or invalid value is refused instead of being cut or coerced |
| **Keys** | `BIGINT AUTO_INCREMENT` for integer keys. UUIDs are `CHAR(36)` |
| **JSON** | The native `JSON` type |
| **Time** | `DATETIME(6)` stored as **naive UTC**. A value sent as `10:00+02:00` is stored as `08:00` |
| **Unique text** | Compared case-insensitively under the default collation |
| **Migrations** | Table and column work is idempotent. Index statements are **not**, since MySQL has no `IF NOT EXISTS` for `CREATE INDEX` |
| **Quoting** | Backticks |

### Two behaviors to plan for

1. **Index statements repeat.** Every migration re-issues the index statements for fields marked `indexed`, `unique` or `owner_field`. On MySQL the repeats fail. See [MySQL has no IF NOT EXISTS on indexes](/data/migrations#mysql-has-no-if-not-exists-on-indexes).
2. **Case-insensitive uniqueness.** `Maya@acme.co` and `maya@acme.co` collide. If that is what you want, you get it for free. If you need them distinct, set a binary collation on the column yourself.

## Layouts for several environments

How you arrange the databases is a decision about blast radius and cost, made with one template and, when needed, more than one installation.

| Layout | How | When it fits |
| --- | --- | --- |
| **Everything in one database** | A template with no placeholders. On PostgreSQL, tables get the `pb_<hash>_` prefix | Getting started. The compose file's default |
| **One database per project** | `.../{project}` | A few projects, with environments kept apart by prefix |
| **One database per project and environment** | `.../{project}_{env}` | Most teams. Isolation by database, with one server to run |
| **Separate installations per tier** | Development and production each run their own Pawabase, with their own environment files and servers | Production kept apart from everything else, with its own backups, sizing and credentials |

One template means one set of credentials per installation, so the isolation between environments of one installation is the isolation between databases on one server. A mistake in `development` cannot write into `production`'s tables, because they are different databases, but the same role can reach both. When that is not enough, give production its own installation.

### A naming scheme

```text
shop_development
shop_staging
shop_production
```

with the role `pawabase_app` owning all of them. For stricter separation, the production installation uses another role and another server in its own file.

## Capacity and what to measure

Pawabase does not size your database for you, and it does not set a pool size beyond what the driver defaults to or what you pass in the URL. The numbers that matter:

| Measure | Why it matters | Where to look |
| --- | --- | --- |
| **Connections** | Replicas multiply them | `pg_stat_activity`, or your provider's dashboard |
| **Slow queries** | An unindexed filter or sort shows up here first | Your server's slow query log, plus `EXPLAIN` in the console |
| **Table and index size** | Drives backup time and cache pressure | The statements above |
| **Write rate** | SQLite's limit, and a replication budget elsewhere | Provider metrics |
| **Disk headroom** | A full disk turns every write into a 500 | Provider alerts |

Set an alert on disk and on connections. Both fail suddenly, and both are invisible from inside Pawabase until requests start failing.

## Direct connections

Sometimes you need to connect with your own tool: to import data, to back up, to investigate.

```bash
psql "postgres://pawabase_app:<password>@db.prod.example.com:5432/shop?sslmode=require"
mysql -h db.prod.example.com -u pawabase_app -p shop
sqlite3 /data/envs/shop__production.db
```

(`psql` uses `sslmode`, which is its own client's spelling. The `ssl=require` form is for the URL Pawabase reads.)

A direct connection bypasses **every** layer Pawabase adds: validation, policies, transformers, the audit log, events, webhooks, realtime and cache invalidation. The write lands in the table and nothing else hears about it.

| What you do directly | What does not happen |
| --- | --- |
| Insert a row | No `resource.created` event, no webhook, no realtime message, no audit entry. Cached lists may stay stale |
| Update a row | The same, and `updated_at` is not touched unless you set it |
| Delete a row | The same, and nothing cleans up rows that refer to it |
| Change a column | The resource's definition does not follow |

If the change should be visible to the rest of the system, either make it through the API, or finish by making any write to the resource through the API (which invalidates the cache tag), or use the [console](/data/database-console), whose writes are recorded in the audit log as `database.write` (with the SQL, cut to 2,000 characters) and invalidate every resource's cache.

<Warning>
Use a **separate role** for direct access, and give the role the least it needs. A direct connection with the application's own role can do anything the application can, with no checks.
</Warning>

## Keeping the connection secret

The database URL carries a password, so treat it like one.

| Practice | Why |
| --- | --- |
| Keep the environment file **out of source control** | A committed password is a leaked password |
| Restrict the file's permissions to the account that runs the stack | Anyone who can read it has the database |
| Inject the variable from your platform's secret store where there is one | The value never sits in a file on disk |
| Require TLS (`?ssl=require`) | The URL travels from the API to the database on your network, and TLS keeps it private |
| Restrict the database's network access to the API hosts | A password is the second line of defence, and the network is the first |
| Do not store connection strings in definitions or settings | Studio shows definitions to everyone who can open the environment |

### Who can read what

| Reader | Sees |
| --- | --- |
| Whoever can read the environment file or the platform's secret store | The URL and its password |
| Someone with **platform operator** rights | Everything that can run through the console: any table's rows. They do not need the password |
| Someone with a **publishable or secret API key** | Only what the policies of each resource allow |

An operator reaches the data without ever seeing the password, because the platform holds the connection. That is the model: **credentials stay on the host, and people reach the data through audited paths**. A person with the URL bypasses all of it, which is why direct access deserves its own, narrower role.

<Warning>
Pawabase's environment record has a field that can store a connection string. Do not use it. A value stored there is kept as plain text and is returned, password included, to anyone who can read the environment. Studio does not offer it for that reason, and this page does not rely on it.
</Warning>

### Rotating the password

<Steps>
  <Step title="Create the new credential">
    On the database server, set a new password for the role, or create a second role with the same grants. For zero downtime, create a second role.
  </Step>
  <Step title="Update the environment file">
    Put the new password (or the new role) in `PAWABASE_DEFAULT_DATA_URL` and in `PAWABASE_DATABASE_URL` if it changed too.
  </Step>
  <Step title="Restart the API">
    The restart makes new connections with the new credential and closes the old ones. With several API processes, restart them one at a time.
  </Step>
  <Step title="Confirm traffic uses it">
    Make a read through `/rest/v1`, and check the database's connection list for connections under the new role.
  </Step>
  <Step title="Revoke the old credential">
    Drop the old role, or change its password. Nothing uses it now.
  </Step>
</Steps>

### If a URL was exposed

If a connection string was committed, pasted into a ticket or shared in a chat, rotate the password as above, and look at the database's connection log for connections you do not recognise, since the password may have been used before you noticed.

## What to watch

Pawabase reports one thing about the database: whether it can connect. Everything else is your database's own monitoring.

| Signal | Where | What it means |
| --- | --- | --- |
| `503 database_unavailable` on `/rest/v1` | Responses, and the [Observability](/operate/observability) log | The connection failed. The message carries the driver's error |
| `connected: false` in the platform overview | `GET /platform/v1/overview` | A URL whose connection failed and has not succeeded since |
| 500 on a read for one resource only | Responses | That resource's table or a column is missing. See [Migrations](/data/migrations) |
| 500 on creates only | Responses | A constraint: a unique index, a length, a type, a missing column |
| Slow lists | Response times | An unindexed filter or sort. See [Filtering](/data/filtering) and [Sorting and pagination](/data/sorting-pagination) |
| Disk full | Your provider | Writes fail as 500s |

A simple external check is a read of one small resource with a publishable key, once a minute. A 200 means the whole path works (gateway, API, connection, table). A 503 says the database. A 500 says the data.

## Troubleshooting

| What you see | Cause | Fix |
| --- | --- | --- |
| **503** `could not connect to the environment database: ConnectionRefusedError` | The host or port is wrong, the server is down, or a firewall blocks the API | Check the URL, the server, and that the API's address is allowed |
| **503** `invalid database URL: Unknown DB scheme` | A scheme Pawabase does not know, such as `mariadb://`, or a malformed value | Use `postgres://`, `mysql://` or `sqlite://` |
| **503** right after editing the template | A typo in the URL, or a database the template names that does not exist | Check the value, and create the database |
| **503** with an authentication error in the message | Wrong user or password | Fix the secret. Special characters need percent-encoding |
| **500** on every read after a switch | The new database has no tables | Migrate each resource |
| Reads work and creates fail with 500 | The role lacks `INSERT`, or a sequence grant (PostgreSQL), or a unique index is violated | Check grants first, then the data |
| Migrate fails with 500 | The role lacks `CREATE` or `ALTER`, or a unique index met duplicates | Check grants, then duplicates. See [Migrations](/data/migrations) |
| Studio's Database page shows an error and the data plane shows 503 | The database is unreachable. Studio's overview is a plain 500 here | Fix the connection |
| Data disappeared after a switch | The new databases are empty. The old data is untouched | Restore the old template value and restart to see it again, or copy the data across |
| Data reappeared after clearing the setting | It was never deleted. It was in the default database | Expected |
| A SQLite environment loses data when the container is replaced | The file is inside the container's filesystem | Put it on a mounted volume, and use a three-slash absolute path |
| Two environments show the same data | Both resolve to the same URL, so they share a connection and tables | Give each its own URL or database, or use the `{env}` placeholder |
| A table has no resource badge in the Database page | Not managed by a resource, or a prefixed table on the shared PostgreSQL default | Match it by the hash. See [prefixed table names](#shared-postgresql-and-prefixed-table-names) |
| `permission denied for sequence` (PostgreSQL) | The role can insert but lacks `USAGE` on the key sequence | `GRANT USAGE, SELECT ON SEQUENCE ...` |
| Too many connections | Replicas multiplied the pool | Reduce replicas or pool size, or raise the server's limit |

## A reproduced incident: pointing at a database that is not ready

This sequence was run on a clean API. The data database was first an unreachable address and then a reachable, empty one, which is what an environment sees after a change to `PAWABASE_DEFAULT_DATA_URL` and a restart. Every response below is what came back.

<Steps>
  <Step title="Start on a working database">
    A `things` resource is migrated and holds a row. `GET /rest/v1/things` answers 200.
  </Step>
  <Step title="Point at an unreachable address">
    The data URL is `postgres://dbuser:<password>@127.0.0.1:1/x`, a port nothing listens on. The environment's definitions are untouched.
  </Step>
  <Step title="Call the data plane">
    `GET /rest/v1/things` answers **503**: `database_unavailable`, `could not connect to the environment database: ConnectionRefusedError: [Errno 61] Connect call failed ('127.0.0.1', 1)`. The message tells you it is the connection, and the old data is not involved.
  </Step>
  <Step title="Point at a real, empty database">
    The data URL is now a SQLite file that does not exist yet.
  </Step>
  <Step title="Read before migrating">
    `GET /rest/v1/things` answers **500** `Internal Server Error`. The database is reachable, and the table is not there.
  </Step>
  <Step title="Migrate">
    **Create / migrate table** runs the `CREATE TABLE` in the new database, and the resource works again. **Build → Database** lists `things` with its resource.
  </Step>
  <Step title="Look at the connections">
    The platform overview lists the connections the process holds: the original, the failed one with `connected: false`, and the new one. Nothing was closed until a restart would close them.
  </Step>
</Steps>

Three lessons:

- **503 and 500 mean different things.** 503 is the connection. 500 on a read is the table. The first tells you to fix the URL, the second to migrate.
- **A connection string is a secret.** Keep it in the environment file, never in a definition.
- **The old data was never at risk.** Restoring the old value brings it back.

## Scenarios

### A new project, on the default

You create resources, migrate, and build. Everything works with the database the compose file gives you. This is the right place to start.

### Moving production to a managed PostgreSQL

Create the managed databases and the role. Rehearse on a second installation pointed at them, with a restored backup. In a short window, switch `PAWABASE_DEFAULT_DATA_URL` on the production installation, restart, migrate each resource, copy the data, and verify. Keep the old databases untouched until you are confident, then drop them.

### Separating staging from production

Run them as **two installations**, each with its own environment file, host and credentials, so that a mistake in staging cannot reach production's server. Promote definitions between environments of one installation as usual. Because promotion never creates tables, migrate in each. See [Environments and promotion](/operate/environments-and-promotion).

### A legacy database you want to expose

Run a **separate installation** (or a development one) whose template points at the legacy database with a **read-only role**, define resources over the tables with `table` set and `timestamps` off, and read them through the API. Add write access only for the resources that need it, with grants per table. Pawabase never alters an existing column and only adds columns that are missing, so exposing a legacy table through a resource is safe as long as the role cannot write where it should not. See [Defining resources](/data/defining-resources).

### A database that has to be in a specific region

The template can point anywhere the API can reach. Latency is the cost: every request makes one or more queries, so a database far from the API adds its round trip to every response. Place the API and the database in the same region.

### Testing against a throwaway database

For CI, start the stack with a template that names a fresh SQLite file or a container database per run, create the resources, migrate, run the tests, and delete the file.

## A pre-flight checklist for a database change

1. **Is the template in the environment file, with the right placeholders,** and is the file out of source control?
2. **Does the role have only the grants listed above,** and can it connect from the API's host?
3. **Is TLS on, and is the network path restricted?**
4. **Does every database the template names exist?**
5. **Does every resource have its table in the new databases?** Compare the Database page's tables with the resource list.
6. **Has the data been copied, with sequences reset on PostgreSQL?**
7. **Is there a backup of both the old and the new databases, taken after the copy?**
8. **Is the cache a concern?** Entries from before the switch may serve old rows until they expire. See [Caching](/data/caching).
9. **Do you know how to go back?** Restore the old value and restart.
10. **Did the API restart,** and did the platform overview show `connected: true` after the first request?

## Environments and their databases

An environment does not store its database. It is derived from the template, so creating, copying and promoting environments never changes it.

| Operation | What it does to the database |
| --- | --- |
| **Create an environment** | Nothing, until you migrate. Its database is the template with its name filled in, and it must exist |
| **Create with `copy_from`** | Copies definitions only. No data is copied |
| **Promote** | Copies definitions. The target keeps using its own database, and its tables are not created |
| **Delete an environment** | Removes the definitions. The environment's database and tables are **not** dropped |

A new environment named `qa` therefore needs a database called `shop_qa` before it can serve data, when the template ends in `{project}_{env}`. Until it exists, reads answer `503`. Create it on the server first.

### A template without `{env}` shares tables

The database is chosen by URL, not by environment. If the template has no `{env}`, every environment of a project resolves to **the same URL** and uses the same database. On PostgreSQL the `pb_<hash>_` prefix still keeps their tables apart. On SQLite or MySQL there is no prefix, so a template without `{env}` makes development, staging and production **one dataset**.

```text
development ─┐
             ├──►  sqlite:///data/shared.db   (one connection, one set of tables)
staging ─────┘
```

That was observed directly: two environments on one SQLite file read each other's rows. It is occasionally useful and usually a mistake. Keep `{project}` and `{env}` in a SQLite template.

### One file per environment on SQLite

With the SQLite template, each environment gets its own file, plus its WAL companions:

```text
acme__development.db
acme__development.db-shm
acme__development.db-wal
acme__staging.db
acme__staging.db-shm
acme__staging.db-wal
```

Back up all three files of an environment together, or use `.backup` as shown earlier.

## What Pawabase creates, and what it leaves alone

| Pawabase creates | When |
| --- | --- |
| A table for each resource, with its indexes | When you press **Create / migrate table** |
| Columns for fields added later | On the next migrate |
| The SQLite file and its directories | On first connection |

| Pawabase never | Notes |
| --- | --- |
| Creates a database, a schema, a role or a grant | You prepare the server |
| Creates an extension | Install what you need yourself |
| Creates a foreign key, a view, a trigger or a stored procedure | Relations are application-level |
| Drops or alters anything | Migrations only add |
| Copies data between databases | Switching starts empty |
| Takes a backup | Backups are yours. See [Backups](/self-hosting/backups) |
| Touches tables it did not create | A table with no resource is left entirely alone |

Nothing is created on first write. A table exists after a migration, so before it, a resource is defined and its endpoints answer with a 500 on the missing table. See [Migrations](/data/migrations).

### What a table looks like

For a resource `orders` with a `uuid` key, on PostgreSQL:

```sql
CREATE TABLE IF NOT EXISTS "orders" (
  "id" UUID PRIMARY KEY,
  "customer_id" BIGINT,
  "status" VARCHAR(255),
  "total_cents" BIGINT,
  "created_at" TIMESTAMPTZ,
  "updated_at" TIMESTAMPTZ
);
CREATE INDEX IF NOT EXISTS "ix_orders_customer_id" ON "orders" ("customer_id");
```

There is no `DEFAULT gen_random_uuid()` on `id` and no `NOT NULL` anywhere. Both are deliberate:

- **UUID keys are generated by Pawabase.** A `uuid4` is made in the API at the moment of creation and inserted explicitly. That is why uuid keys behave the same on SQLite, PostgreSQL and MySQL, none of which share a portable server-side generator.
- **`required` is an API rule.** It never becomes `NOT NULL`. See [Migrations](/data/migrations).

For integer keys the column uses each dialect's own auto-increment: `INTEGER PRIMARY KEY AUTOINCREMENT` on SQLite, `BIGSERIAL PRIMARY KEY` on PostgreSQL and `BIGINT AUTO_INCREMENT PRIMARY KEY` on MySQL.

## How a request uses the database

Knowing what each request costs helps you size and diagnose.

| Request | Statements |
| --- | --- |
| `GET /rest/v1/<resource>` | One `SELECT` with the filters, policy conditions, sort and `LIMIT/OFFSET`, plus one `COUNT(*)` for `total` (skipped when a residual policy makes `total` null) |
| `GET /rest/v1/<resource>/<id>` | One `SELECT` by key |
| `GET` with `expand` | The list query, plus one query per expanded relation. A `has_many` expansion is one query capped at 200 rows across the page |
| `POST`, `PATCH`, `DELETE` | A write statement, with the reads the policy and the response need. Every write also invalidates the resource's cache tag |
| Create / migrate table | One catalog read, then the statements |
| Studio Records tab | The same statements as the API |
| Studio Database page | Catalog reads, `COUNT(*)` for a table's row total, and `SELECT *` with a limit |

So a list page is typically **two queries**, and the count is often the more expensive of the two on a large table. See [Sorting and pagination](/data/sorting-pagination) for what that costs.

### Where a value is converted

Values are encoded on the way in and decoded on the way out, per dialect, in one place, so what you read through the API is the same on all three:

| Direction | What happens |
| --- | --- |
| In | Booleans become `0`/`1` on SQLite. Datetimes keep their offset on SQLite, become instants on PostgreSQL and naive UTC on MySQL. JSON values are serialised. UUIDs are strings except on PostgreSQL |
| Out | JSON text is parsed back. Dates and datetimes are returned in ISO form. A JSON value that fails to parse is returned as the raw text |

Because of this, comparing the API's output between two environments on different dialects is a fair test, and comparing raw SQL output is not. See [Migrations](/data/migrations#what-each-dialect-does-with-values).

## The rest of an environment's infrastructure

The database is one of six things the Overview's infrastructure panel reports. The others are not set in the same way, but they are on the same panel, and a launch checklist should read all six.

| Key | Values you may see | Meaning |
| --- | --- | --- |
| `database` | `platform default`, `configured` | Reads `platform default` when the database comes from the environment file, which is the only way it is configured |
| `storage` | `local` | Where uploaded files go |
| `mail` | `suppressed (not configured)` | Whether mail is actually sent. Suppressed means flows that send mail do not deliver it |
| `cache` | `MemoryCache`, `RedisCache` | Where cached lists and records live. Memory is per process |
| `queue` | `SyncConnection`, and others | How background work runs. `SyncConnection` runs it inline |
| `events` | `memory`, and others | Where events are published |

A development install shows memory, sync and suppressed throughout, which is correct for development and wrong for production. A production environment should show a real queue, a shared cache, and a real mail setting, in addition to its own database. See [Caching](/data/caching) for the cache, and the self-hosting pages for the rest.

`database: configured` only says the environment has its own URL. It does not say the URL works. A configured environment whose database is down looks the same on this panel as a healthy one, so confirm with a read through `/rest/v1` or the platform overview's `connected` flag.
</Note>

## Backups and recovery

Pawabase never backs up an environment's data. Backups are a property of the database, and you are the owner of them.

### What to back up

| What | Lives in | Loss means |
| --- | --- | --- |
| Definitions, keys, secrets, audit log | The control-plane database | Your projects, resources and flows. Rebuilding means redefining everything |
| Each environment's records | That environment's database | The data your application stores |
| Uploaded files | Storage | The files, though not the records that refer to them |
| Your `.env` and the encryption key for secrets | Your host | The ability to decrypt stored secrets |

Back up the first, second and fourth together. A restore of the control-plane database without its secrets key leaves every secret unreadable, including your database URLs.

### Taking a backup

```bash
# PostgreSQL
pg_dump --format=custom --file=shop_production_$(date +%F).dump "$DATABASE_URL"

# MySQL
mysqldump --single-transaction --routines --set-gtid-purged=OFF shop > shop_production.sql

# SQLite
sqlite3 /data/envs/shop__production.db ".backup '/backups/shop__production.db'"
```

On a shared PostgreSQL default, a dump of the whole database is a dump of every environment's tables together. To back up one environment, dump its prefixed tables only (`--table='pb_<hash>_*'`).

### Restoring into a scratch installation

The safest way to test a restore is to restore into a separate database and run a second, throwaway Pawabase against it:

<Steps>
  <Step title="Restore the dump into a new database">
    `pg_restore --dbname="$SCRATCH_URL" shop_production.dump`
  </Step>
  <Step title="Start a scratch installation">
    A copy of your compose project with its own environment file, whose `PAWABASE_DEFAULT_DATA_URL` names the restored database, and the same definitions (restore the control-plane backup into its `PAWABASE_DATABASE_URL` database as well).
  </Step>
  <Step title="Verify">
    Open **Build → Database**. The tables are the ones restored. Open the Records tab and read recent rows. Run a query that proves the newest data is there.
  </Step>
</Steps>

A backup you have never restored is a hope. Doing this once a quarter is what turns it into a backup.

### Recovering from a bad console write

A console write has no undo, so the recovery is a restore. If the damage is small, restore the affected table alone into a scratch database, and copy the rows back with a targeted `INSERT ... SELECT` or `UPDATE`. The audit log's `database.write` event holds the first 2,000 characters of the statement that did it, which tells you what to reverse.

## Common mistakes

| Mistake | What it causes | The habit that prevents it |
| --- | --- | --- |
| Putting a connection string in a definition or a setting | It is readable by everyone who can read the environment | Keep it in the environment file |
| Embedding a secret inside a URL | The URL is used literally and fails to parse | The reference is the entire value |
| Switching a database before migrating there | Reads fail with 500 until you migrate | Rehearse on a second installation |
| Assuming the data moved | The new database is empty | Copy it yourself, then verify counts |
| Giving two environments one URL | They share tables and rows | One database per environment |
| Using the application's role for analysts | Direct, unchecked writes | A read-only role for people |
| Forgetting the sequence grant or reset (PostgreSQL) | Inserts fail on a permission or a duplicate key | Grant it, and reset after a data load |
| A relative SQLite path in a container | Data lost when the container is replaced | A three-slash path on a mounted volume |
| Running SQLite with several replicas | Corruption risk and lock errors | PostgreSQL, or one replica |
| Developing on SQLite, shipping on PostgreSQL | Length and type surprises in production | Develop on the production dialect |
| Revoking the old password before restarting | Old connections fail | Restart first, then revoke |
| Treating `configured` as healthy | A broken URL still reads configured | Probe with a read |
| Expecting the console to be rolled back | A write cannot be undone | Restore from a backup |

## Messages and what they mean

Every message below comes from Pawabase itself or from the database through it.

| Message | From | Meaning |
| --- | --- | --- |
| `database_unavailable` with `could not connect to the environment database: <Driver error>` | Data plane, 503 | The connection failed. The driver's own text follows, such as `ConnectionRefusedError` or an authentication failure |
| `database_unavailable` with `invalid database URL: Unknown DB scheme: <x>` | Data plane, 503 | The URL's scheme is not `sqlite`, `postgres`, `postgresql`, `mysql` or `asyncpg` |
| `Internal Server Error` on a read | Data plane, 500 | The table or a column does not exist, or a stored value no longer fits |
| `Internal Server Error` on a create | Data plane, 500 | A unique violation, an oversize value, a type the column rejects, or a missing column |
| `this statement writes; set allow_write to run it` | Console, 400 | The statement is not read-only and **allow writes** was off |
| `<ExceptionType>: <message>` | Console, 400 | The database rejected the statement. The text is the database's own |
| `the query timed out` | Console, 504 | The query exceeded the environment's `query_timeout` |
| `no table '<name>'` | Database page, 404 | The table does not exist in this environment's database |
| `no resource '<name>'` | Migrate, 404 | The resource name is not defined in this environment |

Of these, the two to learn first are the 503 with a driver error, and the console's `<ExceptionType>: <message>`. Between them they turn almost every database problem from a guess into a message.

## From zero to a production database: the whole sequence

This is the complete sequence for running production on its own PostgreSQL, with each step spelled out. Do it on a staging installation first if you can.

### 1. On the database server

```sql
CREATE ROLE shop_prod_app LOGIN PASSWORD '<a long random password>';
CREATE DATABASE shop_development OWNER shop_prod_app;
CREATE DATABASE shop_staging OWNER shop_prod_app;
CREATE DATABASE shop_production OWNER shop_prod_app;
```

Confirm the role can connect from the API's host:

```bash
psql "postgres://shop_prod_app:<password>@db.prod.example.com:5432/shop_production?sslmode=require" -c "select 1"
```

If this fails from the API host, nothing Pawabase does will fix it. Resolve the network or the credentials first. (The control plane needs a database of its own too, with its own URL in `PAWABASE_DATABASE_URL`.)

### 2. Put the template in the environment file

```bash
PAWABASE_DEFAULT_DATA_URL=postgres://shop_prod_app:<password>@db.prod.example.com:5432/{project}_{env}?ssl=require
```

Keep the file out of source control and readable only by the account that runs the stack. Note `ssl=require` for the URL Pawabase reads (`sslmode=require` was `psql`'s own spelling).

### 3. Restart the API

```bash
docker compose up -d api
```

From the restart on, `/rest/v1` reads and writes the new databases. If the environment already has traffic, do this in a quiet window, because every read fails until step 4.

### 4. Migrate every resource

Press **Create / migrate table** for each resource in Studio. The response of each lists the statements it ran, and the `table` is the declared name with the `pb_<hash>_` prefix on PostgreSQL. For many resources, the same call is available from a script with an operator credential (see [Migrations](/data/migrations)).

### 5. Verify

Open **Build → Database**. The line above the table list reads `postgres · platform default`, and every resource has its table. Then read through the API with a publishable key to check the full path.

### 6. Set up backups and monitoring

Before real data arrives: a backup schedule on the server, an alert on disk and connections, and a read-only role for the people who will query it.

### 7. Copy the data, if there was any

Follow [moving existing data](#moving-existing-data-to-a-new-database). Do this **before** step 3 if you prepared the new databases with the database's own tools, so that step 3 is the last, quick change.

## Other tools against the database

Analysts and BI tools can connect to an environment's database with the read-only role from earlier. The settings are the same for every tool.

| Setting | Value |
| --- | --- |
| Type | PostgreSQL, MySQL or SQLite, as the URL says |
| Host, port | From the URL |
| Database | The database name from the URL |
| User, password | The **reporting** role, not the application's |
| TLS | Required, matching the `ssl` setting |

What the tool will see:

- **Table names** as declared, or `pb_<hash>_` prefixed on the shared PostgreSQL default.
- **Plain columns plus JSON.** `array`, `object` and `ref` fields are JSON columns, and each tool has its own way to extract values from them.
- **Raw timestamps.** On MySQL they are UTC without an offset. On PostgreSQL they are instants.
- **No policies.** Whatever the role can read, the tool shows, including rows an end user could never see through the API.

For dashboards, create **views** in the database that join and shape what you need, and grant the reporting role `SELECT` on the views only. Pawabase never touches views, so they are safe from migrations.

```sql
CREATE VIEW reporting_open_tickets AS
SELECT id, subject, status, priority, created_at
FROM tickets
WHERE status <> 'solved';

GRANT SELECT ON reporting_open_tickets TO reporting;
```

## Read replicas and failover

An environment has **one** database URL. Pawabase does not route reads to a replica, and it does not fail over by itself, so each of these is provided below Pawabase:

| Need | How |
| --- | --- |
| Read scaling | Put a proxy or the provider's reader endpoint in front, and point the template at the writer. Pawabase will use the writer for everything |
| Failover | Use the provider's failover, with a stable hostname that moves to the new primary. After a failover the pooled connections break, and the next request reconnects |
| Maintenance windows | Expect 503 `database_unavailable` during them, and have clients retry |

After a failover, connections opened before it are broken. A connection that **failed to open** is retried on the next request, but a connection that was open and then broke is the driver's to recover, and how quickly it does depends on the driver and the provider. If requests keep failing after the database is healthy, restart the API to rebuild the pool. If the hostname changed instead of moving, update the secret.

## A health probe you can run

A probe that tells the three failure kinds apart saves a lot of guessing. It reads one small resource with a publishable key and classifies the answer.

```python
import os
import sys
import requests

URL = "https://api.example.com/rest/v1/feature_flags?per_page=1"
HEADERS = {"apikey": os.environ["PUBLISHABLE_KEY"]}

response = requests.get(URL, headers=HEADERS, timeout=10)

if response.status_code == 200:
    print("ok: gateway, API, database and table all work")
elif response.status_code == 503:
    detail = response.json().get("message", "")
    print(f"DATABASE UNREACHABLE: {detail}")
    sys.exit(2)
elif response.status_code == 500:
    print("DATA PROBLEM: the table or a column is missing, or a value is invalid")
    sys.exit(3)
else:
    print(f"OTHER: {response.status_code} {response.text[:200]}")
    sys.exit(1)
```

Run it from a scheduler and alert on any non-zero exit. The three codes map to three owners: 2 is the database team, 3 is whoever last changed a resource, and 1 is the gateway or a key.

## Inspection cookbook

Run these in the [Database console](/data/database-console) (reads need no **allow writes**) or in your own client.

### PostgreSQL

```sql
-- table sizes, largest first
SELECT relname AS table, pg_size_pretty(pg_total_relation_size(relid)) AS total,
       pg_size_pretty(pg_relation_size(relid)) AS data, n_live_tup AS rows
FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 20;

-- indexes that are never used (candidates for removal)
SELECT relname AS table, indexrelname AS index, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes WHERE idx_scan = 0 ORDER BY pg_relation_size(indexrelid) DESC;

-- long-running queries
SELECT pid, now() - query_start AS running, state, left(query, 100) AS query
FROM pg_stat_activity WHERE state <> 'idle' ORDER BY running DESC;

-- locks that are waiting
SELECT pid, wait_event_type, wait_event, left(query, 100) AS query
FROM pg_stat_activity WHERE wait_event_type = 'Lock';
```

### MySQL

```sql
-- table sizes
SELECT table_name, ROUND((data_length + index_length) / 1024 / 1024, 1) AS mb, table_rows
FROM information_schema.tables WHERE table_schema = DATABASE() ORDER BY mb DESC;

-- indexes on a table
SHOW INDEX FROM tickets;

-- running queries
SHOW FULL PROCESSLIST;
```

### SQLite

```sql
-- every table and its definition
SELECT name, sql FROM sqlite_master WHERE type = 'table' ORDER BY name;

-- indexes
SELECT name, tbl_name FROM sqlite_master WHERE type = 'index' ORDER BY tbl_name;

-- page and free-page counts (to see how much space a vacuum would return)
PRAGMA page_count;
PRAGMA freelist_count;
```

The `pg_stat_user_indexes` query is worth a look every few months. Pawabase creates an index for every `indexed`, `unique` and `owner_field`, and never removes one, so an index for a field nobody filters on keeps costing writes. Dropping an unused index is a manual change in the console, and then clearing `indexed` in the definition keeps the next migration from re-creating it.

## Connection budget, worked through

An example for the arithmetic. A deployment has:

- 3 API replicas
- 4 environments (development, staging, two production regions) on one PostgreSQL server, each with its own URL
- Each connection object holding up to 10 driver connections (a `maxsize=10` hint in the URL)

The worst case is `3 replicas × 4 URLs × 10 = 120` connections, before anything else connects. A managed database with a limit of 100 will refuse some of them, and the symptom is intermittent 503s under load that disappear when traffic drops.

| Lever | Effect |
| --- | --- |
| Fewer replicas | Linear reduction |
| Smaller `maxsize` hint | Linear reduction per URL, at the cost of waiting under load |
| A pooler in front | Many client connections share few server connections |
| Fewer environments on that server | Move staging to a smaller server |

Measure with `pg_stat_activity` while the system is under load, and size the limit with headroom for your own tools.

## Copying data, in more detail

### Server to server on PostgreSQL

When both databases are PostgreSQL, a pipe avoids a file:

```bash
pg_dump "$OLD_URL" --data-only --table=pb_9c41e0d27a1b_tickets \
  | sed 's/pb_9c41e0d27a1b_tickets/tickets/g' \
  | psql "$NEW_URL"
```

Do one table at a time, check the count, and keep the order that respects your own relations (nothing enforces one, but your application may).

### Verify a copy

Counts first, then a checksum of something stable:

```sql
-- run on both sides and compare
SELECT COUNT(*) AS rows, MIN(id) AS first_id, MAX(id) AS last_id FROM tickets;
SELECT md5(string_agg(id::text || coalesce(subject, ''), ',' ORDER BY id)) FROM tickets;
```

If the two results differ, the copy is not complete. Do not switch.

### After the copy

1. Reset sequences on PostgreSQL (shown earlier).
2. Run `ANALYZE` so the planner has statistics: `ANALYZE tickets;`.
3. Make a read through the API for a few known records.
4. Check that a **create** works, since that is where a stale sequence shows up.

## Putting the settings in `.env`

For a self-hosted installation, the defaults belong in the environment file, where the compose file reads them:

```bash
# the control plane
PAWABASE_DATABASE_URL=postgres://pawabase:<password>@postgres:5432/pawabase

# the default for every environment with no database of its own
PAWABASE_DEFAULT_DATA_URL=postgres://pawabase:<password>@postgres:5432/pawabase

# for development with one SQLite file per environment
# PAWABASE_DEFAULT_DATA_URL=sqlite:///data/envs/{project}__{env}.db
```

Restart the API after changing either.

## The two variables

Two installation-wide settings control where data lives. Both are set in the environment file.

| Variable | Purpose | Default |
| --- | --- | --- |
| `PAWABASE_DATABASE_URL` | The **control-plane** database | PostgreSQL in the compose file |
| `PAWABASE_DEFAULT_DATA_URL` | The **environment** databases, as a template with `{project}` and `{env}` | The bundled PostgreSQL in `docker-compose.yml`. A SQLite file per environment in `docker-compose.dev.yml`. A local PostgreSQL if unset |

Changing `PAWABASE_DEFAULT_DATA_URL` changes where **every environment of every project** looks. Existing data stays in the old databases, and the environments see empty ones, with the 500s that follow. Follow [the switching steps](#switching-the-database). See [Configuration](/self-hosting/configuration).

## Differences you will meet when you change dialect

If you move an environment from one dialect to another, these are the places to check.

| Area | What changes |
| --- | --- |
| **String length** | SQLite has none. PostgreSQL and MySQL cut at `max_length` or 255 |
| **Datetimes** | Offset kept, instant, or naive UTC. Sorting and filtering follow |
| **Booleans** | `0`/`1` or `true`/`false`. A filter `eq` on a boolean is wrong in every dialect, so use `is.true` and `is.false` |
| **Case** | Text comparison and uniqueness differ. `like` is case-insensitive on SQLite as observed |
| **JSON** | Text, `JSONB` or `JSON`. Whole-value equality on a JSON field never matches through the API in any case |
| **UUID** | Text, `UUID` or `CHAR(36)`. A uuid filter must be lowercase and hyphenated on SQLite |
| **Migrations** | MySQL index statements are not repeatable |
| **Ordering ties** | Not defined by Pawabase. Add `id` to a sort to make it stable |
| **Concurrency** | One writer on SQLite, many elsewhere |

A move is a good moment to run your whole API test suite against the new dialect on a second installation before switching.

## Worked example: from a SQLite file to PostgreSQL

A team has run a `tickets` resource on SQLite in development and wants the same data in a PostgreSQL environment. The steps, with what each one handles.

<Steps>
  <Step title="Create the PostgreSQL databases and a scratch installation">
    Follow the sequence above for a second installation whose template points at the new PostgreSQL.
  </Step>
  <Step title="Migrate in the scratch installation">
    The tables are created in PostgreSQL with PostgreSQL's types: `BIGSERIAL`, `VARCHAR(160)`, `TIMESTAMPTZ`, `JSONB`.
  </Step>
  <Step title="Export from SQLite as CSV">
    ```bash
    sqlite3 -header -csv /data/envs/shop__development.db "SELECT * FROM tickets" > tickets.csv
    ```
  </Step>
  <Step title="Load with explicit handling of the awkward types">
    Load into a staging table of text columns, then insert with casts, so each type's conversion is visible:

    ```sql
    CREATE TEMP TABLE tickets_in (id text, subject text, status text, priority text, labels text, created_at text, updated_at text);
    \copy tickets_in FROM 'tickets.csv' WITH (FORMAT csv, HEADER)

    INSERT INTO tickets (id, subject, status, priority, labels, created_at, updated_at)
    SELECT id::bigint, subject, status, NULLIF(priority, '')::bigint,
           NULLIF(labels, '')::jsonb,
           created_at::timestamptz, updated_at::timestamptz
    FROM tickets_in;
    ```
  </Step>
  <Step title="Reset the sequence">
    ```sql
    SELECT setval(pg_get_serial_sequence('tickets', 'id'), COALESCE(MAX(id), 1)) FROM tickets;
    ```
  </Step>
  <Step title="Check for values PostgreSQL would have refused">
    A SQLite column accepted anything, so look for what PostgreSQL's types do not: strings longer than the column, malformed JSON, a boolean stored as a word. The `INSERT` above fails loudly on any of them, which is the point of the staging table.
  </Step>
  <Step title="Compare, then switch the real installation">
    Compare counts and a checksum, run your tests against the scratch installation, then change the real installation's `PAWABASE_DEFAULT_DATA_URL` to the same value and restart.
  </Step>
</Steps>

The conversions worth knowing:

| SQLite value | PostgreSQL column | Conversion |
| --- | --- | --- |
| `0` / `1` in an `INTEGER` column | `BOOLEAN` | `value::int::boolean`, or `value = '1'` |
| ISO text with an offset | `TIMESTAMPTZ` | `::timestamptz` keeps the instant |
| ISO text, date only | `DATE` | `::date` |
| JSON text | `JSONB` | `::jsonb`, which fails on invalid JSON |
| Text uuid | `UUID` | `::uuid`, which fails on a malformed value |
| Text longer than a limit | `VARCHAR(n)` | Fails. Shorten the value or raise `max_length` |

## Where to start, by size

These are starting points, not limits: Pawabase imposes none, and the right numbers come from measuring your own load.

| Stage | Database | Layout |
| --- | --- | --- |
| Exploring | The default | One environment, nothing configured |
| A small team | A single PostgreSQL | Development on the default, staging and production on their own databases |
| A growing product | A managed PostgreSQL | Production on its own server, with backups, alerts and a reporting role |
| High traffic | A managed PostgreSQL behind a pooler | Several API replicas, a connection budget, indexes on every filtered and sorted column |

At each step the change is the same one: a `PAWABASE_DEFAULT_DATA_URL` that points somewhere better. Nothing in your resources changes.

The one thing that does change with size is how much you rehearse. A small table can be copied in seconds and verified by eye. A large one needs a timed run on a second installation, a plan for the writes that arrive during the copy, and a decision about whether a short read-only window is acceptable.

If a short outage is not acceptable, the usual pattern is: copy once, switch reads and writes to a maintenance response for the shortest possible moment, copy the difference since the first copy, then switch the URL. The copy of the difference is why every table should have an `updated_at` or a growing key that you can filter on.
## Questions that come up

<AccordionGroup>
  <Accordion title="Do I have to configure a database?">
    No. The installation's default template works out of the box. Change it when you need separation, your own backups, or access from other tools.
  </Accordion>
  <Accordion title="Is SQLite the default?">
    Only in the development compose file. The built-in default and the production compose file use PostgreSQL. Check `PAWABASE_DEFAULT_DATA_URL`.
  </Accordion>
  <Accordion title="Where do I set a database in Studio?">
    You do not. Studio's Settings page covers API documentation, CORS, realtime and custom settings, and says infrastructure is configured once for the whole installation via `.env`. Set `PAWABASE_DEFAULT_DATA_URL` in the environment file and restart the API.
  </Accordion>
  <Accordion title="Where should the password live?">
    In the environment file, or your platform's secret store, and nowhere else: not in a definition, a setting or source control. Rotate it if it was ever exposed.
  </Accordion>
  <Accordion title="Can I use two databases in one environment?">
    No. One environment has one database, derived from the template. Resources in one environment share it.
  </Accordion>
  <Accordion title="Does Pawabase copy data when I switch?">
    No. The new database is empty, and the old data is untouched. Copy it with your database's tools.
  </Accordion>
  <Accordion title="What do 503 and 500 mean on a read?">
    **503** is the connection: the database is unreachable or the URL is wrong. **500** is the table: it is missing, or a column is. Migrate.
  </Accordion>
  <Accordion title="Can I use MariaDB?">
    Use a `mysql://` URL. The `mariadb://` scheme is not recognised.
  </Accordion>
  <Accordion title="Can two environments share a database?">
    Yes, by giving them the same URL, and then they share tables and rows. Normally you want separate databases.
  </Accordion>
  <Accordion title="Does clearing the setting delete data?">
    No. It returns the environment to the default database, where its old data was left.
  </Accordion>
  <Accordion title="Does the role need DROP?">
    No. Pawabase never drops. It needs read and write on its tables, and `CREATE` and `ALTER` for migrations.
  </Accordion>
  <Accordion title="Does Pawabase run a connection pool?">
    It keeps one connection object per URL per process and passes pool hints from the URL's query string to the driver. Size the database for the number of replicas.
  </Accordion>
</AccordionGroup>

## What to remember

- **Two databases.** The control plane holds definitions. Each environment's database holds rows.
- **One environment, one URL,** derived from `PAWABASE_DEFAULT_DATA_URL` with `{project}` and `{env}` filled in.
- **The default is PostgreSQL** in the production layout, SQLite only in the dev compose file.
- **Configuration is in the environment file,** never in Studio and never through the platform's routes. Change it, restart the API.
- **The connection string is a secret.** Keep it out of definitions and source control.
- **Switching starts empty.** Nothing is copied, and the old data stays where it was.
- **503 is the connection. 500 is the table.**
- **The role never needs `DROP`.** Give it one database and nothing else.
- **Backups are yours.** Restore into a scratch installation to prove them.
- **Promotion and copy-from never change a database.** Only the template does.

| **Physical table name** | The table's name in the database, which may carry a `pb_<hash>_` prefix on the shared default |
| **Pool** | The set of open database connections in an API process, keyed by URL |
| **Dialect** | SQLite, PostgreSQL or MySQL, taken from the URL scheme |
| **Scratch environment** | A short-lived environment used to rehearse a database change |
