## What the console is, and what it is not

The **Database console** is how an operator looks at an environment's database and, when they must, changes it. It is part of Studio's **Database** page and has two surfaces:

| Surface | What it does | Writes? |
| --- | --- | --- |
| **The table browser** | Lists every table, shows a table's columns and indexes, and pages through its rows 50 at a time | Never |
| **The SQL window** (the **SQL** button) | Runs one SQL statement, with a click-through **query builder** that writes the statement for you | Only when **allow writes** is ticked |

Both run against the **environment's own database**, the same connection your resources use, so they see exactly what `/rest/v1` sees and nothing else. See [Your database](/data/your-database) for which database that is.

What makes the console different from the API is what it **skips**:

| The API applies | The console |
| --- | --- |
| Field validation | **Skipped.** A value the API would refuse, the console writes |
| The resource's policy, including owner scoping | **Skipped.** Every row of every table is visible |
| Transformers | **Skipped.** A hidden field is shown |
| Response shaping | **Skipped.** Raw columns, including undeclared ones |
| Events, webhooks and realtime | **Skipped.** Nothing is published for a console write |
| The audit log | **Recorded** for successful writes |
| The cache | **Cleared** for every resource after a successful write |

That is the point of it, and also the danger. The console is for the work the API is deliberately not built to do: inspecting structure, finding out what is really in a row, one-off repairs and backfills, and checking an index. It is not a second API.

<Warning>
Anyone who can open the Database page can read **every table** in the environment and, with **allow writes**, change or delete anything in it, including data that no end user and no API key can reach. Treat access to Studio's Database page as access to the database. The routes behind it require an **operator** session.
</Warning>

## Where the console sits

```text
Studio (operator session)
  └─ Database page
       ├─ Tables card ──── GET  /platform/v1/projects/{ref}/envs/{env}/database
       ├─ Table view ───── GET  .../database/tables/{table}
       │                   GET  .../database/tables/{table}/rows?limit=50&offset=0
       └─ SQL window ───── POST .../database/query   {"sql": "...", "allow_write": false}
```

Four routes, all operator-only, and all of them are plain platform API calls you can make yourself. The last half of this page uses them directly.

## The table browser

Open **Build → Database**. The left card, **Tables**, shows a line with the dialect and where the database comes from (`postgres · platform default`, `sqlite · your database`), then one entry per table. A green badge names the resource when the table's name equals the resource's declared `table`. An environment with no tables says *No tables yet.*

Click a table and the right side shows:

- The title, with the table name and its **row count**: `tickets · 1204 rows`. The count is a `SELECT COUNT(*)` run when you open the table, so on a very large table opening it costs a count.
- A strip of **column badges**, each `name: type`, with a key mark on the primary key. Hovering a badge shows everything the database knows about the column: type, whether it is nullable, its default and whether it is the key.
- A page of rows with **Prev** and **Next**, 50 rows at a time. **Prev** is disabled on the first page, and **Next** is disabled when a page comes back with fewer than 50 rows. An empty table says *The table is empty.*

Before you click a table, the right side reads *Pick a table on the left, or click SQL to run a query.*

### What the table description contains

The route behind the column strip returns more than the strip shows:

```http
GET /platform/v1/projects/acme/envs/development/database/tables/things
```

```json
{
  "name": "things",
  "columns": [
    { "name": "id", "type": "INTEGER", "nullable": true, "default": null, "primary_key": true },
    { "name": "code", "type": "TEXT", "nullable": true, "default": null, "primary_key": false },
    { "name": "note", "type": "TEXT", "nullable": true, "default": null, "primary_key": false },
    { "name": "qty", "type": "INTEGER", "nullable": true, "default": null, "primary_key": false },
    { "name": "created_at", "type": "TEXT", "nullable": true, "default": null, "primary_key": false },
    { "name": "updated_at", "type": "TEXT", "nullable": true, "default": null, "primary_key": false }
  ],
  "indexes": [{ "name": "ix_things_code", "unique": false, "columns": ["code"] }],
  "foreign_keys": [],
  "rows": 2
}
```

Three things in that response are worth reading every time:

- **`nullable` is true for every column**, including the key as SQLite reports it. Pawabase never emits `NOT NULL`, so a table it created has none.
- **`indexes` lists what actually exists.** The migration created `ix_things_code` because `code` is indexed. A field you marked `indexed` that is missing here was never migrated.
- **`foreign_keys` is empty** for tables Pawabase created, because it never creates any. A table you created yourself with real foreign keys lists them.

A table that does not exist answers `404` with the message `no table 'nope'`.

### Browsing rows through the API

```http
GET .../database/tables/things/rows?limit=2&offset=1
```

```json
{
  "data": [
    { "id": 2, "code": "b", "note": "x;y", "qty": 1, "created_at": "2026-10-01T21:39:28.999385+00:00", "updated_at": "2026-10-01T21:39:28.999385+00:00" }
  ],
  "limit": 2,
  "offset": 1
}
```

`limit` is clamped to between 1 and 500 (a request for 9,999 returned a `limit` of 500), and defaults to 50, which is what Studio uses. `offset` is never negative. Rows come back in the **table's natural order**, with no `ORDER BY`, so on a table without a stable order the pages can shift between requests. Use the SQL window with an `ORDER BY` for anything where order matters.

The rows are **raw**, exactly as the driver returns them, with none of the decoding the API does. See [what values look like](#what-values-look-like-in-results) below.

## The SQL window

The **SQL** button, at the right of the page header, opens a window titled **SQL**. Top to bottom:

| Part | What it is |
| --- | --- |
| **Query builder** | A section with a **Hide** / **Show** button. Open by default. Click to build a statement |
| *Each click rewrites the SQL below. Edit it by hand any time; the next click in the builder replaces your edits.* | The hint under the builder |
| **SQL** | A text area for **one** statement |
| Footer: **allow writes** | A checkbox, off by default |
| Footer: **Close**, **Run** | Run is also Cmd or Ctrl and Enter |
| Result area | Appears after a run |

If a table was selected when you opened the window, the text area starts with that table's name already in a query:

```sql
SELECT *
FROM "tickets"
LIMIT 100
```

and otherwise with `SELECT 1 AS ok`, which is also a quick check that the connection works.

### What the result looks like

| You ran | You see |
| --- | --- |
| A read that returns rows | A table, one column per selected column |
| A read that returns nothing | *No rows.* |
| A read with more than 5,000 rows | The first 5,000, and *Showing the first 5000 rows.* |
| A write | A green line: *N row(s) affected.* |
| A statement that fails | An error message from the platform. See [Errors](#errors-and-what-they-mean) |

The window does not keep history, saved queries or tabs. Closing it discards the text.

## The query builder

The builder writes SQL from clicks, so that a statement can be correct before anyone types a word. Every click regenerates the text area, and the text area stays editable. It is a good way to start a statement and a poor way to finish one.

### The controls

| Row | Control | What it does |
| --- | --- | --- |
| **Action** | Select, Insert, Update, Delete | Chooses the statement type. Choosing anything but **Select** ticks **allow writes** for you. Choosing **Select** unticks it |
| **From** / **Table** | One chip per table | Picks the table. Switching tables clears columns, joins and conditions, and keeps the action |
| **Columns** (Select) | **All**, **Count rows**, then one chip per column | **All** is `*`. **Count rows** is `COUNT(*)`. Click columns to select exactly those |
| **Join** (Select) | A chip per suggested join, with a type picker **LEFT** or **INNER** | Joins along a foreign key, in either direction. Tables Pawabase created have none, so the row reads *No foreign keys to join along.* |
| **Values** / **Set** (Insert, Update) | One input per column, showing its type | The value for each column you fill in. An empty input is left out. A column's default or `NULL` shows as the placeholder |
| **Where** (Select, Update, Delete) | **Add condition**, then column, operator and value | Conditions, joined with **AND** or **OR** |
| **Order** (Select) | A column picker and **Ascending** or **Descending** | `ORDER BY` |
| **Limit** (Select) | A number, default 100 | `LIMIT` |

The operators are `=`, `!=`, `>`, `>=`, `<`, `<=`, `LIKE`, `NOT LIKE`, `IN`, `IS NULL` and `IS NOT NULL`. For `IN`, type the values with commas, `a, b, c`. For `LIKE`, the placeholder suggests `%text%`.

### What it generates

These were produced by running the builder's own statement composer. The table is `tickets`, on PostgreSQL.

Select everything (the starting point):

```sql
SELECT *
FROM "tickets"
LIMIT 100
```

Two columns, two conditions, ordered, limited:

```sql
SELECT "id", "subject"
FROM "tickets"
WHERE "status" = 'open'
  AND "priority" >= 2
ORDER BY "id" DESC
LIMIT 50
```

On MySQL the same click-through quotes with backticks:

```sql
SELECT `id`, `subject`
FROM `tickets`
WHERE `status` = 'open'
  AND `priority` >= 2
ORDER BY `id` DESC
LIMIT 50
```

Count rows, with an `IN`:

```sql
SELECT COUNT(*)
FROM "tickets"
WHERE "status" IN ('open', 'pending')
```

`OR` between conditions:

```sql
SELECT *
FROM "tickets"
WHERE "subject" LIKE '%login%'
  OR "status" IS NULL
LIMIT 100
```

An insert, with an apostrophe in a value escaped by doubling it:

```sql
INSERT INTO "tickets" ("subject", "status", "priority")
VALUES ('It''s broken', 'open', 2)
```

An insert with no values filled in:

```sql
INSERT INTO "tickets" DEFAULT VALUES
```

An update, scoped by a condition:

```sql
UPDATE "tickets"
SET "status" = 'solved'
WHERE "id" = 12
```

A delete, with and without a condition:

```sql
DELETE FROM "tickets"
WHERE "status" = 'spam'
```

```sql
DELETE FROM "tickets"
```

The second is what the builder produces when no condition has a value. It deletes every row, and the builder warns you under the **Where** row: *No condition: this affects every row.* Read that warning every time.

### How values are turned into SQL

The builder decides how to write a value from the column's type and what you typed.

| You type | Column type | Written as |
| --- | --- | --- |
| `12` | A numeric column (integer, real, float, double, numeric, decimal, serial) | `12` |
| `12` | A text column | `'12'` |
| `true` or `false` | A boolean column | `TRUE` or `FALSE` |
| `true` | Anything else | `'true'` |
| `null` (any case) | Any column | `NULL` |
| `It's` | Any | `'It''s'`. Apostrophes are doubled |
| (empty) | Insert or update | The column is left out |
| (empty) | A where condition | The condition is left out entirely |

That last row is a trap worth knowing: a condition with an empty value **disappears**. If you add a condition, forget to type its value, and run a delete, the statement has no `WHERE`.

### Two quirks to avoid

**Typing `null` with `=` writes `= NULL`.** SQL never matches that, so the query returns nothing:

```sql
SELECT *
FROM "tickets"
WHERE "subject" = NULL
LIMIT 100
```

To find nulls, pick the **IS NULL** operator, and leave the value empty.

**A boolean written as `true` against a text column is a string.** Choose the operator and value for the column's real type, and check the generated SQL before you run it.

### When to leave the builder

The builder covers one table, simple conditions and foreign-key joins. Leave it, and edit the text, for:

- Aggregates other than a count (`SUM`, `AVG`, `GROUP BY`, `HAVING`).
- Subqueries and common table expressions.
- Joins across tables with no foreign key. Pawabase creates none, so on a Pawabase-made database the join row never offers a join. Write them by hand.
- Dialect-specific catalogs and functions.
- Anything with `RETURNING` (a write answers with a row count, not the returned rows), or several statements (only one runs per click of **Run**).

Remember that your edits last only until the next click in the builder, so finish the statement last.

## Reads and writes: how the console decides

Every statement is classified before it runs, and the class decides **which path** it takes, not only whether it is allowed.

| Class | Path | Result shape | Audited | Clears caches |
| --- | --- | --- | --- | --- |
| **Read** | Fetch rows | `{"rows": [...], "truncated": false}` | No | No |
| **Write** | Execute and count | `{"rows": [], "affected": N}` | Yes, as `database.write` | Yes, every resource |

The classifier is deliberately simple. A statement is a **read** only when all of these hold:

1. After trimming whitespace and one trailing `;`, **no `;` remains anywhere** in the text.
2. It **starts with** `select`, `with`, `explain`, `pragma`, `show` or `describe`, in any case.
3. It does not contain any of the words `insert`, `update`, `delete`, `drop`, `alter`, `create`, `truncate`, `grant` or `attach`, **with a space on each side**.

Anything else is a write. A write without **allow writes** is refused with `400` and the message `this statement writes; set allow_write to run it`.

<Note>
**allow writes** does not turn a read into a write or the other way around. It is only permission. A clean `SELECT` with **allow writes** ticked still takes the read path and returns rows. The path follows the classifier.
</Note>

### Every case, as it was run

These ran against a real API on SQLite, with a `things` resource holding three rows. "Read path" means the classifier called it a read.

| Statement | **allow writes** | What happened |
| --- | --- | --- |
| `SELECT 1 AS ok` | off | Read path, `{"rows":[{"ok":1}],"truncated":false}` |
| `SELECT 1 AS ok;` | off | Read path. One trailing `;` is trimmed |
| `SELECT code FROM things WHERE note = 'update me'` | off | Read path. The word is next to a quote, not a space, so it passes |
| `SELECT code FROM things WHERE note = 'x;y'` | off | **Refused.** A `;` inside a string literal still counts |
| `SELECT code FROM things WHERE note = 'x;y'` | on | **Ran as a write**, and returned `{"rows":[],"affected":1}`. The row you wanted was not returned |
| `-- hi` newline `SELECT 1 AS ok` | off | **Refused.** A statement that starts with a comment does not start with `select` |
| `SELECT code FROM things WHERE code = ?` with `params: ["a"]` | off | Read path, one row. Parameters work through the API |
| `EXPLAIN QUERY PLAN SELECT * FROM things WHERE code = 'a'` | off | Read path. The plan came back as a row |
| `PRAGMA table_info(things)` | off | Read path. One row per column |
| `SELECT * FROM nope` | off | `400`, `OperationalError: no such table: nope` |
| `SELECT * FROM things WHERE id = 999` | off | Read path, `{"rows":[],"truncated":false}` |
| `UPDATE things SET qty = 5 WHERE code = 'a'` | off | **Refused**, `400` |
| `SELECT 1; SELECT 2` | off | **Refused.** Two statements |
| `UPDATE things SET qty = 5 WHERE code = 'a'` | on | Write path, `{"rows":[],"affected":1}` |
| `CREATE TABLE scratch_t (a INTEGER)` | on | Write path, `{"rows":[],"affected":0}` |
| `INSERT INTO scratch_t (a) VALUES (1)` | on | Write path, `affected: 1` |
| `DROP TABLE scratch_t` | on | Write path, `affected: 0` |

Two of those rows deserve a second look.

**A `;` inside a quoted string makes the statement a write.** That is the classifier being cautious, and the cost is that a perfectly innocent read needs **allow writes** and then comes back with `affected` and no rows. If you need to search for text that contains a semicolon, pass the value as a parameter through the API (`WHERE note = ?` with `["a;b"]` in `params`). The semicolon is then not in the SQL text, and the statement stays a read.

**A statement that starts with a comment is a write.** Put the comment on the end, or leave it out.

### The guard is a safeguard, not a security boundary

The classifier looks for forbidden words **surrounded by spaces**. A word at the start of a line, after a bracket, or after a tab is not seen. In one run, this statement was sent with **allow writes off**:

```sql
WITH x AS (SELECT 1)
DELETE FROM things WHERE code = 'c'
```

The `DELETE` follows a newline, so it was not matched. The statement started with `with`, so it was classed as a read, ran down the read path, answered `{"rows":[],"truncated":false}`, and **the row was deleted**: a count afterwards went from 3 to 2. Because it took the read path, no `database.write` audit event was written and no cache was cleared.

What that means in practice:

- **Do not rely on the unticked checkbox to make a session safe.** Its job is to stop accidents by a careful person: a mistyped `UPDATE`, a pasted `DELETE`. It does not stop someone who is trying.
- **Access control is the real protection.** Only operator sessions reach these routes, and an operator already holds the right to write. Limit who holds it, and treat a Studio login with Database access as a database login.
- **If you give a person a read-only view of the data, give them a database role, not a console session.** A role that can only `SELECT` is enforced by the database. See [Your database](/data/your-database#a-role-for-pawabase).
- **Audit coverage is incomplete for statements that evade the classifier.** The `database.write` event covers writes the classifier recognised.

## What a write does around the statement

A write the classifier recognised runs, and then Pawabase does two things.

| After a successful write | Detail |
| --- | --- |
| **Audit** | An event `database.write` is recorded with the project, the environment and the SQL text **cut to its first 2,000 characters** |
| **Cache** | The cache tag of **every resource** in the environment is invalidated, because the console can change any table and Pawabase cannot tell which resource a statement touched |

And what it does **not** do:

| Not done | Consequence |
| --- | --- |
| No `resource.created`, `updated` or `deleted` event | Subscriptions, webhooks and flows triggered by those events never run |
| No realtime message | Connected clients are not told |
| No validation | Values outside enums, ranges and lengths are written |
| No policy check | Every row is reachable, whoever owns it |
| No `updated_at` change | A write does not touch it unless you set it |
| No rollback | A statement that succeeds is final |

A failed statement is not audited and does not clear caches, because nothing changed.

<Tip>
If something downstream must hear about a change, make the change through the API (or a flow) instead of the console. If you did it in the console, follow it with a write through the API for any record the downstream cares about.
</Tip>

## Errors and what they mean

| Status | Message | Meaning |
| --- | --- | --- |
| `400` | `this statement writes; set allow_write to run it` | The classifier called it a write and **allow writes** was off |
| `400` | `<ExceptionType>: <message>` | The database rejected the statement. The text after the colon is the database's own |
| `404` | `no table '<name>'` | The table browser asked for a table that does not exist |
| `504` | `the query timed out` | The statement ran past the environment's `query_timeout`, **15 seconds** by default |
| `422` | A validation list, for example `String should have at least 1 character` for `sql` | The request body is invalid: an empty `sql`, or one over 100,000 characters |
| `401` / `403` | | Not an operator session |
| `503` | | The environment's database cannot be reached. See [Your database](/data/your-database#what-an-invalid-or-missing-url-does) |

The `400` with the database's own text is the most useful message in the platform. A migration that fails with a bare 500 can be diagnosed by running its statement here, and the console says exactly what was wrong:

```text
OperationalError: no such table: nope
```

A typing mistake reads the same way: `SELEC 1` answers `400`, `OperationalError: near "SELEC": syntax error`.

On PostgreSQL the same slot holds messages such as `UndefinedTableError: relation "nope" does not exist` or `UniqueViolationError: duplicate key value violates unique constraint "ix_things_code"`. On MySQL, `OperationalError: (1146, "Table 'shop.nope' doesn't exist")`.

### A timeout does not necessarily stop the work

The `504` means Pawabase stopped waiting. Whether the database stopped working depends on the dialect and driver, so a long write that timed out may still complete, or may be in progress. Check the table before you retry. A statement that regularly times out belongs in a scheduled flow or a direct connection, not in the console.

## The limits

| Limit | Value | Beyond it |
| --- | --- | --- |
| Statements per run | **1** | Without **allow writes**, two statements are refused. With it, SQLite's driver refuses them too (`400`, `ProgrammingError: You can only execute one statement at a time.`) and **neither runs**. Other drivers may behave differently, so do not rely on a batch |
| Rows returned | **5,000** | The first 5,000 come back, with `truncated: true` and the note *Showing the first 5000 rows.* |
| Execution time | **15 seconds** (`query_timeout`) | `504 the query timed out` |
| SQL length | **100,000 characters** | `422` before it reaches the database |
| Table browser page | **50** rows in Studio, **500** at most through the API | `limit` is clamped |
| History | None | Closing the window discards the text |

Rows are limited **after** they are fetched: the database may have produced millions before Pawabase cut the list at 5,000. Put a `LIMIT` in the statement so the work is bounded too.

There is no bulk import: no `COPY` from a file and no upload. For a large load, use the database's own tooling or a flow.

## Parameters

The Studio window sends only the SQL text. The API route also accepts a `params` list, which is the right way to pass a value you did not write yourself:

```http
POST /platform/v1/projects/acme/envs/development/database/query
```

```json
{ "sql": "SELECT code FROM things WHERE code = ?", "params": ["a"], "allow_write": false }
```

The placeholder style is the **driver's**, so it differs by dialect:

| Dialect | Placeholder | Example |
| --- | --- | --- |
| SQLite | `?` | `WHERE code = ?` |
| PostgreSQL | `$1`, `$2`, … | `WHERE code = $1 AND qty > $2` |
| MySQL | `%s` | `WHERE code = %s` |

Parameters keep a value out of the SQL text, so nothing in it can change the statement, and they sidestep the quoting rules above. Use them from any script that builds a statement from data.

### A statement with `RETURNING` does not return rows

`INSERT ... RETURNING id` is a write, so it takes the write path and answers with a count, not the returned values:

```json
{ "rows": [], "affected": 1 }
```

The row was inserted, and the `id` you asked for was discarded. To learn the new key, run a separate `SELECT` afterwards, for example on the column you just set.

## When to use the console and when not to

| Task | Use | Why |
| --- | --- | --- |
| Read or write one record under your application's rules | The resource API | Validation, policies, events and the audit trail apply |
| List, filter, sort and page the normal way | The resource API | See [Filtering](/data/filtering) and [Sorting and pagination](/data/sorting-pagination) |
| Look at a table's structure, or glance at its rows | The table browser | No SQL, and it cannot write |
| Ask a question the API's filters cannot express: a join, a `GROUP BY`, a subquery | The SQL window, as a read | The API has no such operators |
| Check whether an index exists or is used | The SQL window, as a read | `EXPLAIN` and the catalogs |
| Find rows that violate a rule before you add it | The SQL window, as a read | For example duplicates before a unique index |
| A one-off repair or backfill | The SQL window, with **allow writes** | The API has no bulk operation |
| A repair that must be atomic across several statements | A direct connection, or a flow with a transaction | The console runs one statement per run |
| Anything that must trigger events, webhooks or realtime | The API or a flow | The console publishes nothing |
| Something that will happen again | A route, a flow or a schedule | A console fix does not repeat itself |

The last row is the one to remember. A repair you run twice in the console is a repair you should have built.

## Writing safely

The console has no undo, no dry run and no transaction. Safety is a habit, and the habit is the same four steps every time.

<Steps>
  <Step title="Write the SELECT first">
    Turn the `UPDATE` or `DELETE` into a `SELECT *` with the same `WHERE`, and run it. You are looking at exactly the rows that will change.

    ```sql
    SELECT id, status, updated_at FROM tickets WHERE status = 'spam' AND created_at < '2026-01-01';
    ```
  </Step>
  <Step title="Count them">
    Compare the count with what you expect. If you expected a dozen and the count says 40,000, the condition is wrong.

    ```sql
    SELECT COUNT(*) AS n FROM tickets WHERE status = 'spam' AND created_at < '2026-01-01';
    ```
  </Step>
  <Step title="Take a copy of what you are about to change">
    For anything beyond a handful of rows, copy them to a scratch table first, so the old values can be put back:

    ```sql
    CREATE TABLE tickets_backup_20261001 AS
    SELECT * FROM tickets WHERE status = 'spam' AND created_at < '2026-01-01';
    ```

    (The statement needs **allow writes**. Name the copy with the date so you can find it, and drop it when you no longer need it.)
  </Step>
  <Step title="Run the write, then check">
    Swap the `SELECT *` for the `UPDATE` or `DELETE`, keep the `WHERE` identical, run it, and compare `N row(s) affected` with the count. Then read the rows back.
  </Step>
</Steps>

The comparison in step 4 is the safety net. If the affected count is not the count from step 2, something changed between the two, and you should look before doing anything else.

### The builder and safety

When you change a statement with the **Delete** or **Update** action of the builder, the builder ticks **allow writes** for you, which means the one confirmation step is already gone. Read the generated SQL, and especially check that it has a `WHERE`. The warning *No condition: this affects every row.* is the builder's only guard.

### Work in batches for large changes

One statement that touches millions of rows holds locks for its whole run, and with a 15-second limit it will probably time out anyway. Use a batch and repeat:

```sql
-- PostgreSQL
UPDATE tickets SET status = 'closed'
WHERE id IN (SELECT id FROM tickets WHERE status = 'solved' AND updated_at < '2026-01-01' LIMIT 5000);

-- MySQL
UPDATE tickets SET status = 'closed' WHERE status = 'solved' AND updated_at < '2026-01-01' LIMIT 5000;

-- SQLite
UPDATE tickets SET status = 'closed'
WHERE id IN (SELECT id FROM tickets WHERE status = 'solved' AND updated_at < '2026-01-01' LIMIT 5000);
```

Run it until it reports `0 row(s) affected`. Each run is audited, so a long job leaves a long trail, which is useful and noisy. For a really long job, use a scheduled flow.

### Staging first

If you can, run the statement in a copy of the environment first. A scratch environment pointed at a restored backup gives you a place where a mistake costs nothing. See [Your database](/data/your-database#restoring-into-a-scratch-environment).

## Recipes

Every recipe here is a read unless it says otherwise. They use `tickets`, `products` and `profiles` as examples. Replace the names, and on the shared PostgreSQL default use the physical table name.

### Look at a record without any shaping

```sql
SELECT * FROM tickets WHERE id = 12;
```

This is the raw row, with every column, `write_only` fields, columns the resource does not declare, and nothing hidden by a transformer or policy. It is the first fact to establish when the API's answer looks wrong.

### Compare the API's answer with the row

If the API shows a field as `null` and the row has a value, a transformer or `select` is hiding it. If the row is `null` and the API shows a default, a default is applied at read. If the row is missing, a policy hid it. See [Policies](/policies/overview).

### Find duplicates before making a field unique

```sql
SELECT sku, COUNT(*) AS n
FROM products
GROUP BY sku
HAVING COUNT(*) > 1
ORDER BY n DESC;
```

An empty result means a unique index will build. See [Migrations](/data/migrations#the-unique-index-fails-because-duplicates-exist).

### Remove duplicates, keeping the oldest

```sql
-- preview
SELECT id, sku FROM products
WHERE id NOT IN (SELECT MIN(id) FROM products GROUP BY sku);

-- write (allow writes)
DELETE FROM products
WHERE id NOT IN (SELECT MIN(id) FROM products GROUP BY sku);
```

MySQL cannot delete from a table that the subquery reads, so wrap the subquery: `WHERE id NOT IN (SELECT id FROM (SELECT MIN(id) AS id FROM products GROUP BY sku) AS keep)`.

### Find rows that break a rule the database does not enforce

Enums, ranges and lengths are API rules, so rows written by flows, functions, the Records tab or the console can break them:

```sql
SELECT id, status FROM tickets WHERE status NOT IN ('open', 'pending', 'solved');
SELECT id, price_minor FROM products WHERE price_minor < 0;
SELECT id, LENGTH(subject) AS len FROM tickets WHERE LENGTH(subject) > 160;
SELECT id FROM tickets WHERE subject IS NULL;
```

A row that fails the enum breaks reads of the list that includes it (a `500`, *Response validation failed*), so this is the query to run when a list suddenly fails.

### Fix an enum value across the table

```sql
-- preview
SELECT status, COUNT(*) AS n FROM tickets GROUP BY status ORDER BY n DESC;

-- write (allow writes)
UPDATE tickets SET status = 'solved' WHERE status = 'closed';
```

Do this **before** you shrink an enum, never after. See [Validation](/data/validation).

### Backfill a column added later

```sql
SELECT COUNT(*) AS missing FROM tickets WHERE priority IS NULL;

UPDATE tickets SET priority = 2 WHERE priority IS NULL;
```

Columns added by a migration have no default, so old rows are `NULL` until you write them. See [Migrations](/data/migrations#adding-a-field-to-a-table-that-has-rows).

### Find orphans, rows whose parent is gone

Pawabase creates no foreign keys, so a child can outlive its parent. A `has_many` expand then shows `null`:

```sql
SELECT t.id, t.requester_id
FROM tickets t
LEFT JOIN requesters r ON r.id = t.requester_id
WHERE t.requester_id IS NOT NULL AND r.id IS NULL;
```

Resolve them by deleting the children, reassigning them, or restoring the parent. See [Relations](/data/relations).

### Find the biggest rows

```sql
-- PostgreSQL
SELECT id, pg_column_size(t.*) AS bytes FROM tickets t ORDER BY bytes DESC LIMIT 20;

-- MySQL
SELECT id, LENGTH(body) AS bytes FROM tickets ORDER BY bytes DESC LIMIT 20;

-- SQLite
SELECT id, LENGTH(body) AS bytes FROM tickets ORDER BY bytes DESC LIMIT 20;
```

A few very large rows are usually why a list is slow and a table is large.

### Count by day

```sql
-- PostgreSQL
SELECT date_trunc('day', created_at) AS day, COUNT(*) AS n FROM tickets GROUP BY 1 ORDER BY 1 DESC LIMIT 30;

-- MySQL
SELECT DATE(created_at) AS day, COUNT(*) AS n FROM tickets GROUP BY day ORDER BY day DESC LIMIT 30;

-- SQLite (the timestamp is text)
SELECT substr(created_at, 1, 10) AS day, COUNT(*) AS n FROM tickets GROUP BY day ORDER BY day DESC LIMIT 30;
```

### Look inside a JSON column

```sql
-- PostgreSQL (JSONB)
SELECT id, specs->>'color' AS color FROM products WHERE specs->>'color' = 'blue';

-- MySQL (JSON)
SELECT id, JSON_UNQUOTE(JSON_EXTRACT(specs, '$.color')) AS color FROM products
WHERE JSON_UNQUOTE(JSON_EXTRACT(specs, '$.color')) = 'blue';

-- SQLite (JSON as text, with the JSON1 functions)
SELECT id, json_extract(specs, '$.color') AS color FROM products WHERE json_extract(specs, '$.color') = 'blue';
```

The API's filters cannot look inside JSON, and the console can. See [Filtering](/data/filtering).

### Repair a stored object after a schema changed

See the worked repair on [Schemas](/data/schemas), which rewrites keys inside a JSON column with `jsonb_set`, `JSON_SET` or `json_set`.

### Check an index is used

```sql
-- PostgreSQL
EXPLAIN SELECT * FROM tickets WHERE status = 'open' ORDER BY id DESC LIMIT 20;

-- MySQL
EXPLAIN SELECT * FROM tickets WHERE status = 'open' ORDER BY id DESC LIMIT 20;

-- SQLite
EXPLAIN QUERY PLAN SELECT * FROM tickets WHERE status = 'open' ORDER BY id DESC LIMIT 20;
```

`EXPLAIN` is a read, so it needs no **allow writes**. On SQLite the plan came back as a row such as `SEARCH things USING INDEX ix_things_code (code=?)`, which names the index in use. A plan that says `SCAN` on a large table is a full pass. See [Filtering](/data/filtering#filters-and-indexes).

`EXPLAIN ANALYZE` on PostgreSQL **runs** the statement, so never use it on an `UPDATE` or `DELETE` you have not meant to execute. Plain `EXPLAIN` only plans.

### Move rows from one status to another, safely

```sql
SELECT COUNT(*) FROM tickets WHERE status = 'pending' AND updated_at < '2026-06-01';
UPDATE tickets SET status = 'solved', updated_at = CURRENT_TIMESTAMP
WHERE status = 'pending' AND updated_at < '2026-06-01';
```

Set `updated_at` yourself when it matters: the console does not touch it. On SQLite the timestamp column is text, so `CURRENT_TIMESTAMP` writes `2026-10-01 21:39:28` and the API writes `2026-10-01T21:39:28.999385+00:00`. Mixed formats sort and compare as text, which can misorder them. Match the API's form with `strftime('%Y-%m-%dT%H:%M:%S+00:00', 'now')` on SQLite.

## System catalogs by dialect

The catalogs are where a database describes itself, and the console reads them like any table. These are the questions that come up most.

### Which tables, columns and indexes exist

| Question | PostgreSQL | MySQL | SQLite |
| --- | --- | --- | --- |
| List tables | `SELECT tablename FROM pg_tables WHERE schemaname = 'public'` | `SHOW TABLES` | `SELECT name FROM sqlite_master WHERE type = 'table'` |
| A table's columns | `SELECT column_name, data_type, is_nullable FROM information_schema.columns WHERE table_name = 'tickets'` | `DESCRIBE tickets` | `PRAGMA table_info(tickets)` |
| A table's indexes | `SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'tickets'` | `SHOW INDEX FROM tickets` | `PRAGMA index_list(tickets)` |
| The create statement | `\d+ tickets` in `psql` (not SQL) | `SHOW CREATE TABLE tickets` | `SELECT sql FROM sqlite_master WHERE name = 'tickets'` |
| Foreign keys | `SELECT conname FROM pg_constraint WHERE contype = 'f'` | `SELECT * FROM information_schema.key_column_usage WHERE referenced_table_name IS NOT NULL` | `PRAGMA foreign_key_list(tickets)` |

All of these are reads. The ones that start with `select`, `show`, `describe` or `pragma` pass the classifier. On SQLite, `PRAGMA table_info(things)` returned one row per column:

```json
{ "cid": 1, "name": "code", "type": "TEXT", "notnull": 0, "dflt_value": null, "pk": 0 }
```

### How big things are

```sql
-- PostgreSQL
SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS size
FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 10;

-- MySQL
SELECT table_name, ROUND((data_length + index_length) / 1048576, 1) AS mb
FROM information_schema.tables WHERE table_schema = DATABASE() ORDER BY mb DESC LIMIT 10;

-- SQLite: total pages, then page size
PRAGMA page_count;
PRAGMA page_size;
```

### What is running

```sql
-- PostgreSQL
SELECT pid, state, now() - query_start AS running, left(query, 80) AS query
FROM pg_stat_activity WHERE state <> 'idle' ORDER BY running DESC;

-- MySQL
SHOW FULL PROCESSLIST;
```

The console's own statement is on the list too, so ignore the row that is yours.

### Reading a SQLite plan

`EXPLAIN QUERY PLAN` rows have a `detail` column. These are the shapes you will see:

| `detail` | Meaning |
| --- | --- |
| `SEARCH things USING INDEX ix_things_code (code=?)` | The index is used to find matching rows |
| `SEARCH things USING INTEGER PRIMARY KEY (rowid=?)` | A lookup by key |
| `SCAN things` | Every row is read |
| `USE TEMP B-TREE FOR ORDER BY` | The sort is done in a temporary structure, because no index gives the order |

`EXPLAIN` without `QUERY PLAN` on SQLite returns the low-level program (opcodes), as seen in one run, which is rarely what you want.

## Using the routes from a script

The console's routes are ordinary platform API calls, so anything the window does you can do from a script, with the same operator credentials.

```bash
BASE="https://api.example.com/platform/v1/projects/acme/envs/production/database"
AUTH="Authorization: Bearer $OPERATOR_TOKEN"

# overview
curl -s -H "$AUTH" "$BASE"

# one table
curl -s -H "$AUTH" "$BASE/tables/tickets"

# a page of rows
curl -s -H "$AUTH" "$BASE/tables/tickets/rows?limit=100&offset=0"

# a read
curl -s -X POST -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"sql":"SELECT status, COUNT(*) AS n FROM tickets GROUP BY status"}' "$BASE/query"

# a write
curl -s -X POST -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"sql":"UPDATE tickets SET status = $1 WHERE status = $2","params":["solved","closed"],"allow_write":true}' "$BASE/query"
```

A script that runs a repair, checks the count before and after, and stops if they disagree:

```python
import os
import requests

BASE = "https://api.example.com/platform/v1/projects/acme/envs/production/database"
HEADERS = {"Authorization": f"Bearer {os.environ['OPERATOR_TOKEN']}"}


def run(sql, params=(), write=False):
    response = requests.post(
        f"{BASE}/query",
        headers=HEADERS,
        json={"sql": sql, "params": list(params), "allow_write": write},
        timeout=30,
    )
    response.raise_for_status()
    return response.json()


condition = "status = $1 AND updated_at < $2"
args = ["pending", "2026-06-01"]

expected = run(f"SELECT COUNT(*) AS n FROM tickets WHERE {condition}", args)["rows"][0]["n"]
print("rows to change:", expected)

result = run(
    f"UPDATE tickets SET status = 'solved' WHERE {condition}", args, write=True
)
print("affected:", result["affected"])

if result["affected"] != expected:
    raise SystemExit("the count changed between the preview and the write. Investigate")
```

Because the script goes through the same routes, its writes are audited and clear caches exactly as a click would.

### Reading a whole table

The rows route pages with `limit` (at most 500) and `offset`. A script that copies a table reads pages until one comes back short:

```python
def all_rows(table, page=500):
    offset = 0
    while True:
        batch = requests.get(
            f"{BASE}/tables/{table}/rows", headers=HEADERS, params={"limit": page, "offset": offset}, timeout=30
        ).json()["data"]
        yield from batch
        if len(batch) < page:
            return
        offset += page
```

The rows have no `ORDER BY`, so the pages are in the table's natural order. For a table that is changing, use the SQL route with `ORDER BY id` and a keyset condition instead, or the offsets can repeat or skip rows.

## Who can use the console

The four routes require an **operator**, the same level as the rest of Studio's platform API. An end user's token, a publishable key and a secret key do not reach them.

| Credential | Console access |
| --- | --- |
| Studio operator session | Yes |
| An operator token used from a script | Yes |
| A publishable key (`pk_...`) | No |
| A secret key (`sk_...`) | No. It is for the data plane |
| An end user's access token | No |

Two consequences:

- **Console access equals database access.** There is no per-table or per-environment narrowing beyond which environment the URL names, and no read-only operator level for these routes. If someone needs to look at data but not change it, give them a database role that can only read, and let them use their own client. See [Your database](/data/your-database#a-read-only-role-for-people).
- **Every write is attributed.** The `database.write` event records who ran it, so the trail answers "who changed this" for anything the console recognised as a write.

## A reproduced session

This is a real sequence from a clean API on SQLite, in the order it ran, because it shows the classifier's edges better than a description does.

<Steps>
  <Step title="Create three rows">
    A `things` resource is created, migrated, and given three rows through the API with `code` values `a`, `b` and `c`. The second row's `note` is `x;y`, and the first's is `update me`.
  </Step>
  <Step title="Read with a quoted word">
    `SELECT code FROM things WHERE note = 'update me'` returns `a`. The word `update` is next to a quote, not a space, so the classifier does not see it.
  </Step>
  <Step title="Read with a quoted semicolon">
    `SELECT code FROM things WHERE note = 'x;y'` is refused: `this statement writes; set allow_write to run it`. The semicolon is inside a string and still counts.
  </Step>
  <Step title="Force it through with allow writes">
    The same statement with **allow writes** runs, and answers `{"rows": [], "affected": 1}`. It ran as a write, so no rows came back. The fix is a parameter.
  </Step>
  <Step title="Use a parameter">
    `SELECT code FROM things WHERE code = ?` with `["a"]` returns the row. A value containing a semicolon passed the same way also works as a read.
  </Step>
  <Step title="Look at the plan">
    `EXPLAIN QUERY PLAN SELECT * FROM things WHERE code = 'a'` returns `SEARCH things USING INDEX ix_things_code (code=?)`: the index created by the migration is used.
  </Step>
  <Step title="Try to write without permission">
    `UPDATE things SET qty = 5 WHERE code = 'a'` is refused with `400`. With **allow writes** it runs and reports `affected: 1`.
  </Step>
  <Step title="Test the guard">
    A statement beginning `WITH x AS (SELECT 1)`, then a newline, then `DELETE FROM things WHERE code = 'c'`, is sent **without** **allow writes**. It is accepted as a read, answers `{"rows": [], "truncated": false}`, and the row is gone. The next `COUNT(*)` reads 2, not 3. No audit event was written for it.
  </Step>
</Steps>

The last step is why the earlier section says the unticked checkbox is a safeguard against accidents, not a security boundary.

## What values look like in results

The API decodes a value by its field type: a boolean becomes `true`, a JSON column becomes an object. The console has no field types to go by, so it returns what the driver gives it, with a few conversions for JSON-safety. This is one row, written through the API and then read back both ways, on SQLite:

```json
{
  "id": 1,
  "flag": 1,
  "meta": "{\"a\": 1}",
  "tags": "[\"x\", \"y\"]",
  "price": 1.5,
  "u": "123e4567-e89b-12d3-a456-426614174000",
  "d": "2026-10-01",
  "at": "2026-10-01T10:00:00+02:00",
  "created_at": "2026-10-01T21:44:15.501985+00:00",
  "updated_at": "2026-10-01T21:44:15.501985+00:00"
}
```

The same record through `GET /rest/v1/items/1` shows `"flag": true` and `"meta": {"a": 1}`, because the API knows the types.

| Type | In a console result |
| --- | --- |
| Boolean | `1` and `0` on SQLite. `true` and `false` on PostgreSQL and MySQL |
| JSON, array, object | **JSON text** on SQLite, as a string. Other drivers may return text or a parsed value, so check before you rely on one |
| Datetime | A string. On SQLite exactly as stored, offset included. Other dialects return an ISO string from the driver's value |
| Date | An ISO string |
| UUID | A string |
| Decimal | A float |
| `NULL` | `null` |
| A binary column | **A `500`** with no message. The value cannot be written as JSON |

The last row is a trap. `SELECT X'FF00' AS b` answered a plain `500`, and so would the table browser on a table with a binary column. If a table has one, select the other columns by name.

### Why this matters

A query result is the **database's** view, which is the right view for checking storage and a poor one for checking what a client sees. Two habits follow:

- **To check what a client sees, call the API.** The console cannot show you transformers, `select`, or decoding.
- **To check what is stored, use the console, and read booleans and JSON accordingly.** A `1` is a `true`, and a JSON string is an object.

## Queries to keep for each kind of resource

A short library per shape of resource. Each is a read.

### A catalog (`products`)

```sql
-- low stock
SELECT sku, title, stock FROM products WHERE stock < 5 ORDER BY stock, id LIMIT 50;

-- status mix
SELECT status, COUNT(*) AS n FROM products GROUP BY status ORDER BY n DESC;

-- rows with no price
SELECT id, sku FROM products WHERE price_minor IS NULL;

-- products created this week
SELECT id, sku, created_at FROM products WHERE created_at >= '2026-09-24' ORDER BY id DESC;
```

### Tickets with an owner (`tickets`)

```sql
-- load per requester
SELECT requester_id, COUNT(*) AS n FROM tickets GROUP BY requester_id ORDER BY n DESC LIMIT 20;

-- tickets with no owner (invisible to every owner-scoped policy)
SELECT id, subject FROM tickets WHERE requester_id IS NULL;

-- oldest open
SELECT id, subject, created_at FROM tickets WHERE status = 'open' ORDER BY id LIMIT 20;

-- priority mix
SELECT priority, status, COUNT(*) AS n FROM tickets GROUP BY priority, status ORDER BY priority, status;
```

The second query matters more than it looks. A row whose owner is `NULL` matches no owner policy, so it exists and no end user can see it. Rows get there through flows, the Records tab, the console, or a field added after the rows existed.

### An append-only log (`audit_events`)

```sql
-- the newest events
SELECT id, occurred_at, actor, action FROM audit_events ORDER BY id DESC LIMIT 50;

-- volume per day
SELECT substr(occurred_at, 1, 10) AS day, COUNT(*) AS n FROM audit_events GROUP BY day ORDER BY day DESC LIMIT 14;

-- the noisiest actions
SELECT action, COUNT(*) AS n FROM audit_events GROUP BY action ORDER BY n DESC LIMIT 10;
```

### Profiles with a unique owner (`profiles`)

```sql
-- more than one profile per user (should be none)
SELECT user_id, COUNT(*) AS n FROM profiles GROUP BY user_id HAVING COUNT(*) > 1;

-- profiles with no display name
SELECT id, user_id FROM profiles WHERE display_name IS NULL OR display_name = '';
```

### Switches (`feature_flags`)

```sql
SELECT key, enabled, rollout_percent FROM feature_flags ORDER BY key;

-- flags that are on for everyone
SELECT key FROM feature_flags WHERE enabled = 1 AND rollout_percent = 100;
```

On PostgreSQL and MySQL write `enabled = TRUE` instead of `= 1`.

## Keeping a library of statements

The window has no saved queries, so a team that uses the console regularly keeps its own.

| Where | Good for |
| --- | --- |
| A file in your repository, such as `ops/console/*.sql` | Statements you reuse, reviewed like code |
| A runbook with each repair, its preview and its check | Repairs that happen rarely and carry risk |
| A resource of your own with a `sql` text field and a description | A shared, searchable list inside Pawabase |

Whatever the home, store the **preview** and the **check** next to each write. A bare `UPDATE` in a notes file is a hazard. The same statement with its `SELECT COUNT(*)` before and after is a procedure.

## A team policy that works

The console is powerful enough that a few agreements are worth making.

1. **Who may use it.** Operator access is database access, so list the people and review the list when someone leaves.
2. **Read-only first.** Look with a read, and write only when the read shows what the write must do.
3. **Two sets of eyes for destructive statements.** A `DELETE` or an `UPDATE` without a narrow `WHERE` is read by a second person before it runs.
4. **Back up before a bulk change**, and record where the backup is.
5. **Prefer the API or a flow** for anything that must publish events, notify clients or be repeated.
6. **Record what was done.** The audit log keeps the statement for you. Add why, in the ticket or the runbook.
7. **Do not use the console as a viewer for people who should not see everything.** Give them a read-only database role.

## From an API filter to SQL

If you know the resource API's filters, the console is a small step. Each filter operator is one `WHERE` condition, and the table below is how the API writes them. See [Filtering](/data/filtering) for the API side.

| API filter | SQL |
| --- | --- |
| `filter[status]=eq.open` | `status = 'open'` |
| `filter[status]=neq.open` | `status <> 'open'` (and the API's `neq` also drops `NULL` rows, as SQL does) |
| `filter[stock]=gt.10` | `stock > 10` |
| `filter[stock]=gte.10` | `stock >= 10` |
| `filter[stock]=lt.10` | `stock < 10` |
| `filter[stock]=lte.10` | `stock <= 10` |
| `filter[title]=like.mug*` | `title LIKE 'mug%'` |
| `filter[title]=ilike.mug*` | A case-insensitive match: `title ILIKE 'mug%'` on PostgreSQL, `LIKE` on SQLite and MySQL |
| `filter[status]=in.open,pending` | `status IN ('open', 'pending')` |
| `filter[status]=nin.open,pending` | `status NOT IN ('open', 'pending')` |
| `filter[due]=is.null` | `due IS NULL` |
| `filter[active]=is.true` | `active = TRUE` (`= 1` on SQLite) |
| `sort=-id` | `ORDER BY id DESC` |
| `per_page=20&page=3` | `LIMIT 20 OFFSET 40` |
| `select=id,subject` | `SELECT id, subject` |

Three things the API does that SQL does not do for you:

- **The policy's conditions.** The API adds the policy's `WHERE` clauses, such as `requester_id = <caller>`. A console query has none, so it returns rows the caller could never see.
- **The type conversion.** The API converts `10` to an integer for an integer column. In SQL you write `10`, not `'10'`, or you compare text.
- **The decoding.** Booleans and JSON come back raw.


## The console and the Records tab

Studio has a second way to edit rows by hand, the **Records** tab on a resource's sheet, and it behaves differently from the console. Choosing between them is choosing which checks you want to skip.

| | **Records tab** | **Console (SQL window)** |
| --- | --- | --- |
| **Where** | A resource's sheet, tab **Records** | The Database page, **SQL** button |
| **Works on** | One resource's table, row by row | Any table, any statement |
| **Field validation** | **Skipped**: a title past `max_length`, a quantity below `minimum` and an enum violation are all accepted | **Skipped** |
| **Unknown fields** | Refused: `400`, `unknown fields: bogus` | Not applicable. You write columns directly |
| **Policy** | Skipped | Skipped |
| **Events, webhooks, realtime** | **Published**, as for an API write | **Not published** |
| **Cache** | That resource's tag is invalidated | **Every** resource's tag is invalidated |
| **Audit** | **Not recorded** in the audit log (the route calls the same after-write step as the API, which publishes events, but writes no audit entry) | `database.write` with the SQL |
| **Bulk** | One record at a time | A whole table in one statement |

The row that matters is **events**. If a change must reach a subscription, a webhook or connected clients, make it in the Records tab, which publishes them, and not in the console, which does not. If the change is a bulk repair that downstream should not hear about, the console is the right tool, and the silence is the feature.

The audit row is the surprising one: the **console is audited and the Records tab is not**. Someone who edits rows in the Records tab leaves events (if the resource publishes them) and nothing in the audit log, while the same edit as SQL would be recorded. If you need an audit trail of hand edits, prefer SQL in the console, or record the edit yourself.

Both skip validation, so both can write rows the API will later fail to read. A row written by the Records tab with a value outside an enum breaks the list that contains it exactly as a console write does. See [Validation](/data/validation).

## A short SQL primer for the console

People who open the console rarely write SQL every day, so here is the minimum, in the order you meet it.

### Choosing columns and rows

```sql
SELECT id, subject, status      -- the columns you want
FROM tickets                    -- the table
WHERE status = 'open'           -- the rows you want
ORDER BY id DESC                -- the order
LIMIT 20;                       -- how many
```

Always include a `LIMIT` when you are exploring, so a large table does not return 5,000 rows to read.

### Counting and grouping

```sql
SELECT COUNT(*) FROM tickets;                              -- how many rows
SELECT status, COUNT(*) FROM tickets GROUP BY status;      -- how many per status
SELECT status, COUNT(*) AS n FROM tickets GROUP BY status HAVING COUNT(*) > 100;
```

`WHERE` filters rows **before** grouping, and `HAVING` filters groups **after**.

### Combining conditions

```sql
WHERE status = 'open' AND priority >= 2           -- both
WHERE status = 'open' OR status = 'pending'       -- either
WHERE status IN ('open', 'pending')               -- the same, shorter
WHERE (status = 'open' OR status = 'pending') AND priority >= 2   -- brackets decide the order
```

`AND` binds tighter than `OR`, so brackets are not optional when you mix them. A delete that mixes them without brackets deletes a different set than you meant.

### Nulls

```sql
WHERE due IS NULL            -- never `= NULL`
WHERE due IS NOT NULL
```

A comparison with `NULL` is never true, so `status <> 'open'` leaves out the rows where `status` is `NULL`. Add `OR status IS NULL` if you want them.

### Joining two tables

```sql
SELECT t.id, t.subject, r.email
FROM tickets t
JOIN requesters r ON r.id = t.requester_id;
```

`JOIN` keeps rows with a match on both sides. `LEFT JOIN` keeps every ticket and fills `NULL` where there is no requester, which is how you find orphans.

### Changing rows

```sql
UPDATE tickets SET status = 'solved' WHERE id = 12;
DELETE FROM tickets WHERE id = 12;
INSERT INTO tickets (subject, status) VALUES ('Printer is offline', 'open');
```

An `UPDATE` or `DELETE` **without** `WHERE` changes every row. Always write the `WHERE` first, then the rest.

### The habit that prevents most disasters

Write the `WHERE` before anything else. Make it a `SELECT` and look. Only then turn it into an `UPDATE` or `DELETE`.

## Performance and the console

The console runs against the same database as your live traffic, so a heavy query is a slow query for your users.

| Habit | Why |
| --- | --- |
| Always `LIMIT` while exploring | A result over 5,000 rows is cut after the database has produced it |
| Filter on indexed columns | An unindexed filter on a large table reads the whole table |
| Avoid `SELECT *` on a table with large JSON or text columns | You pull data you do not need through the API |
| Do aggregates in SQL, not by reading rows | `COUNT(*)` is cheap, reading a million rows is not |
| Run heavy reports against a replica or a restored copy | They compete with production |
| Stay under the 15-second limit | Past it you get a `504` and an unknown outcome |

A report that takes minutes is not a console job. Use a read-only role from your own tool against a replica, or a scheduled export.

### Reading a plan

Run `EXPLAIN` before a heavy query. The shape to look for is **an index used, and a small number of rows**.

```text
-- PostgreSQL, typical shape
Limit  (cost=0.29..8.31 rows=20 width=...)
  ->  Index Scan Backward using tickets_pkey on tickets  (cost=0.29..400.10 rows=1000 width=...)
        Filter: (status = 'open'::text)
```

An `Index Scan` or `Index Only Scan` is good. A `Seq Scan` over a table of millions of rows is a full pass, and the fix is usually an index on the filtered column or an order by `id`. The plan above scans the key index backwards, which is why `ORDER BY id DESC LIMIT 20` is fast on every table Pawabase creates.

## Where the console ends

The console is the right tool for looking and for occasional, careful repairs. It stops being the right tool when:

- **The work repeats.** Build a route, a flow or a schedule.
- **The change must be announced.** Use the API or a flow so that events, webhooks and realtime fire.
- **The change must be atomic across several statements.** Use a flow with `db.transaction`, or a direct connection.
- **The data is large.** Use the database's bulk tools.
- **Someone who should not see everything needs to look.** Give them a read-only role.
- **You need an audit of what a person *saw*.** The console audits writes, not reads.

Past those edges, the console is a convenience that turns into a risk, and the habits above are what keep it a convenience.

## A final worked example: from a complaint to a fix

A support agent reports that one customer's ticket list is empty in the app, though the customer says they have open tickets. This is the whole path, from the first look to the fix, and where each tool comes in.

**1. Reproduce through the API.** Ask for the customer's tickets with their token. The response is an empty list. The API is working, so the cause is in the data or the policy.

**2. Look at the raw rows in the console.**

```sql
SELECT id, subject, status, requester_id FROM tickets WHERE requester_id = 'u-4821' ORDER BY id DESC LIMIT 20;
```

No rows. So no ticket has that owner. Search by something the customer knows:

```sql
SELECT id, subject, status, requester_id FROM tickets WHERE requester_email = 'maya@acme.co' ORDER BY id DESC LIMIT 20;
```

Three tickets come back, and `requester_id` is `NULL` on all of them.

**3. Find the scope of it.**

```sql
SELECT COUNT(*) AS orphaned FROM tickets WHERE requester_id IS NULL;
SELECT MIN(id), MAX(id), MIN(created_at), MAX(created_at) FROM tickets WHERE requester_id IS NULL;
```

Forty rows, all created in one afternoon. Something wrote tickets without an owner during that window.

**4. Find the cause.** Tickets are only given an owner when a signed-in user creates them through the API. Rows created by a flow, the Records tab or the console have none unless set. A flow triggered by an inbound email created these. That is a bug in the flow, which must set `requester_id`.

**5. Fix the data.** The email address identifies the user, so match on it:

```sql
-- preview
SELECT t.id, t.requester_email, u.id AS user_id
FROM tickets t JOIN users u ON u.email = t.requester_email
WHERE t.requester_id IS NULL;
```

Where the users live depends on how your authentication is set up, and they may not be in this database at all. If they are not, supply the mapping from your user list. Then, in batches, with **allow writes**:

```sql
UPDATE tickets SET requester_id = 'u-4821' WHERE id IN (101, 102, 103);
```

**6. Fix the cause**, in the flow, so it sets `requester_id` from the sender. Without that, the next email repeats the problem, and the console repair is only a patch.

**7. Check from the customer's side**: ask for their tickets again with their token. Three come back.

The console served three of the seven steps: finding, scoping and patching. The API reproduced the symptom and confirmed the fix, and the real repair was a change to a flow. That division is typical, and it is a good test of whether you are using the console well: if every step of a problem was done in it, something that should have been built is missing.

## Finding console writes in the audit log

Studio's **Audit log** page lists every change made in the organisation, with the columns **When**, **Actor**, **Action**, **Where** and **Target**. A console write appears as:

| Column | Value |
| --- | --- |
| **When** | The time of the write |
| **Actor** | The operator who ran it |
| **Action** | `database.write` |
| **Where** | `project/environment`, for example `acme/production` |
| **Target** | Empty. The statement is not tied to one resource |

The statement itself is in the event's details, as `sql`, **cut to the first 2,000 characters**. A long statement therefore shows only its start, which is usually enough to see what it was.

Filter the action to `database.write` and you have the answer to "who changed the data by hand, and when?" Migrations have their own action, `resource.migrated`, with the statements in the details. See [Audit log](/operate/audit-log).

Three limits on what the trail can tell you:

1. **It records recognised writes only.** A statement the classifier treated as a read (including the newline case described earlier) leaves no event.
2. **It records the statement, not the effect.** The log does not say how many rows changed, only what was sent.
3. **It records nothing about direct connections.** A change made with `psql` is in the database's own log and nowhere in Pawabase.

## The same guard in flows

Flows have a `db.query` block for SQL reads, and it uses the **same classifier** as the console. A flow author who needs a join or an aggregate writes SQL in that block, and the block refuses a statement the classifier calls a write. So everything on this page about what passes as a read applies there as well, including the space-delimited word check.

For several writes that must land together, a flow uses `db.transaction` over resource operations, which goes through validation hooks and events in a way the console does not. If a repair must be atomic, that is the tool, not the console. See [Data blocks](/flows/data-blocks).

## Worked repairs

Each of these is a complete repair, in the order you would run it, with the reasoning.

### Purging spam older than a date

**Situation.** A public `comments` resource accepted spam for a week. You want every comment marked `spam` and older than 30 days gone.

```sql
-- 1. how many, and are they what you think?
SELECT COUNT(*) AS n FROM comments WHERE status = 'spam' AND created_at < '2026-09-01';
SELECT id, left_part FROM (SELECT id, substr(body, 1, 60) AS left_part FROM comments
                           WHERE status = 'spam' AND created_at < '2026-09-01' LIMIT 10) AS sample;

-- 2. keep a copy of what will go
CREATE TABLE comments_purged_20261001 AS
SELECT * FROM comments WHERE status = 'spam' AND created_at < '2026-09-01';

-- 3. delete in batches until 0 rows are affected
DELETE FROM comments WHERE id IN (
  SELECT id FROM comments WHERE status = 'spam' AND created_at < '2026-09-01' LIMIT 5000
);

-- 4. confirm
SELECT COUNT(*) AS remaining FROM comments WHERE status = 'spam' AND created_at < '2026-09-01';
```

**Notes.** The second statement of step 1 uses a subquery so that it works on every dialect. The batch limit keeps each statement short enough to finish inside the 15-second limit. On MySQL, use `DELETE FROM comments WHERE status = 'spam' AND created_at < '2026-09-01' LIMIT 5000` directly. The timestamps are text on SQLite, so an ISO date compares correctly as long as every stored value has the same form.

### Renaming an enum value

**Situation.** Tickets were `closed`, and the new vocabulary is `solved`. Clients already send `solved`.

```sql
-- 1. the vocabulary as it is now
SELECT status, COUNT(*) AS n FROM tickets GROUP BY status ORDER BY n DESC;

-- 2. change the data
UPDATE tickets SET status = 'solved' WHERE status = 'closed';

-- 3. only now change the enum in the resource definition
```

**Notes.** The order is the whole repair. If the enum is changed first, every row still holding `closed` breaks the reads of any list that includes it. The data moves first, and the definition follows.

### Cleaning up after a column was split

**Situation.** `full_name` became `first_name` and `last_name`. The new fields are empty for old rows.

```sql
SELECT COUNT(*) AS missing FROM profiles WHERE first_name IS NULL AND full_name IS NOT NULL;

-- PostgreSQL
UPDATE profiles
SET first_name = split_part(full_name, ' ', 1),
    last_name  = NULLIF(trim(substr(full_name, length(split_part(full_name, ' ', 1)) + 1)), '')
WHERE first_name IS NULL AND full_name IS NOT NULL;
```

**Notes.** Names do not split cleanly, so check a sample before running it, and keep `full_name` until clients have moved. SQLite and MySQL have no `split_part`, so use `substr` and `instr` (SQLite) or `SUBSTRING_INDEX` (MySQL).

### Reassigning rows to a different owner

**Situation.** A user was merged into another account, and their tickets must follow.

```sql
SELECT COUNT(*) AS n FROM tickets WHERE requester_id = 'u-old';
UPDATE tickets SET requester_id = 'u-new' WHERE requester_id = 'u-old';
```

**Notes.** The owner field is the one the API never lets a client change, since `PATCH` drops it. This is exactly the kind of change the console exists for. Afterwards, owner-scoped policies show the tickets to the new owner.

### Finding what a slow list is doing

**Situation.** `GET /rest/v1/tickets?sort=created_at` is slow.

```sql
EXPLAIN QUERY PLAN SELECT * FROM tickets ORDER BY created_at DESC LIMIT 20;
-- ... USE TEMP B-TREE FOR ORDER BY   (no index on created_at)
```

**Fix.** Either sort by `id`, which is indexed and tracks creation order, or add the index with **allow writes**:

```sql
CREATE INDEX IF NOT EXISTS ix_tickets_created_at ON tickets (created_at);
```

Run the `EXPLAIN` again to confirm the plan now says `SEARCH ... USING INDEX`. See [Sorting and pagination](/data/sorting-pagination).

## SQL that differs between dialects

A statement that works in one dialect often needs a change in another. These are the differences you meet most in the console.

| Need | SQLite | PostgreSQL | MySQL |
| --- | --- | --- | --- |
| Quote an identifier | `"name"` | `"name"` | `` `name` `` |
| Limit rows | `LIMIT n` | `LIMIT n` | `LIMIT n` |
| Page | `LIMIT n OFFSET m` | `LIMIT n OFFSET m` | `LIMIT n OFFSET m` |
| Boolean literal | `1` / `0` | `TRUE` / `FALSE` | `TRUE` / `FALSE` |
| Concatenate | `a \|\| b` | `a \|\| b` | `CONCAT(a, b)` |
| Now | `CURRENT_TIMESTAMP` (text, no offset) | `now()` | `NOW()` (naive) |
| Date part | `substr(ts, 1, 10)` or `date(ts)` | `date_trunc('day', ts)` | `DATE(ts)` |
| Case-insensitive match | `LIKE` (case-insensitive for ASCII) | `ILIKE` | `LIKE` (follows the collation) |
| Extract from JSON | `json_extract(col, '$.k')` | `col->>'k'` | `JSON_UNQUOTE(JSON_EXTRACT(col, '$.k'))` |
| Insert or ignore | `INSERT OR IGNORE INTO ...` | `INSERT ... ON CONFLICT DO NOTHING` | `INSERT IGNORE INTO ...` |
| Update with a join | `UPDATE ... FROM` | `UPDATE ... FROM` | `UPDATE a JOIN b ON ... SET ...` |
| Delete with a limit | Not available. Use a subquery on `id` | Not available. Use a subquery on `id` | `DELETE ... LIMIT n` |
| Parameter marker (API) | `?` | `$1` | `%s` |

The builder uses only the first row and the boolean literal, which is why a builder statement runs on every dialect. Anything you add by hand is written in the dialect of the environment.

## Mistakes people make

| Mistake | What happens | The habit |
| --- | --- | --- |
| Running a write straight from the builder | The action ticks **allow writes** for you and nothing asks again | Read the generated SQL, check for a `WHERE` |
| A condition with an empty value | It is dropped, and a delete loses its `WHERE` | Look for the warning *No condition: this affects every row.* |
| Typing `null` with `=` | `= NULL` matches nothing | Use **IS NULL** |
| Searching text with a `;` in it | The statement is a write, so it needs **allow writes** and returns no rows | Pass the value as a parameter |
| A leading comment | The statement is refused as a write | Put comments last, or omit them |
| Relying on the unticked box for safety | A newline can defeat the word check | Control who has operator access, use a read-only role for viewers |
| Using the wrong table name on the shared PostgreSQL default | `no such table`, or the wrong environment's table | Use the physical `pb_<hash>_` name from a migrate response |
| Expecting rows back from `RETURNING` | Only `affected` is returned | Read the row afterwards |
| Fixing data and expecting webhooks | None fire | Change through the API or a flow |
| Expecting the table browser's order to be stable | There is no `ORDER BY` | Use the SQL window with an order |
| Running `EXPLAIN ANALYZE` on a write | PostgreSQL runs it | Use plain `EXPLAIN` |
| Retrying after a `504` | The first run may still complete | Check the table, then retry |
| Leaving scratch tables behind | Clutter, and possibly sensitive copies | Drop them when done |

## Troubleshooting

| What you see | Cause | Fix |
| --- | --- | --- |
| The Database page shows an error | The environment's database is unreachable. The page's overview is a plain 500 in that case | Check the connection with a read through `/rest/v1`. See [Your database](/data/your-database) |
| *No tables yet.* | The database has no tables, for example right after a switch | Migrate each resource |
| A resource has no badge in the Tables card | Not a resource table, or a prefixed `pb_` table on the shared PostgreSQL default | Match it by name |
| `this statement writes; set allow_write to run it` | The classifier called it a write | Tick **allow writes**, or rewrite it as a read |
| A read returned `affected` and no rows | It was classed as a write, probably because of a `;` or a leading comment | Remove it, or use a parameter |
| `<Type>: no such table` / `relation does not exist` | The table name is wrong or unmigrated, or it is the unprefixed name on the shared default | Check the Tables card |
| `OperationalError: near "X": syntax error` | A typo, or SQL from another dialect | Check against the table of differences |
| `You can only execute one statement at a time` | A `;` between two statements | Run them one at a time |
| `the query timed out` | More than 15 seconds | Add a `LIMIT`, an index, or batch it |
| *Showing the first 5000 rows.* | The result was cut | Add `LIMIT`, or aggregate in SQL |
| A write succeeded and the API still shows old data | A cache. The console clears every resource tag, so check for a cache outside Pawabase, such as a client or CDN | Refresh with a no-cache request |
| A value you wrote makes a list fail | It breaks a validation rule on read, such as an enum | Fix the value. See [Validation](/data/validation) |
| Nothing happened in webhooks after a fix | The console publishes no events | Re-run the change through the API if downstream must know |

## Questions that come up

<AccordionGroup>
  <Accordion title="Is the console read-only by default?">
    Yes, in the sense that **allow writes** starts unticked and a statement the classifier calls a write is refused. The classifier is a safeguard against mistakes, not a security boundary, so access control is what keeps the database safe.
  </Accordion>
  <Accordion title="Can I run several statements at once?">
    No. Each run is one statement. A statement containing `;` is classed as a write, and with **allow writes** the driver refuses two statements (on SQLite, `You can only execute one statement at a time`).
  </Accordion>
  <Accordion title="Can I use a transaction?">
    Not across runs. Each run is its own statement with nothing to roll back. For atomic work use a flow with `db.transaction`, or a direct connection.
  </Accordion>
  <Accordion title="Does a console write trigger webhooks and realtime?">
    No. It is audited and it clears resource caches, and that is all. Use the API or a flow if downstream systems must hear about the change.
  </Accordion>
  <Accordion title="Why did my SELECT return `affected` and no rows?">
    The classifier treated it as a write, usually because of a `;` inside a quoted value or a comment at the start. Use a parameter through the API, or remove the cause.
  </Accordion>
  <Accordion title="Why is there no history of my queries?">
    The window keeps none. Keep the statements you reuse in your own notes or in source control. Writes are in the audit log, cut to 2,000 characters.
  </Accordion>
  <Accordion title="Can I export a table?">
    Page it with the rows route (500 at a time) or run a `SELECT`, up to 5,000 rows per run. For a whole table, use the database's own dump tools.
  </Accordion>
  <Accordion title="Can end users or API keys reach it?">
    No. The routes require an operator.
  </Accordion>
  <Accordion title="Does a console write respect policies and validation?">
    No. It skips both, which is why it can write values the API would refuse. Check the data afterwards with the queries in the recipes.
  </Accordion>
  <Accordion title="Why can I not join my tables in the builder?">
    The builder joins along foreign keys, and Pawabase creates none. Write the join by hand in the text area.
  </Accordion>
  <Accordion title="Will the console show other environments' data?">
    Only the environment you are in. On the shared PostgreSQL default, all environments live in one database, so a hand-written query that names a prefixed table of another environment can reach it. Name tables carefully.
  </Accordion>
</AccordionGroup>

## What to remember

- **The console skips everything the API adds**: validation, policies, transformers, events, realtime.
- **Two surfaces**: the table browser (read only) and the SQL window (with **allow writes**).
- **The builder writes SQL from clicks.** Read it before you run it, and watch for a missing `WHERE`.
- **A statement is a read only if it has no `;`, starts with a read keyword and contains no space-delimited write word.** Everything else is a write.
- **The classifier is not a security boundary.** A newline defeats the word check. Control operator access.
- **Writes are audited and clear every resource's cache.** They publish no events.
- **Limits**: one statement, 5,000 rows, 15 seconds, 100,000 characters.
- **Errors carry the database's own message**, which makes the console the best place to diagnose a failed migration.
- **Preview, count, back up, write, compare.** Every time.

| Term | Meaning |
| --- | --- |
| **Table browser** | The left card and table view of the Database page. Read only |
| **SQL window** | The modal opened by the **SQL** button |
