## Overview

The **Database console** is a single SQL panel inside Studio's Database page: a modal you open with a **SQL** button, a text box, an "allow writes" checkbox, and a **Run** button. It talks to your environment's database directly — the same connection your Resources use — and bypasses Resource definitions, validation, policies, and transformers entirely. It's the tool for the situations the resource API isn't meant for: inspecting raw structure, one-off backfills, and debugging a support issue where you need to see exactly what's in a row without going through any application-level shaping.

<Warning>
The console reads and writes with full database access. It bypasses every resource-level policy, validation rule, and transformer. Only operator sessions can reach it, so limit Studio access accordingly — anyone who can open this panel can read, modify, or delete anything in the environment's database.
</Warning>

## The real Studio UI

Studio's Database page (`Env → Database`) is two panes, not three:

- **A "Tables" list on the left** — every table in the environment's database (not just ones backed by a Resource), each showing a badge naming the Resource it belongs to when it's Resource-managed.
- **A table view on the right** — clicking a table shows its columns (name, type, and a key marker on the primary key) and a paginated row browser (50 rows per page, using **Prev**/**Next**).

There is no third pane. **SQL is not a pane at all — it's a modal**, opened with the **SQL** button in the page header, entirely separate from the table browser. The modal is:

- A single `<textarea>` for one SQL statement.
- An **allow writes** checkbox, unchecked by default.
- **Run** (also triggered with `Cmd/Ctrl + Enter`) and **Close**.
- A results area beneath the box, once you've run something: either a table of rows, or a message stating how many rows were affected for a write.

There is **no schema-browser pane inside the SQL modal**, no query history, and no saved-queries list. The left-hand "Tables" list in the main Database page is a separate feature from the SQL modal — you can browse table structure there without writing SQL, but the two aren't combined into one three-pane console.

## Running a query

Open the modal with the **SQL** button, type a statement, and run it:

```sql
SELECT id, status, total_cents FROM orders ORDER BY created_at DESC LIMIT 50;
```

With **allow writes** left unchecked (the default), only reads are accepted — see "Read-only enforcement" below. Check **allow writes** before running an `INSERT`, `UPDATE`, `DELETE`, or DDL statement:

```sql
UPDATE orders SET status = 'cancelled' WHERE id = 4821;
```

A read that succeeds shows its rows in a table below the box. A write that succeeds shows how many rows were affected — there is no row-level result for a write, only a count.

## Read-only enforcement, precisely

Whether a statement is treated as read-only is decided by a real check, not a suggestion: it must start with `select`, `with`, `explain`, `pragma`, `show`, or `describe` (case-insensitive), and must not contain any of `insert`, `update`, `delete`, `drop`, `alter`, `create`, `truncate`, `grant`, or `attach` as a standalone word. If it fails that check and **allow writes** isn't checked, the request is rejected with a 400 before anything runs.

**Multiple statements in one query are always rejected outright**, whether or not you've checked "allow writes." The check looks for a semicolon anywhere inside the statement (after trimming a single trailing one) and refuses the whole thing if it finds one. This means you cannot run a query and a `BEGIN`/`COMMIT` pair, and you cannot batch two statements separated by `;` in a single Run — each Run is exactly one statement, full stop.

```sql
-- Rejected: this contains a semicolon before the end
SELECT 1; SELECT 2;
```

```sql
-- Rejected without "allow writes" checked, and rejected outright with two statements
-- even if it were checked
BEGIN; UPDATE orders SET status = 'cancelled' WHERE id = 1; COMMIT;
```

<Warning>
There is no multi-statement transaction support in the console. Each Run is one statement, executed on its own — there is no `BEGIN`/`COMMIT` workflow, and nothing to roll back if you change your mind after running it. If a change needs several statements applied together atomically, that's a case for a flow with a database block, a one-off script, or a direct connection using your own database client — not the console.
</Warning>

## Real limits

These are the actual enforced numbers, not rounded approximations:

| Limit | Value | What happens beyond it |
| --- | --- | --- |
| Result rows returned | **5,000** | Rows beyond the first 5,000 are silently truncated; the response flags `truncated: true` and the modal shows "Showing the first 5000 rows." |
| Execution timeout | **15 seconds** (the API's configured `query_timeout`) | The query is cancelled and the console shows a timeout error (`504`). |
| Statements per Run | **1** | A statement containing a semicolon is rejected outright, for both reads and writes. |
| SQL text length | 100,000 characters | Longer input is rejected by the request body's own validation before it reaches the database. |

There is no `COPY`-from-file support and no bulk file import — use `INSERT ... VALUES`, a script against the API, or a flow for bulk data loading.

<Info>
A write that succeeds is audited (recorded as a `database.write` event with the SQL text, truncated to 2000 characters) and invalidates every cached Resource response in the environment — because the console can change data no Resource-level cache invalidation logic knows about, Pawabase clears all Resource caches after any write through the console, rather than trying to guess which ones might be affected.
</Info>

## The row browser (left pane) vs. the SQL modal

The left-hand table list and its row browser give you read access to any table's structure and data — columns, primary key, row count, and paginated rows — without writing SQL at all. This is the quickest way to just look at a table. Reach for the SQL modal when you need to:

- Filter, join, or aggregate in ways the row browser's plain pagination doesn't do.
- Run a targeted `UPDATE`/`DELETE` to fix specific rows.
- Query dialect-specific system catalogs (`sqlite_master`, `information_schema`, `pg_indexes`, and so on) for a deeper structural question than the row browser's column list answers.

## A realistic use: investigating a support issue

A customer reports an order stuck in `pending` after payment. Rather than guessing from the API's shaped response, open the console and look directly:

```sql
SELECT id, status, total_cents, created_at, updated_at
FROM orders
WHERE id = 4821;
```

If the row shows `status = 'pending'` but your payment webhook should have moved it to `paid`, check whether the webhook fired and check any transformer or policy on `orders.update` that might have silently rejected the update — none of that is visible from the row itself, but seeing the raw row (unfiltered by any policy or transformer) is the first fact to establish. If you conclude the fix genuinely is "flip this one row's status," that's a case for a scoped `UPDATE` with **allow writes** checked:

```sql
UPDATE orders SET status = 'paid', updated_at = CURRENT_TIMESTAMP WHERE id = 4821;
```

Confirm the `WHERE` clause is scoped to exactly the row you mean before running it — there is no undo, and no transaction to roll back if the clause matches more than you intended.

## When to use the console vs. the API

| Task | Use |
| --- | --- |
| Read or write one record through your application's rules | Resource API (`GET`/`PATCH /rest/v1/orders/4821`) |
| Filter, sort, or paginate records the normal way | Resource API (`?filter[...]&sort=...`) |
| A validated, policy-checked write | Resource API |
| Look at a table's raw structure or browse its rows without writing SQL | The Database page's table browser (left pane) |
| Run an ad hoc read that the row browser can't express (joins, aggregates, system catalogs) | Database console (SQL modal, read) |
| A one-off fix or backfill outside what the API's operations allow | Database console (SQL modal, write, with `allow writes` checked) |

The console is a debugging and maintenance tool, not a substitute for building the API surface your application should use day to day — anything routine belongs on a properly defined, policy-gated Resource operation instead.
