The **Database console** is Studio's built-in SQL editor. It gives you direct, read-write access to your environment's database, bypassing resource definitions, validation, policies, and transformers.

It's intended for:
- **One-off inspection** — peek at the raw table structure and data
- **Data backfills** — update or migrate data that doesn't fit the standard API
- **Debugging** — understand why a query isn't behaving as expected
- **Schema exploration** — inspect columns, indexes, and constraints

<Warning>
The database console **bypasses all resource-level security**. Anyone with console access can read, modify, or delete any data in the environment's database. Only grant Studio access (operator sessions) to trusted administrators.
</Warning>

## Opening the console

1. Open your project in Studio.
2. Go to **Data → Database console**.
3. Select the database: by default, this is your environment's primary database.

The console has three panes:
- **Editor** (left) — write and run SQL queries
- **Results** (right, top) — formatted results table
- **History** (right, bottom) — past queries and their execution time

## Running queries

Type SQL into the editor and press `Cmd/Ctrl + Enter` or click **Run**:

```sql
SELECT id, title, completed FROM todos ORDER BY created_at DESC;
```

Results appear in the table below. Click any result row to see its full contents as JSON.

### Safe queries (read-only)

You can run any `SELECT` query:

```sql
-- See the first 100 rows
SELECT * FROM todos LIMIT 100;

-- Count by status
SELECT completed, COUNT(*) FROM todos GROUP BY completed;

-- Find tables that reference todos
SELECT * FROM pg_stat_user_tables WHERE relname LIKE '%todo%';
```

### Write queries

You can also run `INSERT`, `UPDATE`, and `DELETE` — but these **bypass all resource policies and validation**. Use with caution:

```sql
-- Fix a data issue
UPDATE todos SET title = 'Corrected title' WHERE id = 42;

-- Bulk backfill
INSERT INTO todos (title, completed) SELECT 'Imported: ' || name, false FROM legacy_tasks;
```

<Warning>
The database console does not enforce foreign key constraints, check constraints, or row-level security. A malformed `UPDATE` or `DELETE` can corrupt data that the API serves. Always wrap destructive queries in a transaction and verify before committing.
</Warning>

## Schema inspection

Use the schema browser above the editor to explore your database:

- **Tables** — all tables in the `public` schema (including system tables)
- **Columns** — name, type, nullable, default value
- **Indexes** — name, columns, type
- **Foreign keys** — referenced table and column

You can also query PostgreSQL's system catalogs directly:

```sql
-- See all indexes on a table
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'todos';

-- See table size
SELECT pg_size_pretty(pg_total_relation_size('todos')) AS size;
```

## Transaction support

The console runs each query as its own implicit transaction. For multi-step write operations, explicitly wrap them:

```sql
BEGIN;

UPDATE invoices SET balance = 0 WHERE id = 123;

DELETE FROM invoice_items WHERE invoice_id = 123 AND adjusted = false;

-- Review the results, then:
COMMIT;
-- Or: ROLLBACK;
```

<Error>
If you run a query that errors, the transaction is automatically rolled back. Uncommitted changes from a multi-statement transaction are lost when you navigate away or close the tab.
</Error>

## Limitations

- **Maximum result set:** 10,000 rows. Queries returning more are truncated with a warning.
- **Maximum execution time:** 30 seconds. Long-running queries are killed.
- **No file upload:** You can't `COPY` from a file. Use `INSERT ... VALUES` or a function for bulk imports.
- **No DDL persistence:** Schema changes (`ALTER TABLE`, `CREATE INDEX`) persist in the database, but the console doesn't track them as platform definitions.

## When to use the console vs. the API

| Task | Use |
| --- | --- |
| Read or modify a single record | Resource API (`GET /rest/v1/todos/42`) |
| Filter, sort, or paginate records | Resource API (`GET /rest/v1/todos?filter[...]`) |
| Run a validated, policy-checked write | Resource API (`POST /rest/v1/todos`) |
| Inspect raw table structure | Database console |
| Bulk backfill or data migration | Database console or a flow with a `db.execute` block |
| Debug a policy refusal | Database console (to see raw data the policy is checking) |

The database console is a debugging and maintenance tool. For normal application data access, always use the resource API, which enforces your validation rules, policies, and transformations.
