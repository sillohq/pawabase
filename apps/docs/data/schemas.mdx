## The mental model: one field list, named once, used in many places

A field list describes the shape of some JSON: which keys, which types, which limits. A resource has one, so does a custom route's request body, and so does any object nested inside either. When the same shape shows up in several places (an address on a customer, an order and a supplier; an amount of money on every price) writing it out each time means every copy has to be changed by hand when the shape changes, and they drift.

A **schema** is the fix: a field list with a name, stored on its own, that other definitions point at. In Studio it lives under **Schemas** in the **Build** group. A field of type **Schema reference** names it, and a custom route can name it as its request or response schema. Change the schema once and every place that points at it changes with it.

The word is used for two related things in Pawabase, and it helps to separate them before going further.

| Meaning | What it is | Where you meet it |
| --- | --- | --- |
| A **reusable schema** | A stored, named field list, one row under **Schemas** | The **Schemas** page, a `ref` field's **Schema** menu, a route's `input_schema` and `response_schema` |
| A **compiled model** | The Pydantic model that Pawabase builds from any field list so the framework can validate and document with it | Never edited by hand. It is what gets enforced at request time and published in the API document |

This page is about the first, and about how it becomes the second. Everything described here was observed on a running API, including several behaviors that surprise, and each is called out where it applies. The most important is that a reference is **not** the same as writing the fields inline: a nested object defined inline enforces `required` and defaults, and a referenced schema does not. The section on references has the full comparison.

<Note>
Types and constraints themselves are covered on [Field types](/data/field-types), and the failures a schema can produce on a request are on [Validation](/data/validation). This page covers the schema as an object: how it is created, how it is compiled and what depends on it.
</Note>

## The Schemas page in Studio

Open **Build**, **Schemas**. The page header reads **Schemas**, and its description says what the section is for: "Reusable field sets. Resources, routes and flows reference them; they compile to Pydantic models and OpenAPI." The button at the top right is **New schema**.

| Part of the page | What it shows |
| --- | --- |
| The list | One row per schema with the columns **name** and **description**. Clicking a row opens it |
| The empty state | "No schemas yet", the same description, and a **Create the first one** button |
| The sheet | A panel with the tabs **Configure** and **JSON**. A new schema opens with the title "New schema" and an alert, "New here? Start from a worked example and adjust it.", with a **Use example** button |
| The footer | **Delete** (with a confirmation, "Delete Address? This cannot be undone."), **Cancel** and the primary button, **Create schema** for a new one or **Save changes** for an existing one |

The example that **Use example** loads is a postal address, and it is a good picture of what a schema is for:

```json
{
  "name": "Address",
  "description": "",
  "fields": [
    {"name": "street", "type": "string", "required": true},
    {"name": "city", "type": "string", "required": true},
    {"name": "postcode", "type": "string"}
  ]
}
```

### The Configure tab

The form has two sections. **Details** holds the **Name**, with the hint "Starts with a letter; letters, digits and underscores." for a new schema and "Fixed once created; other definitions refer to it by name." once it exists, and an optional **Description**, "What is this for?". **Fields** holds the same field editor used for resources, with the section description "Compiled to a Pydantic model and published in OpenAPI." and the empty message "No fields yet." Everything about that editor, the type menu, **Required**, **More options**, is on [Field types](/data/field-types).

Two differences from a resource's field editor are worth knowing. The editor for a schema does not show the primary key or the timestamp note, because a schema has no table. And the **Schema** menu on a `ref` field inside a schema lists every other schema but not the one you are editing, which is the editor's way of preventing the simplest cycle. The server does not enforce this, and the page on cycles later in this document explains what happens when the editor is bypassed.

### The JSON tab

The **JSON** tab shows exactly what is stored, under the heading "Definition JSON". Changes made there show up in the form when you switch back. If the text is not valid JSON the form is replaced by "The JSON has an error. Fix it on the JSON tab." and **Save changes** stays disabled, with the hint "Fix the JSON first." Use the tab for keys the form does not offer, such as `unique` or a default for a list.

### Saving, and what saving does not check

Saving sends the definition to the Platform API, which validates it and stores it. The checks that run on save are narrow:

| Check | Result when it fails |
| --- | --- |
| The name matches `^[A-Za-z][A-Za-z0-9_]{0,62}$` | `422` with a pattern error naming `name` |
| The name is not already used in this environment | `409` `schema already exists` |
| Every field has a valid name, a known type, no duplicate and a valid `pattern` | `422` with a message such as `fields[1]: duplicate field 'a'` |
| A `ref` field names a schema | `422` `fields[0]: a ref field names a schema` |

What is **not** checked is whether the schema a `ref` names exists. A reference to a schema that has not been created yet saves fine, and the environment reports it as a problem until the missing schema appears. That is deliberate: it lets you create schemas in any order. Two schemas that reference each other in a loop, on the other hand, also save fine, and that one is not harmless.

## What a schema is, as data

A schema is one row, with a name, a description and a list of fields, belonging to one environment. The name is unique within the environment.

| Part | Detail |
| --- | --- |
| `name` | Letters, digits and underscores, starting with a letter, up to 63 characters. Case matters, and by convention schemas are `PascalCase` (`Address`, `Money`) where resources are lowercase (`orders`) |
| `description` | Free text, shown in the list |
| `fields` | A list of field definitions, exactly as in a resource, with no table-related effect |

Because the stored form is a plain list, a schema moves with the rest of an environment's definitions. It is part of a **release**'s snapshot, it is carried forward when you **promote** an environment, and it is exported in a **blueprint**. See [Environments and promotion](/operate/environments-and-promotion) and [Releases and API versions](/operate/releases-and-api-versions).

### The Platform API

Studio calls these endpoints, and scripts can too. They are the same five that every definition kind has, under `/platform/v1/projects/{ref}/envs/{env}/schemas`, with operator rights:

| Operation | Request | Notes |
| --- | --- | --- |
| List | `GET …/schemas` | `{"data": [ … ]}`, ordered by name |
| Create | `POST …/schemas` with `{"name", "description", "fields"}` | `201`, or `409` when the name exists |
| Read | `GET …/schemas/{name}` | `404` `no schema 'x'` if absent |
| Replace | `PUT …/schemas/{name}` | Replaces the whole definition |
| Delete | `DELETE …/schemas/{name}` | `204` with no body |

Two behaviors of those endpoints matter. **Delete does not check for users of the schema.** A schema that a resource's `ref` field names can be deleted, and the resource then fails to compile (details below). And **`PUT` can rename**: Studio fixes the name once created, but the API takes the `name` from the body, so a `PUT` to `…/schemas/Quote` with the name `Quote2` renamed the schema in place in testing. Nothing updates the fields and routes that named `Quote`, and they now point at nothing.

## How a schema becomes a model

Pawabase does not compile on save. The compiled application for an environment is rebuilt lazily, on the first request after any definition changes, from everything defined at that moment. Compiling the schemas is the first part of that build.

| Phase | What happens |
| --- | --- |
| Load | Every schema in the environment is read as a name and a raw field list |
| Resolve | Each schema is compiled into a model, and each `ref` field is resolved against the others by name, so the order they were created in does not matter |
| Report | A schema that cannot be compiled is left out and a message is recorded, so one broken schema does not take the others down |
| Use | Resources and routes that reference a schema receive its compiled model |

Order independence was checked directly. A schema `Outer` that referenced `Inner` before `Inner` existed reported `schema Outer: field 'inner' refers to unknown schema 'Inner'`, and after `Inner` (which referenced a third schema, `Leaf`) and `Leaf` were created, the problem list was empty and a three-level structure validated correctly with errors located at `["outer", "inner", "leaf", "v"]`.

### Where the problems appear

A schema that fails to compile does not stop the environment. It is skipped and listed on the **Overview** page under **Definitions with problems**. The messages observed:

| Cause | Message |
| --- | --- |
| A `ref` to a schema that does not exist | `schema Dangling: field 'x' refers to unknown schema 'Nope'` |
| A resource whose field references a missing schema | `resource uses_dangling: field 'l' refers to unknown schema 'Dangling'` |
| A resource whose field references a schema that was deleted | `resource people: field 'home' refers to unknown schema 'Address'` |

A resource listed in a problem is not served: all of its routes return `404`, while every other resource keeps working. A schema listed in a problem is dropped from the registry, and everything that referenced it is then a problem in turn, which is why a single missing schema can produce several lines. Open **Overview** after changing or deleting a schema.

## What a reference enforces, and what it does not

This is the section to read if you take one thing from the page. A `ref` field behaves like an `object` in most respects: it validates nested keys, rejects unknown ones and reports errors with the full path. But a referenced schema is compiled once, in a generic mode that is shared by every resource and route that uses it, and that mode ignores several keys that an inline `object` honors.

The comparison was run with a schema `Address` (`street` and `city` required, `zip` with a pattern and a default of `"00000"`) and a resource with a required `ref` to it, an optional `ref` to it, and an inline `object` with a required nested field.

| Rule | Inline `object` | Referenced schema | Evidence |
| --- | --- | --- | --- |
| Nested `required` | Enforced | **Not enforced** | `{"home": {}}` created a record with `street` and `city` stored as `null`. `{"inline": {}}` failed with `missing` at `["inline", "a"]` |
| Nested `default` | Applied | **Not applied** | `zip` has the default `"00000"` in the schema and was `null` in the stored record |
| Nested constraints (`pattern`, `minimum`, `maximum`, `enum`, lengths) | Enforced | Enforced | A bad `zip` failed with `string_pattern_mismatch` at `["home", "zip"]` |
| Unknown nested keys | Rejected | Rejected | `extra_forbidden` at the nested path |
| Nested `read_only` | Left out of create and update | **Not applied**, the key is writable | A nested `stamp` marked `read_only` accepted `"client-set"` and stored it |
| Nested `write_only` | Left out of reads | **Not applied**, the key is returned | A nested `secret` marked `write_only` came back as `"s3"` |
| `required` on the `ref` field itself | Enforced | Enforced | `{}` failed with `missing` at `["home"]` |
| `null` for a required `ref` field | Rejected | Rejected | `{"home": null}` failed with `model_type` |

What the table says is that **a schema's own `required`, `default`, `read_only` and `write_only` have no effect when the schema is used through a `ref`**, while its constraints and its set of allowed keys do. The reference itself can be required (the field that points at the schema), but that only means the nested object must be present, not that anything inside it must be.

The consequence for design is direct. If a nested value must carry certain keys, either define it inline as an `object` so `required` is enforced, or enforce the requirement some other way, with a policy on `$input` or a check in a route. Do not rely on `required` inside a reusable schema to protect data.

```text
POST /rest/v1/people  {"home": {}}
  201  {"id": 1, "home": {"street": null, "city": null, "zip": null}, ...}

POST /rest/v1/people  {"home": {"street": "1 Main"}}
  201  {"id": 2, "home": {"street": "1 Main", "city": null, "zip": null}, ...}

POST /rest/v1/people  {"home": {"zip": "1"}}
  422  [{"type": "string_pattern_mismatch", "loc": ["home", "zip"], ...}]

POST /rest/v1/people  {}
  422  [{"type": "missing", "loc": ["home"], ...}]
```

Note how the output shows every key of the schema, with `null` for the ones that were not sent: a nested model is always filled to its full shape.

### Why the two differ

The reason is in how the models are built. A resource's own fields are compiled separately for each operation: one model for creating, one for updating and one for reading, and `required` and `default` are interpreted according to which. A reusable schema is compiled once, ahead of time, in a mode that validates types and constraints and treats everything as optional, because at that point it is not known whether it will end up in a create body, an update body or a response. That single model is then shared. An inline `object` is compiled at the point of use, inside the operation that contains it, and so it follows that operation's rules.

The generic mode has a visible effect in the API document too. The `Address` schema appears once, as a component, with every property nullable and `additionalProperties` set to `false`:

```json
{
  "title": "Address",
  "type": "object",
  "properties": {
    "street": {"title": "Street", "anyOf": [{"type": "string"}, {"type": "null"}]},
    "city":   {"title": "City",   "anyOf": [{"type": "string"}, {"type": "null"}]},
    "zip":    {"title": "Zip",    "anyOf": [{"pattern": "^[0-9]{5}$", "type": "string"}, {"type": "null"}]}
  },
  "additionalProperties": false
}
```

There is no `required` list, so an API reference built from this document tells clients that `street` and `city` are optional, and the server agrees. A schema that you described as "street and city required" is documented and behaves as "street and city optional".

## How a nested value behaves on update

A `PATCH` builds its request model in update mode, where every field is optional. For a nested object, that raises a question: if the body names only some of the nested keys, are the others kept, or replaced?

They are replaced. The nested value in the body becomes the whole stored value, filled out with `null` for the keys it did not mention. A record whose `home` was a complete address, patched with only a new city:

```text
PATCH /rest/v1/people/1  {"home": {"city": "Abuja"}}
  200  {"home": {"street": null, "city": "Abuja", "zip": null}, ...}

GET /rest/v1/people/1
  200  {"home": {"street": null, "city": "Abuja", "zip": null}, ...}
```

The `street` that was there a moment ago is gone. This is the same for a `ref` and for an inline `object`, and it is also true that `required` is relaxed for the nested keys on update: `PATCH {"inline": {}}` on an object whose nested field `a` is required returned `200` and stored `{"a": null}`.

Two rules follow. A client that edits one nested key must send the whole nested object, read from the record first. And there is no per-key merge on the REST API, so two clients editing different keys of the same object at the same time will overwrite each other, with the last write winning. If you need partial updates to a structured value, give each part its own field, or move the structure into a related resource, see [Relations](/data/relations).

## Using a schema in a custom route

A custom route can name a schema for its request body and another for its response, and these behave differently from each other and from inline `input_fields`. All three were exercised through a route whose flow echoes its input.

| Route setting | What it does | What it does not do |
| --- | --- | --- |
| `input_fields` (the route's own list) | Validates the body in create mode: `required` is enforced, defaults are applied, unknown keys are rejected | Nothing is shared with other routes |
| `input_schema` (a named schema) | Validates types, constraints and unknown keys | Does **not** enforce `required` or apply defaults: `{}` for a schema with a required integer was accepted, and the handler received `null` |
| `response_schema` (a named schema) | Documents the response in the API reference | Does **not** filter or check the response: a flow that returned an extra `debug` key sent it to the client |

The first two rows are the same difference as inline versus referenced, and for the same reason. The third is a statement about intent: a response schema is documentation. The route and the flow decide what is sent. To remove a key from a response, shape the data in the flow, or use a [transformer](/data/transformers) on the route, which is applied to the result.

```text
route POST /quote   input_schema Quote (items: integer, required, minimum 1), response_schema QuoteResult
POST /rest/v1/quote  {"items": 3}   ->  200  {"total": 3, "currency": "USD", "debug": "leak"}
POST /rest/v1/quote  {}             ->  200  {"total": null, "currency": "USD", "debug": "leak"}
```

The second request should have been refused, and the response contains a key the response schema does not declare. If a route's request must enforce `required`, give it `input_fields`, which it does enforce. A `ref` field inside `input_fields` pulls in the schema's constraints, and the schema's inner `required` is still inert:

```text
route POST /pay   input_fields: price (ref Money, required), note (string)
POST /rest/v1/pay  {"price": {"amount_minor": 100, "currency": "USD"}}    ->  200
POST /rest/v1/pay  {"price": {"currency": "USD"}}                          ->  200  amount_minor arrives as null
POST /rest/v1/pay  {"price": {"amount_minor": -1, "currency": "XXX"}}      ->  422  greater_than_equal at ["price","amount_minor"], literal_error at ["price","currency"]
```

See [Custom routes](/data/custom-routes) for the routes themselves.

## Nesting and composition

A schema's fields can themselves be references, and a field can be a list of references, so structures can be built from parts. The nesting has no fixed limit that was reached in testing, and errors carry the whole path.

```json
{"name": "Outer", "fields": [{"name": "inner", "type": "ref", "schema": "Inner"}]}
{"name": "Inner", "fields": [{"name": "leaf",  "type": "ref", "schema": "Leaf"}]}
{"name": "Leaf",  "fields": [
  {"name": "v", "type": "integer", "maximum": 9},
  {"name": "tags", "type": "array", "items": {"type": "string"}}
]}
```

| Request body (`outer` field of a resource) | Result |
| --- | --- |
| `{"inner": {"leaf": {"v": 5}}}` | `201` |
| `{"inner": {"leaf": {"v": 50}}}` | `422` `less_than_equal` at `["outer", "inner", "leaf", "v"]` |
| `{}` | `201`, stored as `{"inner": null}`, because nothing inside is required |
| `{"inner": {"leaf": {"v": 5, "other": 1}}}` | `422` `extra_forbidden` at `["outer", "inner", "leaf", "other"]` |

A list of references is `{"type": "array", "items": {"type": "ref", "schema": "Line"}}`, and its errors include the index, for example `["lines", 1, "qty"]`. A list of references is the usual way to model line items, addresses, contacts and other small repeated groups that do not need to be queried on their own.

### Composition patterns

Schemas earn their keep when the same group appears in more than one place. These are patterns that fit.

| Schema | Fields | Used by |
| --- | --- | --- |
| `Money` | `amount_minor` (integer, minimum 0), `currency` (string, enum) | Prices on products, totals on orders, balances on accounts |
| `Address` | `street`, `city`, `region`, `postcode`, `country` | Customers, suppliers, shipping on orders |
| `GeoPoint` | `lat` (number, minimum -90, maximum 90), `lng` (number, minimum -180, maximum 180) | Stores, deliveries, events |
| `ContactMethod` | `kind` (string, enum), `value` (string) | A list of contact methods on a person |
| `AuditStamp` | `by` (string), `at` (datetime) | Any resource that records who changed what |

Put the constraints in the schema, because those are enforced through a reference. Do not rely on `required` in these, for the reason in the previous section. For `Money`, that means `amount_minor` can be omitted and arrives as `null`, so a price that must exist should be declared as a required field of the **resource** (the `ref` field itself being required), and code that reads it should still handle a `null` amount.

## Cycles: the one mistake that takes the environment down

A schema that refers to itself, directly or through other schemas, cannot be compiled, because compiling it needs the compiled form of itself. Pawabase does not detect this. The attempt overflows the stack, and the failure is not contained to the schema.

A schema named `Loop` was saved with one field, `{"name": "me", "type": "ref", "schema": "Loop"}`. Saving it succeeded. Then:

```text
GET /overview                      ->  500
GET /rest/v1/<any resource>        ->  500    (including resources that never mention Loop)
```

Every data-plane request for that environment returned `500` and the **Overview** page itself failed, because the compile that all of them wait on never finished. Two schemas that refer to each other (`A` has a `ref` to `B`, and `B` to `A`) did exactly the same.

| Cycle | Effect |
| --- | --- |
| A schema that refers to itself | Every request to the environment returns `500` |
| Two or more schemas that refer to one another | The same |
| A schema that refers to a missing schema | Only that schema and its users are affected, listed under **Definitions with problems** |

### Recovering

Deleting any schema in the cycle ends it. The schema list is served from stored definitions and does not need the compile to succeed, so **Schemas** still opens, and **Delete** works. After the delete, the surviving schema is reported as an ordinary dangling reference: in the two-schema case the remaining one showed `schema B: field 'a' refers to unknown schema 'A'` on the **Overview** page, and the environment answered normally again. Then fix or delete the remaining schema.

Because the cost of a cycle is a whole environment, make schema changes that touch references in a development environment first and promote them, rather than editing a production environment directly. See [Environments and promotion](/operate/environments-and-promotion).

### Avoiding cycles, and modelling recursive data

The Studio editor keeps a schema's own name out of its **Schema** menu, which prevents the direct case when you use the form. It does not prevent a loop through two schemas, and it does not apply to the **JSON** tab or the API. Review any change that makes a schema point at another that already points back.

Recursive data (a comment with replies, a category with sub-categories, a menu with submenus) cannot be described by a schema that contains itself. Model it with one of these:

| Shape | How |
| --- | --- |
| A tree stored as rows | One resource with a `parent_id` field and a relation named for it, read level by level or with `?expand=`. See [Relations](/data/relations) |
| A tree stored as one value | A `json` field, accepting that nothing inside is validated |
| A bounded depth | Separate schemas for each level (`Reply1`, `Reply2`), which is repetitive and honest about the limit |

## Deleting and renaming a schema that is in use

Neither is blocked, and neither updates what depends on the schema. Both are therefore a way to break a resource without any warning at the time.

**Deleting.** A schema named by a resource's `ref` field was deleted from **Schemas**. The delete returned `204`. The resource was then listed on **Overview**:

```text
resource people: field 'home' refers to unknown schema 'Address'
GET /rest/v1/people    ->  404   (the resource's routes are gone)
POST /rest/v1/quote    ->  200   (a route using unrelated schemas is unaffected)
```

The data is intact in the table. Recreating a schema named `Address` with the same fields restores the resource on the next request, since the reference is by name.

**Renaming.** The Studio form does not allow it. The API does, through a `PUT` whose body has a different `name`. The old name then no longer exists, and every `ref` field and route that used it reports a missing schema. If you must rename, create the new schema, point every user at it, and only then delete the old one.

### Finding what uses a schema

Studio has no "used by" view for schemas. The usage is in the definitions that name it: the `schema` key of `ref` fields (also inside `items`, and inside nested `fields`) in resources, other schemas and route `input_fields`, and the `input_schema` and `response_schema` of routes. A short script can list them from three calls to the Platform API:

```python
def refs(fields):
    """Every schema name mentioned by a field list, however deeply nested."""
    for f in fields or []:
        if f.get("type") == "ref":
            yield f["schema"]
        if f.get("type") == "array":
            yield from refs([f.get("items") or {}])
        if f.get("type") == "object":
            yield from refs(f.get("fields"))


def users_of(name, fetch):
    """`fetch(kind)` returns the list of definitions of that kind from the Platform API."""
    found = []
    for kind in ("resources", "schemas"):
        for item in fetch(kind):
            if name in set(refs(item.get("fields"))):
                found.append(f"{kind}/{item['name']}")
    for route in fetch("routes"):
        named = {route.get("input_schema"), route.get("response_schema")}
        if name in named or name in set(refs(route.get("input_fields"))):
            found.append(f"route {route['method']} {route['path']}")
    return found
```

`fetch` is whatever you use to call `GET …/resources`, `GET …/schemas` and `GET …/routes` and read the `data` list from the answer, with operator credentials. Run it before a delete or a rename. An empty result is the only state in which either is safe.

## Changing a schema that is in use

A change to a schema reaches every resource and route that references it on the next request, because the compiled application is rebuilt from all definitions. That is the point of a schema, and it is also why changes carry the same risks as changing a resource's own fields, multiplied by the number of users.

| Change to the schema | Effect on writes | Effect on stored rows |
| --- | --- | --- |
| Add an optional field | New bodies may include it | Old values read it as `null` |
| Add a field marked `required` | No effect, `required` is inert in a reference | None |
| Remove a field | Bodies that include it fail with `extra_forbidden` | Rows whose stored JSON still holds the key make reads return `500` |
| Tighten a constraint (a maximum, a pattern, an enum) | Bodies that break it fail | Stored values that break it make reads return `500` |
| Relax a constraint | More bodies pass | None |
| Change a field's type | Bodies of the old type may fail | Stored values that no longer convert make reads return `500` |

Removal is the sharpest of these, and it was reproduced first. A row was stored with `home` as `{"street": "1 Main", "city": "Lagos"}`, and then `street` was removed from the `Address` schema:

```text
GET /rest/v1/people/1   ->  500  {"error":"Internal Server Error","detail":"Response validation failed"}
GET /rest/v1/people     ->  500
```

A referenced schema rejects keys it does not declare when reading too, so the stored `street` is now an unexpected key and the row fails the response. Adding `street` back, along with a new optional `zip`, made the same row readable again, with `zip` as `null`. An inline `object` is more forgiving on reads: removing a nested key from an inline definition did not break the rows that still held it, because the read model for a resource allows extra properties at that level. The difference is another reason to prefer inline objects for shapes that change. The tightening case was reproduced too. A three-level structure held a row with `v: 5`. After the schema's `v` was limited to a maximum of 3:

```text
POST /rest/v1/deep  {"outer": {"inner": {"leaf": {"v": 5}}}}  ->  422  less_than_equal at ["outer","inner","leaf","v"]
GET  /rest/v1/deep/1                                          ->  500  {"error":"Internal Server Error","detail":"Response validation failed"}
GET  /rest/v1/deep                                            ->  500
```

The row did not change and could not be read. A structured value inside a JSON column cannot be corrected with a column-level `UPDATE`; you have to rewrite the JSON, with the JSON functions your database provides, or read it, fix it and write it back through a flow or a function. That makes schema changes costlier than changes to flat fields, and it is a good reason to keep schemas small and stable, and to add constraints to them early.

A release's compatibility check does not look at schemas at all. It compares resources, fields and routes, so a release that tightens a schema is reported as compatible. See [Validation](/data/validation) for what the check does catch.

### Removing a key without breaking reads

The sharpest edge of changing a schema is removal, and the reason it is sharper than it looks is how nested values are stored. When a body omits a key of a referenced schema, the API does not store the object as sent. It stores the object filled out to the schema's full shape, with `null` for every key that was not sent. A row created with `{"city": "Abuja"}` is stored as:

```json
{"street": null, "city": "Abuja"}
```

So every row that has the structure holds every declared key, whether or not anyone sent a value for it. Removing `street` from the schema therefore fails every such row, including the ones whose `street` was always `null`. This was run with three rows in a `people` resource: one with both keys, one with only `city`, and one with no `home`.

```text
remove `street` from the Address schema
GET /rest/v1/people   ->  500  {"error":"Internal Server Error","detail":"Response validation failed"}
```

The finder query has to look for the key and not for a value in it. On SQLite, `json_extract(home, '$.street') IS NOT NULL` finds only the first row, because it returns `NULL` for a key that is present with a `null` value, and the repair then leaves the second row broken. `json_type` distinguishes a missing key from a key holding `null`:

```sql
SELECT id, home FROM people WHERE json_type(home, '$.street') IS NOT NULL;
```

```text
id  home
1   {"street": "1 Main", "city": "Lagos"}
2   {"street": null, "city": "Abuja"}
```

Both rows are found, and removing the key from both fixes the list:

```sql
UPDATE people SET home = json_remove(home, '$.street') WHERE json_type(home, '$.street') IS NOT NULL;
```

```text
affected: 2
GET /rest/v1/people   ->  200   (home is now {"city": "Lagos"} and {"city": "Abuja"})
```

The statements differ by database, so this table gives the equivalents. The SQLite forms were run, and the others are the standard syntax for each database.

| Task | SQLite | PostgreSQL (`JSONB`) | MySQL (`JSON`) |
| --- | --- | --- | --- |
| Find rows that hold a key, even as `null` | `json_type(col, '$.key') IS NOT NULL` | `col ? 'key'` | `JSON_CONTAINS_PATH(col, 'one', '$.key')` |
| Remove a key | `json_remove(col, '$.key')` | `col - 'key'` | `JSON_REMOVE(col, '$.key')` |
| Rename a key | `json_set(json_remove(col, '$.old'), '$.new', json_extract(col, '$.old'))` | `jsonb_set(col - 'old', '{new}', col -> 'old')` | `JSON_SET(JSON_REMOVE(col, '$.old'), '$.new', JSON_EXTRACT(col, '$.old'))` |
| Read a nested value | `json_extract(col, '$.key')` | `col ->> 'key'` | `JSON_UNQUOTE(JSON_EXTRACT(col, '$.key'))` |

A rename is a remove plus an add, and it is the same job. Renaming `city` to `town` inside stored JSON on SQLite, then changing the schema to declare `town`, keeps every row readable:

```sql
UPDATE people
SET home = json_set(json_remove(home, '$.city'), '$.town', json_extract(home, '$.city'))
WHERE json_extract(home, '$.city') IS NOT NULL;
```

Run the repair from the **Database** console with **allow writes** ticked, see [Database console](/data/database-console). The order matters. Rewriting the data first and changing the schema second leaves a window in which the old key is still declared and the new one is not. Changing the schema first and rewriting second leaves a window of `500` responses on every read. If neither window is acceptable, make the change as an addition: add the new key to the schema, copy the values across, deploy clients that use the new key, and remove the old one last, with the rewrite above, when nothing reads it.

### Reading and indexing nested values

A value inside a JSON column is not a column, and the data API does not reach into it. These are the consequences, and the ways around each.

| Need | What works |
| --- | --- |
| Filter a list by a nested value | Not through `filter[...]`. Promote the value to a top-level field, or to a related resource |
| Report on nested values | A query in the **Database** console using the functions in the table above |
| Index a nested value | An expression index in the database, created by hand. Pawabase will not use it to answer a filter, but your own queries and reports can |
| Sort by a nested value | Not through `sort`. Promote the value |
| Keep a value both nested and queryable | Write it to a top-level field as well, from a route or a flow, and treat the nested one as a copy |

The last row is a pattern worth knowing. A `Money` reference holds an amount and a currency as a unit, which is how clients read it. If you also need to filter products by price, add a plain `price_minor` integer next to it, and have the route that writes one write the other. Keeping the two in step is your code's job.

## What is actually stored

The previous section turns on a detail worth seeing directly. The **Database** console shows the raw column, and for a `ref` field it is JSON text. These are the stored values for three bodies sent to a resource with `name` and a `home` that references an `Address` schema with `street` and `city`:

| Body sent | Stored in the `home` column |
| --- | --- |
| `{"name": "A", "home": {"street": "1 Main", "city": "Lagos"}}` | `{"street": "1 Main", "city": "Lagos"}` |
| `{"name": "B", "home": {"city": "Abuja"}}` | `{"street": null, "city": "Abuja"}` |
| `{"name": "C", "home": null}` | SQL `NULL`, not the JSON text `null` |

Three consequences. The second row shows that omitted keys are stored as explicit `null`, so the stored shape is always the full shape. The third shows that an absent or null reference is a database `NULL`, which is why `?filter[home]=is.null` finds those rows and a query on a key inside `home` would not. And the text is written with a space after each comma and colon on SQLite, which is how the value was serialized on the way in. A database function that rewrites JSON (`json_remove` on SQLite) may return it in compact form, so a repaired row can look different when read back, with no difference in meaning.

The same body would be stored on PostgreSQL as `JSONB` and on MySQL as `JSON`, both of which parse and normalize the value on write, so the stored text there is not the text that was sent.

## What schemas cannot express

A schema is a plain list of fields. Several things people expect from a schema system are not there, and each has a workaround.

| Not available | Workaround |
| --- | --- |
| Inheritance or extending another schema | Repeat the fields, or compose with a `ref` to the shared part |
| A choice between shapes (a union, `oneOf`) | A discriminator field with an `enum`, and an input policy that checks the rest. Or separate resources per shape |
| A field that is required only when another has a value | An input policy on `$input`, see [Validation](/data/validation) |
| A check across keys (a range in order, a total that matches) | An input policy, as in the date range above |
| Recursion | A resource with a `parent_id`, see [Relations](/data/relations) |
| `required` and defaults inside a reference | An inline `object`, or `input_fields` on a route |
| Unique items in a list, or a length limit on a list | A route or a policy |
| A foreign key from inside a schema to a resource's row | A top-level field with a relation, see [Relations](/data/relations) |
| A parameterised schema (a list of `T`) | A schema per concrete type |
| Documentation of why a key exists beyond its `description` | The schema's own **Description**, and your own docs |

## Managing schemas through the Platform API

Everything the **Schemas** page does can be done from a script, which is how you keep schemas in a repository and apply them from CI. The requests go to Studio's bridge, with the session cookie and the XSRF token that the `curl` examples elsewhere in these docs use:

```bash
# Create a schema
curl -X POST "$STUDIO/studio/api/platform/projects/acme/envs/development/schemas" \
  -H "content-type: application/json" -H "X-XSRF-TOKEN: $XSRF" -b cookies.txt \
  -d '{
    "name": "Address",
    "description": "A postal address",
    "fields": [
      {"name": "street", "type": "string", "max_length": 120},
      {"name": "city", "type": "string", "max_length": 80},
      {"name": "country", "type": "string", "min_length": 2, "max_length": 2, "pattern": "^[A-Z]{2}$"}
    ]
  }'

# Read it back
curl "$STUDIO/studio/api/platform/projects/acme/envs/development/schemas/Address" -b cookies.txt

# Replace it (the whole definition)
curl -X PUT "$STUDIO/studio/api/platform/projects/acme/envs/development/schemas/Address" \
  -H "content-type: application/json" -H "X-XSRF-TOKEN: $XSRF" -b cookies.txt \
  -d '{"name": "Address", "fields": [ ... ]}'

# Delete it (no check for users of the schema)
curl -X DELETE "$STUDIO/studio/api/platform/projects/acme/envs/development/schemas/Address" \
  -H "X-XSRF-TOKEN: $XSRF" -b cookies.txt
```

A create answers `201` with the stored definition, and the same name again answers `409` with `schema already exists`. A body that fails the name pattern or a field check answers `422`. These are the same checks the sheet's **Save changes** triggers, and the messages Studio shows in its error toast are the messages these calls return.

### A check to run in CI

If schemas live in a repository, a short script that loads them and runs the two checks from the testing section fails the build before a cycle or a dangling reference reaches an environment:

```python
import json, sys, pathlib

schemas = {}
for path in pathlib.Path("definitions/schemas").glob("*.json"):
    definition = json.loads(path.read_text())
    schemas[definition["name"]] = definition["fields"]

resources = [json.loads(p.read_text()) for p in pathlib.Path("definitions/resources").glob("*.json")]

problems = []
if (cycle := find_cycle(schemas)):
    problems.append("schema cycle: " + " -> ".join(cycle))
problems += [f"dangling reference: {item}" for item in dangling(schemas, resources)]

if problems:
    print("\n".join(problems))
    sys.exit(1)
```

It does not replace running the definitions in a development environment, since it knows nothing about stored rows, but it catches the failure with the largest blast radius at the cheapest point.

## Schemas next to the other definitions

Schemas are one of several definition kinds that describe what an API accepts and returns, and they are easy to confuse with their neighbors.

| Definition | What it describes | Applied to |
| --- | --- | --- |
| Schema | The shape of a JSON value | Fields of resources, route bodies, route responses (documentation) |
| Resource | A table, its fields, its operations and their policies | Rows at `/rest/v1/<name>` |
| Transformer | How a record is reshaped on the way out (omit, pick, set, rename, case) | Responses of a resource or route |
| Policy | Who may do something, as a condition on the caller, the record and the input | Operations, routes, buckets, channels |
| Route | A custom endpoint and what runs behind it | `/rest/v1/<path>` |

A schema answers "what may this value look like", a policy answers "who may send it", and a transformer answers "what does the reader see". Putting a rule in the wrong one is the usual design mistake, and the rows of the behavior table above are mostly cases of expecting a schema to do the work of a policy.
## Schema, inline object, `json` or a resource

Four ways to represent a nested structure exist, and they differ in what they validate and in what you can do with the data afterwards.

| | Reusable schema (`ref`) | Inline `object` | `json` | A related resource |
| --- | --- | --- | --- | --- |
| Reused across resources | Yes | No, copy the definition | Not applicable | Yes, by relation |
| Validates the shape | Types, constraints, allowed keys | Everything, including `required` and defaults | Nothing | Everything, as a resource |
| `required` and defaults inside | Not enforced | Enforced | Not applicable | Enforced |
| One definition to change | Yes | No | Not applicable | Yes |
| Documented in the API reference | A named component | A component named after the parent | As "any" | As its own endpoints |
| Filterable by inner value | No | No | No | Yes, it has columns |
| Stored | One JSON column | One JSON column | One JSON column | Its own table |
| Best for | Small repeated groups where constraints matter more than presence | A shape used once, with required keys | Opaque data you store and return | Anything you query, sort, count or link |

A decision follows from three questions. If you will query by what is inside, it is a resource. If you will not, but the shape is used once and has keys that must be present, it is an inline `object`. If the same shape appears in several places and its constraints (not its required keys) are what matter, it is a schema. If you do not know or do not care what is inside, it is `json`.

## `read_only` and `write_only` in a schema

These two keys are covered on [Field types](/data/field-types) for a resource's own fields. In a schema, they do less.

| Key | On a resource's own field | On a field inside a referenced schema |
| --- | --- | --- |
| `read_only` | Left out of create and update, so clients cannot write it | **Not applied.** A nested `stamp` marked `read_only` accepted `"client-set"` and stored it |
| `write_only` | Left out of the API document, but still returned at runtime | **Not applied.** A nested `secret` marked `write_only` was returned in the response |

Neither key can be used to protect a nested value. A nested value that clients must not set has to be enforced with a policy that compares `$input` with the stored record, or set by a route. A nested value that clients must not see has to be removed with a transformer's `omit`, which works on top-level fields, so nested secrets belong in a top-level `write_only`-and-omitted field instead, see [Transformers](/data/transformers).

Remember that even at the top level, `write_only` documents and does not hide. The page on field types explains the gap, and the same warning applies here: a column that is not in the definition, or is marked `write_only`, is still returned by the API unless a transformer, or `?select=`, removes it.

## A walkthrough: one address schema, three resources

The patterns above are easier to judge against a concrete build. This one defines five small schemas and uses them in a `stores` resource, and every request and response shown was run.

### Creating the schemas

In **Build**, **Schemas**, **New schema**, each schema is a name and a field list. The five used here:

| Schema | Description | Fields |
| --- | --- | --- |
| `Money` | An amount in the smallest currency unit | `amount_minor` (integer, minimum 0), `currency` (string, enum `USD`, `EUR`, `GBP`, `NGN`) |
| `Address` | A postal address | `street`, `city`, `region` (strings, up to 120, 80 and 80 characters), `postcode` (string, up to 16), `country` (string, exactly two characters, pattern `^[A-Z]{2}$`) |
| `GeoPoint` | WGS84 coordinates | `lat` (number, from -90 to 90), `lng` (number, from -180 to 180) |
| `ContactMethod` | One way to reach a person | `kind` (string, enum `email`, `phone`, `whatsapp`), `value` (string, up to 120) |
| `AuditStamp` | Who and when | `by` (string, up to 128), `at` (datetime) |

None of them uses `required`, for the reason given earlier: it is inert inside a reference. They carry their limits as constraints, which do apply.

### Using them in a resource

In **Resources**, **New resource**, the **Fields** section takes a field per row. A field of type **Schema reference** shows a **Schema** menu in **More options**, listing the five schemas by name. The `stores` resource below has a required reference to `Address`, optional references to `GeoPoint`, `Money` and `AuditStamp`, and a list of `ContactMethod` references with an empty default:

```json
{
  "name": "stores",
  "description": "Pickup locations",
  "fields": [
    {"name": "name", "type": "string", "required": true, "max_length": 80},
    {"name": "address", "type": "ref", "schema": "Address", "required": true},
    {"name": "location", "type": "ref", "schema": "GeoPoint"},
    {"name": "delivery_fee", "type": "ref", "schema": "Money"},
    {"name": "contacts", "type": "array", "items": {"type": "ref", "schema": "ContactMethod"}, "default": []},
    {"name": "updated_by", "type": "ref", "schema": "AuditStamp"}
  ]
}
```

Only `name` and `address` are required. After **Create / migrate table**, a complete record is accepted and filled out:

```json
POST /rest/v1/stores
{
  "name": "Lekki",
  "address": {"street": "12 Admiralty Way", "city": "Lagos", "country": "NG"},
  "location": {"lat": 6.44, "lng": 3.47},
  "delivery_fee": {"amount_minor": 50000, "currency": "NGN"},
  "contacts": [{"kind": "phone", "value": "+2348000000000"}],
  "updated_by": {"by": "maya@acme.co", "at": "2026-10-01T09:30:00Z"}
}

201
{
  "id": 1, "name": "Lekki",
  "address": {"street": "12 Admiralty Way", "city": "Lagos", "region": null, "postcode": null, "country": "NG"},
  "location": {"lat": 6.44, "lng": 3.47},
  "delivery_fee": {"amount_minor": 50000, "currency": "NGN"},
  "contacts": [{"kind": "phone", "value": "+2348000000000"}],
  "updated_by": {"by": "maya@acme.co", "at": "2026-10-01T09:30:00Z"},
  "created_at": "2026-10-01T20:48:44.627413+00:00", "updated_at": "2026-10-01T20:48:44.627413+00:00"
}
```

Note `region` and `postcode` in `address`: they were not sent, and they appear as `null`, because a nested value is filled to the full shape of its schema. Note also that `updated_by.at` came back as `2026-10-01T09:30:00Z`, exactly as sent: values inside a JSON column are stored as JSON, so a `datetime` nested in a schema is validated as a timestamp and returned as the text that was stored, not normalized the way a top-level `datetime` field is.

### What a bad request looks like

A body that breaks a rule in each of four of the nested values:

```json
POST /rest/v1/stores
{
  "name": "X",
  "address": {"country": "nigeria"},
  "location": {"lat": 99, "lng": 3},
  "delivery_fee": {"amount_minor": -5, "currency": "XXX"},
  "contacts": [{"kind": "fax", "value": "1"}]
}

422
[
  {"type": "string_too_long",     "loc": ["address", "country"],            "ctx": {"max_length": 2}},
  {"type": "less_than_equal",     "loc": ["location", "lat"],               "ctx": {"le": 90.0}},
  {"type": "greater_than_equal",  "loc": ["delivery_fee", "amount_minor"],  "ctx": {"ge": 0}},
  {"type": "literal_error",       "loc": ["delivery_fee", "currency"],      "ctx": {"expected": "'USD', 'EUR', 'GBP' or 'NGN'"}},
  {"type": "literal_error",       "loc": ["contacts", 0, "kind"],           "ctx": {"expected": "'email', 'phone' or 'whatsapp'"}}
]
```

Every problem carries the full path through the reference, and the list entries carry an index. Because the paths do not name the schema, a client handles an error in `address.country` the same way whether `address` is a reference or an inline object.

### Using the same schema elsewhere

The point of the exercise is that `Address` can now appear in a second resource, and in a third, with no copying:

```json
{"name": "customers", "fields": [
  {"name": "name", "type": "string", "required": true},
  {"name": "billing", "type": "ref", "schema": "Address"},
  {"name": "shipping", "type": "ref", "schema": "Address"}
]}
```

A change to `Address` (a new optional `landmark` field, a longer `street`) reaches `stores` and `customers` together on the next request. The same holds in reverse for a mistake. The cost of that reach is the subject of the section on changing a schema in use.

## How a schema appears in the API document

The generated reference, in **API Explorer** and on the public docs page, lists each schema once as a component, and every resource that uses it points at that component. For the `stores` resource, the request schema for `POST` is:

```json
{
  "title": "StoresCreate",
  "required": ["name", "address"],
  "type": "object",
  "properties": {
    "name": {"title": "Name", "maxLength": 80, "type": "string"},
    "address": {"$ref": "#/components/schemas/Address"},
    "location": {"anyOf": [{"$ref": "#/components/schemas/GeoPoint"}, {"type": "null"}]},
    "delivery_fee": {"anyOf": [{"$ref": "#/components/schemas/Money"}, {"type": "null"}]},
    "contacts": {
      "title": "Contacts",
      "anyOf": [{"type": "array", "items": {"$ref": "#/components/schemas/ContactMethod"}}, {"type": "null"}],
      "default": []
    },
    "updated_by": {"anyOf": [{"$ref": "#/components/schemas/AuditStamp"}, {"type": "null"}]}
  },
  "additionalProperties": false
}
```

The `required` list names `name` and `address`, the fields of the resource itself, and says nothing about `street` or `city` inside `Address`, in line with the behavior described above. The components available in the document for this environment are `Address`, `AuditStamp`, `ContactMethod`, `GeoPoint`, `Money`, the resource's response schema `Stores`, and the shared error item `ValidationErrorItem`. An inline `object` field produces components named after the parent resource instead (`PeopleInline`, `PeopleCreateInline` and `PeopleUpdateInline` for an inline field called `inline` on `people`), one per mode, which is how an inline object's `required` can differ between create and update in the document.

Two practical points follow. A client generator reading the document produces one type per schema, shared by every resource that uses it, which is the same economy as on the server. And because every property in a schema component is nullable and nothing is required, generated client types for a schema have all-optional properties. Add your own required-ness in the client when a value is conceptually mandatory.

## Schemas in flows and functions

Flows and functions are where a reference does not reach. Both have places that accept a field list, and neither can look a schema up by name.

| Place | Takes | Can it use a `ref` to a stored schema |
| --- | --- | --- |
| A resource's `fields` | A field list | Yes |
| A route's `input_fields` | A field list | Yes |
| A route's `input_schema` and `response_schema` | A schema name | Yes, by name |
| A flow's `validate.schema` block | A field list in its config | **No** |
| A function's `input_fields` | A field list in the decorator | **No**, by the same code path |

A `validate.schema` block given a field whose type is `ref` fails the run, and the failure is a `500`:

```text
fields: [{"name": "home", "type": "ref", "schema": "Address"}]
POST /rest/v1/vs  {"home": {"city": "x"}}
  ->  500  {"error": "block_failed", "message": "field 'home' refers to unknown schema 'Address'"}
```

To validate a nested shape inside a flow, write the nested fields inline, as an `object`, in the block's config. That duplicates the definition, and the duplicate will not follow the schema when it changes, so keep the two next to each other in your notes and review them together. A flow that receives its data from a route with `input_fields` or from a resource operation has already been validated at the edge, and needs the block only for data that arrives some other way.

## Moving schemas between environments

Schemas belong to an environment, and they travel with the rest of its definitions in three ways. Each has a rule you should know before relying on it.

| Mechanism | How schemas are carried | Rule to know |
| --- | --- | --- |
| **Promote** (`POST …/envs/{env}/promote`) | Copied to the target environment by name | An upsert, not a sync. A schema deleted in the source stays in the target |
| **Create environment** with a source to copy from | Copied when the new environment is created | A one-time copy |
| A **release** | Captured in the revision's snapshot, which is what a prepared release serves | The compatibility check does not look at schemas |

The promote rule was checked. Two schemas, `Address` and `Old`, were promoted from `development` to `staging`. Then `Old` was deleted in `development` and `Address` gained a `zip` field, and only the schemas were promoted again:

```text
promote  {"to": "staging", "include": ["schemas"]}   ->  {"copied": {"schemas": 1}}
staging schemas:  Address (city, zip),  Old ()
```

`Address` was updated, and `Old` was still there. A promotion never deletes. If you remove a schema, remove it in each environment yourself, and remember that a resource in the target that still points at it is the dangling reference described earlier. Two other facts from the same run: `include` takes definition kinds (`schemas`, `resources`, `routes`, `flows` and so on), and a kind name it does not know is ignored without an error, so a typo copies nothing and reports `{"copied": {}}`. And promoting a resource does not create its table in the target. The first request to the promoted resource in `staging` fails until **Create / migrate table** is run there. See [Migrations](/data/migrations) and [Environments and promotion](/operate/environments-and-promotion).

## Where a schema shows up in Studio

A schema is created in one place and used in several. This table follows one schema through the places a developer meets it.

| Where | What you do | What it means for the schema |
| --- | --- | --- |
| **Build**, **Schemas** | Create, edit, delete | The only place a schema's own fields are defined |
| **Resources**, a resource, **Fields**, a field of type **Schema reference** | Pick the schema in the **Schema** menu | The resource now depends on the schema by name |
| The same, an `array` field with item type **Schema reference** | Pick the schema in the second menu | A list of that shape |
| **Routes**, a route, **Request & response**, **Request body** | Choose **Use a schema**, then **Choose a schema** | The route's body is validated against the schema's types and constraints, without `required` |
| The same section, **Define fields** | Declare the fields in place, including **Schema reference** fields | The route's body is validated with `required` honored at the top level |
| The same section, **Response schema** | Pick a schema | Documentation only. The response is not filtered |
| **Overview**, **Definitions with problems** | Read the list | Where a missing or deleted schema shows up |
| **API Explorer** | Read the generated endpoint and its request schema | Where you see the schema as a component, and test a body against it |

A route's **Request body** control has three choices, and the difference between the second and the third is the same difference as between an inline object and a reference: **Define fields** enforces `required` and defaults at the top level, and **Use a schema** does not. If a route's body has required keys, use **Define fields**, and put the shared, constraint-heavy parts of it in `ref` fields.

### What Studio does not show

Studio does not show which resources and routes use a schema, does not warn before you delete or rename one, and does not run a check for cycles. The **Delete** button's confirmation names only the schema. The script earlier on this page is the substitute for a "used by" panel, and the **Overview** list is the after-the-fact warning. If you manage definitions through the Platform API in a repository, a CI check that builds the reference graph and fails on a cycle or a dangling name is a small addition that closes the gap, and it is worth having for any environment more than one person edits.

## Designing schemas that last

Schemas are the most widely shared definitions in an environment, which makes careless ones the most expensive to fix. These guidelines come from the behaviors above.

| Guideline | Reason |
| --- | --- |
| Keep a schema small and about one idea | A schema used in many places is hard to change. A small one has fewer reasons to |
| Put constraints in the schema, and requiredness at the point of use | Constraints are enforced through a reference, `required` is not |
| Make every key optional in the schema, and mark the **reference field** required where presence matters | That is what actually happens, so the definition says what it does |
| Prefer adding optional keys over removing or retyping | Adding is safe. Removing breaks reads of rows that still hold the key |
| Never remove a key without first rewriting stored values | Rows that keep the old key fail the read model |
| Treat a schema like a public interface | Resources, routes, clients and the API document all depend on it |
| Name schemas for what they are, not where they are used | `Address`, not `StoreAddress`. Reuse is the point |
| Use `PascalCase` for schemas and lowercase for resources | The two share a namespace in the API document's components, so the case keeps them apart |
| Avoid defaults and `read_only` inside a schema | Neither is applied through a reference |
| Do not nest more deeply than you must | Error paths, API components and stored JSON all get harder to follow |
| Do not use a schema for recursive data | A cycle takes the environment down. Use a self-referencing resource |

### Names in the API document

Schemas and resources both become named components in the generated reference, and a schema's name is used as is. A schema called `Stores` would collide with the response component of a resource called `stores`, whose model is named `Stores`. The case difference in the guideline above is what prevents that by default, and it is why resource names are required to be lowercase. If you name a schema in lowercase, check **API Explorer** for a duplicate component.

## Patterns and their pitfalls

These are common uses, each with the thing that goes wrong.

### Settings with defaults

A user's preferences, with a theme that defaults to `light`. As a reference this does not work, because the default is not applied. As an inline `object` it does:

```json
{"name": "preferences", "type": "object", "fields": [
  {"name": "theme", "type": "string", "enum": ["light", "dark"], "default": "light"},
  {"name": "newsletter", "type": "boolean", "default": false}
]}
```

```text
POST /rest/v1/profiles  {"display_name": "Maya", "preferences": {"theme": "dark"}}
  ->  201  {"preferences": {"theme": "dark", "newsletter": false}, ...}      (the nested default applied)
```

The same two fields in a referenced schema return `{"theme": "dark", "newsletter": null}`. Use an inline object when the defaults matter, and a schema when only the constraints do.

### Money

A price with an amount and a currency, shared by products, orders and invoices. The schema holds the constraints, an `amount_minor` of at least 0 and a currency from a list. The resource that uses it makes the reference required, and treats a missing `amount_minor` as an invalid price in the code that reads it:

```json
{"name": "price", "type": "ref", "schema": "Money", "required": true}
```

A body of `{"price": {"currency": "USD"}}` is accepted, and `price.amount_minor` is `null`. If a missing amount must be refused, add an input policy that requires `$input.price.amount_minor` to exist, or write the two fields at the top level of the resource where `required` is enforced.

### An audit stamp that clients cannot forge

`AuditStamp` with `by` and `at` suggests a record of who changed a row and when. As a reference it protects nothing: `read_only` is not applied, so a client can send any `by` and `at`. Set the values from a route or a flow that reads the caller's identity, and do not accept them from the body. For a creator's identity on a resource, the **Owner field** is the supported mechanism.

### A list of small structured items

Line items on an order, contacts on a person: `{"type": "array", "items": {"type": "ref", "schema": "Line"}}`. Each item is validated, errors carry the index, and the whole list is one JSON value. It is replaced wholesale on update, so a client that edits one item sends the entire list. If two users may edit different items at once, or if you need totals across orders, use a related resource instead.

### A shared shape that must be required

An address that must have a `city`. The schema cannot say so. Put the requirement where it holds: an inline object, an input policy that looks inside the nested value, or a route with `input_fields` whose top-level fields are required. The policy form was tested with `{"exists": "$input.address.city"}` as the `create` policy of a resource whose `address` is a reference to a schema with no required keys:

```text
POST /rest/v1/shops  {"address": {"city": "Lagos"}}      ->  201
POST /rest/v1/shops  {"address": {"street": "x"}}        ->  403  "policy 'needs_city' refused"
POST /rest/v1/shops  {"address": {}}                     ->  403  "policy 'needs_city' refused"
```

The same technique protects the `amount_minor` of a `Money` reference, and it distinguishes zero from absent, which a truthiness test would not:

```text
POST /rest/v1/goods  {"price": {"amount_minor": 5, "currency": "USD"}}   ->  201
POST /rest/v1/goods  {"price": {"currency": "USD"}}                       ->  403  (absent)
POST /rest/v1/goods  {"price": {"amount_minor": 0}}                       ->  201  (zero exists)
POST /rest/v1/goods  {"price": {"amount_minor": null}}                    ->  403  (null does not count)
```

The cost is the one every policy has: the refusal is a `403` that names the policy and not the field. Do not describe `city` as required in the schema's field list and assume it is, because the editor will show it as required and the server will not enforce it.

## More shapes, tested

Six more schemas, each of which came up in practice, and one resource that uses all of them. They show what the reference does well, which is constraints on small groups of values, and the one gap that remains, which is checks across fields.

| Schema | Fields | Why it is a good fit |
| --- | --- | --- |
| `LocalizedText` | `en`, `fr`, `yo`, strings up to 200 characters | A closed set of languages. A key that is not declared is refused, so a typo in a language code is caught |
| `Dimensions` | `w`, `h`, `d` (numbers, minimum 0), `unit` (enum `cm`, `in`) | Numeric bounds and a closed unit list in one reusable group |
| `DateRange` | `from`, `to` (dates) | Two dates that belong together |
| `Label` | `key` (pattern `^[a-z0-9_.-]+$`, up to 40), `value` (up to 120) | A list of tags with a constrained key |
| `Links` | `website`, `github` (urls), `email` (email) | Several fields that share the same format rules |
| `Attachment` | `key`, `name`, `size_bytes` (minimum 0), `content_type` (pattern `^[a-z]+/[a-z0-9.+-]+$`) | Metadata for a file held in a storage bucket |

    {"name": "links", "type": "ref", "schema": "Links"},

  {"type": "string_pattern_mismatch",   "loc": ["files", 0, "content_type"]}

### The one gap: checks across fields

A reference validates each key on its own. It cannot say that `valid.from` must not be later than `valid.to`, and that is the gap:

```text
POST /rest/v1/offers  {"slug": "r", "title": {"en": "t"}, "valid": {"from": "2026-04-01", "to": "2026-03-01"}}
  ->  201   (a range that ends before it starts is accepted)
```

A rule across two keys of a nested value belongs in an input policy, which can compare them. This one allows a missing end date (an open range) and otherwise requires the dates to be in order, and ISO dates compare correctly as text:

```json
{"any": [
  {"not": {"exists": "$input.valid.to"}},
  {"lte": ["$input.valid.from", "$input.valid.to"]}
]}
```

```text
{"valid": {"from": "2026-03-01", "to": "2026-03-31"}}   ->  201
{"valid": {"from": "2026-04-01", "to": "2026-03-01"}}   ->  403  "policy 'ordered' refused"
{"valid": {"from": "2026-04-01"}}                       ->  201  (open ended)
{"valid": {"from": "2026-04-01", "to": "2026-04-01"}}   ->  201  (the same day)
{}                                                      ->  201  (no range at all)
```

The refusal names the policy and not the keys, as with any policy. See [Validation](/data/validation) for the pattern and its trap, a comparison against a missing value.

### Key order in responses

Stored JSON is returned with the keys in the order the database gives it back, and the order is not part of the contract. SQLite stores the text as written and returns it as written. PostgreSQL's `JSONB` does not preserve key order, whitespace or duplicate keys, and MySQL's `JSON` type normalizes the order of keys. A client that compares serialized nested values as text, or that depends on a key coming first, will see differences between environments that use different databases. Compare parsed values, and treat nested objects as unordered.

## Troubleshooting schemas

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| Every request to the environment returns `500`, including **Overview** | A cycle of schemas | Delete a schema in the cycle from **Schemas**, then fix the other |
| One resource returns `404` on all its routes | A `ref` to a schema that does not exist, or a field named like the primary key | Read **Definitions with problems** on **Overview** |
| A nested `required` key is accepted when missing | `required` is inert inside a reference | Make the shape an inline `object`, use `input_fields`, or add an input policy |
| A nested default is `null` | Defaults are not applied through a reference | Use an inline `object`, or fill the value in a route |
| Reads return `500` after editing a schema | Stored rows hold a removed key, or a value that breaks a new constraint | Restore the old definition, or repair the stored JSON, then retry |
| A `PATCH` to one nested key erased the others | The nested value is replaced wholesale | Send the complete nested object |
| `response_schema` does not hide a field | It documents and does not filter | Shape the response in the flow, or use a transformer |
| A flow's `validate.schema` fails on a nested field | It cannot resolve a `ref` | Write the nested fields inline |
| A client's generated type has every property optional | Components list no `required` and every property is nullable | Add the required-ness yourself in the client |
| A schema is missing after promoting | Promote copies by name and the schema did not exist at the source when promoted | Promote with `include` containing `schemas`, or check the source |
| A schema deleted in the source is still in the target | Promote never deletes | Delete it in the target |

## Putting the behaviors side by side

The same field list behaves differently in different places. This table puts the places next to each other, so it can be read when you are choosing where a nested shape should live.

| Behavior | Resource's own fields | Inline `object` field | `ref` to a schema | Route `input_fields` | Route `input_schema` | Route `response_schema` |
| --- | --- | --- | --- | --- | --- | --- |
| `required` | Enforced on create | Enforced inside | **Not enforced** | Enforced | **Not enforced** | Not applicable |
| `default` | Applied on create | Applied inside | **Not applied** | Applied | **Not applied** | Not applicable |
| Type and constraint checks | Yes | Yes | Yes | Yes | Yes | Not applied |
| Unknown keys | Rejected | Rejected | Rejected | Rejected | Rejected | Not filtered |
| `read_only`, `write_only` | `read_only` enforced, `write_only` documented only | Same as the resource | **Neither applied** | Not applicable | Not applicable | Not applicable |
| On update | All optional and nullable | Relaxed inside | Replaced wholesale | Not applicable | Not applicable | Not applicable |
| Extra stored keys on read | Allowed | Allowed | **Fail the read** | Not applicable | Not applicable | Not applicable |
| One definition for many | No | No | Yes | No | Yes | Yes |

The bold cells are the behaviors that differ from what the same field list does when written inline, and they are the ones a design review should look at first.

## Converting between inline objects and schemas

A shape often starts inline and becomes a schema when a second use appears, and sometimes goes the other way. The stored JSON is the same in both forms, so the conversion is a change of definition and not of data, but the two enforce different rules, which is what to check.

| Direction | What changes immediately | Check before you switch |
| --- | --- | --- |
| Inline object to schema | `required` and defaults inside it stop being enforced. Reads begin to reject extra keys | Rows with extra keys inside the object, and any code that relied on a nested default |
| Schema to inline object | `required` and defaults start being enforced. Reads allow extra keys | Rows missing keys that are now required, and a nested default that will now be applied to new rows only |

The first direction is the one that can break reads. An inline `object` allows unexpected nested keys when reading and a referenced schema does not, so a row that holds a key the schema does not declare will fail. Find such rows with the JSON functions of your database, or by reading rows through a function and comparing keys, before making the change.

## Testing schemas

A schema is shared, so a test for it is a test for everything that uses it. Two kinds are worth having: a check on the definitions as data, and a check on behavior through a resource that uses the schema.

The first needs no running API. It reads the definitions and fails on the two things that cost the most, a cycle and a dangling reference:

```python
import json

def find_cycle(schemas: dict[str, list[dict]]) -> list[str] | None:
    """Return one cycle of schema names, or None."""
    def refs(fields):
        for f in fields or []:
            if f.get("type") == "ref":
                yield f["schema"]
            if f.get("type") == "array":
                yield from refs([f.get("items") or {}])
            if f.get("type") == "object":
                yield from refs(f.get("fields"))

    graph = {name: set(refs(fields)) for name, fields in schemas.items()}
    state = {}              # name -> "visiting" | "done"
    stack = []

    def visit(name):
        if state.get(name) == "done":
            return None
        if state.get(name) == "visiting":
            return stack[stack.index(name):] + [name]
        state[name] = "visiting"
        stack.append(name)
        for child in graph.get(name, ()):
            if child in graph:
                found = visit(child)
                if found:
                    return found
        stack.pop()
        state[name] = "done"
        return None

    for name in graph:
        found = visit(name)
        if found:
            return found
    return None


def dangling(schemas, resources) -> list[str]:
    known = set(schemas)
    missing = []
    for owner, fields in [*schemas.items(), *[(r["name"], r["fields"]) for r in resources]]:
        for f in fields:
            if f.get("type") == "ref" and f["schema"] not in known:
                missing.append(f"{owner}.{f['name']} -> {f['schema']}")
    return missing
```

Run both over the definitions you export before every promote. The second kind of test sends requests, and each row below came from a real run against the `stores` resource:

```python
def test_address_constraints_are_enforced_through_the_reference():
    r = create_store(address={"country": "nigeria"})
    assert r.status_code == 422
    assert ("address.country", "string_too_long") in codes(r)


def test_address_required_keys_are_not_enforced():
    # Documents the behavior: required inside a referenced schema is inert.
    r = create_store(address={})
    assert r.status_code == 201
    assert r.json()["address"]["city"] is None


def test_nested_value_is_replaced_on_patch():
    created = create_store(address={"street": "1 Main", "city": "Lagos"}).json()
    r = patch_store(created["id"], address={"city": "Abuja"})
    assert r.json()["address"] == {"street": None, "city": "Abuja", "region": None,
                                   "postcode": None, "country": None}
```

The second and third tests exist to document behavior you rely on and may not like. When Pawabase changes it, they fail, and the failure is the notification.

## Reviewing a change to a schema

| Question | Where to find the answer |
| --- | --- |
| Who uses this schema? | The reference script, since Studio has no view for it |
| Does the change add a cycle? | The cycle check above, or read the `ref` fields of the schemas it points at |
| Does it tighten a constraint, remove a key or retype one? | The table in the section on changing a schema in use |
| Will stored rows still read? | A query for the old shape, or a read of every resource that uses it in a development environment with production-like data |
| Is the compatibility result trustworthy? | No: the release check ignores schemas. Treat it as covering resources and routes only |
| Does a client generator consume the document? | If so, a schema change changes generated types for every resource that uses it |
| Is there a rollback? | A schema is data, so the previous definition can be restored, but rows written under a new one may not fit the old |

## Size and cost of structured values

A schema's reach is paid for in storage and in validation work, and the fill-out behavior makes both larger than the data you sent.

| Factor | Effect |
| --- | --- |
| Stored size | A nested value is stored at its full shape, so a schema with twenty optional keys stores twenty keys per use, mostly `"key": null`, even when one value was sent |
| List length | A list of references is validated item by item, and each item is filled out the same way, so cost and size grow with both the length and the width of the schema |
| Response size | Every read returns the full shape too. A list endpoint that returns fifty rows with three nested values each returns every null |
| Nesting depth | Errors are found by walking the whole body, so deep nesting costs more to validate and to read in an error response |
| Write amplification | A nested value is replaced as a unit, so a one-key edit rewrites the whole value |

None of this is a reason to avoid schemas. It is a reason to keep them narrow. A schema with five keys that are always used is cheaper than one with thirty keys of which two are ever set, and a heavy structure that is read rarely belongs in its own resource, fetched with `?expand=` when needed, so list responses stay small. When you need a lean response, the `select` parameter drops whole fields, and a transformer can `omit` or `pick`, see [Filtering](/data/filtering) and [Transformers](/data/transformers).

## Keeping schemas in a repository

If schemas are managed from scripts, the layout that works is one file per definition, named for the definition, in a folder per kind, so a change to a schema is a one-file diff that reviewers can read:

```text
definitions/
  schemas/
    Address.json
    Money.json
    GeoPoint.json
  resources/
    stores.json
    customers.json
  policies/
    needs_city.json
```

Each file holds the body the Platform API accepts, for example `Address.json`:

```json
{
  "name": "Address",
  "description": "A postal address",
  "fields": [
    {"name": "street", "type": "string", "max_length": 120},
    {"name": "city", "type": "string", "max_length": 80},
    {"name": "country", "type": "string", "min_length": 2, "max_length": 2, "pattern": "^[A-Z]{2}$"}
  ]
}
```

Three conventions pay for themselves. Apply schemas before the resources that reference them, so an environment is never in a state where a reference points at nothing. Keep the cycle and dangling checks from the previous section in CI, so they run on every change. And review a schema change the way you would review a change to a public API, because to every resource and route that uses it, it is one.

## A pre-release checklist for a schema change

| Question | Answer should be |
| --- | --- |
| Does the change remove or retype a key? | If yes, stored rows were rewritten first, with the finder query for the key as `json_type(...)`, not `json_extract(...)` |
| Does it tighten a constraint? | If yes, a query for rows that violate it returned none, or they were repaired |
| Does it add a key that old clients do not send? | Fine, since the key is optional in every reference |
| Does it add a `required`, a default or a `read_only` to a schema? | Remove it. None of them is applied through a reference |
| Does any resource or route use the schema as a `ref` inside a flow's `validate.schema`? | That block cannot resolve it, so its inline copy needs the same change |
| Was the cycle check run? | Yes, and it found none |
| Was the change tried in a development environment with production-like rows? | Yes, with a list and a get of every resource that uses the schema |
| Is there an old **API version** that must keep the old shape? | If so, prepare the release before changing the live definition |
| Who else reads this schema? | Clients that generate types from the API document will regenerate them |

## Anti-patterns

| Anti-pattern | What goes wrong | Instead |
| --- | --- | --- |
| A schema called `Settings` or `Data` holding everything | It is changed constantly and every change touches every user | Several narrow schemas, or an inline object per resource |
| `required` keys inside a schema, relied on for safety | Nothing enforces them, and the editor shows them as if something did | An inline object, an input policy, or `input_fields` |
| A default inside a schema | Never applied | An inline object or a route that fills the value |
| `read_only` or `write_only` inside a schema to protect a value | Writable and readable anyway | A policy, a route, or a transformer |
| A schema that refers to itself | The whole environment returns `500` | A resource with a parent link |
| Deleting a schema without checking its users | The resources that use it stop being served | The reference script, then delete |
| Renaming through the API | Every use now points at nothing | Create the new name, move the users, delete the old |
| Using `response_schema` to hide fields | The response is not filtered | Build the response in the flow, or use a transformer |
| Removing a key and rewriting rows afterwards | A window of `500` responses on every read | Rewrite first, or add before removing |
| Putting a searchable value only inside a schema'd JSON | It cannot be filtered or sorted | Also store it in a column |
| Letting two schemas point at each other for convenience | A cycle | Point one way, and look the other direction up with a relation |

## More questions

<AccordionGroup>
  <Accordion title="Do schemas have versions of their own?">
    No. A schema is a single current definition. Versions come from releases: a release captures all definitions, schemas included, as a snapshot, and an API version serves one release. To run two shapes side by side, serve them from two API versions.
  </Accordion>
  <Accordion title="Can I see the compiled model?">
    Indirectly, through the API document. The components in **API Explorer** are the compiled models, and they show the real constraints, the nullability and `additionalProperties`. They do not show `required` for a referenced schema, because there is none.
  </Accordion>
  <Accordion title="Why does the API document show every property as nullable?">
    A schema is compiled in a generic mode where every key is optional, and a stored value can hold `null` for any key. The document describes what can be returned, which is why client types generated from it need optional properties.
  </Accordion>
  <Accordion title="Does a schema validate values I read from the database?">
    Yes. The same compiled model checks reads, which is why a stored value that no longer fits a schema makes the response fail with `500` "Response validation failed".
  </Accordion>
  <Accordion title="Can a route body be a bare list or a number?">
    No. A route's body must be a JSON object, so a schema describes an object. To accept a list, put it under a key.
  </Accordion>
  <Accordion title="What is the difference between Use a schema and Define fields on a route?">
    **Use a schema** points at a stored schema and enforces its constraints, but not `required` or defaults. **Define fields** writes the list on the route itself, and enforces `required` and defaults at the top level. Fields inside it that are references still follow the reference rules.
  </Accordion>
  <Accordion title="Do I have to create a schema before using it in a resource?">
    No. The order does not matter, and a reference to a schema that does not exist yet is saved and reported as a problem until the schema is created. It is still better to create the schema first, so the environment is never in a state with problems.
  </Accordion>
  <Accordion title="Can a schema hold an enum of values shared by several fields?">
    A schema can hold a field with an `enum`, and a reference to the schema shares the list. To share a list across top-level fields without a nested object, repeat it. There is no named enum type.
  </Accordion>
</AccordionGroup>

## Schemas and releases

A release serves an API version from a snapshot of every definition, and schemas are part of the snapshot. That gives schemas two touchpoints with the release flow, and both were exercised.

**A revision compiles the snapshot, and a broken schema makes the revision invalid.** From **History**, the **Revisions** tab creates a revision of the current definitions. Creating one compiles them, and a dangling reference is recorded on the revision as a problem and marks it `invalid`:

```text
revision 1   status valid     problems []
(delete the Address schema that the people resource references)
revision 2   status invalid   problems ["resource people: field 'home' refers to unknown schema 'Address'"]
```

An invalid revision cannot become a release. Preparing a release from revision 2 was refused with `422`. So a missing schema is caught at the revision step, before it can reach a version that serves clients, which is the safety net the live environment does not have.

**The compatibility check does not read schemas.** A release is compared with the previous one, and breaking changes need an explicit `allow_breaking` acknowledgement, shown in Studio as the checkbox "I acknowledge breaking compatibility findings." The comparison covers resources, their fields and routes. Removing the `nick` field from `people` was reported as breaking and refused with `409` until acknowledged. A revision whose only change was to tighten a constraint inside the `Address` schema was reported as compatible, with no changes listed:

```text
release from a revision that removes a resource field   ->  409  breaking changes require allow_breaking
release from a revision that only tightens a schema     ->  compatible, changes: []
```

The second line is the gap. A tightened schema can make existing rows unreadable on the API version that serves the release, and the release process will not say so. Run the finder queries from the earlier sections against the data before you prepare the release, not after you activate it.

| Stage | Catches | Does not catch |
| --- | --- | --- |
| Saving a schema | Bad names, bad field names and types, duplicate names, an invalid `pattern` | A missing reference, a cycle |
| Creating a revision | A reference to a missing schema, a resource that cannot compile | Rows that no longer fit |
| Preparing a release | A revision with problems, removed fields, retyped fields, new required fields, removed routes | A tightened schema, a removed schema key, changed defaults |
| Serving a request | Nothing new. It compiles lazily and reports problems on **Overview** | A cycle, which fails every request |

Serving a release from an older revision is also the way to keep the previous shape alive. An API version bound to a release uses the schemas that were in that snapshot, so clients on `v1` keep the old `Address` while `v2` uses the new one, over the same tables. The data is shared, so rows written under `v2` have to read under `v1`'s schema as well, or the older version starts returning `500`. See [Releases and API versions](/operate/releases-and-api-versions).

### Where releases show up in Studio

The controls live in the **History** sheet. Its tabs are **Branches**, **Releases**, **Revisions**, **API versions** and **Deployments**, and a schema change touches the middle three.

| Tab | What you do | What it shows about a schema change |
| --- | --- | --- |
| **Revisions** | Type a message, placeholder "Snapshot main", and choose **Create revision** | The table lists each revision with its number, branch, **Status** and message. A revision with a missing schema shows an invalid status and does not appear in the **Revision** menu used to prepare a release |
| **Releases** | Choose a **Revision**, an **API version** and a **Release name** (placeholder `v2.0.0`), tick "I acknowledge breaking compatibility findings." if needed, and choose **Prepare release** | The **Prepared releases** table shows each release's **Path** (`/rest/v1`, `/rest/v2`), **Status** and a **Compatibility** badge, green for compatible and red for breaking. A schema change alone does not turn it red |
| **API versions** | Add a version such as `v2` | The version a release is bound to, and so the schemas its clients see |
| **Deployments** | Read the log of activations | Each row has a **Rollback** button, which returns an API version to its previous release and so to the previous schemas |

**Activate** on a prepared release makes the version serve it. Because a rollback restores the snapshot, the old schemas come back with it, and any rows written in the meantime that do not fit them fail to read. The rollback restores definitions and does not rewrite data.

## Reading a `ref` field's JSON by hand

The form writes a small amount of JSON, and being able to read it helps when you review a definition in a pull request or edit it on the **JSON** tab. Each placement of a reference has the same pieces:

```json
{"name": "home", "type": "ref", "schema": "Address", "required": true}
```

```json
{"name": "others", "type": "array", "items": {"type": "ref", "schema": "Address"}}
```

```json
{"name": "billing", "type": "ref", "schema": "Address", "description": "Where invoices are sent"}
```

| Key | Meaning in a reference |
| --- | --- |
| `type` | `"ref"` |
| `schema` | The name of the schema, case-sensitive |
| `required` | The reference itself must be present. It says nothing about the keys inside |
| `nullable` | Whether an explicit `null` is accepted. A required reference rejects `null` unless this is `true` |
| `description`, `example` | Documentation, like any field |
| `default` | Not offered in the form. Set in JSON, it supplies the whole nested value when the key is omitted, and it is not checked against the schema |
| Everything else (`min_length`, `enum`, and so on) | Stored and ignored. Constraints belong to the schema's own fields |

A reference with a default and a required, nullable reference, both run:

```json
{"name": "home", "type": "ref", "schema": "Address", "default": {"city": "Lagos"}}
{"name": "work", "type": "ref", "schema": "Address", "required": true, "nullable": true}
```

```text
POST /rest/v1/p  {"work": {"city": "x"}}   ->  201  {"home": {"city": "Lagos"}, "work": {"city": "x"}}   (home took the default)
POST /rest/v1/p  {"work": null}            ->  201  {"home": {"city": "Lagos"}, "work": null}            (null accepted because of nullable)
POST /rest/v1/p  {}                        ->  422  missing at ["work"]                                    (required, so it must be present)
```

A default on a reference is the one way to give a nested value a starting shape through a schema, since the schema's own field defaults are not applied. It is a whole value, so it replaces the filled-out shape the schema would otherwise produce.

The `schema` value is the only link, and it is just a name. That is why renaming is dangerous and why a typo in it is reported on **Overview** as an unknown schema and never as a validation error on any request.

## Debugging a schema problem in Studio

| You see | Open | To learn |
| --- | --- | --- |
| A resource that answers `404` on every route | **Overview**, **Definitions with problems** | Which schema it needs and cannot find |
| `500` on one resource's reads only | **Observability**, filtered by **5xx server error**, then the **Request trace** | Which request failed and when it started, which tells you which change it follows |
| `500` on everything | **Schemas** | Whether a cycle was just saved. Delete a schema in the cycle |
| A `422` with a nested `loc` | **API Explorer**, send the same body | The exact entries, with `ctx` |
| A client type that disagrees with the server | **API Explorer**, the request schema | The components, with the nullability the server really has |
| A stored value that will not read | **Database**, query the column | The raw JSON, and which key or value breaks the new definition |

## An incident, start to finish: a cycle in production

The cycle is rare and its effects are dramatic enough that it is worth walking through as it would be experienced, using the requests that were observed.

A developer adds a `parent` field to a `Category` schema so categories can nest, and points it at `Category` itself. Studio's field editor does not offer the schema being edited in its **Schema** menu, so they edit the **JSON** tab instead, which accepts anything:

```json
{"name": "Category", "fields": [
  {"name": "name", "type": "string"},
  {"name": "parent", "type": "ref", "schema": "Category"}
]}
```

**Save changes** succeeds. The save validates the name, the field names and the types, and does not look for cycles. The environment's version is bumped, and nothing is compiled yet.

The next request after the change triggers the rebuild, and every request fails:

```text
GET /rest/v1/products   ->  500  Internal Server Error
GET /rest/v1/orders     ->  500  Internal Server Error
GET Overview            ->  500
```

Resources that have never heard of `Category` fail too, because the compiled application for the environment is one object and it could not be built. Clients see `500` everywhere, and **Observability**, which reads recorded requests, shows a wall of `5xx`. **Overview**, where **Definitions with problems** would normally explain a broken definition, cannot load, because the page's data is computed from the compiled application.

The page that does load is **Schemas**, because the list is read from stored definitions and not from the compiled app. Opening `Category` and choosing **Delete** removes it, and the next request recompiles:

```text
DELETE …/schemas/Category   ->  204
GET /rest/v1/products       ->  200
```

If a second schema had been involved, as in a cycle between `A` and `B`, deleting one is enough. The surviving schema is then reported as an ordinary dangling reference:

```text
Definitions with problems:
  schema B: field 'a' refers to unknown schema 'A'
```

and it is fixed by editing it or deleting it. The data is untouched by any of this, since schemas never touch tables. The cost of the incident was the minutes between the save and the delete, and the way to shorten them is to know that **Schemas** is the page to open first.

Three habits prevent it. Make reference changes in a development environment before they reach one that serves traffic. Run the cycle check from the CI section on every change that touches `ref` fields. And after saving any schema change in an environment that matters, load **Overview** immediately: a blank page there is a signal in itself.

## How this compares to other systems

If you are coming from a system that has its own idea of a reusable type, these comparisons may help with expectations. They are about the concept, not a mapping of features.

| System | Its equivalent | How Pawabase differs |
| --- | --- | --- |
| JSON Schema `$defs` and `$ref` | A named, referenced shape | JSON Schema keeps `required` through a reference. Pawabase does not, and has no `oneOf`, `allOf` or conditional keywords |
| Pydantic models | A class with typed fields, nested by reference | Pawabase builds Pydantic models underneath, and a reference is compiled in a generic mode that drops `required` and defaults |
| Postgres composite types | A named row type usable as a column | A composite is typed by the database. A schema is validated by the API and stored as JSON |
| Firestore maps | An untyped nested object | A schema validates the nested keys and rejects unknown ones |
| OpenAPI `components/schemas` | A reusable response or request type | Pawabase generates the components from schemas, and every property is nullable in them |
| GraphQL types and inputs | A reusable object type | Pawabase serves REST, and a schema describes JSON bodies |

## What to remember

- A schema is a named field list that other definitions refer to by name. It is compiled once, in a generic mode, and shared.
- Through a reference, constraints and allowed keys are enforced. `required`, defaults, `read_only` and `write_only` are not.
- A nested value is stored filled out to the schema's full shape and replaced as a whole on update.
- A schema that refers to itself, directly or through others, makes every request to the environment fail until a schema in the cycle is deleted.
- Deleting or renaming a schema in use is not blocked, and breaks every resource that uses it.
- Removing a key from a schema fails reads of every row that has the structure, including rows that stored the key as `null`.
- Route `input_schema` does not enforce `required`, `response_schema` does not filter, and a flow's `validate.schema` block cannot resolve a reference.
- Promotion copies schemas by name and never deletes one.

## Questions that come up

<AccordionGroup>
  <Accordion title="Why is required ignored inside my schema?">
    A schema is compiled once in a generic mode that treats every key as optional, because it is shared by create bodies, update bodies and responses. Constraints and the set of allowed keys are enforced. `required`, `default`, `read_only` and `write_only` are not. Use an inline `object` or a route with `input_fields` when you need them enforced.
  </Accordion>
  <Accordion title="Can a schema refer to itself for a tree?">
    No. A schema that refers to itself, directly or through other schemas, makes every request to the environment fail with a `500` until a schema in the cycle is deleted. Model trees as a resource with a `parent_id`, see [Relations](/data/relations).
  </Accordion>
  <Accordion title="Can I use one schema for both a resource and a route?">
    Yes. A `ref` field names it in both, and a route can also take it as `input_schema` or `response_schema`. The same rules apply in each place: constraints enforced, `required` not.
  </Accordion>
  <Accordion title="Why does my response_schema not remove fields?">
    It documents the response and does not filter it. The route and its flow decide what is sent. Use a flow that builds the body, or a transformer on the route.
  </Accordion>
  <Accordion title="What happens if I delete a schema that is in use?">
    The delete succeeds. Every resource that referenced it stops being served (`404`) and is listed under **Definitions with problems** on **Overview**. Recreating a schema with the same name restores them, since references are by name.
  </Accordion>
  <Accordion title="Can I rename a schema?">
    Studio does not allow it. The API accepts a `PUT` with a different name and renames the schema in place, and nothing updates the fields that named it. To rename safely, create the new schema, point every use at it, then delete the old one.
  </Accordion>
  <Accordion title="Do schemas appear in a flow's validate.schema block?">
    No. The block takes a field list inline and cannot resolve a `ref`. Write the nested fields inline as an `object`.
  </Accordion>
  <Accordion title="Are schemas copied when I promote an environment?">
    Yes, by name, as an upsert. A schema deleted in the source is not deleted in the target, and promoting does not create tables.
  </Accordion>
  <Accordion title="Why does a row fail to read after I removed a key from a schema?">
    A referenced schema rejects keys it does not declare, on reads as well as writes. A row that still holds the removed key fails the response model. Add the key back, or rewrite the stored JSON, then remove it.
  </Accordion>
  <Accordion title="Can two schemas have the same name as a resource?">
    Names are separate namespaces in Studio, but they share the API document's component list. Use `PascalCase` for schemas so they do not collide with the resource names, which are lowercase.
  </Accordion>
  <Accordion title="Is there a limit on how deep schemas can nest?">
    None was reached. A three-level chain validated and located errors correctly. Deep structures get hard to read in error paths and in stored JSON, so keep them shallow.
  </Accordion>
</AccordionGroup>

## Terms used on this page

| Term | Meaning here |
