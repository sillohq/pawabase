## Overview

Pawabase automatically generates three Pydantic models for each resource: the create model, the update model, and the read model. These models are compiled from the resource's field definitions at request time.

The models determine what the API accepts in request bodies and what it returns in responses. They are the bridge between the resource definition and the runtime behavior.

## Create model

The create model is used for POST /rest/v1/<name> requests. It requires all fields marked required: true in the resource definition. Fields with default values are treated as having the default if omitted.

The create model rejects unknown fields (extra="forbid") and validates all constraints including patterns, enums, ranges, and array element types.

write_only fields are accepted in the create model but are never returned in the response. This allows sensitive data like internal costs or passwords to be submitted without being exposed.

## Update model

The update model is used for PATCH /rest/v1/<name>/{id} requests. Unlike the create model, every field is optional in the update model because a PATCH request by definition only contains the fields being changed.

The update model also rejects unknown fields and validates all constraints for the fields that are present.

## Read model

The read model determines the shape of responses for GET /rest/v1/<name> and GET /rest/v1/<name>/{id}. write_only fields are excluded from the read model entirely.

The read model includes all non-write_only fields from the resource definition, plus any computed or transformed fields added by the transformer.

## Model compilation

Models are compiled at request time and cached per environment version. When you save a resource definition, the platform bumps the version counter and the next request triggers recompilation.

The compilation process generates Pydantic models from the field definitions. Unknown fields are rejected. Required fields are enforced. Constraints are validated.

## Inspecting models

You can inspect the compiled models using the API reference tab in Studio. The compiled OpenAPI document shows the exact request and response schemas for every endpoint.

The platform API also exposes the compiled schemas programmatically. You can retrieve the create, update, and read models for any resource using the platform API.

## Custom model behavior

The transformer function can modify the read model's output. This allows you to add computed fields, format dates, or hide implementation details without changing the resource definition.

## Validation model errors

When a request body does not match the model, the platform returns 422 Unprocessable Entity with a detailed error object. The error object identifies each field that failed validation and the reason for the failure.
