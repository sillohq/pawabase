## Overview

Two related but distinct things share the word "schema" in Pawabase, and it's worth separating them before going further:

1. **A reusable Schema** is a named, saved field list — a Studio entity, created under an environment's **Schemas** section, that you can point `ref`-type fields at from any Resource or from another Schema. This is Pawabase's mechanism for sharing one shape (an address, a line item, a money amount) across several places instead of repeating the field list.
2. **A compiled model** is the Pydantic model Pawabase generates, on the fly, from a field list — a Resource's own `fields`, a reusable Schema's `fields`, or a custom route's `input_fields`. Every field list, wherever it comes from, goes through the same compiler.

This page is about the compiler and about reusable Schemas: what models get generated, how `ref` fields resolve, and the one asymmetry (`read_only` vs `write_only`) that's easy to get backwards.

## What gets compiled, and when

For every Resource, Pawabase compiles up to three models from its `fields`, one per mode:

- **create** — the request model for `POST /rest/v1/<name>`.
- **update** — the request model for `PATCH /rest/v1/<name>/{id}`.
- **read** — the response model for `GET` requests and for what `create`/`update` return.

There's a fourth mode, **any**, used when validating a field list generically — for example, a reusable Schema is compiled in `any` mode when the platform needs to check that it compiles at all, without picking a create/update/read perspective.

Compilation happens when the environment's compiled application is (re)built — after you save a definition and the version counter bumps, the next request rebuilds it — not on every request. The compiled models are what Sillo uses as `request_model`/`response_model` on the generated routes, so the same models drive request validation, response shaping, and the OpenAPI document all at once: there's no separate "docs" schema that could drift from what's actually enforced.

## The four modes, precisely

| Mode | Used for | `required` enforced? | Extra/unknown fields | Fields made optional |
| --- | --- | --- | --- | --- |
| `create` | `POST` request body | Yes (unless `default` is set) | Rejected (422) | No — required fields stay required |
| `update` | `PATCH` request body | No — every field becomes optional | Rejected (422) | Yes, all fields |
| `read` | Response body | N/A (not a request) | N/A | Yes, all fields (nullable) |
| `any` | Generic validation (e.g. compiling a Schema to check it's well-formed) | No | Rejected (422) | Yes, all fields |

In every mode, a field with `enum` set is compiled as a fixed `Literal` of those values regardless of its declared `type`, and every model rejects unknown properties — none of the four modes silently ignores a field the client sent that isn't in the definition.

## The `read_only` / `write_only` asymmetry

These two properties look like mirror images and are easy to swap by mistake. They are not symmetric in *which* models they affect:

- **`read_only` fields are skipped in `create` and `update` mode** — they don't exist in the compiled request model at all. A client cannot set a `read_only` field no matter what it sends; if it tries, the extra-field rejection in `create`/`update` mode rejects the request outright (since `read_only` fields are absent from those models, sending one counts as an unknown field). `read_only` fields **are** included in `read` mode, so they show up in responses normally.
- **`write_only` fields are skipped in `read` mode only** — they're present and settable in both `create` and `update`, but never appear in a response.

So the two properties are gated by different, non-overlapping mode checks:

```
mode in ("create", "update") and read_only  → field is dropped from the model
mode == "read" and write_only               → field is dropped from the model
```

A field can't usefully be both — marking a field `read_only` and `write_only` together drops it from every mode (it would never be settable and never be visible), which is almost certainly not what you want; Pawabase doesn't reject this combination, but it has no useful effect.

Use `read_only` for anything the server computes or owns — a timestamp, a status the platform manages, the primary key (which Pawabase marks `read_only` for you automatically; you never declare it yourself). Use `write_only` for anything the client legitimately sends but that shouldn't be echoed back — a one-time activation code, an internal cost figure a customer-facing response shouldn't include.

```json
{"name": "id", "type": "integer", "read_only": true}
```

```json
{"name": "internal_cost_cents", "type": "integer", "write_only": true}
```

With the second field, a `POST` can include `internal_cost_cents` and it will be stored, but no `GET` response — not `list`, not `get`, not the body returned from the `create` call itself — will ever contain it.

## Reusable Schemas

A Schema is a named field list saved independently of any one Resource, under **Schemas** in Studio for a given environment. It exists for two purposes:

1. **Shared shapes across Resources**, via `ref`-type fields (see [Field types](/data/field-types)):

```json
// Schema "address"
{"name": "address", "fields": [
  {"name": "line1", "type": "string", "required": true},
  {"name": "city", "type": "string", "required": true},
  {"name": "postal_code", "type": "string"}
]}
```

```json
// Resource "orders" field
{"name": "billing_address", "type": "ref", "schema": "address"}
```

```json
// Resource "customers" field
{"name": "shipping_address", "type": "ref", "schema": "address"}
```

Both `orders.billing_address` and `customers.shipping_address` validate against the same `address` shape, defined once. Edit the `address` Schema and both Resources pick up the change the next time the environment recompiles.

2. **Custom route input/response shapes.** A custom route (defined outside Resources, under Routes) can name `input_schema`/`response_schema` pointing at a saved Schema instead of, or alongside, its own inline `input_fields`. If a route names a schema that doesn't exist in the environment, saving the route is rejected outright — this is checked against the same registry `ref` fields resolve against.

### How the registry is built

When an environment's compiled state is (re)built, every Schema in that environment is compiled once, together, into a *registry*: a `{name: compiled_model}` map. Schemas are compiled in dependency order as much as possible, and a Schema that references another (via a `ref` field) resolves against that same registry — so Schemas can reference each other, not just be referenced by Resources.

**A broken Schema doesn't take the whole environment down.** If one Schema fails to compile — an unknown `ref` target, an invalid `pattern`, a duplicate field name — it's left out of the registry and reported as a problem rather than raising immediately. Everything else that doesn't depend on it keeps working. A Resource field that `ref`s the broken Schema will itself fail to compile and that Resource is skipped and reported the same way, but unrelated Resources and Schemas are unaffected. These problems surface in Studio and in the environment's compiled-state diagnostics, so a mistake in one Schema is visible and scoped, not a full outage.

### `ref` resolution failure

If a field's `schema` names something not present in the registry — a typo, or a Schema deleted after something started `ref`-ing it — that field fails to compile with an error naming the missing Schema, and (per the paragraph above) that failure is scoped to whatever was trying to use it.

## Nesting: `object` vs `ref`

Both let a field hold a structured sub-shape; the difference is reuse and origin:

- **`object`** fields carry their `fields` list inline, right there in the Resource or Schema definition. It's private to that one field — nothing else can reference it. Good for a shape that's genuinely local to one field.
- **`ref`** fields point at a Schema that exists independently and can be `ref`-ed from multiple places. Good for a shape you expect to reuse, or one large/important enough to want a single source of truth for.

Both compile identically underneath — `object` compiles its inline `fields` into an anonymous nested model on the spot; `ref` compiles (or reuses an already-compiled) named model from the registry. Nesting composes freely across both: an `object` field can contain a `ref` field, a Schema can have a field that is itself an `array` of `ref`, and so on, to whatever depth the data actually needs.

```json
{
  "name": "line_items",
  "type": "array",
  "items": {"type": "ref", "schema": "order_line_item"}
}
```

## Inspecting compiled schemas

The generated OpenAPI document — visible at `/docs` for the compiled environment, and readable in full through the platform API — is the authoritative view of exactly what every compiled model accepts and returns, per operation, including every constraint from every field. Because Sillo generates the document directly from the same models it validates against, there is no separate "documentation schema" that can drift from enforcement: what you read in the docs is what's checked on the wire.

## Validation errors

A request body that fails against a compiled model returns `422 Unprocessable Entity` with a structured error body identifying each offending field, its location, and the reason (Pydantic's own validation error detail, reshaped into the response). A `ref` to a Schema that failed to compile, or a Resource that references a broken Schema, surfaces as a compiled-state problem rather than a per-request validation error — those are two different failure points: one is "the shape of *this request* is wrong," the other is "the environment's *definitions* don't compile."
