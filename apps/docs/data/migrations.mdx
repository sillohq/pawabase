Resource definitions describe the API. **Migrating** makes the database match, additively.

## Running a migration

- Studio: open the resource → **Create / migrate table**.
- API: `POST /platform/v1/projects/{ref}/envs/{env}/resources/{name}/migrate`.

The response lists the statements that ran:

```json
{ "table": "grades", "created": false, "statements": ["ALTER TABLE grades ADD COLUMN remarks VARCHAR(240)"] }
```

## What migrate does

| Situation | Action |
| --- | --- |
| Table doesn't exist | `CREATE TABLE` with the primary key, every field and the timestamps |
| New field in the definition | `ALTER TABLE … ADD COLUMN` |
| Field removed from the definition | **nothing**: the column stays and is ignored by the API |
| Field type changed | **nothing**: the column keeps its type |
| Constraints changed (`max_length`, `enum`…) | **nothing** in the database; enforced by validation |

Migrate never drops, renames or rewrites columns, never deletes data, and is safe to run repeatedly.

## Changes migrate won't make

For destructive or transforming changes, use your normal database tooling, then align the definition:

<Steps>
  <Step title="Change the database">
    ```sql
    ALTER TABLE students RENAME COLUMN dob TO date_of_birth;
    ```
  </Step>
  <Step title="Update the resource">Rename the field in the definition to match.</Step>
  <Step title="Update dependents">Flows, transformers and policies that mention the old name.</Step>
</Steps>

<Tip>
Use the **Database** console (`POST …/database/query`) to inspect the live schema. It's read-only unless you explicitly allow writes, and writes are audited. See [database console](/data/database-console).
</Tip>

## Across environments

Promotion copies definitions, not schemas. After promoting, migrate each changed resource in the target environment, typically from CI:

```bash
for r in students invoices grades; do
  curl -X POST "$STUDIO/studio/api/platform/projects/school/envs/production/resources/$r/migrate" …
done
```

## Platform migrations

Pawabase's **own** databases (platform state and Akountz) are migrated automatically when containers start (Sillo Record migrations). Set `PAWABASE_MIGRATE=false` to run them yourself with `docker compose run --rm api migrate`. See [upgrades](/self-hosting/upgrades).
