## Overview

Fields are compiled into Pydantic models, so a field's type decides validation, serialization, the OpenAPI schema, and on migrate the column type in the database. Every field type is available across all four places where types matter: the validation model, the read model, the OpenAPI document, and the database column.

This page covers every type, its constraints, its JSON shape, its SQL column, and the subtle differences between types that look similar at first glance.

## The fourteen types at a glance

| Type | JSON representation | Validates | Typical column | Notes |
| --- | --- | --- | --- | --- |
| `string` | string | length, pattern, allowed values | VARCHAR(255) default | The default type when omitted |
| `text` | string | length | TEXT | For longer content |
| `integer` | number (integer) | range, allowed values | INTEGER default | Whole numbers only |
| `number` | number (float) | range | DOUBLE PRECISION default | Decimal numbers |
| `boolean` | true/false | — | BOOLEAN | Stored as true/false |
| `datetime` | ISO-8601 string | A valid timestamp | TIMESTAMP | Includes timezone info |

## String fields

String fields validate as strings and create VARCHAR(n) columns in the database. They support max_length, pattern, and enum constraints.

The max_length constraint limits the maximum number of characters. If a client sends a string longer than max_length, validation fails with a 422 error.

The pattern constraint enforces a regular expression match. The pattern is applied using Python's re.match function. If the client sends a value that does not match, validation fails.

The enum constraint restricts the field to a specific set of string values. The enum list must contain at least one value. If the client sends a value not in the list, validation fails.

String fields are the most commonly used field type because they can represent names, identifiers, codes, descriptions, and any textual data.

When using enum with string fields, consider whether the values might change over time. Adding new enum values requires updating the resource definition and running a migration.

## Number fields

Number fields validate as floating-point numbers and create DECIMAL/NUMERIC columns. They support minimum and maximum constraints.

Number fields are used for monetary amounts, measurements, scores, and any data that requires fractional precision. The platform uses Python's Decimal type for validation to avoid floating-point precision issues.

The minimum and maximum constraints are inclusive. A value equal to minimum or maximum is considered valid.

Number fields can represent very large or very small values depending on the database column type.

## Integer fields

Integer fields validate as whole numbers and create INTEGER/BIGINT columns. They support minimum and maximum constraints.

Integer fields are used for counts, quantities, identifiers, and any data that does not require fractional precision.

Integer fields are also used as foreign key references between resources. When a relation references an integer field, the platform ensures type compatibility.

## Boolean fields

Boolean fields validate as true or false values and create BOOLEAN columns. They do not support any additional constraints.

Boolean fields are used for flags, toggles, and status indicators. They are often used with default to provide an initial value.

Boolean fields are efficient for filtering because the database can quickly compare true or false values.

## Date fields

Date fields validate as YYYY-MM-DD strings and create DATE columns. They do not support additional constraints beyond type validation.

Date fields are used for birthdays, due dates, deadlines, and any data that represents a calendar date without a time component.

## Datetime fields

Datetime fields validate as ISO 8601 strings and create TIMESTAMP columns. They support both date-only and datetime-only strings.

When a datetime string includes a timezone offset, the platform preserves it.

## Array fields

Array fields validate as arrays of items and create TEXT[] or JSONB columns. The items property defines the type of each element.

Array fields are used for tags, lists, multiple selections, and any data that represents a collection of values.

Array fields can be filtered using the filter[<field>] parameter. The platform supports checking if an array contains a specific value.

## Choosing the right type

Always choose the most specific type that fits your data. Using string for numeric data means you lose range validation and the correct database column type.

Use integer for counts and identifiers, number for measurements and amounts, boolean for flags, date for calendar dates, and datetime for timestamps.

Use array for collections of values that share the same type. Avoid using arrays for heterogeneous data — consider a separate resource instead.

## Type constraints reference

| Constraint | Applies to | Meaning |
| --- | --- | --- |
| `max_length` | string | Maximum number of characters |
| `pattern` | string | Regular expression match |
| `enum` | string | Allowed values |
| `minimum`/`maximum` | number, integer | Range bounds |
| `items` | array | Type of array elements |

## Type migration considerations

When you change a field type, the platform updates the validation model immediately. The database column type may also need to change, which requires running a migration.

Some type changes are safe and automatic (e.g., changing max_length on a string field). Others require a manual migration (e.g., changing from integer to number).
