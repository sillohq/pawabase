## Overview

Every field you add to a Resource or a reusable Schema in Studio — a text box, a number, a toggle, a nested object — declares a `type`. That single value decides four things at once, because Pawabase compiles the same field definition into all four places where types matter:

1. **The validation model.** Pawabase compiles your fields into a Pydantic model. The type picks the Python type the incoming JSON value is checked against (`str`, `int`, `float`, `dt.datetime`, and so on).
2. **The response shape.** The same field, compiled in "read" mode, decides what a client sees back in JSON.
3. **The OpenAPI document.** Whatever Pydantic types the model, Atlas (Pawabase's generated docs) describes — so the schema you configure in Studio is exactly the schema published at `/docs`.
4. **The database column.** When you run a migration, the field's type picks a column type for the dialect your environment's database uses (SQLite, PostgreSQL, or MySQL).

This page documents all fourteen types precisely as Pawabase implements them, including two places where it's easy to guess wrong: `number` fields validate as ordinary IEEE-754 floats (not a fixed-point decimal), and every structured type — `array`, `object`, `json`, and `ref` — stores as a single JSON/JSONB/TEXT column, never a native array or composite column type.

## The fourteen types at a glance

| Type | Python/validation type | JSON shape | Column (sqlite / postgres / mysql) |
| --- | --- | --- | --- |
| `string` | `str` | string | `TEXT` / `VARCHAR(n)` / `VARCHAR(n)` |
| `text` | `str` | string | `TEXT` / `TEXT` / `TEXT` |
| `integer` | `int` | number (integer) | `INTEGER` / `BIGINT` / `BIGINT` |
| `number` | `float` | number | `REAL` / `DOUBLE PRECISION` / `DOUBLE` |
| `boolean` | `bool` | `true` / `false` | `INTEGER` / `BOOLEAN` / `BOOLEAN` |
| `datetime` | `dt.datetime` | ISO-8601 string | `TEXT` / `TIMESTAMPTZ` / `DATETIME(6)` |
| `date` | `dt.date` | `YYYY-MM-DD` string | `TEXT` / `DATE` / `DATE` |
| `uuid` | `uuid.UUID` | string | `TEXT` / `UUID` / `CHAR(36)` |
| `email` | `str` (pattern-checked) | string | `TEXT` / `VARCHAR(320)` / `VARCHAR(320)` |
| `url` | `str` (pattern-checked) | string | `TEXT` / `TEXT` / `TEXT` |
| `json` | `Any` | any JSON value | `TEXT` / `JSONB` / `JSON` |
| `array` | `list[...]` | JSON array | `TEXT` / `JSONB` / `JSON` |
| `object` | nested model | JSON object | `TEXT` / `JSONB` / `JSON` |
| `ref` | referenced Schema's model | JSON object | `TEXT` / `JSONB` / `JSON` |

If you omit `type` on a field, it defaults to `string`.

<Note>
`array`, `object`, `json`, and `ref` are collectively the platform's **JSON types**. All four are stored the same way: as a single JSON/JSONB/TEXT column, encoded with `json.dumps` on the way in and `json.loads` on the way out. There is no native array column (`TEXT[]`, PostgreSQL arrays) and no composite/row column anywhere in Pawabase. If you need to filter or index on one element of an array or one key of an object, model it as its own field or its own related Resource instead.
</Note>

## String-like types

### `string`

The default type. Validates as a Python `str` with no length limit unless you set one.

```json
{"name": "title", "type": "string", "required": true, "max_length": 200}
```

- `max_length` — maximum characters. A longer value fails validation with a 422.
- `min_length` — minimum characters.
- `pattern` — a regular expression the value must fully match (compiled with Python's `re`; invalid patterns are rejected when you save the field, not at request time).
- `enum` — a list of allowed values. When `enum` is set, the field's underlying type is overridden entirely: Pawabase compiles it as a `Literal` of exactly those values, regardless of what `type` says. This is the only way to restrict a field to a fixed set of choices — there is no dedicated "enum" or "select" type.

Column: `VARCHAR(n)` on PostgreSQL and MySQL, where `n` is `max_length` if set or `255` otherwise (the column width is fixed at migration time from whatever `max_length` was set then — raising `max_length` later does not widen an existing column; see [Migrations](/data/migrations)). SQLite has no length-limited text type, so it's always `TEXT` regardless of `max_length` — SQLite still enforces the length limit at the application layer during validation, it just doesn't enforce it in the column itself.

### `text`

Identical validation to `string` (a plain `str`, honoring the same `max_length`, `min_length`, `pattern`, and `enum` constraints) but always stored as `TEXT` on every dialect, never a bounded `VARCHAR`. Use it for content you don't want an arbitrary column-width ceiling on: descriptions, notes, article bodies, HTML fragments.

```json
{"name": "body", "type": "text", "required": false}
```

### `email`

A `str` that must match `^[^@\s]+@[^@\s]+\.[^@\s]+$` — a deliberately loose email shape check, not full RFC 5321 validation. It does **not** verify the address exists or is deliverable. If you supply your own `pattern`, it overrides this default; otherwise the email pattern applies automatically.

```json
{"name": "contact_email", "type": "email", "required": true}
```

Column: `VARCHAR(320)` on PostgreSQL/MySQL (320 is the maximum theoretical email length), `TEXT` on SQLite.

### `url`

A `str` that must match `^https?://[^\s]+$`. Only `http://` and `https://` schemes pass; anything else (`ftp://`, `mailto:`, a bare domain with no scheme) fails validation. As with `email`, an explicit `pattern` on the field overrides this default.

```json
{"name": "website", "type": "url"}
```

Column: `TEXT` on every dialect — URLs have no natural bound and PostgreSQL/MySQL gain nothing from `VARCHAR` here.

## Numeric types

### `integer`

Validates as a Python `int`. JSON numbers with a fractional part (`1.5`) are rejected — Pydantic does not silently truncate.

```json
{"name": "quantity", "type": "integer", "required": true, "minimum": 1}
```

- `minimum` / `maximum` — inclusive bounds, compiled to Pydantic's `ge` / `le`.

Column: `INTEGER` on SQLite, `BIGINT` on PostgreSQL and MySQL. There is no separate "small integer" or "big integer" type to choose in Studio — every integer field gets the same column width per dialect.

<Warning>
An `integer` primary key is declared `INTEGER PRIMARY KEY AUTOINCREMENT` (SQLite), `BIGSERIAL PRIMARY KEY` (PostgreSQL), or `BIGINT AUTO_INCREMENT PRIMARY KEY` (MySQL) — the database assigns the value. A non-key `integer` field has no such generator; if you want one you populate it yourself (in a create request, a flow, or a default).
</Warning>

### `number`

Validates as a Python `float`. **This is the fact most worth getting right: `number` is an ordinary IEEE-754 double-precision float, not a fixed-point decimal.** Pawabase does not use Python's `Decimal` anywhere in the compiled model or the value codec — the field compiles to `float`, and the value that comes back out of the database is coerced to `float` as well (even the rare case of a driver returning a `Decimal` is converted straight to `float` on the way out).

```json
{"name": "amount", "type": "number", "minimum": 0}
```

For money, this has a real consequence: floats cannot represent every decimal fraction exactly, so repeated arithmetic on `number` fields can accumulate rounding error. The common workaround is to store money as an `integer` count of the smallest unit (cents, not dollars) rather than as a `number` of dollars — `amount_cents: 1999` instead of `amount: 19.99`. This sidesteps floating-point rounding entirely because integers are exact.

Column: `REAL` (SQLite), `DOUBLE PRECISION` (PostgreSQL), `DOUBLE` (MySQL) — all binary floating-point, consistent with the `float` validation type. There is no `DECIMAL`/`NUMERIC` column type available for `number` fields in Pawabase today.

## Boolean

### `boolean`

Validates as `True`/`False`. No additional constraints apply (`minimum`, `maximum`, `pattern`, and `enum` are meaningless here and are simply ignored by the compiler if present).

```json
{"name": "is_published", "type": "boolean", "default": false}
```

Column: `INTEGER` (0/1) on SQLite — SQLite has no native boolean column type, so the value layer encodes `True`/`False` to `1`/`0` on the way in and decodes back to a real Python `bool` on the way out, so API responses always show `true`/`false`, never `1`/`0`. PostgreSQL and MySQL use a genuine `BOOLEAN` column.

## Temporal types

### `date`

Validates as a Python `date` from a `YYYY-MM-DD` string. No time-of-day component.

```json
{"name": "due_on", "type": "date"}
```

`minimum` / `maximum` compile to `ge`/`le` on the underlying `date`, so you can bound a date field to a range the same way you bound a number.

Column: stored as an ISO date string (`TEXT`) on SQLite, a native `DATE` on PostgreSQL and MySQL.

### `datetime`

Validates as a Python `datetime`, parsed from an ISO-8601 string. Pawabase normalizes every `datetime` value to UTC before it reaches the database: a timestamp you send with no timezone is assumed to be UTC and stamped with it; one with an explicit offset is converted to UTC. On MySQL, which has no timezone-aware column type, the UTC value is stored with its timezone info stripped (the column itself carries no offset, but every value in it is understood to be UTC by convention).

```json
{"name": "published_at", "type": "datetime"}
```

Column: ISO string (`TEXT`) on SQLite, `TIMESTAMPTZ` on PostgreSQL, `DATETIME(6)` (microsecond precision, timezone-naive) on MySQL.

`created_at` and `updated_at`, when a Resource has `timestamps: true` (the default — see [Defining resources](/data/defining-resources)), are ordinary `datetime` fields maintained by the platform: set on `create`, and `updated_at` refreshed on every `update`.

### `uuid`

Validates as a Python `uuid.UUID`, accepting any of the standard UUID string forms.

```json
{"name": "external_ref", "type": "uuid"}
```

Column: `TEXT` (SQLite), native `UUID` (PostgreSQL), `CHAR(36)` (MySQL).

<Warning>
When a Resource's `id_type` is `uuid`, Pawabase does **not** rely on a database-side default (there is no `gen_random_uuid()` or equivalent in the generated DDL). The primary key column is declared as a plain `UUID`/`TEXT`/`CHAR(36)` `PRIMARY KEY` with no default, and the value is generated in Python — with `uuid.uuid4()` — at the moment a record is created, then inserted explicitly along with the rest of the row. This means UUID generation works identically across all three dialects, including SQLite and MySQL, neither of which has a built-in random-UUID function.
</Warning>

## Structured (JSON) types

These four types all compile to `TEXT`/`JSONB`/`JSON` — never a native array or object column — and are all encoded with `json.dumps(value, default=str)` going in and decoded with `json.loads` coming out.

### `json`

An escape hatch: any JSON-serializable value, unconstrained. Validates as Python's `Any` — Pawabase performs no shape checking on it at all beyond "this is valid JSON".

```json
{"name": "metadata", "type": "json", "default": {}}
```

Use `json` when a field's shape genuinely varies per record and you don't want to model it. Prefer `object` (below) whenever the shape is actually fixed — you get real validation and an accurate OpenAPI schema instead of an opaque blob.

### `array`

A JSON array whose elements are described by `items` — itself a field-like spec (it takes a `type` and that type's own constraints, but never a `name`; the compiler assigns it one internally).

```json
{"name": "tags", "type": "array", "items": {"type": "string", "max_length": 40}}
```

```json
{"name": "scores", "type": "array", "items": {"type": "integer"}}
```

If you omit `items` entirely, elements default to `json` (i.e., an array of anything).

Arrays can be nested (an array of arrays) and can hold `object` or `ref` items. There is no minimum/maximum element-count constraint available on `array` itself.

<Warning>
Because the whole array is one JSON column, you cannot filter on "array contains value" through the standard `filter[field]=...` query parameter the way you can filter a scalar column — filtering matches the encoded column value, not an individual element. To query by membership, run SQL through the [Database console](/data/database-console) using your dialect's native JSON functions (`json_each` on SQLite, `@>`/`jsonb_array_elements` on PostgreSQL, `JSON_CONTAINS` on MySQL), or model the relationship as a separate Resource with a `belongs_to`/`has_many` relation instead of an array.
</Warning>

### `object`

A JSON object with a fixed, validated shape, described by a nested `fields` list — the same field-definition syntax as a Resource's top-level `fields`, recursively.

```json
{
  "name": "address",
  "type": "object",
  "fields": [
    {"name": "line1", "type": "string", "required": true},
    {"name": "city", "type": "string", "required": true},
    {"name": "postal_code", "type": "string"}
  ]
}
```

Each nested field gets its own compiled Pydantic model (named after the parent field), so `required`, `enum`, `pattern`, `read_only`, and every other field property apply at any nesting depth. Nesting can go arbitrarily deep — an `object` field can itself contain fields of type `object` or `array` of `object`.

### `ref`

Points at a reusable [Schema](/data/schemas) defined in the same environment, by name, via the `schema` property (required — a `ref` field with no `schema` is rejected when you try to save it).

```json
{"name": "billing_address", "type": "ref", "schema": "address"}
```

This is how you share one shape (an address, a line item, a money amount) across several Resources or Schemas without repeating the field list everywhere. See [Schemas](/data/schemas) for how the reference is resolved and what happens if the named Schema doesn't compile.

## Constraints reference

Not every constraint applies to every type. Constraints outside a type's supported set are silently ignored by the compiler rather than rejected — so a typo (setting `maximum` on a `string` field, say) will not surface as a save-time error; it just does nothing.

| Constraint | Applies to | Effect |
| --- | --- | --- |
| `required` | any type | Enforced only on create; a create request missing the field fails with a 422 unless `default` is set |
| `default` | any type | Value substituted when the field is absent on create; also makes the field effectively optional even if `required: true` |
| `nullable` | any type | Whether `null` is an accepted value; defaults to `true` for optional fields and `false` for required ones, and is forced `true` regardless on update/read responses |
| `enum` | any type, typically `string` | Overrides the field's type entirely with a fixed `Literal` of allowed values |
| `pattern` | `string`, `text`, `email`, `url` | Regex the value must match (auto-set for `email`/`url` if you don't supply one) |
| `min_length` / `max_length` | `string`, `text`, `email`, `url` | Character-count bounds |
| `minimum` / `maximum` | `integer`, `number`, `date`, `datetime` | Inclusive value bounds |
| `items` | `array` | Field spec describing each element |
| `fields` | `object` | Nested field list |
| `schema` | `ref` | Name of the referenced Schema |
| `description` | any type | Shown in the OpenAPI document |
| `example` | any type | Shown in the OpenAPI document as a sample value |
| `read_only` | any type | Excluded from create/update request bodies; included in read responses |
| `write_only` | any type | Accepted in create/update request bodies; excluded from read responses |
| `indexed` | any type | An index is created for this column the next time you migrate |
| `unique` | any type | A unique index is created for this column the next time you migrate |

`read_only`, `write_only`, `indexed`, and `unique` are covered in depth in [Defining resources](/data/defining-resources) and [Migrations](/data/migrations), since they affect the compiled request/response models and the generated DDL rather than validation itself.

## Choosing between similar-looking types

**`string` vs `text`.** Same validation. Choose `text` for content with no natural length ceiling (article bodies, free-form notes); choose `string` when you want the platform to cap length at the database layer via `max_length` (on PostgreSQL/MySQL — SQLite enforces it only at validation time either way).

**`number` vs `integer`.** If the value should never have a fractional part — a count, an ID, a quantity — use `integer`; you get exact arithmetic and no accidental `1.0` where you expected `1`. Reach for `number` only for genuinely fractional values, and remember it's a binary float, not a decimal — for money, an `integer` count of the smallest currency unit is usually the safer choice than a `number` of major units.

**`json` vs `object`.** `object` gives you real validation, a real OpenAPI schema, and lets nested fields be `required`, `read_only`, etc. `json` validates nothing. Use `object` whenever the shape is actually known ahead of time; reserve `json` for genuinely free-form data (arbitrary client-supplied metadata, a webhook payload you're storing verbatim).

**`array` vs `ref` to a Schema with `type: object` items, vs a related Resource.** An `array` of scalars (tags, numeric scores) is fine as-is. An array of structured items (line items on an order) is better modeled as `array` with `items: {"type": "ref", "schema": "..."}` if the item shape is reused elsewhere, or `items: {"type": "object", "fields": [...]}` if it's local to this one field. If the "items" need their own identity, their own lifecycle (created, updated, deleted independently), or need to be queried/filtered on their own, model them as a separate Resource with a `has_many` relation instead — see [Defining resources](/data/defining-resources).
