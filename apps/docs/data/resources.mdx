## The Mental Model

If you have worked with Rails, Django REST Framework, Supabase, Firestore, or any Laravel-style resource layer, a Pawabase resource will feel familiar with one fundamental architectural difference: nothing is inferred from the database schema. A resource is a declaration you write — fields, operations, policies — and the platform compiles it into routes, validation models, and database columns. The table follows the definition, not the other way around.

This means you can prototype an API against a fresh SQLite database and then point the same resource definition at a production Postgres instance that already has a schema from a legacy system, an ETL pipeline, or a data warehouse export, without changing a single line of the definition. The separation of the definition layer from the database layer is the single most important architectural decision in Pawabase because it is what makes the platform feel like a product rather than a framework.

If you know Rails, the Pawabase equivalent is one resource definition replacing a model plus a serializer plus a controller plus a routes file. If you know Supabase, the equivalent is one resource definition where the table and the policies are separate concerns. If you know Firestore, the equivalent is one resource definition minus the client-side query-shape constraints.

The definition is stored as data — a row in Pawabase's own control-plane database, under your project and environment. This is what lets Studio edit it with forms and dropdowns, the platform API create it with curl, and environment promotion copy it between environments without regenerating any code.

## The Five Operations

Every resource exposes up to five operations under /rest/v1/&lt;name&gt;. Each operation is independently enabled and governed by its own policy. Nothing is public by default — an operation does not exist until explicitly enabled, and every enabled operation requires a policy.

| Operation | HTTP Verb | Route | Notes |
| --- | --- | --- | --- |
| `list` | GET | `/rest/v1/&lt;name&gt;` | Filters, sort, pagination, select, expand |
| `get` | GET | `/rest/v1/&lt;name&gt;/{id}` | Single record. Supports expand |
| `create` | POST | `/rest/v1/&lt;name&gt;` | Body validated against create model. Returns 201 |
| `update` | PATCH | `/rest/v1/&lt;name&gt;/{id}` | Partial update. PUT is an alias |
| `delete` | DELETE | `/rest/v1/&lt;name&gt;/{id}` | Returns 204 No Content. Hard delete only |

## list — GET /rest/v1/&lt;name&gt;

The list operation returns a paginated collection of records matching the caller's filters and policy. It accepts six query parameters. The response always has the shape {data, page, per_page, total}. total counts rows matching both filters and the caller's policy. It comes back null only when a residual policy prevents exact counting.

```bash
curl "$GW/rest/v1/invoices?filter[status]=overdue&sort=-due_on&page=1&per_page=20&expand=payments" \
  -H "apikey: $PK" -H "Authorization: Bearer $TOKEN"
```

```json
{"data": [{"id": 44, "invoice_no": "INV-202600001", "student_id": 12, "amount": 210000, "balance": 60000, "status": "overdue", "due_on": "2026-09-01", "payments": [{"id": 91, "amount": 150000, "paid_on": "2026-08-20"}]}], "page": 1, "per_page": 20, "total": 7}
```

| Parameter | Default | Meaning | Limits |
| --- | --- | --- | --- |
| `page` | 1 | 1-indexed page number | >= 1 |
| `per_page` | 20 | Rows per page | 1-200 |
| `sort` | PK ascending | Comma-separated fields, `-` for descending | Must reference declared fields |
| `select` | Every declared field | Comma-separated fields; PK always added back | Column projection |
| `expand` | none | Comma-separated relation names | One level deep; unknown returns 400 |
| `filter[&lt;field&gt;]` | none | Any number of filter parameters | See filtering |

total is the count matching your filters and the policy's WHERE clause. It comes back null only when a residual policy prevents exact database-level counting. See policies -> pushdown for the exact rules governing when pushdown succeeds and when it falls back to row-by-row filtering.

## get — GET /rest/v1/&lt;name&gt;/{id}

Returns a single record with 200 OK. Returns 404 Not Found if the record does not exist or if the caller's get policy refuses it — deliberately indistinguishable so that a policy refusal never confirms a record's existence to someone who should not know it exists. id_type: integer ids that do not parse as digits also return 404 rather than 400.

## create — POST /rest/v1/&lt;name&gt;

The body is validated against the resource's create model before the policy or database ever run. If owner_field is set, it is stamped from the caller's identity, overwriting anything the client sent, after validation and before the policy check. Successful creates return 201 Created with the created record including server-assigned fields.

## update — PATCH /rest/v1/&lt;name&gt;/{id}

PATCH is a partial update: only fields present in the body are validated and written. The update model makes every field optional. PUT is registered as an alias but is not the documented spelling. The policy sees record as the row before the change and input as the submitted patch, enabling transition-aware policies.

## delete — DELETE /rest/v1/&lt;name&gt;/{id}

Returns 204 No Content on success. 404 if the row does not exist. 403/404 on policy refusal following the same signed-in/anonymous split. Deletes are hard deletes — there is no soft-delete flag baked into the platform.

## Anatomy of a Definition

| Group | Keys | What they control |
| --- | --- | --- |
| Identity | `name`, `description`, `table`, `primary_key`, `id_type` | URL segment, database table, id format |
| Shape | `fields` | Validation, serialization, column types |
| Access | `operations` | Which HTTP methods exist and who may use them |
| Graph | `relations` | belongs_to/has_many, ?expand= behavior |
| Behaviour | `owner_field`, `timestamps`, `events`, `realtime`, `transformer`, `cache_ttl`, `rate_limit`, `tags` | Side effects, performance, observability |

## id_type: integer or uuid

Exactly two options are enforced by the platform's request model (Literal["integer", "uuid"] — anything else is refused at save time with 422 Unprocessable Entity). Integer ids are auto-incremented by the database; UUIDs are server-generated v4 UUIDs. Integer ids are sequential and guessable; UUIDs have 122 bits of randomness making them practically unguessable.

|  | integer (default) | uuid |
| --- | --- | --- |
| How ids are assigned | Database auto-increments | Server generates v4 UUID |
| Shape in URLs | `44` | UUID string |
| Sequential / guessable | Yes | No |
| Column type on migrate | `INTEGER`/`BIGINT` | `UUID` or `VARCHAR(36)` |

## table and primary_key

table defaults to name and only needs setting when you want the API name and the database table name to differ. primary_key defaults to id. Both are validated identifiers matching ^[A-Za-z_][A-Za-z0-9_]{0,62}$ and are never exposed to API clients.

## Exposing an Existing Table

Three steps: (1) Set table to the existing table's name and primary_key to its key column. (2) Add fields matching columns you want to expose. (3) Skip migrate if the schema is managed elsewhere. Columns not declared are invisible to API clients even if they exist in the database.

This technique is the standard way to give an API surface to tables populated by ETL jobs, legacy applications, or data warehouse exports without duplicating or transforming the underlying data.

## Behaviour Flags

owner_field stamps the caller's identity on create. timestamps maintains created_at and updated_at. events emits &lt;name&gt;.created|updated|deleted. realtime publishes to resource:&lt;name&gt;. cache_ttl caches per-caller with tag-based invalidation. rate_limit caps requests per caller per window.

## What You Get for Free

Validation before policies and SQL. Typed responses and automatic OpenAPI entries. Server-maintained timestamps. Events with full record payloads. Cache invalidation on every write. Realtime publication. Rate limiting across all instances. Consistent error shapes. Policy pushdown into SQL. None of this is opt-in boilerplate — it is what defining a resource means.

## Resources vs Custom Routes

Resources cover CRUD with rules. Custom routes cover workflows: multiple rows, external calls, business rules, side effects. Use resources when the operation is 'a client sends a row, the system stores it, the system returns it.' Use custom routes when reading multiple rows, calling external services, walking decision trees, or writing to more than one table.

## Resources vs the Database Console

The database console runs SQL directly, bypassing resource definitions, validation, and policies entirely. Use it for one-off inspection, backfills, and debugging. Never use it as an API surface.

## Versioning and Compiled State

Every definition save bumps the environment's version counter. Compiled state is cached per version. The next request after a save triggers recompilation. Testing requires fresh requests. Promotion automatically gives the target environment a new version. The compilation cache also explains why total can appear null after a policy change.

## Troubleshooting

<AccordionGroup>
<Accordion title="A route returns 404 from the router, not a policy 404">
Check that the operation is enabled: true. A disabled operation is not a route at all. GET .../resources/&lt;name&gt;/openapi shows exactly which routes are compiled.
</Accordion>
<Accordion title="The API still behaves like the old definition after a save">
Compiled state is cached per environment version. Retry with a fresh request.
</Accordion>
<Accordion title="create returns 201 but a field is missing from the response">
Either the field is not declared in fields or it is write_only: true and intentionally never returned.
</Accordion>
<Accordion title="total is null on a list response">
A residual policy is active. See policies -> pushdown for what causes a residual.
</Accordion>
</AccordionGroup>

## FAQ

<AccordionGroup>
<Accordion title="Can a resource have more than five operations?">
No — list, get, create, update, delete is the complete set.
</Accordion>
<Accordion title="Can I rename a resource?">
Not in place. Create a new resource with table pointing at the old table.
</Accordion>
<Accordion title="Does deleting a resource definition delete the table?">
No — the table and all its data are untouched.
</Accordion>
<Accordion title="Do resources support soft delete?">
Not as a built-in flag. Model it with a status field and a policy.
</Accordion>
</AccordionGroup>
