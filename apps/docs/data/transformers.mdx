## The mental model: a function between the row and the response

A **transformer** takes the record the database returned and produces the record a consumer receives. It is a small, declarative function made of five steps, and it is stored as data, so Studio edits it and a promotion carries it between environments.

```text
row from the database  ──►  policy gate  ──►  transformer  ──►  JSON response
   (every column)          (who may see)     (what shape)
```

Three facts frame everything else on this page:

1. **It shapes the response. It does not secure the data.** A transformer decides which keys come back. It does not stop a caller from filtering on a key it hides, and it does not reach events, webhooks or realtime. [What a transformer protects](#what-a-transformer-protects-and-what-it-does-not) is the most important section here.
2. **It runs on the way out, after the policy.** The policy decides whether the caller may read the row at all. The transformer then decides what the row looks like.
3. **It has five steps in a fixed order.** You choose which of them to use. You do not choose their order.

| Step | Does | Studio label |
| --- | --- | --- |
| `omit` | Removes named keys | **1 · Omit fields** |
| `pick` | Keeps only named keys | **2 · Keep only** |
| `set` | Adds or overwrites keys with templated values | **3 · Set values** |
| `rename` | Renames keys | **4 · Rename** |
| `case` | Converts every key to camelCase or snake_case | **5 · Key case** |

Everything on this page was run against a real Pawabase API. Where a result is surprising it is shown as it was observed, with the definition that produced it.

## The shape of a definition

A transformer definition is a JSON object with any of the five keys:

```json
{
  "omit": ["secret"],
  "pick": ["id", "title", "author_id", "price_cents", "created_at"],
  "set": {
    "url": "https://example.com/posts/{{ record.id }}",
    "label": "{{ record.title | upper }}"
  },
  "rename": { "author_id": "author_ref" },
  "case": "camel"
}
```

| Key | Value | Rule |
| --- | --- | --- |
| `omit` | A list of field names | Each name is removed. A name that is not in the record is ignored |
| `pick` | A list of field names | Only these keys remain. A name that is not in the record is ignored |
| `set` | An object of `name: template` | Each template is rendered and stored under its name |
| `rename` | An object of `old: new` | Each `old` key that exists is moved to `new` |
| `case` | `"camel"` or `"snake"` | Every key is converted |

Any other key is refused when you save.

### What a bad definition says

Saving checks the **shape** of the definition and answers `422` with a plain message:

| You saved | Message |
| --- | --- |
| `{"keep": ["id"]}` | `unknown transformer step 'keep'; expected one of omit, pick, set, rename, case` |
| `{"case": "pascal"}` | `case is 'camel' or 'snake'` |
| `{"omit": "secret"}` | `omit takes a list of field names` |
| `{"set": ["a"]}` | `set takes an object` |
| An inline definition on a resource with an unknown step | `transformer: unknown transformer step 'foo'; expected one of ...` (prefixed with `transformer:`) |

What saving does **not** check is whether the definition will work: an unknown template filter, or a transformer name that does not exist. Those are found at read time, as [errors](#errors-at-read-time).

## Stored and inline

There are two places a definition can live.

**A stored transformer** has a name and is reused. In Studio, open **Build → Transformers**, whose description reads *Reshape what consumers see: omit, pick, set, rename, case.*, and create one there. Resources and routes then refer to it **by name**.

```http
POST /platform/v1/projects/acme/envs/production/transformers
```

```json
{
  "name": "public_post",
  "description": "What anonymous readers may see",
  "definition": { "omit": ["secret"], "rename": { "author_id": "author_ref" }, "case": "camel" }
}
```

**An inline transformer** is a definition written directly into the resource (or route) body, with no name:

```json
{
  "name": "posts",
  "transformer": { "omit": ["secret"], "case": "camel" }
}
```

| | Stored | Inline |
| --- | --- | --- |
| Reused by several resources and routes | Yes | No |
| Editable in Studio's form | Yes | **No.** Studio's resource form only offers stored transformers, and shows none selected for an inline one |
| Changing it | Edit once, every user of the name changes | Edit the resource |
| Promoted between environments | As its own definition | With the resource |
| Validated on save | The shape | The shape |

**Use stored transformers.** Studio's form edits them, they appear in the list of what exists, and a change in one place applies everywhere. Inline is for an API client that builds a definition in one request and never touches it again.

A stored transformer is looked up **every request**, so editing it takes effect on the next request without saving any resource. This was observed: after changing `public_post` from camel case to snake case and omitting another field, the very next `GET` of a resource that referred to it by name showed the new shape.

## The Studio form

Open **Build → Transformers** and create a new transformer (or open one to edit it). The sheet has a name, an optional description, and a section called **Steps**, described as *Applied in this order to every record a consumer receives.*

| Field | Hint | Control |
| --- | --- | --- |
| **1 · Omit fields** | *Removed from the output, e.g. password_hash.* | A tag input. Type a name, press Enter |
| **2 · Keep only** | *When set, every other field is dropped.* | A tag input, placeholder `id, title, created_at` |
| **3 · Set values** | *Values may use* `{{ record.field }}` *templates.* | Key and value rows, with **Add value**. The value placeholder is `https://example.com/posts/{{ record.id }}` |
| **4 · Rename** | | Key and value rows labelled **from** and **to**, with **Add rename** |
| **5 · Key case** | | Three choices: **Unchanged**, **camelCase**, **snake_case** |

A step you leave empty is not stored. The form keeps the stored keys in the order the steps run, so the **JSON** tab reads top to bottom in the order of execution. The starting example (**Use example**) is a `public_user` transformer: it omits `password_hash`, renames `created_at` to `joined`, and sets the key case to camel.

### Attaching it to a resource

Open the resource, and in the **Behaviour** section, set the optional **Transformer** field (hint *Reshapes rows in responses.*) to the stored transformer. A route has the same optional **Transformer** field, under **Request & response**. Saving takes effect on the next request and touches no table.

## The steps, one at a time

All examples below use this record, which is what the database holds for a `posts` resource:

```json
{
  "id": 1,
  "title": "Hello",
  "secret": "s3",
  "author_id": "a1",
  "price_cents": 4900,
  "is_live": true,
  "created_at": "2026-10-01T21:46:34.188620+00:00",
  "updated_at": "2026-10-01T21:46:34.188620+00:00"
}
```

### `omit`: remove keys

```json
{ "omit": ["secret", "is_live"] }
```

```json
{
  "id": 1, "title": "Hello", "author_id": "a1", "price_cents": 4900,
  "created_at": "2026-10-01T21:46:34.188620+00:00", "updated_at": "2026-10-01T21:46:34.188620+00:00"
}
```

Use `omit` when you know the keys that must not leave. A key added to the table later **will** be returned, because `omit` is a deny list. For a field you never want to expose, that is the weakness: see [deny lists and allow lists](#deny-lists-and-allow-lists).

### `pick`: keep only these keys

```json
{ "pick": ["id", "title", "price_cents"] }
```

```json
{ "id": 1, "title": "Hello", "price_cents": 4900 }
```

`pick` is an allow list. A key added to the table later is **not** returned until you add it. The order of the keys in the response follows the order of the record, not the order in `pick`. A name in `pick` that the record does not have is skipped without an error.

`omit` runs before `pick`, so a key in both is gone.

### `set`: add computed values

`set` adds keys whose values come from templates. It is how a transformer produces a field that is not a column:

```json
{
  "set": {
    "url": "https://example.com/posts/{{ record.id }}",
    "label": "{{ record.title | upper }}",
    "n": "{{ record.price_cents | int }}",
    "live": "{{ record.is_live | bool }}",
    "env": "{{ env }}"
  }
}
```

```json
{
  "id": 1, "title": "Hello", "secret": "s3", "author_id": "a1", "price_cents": 4900, "is_live": true,
  "created_at": "...", "updated_at": "...",
  "url": "https://example.com/posts/1",
  "label": "HELLO",
  "n": 4900,
  "live": true,
  "env": "development"
}
```

Two rules matter:

- **`set` runs after `pick`.** A `set` key is added even if `pick` did not list it, and a `set` key with the same name as an existing key **overwrites** it.
- **Templates read the original record**, not the record as `omit` and `pick` left it. `{{ record.secret }}` still works even if `secret` was omitted, so a `set` can deliberately expose a derived form of a hidden value. See [Templates](#templates).

### `rename`: change a key's name

```json
{ "rename": { "author_id": "author_ref", "price_cents": "price" } }
```

```json
{ "id": 1, "title": "Hello", "secret": "s3", "is_live": true, "created_at": "...", "updated_at": "...", "author_ref": "a1", "price": 4900 }
```

A renamed key moves to the **end** of the object. A rename whose old key is not in the record does nothing. If the new name is already a key, **the renamed value replaces it**:

```json
{
  "pick": ["id", "title"],
  "set": { "extra": "x", "title": "{{ record.title | upper }}" },
  "rename": { "title": "name", "extra": "id" }
}
```

```json
{ "id": "x", "name": "HELLO" }
```

Here `extra` was renamed to `id`, and it replaced the real `id`. A rename onto an existing key is almost always a mistake, and nothing warns you.

### `case`: change every key

`case` converts every key at the top level of the response:

| `case` | `price_cents`, `created_at`, `authorRef` becomes |
| --- | --- |
| `"camel"` | `priceCents`, `createdAt`, `authorRef` |
| `"snake"` | `price_cents`, `created_at`, `author_ref` |

`case` runs **last**, so it converts the names `rename` and `set` produced as well. A `set` key called `isNew` with `"case": "snake"` becomes `is_new`. Only the **top-level** keys change. Values inside a JSON field or an expanded object keep their own keys.

### All five together

```json
{
  "omit": ["secret"],
  "set": {
    "url": "https://example.com/posts/{{ record.id }}",
    "label": "{{ record.title | upper }}",
    "by": "{{ auth.user_id | default:\"anon\" }}",
    "env": "{{ env }}"
  },
  "rename": { "author_id": "author_ref" },
  "case": "camel"
}
```

For the record above, requested anonymously:

```json
{
  "id": 1,
  "title": "Hello",
  "priceCents": 4900,
  "isLive": true,
  "createdAt": "2026-10-01T21:46:34.188620+00:00",
  "updatedAt": "2026-10-01T21:46:34.188620+00:00",
  "url": "https://example.com/posts/1",
  "label": "HELLO",
  "by": "anon",
  "env": "development",
  "authorRef": "a1"
}
```

Follow it step by step: `secret` is removed; `url`, `label`, `by` and `env` are added; `author_id` becomes `author_ref` and moves last; every key is then converted to camel case, so `price_cents` is `priceCents` and `author_ref` is `authorRef`.

## Templates

A `set` value is a **template**: a string with `{{ ... }}` lookups. It is a lookup, not a language, and a small set of filters formats the result.

### What a template can read

| Name | What it is |
| --- | --- |
| `record` | The **original** row, before `omit` and `pick`, as the database returned it (after `select`, see below) |
| `auth` | The caller. `auth.authenticated`, `auth.kind`, `auth.user_id`, `auth.email`, `auth.roles`, `auth.permissions`, `auth.org`, `auth.org_role`, `auth.aal`, `auth.session_id`, `auth.claims` |
| `credential` | The API key or credential used |
| `request` | The request. `request.method`, `request.path`, `request.ip`, `request.params`, `request.query` |
| `project` | The project ref |
| `env` | The environment name |
| `input` | Always empty for a resource transformer |
| `now` | The current time, as an ISO datetime |

There is **no `auth.id`**. The caller's identifier is `auth.user_id`. A template that asks for `auth.id` finds nothing, and with `| default:"anon"` it answers `anon` for **everyone**, which was observed: a signed-in user with a valid token got `"by": "anon"` until the template was changed to `auth.user_id`.

The same definition, with `auth.user_id`, answered per caller:

```json
{ "uid": "anon",  "email": null,             "role": null,    "roles": 0, "authed": false }
{ "uid": "u-9",   "email": "maya@acme.co",   "role": "admin",  "roles": 2, "authed": true  }
```

from these templates:

```json
{
  "set": {
    "uid": "{{ auth.user_id | default:\"anon\" }}",
    "email": "{{ auth.email }}",
    "role": "{{ auth.roles | first }}",
    "roles": "{{ auth.roles | length }}",
    "authed": "{{ auth.authenticated }}",
    "method": "{{ request.method }}",
    "proj": "{{ project }}"
  }
}
```

### Paths

`record.title`, `auth.roles.0`, `request.query.page`. A dot walks into an object, and a number indexes a list. A path that is not found is empty.

### Whole values and embedded values

A template that is **the whole string** returns the value itself, with its type:

| Template | Result |
| --- | --- |
| `"{{ record.price_cents }}"` | `4900` (a number) |
| `"{{ record.is_live \| bool }}"` | `true` (a boolean) |
| `"{{ auth.roles }}"` | `["admin", "editor"]` (a list) |
| `"{{ record.nope }}"` | `null` |

A template **inside** a longer string is substituted as text:

| Template | Result |
| --- | --- |
| `"https://example.com/posts/{{ record.id }}"` | `"https://example.com/posts/1"` |
| `"a {{ record.nope }} b"` | `"a  b"` (a missing value is an empty string) |
| `"{{ record.title }} ({{ record.id }})"` | `"Hello (1)"` |

An object or list inside a longer string is written as JSON text.

### A trap: two templates side by side

A string that **starts** with `{{` and **ends** with `}}` is read as **one** template, even when it contains two. The text between the first `{{` and the last `}}` is then looked up as a single path, which does not exist, and the result is `null`:

```json
{ "set": { "display_name": "{{ record.first_name }} {{ record.last_name }}" } }
```

```json
{ "id": 42, "first_name": "Maya", "last_name": "Obi", "display_name": null }
```

This was run, and `"{{ record.price_minor }} {{ record.currency }}"` gave `null` the same way. There is no error. Put **literal text at the start or the end** and it works:

| Template | Result |
| --- | --- |
| `"{{ record.first_name }} {{ record.last_name }}"` | **`null`** |
| `"Name: {{ record.first_name }} {{ record.last_name }}"` | `"Name: Maya Obi"` |
| `"{{ record.first_name }} {{ record.last_name }}!"` | `"Maya Obi!"` |
| `"{{ record.title }} ({{ record.id }})"` | `"Hello (1)"` (it ends with a bracket) |

If you need exactly two values joined with nothing around them, use a Python transformer, or store the joined value in a column.

### Filters

A filter follows a pipe: `{{ record.title | upper }}`. Filters can be chained, and some take an argument after a colon.

| Filter | Does | Example |
| --- | --- | --- |
| `default:value` | Uses the value when the lookup is empty or `null` | `{{ record.nick \| default:"guest" }}` |
| `upper` | Upper case | `HELLO` |
| `lower` | Lower case | `hello` |
| `str` | Text, with `null` as an empty string | |
| `int` | Integer, `null` for empty | `{{ record.qty \| int }}` |
| `float` | Number, `null` for empty | |
| `bool` | Boolean | |
| `json` | JSON text of the value | |
| `length` | The length of a list or string, `0` for empty | `{{ auth.roles \| length }}` |
| `first` / `last` | The first or last item of a list | |
| `keys` | The keys of an object, as a list | |

The filter set is closed. Any other name is a mistake that only shows when a record is read: see [errors](#errors-at-read-time).

`now` is the current time when the response is built. Use it for values like "generated at":

```json
{ "set": { "served_at": "{{ now }}" } }
```

### Templates see the `select`ed record

When a caller sends `?select=title`, the record the transformer receives has only the selected columns, so a template that reads another column finds nothing. This was observed with a transformer whose `live` was `{{ record.is_live | bool }}` and `n` was `{{ record.price_cents | int }}`:

| Request | `live` | `n` |
| --- | --- | --- |
| `GET /rest/v1/posts/1` | `true` | `4900` |
| `GET /rest/v1/posts?select=title` | **`false`** | **`null`** |

The same template gave different answers because the column it reads was not selected. Either keep `set` templates to columns the caller always gets, or do not let callers `select` a resource whose transformer reads other columns.

## Where a transformer runs

| Response | Transformed? |
| --- | --- |
| `GET /rest/v1/<resource>` (each item of `data`) | Yes |
| `GET /rest/v1/<resource>/<id>` | Yes |
| `POST /rest/v1/<resource>` (the 201 body) | Yes |
| `PATCH /rest/v1/<resource>/<id>` (the 200 body) | Yes |
| `DELETE` | No body, so nothing to shape |
| The list **envelope** (`page`, `per_page`, `total`) | **No.** It stays as it is, whatever `case` says |
| An **expanded** related row | Yes, by the **related resource's own** transformer |
| A **custom route's** response | Yes, when the route has a transformer |
| A flow's `transform.map` block | Yes, for whatever the flow passes it |
| **Events, webhooks, realtime** | **No.** They carry the raw record |
| The **Database console** and the **Records tab** | **No.** They show raw rows |

Creating and updating go through the transformer too, so a client that posts `{"title": "Hi"}` gets back the shaped record, camelCase and all. A client that reads the 201 body to learn the id sees `id`, unless `id` was renamed.

### The list envelope

Only the records in `data` are transformed. This was observed with `case: "camel"`:

```json
{
  "data": [
    { "id": 1, "title": "Hello", "priceCents": 4900, "createdAt": "..." }
  ],
  "page": 1,
  "per_page": 1,
  "total": 2
}
```

`per_page` stays `per_page`. A client that expects an all-camel response must handle the envelope separately.

### Expanded rows keep their own shape

`?expand=` attaches related rows, and each related row is shaped by the **related resource's** transformer, after that resource's read policy has decided whether the caller may see it. With a `posts` resource that has a camel-case transformer, and an `authors` resource whose transformer omits `email` and uses camel case:

```http
GET /rest/v1/posts/1?expand=author
```

```json
{
  "id": 1,
  "title": "T",
  "authorId": 1,
  "createdAt": "...",
  "author": {
    "id": 1,
    "fullName": "Maya Obi",
    "createdAt": "..."
  }
}
```

The author's `email` is gone, because the author's own transformer omits it, and the author's keys are camel case because of **its** transformer. The parent's `case` converts the **name** of the `author` key, and does not reach inside it. If the related resource has no transformer, its rows come back as stored, whatever the parent does, so a camel-case parent can contain a snake-case child.

### Filtering, sorting and selecting use the original names

A transformer changes what a consumer **sees**. It does not change what a consumer **asks for**. Filters, `sort` and `select` always use the stored field names:

| Request | Result |
| --- | --- |
| `?filter[author_id]=eq.a1` (the original name) | Works, and returns the shaped record |
| `?filter[author_ref]=eq.a1` (the renamed name) | `400`, `cannot filter on unknown field 'author_ref'` |
| `?sort=-price_cents` | Works. A client that sees `priceCents` must still sort by `price_cents` |

Consumers of a renamed API therefore need to know both names. If that is a problem, do not rename. Document the stored name next to the response name.

### The OpenAPI document

A resource without a transformer publishes its response as a typed schema. A resource **with** one publishes the `200` response **without** a schema, because the shape is computed at runtime. This was observed in the environment's OpenAPI document: the `GET /rest/v1/posts/{id}` `200` response had no schema for a resource with a transformer, and generated clients get an untyped body. If you need typed clients, leave the transformer off and shape the record in a custom route whose response schema describes the result. A route that has a transformer drops its response schema, in the same way, so give a route one or the other.

## Errors at read time

A definition that saved can still fail when a record is read.

| Situation | What a read does |
| --- | --- |
| The resource names a transformer that **does not exist** | `500` with `{"error": "transformer_error", "message": "unknown transformer 'nope'"}` |
| A stored transformer is **deleted** while a resource still refers to it | The same `500`. Deleting is allowed, and the resource keeps pointing at the name |
| A `set` template uses an **unknown filter**, such as `{{ record.title \| nope }}` | A plain `500`, `Internal Server Error`, with no message |
| A `set` template names a **missing path** | No error. A whole-value template gives `null`, an embedded one an empty string |

Neither of the first two is caught when you save the resource. The save succeeds, and **every read of the resource** fails until you fix it. The recovery is immediate: restore the transformer under the same name, or change the resource's `transformer`. Because every request looks the name up, there is no restart and no cache to clear.

<Warning>
Delete a stored transformer only after nothing refers to it. There is no list of what uses a transformer, so search your resources and routes for the name first. A resource whose transformer disappeared fails **every list and get**, and a public endpoint doing that is an outage.
</Warning>

## Python transformers

A transformer that needs more than five steps can be written in Python and registered by name. The code lives with your project's other code:

```text
code/
  acme/
    transformers.py     # @transformer("public-order") ...
```

```python
from pawabase_kit.transformers import transformer


@transformer("public-order")
async def public_order(record, context):
    return {
        "id": record["id"],
        "status": record["status"],
        "total": record["total_cents"] / 100,
        "placed_by_you": record["customer_id"] == context["auth"]["user_id"],
    }
```

A resource then uses it by name, exactly like a stored transformer:

```json
{ "name": "orders", "transformer": "public-order" }
```

A Python transformer receives each record and the template context (`auth`, `project`, `env` and so on), may be `async`, and returns the dict to send. When a name matches both a Python transformer and a stored one, **the Python one is used**. The code directory is part of your deployment, not of the environment, so a Python transformer is not promoted and is not edited in Studio. See [Code](/code/overview).

Use Python when a record needs real logic: arithmetic, a lookup, a condition. Keep the five steps for everything else, because a declarative transformer can be read, edited and reviewed by anyone in Studio.

## What a transformer protects, and what it does not

The most common mistake with transformers is to treat `omit` as access control. It is a **presentation** step, and the places it does not apply are as important as the places it does.

### Where a hidden field can still be reached

| Path | Does the transformer hide the field? |
| --- | --- |
| `GET /rest/v1/<resource>` and `/<id>` | **Yes** |
| The 201 and 200 bodies of `POST` and `PATCH` | **Yes** |
| `?expand=` of this resource from another | **Yes**, by this resource's transformer |
| **A filter** on the hidden field | **No.** A caller can filter by it, and the rows returned reveal it |
| **Events** (`posts.created` and so on) | **No.** The payload carries the raw record |
| **Webhooks** | **No.** They deliver events |
| **Realtime** broadcasts of the resource | **No.** The raw record is published |
| **The Records tab and the Database console** | **No.** Operators see raw rows |
| **A flow's `resource.*` blocks** | **No.** The transformer runs in the data plane's response path, and flows read through the store as trusted code |
| **A column you did not declare** | Returned unless `omit`ted. A resource returns the whole row |

Read the fourth row twice. It is the one that most often defeats the intention.

### Filters can read what responses hide

A resource `vault` has a transformer that omits `secret` and `cost`. Responses never contain them. But filters accept any stored column, and a filter's result is a yes or no about the value:

```http
GET /rest/v1/vault?filter[secret]=like.bravo-k*
```

If a row comes back, its hidden `secret` starts with `bravo-k`. A caller can extend the prefix one character at a time, or binary search a number with `gt` and `lt`, and recover the value with a few dozen requests. This was run: `filter[secret]=like.b*` returned the `b` row, `like.bravo-k*` narrowed it, `eq.charlie` matched exactly, and `filter[cost]=gte.5` and `gte.9` separated the numeric rows. Every response omitted the field throughout.

The same applies when the field is `write_only`: that flag stops the value being **documented**, not being **returned** or **filtered**. See [Filtering](/data/filtering#filters-can-read-what-responses-hide).

If a value must be unreadable, do not put it in a resource a caller can filter. Options, strongest first:

1. **Keep it out of this table.** Put the secret in a separate resource with a policy that only the owner and operators pass, and keep the public resource free of it.
2. **Gate the list operation** with a policy that only trusted callers pass, so untrusted callers cannot filter at all.
3. **Hash it.** Store only a hash, so a prefix search reveals nothing useful.
4. **Accept the limit**, if the value is low sensitivity, and use the transformer for tidiness only.

### Events, webhooks and realtime carry the raw record

When a resource emits events, the payload is the stored record, before any transformer:

```json
{
  "resource": "posts",
  "change": "created",
  "record": { "id": 1, "title": "Hello", "secret": "s3", "author_id": "a1", "price_cents": 4900 }
}
```

A subscription, a webhook endpoint or a realtime subscriber that receives it sees `secret`, `author_id` and every other column, **in snake case**, whatever the resource's transformer says. If a field is hidden from API readers because it is sensitive, then:

- **Turn off events** for that resource (**Emit events** in the resource's Behaviour section) if nothing needs them.
- **Turn off realtime** (**Broadcast changes**) if the field is sensitive. Realtime pushes the raw record to anyone allowed to subscribe to the channel.
- **Shape in a flow.** A flow triggered by the event can build a safe payload with `transform.map` and send **that** on, instead of handing the raw event to a webhook.

See [Resource events](/data/resource-events).

### Deny lists and allow lists

| | `omit` | `pick` |
| --- | --- | --- |
| Lists | What to **remove** | What to **keep** |
| A new column later | **Returned** | **Not returned** |
| Failure mode | A field you forgot leaks | A field you forgot is missing |
| Better for | Removing one or two known fields | A public shape that must stay stable |

For anything public, prefer `pick`. A leak is worse than a missing field, and a missing field is noticed in testing, whereas a leaked one is not. A column added to the table by a migration, a flow or a colleague appears in an `omit`-only response without anyone deciding it should.

A combined use: `pick` the public fields, and also `omit` the ones that must never be exposed. If someone later adds one to `pick`, the `omit` still removes it, since `omit` runs first.

```json
{
  "omit": ["secret", "cost", "internal_note"],
  "pick": ["id", "title", "price_cents", "created_at"]
}
```

### What `write_only` does instead

A field flag and a transformer are different tools:

| | What it does | What it does not do |
| --- | --- | --- |
| `write_only` on a field | Accepted on write, and kept out of the generated API documentation | Keep the value out of **responses** or **filters**. A `write_only` field was returned on every read, and filterable, until a transformer or `select` removed it |
| `read_only` on a field | Refuses the field on write | Hide it |
| `omit` in a transformer | Removes the key from this resource's responses | Hide it from filters, events, webhooks or realtime |

Use the transformer to hide, and the flag to document intent. See [Field types](/data/field-types).

## Transformers and the cache

When a resource has a cache time (`cache_ttl`), the cached response is the **shaped** one. Two things follow, both observed:

**A transformer change is immediate.** Saving a stored transformer bumps the environment's version, and cache keys include it, so the next request misses and rebuilds with the new shape. No stale shape survives an edit.

**A cached copy is a copy.** On a hit, the body is the stored shaped JSON, and a value computed at build time is **not recomputed**. A `set` of `{{ now }}` on a cached resource showed the same instant on the second request, as it should, but formatted differently:

```text
miss:  "served": "2026-10-01T21:49:18.535995+00:00"
hit:   "served": "2026-10-01 21:49:18.535995+00:00"
```

The hit has a space where the miss has a `T`. The cached copy had been turned to text by a plain string conversion. If a client parses that field strictly, a cached resource will occasionally hand it the other form. Avoid datetimes in `set` on a cached resource, or format them to text in the template with `| str` and accept one form, or normalise on the client.

Because the cache key includes the caller's identity, a template that reads `auth` is safe to cache: each identity has its own entry. See [Caching](/data/caching).

## Transformers and promotion

A stored transformer is a definition like any other. **Promote** copies it by name, as an upsert: a transformer changed in the source overwrites the target's, and one deleted in the source stays in the target.

| Concern | What to do |
| --- | --- |
| A resource promoted without its transformer | Include `transformers` in the promote, or the target's resource points at a name that does not exist and every read of it is a `500` |
| A transformer promoted before its resource | Harmless. It is unused until a resource refers to it |
| A Python transformer | Not promoted. It lives in your code directory, so deploy the code to each environment |
| An inline transformer | Travels with its resource |

The first row is the one that bites. A promote that carries `resources` and not `transformers` can break a target environment completely. When in doubt, promote everything, which is the default when `include` is omitted. See [Environments and promotion](/operate/environments-and-promotion).

## Designing a public shape

The decisions, in the order to make them.

<Steps>
  <Step title="Decide who reads it">
    A transformer shapes for **every** reader of the resource. If admins and anonymous visitors need different shapes, use two stored transformers on two routes or two resources, or branch on `auth` in a `set` template, or use a custom route.
  </Step>
  <Step title="Pick, do not omit">
    List the fields a reader needs. Use `pick`. Add `omit` as a second line of defence for the ones that must never leave.
  </Step>
  <Step title="Add computed fields with set">
    A link, a label, a flag derived from the record or the caller. Keep templates to columns the caller always receives (see the `select` caveat).
  </Step>
  <Step title="Rename only for a reason">
    A rename makes the response differ from the filter and sort names. Rename when an external contract demands it.
  </Step>
  <Step title="Choose one key case, and say so">
    `camel` for JavaScript clients, `snake` otherwise. Remember the list envelope keeps its own names.
  </Step>
  <Step title="Check the other doors">
    Events, realtime, filters, the console. Decide for each whether the raw field is acceptable there.
  </Step>
</Steps>

## Recipes

### A public user

```json
{
  "name": "public_user",
  "definition": {
    "omit": ["password_hash", "email", "phone"],
    "rename": { "created_at": "joined" },
    "case": "camel"
  }
}
```

This is the starting example Studio offers. A user row comes back as `{ "id": 7, "displayName": "Maya", "joined": "..." }`, with no hash, email or phone.

### A stable public shape with `pick`

```json
{
  "name": "public_product",
  "definition": {
    "pick": ["id", "sku", "title", "price_minor", "currency", "tags"],
    "set": { "url": "https://shop.example.com/p/{{ record.sku | lower }}" },
    "case": "camel"
  }
}
```

New columns do not appear until someone adds them to `pick`. `url` is added after `pick`, so it need not be listed.

### Different shapes for different readers

A declarative transformer applies **one** shape to every reader of the resource, because `omit` and `pick` cannot depend on the caller. Two ways to serve two audiences:

- **Two routes**, one open and one for staff, each with its own transformer and its own policy. A custom route returns the same data from a flow. See [Custom routes](/data/custom-routes).
- **A Python transformer** that checks `context["auth"]` and returns a different dict. See the next recipe.

### Showing a value only to its owner

A `set` can reveal a field to the owner by comparing identities in a Python transformer:

```python
@transformer("own-or-public")
async def own_or_public(record, context):
    visible = {k: v for k, v in record.items() if k not in {"email", "phone"}}
    if record.get("owner_id") == context["auth"]["user_id"]:
        visible["email"] = record["email"]
    return visible
```

The declarative steps cannot make a key present for some callers and absent for others, so a Python transformer is the tool for that.

### An absolute URL for a stored file

```json
{ "set": { "avatar_url": "https://cdn.example.com/{{ record.avatar_key }}" } }
```

Keep the key in the table and build the URL in the response, so a change of CDN is one transformer edit and no data migration.

### A flag derived from the caller

```json
{ "set": { "mine": "{{ auth.user_id }}" } }
```

`mine` carries the caller's id on every record, so a client can compare it to `author_id`. For a boolean, use a Python transformer. A template can fetch values and format them, and it cannot compare two of them.

### Consistent output for a client generator

If an SDK generator needs a fixed shape, `pick` the fields, `case` the keys, and keep the transformer's output the contract. Test it (see below), because a transformer response has no schema in the OpenAPI document.

## Testing a transformer

A transformer is a pure function of a record and a context, so the test is a request:

<Steps>
  <Step title="Create a representative record">
    Include every column, including the ones that must not leave, and a null.
  </Step>
  <Step title="Read it through each door">
    The list, the get, the create response, an `?expand=` from a parent, and a `?select=` of a few columns.
  </Step>
  <Step title="Assert the absence of hidden fields">
    The test that matters most is the negative one: `secret` is not in any body.
  </Step>
  <Step title="Add a column and read again">
    Add a new column in a development environment and check it. With `pick` it is absent. With `omit` it is present. That tells you which kind of list you wrote.
  </Step>
  <Step title="Try the caller variations">
    Anonymous, signed in, an admin. If a template reads `auth`, the output should differ as intended.
  </Step>
  <Step title="Try the filter door">
    Send `?filter[secret]=like.a*` and see whether the response reveals anything.
  </Step>
</Steps>

A short script:

```python
def test_public_shape(api):
    row = api.post("/rest/v1/posts", json={"title": "Hello", "secret": "s3", "author_id": "a1"}).json()
    for body in (
        api.get(f"/rest/v1/posts/{row['id']}").json(),
        api.get("/rest/v1/posts").json()["data"][0],
        row,
    ):
        assert "secret" not in body
        assert "authorRef" in body and "author_id" not in body
        assert body["url"].endswith(f"/posts/{row['id']}")
```

## Case conversion in detail

`case` is simple, and a few of its edges are worth knowing before you point it at a table you did not design. These conversions were run on a set of awkward key names.

### To camel case

| Key | Becomes |
| --- | --- |
| `created_at` | `createdAt` |
| `price_cents` | `priceCents` |
| `x1_y2` | `x1Y2` |
| `a_1` | `a1` |
| `already_Camel` | `alreadyCamel` |
| `snake_UPPER` | `snakeUPPER` |
| `a__b` | `a_B` |
| `_private` | `Private` |
| `__x` | `_X` |
| `_id` | `Id` |
| `trailing_` | `trailing_` |
| `id`, `url2`, `ID` | unchanged |
| `camelCase`, `PascalCase`, `userID`, `HTTPStatus` | unchanged |
| `with-dash`, `with space` | unchanged |

What to take from it:

- **Only underscores trigger a change.** A key that is already camel or Pascal case, or that has dashes or spaces, is left as it is.
- **A leading underscore is consumed.** `_private` becomes `Private`, which is no longer the name a client would guess. Avoid leading underscores in field names if you use camel case.
- **Digits can swallow the underscore.** `a_1` becomes `a1`, and `x1_y2` becomes `x1Y2`.
- **A double underscore** keeps one: `a__b` becomes `a_B`.

### To snake case

| Key | Becomes |
| --- | --- |
| `camelCase` | `camel_case` |
| `PascalCase` | `pascal_case` |
| `userID` | `user_id` |
| `HTTPStatus` | `http_status` |
| `already_Camel` | `already_camel` |
| `snake_UPPER` | `snake_upper` |
| `created_at`, `price_cents`, `x1_y2`, `url2`, `a_1` | unchanged |
| `with-dash`, `with space` | unchanged |
| `ÅngströmValue` | `ångström_value` |

Runs of capitals become one word, so `HTTPStatus` is `http_status` and `userID` is `user_id`.

### Two keys can collapse into one, silently

Both conversions can map two different keys to the same name. The later one wins and the earlier **disappears**, with no error:

```json
{ "a_b": 1, "aB": 2 }
```

With `"case": "camel"` this becomes `{ "aB": 2 }`, and with `"case": "snake"` it becomes `{ "a_b": 2 }`. One value was lost either way. It cannot happen when every field of a resource follows one convention, which is why mixed-convention tables are the ones to check. A `set` key can collide with a column in the same way.

<Warning>
Before you add `case` to an existing resource, list its columns and check that no two differ only by convention. The silent loss is easy to miss, because every record still looks well formed.
</Warning>

### Only the top level

`case` converts the keys of the record, and **not** the keys inside values. A JSON field keeps whatever keys it holds:

```json
{ "n": { "inner_key": 1 } }
```

stays exactly that with `"case": "camel"`.

## The order of a request

A transformer sits at one point in a longer path. Knowing where tells you what it can and cannot see.

| Order | Stage | Effect on the transformer |
| --- | --- | --- |
| 1 | Credential and scope | Decides the caller. Its result is in `auth` and `credential` |
| 2 | Body validation (writes) | Not related to the transformer |
| 3 | Policy gate | Decides whether the caller may read at all |
| 4 | Query: filters, sort, page, **select** | The record the transformer receives has only the selected columns |
| 5 | The row is read | |
| 6 | **Expand** | Related rows are attached, each shaped by **its** resource's transformer |
| 7 | **This resource's transformer** | Omit, pick, set, rename, case |
| 8 | Cache write (when `cache_ttl` is set) | The shaped output is stored |
| 9 | Response | |

Two consequences:

- **`set` can read an expanded relation**, because the relation was attached at step 6, before the transformer ran at step 7. See the example below.
- **A transformer never sees rows the policy removed**, and cannot be used to filter rows. See [Policies](/policies/overview).

### Reading an expanded relation in `set`

A `posts` resource with a `belongs_to` relation `author`, and this inline transformer:

```json
{
  "set": {
    "by": "{{ record.author.full_name }}",
    "nm": "Author: {{ record.author.full_name }}"
  }
}
```

Without `expand`, the relation is not on the record, so both values are empty:

```http
GET /rest/v1/posts/1
```

```json
{ "id": 1, "title": "T", "author_id": 1, "by": null, "nm": "Author: " }
```

With `?expand=author`, they are filled in, and the `author` object is also in the response:

```http
GET /rest/v1/posts/1?expand=author
```

```json
{
  "id": 1, "title": "T", "author_id": 1,
  "author": { "id": 1, "full_name": "Maya Obi" },
  "by": "Maya Obi",
  "nm": "Author: Maya Obi"
}
```

(The timestamps are left out above.) Two things to note. A transformer whose output depends on a relation gives a different answer for a client that forgets `expand`, so make the value tolerant of `null`, or use `| default:`. And `set` can lift a value out of an expanded row, while an `omit: ["author"]` removes the object itself, which is how a response can show `by` without exposing the whole author.

## Transformers on custom routes

A custom route has its own optional **Transformer** field, under **Request & response** in the route's sheet. It works the same way, with these differences:

| | Resource | Route |
| --- | --- | --- |
| What it shapes | Every list, get, create and update of the resource | The result of the route's flow or function |
| What the context's `record` is | The row | Whatever the handler returned, for a single object |
| A list | Applied to each item | Applied to each item when the handler returns a list |
| Response schema | Dropped | **Dropped** as well: a route with a transformer has no response schema in OpenAPI |
| Cache | Stores the shaped output | Stores the shaped output, for `GET` routes with a cache time |
| Errors | A bad definition is a `500` | The same |

The route's transformer is applied to the handler's result before the response is built. Check what your flow returns on its **error** paths too, with the transformer attached, so that an `omit` or a `case` does not reshape an error body your client depends on.

## Transformers in flows

A flow can apply a transformer to any value with the **Transform** block (`transform.map`), which takes two settings:

| Setting | Meaning |
| --- | --- |
| `value` | The data to shape. A record or a list of records |
| `transformer` | An inline definition, or the **name** of a stored or Python transformer |

The template context for `set` is the **flow's state** (the trigger, step outputs and so on) instead of the request, so a template reads `{{ steps.fetch.output.id }}` where a resource transformer reads `{{ record.id }}`. The same five steps, in the same order.

This is the way to build a safe payload for a webhook from an event, since the event carries the raw record:

```text
trigger: posts.created
  └─ transform.map   value = {{ trigger.record }}   transformer = public_post
      └─ http.request   body = {{ steps.shape.output }}
```

The webhook then receives the shaped record, with `secret` removed. Pair this with turning off the raw delivery. See [Data blocks](/flows/data-blocks) and [Resource events](/data/resource-events).

## A worked design: a mobile API

A team serves a mobile app and a web admin from one set of resources. The app wants camel case, a small payload and stable names. The admin wants everything.

**The resource**, `products`, has columns `id`, `sku`, `title`, `description`, `price_minor`, `currency`, `stock`, `cost_minor`, `supplier_id`, `internal_note`, `created_at`, `updated_at`.

**Step 1: a stored transformer for the app.**

```json
{
  "name": "app_product",
  "definition": {
    "pick": ["id", "sku", "title", "description", "price_minor", "currency", "stock"],
    "set": {
      "url": "https://shop.example.com/p/{{ record.sku | lower }}",
      "in_stock": "{{ record.stock | int }}"
    },
    "rename": { "price_minor": "price" },
    "case": "camel"
  }
}
```

The app receives `id`, `sku`, `title`, `description`, `currency`, `stock`, `url`, `inStock` and `price`. `cost_minor`, `supplier_id` and `internal_note` are not on the allow list, so they are absent, and so would be any column added later.

**Step 2: the resource uses it.** `products` has `"transformer": "app_product"`, and its `list` and `get` operations are public.

**Step 3: the admin needs the raw shape.** The admin is a different consumer of the same resource, and a resource has one transformer. So the admin does not read `/rest/v1/products`. It reads a **route**, `GET /rest/v1/admin/products`, gated by an admin policy, backed by a flow that lists products, and with **no transformer**, or a different stored one (`admin_product`) that only adds a margin:

```json
{ "name": "admin_product", "definition": { "set": { "margin_note": "{{ record.price_minor }}" } } }
```

**Step 4: close the other doors.** `cost_minor` is sensitive, and the app can still filter on it (`?filter[cost_minor]=gte.500`). The fix is the one from earlier: the public resource does not hold the cost. Margins live in a separate `product_costs` resource that only admins can read, joined by `product_id`. The transformer stays a convenience, and the data is where it belongs.

**Step 5: events.** `products` emits events for the admin flows. The payload carries the raw record, `cost_minor` included. Since the only subscribers are internal flows, that is acceptable, and the **Broadcast changes** switch stays off so nothing pushes the raw record to clients.

**What the design shows.** The transformer did one job, which was shaping for the app. The sensitive value was handled by where it lives, the admin shape by a route, and the raw-event risk by what subscribes. No single mechanism was asked to be a security boundary.

## Changing a shape without breaking clients

A transformer is part of your API's contract, so changing it is changing the API.

| Change | Breaks clients? |
| --- | --- |
| Adding a `set` key | Rarely. Clients ignore unknown keys |
| Adding a field to `pick` | Rarely, for the same reason |
| Removing a field from `pick`, or adding it to `omit` | **Yes**, for any client that reads it |
| Renaming a key | **Yes** |
| Turning `case` on, off or switching it | **Yes**, for every key |
| Changing a `set` value's type | **Yes** |

To change a shape safely, add before you remove: serve both names for a while (a `set` can copy a value under the old name), move clients, then drop the old name. Or version the shape with a new route (`/rest/v1/v2/products`) and leave the old one alone. For releases and pinned versions of definitions, see [Releases and API versions](/operate/releases-and-api-versions).

Because the response has no OpenAPI schema, nothing flags a break automatically. A test that reads one record and compares its keys to a fixed list is the cheapest guard.

## How a transformer differs from its neighbours

Several features reshape or restrict a response. They work at different points and answer different questions.

| | Answers | Decided by | Applies to |
| --- | --- | --- | --- |
| **Policy** | May this caller read this row at all? | The resource, per operation | Rows, and write bodies |
| **`select`** | Which columns does this request want? | The caller | One request |
| **Transformer** | What shape does every reader get? | The resource | Every response of the resource |
| **Field flags** (`read_only`, `write_only`) | May this field be written, and is it documented? | The field | Writes, and the generated docs |
| **Response schema** (routes) | What does this route promise to return? | The route | OpenAPI, for routes without a transformer |
| **A custom route** | What should this endpoint return, from any data? | A flow or function | One endpoint |

Reading the table as a decision:

- **To hide rows from a caller**, use a policy, never a transformer.
- **To let a caller trim a response**, they use `select`.
- **To fix the public shape for everyone**, use a transformer.
- **To keep a field out of writes**, use `read_only`.
- **To give a different shape to a different audience**, use a route.

## Patterns at a glance

| I want to | Definition |
| --- | --- |
| Remove a field | `{"omit": ["password_hash"]}` |
| Publish only a fixed set | `{"pick": ["id", "title"]}` |
| Add a link | `{"set": {"url": "https://x.com/{{ record.id }}"}}` |
| Add a label in upper case | `{"set": {"label": "{{ record.title \| upper }}"}}` |
| Default an empty value | `{"set": {"bio": "{{ record.bio \| default:\"None\" }}"}}` |
| Count a list | `{"set": {"n": "{{ record.tags \| length }}"}}` |
| Show the caller's id | `{"set": {"me": "{{ auth.user_id }}"}}` |
| Rename a field | `{"rename": {"created_at": "joined"}}` |
| camelCase every key | `{"case": "camel"}` |
| A public shape with a link, camelCase | `{"pick": [...], "set": {...}, "case": "camel"}` |
| Pull a value out of an expanded row | `{"set": {"by": "{{ record.author.full_name }}"}}` with `?expand=author` |

## Before you ship a transformer

1. **Is it `pick` or `omit`?** If it protects anything, is it `pick`?
2. **Did you check the other doors?** Filters, events, webhooks, realtime and the console.
3. **Do any two `set` templates sit side by side** with nothing around them?
4. **Does every template read `auth.user_id`**, not `auth.id`?
5. **Does a `?select=` leave a template with nothing to read?**
6. **Do two columns collide after `case` or `rename`?**
7. **Does a promote carry the transformer along with its resource?**
8. **Does a client depend on the old shape?** If so, add before you remove.
9. **Is the transformer stored, so Studio can edit it?**
10. **Did you read one record from each door and look at the keys?**

## Organising transformers

A project with many resources accumulates transformers. A few conventions keep them readable.

| Convention | Why |
| --- | --- |
| **Name by audience and subject**: `public_user`, `app_product`, `admin_order` | The name says who the shape is for, so a reviewer can judge whether a field belongs |
| **One transformer per shape, shared across resources** | `public_user` can serve `users` and an `authors` view alike. A change is made once |
| **Write a description** | The Transformers list shows **name** and **description**, so the description is what people search |
| **Keep stored transformers in step across environments** | Promote with the default `include`, so none are missing in a target |
| **Prefer `pick` in anything named `public_*`** | The name promises an allow list |

The Transformers page lists each one with its name and description. There is no usage column, so to find what refers to a transformer, search your resource and route definitions for its name, or export the definitions as a blueprint and search the JSON.

### Reviewing a change

A transformer edit changes every response that uses it, immediately and in every environment it is promoted to. A review is short:

1. **Read the diff of the definition**: which keys were added to `omit` or removed from `pick`.
2. **Ask what a client sees change.** Adding a `set` key is invisible to most clients. Removing or renaming a key is not.
3. **Check the other doors** for any field newly exposed or hidden.
4. **Read one record** from a development environment, through the list, the get and an expand.
5. **Promote deliberately**, to staging first.

## A second design: a multi-tenant directory

A SaaS product stores `members` for many organisations. Each organisation's staff read their own members, and members read a limited view of one another.

**The resource.** `members` has `org_id`, `user_id`, `display_name`, `email`, `phone`, `role`, `salary_minor`, `notes`, `created_at`. Its `list` and `get` policy passes callers in the same organisation (`record.org_id == auth.org`), so tenants cannot see each other's rows. That is the **policy's** job.

**The shapes.** Two readers need different data from the same rows:

| Reader | Needs | Shaped by |
| --- | --- | --- |
| A colleague | `id`, `displayName`, `role`, a profile link | `directory_member` |
| HR | everything except `notes` | `hr_member` |

```json
{
  "name": "directory_member",
  "definition": {
    "pick": ["id", "display_name", "role"],
    "set": { "profile_url": "https://app.example.com/people/{{ record.id }}" },
    "case": "camel"
  }
}
```

```json
{
  "name": "hr_member",
  "definition": {
    "omit": ["notes"],
    "case": "camel"
  }
}
```

**The wiring.** One resource carries one transformer, so the resource `members` takes `directory_member`, which is what most readers should get. HR reads through a route, `GET /rest/v1/hr/members`, gated by an HR policy, backed by a flow that lists members and tagged with `hr_member`.

**What each mechanism did.**

| Concern | Mechanism |
| --- | --- |
| Tenants must not see each other | The **policy**, on every operation |
| Colleagues must not see salary | `pick`, which also keeps a future column hidden |
| HR may see salary and not notes | A **route** with its own policy and transformer |
| Salary must not be learnable by a colleague | Not the transformer. A colleague can still `filter[salary_minor]=gte.100000`. So the salary does not live in `members`; it lives in `member_pay`, readable only by HR, and the join is by `member_id` |
| A webhook announcing new members | A flow on `members.created` with `transform.map` and `directory_member`, so the raw record never leaves |

The design uses the transformer where shaping is the problem, and uses data layout and policies where secrecy is the problem.

## Following one record through a transformer

A short trace makes the fixed order concrete. The definition:

```json
{
  "omit": ["secret"],
  "pick": ["id", "title", "author_id"],
  "set": { "label": "{{ record.title | upper }}", "title": "Untitled" },
  "rename": { "author_id": "author_ref", "label": "tag" },
  "case": "camel"
}
```

and the record the database returned:

```json
{ "id": 1, "title": "Hello", "secret": "s3", "author_id": "a1", "price_cents": 4900 }
```

| After step | The object |
| --- | --- |
| Start | `{id: 1, title: "Hello", secret: "s3", author_id: "a1", price_cents: 4900}` |
| **omit** `secret` | `{id: 1, title: "Hello", author_id: "a1", price_cents: 4900}` |
| **pick** `id`, `title`, `author_id` | `{id: 1, title: "Hello", author_id: "a1"}`. `price_cents` is gone |
| **set** `label`, `title` | `{id: 1, title: "Untitled", author_id: "a1", label: "HELLO"}`. `label` is added from the **original** `title`, and `title` is overwritten |
| **rename** `author_id`, `label` | `{id: 1, title: "Untitled", author_ref: "a1", tag: "HELLO"}`. Both renamed keys moved to the end |
| **case** `camel` | `{id: 1, title: "Untitled", authorRef: "a1", tag: "HELLO"}` |

The point to hold on to is the third row: `label` was computed from `"Hello"`, the title **before** `set` overwrote it, because every template reads the original record. A transformer cannot build a value from another step's output.

## Questions about `auth` in templates

**Is the caller always an end user?** No. `auth.kind` says what kind of principal it is, and a service credential has no user: `auth.user_id` is empty, so `default:` is how you give it a value.

**Can I show something only to the owner?** A template can print the caller's id next to the owner's, and cannot compare them. Use a Python transformer for a condition, or a route with a policy.

**Does a cached response leak one caller's `auth` to another?** No. The cache key includes the caller's identity and role, so each has its own entry. The cost is a lower hit rate for resources whose output depends on `auth`.

**Can a template read the request body?** No. `input` is empty for a resource transformer, and `request` carries the method, path, parameters and query, not the body.

### Why the order is fixed

The order was chosen so that the common cases read naturally: remove, then narrow, then add, then rename, then style. Some consequences follow directly:

- To **hide** something, use `omit` or leave it out of `pick`. A `rename` or a `set` of the same name cannot undo it, because `omit` and `pick` have already run.
- To **replace** a value, use `set` with the same key. It runs after `pick`, so it overwrites.
- To **rename a computed value**, add it with `set` and then rename it, as the trace did with `label`.
- To **style** every key including computed ones, use `case`, which runs last.
- There is no way to run a step twice, or to run `rename` before `set`. If you need that order, use two transformers in a flow, or a Python transformer.

### Reading the order when something looks wrong

When a response is not what you expected, replay the steps on the original record in your head, in order. Nine times in ten the cause is that a later step overwrote an earlier one: a `set` replaced a picked value, a `rename` landed on an existing key, or a `case` merged two keys.

## Limits and performance

| Topic | What to know |
| --- | --- |
| **Cost** | A transformer is a few dictionary operations per record, done in process. It adds no database query. For a page of 200 records it is negligible next to the query |
| **Templates** | Each `set` value is rendered per record, so a hundred templates times a hundred records is ten thousand lookups. Keep `set` to what a client needs |
| **Python transformers** | Run per record, and may be `async`. A transformer that makes a network call per record will dominate response time. Do that work in a flow, or fetch once |
| **Number of steps** | Five, fixed |
| **Size of a definition** | No limit is enforced beyond the request body's own |
| **Caching** | The cache stores the shaped output, so the transformer's cost is paid once per cache entry |
| **Large lists** | `per_page` is capped by the resource API (see [Sorting and pagination](/data/sorting-pagination)), which bounds the work per request |

## Moving shaping out of the client

Many applications start by reshaping responses in the client: renaming keys, dropping fields, computing a URL. A transformer moves that work to the server, once.

| Client code | Becomes |
| --- | --- |
| `const { password_hash, ...safe } = user` | `omit: ["password_hash"]` (and the field never leaves the server) |
| `toCamel(response)` | `case: "camel"` |
| `product.url = base + "/p/" + product.sku` | A `set` of `url` with a template |
| `price: row.price_minor / 100` | A Python transformer, since a template cannot divide |
| `row.bio \|\| "No bio yet"` | `set: { bio: "{{ record.bio \| default:... }}" }` |

The gain is that **every client** gets the same shape, including ones you did not write. The cost is that the shape becomes part of the server's contract: change it deliberately, per the earlier table.

One thing does not move: a client that needs to hide something from **itself** (a screen that should not show a field) can keep doing that in the client, since that is presentation. A server-side `omit` is for what must not leave the server at all, and even then only for the doors it covers.

## A gallery, run

Each definition below was applied to this record, and the output is what came back. The context is an anonymous caller in `production` unless it says otherwise.

```json
{
  "id": 42, "first_name": "Maya", "last_name": "Obi", "email": "maya@acme.co",
  "password_hash": "x9f", "role": "admin", "created_at": "2026-09-01T10:00:00+00:00",
  "bio": null, "tags": ["a", "b"], "price_minor": 1250, "currency": "USD",
  "sku": "MUG-01", "status": "live", "avatar_key": "u/42.png", "org_id": 7
}
```

### Drop what must not leave, rename one key, camel-case the rest

```json
{ "omit": ["password_hash", "email"], "rename": { "created_at": "joined" }, "case": "camel" }
```

```json
{
  "id": 42, "firstName": "Maya", "lastName": "Obi", "role": "admin", "bio": null,
  "tags": ["a", "b"], "priceMinor": 1250, "currency": "USD", "sku": "MUG-01",
  "status": "live", "avatarKey": "u/42.png", "orgId": 7,
  "joined": "2026-09-01T10:00:00+00:00"
}
```

`joined` is last, because a renamed key moves to the end. Note that this is an `omit` list, so `role` and `org_id` came through. If those were not meant for the public, this is the leak that `pick` prevents.

### An allow list with a computed link

```json
{
  "pick": ["id", "sku", "price_minor", "currency", "tags"],
  "set": { "url": "https://shop.example.com/p/{{ record.sku | lower }}" },
  "case": "camel"
}
```

```json
{
  "id": 42, "sku": "MUG-01", "priceMinor": 1250, "currency": "USD",
  "tags": ["a", "b"], "url": "https://shop.example.com/p/mug-01"
}
```

### A URL built from a stored key, with the key hidden

```json
{
  "pick": ["id", "avatar_key"],
  "set": { "avatar_url": "https://cdn.example.com/{{ record.avatar_key }}" },
  "omit": ["avatar_key"]
}
```

```json
{ "id": 42, "avatar_url": "https://cdn.example.com/u/42.png" }
```

`omit` removed `avatar_key` from the output, and the template still read it, because `set` sees the original record.

### A default for an empty value

```json
{ "pick": ["id", "bio"], "set": { "bio": "{{ record.bio | default:\"No bio yet\" }}" } }
```

```json
{ "id": 42, "bio": "No bio yet" }
```

The `set` overwrote the picked `bio`, which was `null`.

### Counting and picking from a list

```json
{
  "pick": ["id", "tags"],
  "set": { "tag_count": "{{ record.tags | length }}", "first_tag": "{{ record.tags | first }}" }
}
```

```json
{ "id": 42, "tags": ["a", "b"], "tag_count": 2, "first_tag": "a" }
```

### Values that depend on the caller

```json
{
  "pick": ["id"],
  "set": {
    "viewer": "{{ auth.user_id | default:\"guest\" }}",
    "signed_in": "{{ auth.authenticated }}",
    "lang": "{{ request.query.lang | default:\"en\" }}"
  }
}
```

Anonymous, with `?lang=fr`:

```json
{ "id": 42, "viewer": "guest", "signed_in": false, "lang": "fr" }
```

Signed in as user `42`, with no `lang`:

```json
{ "id": 42, "viewer": "42", "signed_in": true, "lang": "en" }
```

A transformer can read the request's query string, so a resource can answer differently to `?lang=fr` without any column for it. Because the cache key includes the query, each combination is cached separately.

### Text, JSON text and numbers

```json
{
  "pick": ["id"],
  "set": {
    "price": "{{ record.price_minor | int }}",
    "tags_json": "{{ record.tags | json }}",
    "tags_text": "tags: {{ record.tags }}",
    "id_text": "{{ record.id | str }}"
  }
}
```

```json
{
  "id": 42,
  "price": 1250,
  "tags_json": "[\"a\", \"b\"]",
  "tags_text": "tags: [\"a\", \"b\"]",
  "id_text": "42"
}
```

`| json` and an embedded list both give JSON **text** (a string). A whole-value template with no filter would have given the list itself.

### Case after set

```json
{ "set": { "isNew": "{{ record.status }}" }, "pick": ["id", "isNew"], "case": "snake" }
```

```json
{ "id": 42, "is_new": "live" }
```

`case` converted the key `set` created. A `set` key you name in one case ends up in the other.

### Lists

A list is transformed record by record, with the same context for each:

```json
[{ "id": 42 }, { "id": 43 }]
```

from `{"pick": ["id"], "case": "camel"}`. A transformer cannot see the other records of the page, so it cannot rank, count or compare them.

## A debugging session, from a missing field to the cause

A client team reports that the `priceCents` field is `undefined` for some products.

**1. Read the raw response.** `GET /rest/v1/products/7` shows `price_cents`, snake case, and no `priceCents`. So this resource has no camel-case transformer, or an old one.

**2. Look at what the resource points at.** In **Build → Resources**, open `products`: the **Transformer** field in **Behaviour** is empty. Someone detached it, or the resource was promoted from an environment where it was never set.

**3. Check the other environment.** In staging, the same resource has `public_product` attached, and it shows `priceCents`. So the transformer exists in staging, and in production the resource simply does not name it. The resource was promoted **before** the transformer was attached in staging, and nobody promoted again.

**4. Fix.** Attach `public_product` to the production resource. The next request is correct, with no restart.

**5. Prevent it.** Promote with the default `include` (everything), so a resource and its transformer always travel together. Add a test that reads one product from each environment and checks for `priceCents`.

The lesson generalises: when a response shape differs between environments, compare **the resource's transformer field** first, then the transformer's definition. Both are definitions, so both are promoted, and either can lag.

## Troubleshooting

| What you see | Cause | Fix |
| --- | --- | --- |
| Every read of a resource is a `500` with `transformer_error` and `unknown transformer '<name>'` | The resource names a transformer that does not exist (never created, deleted, or not promoted) | Create or restore it under that name, or change the resource |
| Every read is a plain `500` after editing a transformer | A `set` template uses a filter that does not exist | Fix the filter name. The set is `default`, `upper`, `lower`, `str`, `int`, `float`, `bool`, `json`, `length`, `first`, `last`, `keys` |
| A `set` value is `null` and the column has data | Two templates side by side, or a path that is wrong | Add literal text at one end, or check the path. `auth.id` is `auth.user_id` |
| A `set` value is `false` or `null` only when the client uses `?select=` | The template reads a column the `select` dropped | Keep templates to columns always returned |
| A field I omitted is still in the response | The field is in a different door: an expanded row of another resource, an event, a Records read | Check the door. Each resource's own transformer applies only to its own responses |
| A field I omitted can still be learned | A filter on it | See [Filters can read what responses hide](#filters-can-read-what-responses-hide) |
| `cannot filter on unknown field '<renamed>'` | A client used the response name in a filter | Filters and sorts use the stored name |
| A new column shows up in responses | The transformer uses `omit` | Use `pick` |
| A column I added is missing from responses | The transformer uses `pick` | Add it to `pick` |
| `rename` made a field vanish | The new name was already a key, so one replaced the other | Choose a name that is not in use |
| Keys are snake case in the list envelope and camel case in the data | `case` applies to records only | Handle `per_page` in the client |
| A nested object keeps its snake case keys | `case` converts top-level keys only | Convert on the client, or store camel case in the JSON |
| A cached response has a space where a time has a `T` | A cached copy of a `set` datetime | Use `\| str` and accept one form, or avoid datetimes in `set` |
| The OpenAPI response has no schema | A resource with a transformer drops its schema | Describe the shape in a schema and route, or accept an untyped body |
| Studio's resource form does not show my transformer | It was set inline | Create a stored transformer and select it |
| My change does not seem to apply | A client or CDN caches the response | Request with a cache-busting header. Pawabase itself applies the change on the next request |

## Questions that come up

<AccordionGroup>
  <Accordion title="Does a transformer make a field secret?">
    No. It changes the response. The field can still be filtered on, appears in events, webhooks and realtime broadcasts, and is visible in the console. Treat `omit` as presentation.
  </Accordion>
  <Accordion title="Should I use omit or pick?">
    `pick` for anything public, because a column added later stays hidden. `omit` to remove a few known fields from an otherwise open shape. Using both is fine: `omit` runs first.
  </Accordion>
  <Accordion title="Can a transformer add a field?">
    Yes, with `set`. It can build a URL, a label, a default, a count or a caller-dependent value from templates.
  </Accordion>
  <Accordion title="Can a transformer change the shape for admins only?">
    Not declaratively. Use two routes with two transformers and two policies, or a Python transformer that reads `auth`.
  </Accordion>
  <Accordion title="Does it apply to create and update responses?">
    Yes. The 201 and the 200 bodies are shaped. Deletes return no body.
  </Accordion>
  <Accordion title="Does it apply to events?">
    No. Events, webhooks and realtime carry the raw record.
  </Accordion>
  <Accordion title="Do expanded relations use the parent's transformer?">
    No. Each related row uses its own resource's transformer. The parent's `case` renames only the key that holds the relation.
  </Accordion>
  <Accordion title="Why did the OpenAPI schema disappear?">
    A resource with a transformer has a computed response shape, so its `200` has no schema. Shape in a custom route if you need a typed contract.
  </Accordion>
  <Accordion title="What happens if I delete a transformer that is in use?">
    The delete succeeds, and every read of any resource that names it fails with `transformer_error`. Search for the name first.
  </Accordion>
  <Accordion title="Is there a limit on the number of steps or keys?">
    There are exactly five steps, in a fixed order. No other limit is enforced beyond what the response size allows.
  </Accordion>
  <Accordion title="Can I use a transformer in a flow?">
    Yes, with the **Transform** block (`transform.map`), which takes a value and a transformer, inline or by name. The template context is the flow's state instead of the request's.
  </Accordion>
  <Accordion title="Can I test a transformer without a resource?">
    Use a flow with `transform.map` and a fixed value, and run the flow. See [Flows](/flows/overview).
  </Accordion>
</AccordionGroup>

## What to remember

- **A transformer shapes a response. It does not secure data.** Filters, events, webhooks, realtime and the console see the raw field.
- **Five steps, fixed order**: `omit`, `pick`, `set`, `rename`, `case`.
- **Prefer `pick`.** An `omit` list leaks every column added later.
- **`set` reads the original record**, so a hidden column can feed a visible value.
- **Two templates side by side give `null`.** Put literal text at one end.
- **The caller is `auth.user_id`**, not `auth.id`.
- **Filters, sorts and `select` use stored names**, not renamed ones.
- **Create and update responses are shaped too.** The list envelope is not.
- **A missing or deleted transformer makes every read `500`.** It is not caught on save.
- **Editing a stored transformer applies on the next request**, cache included.
- **No schema in OpenAPI** for a resource with a transformer.

## Terms

| Term | Meaning |
| --- | --- |
| **Transformer** | A definition that reshapes a record on its way out |
| **Stored transformer** | A named definition that resources and routes refer to |
| **Inline transformer** | A definition written into one resource or route |
| **Python transformer** | A function registered with `@transformer("name")` in the project's code |
| **Step** | One of `omit`, `pick`, `set`, `rename`, `case` |
| **Template** | A `{{ path \| filter }}` string in a `set` value |
| **Record** | The row as the database returned it, with every column |
| **Raw record** | The record before any transformer. What events carry |
| **Deny list / allow list** | `omit` / `pick` |
| **Envelope** | The `data`, `page`, `per_page` and `total` wrapper of a list |
