One of the most common questions for new Pawabase developers is: *should this logic be a flow or a Python function?* The answer depends on the shape of the problem.

  <Card title="Flow" icon="waypoints">Declarative, visual, inspectable — the shape of the operation.</Card>
  <Card title="Code" icon="code">Imperative, compact, flexible — the algorithm itself.</Card>

## The decision framework

| Characteristic | Flow | Function |
| --- | --- | --- |
| **Shape** | Multi-step with branches, loops, error handling | A single algorithm or computation |
| **Visibility** | Anyone can follow arrows in Studio | Requires reading Python |
| **Versioning** | Saved per environment as JSON | Saved in project code, versioned with git |
| **Run history** | Built-in (`flow_runs`) | Only when dispatched as a job |
| **Best for** | *when X happens, check Y, then do Z* | *compute this from that* |
| **Escape hatch** | Calls functions via `function.call` | Can be called from flows |

## The hybrid pattern

The most common and recommended pattern is a **hybrid**: a flow handles the shape, and a function handles the algorithm.

```
flow: trigger → validate → function.call (algorithm) → write → notify
```

This pattern appears throughout the platform's own blueprints. The commerce blueprint's `submit_review` flow uses blocks for everything except one `db.query` step that checks for duplicate reviews — that step reads more naturally as SQL than as a chain of resource calls. But for the *algorithm* (pricing calculations, ranking, parsing), a function is clearer.

## When flows win

- **Multi-step automation** with branches, loops, and error handling
- **Operations triggered by events** (webhooks, schedules, resource changes)
- **Anything a non-engineer should understand** — flows are visible as graphs in Studio
- **Operations that need audit history** — every run is recorded in `flow_runs`

## When code wins

- **Pricing algorithms** — complex math with conditional logic
- **Parsing and transformation** — CSV imports, data normalization
- **Third-party SDK integration** — a library with a specific API
- **Anything performance-sensitive** — tight loops, numerical computation

## Calling code from flows

A flow calls a function with `function.call` for synchronous results or `queue.function` for background dispatch:

```json
{"id": "price", "data": {"block": "function.call", "config": {"function": "calculate_price", "input": {"items": "{{ steps.cart.output }}", "discount": "{{ vars.discount }}"}}}}
```

The function's return value is available immediately as `steps.price.output`.

## Calling flows from code

Code can dispatch flows as background jobs with `queue.flow` — but a function cannot call a function synchronously from within a flow's execution graph. Use `function.call` for synchronous composition within a flow, and `queue.function` for fire-and-forget.

## Detailed comparison

A deeper look at the differences between flows and code across every dimension of the platform. This comparison covers shape, visibility, versioning, run history, error handling, testing, performance, collaboration, flexibility, reusability, composition, security, observability, debugging, deployment, and cost.

## The flow lifecycle

Flows have a lifecycle that code does not: creation, compilation, execution, and run history. When you create a flow in Studio or in code, it is compiled into a graph of blocks. This graph is stored as a JSON document in the environment. When a trigger fires, the flow engine walks the graph step by step, executing each block and tracking state between blocks.

## The function lifecycle

Functions have a simpler lifecycle: registration, invocation, and result. A function is registered with the @function decorator, which validates that the handler is an async callable and stores it in the global function registry. When a flow calls the function via function.call, the worker looks up the function by project and name, creates a FunctionContext, and invokes the handler.

## Versioning differences

Flows are saved per environment as JSON documents with a version counter. The platform tracks flow versions automatically. Functions are saved in project code and versioned with git.

## Audit trail differences

Flows have built-in run history in the flow_runs table. Every execution is recorded with its steps, outputs, and duration. Functions only have run history when dispatched as background jobs.

## Error handling differences

Flows have built-in error handling with error edges on blocks. When a block raises an exception, the flow follows the error edge if available. Functions raise exceptions that propagate to the caller.

## Testing differences

Flows are tested by running the flow graph with a fake runtime. You create a FlowRun with the flow definition and a fake Runtime that implements the protocol. Functions are tested by calling the handler with a fake FunctionContext.

## Performance differences

Flows have the overhead of graph execution — each block is executed sequentially, and the state is tracked between blocks. Functions run directly without this overhead. However, inline function calls within a flow are fast, and background function calls have the overhead of job serialization and queueing.

## Visibility differences

Flows are visible as graphs in Studio. Anyone can follow the arrows and understand what happens. Functions require reading Python source code.

## Collaboration differences

Flows can be edited by non-engineers in Studio using the visual editor. Functions require Python knowledge. This makes flows better for teams where business stakeholders need to understand and modify logic.

## When to use both

The hybrid pattern: flow for orchestration, function for algorithm. A flow handles the shape — trigger, validate, branch, write, notify. A function handles the algorithm — pricing, ranking, parsing. The flow calls the function via function.call for the one step that is genuinely an algorithm.

## When to use neither

Some logic belongs in a resource hook or a policy, not in a flow or function. Resource hooks run at specific points in the resource lifecycle. Policies are conditions that decide yes/no. Transformers shape response data. Blocks are reusable flow components.

## Resource hooks vs flows

Resource hooks run at specific points in the resource lifecycle — on_create, on_update, on_delete. Flows are triggered by events, schedules, routes, and manual dispatches.

## Policies vs functions

Policies are conditions that decide yes/no. They are used to gate access and validate operations. Functions are computations that return values. Both use the same @policy and @function decorators.

## Transformers vs functions

Transformers shape response data. They are defined as @transformer-decorated functions and are applied to resource responses automatically. Functions are general-purpose computations called from flows.

## Blocks vs functions

Blocks are reusable flow components that appear in Studio's block palette. Functions are reusable Python code that can be called from flows.

## Custom blocks vs functions

Custom blocks are flow-level components added via the pawabase.blocks entry point. Functions are computation-level components added via the pawabase.functions entry point.

## Extension routes vs functions

Extension routes are HTTP handlers added via the pawabase.routes entry point. Functions are computation units called from flows.

## Events vs functions

Events trigger flows. The event system is the nervous system of the platform. Functions can emit events. The event system allows different parts of the platform to communicate.

## Schedules vs functions

Schedules trigger flows. The scheduler dispatches flow or function jobs at specified intervals. Functions can be called by schedules as background jobs.

## Summary

Choose flow for orchestration, function for algorithm, extension route for HTTP-specific logic.
