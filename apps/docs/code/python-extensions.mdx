Pawabase is extensible through Python packages installed in the platform's virtual environment. A package can add blocks, functions, and routes by declaring them in specific entry point groups. The platform discovers and loads them automatically at startup.

<CardGroup cols={3}>
  <Card title="Blocks" icon="puzzle-piece">`pawabase.blocks` - add custom blocks to Studio palette.</Card>
  <Card title="Functions" icon="function">`pawabase.functions` - add callable Python functions.</Card>
  <Card title="Routes" icon="route">`pawabase.routes` - add HTTP routes to the compiled app.</Card>
</CardGroup>

## Entry point groups

All extension types are discovered through Python importlib.metadata.entry_points():

| Entry point group | What it adds | Example |
| --- | --- | --- |
| `pawabase.blocks` | Custom blocks to the block registry | `stripe = "my_package.blocks:register"` |
| `pawabase.functions` | Callable functions to the function registry | `pricing = "my_package.functions:pricing"` |
| `pawabase.routes` | HTTP routes to the compiled app | `api = "my_package.routes:router"` |

## Package structure

```
my_package/
├── pyproject.toml
├── my_package/
│   ├── __init__.py
│   ├── blocks.py
│   ├── functions.py
│   └── routes.py
```

## pyproject.toml

```toml
[project]
name = "my-pawabase-extension"
version = "0.1.0"
dependencies = []

[project.entry-points."pawabase.blocks"]
stripe = "my_package.blocks:register"

[project.entry-points."pawabase.functions"]
pricing = "my_package.functions:calculate_price"

[project.entry-points."pawabase.routes"]
api = "my_package.routes:router"
```

## Registration functions

Each entry point resolves to a registration function that adds the extension to the platform registry:

```python
# my_package/blocks.py
from pawabase_core.flows.registry import BlockRegistry

def register(registry: BlockRegistry) -> None:
    registry.add(CreateCharge)
    registry.add(RefundCharge)

# my_package/functions.py
from pawabase import function

@function("calculate_price")
async def calculate_price(ctx, items, discount_code=None):
    ...

# my_package/routes.py
from sillo import router

@router.get("/health")
async def health(ctx):
    return {"status": "ok"}
```

<Note>
Entry points whose value starts with `pawabase_core.flows.blocks` are skipped during block registration. The built-in blocks are registered separately to prevent duplicate registration.
</Note>

## Loading order

Extensions load in dependency order. Errors during entry point loading are logged but do not crash the process.

## How blocks work

Blocks are the building blocks of flows. Each block has a key, title, category, config schema, and a run method. The BlockRegistry collects all blocks by key.

## Block registry details

The BlockRegistry is a dataclass with a blocks dictionary. The add() method validates that the block has a key. The catalogue() method returns descriptions for Studio.

## The default registry

default_registry() creates the process-wide registry. It registers built-in blocks first, then loads entry points from pawabase.blocks.

## Block describe

Each block class has a describe() method that returns a dict with the key, title, category, description, config, handles, and trigger flag.

## Block run method

The run method takes config and run parameters and returns a BlockResult. The BlockResult has output, handle, and stop fields.

## Block config schema

The config class attribute describes the block's configuration fields in the schema format of pawabase_core.schemas.

## Block handles

The handles class attribute lists the output handles in display order. The default is ['next']. Blocks with branching logic have additional handles.

## Block triggers

The trigger class attribute marks blocks that start a flow run. Only one trigger block should exist in a flow.

## Block raw_config

The raw_config class attribute indicates whether the configuration should have templates rendered.

## BlockResult

A BlockResult has output, handle, and stop fields. The flow engine uses these to determine the next step in the graph.

## Block errors

Blocks raise FlowError for expected errors and let unexpected errors propagate. The flow engine catches both and follows the error edge.

## Building custom blocks

To create a custom block, subclass Block, set the class attributes, and implement the run method. Register it via the pawabase.blocks entry point.

## Platform blocks

Platform blocks include: RequireAuth, CurrentUser, LookupUser, CheckPolicy, ResourceList, ResourceGet, ResourceCreate, ResourceUpdate, ResourceDelete, DatabaseQuery, DatabaseTransaction, CacheGet, CacheSet, CacheDelete, CacheInvalidate, EmitEvent, DispatchFlow, DispatchFunction, Publish, StoragePut, StorageRead, StorageSignedUrl, StorageDelete, SendMail, HttpRequest, SendWebhook, GetSecret, CallFunction, Log, Metric, Respond, RaiseError.

## Trigger blocks

Trigger blocks include: HttpTrigger, EventTrigger, ScheduleTrigger, ResourceTrigger, WebhookTrigger, RealtimeTrigger, JobTrigger, ManualTrigger.

## Control blocks

Control blocks include: If, Switch, ForEach, SetVariables, Merge, Delay, Stop, Retry.

## Data blocks

Data blocks include: Transform, Template, Pick, Validate, JsonParse, JsonStringify, Calculate, GenerateId, Hash, Now.

## Writing custom blocks

To write a custom block, create a class that subclasses Block, set the key, title, category, config, and handles, and implement the run method.

## Block testing

Blocks are tested by creating a FlowRun with the block and a fake runtime, then calling block.run(config, run) and checking the BlockResult.

## Block performance

Blocks are executed sequentially. The flow engine tracks the number of steps (max 10,000). Each block's run method is awaited.

## Block observability

Each block execution is recorded as a Step in the flow run's trace. The step includes the node, block, started_at, duration_ms, handle, output, and error.

## Functions extension

Functions are registered via the pawabase.functions entry point. Each entry point resolves to a callable that registers one or more functions.

## Routes extension

Routes are registered via the pawabase.routes entry point. Each entry point resolves to a Sillo Router instance.

## Extension loading

Extensions load in dependency order. The default_registry() function loads built-in blocks first, then loads entry points.

## Extension errors

If an extension fails to load, the error is logged and the extension is skipped. The platform continues to work with the extensions that loaded successfully.

## Extension development

To develop an extension, create a Python package with the entry point declarations. Install it in the platform's virtual environment.

## Extension distribution

Extensions are distributed as Python packages on PyPI or as local packages. They import `pawabase_core` from the Pawabase runtime they are installed into; it is not a separately installable package, so do not list it as a dependency.

## Extension testing

Extensions are tested by creating a BlockRegistry, calling the register() function, and verifying the blocks are added.

## Extension documentation

Extensions should document their blocks, functions, and routes. Each block should have a description shown in Studio.

## Extension loading mechanism

The default_registry() function creates the process-wide registry. It calls BlockRegistry() to create a fresh registry, then registers all built-in blocks, and finally loads entry points from pawabase.blocks.

## Extension entry point format

Each entry point value must be a callable that accepts a BlockRegistry and returns None. The callable is invoked during registry initialization.

## Extension skip list

Entry points whose value starts with pawabase_core.flows.blocks are skipped. This prevents duplicate registration of built-in blocks.

## Extension error handling

Errors during entry point loading are caught individually. The error is logged and the entry point is skipped.

## Extension dependency order

Extensions load in dependency order as specified in pyproject.toml.

## Extension block discovery

Blocks are discovered through entry_points(group='pawabase.blocks'). Each entry point resolves to a registration function.

## Extension function discovery

Functions are discovered through entry_points(group='pawabase.functions'). Each entry point resolves to a module containing @function-decorated callables.

## Extension route discovery

Routes are discovered through entry_points(group='pawabase.routes'). Each entry point resolves to a Sillo Router instance.

## Extension block describe metadata

Each block class has a describe() method that returns metadata for Studio. The metadata includes the key, title, category, description, config, handles, and trigger flag.

## Extension block configuration

Blocks have a config class attribute that describes configuration fields. Fields follow the schema format of pawabase_core.schemas.

## Extension block handles

Blocks have a handles class attribute that lists output handles in display order. The default is ['next'].

## Extension block triggers

Blocks have a trigger class attribute that marks blocks that start a flow run. Only one trigger block should exist in a flow.

## Extension block raw_config

Blocks have a raw_config class attribute that indicates whether templates should be rendered.

## Extension BlockResult

A BlockResult has output, handle, and stop fields. The flow engine uses these to determine the next step in the graph.

## Extension block error types

Blocks raise FlowError for expected errors and let unexpected errors propagate. The flow engine catches both and follows the error edge if available.

## Extension block testing

Blocks are tested by creating a FlowRun with the block and a fake runtime, then calling block.run(config, run) and checking the BlockResult.

## Extension block performance

Blocks are executed sequentially. The flow engine tracks the number of steps (max 10,000). Each block's run method is awaited.

## Extension block observability

Each block execution is recorded as a Step in the flow run's trace. Studio displays the trace visually.

## Extension function registry

Functions are stored in _registry in pawabase_core/functions.py. The registry maps (project, name) tuples to FunctionSpec objects.

## Extension function validation

Functions must be async callables. The @function decorator validates this using inspect.iscoroutinefunction(). Non-async functions raise TypeError.

## Extension function depth limit

call_function is depth-limited to 8 levels. This prevents infinite recursion from crashing the worker.

## Extension function timeout

Each function has a timeout parameter (default 30 seconds). The worker's WorkerOptions.timeout (default 300 seconds) controls the maximum job duration.

## Extension route registration

Routes use standard Sillo decorators. The router object is mounted alongside the generated routes.

## Extension route path

Extension routes are reachable at the path they are registered under. They are compiled into the environment's app alongside flow routes and resource routes.

## Extension summary

Extensions add custom blocks, functions, and routes through entry point groups. The platform discovers and loads them automatically.
