Most backend logic fits a flow's graph-of-blocks model. But some routes need capabilities a flow can't provide: streaming responses, WebSocket upgrades, custom middleware, file uploads processed in memory, or any logic that needs direct access to Sillo's `SilloApp` router and its full feature set. For those, **extension routes** let you write a standard Sillo route handler in Python.

## When to use extension routes

| Reach for | Why |
| --- | --- |
| **Extension routes** | Routes needing middleware, streaming, WebSockets, file uploads, or custom request/response handling |
| **Flows** | Multi-step automation that can be expressed as a graph |
| **Custom blocks** | Logic that needs to be reusable across multiple flows |

## Writing an extension route

Extension routes live in `code/<project>/routes.py` and register through the `pawabase.routes` entry point. They use standard Sillo decorators:

```python
# code/myproject/routes.py
from sillo import SilloApp, HttpContext
from sillo.app import router

@router.get("/export/{store_id}")
async def export_orders(ctx: HttpContext, store_id: str):
    # Full access to Sillo's request/response machinery
    rows = await ctx.db.query("SELECT * FROM orders WHERE store_id = ?", [store_id])
    return ctx.stream(rows, content_type="text/csv")
```

The route is compiled into the environment's app alongside flow routes and resource routes. It's reachable at `/rest/v1/...` or the path you register it under.

## Middleware and auth

Extension routes support the full Sillo middleware stack:

```python
@router.post("/webhook/stripe")
async def stripe_webhook(ctx: HttpContext):
    # Custom auth, custom headers, raw body access
    payload = await ctx.body()
    sig = ctx.headers.get("stripe-signature")
    # ... verify signature ...
    return {"received": True}
```

This is the only way to access the raw request body, custom headers, or WebSocket upgrade paths — flows only see the parsed `input` envelope.
