Most backend logic fits a flow's graph-of-blocks model. But some routes need capabilities a flow can't provide: streaming responses, WebSocket upgrades, custom middleware, file uploads processed in memory, or any logic that needs direct access to Sillo's `SilloApp` router and its full feature set.

<CardGroup cols={2}>
  <Card title="Flows" icon="waypoints">The default for backend logic -- declarative, inspectable, runs everywhere.</Card>
  <Card title="Extension routes" icon="route">Full Python access -- for routes that need middleware, streaming, or framework features.</Card>
</CardGroup>

## When to use extension routes

| Reach for | Why |
| --- | --- |
| **Extension routes** | Routes needing middleware, streaming, WebSockets, file uploads, or custom request/response handling |
| **Flows** | Multi-step automation that can be expressed as a graph |
| **Custom blocks** | Logic that needs to be reusable across multiple flows |

## Writing an extension route

Extension routes live in `code/<project>/routes.py` and register through the `pawabase.routes` entry point. They use standard Sillo decorators:

```python
# code/myproject/routes.py
from sillo import SilloApp, HttpContext
from sillo.app import router

@router.get("/export/{store_id}")
async def export_orders(ctx: HttpContext, store_id: str):
    rows = await ctx.db.query("SELECT * FROM orders WHERE store_id = ?", [store_id])
    return ctx.stream(rows, content_type="text/csv")
```

The route is compiled into the environment's app alongside flow routes and resource routes.

## Middleware and auth

Extension routes support the full Sillo middleware stack:

```python
@router.post("/webhook/stripe")
async def stripe_webhook(ctx: HttpContext):
    payload = await ctx.body()
    sig = ctx.headers.get("stripe-signature")
    return {"received": True}
```

This is the only way to access the raw request body, custom headers, or WebSocket upgrade paths.

## Streaming responses

Extension routes can stream responses using Sillo's streaming capabilities:

```python
@router.get("/stream")
async def stream(ctx: HttpContext):
    async def generate():
        for i in range(100):
            yield f"data: {i}\n\n"
    return StreamingResponse(generate(), media_type='text/event-stream')
```

## File uploads

Extension routes can handle file uploads directly:

```python
@router.post("/upload")
async def upload(ctx: HttpContext):
    file = await ctx.request.form()
    return {"filename": file.filename}
```

## WebSocket support

Extension routes can handle WebSocket upgrades:

```python
@router.websocket("/ws")
async def websocket_handler(ctx: HttpContext):
    async for message in ctx.websocket.iter_messages():
        await ctx.websocket.send_text(f"Echo: {message}")
```

## Custom response handling

Extension routes can return any response type supported by Sillo:

```python
@router.get("/download")
async def download(ctx: HttpContext):
    return FileResponse("/path/to/file.pdf", media_type="application/pdf")

@router.get("/redirect")
async def redirect(ctx: HttpContext):
    return RedirectResponse(url="https://example.com")
```

## Error handling

Extension routes can raise HTTP exceptions:

```python
from sillo import HTTPException

@router.get("/not_found")
async def not_found(ctx: HttpContext):
    raise HTTPException(status_code=404, detail="Not found")
```

## Route registration

Routes are registered via the `pawabase.routes` entry point group in `pyproject.toml`:

```toml
[project.entry-points."pawabase.routes"]
api = "my_package.routes:router"
```

## Routes vs functions

Extension routes are for HTTP-specific logic. Functions are for computation. Use extension routes when you need full HTTP framework access.

## Routes vs flows

Extension routes handle HTTP requests directly. Flows handle backend orchestration. Use extension routes for API endpoints that need to return HTTP responses.

## Testing routes

Test extension routes by creating a test client and making requests to the routes:

```python
from sillo.testclient import TestClient

async def test_health():
    client = TestClient(app)
    response = await client.get('/health')
    assert response.status_code == 200
    assert response.json() == {'status': 'ok'}
```

## Performance

Extension routes run in the API process. They have direct access to the Sillo framework and do not have the overhead of flow execution or job queueing.

## Security

Extension routes are subject to the same security model as the rest of the platform. Use middleware for authentication and authorization.

## Observability

Extension routes appear in the OpenAPI schema. Request and response data is logged.

## Adding routes

Extension routes are added through the pawabase.routes entry point group. Each entry point resolves to a Sillo Router instance.

## Router methods

The Sillo router supports all standard HTTP methods: get, post, put, delete, patch.

## Middleware

Extension routes can use Sillo middleware for authentication, logging, CORS, and other cross-cutting concerns.

## Streaming

Extension routes can stream responses using Sillo streaming capabilities. This is useful for Server-Sent Events, file downloads, and real-time data feeds.

## Request handling

Extension routes have full access to the HTTP request object. Use ctx.request to access the method, headers, body, query parameters, and cookies.

## Response customization

Extension routes can return any response type supported by Sillo. This includes JSON, HTML, file downloads, redirects, and custom headers.

## Authentication

Extension routes can use any authentication method supported by Sillo. Use middleware for JWT authentication, session-based authentication, or API key authentication.

## Error handling

Extension routes can raise HTTP exceptions for error responses. Use the Sillo HTTPException class.

## Route path

Extension routes are reachable at the path they are registered under. They are compiled into the environment app alongside flow routes and resource routes.

## Route registration

Routes are registered via the pawabase.routes entry point group. Each entry point resolves to a Sillo Router instance.

## Routes vs functions

Extension routes are for HTTP-specific logic. Functions are for computation. Use extension routes when you need full HTTP framework access.

## Routes vs flows

Extension routes handle HTTP requests directly. Flows handle backend orchestration. Use extension routes for API endpoints that need to return HTTP responses.

## Testing routes

Test extension routes by creating a test client and making requests to the routes. Use the Sillo test client.

## Performance

Extension routes run in the API process. They have direct access to the Sillo framework and do not have the overhead of flow execution.

## Security

Extension routes are subject to the same security model as the rest of the platform.

## Observability

Extension routes appear in the OpenAPI schema. Request and response data is logged.

## WebSocket support

Extension routes can handle WebSocket upgrades using the @router.websocket decorator.

## File uploads

Extension routes can handle file uploads directly using ctx.request.form().

## Custom response handling

Extension routes can return FileResponse, RedirectResponse, and other Sillo response types.
