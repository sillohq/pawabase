Every block's `run()` method and every function's body receive access to a `Runtime` -- a protocol defined in `pawabase_kit.flows.runtime` that declares one async method per platform capability.

<CardGroup cols={2}>
  <Card title="ApiRuntime" icon="server">The real implementation in `services/api/app/runtime.py` -- calls Sillo capabilities, Akountz, Angula, and the database.</Card>
  <Card title="FakeRuntime" icon="flask">A test double used in unit tests -- no network, no database, no real mail server.</Card>

## Why a protocol

A flow is data -- a JSON graph of blocks. For the engine to execute it without knowing anything about the platform, every block must call into a uniform interface rather than importing services directly.

1. **The same block code runs everywhere** -- against the real API in production, against a fake runtime in tests
2. **Blocks are testable without infrastructure** -- mock the runtime, feed it a definition, and verify the logic
3. **The platform can evolve its internals** without changing block code

## The protocol

```python
class Runtime(Protocol):
    # Data operations
    async def resource_list(self, resource, *, filters=None, sort=None, limit=50, offset=0) -> dict: ...
    async def resource_get(self, resource, record_id) -> dict | None: ...
    async def resource_create(self, resource, data) -> dict: ...
    async def resource_update(self, resource, record_id, data) -> dict | None: ...
    async def resource_delete(self, resource, record_id) -> bool: ...
    async def db_query(self, sql, params=None) -> list[dict]: ...
    async def db_transaction(self, operations) -> list: ...

    # Cache
    async def cache_get(self, key) -> Any: ...
    async def cache_set(self, key, value, ttl=None, tags=None) -> None: ...
    async def cache_delete(self, key) -> bool: ...
    async def cache_invalidate(self, tags) -> int: ...

    # Events, queues, realtime
    async def emit(self, name, payload) -> str: ...
    async def dispatch_flow(self, flow, input, *, delay=0, queue=None) -> str: ...
    async def dispatch_function(self, function, input, *, delay=0, queue=None) -> str: ...
    async def publish(self, channel, event, payload) -> dict: ...

    # Storage, mail, outbound
    async def storage_put(self, bucket, key, content, content_type='') -> dict: ...
    async def storage_read(self, bucket, key) -> str: ...
    async def storage_signed_url(self, bucket, key, method='GET', expires_in=300) -> str: ...
    async def storage_delete(self, bucket, key) -> bool: ...
    async def send_mail(self, to, subject, *, text=None, html=None, template=None, data=None) -> dict: ...
    async def http_request(self, method, url, *, headers=None, params=None, body=None, timeout=30, retries=0) -> dict: ...
    async def webhook_send(self, event, payload) -> dict: ...

    # Platform
    async def secret(self, name) -> str | None: ...
    async def call_function(self, name, input) -> Any: ...
    async def identity_user(self, user_id) -> dict | None: ...
    async def check_policy(self, ref, context) -> bool: ...
    async def log(self, level, message, data=None) -> None: ...
    async def metric(self, name, value=1.0, tags=None) -> None: ...
```

## Implementation: ApiRuntime

In the API, `ApiRuntime` implements every method by calling into Sillo's capabilities:

- `resource_*` -> the environment's `Store` via `state.store(resource)`
- `db_query` / `db_transaction` -> the environment's SQL source, with `is_read_only` enforcement on `db_query`
- `cache_*` -> `sillo.cache` (namespaced with `user:` prefix)
- `emit` -> the platform event bus
- `dispatch_flow` / `dispatch_function` -> `sillo.work.queue` via `RunFlowJob` / `RunFunctionJob`
- `publish` -> Angula
- `storage_*` -> `sillo.storage` (service credential)
- `send_mail` -> `sillo.mail` (dispatched as `SendMailJob`)
- `http_request` -> Sillo's HTTP client with retry
- `webhook_send` -> outbound webhook delivery queue
- `secret` -> the environment's secret store
- `call_function` -> in-process function call (depth-limited to 8)
- `identity_user` -> Akountz
- `check_policy` -> the policy engine
- `log` / `metric` -> structured logging / metrics store

## Implementation: BaseRuntime

`BaseRuntime` in `pawabase_kit.flows.runtime` provides a fallback via `__getattr__`. If a runtime doesn't implement a capability, `__getattr__` returns an async function that raises `NotAvailable`.

This means:
- A block using a missing capability fails with a clear message
- Custom blocks that assume capabilities not provided by a lightweight host get a descriptive error
- Test doubles only need to implement the methods they actually test

## Runtime in functions

Functions access the runtime through `ctx.runtime`, where `ctx` is a `FunctionContext` passed as the first argument.

```python
@function("my_func")
async def my_func(ctx: FunctionContext, query: str) -> list[dict]:
    rows = await ctx.runtime.db_query("SELECT * FROM items WHERE name = ?", [query])
    await ctx.runtime.cache_set("last_query", query, ttl=60)
    return rows
```

## Runtime in flows

Blocks use the runtime via the `run` method's `runtime` parameter. The flow engine passes the runtime to every block execution.

```python
class MyBlock(Block):
    async def run(self, config, run):
        rows = await run.runtime.db_query('SELECT * FROM items', [])
        return BlockResult(output=rows)
```

## Custom runtime

To create a custom runtime, subclass `BaseRuntime` and override the methods you need to customize.

```python
from pawabase_kit.flows.runtime import BaseRuntime

class CustomRuntime(BaseRuntime):
    async def current_user(self):
        return await self._get_user_from_token()

    async def check_policy(self, policy, subject, obj):
        return await self._check_custom_policy(policy, subject, obj)
```

## Runtime and the flow engine

The flow engine uses the runtime to execute blocks. Each block execution calls the runtime methods to access platform services. The flow engine manages the execution graph and tracks state between blocks.

## Runtime and the worker

The worker creates a runtime instance for each job. The runtime is passed to the function handler and the flow executor.

## Runtime configuration

The runtime is configured by the `WorkerOptions` and `SchedulerOptions`. The `PAWABASE_WORKER_CONCURRENCY` environment variable controls the number of concurrent runtime instances.

## Runtime observability

The runtime produces observable data including logs, metrics, and traces. Every method call is recorded in the flow trace.

## Runtime security

The runtime enforces security policies. The `check_policy` method is called before sensitive operations.

## The Runtime protocol

The Runtime protocol defines how the platform executes flows and functions. It is the interface between the execution engine and the platform services.

## BaseRuntime

BaseRuntime is the base implementation of the Runtime protocol. It provides default implementations for all methods.

## ApiRuntime

ApiRuntime is the runtime implementation used by the API worker. It extends BaseRuntime and provides HTTP-specific functionality.

## Worker runtime

The worker runtime is the runtime implementation used by the worker process. It handles job execution and function invocation.

## Runtime methods

The Runtime protocol defines methods for data operations, cache, events, storage, mail, and platform capabilities.

## Data operations

The runtime provides resource_list, resource_get, resource_create, resource_update, resource_delete, db_query, and db_transaction methods.

## Cache operations

The runtime provides cache_get, cache_set, cache_delete, and cache_invalidate methods for caching.

## Event emission

The emit method emits a platform event. Events are used for notifications and cross-service communication.

## Queue operations

The dispatch_flow and dispatch_function methods dispatch flows and functions as background jobs.

## Storage operations

The runtime provides storage_put, storage_read, storage_signed_url, and storage_delete methods.

## Mail operations

The send_mail method sends an email. It is dispatched as a SendMailJob in the background.

## HTTP operations

The http_request method makes an HTTP request. It uses Sillo's HTTP client with retry.

## Platform operations

The runtime provides secret, call_function, identity_user, and check_policy methods.

## Observability operations

The log and metric methods provide logging and metrics capabilities.

To create a custom runtime, subclass BaseRuntime and override the methods you need to customize.

## Runtime and the flow engine

The flow engine uses the runtime to execute blocks. Each block execution calls the runtime methods.

## Runtime and the worker

## Runtime configuration

## Runtime observability

## Runtime security

## Runtime testing

The FakeRuntime is used in unit tests. It implements the Runtime protocol without network or database access.

## Runtime best practices

Use the runtime protocol to access platform services. Never import services directly in block code.

## Runtime errors

If a runtime doesn't implement a capability, __getattr__ returns a function that raises NotAvailable.

## Runtime performance

The runtime is optimized for async execution. All methods are async coroutines.
