## Naming conventions

Event names follow a `domain.action` pattern using lowercase letters and dots:

```
domain.action
```

- **`domain`** — The source or category of the event (e.g., `order`, `user`, `mail`, `scheduler`)
- **`action`** — What happened (e.g., `paid`, `created`, `sent`, `fired`)

### Rules

1. **Lowercase only** — Event names are case-sensitive via `fnmatch.fnmatchcase`, so `order.paid` and `Order.Paid` are different events
2. **Dot-separated** — Use dots to separate domain and action, and segments within the domain or action
3. **No spaces or special characters** — Only lowercase letters, numbers, dots, and underscores
4. **Reverse-domain prefix for custom events** — Use `com.acme.order.paid` to avoid collisions with system events
5. **Consistent naming** — Once you define an event name, keep it stable. Changing it breaks existing subscriptions

### Reserved namespaces

The following event name prefixes are reserved by the platform and should not be used for custom events:

| Prefix | Reserved for |
| --- | --- |
| `user.` | Auth events (`user.signed_up`, `user.signed_in`, etc.) |
| `scheduler.` | Scheduler events (`scheduler.fired.<flow>`) |
| `job.` | Job lifecycle events (`job.dispatched.*`, `job.completed.*`, `job.failed.*`) |
| `mail.` | Mail events (`mail.sent`, `mail.failed`) |
| `webhook.` | Webhook events (`webhook.delivered`, `webhook.failed`) |
| `realtime.` | Realtime events (`realtime.message`) |
| `events.` | Internal event processing |

## System event names

### Resource events

Every resource emits events in the `<resource>.<action>` format where `<resource>` is the resource name and `<action>` is one of `created`, `updated`, `deleted`:

| Event name | Triggered by | Payload |
| --- | --- | --- |
| `<resource>.created` | `resource.create` | The created record |
| `<resource>.updated` | `resource.update` | The updated record |
| `<resource>.deleted` | `resource.delete` | The record before deletion |

Replace `<resource>` with your actual resource name (e.g., `orders.created`, `students.updated`, `teachers.deleted`).

### Auth events

| Event name | Triggered by | Payload |
| --- | --- | --- |
| `user.signed_up` | New account created | `{ email, user_id }` |
| `user.signed_in` | Successful sign-in | `{ user_id, method }` |
| `user.email_verified` | Email verification completed | `{ user_id, email }` |
| `user.password_changed` | Password changed | `{ user_id }` |
| `user.signed_out` | Session terminated | `{ user_id, method }` |
| `user.updated` | Profile updated | `{ user_id, fields }` |

### Scheduler events

| Event name | Triggered by | Payload |
| --- | --- | --- |
| `scheduler.fired.<flow>` | A schedule fires a flow | `{ flow, node, scheduled_at }` |
| `job.dispatched.<flow>` | `queue.flow` dispatches a flow | `{ flow, job_id, input }` |
| `job.dispatched.<function>` | `queue.function` dispatches a function | `{ function, job_id, input }` |
| `job.completed.<job_id>` | A background job finishes | `{ job_id, status, result }` |
| `job.failed.<job_id>` | A background job fails | `{ job_id, error }` |

### Mail events

| Event name | Triggered by | Payload |
| --- | --- | --- |
| `mail.sent` | An email is sent successfully | `{ to, subject, message_id }` |
| `mail.failed` | An email delivery fails | `{ to, subject, error }` |
| `mail.queued` | An email job is dispatched | `{ to, subject, template }` |

### Webhook events

| Event name | Triggered by | Payload |
| --- | --- | --- |
| `webhook.delivered` | A webhook delivery succeeds | `{ endpoint, event, status }` |
| `webhook.failed` | A webhook delivery fails | `{ endpoint, event, error }` |

### Flow and function events

| Event name | Triggered by | Payload |
| --- | --- | --- |
| `flow.completed.<flow>` | A flow finishes successfully | `{ flow, run_id, result }` |
| `flow.failed.<flow>` | A flow fails | `{ flow, run_id, error }` |

### Realtime events

| Event name | Triggered by | Payload |
| --- | --- | --- |
| `realtime.message` | A message is published to a channel | `{ channel, event, payload }` |
| `realtime.presence` | Presence state changes | `{ channel, joins, leaves }` |

### Platform events

| Event name | Triggered by | Payload |
| --- | --- | --- |
| `platform.started` | Platform initializes | `{ version, services }` |
| `platform.stopped` | Platform shuts down | `{ uptime }` |

## Wildcard patterns

`trigger.event` supports wildcard patterns using `*` which matches exactly one dot-separated segment:

| Pattern | Matches | Doesn't match |
| --- | --- | --- |
| `order.paid` | `order.paid` | `order.shipped` |
| `order.*` | `order.paid`, `order.cancelled`, `order.refunded` | `order.us.paid` |
| `*.created` | `user.created`, `order.created` | `user.deleted` |
| `order.*.paid` | `order.us.paid` | `order.paid` |
| `*.sent` | `mail.sent`, `webhook.sent` | `mail.failed` |
| `*` | All events | Nothing |

### Matching behavior

- Matching uses `fnmatch.fnmatchcase`, which is **case-sensitive**
- The `*` matches exactly one dot-separated segment — it does not match across dots
- Multiple wildcards are allowed in a single pattern
- An empty pattern or `*` matches all events

### Practical wildcard patterns

| Pattern | Use case |
| --- | --- |
| `*.created` | React to any resource creation |
| `order.*` | React to all order-related events |
| `mail.*` | React to all mail delivery events |
| `job.*` | React to all job lifecycle events |
| `com.acme.*` | React to all events from a specific tenant |
| `*.error` | React to all error events |

## Custom event naming

For custom events emitted via `event.emit`, choose names that follow the same `domain.action` pattern but use a reverse-domain prefix to avoid collisions:

```json
{
  "id": "emit-payment",
  "data": {
    "block": "event.emit",
    "config": {
      "event": "com.acme.payment.processed",
      "payload": { "charge_id": "ch_123", "amount": 2999 }
    }
  }
}
```

### Naming guidelines

1. **Use your domain as the prefix** — `com.yourcompany.*`, `org.yourschool.*`
2. **Keep actions specific** — `created`, `updated`, `deleted`, `processed`, `failed`, `completed`
3. **Don't use system prefixes** — Avoid `user.`, `order.`, `mail.`, `scheduler.`, `job.` prefixes
4. **Be consistent within your project** — Use the same pattern across all custom events
5. **Version your event names if needed** — `com.acme.v2.order.paid` for breaking changes

## Event name registry

You can discover all registered event names programmatically by checking the `EventLog`:

```python
from database.models import EventLog

# Get all unique event names in a project
event_names = await EventLog.filter(project=project_ref, env=env_name).values_list("name", flat=True).distinct()
```

## Event name discovery

You can discover all event names that have been emitted in a project programmatically:

```python
from database.models import EventLog

# Get all unique event names in a project/environment
event_names = await EventLog.filter(
    project=project_ref, env=env_name
).values_list("name", flat=True).distinct().order_by("name")
```

This is useful for building dynamic subscriptions — for example, a management dashboard that lists all available events and lets operators create subscriptions to them.

### Event name counts

You can also count events by name to understand your event volume:

```python
from collections import Counter
from database.models import EventLog
from datetime import datetime, timedelta

since = datetime.now(UTC) - timedelta(days=30)
counts = await EventLog.filter(
    project=project_ref, env=env_name, occurred_at__gte=since
).values_list("name", flat=True)
event_counts = Counter(counts)
# {"orders.created": 1452, "user.signed_up": 328, ...}
```

## Event name best practices

### Use descriptive names

Choose event names that clearly describe what happened:

- **Good**: `order.paid`, `user.signed_up`, `invoice.overdue`
- **Bad**: `evt1`, `action`, `something.happened`

### Keep names short but specific

Balance brevity with clarity. The name should be understandable without additional context:

- **Good**: `payment.processed`, `student.graded`
- **Bad**: `com.acme.platform.payment.transaction.processed.successfully`

### Version when the semantics change

If an event's payload shape or semantics change significantly, consider versioning the event name:

```json
// v1 - old format
{"event": "order.paid", "payload": {"order_id": "42"}}

// v2 - new format with tax info
{"event": "order.paid.v2", "payload": {"order_id": "42", "tax_minor": 299}}
```

This allows subscribers to migrate gradually. Old subscribers continue listening for `order.paid` while new subscribers listen for `order.paid.v2`.

## Event name troubleshooting

### Events not being received

1. **Check the event name** — Is it spelled correctly? Is it case-sensitive? Remember `fnmatch.fnmatchcase` is case-sensitive.
2. **Check the pattern** — Does your `trigger.event` pattern match the event name? `order.*` matches `order.paid` but not `order.us.paid`.
3. **Check the environment** — Is the event emitted in the same environment as the subscription?
4. **Check the project** — Events are scoped to a project. A subscription in project A doesn't see events from project B.

### Events being received multiple times

If you're receiving duplicate events, check:
- Are there multiple subscriptions matching the same event?
- Is the event being emitted from multiple sources?
- Are you running multiple instances of the event processor? (At-least-once delivery means duplicates are possible but rare.)

## Summary

Event names in Pawabase follow a simple `domain.action` pattern with case-sensitive matching, wildcard support via `*`, and reserved namespaces for platform events. Whether you're using system events from resource writes, auth actions, and scheduler firings, or emitting custom events via `event.emit`, the naming conventions ensure consistency and prevent collisions. Use reverse-domain prefixes for custom events, `fnmatch.fnmatchcase`-compatible patterns for subscriptions, and version your event names when semantics change.
