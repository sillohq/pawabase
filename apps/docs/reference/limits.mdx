Pawabase has well-defined limits for every aspect of the platform. These limits protect your deployment from runaway requests, excessive resource consumption, and denial-of-service scenarios. Most limits are configurable via environment variables, so you can tune them for your workload.

## Request limits

These limits control how large and how long requests can be.

### Body size limits

| Limit | Default | Configurable via | Description |
| --- | --- | --- | --- |
| `max_body_bytes` | 100 MB | `PAWABASE_MAX_BODY_BYTES` | Largest request body forwarded by the gateway |
| `max_upload_bytes` | 50 MB | `PAWABASE_MAX_UPLOAD_BYTES` | Maximum upload size in the API |
| `max_message_bytes` | 64 KB | `PAWABASE_ANGULA_MAX_MESSAGE_BYTES` | Largest WebSocket client message |

The gateway's `max_body_bytes` (default 100 MB) applies to all proxied requests. If a request body exceeds this limit, the gateway returns `413 payload_too_large` without forwarding to the upstream. The `max_upload_bytes` API setting (default 50 MB) is a secondary limit applied within the API's own request handling.

### Timeout limits

| Limit | Default | Configurable via | Description |
| --- | --- | --- | --- |
| `upstream_timeout` | 60s | `PAWABASE_UPSTREAM_TIMEOUT` | Gateway waits this long for an upstream response |
| `query_timeout` | 15s | `PAWABASE_QUERY_TIMEOUT` | Maximum time for `db.query` operations |
| `flow timeout` | flow-specific | Flow definition | Maximum execution time for a flow |
| `function timeout` | function-specific | Function definition | Maximum execution time for a function |
| `webhook timeout` | 15s | `DeliverWebhookJob` | Time limit for a single webhook delivery attempt |
| `job timeout` | 300s | `Job.timeout` | Maximum time a queued job can run |
| `websocket open_timeout` | 10s | `gateway/proxy.py` | Time to wait for the first WebSocket message |
| `request timeout` | 30s | `platform.outbound` | HTTP client timeout for outbound calls |

## Rate limits

The gateway enforces rate limiting on all authenticated requests. Rate limits are configured per-key (API key) and per-client address (IP).

| Limit | Default | Configurable via | Description |
| --- | --- | --- | --- |
| `rate_limit` | 600 | `PAWABASE_RATE_LIMIT` | Requests per rate limit window |
| `rate_window` | 60s | `PAWABASE_RATE_WINDOW` | Duration of the rate limit window in seconds |

Rate limiting uses Sillo's built-in limiter. The backend is Redis in production (shared across all gateway replicas) and in-memory for a single instance. With the in-memory backend, each gateway replica enforces its own limit independently — so if you run multiple gateway replicas with the in-memory backend, the effective limit is multiplied by the number of replicas.

When a client exceeds the rate limit, the gateway returns `429 Too Many Requests` with a `Retry-After` header indicating how many seconds to wait.

<Note>
Rate limits apply per publishable key or per client IP address (for unauthenticated requests). Different API keys have independent rate limits. The rate limit counter is scoped to the `(project, env, key)` tuple.
</Note>

## Concurrency and queue limits

### Worker concurrency

| Limit | Default | Configurable via | Description |
| --- | --- | --- | --- |
| `worker concurrency` | 4 | `PAWABASE_WORKER_CONCURRENCY` | Concurrent jobs per worker process |
| `inline worker concurrency` | 2 | `InlineWorker` | Concurrency for inline workers (half of standalone) |

More worker replicas or higher concurrency means more jobs processed in parallel. The practical limit depends on your database connection pool size and the I/O profile of your jobs. CPU-bound jobs are limited by CPU; I/O-bound jobs are limited by network latency.

### Job timeouts

| Limit | Default | Description |
| --- | --- | --- |
| `flow job timeout` | 300s | `RunFlowJob.timeout` — maximum time a flow job can execute |
| `function job timeout` | 300s | `RunFunctionJob.timeout` — maximum time a function job can execute |
| `webhook job timeout` | 30s | `DeliverWebhookJob.timeout` — time limit for a single delivery attempt |
| `mail job retries` | 3 | `SendMailJob.tries` — number of retry attempts for email delivery |
| `mail job backoff` | 5s | `SendMailJob.backoff` — seconds between mail job retries |
| `webhook job retries` | 5 | `DeliverWebhookJob.tries` — number of retry attempts for webhook delivery |
| `webhook job backoff` | 2s | `DeliverWebhookJob.backoff` — seconds between webhook retries |

### Queue limits

The platform uses Redis-backed queues via Sillo's `ConnectionManager`. The default platform queues are:

- `events` — event fan-out and processing
- `webhooks` — outbound webhook deliveries
- `flows` — flow executions triggered by events or schedules
- `functions` — Python function invocations
- `mail` — email sending
- `default` — catch-all queue

You can add custom queues via `PAWABASE_WORKER_QUEUES`. Each queue has no hard depth limit — jobs accumulate in Redis until a worker processes them.

## Scheduler limits

| Limit | Default | Configurable via | Description |
| --- | --- | --- | --- |
| `RECONCILE_SECONDS` | 15s | `scheduler.py` | How often the scheduler reconciles its job table |
| Schedule count | No limit | Database | Any number of schedules can be registered |

**Run exactly one scheduler.** Sillo's scheduler keeps its registered jobs in memory. Two scheduler processes will each independently decide "it's time" and each independently queue or emit the same job. This is the one process in the topology that does **not** scale horizontally.

## Storage limits

| Limit | Default | Configurable via | Description |
| --- | --- | --- | --- |
| `storage_root` | `storage/objects` | `PAWABASE_STORAGE_ROOT` | Directory for local object storage |
| `default_data_url` | `sqlite:///data/envs/{project}__{env}.db` | `PAWABASE_DEFAULT_DATA_URL` | Fallback database for unconfigured environments |
| SQLite concurrency | 1 connection | N/A | SQLite doesn't support concurrent writes — use Postgres for multi-replica |

The default SQLite fallback databases are **not** safe for concurrent access. If any environment uses SQLite as its `database_url`, run only one API replica for that environment. Postgres is the only safe choice for multi-replica API deployments.

## Angula realtime limits

| Limit | Default | Configurable via | Description |
| --- | --- | --- | --- |
| `max_channels` | 100 | `PAWABASE_ANGULA_MAX_CHANNELS` | Maximum channels one connection may join |
| `max_message_bytes` | 64 KB | `PAWABASE_ANGULA_MAX_MESSAGE_BYTES` | Largest client message accepted |
| `history_bytes` | 256 KB | `PAWABASE_ANGULA_HISTORY_BYTES` | Payload bytes retained per channel for replay |
| `idle_timeout` | 300s | `PAWABASE_ANGULA_IDLE_TIMEOUT` | Seconds without traffic before a peer is pruned |
| `PRUNE_SECONDS` | 30s | `angula/bootstrap.py` | How often the prune loop runs |

## Mail limits

| Limit | Default | Configurable via | Description |
| --- | --- | --- | --- |
| `mail job retries` | 3 | `SendMailJob.tries` | Number of retry attempts for email delivery |
| `mail job backoff` | 5s | `SendMailJob.backoff` | Seconds between mail job retries |
| `suppress_send` | false (if mail configured) | `infra.mail.suppress` | When true, messages are logged but not sent |

If no SMTP configuration is present (`infra.mail.host` is not set), all messages are automatically suppressed. The `MailLog` records `status: "suppressed"` for each message, so you can verify that mail logic is working correctly without an SMTP server.

## Tuning limits for production

For high-traffic deployments, consider these adjustments:

### Increase request limits

```bash
PAWABASE_MAX_BODY_BYTES=500000000    # 500 MB for large file uploads
PAWABASE_UPSTREAM_TIMEOUT=120.0       # 2 minutes for slow upstreams
```

### Increase rate limits

```bash
PAWABASE_RATE_LIMIT=2000              # 2000 requests per window
PAWABASE_RATE_WINDOW=60               # 60-second window
```

### Increase worker capacity

```bash
PAWABASE_WORKER_CONCURRENCY=16        # 16 concurrent jobs per worker
PAWABASE_WORKER_QUEUES="events,webhooks,flows,functions,mail,default,bulk"
```

### Adjust timeouts for long-running jobs

```python
# In your job class definition
class LongRunningJob(PawabaseJob):
    queue = "default"
    timeout = 900.0  # 15 minutes instead of the default 120s
```

<Warning>
Increasing `max_body_bytes` beyond what your gateway can handle may cause memory issues. The gateway streams request bodies and does not buffer them, but very large bodies will consume file descriptors and network bandwidth. Always test with realistic payload sizes before changing production limits.
</Warning>

## Platform architecture limits

### Process limits

| Limit | Value | Description |
| --- | --- | --- |
| Services | 7 | Gateway, API, worker, scheduler, Akountz, Angula, Studio |
| Scheduler instances | 1 | Must run exactly one scheduler process |
| Gateway replicas | Unlimited | Stateless, horizontally scalable |
| Worker replicas | Unlimited | Queue-based, safe for horizontal scaling |
| API replicas | Unlimited | Stateless, compiled-app cache is a pure function |
| Angula instances | Multiple | With Redis pub/sub, instances share publications |

### Port assignments

| Service | Port | Environment variable |
| --- | --- | --- |
| Gateway | 8080 | `PAWABASE_GATEWAY_PORT` |
| API | 8001 | — |
| Worker | (no port) | — |
| Scheduler | (no port) | — |
| Akountz | 8002 | — |
| Angula | 8003 | — |
| Studio | 8090 | `PAWABASE_STUDIO_PORT` |

### Docker Compose configuration

The `docker-compose.yml` provides the default environment for all services. Key settings:

```yaml
x-pawabase: &pawabase
  image: ${PAWABASE_IMAGE:-pawabase:local}
  restart: unless-stopped
  env_file: .env

x-api-env: &api-env
  PAWABASE_APP_ENV: ${PAWABASE_APP_ENV:-production}
  PAWABASE_REDIS_URL: redis://redis:6379/0
  PAWABASE_API_URL: http://api:8001
  PAWABASE_AKOUNTZ_URL: http://akountz:8002
  PAWABASE_ANGULA_URL: http://angula:8003
  PAWABASE_GATEWAY_URL: http://gateway:8080
  PAWABASE_STUDIO_URL: http://studio:8090
  PAWABASE_DATABASE_URL: postgres://pawabase:${POSTGRES_PASSWORD}@postgres:5432/pawabase
  PAWABASE_DEFAULT_DATA_URL: ${PAWABASE_DEFAULT_DATA_URL:-sqlite:///data/envs/{project}__{env}.db}
  PAWABASE_STORAGE_ROOT: /data/objects
  PAWABASE_CODE_PATH: /code
  PAWABASE_INLINE_WORKER: "false"
  PAWABASE_INLINE_SCHEDULER: "false"
```

The `x-pawabase` and `x-api-env` compose extensions keep the configuration DRY across all 7 services.

## Database limits

| Limit | Default | Description |
| --- | --- | --- |
| Platform DB | Postgres | The main platform database |
| Per-environment DB | SQLite (dev) / Postgres (prod) | Each environment can have its own database |
| SQLite concurrency | 1 connection | SQLite doesn't support concurrent writes |
| Connection pool | Per-environment | `DataSourcePool` manages connections lazily |
| Query timeout | 15s | `PAWABASE_QUERY_TIMEOUT` |

When no `database_url` is configured for an environment, it falls back to `PAWABASE_DEFAULT_DATA_URL` (default: `sqlite:///data/envs/{project}__{env}.db`). The `{project}` and `{env}` placeholders are substituted at runtime, so each environment gets its own SQLite file.

<Warning>
SQLite fallback databases are not safe for concurrent access. If any environment uses SQLite, run only one API replica for that environment. Postgres is the only safe choice for multi-replica API deployments. In production, configure each environment with an explicit Postgres URL through Studio's Infrastructure settings.
</Warning>

## Redis limits

Redis is used for the event bus, queues, cache, and pub/sub. Key considerations:

- **Event stream** — The Redis-backed event bus uses Redis streams. Configure `maxlen` to control stream size and prevent unbounded memory growth.
- **Queue depth** — Queues have no hard depth limit. Jobs accumulate in Redis until a worker processes them.
- **Cache** — Sillo's cache (RedisCache or MemoryCache) stores compiled apps and key lookups. The cache is a pure function of the data it caches, so any replica can rebuild it independently.
- **Pub/sub** — Angula uses Redis pub/sub for multi-instance realtime. Without Redis, realtime works within a single instance only.

If `PAWABASE_REDIS_URL` is empty, all services fall back to in-memory implementations. This is only correct for a single-process development setup, not for production or multi-replica deployments.

## Security limits

| Limit | Default | Description |
| --- | --- | --- |
| Secret length | 32+ chars | `INTERNAL_SECRET`, `JWT_MASTER_SECRET`, `MASTER_KEY` |
| Key cache TTL | 30s | How long resolved API keys are cached |
| Auth lockout threshold | 10 | Failed sign-ins before a temporary lock |
| Auth lockout duration | 15min | Duration of temporary lockout |
| Session TTL | 12 hours | Idle operator session duration |
| CORS origins | `*` (gateway) | Comma-separated list for gateway and Studio |

### Production security requirements

The `validate_for_production()` method checks that all three master secrets are 32+ character random values. If any development default (`dev-internal-secret-change-me-please`, etc.) remains, the service refuses to start in production mode (`PAWABASE_APP_ENV=production`).

Generate secrets with `openssl rand -hex 32` and store them in a secrets manager. Rotate them only as a break-glass operation — see [Upgrades](/self-hosting/upgrades) for the procedure.

## Deployment limits

### Single-host deployment

The `docker-compose.yml` runs all 7 services on a single host. This is suitable for development, testing, and small production deployments.

### Multi-host deployment

For larger deployments, you can run:
- Multiple gateway replicas behind a load balancer
- Multiple API replicas (each with its own compiled-app cache)
- Multiple worker replicas (independent consumers of the same queues)
- Multiple Akountz replicas (stateless, scale horizontally)
- Multiple Angula instances (with Redis pub/sub for shared realtime)
- Exactly one scheduler process (singleton constraint)
- Exactly one Studio instance (or multiple behind a session-consistent load balancer)

### Kubernetes deployment

In Kubernetes, internal service discovery is handled by DNS. The `PAWABASE_API_URL`, `PAWABASE_AKOUNTZ_URL`, `PAWABASE_ANGULA_URL`, `PAWABASE_GATEWAY_URL`, and `PAWABASE_STUDIO_URL` environment variables map to ClusterIP Services. Each service gets its own deployment and service resource.

## Summary

Pawabase's limits are designed to protect your deployment while providing enough flexibility for most workloads. Most limits are configurable via environment variables, so you can tune them for your specific needs. The one hard constraint — run exactly one scheduler — is fundamental to the architecture and cannot be relaxed. For everything else, whether it's increasing body sizes for large file uploads, adjusting rate limits for high-traffic projects, or scaling workers for more concurrent jobs, the platform gives you the knobs to optimize your deployment.
