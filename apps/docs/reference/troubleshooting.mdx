This page collects the issues you're most likely to hit when building and operating a Pawabase backend, what they mean, and how to fix them. It's organized by symptom — if you see something unexpected, scan the table below and jump to the relevant section.

> This page covers **platform-level** issues you encounter when running Pawabase or configuring your backend through Studio or the API. For application-level errors (HTTP 400s, 401s, 403s, policy refusals), see [Errors](/reference/errors) and [Policies → Debugging](/policies/debugging).

## Quick reference

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| API returns 401 for a key that worked yesterday | Key expired, environment changed, or secret rotated | Check [API keys](/operate/api-keys) and [Secrets](/operate/secrets) |
| Flow doesn't trigger on event | Trigger not connected to the event, or subscription missing | Check [Event subscriptions](/events/subscriptions) and the flow's trigger block |
| Policy refuses access unexpectedly | `$auth` or `$record` resolves differently than expected | Use the [policy debugger](/policies/debugging) and the state inspector |
| Database connection errors on startup | DATABASE_URL misconfigured or database unreachable | Verify [environment settings](/reference/environment-settings) |
| Realtime channel not receiving updates | Channel rule doesn't match the event, or connection not subscribed | Check [channel rules](/realtime/channel-rules) |
| File upload fails with 403 | Storage policy refusal | Check [storage access](/storage/access) policies |
| Function times out | Function exceeds the configured timeout, or blocks the worker | Review [function timeout](/reference/limits) and async dispatch |
| Migration fails during upgrade | Schema conflict between old and new versions | Follow the [upgrade guide](/self-hosting/upgrades) |

## Authentication and authorization

### "401 Unauthorized" on a key that worked before

**What it means:** The API key you're using is no longer valid for this environment.

**Check:**
1. **Key rotation** — If you recently rotated the secret key in Studio, old keys stop working immediately. Generate a new one under [API keys](/operate/api-keys).
2. **Environment mismatch** — Each environment has its own set of keys. A key issued for `development` won't work in `production`. Verify you're using the right key for the environment.
3. **Expired user token** — If you're using a user's Bearer token (not an API key), check if it expired. User access tokens expire after 1 hour; use the refresh token to get a new one. See [Tokens and sessions](/auth/tokens-and-sessions).

**Fix:** Use the correct, current key from the right environment's API keys page in Studio.

### "403 Forbidden" on a resource you should have access to

**What it means:** The policy engine evaluated and refused the request. This is different from "no policy exists" — it means a policy exists and said "no."

**Check using the policy debugger:**
1. In Studio, open the resource and the specific operation (e.g., `products.create`).
2. Click "Debug policy."
3. Select the caller context (user, role, org, AAL) and the input data.
4. The debugger shows every step: which policy matched, what `$auth` and `$record` resolved to, and which condition caused the refusal.

**Common causes:**
- **Role mismatch:** The caller's `$auth.roles` doesn't include the role required by the policy.
- **Org mismatch:** `$auth.org` doesn't match `$record.organization_id`.
- **AAL too low:** The policy requires `aal2` (MFA) but `$auth.aal` is `aal1`.
- **Owner field:** The policy assumes `owner_field` is set, but the record's field is null or mismatches the caller.

**Fix:** Adjust the policy condition in Studio, or fix the data so the condition matches.

### User can't see records from other users

**What it means:** This is usually **by design** — the policy is working correctly by scoping records to the owner.

**Check:**
- If this is a `list` operation, check whether the policy includes a `filter` that restricts to records owned by `$auth.user_id`. A well-designed list policy should filter by ownership AND enforce per-row access.
- If this is a `get` operation, check the policy's `eq` condition comparing `$auth.user_id` to the record's `owner_field`.

**Fix:** If cross-user access is needed, design a policy that explicitly grants it (e.g., a "viewer" role that can read all records). Otherwise, this is expected behavior.

## Flows

### Flow doesn't trigger when expected

**Check:**
1. **Trigger connection** — In the flow editor, verify the trigger block is connected. A flow with no trigger runs only when invoked manually or via API call.
2. **Event subscription** — If the trigger is an event trigger, verify the subscription exists. Go to [Events → Subscriptions](/events/subscriptions) and confirm the event name matches what your code emits.
3. **Schedule syntax** — If the trigger is a schedule, verify the cron expression is valid. `* * * * *` runs every minute; `0 3 * * *` runs at 3 AM daily.
4. **HTTP route** — If the trigger is an HTTP route, verify the route path matches what callers send.

**Debug:**
- In Studio, check the **Flow runs** panel. If the flow never appears, it was never triggered.
- Check the **Events** panel to see if the triggering event was emitted.
- Check the **Audit log** for any error during trigger evaluation.

### Step output is `null` when I expect a value

**What it means:** The step either didn't run, produced no output, or its output is at a different key.

**Check:**
1. **Step ran** — In the execution trace, verify the step's handle was taken. If a `control.if` before this step took the `false` branch, this step never ran.
2. **Output key** — Every block writes its output under a key. Check the block's documentation in [Block reference](/flows/block-reference) to see what key it writes.
3. **Step ID** — When referencing a step's output, use `$step.<block_id>`, not `$step.<display_name>`. The block ID is the lowercase identifier you set in the editor, not the step's title.

**Debug:**
- In Studio's execution inspector, expand the **State** panel at the step boundary. You can see the exact content of `steps` at that point.

### Condition always evaluates to `false`

**Check:**
1. **Literal vs. path** — `{"truthy": "name"}` checks whether the literal string `"name"` is truthy (it is — any non-empty string is). To check a runtime value, use `{"truthy": "$input.name"}`.
2. **Type mismatch** — `{"eq": ["$input.count", "5"]}` compares a number to the string `"5"`, which is always `false`. If `$input.count` is a number, use `{"eq": ["$input.count", 5]}` (without quotes).
3. **Missing path** — `$input.missing_key` resolves to `null`, and `{"truthy": null}` is `false`. Add a default or check for existence first.
4. **Boolean operators** — `all` requires every sub-condition to be `true`. If one fails, the whole thing fails. Check each sub-condition individually.

### "Function call failed" or "Step crashed"

**What it means:** A `function.call` block invoked a Python function that raised an exception or timed out.

**Check:**
1. **Error details** — In the execution trace, the step that failed shows the exception type and message. Click to expand the full traceback.
2. **Timeout** — Functions have a configurable timeout (default 30s for inline calls, 300s for background jobs). If the function takes longer, it's killed. See [Limits](/reference/limits).
3. **Input validation** — The function received input that didn't match its expected type. Check the function's signature and the data being passed.
4. **External dependency** — The function tried to reach a database, HTTP endpoint, or file that was unavailable.

**Fix:** Add error handling inside the function (try/except), validate input types, and use background dispatch (`queue.function` instead of `function.call`) for long-running work.

## Storage

### Upload fails with 403 "Not allowed"

**What it means:** The storage policy refused the upload.

**Check:**
1. **Bucket policy** — Go to Studio → Storage → Buckets, select the bucket, and check the "Write" policy. The policy must evaluate to `true` for the caller's `$auth` context and the file being uploaded.
2. **Content type** — If the policy filters by MIME type, verify the file's content type matches.
3. **File size** — Check the [limits](/reference/limits) page. Payloads over 100MB are rejected before policy evaluation.

### Downloaded file has wrong content type or encoding

**What it means:** The file's metadata wasn't set correctly at upload time.

**Check:**
- When uploading via the SDK, explicitly pass `contentType`. If omitted, Pawabase guesses from the file extension, which can be wrong for unusual formats.
- For files stored with a driver (e.g., S3-compatible), verify the bucket's metadata settings in Studio.

## Realtime

### "Connection refused" or WebSocket won't connect

**Check:**
1. **Gateway URL** — The realtime endpoint is `wss://api.<project>.pawabase.io/realtime` (or your custom domain). Verify the URL and protocol (`wss://`, not `ws://`).
2. **API key** — Pass the publishable key as the `apikey` query parameter. Service keys don't work over WebSocket.
3. **CORS** — If connecting from a browser, the gateway must allow the origin. Check [Rate limits and CORS](/operate/rate-limits-and-cors).

### Not receiving expected messages on a channel

**Check:**
1. **Channel rule** — Each channel has a rule that determines who can subscribe and what events they receive. See [Channel rules](/realtime/channel-rules).
2. **Subscription** — Verify the client is subscribed to the correct channel path. Channel paths are case-sensitive.
3. **Event emission** — The event must be emitted by a flow, function, or resource operation. Check the [Events catalog](/events/catalog) for the exact event name.

### Realtime updates stop after a while

**What it means:** The WebSocket connection was likely dropped by an intermediate proxy or load balancer.

**Check:**
1. **Keepalive interval** — Pawabase sends WebSocket ping frames every 30 seconds. If your proxy has a shorter idle timeout (common: 60s), the connection drops. Set your proxy's idle timeout to at least 120s.
2. **Token expiry** — If using a user token, it expires after 1 hour. The client must refresh the token and reconnect.

## Database and data

### "relation does not exist" when querying a resource

**What it means:** The resource definition references a table or column that doesn't exist in your database.

**Check:**
1. **Database connection** — Verify `DATABASE_URL` points to the right database. The database must be running and accessible.
2. **Schema migration** — Resources automatically create tables on their first request, but only if the database user has `CREATE TABLE` permissions. If the table was created by an external migration, verify the column names match the resource definition.
3. **Schema name** — Resources default to the `public` schema. If your tables are in a different schema, set the schema in the resource definition under "Database schema."

### Resource operations return stale data

**What it means:** The cache hasn't been invalidated after a write.

**Check:**
1. **Cache TTL** — Resource responses are cached. The default TTL is 60 seconds. Check the resource's caching configuration.
2. **Cache bypass** — For reads that must be fresh, use the `?cache=false` query parameter (available on `list` and `get` operations).
3. **Write-through** — After a successful create/update/delete, the cache is invalidated. If you're writing directly to the database (bypassing the API), you need to invalidate the cache manually.

## Self-hosting and infrastructure

### "FATAL: database is uninitialized" in logs

**What it means:** The database container started but has no data, or the database URL doesn't match.

**Check:**
1. **First run** — On a fresh setup, run migrations before starting the stack: `docker compose run --rm api migrate`.
2. **DATABASE_URL** — Verify the URL in your `.env` matches the actual database container name and port. With Docker Compose, it's typically `postgresql://pawabase:secret@db:5432/pawabase`.
3. **Postgres version** — Pawabase requires PostgreSQL 16+. Check the version with `docker compose exec db pg_config --version`.

### "Address already in use" on port 8080

**What it means:** Another process is already listening on the gateway port.

**Fix:**
1. Stop the existing process: `docker compose down` or find and stop the process.
2. Or change the port in `.env` and `docker-compose.yml`:
   ```env
   PAWABASE_GATEWAY_PORT=8081
   ```

### Health check endpoint returns 503

**What it means:** One or more services are unhealthy.

**Check the health endpoint:**
```bash
curl -s https://your-domain/health
```

The response includes per-service status. Common causes:
- **Redis unavailable** — The API worker and event processor need Redis. Verify the Redis container is running.
- **Database unreachable** — Check the database connection and that migrations have been applied.
- **Missing environment variable** — Required variables like `PAWABASE_SECRET_KEY` or `DATABASE_URL` must be set.

### Slow first request after idle

**What it means:** The compiled app for the environment hasn't been built yet, and the first request triggers compilation.

**What happens:** The gateway receives the request, asks the platform API to compile the environment's definitions, and then forwards the request to the compiled app. This adds 1-5 seconds to the first request after a definition change.

**Fix:** This is expected behavior. Subsequent requests are fast. To pre-warm, trigger a request during deployment (e.g., a health check).

## Deployment and upgrades

### Migration failed during upgrade

**What it means:** The new version of Pawabase includes database migrations that couldn't be applied to your existing data.

**Check:**
1. **Read the changelog** — The entry in [Changelog](/reference/changelog) for your target version tells you whether the migration is destructive.
2. **Backup first** — Before any upgrade, create a backup: see [Backups](/self-hosting/backups).
3. **Error details** — The migration error specifies which column or constraint failed. Most failures are due to existing data violating the new constraint (e.g., null values in a column being made non-null).

**Fix:**
- If the migration is destructive and you have data you need to keep, you'll need to manually transform the data before re-running the migration.
- If you can't resolve the migration failure, roll back to the previous version and investigate.

### New feature doesn't appear after upgrade

**What it means:** The platform code was updated, but the environment's compiled app hasn't picked up the change.

**Fix:**
- Trigger a recompilation by making any change to a resource definition and saving it in Studio (even adding and removing a field).
- Or call the Platform API to invalidate the environment's compiled app cache.

## Getting help

If none of the above covers your issue:

1. **Check the logs** — Studio's observability panel shows recent logs from all services. Filter by service, severity, or search for keywords from the error message.
2. **Check the audit log** — Go to Operate → Audit log to see exactly what changed and when.
3. **Search the changelog** — Recent bug fixes are listed in the [Changelog](/reference/changelog).
4. **Report an issue** — If you've found a genuine bug, report it at `https://github.com/silloHQ/pawabase/issues` with the error message, steps to reproduce, and your Pawabase version.
