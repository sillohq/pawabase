Every request to a Pawabase project returns either a successful response or a structured error. Understanding the error shapes — and how to distinguish a validation failure from a server error, or a transient failure from a permanent one — is essential for building resilient clients.

## Error body shape

All errors return `application/json` with a consistent structure:

```json
{
  "message": "a human-readable description",
  "code": "machine_readable_code"
}
```

For validation failures, the shape differs slightly:

```json
{
  "message": "the request body is invalid",
  "details": [
    {"field": "email", "message": "must be a valid email address"},
    {"field": "quantity", "message": "must be at least 1"}
  ]
}
```

The `code` field is the most reliable way to distinguish errors programmatically — it never changes, unlike the human-readable `message` which may be localized or updated between versions.

## Status codes

| Code | Meaning | When |
| --- | --- | --- |
| `200`–`299` | Success | Normal operation |
| `400` | Bad request | Malformed JSON, unknown fields, invalid types |
| `401` | Unauthenticated | Missing or invalid API key / bearer token |
| `403` | Forbidden | Authenticated but not authorized — `sign-up is disabled`, `missing_role`, `confirm your email address first` |
| `404` | Not found | Resource, flow, project, or environment doesn't exist |
| `409` | Conflict | Resource already exists, flow is disabled |
| `422` | Validation | Field-level validation failure |
| `500` | Server error | Unexpected failure in the API |
| `504` | Timeout | Flow exceeded its `timeout` setting |
| `502` | Bad gateway | Upstream service unavailable |
| `503` | Service unavailable | Service is starting or restarting |
| `504` | Upstream timeout | Gateway timed out waiting for the upstream |
| `413` | Payload too large | Request body exceeds `max_body_bytes` |
| `429` | Too many requests | Rate limit exceeded |

## Error code taxonomy

Error codes follow a `domain.action` pattern. They are stable across versions and can be used programmatically:

### Authentication and authorization

| Code | Status | Description |
| --- | --- | --- |
| `missing_api_key` | 401 | No API key provided |
| `invalid_api_key` | 401 | API key does not exist or is invalid |
| `unauthenticated` | 401 | Token present but invalid or expired |
| `missing_role` | 403 | User lacks the required role |
| `signup_disabled` | 403 | Sign-up is disabled for this project |
| `email_not_verified` | 403 | Email verification required but not completed |
| `account_locked` | 403 | Too many failed sign-in attempts |
| `invalid_credentials` | 401 | Wrong password or invalid grant type |
| `token_expired` | 401 | Access token has expired |
| `token_revoked` | 401 | Token was explicitly revoked |
| `mfa_required` | 403 | MFA verification required |

### Resource and data errors

| Code | Status | Description |
| --- | --- | --- |
| `resource_not_found` | 404 | The specified resource doesn't exist |
| `field_not_found` | 404 | A field within a resource doesn't exist |
| `record_not_found` | 404 | A specific record with the given ID doesn't exist |
| `resource_conflict` | 409 | A resource with this name already exists |
| `write_refused` | 403 | Policy prevented the write |
| `invalid_schema` | 422 | Data doesn't match the resource schema |
| `validation_failed` | 422 | Field-level validation error (see details array) |
| `missing_secret` | 400 | A `secret://NAME` reference can't be resolved |

### Flow and function errors

| Code | Status | Description |
| --- | --- | --- |
| `flow_not_found` | 404 | The specified flow doesn't exist |
| `flow_disabled` | 409 | The flow is disabled and cannot be invoked |
| `function_not_found` | 404 | The specified function doesn't exist |
| `timeout` | 504 | Flow or function exceeded its timeout |
| `unknown_block` | 400 | A flow references a block type that doesn't exist |
| `invalid_input` | 422 | Function input doesn't match the function's input schema |
| `flow_failed` | 500 | An unhandled error occurred during flow execution |
| `flow_cancelled` | 409 | The flow was cancelled (e.g., by a condition) |

### Queue and job errors

| Code | Status | Description |
| --- | --- | --- |
| `job_not_found` | 404 | The specified job run doesn't exist |
| `job_failed` | 500 | A job failed after all retries |
| `job_too_many_attempts` | 429 | Too many job failures in a short period |
| `queue_full` | 503 | The queue is at capacity |
| `job_timeout` | 504 | A job exceeded its timeout |

### Event and realtime errors

| Code | Status | Description |
| --- | --- | --- |
| `event_not_found` | 404 | The event log entry doesn't exist |
| `unknown_environment` | 404 | The project/environment combination doesn't exist |
| `channel_not_found` | 404 | The realtime channel doesn't exist |
| `channel_policy_denied` | 403 | The client's context can't subscribe or publish |
| `webhook_not_found` | 404 | The webhook endpoint doesn't exist |

### Gateway and infrastructure errors

| Code | Status | Description |
| --- | --- | --- |
| `missing_api_key` | 401 | No API key in the request |
| `invalid_api_key` | 401 | API key is malformed or doesn't match any key |
| `rate_limited` | 429 | Too many requests in the rate limit window |
| `origin_not_allowed` | 403 | CORS origin not in the allowed list |
| `payload_too_large` | 413 | Request body exceeds `max_body_bytes` |
| `upstream_timeout` | 504 | Upstream service timed out |
| `upstream_unavailable` | 502 | Upstream service is unreachable |

## Distinguishing error types

The `code` field is the most reliable way to distinguish errors programmatically:

- **Validation errors** — `code` is a validation-related string like `validation_failed`, `invalid_input`, `invalid_schema`; `details` array present with `422` status
- **Auth errors** — `code` like `unauthenticated`, `missing_role`, `signup_disabled`, `mfa_required`
- **Not found** — `code` like `resource_not_found`, `flow_not_found`, `unknown_environment`, `function_not_found`
- **Conflict** — `code` like `resource_conflict`, `flow_disabled`, `flow_cancelled`
- **Flow errors** — `code` like `timeout`, `unknown_block`, `flow_failed`, `invalid_input`
- **Resource errors** — `code` like `write_refused`, `missing_secret`, `validation_failed`
- **Queue errors** — `code` like `job_failed`, `job_timeout`, `queue_full`
- **Gateway errors** — `code` like `rate_limited`, `origin_not_allowed`, `upstream_timeout`

## Common validation errors

A `422` response includes a `details` array. Each entry has a `field` and `message`:

```json
{
  "message": "the request body is invalid",
  "details": [
    {"field": "email", "message": "must be a valid email address"},
    {"field": "quantity", "message": "must be at least 1 and at most 99"}
  ]
}
```

Clients should surface each `detail.message` to the user, ideally next to the corresponding form field. The `field` value matches the JSON path of the invalid field, so you can map it directly to a form input.

## Retry behavior

Some errors are transient and safe to retry:

| Status | Retry? | Strategy |
| --- | --- | --- |
| `500` | Yes | Exponential backoff with jitter |
| `504` | Yes | Retry the flow — it may have timed out but could succeed on a subsequent attempt |
| `429` | Yes | Respect the `Retry-After` header |
| `502` | Yes | Upstream temporarily unavailable — retry with backoff |
| `503` | Yes | Service restarting — retry with backoff |
| `400` | No | The request is malformed — fix it before retrying |
| `401` | No | Re-authenticate, don't retry the same request |
| `403` | No | The caller isn't authorized — retrying won't help |
| `404` | No | The resource doesn't exist |
| `409` | Sometimes | If the conflict is a duplicate creation, consider merging instead |
| `422` | No | Fix the input before retrying |
| `413` | No | The request is too large — reduce the payload size |

## Gateway-specific errors

When the gateway returns an error, it may include additional context in headers:

| Header | Description |
| --- | --- |
| `X-Request-ID` | Unique request identifier for tracing |
| `X-Service` | Which internal service the error came from |
| `Retry-After` | Seconds to wait before retrying (for 429 and 503) |

Use the `X-Request-ID` when reporting issues to the platform team — it allows them to trace the exact request through the gateway, API, and worker logs.

## Worker-specific errors

When a queued job fails, the error is recorded in the `FailedJobRecord` table and surfaced through Studio's **Observability → Jobs and Failures**:

```json
{
  "message": "job failed after 3 attempts",
  "code": "job_failed",
  "details": {
    "job_id": "job_abc123",
    "queue": "mail",
    "attempts": 3,
    "error": "SMTPConnectionError: Connection refused"
  }
}
```

The `error` field in the details contains the actual exception message from the job's `perform()` method. For webhook deliveries, it also includes the HTTP status code from the upstream endpoint.
