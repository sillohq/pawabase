Docker Compose is the recommended way to run Pawabase. A single command starts all services — the gateway, API, worker, scheduler, identity service (Akountz), realtime service (Angula), and Studio — each as a separate container with its own health checks and restart policy.

<Steps>
  <Step title="1. Install Docker">
    Pawabase requires Docker Engine 24+ with Compose V2. If you don't have Docker, install it from [docker.com](https://docs.docker.com/get-docker/).

    Verify:

    ```bash
    docker --version
    docker compose version
    ```
  </Step>

  <Step title="2. Get the compose file">
    Download the latest `docker-compose.yml` and `.env.example` from the [Pawabase release page](https://github.com/silloHQ/pawabase/releases):

    ```bash
    mkdir pawabase && cd pawabase
    curl -L https://github.com/silloHQ/pawabase/releases/latest/download/docker-compose.yml -o docker-compose.yml
    curl -L https://github.com/silloHQ/pawabase/releases/latest/download/.env.example -o .env.example
    ```
  </Step>

  <Step title="3. Configure secrets">
    Copy the example file and set the required secrets:

    ```bash
    cp .env.example .env
    ```

    Edit `.env` and fill in these **required** values:

    | Variable | What to set | How to generate |
    | --- | --- | --- |
    | `POSTGRES_PASSWORD` | Password for the Postgres user | `openssl rand -hex 16` |
    | `PAWABASE_INTERNAL_SECRET` | Signs internal service tokens | `openssl rand -hex 32` |
    | `PAWABASE_JWT_MASTER_SECRET` | Derives user token secrets | `openssl rand -hex 32` |
    | `PAWABASE_MASTER_KEY` | Encrypts secrets at rest | `openssl rand -hex 32` |
    | `PAWABASE_ADMIN_EMAIL` | First Studio operator email | Your email address |
    | `PAWABASE_ADMIN_PASSWORD` | First Studio operator password | 8+ chars, upper+lower+digit+symbol |
    | `PAWABASE_PUBLIC_URL` | Public URL clients use | `http://localhost:8080` for local, `https://api.yourdomain.com` for production |

    <Warning>
    **Never reuse secrets between environments.** Generate unique secrets for each project. Store `.env` outside version control; the file contains passwords and encryption keys.
    </Warning>

    <Note>
    `PAWABASE_COOKIE_SECURE` controls whether Studio's session cookie requires HTTPS. Leave it `false` for local development; set to `true` in production behind a TLS-terminating proxy.
    </Note>
  </Step>

  <Step title="4. Start the platform">
    ```bash
    docker compose up -d
    ```

    The first start pulls Docker images and initializes the database. This takes 30–60 seconds. Track progress:

    ```bash
    docker compose logs -f --wait
    ```
  </Step>

  <Step title="5. Verify everything is healthy">
    Each service has a health check. Wait for all to report healthy:

    ```bash
    docker compose ps
    ```

    All services should show `healthy` in the `State` column. If any shows `unhealthy`, check its logs:

    ```bash
    docker compose logs api
    ```

    Once healthy, Studio is at [http://localhost:8090](http://localhost:8090) and the API gateway is at `http://localhost:8080`.
  </Step>
</Steps>

## What each service does

| Service | Port | Purpose |
| --- | --- | --- |
| **gateway** | 8080 | The only public entry point for clients. Routes to API, Akountz, and Angula based on the path. |
| **studio** | 8090 | The web UI for configuring projects, resources, flows, and observing runs. |
| **api** | 8001 | Handles REST API requests, data plane operations, and triggers flow execution. |
| **akountz** | 8002 | Identity management: users, sessions, MFA, organizations. |
| **angula** | 8003 | Realtime engine: WebSocket channels, presence, message history. |
| **worker** | — | Background job processing, flow execution, email, webhooks. |
| **scheduler** | — | Cron and interval-based scheduled triggers. |
| **postgres** | 5432 | Platform state (definitions, audit log, sessions). |
| **redis** | 6379 | Job queue, event bus, realtime pub/sub, caching. |

<Note>
The gateway is the **only** port you need to expose to clients in production. Studio, API, Akountz, and Angula are on the internal network and should not be directly reachable from the internet.
</Note>

## Full environment variable reference

`.env.example` lists every variable Docker Compose reads. Everything below `POSTGRES_PASSWORD` in the file is either required or has a documented default:

| Variable | Required | Default | Purpose |
| --- | --- | --- | --- |
| `PAWABASE_INTERNAL_SECRET` | Yes | — | Signs service-to-service tokens and the gateway's signed `X-Pawabase-Context` header. Every service must see the same value. |
| `PAWABASE_JWT_MASTER_SECRET` | Yes | — | The master secret Akountz derives each environment's user-token signing key from (`derive_env_secret`). Rotating it invalidates every issued access and refresh token across every project and environment. |
| `PAWABASE_MASTER_KEY` | Yes | — | Encrypts environment secrets and webhook signing keys at rest, and seals MFA TOTP secrets in Akountz's database. |
| `POSTGRES_PASSWORD` | Yes | — | Password for the `pawabase` Postgres role. Compose creates the role and the `pawabase` and `akountz` databases (see `docker/postgres/init.sql`) using this value. |
| `PAWABASE_ADMIN_EMAIL` | Yes | `admin@example.com` | The first Studio operator's email, created automatically on first boot when no operator exists. |
| `PAWABASE_ADMIN_PASSWORD` | Yes | — | The first operator's password. Must contain upper- and lower-case letters, a digit and a symbol. |
| `PAWABASE_PUBLIC_URL` | Yes | `http://localhost:8080` | The externally-reachable gateway URL. Used to build links in emails, OAuth callback URLs, and signed storage URLs. Set this to your real domain before going live — see the [production checklist](#production-checklist) below. |
| `PAWABASE_PUBLIC_GATEWAY_URL` | Yes | `http://localhost:8080` | Usually identical to `PAWABASE_PUBLIC_URL`; kept as a separate variable for setups where the gateway is reachable at a different externally-visible address than the general public URL (for example behind two different reverse-proxy hostnames). |
| `PAWABASE_COOKIE_SECURE` | No | `false` | Whether Studio's session cookie requires HTTPS. Leave `false` for `http://localhost`; set `true` once you're behind TLS, or the cookie won't be sent and Studio sign-in will silently fail. |
| `PAWABASE_GATEWAY_PORT` | No | `8080` | The host port the `gateway` container's `8080` is published on. Change this if `8080` is already taken on your host. |
| `PAWABASE_STUDIO_PORT` | No | `8090` | Same idea, for Studio. |
| `PAWABASE_DEFAULT_DATA_URL` | No | `sqlite:///data/envs/{project}__{env}.db` | Where a project environment's own data lives when nothing is configured for it in Studio under **Settings → Infrastructure**. `{project}` and `{env}` are substituted per environment. Point this at a Postgres or MySQL URL instead if you don't want the default per-environment SQLite files inside the `api-data` volume. |
| `PAWABASE_IMAGE` | No | `pawabase:local` | The image tag Compose builds and runs. Set this to a published tag (for example from your CI registry) instead of building locally, once you have one. |
| `PAWABASE_APP_ENV` | No | `production` | Set automatically by the compose file's `x-pawabase` anchor; not something you normally need to touch by hand. |
| `PAWABASE_WORKER_CONCURRENCY` | No | `4` | How many jobs the `worker` container processes concurrently. Raise this if your flows do a lot of I/O-bound waiting (webhooks, outbound API calls); keep it closer to your CPU count if your workload is CPU-bound. |

<Note>
`PAWABASE_REDIS_URL`, `PAWABASE_API_URL`, `PAWABASE_AKOUNTZ_URL`, `PAWABASE_ANGULA_URL`, `PAWABASE_GATEWAY_URL` and `PAWABASE_STUDIO_URL` are set for you by the compose file's shared `x-pawabase` environment block, pointing at the other containers by their Compose service name (`http://api:8001`, `redis://redis:6379/0`, and so on). You don't set these yourself unless you're editing `docker-compose.yml` to change the topology.
</Note>

## Health checks in detail

Every service exposes `GET /health`, and Compose's health check for the application containers is identical (the `&health` YAML anchor):

```yaml
test: ["CMD", "python", "-c", "import os,urllib.request; urllib.request.urlopen('http://127.0.0.1:%s/health' % os.environ.get('PORT', '8001'), timeout=3)"]
interval: 10s
timeout: 5s
retries: 12
start_period: 20s
```

This runs *inside* the container, against the port that container's own `PORT` environment variable names (each service sets `PORT` explicitly in its `environment:` block — `8001` for `api`, `8002` for `akountz`, and so on). A `20s` start period means Compose won't mark a container unhealthy just because it's still booting; after that grace period, `12` retries at `10s` intervals means a container has up to two minutes of intermittent failures before Compose gives up and reports `unhealthy`.

`postgres` and `redis` use their own native health checks (`pg_isready`, `redis-cli ping`) with a shorter `5s` interval, because they typically become ready much faster than an application container that has to import Python modules and connect out to its database.

The `depends_on: { condition: service_healthy }` relationships in the compose file mean `akountz`, `api`, `worker` and `scheduler` all wait for `postgres` and `redis` to report healthy before starting, and `gateway`/`studio` wait for `api`/`akountz` (and, for `gateway`, `angula`) to report healthy before starting. This is why a `docker compose up -d` on a cold start takes 30–60 seconds even though the containers themselves start almost instantly — most of that time is health checks gating the startup order.

## Volumes and data persistence

```text
postgres  →  /var/lib/postgresql/data   (platform state)
redis     →  /data                      (queues, events, cache)
api-data  →  /data                      (compiled apps, storage objects, file-based queues)
```

Named volumes persist across `docker compose down` and `docker compose up`. They are also preserved across image upgrades, so your projects, users, and data survive restarts.

Back up regularly — see [Self-hosting → Backups](/self-hosting/backups).

## Production checklist

Before going live:

1. **Set `PAWABASE_PUBLIC_URL`** to your real domain with HTTPS.
2. **Set `PAWABASE_COOKIE_SECURE=true`** so Studio sessions require HTTPS.
3. **Use a reverse proxy** (Caddy or Nginx) in front of the gateway to terminate TLS. See [TLS setup](/self-hosting/tls).
4. **Set strong, unique secrets** — never commit `.env` with real secrets.
5. **Review resource limits** — set `PAWABASE_WORKER_CONCURRENCY` based on your CPU cores.
6. **Enable health checks** — the gateway exposes `/health` for your load balancer to monitor.
7. **Configure backups** — see the production checklist page.

## Managing the stack

```bash
docker compose up -d        # Start all services
docker compose down         # Stop all services (data persists)
docker compose restart      # Restart everything
docker compose logs -f api  # Follow API logs
docker compose exec api sh  # Open a shell in the API container
```

## Upgrading

```bash
docker compose pull          # Get the latest image
docker compose up -d         # Restart with the new version
```

Database migrations run automatically on startup. Check the [Upgrade guide](/self-hosting/upgrades) for version-specific steps and breaking changes.
