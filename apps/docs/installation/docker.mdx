Docker Compose is the recommended starting point for a self-hosted Pawabase installation. It runs Studio, the public gateway, background processing, PostgreSQL, Redis, and the platform services Pawabase needs as one managed stack.

This guide gets the platform running and ready for its first project. For a disposable workstation setup, [Run Pawabase locally](/installation/local-development) instead.

## Before you begin

You need:

- Docker Engine 24 or newer with Compose V2;
- a host with persistent disk and enough memory for the full stack;
- a DNS name and TLS termination before exposing Pawabase publicly;
- a secure place to store deployment secrets and backups.

Verify Docker:

```bash
docker --version
docker compose version
```

## 1. Get the deployment files

Download a tagged Pawabase release or clone the repository and check out the version you intend to operate. Keep `docker-compose.yml` and `.env.example` from the same release.

```bash
git clone https://github.com/silloHQ/pawabase.git
cd pawabase
git checkout <release-tag>
```

Do not combine a Compose file from one release with application images or environment examples from another.

## 2. Create the environment file

```bash
cp .env.example .env
```

At minimum, review and set:

| Variable | Purpose | Recommended value |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | Protects the bundled PostgreSQL role | Unique random value |
| `PAWABASE_INTERNAL_SECRET` | Authenticates communication inside the installation | `openssl rand -hex 32` |
| `PAWABASE_JWT_MASTER_SECRET` | Protects application user tokens | `openssl rand -hex 32` |
| `PAWABASE_MASTER_KEY` | Protects encrypted platform values | `openssl rand -hex 32` |
| `PAWABASE_ADMIN_EMAIL` | Email for the first Studio operator | Individual administrator address |
| `PAWABASE_ADMIN_PASSWORD` | Password for the first Studio operator | Unique strong password |
| `PAWABASE_PUBLIC_URL` | Externally reachable gateway URL | `https://api.example.com` |
| `PAWABASE_PUBLIC_GATEWAY_URL` | Gateway URL used in generated public links | Normally the same public URL |
| `PAWABASE_COOKIE_SECURE` | Requires HTTPS for Studio's session cookie | `true` in production |

Generate different random values for the three Pawabase secrets. These are installation-level root secrets, not ordinary project secrets.

<Warning>
Do not commit `.env`, print it in CI logs, paste it into support tickets, or copy production values into development. Losing the master or token secret can make encrypted data or active sessions unusable; exposing one can compromise every project on the installation.
</Warning>

Store the file with restrictive permissions:

```bash
chmod 600 .env
```

## 3. Choose public addresses

Applications call the gateway. Operators use Studio. Put both behind TLS before production, usually on separate hostnames:

```text
https://api.example.com     → Pawabase gateway
https://studio.example.com  → Pawabase Studio
```

Set `PAWABASE_PUBLIC_URL` and `PAWABASE_PUBLIC_GATEWAY_URL` to the gateway address that users and external providers can actually reach. These values are used for OAuth callbacks, email links, and signed URLs, so `localhost` is wrong in production even when the containers themselves are healthy.

Expose the gateway and Studio through your reverse proxy. Keep service ports, PostgreSQL, and Redis on a private network.

## 4. Start Pawabase

```bash
docker compose up -d
```

Watch startup:

```bash
docker compose ps
docker compose logs -f
```

The first start may take longer while images are built or pulled and databases are initialized. Do not begin configuration until the application containers report healthy.

## 5. Verify the installation

Check the gateway from the same network path your applications will use:

```bash
curl https://api.example.com/health
```

Open Studio over HTTPS and sign in with `PAWABASE_ADMIN_EMAIL` and `PAWABASE_ADMIN_PASSWORD`.

On first sign-in:

1. create the platform organization;
2. create a small test project;
3. save the generated keys;
4. call `/auth/v1/settings` through the public gateway with the test environment's publishable key;
5. confirm the request appears in Studio observability.

```bash
curl "https://api.example.com/auth/v1/settings" \
  -H "apikey: your-test-publishable-key"
```

This smoke test checks more than container health: it verifies public routing, API-key resolution, and project-environment selection.

## What to expose

| Surface | Internet access | Audience |
| --- | --- | --- |
| Gateway | Yes, through HTTPS | Web, mobile, server clients, and integrations |
| Studio | Restricted HTTPS | Trusted operators only |
| PostgreSQL | No | Pawabase services and backup tooling |
| Redis | No | Pawabase services only |
| Internal service ports | No | Compose network only |

Protect Studio with network controls or an identity-aware proxy in addition to its sign-in when possible. Studio can manage keys, secrets, users, data, and backend definitions.

## Persistent data

Compose volumes preserve platform databases, environment data that uses the bundled default, queued state, and locally stored objects across normal restarts.

```bash
docker compose down
docker compose up -d
```

Do not use `docker compose down -v` on an installation you intend to keep. The `-v` flag removes named volumes and can delete material data.

Before production:

- identify every persistent volume and external data service;
- create automated backups;
- encrypt backups and restrict access;
- test a restore into an isolated installation;
- document recovery time and recovery point expectations.

See [Backups](/self-hosting/backups) for the complete procedure.

## Application infrastructure

Pawabase platform state and your application's resource data are separate concerns. In the current Studio, database, storage, and mail infrastructure are configured by the installation operator rather than on the environment Settings page. Coordinate these values as part of deployment, and use Studio's **Operate → Settings** for CORS, public API documentation, realtime rules, and application-defined settings.

Use distinct production credentials for:

- the application database;
- S3-compatible object storage, if used;
- SMTP delivery;
- OAuth providers;
- outbound integrations and webhook signing.

Store sensitive provider values as Pawabase secrets and reference them using supported secret references instead of pasting credentials into reusable definitions.

## Browser origins

For every browser application, add the exact production origin under **Operate → Settings → CORS** in the correct project environment.

```text
https://app.example.com
https://admin.example.com
```

Do not add the gateway or Studio origin unless a browser application actually runs there. CORS controls which browser origins can make requests; it does not authorize a user or replace resource policies.

## Routine operations

```bash
docker compose ps                 # Check container health
docker compose logs -f gateway   # Follow gateway logs
docker compose restart           # Restart the stack
docker compose down              # Stop without deleting volumes
docker compose up -d             # Start again
```

Use Studio for application-level operations:

- **Observability** for request volume, latency, and failures;
- **Events & runs** for events, flow traces, webhooks, and mail;
- **Jobs & queues** for asynchronous work;
- **API keys** for issue, scope, and revocation;
- **Audit log** for operator changes.

Container logs are most useful for startup, dependency, network, or platform-health failures.

## Upgrade safely

Before an upgrade:

1. read the release notes and [upgrade guide](/self-hosting/upgrades);
2. back up all persistent data;
3. verify that the backup can be restored;
4. test the target version against a non-production copy;
5. record the currently deployed image or release tag;
6. plan a rollback window.

Then pull or build the approved version and recreate the stack:

```bash
docker compose pull
docker compose up -d
docker compose ps
```

Afterward, smoke-test sign-in, one protected resource operation, storage if used, realtime if used, and at least one important flow or job.

## Troubleshooting

| Symptom | First checks |
| --- | --- |
| A container is unhealthy | `docker compose ps` and that container's logs |
| Studio sign-in loops | HTTPS termination, `PAWABASE_COOKIE_SECURE`, browser cookie, public host |
| Public requests return `401` | `apikey` header and the key's project environment |
| Email or OAuth links point to localhost | Public URL settings and provider callback configuration |
| Browser requests fail before reaching the API | Exact CORS origin and reverse-proxy headers |
| Jobs remain pending | Worker health, Redis availability, and **Jobs & queues** |
| Realtime cannot connect | WebSocket proxying, gateway URL, key, token, and channel policy |
| Data disappears after recreation | Missing volume, changed mount, or different environment database setting |

## Production handoff

An installation is not production-ready merely because every container is healthy. Complete the [production checklist](/self-hosting/production-checklist), including TLS, restricted Studio access, durable infrastructure, backups, monitoring, key rotation, mail, CORS, rate limits, and restore testing.

After installation, continue with the [Quickstart](/quickstart) to build and call a backend through supported product interfaces.
