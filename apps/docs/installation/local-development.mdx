Run Pawabase locally when you want to learn the product, prototype a backend, or develop an application without connecting to shared infrastructure. This page is for people **using Pawabase to build an application**. It does not cover developing Pawabase itself.

The local stack gives you two addresses:

| Address | Purpose |
| --- | --- |
| `http://localhost:8090` | Pawabase Studio, where you configure the backend |
| `http://localhost:8080` | The gateway your application calls |

<Info>
For the quickest supported setup, use Docker Compose. If your team already operates a Pawabase installation, skip this page and use the Studio and gateway URLs they provide.
</Info>

## Prerequisites

Install Docker Engine with Compose V2. Give Docker enough memory for Pawabase, PostgreSQL, and Redis to run together.

```bash
docker --version
docker compose version
```

If either command is unavailable, install Docker Desktop or Docker Engine before continuing.

## 1. Get Pawabase

Clone the repository and enter it:

```bash
git clone https://github.com/silloHQ/pawabase.git
cd pawabase
```

For application development, use a tagged release or another version your team has approved. Avoid building important work against an arbitrary moving branch.

## 2. Start the development stack

The repository includes a development Compose configuration with local-only credentials:

```bash
docker compose -f docker-compose.dev.yml up
```

Keep this terminal open while you use Pawabase. On the first run, Docker builds images and downloads dependencies, so startup takes longer than later runs.

When the services are ready, open `http://localhost:8090` and sign in with:

```text
Email:    admin@pawabase.local
Password: Pawabase!admin1
```

<Warning>
These credentials and the bundled development secrets are public and intentionally weak. Use them only on your own computer. Never expose this development stack to the internet or reuse its credentials in a shared environment.
</Warning>

## 3. Create your workspace

On first sign-in, Studio asks for an organization. An organization owns projects and controls which teammates can manage them.

1. Enter an organization name and URL name.
2. Create a blank project.
3. Give it a stable reference such as `tasks-demo`.
4. Keep `development`, `staging`, and `production`, or remove the environments you do not need for this local experiment.
5. Create the project and save the generated keys.

Keys are shown once in the creation dialog. You can create replacements later under **Operate → API keys**, but you cannot reveal an existing secret value again.

Continue with the [Quickstart](/quickstart) to create a resource, configure access, and call the public API.

## 4. Confirm the gateway

The gateway is the only application-facing base URL. Check its health from another terminal:

```bash
curl http://localhost:8080/health
```

Then use the publishable key for your development environment to inspect the public authentication settings:

```bash
export PAWABASE_URL="http://localhost:8080"
export PAWABASE_KEY="your-development-publishable-key"

curl "$PAWABASE_URL/auth/v1/settings" \
  -H "apikey: $PAWABASE_KEY"
```

This checks the same boundary your web or mobile application uses. A healthy Studio alone does not prove that a client can reach the gateway with the correct environment key.

## Local data and isolation

The development stack is disposable. It is suitable for sample users, synthetic records, and test integrations. Do not copy production customer data into it.

Each Pawabase environment remains isolated even inside one local installation:

- API keys identify one environment;
- users and sessions belong to one environment;
- resource records belong to that environment's configured database;
- secrets, auth settings, webhook destinations, and realtime rules are environment-specific.

If a request returns an empty list or a token suddenly stops working, first check that the application's URL, API key, and user session all belong to the same environment.

## Start and stop the stack

Start in the foreground while learning:

```bash
docker compose -f docker-compose.dev.yml up
```

Stop it with `Ctrl+C`. To run it in the background:

```bash
docker compose -f docker-compose.dev.yml up -d
docker compose -f docker-compose.dev.yml ps
```

Stop background containers without deleting their data:

```bash
docker compose -f docker-compose.dev.yml down
```

Restart after a configuration change:

```bash
docker compose -f docker-compose.dev.yml restart
```

## Read logs

Follow all logs:

```bash
docker compose -f docker-compose.dev.yml logs -f
```

Choose logs based on the failed boundary:

```bash
# Application data request
docker compose -f docker-compose.dev.yml logs -f gateway api

# Sign-up or sign-in
docker compose -f docker-compose.dev.yml logs -f gateway akountz

# Flow or queued work
docker compose -f docker-compose.dev.yml logs -f api worker
```

Studio's **Events & runs**, **Jobs & queues**, and **Observability** pages should be your first debugging tools for configured application behavior. Container logs are most useful when the platform itself is unhealthy or a request never reaches those product-level records.

## Reset local data

A full reset deletes your local projects, users, resource records, uploaded files, keys, and run history. Export anything you want to keep before doing this.

```bash
docker compose -f docker-compose.dev.yml down -v
docker compose -f docker-compose.dev.yml up
```

<Warning>
The `-v` flag deletes the Compose volumes for this stack. It is intentionally destructive and cannot be undone unless you made a backup.
</Warning>

If you only need a clean application project, deleting that project in Studio is narrower than resetting the whole installation.

## Browser applications and CORS

A browser can call the gateway only from an allowed origin. In Studio:

1. Open the development environment.
2. Go to **Operate → Settings**.
3. Under **CORS**, add the exact origin of your application, such as `http://localhost:5173`.
4. Save the setting.

An origin includes the scheme, host, and port. `http://localhost:5173` and `http://127.0.0.1:5173` are different origins. Do not use a production-wide wildcard simply to fix a local CORS error.

## Connect a local application

Give the application only the gateway URL and a publishable key:

```bash
VITE_PAWABASE_URL=http://localhost:8080
VITE_PAWABASE_KEY=pk_your_publishable_key
```

Publishable keys are designed for browser and mobile clients. Secret keys bypass policies and must never appear in client bundles, mobile packages, public repositories, logs, or screenshots.

```js
const response = await fetch(`${import.meta.env.VITE_PAWABASE_URL}/rest/v1/tasks`, {
  headers: {
    apikey: import.meta.env.VITE_PAWABASE_KEY,
    Authorization: `Bearer ${accessToken}`,
  },
});

if (!response.ok) throw new Error(`Pawabase request failed: ${response.status}`);
const page = await response.json();
```

The publishable key selects the environment. The bearer token identifies the signed-in user. Most protected application requests need both.

## Common problems

| Symptom | What to check |
| --- | --- |
| Studio does not open | Run `docker compose ... ps`, then inspect Studio logs. |
| Gateway health check fails | Confirm port `8080` is free and inspect gateway dependencies. |
| Studio opens but API calls return `401` | Send the correct environment's publishable key in `apikey`. |
| Sign-in succeeds but a data request returns `401` | Send the access token as `Authorization: Bearer <token>`. |
| A request returns `403` | The caller reached Pawabase but the operation policy denied it. |
| A resource returns `404` | Confirm the operation is enabled and the table was created or migrated. |
| Browser reports a CORS error | Add the application's exact origin under **Operate → Settings**. |
| Data appears to vanish | Check the selected Studio environment and the application's API key. |
| A flow does not run | Confirm it is enabled, then inspect **Events & runs**. |
| Mail does not arrive | Configure mail for this environment and inspect its delivery record. |

## Move beyond local development

The development Compose stack is not a production deployment. Before accepting real traffic:

- use unique, randomly generated secrets;
- terminate TLS for the gateway and Studio;
- restrict Studio access;
- configure durable database and object storage;
- configure SMTP and external provider credentials;
- establish backups and restore tests;
- review CORS, API-key scopes, policies, and realtime channel rules;
- run the [production checklist](/self-hosting/production-checklist).

For a deployment-oriented setup, use [Docker installation](/installation/docker). For application building, continue to the [Quickstart](/quickstart).
