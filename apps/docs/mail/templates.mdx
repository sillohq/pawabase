Pawabase mail templates are written in Jinja2 and stored per environment. Templates define a subject line, an HTML body, and an optional plain-text body. They are rendered in Jinja2's sandboxed environment, so template authors cannot access Python internals or execute arbitrary code. This page covers the template system in complete detail: template structure, creation, data binding, Jinja2 features, sandbox restrictions, rendering without sending, naming conventions, storage, design patterns, partials, testing, and performance.

## Template structure

Each template has three fields:

| Field | Required | Description |
| --- | --- | --- |
| `subject` | Yes | The email subject line, rendered as a Jinja2 string |
| `html` | No | The HTML body, rendered as a Jinja2 template |
| `text` | No | The plain-text body, rendered as a Jinja2 template |

If `html` is not provided, the email is sent as plain text using the `text` field. If neither `html` nor `text` is provided, the template is invalid.

The `subject` field is always rendered through Jinja2, even if it contains no template expressions. This means you can use Jinja2 variables and filters in the subject line.

## Creating templates

Templates are created and managed in Studio's **Mail Templates** section. Each template is identified by a name and belongs to a specific project environment. When you create a template in Studio, you define the template name, subject, HTML body, and plain-text body. Changes take effect immediately — the next time `platform.mail.render()` is called with that template name, the updated content is used.

## Template data

When sending a mail message with a template, you pass a `data` dictionary that is used as the Jinja2 context:

```python
await platform.mail.send(
    state,
    to=["student@example.com"],
    template="report-card",
    data={
        "student_name": "Ada Lovelace",
        "grade": "A",
        "subjects": ["Math", "Science", "English"],
        "enrollment_date": "2024-09-01",
    },
)
```

Inside the template, these variables are accessible:

```jinja2
{# report-card.html #}
<h1>Report card for {{ student_name }}</h1>
<p>Grade: {{ grade }}</p>
<ul>
{% for subject in subjects %}
  <li>{{ subject }}</li>
{% endfor %}
</ul>
<p>Enrolled since {{ enrollment_date | format_date }}</p>
```

The `data` dictionary becomes the Jinja2 context. All keys in the dictionary are available as variables in the template. Template expressions like `{{ student_name }}` are replaced with the corresponding value from the data dictionary.

## Jinja2 features available

Templates have access to the full Jinja2 template language. The `_jinja` instance is a `SandboxedEnvironment` with `autoescape=True`, which means HTML escaping is enabled by default and potentially dangerous constructs are restricted.

### Variables and expressions

```jinja2
Hello {{ name }}, your order {{ order_id }} has shipped.
Total: {{ total_minor | int }} cents.
```

Template expressions support variable access, attribute access, and filter application. The pipe `|` operator applies filters to values.

### Filters

```jinja2
{{ email | lower }}
{{ count | int }}
{{ price | round(2) }}
{{ date | format_date }}
{{ description | truncate(100) }}
```

Built-in Jinja2 filters include `lower`, `upper`, `capitalize`, `trim`, `round`, `int`, `float`, `length`, `default`, `safe`, `escape`, `truncate`, and `format_date` (a custom filter). You can also define custom filters through the Jinja2 environment configuration.

### Control structures

```jinja2
{% if order.total_minor > 1000 %}
  <p>Premium customer!</p>
{% else %}
  <p>Standard customer.</p>
{% endif %}

<ul>
{% for item in items %}
  <li>{{ item.name }} — {{ item.price }}</li>
{% endfor %}
</ul>
```

Jinja2 supports `if/elif/else` conditionals, `for` loops with `loop` variables, and `block` definitions for template inheritance.

### Macros

```jinja2
{% macro button(label, url) %}
  <a href="{{ url }}" style="background: #6D5BD0; color: white; padding: 12px 24px; border-radius: 6px;">{{ label }}</a>
{% endmacro %}

{{ button("View order", order_url) }}
```

Macros are reusable template functions that accept arguments and return HTML. They are useful for creating consistent UI components across templates.

### Includes

Templates can include other templates by name:

```jinja2
{% include "partials/header.html" %}
{% include "partials/footer.html" %}
```

The `include` directive renders another template at the current position. The included template has access to the same context as the parent template.

### Template inheritance

Jinja2 supports template inheritance through the `block` and `extends` directives:

```jinja2
{# base.html #}
<!DOCTYPE html>
<html>
<head>
  <title>{% block title %}Default Title{% endblock %}</title>
  {% block head %}{% endblock %}
</head>
<body>
  {% block body %}{% endblock %}
</body>
</html>

{# welcome.html #}
{% extends "base.html" %}
{% block title %}Welcome — {{ name }}{% endblock %}
{% block body %}
  <h1>Welcome, {{ name }}!</h1>
{% endblock %}
```

Template inheritance allows you to define a base template with named blocks, and child templates override specific blocks.

## Sandbox restrictions

Templates are rendered in `SandboxedEnvironment` with `autoescape=True`. This means:

- **No access to `__import__`**, `exec`, `eval`, or other builtins that could execute code
- **HTML autoescaping** is on by default — `<`, `>`, `&`, `"`, `'` are escaped in template output
- **No access to the filesystem, network, or Python internals**
- **Only safe filters and tests** are available

This sandbox ensures that anyone who can edit templates in Studio cannot break out of the template and access the server or database. The `SandboxedEnvironment` is created once and shared across all renders:

```python
_jinja = SandboxedEnvironment(autoescape=True)
```

The autoescape feature means that all variable output is automatically HTML-escaped. If you need to output raw HTML, use the `| safe` filter:

```jinja2
{{ html_content | safe }}
```

<Warning>
Only use the `| safe` filter when the content is trusted (not user-generated). Using `| safe` on untrusted content could introduce XSS vulnerabilities.
</Warning>

## Rendering without sending

You can render a template to preview what it would look like without sending an email:

```python
subject, html, text = platform.mail.render(
    state,
    "report-card",
    {"student_name": "Ada", "grade": "A"},
)
```

This returns a tuple of `(subject, html_body, text_body)`. If the template doesn't exist, a `KeyError` is raised with the message `no mail template {template!r}`.

The `render` method in `MailManager` uses the shared `_jinja` instance:

```python
def render(
    self, state: EnvironmentState, template: str, data: Mapping[str, Any]
) -> tuple[str, str | None, str | None]:
    stored = state.mail_templates.get(template)
    if stored is None:
        raise KeyError(f"no mail template {template!r}")
    subject = _jinja.from_string(stored.subject or "").render(**data)
    html = _jinja.from_string(stored.html).render(**data) if stored.html else None
    text = _jinja.from_string(stored.text).render(**data) if stored.text else None
    return subject, html, text
```

You can use this in a preview endpoint, a test suite, or a Studio preview feature to verify templates before sending.

## Template storage

Templates are stored as `MailTemplate` records in the platform database, scoped per environment. Each template is loaded into `EnvironmentState.mail_templates` when the environment state is built:

```python
templates = await MailTemplate.filter(environment_id=env_id).all()
state.mail_templates = {t.name: t for t in templates}
```

The `MailTemplate` model has these fields:

| Field | Type | Description |
| --- | --- | --- |
| `name` | string | Template identifier (used in `platform.mail.send(template=...)`) |
| `subject` | string | Email subject line |
| `html` | string | HTML body template |
| `text` | string | Plain-text body template |
| `environment` | reference | The environment this template belongs to |

Templates are created and edited in Studio's **Mail Templates** section. Changes take effect immediately — the next time `platform.mail.render()` is called with that template name, the updated content is used.

The `EnvironmentCache` caches environments including their templates. When an environment's version changes, the cache is invalidated and templates are reloaded:

```python
class EnvironmentCache:
    async def get(self, project, env) -> EnvironmentState:
        ...
        state = await load_state(self.platform, environment)
        self._states[key] = state
        return state
```

## Template design patterns

### Transactional emails

These are single-purpose emails triggered by user actions:

- **Welcome email** — Sent after sign-up
- **Password reset** — Sent after a password recovery request
- **Email verification** — Sent when a user verifies their email
- **Order confirmation** — Sent after a purchase
- **Invoice notification** — Sent when an invoice is created
- **Shipping notification** — Sent when an order ships
- **Password change confirmation** — Sent after a password change

Transactional emails should be concise and focused on a single action. They typically include the relevant data and a call to action.

### Digest emails

These aggregate multiple events into a single email, sent on a schedule:

```jinja2
{# daily-digest.html #}
<h1>Daily Digest</h1>
<p>Here's what happened today:</p>
<ul>
{% for event in events %}
  <li>{{ event.type }}: {{ event.description }} at {{ event.time }}</li>
{% endfor %}
</ul>
{% if events|length == 0 %}
  <p>No activity today.</p>
{% endif %}
```

The data dictionary for digest emails would include an `events` list, which the template iterates over using Jinja2's `for` loop. Digest emails are typically sent via scheduled flows that collect events from the `EventLog` table.

### Notification emails

These alert users to important events:

```jinja2
{# notification.html #}
<h1>{{ level | title }}: {{ title }}</h1>
<div class="content">
{{ body | safe }}
</div>
{% if action_url %}
  <a href="{{ action_url }}">Take action</a>
{% endif %}
```

The `safe` filter marks the body as safe HTML — use this only when the body content is trusted (not user-generated).

### Account emails

These handle account lifecycle events:

```jinja2
{# account-deactivated.html #}
<h1>Account Deactivated</h1>
<p>Your account has been deactivated on {{ deactivated_at }}.</p>
{% if reason %}
  <p>Reason: {{ reason }}</p>
{% endif %}
<p>If you believe this is a mistake, contact support at {{ support_email }}.</p>
```

### Multi-part emails

Templates can provide both HTML and plain-text versions for email clients that prefer plain text:

```jinja2
{# Subject is shared #}
{% block subject %}Order Confirmation — {{ order_id }}{% endblock %}

{# HTML version #}
{% block html %}
<h1>Order {{ order_id }} Confirmed</h1>
<p>Thank you for your order!</p>
{% endblock %}

{# Plain-text version #}
{% block text %}
Order {{ order_id }} Confirmed
Thank you for your order!
{% endblock %}
```

## Template partials

For consistent branding across all templates, create partial templates that can be included:

```jinja2
{# partials/header.html #}
<!DOCTYPE html>
<html>
<head>
  <style>{{ global_styles | default("") }}</style>
</head>
<body>
  <header>{{ brand_name | default("Pawabase") }}</header>

{# partials/footer.html #}
</body>
<footer>{{ footer_text | default("") }}</footer>
</html>

{# Welcome email using partials #}
{% include "partials/header.html" %}
<main>
  <h1>Welcome, {{ name }}!</h1>
  <p>Your account has been created.</p>
</main>
{% include "partials/footer.html" %}
```

Partials allow you to define reusable template fragments. The `include` directive renders the partial at the current position with the same context as the parent template.

You can define blocks in partials for further customization:

```jinja2
{# partials/header.html #}
<head>
  <title>{% block title %}Pawabase{% endblock %}</title>
  <style>
    {{ global_styles | default("body { font-family: sans-serif; }") }}
  </style>
</head>
<body>
  <header>{% block header %}{% endblock %}</header>
```

## Template testing

You can test templates before deploying them by rendering them with sample data:

```python
subject, html, text = platform.mail.render(

```

If the template doesn't exist, a `KeyError` is raised with the message `no mail template {template!r}`.

For unit testing templates, you can write test cases that verify the rendered output:

```python
def test_welcome_template():

        "email": "test@example.com",
    })
    assert "Test User" in subject
    assert "Test User" in html
    assert "test@example.com" in text
```

```python

assert result["suppressed"] is True
# Check MailLog for the suppressed record
```

## Template performance

Template rendering is fast — Jinja2 compiles templates to Python bytecode on first render and caches the compiled template. The `_jinja` instance is shared across all renders, so there's no overhead from creating a new environment for each email.

For high-volume senders (thousands of emails per minute), consider:

- Pre-rendering templates with common data
- Using simple templates with minimal logic
- Avoiding complex macros and nested includes
- Caching rendered template results where appropriate

The `SandboxedEnvironment` caches compiled templates internally. The first render of a template is slightly slower because Jinja2 compiles the template source to bytecode. Subsequent renders use the cached bytecode.

## Template debugging

When templates aren't rendering correctly:

1. **Check the template name** — `MailManager.render()` raises `KeyError` if the template doesn't exist
2. **Check template variables** — Ensure all variables used in the template are present in the data dictionary
3. **Check filter names** — Ensure all filters used in the template exist
4. **Use render() to preview** — Call `platform.mail.render()` to see the rendered output without sending
5. **Check the sandbox** — Ensure no Python internals are accessed in the template
6. **Check HTML escaping** — If HTML is being escaped unexpectedly, use the `| safe` filter

```python
# Debug template rendering
try:
    subject, html, text = platform.mail.render(state, "my-template", data)
    print(f"Subject: {subject}")
    print(f"HTML: {html[:200]}...")
    print(f"Text: {text[:200]}...")
except KeyError as e:
    print(f"Template not found: {e}")
```

## Template syntax (expanded)

### Template variables

Template variables are resolved using the `render` function from `pawabase_kit/templating.py`:

```python
def render(value: Any, state: Mapping[str, Any]) -> Any:
    if isinstance(value, str):
        whole = _WHOLE.match(value)
        if whole:
            return evaluate_expression(whole.group(1), state)
        if "{{" not in value:
            return value
        def substitute(match: re.Match[str]) -> str:
            result = evaluate_expression(match.group(1), state)
            if result is None:
                return ""
            if isinstance(result, (dict, list)):
                return json.dumps(result, default=str)
            return str(result)
        return _TEMPLATE.sub(substitute, value)
    if isinstance(value, list):
        return [render(item, state) for item in value]
    if isinstance(value, Mapping):
        return {key: render(item, state) for key, item in value.items()}
    return value
```

### Template expression syntax

Template expressions use `{{ ... }}` delimiters:

| Expression | Result | Description |
| --- | --- | --- |
| `{{ user.name }}` | `Ada` | Access variable property |
| `{{ user.name | upper }}` | `ADA` | Apply filter |
| `{{ user.name | default:"Guest" }}` | `Ada` or `Guest` | Default value |
| `{{ order.total | int }}` | `2999` | Convert to integer |
| `{{ order.items | json }}` | `[...]` | Serialize as JSON |
| `{{ user.id | int }}` | `12345` | Convert to integer |

### Expression evaluation

The `evaluate_expression` function processes template expressions:

```python
def evaluate_expression(expression: str, state: Mapping[str, Any]) -> Any:
    parts = [part.strip() for part in expression.split("|")]
    value = lookup(state, parts[0])
    for spec in parts[1:]:
        name, _, argument = spec.partition(":")
        value = _apply_filter(value, name.strip(), argument.strip() or None)
    return value
```

The expression is split by `|` for filters. The first part is the variable path, subsequent parts are filters applied in order.

### Variable lookup

The `lookup` function resolves variable paths:

```python
def lookup(state: Mapping[str, Any], path: str) -> Any:
    parts = path.split(".")
    value = state
    for part in parts:
        if isinstance(value, Mapping):
            value = value.get(part)
        elif isinstance(value, list):
            try:
                value = value[int(part)]
            except (ValueError, IndexError):
                return None
        else:
            return None
        if value is None:
            return None
    return value
```

Variable paths can access nested objects: `user.profile.name` resolves `state["user"]["profile"]["name"]`.

## Available filters (expanded)

### String filters

| Filter | Syntax | Description |
| --- | --- | --- |
| `upper` | `{{ name | upper }}` | Convert to uppercase |
| `lower` | `{{ name | lower }}` | Convert to lowercase |
| `capitalize` | `{{ name | capitalize }}` | Capitalize first letter |
| `trim` | `{{ name | trim }}` | Remove leading/trailing whitespace |
| `default` | `{{ name \| default:"Guest" }}` | Use default if null |
| `json` | `{{ data \| json }}` | Serialize as JSON string |
| `int` | `{{ value \| int }}` | Convert to integer |
| `float` | `{{ value \| float }}` | Convert to float |
| `first` | `{{ items \| first }}` | Get first element |
| `last` | `{{ items \| last }}` | Get last element |
| `keys` | `{{ obj \| keys }}` | Get object keys |
| `length` | `{{ items \| length }}` | Get array length |
| `contains` | `{{ text \| contains:"search" }}` | Check if contains substring |

### Filter chaining

Filters can be chained:

```
{{ user.name | trim | upper | default:"ANONYMOUS" }}
```

Each filter is applied in sequence: trim → upper → default.

### Custom filters

Filters can be extended by modifying the `_apply_filter` function:

```python
def _apply_filter(value: Any, name: str, argument: str | None) -> Any:
    if name == "upper":
        return str(value).upper() if value is not None else value
    ...
```

## Template rendering modes (expanded)

### HTML rendering

HTML templates render as HTML email bodies:

```python
html = render(template.html, state)
```

The `template.html` field contains the HTML template. All `{{ ... }}` expressions are resolved.

### Text rendering

Text templates render as plain text email bodies:

```python
text = render(template.text, state)
```

The `template.text` field contains the plain text template. Template expressions are resolved.

### Combined rendering

Both HTML and text can be rendered simultaneously:

```python
html = render(template.html, state)
text = render(template.text, state)
```

The HTML version is used for email clients that support HTML, the text version is the fallback.

### Template variables in rendering

Template variables are resolved from the state:

```python
state = {
    "user": {"name": "Ada", "email": "ada@example.com"},
    "order": {"id": "1", "total": 2999},
    "project": {"name": "Acme"},
    "env": "production",
}
```

Access nested properties with dot notation: `{{ user.name }}`, `{{ order.total }}`.

## Template storage (expanded)

### Template model

Templates are stored as `Template` records:

```python
class Template(Model):
    id = UUIDField(primary_key=True)
    name = CharField(unique=True)
    subject = CharField(null=True)

    text = TextField(null=True)

```

The `vars` field defines the template variables and their types:

```json
{
  "name": {"type": "string", "required": true},
  "amount": {"type": "number", "required": true},
  "url": {"type": "string", "required": false},
  "items": {"type": "array", "required": false}
}
```

### Template lifecycle

Template lifecycle:

1. **Create**: Define name, subject, HTML, text, and variables
2. **Version**: Templates can have versions for tracking changes
3. **Activate**: Set as active for use in flows and mail calls
4. **Deactivate**: Remove from active use
5. **Archive**: Keep for reference but remove from use
6. **Delete**: Permanently remove

Templates support versioning:

## Template error handling (expanded)

### Missing variable errors

When a required variable is missing:

```python
def render(value: Any, state: Mapping[str, Any]) -> Any:
    ...
    if isinstance(value, str):
        whole = _WHOLE.match(value)
        if whole:
            result = evaluate_expression(whole.group(1), state)
            if result is None:
                raise TemplateError(f"Variable not found: {whole.group(1)}")
```

Required variables must be provided when calling `send_mail`.

### Template syntax errors

Template syntax errors are caught during rendering:

```python
def evaluate_expression(expression: str, state: Mapping[str, Any]) -> Any:
    try:
        ...
    except Exception as exc:
        raise TemplateError(f"Invalid template expression: {expression}") from exc
```

Invalid expressions raise a `TemplateError` with the expression details.

### Rendering fallbacks

Templates can provide fallbacks for missing data:

```html
<!-- Using the default filter -->
<p>Hello {{ user.name | default:"Customer" }}!</p>

<!-- Using conditional blocks -->
<p>Hello {{ user.name }}!</p>
{{#if user.name}}
  <!-- shown only if name exists -->
{{/if}}
```

## Template rendering engine (expanded)

### The `render` function in detail

The `render` function in `pawabase_kit/templating.py` is the core of template rendering:

```python
_TEMPLATE = re.compile(r"{{")
_WHOLE = re.compile(r"^\s*{{\s*(.+?)\s*}}\s*$")

def render(value: Any, state: Mapping[str, Any]) -> Any:
    if isinstance(value, str):
        whole = _WHOLE.match(value)
        if whole:
            return evaluate_expression(whole.group(1), state)
        if "{{" not in value:
            return value
        def substitute(match: re.Match[str]) -> str:
            result = evaluate_expression(match.group(1), state)
            if result is None:
                return ""
            if isinstance(result, (dict, list)):
                return json.dumps(result, default=str)
            return str(result)
        return _TEMPLATE.sub(substitute, value)
    if isinstance(value, list):
        return [render(item, state) for item in value]
    if isinstance(value, Mapping):
        return {key: render(item, state) for key, item in value.items()}
    return value
```

The function processes strings, lists, and dicts recursively. For strings:

1. If the entire string is a single `{{ ... }}` expression, evaluate and return directly
2. If the string contains `{{` but isn't a single expression, substitute all occurrences
3. If the string contains no `{{`, return as-is
4. For lists and dicts, recurse into each element

### The `evaluate_expression` function in detail

The `evaluate_expression` function processes template expressions:

```python
def evaluate_expression(expression: str, state: Mapping[str, Any]) -> Any:
    parts = [part.strip() for part in expression.split("|")]
    value = lookup(state, parts[0])
    for spec in parts[1:]:
        name, _, argument = spec.partition(":")
        value = _apply_filter(value, name.strip(), argument.strip() or None)
    return value
```

The expression is split by `|` for filters. The first part is the variable path, subsequent parts are filters applied in sequence.

Example: `{{ user.name | trim | upper | default:"Guest" }}` splits to `["user.name", "trim", "upper", "default:Guest"]`.

### The `lookup` function in detail

The `lookup` function resolves variable paths against state:

```python
def lookup(state: Mapping[str, Any], path: str) -> Any:
    parts = path.split(".")
    value = state
    for part in parts:
        if isinstance(value, Mapping):
            value = value.get(part)
        elif isinstance(value, list):
            try:
                value = value[int(part)]
            except (ValueError, IndexError):
                return None
        else:
            return None
        if value is None:
            return None
    return value
```

Path segments can access nested dicts with dot notation. Array indices are specified with numbers (0-indexed).

Example: `{{ user.profile.name }}` resolves `state["user"]["profile"]["name"]`.

### The `_apply_filter` function in detail

The `_apply_filter` function applies filters to values:

```python
def _apply_filter(value: Any, name: str, argument: str | None) -> Any:
    if name == "upper":
        return str(value).upper() if value is not None else value
    if name == "lower":
        return str(value).lower() if value is not None else value
    if name == "trim":
        return str(value).strip() if value is not None else value
    if name == "default":
        return value if value is not None else argument
    if name == "json":
        return json.dumps(value, default=str)
    if name == "int":
        return int(value) if value is not None else value
    if name == "float":
        return float(value) if value is not None else value
    if name == "first":
        return value[0] if isinstance(value, list) and len(value) > 0 else None
    if name == "last":
        return value[-1] if isinstance(value, list) and len(value) > 0 else None
    if name == "keys":
        return list(value.keys()) if isinstance(value, dict) else []
    if name == "length":
        return len(value) if isinstance(value, (list, dict)) else 0
    if name == "contains":
        return argument in str(value) if value is not None else False
    return value
```

Additional filters can be added by extending this function.

## Template rendering engine deep dive (expanded)

### The rendering pipeline

The template rendering pipeline processes templates through multiple stages:

```
1. Input Template → 2. Parse Expressions → 3. Resolve Variables → 4. Apply Filters → 5. Generate Output
```

**Stage 1: Input Template** — The raw template string with `{{ ... }}` expressions
**Stage 2: Parse Expressions** — Extract all `{{ ... }}` expressions using regex
**Stage 3: Resolve Variables** — Look up variable paths in the state
**Stage 4: Apply Filters** — Apply filter chains to variable values
**Stage 5: Generate Output** — Replace expressions with resolved values

### State resolution order

When resolving template variables, the state is searched in this order:

```python
def lookup(state: Mapping[str, Any], path: str) -> Any:
    parts = path.split(".")
    value = state
    for part in parts:
        if isinstance(value, Mapping):
            value = value.get(part)
        elif isinstance(value, list):
            try:
                value = value[int(part)]
            except (ValueError, IndexError):
                return None
        else:
            return None
        if value is None:
            return None
    return value
```

1. **Top-level keys**: Check if the first part is a top-level key
2. **Nested keys**: Recursively resolve nested keys
3. **Array indices**: Support numeric indices for arrays
4. **Missing keys**: Return `None` for missing keys

### Filter application order

Filters are applied left to right:

```python
def evaluate_expression(expression: str, state: Mapping[str, Any]) -> Any:
    parts = [part.strip() for part in expression.split("|")]
    value = lookup(state, parts[0])
    for spec in parts[1:]:
        name, _, argument = spec.partition(":")
        value = _apply_filter(value, name.strip(), argument.strip() or None)
    return value
```

Example: `{{ user.name | trim | upper | default:"Guest" }}`

1. Lookup `user.name` → `"  Ada  "`
2. Apply `trim` → `"Ada"`
3. Apply `upper` → `"ADA"`
4. Apply `default:"Guest"` → `"ADA"` (not None, so default is not applied)
