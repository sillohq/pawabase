Pawabase mail templates are written in Jinja2 and stored per environment. Templates define a subject line, an HTML body, and an optional plain-text body. They are rendered in Jinja2's sandboxed environment, so template authors cannot access Python internals or execute arbitrary code.

## Template structure

Each template has three fields:

| Field | Required | Description |
| --- | --- | --- |
| `subject` | Yes | The email subject line, rendered as a Jinja2 string |
| `html` | No | The HTML body, rendered as a Jinja2 template |
| `text` | No | The plain-text body, rendered as a Jinja2 template |

If `html` is not provided, the email is sent as plain text using the `text` field. If neither `html` nor `text` is provided, the template is invalid.

## Creating templates

Templates are created and managed in Studio's **Mail Templates** section. Each template is identified by a name and belongs to a specific project environment.

## Template data

When sending a mail message with a template, you pass a `data` dictionary that is used as the Jinja2 context:

```python
await platform.mail.send(
    state,
    to=["student@example.com"],
    template="report-card",
    data={
        "student_name": "Ada Lovelace",
        "grade": "A",
        "subjects": ["Math", "Science", "English"],
        "enrollment_date": "2024-09-01",
    },
)
```

Inside the template, these variables are accessible:

```jinja2
{# report-card.html #}
<h1>Report card for {{ student_name }}</h1>
<p>Grade: {{ grade }}</p>
<ul>
{% for subject in subjects %}
  <li>{{ subject }}</li>
{% endfor %}
</ul>
<p>Enrolled since {{ enrollment_date | format_date }}</p>
```

## Jinja2 features available

Templates have access to the full Jinja2 template language:

### Variables and expressions

```jinja2
Hello {{ name }}, your order {{ order_id }} has shipped.
Total: {{ total_minor | int }} cents.
```

### Filters

```jinja2
{{ email | lower }}
{{ count | int }}
{{ price | round(2) }}
{{ date | format_date }}
{{ description | truncate(100) }}
```

### Control structures

```jinja2
{% if order.total_minor > 1000 %}
  <p>Premium customer!</p>
{% else %}
  <p>Standard customer.</p>
{% endif %}

<ul>
{% for item in items %}
  <li>{{ item.name }} — {{ item.price }}</li>
{% endfor %}
</ul>
```

### Macros

```jinja2
{% macro button(label, url) %}
  <a href="{{ url }}" style="background: #6D5BD0; color: white; padding: 12px 24px; border-radius: 6px;">{{ label }}</a>
{% endmacro %}

{{ button("View order", order_url) }}
```

### Includes

Templates can include other templates by name:

```jinja2
{% include "partials/header.html" %}
{% include "partials/footer.html" %}
```

## Sandbox restrictions

Templates are rendered in `SandboxedEnvironment` with `autoescape=True`. This means:

- **No access to `__import__`**, `exec`, `eval`, or other builtins that could execute code
- **HTML autoescaping** is on by default — `<`, `>`, `&`, `"`, `'` are escaped in template output
- **No access to the filesystem, network, or Python internals**
- **Only safe filters and tests** are available

This sandbox ensures that anyone who can edit templates in Studio cannot break out of the template and access the server or database.

## Rendering without sending

You can render a template to preview what it would look like without sending an email:

```python
subject, html, text = platform.mail.render(
    state,
    "report-card",
    {"student_name": "Ada", "grade": "A"},
)
```

This returns a tuple of `(subject, html_body, text_body)`. If the template doesn't exist, a `KeyError` is raised.

## Template naming conventions

Template names should use lowercase kebab-case and describe the purpose:

| Template name | Purpose |
| --- | --- |
| `welcome-email` | New user welcome |
| `password-reset` | Password recovery email |
| `report-card` | Academic progress reports |
| `invoice-notification` | Invoice creation alerts |
| `daily-digest` | Daily summary emails |
| `order-confirmation` | Order placement confirmation |

## Template storage

Templates are stored as `MailTemplate` records in the platform database, scoped per environment. Each template is loaded into `EnvironmentState.mail_templates` when the environment state is built.

The `MailTemplate` model has these fields:

| Field | Type | Description |
| --- | --- | --- |
| `name` | string | Template identifier (used in `platform.mail.send(template=...)`) |
| `subject` | string | Email subject line |
| `html` | string | HTML body template |
| `text` | string | Plain-text body template |
| `environment` | reference | The environment this template belongs to |

Templates are created and edited in Studio's **Mail Templates** section. Changes take effect immediately — the next time `platform.mail.render()` is called with that template name, the updated content is used.

## Template design patterns

### Transactional emails

These are single-purpose emails triggered by user actions:

- **Welcome email** — Sent after sign-up
- **Password reset** — Sent after a password recovery request
- **Email verification** — Sent when a user verifies their email
- **Order confirmation** — Sent after a purchase
- **Invoice notification** — Sent when an invoice is created

### Digest emails

These aggregate multiple events into a single email, sent on a schedule:

```jinja2
{# daily-digest.html #}
<h1>Daily Digest</h1>
<p>Here's what happened today:</p>
<ul>
{% for event in events %}
  <li>{{ event.type }}: {{ event.description }} at {{ event.time }}</li>
{% endfor %}
</ul>
{% if events|length == 0 %}
  <p>No activity today.</p>
{% endif %}
```

The data dictionary for digest emails would include an `events` list, which the template iterates over using Jinja2's `for` loop.

### Notification emails

These alert users to important events:

```jinja2
{# notification.html #}
<h1>{{ level | title }}: {{ title }}</h1>
<div class="content">
{{ body | safe }}
</div>
{% if action_url %}
  <a href="{{ action_url }}">Take action</a>
{% endif %}
```

The `safe` filter marks the body as safe HTML — use this only when the body content is trusted (not user-generated).

## Template partials

For consistent branding across all templates, create partial templates that can be included:

```jinja2
{# partials/header.html #}
<!DOCTYPE html>
<html>
<head>
  <style>{{ global_styles | default("") }}</style>
</head>
<body>
  <header>{{ brand_name | default("Pawabase") }}</header>

{# partials/footer.html #}
</body>
<footer>{{ footer_text | default("") }}</footer>
</html>

{# Welcome email using partials #}
{% include "partials/header.html" %}
<main>
  <h1>Welcome, {{ name }}!</h1>
  <p>Your account has been created.</p>
</main>
{% include "partials/footer.html" %}
```

## Template testing

You can test templates before deploying them by rendering them with sample data:

```python
subject, html, text = platform.mail.render(
    state,
    "welcome-email",
    {
        "name": "Ada Lovelace",
        "email": "ada@example.com",
        "enrollment_date": "2024-09-01",
    },
)
print(subject)  # Welcome, Ada Lovelace!
print(html[:100])  # <!DOCTYPE html>...
```

If the template doesn't exist, a `KeyError` is raised with the message `no mail template {template!r}`.

## Template performance

Template rendering is fast — Jinja2 compiles templates to Python bytecode on first render and caches the compiled template. The `_jinja` instance is shared across all renders, so there's no overhead from creating a new environment for each email.

For high-volume senders (thousands of emails per minute), consider:
- Pre-rendering templates with common data
- Using simple templates with minimal logic
- Avoiding complex macros and nested includes

## Summary

Pawabase mail templates provide a safe, flexible, and powerful way to create rich email content. With Jinja2's full template language, sandboxed rendering, per-environment storage, and template partials, you can create consistent, branded emails for any use case. Templates are managed in Studio, rendered at send time, and logged in `MailLog` for full observability.
