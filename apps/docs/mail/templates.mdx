Mail templates use **Jinja2** syntax — the same templating engine used by Flask, Django, and many other Python frameworks. You create and edit them entirely in Studio at **Mail → Templates**.

Each template has three parts:
- **Subject** — the email subject line
- **HTML body** — the email content (HTML)
- **Text body** — plain-text fallback (optional)

## Creating a template

1. Go to **Studio → Mail → Templates**.
2. Click **New template**.
3. Enter a **name** — this is how you reference the template when sending mail (e.g., `welcome_email`).

<Note>
Template names must be unique per environment. Use descriptive names: `welcome_email`, `password_reset`, `order_confirmation`, `weekly_digest`.
</Note>

## Template data

When you send mail, you pass a **data object** — a JSON dictionary of variables that the template can use. The data becomes available as top-level variables in the template.

```json
{
  "student_name": "Ada Lovelace",
  "grade": "A",
  "subjects": ["Math", "Science", "English"],
  "due_date": "2024-10-15",
  "teacher_name": "Dr. Smith"
}
```

In the template, reference these with `\{\{ \}\}`:

```jinja2
Hi {{ student_name }},

Your report card is ready.

Grade: {{ grade }}
Subjects: {{ subjects | join(", ") }}
Due date: {{ due_date | date("MMMM D, YYYY") }}

— {{ teacher_name }}
```

## Jinja2 features available

### Variables and expressions

Use `\{\{ \}\}` to output variable values:

```jinja2
{{ user.name }}
{{ order.total | currency }}
{{ items | length }}
```

You can access nested properties with `.` or `[]`:

```jinja2
{{ user.profile.email }}
{{ user["profile"]["email"] }}
```

### Filters

Filters transform values using `|`:

| Filter | What it does | Example |
| --- | --- | --- |
| `upper` | Uppercase | `\{\{ name | upper \}\}` |
| `lower` | Lowercase | `\{\{ name | lower \}\}` |
| `title` | Title case | `\{\{ name | title \}\}` |
| `join(", ")` | Join array elements | `\{\{ items | join(", ") \}\}` |
| `length` | Array/string length | `\{\{ items | length \}\}` |
| `default("—")` | Fallback if undefined | `\{\{ user.name | default("Friend") \}\}` |
| `date("MMMM D, YYYY")` | Format a date | `\{\{ created_at | date("MMMM D, YYYY") \}\}` |
| `currency` | Format as currency | `\{\{ total | currency \}\}` |
| `urlencode` | URL-encode | `\{\{ token | urlencode \}\}` |

### Control structures

Use `{% %}` for logic:

```jinja2
{% if grade == "A" %}
    Excellent work!
{% elif grade == "B" %}
    Good job!
{% else %}
    Keep trying!
{% endif %}

{% for subject in subjects %}
    - {{ subject }}
{% endfor %}

{% set total = sum(item.price for item in items) %}
Total: {{ total | currency }}
```

### Macros (reusable blocks)

```jinja2
{% macro button(label, url) %}
<a href="{{ url }}" style="display: inline-block; padding: 12px 24px; background: #0070f3; color: white; text-decoration: none; border-radius: 6px;">{{ label }}</a>
{% endmacro %}

{{ button("View Report", "https://app.example.com/reports/123") }}
{{ button("Download PDF", "https://app.example.com/reports/123.pdf") }}
```

### Includes (partial templates)

If you have shared components (headers, footers, button styles), define them as Jinja2 `{% include %}` blocks within the same template or reference reusable snippets.

### Template inheritance

You can define a base template with blocks and extend it:

```jinja2
{# base.html #}
<html>
<body>
  {% block content %}{% endblock %}
  {% block footer %}{% endblock %}
</body>
</html>
```

```jinja2
{# child template #}
{% extends "base.html" %}
{% block content %}Hello, {{ name }}!{% endblock %}
```

<Note>
Template inheritance and includes are limited to templates within the same environment. You cannot reference templates from other environments.
</Note>

## Sandbox restrictions

Templates run in a **sandboxed** environment. The sandbox restricts:

- **No imports** — you cannot `import` Python modules from within a template.
- **No arbitrary code execution** — `{% exec %}` and similar tags are blocked.
- **No attribute access to dunder methods** — `\{\{ obj.__class__ \}\}` returns nothing.
- **No file access** — templates cannot read or write files on the server.
- **No network access** — templates cannot make HTTP requests.
- **Limited built-in functions** — only the filters and tags documented above are available.

<Warning>
These restrictions prevent template injection attacks. Even if a user can control template content (e.g., through user-supplied data), they cannot execute arbitrary code on the server.
</Warning>

## Previewing templates

Every template has a **Preview** button in Studio. Click it to:

1. Enter sample JSON data.
2. See the rendered subject, HTML, and text side by side.
3. Toggle between desktop and mobile width previews.
4. Copy the rendered HTML.

Use preview to verify your template renders correctly before deploying.

## Sending from a flow

Add a **mail.send** block to a flow:

1. Drag a **Platform → Mail send** block onto the canvas.
2. Configure the fields:
   - **To** — recipient email (can be an expression like `\{\{ input.event.payload.email \}\}`)
   - **Template** — select from the dropdown (templates you created in Studio)
   - **Data** — JSON object with template variables

The data object can use `\{\{ \}\}` expressions resolved from earlier steps:

```json
{
  "student_name": "{{ steps.lookup_student.output.name }}",
  "grade": "{{ input.grade }}",
  "subjects": "{{ steps.get_subjects.output }}"
}
```

## Sending from a function

Use the `ctx.mail` client:

```javascript
// In a function (Python)
await ctx.mail.send(
    to="student@example.com",
    template="report_card",
    data={
        "student_name": "Ada",
        "grade": "A",
    },
)
```

The function's `ctx` object provides `mail.send` and `mail.render` methods. See [Functions → Sending mail](/code/functions) for complete examples.

## Template design patterns

### Transactional emails

For single-event emails (welcome, receipt, password reset):

- Keep the data minimal — only what's needed for this email
- Use a clear call-to-action button
- Include the event context (what triggered the email)
- Set a plain-text fallback for email clients that don't render HTML

### Digest emails

For batch/combined emails (weekly summary, daily report):

```jinja2
{% for item in items %}
  <tr>
    <td>{{ item.date | date("MMM D") }}</td>
    <td>{{ item.description }}</td>
    <td>{{ item.amount | currency }}</td>
  </tr>
{% endfor %}
```

- Group related items in a table
- Include a summary total
- Provide links to the full dashboard

### Multi-part emails (HTML + text)

Always provide both HTML and text bodies:
- **HTML** — the rich, formatted version
- **Text** — the plain-text fallback for email clients that block HTML

If you omit the text body, Pawabase auto-generates it by stripping HTML tags from the HTML body.

## Testing templates

### Studio preview

The fastest way to test is Studio's **Preview** button. Enter sample data and see the exact rendered output:

```json
{
  "student_name": "Test Student",
  "grade": "A",
  "subjects": ["Math", "Science"]
}
```

### Sending a test email

From the template editor in Studio, click **Send test**. Enter a recipient email address and sample data — Pawabase sends the email immediately using the environment's current SMTP configuration.

<Info>
Test emails count toward your provider's rate limits but are free within Pawabase. Use Ethereal (a fake SMTP provider) in development to avoid sending real emails.
</Info>

### Testing from a flow

Create a flow with a manual trigger and a `mail.send` block:

```text
Trigger (manual)
   ↓
mail.send (template: "welcome_email", to: "test@example.com")
   ↓
Done
```

Run the flow from Studio's **Run** button to send a test email.

## Naming conventions

Follow this pattern for template names:

```text
<purpose>_<variant>
```

Examples:
- `welcome_email`
- `welcome_email_reminder`
- `password_reset`
- `password_reset_confirmation`
- `order_confirmation`
- `order_shipped`
- `weekly_digest`
- `weekly_digest_admin`

<Note>
Prefix templates with a category to make them easy to find: `welcome_`, `password_`, `order_`, `invoice_`, `notification_`, `admin_`.
</Note>

## Template performance

Templates are compiled once and cached per environment version. Changes to a template take effect on the next request that sends mail — no restart needed.

- **Compilation** happens when the template is saved in Studio. Syntax errors prevent saving.
- **Caching** — compiled templates are cached in memory per worker process. Cache invalidation happens automatically when a template is updated.
- **Rendering** — each `mail.send` call renders the template with the provided data. For bulk sends (hundreds of emails), consider batching or using a queue to avoid blocking.

## Debugging templates

<AccordionGroup>
  <Accordion title="Template doesn't render variables">
    Check that the data key names match exactly. `\{\{ studentName \}\}` is different from `\{\{ student_name \}\}`. Use `\{\{ vars.student_name \}\}` in Studio's preview to debug.
  </Accordion>
  <Accordion title="Filter not available">
    Only documented filters are available. Custom Jinja2 extensions are not supported for security reasons.
  </Accordion>
  <Accordion title="Conditional not working">
    Conditions evaluate against the data object you pass. Check that the condition references the correct variable name.
  </Accordion>
  <Accordion title="HTML not rendering">
    Jinja2 auto-escapes HTML by default. If you need to output raw HTML (e.g., from a rich text field), use the `| safe` filter: `\{\{ content | safe \}\}`. But be careful — this can introduce XSS if the content comes from user input.
  </Accordion>
</AccordionGroup>
