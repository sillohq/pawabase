Pawabase provides a complete outbound email system. You configure an SMTP connection per environment, create templates in Studio, and send mail from flows or functions. Every message is queued as a background job so SMTP latency never slows down your API responses, and every delivery is tracked in a log you can inspect from Studio.

## How mail fits in

```text
Flow or Function
       ↓
mail.send block (or platform.mail.send)
       ↓
Template rendered in sandbox
       ↓
Queued as background job
       ↓
Worker delivers via SMTP
       ↓
Delivery logged
```

Mail is always sent asynchronously. When you call `mail.send` from a flow or function, the message is queued immediately and the calling code continues. A background worker picks it up and delivers it via SMTP, retrying on failure. Every send — successful or not — is recorded in the **Mail log** in Studio.

## Configuring SMTP

Each environment has its own SMTP configuration. In Studio:

1. Go to **Settings → Infrastructure**.
2. Under **Mail**, enter your SMTP details.

| Field | Description | Example |
| --- | --- | --- |
| **Host** | SMTP server hostname | `smtp.sendgrid.net` |
| **Port** | SMTP server port | `587` |
| **Username** | SMTP authentication username | `apikey` (for SendGrid) |
| **Password** | SMTP authentication password | Your provider's API key |
| **From address** | Default sender email | `no-reply@yourapp.com` |
| **StartTLS** | Use TLS encryption | Usually `true` |

<Note>
You can configure different SMTP settings for each environment. A common pattern: use a development provider (like Ethereal) for `development` and your production provider (SendGrid, Postmark, AWS SES) for `production`.
</Note>

## Creating templates

Mail templates are created in **Studio → Mail → Templates**:

1. Click **New template**.
2. Enter a **name** — this is what you reference when sending mail (e.g., `welcome_email`).
3. Write the email content using **Jinja2** template syntax.

Templates support:
- **Subject** — plain text, can include `{{ }}` expressions
- **HTML body** — HTML with inline `{{ }}` expressions
- **Text body** — plain-text fallback (optional, auto-generated from HTML if omitted)

Example template:

```
Subject: Welcome, {{ user.name }}!

Hi {{ user.name }},

Thanks for signing up. Your account is ready.

To verify your email, click: {{ verify_link }}

Or enter this code: {{ verification_code }}

— The Team
```

<Warning>
Templates run in a **sandboxed** environment. You can use `{{ }}` expressions, `{% if %}`, `{% for %}`, and other Jinja2 syntax, but you cannot access Python internals, import modules, or execute arbitrary code.
</Warning>

## Sending mail

### From a flow

Use the **`mail.send`** block in the flow editor:

1. Add a **Platform → Mail send** block to your flow.
2. Configure the fields:
   - **To** — the recipient's email address (can be an expression like `$input.event.payload.email`)
   - **Template** — the template name you created
   - **Data** — the variables to pass to the template (as a JSON object)

The flow receives the template variables in the `data` field. For example, if your template uses `{{ user.name }}`, pass:

```json
{ "user": { "name": "Ada" }, "verify_link": "https://..." }
```

### From a function

Use the `mail` client from the function context:

```python
from pawabase_kit import function

@function("send_welcome")
async def send_welcome(ctx, email, name):
    await ctx.mail.send(
        to=email,
        template="welcome_email",
        data={"user": {"name": name}, "verify_link": "https://..."},
    )
    return {"sent": True}
```

Functions must import `pawabase_kit` and use the `@function` decorator. See [Functions → Sending mail](/code/functions#sending-mail-from-functions) for details.

### From a resource hook

Flows triggered by resource events can send mail automatically. Connect a `mail.send` block to a `resource.created` trigger to send a notification whenever a new record is created.

## Delivery tracking

Every email send creates a **MailLog** entry, visible in Studio under **Operate → Mail log**:

| Status | What it means |
| --- | --- |
| `sent` | The SMTP server accepted the message |
| `failed` | SMTP delivery failed (bad address, server error, etc.) |
| `suppressed` | The recipient was on a suppression list (unsubscribed, bounced, or marked as spam) |

### Retry policy

Failed deliveries are retried with exponential backoff:
- Attempt 1: immediate
- Attempt 2: 5 minutes
- Attempt 3: 15 minutes
- Attempt 4: 1 hour
- Attempt 5: 6 hours
- After 5 attempts: marked as `failed` permanently

### Suppression lists

When an email bounces or a recipient marks your email as spam, their address is added to a suppression list. Future sends to that address return `suppressed` immediately — they're never attempted. You can manage suppression lists in **Studio → Mail → Suppressions**.

## Testing mail

For development and testing, you can use a fake SMTP server:

| Environment | Recommended for testing |
| --- | --- |
| `development` | [Ethereal](https://ethereal.email/) — free test inboxes |
| `staging` | Your real provider with a test sender |

You can also preview templates in Studio by clicking **Preview** in the template editor — enter sample data and see exactly how the email renders before sending.

## Common issues

**"Mail log shows 'failed' with no SMTP error"** — The SMTP server rejected the connection silently. Check host, port, and StartTLS settings in **Settings → Infrastructure → Mail**.

**"Message marked as spam"** — Verify your SPF/DKIM/DMARC records match your sending domain. Most providers (SendGrid, PostMark, AWS SES) provide these records in their dashboard.

**"Recipients can't see images"** — Link images should use absolute URLs served over HTTPS. Inline base64 images work but increase email size.

**"Template variable is missing"** — Check that the variable name matches exactly. `{{ user_name }}` is different from `{{ userName }}`. Use `{{ vars.name }}` for a quick debug.
