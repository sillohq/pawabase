Pawabase dispatches background jobs through named queues. Every `queue.flow` and `queue.function` dispatch targets a queue — either a named queue or the default. Queues control concurrency, prioritization, and failure handling for background work.

## How jobs are dispatched

When a flow calls `queue.flow` or a function calls `queue.function`, the job is enqueued on the specified queue:

```json
{
  "id": "background",
  "data": {
    "block": "queue.flow",
    "config": { "flow": "export_orders", "queue": "priority" }
  }
}
```

The job is picked up by a worker on that queue and executed with the dispatched `input` and `trigger: "job"` context.

## Queue configuration

Queues are configured per environment in the platform settings:

| Property | Default | Description |
| --- | --- | --- |
| `concurrency` | `1` | Maximum concurrent jobs on this queue |
| `max_retries` | `3` | How many times to retry a failed job |
| `retry_delay` | `30` | Seconds to wait before retrying |
| `dead_letter` | `true` | Whether failed jobs go to a dead-letter queue |

## Default queue

The `default` queue exists in every environment. If you dispatch a job without specifying a queue, it goes to `default`:

```json
{
  "id": "default_dispatch",
  "data": { "block": "queue.flow", "config": { "flow": "process_order" } }
}
```

This is equivalent to specifying `queue: "default"` explicitly.

## Named queues

Create named queues for different priority levels or worker types:

```json
[
  { "id": "priority", "data": { "block": "queue.flow", "config": { "flow": "urgent", "queue": "priority" } } },
  { "id": "background", "data": { "block": "queue.flow", "config": { "flow": "export", "queue": "batch" } } }
]
```

## Concurrency

Each queue has its own concurrency limit. A queue with `concurrency: 1` processes one job at a time; a queue with `concurrency: 5` processes up to 5 jobs simultaneously.

<Tip>
Use separate queues for different workload types: a `priority` queue for time-sensitive jobs, a `batch` queue for heavy background processing, and the `default` queue for general work. This prevents a long-running batch job from blocking urgent dispatches.
</Tip>

## Dead-letter queue

Jobs that fail after all retries are moved to a dead-letter queue. You can inspect dead-letter jobs from Studio's **Jobs** page — see [Runs and testing → The job queue](/flows/runs-and-testing) for details. Dead-letter jobs can be retried manually or inspected for error details.
