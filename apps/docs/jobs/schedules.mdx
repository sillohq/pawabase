Pawabase's scheduler runs flows on a schedule — either a cron expression or a fixed interval. The `PlatformScheduler` reconciles its registered jobs with the database every `RECONCILE_SECONDS` (15) seconds, adding new schedules, re-registering changed ones, and dropping removed ones.

  <Card title="Interval" icon="repeat">Fixed intervals in seconds — e.g., `3600` for hourly.</Card>
</CardGroup>

## How schedules work

A schedule targets a flow and a specific `trigger.schedule` node. When the scheduler fires:

1. It creates a `RunFlowJob` with `trigger: "schedule"` and `input: {"scheduled_at": "<iso timestamp>"}`
2. The job is dispatched to the `default` queue
3. The flow runs with the named `trigger.schedule` node as the entry point
4. The run's `input` contains `scheduled_at` for time-based logic

```json
{
  "id": "start",
  "data": { "block": "trigger.schedule", "config": { "cron": "0 3 * * *" } }
}
```

## Schedule configuration

Each schedule has:

| Property | Description |
| --- | --- |
| `flow` | The flow name |
| `node` | The `trigger.schedule` node id within the flow |
| `cron` | A cron expression (optional) |
| `every` | An interval in seconds (optional) |
| `enabled` | Whether the schedule is active |
| `input` | Additional input passed to the run |
| `entry` | Which node to start from (typically the `trigger.schedule` node) |

At least one of `cron` or `every` is required.

## Cron expressions

Cron expressions follow the standard 5-field format:

```
┌───────── minute (0–59)
│ ┌───────── hour (0–23)
│ │ ┌───────── day of month (1–31)
│ │ │ ┌───────── month (1–12)
│ │ │ │ ┌───────── day of week (0–6, 0=Sunday)
│ │ │ │ │
│ │ │ │ │
* * * * *
```

Common examples:

| Expression | Fires |
| --- | --- |
| `0 3 * * *` | 3 AM UTC daily |
| `0 9 * * 1` | 9 AM every Monday |
| `0 0 1 * *` | Midnight on the 1st of each month |
| `*/15 * * * *` | Every 15 minutes |
| `0 0 * * 0` | Midnight every Sunday |

## Intervals

For simple periodic jobs, use `every` instead of `cron`:

```json
{
  "id": "start",
  "data": { "block": "trigger.schedule", "config": { "every": 3600 } }
}
```

This fires every 3600 seconds (1 hour). The scheduler uses `IntervalTrigger` for intervals and `CronTrigger` for cron expressions — both from Sillo's scheduler library.

## The scheduler reconciliation loop

The `PlatformScheduler` runs a reconciliation loop every `RECONCILE_SECONDS` (15) seconds:

```python
async def reconcile():
    for flow in state.flows.values():
        for node in flow.definition.get("nodes", []):
            if node["data"].get("block") != "trigger.schedule":
                continue
            config = node["data"].get("config", {})
            if not config.get("cron") and not config.get("every"):
                continue
            # Register or update the job
            ...
    # Drop jobs for removed triggers
    ...
```

This means:

- New `trigger.schedule` nodes are picked up within 15 seconds of saving
- Changed schedules are re-registered automatically
- Removed triggers are dropped
- Multiple `trigger.schedule` nodes in the same flow each register as independent jobs

## Running exactly one scheduler

<Tip>
Sillo's scheduler keeps its schedule registry in memory. Two scheduler processes would each fire every job, doubling your workload. If you scale the scheduler horizontally, use only one instance.
</Tip>

## Common patterns

### Nightly rollup

```json
{
  "id": "start",
  "data": { "block": "trigger.schedule", "config": { "cron": "0 3 * * *" } }
}
```

Use `time.now` with `offset_seconds: -86400` inside the flow to summarize the previous day regardless of when the job fires.

### Heartbeat

```json
{
  "id": "start",
  "data": { "block": "trigger.schedule", "config": { "every": 60 } }
}
```

A flow that runs every 60 seconds to check system health and emit metrics.
