Supabase and Pawabase both offer open-source backend platforms with auth, database, and realtime capabilities. They share some surface-level similarities — both provide Postgres-based databases, authentication, and realtime subscriptions — but diverge significantly in how backend logic is authored, how access control is enforced, and what guarantees each platform can make. This comparison focuses on the differences that matter when choosing between them, with honest treatment of where Supabase is stronger.

## The core architectural difference

The single most important difference between Supabase and Pawabase is **where access control lives**. Supabase's security boundary is Postgres itself — Row Level Security is enforced by the database, protecting even direct connections with valid credentials. Pawabase's security boundary is the application layer — policies run inside the API service and can be bypassed by a direct database connection.

This is not a matter of one being "better" than the other. It's a matter of optimizing for different threats:

- **Supabase optimizes against a compromised database.** If an attacker gets valid Postgres credentials (through a SQL injection vulnerability, a misconfigured backup, or a compromised operator), RLS still applies.
- **Pawabase optimizes for coverage and simplicity.** One policy language guards everything — resources, routes, functions, flows, storage, realtime — rather than stitching together RLS, route guards, storage rules, and a realtime authorization story.

Both are legitimate designs. Understanding which threat you're more concerned about is the first step in choosing between them. See [When not to use Pawabase](#policies-are-enforced-in-the-app-layer-not-the-database) for the full treatment.

## Database and data model

| | Supabase | Pawabase |
| --- | --- | --- |
| **Engine** | Postgres only (by hard architectural requirement — RLS *is* a Postgres feature) | Postgres, MySQL, or SQLite — your choice, per environment |
| **Data model** | Raw Postgres tables, exposed by PostgREST | Declared resources with typed fields, validation, and relations |
| **Exposure model** | **Opt-out**: PostgREST exposes every table and column immediately until you add RLS | **Opt-in**: operations are disabled until you enable them |
| **Schema** | Full Postgres DDL — extensions, foreign keys, stored procedures | Resource definition JSON — fields, types, constraints, relations |
| **Querying** | Full SQL via PostgREST filters, raw SQL via Edge Functions | `filter[<field>]`, `?expand=`, and `db.query` in flows for complex queries |
| **Existing tables** | PostgREST automatically exposes them | Resources can point at existing tables via `table` and `primary_key` |
| **Existing schemas** | Full Postgres schema access | Declare only the columns the API should see |

### The opt-out problem

Supabase's opt-out model is its most infamous failure mode. PostgREST inspects your schema and exposes every table and column it finds, over REST, immediately — an **opt-out** model. A table is world-readable and world-writable the moment it exists, until you run `ALTER TABLE … ENABLE ROW LEVEL SECURITY` and add policies. Forgetting that step is a well-known category of real Supabase security incidents, not a hypothetical.

Pawabase's opt-in model is structurally safer: nothing is exposed until you explicitly enable it. Every one of the five possible operations (`list`, `get`, `create`, `update`, `delete`) is switched on individually, and each carries its own policy. An operation you never enable simply doesn't exist as a route and never appears in the generated API docs.

<Warning>
The opt-in model is safer but requires more up-front configuration. With Supabase, a new table is immediately queryable (just potentially restricted by RLS). With Pawabase, a new resource must be declared with its fields, operations, and policies before it serves any traffic. Both approaches have trade-offs: Supabase's is faster to get started with but easier to get wrong; Pawabase's is slower to start but harder to accidentally expose data.
</Warning>

### Multi-database support

Pawabase supports Postgres, MySQL, and SQLite per environment. Supabase is Postgres-only by design — RLS is a Postgres feature, so the floor can't move to another engine without losing the entire security model built on top of it. This means:

- If you need MySQL (e.g., for legacy integration, licensing constraints, or team expertise), Pawabase supports it and Supabase doesn't.
- If you need SQLite for development or embedded scenarios, Pawabase supports it and Supabase doesn't.
- If you need Postgres extensions like `pgvector` or `PostGIS`, both support them — Pawabase because it runs on a real Postgres database, Supabase natively.

<AccordionGroup>
  <Accordion title="Does Pawabase support Postgres extensions like pgvector or PostGIS?">
    Since Pawabase resources sit on top of a real Postgres database when you choose Postgres, extension-backed columns and queries work at the database level. There's no first-class Pawabase abstraction for vector similarity search the way some platforms bolt one on — you'd reach for a Python function or a flow's `db.query` block to run that SQL directly.
  </Accordion>
  <Accordion title="Can I use my existing Postgres database with Pawabase?">
    Yes. Pawabase resources can be defined against existing tables (set `table` and `primary_key` to match), and you can declare only the columns you want the API to see. You are not required to let Pawabase own or migrate your schema. See [Use your own database](/data/your-database).
  </Accordion>
</AccordionGroup>

## Access control — RLS vs policies

This is the deepest comparison in this page. Supabase's Row Level Security and Pawabase's policies aim at the same goal (controlling who can read and write what) but enforce it at different layers with different guarantees.

**Supabase's Row Level Security** is SQL, evaluated inside Postgres itself:

```sql
create policy "own rows" on notes for select
  using (auth.uid() = user_id);
```

This is extremely powerful for a team that thinks fluently in SQL, and it has one property Pawabase's app-layer policies genuinely don't: **it protects the database even from a direct, non-API connection.** If an attacker gets valid Postgres credentials and connects with `psql`, RLS still applies. Pawabase's policy engine runs in the application layer — a direct database connection with valid credentials bypasses it entirely.

**Pawabase's policies** are JSON conditions, stored as named definitions, referenced from resources, custom routes, functions, flows, storage buckets, and realtime channels — one engine, one vocabulary, everywhere:

```json
{
  "name": "own_rows",
  "description": "Signed-in users see their own rows",
  "condition": {
    "all": [
      { "authenticated": true },
      { "eq": ["$record.user_id", "$auth.user_id"] }
    ]
  }
}
```

On `list` requests, Pawabase **plans** the policy into the query rather than filtering results afterward: anything that doesn't depend on the row (roles, authentication, scopes) is checked before any SQL runs; AND-ed equalities between a record field and a known value become a SQL `WHERE` clause; anything left over is checked per row as it's read. The practical effect is that a paginated list is *correct* — the right rows, the right total — not "20 rows, 3 of which turned out to be visible."

| | Pawabase policies | Supabase RLS |
| --- | --- | --- |
| Language | JSON conditions (+ Python escape hatch) | SQL |
| Evaluated | App layer, per request | Inside Postgres, per row |
| Protects direct DB access | No | Yes |
| Query behavior on partial access | Rows filtered/pushed down, list stays correct | Rows filtered by Postgres itself |
| Databases it works with | Postgres, MySQL, SQLite | Postgres only |
| Scope | Resources, routes, functions, flows, buckets, channels | Tables, and storage via `storage.objects` |
| Reuse | Named, referenced anywhere | Copy per table/command, or SQL functions |
| Learning curve | JSON conditions — familiar to any developer | SQL — requires Postgres fluency |

### Which guarantee matters more to you?

If the thought "what if someone gets direct database access?" keeps you up at night, Supabase's RLS provides a guarantee Pawabase cannot match. This is especially relevant for regulated industries, financial data, or any system where a database credential leak would be catastrophic.

If the thought "I want one policy language that covers every entry point" matters more to you, Pawabase's unified policy engine is the stronger choice. You write one JSON condition and it guards your REST API, your custom routes, your functions, your flows, your storage buckets, and your realtime channels. Supabase requires RLS for tables, `storage.objects` policies for storage, and whatever you write for custom route guards — three different surfaces, potentially different languages (SQL + rules DSL + your own code).

## Realtime

| | Supabase Realtime | Pawabase (Angula) |
| --- | --- | --- |
| **Mechanism** | Postgres Changes (WAL-based change feed) | Named channels, pub/sub, presence, replayable history |
| **Governed by** | RLS on the underlying table | Channel policies (`subscribe`/`publish` per channel) |
| **Triggered by** | Row-level Postgres changes | Resource writes (`realtime: true` + events), or explicit publish |
| **Scaling** | Managed by Supabase, or self-hosted alongside Postgres | Multiple Angula instances share state via Redis pub/sub |
| **Presence** | Yes (separate Presence primitive) | Yes (with replayable history) |
| **Broadcast** | Yes (separate Broadcast primitive) | Yes (channel-based) |

Supabase's Postgres Changes is closer to Pawabase's model in spirit (a stream of row-level changes) but is tied directly to Postgres's write-ahead log, alongside separate Presence and Broadcast APIs that don't share a security model with your table's RLS. Angula's channels are an explicit concept — you subscribe to `resource:<name>` or a channel you define — and every channel has its own policies that govern who can subscribe and who can publish.

<Note>
Angula never touches Postgres. Its channel state, presence, and replay history live in Redis-backed structures (via `sillo-wire`). If you run Angula without Redis it still works for a single instance, but presence and history won't survive a restart and multiple instances won't see each other's publications. See [Angula — scaling](/concepts/architecture#angula--realtime).
</Note>

## Edge functions vs flows

Supabase Edge Functions are one thing: TypeScript running on Deno, deployed with the CLI (`supabase functions deploy`). There's no visual builder — every piece of automation is hand-written code.

Pawabase gives you **two** mechanisms:

- **Visual flows** — JSON node graphs built with Studio's visual editor, versioned as definitions, triggered by HTTP, events, schedules, webhooks, realtime, or manually from Studio.
- **Python functions** — for logic a visual graph can't express cleanly, called inline via `function.call` or dispatched as background jobs via `queue.function`.

The practical consequence: a non-engineer on a Pawabase team can build a real automation ("when an invoice goes overdue, email the guardian and post a note to the finance channel") entirely in Studio's visual editor, with policy checks and database reads built from blocks, and reach for Python only when the flow's block vocabulary genuinely runs out. On Supabase, every piece of server-side automation is a code change, a deploy, and a review, no matter how small.

| | Supabase Edge Functions | Pawabase Flows + Functions |
| --- | --- | --- |
| **Primary language** | TypeScript (Deno) | Python |
| **Visual builder** | No | Yes (Studio) |
| **Trigger types** | HTTP, database events | HTTP, events, schedules, resources, webhooks, realtime, jobs, manual |
| **Run history** | Manual logging | Built-in `flow_runs` with full traces |
| **Versioning** | Per-function | Per-environment |
| **Deployment** | `supabase functions deploy` | Save definition — instant |
| **Subflows / composition** | Function calls | `queue.flow`, `function.call` |

## Auth comparison

| | Supabase (GoTrue) | Pawabase (Akountz) |
| --- | --- | --- |
| **Email/password** | Yes | Yes |
| **Magic links** | Yes | Yes |
| **Social login** | Yes (Google, GitHub, Apple, etc.) | Yes (Google, GitHub, generic OAuth/OIDC) |
| **MFA** | Yes (TOTP) | Yes (TOTP, with configurable enforcement) |
| **Phone auth** | Yes (SMS) | Coming |
| **Custom claims** | Auth claims | RBAC roles and permissions |
| **Token management** | JWT with refresh | Token pair with rotation and theft detection |
| **Organizations** | Yes | Yes |
| **Per-environment isolation** | No — `auth.users` is project-wide | Yes — users are isolated per project environment |
| **Operator accounts** | No equivalent | Yes — platform-level accounts for Studio sign-in |

The critical difference: Supabase's auth is project-wide — one `auth.users` table shared across all environments. Pawabase's auth is **per environment** — `acme/development` and `acme/production` have entirely separate users. A token minted in `development` is signed with the `development` environment's key material and will not authenticate against `production`. This makes it structurally impossible to accidentally use a dev token in production, which is a genuine safety feature for teams with multiple environments.

## Self-hosting and operations

| | Supabase | Pawabase |
| --- | --- | --- |
| **Can self-host** | Yes, official docker-compose | Required — it's the only option |
| **Can use managed cloud** | Yes, generous free tier + usage-based paid | No, not yet |
| **What you operate if self-hosted** | ~10 containers (postgres, gotrue, postgrest, realtime, storage-api, imgproxy, kong, studio, meta, edge-runtime) | 7 processes, 1 image, your Postgres/MySQL/SQLite, Redis, S3-compatible storage |
| **Backups, TLS, scaling, upgrades** | Your responsibility if self-hosted; handled for you on Cloud | Your responsibility — see [self-hosting docs](/self-hosting/requirements) |
| **Complexity** | ~10 containers to manage | 7 processes from one image |

Self-hosting Supabase means running around ten containers. Self-hosting Pawabase means running seven processes from a single image, with your database and storage being external concerns. Pawabase's self-hosting surface is simpler to operate, but neither platform makes it trivial. Both require you to handle backups, TLS, scaling, and patching.

## Pricing model

The three platforms don't just charge differently — they put the *risk* in different places.

**Supabase** offers a genuinely generous free tier on its managed cloud, then usage-based billing across several dimensions at once — database size, egress bandwidth, monthly active users, storage gigabytes, Edge Function invocations. Self-hosting removes the platform fee entirely, in exchange for taking on the ~10-container operational surface.

**Pawabase** has no platform fee: the docs describe an open-source, self-hosted positioning, so your cost is whatever infrastructure you provision (Postgres/MySQL instance, Redis, S3-compatible storage, compute for the seven processes). That cost is predictable in the sense that it scales with decisions *you* make about instance sizes, not with usage spikes you don't control — but you're the one sizing it, and you're the one paying for headroom you don't end up using.

<Tip>
If you're cost-sensitive and have predictable infrastructure needs, Pawabase's flat infrastructure cost can be significantly cheaper than Supabase's usage-based billing at scale. If you want a free tier to get started with zero commitment, Supabase's managed cloud is the easier entry point.
</Tip>

## When to choose Supabase

- **Your team already thinks fluently in SQL and wants RLS as the primary security boundary**, including protecting direct database connections. RLS-in-Postgres is a genuinely stronger guarantee against a compromised application server or a leaked database credential than an app-layer policy engine.
- **You want a managed cloud with a generous free tier.** Supabase Cloud's free tier is one of the most generous in the BaaS space. Pawabase has no managed offering.
- **You need TypeScript over Python.** Supabase Edge Functions run TypeScript/Deno; Pawabase functions are Python-only.
- **You want edge deployment.** Supabase Edge Functions deploy to Deno's edge network. Pawabase's flows run wherever you host the API.
- **You need Postgres-specific features** (extensions, stored procedures, `LISTEN/NOTIFY`, full SQL) and want them as the primary interface rather than as escape hatches.
- **You need mature offline sync.** Supabase's offline persistence is more mature than Pawabase's (which has none built-in).

## When to choose Pawabase

- **You want a unified policy engine across your whole backend** rather than stitching together RLS, storage rules, route guards, and realtime authorization.
- **You want the opt-in exposure model** — nothing is served until you explicitly enable it — rather than Supabase's opt-out model where every table is immediately exposed.
- **You want to use MySQL or SQLite** instead of Postgres.
- **You want a visual builder** for automation — Studio's flow editor is first-class and editable by non-engineers.
- **You want no-deploy iteration** — saving a definition updates the compiled app immediately, with no deploy step.
- **You want per-environment auth isolation** — dev users are never prod users.
- **You want a whole-backend export** as a single JSON document (blueprints).
