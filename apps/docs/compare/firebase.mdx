Firebase and Pawabase both offer backend-as-a-service, but they make fundamentally different bets. Firebase is Google-managed, document-oriented, and has no self-hosting option at all. Pawabase is self-hosted, relational, and uses one policy language across every entry point. This comparison focuses on the differences that matter when choosing between them, with honest treatment of where Firebase is stronger.

## Architecture

| | Firebase | Pawabase |
| --- | --- | --- |
| **Hosting model** | Google-managed only — no self-hosting | Self-hosted required — no managed cloud offering |
| **Logic authoring** | Cloud Functions (Node/Python/Go) triggered by Firestore events | Flows (visual graphs) + Python functions |
| **Trigger model** | Firestore document events, HTTP, auth events, scheduled | 8 trigger types: HTTP, events, schedules, resources, webhooks, realtime, jobs, manual |
| **Deployment** | `firebase deploy` — deploys functions to Google's infrastructure | Save definitions — no deploy, the compiled app updates instantly |
| **Run history** | Stackdriver logging | Built-in `flow_runs` with full step-by-step traces |
| **Visibility** | Functions are code — only engineers can read them | Flows are graphs — anyone can follow arrows, plus JSON |
| **Versioning** | Per-function versioning | Per-environment versioning |
| **Processes** | Google-managed, opaque | 7 processes from one Docker image, visible and configurable |

Firebase's architecture has a single center of gravity: Google's infrastructure. You configure services through the Console or CLI, and Google handles everything else — scaling, patching, TLS, backups. Pawabase's architecture is a small set of cooperating services from one image: Gateway, API, Worker, Scheduler, Akountz, Angula, and Studio. You operate all of them. This means Firebase has zero operational surface, while Pawabase gives you full control at the cost of full operational responsibility.

<Warning>
If "no infrastructure to think about, ever" is the actual requirement, Firebase (or Supabase Cloud) will get you there in a way Pawabase currently cannot. Pawabase is self-hosted only, and self-hosting means backups, TLS, scaling, and patching are your team's job starting on day one. See [When not to use Pawabase](/compare/when-not-to-use-pawabase#you-want-a-fully-managed-platform-with-zero-infrastructure).
</Warning>

## Data model — the part that actually differs

This is the deepest structural difference between the two platforms, and it's worth being precise rather than hand-wavy about it.

**Firebase (Firestore)** removes schema from the equation almost entirely. Collections hold documents; documents hold arbitrary JSON-ish fields; there's no `CREATE TABLE`, no column types enforced by the server beyond what your Security Rules happen to assert on write, and — critically — **no joins**. A `posts` collection with a `comments` subcollection can't be queried "post with author name and comment count" in one round trip. You either issue multiple reads client-side or you denormalize the author's name onto every post and comment at write time, and now you own keeping those copies in sync whenever the author's name changes.

**Pawabase** keeps your application data in a database *you* configure — Postgres, MySQL, or SQLite. Resources are relational: fields have types, relations are declared (`belongs_to`, `has_many`), and related data is fetched with a query parameter rather than a second round trip:

```bash
# a post plus its author and its comments, one request
curl "$GW/rest/v1/posts/42?expand=author,comments" -H "apikey: $PK"
```

Pawabase resources also **declare which operations are enabled**. An operation you never enable simply doesn't exist as a route. This is an opt-in model — unlike Firestore's implicit "everything is readable" model where Security Rules are the only gate.

### Worked example: modeling a blog both ways

Consider a blog with authors and posts. In Firestore, you'd model it as:

```javascript
// Firestore — denormalized
db.collection("posts").doc("42").set({
  title: "Hello",
  authorName: "Ada Lovelace",   // denormalized — must be kept in sync
  authorId: "8",
  content: "…",
  createdAt: firestore.FieldValue.serverTimestamp()
});
```

When Ada changes her name, you must update every post document that references her. There's no SQL `UPDATE posts SET authorName = … WHERE authorId = '8'` — you must query all posts and update each one individually, or maintain a Cloud Function that listens for profile changes and propagates them.

In Pawabase, the same blog is:

```json
{
  "name": "posts",
  "fields": [
    {"name": "title", "type": "string", "required": true},
    {"name": "author_id", "type": "integer", "required": true},
    {"name": "content", "type": "string"},
    {"name": "created_at", "type": "date"}
  ],
  "relations": [{ "name": "author", "type": "belongs_to", "resource": "users", "field": "author_id" }]
}
```

The author's name lives in one place — the `users` resource — and is fetched via `?expand=author`. When the name changes, it changes once. No denormalization, no sync logic, no Cloud Function to maintain.

<AccordionGroup>
  <Accordion title="What does Firestore's lack of joins cost?">
    For simple, flat data models (user preferences, app settings, simple state), Firestore's document model is perfectly adequate and arguably simpler than relational. For anything with meaningful relationships — orders with line items, invoices with line items and payments, hierarchical data — the denormalization burden grows quickly and the cost of keeping copies in sync is real. Pawabase's relational model eliminates this class of problems entirely.
  </Accordion>
  <Accordion title="What does Pawabase's relational model cost?">
    You need to define your schema up front — field types, validation, relations — before creating the resource. This is more structure than Firestore's schemaless approach, but it's also what gives you server-enforced validation, relation fetching, and correct paginated lists. For projects where the data model is still evolving rapidly and you want to store arbitrary JSON without defining a schema, Firestore's flexibility has genuine appeal.
  </Accordion>
</AccordionGroup>

## Access control — Security Rules vs policies

**Firebase Security Rules** are a custom DSL evaluated per document:

```javascript
match /posts/{id} {
  allow read, update, delete: if request.auth != null && request.auth.uid == resource.data.authorId;
  allow create: if request.auth != null;
}
```

The rule that trips people up moving away from Firebase: Security Rules aren't a filter applied after a query runs — they're a gate the *query itself* must satisfy. A Firestore query that could return a document the caller isn't allowed to read is rejected outright. Client code has to be written defensively, constraining its own queries to match the rules.

**Pawabase policies** are JSON conditions, evaluated by a policy engine in the application layer:

```json
{
  "name": "own_rows",
  "condition": {
    "all": [
      { "authenticated": true },
      { "eq": ["$record.user_id", "$auth.user_id"] }
    ]
  }
}
```

Pawabase **plans** the policy into the query rather than filtering results afterward. Equalities between a record field and a known value become SQL `WHERE` clauses; anything left over is checked per row. The practical effect is that a paginated list is correct — the right rows, the right total — not "20 rows, 3 of which turned out to be visible."

| | Firebase Security Rules | Pawabase policies |
| --- | --- | --- |
| Language | Custom rules DSL | JSON conditions |
| Evaluated | Per document, at query time | App layer, per request |
| Query behavior on partial access | **Query rejected** if it could violate the rule | Rows filtered/pushed down, list stays correct |
| Protects direct DB access | N/A (no direct DB access exists) | No — policies run in the app layer |
| Databases it works with | Firestore, Realtime Database, Storage | Postgres, MySQL, SQLite |
| Scope | Firestore/RTDB reads & writes, Storage | Resources, routes, functions, flows, buckets, channels |

### The honest trade-off

Firebase's Security Rules have one property Pawabase's policies genuinely don't: because there's no direct database access in Firebase, the rules are the *only* gate, and they're evaluated at query time. A malformed query that could leak data is rejected outright. Pawabase's policies run in the application layer — a direct database connection with valid credentials bypasses them entirely.

This is an honest, important trade-off. See [When not to use Pawabase](#policies-are-enforced-in-the-app-layer-not-the-database) for the full treatment, and [Compared with Supabase and Firebase](/policies/overview#compared-with-supabase-and-firebase) for the complete technical discussion.

## Functions

| | Firebase Cloud Functions | Pawabase Functions |
| --- | --- | --- |
| **Trigger** | Firestore events (`onCreate`, `onUpdate`, `onDelete`, `onWrite`), HTTP, scheduled | `queue.function` (background), `function.call` (inline), or triggered by a flow |
| **Runtime** | Node.js, Python, Go | Python only |
| **Run history** | Cloud Logging | `flow_runs` with full traces (when triggered through a flow) |
| **Integration** | Tightly coupled with Firestore | Works with any resource, flow, or event |
| **Scaling** | Automatic (Google manages) | Via Sillo's work queue |
| **Visibility** | Code only — no visual representation | Flows are graphs; functions are Python code |
| **Deploy** | `firebase deploy --only functions` | Save definition — no deploy |

Firebase functions are the more mature offering in terms of runtime options and Google integration. Pawabase functions are more integrated with the rest of the platform — a function called via `function.call` inside a flow has access to the flow's `run.state`, `vars`, and `steps`, and can call `resource.*` blocks, `http.request`, `mail.send`, and everything else a flow can do.

## Realtime

| | Firebase | Pawabase (Angula) |
| --- | --- | --- |
| **Model** | `onSnapshot` listeners per query/document | Named channels, pub/sub, presence, replayable history |
| **Governed by** | Same Security Rules as reads | Channel policies (`subscribe`/`publish` per channel) |
| **Triggered by** | Any write matching the listener's query/document | Resource writes (`realtime: true`), or explicit publish |
| **Offline persistence** | **Mature and widely used** | Not built-in |
| **Scaling** | Fully managed | Multiple Angula instances share state via Redis pub/sub |

Firebase's realtime is the stronger offering in one critical dimension: **offline persistence and sync**. Firestore's offline persistence is mature, heavily used in production, and has no equivalent in Pawabase today. For mobile-first apps that must work without connectivity, this alone can be decisive.

Pawabase's realtime is the stronger offering in another dimension: **channel-level authorization**. You can write a policy that says "only users in the `team:acme` channel can subscribe to `resource:orders`" — a level of per-channel access control that Firestore's Security Rules don't natively support at the listener level.

## When to choose Firebase

- **You need offline-first mobile with local data persistence.** Firestore's offline persistence and sync is mature and has no equivalent in Pawabase today. See [When not to use Pawabase](#you-need-offline-first-mobile-with-local-data-persistence).
- **You want zero operational surface.** Firebase is Google-managed — you configure it, you never see or operate the machines it runs on. Pawabase is self-hosted only.
- **Your team already uses Google Cloud and wants tight integration.** Firebase Auth, Firestore, Cloud Functions, and Cloud Storage work together as part of the Google Cloud ecosystem.
- **Your data model is flat and schemaless works fine.** If you don't need joins, typed fields, or server-enforced validation, Firestore's flexibility is simpler than declaring a resource schema.
- **You need a managed service with no self-hosting.** Firebase is the only option here — Pawabase doesn't have a managed offering.

## When to choose Pawabase

- **You want relational data with joins, typed fields, and server-enforced validation.** Firestore has none of these. Pawabase resources have all of them.
- **You want one policy language for everything.** Firebase's Security Rules govern Firestore and Storage separately. Pawabase's policies govern resources, routes, functions, flows, buckets, and channels with the same JSON vocabulary.
- **You want visual, inspectable backend logic.** Firebase's automation is code-only. Pawabase's flows are graphs visible in Studio, editable by non-engineers.
- **You want no-deploy iteration.** Saving a Pawabase definition takes effect on the next request. Firebase requires `firebase deploy` for any change to functions or security rules.
- **You want self-hosting or to avoid vendor lock-in.** Pawabase is self-hosted and vendor-neutral. Firebase is Google-managed only.
- **You want a whole-backend export.** Pawabase's blueprints export everything as one JSON document. Firebase has no equivalent.

## Full comparison table

| Dimension | Firebase | Pawabase |
| --- | --- | --- |
| Underlying database | Firestore (NoSQL documents) or RTDB (JSON tree) | Postgres, MySQL, or SQLite — your choice per environment |
| Data model | Document/NoSQL, no joins | Relational with fields, types, relations, `?expand=` |
| Schema | Schemaless | Declared per resource, opt-in API surface |
| Access control | Security Rules: custom DSL, per-document | Policies: JSON conditions, one engine, every entry point, app-layer |
| Auth service | Firebase Auth — project-wide, huge provider list | Akountz — per-project-environment user pools, OAuth/OIDC, MFA, orgs |
| Storage | Cloud Storage, GCS-backed | Buckets with `read_policy`/`write_policy`, S3-compatible backends |
| Realtime | `onSnapshot` listeners, RTDB listeners | Angula — policy-gated channels, presence, replayable history |
| Server-side logic | Cloud Functions — Node/Python/Go only | Visual flows (JSON graphs) **and** Python functions |
| Offline sync | Mature, widely used | Not built-in |
| Whole-backend export | No equivalent | Blueprints — one JSON document, new-project-only |
| Self-hosting | Not available at all | Required — it's the only option |
| Managed hosting | Yes, usage-based "Blaze" plan | None today |
| Pricing | Usage-based (reads/writes/deletes, bandwidth, GB-months, invocations) | Your own infrastructure cost; no platform fee |
| Mobile SDKs | Official SDKs for essentially every platform | None native yet; REST API + JS client (React Native-usable) |
| Ecosystem | Google-scale, over a decade in production | New, small team, docs actively being completed |
