Pawabase ships with a broad feature set across auth, data, automation, integrations, and observability. This matrix covers every capability and where it lives — built-in, available through extensions, or requiring a specific deployment mode. Where Pawabase's behavior differs from Supabase's or Firebase's, the comparison notes it.

<CardGroup cols={3}>
  <Card title="Built-in" icon="check-circle">Available out of the box with any project.</Card>
  <Card title="Extension" icon="puzzle-piece">Requires a custom package or `pawabase.blocks` entry point.</Card>
  <Card title="Self-hosted" icon="server">Requires your own deployment of the platform.</Card>
</CardGroup>

<Note>
This matrix describes Pawabase's current behavior as documented throughout this site. "Self-hosted" here means the feature requires self-hosting to be available at all (Pawabase has no managed cloud offering). Supabase and Firebase comparisons reflect the current widely-documented behavior of those platforms as of this writing — both evolve quickly, so double-check their own docs for the latest state.
</Note>

## Auth

| Feature | Status | Notes |
| --- | --- | --- |
| Email/password signup & signin | Built-in | Configurable per environment |
| Magic links | Built-in | Configurable |
| Social login (Google, GitHub, etc.) | Built-in | Add providers via `providers` config. OAuth/OIDC supported generically. |
| MFA (TOTP) | Built-in | Enforced per environment. AAL (`aal1`/`aal2`) visible in policy context. |
| Email verification | Built-in | Required or optional per environment |
| Password recovery | Built-in | Token-based, with configurable TTL |
| RBAC | Built-in | Roles and permissions per environment, isolated per environment |
| Organizations | Built-in | Multi-tenant support with org-scoped roles |
| Session management | Built-in | Token-based with rotating refresh tokens and theft detection |
| Token revocation | Built-in | Per-session revocation (`scope: "local"`, `"others"`, `"global"`) |
| Per-environment identity | Built-in | Users are isolated per project environment — a dev user is not a prod user |
| Operator accounts | Built-in | Platform-level accounts for Studio sign-in, isolated from project users |

### Compared with Supabase and Firebase

Supabase's auth (GoTrue) is project-wide — `auth.users` is a single table shared across environments. Pawabase's Akountz is **per environment** — `acme/development` and `acme/production` have entirely separate users. Firebase Auth is also project-wide. If you need environment-isolated auth, Pawabase is structurally different from both competitors.

## Complete feature matrix with comparisons

| Dimension | Pawabase | Supabase | Firebase |
| --- | --- | --- | --- |
| Underlying database | Postgres, MySQL, or SQLite | Postgres only | Firestore (NoSQL) or Realtime Database |
| Data model | Relational with fields, types, relations, `?expand=` | Relational (raw Postgres, PostgREST) | Document/NoSQL, no joins |
| Schema | Declared per resource, opt-in | Raw Postgres DDL, opt-out (PostgREST) | Schemaless |
| Access control | JSON conditions, one engine, every entry point, app-layer | SQL RLS, Postgres only, DB-layer | Custom DSL, per-document, also constrains queries |
| Auth | Akountz, per environment | GoTrue, project-wide | Firebase Auth, project-wide |
| Storage | Buckets with same policy engine | `storage.objects` RLS | Cloud Storage, Security Rules |
| Realtime | Angula — policy-gated channels | Postgres Changes (WAL) | `onSnapshot` listeners |
| Server-side logic | Visual flows **and** Python functions | Edge Functions (TypeScript) only | Cloud Functions (Node/Python/Go) only |
| Whole-backend export | Blueprints — one JSON document | No equivalent | No equivalent |
| Self-hosting | Required | Optional (docker-compose) | Not available |
| Managed hosting | None today | Yes, generous free tier | Yes, Blaze plan only |
| Pricing | Your own infrastructure cost | Free tier + usage-based | Usage-based |
| Mobile SDKs | None native yet | Official SDKs (JS, Dart, Swift, Kotlin, Python) | Official SDKs for essentially every platform |
| Ecosystem | New, small team | Large, VC-backed | Google-scale |
| Offline sync | None built-in | Partial | Mature |
| Visual builder | Studio — flows, resources, policies | Studio (limited) | Firebase Console |

### If you're doing X in Supabase or Firebase, here's the closest Pawabase block

| Doing this today | In Supabase | In Firebase | Pawabase block(s) |
| --- | --- | --- | --- |
| Run a query on write | Postgres trigger + `plpgsql` function | `onCreate`/`onUpdate`/`onDelete` Cloud Function | `trigger.resource` → flow with `db.query` or `resource.*` blocks |
| Send a transactional email | `pg_net` HTTP call to an email API, or an Edge Function | Cloud Function calling an email API/extension | `mail.send` |
| Call a third-party REST API | Edge Function with `fetch` | Cloud Function with `fetch`/`axios` | `http.request` |
| Debounce/delay a side effect | `pg_cron` + a flag column, or a queue | Cloud Tasks | `control.delay`, or `trigger.schedule` + `resource.list` filtering |
| Validate a complex payload shape | Hand-written checks in an Edge Function, or a Postgres `CHECK` constraint | Hand-written checks in a Cloud Function | `validate.schema` |
| Fan a webhook out to multiple internal listeners | `pg_net` + custom dispatch table | Pub/Sub topic + multiple Cloud Functions | `event.emit`, consumed by multiple flows subscribed to the same event |
| Cache an expensive read | Application-level cache (Redis you run yourself) or materialized view | Application-level cache you run yourself | `cache.get` / `cache.set` with `tags` for invalidation |
| Hash a password or token before storing it | `pgcrypto`'s `crypt()` in SQL, or Node's `crypto` in an Edge Function | Node's `crypto` in a Cloud Function | `crypto.hash` |
| Run a scheduled cleanup job | `pg_cron` | Cloud Scheduler + Cloud Function | `trigger.schedule` |
| Read a secret/API key at runtime | Supabase Vault, or an environment variable on the Edge Function | Cloud Secret Manager, or a Firebase Functions config value | `secret.get`, resolves `secret://NAME` |
| Increment a counter/metric | Hand-rolled SQL `UPDATE … SET count = count + 1`, or an external metrics service | An external metrics service (Firebase has no built-in flow metrics) | `metric.increment` |
| Retry a flaky external call | Hand-written retry loop in an Edge/Cloud Function | Hand-written retry loop in a Cloud Function | `control.retry` |

## Auth: feature-by-feature with equivalents

| Pawabase (Akountz) | Supabase (GoTrue) equivalent | Firebase Auth equivalent | Notes |
| --- | --- | --- | --- |
| Email/password | Email/password | Email/password | All three support this as the baseline flow. |
| Magic links | Magic links | Email link sign-in | Same concept everywhere; token TTL is configurable in all three. |
| Social login | OAuth providers (Google, GitHub, Apple, Azure, etc. — a longer provider list than Pawabase's) | OAuth providers (an even longer list, including gaming and regional providers) | Pawabase supports Google, GitHub, and generic OAuth/OIDC — enough to cover most providers, but you configure the OIDC endpoints yourself for anything not built in, rather than picking from a long pre-integrated list. |
| MFA (TOTP) | TOTP MFA | TOTP + SMS MFA | Firebase and Supabase both support SMS-based MFA; Pawabase's MFA is TOTP-only as of this writing. |
| Phone auth (SMS) | Yes | Yes | Not available in Pawabase today — see [When not to use Pawabase](/compare/when-not-to-use-pawabase). |
| Email verification | Yes, configurable | Yes, configurable | Equivalent behavior across all three. |
| Password recovery | Token-based | Token-based | Equivalent behavior across all three. |
| Custom claims / roles | Postgres custom claims via a function, surfaced in the JWT | Custom claims set via the Admin SDK | Pawabase's RBAC (roles + permissions) is a first-class definition kind rather than a claim you set by hand; policies reference `$auth.roles` and `$auth.permissions` directly. |
| Organizations / multi-tenancy | Hand-rolled (a `memberships` table + RLS), or a community extension | Hand-rolled (a `memberships` collection + Security Rules) | Pawabase ships organizations and org-scoped roles as a built-in concept; Supabase and Firebase require you to build the multi-tenancy model yourself on top of their primitives. |
| Session/token model | JWT + refresh token | Firebase ID token + refresh token | Pawabase's refresh tokens rotate on use and include theft detection (reuse of a superseded refresh token revokes the whole session chain). |
| Per-environment isolation | No — `auth.users` is project-wide across all Supabase environments you configure | No — Firebase Auth is project-wide | This is the one auth dimension where Pawabase is structurally different, not just differently implemented — see [Auth vocabulary](/compare/concept-map#authentication-vocabulary). |
| Operator/admin accounts | Dashboard login is a separate Supabase account system, unrelated to `auth.users` | Firebase Console login is a Google account, unrelated to Firebase Auth users | Pawabase's operator accounts (Studio sign-in) are likewise fully separate from Akountz's project users — the same shape as both competitors here. |

## Data: feature-by-feature with equivalents

| Pawabase | Supabase equivalent | Firebase equivalent | Notes |
| --- | --- | --- | --- |
| `?expand=<relation>` | PostgREST embedded resources (`?select=*,author(*)`) | No equivalent — denormalize or issue multiple reads | Conceptually closest to PostgREST's embeds; Firestore has nothing comparable because it has no joins. |
| `filter[<field>]=<value>` | PostgREST operators (`?field=eq.value`, `gte.`, `like.`, etc. — a richer operator set) | Firestore query constraints (`where()`, limited to indexed fields and composite index rules) | Pawabase's filters are equality-only as of this writing; PostgREST supports a wider range of comparison operators directly in the URL. Complex filtering in Pawabase means a custom route or a flow with `db.query`. |
| Transformers | Postgres views, or PostgREST's `?select=` column picking | Reshaping done client-side, or in a Cloud Function | Pawabase transformers are a named, reusable definition; Supabase and Firebase equivalents are either ad hoc (client-side) or require a view/materialized view. |
| Migrations | Supabase CLI migration files (raw SQL) | No schema concept — nothing to migrate | Pawabase's migrations are generated from resource/field changes automatically; Supabase's are hand-written SQL you author and run yourself. |
| `db.query` (read-only SQL in a flow) | Direct SQL via `postgres-js`/`pg` in an Edge Function, or PostgREST RPC to a SQL function | Not applicable — no SQL engine | Pawabase enforces read-only at the block level (`is_read_only`); write access goes through `resource.*` blocks or `db.transaction`. |
| Existing table support | Native — Postgres is Postgres | Not applicable — Firestore has no tables | Firebase migrations from an existing relational system require redesigning the data model as documents; Pawabase and Supabase can both point at a schema that already exists. |

## Self-hosting requirements

Pawabase self-hosting requires:

| Requirement | Details |
| --- | --- |
| **Docker** | One image, seven processes. `docker compose up` starts the full platform. |
| **Postgres** | For the platform's own state (definitions, keys, secrets, jobs, audit log). Pawabase's own database — separate from your application's database. |
| **Redis** | For queues, events, cache, and Angula's pub/sub. Required for multi-instance scaling and realtime across instances. |
| **Your database** | Postgres, MySQL, or SQLite — your choice, configured per environment via `database_url`. |
| **S3-compatible storage** | For file storage buckets. Any S3-compatible provider works. |
| **SMTP** | For email delivery (magic links, password recovery, email verification). |
| **Network** | The gateway must be publicly reachable. Internal services communicate over a private network. |
| **Secrets** | The `jwt_master_secret`, `internal_secret`, and `admin_email`/`admin_password` for the first operator. |

See [Self-hosting requirements](/self-hosting/requirements) for the complete infrastructure and configuration reference.

## Extensions and customization

Pawabase's extension system allows you to add custom blocks, functions, and routes:

| Extension type | Mechanism | Use case |
| --- | --- | --- |
| **Custom blocks** | `pawabase.blocks` entry point | Add domain-specific block types to the flow editor |
| **Python functions** | `@function` decorator in project code | Algorithms that need Python's full expressiveness |
| **Extension routes** | Python routers with Sillo framework access | Custom API endpoints that need full framework access |
| **Packages** | `pawabase.functions` entry point | Extend the Python function runtime |

Extensions are loaded at startup via Python's entry point mechanism. They're compiled into the platform's `BlockRegistry`, `FunctionRegistry`, and route table alongside Pawabase's built-in components.

## Security architecture

Pawabase's security model operates at multiple layers:

| Layer | Mechanism | Protects against |
| --- | --- | --- |
| **Gateway** | API key resolution, CORS, rate limiting, header stripping | Invalid keys, origin abuse, rate-limit abuse, header injection |
| **Policy engine** | JSON conditions, applied per resource/route/flow/bucket/channel | Unauthorized access to data |
| **Credential scopes** | Key-level scope enforcement at the gateway | Over-privileged integrations |
| **Token verification** | Per-environment derived keys, stateless verification | Token forgery, cross-environment replay |
| **Internal trust** | Service tokens with audience binding, signed contexts | Internal service impersonation |
| **Header stripping** | Gateway removes all `x-pawabase-*` headers from outgoing requests | Client header injection |

The gateway is the first and most important security layer. It resolves keys, enforces CORS and rate limits, strips anything a client could use to impersonate the platform, and signs the internal context. Nothing reaches an internal service without this processing.

## Monitoring and observability

When self-hosting Pawabase, you're responsible for monitoring it. The platform provides several signals:

| Signal | Source | Purpose |
| --- | --- | --- |
| `X-Request-ID` | Gateway, propagated through all services | Trace a request end to end |
| `flow_runs` table | Flow execution traces | Debug flow behavior, audit what ran |
| Process heartbeats | Worker and scheduler heartbeat rows | Studio's status page shows which processes are up |
| Audit log | Platform-level event log | Track definition changes and operator actions |
| `last_used_at` / `use_count` | API key tracking | Identify unused or overused keys |
| Gateway rate-limit headers | `X-RateLimit-*` on every response | Monitor rate limit utilization |

See [Observability](/operate/observability) for the complete monitoring setup.
