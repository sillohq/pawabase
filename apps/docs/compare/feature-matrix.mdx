Pawabase ships with a broad feature set across auth, data, automation, integrations, and observability. This matrix covers every capability and where it lives — built-in, available through extensions, or requiring a specific deployment mode. Where Pawabase's behavior differs from Supabase's or Firebase's, the comparison notes it.

<CardGroup cols={3}>
  <Card title="Built-in" icon="check-circle">Available out of the box with any project.</Card>
  <Card title="Extension" icon="puzzle-piece">Requires a custom package or `pawabase.blocks` entry point.</Card>
  <Card title="Self-hosted" icon="server">Requires your own deployment of the platform.</Card>
</CardGroup>

<Note>
This matrix describes Pawabase's current behavior as documented throughout this site. "Self-hosted" here means the feature requires self-hosting to be available at all (Pawabase has no managed cloud offering). Supabase and Firebase comparisons reflect the current widely-documented behavior of those platforms as of this writing — both evolve quickly, so double-check their own docs for the latest state.
</Note>

## Auth

| Feature | Status | Notes |
| --- | --- | --- |
| Email/password signup & signin | Built-in | Configurable per environment |
| Magic links | Built-in | Configurable |
| Social login (Google, GitHub, etc.) | Built-in | Add providers via `providers` config. OAuth/OIDC supported generically. |
| MFA (TOTP) | Built-in | Enforced per environment. AAL (`aal1`/`aal2`) visible in policy context. |
| Email verification | Built-in | Required or optional per environment |
| Password recovery | Built-in | Token-based, with configurable TTL |
| RBAC | Built-in | Roles and permissions per environment, isolated per environment |
| Organizations | Built-in | Multi-tenant support with org-scoped roles |
| Session management | Built-in | Token-based with rotating refresh tokens and theft detection |
| Token revocation | Built-in | Per-session revocation (`scope: "local"`, `"others"`, `"global"`) |
| Per-environment identity | Built-in | Users are isolated per project environment — a dev user is not a prod user |
| Operator accounts | Built-in | Platform-level accounts for Studio sign-in, isolated from project users |

### Compared with Supabase and Firebase

Supabase's auth (GoTrue) is project-wide — `auth.users` is a single table shared across environments. Pawabase's Akountz is **per environment** — `acme/development` and `acme/production` have entirely separate users. Firebase Auth is also project-wide. If you need environment-isolated auth, Pawabase is structurally different from both competitors.

## Data

| Feature | Status | Notes |
| --- | --- | --- |
| Resource CRUD | Built-in | Auto-generates REST endpoints from resource definitions |
| Field validation | Built-in | Declared in resource schema (`required`, `pattern`, `minimum`, `maximum`, `enum`, `email`, `date`, …) |
| Transformers | Built-in | Shape API responses per resource |
| Sorting & pagination | Built-in | `sort`, `limit`, `offset` query params |
| Filtering | Built-in | Equality filters via `filter[<field>]` — AND-ed across multiple filters |
| Relation expansion | Built-in | `?expand=<relation>` loads related records in one request |
| Raw SQL (`db.query`) | Built-in | Read-only, `is_read_only` enforced in flows |
| Transactions (`db.transaction`) | Built-in | Atomic multi-resource writes |
| Migrations | Built-in | Built-in migration system, definitions versioned per environment |
| Database console | Built-in | Studio's data browser |
| Caching | Built-in | Tag-based invalidation, TTL support |
| Custom routes | Built-in | Python handlers with full Sillo framework access |
| Existing table support | Built-in | Point a resource at a table Pawabase didn't create via `table` and `primary_key` |
| Multi-database support | Built-in | Postgres, MySQL, or SQLite — chosen per environment |
| Opt-in operations | Built-in | Enable list/get/create/update/delete individually per resource |

### Compared with Supabase and Firebase

Supabase is Postgres-only and exposes every table automatically (opt-out model with PostgREST). Pawabase is opt-in — an operation you never enable simply doesn't exist as a route. Pawabase also supports MySQL and SQLite, which Supabase doesn't. Firestore is schemaless with no joins; Pawabase resources have typed fields, validation, and relation expansion via `?expand=`.

## Automation

| Feature | Status | Notes |
| --- | --- | --- |
| Flows | Built-in | Graph of blocks, Studio visual editor, JSON definitions |
| Triggers (HTTP, event, schedule, resource, webhook, realtime, job, manual) | Built-in | 8 trigger types |
| Control blocks (if, switch, foreach, set, merge, delay, stop, retry) | Built-in | Full branching and looping |
| Data blocks (transform, validate, JSON, math, util, crypto, time) | Built-in | Value transformation and computation |
| Resource blocks (list, get, create, update, delete, db.query, db.transaction) | Built-in | Resource CRUD and raw database access |
| Platform blocks (auth, cache, events, jobs, realtime, storage, mail, HTTP, code, observability, responses) | Built-in | ~50 blocks in total |
| Custom blocks | Extension | `pawabase.blocks` entry point |
| Background jobs | Built-in | `queue.flow`, `queue.function` — dispatched to Sillo's work queues |
| Scheduler | Built-in | Cron and interval, reconciled every 15s — **run exactly one** |
| Functions (Python) | Built-in | `@function` decorator, called inline via `function.call` or as background jobs |
| Run history | Built-in | `flow_runs` with input, output, full step trace, logs, duration |
| Flow validation | Built-in | `validate_flow` catches unknown blocks, dangling edges, missing triggers before saving |
| Blueprint export | Built-in | One JSON document — entire backend definition for a new project |

### Compared with Supabase and Firebase

Supabase's automation is Edge Functions (TypeScript/Deno) only — no visual builder. Firebase's is Cloud Functions (Node/Python/Go) only — also no visual builder. Pawabase is the only one of the three with a visual flow builder that is first-class and editable by non-engineers. Supabase and Firebase require every piece of automation to be a code change, review, and deploy.

## Integrations

| Feature | Status | Notes |
| --- | --- | --- |
| Storage (buckets, uploads, downloads, signed URLs) | Built-in | S3-compatible backends, your choice |
| Mail | Built-in | Templates, SMTP configuration per environment |
| Realtime (channels, presence, history) | Built-in | Via Angula, policy-gated |
| Outbound webhooks | Built-in | Subscribe to platform events |
| HTTP requests | Built-in | `http.request` block in flows |
| Secret management | Built-in | Per-environment secrets, referenced as `secret://NAME` |
| Event system | Built-in | Durable event queue with fan-out |
| Inbound webhooks | Built-in | Signed by hook's own secret, no API key required |
| OAuth/OIDC providers | Built-in | Configured per environment |
| Storage policy | Built-in | `read_policy`/`write_policy` per bucket, same policy engine |
| CORS configuration | Built-in | Per-environment allowed-origins list, enforced at gateway |
| Rate limiting | Built-in | Per-key and per-IP, sliding window, configurable |

### Compared with Supabase and Firebase

All three offer S3-compatible or backed storage with policy-gated access. Supabase uses `storage.objects` RLS policies; Firebase uses Cloud Storage Security Rules; Pawabase uses the same JSON policy engine as everything else. Pawabase's storage policies can reference `$object` (key/segments/action) and the same roles and scopes a resource policy can — a more unified model than having a separate rules language for storage.

## Observability

| Feature | Status | Notes |
| --- | --- | --- |
| Flow run history (`flow_runs`) | Built-in | Input, output, full step trace, logs, duration — for every trigger kind |
| Structured logging | Built-in | `log.write` block in flows |
| Metrics | Built-in | `metric.increment` block in flows |
| Dashboard | Built-in | Studio observability views |
| Audit log | Self-hosted | Platform-level, tracks definition changes and operator actions |
| Rate limiting dashboard | Self-hosted | Per-environment configuration and monitoring |
| Request tracing | Self-hosted | `X-Request-ID` propagated through the gateway and internal services |
| Health checks | Self-hosted | `/studio/status` endpoint reports all processes |
| Error tracking | Self-hosted | Structured errors with `code`, `message`, `details` — integrate with your own error tracking |

### Compared with Supabase and Firebase

Supabase offers managed observability on its cloud (dashboards, usage metrics). Firebase offers Stackdriver logging and managed monitoring. Pawabase's observability is self-hosted — the data is yours, but so is the operational overhead of running it. The `flow_runs` table is a genuine differentiator: it records full step-by-step traces for every trigger kind (HTTP, event, schedule, webhook, manual), not just function invocations.

### Compared with Supabase and Firebase

Supabase offers managed cloud with a generous free tier, or self-hosting via docker-compose. Firebase is managed-only — no self-hosting option. Pawabase is self-hosted only, with no managed offering yet. This is the most significant practical difference for teams that don't want to operate infrastructure.

## Self-hosting requirements

Pawabase self-hosting requires:

| Requirement | Details |
| --- | --- |
| **Docker** | One image, seven processes. `docker compose up` starts the full platform. |
| **Postgres** | For the platform's own state (definitions, keys, secrets, jobs, audit log). Pawabase's own database — separate from your application's database. |
| **Redis** | For queues, events, cache, and Angula's pub/sub. Required for multi-instance scaling and realtime across instances. |
| **Your database** | Postgres, MySQL, or SQLite — your choice, configured per environment via `database_url`. |
| **S3-compatible storage** | For file storage buckets. Any S3-compatible provider works. |
| **SMTP** | For email delivery (magic links, password recovery, email verification). |
| **Network** | The gateway must be publicly reachable. Internal services communicate over a private network. |
| **Secrets** | The `jwt_master_secret`, `internal_secret`, and `admin_email`/`admin_password` for the first operator. |

See [Self-hosting requirements](/self-hosting/requirements) for the complete infrastructure and configuration reference.

## Extensions and customization

Pawabase's extension system allows you to add custom blocks, functions, and routes:

| Extension type | Mechanism | Use case |
| --- | --- | --- |
| **Custom blocks** | `pawabase.blocks` entry point | Add domain-specific block types to the flow editor |
| **Python functions** | `@function` decorator in project code | Algorithms that need Python's full expressiveness |
| **Extension routes** | Python routers with Sillo framework access | Custom API endpoints that need full framework access |
| **Packages** | `pawabase.functions` entry point | Extend the Python function runtime |

Extensions are loaded at startup via Python's entry point mechanism. They're compiled into the platform's `BlockRegistry`, `FunctionRegistry`, and route table alongside Pawabase's built-in components.

## Security architecture

Pawabase's security model operates at multiple layers:

| Layer | Mechanism | Protects against |
| --- | --- | --- |
| **Gateway** | API key resolution, CORS, rate limiting, header stripping | Invalid keys, origin abuse, rate-limit abuse, header injection |
| **Policy engine** | JSON conditions, applied per resource/route/flow/bucket/channel | Unauthorized access to data |
| **Credential scopes** | Key-level scope enforcement at the gateway | Over-privileged integrations |
| **Token verification** | Per-environment derived keys, stateless verification | Token forgery, cross-environment replay |
| **Internal trust** | Service tokens with audience binding, signed contexts | Internal service impersonation |
| **Header stripping** | Gateway removes all `x-pawabase-*` headers from outgoing requests | Client header injection |

The gateway is the first and most important security layer. It resolves keys, enforces CORS and rate limits, strips anything a client could use to impersonate the platform, and signs the internal context. Nothing reaches an internal service without this processing.

## Monitoring and observability

When self-hosting Pawabase, you're responsible for monitoring it. The platform provides several signals:

| Signal | Source | Purpose |
| --- | --- | --- |
| `X-Request-ID` | Gateway, propagated through all services | Trace a request end to end |
| `flow_runs` table | Flow execution traces | Debug flow behavior, audit what ran |
| Process heartbeats | Worker and scheduler heartbeat rows | Studio's status page shows which processes are up |
| Audit log | Platform-level event log | Track definition changes and operator actions |
| `last_used_at` / `use_count` | API key tracking | Identify unused or overused keys |
| Gateway rate-limit headers | `X-RateLimit-*` on every response | Monitor rate limit utilization |

See [Observability](/operate/observability) for the complete monitoring setup.
