**Resource changes** in Pawabase realtime refer to automatic broadcasts that occur when a database record is created, updated, or deleted. Resources marked with `realtime: true` emit a message to a dedicated channel every time a write operation happens, allowing connected clients to see data changes instantly without polling.

## How resource broadcasts work

When a resource has `realtime: true` enabled in its definition, the API automatically broadcasts a message to the `resource:<name>` channel for every create, update, and delete operation. This happens inline within the write transaction — the broadcast is a side effect, not a dependency. If the broadcast fails, the write still succeeds.

```python
# Inside the resource write path:
if resource.realtime:
    await platform.bus.emit_async(FANOUT_CHANNEL, {
        "room": room_name(project, env, f"resource:{resource.name}"),
        "message": {
            "type": "message",
            "event": operation,  # "created", "updated", "deleted"
            "payload": {
                "operation": operation,
                "record": record_data,
                "record_id": record_id,
            },
            "from": "service",
            "sent_at": datetime.now(UTC).isoformat(),
        },
        "origin": INSTANCE,
    })
```

## Channel naming

Resource broadcasts use a consistent channel naming convention:

| Resource name | Channel | Subscribers receive |
| --- | --- | --- |
| `invoices` | `resource:invoices` | All invoice changes |
| `users` | `resource:users` | All user changes |
| `orders` | `resource:orders` | All order changes |

Clients subscribe to `resource:<name>` to receive all changes for that resource. A client subscribed to `resource:invoices` will receive create, update, and delete events as they happen.

## Message format

Every resource change produces a message with this structure:

```json
{
  "type": "message",
  "id": "abc123",
  "channel": "resource:invoices",
  "event": "created",
  "payload": {
    "operation": "created",
    "record": {"id": 42, "client_id": "cl_123", "amount": 210000},
    "record_id": 42
  },
  "from": "service",
  "sent_at": "2026-09-28T10:00:00+00:00"
}
```

The `event` field is one of `"created"`, `"updated"`, or `"deleted"`. The `payload` contains the full record data and the operation type.

## Integrating with flows and events

Resource changes can trigger downstream flows and events through the platform's event system. When a resource is configured with both `realtime: true` and an event trigger, the write emits both a realtime broadcast and a platform event:

```json
{
  "nodes": [
    {"id": "trigger", "data": {"block": "trigger.resource", "config": {"resource": "invoices", "operations": ["created", "updated"]}}},
    {"id": "publish", "data": {"block": "realtime.publish", "config": {"channel": "invoices:processed", "event": "invoice.processed"}}},
    {"id": "emit", "data": {"block": "event.emit", "config": {"event": "invoice.created", "payload": "{{ steps.trigger.output }}"}}}
  ],
  "edges": [{"source": "trigger", "target": "publish"}, {"source": "trigger", "target": "emit"}]
}
```

This pattern lets you process resource changes in a flow (e.g., sending notifications, updating analytics) while simultaneously broadcasting to realtime channels.

## Subscription patterns

Common patterns for subscribing to resource changes:

```javascript
// Subscribe to all invoice changes
socket.subscribe("resource:invoices");

// Filter by operation type in the handler
socket.on("message", (msg) => {
  if (msg.channel === "resource:invoices") {
    const { operation, record } = msg.payload;
    if (operation === "created") {
      addInvoice(record);
    } else if (operation === "updated") {
      updateInvoice(record);
    } else if (operation === "deleted") {
      removeInvoice(record.id);
    }
  }
});
```

## Resource triggers in flows

The `trigger.resource` block in a flow starts a run when a resource changes:

```json
{
  "block": "trigger.resource",
  "config": {
    "resource": "invoices",
    "operations": ["created", "updated"]
  }
}
```

This is distinct from realtime broadcasting — the trigger starts a flow execution, while the broadcast goes to subscribed WebSocket clients. Both operate on the same resource change event.

## Performance considerations

- Resource broadcasts happen **inline** with the write, adding minimal latency
- The broadcast uses the platform event bus, which is non-blocking
- If Angula is unreachable, the event is queued but not delivered; the write is unaffected
- High-frequency writes to a resource with many subscribers may cause backpressure on the fanout channel

<Warning>
Resource broadcasts are a side effect, not a dependency. If Angula is down or a subscriber drops a message, the write still succeeds. Always design your application to tolerate missed realtime messages — use history replay and polling as fallbacks for critical data.
</Warning>
