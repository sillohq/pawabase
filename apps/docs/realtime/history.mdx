**History** in Pawabase realtime provides replayable message storage for every channel. When a new subscriber joins a channel, they can receive the last N messages that were published before they connected. This makes it possible to build UIs that show recent activity without needing the client to have been online when the messages were originally sent.

## How history works

Every message published to a channel is stored in `sillo-wire`'s `MemoryBacklog`. The backlog retains messages up to `history_bytes` bytes (default 256 KB) per channel. When a new subscriber requests history, Angula reads the last N messages from the backlog and returns them.

```python services/angula/app/realtime.py
async def history(self, project, env, channel, limit=50):
    envelopes = await self.hub.history(
        room_name(project, env, channel), limit=limit
    )
    return [
        {**envelope.payload, "seq": envelope.seq}
        for envelope in envelopes
        if isinstance(envelope.payload, dict) and envelope.payload.get("type") == "message"
    ]
```

Messages are returned in chronological order (oldest first), each with a `seq` field that's a monotonically increasing sequence number within the channel.

## Requesting history

History can be requested in two ways:

1. **Implicit**: Include `history: true` and optionally `history_limit` in the subscribe message
2. **Explicit**: Send a dedicated `history` request after subscribing

```json
{"type": "history", "channel": "store:7", "limit": 50}
```

Angula responds with a `history` message:

```json
{
  "type": "history",
  "channel": "store:7",
  "messages": [
    {"event": "order.paid", "payload": {...}, "seq": 1, "sent_at": "..."},
    {"event": "inventory.low", "payload": {...}, "seq": 2, "sent_at": "..."}
  ]
}
```

If the channel has fewer than `limit` messages, all available messages are returned. If the channel has no history, an empty array is returned.

## History configuration

Each channel rule defines its own history retention:

```json
{
  "pattern": "store:*",
  "subscribe": {"eq": ["$auth.org", "store-7"]},
  "history": 100
}
```

The `history` field (default 50) controls how many messages are retained for replay. The total bytes retained is capped by `history_bytes` (default 256 KB) in `AngulaSettings`. Older messages are evicted to make room for newer ones.

| Setting | Default | Description |
| --- | --- | --- |
| `history` per rule | 50 | Messages retained per channel rule |
| `history_bytes` global | 256 KB | Maximum bytes across all channels |
| `config_ttl` | 10s | How long channel config is cached |

## Message format in history

Messages in the history backlog have this shape:

```json
{
  "type": "message",
  "id": "abc123",
  "channel": "store:7",
  "event": "order.paid",
  "payload": {"order_id": 42},
  "from": "user:8",
  "sent_at": "2026-09-28T10:00:00+00:00",
  "seq": 1
}
```

The `seq` field is a monotonic sequence number assigned at publish time. It can be used by clients to determine which messages they've already seen and to request only new messages since their last receipt.

## Presence and history interaction

History is independent of presence. A client that subscribes to a channel receives the history regardless of whether they also register presence metadata. The history replay happens before the client begins receiving live messages, so the sequence is:

1. Client sends subscribe message
2. Angula authorizes the subscription
3. Angula returns history replay
4. Client receives `history` message with recent messages
5. Client receives live messages going forward

## Performance characteristics

History is stored in `sillo-wire`'s `MemoryBacklog`, which is an in-memory ring buffer per channel. This means:

- History access is fast (O(1) for the most recent messages)
- History is lost when the Angula instance restarts (no persistence)
- Multiple Angula instances each maintain their own history
- Redis pub/sub fanout is for message delivery, not history replication

<Warning>
History is not persisted across restarts. If an Angula instance restarts, its in-memory backlog is lost and new subscribers will receive no history until new messages are published. For durable message history, use the event system or a separate storage layer.
</Warning>
