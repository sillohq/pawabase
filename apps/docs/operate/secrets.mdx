Pawabase stores sensitive configuration values — database passwords, SMTP credentials, third-party API keys — encrypted at rest in the platform database. No plaintext secret ever persists in a table or appears in a log. Instead, every secret is encrypted with a master key, referenced by name, and resolved only at the moment a compiled app needs it.

This page covers how secrets are stored, encrypted, referenced in environment configuration, and consumed by functions and flows. It also covers the operational concerns around rotating a master key and auditing secret access.

<CardGroup cols={3}>
  <Card title="Encrypted at rest" icon="shield">Every secret is encrypted with AES-GCM via a Fernet key derived from the platform `master_key`. The platform database only holds ciphertext.</Card>
  <Card title="Named references" icon="tag">Code and environment config refer to secrets as `secret://NAME`, never by value. Resolution happens inside the running app, not in a config file.</Card>
  <Card title="Resolved at runtime" icon="clock">A `secret://NAME` reference is resolved when a compiled app starts or when a function loads — not at definition time, not when the environment is saved.</Card>
</CardGroup>

## How secrets are stored

The `Secret` model (`api/database/models/projects.py`) lives in the platform database, one row per named secret per environment:

| Column | Purpose |
| --- | --- |
| `environment` | Which project environment owns this secret |
| `name` | The reference name (e.g. `smtp-password`) |
| `ciphertext` | The encrypted value — the only place the plaintext exists after creation |
| `description` | Human-readable note, shown in Studio |
| `updated_by` | Who last changed it |

The `ciphertext` field is produced by `SecretBox.seal()`:

```python api/app/secrets.py
from pawabase_core.crypto import SecretBox, SECRET_PREFIX

box = SecretBox(master_key)          # derives a Fernet key from the master key
ciphertext = box.seal("pb_real_password")   # → "gAAAAAB..."
plaintext = box.open(ciphertext)          # → "pb_real_password"
```

The Fernet key is derived from the `master_key` setting using PBKDF2-HMAC-SHA256 with a fixed installation salt (`b"pawabase:secrets:v1"`) and 200,000 iterations. The salt is fixed on purpose: it means the same master key always derives the same Fernet key, so existing secrets stay readable across restarts and process restarts. Rotating the master key *does* break existing secrets — more on that below.

```python pawabase_core/crypto.py
@functools.lru_cache(maxsize=8)
def _fernet_key(master_key: str) -> bytes:
    raw, _ = derive_key(master_key, salt=_SALT, iterations=200_000)
    return base64.urlsafe_b64encode(raw)
```

The `lru_cache` with `maxsize=8` means the key derivation runs at most 8 times per process (one per distinct master key). This is a performance optimization — the derivation is expensive by design, and the cache ensures a process that handles many environments pays the cost once per key, not once per secret resolution.

## Referencing secrets: `secret://NAME`

Code and configuration never embed a secret value directly. They use a `secret://NAME` reference string, which is a pointer to a `Secret` row. The helper functions `is_reference()` and `reference_name()` distinguish references from literal values and extract the name:

```python pawabase_core/crypto.py
SECRET_PREFIX = "secret://"

def is_reference(value: object) -> bool:
    return isinstance(value, str) and value.startswith(SECRET_PREFIX)

def reference_name(value: str) -> str:
    return value[len(SECRET_PREFIX):]
```

Where do these references appear? In two places:

1. **Environment `infra` and `auth` config.** When a developer configures an environment's database URL, storage credentials, or SMTP settings, they write `secret://DB_PASSWORD` instead of `hunter2`. The `infra` and `auth` JSON fields on the `Environment` model hold these references.
2. **Function code.** Functions can call `resolve_value()` (or work with `secret://` references through the platform's secret resolution) to get the actual value at runtime.

```python api/app/platform.py
def resolve_value(self, state: EnvironmentState, value: Any) -> Any:
    """Replace a ``secret://NAME`` reference with the secret's value."""
    if is_reference(value):
        return state.secret_values.get(reference_name(value), "")
    return value
```

`state.secret_values` is a dict populated from the environment's `Secret` rows at compile time (or loaded lazily). The `Platform` object calls `resolve_value()` wherever a reference appears in a config value that gets passed to a database driver, an SMTP client, or a storage client.

## Creating and managing secrets

### In Studio

Studio's **Secrets** section provides the primary interface: **Build → Secrets → New secret**. You pick the environment, give the secret a name, paste the value, and optionally add a description. The value is encrypted with the platform's master key before it reaches the database — Studio never sees the plaintext after the initial submit.

The plaintext is shown exactly once, at creation time. After that, Studio shows only a masked form (`••••••••xxxx`) so an operator can confirm which secret they're looking at without reading the actual value.

### Via the Platform API

```bash Create a secret
curl -X POST "$STUDIO/studio/api/platform/projects/acme/envs/production/secrets" \
  -H "content-type: application/json" -H "X-XSRF-TOKEN: $XSRF" -b cookies.txt \
  -d '{
    "name": "stripe-webhook-secret",
    "value": "whsec_...",
    "description": "Stripe webhook signing secret"
  }'
```

The response includes the plaintext once and the masked form thereafter. Updates follow the same pattern — the new value is encrypted and stored, replacing the old ciphertext.

```bash Rotate a secret
curl -X PATCH "$STUDIO/studio/api/platform/projects/acme/envs/production/secrets/stripe-webhook-secret" \
  -H "content-type: application/json" -H "X-XSRF-TOKEN: $XSRF" -b cookies.txt \
  -d '{"value": "whsec_new_value"}'
```

### Programmatically

If you need to resolve secrets inside a custom Python function or policy, the `SecretBox` is available through the `Platform`:

```python
from app.platform import get_platform

platform = get_platform()
value = platform.box.open(ciphertext)   # decrypt a stored ciphertext
```

This is rarely needed directly — the platform resolves `secret://` references automatically in environment config and function loading. But if you're writing a custom integration that stores its own encrypted values, this is the pattern to follow.

## Secrets in environment configuration

The `Environment.infra` and `Environment.auth` JSON fields are where secrets flow into the running app. Both fields use `secret://NAME` references, and both are resolved when the environment's compiled app is built or when a function loads.

```json
Environment.infra (example)
{
  "database": {
    "url": "postgres://user:secret://DB_PASSWORD@host:5432/db",
    "pool_size": 10
  },
  "storage": {
    "bucket": "my-bucket",
    "credentials": "secret://S3_CREDENTIALS"
  },
  "mail": {
    "smtp_host": "smtp.mailgun.org",
    "smtp_user": "secret://SMTP_USER",
    "smtp_password": "secret://SMTP_PASSWORD"
  }
}
```

```json Environment.auth (example)
{
  "providers": {
    "google": {
      "client_id": "google-client-id",
      "client_secret": "secret://GOOGLE_CLIENT_SECRET"
    }
  },
  "token": {
    "access_ttl": 900,
    "refresh_ttl": 2592000
  }
}
```

The platform's `DataSourcePool`, `StorageManager`, and `MailManager` each call `resolve_value()` on the relevant config fields before passing them to their underlying drivers. A developer never has to write secret-resolution code — the platform handles it as long as the config uses `secret://` references.

<Note>
If a `secret://NAME` reference points to a `Secret` row that doesn't exist, `resolve_value()` returns an empty string (`""`). This means a misconfigured reference won't crash at startup — it will silently pass an empty value to a driver, which will typically fail at connection time with a clear error from the driver itself. Check Studio's environment settings if a service fails to connect and the error looks like a credential problem.
</Note>

## The master key: what it protects and how to rotate it

The `master_key` setting (from `pawabase_core.settings`) is the root of trust for all stored secrets. It is used to derive the Fernet key via `derive_key()`. Every `Secret` row's ciphertext is encrypted under this key.

Rotating the master key makes all existing secrets unreadable, because the new key derives a different Fernet key and cannot decrypt ciphertext produced by the old one. This is by design — if a master key is compromised, you want the old ciphertext to be permanently inaccessible. The tradeoff is that after rotating, you must re-encrypt every secret with the new key.

```bash Rotate the master key (emergency procedure)
1. Set PAWABASE_MASTER_KEY to the new value
2. Re-save every Secret row through the Platform API
   (Studio's Secrets page does this automatically on edit)
3. Verify by reading back each secret
4. Back up the old master key securely, in case you need to decrypt
   historical ciphertext from backups
```

Because rotating the master key is an operation that touches every secret, it should be treated with the same gravity as rotating a database encryption key. Back up the old key before rotating, and schedule the re-encryption of all secrets as a single coordinated operation.

<Warning>
Never share the `master_key` between installations. It is installation-specific — a key from one Pawabase instance cannot decrypt secrets from another. The salt is fixed per installation, so the same key string produces different Fernet keys across different installations. This means backing up a `master_key` from one environment and restoring it in another will silently fail to decrypt existing secrets.
</Warning>

## Masking and display

The `mask()` function provides a display form that proves a value exists without revealing it:

```python pawabase_core/crypto.py
def mask(value: str | None) -> str:
    """A display form that proves a value exists without revealing it."""
    if not value:
        return ""
    return "•" * 8 + (value[-4:] if len(value) > 12 else "")
```

A 20-character secret displays as `••••••••••••••••••5678`. This is what Studio shows in the Secrets list and what the Platform API returns after the initial creation. The full plaintext is only ever exposed once — at creation or rotation time — and is never returned in list or read operations.

## Secret access auditing

Every secret resolution is recorded as part of the environment's compiled app activity, and every secret creation, update, or deletion is recorded in the [audit log](/operate/audit-log). The `Secret` model tracks `updated_by`, so Studio can show who changed a secret and when. Combined with the audit log's `action` field (`secret.created`, `secret.updated`, `secret.deleted`), you can reconstruct the full lifecycle of any secret.

## Operational checklist

<AccordionGroup>
  <Accordion title="Adding a new secret to an environment">
    1. In Studio, navigate to the environment and open **Secrets**.
    2. Click **New secret** and give it a descriptive name (e.g. `stripe-webhook-secret`).
    3. Paste the plaintext value. The value is encrypted and stored immediately.
    4. In the environment's `infra` or `auth` config, add a `secret://NAME` reference where the driver needs it.
    5. Recompile the environment (or deploy) so the reference is resolved into the running app.
    6. Verify by checking that the service connects — a failed connection usually means the reference name doesn't match the secret's `name`.
  </Accordion>
  <Accordion title="Rotating a secret without downtime">
    1. Create the new secret value as a *new* row with a different name (e.g. `stripe-webhook-secret-v2`).
    2. Update the environment config to reference the new name.
    3. Recompile the environment. The old secret is now unused but still intact.
    4. Verify the service works with the new secret.
    5. Delete the old secret row. This removes the ciphertext and the reference from the environment config.
  </Accordion>
  <Accordion title="Emergency: master key compromise">
    1. Rotate `PAWABASE_MASTER_KEY` immediately.
    2. Re-save every `Secret` row through the Platform API or Studio (each edit re-encrypts with the new key).
    3. Back up the old master key securely — you may need it to decrypt database backups taken before the rotation.
    4. Investigate how the key was exposed. A `master_key` in a `.env` file or a repository means every secret was readable to anyone with access to that file.
  </Accordion>
</AccordionGroup>

## Reference: environment config fields that accept secrets

| Config field | Environment | Example reference | Driver |
| --- | --- | --- | --- |
| `database.url` | `infra` | `secret://DB_URL` | `DataSourcePool` |
| `storage.credentials` | `infra` | `secret://S3_CREDENTIALS` | `StorageManager` |
| `mail.smtp_password` | `infra` | `secret://SMTP_PASSWORD` | `MailManager` |
| `providers.google.client_secret` | `auth` | `secret://GOOGLE_CLIENT_SECRET` | `Akountz` (OAuth provider config) |
| `providers.mailgun.api_key` | `auth` | `secret://MAILGUN_API_KEY` | `Akountz` |

Any `secret://NAME` reference in these fields is resolved by the corresponding manager at the moment it builds its connection configuration. The platform never stores a resolved secret in a config blob — the reference stays in the database, and resolution happens in memory, per process, at startup or compile time.
