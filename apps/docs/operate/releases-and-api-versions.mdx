title: "Releases and API versions"
description: "Freeze definitions, publish independent /rest/v1 and /rest/v2 APIs, and roll back safely."
---

Pawabase separates editing from serving. Resources, routes, policies, schemas, flows, and automation definitions remain editable in an environment, while public traffic can run an immutable release.

## The release model

A **revision** is a read-only snapshot of every executable definition in an environment. A **branch** records a revision lineage. A **release** assigns one validated revision to a public API version such as `v1` or `v2`. Activation changes that version's pointer atomically; it does not copy definitions into the live editor.

```text
editable definitions -> revision -> release -> /rest/v2
                                      ^
                                      └─ atomic active pointer
```

Create and operate these objects from **Studio → Releases & versions**. The equivalent Platform API paths live below:

```text
/platform/v1/projects/{project}/envs/{env}/branches
/platform/v1/projects/{project}/envs/{env}/revisions
/platform/v1/projects/{project}/envs/{env}/api-versions
/platform/v1/projects/{project}/envs/{env}/releases
/platform/v1/projects/{project}/envs/{env}/deployments
```

## Publishing `v2`

1. Finish and test the working definitions.
2. Create a revision on `main` or another branch. Pawabase compiles the snapshot and records any problems.
3. Create the `v2` API version once.
4. Prepare a release from a valid revision. Pawabase compares it with the currently active `v2` release.
5. Review breaking findings, then activate the release.

After activation, clients can use both paths independently:

```text
GET /rest/v1/orders
GET /rest/v2/orders
```

Changing definitions in Studio does not alter either released API. Existing projects that have not activated a release retain the previous behavior: `/rest/v1` serves the current compiled environment.

## Compatibility checks

Release preparation blocks breaking changes unless the operator explicitly acknowledges them. Current checks cover removed resources, removed custom routes, removed fields, field type changes, optional fields becoming required, and newly required fields without defaults. Policy changes are warnings because their compatibility depends on application intent.

Compatibility checks reduce risk; they do not replace contract tests against real clients.

## Rollback

Every activation records the old release as the version's previous release. Rollback compiles that previous snapshot, atomically restores its pointer, and writes an append-only deployment record. No definition rewrite or process restart is required.

Rollback changes behavior, not data. All releases in one environment share its application database, secrets, and infrastructure. Destructive database migrations therefore need their own expand-and-contract rollout; restoring an older definition cannot restore deleted columns or records.

## Runtime consistency

Requests are tagged with their API version, release, and revision in observability. Events and queued flow, function, and mail work carry the originating release id, so delayed work does not silently switch to newer definitions. Webhook routing is selected from the release, while the persisted endpoint remains environment-owned. Cache namespaces are release-specific as well.

Python extension code is loaded from the project code directory and is not embedded in a definition revision. If released routes depend on Python extensions, deploy compatible code before activating the release.
