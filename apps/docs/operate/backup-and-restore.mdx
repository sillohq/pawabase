A backup is one JSON file that holds what makes an environment yours: what you designed, who your users are, and what they stored. You download it from **Backups** in Studio (under **Operate**), keep it somewhere safe, and restore it when something goes wrong or when you want the same system in another environment.

## What a backup holds

| Part | Contents |
| --- | --- |
| **Definitions** | Resources, policies, schemas, transformers, flows, routes, buckets, mail templates, event subscriptions, webhooks, inbound hooks and schedules |
| **Settings** | The environment's auth configuration and settings: token lifetimes, password rules, CORS origins, rate limits |
| **Users & access** | Roles and their permissions, users with their password hashes, each user's roles and direct permissions, linked sign-in identities, MFA factors and recovery codes, organizations with members and teams |
| **Data** | Every row of every resource's table, with ids preserved |

Because password hashes are included, people keep their passwords after a restore. Because ids are preserved, a row whose `owner_id` points at a user still points at them.

### What it leaves out

API keys, secret values, stored files, sessions, logs and jobs are not part of a backup. Keys exist only as hashes and secrets only as ciphertext, so neither can be exported usefully; recreate them when you restore into a new installation. The file lists the names of your secrets so you know what to recreate. Infrastructure (the database, storage and mail) comes from the installation's `.env`, so it is not in the file either.

Sessions are not restored. A replace removes the environment's users, and their sessions with them, so those people sign in again.

<Warning>
A backup contains password hashes and personal data. Store it like a database dump: private, encrypted at rest, and not in a repository.
</Warning>

## Downloading a backup

1. Open **Backups** for the environment.
2. Tick the parts you want. All four are ticked by default.
3. Select **Download backup**.

The file is named `<project>-<env>-<time>.pawabase-backup.json`. Only organization **admins and owners** can download or restore a backup, because the file contains password hashes.

The same download is available from the Platform API:

```bash
curl "$API/platform/v1/projects/acme/envs/production/backup?include=definitions,users,data" \
  -H "Authorization: Bearer $TOKEN" -o acme-production.json
```

`include` takes any of `definitions`, `settings`, `users`, `data`, separated by commas. Leave it out for everything.

Each file carries a checksum. A restore refuses a file whose checksum no longer matches, which catches a truncated download or a hand edit.

## Restoring

Open **Backups**, choose the file, and Studio reads it and shows what it contains without changing anything. Then choose what to restore and how.

| Strategy | What it does |
| --- | --- |
| **Merge** (default) | Adds what is missing and updates what matches: definitions by name, rows by id, users by email. Anything the backup does not mention stays |
| **Replace** | First removes what the chosen parts hold in this environment, then loads the backup. Afterwards the environment holds exactly what the backup held |

Replace deletes current definitions, rows or users, so Studio asks you to type the environment's name first. Download a fresh backup before you replace.

A restore applies its parts in this order:

- **Definitions** are restored first and the environment's version is bumped, so the API recompiles.
- **Data** tables are created if they are missing, then rows are loaded. With a PostgreSQL data database the id counter is moved past the highest restored id, so new rows do not collide.
- **Users** are restored in Akountz with their original ids. If an id is already taken by a different person, the user is restored under a new id and the response says so, because rows that refer to the old id will not follow.

The response lists what was restored and any warnings, such as columns in the backup that are no longer fields of the resource.

### Restoring into another environment

A backup restores into any environment, not only the one it came from. This is how you clone production into a staging environment. Remember that:

- Webhook and inbound-hook signing secrets are stored encrypted with the installation's key, and the backup carries them as they are. Into a different installation they will not decrypt, so set those secrets again.
- Settings such as CORS origins come across with the file. Review them in the target before you open it to traffic.
- Replacing users in a target environment removes its current users and their sessions.

## From the API

```bash
# See what a file contains, changing nothing
curl -X POST "$API/platform/v1/projects/acme/envs/staging/restore" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d "{\"backup\": $(cat acme-production.json), \"dry_run\": true}"

# Replace staging with it
curl -X POST "$API/platform/v1/projects/acme/envs/staging/restore" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d "{\"backup\": $(cat acme-production.json), \"strategy\": \"replace\", \"confirm\": \"staging\"}"
```

| Body field | Meaning |
| --- | --- |
| `backup` | The document a backup produced |
| `include` | Parts to restore. Defaults to every part the file holds |
| `strategy` | `merge` or `replace` |
| `dry_run` | Report what the file contains and what would be restored |
| `confirm` | For `replace`, the environment's name |

A request that names a part the file does not hold, a file in another format, a damaged file, or a `replace` without `confirm` is refused with `422` and nothing changes. Both actions are written to the [audit log](/operate/audit-log) as `backup.created` and `backup.restored`.

## Limits and good habits

| Limit | Detail |
| --- | --- |
| Size | A backup is one JSON document built in memory, capped at 250,000 rows. Beyond that, dump the database with its own tools |
| Tables outside resources | Only tables that belong to a resource are backed up. Tables you made in the database console are not |
| Not atomic across services | Definitions, users and data are restored one after another. If a restore stops part-way, run it again: merge is safe to repeat |
| Branch drafts | A backup reads the environment's live definitions, not a branch's draft changes |

A schedule you can rely on beats an occasional download: take a backup before every promotion and before every `replace`, and restore one into a scratch environment now and then to prove it works.
