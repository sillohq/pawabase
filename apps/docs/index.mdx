## What Pawabase is

Pawabase is a **backend platform you run yourself**. You describe your application as data: resources (tables), policies (who may do what), flows (what happens when), and Pawabase compiles those definitions into a live, documented, validated API behind a single gateway.

It is built on [Sillo](https://sillo.build), a batteries-included Python framework, and follows one rule: **use the framework's primitive when one exists, and add product only where it stops**. Routing, validation, auth backends, the ORM, queues, the scheduler, storage, mail and OpenAPI are Sillo's. Pawabase adds the policy engine, the flow engine, the schema compiler and the control plane.

## Why teams choose it

<AccordionGroup>
  <Accordion title="You own every byte" icon="lock">
    Resource data lives in **your** database, files in **your** bucket, mail through **your** SMTP. Pawabase stores definitions and platform state; it never takes custody of your application data.
  </Accordion>
  <Accordion title="Policies you can read" icon="book-open">
    Access rules are small JSON conditions with named, reusable policies, not SQL functions scattered across migrations. Studio edits them with a rule builder; the engine explains every decision.
  </Accordion>
  <Accordion title="Logic without a deploy" icon="workflow">
    Most backend logic (validate, write, notify, charge, sync) is composed from blocks in Studio and changes the moment you save. Python is there for the rest.
  </Accordion>
  <Accordion title="Environments are real" icon="layers">
    Each project has isolated environments with their own keys, secrets, signing keys, data and queues, and a one-click promotion of definitions between them.
  </Accordion>
</AccordionGroup>
