## The mental model: a policy is a yes-or-no question about a situation

Every time something tries to read or change data in Pawabase, one question has to be answered: **may this caller do this, here, now?** A **policy** is how you write the answer down. It is not code that runs in your application and it is not a database permission. It is a small piece of data, a **condition**, that the platform evaluates against a description of the situation:

| The situation is described by | Path | Examples |
| --- | --- | --- |
| **Who is calling** | `$auth` | `$auth.user_id`, `$auth.roles`, `$auth.org`, `$auth.aal` |
| **Which key they used** | `$credential` | `$credential.is_service`, `$credential.scopes` |
| **The record being touched** | `$record` | `$record.owner_id`, `$record.status` |
| **The data being submitted** | `$input` | `$input.status`, `$input.price` |
| **The request itself** | `$request` | `$request.method`, `$request.query.x` |
| **Where it happens** | `$project`, `$env`, `$now` | |

A condition combines checks on those values with `all`, `any` and `not`, and the answer is true or false. That is the whole idea, and it has three consequences that shape the rest of the platform:

1. **Policies are data.** They are stored per environment, validated when you save them, edited in Studio, promoted between environments and referenced by name. Changing who may do something is an edit, not a deploy.
2. **One engine decides everything.** The same evaluator answers for resource operations, custom routes, functions, flows, storage buckets and realtime channels. What differs is the situation it is shown, and what the entry point does with a refusal.
3. **A list is planned, not filtered afterwards.** For a request that returns many rows, the engine can turn part of a policy into SQL, so the database does the filtering and pagination stays correct. This is the single biggest reason to write policies in the condition language rather than in code.

```json
{
  "all": [
    { "authenticated": true },
    { "eq": ["$record.owner_id", "$auth.user_id"] }
  ]
}
```

Read it as a sentence: the caller must be signed in, and the record's owner must be the caller. A resource that attaches this to `list` returns each user their own rows and nobody else's.

Everything on this page was run against a real Pawabase API: resources, routes, buckets and flows were created, called by different callers, and the responses below are what came back. Where something is read from code and not run, it says so.

<Warning>
Several behaviors on this page are **traps**, and they are marked where they appear: a plain `eq` on an owner column lets anonymous callers reach rows that have no owner, a value taken from the query string can rewrite a policy, `DELETE` skips the key-scope check, and a stored policy can silently replace a built-in one. They are collected under [Where the guarantees stop](#where-the-guarantees-stop), and each has its own section where it matters.
</Warning>

## Where policies apply

A policy is attached wherever the platform needs an answer. Every attachment point has a **default** for when no policy is named, and a refusal looks different at each.

| Entry point | Attached in Studio | Default when empty | Refusal |
| --- | --- | --- | --- |
| **Resource operation** (`list`, `get`, `create`, `update`, `delete`) | The resource sheet, **Access** | `authenticated` | `401`, `403` or `404`, depending on the operation. See [the status codes](#from-decision-to-status-code) |
| **Custom route** | The route sheet, **Access** | `authenticated` | `401` or `403` |
| **Function** called directly (`/functions/v1/<name>`) | The function's `@function(policy=...)` | `authenticated` | `401` or `403` |
| **Flow** called directly (`/flows/v1/<name>`) | The flow's HTTP trigger `policy` | `authenticated` | `401` or `403` |
| **Storage bucket** | The bucket sheet, **Read policy** and **Write policy** | `authenticated` (reads `public` when the bucket is public) | `404` for reads and deletes, `403` for uploads and listings |
| **Realtime channel** | **Settings → Realtime**, channel rules and the **Default policy** | `authenticated` | The subscribe or publish is refused |
| **Event subscription** | The subscription's **Only when…** | No condition (always fires) | The subscription does not fire |
| **Inside a flow** | The **Check policy** block (`policy.check`) | n/a | The flow follows the `denied` edge |

Two things are not on the list on purpose. **A resource's `list` is not "filtered" by a policy after the fact**: the policy is planned first. And **the Records tab, the Database console and flows' resource blocks are not governed by caller policies at all**: they act with the platform's own authority. [Where policies are enforced](/policies/enforcement-points) lists everything that is and is not governed, in order.

## A first policy, run end to end

A `notes` resource has an `owner_field` of `user_id`, and two stored policies are involved. The simplest is the shorthand reference `owner:user_id`, written straight into the resource's **Access** section for `list`, `get`, `update` and `delete`. This is the run, with two signed-in users:

| Request | Answer |
| --- | --- |
| `u-1` creates a note | `201`. The server stamps `user_id: "u-1"` |
| `u-2` creates a note | `201`. `user_id: "u-2"` |
| `u-1` lists | `200`, only `u-1`'s note, `total: 1` |
| `u-2` lists | `200`, only `u-2`'s note |
| `u-1` gets `u-2`'s note | `404`, `Not found` |
| Someone not signed in lists | `401`, `Authentication required` |

The same rule written as a stored policy, `own_rows`, with the condition `{"eq": ["$record.user_id", "$auth.user_id"]}`, gave the same answers for signed-in users, **and one different one**: a caller who is not signed in got `200` with an empty list instead of `401`. The difference is that `owner:<column>` includes a `{"authenticated": true}` check and the plain `eq` does not. That difference is the subject of [a trap below](#a-plain-eq-on-an-owner-column-fails-open), and it is the reason this documentation recommends the shorthand.

## The Studio workspace

Open **Build → Policies**. The page is described as *Named conditions. Reference them anywhere a policy is accepted; equality checks are pushed down to SQL.* It lists each policy with its **name** and **description**. Creating one opens a sheet with:

| Part | What it is |
| --- | --- |
| **Name** | Placeholder `own_rows`. Lowercase letters, digits, hyphens and underscores, starting with a letter, up to 63 characters |
| **Description** | Optional, shown in the list |
| **Who passes** | The section that holds the rule, described as *Checks on record fields are pushed down to SQL, so filtered lists stay paginated correctly. Secret keys always pass.* |
| The rule builder | A **group** (**All of**, **Any of** or **None of** *these rules pass*) with **Rule** and **Group** buttons |
| **JSON** tab | The condition exactly as stored |

A new policy starts with the condition `{"authenticated": true}`, and **Use example** fills in `own_rows`. A group with no rules reads *No rules: everyone passes.* for **All of** and *No rules: nobody passes.* for **Any of**. The rule builder is covered in [the condition language](/policies/conditions#the-rule-builder-in-studio).

### Picking a policy where it is used

Wherever a policy is attached, the same **picker** appears:

| Group | Choices |
| --- | --- |
| **Built-in** | **Anyone (public)**, **Signed-in users**, **Record owner (owner_id)**, **Signed in with 2FA**, **Secret keys & operators**, **Nobody** |
| **This project** | Every stored policy, by name |
| **More** | **Users with role…**, **Users with permission…**, **Owner via field…**, **Keys with scope…**, **Custom rules…**, and **Must satisfy several policies (all of)…** |

The first choice in the list is the **default** and its label depends on where you are: **Default (signed-in users)** on a route, **Default** on a bucket, **Default (authenticated)** for realtime, and **Secret keys only** on a resource operation.

<Warning>
The resource operation's default label is wrong. **Secret keys only** suggests that leaving a resource operation without a policy restricts it to secret keys. It does not: a resource operation with no policy (or `null`) uses `authenticated`, which any **signed-in user** passes. This was run: an operation with a `null` policy answered `200` and `201` for a signed-in user, `401` for a signed-out caller, and `200` for a secret key. If you mean "secret keys only", choose **Secret keys & operators** (the `service` policy) explicitly.
</Warning>

An unknown stored name, for example one that has since been deleted, appears in the picker as `name (unknown)`.

## From decision to status code

A refusal is reported differently depending on whether the caller is signed in, whether the record exists, and which operation was attempted. The rules are consistent enough to learn, and they have a few surprises. These were run with a resource whose `list`, `get`, `update` and `delete` use `{"owner": "owner_id"}` (so only the owner passes) and whose `create` is `authenticated`:

| Request | Caller | Answer |
| --- | --- | --- |
| `POST` | Signed out | `401`, `Authentication required` |
| `GET` list | Signed out | `401`, `Authentication required` |
| `GET` one | Signed out | `401`, `Authentication required` |
| `GET` one | Signed in, **not the owner** | **`404`**, `Not found` |
| `GET` one | Signed in, record does not exist | `404`, `Not found` |
| `PATCH` | Signed out | `401`, `Authentication required` |
| `PATCH` | Signed in, **not the owner** | **`403`**, `policy 'own' refused` |
| `PATCH` | Signed in, record does not exist | `404`, `Not found` |
| `DELETE` | Signed out | **`404`**, `policy 'own' refused` |
| `DELETE` | Signed in, not the owner | `403`, `policy 'own' refused` |
| `DELETE` | Signed in, record does not exist | `404`, `Not found` |
| Any | A secret key | The policy is skipped. See [secret keys bypass policies](#secret-keys-and-operators-bypass-every-policy) |

Read the table as four rules and two oddities:

- **Not signed in and not allowed is a `401`.** The caller is told to authenticate, whatever the real reason was. A client cannot tell "you need to sign in" from "signing in will not help".
- **A single record you may not read is a `404`.** `GET` of someone else's record answers exactly as a record that does not exist does, so a caller cannot probe which ids exist.
- **A refused write by a signed-in caller is a `403`, with the policy's name.** This **does** reveal that the record exists, since a missing record is a `404`. If existence is sensitive, make `update` and `delete` unreadable for strangers too, with a policy that is checked before the lookup, or accept the disclosure.
- **A refused `create` is a `403`.**
- **Oddity: a signed-out `DELETE` is a `404` whose message says `policy ... refused`.** Every other operation turns a signed-out caller away with a `401` before the handler runs. `DELETE` does not, for the reason in [the `DELETE` trap](#delete-skips-the-key-scope-check-and-the-sign-in-gate).
- **Oddity: a refusal can carry a status that contradicts its message.** The `404` above says `policy 'own' refused`. Read the **message**, not only the status, when debugging.

The messages have two forms:

| Message | Meaning |
| --- | --- |
| `policy '<name>' refused` | A named policy said no. An inline condition is named `inline`, and a list is named `a+b` |
| `Authentication required` | The caller is not signed in, and the check that refused them was a policy |
| `This API key lacks the '<scope>' scope` | The key does not carry `resource:read`, `resource:write` or `routes:invoke` |
| `Not found` | A single record the caller may not see, or that does not exist |

## Lists are planned, not filtered after the fact

A list request returns many rows, and a policy that depends on the row cannot be answered by one yes or no. Pawabase handles this in two stages:

1. **Plan.** Before any row is read, the engine evaluates everything in the policy that does **not** depend on the row (who the caller is, their roles, the key's scopes). If that alone decides it, the request is allowed or refused outright. If what remains is a set of equalities between a column and a known value, such as `owner_id = '7'`, those become **SQL filters**.
2. **Residual.** Whatever cannot be turned into SQL is checked **per row**, after the query, in Python.

When the whole policy becomes SQL, the database returns exactly the rows the caller may see, with a correct `total` and correct pages. When there is a residual, rows are removed after the page was fetched, and the list reports `"total": null` and may return short or empty pages. [SQL pushdown](/policies/pushdown) explains how to write policies that stay in SQL, and what a residual costs.

A signed-in user without an organisation asking for a list under a tenant policy was refused before any query ran (`403`, `policy 'same_org' refused`), which is the plan deciding "no row could ever match".

## Secret keys and operators bypass every policy

The first thing the engine checks is whether the credential is a **service** credential, meaning a secret key or an operator. If it is, the answer is yes, with the reason `service credential bypasses policies`, and the policy is never read.

| Credential | Passes every policy? |
| --- | --- |
| A **publishable key**, signed out | No. It is an ordinary anonymous caller |
| A **user's access token** with a publishable key | No. The policy decides |
| A **secret key** | **Yes** |
| A Studio **operator** | **Yes** |
| A **flow** or **function** acting with its own authority | Yes, through the runtime. Resource blocks are trusted |

This is deliberate. Secret keys are how your own servers act, and Studio operates on the data with them. It has two consequences worth stating plainly:

- **A policy is a promise about your public surface only.** It says nothing about what a secret key can do, so a secret key must never reach a browser.
- **You cannot test a policy with a secret key.** It passes everything. Test with a publishable key and a user token, as the callers you are protecting against.

The Studio rule builder says it too, in the policy form: *Secret keys always pass.*

## Defining policies

A stored policy has three fields:

```json
{
  "name": "own_rows",
  "description": "Rows whose user_id is the caller",
  "condition": { "eq": ["$record.user_id", "$auth.user_id"] }
}
```

| Field | Rule |
| --- | --- |
| `name` | `^[a-z][a-z0-9_-]{0,62}$`. Lowercase, starting with a letter. Hyphens are allowed. Anything else is a `422` |
| `description` | Optional text |
| `condition` | `true`, `false`, or an object with one key. See [the condition language](/policies/conditions) |

Saving checks the **shape** of the condition and answers `422` with a message that names the path:

| You saved | Message |
| --- | --- |
| `{"eq": [1]}` | `condition.eq: expected [left, right]` |
| `{"all": [{"zz": 1}]}` | `condition.all[0]: unknown operator 'zz'` |
| A name with a capital or a space | A pattern mismatch on `name` |
| A second policy with an existing name | `409`, `policie already exists` |

Saving does **not** check that the condition is sensible. `{"eq": ["$nope", "$alsono"]}` is valid, and it is **true** for everyone, because two missing values are equal (see [missing is not false](#a-missing-value-equals-a-missing-value)).

### Attaching one

A policy is attached **by name** (or by an inline condition, or a list) wherever the form offers the picker. The attachment is validated when you save the resource, route or bucket:

| You attached | Message |
| --- | --- |
| A name that does not exist | `operations.list.policy: unknown policy 'nope'` |
| An inline condition with a bad shape | `operations.list.policy: condition.eq: expected [left, right]` |
| A Python policy in a list | `operations.list.policy: Python policies cannot be combined in a list; call them from Python` |
| A bucket policy that does not exist | `read_policy: unknown policy 'nope'` |

Two attachment points are **not** checked at save time: a flow's HTTP trigger `policy`, and the policies named in realtime channel rules. A flow whose trigger names a policy that does not exist saves without complaint, and then answers every non-service caller with a plain `500`. See [references](/policies/references).

### The three kinds of policy, and which wins

| Kind | Defined | Referenced as |
| --- | --- | --- |
| **Built-in** | In the platform: `public`, `deny`, `authenticated`, `service`, `owner`, `mfa` | By name |
| **Python** | In your project's code, with `@policy("name")` | By name |
| **Stored** | In Studio, per environment | By name |

When two kinds share a name, **the stored policy wins over the Python one, and both win over the built-in**. That is a trap: a stored policy named `authenticated` replaces the built-in `authenticated` everywhere it is referenced, including every resource operation that has no policy at all. See [a stored policy can replace a built-in](#a-stored-policy-can-replace-a-built-in-one).

### Changing and deleting

Saving a policy takes effect on the next request, and, like any definition save, it bumps the environment's version, so cached responses stop being served (see [Caching](/data/caching)). **Deleting** a policy that something still names is allowed and is not reported. Requests that reach the missing policy fail with a plain `500` for every caller except a secret key, which bypasses policies before the name is resolved. Check where a policy is used before you delete it. [References](/policies/references) covers the lifecycle in detail.

## Why policies instead of code

| | A policy | Code in a handler |
| --- | --- | --- |
| **Where it lives** | A definition in the environment | Your application |
| **Changing it** | Edit and save | Change, review, deploy |
| **One place for many entry points** | Yes: a name used by resources, routes, buckets and channels | You repeat it, or share a function |
| **Lists** | Planned into SQL | You filter in the query yourself, or after |
| **Visible to non-engineers** | Yes, in Studio's rule builder | No |
| **Expressiveness** | Comparisons, membership, patterns, combinations | Anything |
| **Fails how** | Closed for malformed references at save time, open for unvalidated ones | However you wrote it |

The trade is expressiveness for visibility and reuse. When a rule needs a lookup, a calculation or another service, write a [Python policy](/policies/python-policies), and keep the rest in conditions.

## The order of checks in a request

A policy is one of several checks, and knowing the order explains most "why did I get that status" questions. For a resource operation, in the order they happen:

| Order | Check | Refusal |
| --- | --- | --- |
| 1 | **Rate limit**, if the resource has one | `429` |
| 2 | **Body validation**, for `create` and `update` | `422` |
| 3 | **Key scope** (`resource:read` or `resource:write`), for every operation except `DELETE` | `403`, `This API key lacks the '...' scope` |
| 4 | **The plan**: the part of the policy that does not depend on a record | `401` or `403` |
| 5 | **The query and the per-row checks** | rows are removed, or `404` for a single record |
| 6 | **The write**, then events and cache clearing | |

Two orderings have security consequences:

- **Validation runs before the policy.** A signed-out caller who sends an **invalid** body to a protected `POST` gets a `422` that names the offending fields and rules; sent a **valid** body they get a `401`. The field names of a protected resource are therefore visible to anyone who can reach it. Treat the shape of your API as public.
- **The policy runs before the cache.** A cached list is served only to a caller who passed the gate, and the cache key includes the caller's identity and role. A refused caller stays refused, and one user's entry is never served to another. See [Caching](/data/caching#the-policy-runs-first).

A custom route adds the key scope `routes:invoke`, runs the plan before its cache lookup, and runs the **full** policy (with the submitted body as `$input`) after it. See [Custom routes](/data/custom-routes#who-may-call-a-route).

## Policies and the rest of the platform

| Part | How it relates to policies |
| --- | --- |
| **Field validation** | Runs first. A field's rules and a policy's conditions are independent. `required`, `enum` and `pattern` are not policies |
| **Transformers** | Reshape the response after the policy allowed it. They do not decide access, and a field they hide can still be filtered on. See [Transformers](/data/transformers#what-a-transformer-protects-and-what-it-does-not) |
| **Filtering** | A caller's filters can only narrow what the policy allows. They add `AND`. See [Filtering](/data/filtering#filters-and-policies) |
| **Relations (`expand`)** | Each related row is checked against the **related** resource's read policy, and a row the caller may not read comes back as `null`. See below |
| **The cache** | Reads are cached per caller, after the gate |
| **Events and realtime** | Carry the raw record to every consumer. A policy does not apply to them |
| **Migrations and the console** | Not governed. They act with the platform's authority |
| **Rate limits** | Counted per caller, before policies |
| **API keys** | A key has a role and **scopes**. Scopes are checked before policies, except for `DELETE` |

### Relations answer to the related resource's policy

When a list is requested with `?expand=`, each related row is checked against the policy of the resource it comes from (its `get`, or its `list` when it has no `get`). A row the caller may not read comes back as `null`. This was run: a public `notes` resource with a `belongs_to` relation to a `secrets_` resource whose `get` is `{"owner": "owner_id"}`:

```json
{ "id": 1, "t": "n", "secret_id": 1, "secret": null }
```

The caller received the note, the foreign key and `null` for the secret they do not own. The foreign key itself is not hidden, since it belongs to the note. If a foreign key is sensitive, it needs its own protection. See [Relations](/data/relations).

## The decision, as an operator sees it

Every request records which policy decided. In **Observability**, open a request and the trace's HTTP block carries `notes`, which includes the policy that was applied to the request (`policy: "own_rows"`, or `"inline"`). The refusal message in the response names the same policy, so a `403` that says `policy 'org_admin' refused` points straight at the definition to open. For a list that was refused by the plan, the name is the policy that produced the plan.

What the trace does **not** show is *why* the condition was false: which comparison failed and with which values. For that, evaluate the condition yourself with a **Check policy** block in a flow, which returns `allowed` or `denied` for a context you supply. See [Testing and debugging](/policies/debugging#evaluating-a-condition-with-policycheck).

## Policies for each kind of caller

Policies are easiest to design from the callers outward. For each audience, choose the **least** that works.

| Audience | Typical access | Policies to reach for |
| --- | --- | --- |
| **The public** (a marketing site, a catalogue) | Read some things, never write | `public` on `list` and `get` of a read-only resource, with `create`, `update` and `delete` left **disabled** (not set to `deny`: a disabled operation has no endpoint at all) |
| **Signed-in members** (an app) | Read and write their own data | `owner:<column>` for reads and writes, `authenticated` for create, with the owner stamped by the server |
| **Team members** (a SaaS) | Read and write the organisation's data | A tenant comparison on `$auth.org`, plus checks on `$input` for create and update |
| **Staff** (a back office) | Everything, with audit | `role:staff` or `permission:...` on the staff routes, and the Records tab for ad hoc fixes |
| **Partners** (an API consumer) | A narrow surface | A **route** with a policy on `scope:` or a role, not direct resource access |
| **Your servers** | Everything | A **secret key**, which bypasses policies, never exposed to a browser |
| **Third parties calling in** (callbacks) | One endpoint | An inbound hook or a route that verifies a shared secret, not a public resource |

The first row has a point worth making: **an operation that is not enabled does not exist**. A disabled operation is answered by the router (`405 Method Not Allowed` for a method on a path that still serves another), with no policy to misconfigure. Enable only what a caller needs.

## Reading a policy aloud

A condition is easy to review when it can be said as a sentence. These are the conditions used on this page, read aloud:

| Condition | In words |
| --- | --- |
| `{"authenticated": true}` | The caller is signed in |
| `{"role": ["staff", "admin"]}` | The caller has at least one of those roles |
| `{"permission": ["posts.write", "posts.publish"]}` | The caller has **all** of those permissions (or the `*` permission) |
| `{"owner": "owner_id"}` | The caller is signed in, and is the record's owner |
| `{"all": [{"exists": "$auth.org"}, {"eq": ["$record.org_id", "$auth.org"]}]}` | The caller belongs to an organisation, and the record belongs to the same one |
| `{"any": [{"eq": ["$record.status", "published"]}, {"role": "editor"}]}` | The record is published, or the caller is an editor |
| `{"ne": ["$input.status", "published"]}` | The submitted status is not `published` (and is true when no status is sent) |
| `{"lte": ["$input.qty", 10]}` | The submitted quantity is at most ten (and false when none is sent) |
| `{"in": ["$auth.org_role", ["owner", "admin"]]}` | The caller's role in their organisation is owner or admin |
| `{"scope": "resource:write"}` | The key carries the write scope |
| `{"aal": "aal2"}` | The caller has passed a second factor |
| `{"not": {"role": "banned"}}` | The caller does not have the `banned` role |

Notice the two parenthetical remarks. `ne` with a missing value is **true**, and `lte` with a missing value is **false**. They follow from how missing values compare, and they decide whether a policy guards what you meant it to. See [operators](/policies/operators#null-handling).

## Policies across environments

A policy is a definition, so **promoting** an environment copies it to the target, by name, as an upsert: a policy with the same name is overwritten and a new one is created. Nothing is deleted, so a policy you removed in the source stays in the target.

| Situation | What to check |
| --- | --- |
| A resource promoted whose policy was not | The target's resource names a policy that does not exist there, and requests answer `500` for every caller except a secret key. Promote with the default `include` so policies and resources travel together |
| A policy edited in development and promoted | The change reaches every resource, route and bucket that uses it. A broader condition opens everything at once |
| A policy removed in development | It remains in production until you remove it there |
| A Python policy | Part of your deployed code, not a definition, so it is never promoted. Deploy the code to each environment |

A **release** (a pinned API version) carries the policies of its revision, so a released API keeps enforcing the policies it was published with, whatever you edit in the live definitions. See [Releases and API versions](/operate/releases-and-api-versions).

## What policies are not

| A policy is not | Use instead |
| --- | --- |
| **Field validation** | The resource's field rules. A policy cannot say "price must be positive", only who may submit one |
| **Field hiding** | A [transformer](/data/transformers) or `select`, bearing in mind that filters can still read hidden fields |
| **Rate limiting** | A resource or route `rate_limit`, which counts per caller |
| **Secrecy for the response shape** | Nothing. Validation errors name fields before the policy runs |
| **A guarantee about secret keys** | Keep them on the server |
| **An audit log** | The platform's [audit log](/operate/audit-log) records management actions. Reads are not audited |
| **Row-level security in the database** | A policy acts in the API. A direct database connection bypasses it |

The last row is worth repeating for anyone who gives out database credentials: **a database role is not subject to Pawabase's policies.** See [Your database](/data/your-database#a-read-only-role-for-people).

## A checklist before launch

1. **Every enabled operation has a policy you chose,** not the default.
2. **No policy is named `public`, `authenticated`, `deny`, `service`, `owner` or `mfa`.**
3. **Ownership comparisons use `owner:<column>`,** or start with `{"authenticated": true}`.
4. **No condition compares a record to a query or path value.**
5. **Create and update pin the tenant,** and the owner cannot be changed.
6. **`delete` is closed on every public resource.**
7. **Nothing trusts `meta` claims.**
8. **Hidden fields are also kept out of events,** or events are off.
9. **Every path you wrote exists in the context** (no `$auth.id`, no `$auth.org_id`).
10. **You tested as a signed-out caller, a stranger, a member and an admin,** with a publishable key and user tokens.
11. **No policy was deleted that something still names.**
12. **You know which lists have a residual,** and what `total: null` does to your UI.

## Where the guarantees stop

The engine is small and predictable, and that is also why its failure modes are easy to describe. Each of these was reproduced on a running API. They are grouped by what they let a caller do, and each says what to write instead.

### A plain `eq` on an owner column fails open

The natural way to write "the owner may read their rows" is a stored policy:

```json
{ "eq": ["$record.owner_id", "$auth.user_id"] }
```

It works for signed-in users. It also lets **anyone who is not signed in** reach every row whose `owner_id` is `NULL`. For a signed-out caller `$auth.user_id` is empty, a `NULL` column is empty too, and the engine treats two empty values as **equal**. This was run on a resource with three rows (owned by `u-1`, owned by `u-2`, and **no owner**), with that policy on `list`, `get`, `update` and `delete`:

| Request, signed out | Answer |
| --- | --- |
| List | `200`, empty (the SQL filter `owner_id = NULL` matches nothing) |
| Get the row owned by `u-1` | `404` |
| **Get the row with no owner** | **`200`**, the row |
| **`PATCH` the row with no owner** | **`200`**, and the title became `hijacked by anon` |
| **`DELETE` the row with no owner** | **`204`**, and the row was gone |

Rows with no owner are not exotic. They are rows created by a flow, the Records tab, the Database console, an import, or before the owner field existed. A policy that was safe on the day you wrote it stops being safe the first time such a row appears.

The `owner:` shorthand does not have the problem, because it expands to **both** halves:

```json
{ "all": [{ "authenticated": true }, { "eq": ["$record.owner_id", "$auth.user_id"] }] }
```

Write `"owner:user_id"` (or `{"owner": "user_id"}`), or put `{"authenticated": true}` in front of any hand-written ownership comparison. The general rule: **a comparison between a caller value and a record value must first establish that the caller value exists.** See [Shorthands](/policies/shorthands#owner).

### A missing value equals a missing value

The root of the trap above is general. A path that does not resolve, such as a typo or a field the context does not have, becomes empty, and two empty values are equal:

| Condition | Result |
| --- | --- |
| `{"eq": ["$nope", "$alsono"]}` | **true** |
| `{"eq": ["$nope", null]}` | true |
| `{"eq": ["$record.missing", null]}` | true |
| `{"ne": ["$record.missing", "x"]}` | true |

A misspelled path therefore does not fail closed. It evaluates to "empty", and a comparison with another empty value passes. When a policy that should refuse starts passing, look for a path that resolves to nothing: `$auth.org_id` (the key is `$auth.org`), `$auth.id` (the key is `$auth.user_id`), `$event.data` (the key is `$event.payload`). Studio's own path suggestions include two of those names, and neither exists. See [the context reference](/policies/context).

### A request value can rewrite the policy

Some policies compare a record to something the caller **controls**, such as a query parameter:

```json
{ "eq": ["$record.owner_id", "$request.query.as"] }
```

With `?as=u-1` this returns `u-1`'s rows, as intended. With the value **`$record.owner_id`** it returns **every row**. This was run on a resource with rows owned by `u-1`, `u-2` and nobody:

| Request, as `u-2` | Answer |
| --- | --- |
| `GET /rest/v1/qdocs?as=u-1` | `200`, one row |
| `GET /rest/v1/qdocs?as=$record.owner_id` | **`200`, every row** |
| `GET /rest/v1/qdocs/1?as=$record.owner_id` | **`200`**, a row owned by someone else |
| `GET /rest/v1/qdocs?as=$$record.owner_id` | `200`, empty |

When the engine plans a request, it substitutes the values it already knows (the query string, the claims) into the part of the condition that must wait for each row. A substituted value that begins with `$record` or `$input` is read **again** as a path, so the caller's text becomes part of the rule. A value that begins with `$$` is treated as a literal, which is why the last request was safe.

The practical rule: **do not compare a record field to a value the caller supplies in the request** (query string, path parameters). Compare it to the caller's identity (`$auth.*`), which comes from a verified token, or filter on the value in the client with an ordinary `filter[...]` and let the policy decide only who may read.

### `DELETE` skips the key-scope check and the sign-in gate

For every other operation a request first passes a **gate** that checks the key's scope (`resource:read` for reads, `resource:write` for writes) and turns a signed-out caller away early. `DELETE` does not pass through that gate. The policy is still evaluated inside the handler, but nothing else is:

| Request, on a resource whose `delete` policy is `public` | Answer |
| --- | --- |
| `POST` with a key that has only `resource:read` | `403`, `This API key lacks the 'resource:write' scope` |
| `PATCH` with the same key | `403`, `This API key lacks the 'resource:write' scope` |
| **`DELETE` with the same key** | **`204`**, and the record was deleted |
| `GET` with a key that has only `resource:write` | `403`, `This API key lacks the 'resource:read' scope` |
| **`DELETE` with a key that has neither scope** | `404` (the record was already gone), not `403` |

So **scopes do not protect `DELETE`**. A read-only key, such as one you hand to a public website, can delete anything the `delete` policy allows. Two defences:

- **Do not enable `delete` for a public resource at all**, or give it a policy that needs a user (`authenticated` or `owner:...`), so a bare key cannot pass.
- **Keep read-only keys read-only by policy, not by scope.** Treat the `delete` policy as the only protection.

A signed-out `DELETE` that the policy refuses answers `404` with the refusal message, as in [the table above](#from-decision-to-status-code), and it did not delete anything.

### A stored policy can replace a built-in one

Built-in policies and stored policies share one namespace, and **stored wins**. This was run: a stored policy named `authenticated` with the condition `false` was created. From then on, every resource operation that used `authenticated`, including every operation with **no policy at all** (the default is `authenticated`), refused every signed-in caller:

```text
POST /rest/v1/py   as a signed-in user   →   403  policy 'authenticated' refused
```

Deleting the stored policy restored the built-in. The same holds for `public`, `deny`, `service`, `owner` and `mfa`, and for a stored policy that shares a name with a Python policy.

Do not name a stored policy after a built-in. Anyone who can create policies in an environment can change what `public` means, so creating policies is an administrative right.

### Deleting a policy that is in use

Deleting is allowed, and nothing checks references. After a stored policy that a resource named was deleted:

| Request | Answer |
| --- | --- |
| A signed-in user lists the resource | **`500`**, `Internal Server Error` |
| A secret key lists it | `200`. The bypass happens before the name is looked up |
| The Overview's definitions-with-problems list | Empty. The problem is not reported |

The failure is a plain `500`, not a refusal, so the resource looks broken, not locked. Search for a policy's name before deleting it. [References](/policies/references#deleting-and-renaming) gives a checklist.

### An update that moves a row out of your scope

A policy on `update` decides from the **existing** record and, if you write it, from the **submitted** data. A tenancy policy that only looks at the record lets a user change the tenant column:

```json
{ "all": [{ "exists": "$auth.org" }, { "eq": ["$record.org_id", "$auth.org"] }] }
```

On an `update` that passes, because the row is currently theirs. This was run: a member of `acme-co` sent `PATCH {"org_id": "beta-co"}` for their own task and got **`200`**. They could no longer read it (`404`), and a member of `beta-co` could (`200`). A user can push rows **into** another tenant. Add a check on the submitted value so the tenant cannot change:

```json
{
  "all": [
    { "exists": "$auth.org" },
    { "eq": ["$record.org_id", "$auth.org"] },
    { "any": [{ "not": { "exists": "$input.org_id" } }, { "eq": ["$input.org_id", "$auth.org"] }] }
  ]
}
```

And the same on `create`, where the policy must pin the tenant to the caller's own. See [the multi-tenant recipe](/policies/recipes#multi-tenancy).

### `exists` is false for `null`, so `not exists` allows nulling

A field-level guard such as "only admins may change the price" is often written:

```json
{ "any": [{ "role": "admin" }, { "not": { "exists": "$input.price" } }] }
```

For a `PATCH` that omits `price` the guard passes, correctly. For one that sends `"price": null` it **also passes**, because `exists` is false for `null`. This was run: a user's `PATCH {"price": 1}` was refused (`403`), and `PATCH {"price": null}` answered `200` and **cleared the price**. A guard on a field must handle explicit `null` too. A condition cannot ask "was the key sent" separately from "is its value present", so use a [Python policy](/policies/python-policies) that checks `"price" in context["input"]`, or reject the change in a route that validates it. See [operators](/policies/operators#null-handling).

### Claims the user can edit

Tokens carry two bags of free-form claims. **`app`** is controlled by administrators. **`meta`** is edited by the user. Both are readable in a policy under `$auth.claims`:

| Condition | Trust |
| --- | --- |
| `{"eq": ["$auth.claims.app.plan", "pro"]}` | Safe. Only an administrator sets it |
| `{"eq": ["$auth.claims.meta.plan", "pro"]}` | **Not safe.** The user wrote it |

This was run: a user whose token had `meta.plan = "pro"` was refused by the policy that checked `app.plan` (`403`) and **passed the policy that checked `meta.plan`**, and deleted a record. Never base access on `meta`.

### Time cannot be compared

`$now` exists, and it is a real date and time, not text. Record fields come back as text from the database, and comparing text with a date is an error that makes the condition **false**. A policy `{"gt": ["$record.expires_at", "$now"]}` refused every row in a run, including one that expired in 2099, and the list reported `total: null`. A policy cannot express "not expired". Maintain a flag with a schedule instead. See [operators](/policies/operators#time).

### Refusing existence

A refused `PATCH` or `DELETE` by a signed-in caller is a `403`, while a missing record is a `404`, so the two can be told apart. A refused `GET` is a `404` and cannot. If the existence of a record is itself sensitive, a signed-in stranger can learn it by trying to update it.

## Designing a policy set

A short list of habits that remove most of the traps above.

| Habit | Why |
| --- | --- |
| **Start closed.** Choose `deny` or a role, and open up deliberately | An operation you forgot is closed instead of open. Remember that an empty policy means `authenticated`, not `deny` |
| **Prefer shorthands for identity.** `owner:user_id`, `role:admin`, `permission:posts.write` | They include the `authenticated` check and the null handling you would forget |
| **Compare against `$auth`, not `$request`.** | Tokens are verified. Query strings are not |
| **Pin the tenant on `create` and `update`.** | Otherwise rows can be created in or moved to another tenant |
| **Separate read and write policies.** | A policy that is right for reading is rarely right for writing |
| **Keep `delete` closed on public resources.** | Scopes do not protect it |
| **Name policies for what they allow:** `own_rows`, `org_admin`, `published_or_owned` | A reader sees intent, not mechanics |
| **Never name a policy after a built-in.** | The stored one wins |
| **Test as the callers you fear.** | Signed out, a stranger, a member, an admin. Never with a secret key |
| **Check the Overview after deleting or renaming.** | Missing policies are not reported |

## A complete example: a small notes service

A service where users keep private notes, everyone can read notes marked public, and staff can read and delete anything.

```json
{
  "name": "readable_note",
  "description": "Public notes, the owner's own, or anything for staff",
  "condition": {
    "any": [
      { "eq": ["$record.visibility", "public"] },
      { "owner": "owner_id" },
      { "role": "staff" }
    ]
  }
}
```

```json
{
  "name": "pinned_to_owner_or_staff",
  "description": "Edit only your own, and never change who owns it",
  "condition": {
    "any": [
      { "role": "staff" },
      {
        "all": [
          { "owner": "owner_id" },
          { "not": { "exists": "$input.owner_id" } }
        ]
      }
    ]
  }
}
```

attached as:

| Operation | Policy | Why |
| --- | --- | --- |
| `list` | `readable_note` | Public notes for everyone, the caller's own, all for staff |
| `get` | `readable_note` | The same, one record |
| `create` | `authenticated` | A signed-in user. The server stamps the owner |
| `update` | `pinned_to_owner_or_staff` | Own notes, and the owner column is stripped from a patch anyway |
| `delete` | `owner:owner_id` | Owners only. Staff delete through the Records tab or a secret key |

What each caller sees: a signed-out visitor lists only public notes (the plan turns `visibility = 'public'` into a SQL filter only when it can, and here the `any` makes it a **per-row check**, so `total` is `null`: see [pushdown](/policies/pushdown)); a signed-in user lists public notes and their own; staff list everything; nobody but the owner deletes through the API.

## Common mistakes

| Mistake | What goes wrong | Instead |
| --- | --- | --- |
| Testing with a secret key | Everything passes | A publishable key and user tokens |
| An ownership `eq` with no `authenticated` | Anonymous access to unowned rows | `owner:<column>` |
| Believing "Secret keys only" on a resource operation | It is `authenticated` | Choose **Secret keys & operators** |
| Naming a policy `public` or `authenticated` | Replaces the built-in | A descriptive name |
| Deleting a policy without searching | Silent `500` | Search, then delete |
| A path with a typo | Two empties are equal | Check the [context reference](/policies/context) |
| Comparing to a query parameter | The caller rewrites the rule | Compare to `$auth` |
| An update policy that ignores `$input` | Rows move between tenants | Check the submitted tenant |
| Using `meta` claims | The user wrote them | Use `app` claims |
| Using `$now` | Always false | A scheduled flag |
| Relying on scopes for `DELETE` | Not enforced | A policy that needs a user |
| Expecting `total` with a residual | It is `null` | Design for [pushdown](/policies/pushdown) |

## Questions that come up

<AccordionGroup>
  <Accordion title="What is the default policy?">
    `authenticated` for resource operations, routes, functions, flows and buckets, which any signed-in user passes. Studio labels the resource operation default **Secret keys only**, which is wrong.
  </Accordion>
  <Accordion title="Can a secret key be refused by a policy?">
    No. A service credential passes before the policy is read.
  </Accordion>
  <Accordion title="Are policies checked on every request?">
    Yes. The gate and the handler evaluate them for each request. A cached response is served only after the policy gate has run, so a refused caller stays refused.
  </Accordion>
  <Accordion title="Can a policy call an external service?">
    A condition cannot. A Python policy can, with the cost described on its page.
  </Accordion>
  <Accordion title="Why does my list say `total: null`?">
    A part of the policy could not become SQL, so rows are checked one at a time after the query. See [pushdown](/policies/pushdown).
  </Accordion>
  <Accordion title="Do policies apply to the Records tab and the console?">
    No. They act with the platform's authority. Only operators can reach them.
  </Accordion>
  <Accordion title="Do events respect policies?">
    No. Events carry the raw record to every consumer. See [Resource events](/data/resource-events).
  </Accordion>
  <Accordion title="Can I use the same policy for a route and a bucket?">
    Yes, if it only reads values both contexts have. `$record` is empty for a route and `$object` exists only for storage.
  </Accordion>
  <Accordion title="How do I find which policy refused a request?">
    The message names it, and the request's trace in **Observability** records it. See [Testing and debugging](/policies/debugging).
  </Accordion>
</AccordionGroup>

## What to remember

- **A policy is data: a condition evaluated against `$auth`, `$credential`, `$record`, `$input` and `$request`.**
- **One engine, many entry points, each with its own default and its own status codes.**
- **Lists are planned into SQL where possible. Whatever is left is checked per row, and then `total` is `null`.**
- **Secret keys and operators bypass every policy.**
- **Not signed in and not allowed is `401`. A record you may not read is `404`. A refused write is `403`.**
- **Write ownership with `owner:<column>`.** A bare `eq` fails open for unowned rows.
- **Missing equals missing.** A typo in a path does not fail closed.
- **Never compare a record to a request value.** Compare to `$auth`.
- **`DELETE` skips scopes.** Do not rely on them.
- **A stored policy named like a built-in replaces it.**
- **Pin the tenant on create and update.**
- **Trust `app` claims, never `meta`.**

## Terms

| Term | Meaning |
| --- | --- |
| **Policy** | A named condition, or a Python function, that answers whether an operation may proceed |
| **Condition** | The JSON that expresses a yes-or-no rule |
| **Context** | The facts a condition can read: `auth`, `credential`, `request`, `record`, `input`, and the rest |
| **Reference** | How a policy is named where it is attached |
| **Entry point** | A place that asks the engine for a decision |
| **Plan** | The decision of a list request before rows are read |
| **Residual** | The part of a list policy checked per row |
| **Service credential** | A secret key or operator, which bypasses every policy |
| **Decision** | The yes or no, with the policy's name and a reason |
