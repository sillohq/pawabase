## When a condition is not enough

A JSON condition compares values it is given. It cannot look anything up, count, call another service, parse a date, or walk a hierarchy. When a rule needs any of that, you write it in Python and register it as a **Python policy**: an ordinary function that receives the same context a condition would read and answers true or false.

```python
from pawabase_kit.policies import policy


@policy("nonempty-title", description="A title must be sent and not empty")
async def nonempty_title(context):
    return bool((context.get("input") or {}).get("title"))
```

A registered policy is referenced **by name**, exactly like a stored policy (`"nonempty-title"` in a resource operation's **Access** section, a route's policy, or a function's `policy=`). The rest of the platform does not know or care that it is Python.

Python policies are a cost as well as a power, and the cost is concentrated in three places: they are **opaque to the planner** (lists become per-row), they are **code** (deployed with your project, not edited in Studio), and they can **fail** in ways a condition cannot. This page covers all three. Everything here was run, including the reload behavior.

## When to reach for Python

| The rule | Condition? | Python? |
| --- | --- | --- |
| Owner, role, tenant, published | Yes | Overkill |
| Compare two columns | Yes | |
| "A field was **sent**, even as `null`" | **No.** A condition cannot tell "sent as null" from "not sent" | Yes: `"price" in context["input"]` |
| "The caller manages the record's owner" (a hierarchy) | No | Yes |
| "This plan includes this feature" from another service | No | Yes |
| "The caller has made fewer than five of these today" | No | Yes, or a rate limit |
| "The address is in one of these networks" | No | Yes, with the proxy caveat |
| "The date is in the past" | **No** (`$now` cannot be compared with text) | Yes |
| A regular expression built from data | Fails at evaluation | Yes |

The "was it sent as `null`" row is worth remembering. It is the one guard that conditions cannot express and that comes up in field-level rules, and it is a good reason for a Python policy that has nothing to do with a lookup.

<Warning>
Python policies are opaque to the planner. On a **list** request a Python policy always runs **per row**, after the query: nothing is pushed into SQL, pages come back short, `total` is `null`, and a `select` that omits a column the function reads changes what it sees. Use them for single-record operations and routes, and keep list access rules in conditions. See [SQL pushdown](/policies/pushdown).
</Warning>

## Where the code lives

A project's code is a folder the API loads, one per project:

```text
code/
  acme/
    policies.py        # @policy("name") ...
    functions/         # @function("name") ...
    transformers.py    # @transformer("name") ...
    routes.py          # extension routes
```

`code` is the API's `code_path` setting, resolved where the API process runs. Getting the folder onto the API's filesystem (an image layer, a mounted volume, a checkout) is part of your deployment. See [Code](/code/overview). Policies go in `policies.py`, and a Python policy is **registered when the module is imported**: the `@policy` decorator stores the function in a registry under its name.

Because the code is part of the deployment and not of the environment, **Promote never carries a Python policy.** Deploy the same code to every environment that needs it.

## What a policy receives and returns

The function receives **one argument**, a plain dictionary: the same context a condition reads.

| Key | Content |
| --- | --- |
| `auth` | The caller: `authenticated`, `user_id`, `email`, `roles`, `permissions`, `org`, `org_role`, `aal`, `claims` |
| `credential` | The key: `role`, `is_service`, `scopes`, `key_id` |
| `request` | `method`, `path`, `ip`, `params`, `query` |
| `project`, `env` | Where it runs |
| `record` | The row, per the operation (empty for a route) |
| `input` | The submitted data, per the operation |

See [the context reference](/policies/context) for what each is at each entry point. The function may be **synchronous or `async`**, and it **returns anything**: the result is converted with Python's truthiness, so `True`, a non-empty string and a non-empty list allow, and `None`, `False`, `0` and `""` refuse. This was run: a policy that returned the string `"yes"` allowed the request.

```python
@policy("is-owner", description="The caller owns the record")
async def is_owner(context):
    record = context.get("record") or {}
    return record.get("owner_id") == context["auth"].get("user_id")
```

Return **exactly** `True` or `False`. A function that returns a value by accident (a list, a dict) allows, and one that returns nothing refuses.

## Loading and reloading

A Python policy exists only after its module has been **loaded**. Three things control that, and each was run.

**It loads once, when the project's code is first used**, and Studio's **Reload code** loads it again. The button is on the **project** page and on **Build → Functions** (the toast reads *Code reloaded*), and the equivalent call is `POST /platform/v1/projects/{ref}/code/reload`, which answers with what it loaded:

```json
{ "modules": ["pawabase_code.acme.policies"], "errors": [], "router": false }
```

| Situation | What happens |
| --- | --- |
| You **edit** the file | **Nothing**, until you reload. Requests keep using the old code. A policy that returned `True` kept allowing until the reload, then refused |
| You reload, and the module **raises** on import | `errors` lists it (`policies.py: RuntimeError: syntax mishap`), `modules` is empty, and **the previously registered policies keep working** |
| You **remove** a policy from the file and reload | The old name **stays registered** until the process restarts. A removed policy kept refusing requests |
| You attach a policy name **before** the code has loaded | The save is refused: `operations.create.policy: unknown policy 'nonempty-title'`. Reload the code first, then attach |

Three things follow. A **bad deploy does not take down the policies you already have**, which is good. A policy you meant to retire **keeps enforcing** until a restart, which is surprising: do not rely on deleting the function to remove the rule, detach it from every reference as well. And the registry is **per process**, so with several API processes each one loads and reloads its own copy: roll the code out to all of them before you depend on a change.

A reload also forgets cached environment states so the engines are rebuilt, which is why the new code takes effect on the next request.

## Referencing

A Python policy is named like any other:

```json
{
  "operations": {
    "create": { "enabled": true, "policy": "nonempty-title" },
    "list": { "enabled": true, "policy": "authenticated" }
  }
}
```

The reference is validated when you save the resource, against stored, Python and built-in names together, which is why the name must be loaded first. Details that differ from a stored policy:

| | Stored | Python |
| --- | --- | --- |
| Edited in | Studio's rule builder | Your code |
| Listed on **Build → Policies** | **Yes** | **No.** The page lists stored policies only |
| Offered in the **picker** | Yes, under **This project** | **No.** Set the name in the **JSON** tab. A name the picker does not know is shown as `name (unknown)`, which is expected for a Python policy |
| Validated | Shape, when saved | Not at all: it is code |
| Used in a **list** of references | Yes | **No.** `Python policies cannot be combined in a list; call them from Python` |
| Used for a **bucket** | Yes | **No.** Bucket policies must be JSON conditions |
| Used for a **realtime channel rule** | Yes | **No.** The realtime service has only stored and built-in policies |
| Promoted | Yes | No (it is code) |
| Wins a name clash | **Over Python** | Loses to a stored policy of the same name |

The last row is the registry's merge order: **built-in, then Python, then stored**, so a stored policy named like a Python one replaces it. Pick distinct names, and a prefix helps (`acme-same-team`).

### Combining a Python policy with others

A list cannot contain one, so to combine, call the other rule from inside it, or give the resource a Python policy that does all the work:

```python
@policy("acme-owner-or-manager")
async def owner_or_manager(context):
    auth, record = context["auth"], context.get("record") or {}
    if not auth.get("authenticated"):
        return False
    if record.get("owner_id") == auth.get("user_id"):
        return True
    return await is_manager_of(auth["user_id"], record.get("owner_id"))
```

Always check `authenticated` first, as the `owner` shorthand does. A function that compares two values without it has the same fail-open as a bare `eq`: `None == None`. See [the overview](/policies/overview#a-plain-eq-on-an-owner-column-fails-open).

## What a Python policy does at run time

These were run with a Python policy `is-weekday-owner` (the owner test above) on a resource whose `list`, `get` and `update` named it.

| Request | Answer |
| --- | --- |
| A user lists | `200`, only their own rows, and **`"total": null`** |
| A user gets someone else's row | `404`, `Not found` |
| A user updates someone else's row | `403`, `policy '<name>' refused` |
| A secret key lists | `200`, every row: the **service bypass happens before the function is called** |

On a **list**, the engine cannot see inside the function, so it plans "allowed, with a per-row check": the query runs unfiltered, the page is fetched, and the function is called **once per row of the page**. Whatever survives is returned. That is the same residual path as any non-pushable condition, with `total` reported as `null`, and it has the same hazards: short pages, empty pages, and rows that depend on which columns were selected.

On a **single record** (`get`, `create`, `update`, `delete`) the function is called once, with the full context.

### Service credentials never reach the function

A secret key or operator passes before the policy is resolved, so a Python policy is **never called** for them. That matters for testing: a policy that raises an exception answered `500` to a signed-in user and `200` to a secret key. If you test your function through the API with a secret key, it was never run.

## When the function fails

A Python policy is code, and code can raise. A condition cannot.

| Situation | What happens |
| --- | --- |
| The function **raises** | **`500`**, `Internal Server Error`, for a list and for a `get`. This was run with a function that raised `RuntimeError` |
| The function returns a **falsy** value | A refusal (`403` or `404` or `401`, as for any policy) |
| The function returns a **truthy** value, of any type | An allow |
| The function **hangs** | The request hangs. There is no timeout on a policy |
| The function calls something **slow** | Every request (and, for a list, every row) pays for it |
| The module **does not load** | The policy is not registered, and references to it fail at save time, or with a `500` at request time |

So a Python policy fails **open or closed depending on how you wrote it**, and when it fails by raising it fails as a `500`, not as a refusal. Two defensive habits:

- **Catch what you expect and return `False`.** A policy that cannot decide should refuse.
- **Let truly unexpected errors raise.** A `500` is loud, which is better than a silent allow. Do not wrap the whole function in a bare `except` that returns `True`.

```python
@policy("acme-office-network", description="Requests from the office networks")
def office_network(context):
    ip = (context.get("request") or {}).get("ip")
    if not ip:
        return False
    try:
        return any(ip_address(ip) in net for net in OFFICE_NETWORKS)
    except ValueError:
        return False        # a malformed address is a refusal, not an error
```

## Performance

A policy runs for every request that names it, and for a list, for every row on the page:

| Factor | Effect |
| --- | --- |
| Pure Python on the context | Microseconds. Fine, even per row |
| A database query per call | A query per request, or per **row** of a list. Avoid: a page of 20 means 20 queries |
| A network call | Added to every request. Cache the answer, or move the check into a flow or route |
| Per-row on a large page | `per_page` rows times the function's cost. Keep pages small |
| An `async` function | May await I/O, and still runs sequentially across rows |

Rules of thumb: do the **expensive lookup once** per request (cache it in a module-level dictionary with an expiry, keyed by the caller), keep the per-row part to a comparison, and prefer a **flag column** that a flow keeps up to date over a lookup in the policy. A policy that has to ask another service should usually be a route with its own check instead.

## Where a Python policy cannot be used

Three entry points only accept JSON conditions or stored policies:

| Entry point | What happens with a Python policy |
| --- | --- |
| **Lists of references** | Refused when you save: `Python policies cannot be combined in a list; call them from Python` |
| **Buckets** | Bucket policies must be JSON conditions. A Python name resolves at save time but cannot run in the storage layer: the code states `storage policies must be JSON conditions`. Treat it as unsupported |
| **Realtime channel rules** | The realtime service builds its engine from stored policies only, so a Python name is not available there |

If a bucket or a channel needs a rule a condition cannot express, enforce it in a route (a flow that checks, then uploads or publishes) and keep the bucket or channel closed.

## Testing

A Python policy is a function of a dictionary, so it is the easiest kind of policy to test: no API, no database, no token.

```python
import pytest

from acme_policies import is_owner  # import the function from your project's policies module


def context(user_id, owner_id):
    return {
        "auth": {"authenticated": user_id is not None, "user_id": user_id},
        "record": {"owner_id": owner_id},
        "input": None,
    }


@pytest.mark.asyncio
async def test_owner_passes():
    assert await is_owner(context("u-1", "u-1"))


@pytest.mark.asyncio
async def test_stranger_is_refused():
    assert not await is_owner(context("u-2", "u-1"))


@pytest.mark.asyncio
async def test_signed_out_is_refused_even_for_an_unowned_row():
    assert not await is_owner(context(None, None))   # None == None must not allow
```

The third test is the one that earns its keep: it is the `None == None` case that makes a hand-written ownership comparison fail open.

Test the **data your policies see** too: a record with `null` in every column the function reads, and a missing `record` for a route. Then test **through the API** once, with a publishable key and user tokens, to prove the reference, the reload and the status codes. Never with a secret key.

## Security

| Concern | Guidance |
| --- | --- |
| **Fail closed** | Refuse when a value is missing or malformed |
| **Check `authenticated` first** | A comparison of two missing values is true |
| **Do not trust `request.query` or `params`** | The caller controls them |
| **Do not trust `auth.claims.meta`** | Users edit it. Use `claims.app` |
| **Do not leak** | A policy's return value is a bool. Do not raise exceptions that include data, since a `500` body is a plain string but logs are not |
| **Do not mutate the context** | It is a shallow copy, so nested values are shared. Treat it as read-only |
| **Do not do writes** | A policy decides. It must not change anything: it may run more than once per request, and per row |
| **Keep it deterministic** | The same context should give the same answer |
| **Do not depend on the order of calls** | A list runs a policy per row, in row order, and a get runs it once |

A Python policy has **no sandbox**: it is your code, running in the API process, with the API's authority. Review it like any code that runs with that privilege, and keep third-party calls to a minimum.

## Python policies, flows and routes

When a rule needs more than a function of the context, there are better homes:

| You need | Use |
| --- | --- |
| A check that depends on data in several resources | A **route** with a flow that queries, then acts or refuses (`error.raise`) |
| A check before a particular action | The **Check policy** block in a flow, which evaluates a named policy, Python included |
| A check that must hold for a whole table | A **flag column** maintained by a flow, and a condition on it |
| A rate or count limit | A resource or route **rate limit** |

A flow's **Check policy** block can name a Python policy (it resolves like any reference), which makes it a way to test one inside Studio, with a context you assemble. See [Testing and debugging](/policies/debugging#evaluating-a-condition-with-policycheck).

## Questions that come up

<AccordionGroup>
  <Accordion title="Can a Python policy read the database?">
    The function is plain Python in the API process, so it can import your own client. The platform does not hand it a database handle. A query per call is expensive, and per row on a list it is multiplied.
  </Accordion>
  <Accordion title="Why is my Python policy not in the picker?">
    The picker lists stored policies. Set a Python policy's name in the **JSON** tab. A name Studio does not know is shown as `name (unknown)`.
  </Accordion>
  <Accordion title="Why did my edit not take effect?">
    The code is loaded once. Press **Reload code**, or restart the API. A reload re-imports the module and registers the names again.
  </Accordion>
  <Accordion title="I deleted the function and the policy still applies. Why?">
    Reloading does not unregister names that are no longer in the file. Detach the policy from every reference, and restart the API to clear the registry.
  </Accordion>
  <Accordion title="Can I use async code and await I/O?">
    Yes. The function may be `async`. It is awaited for each call.
  </Accordion>
  <Accordion title="Why does a list under a Python policy have a null total?">
    Because the engine cannot push a function into SQL, so every row is checked after the query.
  </Accordion>
  <Accordion title="Is a Python policy slower than a condition?">
    A pure comparison is not meaningfully slower. The difference is the list: a condition can become SQL, and a function cannot.
  </Accordion>
  <Accordion title="Can two environments use different Python policies?">
    Not by environment: the code is per project, and the registry is per process. A stored policy of the same name wins in the environment that defines it, which is a way to override.
  </Accordion>
</AccordionGroup>

## What to remember

- **A Python policy is a function of the context dictionary, registered with `@policy`, referenced by name.**
- **Truthy allows. Falsy refuses. Raising is a `500`.**
- **It is never called for secret keys.**
- **On a list it is per row, `total` is `null`, and `select` changes what it sees.**
- **It cannot be in a list of references, a bucket policy or a realtime rule.**
- **Edits need a reload. Removed names persist until restart. A bad reload keeps the old policies.**
- **Attach a policy only after its code has loaded.**
- **It is code: fail closed, check `authenticated` first, test it as a function.**
