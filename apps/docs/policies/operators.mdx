## The operators at a glance

A comparison is `{"<operator>": [left, right]}`. There are twelve operators, and every result in this page was produced by evaluating the condition with the real engine.

| Operator | Studio label | True when | Pushed into SQL? |
| --- | --- | --- | --- |
| `eq` | equals | The two values are equal, after normalising integers | **Yes**, when one side is a record column and the other a known value |
| `ne` | does not equal | They are not equal | No. Checked per row |
| `gt`, `gte`, `lt`, `lte` | `>`, `≥`, `<`, `≤` | The ordering holds. False if either side is `null` or the types cannot be ordered | No |
| `in` | is one of | The left value is one of the items on the right | No |
| `not_in` | is not one of | The left value is not one of them | No |
| `contains` | contains | The left list holds the right value, or the left text contains the right text | No |
| `starts_with` | starts with | The left text starts with the right | No |
| `ends_with` | ends with | The left text ends with the right | No |
| `matches` | matches regex | A regular expression **finds** a match in the left text | No |

Only the first row matters to the planner: an `eq` between a record column and a value the request already knows becomes a SQL filter. Every other operator is evaluated **per row, in Python, after the query**. That has performance and pagination consequences, covered in [SQL pushdown](/policies/pushdown), and it means the semantics below are Python's, not SQL's. In particular, `ne` against a missing value is **true** here, where SQL's `<>` against `NULL` would be unknown.

Operators are lowercase and exact. `neq`, `==`, `and` and `or` are not operators here. The names are `ne`, `eq`, `all` and `any`.

## Reading the tables

Each table shows an expression, with the left and right operands written as JSON, and what it evaluated to. `null` is JSON `null`, and **missing** means a path that does not exist, which resolves to `null` as well.

## Equality: `eq` and `ne`

`eq` is true when both values are equal **after one normalisation**: an integer is compared as its text. That exists because identities arrive as numbers from the database and as text from tokens, and a policy comparing an owner column to a user id should not depend on which side was which.

| Left | Right | `eq` | Why |
| --- | --- | --- | --- |
| `7` | `"7"` | **true** | An integer is compared as text |
| `"7"` | `7` | true | The same, the other way |
| `5` | `5` | true | |
| `5` | `5.0` | **false** | `5` becomes `"5"`, a float is left alone |
| `5.0` | `5.0` | true | |
| `0` | `"0"` | true | Integers are text |
| `0` | `""` | false | |
| `true` | `true` | true | Booleans are not normalised |
| `true` | `1` | **false** | A boolean is not the integer one |
| `false` | `0` | false | |
| `"abc"` | `"abc"` | true | Text is compared as is, case-sensitively |
| `"Open"` | `"open"` | false | |
| `[]` | `[]` | true | Lists compare by value |
| `null` | `null` | **true** | Both empty |
| `null` | `0` | false | |

Three consequences:

- **Integers and their text forms match, floats do not.** A numeric column stored as a float (`5.0`) and a literal `5` are different. If a column is a float in the database, compare against a float.
- **A boolean never equals a number.** Compare a boolean column to `true` or `false`, not to `1` or `0`. This was run: `{"eq": ["$record.flag", 1]}` against `true` is false.
- **`null` equals `null`.** This is the source of the most dangerous policy bug. `{"eq": ["$record.owner_id", "$auth.user_id"]}` is true for a signed-out caller on a row with no owner. See [the overview](/policies/overview#a-plain-eq-on-an-owner-column-fails-open).

### `ne` is the exact opposite

`ne` is `not eq`, with the same normalisation. It is true whenever `eq` is false, including when either side is missing:

| Condition | Result |
| --- | --- |
| `{"ne": ["$record.missing", "x"]}` | **true** |
| `{"ne": ["$record.status", "draft"]}` for a row whose status is `null` | **true** |
| `{"ne": ["$input.status", "published"]}` when no status is submitted | **true** |
| `{"ne": [null, null]}` | false |

So `ne` **admits rows with no value**. A policy `{"ne": ["$record.status", "archived"]}` shows every row that is not archived, including those whose status was never set. That is usually what is wanted. It matters for guards on writes: "the submitted status must not be `published`" is satisfied by **omitting** the status, which is why an editor-only publish rule works only if an omitted status cannot publish anything.

## Ordering: `gt`, `gte`, `lt`, `lte`

Ordering compares two values of the same kind. Anything the language cannot order is **false**, with no error:

| Expression | Result | Why |
| --- | --- | --- |
| `5 > 3` | true | |
| `5.5 > 5` | true | Numbers mix |
| `"b" > "a"` | true | Text compares by character, left to right |
| `"2026-01-02" > "2026-01-01"` | true | ISO dates compare correctly **as text** |
| `5 > "3"` | **false** | A number and text cannot be ordered. No error, just false |
| `"5" > 3` | false | The same |
| `null > 3` | false | A `null` on either side is false |
| `3 > null` | false | |
| `true > 0` | true | A boolean is a number to the language |

The rule is simple and strict: **mixed types and `null` are false for all four operators**. In particular, `gte` and `lte` are not "greater or equal, or maybe equal": `null >= null` is false, and `5 >= "5"` is false.

### Guards on submitted numbers

A limit on a submitted value reads naturally:

```json
{ "lte": ["$input.qty", 10] }
```

and it is **false when `qty` is not submitted**, because `null <= 10` is false. This was run: a stored policy `{"lte": ["$input.n", 10]}` refused `{}` as well as `{"n": 50}`. That is usually the right way round for a cap on a required field, and the wrong way round for an optional one, where you want "if given, at most ten":

```json
{ "any": [{ "not": { "exists": "$input.qty" } }, { "lte": ["$input.qty", 10] }] }
```

### Dates

Dates stored as ISO text (`2026-10-01T10:00:00+00:00`) order correctly as text **when both sides are text in the same format and zone**. A mixed offset breaks it: `10:00+02:00` sorts after `09:30+00:00` as text though it is earlier. Compare dates in UTC, in one format. See [Time](#time) for why `$now` cannot be one side.

## Sets: `in` and `not_in`

`in` is true when the left value is **one of** the items of the right-hand list. Both normalise integers the way `eq` does:

| Left | Right | `in` | `not_in` |
| --- | --- | --- | --- |
| `"a"` | `["a", "b"]` | true | false |
| `"a"` | `["b"]` | false | true |
| `1` | `["1"]` | true | false |
| `"1"` | `[1]` | true | false |
| `1` | `[1.0]` | **false** | true |
| `true` | `[1]` | false | true |
| `null` | `[null]` | true | false |
| `null` | `["a"]` | false | true |
| `"a"` | `[]` | false | true |
| `"a"` | `null` | false | **true** |

The right side should be a list. When it is **not**, the operator does not complain, it iterates whatever it was given:

| Left | Right | `in` | What happened |
| --- | --- | --- | --- |
| `"a"` | `"abc"` | **true** | A string is a list of its characters |
| `"o"` | `"open"` | **true** | The same |
| `"ab"` | `"abc"` | false | No single character is `ab` |
| `"a"` | `{"a": 1}` | true | A dictionary is a list of its keys |

<Warning>
`in` with a **string** on the right is a substring-by-character test, not a set test. `{"in": ["$record.status", "$auth.role"]}`, where `role` is a string, passes when the status is **any single character** of the role. Always put a list on the right. If the right side is a path, make sure it resolves to a list (`$auth.roles`, not `$auth.role`).
</Warning>

`not_in` is not quite the opposite: a **missing** right side (`null`) makes `not_in` true and `in` false, so a policy that reads `{"not_in": ["$auth.user_id", "$record.blocked_users"]}` **admits everyone** when the record has no `blocked_users` list.

### Roles, permissions and organisation roles

The common uses are literal lists on the right:

```json
{ "in": ["$auth.org_role", ["owner", "admin"]] }
{ "in": ["$record.status", ["draft", "review"]] }
```

For the caller's **roles**, use the `role` shorthand, or `contains` with the list on the left.

## Membership: `contains`

`contains` asks whether the left **holds** the right. It has two behaviors, chosen by the left value's type:

| Left is | `contains` means | Example | Result |
| --- | --- | --- | --- |
| A **list** (or tuple, set) | The right is one of its items, after integer normalisation | `["a","b"]` contains `"a"` | true |
| | | `["a","b"]` contains `"c"` | false |
| | | `["1"]` contains `1` | true |
| | | `[1, 2]` contains `"1"` | true |
| | | `[]` contains `"a"` | false |
| **Text** | The right appears as a substring, case-sensitively | `"hello"` contains `"ell"` | true |
| | | `"hello"` contains `"ELL"` | false |
| | | `"hello"` contains `""` | **true** |
| Anything else | The two are compared as text | `5` contains `5` | true |
| | | `{"a": 1}` contains `"a"` | true (a dictionary's keys) |
| `null` | Always false | `null` contains `"a"` | false |

The use that matters is the first: **checking a caller's roles or a record's tags**.

```json
{ "contains": ["$auth.roles", "admin"] }
{ "contains": ["$record.tags", "public"] }
```

The `role` shorthand is exactly the first, repeated for each role. See [Shorthands](/policies/shorthands#role). A `contains` with an **empty** right-hand text is true for any text, so a policy built from a value that can be empty (`{"contains": ["$record.title", "$request.query.q"]}`) admits everything when the parameter is blank.

## Strings: `starts_with` and `ends_with`

Both turn **both sides into text** before comparing, and both are case-sensitive:

| Expression | Result |
| --- | --- |
| `"hello"` starts with `"he"` | true |
| `"Hello"` starts with `"he"` | **false** |
| `"hello"` ends with `"llo"` | true |
| `"hello"` ends with `"LLO"` | false |
| `"hello"` starts with `""` | **true** (the empty prefix) |
| `null` starts with `"a"` | false |
| `5` starts with `5` | true (compared as `"5"`) |
| `["a"]` starts with `"["` | true (a list is turned into its text) |

Use them for **prefix layouts**, such as object keys or channel names:

```json
{ "starts_with": ["$object.key", "public/"] }
```

For a prefix that comes from the caller, `$object.segments.0` is usually clearer and cannot be fooled by a key that merely begins with the same characters (`users/7` and `users/70` both start with `users/7`).

Remember the empty case. `{"starts_with": ["$record.slug", "$request.query.prefix"]}` is **true for every record** when the prefix is empty, and a prefix taken from the request is the kind of value [a caller can rewrite](/policies/overview#a-request-value-can-rewrite-the-policy).

## Patterns: `matches`

`matches` is true when a **regular expression finds a match anywhere** in the left text. It is a search, not a full match:

| Left | Pattern | Result | Note |
| --- | --- | --- | --- |
| `"hello"` | `^h` | true | Anchored at the start |
| `"hello"` | `l+` | true | Found in the middle |
| `"hello"` | `^l` | false | |
| `"hello"` | `^hello$` | true | Both ends anchored |
| `"Hello"` | `hello` | false | Case-sensitive |
| `"Hello"` | `(?i)hello` | true | An inline flag makes it case-insensitive |
| `"a.b"` | `a\.b` | true | Escape a dot |
| `"hello"` | *(empty)* | **true** | An empty pattern matches anything |
| `5` | `^5$` | true | A number is matched as text |
| `null` | `a` | false | |
| `"hello"` | `null` | false | A missing pattern matches nothing |

The pattern is Python's regular-expression syntax. Anchor it with `^` and `$` whenever you mean "the whole value", since without them `matches` is a `contains`: `{"matches": ["$auth.email", "@acme\\.co"]}` also matches `evil@acme.co.attacker.com`. Write `@acme\\.co$`, and consider whether `ends_with` says it more plainly.

### When the pattern is checked

A **literal** pattern is compiled when you save the policy, and an invalid one is refused:

```text
condition.matches: invalid pattern: missing ), unterminated subpattern at position 0
```

A pattern read from a **path** is not checked at save time. A bad one raises an error when the policy is evaluated, and the request fails with a `500`, not a refusal. Use a literal pattern unless you control the data it comes from.

Regular expressions run per row for a list, so a slow pattern on a large page is slow for every request. Keep them simple.

## Null handling

`null` and a **missing** path are the same thing to a condition: both resolve to nothing. Every operator treats nothing in one fixed way, and getting a policy right means knowing which.

| Operator | When one side is nothing |
| --- | --- |
| `eq` | **True only if both sides are nothing** |
| `ne` | **True unless both sides are nothing** |
| `gt`, `gte`, `lt`, `lte` | **False** |
| `in` | False when the left is nothing and the list has no nothing, or when the right is nothing |
| `not_in` | **True** when the right is nothing; true when the left is nothing and the list has none |
| `contains` | **False** when the left is nothing |
| `starts_with`, `ends_with` | **False** when the left is nothing |
| `matches` | **False** when the left is nothing |
| `exists` | **False** |
| `truthy` | **False** |
| `empty` | **True** |

Group them by what they do to a policy:

- **`eq`, `ne` and `not_in` can be true on nothing.** These are the operators that **fail open**. A guard built from them needs a separate check that the value exists.
- **Ordering, `in`, `contains`, the string operators and `matches` are false on nothing.** They **fail closed**, which is usually what you want from a positive condition, and surprising from a negative one inside a `not`.
- **`not` flips whichever it wraps.** `{"not": {"gt": ["$record.n", 3]}}` is **true** when `n` is missing, because `gt` was false.

### The pairs of conditions that look equivalent and are not

| These look the same | They differ when the value is nothing |
| --- | --- |
| `{"ne": ["$record.status", "x"]}` and `{"not": {"eq": ["$record.status", "x"]}}` | They do not differ. They are the same |
| `{"lte": ["$input.n", 10]}` and `{"not": {"gt": ["$input.n", 10]}}` | The first is **false** for a missing `n`, the second **true** |
| `{"in": ["$x", ["a"]]}` and `{"not": {"not_in": ["$x", ["a"]]}}` | They do not differ |
| `{"exists": "$x"}` and `{"truthy": "$x"}` | They differ for `0`, `false` and `""`: `exists` is true, `truthy` is false |
| `{"empty": "$x"}` and `{"not": {"exists": "$x"}}` | They differ for `0`, `false`, `""` and `[]`: `empty` is true, `not exists` is false |

The second row is the one that bites. "At most ten" written as `lte` rejects a missing value, and written as `not gt` accepts it. Choose deliberately.

### Distinguishing "not submitted" from "submitted as null"

A condition cannot tell the two apart: both read as nothing. A `PATCH` that sends `{"price": null}` and one that omits `price` are identical to `$input.price`. That is how a guard like `{"not": {"exists": "$input.price"}}` is passed by an explicit `null`, as run in [the overview](/policies/overview#exists-is-false-for-null-so-not-exists-allows-nulling). The ways out (a resource's `nullable: false` is **not** one of them: a `PATCH` accepts `null` for every field, as [Validation](/data/validation) describes):

- Check in a [Python policy](/policies/python-policies), where `"price" in context["input"]` tells the two apart.
- Put the rule in a **route** that validates the change, and disable `update` on the resource.

## Time

`$now` is the current date and time as a **date object**, not as text. Everything a record or a request contributes is **text**, because it came from JSON or a database column, and the language cannot order a date against text. The result is not an error: it is **false**.

| Expression | Result |
| --- | --- |
| `$now > <a date object>` | true |
| `<ISO text> > <a date object>` | **false** |
| `$now < "2099-01-01"` | **false** |
| `"2026-10-01T10:00:00+00:00" > "2026-09-30T23:59:59+00:00"` | true (both text) |

This was run as a policy. A resource with a `datetime` field `expires_at` had the list policy `{"gt": ["$record.expires_at", "$now"]}` and one record that expires in 2099. The list answered `200` with **no rows** and `total: null`: the comparison was false for every row, including one that will not expire for decades.

So **a policy cannot say "not expired"** by comparing a field to `$now`. Options:

| Approach | How |
| --- | --- |
| **A flag you maintain** | A boolean `active` field, flipped by a [schedule](/jobs/schedules) when `expires_at` passes. The policy checks `{"eq": ["$record.active", true]}` |
| **Filter in the request** | Let the client pass `filter[expires_at]=gt.<now>` and keep the policy about who may read |
| **A Python policy** | Parse the field and compare dates in code |
| **A route** | A flow computes the cutoff and queries |

Comparing two **text** dates works, so a policy can order a record's date against a **literal** date, or against `$input` data that arrived as text, as long as the format and zone match. It cannot order against the clock.

## Operators and SQL

The planner turns **`eq`** into SQL and nothing else. An `eq` between a single record column and a known value (a literal, or a value from the caller such as `$auth.user_id`) becomes a `WHERE` filter, and every other comparison is evaluated per row.

| Condition | On a list |
| --- | --- |
| `{"eq": ["$record.owner_id", "$auth.user_id"]}` | A SQL filter: `owner_id = '7'` |
| `{"eq": ["$record.status", "published"]}` | A SQL filter |
| `{"all": [eq on owner, eq on status]}` | Two SQL filters |
| `{"in": ["$record.status", ["a", "b"]]}` | **Per row.** No SQL filter |
| `{"gt": ["$record.n", 3]}` | Per row |
| `{"ne": ["$record.status", "draft"]}` | Per row |
| `{"starts_with": ["$record.slug", "doc-"]}` | Per row |
| `{"eq": ["$record.a", "$record.b"]}` | Per row (two columns) |
| `{"eq": ["$record.address.city", "Lagos"]}` | Per row (a nested path is not pushed down) |

When a list has per-row checks, the database returns a page first and rows are removed afterwards, so the page can be short or empty, and `total` is `null`. That is cheap to fix when you control the policy: **prefer `eq` for the access rule, and express the rest as filters the client sends**. See [SQL pushdown](/policies/pushdown).

## Choosing between similar operators

| You want | Use | Not |
| --- | --- | --- |
| The caller has a role | `{"role": "admin"}` | A hand-written `in` or `contains` (equivalent, but longer) |
| The caller has one of several roles | `{"role": ["a", "b"]}` | Several `in` |
| The record is one of several statuses | `{"in": ["$record.status", ["a", "b"]]}` | Several `eq` with `any` (equivalent, but per row either way) |
| The record's tags include a value | `{"contains": ["$record.tags", "x"]}` | `matches` on JSON text |
| A prefix | `starts_with` | `matches` with `^` (same result, more cost) |
| A suffix of a domain | `ends_with` | `matches` without `$` |
| A value in a numeric range | `gte` and `lte` in an `all` | `in` over a long list |
| Presence | `exists` | `ne` against `null` (which is true for missing and for `null` alike) |
| A flag is on | `{"eq": [path, true]}` or `truthy` | `eq` against `1` |
| Ownership | `{"owner": "col"}` | A bare `eq`, which fails open |

## Pitfalls, collected

| Pitfall | Effect | Fix |
| --- | --- | --- |
| `in` with a string on the right | A character test | A list, or `$auth.roles` |
| `eq` with `5` and `5.0` | False | Match the stored type |
| `eq` boolean with `1` | False | `true` |
| Ordering a number against text | False, silently | Convert the data to one type |
| Ordering against `$now` | False | A flag you maintain |
| `ne` on a missing value | True | Add `exists` |
| `not_in` with a missing list | True | Add `exists` on the list |
| `lte` on an optional input | False when omitted | `any` with `not exists` |
| `matches` unanchored | Substring search | `^` and `$` |
| `matches` with an empty pattern | Everything | Do not build it from data |
| `starts_with` with an empty prefix | Everything | Do not build it from the request |
| `contains` with an empty text | Everything | The same |
| A pattern from a path | Fails at evaluation | A literal |
| Case differences | No match | Normalise the data |
| A typo in the operator | Rejected on save | `ne`, `all`, `any` |

## Questions that come up

<AccordionGroup>
  <Accordion title="Are string comparisons case-insensitive?">
    No. `eq`, `starts_with`, `ends_with` and `contains` are exact. `matches` with the `(?i)` flag is the only case-insensitive form.
  </Accordion>
  <Accordion title="Does `gt` work on dates?">
    On ISO text in one format and zone, yes. Against `$now`, no: the result is false.
  </Accordion>
  <Accordion title="Is `eq` between a number and its text true?">
    For integers, yes: `7` equals `"7"`. For floats, no: `5` does not equal `5.0`.
  </Accordion>
  <Accordion title="What does `matches` do with a number?">
    It matches the number as text, so `5` matches `^5$`.
  </Accordion>
  <Accordion title="How do I write 'not null'?">
    `{"exists": "$record.x"}`. Remember that `exists` is also false for an explicit `null` on a submitted body.
  </Accordion>
  <Accordion title="Can the left side be a literal?">
    Yes, either side may be a path or a literal. `{"in": ["admin", "$auth.roles"]}` happens to work, because `in` over a list is a membership test, but `contains` with the list on the left says what you mean and matches how the `role` shorthand is built. Prefer it.
  </Accordion>
  <Accordion title="Which operators are slow?">
    Anything per row on a large page. `matches` is the most expensive, then `contains` on large lists. `eq` on a column is a SQL filter and is as fast as the query.
  </Accordion>
</AccordionGroup>

## What to remember

- **Twelve operators. Only `eq` becomes SQL.**
- **`eq` normalises integers to text, not floats, and a boolean never equals a number.**
- **Mixed types and `null` are false for ordering, silently.**
- **`eq`, `ne` and `not_in` can be true on nothing. Add `exists`.**
- **`in` needs a list on the right.** A string is a character test.
- **`matches` is a search.** Anchor it. An empty pattern matches everything.
- **`$now` cannot be compared with record data.** Keep a flag.
- **A missing value and `null` are the same, and cannot be told apart from a submitted `null`.**
