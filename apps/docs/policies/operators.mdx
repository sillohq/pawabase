Comparisons have the form `{"operator": [left, right]}`. Either operand may be a path (`$record.status`) or a literal (`"published"`). This page documents each of the twelve operators precisely: what makes it true, what happens with `null`, how types are treated, and whether it can be pushed into SQL on list requests.

## Summary

| Operator | True when | With `null` | Pushed into SQL? |
| --- | --- | --- | --- |
| `eq` | left equals right | `null == null` is true | **Yes**, `$record.field` vs a known value |
| `ne` | left differs from right | `null != "x"` is true | No |
| `gt` | left > right | false if either is null | No |
| `gte` | left ≥ right | false if either is null | No |
| `lt` | left < right | false if either is null | No |
| `lte` | left ≤ right | false if either is null | No |
| `in` | left is an element of the list right | false if right is null | No |
| `not_in` | left is not an element of right | **true** if right is null | No |
| `contains` | left (a list) contains right, or left (a string) contains right | false if left is null | No |
| `starts_with` | `str(left)` starts with `str(right)` | false if left is null | No |
| `ends_with` | `str(left)` ends with `str(right)` | false if left is null | No |
| `matches` | the regex right is found in `str(left)` | false if left is null | No |

Comparing types that can't be ordered (a number with a string in `gt`) is **false**, never an error. A policy never crashes a request because a field had an unexpected type; it just doesn't match.

The `_compare` function in the engine wraps every comparison in a try/except that catches `TypeError`. This is a deliberate design choice: when a policy encounters a type mismatch (for example comparing a number to a string), it returns `false` rather than raising an exception. This means that even if your data is inconsistent — perhaps a field that should be a number contains a string — your policy doesn't crash. It simply doesn't match, which is the safe default.

## Equality: `eq` and `ne`

```json
{ "eq": ["$record.owner_id", "$auth.user_id"] }
{ "ne": ["$record.status", "void"] }
```

### Id normalisation

Integers are compared as strings in `eq` and `ne`, because ids come from databases as integers and from tokens as strings:

| Left | Right | `eq` |
| --- | --- | --- |
| `42` | `"42"` | **true** |
| `"42"` | `42` | **true** |
| `true` | `"true"` | false (booleans aren't normalised) |
| `null` | `null` | **true** |
| `null` | `"x"` | false |
| `1.5` | `"1.5"` | false (floats aren't normalised) |

<Warning>
`null == null` is **true**. Comparing `$record.owner_id` with `$auth.user_id` for an anonymous caller on a row with no owner would pass. Always combine ownership comparisons with `{"authenticated": true}`, or use the `owner` shorthand, which does that for you.
</Warning>

The id normalisation is implemented by the `_norm` function, which converts integers to strings while leaving booleans, null, and floats unchanged. This normalisation applies only to `eq` and `ne` — ordering operators (`gt`, `gte`, `lt`, `lte`) do not normalise. The reason is that normalisation is specifically designed to handle the id mismatch between database integers and token strings. For ordering, the types must be compatible (both numbers, or both ISO date strings) for a meaningful comparison.

### Pushdown

`eq` between a **single-level** record path and a value known before the query (a literal, or an `$auth`/`$credential`/`$request` path) becomes a SQL equality when it's part of an AND:

```json
{ "all": [ { "eq": ["$record.org_id", "$auth.org"] }, { "eq": ["$record.archived", false] } ] }
```

→ `WHERE org_id = 'acme' AND archived = false`. Nested paths like `$record.address.city` aren't pushed down.

The pushdown check requires the record path to be exactly one level deep (`$record.field` not `$record.nested.field`). The reason is database-specific: different databases handle JSON column queries differently, and a simple `column = value` equality is the most portable and indexable form. For nested paths, the value would need to be extracted from a JSON column, which varies by database.

The pushdown code in the engine checks this explicitly:

```python
if _mentions_record(left) and not _deferred(right) and left.count(".") == 1:
    column = left.split(".", 1)[1]
    value = resolve(right, {})
```

The `left.count(".") == 1` check ensures exactly one dot, meaning the path is `$record.field` and not `$record.nested.field` (which would have two dots) or `$auth.user_id` (which has a dot but doesn't mention `$record`).

### List equality

`eq` also works with lists, comparing them element-wise with id normalisation:

| Left | Right | `eq` |
| --- | --- | --- |
| `[1, 2]` | `[1, 2]` | true |
| `[1, 2]` | `[2, 1]` | false (order matters) |
| `["a"]` | `["a", "b"]` | false |

This means you can check if a list field exactly matches an expected value. For "does this list contain this element," use `contains` instead.

## Ordering: `gt`, `gte`, `lt`, `lte`

```json
{ "gte": ["$record.score", 50] }
{ "lte": ["$input.amount", 5000] }
{ "all": [ { "gte": ["$input.age", 13] }, { "lt": ["$input.age", 19] } ] }
```

- Both operands must be non-null; otherwise the comparison is **false**.
- Numbers compare numerically, strings lexicographically. Mixing them is false.
- ISO dates in the same format (`"2026-09-28"`) compare correctly as strings, because ISO format sorts chronologically.

### Spending limits

```json
{ "any": [
  { "role": "principal" },
  { "all": [ { "role": "bursar" }, { "lte": ["$input.amount", 500000] } ] }
] }
```

"Bursars can record payments up to ₦500,000; larger ones need the principal."

### The null problem with ordering

One of the most common pitfalls with ordering operators is the null behavior. If `$record.amount` is `null` for any row (perhaps the field is optional and wasn't set), `gte($record.amount, 50)` returns `false` for that row. The row is excluded from the results. This is semantically correct (a null amount is not ≥ 50), but it can be surprising if you expect null rows to be included.

If you want to include rows with null amounts, you need an explicit condition: `{"any": [{"gte": ["$record.amount", 50]}, {"exists": false, "$record.amount"]}` — but this doesn't work because `exists` with `false` means "the field doesn't exist," not "the field is null." Instead, use `{"ne": ["$record.amount", null]}` in an `any` to include rows where the field is set and ≥ 50, or handle it differently based on your business logic.

### ISO date comparisons

ISO 8601 date strings compare correctly as strings because the format is lexicographically ordered: `"2026-09-28"` > `"2026-09-27"` > `"2026-01-01"`. This works for:

- Dates: `"YYYY-MM-DD"`
- Datetimes: `"YYYY-MM-DDTHH:MM:SSZ"`
- With timezone offsets: `"2026-09-28T10:00:00+00:00"`

However, the comparison is **string-based**, so `"2026-09-28"` > `"2026-10-1"` because `"1"` < `"8"` in string comparison. Always use zero-padded ISO format consistently. Pawabase's `date` field type produces zero-padded ISO strings, so this works correctly for fields declared as dates.

## Sets: `in` and `not_in`

```json
{ "in": ["$record.status", ["draft", "review"]] }
{ "not_in": ["$request.ip", ["203.0.113.4", "203.0.113.5"]] }
{ "in": ["$auth.claims.app.plan", ["pro", "enterprise"]] }
```

- `right` must be a list (literal or path). Elements are compared with id normalisation, like `eq`.
- `in` with `right = null` is **false**; `not_in` with `right = null` is **true** (nothing is excluded from nothing).

The right side can itself be a path to a list on the record:

```json
{ "in": ["$auth.user_id", "$record.editor_ids"] }
```

That's equivalent to `contains` with the operands swapped. This pattern is useful when the set of allowed values lives on the record rather than as a fixed literal. The pushdown mechanism doesn't apply here because the right side is a `$record` path, which is deferred.

### `in` with a `$record` path

When the right side of `in` is a `$record` path (a list stored on the record), the comparison can't be pushed down because the list is unknown at plan time. Each row's list must be checked individually. This is fine for small lists, but can be slow on large tables with large list fields.

If you find yourself using `in` with a `$record` path frequently, consider denormalising the data. For example, if you often check `{"in": ["$auth.user_id", "$record.editor_ids"]}`, consider maintaining a `viewer_user_ids` list or using a separate membership resource.

### `not_in` semantics

`not_in` with a `null` list returns `true`. This means `{"not_in": ["$record.status", null]}` is `true` when the list is missing, which could accidentally allow access. If the list might be null, add an existence check:

```json
{ "all": [ { "exists": "$record.blocked_ids" }, { "not_in": ["$request.ip", "$record.blocked_ids"] } ] }
```

This ensures the blocked list exists before checking membership. The `exists` check guarantees that `blocked_ids` is not null, and only then does the `not_in` comparison execute.

## Membership: `contains`

`contains` has two meanings, chosen by the type of the **left** operand:

| Left is | True when | Example |
| --- | --- | --- |
| a list | the list has an element equal to right (normalised) | `{"contains": ["$auth.roles", "admin"]}` |
| anything else | `str(right)` is a substring of `str(left)` | `{"contains": ["$record.title", "urgent"]}` |

This is the workhorse for **user-id lists** and **roles**:

```json
{ "contains": ["$record.guardian_user_ids", "$auth.user_id"] }
{ "contains": ["$auth.roles", "$record.audience"] }
{ "contains": ["$credential.scopes", "reports:export"] }
```

The second example is particularly useful: an announcement whose `audience` is `"guardian"` is visible to callers whose roles include `guardian`. This creates a bidirectional relationship between the record's audience field and the caller's roles.

### List vs string containment

The behavior depends entirely on the left operand's type at runtime:

- If `$record.tags` is stored as a list `["bug", "feature"]`, `{"contains": ["$record.tags", "bug"]}` checks list membership.
- If `$record.tags` is stored as a string `"bug,feature"`, the same condition checks substring containment: is `"bug"` a substring of `"bug,feature"`? Yes.

This type-dependent behavior is a source of bugs. Declare list fields with the `array` type in your resource definition so they always arrive as lists. If you're unsure whether a field is a list or a string, use `exists` to check first, or use `contains` with a string literal on both sides.

The `contains` implementation checks the type explicitly: if the left operand is a list, tuple, or set, it checks membership. Otherwise, it converts both operands to strings and checks for substring containment.

### `contains` with null

`contains` returns `false` when the left operand is `null`. It does not raise. This means that if a record has a null value for a field you're checking with `contains`, the condition simply fails — the row is not visible. This is the safe default.

For `contains` where the left is a list and the right is `null`, the behavior is: `{"contains": [[], null]}` is `false` (an empty list doesn't contain null). `{"contains": [[null], null]}` is `true` (the list `[null]` contains `null`). This follows from the id-normalised membership check.

## Strings: `starts_with`, `ends_with`, `matches`

```json
{ "starts_with": ["$object.key", "public/"] }
{ "ends_with": ["$auth.email", "@brightfield.example"] }
{ "matches": ["$record.code", "^[A-Z]{3}\\d{3}$"] }
```

- Operands are converted to strings; a `null` left operand is **false**.
- `matches` uses Python regular expressions with **search** semantics: the pattern may match anywhere unless you anchor it with `^` and `$`.
- Escape backslashes in JSON: `\\d`, `\\.`.

<Tip>
Email-domain rules are tempting but weak: anyone who controls an address at that domain passes, including departed staff whose accounts weren't closed. Prefer roles for authorization, and use domains only to decide default roles at sign-up.
</Tip>

### `starts_with` and `ends_with` on numbers

When the left operand is a number, `starts_with` and `ends_with` convert it to a string first:

| left | right | result |
| --- | --- | --- |
| `42` | `"4"` | starts_with: true |
| `42` | `"2"` | ends_with: true |
| `42` | `"5"` | starts_with: false |

This is occasionally useful (for example, checking that a numeric code starts with a specific digit), but it's usually clearer to use `eq` with a numeric literal.

### `matches` with Python regex

The `matches` operator uses Python's `re.search`, which means the pattern is searched anywhere in the string. To match the entire string, anchor with `^` and `$`:

```json
{ "matches": ["$auth.email", "^[a-z]+@school\\.example\\.com$"] }
```

Without anchors, `@school.example` matches `evil@school.example.attacker.com`. Always anchor regex patterns unless you intentionally want a partial match.

Python regex features like lookaheads, backreferences, and named groups are all available because `re.search` supports the full Python regex dialect. However, complex regex patterns can be slow, so keep them simple. A regex like `^[A-Z]{3}\\d{3}$` is fast; a pattern with nested quantifiers on long strings could cause catastrophic backtracking.

### Inline regex flags

You can add inline flags with `(?i)` for case-insensitive matching:

```json
{ "matches": ["$auth.email", "(?i)^ada@example\\.com$"] }
```

This is useful when you need case-insensitive matching but don't want to normalize the data. However, the recommended approach is to normalize data at storage time (store emails lowercase) and use `eq` — it's faster and more predictable.

## Null handling

Missing paths resolve to `null`. Here is every operator's behaviour when one side is null:

| Operator | `left = null` | `right = null` |
| --- | --- | --- |
| `eq` | true only if right is null | true only if left is null |
| `ne` | false only if right is null | false only if left is null |
| `gt` `gte` `lt` `lte` | false | false |
| `in` | true if the list contains null | false |
| `not_in` | false if the list contains null | true |
| `contains` | false | list: true if it contains null; string: false |
| `starts_with` `ends_with` `matches` | false | compares with the string `"None"`, avoid |

To test for null explicitly, use the checks: `{"exists": "$record.returned_on"}` or `{"not": {"exists": "$record.returned_on"}}`.

### The `null` edge case in `eq`

The most dangerous null behavior is `eq(null, null) → true`. This means that if both `$record.owner_id` and `$auth.user_id` are null, the equality passes. An anonymous caller on a row with no owner would be treated as the owner. This is why the `owner` shorthand always includes `{"authenticated": true}` in its expansion, and why you should always combine ownership checks with an authentication requirement.

The `ne` operator has the opposite edge case: `ne(null, null)` is `false`. So `{"ne": ["$record.owner_id", "$auth.user_id"]}` is `false` when both are null, which means it doesn't pass — this is actually safe for exclusion checks.

### Null in `in` and `not_in`

When the right side of `in` is a list that contains `null`:

```json
{"in": [null, [null, "a"]]}  // true
{"not_in": [null, [null, "a"]]}  // false
```

`in` returns `true` if the list contains `null` and the left operand is `null`. `not_in` returns `false` in the same case. This means that a null left operand is treated as "is null in the list." If you want to exclude null values from consideration, add an explicit `{"exists": "$field"}` check.

When the right side is `null` (not a list containing null, but the value `null` itself):

```json
{"in": ["$record.status", null]}  // false
{"not_in": ["$record.status", null]}  // true
```

This is consistent: `in` with a null list is always `false` (nothing is an element of nothing), and `not_in` with a null list is always `true` (nothing is excluded from nothing).

## Time

`$now` is the current time as a timezone-aware UTC datetime. Stored datetimes arrive in records as ISO strings. Comparing a datetime with a string is false, so `{"lt": ["$record.publish_at", "$now"]}` does **not** work as you might hope.

Reliable patterns:

1. **Maintain a boolean.** A scheduled flow sets `published = true` when `publish_at` passes. The policy checks `{"eq": ["$record.published", true]}`, which also pushes down into SQL.
2. **Compare ISO strings of the same format.** If both sides are ISO dates you control (for example `$record.due_on` and a date passed in `$input`), string ordering matches chronological ordering.
3. **Decide in a flow.** For complex windows, guard a custom route with a simple policy and let the flow compare with `time.now` before acting.

The reason this matters is that `_compare` for ordering operators uses Python's native comparison operators. Comparing a `datetime` object with a string raises `TypeError`, which `_compare` catches and returns `false`. The result is that every time-based ordering comparison returns `false`, silently denying access. This is the most common time-related pitfall in policy writing.

For `eq` comparisons with datetimes, the same issue applies: `eq(datetime_obj, "2026-09-28")` returns `false` because they're different types. The solution is always to maintain a boolean flag or store dates as strings consistently.

## Choosing operators for performance

On `get`, `create`, `update` and `delete`, all operators cost about the same: one record, one evaluation. On `list`, only AND-ed `eq` conditions on record fields become SQL. Everything else is evaluated on each row the query returns, and `total` becomes `null`. For big lists:

| Rule | Instead of | Prefer |
| --- | --- | --- |
| Family members can read | `contains($record.guardian_user_ids, $auth.user_id)` | `eq($record.family_id, $auth.claims.app.family_id)` |
| Visible statuses | `in($record.status, [...])` for guests | a boolean `visible` maintained by the platform |
| Recent rows only | `gte($record.created_at, …)` | a client filter `filter[created_at]=gte.…` (it's SQL) plus a simple policy |

The key insight is that on lists, only `eq` can become SQL, and only when comparing a single-level record field against a known value. Everything else — `contains`, `in`, `gt`, `any` — is evaluated per row. This doesn't mean those operators are bad; it means they're appropriate for different scenarios. For small tables (thousands of rows), per-row evaluation is perfectly fine. For large tables (millions of rows), restructure so the heavy lifting is done by an AND-ed equality.

The `total: null` signal is your indicator that a residual remains. When you see it, you know the query is being filtered client-side, and you should consider whether the policy could be restructured for pushdown.

### Checks

| Check | Value | Result |
| --- | --- | --- |
| `exists` | `"ada@example.com"` | true |
| `exists` | `null` | false |
| `exists` | `false` | true |
| `exists` | `0` | true |
| `truthy` | `true` | true |
| `truthy` | `0` | false |
| `truthy` | `""` | false |
| `truthy` | `["a"]` | true |
| `empty` | `[]` | true |
| `empty` | `null` | true |
| `empty` | `"x"` | false |
| `empty` | `0` | true |

Note the difference between `exists` and `truthy`: `false` and `0` **exist**, but aren't **truthy**. Use `exists` to ask "was this field sent?" and `truthy` to ask "is this switched on?".

## In Studio's rule builder

Studio's policy editor offers every operator under **Compare values…**, with plain-English labels. The JSON tab shows the operator it maps to.

| Rule builder label | Operator | Right-hand input |
| --- | --- | --- |
| equals | `eq` | a value or `$path` |
| does not equal | `ne` | a value or `$path` |
| `>` · `≥` · `<` · `≤` | `gt` · `gte` · `lt` · `lte` | a number, ISO date or `$path` |
| is one of | `in` | comma-separated values (`a, b, c`) |
| is not one of | `not_in` | comma-separated values |
| contains | `contains` | a value or `$path` |
| starts with · ends with | `starts_with` · `ends_with` | text |
| matches regex | `matches` | a regular expression |

Values typed into the builder are interpreted like JSON literals: `42` becomes a number, `true`/`false` booleans, `null` null, and anything starting with `$` a path. Everything else is a string. The left-hand box offers autocomplete for common paths (`$auth.user_id`, `$auth.roles`, `$record.owner_id`, `$input.`, `$request.ip`, `$credential.scopes`, `$event.name`, `$now`).

**Check a value…** covers the three checks: *exists*, *is set / true* (`truthy`) and *is empty*.

## Choosing between similar operators

<AccordionGroup>
  <Accordion title="eq vs in">
    Use `eq` for a single value, especially on record fields in list rules, because it's the only operator that becomes SQL. Use `in` for small fixed sets (statuses, plans).
  </Accordion>
  <Accordion title="contains vs in">
    Put the list on the side that holds it: `contains` when the **left** operand is the list (`$auth.roles`, `$record.editor_ids`), `in` when the **right** is. They're otherwise equivalent.
  </Accordion>
  <Accordion title="exists vs truthy vs ne null">
    `exists` answers *was a value given?*; `truthy` answers *is it on?*; `{"ne": [x, null]}` is the same as `exists` but less readable. Prefer the checks.
  </Accordion>
  <Accordion title="starts_with vs matches">
    Use `starts_with`/`ends_with` whenever they're enough: they're clearer and can't be mis-anchored. Reach for `matches` only for real patterns.
  </Accordion>
  <Accordion title="role shorthand vs contains on $auth.roles">
    `{"role": "admin"}` and `{"contains": ["$auth.roles", "admin"]}` are equivalent. Use the shorthand for fixed roles, and `contains` when the role comes from the record (`$record.audience`).
  </Accordion>
  <Accordion title="in with path on right">
    `{"in": ["$auth.user_id", "$record.editor_ids"]}` is equivalent to `{"contains": ["$record.editor_ids", "$auth.user_id"]}`. Choose based on readability: `in` reads as "is the user in the editors list," `contains` reads as "does the editors list contain the user."
  </Accordion>
  <Accordion title="gt vs gte on boundaries">
    `{"gt": ["$record.score", 50]}` excludes 50; `{"gte": ["$record.score", 50]}` includes it. Be explicit about whether the boundary is inclusive or exclusive.
  </Accordion>
</AccordionGroup>

## Pitfalls

<AccordionGroup>
  <Accordion title="Using gt on dates stored as datetimes">
    Records carry datetimes as ISO strings; `$now` is a datetime object. Mixing them makes every ordering comparison false, which silently denies. Use a maintained boolean or compare strings of the same format.
  </Accordion>
  <Accordion title="Forgetting that contains checks substrings on strings">
    `{"contains": ["$record.tags", "art"]}` is true for the **string** `"smart"` if `tags` was stored as a string rather than a list. Declare list fields as `array` so they arrive as lists.
  </Accordion>
  <Accordion title="Unanchored regular expressions">
    `{"matches": ["$auth.email", "@school.example"]}` also matches `evil@school.example.attacker.com`. Anchor with `$`: `"@school\\.example$"`.
  </Accordion>
  <Accordion title="Comparing roles with eq">
    `$auth.roles` is a **list**. `{"eq": ["$auth.roles", "admin"]}` is always false. Use `{"role": "admin"}` or `contains`.
  </Accordion>
  <Accordion title="Expecting not_in to deny when the list is missing">
    `not_in` with a `null` list is **true**. If the list might be missing, add `{"exists": "$record.blocked_ids"}` to the condition.
  </Accordion>
  <Accordion title="Case-sensitive comparisons">
    `eq` is case-sensitive. `"Published"` ≠ `"published"`. Normalize data at storage time or use `matches` with `(?i)`.
  </Accordion>
  <Accordion title="Floating point comparisons">
    `eq` does not normalize floats. `1.5` ≠ `"1.5"`. If you need to compare floats across type boundaries, use `matches` with a regex or normalize at storage time.
  </Accordion>
  <Accordion title="String vs number in ordering">
    `gt` between a number and a string is always `false`, not an error. Make sure both sides are the same type before using ordering operators.
  </Accordion>
</AccordionGroup>

## Performance notes

Each operator has a specific performance characteristic that matters when evaluating thousands or millions of conditions:

**`eq` and `ne`** are the fastest comparisons: a single equality check, O(1). They're also the only operators that can be pushed into SQL on lists, which means they avoid per-row evaluation entirely. This is why AND-ed equalities are the gold standard for list policies.

**`contains`** on lists requires scanning the list, which is O(n) where n is the list length. For short lists (a few roles, a handful of IDs), this is negligible. For long lists (hundreds of IDs), it adds up. If a list field grows large, consider indexing or denormalizing.

**`matches`** requires regex compilation and matching, which is the most expensive operator. Python's `re.search` uses backtracking, which can be slow on complex patterns or long strings. Avoid `matches` in high-throughput list policies. If you need pattern matching on lists, consider maintaining a boolean flag that's set by a flow when a pattern match is detected.

**`in` and `not_in`** require building a set from the right operand and doing membership checks, which is O(m) where m is the right operand length. For small literal lists, this is fast. For path-to-list comparisons, it requires resolving the path first, which adds overhead.

**`starts_with` and `ends_with`** are simple string operations, O(k) where k is the prefix/suffix length. They're fast and predictable.

**Ordering operators** (`gt`, `gte`, `lt`, `lte`) require type checking and comparison. They're fast for compatible types but return `false` immediately for incompatible types.

On list requests, all non-`eq` operators contribute to the per-row residual check. The residual is evaluated for every row the query returns, so if the query returns 10,000 rows and the residual involves three `contains` checks, that's 30,000 containment checks. This is fine for moderate row counts but can become a bottleneck for large tables. The `total: null` response field is your signal that a residual exists, and you should investigate whether the policy could be restructured for pushdown.

## FAQ

<AccordionGroup>
  <Accordion title="Is there a case-insensitive equals?">
    Not as an operator. Normalise the data (store emails lower-case) or use `matches` with an inline flag: `"(?i)^ada@example\\.com$"`.
  </Accordion>
  <Accordion title="Can I compare two record fields?">
    Yes: `{"lte": ["$record.amount_paid", "$record.amount"]}`. It can't be pushed into SQL, so on lists it's checked per row.
  </Accordion>
  <Accordion title="Can operators do arithmetic?">
    No. The language compares values; it doesn't compute them. Compute in a flow (`math.calculate`) or store the derived value on the record.
  </Accordion>
  <Accordion title="What's the difference between in and contains?">
    `in` asks "is left one of the values in right?" and `contains` asks "does left (a list) include right?" They're mirror images: `{"in": ["$auth.user_id", "$record.editors"]}` equals `{"contains": ["$record.editors", "$auth.user_id"]}`.
  </Accordion>
  <Accordion title="Does `eq` on lists use set semantics?">
    No. `eq` on lists compares element-by-element in order. `[1, 2]` ≠ `[2, 1]`. Use `contains` for set membership checks.
  </Accordion>
  <Accordion title="Can I use `matches` for exact string matching?">
    Yes, anchor the pattern: `{"matches": ["$record.code", "^ABCD$"]}`. But `eq` is faster and more readable for exact matches.
  </Accordion>
  <Accordion title="Why does `contains` with a string check substrings?">
    The operator is type-aware. If the left operand is a list, it checks membership. If it's a string, it checks substring containment. This dual behavior is intentional: the same `contains` operator handles both "is this role in the list?" and "does this title contain the word?" Use the builder to see which mode applies.
  </Accordion>
</AccordionGroup>

## Operators in the five business scenarios

Each of the recurring authorization shapes leans on a small, predictable set of operators. Seeing them side by side clarifies which operator is the right default for which kind of fact.

<AccordionGroup>
  <Accordion title="Multi-tenant isolation → eq">
    `{"eq": ["$record.org_id", "$auth.org"]}` is the entire mechanism. It's the only operator in the twelve that becomes a SQL filter, which is exactly why tenant isolation should be modeled as a single equality against a token-carried slug rather than, say, `in` against a list of allowed org ids — even if a caller could theoretically belong to several orgs, resolve *which one* at token-issue time (the active org) rather than pushing multi-org membership into the condition itself. See [organizations](/auth/organizations) for how the active org is chosen.
  </Accordion>
  <Accordion title="Role-gated admin actions → contains (via the role shorthand)">
    `{"role": "finance_admin"}` expands to `{"contains": ["$auth.roles", "finance_admin"]}`. There's rarely a reason to write the `contains` form directly for roles — the shorthand is clearer and identical in cost — but recognizing the expansion matters when you're debugging with `evaluate()` directly, since the trace you'll see mentions `contains`, not `role`.
  </Accordion>
  <Accordion title="Owner-only access → eq, guarded by authenticated">
    The `owner` shorthand is `eq` plus an explicit `authenticated` guard. If you ever write the equality by hand instead of using the shorthand — for instance, comparing two different id-shaped fields that aren't a literal owner relationship, like `{"eq": ["$record.assigned_to", "$auth.user_id"]}` — remember to add `{"authenticated": true}` yourself. Nothing does it for you outside the shorthand.
  </Accordion>
  <Accordion title="Org-membership visibility → eq or contains, depending on cardinality">
    Single membership (a user belongs to exactly one department at a time) is `eq` against a token claim, and pushes down. Multiple simultaneous memberships push you to `contains` or `in` against a list, which does not push down and becomes a residual — a direct example of the "OR can't be pushed down" caution in [pushdown](/policies/pushdown#rewriting-common-slow-policies) applying just as much to "is a member of any of these groups" as it does to a literal `any` of conditions.
  </Accordion>
  <Accordion title="Time-boxed AAL access → eq on aal, never ordering on time">
    `{"aal": "aal2"}` is an `eq` shorthand under the hood (`{"eq": ["$auth.aal", "aal2"]}`), which is why it plans cleanly. The temptation to also bound *how recently* using `gte`/`lte` against `$now` runs straight into the [time](#time) section below: there's no reliable ordering comparison available for it inside the condition language, which is exactly why that scenario needs a Python policy or a shortened token lifetime instead.
  </Accordion>
</AccordionGroup>

## Operator combinations that look equivalent but aren't

A handful of pairs of expressions produce the same result in most everyday cases, which is precisely what makes their edge-case divergence dangerous — the difference only shows up on data you didn't think to test.

<AccordionGroup>
  <Accordion title="{eq: [$record.status, null]} vs {not: {exists: $record.status}}">
    These agree whenever `status` is either present-and-non-null or genuinely absent. They diverge if the column exists but a *different* field resolution quirk is in play — for instance if `status` is present but is the literal string `"null"` (a common data-entry mistake from a CSV import): `eq(..., null)` is `false` (a string is never equal to the JSON `null`), while `exists` is `true` (a string is not `None`), so `{"not": {"exists": ...}}` is also `false`. They happen to agree here, but for a field that's an **empty string** `""`: `eq(..., null)` is `false`, `exists` is `true` (empty string is not `None`), `not(exists)` is `false` — still agreeing. Where they genuinely diverge is a field whose value is the boolean `false` or the number `0`: `eq(false, null)` is `false`, and `exists(false)` is `true` (per the [truth table](#checks)), so both forms agree there too. In practice `eq(x, null)` and `not(exists(x))` are equivalent for every value the condition language can produce from `lookup()`, because a missing path and a `None` value are the same `_MISSING`-collapsed result — but prefer `{"not": {"exists": ...}}` anyway, because it reads as intent ("is this absent?") rather than as a coincidental equality.
  </Accordion>
  <Accordion title="{in: [$auth.user_id, $record.editor_ids]} vs {contains: [$record.editor_ids, $auth.user_id]}">
    Functionally identical for a well-formed list column, and the [operators reference](#choosing-between-similar-operators) already covers the readability trade-off. The divergence appears when `editor_ids` is stored as a **string** rather than an `array`-typed field: `contains` on a non-list left operand silently switches to substring matching (`"7"` is a substring of `"71"`, a false positive), while `in` requires its **right** operand to genuinely be iterable — a plain string is iterable character-by-character in Python, so `in("7", "71")` would actually check whether the single character `"7"` normalises to match one of `"7"` or `"1"` after `_norm` is applied to each character, which is almost certainly not what you meant and will behave unpredictably rather than cleanly failing. Neither form protects you from a wrongly-typed column; declaring the field as `array` is the only real fix.
  </Accordion>
  <Accordion title="{ne: [$record.owner_id, $auth.user_id]} vs {not: {eq: [$record.owner_id, $auth.user_id]}}">
    These are true logical negations of each other for every input, including nulls — `ne(null, null)` is `false` (matching `not(eq(null, null) == true)`), and `ne(null, "x")` is `true` (matching `not(eq(null, "x") == false)`). There is no divergence here; this pair is listed specifically because people sometimes *assume* a divergence exists (reasoning "ne must have different null handling from not-eq") and it doesn't. Prefer `ne` for a plain negated equality — it's one condition object instead of two nested ones.
  </Accordion>
</AccordionGroup>

## Reading an operator's cost into policy design

Beyond the pushdown/residual distinction already covered, it's worth internalizing roughly how "far" each operator is from becoming free at scale, so a policy review can spot expensive choices before they ship:

```text
free at any scale        eq / ne on a single-level $record field, AND-ed at the top level
cheap per row             starts_with / ends_with, gt / gte / lt / lte, small contains / in
moderate per row          contains / in against a $record-side list of nontrivial length
avoid on large tables      matches (regex) as part of a per-row residual
never pushed, ever         any Python policy, any nested-path comparison, any top-level any/not
```

This isn't a hard rule to enforce in Studio — nothing stops you from writing a `matches` inside a list policy's residual — but it's the mental model that should guide a second look whenever a list endpoint feels slower than the table size would suggest. Pair it with the `total: null` signal from [pushdown](/policies/pushdown#residuals-what-they-mean-for-you): if you see it on a resource you expected to plan cleanly, this ladder tells you which operator in the condition is the likely culprit.

## Operator implementation details

For teams who want to understand exactly how each operator works under the hood, this section traces through the engine's `_compare` function. Every comparison goes through the same code path in `pawabase_kit/policies/engine.py`:

```python
def _compare(op: str, left: Any, right: Any) -> bool:
    try:
        if op == "eq":
            return _norm(left) == _norm(right)
        if op == "ne":
            return _norm(left) != _norm(right)
        if op == "gt":
            return left is not None and right is not None and left > right
        ...
    except TypeError:
        return False
    raise PolicyError(f"unknown operator {op!r}")
```

The `try/except TypeError` wrapper is the safety net. If any comparison raises a `TypeError` — for example, comparing a list with a string using `>`, or comparing a datetime with a string — the function catches it and returns `false`. This means that type mismatches never propagate to the caller as exceptions. A policy never crashes a request because a field had an unexpected type; it just doesn't match.

The `_norm` function is specific to `eq` and `ne`. For all other operators, values are compared as-is. This means that `gt(42, "42")` is `false` (number vs string), while `eq(42, "42")` is `true` (ids normalised). The asymmetry is deliberate: normalisation is a convenience for id comparison, not a general type coercion mechanism.

For `matches`, the implementation uses `re.search(str(right), str(left))`. This means the pattern (`right`) is compiled as a regex and searched within the stringified left operand. The `re.search` semantics mean the pattern can match anywhere, so unanchored patterns match substrings. The `PolicyError` for invalid regex patterns is raised during validation (`validate_condition`), not during evaluation, so invalid patterns are caught at save time.

The `contains` operator has the most complex implementation because it's type-aware:

```python
if op == "contains":
    return (
        left is not None and _norm(right) in [_norm(v) for v in left]
        if isinstance(left, (list, tuple, set))
        else (left is not None and str(right) in str(left))
    )
```

For list-like left operands, it converts both sides through `_norm` and checks membership. For other left operands, it converts both to strings and checks for substring containment. This dual behavior is the source of the most common `contains` bugs — declaring a list field without the `array` type causes it to arrive as a string, which silently switches the semantics.

The `starts_with` and `ends_with` implementations are straightforward string method calls on the stringified left operand, with a null guard that returns `false`. These are O(k) operations where k is the prefix/suffix length, making them very fast even on large strings.

The `in` and `not_in` implementations convert the right operand to a list of normalized values and check membership. `not_in` with a `null` right operand returns `true` — this is because `not_in` asks "is the left operand not in the right list?" and when the right list is null, there's nothing to be in, so the answer is true. This semantic is consistent with SQL's `NOT IN` behavior with NULL.
