## One engine, many doors

Pawabase has one policy engine and several **entry points** that ask it for a decision. Each entry point builds a context from what it knows, asks the engine, and turns a refusal into its own kind of failure. Knowing the entry points is knowing where your rules apply, and, as important, where they do not.

| Entry point | Asks about | Refusal looks like |
| --- | --- | --- |
| [Resource operations](#resource-operations) | `list`, `get`, `create`, `update`, `delete` on a table | `401`, `403`, or `404` |
| [Custom routes](#custom-routes) | A flow or function behind `/rest/v1/<path>` | `401` or `403` |
| [Functions](#functions-and-flows-called-directly) | `/functions/v1/<name>` | `401` or `403` |
| [Flows](#functions-and-flows-called-directly) | `/flows/v1/<name>` | `401` or `403` |
| [Storage](#storage-buckets) | An object, a listing, a signed URL | `404`, or `403` |
| [Realtime](#realtime-channels) | A subscribe, a publish, presence | The operation is refused |
| [Event subscriptions](#event-subscriptions) | Whether a subscription fires | It does not fire |
| [Inside flows](#inside-flows) | The **Check policy** block | The `denied` edge |

In Studio you attach a policy on the resource's **Access** section, the route's **Access** section, a bucket's **Read policy** and **Write policy**, **Settings → Realtime**, a subscription's **Only when…**, and a flow's HTTP trigger configuration. See [Policies](/policies/overview#where-policies-apply).

## The layers of a request

A policy is one layer in a stack. For a request to `/rest/v1/...`, the checks run in this order, and a refusal at any layer ends the request:

| Layer | Where | Refusal |
| --- | --- | --- |
| **API key** | The gateway: is the key valid, in its allowed IP ranges, and allowed for this route? | `401` or `403` before the API sees it |
| **Rate limit** | The resource or route, per caller | `429` |
| **Body validation** | `create`, `update` and routes with an input model | `422` |
| **Key scope** | `resource:read`, `resource:write`, `routes:invoke`, `functions:invoke` | `403`, `This API key lacks the '...' scope` |
| **Policy: the plan** | The part that does not need a record | `401` or `403` |
| **Policy: the full check** | With the record and the input | `403` or `404` |
| **The data layer** | Constraints, uniqueness | `500` or `4xx` |

The two orderings that matter for security: **validation runs before the policy**, so the field names of a protected endpoint are visible to anyone who can reach it; and **`DELETE` skips the scope check**, so a key with no write scope can still delete what the policy allows. Both are covered below.

The gateway layer is separate from policies and deserves a mention: a key's **Allowed IP ranges** (*Optional comma-separated IPs or CIDRs. The gateway rejects every other client.*) and **Allowed routes** (*Optional comma-separated gateway rules: GET /rest/v1/\* or POST /functions/v1/\**) restrict a key **before** any policy runs. A public read-only key set to `GET /rest/v1/*` cannot be used to `DELETE`.

## Resource operations

Every enabled operation of a resource has a policy, set in the resource's **Access** section: *Which endpoints exist, and who may call each.* Each row has a switch, the method (`GET`, `GET`, `POST`, `PATCH`, `DELETE`), the operation name, and a policy picker. A row switched off reads *Off: the endpoint is not served.*

| Operation | Method and path | Context | Evaluated |
| --- | --- | --- | --- |
| `list` | `GET /rest/v1/<name>` | `auth`, `credential`, `request`; `record` per row | Planned, then per-row for a residual |
| `get` | `GET /rest/v1/<name>/<id>` | the same, with the row | The plan, then the loaded row |
| `create` | `POST /rest/v1/<name>` | `record` and `input` both the new data | Once, after validation |
| `update` | `PATCH` or `PUT /rest/v1/<name>/<id>` | `record` the existing row, `input` the patch | Once, after loading the row |
| `delete` | `DELETE /rest/v1/<name>/<id>` | `record` the existing row | Once, after loading the row |

An operation that is **not enabled** has no endpoint. A request to it is answered by the router, not by a policy, so there is nothing to misconfigure: a disabled `DELETE` on a path that still serves `GET` answered **`405`, `Method Not Allowed`**, and a path that serves nothing answers `404`.

### What each refusal looks like

These were run on a resource whose `list`, `get`, `update` and `delete` use `owner:owner_id` and whose `create` is `authenticated`:

| Operation | Signed out | Signed in, not allowed | Record missing |
| --- | --- | --- | --- |
| `list` | `401`, `Authentication required` | `403`, `policy '<name>' refused` (when the plan refuses outright) | n/a |
| `get` | `401` | **`404`**, `Not found` | `404`, `Not found` |
| `create` | `401` | `403`, `policy '<name>' refused` | n/a |
| `update` | `401` | `403`, `policy '<name>' refused` | `404`, `Not found` |
| `delete` | **`404`**, `policy '<name>' refused` | `403`, `policy '<name>' refused` | `404`, `Not found` |

Why each cell is what it is:

- **`401` for a signed-out caller** comes from the plan: a policy that no signed-out caller can satisfy refuses at the gate, and a refusal of someone who is not signed in is always `401`.
- **`get` is a `404` for a stranger** so that a refused record and a missing record look the same.
- **`update` and `delete` are `403` for a signed-in stranger**, because the record was loaded before the check. That distinguishes "exists but not yours" from "missing". If existence is sensitive, a policy cannot hide it here.
- **`delete` for a signed-out caller is a `404` with a refusal message.** The gate that turns signed-out callers away early is not applied to `DELETE`, so the request reaches the handler, which refuses it. The record is not deleted.

### The `DELETE` gap

The gate that applies to every other operation does two things before the handler: it checks the **key's scope**, and it turns a signed-out caller away when the plan refuses. `DELETE` does not go through it. The policy is still checked in the handler, but:

| Key and request | `POST`, `PATCH` | `DELETE` |
| --- | --- | --- |
| A key with only `resource:read` | `403`, lacks `resource:write` | **`204`. The record was deleted** |
| A key with no relevant scope | `403` | `404` if the record is already gone, otherwise it runs |
| A signed-out caller where the policy refuses | `401` | `404` with the refusal message |

A scope-limited public key, the kind meant for reading, **can delete anything the `delete` policy allows**. Close it with the policy (do not enable `delete` for a public resource, or require a user), and with the key's **Allowed routes** (`GET /rest/v1/*`). See [the overview](/policies/overview#delete-skips-the-key-scope-check-and-the-sign-in-gate).

### Scopes on resources

| Operation | Needs the scope |
| --- | --- |
| `list`, `get` | `resource:read` |
| `create`, `update` | `resource:write` |
| `delete` | none (the gap above) |

A key with **no scopes** is unrestricted. A key with some scopes needs the right one: a key with only `resource:write` was refused on `list` and `get` with `This API key lacks the 'resource:read' scope`. A key with `storage:read` and nothing else was refused on all of them.

### Related rows

`?expand=` fetches related rows and checks **each one** against the related resource's read policy (its `get`, or its `list` when it has no `get`). A row the caller may not read comes back as `null`. A related resource with **no readable operation** is shown only to service credentials. See [Relations](/data/relations).

### Records the caller never sees

For `list`, a row the policy does not admit is removed by SQL or by the residual, and never reaches the response. For `get`, `update` and `delete`, the check is on the one row. Nothing is returned for a refused record other than the status.

## Custom routes

A route has one policy, set in the route's **Access** section, and a body that may be validated. The order is:

| Order | Check |
| --- | --- |
| 1 | Rate limit |
| 2 | Body validation, if the route has an input model |
| 3 | Key scope: **`routes:invoke`** |
| 4 | The **plan**: the parts of the policy that do not need the body |
| 5 | The route's **cache**, for a `GET` route with a `cache_ttl` |
| 6 | The **full policy**, with the body as `$input` |
| 7 | The handler |

A request that fails the plan answers `401` or `403` without reading further. A request that passes the plan but fails the full check, because a condition on `$input` is false, answers the same way. Two consequences:

- **A cached answer is returned before the full check.** For a cached `GET` route the plan has run, but a condition that depends on the body or on state the plan could not see is not re-evaluated on a hit. Keep a cached route's policy to conditions on the caller. See [Custom routes](/data/custom-routes#caching-a-route).
- **A condition on `$input` for a `GET` route fails closed.** A `GET` has no body, so `$input.n` is empty, and `{"lte": ["$input.n", 10]}` is false. A stored policy of that shape refused a signed-in caller on a `GET` route with `403`.

A route's refusals read `policy '<name>' refused` for a signed-in caller and `Authentication required` for a signed-out one.

## Functions and flows called directly

Two more doors reach code without a route:

| Door | Path | Policy | Notes |
| --- | --- | --- | --- |
| A **function** | `POST /functions/v1/<name>` | The **function's** `policy` (the `@function(policy=...)` argument, default `authenticated`) | Needs the key scope `functions:invoke`. The result is wrapped as `{"data": ...}` |
| A **flow** | `POST /flows/v1/<name>` | The **HTTP trigger's** `policy` setting (default `authenticated`) | Only a flow whose HTTP trigger has **no path** is reachable here. A flow with a path answers `404`, `no directly invocable flow '<name>'` |

These doors have their own policies, and they are **separate from any route**. This is the most useful fact on this page for review:

- **A route that calls a function does not apply the function's policy.** Only the **route's** policy decides. A function with the policy `deny` returned its result through a route whose policy was `public`, while the same function called directly answered `403`, `policy 'deny' refused`.
- **A flow behind a locked route can still be open at `/flows/v1`.** If its HTTP trigger has no path and no restrictive `policy`, the default `authenticated` applies there, whatever the route says.

For every function and flow, ask: *what is its direct door's policy, and does it differ from the route that fronts it?*

A flow's trigger `policy` is **not validated** when you save it. A name that does not exist saves, and non-service callers then get a plain `500`.

## Storage buckets

A bucket has a **Read policy** and a **Write policy** in its sheet, with the choice **Default** meaning `authenticated`. A bucket marked public reads with `public`. The policies run **per object**, with the context `auth`, `credential`, `project`, `env` and `object` (the key, its segments and the action), and they must be JSON conditions.

| Request | Policy | Refusal |
| --- | --- | --- |
| Download (`GET /storage/v1/object/<bucket>/<key>`) | Read | `404`, `Not found` |
| Upload (`PUT` or `POST`) | Write | `403`, `the bucket's policy refused this upload` |
| Delete (`DELETE`) | Write | `404`, `Not found` |
| List (`GET /storage/v1/list/<bucket>?prefix=...`) | Read, with the **prefix** as the key | `403`, `the bucket's policy refused this listing` |
| Signed URL (`POST /storage/v1/sign/<bucket>/<key>`) | The read or write policy, for the **requester** | `403`, `you may not grant access you do not have` |

Details worth knowing:

- **Reads and deletes that are refused are `404`s**, the same as a missing object, so a stranger cannot probe for keys.
- **A signed URL grants only what the signer already has.** A caller who may not read a key cannot mint a link to it.
- **A listing is judged by its prefix**, so with the per-user layout `users/<id>/...` a caller must list inside their own folder, and listing the whole bucket is refused.
- **Storage requests do not check key scopes.** The storage routes in the code ask only the bucket's policy, and the scopes the platform enforces (`resource:read`, `resource:write`, `routes:invoke`, `functions:invoke`) do not include a storage scope. The bucket's policy is therefore the only guard. A public bucket's write policy is `authenticated` by default, which is what refused a signed-out upload.
- **`GET /storage/v1/buckets` has no policy.** It lists every bucket's name, whether it is public, its accepted types and size limit, to any caller with a key.
- **A public bucket is readable and listable by anyone** with the key, signed out included.

See [the context reference](/policies/context#storage-object) for the `object` paths.

## Realtime channels

Realtime is served by a separate service, and its policies are **channel rules** set under **Settings → Realtime**. Each rule has a **Pattern**, a **Subscribe** policy, a **Publish** policy, **Presence** and **History depth**, and the environment has a **Default policy** and **Clients may publish**.

| Action | Checked by |
| --- | --- |
| Subscribe | The matching rule's Subscribe policy |
| Publish | The matching rule's Publish policy, and **Clients may publish** |
| Presence | The rule's **Presence** switch, and the Subscribe policy |

The order of evaluation for an action on a channel:

| Order | Check | Refusal |
| --- | --- | --- |
| 1 | The channel name is valid: not empty, at most 200 characters, no `/` | `invalid channel name` |
| 2 | **Which rule governs it**: the first rule, top to bottom, whose pattern matches | (falls to the default policy if none) |
| 3 | A **service credential** passes from here on | |
| 4 | A **templated rule** must name this channel for this caller | `this channel belongs to someone else` |
| 5 | **Clients may publish** is on, for a publish | `clients may not publish in this environment` |
| 6 | **Presence** is on, for a presence action | `presence is off for this channel` |
| 7 | The rule's policy, with the channel context | the policy's refusal |

A pattern may contain `*` wildcards and `{{ ... }}` templates. A **templated** pattern such as `user:{{ auth.user_id }}` governs **every** channel that has the shape `user:*`, and then admits only the one it renders to for the caller. So a user may join `user:u-1` as `u-1`, and `user:u-2` is refused by that rule with `this channel belongs to someone else`, rather than falling through to the default. A caller for whom the template renders to nothing (a signed-out caller, `user:None`) is refused.

The context a channel policy sees is `auth`, `credential`, `project`, `env`, and **`channel`** (`name`, `segments` split on `:` and `/`, and `action`), plus the payload as `input` for a publish. Realtime policies must be **stored** (or built-in) policies: Python policies are not available to the realtime service, and a rule whose policy cannot be loaded is skipped.

The defaults are `authenticated` for subscribe, publish, and the **Default policy**. A channel that matches no rule is therefore open to **every signed-in user**, including channels you never meant to expose. Add a rule for each family of channels, and treat the default as the fallback you are accepting.

A resource whose **Broadcast changes** switch is on publishes every change, with the **raw record**, to `resource:<name>`. That channel's Subscribe policy is a data-access policy: add a rule for `resource:*` that is at least as strict as the resource's own `list` policy. See [Resource events](/data/resource-events#the-two-switches-on-a-resource).

## Event subscriptions

A subscription's **Only when…** condition decides whether the subscription fires for an event. It is evaluated against the event alone (`{"event": {...}}`), with no `auth` and no `request`. It is a filter, not an access check:

| What it does | What it does not |
| --- | --- |
| Decides whether a flow, function or channel is notified | Decide who may see the event. The event reaches every subscription whose pattern matches |
| Reads `$event.name`, `$event.payload`, `$event.actor` | Read the caller. There is none |

The default condition Studio fills in, `{"exists": "$event.data"}`, never matches, so a subscription with it never fires. See [the context reference](/policies/context#event-subscriptions-event).

## Inside flows

The **Check policy** block (`policy.check`) asks the engine about a policy for a context you build, and follows `allowed` or `denied`:

| Config | |
| --- | --- |
| `policy` | A name, or an inline condition |
| `record` | The `$record` for the check |
| `input` | The `$input` for the check |

The block uses the flow run's `auth` and `credential`. When a flow was started by a **service credential**, the engine's first step makes every check **allowed**, so the block cannot refuse in that case. For flows started by users, it enforces as a user. A flow started by an **event** or a **schedule** has the system's identity (not signed in), so a policy that needs a user refuses.

**Resource blocks inside a flow are not governed by policies at all.** `resource.list`, `resource.get`, `resource.create`, `resource.update` and `resource.delete` act with the platform's authority, which is why a flow can write a record the caller could not. A flow is code that you wrote, running as the system. If a flow acts on behalf of a user, it must **check** (with `policy.check`, or with explicit conditions) what the user may do. The route or trigger that started it gets one decision, and everything after that is the flow's own responsibility.

The **Require sign-in** block (`auth.require`) is a simpler check: it fails the flow with `401` for a signed-out caller, and with `403` when a required role or permission is missing.

## What is not governed by caller policies

Policies decide what **callers of the public surface** may do. These act with the platform's own authority, and no caller policy applies:

| Thing | Why it matters |
| --- | --- |
| **Secret keys and operators** | They bypass every policy, by design |
| **The Records tab** in Studio | Operators read and write any row. Its writes publish events (actor `studio`) and clear caches, and are not audited in the audit log |
| **The Database console** | Any SQL. Its writes are audited as `database.write` and clear every resource's cache. It publishes no events |
| **Migrations** | Structural changes with the platform's authority |
| **Resource blocks and the runtime in flows and functions** | Trusted code. See above |
| **Events, webhooks and realtime fan-out** | They carry the raw record to every consumer. A policy does not filter an event |
| **A direct database connection** | Bypasses Pawabase entirely. A database role has its own grants |
| **`GET /storage/v1/buckets`** | Lists buckets to any key |
| **The OpenAPI document**, if you publish it | Shows every operation and field name |
| **Validation errors** | Reveal field names before any policy runs |

Two of these deserve a decision rather than a note. **Events** carry hidden fields to consumers, so a resource with sensitive columns needs its events off or shaped. And **flows and functions** are a way for a policy-limited caller to cause writes the caller could not make directly: review each flow that a public route can start.

## Defaults at a glance

| Where | Default policy |
| --- | --- |
| Resource operation | `authenticated` (labelled **Secret keys only** in Studio, which is wrong) |
| Custom route | `authenticated` |
| Function | `authenticated` |
| Flow HTTP trigger | `authenticated` |
| Bucket read | `authenticated` (`public` if the bucket is public) |
| Bucket write | `authenticated` |
| Realtime subscribe and publish | `authenticated` |
| Realtime default policy | `authenticated` |
| Event subscription | No condition: it always fires |
| Operation not enabled | There is no endpoint (`405` or `404` from the router) |

`authenticated` is the same everywhere, and it admits **every signed-in user**. If your project lets anyone sign up, `authenticated` is effectively public. Choose a real policy for each thing that holds anything private.

## A coverage review

When you inherit a project, or before a launch, walk this list once. Each line is a door, and the question is who can pass.

| Door | Question | Where to look |
| --- | --- | --- |
| Each resource, each operation | Is it enabled, and what is its policy? | The resource's **Access** section |
| Each resource's `delete` | Does a key with no write scope reach it? | The `delete` policy and the key's scopes |
| Each custom route | What is its policy, and what does its handler do with the caller? | The route's **Access** |
| Each function | Is it reachable directly, and with what policy? | `@function(policy=...)` |
| Each flow | Is there an HTTP trigger with no path, and what policy? | The flow's trigger |
| Each bucket | Read and write policies? Public? | The bucket sheet |
| Each realtime family | Is there a rule, or does the default admit all signed-in users? | **Settings → Realtime** |
| Each resource with **Broadcast changes** | Is `resource:<name>` as strict as `list`? | The channel rules |
| Each resource with **Emit events** | Do consumers need the hidden fields? | The subscriptions and webhooks |
| Each key | Which scopes, IPs and routes? | **API keys** |
| Each secret key | Where is it, and is it on a server? | Your deployment |

## Questions that come up

<AccordionGroup>
  <Accordion title="Where is the policy for a flow started by a route?">
    The route's policy decides whether the flow starts. After that, the flow's blocks act with the platform's authority, and the flow is responsible for any further checks.
  </Accordion>
  <Accordion title="Why can a key with no write scope delete?">
    `DELETE` is not behind the scope gate. The policy still applies. Restrict the key's allowed routes and do not enable `delete` for public resources.
  </Accordion>
  <Accordion title="Does the Records tab respect policies?">
    No. It is for operators, and acts with the platform's authority.
  </Accordion>
  <Accordion title="Are events filtered by the resource's policy?">
    No. Every matching consumer receives the raw record.
  </Accordion>
  <Accordion title="Do policies apply to the OpenAPI document?">
    No. The document describes the surface, and a policy does not hide an operation or a field from it.
  </Accordion>
  <Accordion title="What does a refused realtime subscribe look like?">
    The subscription is rejected with the policy's refusal, or `this channel belongs to someone else` for a templated rule.
  </Accordion>
  <Accordion title="Can I use the same policy on a bucket and a resource?">
    If it reads only paths both have: `auth` and `credential`. `$record` does not exist for a bucket and `$object` does not exist for a resource.
  </Accordion>
</AccordionGroup>

## What to remember

- **One engine, eight kinds of door.** Each has a context, a default and its own refusal.
- **`authenticated` is the default everywhere,** and admits every signed-in user.
- **Validation runs before policies.** Field names are public.
- **`DELETE` skips the scope gate.** The policy is the only guard.
- **A route does not apply the policy of the function or flow it calls.** Those have direct doors of their own.
- **Reads that are refused are `404`s for single records and objects.** Writes by signed-in strangers are `403`s.
- **Realtime's default admits every signed-in user.** Add rules per channel family.
- **Flows, resource blocks, the Records tab, the console, events and secret keys are not governed by caller policies.**
