## Why shorthands exist

Most access rules are about the same few facts: is the caller signed in, what are their roles, do they own this record, which key did they use. Writing each as a comparison would bury the idea in mechanics. A **shorthand** is a one-key condition that **expands** to the comparison it stands for, so the policy reads as the rule.

```json
{ "role": "admin" }
```

is evaluated as

```json
{ "any": [{ "contains": ["$auth.roles", "admin"] }] }
```

The expansion is not a convenience layered on top of the engine. **The engine evaluates shorthands by expanding them, and the list planner expands them too**, so a shorthand behaves exactly like the longer condition in every way, including how a list turns it into SQL. Choose a shorthand whenever one fits: it is shorter, harder to get wrong, and carries safeguards you would otherwise have to remember (`owner` includes the signed-in check).

Everything here was run against the real engine. The expansions are quoted from it.

## At a glance

| Shorthand | Argument | Expands to | Studio rule label |
| --- | --- | --- | --- |
| `authenticated` | `true` or `false` | `eq` of `$auth.authenticated` with the value | **Is signed in** |
| `role` | A role, or a list | `any` of `contains` on `$auth.roles` | **Has role** |
| `permission` | A permission, or a list | `all` of (`any` of the permission, or `*`) over `$auth.permissions` | **Has permission** |
| `owner` | A column name | `all` of signed in and `$record.<column>` equals `$auth.user_id` | **Owns the record (field)** |
| `service` | `true` or `false` | `eq` of `$credential.is_service` with the value | **Uses a secret key** |
| `kind` | A caller kind | `eq` of `$auth.kind` with the value | **Caller kind is** |
| `scope` | A scope | `contains` on `$credential.scopes` | **Key has scope** |
| `aal` | A level, such as `aal2` | `eq` of `$auth.aal` with the value | **Signed in with 2FA** |

None of the arguments is validated when you save. A policy `{"role": {}}` is accepted and is false for everyone. See [what saving checks](/policies/conditions#what-saving-checks-and-what-it-does-not).

## `authenticated`

True when the caller is signed in.

```json
{ "authenticated": true }
```

The argument is converted with the language's truthiness, so `true` means "signed in" and `false` means "signed out":

| Argument | Meaning | Result for a signed-in caller |
| --- | --- | --- |
| `true` | Signed in | true |
| `false` | Signed out (anonymous) | false |
| `"yes"` | Any non-empty text is true | **true** |
| `"false"` | **A non-empty text is true** | **true** |

<Warning>
`{"authenticated": "false"}` means **signed in**, because the text `"false"` is not empty. The argument must be a JSON boolean. A form that stores the value as text, or a policy written by hand with quotes, inverts the rule.
</Warning>

**What "signed in" means.** `$auth.authenticated` is true for a caller with a verified user token. A **publishable key alone** is anonymous: it identifies the project and the key's role, not a person. A **secret key** is not signed in as a user either (it carries `credential.is_service` instead, and it bypasses policies anyway).

**The built-in.** `authenticated` is also the name of a built-in policy whose condition is `{"authenticated": true}`, and it is the default for resource operations, routes, functions, flows and buckets. See [the built-in policies](#the-built-in-policies).

`{"authenticated": false}` admits only anonymous callers. It is rarely what you want, since a signed-in caller is refused, and it is not how you make something public (use `public`).

## `role`

True when the caller has **at least one** of the named roles.

```json
{ "role": "admin" }
{ "role": ["editor", "admin"] }
```

| Condition | Caller's roles | Result |
| --- | --- | --- |
| `{"role": "admin"}` | `["admin", "editor"]` | true |
| `{"role": ["x", "editor"]}` | `["admin", "editor"]` | true (any) |
| `{"role": "Admin"}` | `["admin", "editor"]` | **false** (roles are case-sensitive) |
| `{"role": []}` | anything | **false** (an empty list matches nobody) |
| `{"role": "admin"}` | `[]` (anonymous) | false |

A list means **any**, not all. To require two roles, put two shorthands in an `all`:

```json
{ "all": [{ "role": "editor" }, { "role": "reviewer" }] }
```

**Where roles come from.** `$auth.roles` is the list of roles in the caller's token, assigned in the project's user management. A role is a name, and Pawabase does not define what `admin` or `editor` mean: a policy does. Keep the names in one place, since a typo in a role name silently matches nobody.

A role in a **list request** is decided at **plan time**: it depends only on the caller, so the engine knows the answer before reading any row. `{"any": [{"owner": "owner_id"}, {"role": "admin"}]}` for an admin is simply true (no filter, every row), and for a non-admin it plans to the owner filter. That is why a policy that says "owner or admin" is cheap for both.

## `permission`

True when the caller has **every** permission named. A caller whose permissions include `*` has them all.

```json
{ "permission": "posts.write" }
{ "permission": ["posts.write", "posts.publish"] }
```

| Condition | Caller's permissions | Result |
| --- | --- | --- |
| `{"permission": "posts.write"}` | `["posts.write"]` | true |
| `{"permission": ["posts.write", "x"]}` | `["posts.write"]` | **false** (**all** are required) |
| `{"permission": "*"}` | `["posts.write"]` | false (`*` is a wildcard for the **caller**, not a permission to ask for) |
| `{"permission": "anything.x"}` | `["*"]` | **true** (the caller's wildcard grants it) |
| `{"permission": "posts.write"}` | `[]` | false |

Contrast with `role`: **a list of roles is "any", a list of permissions is "all"**. This is the most common source of a role/permission mixup. To require **one of** several permissions, use `any`:

```json
{ "any": [{ "permission": "posts.write" }, { "permission": "posts.admin" }] }
```

This was run on a resource with `create` set to `permission:feat.write`: a caller with that exact permission got `201`, a caller whose permissions were `["*"]` got `201`, and a caller with none got `403`, `policy 'permission:feat.write' refused`.

**Where permissions come from.** `$auth.permissions` is the list in the caller's token. Permissions are finer-grained than roles, and they are what a policy should check when an action has a name (`posts.publish`), leaving roles for audiences (`editor`).

## `owner`

True when the caller is **signed in** and the record's column equals the caller's id. This is the shorthand to use for "my rows".

```json
{ "owner": "user_id" }
```

It expands to **two** conditions:

```json
{
  "all": [
    { "authenticated": true },
    { "eq": ["$record.user_id", "$auth.user_id"] }
  ]
}
```

The first half is the point. A bare `eq` between a record column and the caller's id is **true for a signed-out caller on a row whose column is `null`**, because two empty values are equal. `owner` cannot be fooled that way. This was run, with the same three rows (owned by `u-1`, owned by `u-2`, no owner) under both forms:

| Signed-out request | `{"eq": ["$record.owner_id", "$auth.user_id"]}` | `{"owner": "owner_id"}` |
| --- | --- | --- |
| List | `200`, empty | `401` |
| Get the row with no owner | **`200`, the row** | `401` |
| `PATCH` the row with no owner | **`200`, changed** | `401` |
| `DELETE` the row with no owner | **`204`, deleted** | `404` (refused) |

Use `owner` for every ownership rule. See [the overview](/policies/overview#a-plain-eq-on-an-owner-column-fails-open).

| Argument | Meaning |
| --- | --- |
| `"user_id"` | The column to compare |
| Any other text | That column |
| A non-text value (`true`, a number) | The column `owner_id` |

The column name is not checked against the resource's fields. A typo is a path that does not exist, and the comparison is false for signed-in callers and, with a typo on the **record** side, never matches.

**Integer ids work.** An owner column holding the integer `7` and a token whose user id is the text `"7"` compare equal, because `eq` normalises integers. So `owner` works whether you store ids as numbers or text.

**On a list**, `owner` is the textbook case for SQL pushdown: it becomes `WHERE user_id = '7'`, with correct pages and a correct `total`. Verified with a signed-in caller: the plan was `{"filters": {"user_id": "7"}}` and no residual. For a signed-out caller the plan is refused before any query, which is why the list answered `401`.

**`owner_field` is not `owner`.** A resource's `owner_field` stamps the caller's id on `create` and keeps clients from changing it. It does **not** restrict who can read. Pair it with `owner` on `list`, `get`, `update` and `delete`. See [Defining resources](/data/defining-resources).

## `service`

True when the credential is a **service** credential: a secret key or an operator.

```json
{ "service": true }
```

The condition reads `$credential.is_service`, which is true for the credential roles `service` and `operator`, and for a caller whose principal is a service or an operator.

This shorthand is unusual in one respect: **it is almost redundant**, because the engine already passes service credentials through **every** policy before reading it. A policy of `{"service": true}` therefore behaves as "service credentials only" for the reason that **everyone else fails the condition**, and the secret key passes it twice over. That makes it the way to say *this is for servers*:

| Caller | `{"service": true}` |
| --- | --- |
| A signed-in user | false |
| A publishable key, signed out | false |
| A secret key | true |
| A Studio operator | true |

It was run on a route: a signed-out caller got `401`, a signed-in user got `403` (`policy 'service' refused`), and a secret key got `200`.

`{"service": false}` is true for everyone who is **not** a service credential, and a secret key still passes it, because the bypass comes first. Do not use it to keep servers out: nothing can.

## `kind`

True when the **kind of principal** matches.

```json
{ "kind": "user" }
```

| Kind | Who |
| --- | --- |
| `user` | A project's end user, with a user token |
| `operator` | A Studio user acting on the environment |
| `service` | Another Pawabase service |
| `anonymous` | No one signed in |

`kind` is how a condition separates people from machines when both are signed in. In practice it is rarely needed: a policy for people uses `authenticated`, and a policy for machines uses `service`. It matters in a rule such as "signed in, and an actual end user, not an operator impersonating one": `{"all": [{"authenticated": true}, {"kind": "user"}]}`.

## `scope`

True when the **API key** carries the named scope.

```json
{ "scope": "resource:write" }
```

A scope is a permission on the **key**, not on the person. It comes from `$credential.scopes`, the list the key was created with. In Studio, **API keys → New API key** has a **Scopes** field with the hint *Click a scope to limit the key. Leave empty for unrestricted access within its role.* The scopes the platform itself enforces are:

| Scope | Enforced for |
| --- | --- |
| `resource:read` | `list` and `get` on resources |
| `resource:write` | `create`, `update` on resources (**not** `delete`) |
| `routes:invoke` | Custom routes |
| `functions:invoke` | Calling a function directly at `/functions/v1` |

Any other text is accepted as a **custom scope**, and a policy can require it with `scope`. That makes scopes a way to give different keys different powers over the same resource:

```json
{ "scope": "reports:export" }
```

| Key created with | `{"scope": "resource:write"}` | `{"scope": "reports:export"}` |
| --- | --- | --- |
| Nothing (empty scopes) | **false** | false |
| `resource:read` | false | false |
| `resource:read`, `resource:write` | true | false |
| `reports:export` | false | true |

The first row needs attention. An **empty** scope list means "unrestricted" for the platform's own checks (`resource:read` and the rest are all allowed), but the `scope` **shorthand** reads the list literally, so with an empty list it is false. A key with no scopes passes every built-in scope check and fails every `{"scope": ...}` policy. If a policy requires a scope, give the key that scope explicitly.

**A scope check is not a permission model for people.** Anyone who holds the key has its scopes. Combine it with a user check where both matter: a key with `reports:export` *and* a signed-in user with `permission:reports.read`.

Also remember that `resource:write` does not guard `DELETE`. See [the overview](/policies/overview#delete-skips-the-key-scope-check-and-the-sign-in-gate). The key's **Allowed routes** setting (*Optional comma-separated gateway rules: GET /rest/v1/\* or POST /functions/v1/\**) is a separate, gateway-level restriction, and a read-only public key should have it set to `GET /rest/v1/*`.

## `aal`

True when the caller's **authentication assurance level** matches.

```json
{ "aal": "aal2" }
```

`$auth.aal` is `aal1` for a caller who signed in with a password or similar, and `aal2` after a **second factor**. The rule means "passed multi-factor authentication", and it is the shorthand behind the built-in `mfa` policy. Verified:

| Caller | `{"aal": "aal2"}` | The built-in `mfa` |
| --- | --- | --- |
| Signed in, `aal1` | false | `403`, `policy 'mfa' refused` |
| Signed in, `aal2` | true | passes the policy |
| Signed out | false | `401` |

An `aal` check compares for **equality**. `{"aal": "aal1"}` is true only for callers at exactly `aal1`, which excludes callers who completed a second factor. There is no "at least". For step-up protection use `aal2`, and put it on the operations that need it (`delete`, payment) rather than on a whole resource.

Studio's label for it is **Signed in with 2FA**, and the picker's built-in is **Signed in with 2FA**.

## Combining shorthands

Shorthands are conditions, so they compose with `all`, `any` and `not` like any other:

| Rule | Condition |
| --- | --- |
| The owner, or an admin | `{"any": [{"owner": "user_id"}, {"role": "admin"}]}` |
| An admin who passed 2FA | `{"all": [{"role": "admin"}, {"aal": "aal2"}]}` |
| A signed-in user who is not banned | `{"all": [{"authenticated": true}, {"not": {"role": "banned"}}]}` |
| Staff with the write permission, or a server | `{"any": [{"service": true}, {"all": [{"role": "staff"}, {"permission": "records.write"}]}]}` |
| A key that may write, used by a signed-in user | `{"all": [{"scope": "resource:write"}, {"authenticated": true}]}` |

Mixed in a list request, the planner handles each shorthand by what it needs. Anything that depends only on the caller (`authenticated`, `role`, `permission`, `service`, `kind`, `scope`, `aal`) is decided at plan time. `owner` becomes a SQL filter. See [SQL pushdown](/policies/pushdown).

## Parameterised names: shorthands as references

Where a policy is **attached** (a resource operation, a route, a bucket), you do not have to create a stored policy for a shorthand. A string of the form `kind:argument` is understood directly:

| Written | Same as |
| --- | --- |
| `role:admin` | `{"role": "admin"}` |
| `permission:posts.write` | `{"permission": "posts.write"}` |
| `owner:author_id` | `{"owner": "author_id"}` |
| `scope:resource:write` | `{"scope": "resource:write"}` |
| `kind:user` | `{"kind": "user"}` |

The split is at the **first** colon, so `scope:resource:write` is the scope `resource:write`. Only these five kinds are recognised as strings:

| Written | Result |
| --- | --- |
| `aal:aal2` | **`unknown policy 'aal:aal2'`**. Use `mfa`, or `{"aal": "aal2"}` |
| `service:true` | **`unknown policy 'service:true'`**. Use `service` |
| `authenticated:true` | Unknown. Use `authenticated` |
| `role:` (nothing after the colon) | `unknown policy 'role:'` |
| `role` (no colon) | `unknown policy 'role'` |
| `Role:admin` | Unknown. The kind is case-sensitive |

The multi-role and multi-permission forms (`{"role": ["a", "b"]}`) cannot be written as a string. Use a stored policy, an inline condition, or a list of references. Studio's picker offers the same five under **More**: **Users with role…** (placeholder `admin`), **Users with permission…** (`posts.write`), **Owner via field…** (`author_id`), **Keys with scope…** (`resource:write`), and an input for the argument. `kind` has no entry in the picker, though the engine accepts `kind:user`.

## The built-in policies

Six policies exist in every environment, built from the shorthands and constants:

| Name | Condition | Studio label | Description |
| --- | --- | --- | --- |
| `public` | `true` | **Anyone (public)** | Anyone, including anonymous callers. |
| `authenticated` | `{"authenticated": true}` | **Signed-in users** | Any signed-in user. |
| `owner` | `{"owner": "owner_id"}` | **Record owner (owner_id)** | The user whose id is in the record's owner_id. |
| `mfa` | `{"all": [{"authenticated": true}, {"aal": "aal2"}]}` | **Signed in with 2FA** | Signed in with a second factor. |
| `service` | `{"service": true}` | **Secret keys & operators** | Secret keys and operators only. |
| `deny` | `false` | **Nobody** | Nobody except service credentials. |

Three points to know:

- **`owner` is hard-wired to the column `owner_id`.** On a resource whose owner column has another name it does not work. This was run on a resource with `owner_field: "user_id"`: `create` was refused (`403`), `list` answered `400` (`notes has no field 'owner_id'`) and `get` answered `404`. Use `owner:user_id`, which names the column.
- **`deny` still lets secret keys through**, as every policy does. *Nobody except service credentials* is exactly right.
- **A stored policy with one of these names replaces it.** See [the overview](/policies/overview#a-stored-policy-can-replace-a-built-in-one).

## Which one to reach for

| You want | Use |
| --- | --- |
| Anyone | `public` |
| Anyone signed in | `authenticated` |
| The record's owner | `owner:<column>` |
| People of one kind of audience | `role:<name>` |
| People who may do one named thing | `permission:<name>` |
| Servers only | `service` |
| A step-up for sensitive operations | `mfa` |
| Keys with a particular power | `scope:<name>` |
| End users, not operators | `kind:user` |
| Nobody through the API | `deny`, or leave the operation **off** |

The last row has a better answer than `deny`: a resource operation that is switched **off** has no endpoint, and is answered by the router (`405` for a method on a path that serves another). A `deny` policy leaves an endpoint that answers `401` or `403` and shows up in the documentation.

## Pitfalls

| Pitfall | Effect | Fix |
| --- | --- | --- |
| `{"authenticated": "false"}` | Means signed in | A JSON boolean |
| A role list meant as "all of" | It is "any of" | Two `role` shorthands in an `all` |
| A permission list meant as "one of" | It is "all of" | `any` of single permissions |
| `Admin` against `admin` | No match | Match the case |
| `owner` on a column that is not `owner_id` and no argument | Uses `owner_id` | `owner:<column>` |
| The built-in `owner` on a resource with another owner column | Fails | `owner:<column>` |
| A bare ownership `eq` | Fails open for unowned rows | `owner` |
| A `scope` policy on a key with no scopes | False | Give the key the scope |
| `aal1` meaning "at least first factor" | Excludes `aal2` callers | Compare to `aal2` or use `any` |
| Naming a stored policy `owner` | Replaces the built-in | A descriptive name |
| `aal:aal2` or `service:true` as a reference | Unknown policy | `mfa`, `service` |

## Questions that come up

<AccordionGroup>
  <Accordion title="Do shorthands cost more than the longer condition?">
    No. They are expanded before evaluation and before planning, so they are the same condition.
  </Accordion>
  <Accordion title="Can I add my own shorthand?">
    No. There are eight. For a rule you repeat, make a stored policy and reference it by name, or write a Python policy.
  </Accordion>
  <Accordion title="Where do roles and permissions come from?">
    From the signed-in user's token, assigned in the project's user management. They are plain text, and Pawabase attaches no meaning to the names.
  </Accordion>
  <Accordion title="Is `role` the same as `$auth.org_role`?">
    No. `role` reads the project-wide `$auth.roles`. `$auth.org_role` is the caller's role inside their organisation, read with a comparison such as `{"in": ["$auth.org_role", ["owner", "admin"]]}`.
  </Accordion>
  <Accordion title="Why does a secret key pass the service shorthand with false?">
    Because service credentials bypass every policy before the condition is read, so `{"service": false}` cannot keep them out.
  </Accordion>
  <Accordion title="Does `permission` with `*` in the policy grant everything?">
    No. The wildcard works on the **caller's** side: a caller whose permissions contain `*` passes every `permission` check. Asking for `*` in a policy is just asking for a permission named `*`.
  </Accordion>
</AccordionGroup>

## What to remember

- **Eight shorthands, each an ordinary condition.** The engine and the planner expand them.
- **`role` lists are any. `permission` lists are all.**
- **`owner` is signed in plus a column comparison.** Use it for every ownership rule.
- **The built-in `owner` means `owner_id`.** Name the column: `owner:user_id`.
- **`authenticated` takes a boolean.** The text `"false"` is true.
- **`scope` reads the key's scopes literally.** An empty list is false.
- **`aal` is an equality.** There is no "at least".
- **`role:`, `permission:`, `owner:`, `scope:` and `kind:` work as references.** `aal:` and `service:` do not.
