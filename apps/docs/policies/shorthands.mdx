Most access rules are built from the same handful of questions: *is the caller signed in? do they have this role? do they own this row? are they using a server key?* **Shorthands** answer those in one key each. They're ordinary conditions under the hood: before evaluation, each shorthand **expands** into comparisons, so it combines freely with groups, comparisons and checks, and pushes down into SQL exactly like the conditions it stands for.

## At a glance

| Shorthand | Argument | Expands to | Decided without the record? |
| --- | --- | --- | --- |
| `authenticated` | `true` / `false` | `eq($auth.authenticated, arg)` | Yes |
| `role` | a role, or a list (**any**) | `any(contains($auth.roles, r) for r)` | Yes |
| `permission` | a permission, or a list (**all**) | `all(any(contains($auth.permissions, p), contains($auth.permissions, "*")) for p)` | Yes |
| `owner` | a column name (default `owner_id`) | `all(authenticated, eq($record.<col>, $auth.user_id))` | No: it needs the record |
| `service` | `true` / `false` | `eq($credential.is_service, arg)` | Yes |
| `kind` | a principal kind | `eq($auth.kind, arg)` | Yes |
| `scope` | an API-key scope | `contains($credential.scopes, arg)` | Yes |
| `aal` | `"aal1"` / `"aal2"` | `eq($auth.aal, arg)` | Yes |

"Decided without the record" matters for lists: those shorthands are evaluated **before** the query, so they cost nothing per row and can make a list unrestricted (true) or refused (false) outright. See [pushdown](/policies/pushdown).

## `authenticated`

```json
{ "authenticated": true }
```

True when the request carries a **valid user access token** for this environment. Expired, malformed or foreign-environment tokens don't count; they're rejected with `401` before policies run.

```json
{ "authenticated": false }
```

True only for **anonymous** callers. It's rarely what you want in a policy, but it's useful for sign-up-style routes you want to hide from already-signed-in users, or in subscription conditions.

The built-in policy `authenticated` is exactly `{"authenticated": true}`.

<Note>
A request with a **secret key** and no token isn't "authenticated" in this sense, but it doesn't need to be: secret keys bypass policies entirely. `authenticated` is about people.
</Note>

## `role`

```json
{ "role": "teacher" }
{ "role": ["admin", "principal"] }
```

True when the caller's `auth.roles` includes the role; with a list, **any** of them. Roles are defined per environment in Akountz and copied into every access token, so the check is a list lookup with no database query.

### Any, not all

A list means *any of these roles*, because that's nearly always the intent: "admins or principals may…". If you really need several roles at once, use an `all`:

```json
{ "all": [ { "role": "teacher" }, { "role": "form_tutor" } ] }
```

### Role vs permission

Roles describe **who someone is**; permissions describe **what they can do**. Checking roles is simple and reads naturally in small systems. Permissions scale better when roles multiply, because many roles can grant the same permission and the policy doesn't change when you add a role. See [permission](#permission) and [roles and permissions](/auth/roles-and-permissions).

### Parameterised form

Anywhere a policy reference is accepted, `"role:librarian"` is shorthand for `{"role": "librarian"}`:

```json
"operations": { "create": { "enabled": true, "policy": "role:librarian" } }
```

## `permission`

```json
{ "permission": "reports.publish" }
{ "permission": ["finance.read", "finance.export"] }
```

True when the caller has the permission, **or the wildcard permission `*`**. With a list, the caller needs **all** of them, since that's the usual intent for capabilities ("may read *and* export").

Permissions come from the caller's roles plus any permissions granted directly to the user, and are copied into the token as `auth.permissions`.

### Naming permissions

Use a `resource.action` convention and grant broad ones with a trailing wildcard in role definitions:

| Role | Permissions |
| --- | --- |
| `admin` | `*` |
| `principal` | `students.*`, `reports.publish`, `finance.read` |
| `bursar` | `finance.*` |

<Warning>
Only the literal permission `*` is treated as a wildcard **by the shorthand**. A role holding `finance.*` does **not** automatically pass `{"permission": "finance.read"}`. Grant the specific permissions your policies check, or check the wildcard explicitly: `{"any": [{"permission": "finance.read"}, {"permission": "finance.*"}]}`.
</Warning>

### Parameterised form

`"permission:reports.publish"`.

## `owner`

```json
{ "owner": "author_id" }
{ "owner": true }          // uses the owner_id column
```

True when the caller is signed in **and** the record's column equals the caller's user id. It expands to:

```json
{ "all": [
  { "authenticated": true },
  { "eq": ["$record.author_id", "$auth.user_id"] }
] }
```

The `authenticated` half matters: without it, an anonymous caller (whose `user_id` is `null`) would "own" every row whose column is `null`.

### Owner and owner fields

The `owner` shorthand is a **check**. A resource's **owner field** is a **write rule**: on create, the server sets that column to the caller's id. Use them together for private data:

```json
{ "name": "notes", "owner_field": "owner_id",
  "operations": {
    "list":   { "enabled": true, "policy": "owner" },
    "get":    { "enabled": true, "policy": "owner" },
    "create": { "enabled": true, "policy": "authenticated" },
    "update": { "enabled": true, "policy": "owner" },
    "delete": { "enabled": true, "policy": "owner" }
  } }
```

On updates, Pawabase also drops the owner field from the patch, so ownership can't be changed through the API even by the owner.

### Pushdown

For lists, `owner` becomes `WHERE <column> = '<your user id>'`. That's the fastest possible private list: an indexed equality, exact pages and exact totals.

### Parameterised form

`"owner:borrower_user_id"`.

## `service`

```json
{ "service": true }
```

True for **service credentials**: secret keys, and operators acting through Studio. The built-in `service` policy is exactly this.

Because service credentials bypass policies before any condition is evaluated, `{"service": true}` only makes a difference where the bypass doesn't apply: inside a flow's `policy.check` block (which receives the flow's own credential context), or as part of a larger condition you evaluate yourself. As an operation policy it effectively means *nobody except service credentials*, which is also what the built-in `deny` and a `null` resource policy do. Use `service` when you want that intent to read clearly.

## `kind`

```json
{ "kind": "user" }
```

True when `$auth.kind` equals the argument. For people signed in with a token it's `user`; anonymous callers have kind `anonymous`; internal platform callers are `service` or `operator`. Use it to keep a route strictly for people, even if a future credential type is added.

Parameterised: `"kind:user"`.

## `scope`

```json
{ "scope": "reports:export" }
```

True when the request's **API key** carries the scope. Key scopes are set when the key is created; an empty scope list means "unrestricted", and the shorthand is false in that case, because it asks whether this specific scope was **granted**.

Pawabase already enforces the built-in scopes (`resource:read`, `resource:write`, `routes:invoke`) before policies run. Use the `scope` shorthand for **your own** scopes:

```json
{ "all": [ { "authenticated": true }, { "scope": "partner:orders" } ] }
```

A partner integration then needs both a user token and a key minted with `partner:orders`.

Parameterised: `"scope:partner:orders"`.

## `aal`

```json
{ "aal": "aal2" }
```

True when the token's **authentication assurance level** matches. Tokens issued after a password, magic link or social sign-in carry `aal1`; after completing a TOTP or recovery-code challenge they carry `aal2`.

The built-in policy `mfa` is:

```json
{ "all": [ { "authenticated": true }, { "aal": "aal2" } ] }
```

Use it to protect money, deletions and role changes:

```json
"operations": { "delete": { "enabled": true, "policy": ["mfa", "role:admin"] } }
```

Users who haven't enrolled in MFA can't reach `aal2`, so pair these rules with a UI that invites them to enrol. See [MFA](/auth/mfa).

## Combining shorthands

Shorthands are conditions, so they nest anywhere:

```json
{ "any": [
  { "role": "admin" },
  { "all": [ { "role": "bursar" }, { "aal": "aal2" }, { "lte": ["$input.amount", 500000] } ] },
  { "all": [ { "owner": "requested_by" }, { "eq": ["$record.status", "draft"] } ] }
] }
```

"Admins always; bursars with 2FA for amounts up to 500,000; the requester while it's still a draft."

## Parameterised references, in one table

Where a policy **reference** is expected (resource operations, routes, buckets, channels, `@function`), five shorthands have a string form:

| String | Same as |
| --- | --- |
| `role:admin` | `{"role": "admin"}` |
| `permission:reports.publish` | `{"permission": "reports.publish"}` |
| `owner:author_id` | `{"owner": "author_id"}` |
| `scope:partner:orders` | `{"scope": "partner:orders"}` |
| `kind:user` | `{"kind": "user"}` |

Only one argument fits in the string form. For role lists use the object form: `{"role": ["admin", "principal"]}`.

## Choosing the right shorthand

<AccordionGroup>
  <Accordion title="Private data">
    `owner`, with an owner field on the resource.
  </Accordion>
  <Accordion title="Staff-only screens and endpoints">
    `role` with a list of staff roles, ideally wrapped in a named policy like `staff`.
  </Accordion>
  <Accordion title="Capabilities that many roles share">
    `permission`, so adding a role never requires editing policies.
  </Accordion>
  <Accordion title="Money, deletions, role changes">
    Add `aal: aal2` (or reference `mfa`) to whatever else the rule requires.
  </Accordion>
  <Accordion title="Partner and machine integrations">
    `scope` for your own scopes; built-in scopes are already enforced.
  </Accordion>
  <Accordion title="Server-only operations">
    Leave the resource operation's policy `null`, or reference `service`/`deny`. Your servers use a secret key.
  </Accordion>
</AccordionGroup>

## Compared with Supabase and Firebase

| Pawabase | Supabase (RLS) | Firebase (rules) |
| --- | --- | --- |
| `{"authenticated": true}` | `auth.role() = 'authenticated'` | `request.auth != null` |
| `{"owner": "user_id"}` | `auth.uid() = user_id` | `request.auth.uid == resource.data.userId` |
| `{"role": "admin"}` | custom claim in `auth.jwt()` or a roles table lookup | `request.auth.token.admin == true` (custom claims) |
| `{"permission": "x"}` | a permissions table + SQL function | custom claims |
| `{"aal": "aal2"}` | `auth.jwt()->>'aal' = 'aal2'` | not built in |
| `{"scope": "x"}` | not built in (API keys have no scopes) | not built in |

In Pawabase, roles and permissions are managed by Akountz and present in every token, so these checks need neither custom-claim plumbing nor database lookups.

## Seeing the expansion

It helps to see exactly what a shorthand becomes. Here are three, fully expanded:

<CodeGroup>
```json role with a list
// { "role": ["admin", "principal"] }
{ "any": [
  { "contains": ["$auth.roles", "admin"] },
  { "contains": ["$auth.roles", "principal"] }
] }
```
```json permission with a list
// { "permission": ["finance.read", "finance.export"] }
{ "all": [
  { "any": [ { "contains": ["$auth.permissions", "finance.read"] },   { "contains": ["$auth.permissions", "*"] } ] },
  { "any": [ { "contains": ["$auth.permissions", "finance.export"] }, { "contains": ["$auth.permissions", "*"] } ] }
] }
```
```json owner
// { "owner": "borrower_user_id" }
{ "all": [
  { "authenticated": true },
  { "eq": ["$record.borrower_user_id", "$auth.user_id"] }
] }
```
</CodeGroup>

The expansion happens at evaluation time. What's stored (and shown in Studio's JSON tab) is always the short form.

## Shorthands in Studio

In the policy rule builder, each shorthand is a rule type with a plain-English label:

| Rule builder label | Shorthand | Input |
| --- | --- | --- |
| Is signed in | `authenticated` | yes / no (anonymous) |
| Has role | `role` | one role, or several separated by commas |
| Has permission | `permission` | one permission, or several separated by commas |
| Owns the record (field) | `owner` | the column name, default `owner_id` |
| Uses a secret key | `service` | — |
| Signed in with 2FA | `aal` | — (sets `aal2`) |
| Key has scope | `scope` | the scope |
| Caller kind is | `kind` | the kind |

In policy **pickers** (on resources, routes and buckets), the *More* group offers *Users with role…*, *Users with permission…*, *Owner via field…* and *Keys with scope…*, which store the parameterised string form (`role:librarian`).

## Worked scenarios: a clinic

To see how shorthands carry real requirements, here's the access model of a small clinic system, built almost entirely from shorthands.

**Roles:** `admin`, `doctor`, `nurse`, `receptionist`, `patient`.
**Permissions:** `records.read`, `records.write`, `prescriptions.issue`, `billing.manage`.

<Steps>
  <Step title="Patients see their own appointments">
    Resource `appointments` with owner field `patient_user_id`:
    ```json
    "list": { "enabled": true, "policy": { "any": [
      { "role": ["doctor", "nurse", "receptionist", "admin"] },
      { "owner": "patient_user_id" }
    ] } }
    ```
    For staff, the `role` branch is true before the query, so the list is unrestricted. For a patient, it becomes `WHERE patient_user_id = '<id>'`.
  </Step>
  <Step title="Receptionists book, but only for today or later">
    ```json
    "create": { "enabled": true, "policy": { "all": [
      { "role": ["receptionist", "admin"] },
      { "gte": ["$input.date", "$request.query.today"] }
    ] } }
    ```
    Clinical dates are better validated in a flow; this shows that shorthands mix freely with comparisons.
  </Step>
  <Step title="Clinical notes need a permission, not a role">
    ```json
    "get": { "enabled": true, "policy": "permission:records.read" },
    "update": { "enabled": true, "policy": { "permission": ["records.read", "records.write"] } }
    ```
    Doctors and nurses both get `records.read`; only doctors get `records.write`. Adding a *locum* role later means granting permissions, not editing policies.
  </Step>
  <Step title="Prescriptions need 2FA">
    ```json
    "create": { "enabled": true, "policy": ["mfa", "permission:prescriptions.issue"] }
    ```
  </Step>
  <Step title="The billing integration uses a scoped key">
    The billing partner's server gets a **publishable** key minted with the scope `partner:billing` and signs in as a service-account user with the `receptionist` role. The route policy:
    ```json
    { "all": [ { "role": "receptionist" }, { "scope": "partner:billing" } ] }
    ```
    If the key leaks, it's useless without the account's password; if the password leaks, it's useless without the key.
  </Step>
</Steps>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `{"role": "admin"}` refuses a user you just made admin | Their token was issued before the change | Sign in again or wait for refresh; revoke sessions for immediate effect |
| `permission` refuses a user whose role has `finance.*` | Only `*` is a wildcard for the shorthand | Grant `finance.read` explicitly |
| `owner` refuses the creator on update | The resource has no owner field, so the column was never set; or the client sent a different id on create | Add the owner field and backfill existing rows |
| `aal: aal2` always refuses | The user never enrolled in MFA, or signed in without a code | Enrol, then sign in with the TOTP step |
| `scope` refuses a key you think is unrestricted | Unrestricted keys have **no** scopes, so `scope` is false | Mint the key with the scope |
| Everything passes with a secret key | Secret keys bypass policies | Test with a publishable key and a user token |

## FAQ

<AccordionGroup>
  <Accordion title="Can I use a shorthand inside comparisons?">
    No. Shorthands are conditions, not values. Put them next to comparisons inside a group.
  </Accordion>
  <Accordion title="Are shorthands slower than writing the comparison myself?">
    No. They expand to the same comparisons once, before evaluation.
  </Accordion>
  <Accordion title="Can I add my own shorthand?">
    Not as new syntax. Define a named policy instead (`staff`, `family_access`) and reference it; that's the extension point.
  </Accordion>
  <Accordion title="Does role check organization roles?">
    No. `role` checks **environment** roles from Akountz. Organization roles (`owner`, `admin`, `member`, `viewer`) are per organization and arrive in org-scoped tokens as `$auth.org_role`. Check them with a comparison:
    ```json
    { "all": [ { "eq": ["$record.org_id", "$auth.org"] }, { "in": ["$auth.org_role", ["owner", "admin"]] } ] }
    ```
    See [organizations](/auth/organizations).
  </Accordion>
</AccordionGroup>
