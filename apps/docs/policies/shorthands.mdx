Most access rules are built from the same handful of questions: *is the caller signed in? do they have this role? do they own this row? are they using a server key?* **Shorthands** answer those in one key each. They're ordinary conditions under the hood: before evaluation, each shorthand **expands** into comparisons, so it combines freely with groups, comparisons and checks, and pushes down into SQL exactly like the conditions it stands for.

## Shorthands in Studio

Studio presents common shorthands as decisions rather than asking you to memorise JSON. In **Build → Policies** → **Who passes**, the **Rule** menu includes **Is signed in**, **Has role**, **Has permission**, **Owns the record (field)**, **Uses a secret key**, **Signed in with 2FA**, **Key has scope**, and **Caller kind is**. Those labels serialize to the shorthand keys in this reference.

When attaching a policy, the **Policy** picker presents the same ideas at a different level: its **Built-in** choices include **Anyone (public)**, **Signed-in users**, **Record owner (owner_id)**, **Signed in with 2FA**, **Secret keys & operators**, and **Nobody**. Its **More** group can create parameterised roles, permissions, owner fields, and scopes. Choose a named policy when the rule is a business boundary worth reusing; choose a parameterised form when one attachment is its only consumer and the parameter makes intent obvious.

## At a glance

| Shorthand | Argument | Expands to | Decided without the record? |
| --- | --- | --- | --- |
| `authenticated` | `true` / `false` | `eq($auth.authenticated, arg)` | Yes |
| `role` | a role, or a list (**any**) | `any(contains($auth.roles, r) for r)` | Yes |
| `permission` | a permission, or a list (**all**) | `all(any(contains($auth.permissions, p), contains($auth.permissions, "*")) for p)` | Yes |
| `owner` | a column name (default `owner_id`) | `all(authenticated, eq($record.<col>, $auth.user_id))` | No: it needs the record |
| `service` | `true` / `false` | `eq($credential.is_service, arg)` | Yes |
| `kind` | a principal kind | `eq($auth.kind, arg)` | Yes |
| `scope` | an API-key scope | `contains($credential.scopes, arg)` | Yes |
| `aal` | `"aal1"` / `"aal2"` | `eq($auth.aal, arg)` | Yes |

"Decided without the record" matters for lists: those shorthands are evaluated **before** the query, so they cost nothing per row and can make a list unrestricted (true) or refused (false) outright. See [pushdown](/policies/pushdown).

## `authenticated`

```json
{ "authenticated": true }
```

True when the request carries a **valid user access token** for this environment. Expired, malformed or foreign-environment tokens don't count; they're rejected with `401` before policies run.

```json
{ "authenticated": false }
```

True only for **anonymous** callers. It's rarely what you want in a policy, but it's useful for sign-up-style routes you want to hide from already-signed-in users, or in subscription conditions.

The built-in policy `authenticated` is exactly `{"authenticated": true}`.

<Note>
A request with a **secret key** and no token isn't "authenticated" in this sense, but it doesn't need to be: secret keys bypass policies entirely. `authenticated` is about people.
</Note>

The `authenticated` shorthand expands to `{"eq": ["$auth.authenticated", true]}`. Since `$auth.authenticated` is `true` only for valid user tokens (not for anonymous callers or service credentials), this shorthand is the cleanest way to require a signed-in user. The `false` variant (`{"authenticated": false}`) checks that the caller has no valid token, which is useful for routes that should only be accessible to anonymous users (like a sign-up form) or for subscription conditions that need to check for anonymous access.

It's important to understand that a request with a secret key and no user token is *not* "authenticated" in the `authenticated` shorthand's sense. However, secret keys bypass all policies before any condition is evaluated, so the `authenticated` check never actually runs for service credentials. This means `{"authenticated": true}` effectively means "any signed-in user with a valid access token, but service credentials are always allowed." If you need to restrict to human users only (excluding service credentials), use `{"all": [{"authenticated": true}, {"kind": "user"}]}`.

## `role`

```json
{ "role": "teacher" }
{ "role": ["admin", "principal"] }
```

True when the caller's `auth.roles` includes the role; with a list, **any** of them. Roles are defined per environment in Akountz and copied into every access token, so the check is a list lookup with no database query.

### Any, not all

A list means *any of these roles*, because that's nearly always the intent: "admins or principals may…". If you really need several roles at once, use an `all`:

```json
{ "all": [ { "role": "teacher" }, { "role": "form_tutor" } ] }
```

The distinction between "any of these roles" (a list to `role`) and "all of these roles" (an `all` of `role` conditions) is a common source of confusion. `{"role": ["admin", "teacher"]}` means "the caller is an admin OR a teacher." `{"all": [{"role": "admin"}, {"role": "teacher"}]}` means "the caller is both an admin AND a teacher." The latter is almost never what you want — it would only match a user who has been assigned both roles simultaneously.

The expansion for `{"role": ["admin", "principal"]}` is `{"any": [{"contains": ["$auth.roles", "admin"]}, {"contains": ["$auth.roles", "principal"]}]}`. This is evaluated by the `_shorthand` function in the engine, which converts the shorthand to its full condition before evaluation. The expansion happens at evaluation time, not storage time — what's stored is always the short form.

### Role vs permission

Roles describe **who someone is**; permissions describe **what they can do**. Checking roles is simple and reads naturally in small systems. Permissions scale better when roles multiply, because many roles can grant the same permission and the policy doesn't change when you add a role. See [permission](#permission) and [roles and permissions](/auth/roles-and-permissions).

For a small team with 5-10 roles, role checks are perfectly adequate and more readable. For a system with 20+ roles where the same permission might be granted to multiple roles (like "can view invoices"), permissions are more maintainable. You define the permission once and grant it to all relevant roles. When you add a new role that should also have that capability, you grant the permission, not edit policies.

### Parameterised form

Anywhere a policy reference is accepted, `"role:librarian"` is shorthand for `{"role": "librarian"}`:

```json
"operations": { "create": { "enabled": true, "policy": "role:librarian" } }
```

The parameterised form is resolved by the `PolicyEngine.resolve_ref` method. When it encounters a string containing a colon, it splits on the first colon and checks if the part before is a known shorthand kind (`role`, `permission`, `owner`, `scope`, `kind`). If so, it creates an inline policy from the shorthand.

## `permission`

```json
{ "permission": "reports.publish" }
{ "permission": ["finance.read", "finance.export"] }
```

True when the caller has the permission, **or the wildcard permission `*`**. With a list, the caller needs **all** of them, since that's the usual intent for capabilities ("may read *and* export").

Permissions come from the caller's roles plus any permissions granted directly to the user, and are copied into the token as `auth.permissions`.

### Naming permissions

Use a `resource.action` convention and grant broad ones with a trailing wildcard in role definitions:

| Role | Permissions |
| --- | --- |
| `admin` | `*` |
| `principal` | `students.*`, `reports.publish`, `finance.read` |
| `bursar` | `finance.*` |

<Warning>
Only the literal permission `*` is treated as a wildcard **by the shorthand**. A role holding `finance.*` does **not** automatically pass `{"permission": "finance.read"}`. Grant the specific permissions your policies check, or check the wildcard explicitly: `{"any": [{"permission": "finance.read"}, {"permission": "finance.*"}]}`.
</Warning>

This is a crucial detail that causes many bugs. The `permission` shorthand checks whether the exact permission string is in the caller's `auth.permissions` list. A role with `finance.*` grants the literal permission string `"finance.*"` to the user's token. When the policy checks `{"permission": "finance.read"}`, it looks for `"finance.read"` in the list, which isn't there (only `"finance.*"` is). To handle this, you must either grant the specific permission (`finance.read`) to the role, or check both: `{"any": [{"permission": "finance.read"}, {"permission": "finance.*"}]}`.

The `admin` role is special because `*` is in its permissions, which means `{"permission": "*"}` evaluates to `true` for any admin. This is how the wildcard works: it matches everything for that specific shorthand.

## `owner`

```json
{ "owner": "author_id" }
{ "owner": true }          // uses the owner_id column
```

True when the caller is signed in **and** the record's column equals the caller's user id. It expands to:

```json
{ "all": [
  { "authenticated": true },
  { "eq": ["$record.author_id", "$auth.user_id"] }
] }
```

The `authenticated` half matters: without it, an anonymous caller (whose `user_id` is `null`) would "own" every row whose column is `null`.

### Owner and owner fields

The `owner` shorthand is a **check**. A resource's **owner field** is a **write rule**: on create, the server sets that column to the caller's id. Use them together for private data:

```json
{ "name": "notes", "owner_field": "owner_id",
  "operations": {
    "list":   { "enabled": true, "policy": "owner" },
    "get":    { "enabled": true, "policy": "owner" },
    "create": { "enabled": true, "policy": "authenticated" },
    "update": { "enabled": true, "policy": "owner" },
    "delete": { "enabled": true, "policy": "owner" }
  } }
```

On updates, Pawabase also drops the owner field from the patch, so ownership can't be changed through the API even by the owner.

### Pushdown

For lists, `owner` becomes `WHERE <column> = '<your user id>'`. That's the fastest possible private list: an indexed equality, exact pages and exact totals.

The pushdown for `owner` is the reason it's the most widely used shorthand for private data. The expansion produces `{"all": [{"authenticated": true}, {"eq": ["$record.<col>", "$auth.user_id"]}]}`. The `authenticated` part is decided at plan time (true for signed-in users, false for anonymous). The `eq` part is pushed down because it's a single-level record path compared with `$auth.user_id` (a known value). For anonymous callers, the `authenticated` part evaluates to false at plan time, and the request is refused with `403` without any SQL.

## `service`

```json
{ "service": true }
```

True for **service credentials**: secret keys, and operators acting through Studio. The built-in `service` policy is exactly this.

Because service credentials bypass policies before any condition is evaluated, `{"service": true}` only makes a difference where the bypass doesn't apply: inside a flow's `policy.check` block (which receives the flow's own credential context), or as part of a larger condition you evaluate yourself. As an operation policy it effectively means *nobody except service credentials*, which is also what the built-in `deny` and a `null` resource policy do. Use `service` when you want that intent to read clearly.

Consider the scenarios where `service` is genuinely useful:

1. **Inside a flow's `policy.check`**: Flows can be triggered by HTTP routes where `auth` is the caller. A `policy.check` inside the flow can check `{"service": true}` to determine whether the flow is being called by a server (which might have broader access) or by a user.
2. **As a named policy for an internal route**: If you have a route that should only be called by your own servers (not by users), `service` makes that intent explicit in the policy definition.
3. **In a list of references**: `["service", "mfa"]` means "service credentials OR (mfa + whatever else)," though this is a rare combination.

The `service` shorthand expands to `{"eq": ["$credential.is_service", true]}`. Since the engine checks `credential.is_service` first in `PolicyEngine.check` and returns immediately if it's true (bypassing all policies), the `service` shorthand in a condition is primarily useful for cases where the bypass doesn't apply.

## `kind`

```json
{ "kind": "user" }
```

True when `$auth.kind` equals the argument. For people signed in with a token it's `user`; anonymous callers have kind `anonymous`; internal platform callers are `service` or `operator`. Use it to keep a route strictly for people, even if a future credential type is added.

Parameterised: `"kind:user"`.

The `kind` field in the context comes from the user's identity. For `Principal` objects, `kind` is stored as `self.kind` and comes from the token claims. The `policy_auth` function maps the principal's kind to `auth.kind`. For anonymous callers, `auth.kind` is `"anonymous"`.

`kind` is particularly useful when you want a policy that works regardless of what credential type might exist in the future. For example, `"kind": "user"` will always match human users, even if the platform adds a new credential type like `"service_account"` or `"api_key_user"`. Without `kind`, a policy designed for users might accidentally match a new credential type.

## `scope`

```json
{ "scope": "reports:export" }
```

True when the request's **API key** carries the scope. Key scopes are set when the key is created; an empty scope list means "unrestricted", and the shorthand is false in that case, because it asks whether this specific scope was **granted**.

Pawabase already enforces the built-in scopes (`resource:read`, `resource:write`, `routes:invoke`) before policies run. Use the `scope` shorthand for **your own** scopes:

```json
{ "all": [ { "authenticated": true }, { "scope": "partner:orders" } ] }
```

A partner integration then needs both a user token and a key minted with `partner:orders`.

Parameterised: `"scope:partner:orders"`.

The `scope` shorthand checks `contains($credential.scopes, arg)`. For unrestricted keys (empty scope list), `contains([], "partner:orders")` is `false`. This is intentional: an unrestricted key has *no specific scopes granted*, so asking "does this key have scope X?" returns `false`. If you want to check "does this key have any scope at all," use `{"exists": "$credential.scopes"}` — but in practice, unrestricted keys pass all other policy checks, so you usually don't need to check this.

The `scope` shorthand is the primary mechanism for **scoped integrations** — API keys that can only do specific things. A billing integration might get a key with `partner:billing` scope, and the policy checks `{"all": [{"role": "receptionist"}, {"scope": "partner:billing"}]}`. If the key leaks, it's useless without the account's password; if the password leaks, it's useless without the key.

## `aal`

```json
{ "aal": "aal2" }
```

True when the token's **authentication assurance level** matches. Tokens issued after a password, magic link or social sign-in carry `aal1`; after completing a TOTP or recovery-code challenge they carry `aal2`.

The built-in policy `mfa` is:

```json
{ "all": [ { "authenticated": true }, { "aal": "aal2" } ] }
```

Use it to protect money, deletions and role changes:

```json
"operations": { "delete": { "enabled": true, "policy": ["mfa", "role:admin"] } }
```

Users who haven't enrolled in MFA can't reach `aal2`, so pair these rules with a UI that invites them to enrol. See [MFA](/auth/mfa).

The `aal` field comes from the token claims. Akountz sets `aal` based on the authentication methods used during sign-in. A user who signed in with just a password has `aal1`; a user who also completed a TOTP challenge has `aal2`. The `aal` value is a snapshot — if a user enrolls in MFA after signing in, their existing token still has `aal1` until they sign in again.

For immediate MFA enforcement (rather than waiting for the token to refresh), you can check `auth.claims` directly in a custom policy, but the standard pattern is to require the user to sign in again to get an `aal2` token.

## Combining shorthands

Shorthands are conditions, so they nest anywhere:

```json
{ "any": [
  { "role": "admin" },
  { "all": [ { "role": "bursar" }, { "aal": "aal2" }, { "lte": ["$input.amount", 500000] } ] },
  { "all": [ { "owner": "requested_by" }, { "eq": ["$record.status", "draft"] } ] }
] }
```

"Admins always; bursars with 2FA for amounts up to 500,000; the requester while it's still a draft."

The `any` combinator means that if the caller is an admin, the entire condition is `true` and the request is allowed immediately (at plan time, before any SQL). For a bursar, the first branch is `false`, and the second branch is evaluated — it requires both `aal2` and the amount check. For the requester, the third branch applies.

This pattern of "admin override + role-specific rules + relationship rules" is the most common structure for complex policy sets. The admin branch is always first (cheapest to evaluate, and most decisive), followed by role-specific conditions, and finally relationship-based conditions that need the record.

## Parameterised references, in one table

Where a policy **reference** is expected (resource operations, routes, buckets, channels, `@function`), five shorthands have a string form:

| String | Same as |
| --- | --- |
| `role:admin` | `{"role": "admin"}` |
| `permission:reports.publish` | `{"permission": "reports.publish"}` |
| `owner:author_id` | `{"owner": "author_id"}` |
| `scope:partner:orders` | `{"scope": "partner:orders"}` |
| `kind:user` | `{"kind": "user"}` |

Only one argument fits in the string form. For role lists use the object form: `{"role": ["admin", "principal"]}`.

The parameterised string form is resolved by `PolicyEngine.resolve_ref`. The method splits the string on the first colon, checks if the prefix is a known shorthand kind, and creates an inline policy from the shorthand name and argument. This resolution happens **fresh on every request**: `resolve_ref` re-parses the string and builds a new `Policy` object each time it's called, and there is no caching layer in the engine at any level. The cost of this is negligible — string splitting and a dict construction — and the benefit is that a stored policy can be edited or a Python policy reloaded without anything needing to be invalidated.

## Choosing the right shorthand

<AccordionGroup>
  <Accordion title="Private data">
    `owner`, with an owner field on the resource.
  </Accordion>
  <Accordion title="Staff-only screens and endpoints">
    `role` with a list of staff roles, ideally wrapped in a named policy like `staff`.
  </Accordion>
  <Accordion title="Capabilities that many roles share">
    `permission`, so adding a role never requires editing policies.
  </Accordion>
  <Accordion title="Money, deletions, role changes">
    Add `aal: aal2` (or reference `mfa`) to whatever else the rule requires.
  </Accordion>
  <Accordion title="Partner and machine integrations">
    `scope` for your own scopes; built-in scopes are already enforced.
  </Accordion>
  <Accordion title="Server-only operations">
    Leave the resource operation's policy `null`, or reference `service`/`deny`. Your servers use a secret key.
  </Accordion>
  <Accordion title="User-only routes">
    `{"kind": "user"}` ensures that even if a new credential type is added, the route stays restricted to human users.
  </Accordion>
  <Accordion title="Conditional access based on organization">
    Combine `eq($record.org_id, $auth.org)` with `role` or `permission` for organization-scoped access.
  </Accordion>
</AccordionGroup>

## Compared with Supabase and Firebase

| Pawabase | Supabase (RLS) | Firebase (rules) |
| --- | --- | --- |
| `{"authenticated": true}` | `auth.role() = 'authenticated'` | `request.auth != null` |
| `{"owner": "user_id"}` | `auth.uid() = user_id` | `request.auth.uid == resource.data.userId` |
| `{"role": "admin"}` | custom claim in `auth.jwt()` or a roles table lookup | `request.auth.token.admin == true` (custom claims) |
| `{"permission": "x"}` | a permissions table + SQL function | custom claims |
| `{"aal": "aal2"}` | `auth.jwt()->>'aal' = 'aal2'` | not built in |
| `{"scope": "x"}` | not built in (API keys have no scopes) | not built in |

In Pawabase, roles and permissions are managed by Akountz and present in every token, so these checks need neither custom-claim plumbing nor database lookups.

## Shorthands in Studio

In the policy rule builder, each shorthand is a rule type with a plain-English label:

| Rule builder label | Shorthand | Input |
| --- | --- | --- |
| Is signed in | `authenticated` | yes / no (anonymous) |
| Has role | `role` | one role, or several separated by commas |
| Has permission | `permission` | one permission, or several separated by commas |
| Owns the record (field) | `owner` | the column name, default `owner_id` |
| Uses a secret key | `service` | — |
| Signed in with 2FA | `aal` | — (sets `aal2`) |
| Key has scope | `scope` | the scope |
| Caller kind is | `kind` | the kind |

In policy **pickers** (on resources, routes and buckets), the *More* group offers *Users with role…*, *Users with permission…*, *Owner via field…* and *Keys with scope…*, which store the parameterised string form (`role:librarian`).

## Worked scenarios: a clinic

To see how shorthands carry real requirements, here's the access model of a small clinic system, built almost entirely from shorthands.

**Roles:** `admin`, `doctor`, `nurse`, `receptionist`, `patient`.
**Permissions:** `records.read`, `records.write`, `prescriptions.issue`, `billing.manage`.

<Steps>
  <Step title="Patients see their own appointments">
    Resource `appointments` with owner field `patient_user_id`:
    ```json
    "list": { "enabled": true, "policy": { "any": [
      { "role": ["doctor", "nurse", "receptionist", "admin"] },
      { "owner": "patient_user_id" }
    ] } }
    ```
    For staff, the `role` branch is true before the query, so the list is unrestricted. For a patient, it becomes `WHERE patient_user_id = '<id>'`.
  </Step>
  <Step title="Receptionists book, but only for today or later">
    ```json
    "create": { "enabled": true, "policy": { "all": [
      { "role": ["receptionist", "admin"] },
      { "gte": ["$input.date", "$request.query.today"] }
    ] } }
    ```
    Clinical dates are better validated in a flow; this shows that shorthands mix freely with comparisons.
  </Step>
  <Step title="Clinical notes need a permission, not a role">
    ```json
    "get": { "enabled": true, "policy": "permission:records.read" },
    "update": { "enabled": true, "policy": { "permission": ["records.read", "records.write"] } }
    ```
    Doctors and nurses both get `records.read`; only doctors get `records.write`. Adding a *locum* role later means granting permissions, not editing policies.
  </Step>
  <Step title="Prescriptions need 2FA">
    ```json
    "create": { "enabled": true, "policy": ["mfa", "permission:prescriptions.issue"] }
    ```
  </Step>
  <Step title="The billing integration uses a scoped key">
    The billing partner's server gets a **publishable** key minted with the scope `partner:billing` and signs in as a service-account user with the `receptionist` role. The route policy:
    ```json
    { "all": [ { "role": "receptionist" }, { "scope": "partner:billing" } ] }
    ```
    If the key leaks, it's useless without the account's password; if the password leaks, it's useless without the key.
  </Step>
</Steps>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `{"role": "admin"}` refuses a user you just made admin | Their token was issued before the change | Sign in again or wait for refresh; revoke sessions for immediate effect |
| `permission` refuses a user whose role has `finance.*` | Only `*` is a wildcard for the shorthand | Grant `finance.read` explicitly |
| `owner` refuses the creator on update | The resource has no owner field, so the column was never set; or the client sent a different id on create | Add the owner field and backfill existing rows |
| `aal: aal2` always refuses | The user never enrolled in MFA, or signed in without a code | Enrol, then sign in with the TOTP step |
| `scope` refuses a key you think is unrestricted | Unrestricted keys have **no** scopes, so `scope` is false | Mint the key with the scope |
| Everything passes with a secret key | Secret keys bypass policies | Test with a publishable key and a user token |

## FAQ

<AccordionGroup>
  <Accordion title="Can I use a shorthand inside comparisons?">
    No. Shorthands are conditions, not values. Put them next to comparisons inside a group.
  </Accordion>
  <Accordion title="Are shorthands slower than writing the comparison myself?">
    No. They expand to the same comparisons once, before evaluation.
  </Accordion>
  <Accordion title="Can I add my own shorthand?">
    Not as new syntax. Define a named policy instead (`staff`, `family_access`) and reference it; that's the extension point.
  </Accordion>
  <Accordion title="Does role check organization roles?">
    No. `role` checks **environment** roles from Akountz. Organization roles (`owner`, `admin`, `member`, `viewer`) are per-organization and arrive in org-scoped tokens as `$auth.org_role`. Check them with a comparison:
    ```json
    { "all": [ { "eq": ["$record.org_id", "$auth.org"] }, { "in": ["$auth.org_role", ["owner", "admin"]] } ] }
    ```
    See [organizations](/auth/organizations).
  </Accordion>
  <Accordion title="Does the `service` shorthand work on resource operations?">
    Technically yes, but it's redundant. Service credentials bypass all resource operation policies entirely, so `{"service": true}` on a resource operation is functionally equivalent to `null` (secret keys only) or `deny`. Use `service` when you want the intent to be explicit, or inside flows where the bypass doesn't apply.
  </Accordion>
  <Accordion title="Can I combine `role` and `permission` in the same condition?">
    Yes, freely. `{"any": [{"role": "admin"}, {"permission": "reports.publish"}]}` means "admins or anyone with the reports.publish permission." This is a common pattern for systems where some users have roles and others have direct permissions.
  </Accordion>
</AccordionGroup>

## Deep dives: each shorthand in a realistic system

The scenarios above show shorthands one at a time. Real projects lean on all eight together, and the interesting decisions are usually at the edges: what happens when a role is renamed, what a scope-only integration can and can't do, what an `aal2` requirement means for a support workflow. This section works through each shorthand once more, this time all the way to the edge cases.

### `authenticated`, in depth

`authenticated` looks like the simplest shorthand, but it's worth being precise about what it does and doesn't cover, because it's the shorthand every other private-data rule builds on.

**Scenario: a newsletter sign-up form that should disappear once you've subscribed.**

A marketing site has a resource `subscribers` with an owner field `user_id`, and a route `POST /newsletter/subscribe`. The product requirement is: signed-out visitors see the sign-up form; signed-in subscribers see "you're on the list" instead. The route itself doesn't need a policy change for this — that's a frontend concern, decided by whether the client has a token — but the **API** still needs to refuse a duplicate subscribe:

```json
// subscribers.create
{ "all": [
  { "authenticated": true },
  { "not": { "exists": "$record.id" } }
] }
```

That second clause doesn't make sense as written (a new record never has an id yet), which is exactly the kind of mistake `authenticated` alone won't catch — the real duplicate check belongs in a **unique index** on `user_id`, with the policy simply being `authenticated`. The lesson: `authenticated` answers "is anyone signed in", never "has this specific thing already happened." Reach for a database constraint or a flow's `control.if` for the latter.

**Scenario: hiding a route from signed-in users entirely.**

A "claim your account" route should only work for a token that doesn't exist yet, because a signed-in user has nothing to claim:

```json
{ "method": "POST", "path": "/accounts/claim", "policy": { "authenticated": false }, "…": "…" }
```

A signed-in caller hitting this route gets a `403` from the policy, before the handler ever runs a lookup on the claim code. Without this guard, a signed-in user could accidentally (or maliciously) claim an account that isn't theirs while still authenticated as themselves, and the handler would need to defend against that itself. Putting the check in the policy means it can never be forgotten when the route is edited later.

**Edge case: what `authenticated` does *not* protect you from.**

`{"authenticated": true}` says nothing about *which* user, only that there is one. A resource with `list` → `authenticated` and no further condition returns **every row in the table** to every signed-in user — it is not a private-data policy by itself. This is the single most common mistake teams make when they're moving fast: they set `authenticated` intending "logged-in users see their own stuff" and get "logged-in users see everyone's stuff." If the resource is meant to be private, `authenticated` is a floor, not the whole rule — it belongs inside an `all` with an ownership or tenancy comparison, or you reach for the `owner` shorthand directly.

### `role`, in depth

**Scenario: renaming a role without breaking policies.**

A project ships with a role called `staff`, referenced from a dozen policies as `{"role": "staff"}`. Eighteen months later, the team splits `staff` into `teaching_staff` and `support_staff` because the two groups need different access. Renaming or splitting a role in Akountz does **not** automatically update policy conditions — `role` checks a literal string against `auth.roles`, and the policy JSON still says `"staff"`. After the split, every policy still checking `{"role": "staff"}` refuses everyone, because nobody carries that role anymore.

The safe sequence:

<Steps>
  <Step title="Add the new roles alongside the old one">
    Create `teaching_staff` and `support_staff` in Akountz, and grant them to the right users, **without removing** `staff` yet.
  </Step>
  <Step title="Widen the policies first">
    Change `{"role": "staff"}` to `{"role": ["staff", "teaching_staff", "support_staff"]}` everywhere it's used. Anyone with any of the three roles now passes.
  </Step>
  <Step title="Remove the old role from users">
    Once every user has one of the two new roles, remove `staff` from their role assignments.
  </Step>
  <Step title="Narrow the policies">
    Change the widened `role` lists to just the two new roles, or split the policy into `teaching_staff`-only and `support_staff`-only variants where access actually differs.
  </Step>
</Steps>

Skipping the widen step (going straight from `"staff"` to `["teaching_staff", "support_staff"]` in one deploy, before users are reassigned) locks everyone out between the policy change and the role reassignment.

**Scenario: a role that exists in the token but shouldn't grant access here.**

A school project has a `parent_portal_beta` role used only to gate a frontend feature flag — it's not meant to be a policy input at all. Nothing stops someone from referencing `{"role": "parent_portal_beta"}` in a policy by mistake, and it would work exactly like any other role check. The distinction between "roles that are UI feature flags" and "roles that are access-control facts" is not enforced by the platform; it's a convention your team has to keep. A `description` on every policy, and a naming convention (`*_beta`, `*_flag` for UI-only roles) makes the difference visible in Studio's pickers.

### `permission`, in depth

**Scenario: two permissions that sound related but aren't.**

A finance module defines `invoices.read` and `invoices.export`. A support engineer is granted `invoices.read` so they can help customers with billing questions, but not `invoices.export`, because exports include bank details in bulk. A policy written as:

```json
{ "permission": "invoices.read" }
```

correctly admits the support engineer to `GET /invoices` and `GET /invoices/{id}`, but a **separate** route `POST /invoices/export` must check `{"permission": "invoices.export"}` — not `invoices.read` — or the separation is meaningless. This sounds obvious in the abstract, but the common bug is copy-pasting the read policy onto the export route and changing only the resource name, forgetting that export is a materially different capability.

**Scenario: an "any of several permissions" requirement.**

A dashboard route should be visible to anyone with at least one reporting permission, not all of them:

```json
{ "any": [
  { "permission": "reports.finance" },
  { "permission": "reports.attendance" },
  { "permission": "reports.enrollment" }
] }
```

This is **not** the same as `{"permission": ["reports.finance", "reports.attendance", "reports.enrollment"]}`, which requires all three. Get this backwards and either everyone with just one reporting permission is locked out (if you meant `any` but wrote the list form), or everyone with just one reporting permission gets the dashboard anyway when you meant to require all three for a "senior report viewer" tier (if you meant the list form but wrote `any`). Read the requirement in plain English before choosing the shape: "any of" is `any` of single-permission conditions; "all of" is the list form (or an explicit `all`, which is equivalent but more verbose).

**Scenario: the wildcard trap surfacing in an audit.**

A compliance review asks "who can export finance records?" The obvious query is "which roles have `finance.export`?" — but if any role has been granted the literal permission `*` (as `admin` typically is), that role's holders can also export, and they won't show up in a search for `finance.export` specifically. When auditing permission-based policies, always check for `*` holders separately: `{"any": [{"permission": "finance.export"}, {"permission": "*"}]}` is the actual admitted set, not just `{"permission": "finance.export"}`.

### `owner`, in depth

**Scenario: an owner field that used to be nullable.**

A `documents` resource originally allowed anonymous uploads (a public drop-box feature), so `owner_id` is nullable and old rows have `owner_id = null`. After the feature is retired and every new document requires sign-in, someone adds `"policy": "owner"` to `get` and `update`. The old anonymous rows, with `owner_id = null`, become **permanently inaccessible** through the API: no signed-in user's `$auth.user_id` will ever equal `null` (the `authenticated` half of `owner`'s expansion also rules out anonymous callers seeing them). This is usually the *correct* outcome from a security standpoint — nobody should "own" an anonymous upload — but it surprises teams who expected old data to still be reachable. If those documents need to stay reachable, backfill `owner_id` to a service account or an admin's id before switching the policy over, or add an explicit branch: `{"any": [{"owner": "owner_id"}, {"all": [{"not": {"exists": "$record.owner_id"}}, {"role": "admin"}]}]}`.

**Scenario: two owner-like fields on the same resource.**

A `swap_requests` resource in a scheduling app has both `requested_by` and `requested_with` — either party should be able to view and cancel the request, but neither should be able to unilaterally approve it:

```json
// view_or_cancel
{ "any": [ { "owner": "requested_by" }, { "owner": "requested_with" } ] }
```

```json
// approve: only the *other* party may approve
{ "all": [
  { "authenticated": true },
  { "eq": ["$record.requested_with", "$auth.user_id"] },
  { "not": { "eq": ["$record.requested_by", "$auth.user_id"] } }
] }
```

The `approve` policy can't be written as a single `owner` shorthand because "the other party, not this one" isn't an ownership check — it's a relationship check that happens to look similar. This is a good signal for when to stop reaching for `owner` and write the comparison directly.

### `service`, in depth

**Scenario: a route deliberately restricted to your own backend, called from a flow.**

An internal route `POST /internal/recompute-balances` should only ever be triggered by a nightly schedule flow, never by a client, even an admin client. Marking its policy `"service"` makes that explicit:

```json
{ "method": "POST", "path": "/internal/recompute-balances", "policy": "service", "…": "…" }
```

Since service credentials bypass the policy engine before any condition runs, this is functionally identical to leaving the route's policy `null`... except `null` on a **custom route** defaults to `authenticated`, not to service-only (see the [enforcement-points defaults table](/policies/enforcement-points#defaults-at-a-glance)). Writing `"service"` explicitly is the only way to get "service credentials only" on a route — you cannot get that behavior by omission the way you can on a resource operation. This is one of the few places where `service` is not redundant but load-bearing.

**Scenario: telling apart a user-triggered flow run from an operator's manual re-run.**

A refund-processing flow can be triggered two ways: a route that customers hit (`policy: "authenticated"`), and a "re-run failed refund" button in Studio that an operator clicks directly on a failed flow run. Inside the flow, a `policy.check` on `{"service": true}` distinguishes the two, because Studio's manual re-run passes an operator credential while the route passes the customer's token:

```text
policy.check {"service": true}
  allowed (operator re-run): control.if skip_duplicate_notification = true
  denied (customer-triggered): continue normally, send the customer a status email
```

This is the scenario the `service` shorthand exists for: everywhere else, the bypass makes the check moot, but inside a flow's own `policy.check`, the flow's caller context is exactly what's being examined, and the bypass rule doesn't apply to that block.

### `kind`, in depth

**Scenario: preparing for a credential type that doesn't exist yet.**

A platform roadmap includes a future "service account" login flow — a non-human identity that signs in with a long-lived token but should be treated differently from both regular users and secret-key servers for a specific reporting route. Writing the route's policy today as `{"kind": "user"}` rather than `{"authenticated": true}` means that when service accounts ship and get their own `auth.kind` value (say, `service_account`), this route continues to admit only humans without any change — a plain `authenticated` check would have started admitting service accounts too, since they'd carry valid tokens.

**Scenario: distinguishing anonymous from unauthenticated.**

A publishable key with no token produces `auth.kind = "anonymous"`, not an absence of `auth` — the context always has an `auth` object, even for anonymous callers. `{"kind": "anonymous"}` is occasionally useful for a policy that behaves differently for browsing-without-an-account versus a signed-in session, such as showing a "sign in to save this" prompt via a `403` with a specific reason on an otherwise-public route:

```json
{ "any": [ { "kind": "user" }, { "kind": "anonymous" } ] }
```

is equivalent to `public`, included here only to show that `kind` can express the same thing verbosely — the real value of `kind` is in *excluding* a specific caller type, not including all of them.

### `scope`, in depth

**Scenario: two integrations, two scopes, one route.**

A logistics partner reads order data (`scope: "logistics:read"`) and a payments processor writes refund confirmations (`scope: "payments:write"`). Both hit the same webhook-acknowledgement route, but should be authorized differently depending on which scope their key carries:

```json
{ "any": [
  { "all": [ { "scope": "logistics:read" }, { "in": ["$input.type", ["ship", "deliver"]] } ] },
  { "all": [ { "scope": "payments:write" }, { "eq": ["$input.type", "refund_ack"]} ] }
] }
```

A logistics key attempting to send a `refund_ack` is refused, even though it's a valid key with a valid scope — just not the scope this input type requires. This pattern (scope decides *which branch*, not just *whether to allow*) is common once an integration surface has more than one partner.

**Scenario: scope creep from reusing a key.**

A team mints one publishable key with `scope: ["partner:orders", "partner:invoices"]` and hands it to a single partner who only integrates with orders today. Six months later, a second, unrelated partner is onboarded and — to save a step — given the *same* key. Now both partners can read invoices, because the scope check only asks "does this key have the scope," not "does this key belong to the partner asking." Scopes authorize a **key**, not an **organization**; if partners must be isolated from each other, each needs its own key, and the policy should additionally check a partner identifier carried on the record or in a service-account role, not scope alone.

### `aal`, in depth

**Scenario: requiring 2FA for a specific field, not the whole operation.**

A `users` resource lets any signed-in user update their own profile, but changing the registered email address should require `aal2`:

```json
// update
{ "any": [
  { "all": [ { "owner": "id" }, { "not": { "exists": "$input.email" } } ] },
  { "all": [ { "owner": "id" }, { "aal": "aal2" } ] }
] }
```

"Owner, and not touching email" **or** "owner, with 2FA" — either branch admits the update, but only the second covers a request that includes `email` in the patch. A request that changes `email` without `aal2` fails the first branch (because `$input.email` exists) and fails the second (no `aal2`), so it's refused; a request changing only `display_name` passes the first branch immediately.

**Scenario: session freshness versus assurance level.**

`aal` reflects **how** you signed in, not **when**. A user who authenticated with TOTP three months ago and has a long-lived refresh token still carries `aal2` today, even though the "moment" of proving the second factor is long past. If a workflow needs "confirmed 2FA in this session, recently" rather than "this token's aal claim says aal2," `aal` alone isn't enough — that's a step-up re-authentication flow at the application layer (prompting for the TOTP code again before a sensitive action), which Akountz supports but which isn't expressed as a policy condition. Don't try to encode a time window against `aal` in a policy; there's no timestamp on when the second factor was verified, only the resulting level on the current token.

## Shorthand implementation in the engine

The `_shorthand` function in `pawabase_kit/policies/engine.py` implements the expansion for all eight shorthands. Each shorthand maps to a specific condition:

```python
def _shorthand(op: str, arg: Any, context: Mapping[str, Any]) -> Condition:
    if op == "authenticated":
        return {"eq": ["$auth.authenticated", bool(arg)]}
    if op == "role":
        roles = arg if isinstance(arg, list) else [arg]
        return {"any": [{"contains": ["$auth.roles", role]} for role in roles]}
    if op == "permission":
        perms = arg if isinstance(arg, list) else [arg]
        return {
            "all": [
                {
                    "any": [
                        {"contains": ["$auth.permissions", p]},
                        {"contains": ["$auth.permissions", "*"]},
                    ]
                }
                for p in perms
            ]
        }
    if op == "owner":
        column = arg if isinstance(arg, str) else "owner_id"
        return {"all": [{"authenticated": True}, {"eq": [f"$record.{column}", "$auth.user_id"]}]}
    if op == "service":
        return {"eq": ["$credential.is_service", bool(arg)]}
    if op == "kind":
        return {"eq": ["$auth.kind", arg]}
    if op == "scope":
        return {"contains": ["$credential.scopes", arg]}
    if op == "aal":
        return {"eq": ["$auth.aal", arg]}
    raise PolicyError(f"unknown shorthand {op!r}")
```

The `permission` expansion is the most complex because it implements the "all of" semantics for lists while also checking the wildcard `*`. For `{"permission": ["finance.read", "finance.export"]}`, the expansion creates an `all` of two sub-conditions, each of which is an `any` checking whether the permission or the wildcard is in the caller's permissions. This means the caller needs both `finance.read` AND `finance.export` (or `*`), which is the correct semantics for "the caller needs all of these permissions."

For the `role` expansion, the `any` combinator means that having *any* of the listed roles is sufficient. This is the standard "any of these roles" pattern. The `contains` check uses id normalisation, so `contains(["admin", "teacher"], "admin")` is `true` and `contains(["admin", "teacher"], 1)` is also `true` (because `"1"` normalizes to `"1"` and `"admin"` doesn't match `1` — actually, `"1"` in `["admin", "teacher"]` is `false` because `"1" != "admin"`).

The `owner` expansion always includes `{"authenticated": True}` (note: Python's `True`, not the condition form — it's wrapped in the `all`). This is because the `_shorthand` function returns a condition object, and `{"authenticated": True}` is a boolean condition that's always `true` for authenticated callers. Without it, the `owner` check would pass for anonymous callers whose `user_id` is `null` and whose record's owner field is also `null`.

### No caching, anywhere

Shorthand expansion is **not cached anywhere**. When the `evaluate` function encounters a shorthand, it calls `_shorthand` to get the full condition, then recursively calls `evaluate` on the result — every single time the condition is checked, for every request and every row. There is no memoisation of the expansion, no cache of resolved `Policy` objects keyed by reference string, and no cache of decisions keyed by context. `_shorthand` is a pure function (no side effects, no I/O) that runs in microseconds, so re-deriving the same expansion on every call is cheap enough that caching it would add complexity without a measurable benefit. It also means a shorthand's behaviour can never go stale within a request: `{"role": ["admin", "principal"]}` expands the same way whether it's the first condition evaluated in a cold process or the millionth in a long-running one, and there's no cache to invalidate when a stored policy, a Python policy, or an environment's role definitions change. The thing that does get rebuilt on change is the environment's **compiled configuration** (which policies exist, what they're named) — that's a version-driven recompilation of the whole environment, not a cache inside the policy engine itself, and it's covered in [references](/policies/references#promotion-and-environments).

## Composing shorthands with full condition objects

Every example so far nests shorthands inside `all`/`any`/`not`, but shorthands also mix freely with the raw comparison and check operators from the [condition language](/policies/conditions) and [operators](/policies/operators) reference. The rule of thumb: a shorthand is just another condition object, so anywhere a condition is expected, a shorthand fits.

### Shorthand + comparison, in one `all`

**Scenario: a discount code that only staff may apply, and only below a cap.**

```json
{ "all": [
  { "role": ["cashier", "manager"] },
  { "lte": ["$input.discount_percent", 25] },
  { "any": [ { "role": "manager" }, { "lte": ["$input.discount_percent", 10] } ] }
] }
```

Cashiers may apply up to 10%; managers up to 25%. The outer `role` check gates the operation to staff at all; the numeric `lte` caps it hard at 25% for anyone; the inner `any` narrows further for non-managers. Three shorthands and comparisons, one readable rule.

### Shorthand + `exists`/`empty` for conditional requirements

**Scenario: an update that's free-form for admins but must include a reason for everyone else.**

```json
{ "any": [
  { "role": "admin" },
  { "all": [ { "authenticated": true }, { "not": { "empty": "$input.reason" } } ] }
] }
```

`empty` (from the [operators](/policies/operators) list) checks for a missing or blank value; combined with `authenticated` this reads as "any signed-in user, provided they filled in a reason." Admins skip the requirement entirely via the first branch.

### Shorthand + `matches` for format constraints as authorization

**Scenario: only allow writes where the input's category matches an allowed prefix, scoped by role.**

```json
{ "any": [
  { "role": "admin" },
  { "all": [ { "role": "editor" }, { "matches": ["$input.category", "^public-"] } ] }
] }
```

Editors may only create content in categories beginning with `public-`; admins have no such restriction. This isn't a validation rule (validation happens earlier, against the schema) — it's a business rule about *who* may write *what*, which is exactly what policies are for even when the check looks like a format constraint.

### A composed policy end to end: a library system

Pulling several shorthands and comparisons together for a `loans` resource in a library system, with roles `librarian`, `admin`, and an ordinary `patron`:

```json
// loans.update — librarians manage any loan; patrons may only renew their own,
// and only if it isn't already overdue, and never more than twice
{ "any": [
  { "role": ["librarian", "admin"] },
  { "all": [
    { "owner": "patron_user_id" },
    { "eq": ["$record.status", "active"] },
    { "lt": ["$record.renewal_count", 2] },
    { "eq": ["$input.due_date", null] },
    { "not": { "eq": ["$record.status", "overdue"] } }
  ] }
] }
```

Reading it as a sentence: "librarians and admins may update any loan; a patron may update their own loan if it's active, has been renewed fewer than two times, isn't overdue, and the update doesn't try to set `due_date` directly" (renewal logic computes the new due date server-side, in a flow, rather than trusting a client-supplied date). Every clause here is either a shorthand (`role`, `owner`) or a plain comparison — no Python policy needed, and because the `role` branch is decided at plan time, librarians get an unrestricted list while patrons get a residual on their own loans.

## Common combinations, as a lookup table

A cheat-sheet for translating a requirement in English into a shorthand combination:

| Requirement | Condition |
| --- | --- |
| Anyone signed in | `{"authenticated": true}` |
| Only anonymous callers | `{"authenticated": false}` |
| Exactly this role | `{"role": "librarian"}` |
| Any of several roles | `{"role": ["librarian", "admin"]}` |
| All of several roles at once (rare) | `{"all": [{"role": "a"}, {"role": "b"}]}` |
| Has this one capability | `{"permission": "reports.publish"}` |
| Has this capability, or is an admin | `{"any": [{"permission": "reports.publish"}, {"permission": "*"}]}` |
| Owns the row (default column) | `{"owner": true}` or the built-in `"owner"` |
| Owns the row (named column) | `{"owner": "author_id"}` |
| Owner or staff | `{"any": [{"owner": "author_id"}, {"role": "staff"}]}` |
| A server, never a person | `{"service": true}`, or `null` on a resource operation |
| A human, even future credential types | `{"kind": "user"}` |
| This API key was minted for a partner | `{"scope": "partner:orders"}` |
| Signed in with a second factor | `{"aal": "aal2"}`, or the built-in `"mfa"` |
| Staff, with 2FA, for a sensitive action | `{"all": [{"role": "admin"}, {"aal": "aal2"}]}`, or `["mfa", "role:admin"]` |
| Owner, but not while archived | `{"all": [{"owner": "author_id"}, {"eq": ["$record.archived", false]}]}` |
| Admin overrides everything else | `{"any": [{"role": "admin"}, <everything else>]}` |

## Anti-patterns

A short list of shorthand mistakes that pass code review but fail in production:

<AccordionGroup>
  <Accordion title="Writing owner's expansion by hand and forgetting `authenticated`">
    `{"eq": ["$record.owner_id", "$auth.user_id"]}` alone passes for an anonymous caller on a row with a `null` owner_id, because `null == null` is `true` for `eq`. Use the `owner` shorthand, which includes the `authenticated` guard, rather than reimplementing it.
  </Accordion>
  <Accordion title="Treating role lists as AND">
    `{"role": ["admin", "editor"]}` is "admin or editor," never "admin and editor." If a policy that should admit two different groups is refusing everyone, this is the first thing to check.
  </Accordion>
  <Accordion title="Assuming a role wildcard covers `permission`">
    A role granted `finance.*` does not pass `{"permission": "finance.read"}`. Only the literal string `*` is treated as a wildcard by the shorthand.
  </Accordion>
  <Accordion title="Checking `scope` on an unrestricted key and expecting `true`">
    An unrestricted key (no scopes set) fails every `scope` check, by design — it has no *specific* scopes granted, even though it can do everything the endpoint's built-in scope allows.
  </Accordion>
  <Accordion title="Expecting `aal` to reflect a fresh, in-session second factor">
    `aal` is a property of the current token, set once at sign-in. It doesn't expire mid-session and it doesn't retroactively upgrade when a user enrols in MFA later — they need a fresh sign-in for their token to carry `aal2`.
  </Accordion>
  <Accordion title="Using `service` on a resource operation and expecting anything beyond the default">
    A resource operation with `policy: null` already means secret keys and operators only. Writing `"service"` there is harmless but adds nothing — the two are equivalent for resource operations specifically (this is not true for routes, where `null` means `authenticated`).
  </Accordion>
</AccordionGroup>
