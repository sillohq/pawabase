## How to use these recipes

Each recipe states a requirement, gives the resource shape and the policies, shows **what was run and what came back**, and names the trap that a naive version falls into. The traps are the point. Most access rules are easy to write and easy to write slightly wrong, and the wrong version usually works for the people you tested with.

Every recipe was run against a real API with tokens for the callers named, unless it says it was not. Results are quoted as they came back, with the policy name in refusals (`policy 'org_admin' refused`).

Three habits apply to all of them:

- **Test as the callers you fear**, never with a secret key, which passes before the policy is read.
- **Test the rows you forgot**: a row with no owner, a user with no organisation, a record with `null` in each column the policy reads.
- **Read the status as well as the body.** A `404` where you expected `403` is information.

## Private data

**Requirement.** Each signed-in user sees and edits only their own rows.

**Shape.** An `owner_field` of `owner_id` (or `user_id`), which stamps the caller's id on `create` and keeps clients from changing it.

| Operation | Policy |
| --- | --- |
| `create` | `authenticated` |
| `list`, `get`, `update`, `delete` | `owner:owner_id` |

**Run.** Two users each created a note, then:

| Request | Answer |
| --- | --- |
| `u-1` lists | Only `u-1`'s note, `total: 1` |
| `u-2` lists | Only `u-2`'s note |
| `u-1` gets `u-2`'s note | `404`, `Not found` |
| Signed out lists | `401` |
| `u-1` `PATCH`es `u-2`'s note | `403`, `policy 'owner:owner_id' refused` |

**The trap.** Writing the ownership as a bare `eq`:

```json
{ "eq": ["$record.owner_id", "$auth.user_id"] }
```

lets a **signed-out** caller read, change and delete any row whose owner is `null`. This was run: the anonymous `GET` returned the unowned row, the `PATCH` changed its title, and the `DELETE` removed it. The shorthand `owner:owner_id` includes `{"authenticated": true}` and does not have the problem. See [Shorthands](/policies/shorthands#owner).

**Also.** `owner_field` alone does not restrict reads. A resource with an `owner_field` and `authenticated` on `list` let every signed-in user see every note. And the built-in `owner` policy is hard-wired to the column `owner_id`: on a resource whose owner field is `user_id` it failed (`create` `403`, `list` `400`), so write `owner:user_id`.

## Multi-tenancy

**Requirement.** Members of an organisation see and change only that organisation's rows, and cannot create rows in, or move rows to, another organisation.

**Shape.** An `org_id` column on every tenant table, and users whose token carries an `org`.

| Policy | Condition |
| --- | --- |
| `same_org` | `{"all": [{"exists": "$auth.org"}, {"eq": ["$record.org_id", "$auth.org"]}]}` |
| `create_in_own_org` | `{"all": [{"exists": "$auth.org"}, {"eq": ["$input.org_id", "$auth.org"]}]}` |

| Operation | Policy |
| --- | --- |
| `list`, `get`, `update` | `same_org` |
| `create` | `create_in_own_org` |
| `delete` | `org_admin` (below) |

**Run.** Members of `acme-co` and `beta-co`, and a user with no organisation:

| Request | Answer |
| --- | --- |
| `acme-co` member creates a task in `acme-co` | `201` |
| `acme-co` member creates a task in `beta-co` | `403`, `policy 'create_in_own_org' refused` |
| A user with **no organisation** creates a task | `403`, `policy 'create_in_own_org' refused` |
| `acme-co` admin lists | Only `acme-co`'s task, `total` 1 |
| `beta-co` owner lists | Only `beta-co`'s task |
| A user with **no organisation** lists | `403`, `policy 'same_org' refused` (refused by the plan, before any query) |
| `beta-co` gets an `acme-co` task | `404`, `Not found` |
| `beta-co` `PATCH`es an `acme-co` task | `403` (it exists, so it is not a `404`) |

The `list` for a user with no organisation is the plan at work: `$auth.org` is empty, so `exists` is false and no row could ever match.

**The traps.**

1. **Updating the tenant.** `same_org` on `update` checks only the existing row, so an `acme-co` member who sent `PATCH {"org_id": "beta-co"}` for their own task got `200`. They lost access to it (`404`) and a `beta-co` member gained it. Pin the tenant on update too:

```json
{
  "all": [
    { "exists": "$auth.org" },
    { "eq": ["$record.org_id", "$auth.org"] },
    { "any": [
      { "not": { "exists": "$input.org_id" } },
      { "eq": ["$input.org_id", "$auth.org"] }
    ] }
  ]
}
```

2. **The null tenant.** Without `{"exists": "$auth.org"}`, a user with no organisation compares `null` with the `org_id` of every row that has none, and passes.
3. **The wrong path.** `$auth.org_id` does not exist. Studio suggests it. The key is `$auth.org`.

An `update` guard written this way can still be passed by `{"org_id": null}`: `exists` is false for `null`, so `not exists` is true. A resource's `nullable: false` does **not** stop this (a `PATCH` accepts `null` for every field), so use a [Python policy](/policies/python-policies) that checks `"org_id" in context["input"]`, or reject the change in a route. See [the overview](/policies/overview#exists-is-false-for-null-so-not-exists-allows-nulling).

### Roles inside an organisation

**Requirement.** Anyone in the organisation may read, but only owners and admins of it may delete.

```json
{
  "all": [
    { "exists": "$auth.org" },
    { "eq": ["$record.org_id", "$auth.org"] },
    { "in": ["$auth.org_role", ["owner", "admin"]] }
  ]
}
```

attached to `delete` as `org_admin`. **Run:** a `member` got `403`, `policy 'org_admin' refused`; an `admin` of the same organisation got `204`. The role in the organisation is `$auth.org_role`, which is not the same as the project-wide `$auth.roles` that the `role` shorthand reads.

## Publishing workflow

**Requirement.** Anyone can read **published** posts. Authors read and edit their own drafts. Editors can see and publish everything. An author cannot publish their own post.

**Shape.** A `status` column, an `author_id` owner field.

| Policy | Condition |
| --- | --- |
| `can_read_post` | `{"any": [{"eq": ["$record.status", "published"]}, {"eq": ["$record.author_id", "$auth.user_id"]}, {"role": "editor"}]}` |
| `can_create_post` | `{"any": [{"role": "editor"}, {"all": [{"authenticated": true}, {"ne": ["$input.status", "published"]}]}]}` |
| `can_update_post` | `{"any": [{"role": "editor"}, {"all": [{"eq": ["$record.author_id", "$auth.user_id"]}, {"ne": ["$input.status", "published"]}]}]}` |

| Operation | Policy |
| --- | --- |
| `list`, `get` | `can_read_post` |
| `create` | `can_create_post` |
| `update` | `can_update_post` |

**Run.**

| Request | Answer |
| --- | --- |
| Author creates a draft | `201` |
| Author creates a post with `status: "published"` | `403`, `policy 'can_create_post' refused` |
| Author creates a post with **no status** | `201` (`ne` is true for a missing value) |
| Editor creates a published post | `201` |
| Signed out lists | Only the published post |
| The author lists | Their drafts and every published post |
| Another author lists | Only the published post |
| An editor lists | Everything |
| Author `PATCH`es their draft to `published` | `403`, `policy 'can_update_post' refused` |
| Author edits their draft's title | `200` |
| Editor publishes the author's draft | `200` |
| Signed out gets the now-published post | `200` |

**The traps.**

- **A post with no status is not published**, because the status is `null`, which is not `"published"`. But it is also not **protected**: the author may submit no status. Give the column a default (`draft`), so a missing value is the safe one.
- **`can_read_post` is not pushable.** It is an `any` of two record conditions, so the list has a residual: `total` is `null`, pages are short, and **`?select=` can bypass it**. See [SQL pushdown](/policies/pushdown#a-select-can-walk-around-a-residual). For a list that must be safe, use the flag design below.

### The same workflow, pushable

Add a boolean `public`, set to `true` when a post is published, and serve the two audiences from two lists:

| List | Policy | Why |
| --- | --- | --- |
| Public posts | `{"eq": ["$record.public", true]}` on one resource, or route | A SQL filter. Exact `total`, full pages, immune to `select` |
| My posts | `owner:author_id` on a second resource over the table, or a route | A SQL filter |

The client asks for the list it needs. An editor's "everything" is a route for staff.

## Soft delete

**Requirement.** Deleted rows disappear for everyone, but stay in the table.

**Shape.** A boolean `deleted`, default `false`, and `update` to set it. Do not enable `delete`.

| Policy | Condition |
| --- | --- |
| `live_rows` | `{"eq": ["$record.deleted", false]}` |
| `not_banned` | `{"not": {"role": "banned"}}` |

`list` and `get` take `["not_banned", "live_rows", "authenticated"]`. **Run**, with six notes of which two were marked deleted:

| Request | Answer |
| --- | --- |
| Another user lists, `per_page=2` | Page 1: ids 1 and 3. Page 2: ids 5 and 6. Page 3: empty. **`total` 4** |
| Another user gets a deleted note | `404`, `Not found` |
| A banned user lists | `403`, `policy 'not_banned+live_rows+authenticated' refused` |
| A banned user edits their own note | `403`, `policy 'not_banned+owner_or_staff' refused` |

Because `live_rows` is an equality on a column, the list is **exact**: full pages and a real total. The stacked list `["not_banned", "live_rows", "authenticated"]` was planned into the SQL filter `deleted = false`, and the two caller-only members were decided before the query. Compare the same rule written as `{"ne": ["$record.deleted", true]}`, which is a residual with `total: null`.

The booleans compare with `eq` against `true` or `false`. A boolean never equals the numbers `1` and `0`.

### Banned users

`{"not": {"role": "banned"}}` as a **list member** in front of other policies removes the banned role everywhere it is used, with one definition. It is true for everyone without the role, so it never admits anyone by itself, and it composes with `and` as a list does.

## Field-level protection and immutable fields

**Requirement.** Anyone may edit a record, but only admins may change its `price`, and nobody may change its `sku`.

| Policy | Condition |
| --- | --- |
| `price_by_admin` | `{"any": [{"role": "admin"}, {"not": {"exists": "$input.price"}}]}` |
| `immutable_sku` | `{"any": [{"not": {"exists": "$input.sku"}}, {"eq": ["$input.sku", "$record.sku"]}]}` |

**Run** (`price_by_admin` on `update`):

| Request | Answer |
| --- | --- |
| A user edits `name` | `200` |
| A user sends `price: 1` | `403`, `policy 'price_by_admin' refused` |
| **A user sends `price: null`** | **`200`, and the price was cleared** |
| An admin sends `price: 12` | `200` |

And `immutable_sku`: the same `sku` `200`, a different `sku` `403`, no `sku` key `200`, and **`sku: null` `200`, which erased the sku**. In both, `exists` is false for an explicit `null`, so `not exists` is true and the guard passes. The rule "do not change this field" is not enforceable with a condition when the column accepts `null`. Marking the column non-nullable does **not** help: a `PATCH` accepts `null` for every field, `nullable: false` included. Two ways out:

- **A [Python policy](/policies/python-policies)** that checks `"price" in context["input"]`, which distinguishes "sent as null" from "not sent".

Never rely on the guard alone for a field whose loss matters.

## Limits and conditional requirements

**Requirement.** A user may order at most ten of an item, staff are exempt; an order marked `shipped` must carry a tracking number; a range's minimum must not exceed its maximum.

| Policy | Condition | Attached to |
| --- | --- | --- |
| `qty_cap` | `{"any": [{"role": "staff"}, {"lte": ["$input.qty", 10]}]}` | `create` |
| `tracking_when_shipped` | `{"any": [{"ne": ["$input.status", "shipped"]}, {"exists": "$input.tracking"}]}` | `create` |
| `range_ok` | `{"lte": ["$input.min", "$input.max"]}` | `create` |

**Run.**

| Request | Answer |
| --- | --- |
| `qty_cap`: a user sends `qty: 5` | `201` |
| a user sends `qty: 50` | `403`, `policy 'qty_cap' refused` |
| staff send `qty: 50` | `201` |
| a user sends **no** `qty` | **`403`** (`lte` on a missing value is false) |
| `tracking_when_shipped`: `status: "shipped"` without tracking | `403` |
| `status: "shipped"` with tracking | `201` |
| no `status` | `201` |
| `range_ok`: `min` 1, `max` 5 | `201` |
| `min` 9, `max` 5 | `403` |
| both absent | `403` (a comparison with a missing value is false) |

The missing-value rows matter. `lte` fails closed: a cap on a **required** quantity is right as written, and a cap on an **optional** one needs `any` with `not exists`, or omitting the field would be refused. `ne` fails open: "status must not be `shipped` unless there is tracking" is satisfied by sending no status.

## Plans and tiers

**Requirement.** Features for the `pro` plan only, and users must not be able to grant themselves the plan.

A plan belongs in the token's **`app`** claims, which only administrators set. A policy reads it as `$auth.claims.app.plan`:

```json
{ "eq": ["$auth.claims.app.plan", "pro"] }
```

**Run**, with three tokens and a resource whose `list` used that policy:

| Caller | Answer |
| --- | --- |
| `app.plan = "pro"` | `200` |
| `app.plan = "free"` | `403`, `policy 'pro_plan' refused` |
| Only **`meta.plan = "pro"`** (user-editable) | `403` |

and, as the **trap**, a second policy that read `$auth.claims.meta.plan` for `delete`: a caller whose token carried `meta.plan = "pro"` passed it and **deleted a record**. The `meta` bag is edited by the user, so whatever they write there they can claim. Keep every access decision on `app` claims, roles and permissions.

## Permissions and step-up

**Requirement.** Creating a feature record needs the `feat.write` permission. Reading a sensitive record needs a second factor.

Attach `permission:feat.write` to `create` and `mfa` to `get`. **Run:**

| Caller | Answer |
| --- | --- |
| Permissions `["feat.write"]` creates | `201` |
| Permissions `["*"]` creates | `201` (a wildcard grants every permission) |
| No permission creates | `403`, `policy 'permission:feat.write' refused` |
| Signed in at `aal1` reads | `403`, `policy 'mfa' refused` |
| Signed in at `aal2` reads | passes the policy |

`mfa` is `{"all": [{"authenticated": true}, {"aal": "aal2"}]}`. Attach it to the operations that need step-up (a delete, a payout, a data export) and leave the rest on `authenticated`. A list of permissions in one `permission` shorthand needs **all** of them.

## Server-only routes

**Requirement.** An internal endpoint that only your servers can call.

A route with the policy `service`, called with a **secret key**:

```json
{ "method": "POST", "path": "/internal/ping", "handler": "ping", "policy": "service" }
```

**Run:**

| Caller | Answer |
| --- | --- |
| Signed out | `401`, `Authentication required` |
| A signed-in user | `403`, `policy 'service' refused` |
| A secret key | `200` |

A user's token cannot satisfy it, and neither can a publishable key. The secret key must stay on the server. See [Custom routes](/data/custom-routes).

## Storage layouts

### Private folders per user

**Requirement.** Each user owns the folder named for their id.

Both the read and the write policy of the bucket:

```json
{ "eq": ["$object.segments.0", "$auth.user_id"] }
```

**Run** (a `vault` bucket): the owner uploads and reads inside their folder (`201`, `200`); anyone else is refused (`403` on upload, `404` on read and delete); the owner may list **inside** their folder (`prefix=u-1/`) and is refused for the whole bucket; and asking for a signed URL for someone else's object answers `403`, `you may not grant access you do not have`.

### Public files, private folders, staff everywhere

**Requirement.** Anything under `public/` is readable by everyone, each user's own folder is private, and staff can do everything.

| Policy | Condition |
| --- | --- |
| Read | `{"any": [{"eq": ["$object.segments.0", "public"]}, {"eq": ["$object.segments.0", "$auth.user_id"]}, {"role": "staff"}]}` |
| Write | `{"any": [{"all": [{"authenticated": true}, {"eq": ["$object.segments.0", "$auth.user_id"]}]}, {"role": "staff"}]}` |

**Run:**

| Request | Answer |
| --- | --- |
| A user uploads to their own folder | `201` |
| A user uploads to `public/` | `403`, `the bucket's policy refused this upload` |
| Staff upload to `public/` | `201` |
| A signed-out caller uploads to a user's folder | `403` |
| Anyone reads `public/hello.txt` (signed out, another user, owner, staff) | `200` |
| A stranger or a signed-out caller reads `u-1/private.txt` | `404` |
| The owner and staff read it | `200` |
| A signed-out caller lists `public/` | `200`, with the file |
| A signed-out caller lists `u-1/` | `403` |
| A key with a path-traversal segment (`public/../u-1/private.txt`) | `404` |

**The trap** in the write policy is the `authenticated` inside it. Without it, a signed-out caller's empty id would equal an empty first segment on a key such as `/x`. Keep the signed-in check in front of every comparison between the caller and the key.

## Realtime channels

These two patterns come from reading the realtime service's rules, and were **not run**. Test them in a development environment.

| Requirement | Rule |
| --- | --- |
| Each user has a private channel | Pattern `user:{{ auth.user_id }}`, Subscribe and Publish `authenticated` |
| Members of an organisation share a channel | Pattern `org:{{ auth.org }}`, Subscribe `authenticated` |
| Everyone may watch a public channel, only staff may publish | Pattern `announcements`, Subscribe `public`, Publish `role:staff` |
| Row changes of a private resource reach only the right people | Pattern `resource:orders`, Subscribe the **same** condition as the resource's `list` |

A templated rule governs every channel of its shape and admits only the one it renders to for the caller, so `user:u-2` is refused to `u-1` rather than falling through to the default. See [Where policies are enforced](/policies/enforcement-points#realtime-channels).

## Time windows

**Requirement.** A record is readable until it expires.

A policy cannot compare a record's date with the clock: `$now` is a date value and a column is text, so the comparison is false. This was run: `{"gt": ["$record.expires_at", "$now"]}` returned **no rows**, including one that expires in 2099. Use a flag that a schedule maintains:

| Piece | What it does |
| --- | --- |
| A boolean `active`, default `true` | The access rule: `{"eq": ["$record.active", true]}`, which is a SQL filter |
| A [schedule](/jobs/schedules) | Runs hourly and sets `active` to `false` for rows whose `expires_at` has passed |

The window is as exact as the schedule's interval, and the list stays exact, with full pages and a real total. For a hard cut-off, check the date in the handler of a route.

## Partners and integrations

**Requirement.** An outside system reads a subset of data and writes through a narrow door.

| Piece | Design |
| --- | --- |
| A **key** | A publishable or secret key with scopes: `resource:read` and a custom scope such as `partner:acme` |
| A **route** | `GET /partner/orders`, policy `scope:partner:acme`, a flow that queries and returns only the fields the partner may see |
| **Allowed routes** | The key's gateway rule set to `GET /rest/v1/partner/*`, so it cannot call anything else |
| **Allowed IP ranges** | The partner's addresses |

Give the partner a route, not a resource. The route's flow decides the fields and the rows, the scope policy decides who may call it, and the gateway rules keep the key from being used anywhere else. Remember that a **scope** policy reads the key's list literally, so a key created with no scopes fails `scope:partner:acme`: give the key the scope explicitly.

## Putting it together: a task tracker

A small multi-tenant tracker, assembled from the recipes above. Each piece was run on its own; the combination was not run as a whole, so test it before you rely on it.

| Resource | Operation | Policy |
| --- | --- | --- |
| `tasks` (`org_id`, `title`, `status`, `deleted`) | `list`, `get` | `["not_banned", "same_org", "live_rows"]` |
| | `create` | `create_in_own_org` |
| | `update` | `["not_banned", "same_org_pinned"]` (the tenant-pinned policy above) |
| | `delete` | Not enabled. Soft delete through `update` |
| `comments` (`task_id`, `org_id`, `body`) | `list`, `get` | `["not_banned", "same_org"]` |
| | `create` | `create_in_own_org` |
| `attachments` (a bucket) | Read, write | `{"eq": ["$object.segments.0", "$auth.org"]}` (keys start with the organisation) |

What this gives you: every list is a SQL filter on `org_id` and `deleted` (exact totals, full pages, immune to `select`); a user without an organisation is refused at the plan; nobody can move a row between tenants; banned users are removed everywhere with one list member; and files live under their organisation's prefix. The remaining decisions are product ones: who may administer an organisation (`org_admin` on the routes that do it), and what staff can do (a route, not a wider resource policy).

## A checklist before shipping a policy set

1. **Every enabled operation has a policy you chose.**
2. **Ownership uses `owner:<column>`,** or starts with `authenticated`.
3. **Every tenant comparison is preceded by `exists` on the caller's tenant.**
4. **Create and update pin the tenant,** and the owner cannot be changed.
5. **`delete` is closed on public resources,** and the key's allowed routes exclude it.
6. **No access decision reads `meta` claims or a request value.**
7. **Lists that matter are pushable equalities,** so `select` cannot bypass them and `total` is exact.
8. **Guards on fields handle `null`.**
9. **Buckets have a policy per folder shape,** with the signed-in check in front.
10. **Realtime has a rule per channel family,** and `resource:*` matches the list policy.
11. **Every policy was tested as a signed-out caller, a stranger, a member and an admin,** with a publishable key and user tokens.
