## A condition reads a context

A policy never looks anything up. It is evaluated against a **context**: a nested object that the entry point builds for each request and hands to the engine. Every `$path` in a condition is a lookup into that object, and a path that is not there is empty. So the question behind most policy bugs is the same: **what is actually in the context at this entry point?**

This page answers it, per entry point. The shapes were taken from the code that builds each context and checked against requests made to a running API.

## The roots

A context has these top-level keys. Which of them have values depends on where the policy is running:

| Root | What it is | Resource ops | Routes | Storage | Realtime | Subscriptions | `policy.check` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `auth` | Who is calling | yes | yes | yes | yes | no | from the flow |
| `credential` | Which key was used | yes | yes | yes | yes | no | from the flow |
| `request` | The HTTP request | yes | yes | **no** | **no** | no | no |
| `project`, `env` | Where it is happening | yes | yes | yes | yes | no | yes |
| `record` | The row being touched | per operation | `null` | no | `null` | no | what you pass |
| `input` | The submitted data | per operation | the body | no | the message | no | what you pass |
| `object` | The stored file | no | no | **yes** | no | no | no |
| `channel` | The realtime channel | no | no | no | **yes** | no | no |
| `event` | The event envelope | no | no | no | no | **yes** | no |
| `now` | The current date and time | yes | yes | yes | yes | yes | yes |

A path under a root that the entry point does not supply, for example `$record.owner_id` in a bucket policy, is empty. It does not fail, and it equals every other empty value.

## `$auth`: who is calling

`auth` describes the caller. It is built from the verified token, so its values can be trusted, with one exception covered below.

| Path | Type | Meaning |
| --- | --- | --- |
| `$auth.authenticated` | boolean | True for a caller with a verified user token |
| `$auth.kind` | text | `user`, `operator`, `service`, or `anonymous` |
| `$auth.user_id` | text | The user's id. Empty when signed out |
| `$auth.email` | text | The user's email, if the token has one |
| `$auth.roles` | list | The caller's roles, such as `["admin", "editor"]`. Empty when signed out |
| `$auth.permissions` | list | The caller's permissions, such as `["posts.write"]`, or `["*"]` |
| `$auth.org` | text | The caller's organisation. Empty when none |
| `$auth.org_role` | text | The caller's role in that organisation: `owner`, `admin`, `member` or `viewer` |
| `$auth.aal` | text | `aal1` for a first factor, `aal2` after a second |
| `$auth.session_id` | text | The session the token belongs to |
| `$auth.claims` | object | The raw token claims. See below |

For a **signed-out** caller every key exists with an empty value: `authenticated` is `false`, `kind` is `anonymous`, `roles` and `permissions` are `[]`, and the rest are `null`. So a path like `$auth.roles.0` is `null` for them, and `$auth.claims.app.plan` is `null`.

<Warning>
The names people guess are wrong more often than right. There is **no `$auth.id`** (the key is `user_id`), **no `$auth.org_id`** (the key is `org`), and **no `$auth.role`** (the key is `roles`, a list). A path that does not exist is empty, not an error, and two empty values are equal. Studio's own path suggestions include `$auth.org_id`.
</Warning>

### `$auth.claims`

`claims` is the verified token, passed through. The ones that matter:

| Path | Meaning | Trust |
| --- | --- | --- |
| `$auth.claims.sub` | The user id (the same as `$auth.user_id`) | Verified |
| `$auth.claims.email`, `.roles`, `.perms`, `.org`, `.org_role`, `.aal` | The same values, under the token's own names (`perms`, not `permissions`) | Verified |
| `$auth.claims.app.*` | **Administrator-controlled** claims, such as `app.plan` | **Safe to base access on.** Only an administrator sets them |
| `$auth.claims.meta.*` | **User-editable** claims | **Never base access on them** |
| `$auth.claims.exp`, `.iat`, `.jti`, `.sid`, `.prj`, `.env` | Token bookkeeping | Verified, rarely useful |

This was run. A policy `{"eq": ["$auth.claims.app.plan", "pro"]}` passed a caller whose token had `app.plan = "pro"`, refused one with `app.plan = "free"`, and **refused a caller whose token had only `meta.plan = "pro"`**. A second policy that read `$auth.claims.meta.plan` was passed by that caller, who then deleted a record. Whatever the user can edit, the user can claim.

## `$credential`: which key was used

`credential` describes the **API key**, separately from the person:

| Path | Type | Meaning |
| --- | --- | --- |
| `$credential.role` | text | `anon` for a publishable key, `service` for a secret key, `operator` for a Studio operator |
| `$credential.is_service` | boolean | True for a secret key or an operator. **These bypass every policy before it is read** |
| `$credential.scopes` | list | The scopes the key was created with. Empty for an unrestricted key |
| `$credential.key_id` | text | The key's id |

Because a service credential has already passed by the time a policy is read, `$credential.is_service` is false in every condition that is actually evaluated for a caller. It is useful inside a **Check policy** block, where you supply the context yourself, and for the `service` shorthand's expansion.

`scopes` is a list, and an unrestricted key has an **empty** list, which the platform's own scope checks treat as "all allowed" while `contains` on it is false. See [the `scope` shorthand](/policies/shorthands#scope).

## `$request`: the HTTP request

For resource operations and routes:

| Path | Type | Meaning |
| --- | --- | --- |
| `$request.method` | text | `GET`, `POST`, `PATCH`, `PUT`, `DELETE` |
| `$request.path` | text | The request path |
| `$request.ip` | text | The address of the connection the API received |
| `$request.params` | object | The path parameters |
| `$request.query` | object | The query string, as text values |

Treat **`$request.query` and `$request.params` as attacker-controlled**, because they are. Comparing a record field to one of them lets the caller rewrite the policy, as run in [the overview](/policies/overview#a-request-value-can-rewrite-the-policy). Reading them to **narrow** (a `$request.method` check, for example) is fine. Comparing the record to them is not.

`$request.ip` is the address the API's connection came from. When requests reach the API through the gateway or another proxy, that can be the proxy's address, not the end user's, so test what your deployment reports before you write a rule that depends on it. A key's **Allowed IP ranges** setting is enforced at the gateway and is the better place for an address restriction.

`request` is **not** present for storage objects, realtime channels or event subscriptions.

## `$project`, `$env` and `$now`

| Path | Type | Meaning |
| --- | --- | --- |
| `$project` | text | The project's ref |
| `$env` | text | The environment's name, such as `production` |
| `$now` | **date** | The current date and time (UTC). It is a date value, not text |

`$env` lets one policy behave differently per environment (`{"ne": ["$env", "production"]}`), though that is usually a sign the two environments should have different definitions.

`$now` is the exception to "everything is text". Comparing it with record or request data is false, because a date cannot be ordered against text. See [Operators](/policies/operators#time).

## `$record`: the row being touched

`record` is the row, as the database returned it, with every column, declared or not. What it holds depends on the operation:

| Operation | `$record` | `$input` |
| --- | --- | --- |
| `list` | Each candidate row, **after** the plan. The plan itself has no record | n/a |
| `get` | The row, checked after it is loaded | n/a |
| `create` | The **new** row's data, the same as `$input`, with the owner stamped | The submitted data, with defaults and the owner stamp applied |
| `update` | The **existing** row, before the change | The **patch**: only the fields the client sent (and without the owner field) |
| `delete` | The existing row | n/a |
| A route | **Empty** | The request body |

Three things follow:

- **On `create`, `$record` is not a stored row.** It is the data about to be inserted. It has no `id` and no timestamps. A condition on `$record.status` for `create` reads the submitted status, the same as `$input.status`.
- **On `update`, `$record` is the row as it is now,** and `$input` is only what changes. A rule about **the result** of the update (the final status) needs both: `$input.status` if it is being set, `$record.status` if not. A condition that reads only `$record` checks the old row, so it cannot stop a change **to** a forbidden value.
- **On `list`, `$record` exists only per row.** The plan is made before any row is read, so conditions that need the row are either turned into SQL filters or kept as a per-row check. See [SQL pushdown](/policies/pushdown).

Dotted paths read into nested values: `$record.address.city` for a JSON column. A nested `eq` is a per-row check on a list, not a SQL filter.

### What a column holds

Values are what the database stores, decoded for JSON. Numbers are numbers, booleans are booleans, and **dates and datetimes are text** (ISO strings). An integer id arrives as an integer, and the engine normalises integers to text when it compares, so `$record.owner_id` (integer `7`) equals `$auth.user_id` (text `"7"`).

## `$input`: the submitted data

| Where | `$input` |
| --- | --- |
| `create` | The new row's data |
| `update` | The patch (only the sent fields) |
| A route | The validated body, as an object. Empty for a `GET` |
| A realtime publish | The message payload |
| A **Check policy** block | The `input` you pass |
| `list`, `get`, `delete` | Empty |

A path into a body that was not sent is empty, and so is a field sent as `null`. A condition cannot tell the two apart. See [Operators](/policies/operators#null-handling).

`$input` is **deferred** during planning: it is not known until the body is read, so a condition that mentions it is kept for the full check. For a custom route this is why the gate and the handler each evaluate part of the policy. See [Custom routes](/data/custom-routes#who-may-call-a-route).

## Storage: `$object`

A bucket's read and write policies run for every object operation, with a context that **describes the object**:

| Path | Type | Meaning |
| --- | --- | --- |
| `$object.key` | text | The full key, such as `u-1/avatars/me.png`. For a listing, the **prefix** being listed |
| `$object.segments` | list | The key split on `/`: `["u-1", "avatars", "me.png"]` |
| `$object.segments.0` | text | The first segment, the usual place to put an owner or a tenant |
| `$object.action` | text | `read`, `list`, `stat`, `write` or `delete` |

The context also carries `auth`, `credential`, `project` and `env`, and **no** `request`, `record` or `input`. A bucket policy may only be a JSON condition. A Python policy is rejected when the bucket is saved with `storage policies must be JSON conditions`.

The standard layout puts the owner first:

```json
{ "eq": ["$object.segments.0", "$auth.user_id"] }
```

With that as both the read and write policy of a `vault` bucket, this was run:

| Request | Answer |
| --- | --- |
| `u-1` uploads `u-1/a.txt` | `201` |
| `u-2` uploads `u-1/a.txt` | `403`, `the bucket's policy refused this upload` |
| A signed-out caller uploads | `403`, the same |
| `u-1` reads `u-1/a.txt` | `200` |
| `u-2` or a signed-out caller reads it | `404`, `Not found` |
| `u-1` lists the prefix `u-1/` | `200`, with the file |
| `u-1` lists the **whole bucket** (no prefix) | **`403`**, `the bucket's policy refused this listing` |
| `u-1` lists the prefix `u-2/` | `403` |
| `u-2` deletes `u-1/a.txt` | `404` |
| `u-2` asks for a signed URL for `u-1/a.txt` | `403`, `you may not grant access you do not have` |

Two details to notice. A **listing** is evaluated with the *prefix* as the key, so `segments.0` of an empty prefix is empty and a listing of the whole bucket is refused, which is the right outcome, and the client must list inside its own folder. And a read or delete that is refused is a **`404`**, so a stranger cannot tell a missing file from someone else's.

A **public** bucket uses `public` for reads, which is why a signed-out caller read and listed a public bucket, while its write policy (`authenticated` by default) still refused a signed-out upload.

## Realtime: `$channel`

A channel rule's **Subscribe** and **Publish** policies run against a context that describes the channel:

| Path | Type | Meaning |
| --- | --- | --- |
| `$channel.name` | text | The channel, such as `org:acme` |
| `$channel.segments` | list | The name split on `:` and `/`: `["org", "acme"]` |
| `$channel.action` | text | `subscribe`, `publish` or `presence` |
| `$input` | any | For a publish, the message payload |

with `auth`, `credential`, `project` and `env` as everywhere, and `record` empty. Realtime policies can only be **stored** policies (and the built-ins): Python policies are not available to the realtime service.

Rules are matched **top to bottom** by pattern, and the first match governs. A pattern can contain `*` wildcards and **templates**:

| Pattern | Governs | Effect |
| --- | --- | --- |
| `user:{{ auth.user_id }}` | Every `user:*` channel | A signed-in user may join only `user:<their id>`. Someone else's `user:*` channel is refused by this rule, with `this channel belongs to someone else` |
| `org:{{ auth.org }}` | Every `org:*` channel | A caller may join only their organisation's channel |
| `public:*` | Public channels | Matched by any caller the policy admits |
| *(no rule matches)* | | The environment's **Default policy** |

A template that renders to nothing for the caller, such as `user:{{ auth.user_id }}` for a signed-out caller, becomes `user:None`, and the rule refuses it. The default policy for both subscribe and publish is `authenticated`.

The realtime settings, under **Settings → Realtime**, are:

| Setting | Hint or meaning |
| --- | --- |
| **Clients may publish** | *Off restricts publishing to servers and flows; clients can still subscribe.* |
| **Default policy** | *Used by any channel that matches no rule below.* Choices: **Default (authenticated)** or any policy |
| **Channel rules** | *Rules are matched top to bottom. Patterns support* `{{ auth.org }}` *templates and* `*` *wildcards.* Each has a **Pattern**, **Subscribe**, **Publish**, **Presence** and **History depth** (*Messages kept for late subscribers.*) |

The resource-change channel is `resource:<name>`, so the rule for it is `resource:*` or a more specific one. **That channel carries the raw record** of every change when the resource's **Broadcast changes** switch is on, so its subscribe policy is a data-access policy. See [Resource events](/data/resource-events#realtime).

## Event subscriptions: `$event`

A subscription's **Only when…** condition is evaluated against **only** the event, wrapped in one key:

```json
{
  "event": {
    "name": "orders.created",
    "project": "acme",
    "env": "production",
    "payload": { "resource": "orders", "change": "created", "record": { "id": 12, "total": 1500, "status": "paid" } },
    "source": "api",
    "actor": "u-1",
    "id": "5977bd30d884497ea0df5f629a28e7c9",
    "occurred_at": "2026-10-01T22:13:35+00:00",
    "request_id": "6b77620d-40fe-4cd7-aae5-0b33d5af25d6",
    "release_id": null,
    "api_version": null
  }
}
```

| Path | Meaning |
| --- | --- |
| `$event.name` | The event name |
| `$event.payload` | The payload. For a resource event `{resource, change, record}` |
| `$event.payload.record.total` | A field of the changed record |
| `$event.payload.change` | `created`, `updated` or `deleted` |
| `$event.actor` | Who made the change, or empty for a system write |
| `$event.source`, `.project`, `.env`, `.id`, `.occurred_at`, `.request_id` | The envelope |

There is **no `auth`, `credential`, `record` or `request`** here: a subscription is not a request. And there is **no `$event.data`**: Studio's **Only when…** switch fills in `{"exists": "$event.data"}`, which is never true, so a subscription with that default **never fires**. Replace it with a path under `$event.payload`. See [Resource events](/data/resource-events#the-condition-and-a-trap-in-the-default).

## Inside a flow: `policy.check`

The **Check policy** block (`policy.check`) evaluates a policy for a context **you assemble**:

| Config | Meaning |
| --- | --- |
| `policy` | A policy name, or an inline condition |
| `record` | A value to use as `$record` |
| `input` | A value to use as `$input` |

The context the block builds:

| Root | From |
| --- | --- |
| `auth` | The flow run's caller (empty for a flow started by an event or a schedule) |
| `credential` | The flow run's credential, with `is_service` false when none |
| `project`, `env` | The flow's environment |
| `record`, `input` | The block's config |

and it follows the **`allowed`** or **`denied`** edge. This was run: a flow with the condition `{"gte": ["$input.total", 100]}` and `input` set to `{{ input.body }}` followed `allowed` for a body of `{"total": 500}` and `denied` for `{"total": 5}`.

Remember the engine's first step. A flow that was started by a **secret key** carries a service credential, and `policy.check` then answers **allowed** for every policy, because the bypass comes first. This is also why running a flow as a service and testing a policy inside it proves nothing about real callers. Test with a user's token, or pass a context with `is_service` false.

## Direct invocation of functions and flows

`/functions/v1/<name>` and `/flows/v1/<name>` evaluate the function's or flow trigger's policy with the **resource-style** context: `auth`, `credential`, `request`, `project`, `env`, and `input` set to the JSON body, with `record` empty. The same shape applies to a custom route's policy.

## A full context, for reference

This is the whole context for a signed-in user's `PATCH` of a record, as the engine receives it (the `request` and `credential` values are illustrative):

```json
{
  "auth": {
    "authenticated": true,
    "kind": "user",
    "user_id": "u-1",
    "email": "maya@acme.co",
    "roles": ["member"],
    "permissions": [],
    "org": "acme-co",
    "org_role": "member",
    "aal": "aal1",
    "session_id": "s-91",
    "claims": { "sub": "u-1", "prj": "acme", "env": "production", "app": { "plan": "pro" }, "meta": { "theme": "dark" } }
  },
  "credential": { "role": "anon", "is_service": false, "scopes": ["resource:read", "resource:write"], "key_id": "k-1" },
  "request": { "method": "PATCH", "path": "/rest/v1/tasks/7", "ip": "203.0.113.9", "params": { "id": "7" }, "query": {} },
  "project": "acme",
  "env": "production",
  "record": { "id": 7, "title": "Write docs", "org_id": "acme-co", "status": "open" },
  "input": { "status": "done" }
}
```

and for a signed-out caller reading a list, after the plan:

```json
{
  "auth": { "authenticated": false, "kind": "anonymous", "user_id": null, "email": null, "roles": [], "permissions": [], "org": null, "org_role": null, "aal": null, "session_id": null, "claims": {} },
  "credential": { "role": "anon", "is_service": false, "scopes": [], "key_id": "k-1" },
  "request": { "method": "GET", "path": "/rest/v1/tasks", "ip": "203.0.113.9", "params": {}, "query": {} },
  "project": "acme",
  "env": "production",
  "record": null,
  "input": null
}
```

## When a value is not what you expected

| Symptom | Likely cause |
| --- | --- |
| A comparison with `$auth.<something>` is always true | The key does not exist, so it is empty and equal to another empty value. Check the names in the table above |
| A tenant policy admits everyone, or no one | `$auth.org_id` instead of `$auth.org`, or a token with no `org` claim |
| A role check never passes | `$auth.role` (singular), or a case difference in the role name |
| A rule on `$record.x` does nothing on `create` | On `create`, `$record` is the submitted data, not a stored row |
| A rule on `$record.status` does not stop a change to a status | On `update`, `$record` is the existing row. Check `$input.status` for the new value |
| `$request.ip` is the same for every caller | The API sees the proxy's address |
| A subscription never fires | `$event.data` instead of `$event.payload` |
| A bucket rule on `$record` or `$request` never matches | Storage has `object`, not `record` or `request` |
| A condition on a date is always false | `$now` is a date and a column is text |
| A claim check passes for the wrong people | The claim is under `meta`, which users edit. Use `app` |
| A value looks right in the response and wrong in the policy | The policy sees the **stored** column, before any [transformer](/data/transformers) |

## Designing data so policies can see it

A policy can only reason about what is in the context, so the data model decides what policies can say. A few choices make the difference.

| Choose | So that a policy can say |
| --- | --- |
| An **owner column** on every private table, set by `owner_field` | `owner:<column>`, which also gives you a SQL filter |
| An **org column** on every tenant table | `eq` against `$auth.org`, pinned on create and update |
| A **status column** with a short fixed set | Visibility rules, and `ne`/`in` guards on submitted status |
| A **flag** you maintain (`active`, `published`) | Rules that would otherwise need a date comparison |
| **Roles and permissions** in tokens | `role` and `permission` shorthands |
| **`app` claims** for plan or tier | Plan gating that users cannot forge |
| **Object keys that start with the owner or tenant** | A single `segments.0` rule for a whole bucket |
| **Channel names that include the owner or tenant** | A templated channel rule |

The columns a policy compares should be **indexed**, because an `eq` on them becomes a SQL filter on every list. See [Migrations](/data/migrations#indexes).

## Quick reference

| Entry point | Roots present |
| --- | --- |
| Resource operations | `auth`, `credential`, `request`, `project`, `env`, `record`, `input` |
| Custom routes, functions, flows (direct) | `auth`, `credential`, `request`, `project`, `env`, `input` |
| Storage buckets | `auth`, `credential`, `project`, `env`, `object` |
| Realtime channels | `auth`, `credential`, `project`, `env`, `channel`, `input` |
| Event subscriptions | `event` |
| `policy.check` | `auth`, `credential`, `project`, `env`, and the `record` and `input` you give |

| Common path | Meaning |
| --- | --- |
| `$auth.user_id` | The caller's id |
| `$auth.roles` | The caller's roles (a list) |
| `$auth.permissions` | The caller's permissions (a list) |
| `$auth.org`, `$auth.org_role` | The organisation and the role in it |
| `$auth.aal` | The assurance level |
| `$auth.claims.app.*` | Trusted claims |
| `$credential.scopes` | The key's scopes |
| `$record.<column>` | A column of the row |
| `$input.<field>` | A submitted field |
| `$object.segments.0` | The first key segment |
| `$channel.name` | The channel |
| `$event.payload.record.<column>` | A field of the changed record |
| `$env`, `$project`, `$now` | Where and when |
