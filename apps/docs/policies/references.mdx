## A reference is how a policy is named

A policy is **defined** once and **referenced** wherever it is used. The reference is what you type or pick in the **Access** section of a resource, a route, a bucket, or a realtime rule. It can take five forms, and the engine resolves any of them to the same thing: a condition (or a Python function) with a name.

| Form | Example | Resolves to |
| --- | --- | --- |
| **A name** | `"own_rows"` | The policy with that name: stored, Python or built-in |
| **A parameterised name** | `"role:admin"`, `"owner:author_id"` | A shorthand with its argument |
| **An inline condition** | `{"role": "admin"}` | That condition, named `inline` |
| **A list** | `["authenticated", "own_rows"]` | All of them must pass, named `authenticated+own_rows` |
| **Nothing** | `null` | The entry point's default |

Everything below was run against a real API, and the messages are quoted as they came back.

## Names

A string is looked up in the environment's policy table, which is built from three sources:

| Source | Defined | Examples |
| --- | --- | --- |
| **Built-in** | In the platform | `public`, `deny`, `authenticated`, `service`, `owner`, `mfa` |
| **Python** | In your project's code, with `@policy("name")` | `is-weekday-owner` |
| **Stored** | In Studio, per environment | `own_rows`, `org_admin` |

The table is made by merging them in that order, so **a later source replaces an earlier one of the same name**: stored over Python over built-in. A stored policy called `authenticated` therefore **becomes** the policy `authenticated` for every resource operation, route and bucket that uses the name, including every one that uses it by default. This was run, and it made every signed-in `POST` answer `403`, `policy 'authenticated' refused`, until the stored policy was deleted. See [the overview](/policies/overview#a-stored-policy-can-replace-a-built-in-one).

Names are matched **exactly and case-sensitively**. `Public` is not `public`:

| Written | Result |
| --- | --- |
| `public` | The built-in |
| `Public` | `unknown policy 'Public'` |
| `own_rows` | The stored policy, if it exists |
| `nope` | `unknown policy 'nope'` |

A stored policy's name is `^[a-z][a-z0-9_-]{0,62}$`: lowercase, starting with a letter, with digits, hyphens and underscores. A Python policy's name is whatever you give `@policy`, and a hyphen is common (`is-weekday-owner`).

## Parameterised names

A string with a colon is read as a **shorthand and its argument**, when the part before the first colon is one of five kinds:

| Written | Condition |
| --- | --- |
| `role:admin` | `{"role": "admin"}` |
| `permission:posts.write` | `{"permission": "posts.write"}` |
| `owner:author_id` | `{"owner": "author_id"}` |
| `scope:resource:write` | `{"scope": "resource:write"}` |
| `kind:user` | `{"kind": "user"}` |

They are resolved **after** the name lookup, so a stored policy named `role:admin` would win. Stored names cannot contain a colon, so in practice they do not collide.

The parameterised form is for a **single** value. A list of roles (`{"role": ["a", "b"]}`) cannot be written as a string, and `aal:`, `service:` and `authenticated:` are **not** recognised kinds: `aal:aal2` answers `unknown policy 'aal:aal2'`. Use the built-ins `mfa` and `service`, or an inline condition. [Shorthands](/policies/shorthands#parameterised-names-shorthands-as-references) has the full table.

## Inline conditions

Anywhere a reference is accepted, you can write a **condition object** instead of a name:

```json
{ "all": [{ "authenticated": true }, { "eq": ["$record.status", "published"] }] }
```

It is validated when you save, with the same checks as a stored policy, and the message begins with where it was attached:

```text
operations.list.policy: condition.eq: expected [left, right]
```

An inline condition is named **`inline`** in decisions and messages: a refusal reads `policy 'inline' refused`, which tells you nothing about *which* inline condition. That is the first cost of inline conditions. The others:

| | Inline | Stored |
| --- | --- | --- |
| **Reuse** | Written again on each attachment | One definition, many references |
| **A change** | Edit every attachment | Edit once |
| **Readable refusals** | `policy 'inline' refused` | `policy 'org_admin' refused` |
| **Visible in the Policies list** | No | Yes |
| **Promoted** | With the resource | As its own definition |

Use inline conditions for a rule that exists in exactly one place and is short. Anything you would want to name, name.

### Constants as references

`true` and `false` are conditions, and are accepted as inline references. **They do not behave as you would expect on a resource operation:**

| Attached to a resource operation | Anonymous | Signed-in user |
| --- | --- | --- |
| `true` | `200`, passes | passes. Same as `public` |
| **`false`** | **`401`** | **`200`, passes** |
| **`[]`** (an empty list) | **`401`** | **`200`, passes** |

A `false` or an empty list is **treated as if no policy were set**: it is replaced by the default, `authenticated`. This was run on a resource with the attachment `false`: a signed-in caller listed and fetched records. To refuse everyone, attach the built-in **`deny`** (or switch the operation off). Do not attach `false`. The same `policy or default` replacement is in the code for custom routes, bucket policies and flow HTTP triggers, which this page read from the code and did not run.

<Warning>
On a resource operation, a `false` or `[]` policy means **`authenticated`**, not "nobody". The reference is replaced by the default when it is falsy. Use `deny`, or leave the operation switched off.
</Warning>

## Lists

A list of references is an **`and`**: every policy in it must pass.

```json
["authenticated", "own_rows"]
```

It resolves to one policy named by joining the members with `+`, whose condition is `{"all": [<each condition>]}`:

| List | Named | Condition |
| --- | --- | --- |
| `["authenticated", "own_rows"]` | `authenticated+own_rows` | `{"all": [{"authenticated": true}, {"owner": "owner_id"}]}` |
| `["role:editor", "own_rows"]` | `role:editor+own_rows` | `{"all": [{"role": "editor"}, {"owner": "owner_id"}]}` |
| `["authenticated", {"eq": [...]}]` | `authenticated+inline` | An inline member is allowed |
| `["public", "deny"]` | `public+deny` | `{"all": [true, false]}`, which is never true |

and a refusal names the combined policy:

```text
policy 'role:editor+own_rows' refused
```

Verified on a resource with `list` and `get` set to `["role:editor", "own_rows"]`: a signed-in user without the role got `403` on both, an editor who owned the row passed, and a signed-out caller got `401`.

Things to know about lists:

- **A list cannot express `or`.** For "owner or admin", write one policy with `any`. Lists are for stacking independent requirements (`not_banned` **and** `readable_document`).
- **The planner understands lists.** `["authenticated", "own_rows"]` planned to the same SQL filter as `own_rows` alone, so a list of well-behaved policies still gives correct pages.
- **An empty list is `true`, which on a resource operation means `authenticated`.** See above.
- **A Python policy cannot be in a list.** Saving fails with `Python policies cannot be combined in a list; call them from Python`. Call the Python policy by name, alone, or call it from another Python policy.
- **Members are resolved when the list is used.** An unknown member fails the whole reference: `["nope"]` answers `unknown policy 'nope'`.

In Studio's picker, **Must satisfy several policies (all of)…** turns the choice into a list, with an **Add another** button, one picker per member, and a trash button for each (the last cannot be removed). A member cannot itself be a list.

## `null`: the entry point's default

An attachment that is empty (`null`, or no key at all) falls back to the entry point's **default**:

| Entry point | Default | Studio's label for it |
| --- | --- | --- |
| Resource operation | `authenticated` | **Secret keys only** |
| Custom route | `authenticated` | **Default (signed-in users)** |
| Bucket read | `authenticated`, or `public` for a public bucket | **Default** |
| Bucket write | `authenticated` | **Default** |
| Realtime channel rule | `authenticated` | **Default (authenticated)** |
| Realtime default policy | `authenticated` | **Default (authenticated)** |
| Function (`@function`) | `authenticated` | n/a |
| Flow HTTP trigger | `authenticated` | n/a |

All of them are `authenticated`, which any signed-in user passes. The one label that disagrees is the resource operation's, **Secret keys only**. It is wrong: an operation left on that choice answered `401` to a signed-out caller and **`200` and `201` to a signed-in user**. To restrict an operation to secret keys, choose **Secret keys & operators** (the `service` policy).

The default is applied silently, so "I did not set a policy" and "I set `authenticated`" are the same, and neither is "closed". Always choose a policy for each enabled operation.

## When a reference cannot be resolved

A reference that names nothing is an error, but **when** the error happens depends on the attachment point, and that is where policies break in production.

| Attachment | Checked when you save? | What an unknown name does |
| --- | --- | --- |
| Resource operation | **Yes** | `422`, `operations.list.policy: unknown policy 'nope'` |
| Custom route | **Yes** | `422`, `policy: unknown policy 'nopolicy'` |
| Bucket read and write policy | **Yes** | `422`, `read_policy: unknown policy 'nope'` |
| Flow HTTP trigger `policy` | **No** | Saves. Every non-service caller then gets a plain **`500`** |
| Realtime channel rule | **No** | Not validated by the platform. The realtime service cannot load a rule it cannot resolve |
| Function `@function(policy=...)` | n/a (code) | A name that does not resolve is an error at call time |

The three that are checked are checked **at save time only**. A reference that was valid when saved stays in the definition after the policy is deleted or renamed, and then fails at **request** time.

### What a missing policy looks like at request time

This was run. A resource named a stored policy, the policy was then deleted, and the resource's list was requested:

| Caller | Answer |
| --- | --- |
| A signed-in user | **`500`**, `Internal Server Error` |
| A secret key | **`200`**. The service bypass happens before the name is looked up |
| The Overview's definitions-with-problems list | **Empty** |

A missing policy is not reported anywhere. The resource simply starts failing, and only for callers who are subject to policies, which can make it look like an outage that does not affect your own testing with a secret key.

## Deleting and renaming

Both are allowed, neither checks for users of the name, and both produce the failure above.

| Action | Effect |
| --- | --- |
| **Delete** a policy that something references | Every reference to it now fails with a `500` for non-service callers |
| **Rename** a policy (editing its `name`) | The old name no longer exists. Every reference to it fails the same way. This was run: renaming `own_rows` to `own_rows2` left a resource's `["role:editor", "own_rows"]` answering `500` |
| **Edit** a policy's condition | Takes effect for every reference on the next request |

So treat the name as a **public identifier**, and before you delete or rename:

1. **Search for the name.** The Policies page does not show where a policy is used. Search the resources (every operation), routes, buckets, the realtime channel rules, and the flows' HTTP triggers. The environment's definitions can be exported as a blueprint and searched as text.
2. **Add the new policy first** under its new name, move each reference to it, then delete the old one.
3. **Check the Overview** afterwards. It will not list a missing policy, so read it for other problems and test an endpoint as a signed-in user.

A rename is really "create new, repoint, delete old". There is no rename-with-update.

## Policies and environments

A policy is a definition, and **promotion** copies it between environments:

| Fact | Consequence |
| --- | --- |
| Promotion is an **upsert by name** | A policy changed in the source overwrites the target's. A new one is created |
| Promotion **never deletes** | A policy removed in the source stays in the target |
| A resource and its policy are separate definitions | Promote them together (omit `include`), or the target's resource names a policy that does not exist there, and fails with a `500` |
| A **Python** policy is code | It is not promoted. Deploy the code to each environment |
| A **release** pins its policies | A pinned API keeps the policies it was published with, whatever you edit live |

Because a stored policy overwrites by name, the same name must mean the same thing in every environment, and a policy whose behavior legitimately differs between development and production should be **two** policies, chosen by the resource's definition, not one policy edited differently in each place.

## Organising a policy library

A project accumulates policies. These conventions keep a library of fifty as readable as a library of five.

### Name for the rule

| Name | Reads as |
| --- | --- |
| `own_rows` | The caller's own rows |
| `org_member` | Members of the record's organisation |
| `org_admin` | Admins of the record's organisation |
| `published_or_owned` | Published records, or the caller's own |
| `staff_only` | The `staff` role |
| `pinned_org_on_write` | A write that keeps the tenant column fixed |

Avoid names that describe where a policy is used (`tasks_list`) or that can drift (`temp`, `new_policy`). The same policy is often used in many places, and a name that mentions one of them is wrong in the others.

### One idea per policy

A policy that says "the owner, or staff, or anyone for public records" is three ideas. If any of them is used on its own elsewhere, it should be its own policy. Policies that are only ever used together can stay as one `any`.

### Describe the allowance

The **Description** is shown in the Policies list. Write what the policy **allows**, in a sentence, as you would explain it to the person who asks "who can read this?": *Members of the record's organisation. Signed-out callers and people without an organisation are refused.*

### Keep a short list of building blocks

Most libraries settle into three layers:

| Layer | Examples | Used by |
| --- | --- | --- |
| **Identity** | `signed_in` (not needed: the built-in), `staff_only`, `org_member` | Everything |
| **Row rules** | `own_rows`, `published_or_owned`, `same_org` | `list`, `get`, `update`, `delete` |
| **Write guards** | `create_in_own_org`, `pinned_org_on_write`, `no_self_publish` | `create`, `update` |

Resources then stack them with lists (`["staff_only", "pinned_org_on_write"]`).

### Decide where the policy lives

| If the rule is | Put it |
| --- | --- |
| A single operation of a single resource, and short | Inline |
| Used in several places | A stored policy |
| A built-in's exact meaning | The built-in |
| One shorthand with one argument | A parameterised name (`role:admin`) |
| A lookup, a calculation, another service | A Python policy |

## Changing a policy safely

Because an edit reaches every reference at once, treat a change to a shared policy like a change to shared code.

| Step | Why |
| --- | --- |
| **List the references first** | You can only judge a change if you know what it affects |
| **Widen deliberately.** A condition that gets broader opens every reference at once | A mistake leaks everywhere |
| **Narrow carefully.** A condition that gets tighter can lock real users out of everything that uses it | Test the callers you still want to admit |
| **Try it on a copy.** Create `own_rows_v2`, point one resource at it, test, then repoint the rest | Limits the blast radius |
| **Keep the old one until the last reference is gone** | A missing policy is a `500` |
| **Promote with the resources** | The target must have both |

## Catalogue of reference patterns

| You want | Reference |
| --- | --- |
| Anyone | `"public"` |
| Signed-in users | `"authenticated"` |
| The record's owner (column `user_id`) | `"owner:user_id"` |
| Members of a role | `"role:editor"` |
| Callers with a permission | `"permission:posts.write"` |
| Keys with a scope | `"scope:reports:export"` |
| Servers only | `"service"` |
| A second factor | `"mfa"` |
| Nobody (through the API) | `"deny"` |
| A named rule | `"org_admin"` |
| Two rules together | `["not_banned", "readable_document"]` |
| One rule, once | `{"role": "admin"}` |
| Whatever the entry point defaults to | `null` (which is `authenticated`) |

## Questions that come up

<AccordionGroup>
  <Accordion title="Can a policy reference another policy?">
    A condition cannot. A **list** of references combines policies, and a Python policy can call another. There is no `{"policy": "other"}` operand.
  </Accordion>
  <Accordion title="Is a name matched case-insensitively?">
    No. `Public` is unknown. Names are lowercase.
  </Accordion>
  <Accordion title="What is the reference when I pick a built-in in Studio?">
    The built-in's name as text: `public`, `authenticated`, `owner`, `mfa`, `service` or `deny`.
  </Accordion>
  <Accordion title="How do I find where a policy is used?">
    Studio does not list usages. Search the definitions (a blueprint export, or each resource, route and bucket), and the flows' HTTP triggers and realtime rules.
  </Accordion>
  <Accordion title="What happens to a policy's name in a decision?">
    A stored or built-in policy is named as itself, a parameterised name as that string (`role:admin`), an inline condition as `inline`, and a list as the members joined with `+`.
  </Accordion>
  <Accordion title="Can I attach `false` to close an operation?">
    No. On a resource operation it is replaced by the default `authenticated`. Use `deny`, or leave the operation off.
  </Accordion>
  <Accordion title="Can I rename a policy and keep its users working?">
    Not in one step. Create the new name, repoint every reference, then delete the old one.
  </Accordion>
</AccordionGroup>

## What to remember

- **Five forms: a name, `kind:argument`, an inline condition, a list, `null`.**
- **Stored beats Python beats built-in.** Never reuse a built-in's name.
- **A list is `and`.** It cannot express `or`, cannot contain a Python policy, and is named `a+b`.
- **`false` and `[]` become `authenticated` on resource operations.** Use `deny`.
- **`null` is `authenticated` everywhere,** and Studio mislabels it on resource operations.
- **Unknown names are caught at save time for resources, routes and buckets, and not for flow triggers or realtime rules.**
- **Deleting or renaming a used policy is a silent `500`.** Repoint first.
- **Promote policies with the resources that use them.**
