Everywhere Pawabase asks *who may do this?*, you answer with a **policy reference**. A reference can be a name, a parameterised name, an inline condition, a list or `null`. This page explains each form, the order names are resolved in, what `null` means at each entry point, and how to organise a policy library as a project grows.

## References in Studio are attachment choices

The Studio **Policy** picker is a compact UI for the reference forms on this page. In an attachment field, **Built-in** selects a built-in reference; **This project** selects a saved name from **Build → Policies**; **Custom rules…** stores an inline condition; and **Must satisfy several policies (all of)…** stores a list. Seeing a policy name in that picker does not prove it suits the attachment's context—only that it resolves.

The empty-looking choice is contextual. An enabled resource operation shows **Secret keys only** when its policy is empty, because it is not an ordinary authenticated default. Other forms may label it **Default (signed-in users)** or **Default**. Read the entry point's default in [where policies are enforced](/policies/enforcement-points) rather than treating an empty picker as a universal access rule.

## The forms at a glance

```json
"policy": "finance_staff"                    // 1. a name
"policy": "role:librarian"                   // 2. a parameterised built-in
"policy": { "role": ["admin", "bursar"] }    // 3. an inline condition
"policy": true                               // 3b. an inline boolean
"policy": ["mfa", "role:bursar"]             // 4. a list: all must pass
"policy": null                               // 5. the entry point's default
```

## 1. Names

A string without a colon is a **name**, resolved in this order:

1. **Stored policies**: those you define in Studio or through the Platform API, per environment.
2. **Python policies**: registered with `@policy` in the project's code.
3. **Built-ins**: always available.

A stored policy with the same name as a built-in **overrides** it for that environment. That's occasionally useful (for example making `authenticated` also require verified email) but usually confusing. Prefer new names.

### The built-ins

<ResponseField name="public" type="true">Anyone, including anonymous callers with a publishable key.</ResponseField>
<ResponseField name="deny" type="false">Nobody. Service credentials still pass, as they bypass all policies.</ResponseField>
<ResponseField name="authenticated" type='{"authenticated": true}'>Any signed-in user of this environment.</ResponseField>
<ResponseField name="service" type='{"service": true}'>Secret keys and operators only.</ResponseField>
<ResponseField name="owner" type='{"owner": "owner_id"}'>The user whose id is in the record's `owner_id`.</ResponseField>
<ResponseField name="mfa" type='{"all": [{"authenticated": true}, {"aal": "aal2"}]}'>Signed in with a second factor.</ResponseField>

### Stored policies

```json
{
  "name": "family_access",
  "description": "Staff, the student themself, or one of their guardians.",
  "condition": { "any": [
    { "role": ["admin", "principal", "teacher", "bursar", "librarian"] },
    { "owner": "user_id" },
    { "contains": ["$record.guardian_user_ids", "$auth.user_id"] }
  ] }
}
```

Names are lower-case letters, digits, underscores and dashes, starting with a letter (`^[a-z][a-z0-9_-]{0,62}$`). They're **fixed once created**, because other definitions refer to them by name. To rename, create the new policy, repoint references, then delete the old one.

### Python policies

```python code/<project>/policies.py
from pawabase_kit.policies import policy

@policy("same_department", description="Staff in the record's department")
async def same_department(context):
    ...
```

Once the project's code is loaded (Studio → Project → **Reload code**), `"same_department"` works anywhere a name does, with two exceptions: Python policies can't be used in **lists** and can't be used by **storage buckets**. [Python policies →](/policies/python-policies)

## 2. Parameterised built-ins

A string of the form `kind:argument` creates a shorthand policy on the fly, for `role`, `permission`, `owner`, `scope` and `kind`:

| Reference | Equivalent condition |
| --- | --- |
| `role:librarian` | `{"role": "librarian"}` |
| `permission:reports.publish` | `{"permission": "reports.publish"}` |
| `owner:borrower_user_id` | `{"owner": "borrower_user_id"}` |
| `scope:partner:orders` | `{"scope": "partner:orders"}` |
| `kind:user` | `{"kind": "user"}` |

Parameterised names are checked **after** stored policies, so a stored policy literally named `role:librarian` would win. Don't do that.

## 3. Inline conditions

Any condition object, or `true`/`false`, can be used directly:

```json
"operations": {
  "update": { "enabled": true, "policy": {
    "any": [ { "role": "admin" }, { "all": [ { "owner": "author_id" }, { "eq": ["$record.status", "draft"] } ] } ]
  } }
}
```

Inline conditions are validated when the definition that contains them is saved. They're right for rules used exactly once; anything used twice should be named, so a change happens in one place.

## 4. Lists

A list means **all references must pass**:

```json
"policy": ["mfa", "role:bursar"]
"policy": ["family_access", { "eq": ["$record.archived", false] }]
```

Lists compose named and inline references without writing a new policy. Internally they become one condition, `{"all": [ … ]}`, named after its parts (`mfa+role:bursar`), so lists are planned and pushed down like any other condition.

Lists can't contain **Python policies**, because a Python policy is a function, not a condition that can be merged. Call other policies from Python instead.

## 5. `null`: the entry point's default

`null` (or leaving the policy out) means different things in different places, chosen to be safe:

| Entry point | `null` means | Why |
| --- | --- | --- |
| Resource operation | **Secret keys and operators only** | An enabled operation with no rule shouldn't be open |
| Custom route | `authenticated` | Routes are called by your app's users |
| Direct function call | `authenticated` | Same |
| Direct flow call (`trigger.http` policy) | `authenticated` | Same |
| Bucket read | `authenticated`, or anyone if the bucket is **public** | |
| Bucket write | `authenticated` | |
| Channel subscribe / publish | the environment's `default_policy` for realtime, `authenticated` by default | |

In Studio the policy picker labels the `null` option for each context: *Secret keys only* on resource operations, *Default (signed-in users)* on routes, *Default* on buckets.

## When a reference can't be resolved

Pawabase checks references **when you save** the definition that contains them:

- a resource, route, bucket or flow that references an unknown policy name is **refused** with `422`, naming the field (`operations.update.policy: unknown policy 'editors'`);
- an inline condition with a bad operator or shape is refused the same way;
- a bucket that references a Python policy is refused (buckets need JSON conditions).

So the usual order is: create the policy, then reference it.

At request time the engine also **fails closed**. If a referenced policy disappears later (for example it's deleted while still in use), operations that reference it are refused, and the environment's **Overview → Definitions with problems** lists what's broken.

<Warning>
Before deleting a policy, find where it's used. The quickest way is the Platform API: list resources, routes, buckets and flows, and search their JSON for the name.
</Warning>

## Organising a policy library

As projects grow, policies become the vocabulary your team uses to talk about access. A few conventions keep that vocabulary clear.

### Name for who's admitted, not where it's used

| Good | Avoid |
| --- | --- |
| `finance_staff` | `invoices_create_policy` |
| `family_access` | `students_read` |
| `report_publisher` | `publish_route_policy` |
| `author_or_admin` | `posts_update` |

A name that describes *who* can be reused wherever those people should be admitted.

### Build in layers

<Steps>
  <Step title="Actor groups (role-only)">
    `staff`, `school_admin`, `teaching_staff`, `finance_staff`, `library_staff`. These are cheap, decided without records, and the building blocks of everything else.
  </Step>
  <Step title="Relationships">
    `family_access`, `author_or_admin`, `borrower_or_library`. An actor group OR a relationship to the record.
  </Step>
  <Step title="State">
    `report_access` (staff, or family once published), `announcement_audience`. Relationships plus record state.
  </Step>
  <Step title="Assurance">
    Combine with `mfa` in lists for sensitive operations: `["mfa", "finance_staff"]`.
  </Step>
</Steps>

### Keep role lists consistent

Inline conditions can't reference named policies, so layer-2 policies repeat the staff role list. Keep the lists identical by generating definitions from a script, or switch to **permissions** (`{"permission": "students.read"}`), so adding a role changes roles, not policies.

### Describe everything

The `description` appears in Studio's pickers and editors. Write it for the person choosing a policy for a new endpoint: *Staff always; the student and guardians once the report is published.*

## Promotion and environments

Policies are per-environment definitions:

- They're included when you [promote](/operate/environments-and-promotion) definitions; select **policies** along with the resources that reference them.
- Python policies come from project code, which is shared by every environment of a project.
- A stored policy can deliberately differ between environments, but make that a conscious decision and document it.

## Evolving a policy library safely

Policies change as your product does. These techniques keep changes safe.

<Steps>
  <Step title="Add, don't edit, when semantics change">
    If `staff` needs to mean something different for one resource, create `teaching_staff` rather than changing `staff` for everyone. Editing a shared policy changes every entry point that references it, which is powerful when intended and surprising when not.
  </Step>
  <Step title="Find every use before editing">
    Search your definitions for the name. In a definitions-as-code setup this is a `grep`; otherwise list resources, routes, buckets and flows through the Platform API.
  </Step>
  <Step title="Change in development, test, promote">
    Edit the policy in development, run your role-by-role checks, then [promote](/operate/environments-and-promotion) policies (and anything depending on them) to staging and production.
  </Step>
  <Step title="Keep a test per rule">
    One request per role per sensitive endpoint, asserting the expected status. The school tutorial's 33 checks are a model.
  </Step>
</Steps>

### Example: from roles to permissions

A project that started with role checks everywhere can migrate to permissions without downtime:

1. Define permissions on roles in Akountz (`finance.read` on `bursar`, `principal`, `admin`).
2. Change `finance_staff` from `{"role": ["admin", "principal", "bursar"]}` to `{"permission": "finance.read"}`.
3. Every entry point referencing `finance_staff` now checks the permission.
4. Adding an *accountant* role later is a role definition with `finance.read`. No policy changes.

## A catalogue of reference patterns

| Need | Reference |
| --- | --- |
| Public read | `"public"` |
| Signed-in users | `"authenticated"` |
| Server only | `null` (resource ops) or `"service"` |
| One role | `"role:editor"` |
| Several roles | `{"role": ["editor", "admin"]}` |
| A capability | `"permission:posts.publish"` |
| Owner | `"owner"` or `"owner:author_id"` |
| Owner or admin | `{"any": [{"role": "admin"}, {"owner": "author_id"}]}` |
| Tenant members | `{"eq": ["$record.org_id", "$auth.org"]}` |
| Sensitive + role | `["mfa", "role:bursar"]` |
| Named rule + extra condition | `["family_access", {"eq": ["$record.archived", false]}]` |
| Nobody (explicitly) | `"deny"` |

## Walkthrough: references for a marketplace

A marketplace has **buyers**, **sellers**, **support agents** and **admins**. Sellers belong to a **shop** (an Akountz organization). Let's design its references from scratch.

<Steps>
  <Step title="Actor groups">
    ```json
    // support
    { "role": ["support", "admin"] }
    ```
    ```json
    // shop_member: a signed-in user acting inside the record's shop
    { "all": [ { "authenticated": true }, { "eq": ["$record.shop_id", "$auth.org"] } ] }
    ```
    `shop_member` is an AND-ed equality on a record field, so on list requests it becomes `WHERE shop_id = '<active org>'`.
  </Step>
  <Step title="Products">
    | Operation | Reference | Why |
    | --- | --- | --- |
    | list, get | `public` | Anyone can browse |
    | create | `{"all": [{"authenticated": true}, {"eq": ["$input.shop_id", "$auth.org"]}]}` | Sellers create products in their own shop only |
    | update | `["shop_member", {"not": {"exists": "$input.shop_id"}}]` | Members edit, but can't move products between shops |
    | delete | `["shop_member", "mfa"]` | Deleting listings needs 2FA |
  </Step>
  <Step title="Orders">
    Orders have `buyer_id` (the owner field) and `shop_id`.
    ```json
    // order_party: the buyer, the shop, or support
    { "any": [ { "owner": "buyer_id" }, { "eq": ["$record.shop_id", "$auth.org"] }, { "role": ["support", "admin"] } ] }
    ```
    | Operation | Reference |
    | --- | --- |
    | list, get | `order_party` |
    | create | `authenticated` (via a checkout route, not directly) |
    | update | `["shop_member", {"in": ["$input.status", ["shipped", "cancelled"]]}]` |
    | delete | *disabled* |
  </Step>
  <Step title="Routes">
    | Route | Reference |
    | --- | --- |
    | `POST /checkout` | `authenticated` |
    | `POST /orders/{id}/refund` | `["mfa", "support"]` |
    | `GET /shop/dashboard` | `{"exists": "$auth.org"}` |
  </Step>
  <Step title="Storage">
    | Bucket | Read | Write |
    | --- | --- | --- |
    | `product-images` (public) | anyone | `{"eq": ["$object.segments.0", "$auth.org"]}` |
    | `invoices` | `{"eq": ["$object.segments.0", "$auth.org"]}` | `service` |
  </Step>
</Steps>

Eight names and a handful of inline conditions describe the whole marketplace's access model, and every entry point uses the same vocabulary.

## FAQ

<AccordionGroup>
  <Accordion title="Can a named policy reference another named policy?">
    Not inside its condition: conditions reference context values, not policies. Compose at the reference instead, with a list (`["staff", "mfa"]`), or duplicate the small role list.
  </Accordion>
  <Accordion title="Do built-ins change between versions?">
    The six built-ins are part of the platform's contract and are stable. If you need a variation, define your own name rather than overriding a built-in.
  </Accordion>
  <Accordion title="Why is my list reference named 'mfa+role:bursar' in logs?">
    Lists are merged into one policy named after its parts, so logs and refusal messages show exactly which combination applied.
  </Accordion>
  <Accordion title="Is there a performance difference between named and inline?">
    No. Both resolve to the same condition. Named policies are cached with the environment's configuration.
  </Accordion>
</AccordionGroup>

## Named-policy reuse across resources, routes and flows, in depth

The value of a named policy is that the same name resolves identically everywhere it's referenced — a resource operation, a custom route's `policy` field, a bucket's `read_policy`, a channel rule's `subscribe`, and a flow's `policy.check` block all call the same `PolicyEngine.resolve_ref` with the same string, against whatever context that entry point builds. This section works through what that sharing actually looks like end to end, and the two situations where it's easy to get wrong: a name meant for one shape of entry point used at another, and a rename that misses a reference.

### The same policy, five different contexts

Take `family_access` from the school system, defined once:

```json
{
  "name": "family_access",
  "condition": { "any": [
    { "role": ["admin", "principal", "teacher", "bursar", "librarian"] },
    { "owner": "user_id" },
    { "contains": ["$record.guardian_user_ids", "$auth.user_id"] }
  ] }
}
```

Referencing `"family_access"` from five places evaluates the *same condition object* each time, but against five different contexts, because each entry point builds `$record` (and everything else) differently:

| Entry point | Reference | `$record` at evaluation time |
| --- | --- | --- |
| `students.get` | `"policy": "family_access"` | the student row being fetched |
| `students.list` | `"policy": "family_access"` | each row, during planning/residual (see [pushdown](/policies/pushdown)) |
| `POST /students/{id}/transcript` (custom route) | `"policy": "family_access"` | `null` — routes have no `$record` at all |
| `policy.check` inside a flow | `{"block": "policy.check", "config": {"policy": "family_access", "record": "{{ steps.load_student.output }}"}}` | whatever record the flow explicitly passed in |
| bucket `student-photos` read | *(not used here — see below)* | — |

The route row above is the one worth pausing on: `family_access` references `$record.guardian_user_ids` and the `owner` shorthand's `$record.<column>`, but a **custom route has no record in its context at all** (per [enforcement points](/policies/enforcement-points#custom-routes)). Evaluated there, every `$record.*` path resolves to `null` via `lookup()`'s default-on-missing behavior, `contains(null, ...)` and the `owner` shorthand's `eq(null, $auth.user_id)` both evaluate to `false` (assuming the caller isn't literally `null`), and the whole condition degrades to just its first branch: staff roles. That's not a validation error — the reference resolves fine, the condition is well-formed — it's a **silent semantic mismatch**: a policy written with a record-shaped resource in mind, reused on a route, quietly stops admitting guardians and students, without any error telling you so.

This is the practical reason [names should describe *who's admitted*, not *where they're used*](#name-for-whos-admitted-not-where-its-used) — but it cuts both ways: a policy name that reads like it should work anywhere (`family_access`) can still be **record-shaped** in its condition even though nothing about the name says so. Before reusing a named policy at a new kind of entry point, check whether its condition mentions `$record` at all; if it does, confirm the new entry point actually populates one, or the reuse will silently narrow (or, in an `any` starting with a broad branch, sometimes silently widen) what the policy admits there.

### Reuse that works cleanly: role- and permission-only names

Policies built entirely from `role`, `permission`, `authenticated`, `service`, `kind`, `scope`, `aal` — the shorthands whose column notes "decided without the record" in [shorthands](/policies/shorthands#at-a-glance) — never touch `$record` or `$input`, so they resolve identically at *every* entry point, records or none: a resource operation, a route, a function, a flow's `trigger.http`, a bucket, a channel rule, and a `policy.check` block all get the same answer for the same caller. This is why the "actor group" layer in a [layered policy library](#build-in-layers) is the safest, most freely reusable tier: `staff`, `finance_staff`, `library_staff` work anywhere without the record-shape caveat above.

### What "ambiguous" means for a name, precisely

There is exactly one place a name is genuinely ambiguous rather than merely reused for the wrong shape of entry point: when a **stored policy** and a **parameterised built-in** would both match the same string. `resolve_ref` checks stored/Python/built-in names first (`if ref in self.policies`), and only falls through to parsing `kind:argument` syntax if the string isn't already a registered name:

```python
if isinstance(ref, str):
    if ref in self.policies:
        return self.policies[ref]
    kind, _, argument = ref.partition(":")
    if argument and kind in ("role", "permission", "owner", "scope", "kind"):
        return Policy(ref, {kind: argument})
```

In practice this particular collision can't happen for a *stored* policy: names are validated against `^[a-z][a-z0-9_-]{0,62}$`, which has no colon in it, so Studio and the Platform API both refuse to save a policy named `"role:librarian"` before the ambiguity could ever arise. The check in `resolve_ref` (registry lookup before colon-parsing) is really there for the **Python policy** registry, which enforces no such naming pattern — nothing stops `@policy("role:librarian")` in project code. If a Python policy is ever registered under a string that happens to look like `kind:argument`, every reference to that string resolves to the Python function, never to the shorthand, with no error and no warning at save time. The fix is the same preventive one either way: keep Python policy names out of `kind:argument` shape, and prefer the project-prefixed convention from [naming and isolation](/policies/python-policies#naming-and-isolation) (`school.office_network`), which can't collide with parameterised syntax at all since it contains a `.` before any `:` would appear.

A second, milder ambiguity: a **stored policy with the same name as a built-in** (`"authenticated"`, `"owner"`, `"mfa"`, etc.) overrides the built-in for that environment, as noted [above](#the-built-ins), because `PolicyEngine.__init__` merges dictionaries as `{**BUILTIN_POLICIES, **(python or {}), **(policies or {})}` — stored policies are merged in last, so they win. This isn't a resolution-order accident so much as a deliberate escape hatch (redefining what `authenticated` means for one environment), but it means every place in your documentation, your team's mental model, and even this documentation site that says "`authenticated` means `{"authenticated": true}`" is describing the **built-in**, not necessarily what `"authenticated"` resolves to in a specific environment that has overridden it. If you ever do this, say so loudly in the policy's own `description`, because every other engineer on the project will otherwise assume the built-in's well-known behavior.

### Resolution order, restated precisely

Putting the exact order in one place, since it determines every case above:

1. Is the reference a `Policy` object already? (Only reachable programmatically, not from JSON.) Return it as-is.
2. Is the reference `None`? Return the environment's `authenticated` policy — the built-in, or an override if one exists (see above).
3. Is the reference a `bool` or a `Mapping` (an inline condition)? Validate it and wrap it in an anonymous `Policy` named `"inline"`.
4. Is the reference a `list`? Resolve every item recursively (following this same order for each), refuse if any resolved item has a Python handler, otherwise merge all their conditions into one `{"all": [...]}` named by joining their names with `+`.
5. Is the reference a `str`? Check the **merged name registry** first — built-ins, then Python policies, then stored policies, with each later group able to override an earlier one by name. If found, return it.
6. Still a `str` and not found? Split on the first `:`. If the prefix is one of `role`, `permission`, `owner`, `scope`, `kind` and there's a non-empty argument, build a parameterised inline policy.
7. Nothing matched: raise `PolicyError("unknown policy ...")`.

Steps 5 and 6 are where the "stored beats Python beats built-in, and names beat parameterised syntax" rule actually lives in code — everything in the earlier [names](#1-names) and [parameterised built-ins](#2-parameterised-built-ins) sections is this same logic, described for someone who isn't reading Python.

## Flows: `policy.check` as a fourth reuse pattern

The four forms of reference (name, parameterised, inline, list) all pass through `resolve_ref` identically whether they're attached to a resource, a route, or used inside a flow's `policy.check` block — the block just calls `engine.check(config["policy"], context)` with a context the flow assembles itself from `record` and `input` fields you configure on the block. This has one consequence worth calling out for named-policy reuse specifically: because the flow author chooses exactly what becomes `$record` and `$input` for that one check, a record-shaped policy like `family_access` can be reused **correctly** inside a flow even though it can't be reused correctly on a bare custom route — the flow explicitly supplies a record, where the route simply has none:

```text
http (policy: authenticated) → resource.get student → policy.check family_access (record = {{ steps.load_student.output }})
  → allowed: continue
  → denied: error.raise 404
```

This is the general escape valve for "I want to reuse a record-shaped named policy somewhere that doesn't naturally have a record": put a `resource.get` (or any block that loads the relevant object) before the `policy.check`, and pass its output in as `record`. It's exactly what the [enforcement points](/policies/enforcement-points#inside-flows) page's example does, and it's the reason `policy.check` exists as a separate block rather than routes simply gaining a `record` parameter of their own — the record has to come from *somewhere*, and a flow is where "load a record, then check a policy against it" is expressed as an explicit, visible step rather than an implicit one.
