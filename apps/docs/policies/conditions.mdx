## What a condition is

A **condition** is a piece of JSON that evaluates to true or false against a context. There are no variables, no functions and no loops. That restriction is the point: a condition can be validated when it is saved, shown as a tree in Studio, planned into SQL for lists, and read by someone who does not write code.

```json
{
  "all": [
    { "authenticated": true },
    { "any": [
      { "eq": ["$record.owner_id", "$auth.user_id"] },
      { "role": "admin" }
    ] }
  ]
}
```

Every condition is one of five **forms**. The parser, the validator and Studio's builder all know exactly these five:

| Form | Looks like | Means |
| --- | --- | --- |
| **Constant** | `true` or `false` | Always allow, or always refuse |
| **Group** | `{"all": [...]}`, `{"any": [...]}`, `{"not": ...}` | Combine other conditions |
| **Comparison** | `{"eq": [left, right]}` | Compare two operands. Twelve operators |
| **Check** | `{"exists": "$path"}` | Ask one thing about one value: `exists`, `truthy`, `empty` |
| **Shorthand** | `{"role": "admin"}`, `{"owner": "owner_id"}` | A short form that expands to one of the above. Eight of them |

An object always has **exactly one key**. `{"eq": [...], "ne": [...]}` is not a condition with two checks. It is an error. To require both, wrap them: `{"all": [{"eq": ...}, {"ne": ...}]}`.

Everything on this page was run against the real engine, and the results are quoted as they came back.

## Constants

`true` and `false` are conditions in their own right:

| Condition | Effect | Where it is used |
| --- | --- | --- |
| `true` | Passes for everyone | The built-in `public` policy |
| `false` | Passes for nobody except a secret key | The built-in `deny` policy |

A policy whose whole condition is `false` is the same as `deny`. A condition with a constant inside a group is legal and occasionally useful while editing (`{"all": [true, {"role": "admin"}]}` is just the role check), but a constant buried in a real policy is usually a leftover.

## Groups

Three combinators, and they compose to any depth:

| Group | True when | Empty group |
| --- | --- | --- |
| `{"all": [c1, c2, ...]}` | **Every** child is true | **True** |
| `{"any": [c1, c2, ...]}` | **At least one** child is true | **False** |
| `{"not": c}` | The child is **false** | n/a. `not` takes exactly one condition |

The empty cases matter, and they run in opposite directions:

```json
{ "all": [] }     // true:  "everyone passes", an AND over nothing
{ "any": [] }     // false: "nobody passes",   an OR over nothing
```

Studio shows both as hints under an empty group: *No rules: everyone passes.* for **All of**, and *No rules: nobody passes.* for **Any of**. An `all` group that loses its last child, because someone deleted a rule, therefore becomes **open**. When you remove the last rule from a policy, check what the group now means.

### Evaluation order

`all` and `any` stop at the first child that decides them, so the order of children is the order of evaluation, left to right. For conditions that only read values this changes nothing, except that a child that would raise an error is never reached. Put cheap, decisive checks first (`authenticated`, a role) and per-row comparisons later.

### Nesting

The engine accepts any depth. Studio's builder offers a **Group** button up to **three levels deep** (the root group and two nested levels), which is enough for nearly every real policy. A condition that is deeper than that still evaluates, and the builder still displays and edits it. It only stops offering the **Group** button on the deepest level.

Deep nesting is a readability problem before it is a technical one. When a condition needs more than two levels, split it into [stored policies](/policies/references) and combine them with a list, so each piece has a name.

## Comparisons

A comparison has an operator and exactly two operands:

```json
{ "eq": ["$record.status", "published"] }
{ "in": ["$auth.org_role", ["owner", "admin"]] }
{ "gte": ["$input.qty", 1] }
```

| Operators | Meaning |
| --- | --- |
| `eq`, `ne` | Equal, not equal |
| `gt`, `gte`, `lt`, `lte` | Ordering |
| `in`, `not_in` | The left value is, or is not, one of the right-hand list |
| `contains` | The left value (a list or a string) contains the right |
| `starts_with`, `ends_with` | String prefix and suffix |
| `matches` | The left value contains a match for a regular expression |

Each has its own rules for null, types and edge cases, collected in [Operators](/policies/operators). The two operands are called **left** and **right**, and for most operators the order matters.

## Checks

A check asks one question of one value, written as the operator with a single operand:

| Check | True when |
| --- | --- |
| `{"exists": "$path"}` | The value is **not null** (present and not empty-as-null) |
| `{"truthy": "$path"}` | The value is truthy: not `null`, `false`, `0`, `""`, `[]` or `{}` |
| `{"empty": "$path"}` | The value is falsy. The opposite of `truthy` |

These were run against a record with `nothing: null`, `n: 5`, `tags: ["a", "b"]` and `status: "open"`:

| Condition | Result |
| --- | --- |
| `{"exists": "$record.nothing"}` | false |
| `{"exists": "$record.missing"}` | false |
| `{"exists": "$record.status"}` | true |
| `{"truthy": "$record.n"}` | true |
| `{"truthy": "$record.tags"}` | true |
| `{"empty": "$record.tags"}` | false |
| `{"empty": "$record.nothing"}` | true |
| `{"empty": "$record.missing"}` | true |

`exists` and `truthy` differ for `0`, `false` and the empty string: `exists` is true for them and `truthy` is false. A boolean column set to `false` **exists** and is not **truthy**, so use `truthy` to test a flag and `exists` to test presence.

Remember that `exists` is false for an explicit `null`. A submitted `{"price": null}` is "not present" to `exists`, which is how a guard written as `{"not": {"exists": "$input.price"}}` can be walked past by sending `null`. See [the overview](/policies/overview#exists-is-false-for-null-so-not-exists-allows-nulling).

## Shorthands

Eight short forms stand for longer conditions, so common rules read as one line:

```json
{ "role": "admin" }                  // any of the caller's roles is "admin"
{ "owner": "user_id" }               // signed in, and $record.user_id is the caller
{ "permission": "posts.write" }      // the caller has that permission
```

They are covered in [Shorthands](/policies/shorthands). Two facts matter here: a shorthand is evaluated by **expanding it** to the longer condition first, and the **planner expands it too**, which is why `owner` becomes a SQL filter on a list. A shorthand is never slower or less precise than what it expands to.

## Operands: paths and literals

Each side of a comparison is an **operand**, and an operand is one of two things:

| Operand | Written | Meaning |
| --- | --- | --- |
| A **path** | A string starting with `$` | A lookup into the context |
| A **literal** | Anything else | Itself: a string, number, boolean, `null` or list |

```json
{ "eq": ["$record.status", "published"] }
```

`$record.status` is a path, read from the record. `"published"` is a literal. A path may be on either side, or both: `{"eq": ["$record.owner_id", "$auth.user_id"]}` compares two paths.

### Path syntax

A path is `$` followed by names separated by dots. Each name steps into the value before it:

| Path | Reads |
| --- | --- |
| `$auth.user_id` | The `user_id` key of `auth` |
| `$auth.roles.0` | The **first** item of the `roles` list. A digit indexes a list |
| `$auth.roles.5` | Nothing, when there is no sixth item |
| `$auth.claims.app.plan` | A nested claim, three levels down |
| `$request.query.q` | The `q` query parameter |
| `$record.address.city` | A nested value inside a JSON column |
| `$env`, `$project` | The environment name and the project ref |
| `$now` | The current date and time, as a date, not text |

A path that does not resolve is **empty** (`null`), and it does so silently: a missing key, a missing list item, a step into something that is not a container. There is no error and no warning, which makes a typo in a path a quiet failure. See [missing equals missing](/policies/overview#a-missing-value-equals-a-missing-value).

### Literals

Anything that does not begin with `$` is a literal, and JSON's own types carry through:

| Literal | Written as |
| --- | --- |
| Text | `"published"` |
| A number | `10` or `2.5` |
| A boolean | `true` or `false` |
| Nothing | `null` |
| A list | `["owner", "admin"]`. Lists are literals too, for `in` and `not_in` |

A list may contain only literals. A path inside a list is not resolved: `{"in": ["$auth.org", ["$record.a", "$record.b"]]}` compares against the strings `"$record.a"` and `"$record.b"`, not against the record's values. To compare against two record values, use `any` with two comparisons.

### A literal that starts with a dollar sign

To compare against text that really begins with `$`, double it. `$$5` is the literal text `$5`, and only the first `$` is removed:

| Operand | Is |
| --- | --- |
| `"$record.status"` | A path |
| `"$$record.status"` | The text `$record.status` |
| `"$$literal"` | The text `$literal` |

This was run: `{"eq": ["$$literal", "$literal"]}` is false, because the right side is a **path** that resolves to nothing, not the literal.

## What saving checks, and what it does not

A condition is validated when you save a policy, and again wherever it is attached inline. The validator checks **shape**:

| You saved | Message |
| --- | --- |
| `null`, `"x"`, `1`, `[]` or `{}` | `condition: a condition is true, false, or an object with one key` |
| An object with two keys | The same message |
| `{"eq": 1}`, `{"eq": [1]}` or `{"eq": [1, 2, 3]}` | `condition.eq: expected [left, right]` |
| `{"all": {}}` | `condition.all: expected a list of conditions` |
| `{"all": [{"zz": 1}]}` | `condition.all[0]: unknown operator 'zz'` |
| `{"not": []}` | `condition.not: a condition is true, false, or an object with one key` |
| `{"nope": 1}` | `condition: unknown operator 'nope'` |
| `{"matches": ["$x", "("]}` | `condition.matches: invalid pattern: missing ), unterminated subpattern at position 0` |

The message names the **path** of the problem (`condition.all[0]`), so a deeply nested mistake points at the child that is wrong. These are `422` responses from the platform API, and in Studio they appear as the error under the form.

It does **not** check meaning, and these all save without complaint:

| Accepted | Why it is worth knowing |
| --- | --- |
| `{"role": {}}` | A shorthand's argument is not checked. It evaluates to nobody |
| `{"authenticated": "anything"}` | Evaluated as truthy. **`"false"` is a non-empty string, so it means true** |
| `{"exists": ["a"]}` | A check on a list literal, which is always present |
| `{"matches": ["$x", "$y"]}` | A pattern taken from a path is not validated, and a bad one fails at evaluation |
| `{"eq": ["$nope", "$alsono"]}` | Two paths that do not exist, which is true |
| `{"all": [true, false]}` | Constants inside a group |

The regular expression is validated only when it is a **literal**. A pattern read from a path (`$record.pattern`) is compiled at evaluation, and a bad one raises an error then, not at save time. See [Operators](/policies/operators#patterns-matches).

## How a condition is evaluated

Two modes, with the same grammar:

| Mode | Used for | Question |
| --- | --- | --- |
| **Check** | One record, one request: `get`, `create`, `update`, `delete`, routes, storage, channels | May this caller do this to this record? |
| **Plan** | A list request, before any row is read | Which rows could this caller possibly see? |

A **check** evaluates the whole condition against the full context and returns a decision: allowed or refused, with the policy's name and a reason such as `policy 'own_rows' allowed`.

A **plan** evaluates only what it can without a record. Everything that depends on the caller and the request is decided now. What remains, the parts that mention `$record` or `$input`, is kept. If nothing remains the plan is simply allow or refuse. If the remainder is a conjunction of equalities between one record column and a known value, they become SQL filters; anything else is checked per row. The algorithm and its consequences have their own page: [SQL pushdown](/policies/pushdown).

The practical consequence for writing conditions: **put what is known about the caller in `all` with what is true of the row, and let the engine do the splitting.** You do not mark which part is which.

## The rule builder in Studio

Wherever a policy can be edited (a stored policy's **Who passes**, a **Custom rules…** choice in the picker, a subscription's **Only when…**), Studio shows the condition as a **tree of rules and groups** instead of JSON. The builder reads whatever JSON it is given into that tree and writes it back, so anything you can type in the **JSON** tab you can also see as rules, and the reverse.

### Groups

A group's header has three choices, followed by the words *these rules pass*:

| Choice | Stores | Reads as |
| --- | --- | --- |
| **All of** | `{"all": [...]}` | Every rule passes |
| **Any of** | `{"any": [...]}` | At least one passes |
| **None of** | `{"not": {"any": [...]}}` (or `{"not": rule}` for one rule) | No rule passes |

Beneath the header are the group's rules, joined by the word **and** (for **All of**) or **or** (for **Any of** and **None of**), and two buttons: **Rule** adds a rule and **Group** adds a nested **Any of** group. A group can be removed with the trash button, and the root group cannot.

The root group is always shown, even for a simple condition. A condition with one rule and no group is shown as an **All of** with one rule, and written back as that single rule, with the group flattened away. So a `{"role": "admin"}` stays `{"role": "admin"}` after a round trip through the builder.

### Rules

Each rule begins with a **type** chooser:

| Type | Label in the chooser | Stores | Fields |
| --- | --- | --- | --- |
| Signed in | **Is signed in** | `{"authenticated": true}` | A choice: **yes** or **no (anonymous)** |
| Role | **Has role** | `{"role": "admin"}` | Text, placeholder `admin, editor`. A comma makes it a list |
| Permission | **Has permission** | `{"permission": "posts.write"}` | Text, a comma makes it a list |
| Owner | **Owns the record (field)** | `{"owner": "owner_id"}` | The column name |
| Secret key | **Uses a secret key** | `{"service": true}` | None |
| Second factor | **Signed in with 2FA** | `{"aal": "aal2"}` | None |
| Key scope | **Key has scope** | `{"scope": "resource:write"}` | Text |
| Caller kind | **Caller kind is** | `{"kind": "user"}` | Text, placeholder `user` |
| Comparison | **Compare values…** | `{"eq": [left, right]}` | Left, an operator, right |
| Check | **Check a value…** | `{"exists": "$input."}` | A path and one of the checks |
| Never | **Nobody (always deny)** | `false` | None |

A rule that is the constant `true` is shown as **Anyone (always allow)**, and a rule the builder does not recognise, such as a condition whose shape it cannot read, is shown as **Custom (JSON)** with a JSON box. **The builder never drops what it does not understand.** A hand-written condition with an unusual form survives a visit to the builder unchanged.

A new **Compare values…** rule starts as `{"eq": ["$record.user_id", "$auth.user_id"]}`, which is the most common comparison. A new **Check a value…** starts as `{"exists": "$input."}` with the path unfinished.

### Comparisons

A comparison rule has a **left** path or value, an operator chooser, and a **right** value. The operator labels:

| Label | Operator | Label | Operator |
| --- | --- | --- | --- |
| equals | `eq` | is one of | `in` |
| does not equal | `ne` | is not one of | `not_in` |
| `>` | `gt` | contains | `contains` |
| `≥` | `gte` | starts with | `starts_with` |
| `<` | `lt` | ends with | `ends_with` |
| `≤` | `lte` | matches regex | `matches` |

A **Check a value…** rule offers **exists**, **is set / true** (`truthy`) and **is empty** (`empty`).

### How what you type becomes JSON

The builder turns text into a typed value, so you do not write quotes:

| You type | Stored as |
| --- | --- |
| `$auth.user_id` | The path `"$auth.user_id"`. Anything starting with `$` stays text |
| `true` or `false` | A boolean |
| `null` | `null` |
| `42` or `2.5` | A number |
| `published` | The text `"published"` |
| `a, b, c` after **is one of** or **is not one of** | The list `["a", "b", "c"]`, with each item typed the same way |

The consequence: a text value that **looks like** a number becomes a number. Typing `007` stores `7`. If a column holds the text `"007"`, edit the **JSON** tab so the value is quoted. Similarly, typing `true` into a text comparison stores a boolean.

Left and right accept a **datalist of suggested paths**:

| Suggestion | Real? |
| --- | --- |
| `$auth.user_id`, `$auth.email`, `$auth.roles`, `$auth.permissions`, `$auth.aal` | Yes |
| `$record.id`, `$record.owner_id`, `$record.user_id`, `$input.` | Yes (the column must exist) |
| `$request.ip`, `$request.method` | Yes |
| `$credential.is_service`, `$credential.scopes` | Yes |
| `$env`, `$now` | Yes |
| `$event.name` | Yes, in a subscription's condition |
| **`$auth.org_id`** | **No.** The key is **`$auth.org`** |
| **`$event.data`** | **No.** The key is **`$event.payload`** |

<Warning>
Two of Studio's own suggestions do not exist, and **a path that does not exist is not an error**. It resolves to nothing, and two nothings are equal. A tenancy policy written with `$auth.org_id` compares the record to nothing, and a subscription filter written with `$event.data` never matches. Type `$auth.org` and `$event.payload...` yourself. The [context reference](/policies/context) lists the real keys for every entry point.
</Warning>

### Empty groups

A group with no rules reads *No rules: everyone passes.* (**All of**) or *No rules: nobody passes.* (**Any of**), and the builder writes `true` or `false` for an empty root. If you clear every rule from a stored policy and save it, it becomes **public**. Review the hint before you save.

### Editing JSON directly

The **JSON** tab shows the condition exactly as it will be stored, and changes there appear in the builder at once. Edit JSON when you need:

- A **quoted number** the builder would unquote.
- A **list** inside a condition other than `in` and `not_in`.
- A **regular expression** with characters the text box mangles.
- A **deep** nesting the builder does not offer.

An invalid condition is not saved. The error names the path, as in [the validation table](#what-saving-checks-and-what-it-does-not).

## From requirements to conditions

Most policies start as a sentence. This table translates the common ones.

| Requirement | Condition |
| --- | --- |
| Anyone can read | `true` (the `public` policy) |
| Only signed-in users | `{"authenticated": true}` |
| Only the record's owner | `{"owner": "user_id"}` |
| Owner or an admin | `{"any": [{"owner": "user_id"}, {"role": "admin"}]}` |
| Staff or the owner, never a banned user | `{"all": [{"not": {"role": "banned"}}, {"any": [{"role": "staff"}, {"owner": "user_id"}]}]}` |
| Members of the record's organisation | `{"all": [{"exists": "$auth.org"}, {"eq": ["$record.org_id", "$auth.org"]}]}` |
| Organisation admins only | `{"in": ["$auth.org_role", ["owner", "admin"]]}` |
| Only published records, or your own | `{"any": [{"eq": ["$record.status", "published"]}, {"owner": "author_id"}]}` |
| Nobody may set `status` to `published` except editors | `{"any": [{"role": "editor"}, {"ne": ["$input.status", "published"]}]}` |
| At most ten items per request | `{"lte": ["$input.qty", 10]}` |
| Writing requires a second factor | `{"aal": "aal2"}` |
| Only your servers | `{"service": true}` |
| Keys that may write | `{"scope": "resource:write"}` |
| Pro plan customers (trusted claim) | `{"eq": ["$auth.claims.app.plan", "pro"]}` |
| Only from a particular host | `{"eq": ["$request.ip", "203.0.113.7"]}` |
| Path under the caller's own folder (storage) | `{"eq": ["$object.segments.0", "$auth.user_id"]}` |

Each of these was evaluated. The ones involving `$record` and `$auth` were also run as resource policies with real callers, and the results are in [Policy recipes](/policies/recipes).

## Writing conditions people can read

A policy is read far more often than it is written. A few habits keep it legible.

**Prefer a shorthand to the thing it expands to.** `{"owner": "user_id"}` is one idea. Its expansion is a group with two comparisons, and is also less safe to retype.

**Put the caller before the record.** Conditions that establish who is asking (`authenticated`, a role, `exists` on a claim) belong at the start of an `all`, so the reader learns the precondition before the comparison.

**Use the description.** A stored policy has a description that Studio shows in lists. Say what the rule **allows**, not how it is built: *Public notes, the owner's own, or anything for staff*.

**Split at the seams.** A condition with three `any` branches that each stand alone is three policies. Name them, and combine with a list (see [References](/policies/references#lists)).

**Name by intent.** `own_rows`, `org_admin`, `published_or_owned`. Names are how a policy is referenced everywhere, and a name that says nothing (`policy2`) hides what a resource allows.

**Keep literals visible.** A role name or a status value inside a condition is a magic string. If it appears in more than one policy, a rename has to find them all, so keep such values few.

**Avoid double negatives.** `{"not": {"ne": [...]}}` is `eq`. `{"not": {"not_in": [...]}}` is `in`.

## Where conditions are used

The same language appears in several places, with a different context in each:

| Place | The condition decides | Context |
| --- | --- | --- |
| A stored policy | Anything that references it | The entry point's |
| An **inline** condition in a picker | That one attachment | The entry point's |
| A bucket's read and write policy | Access to objects | `auth`, `credential`, `project`, `env`, `object` |
| A realtime channel rule | Subscribe, publish | `auth`, `credential`, `channel`, `input` |
| An **event subscription's** **Only when…** | Whether the subscription fires | `{"event": {...}}` |
| A **Check policy** block | Which edge a flow follows | `auth`, `credential`, `project`, `env`, and the `record` and `input` you pass |

A condition written for one place may read paths that do not exist in another. `$record` is empty for a bucket and a route, `$object` exists only for storage, and `$event` only for subscriptions. See [the context reference](/policies/context).

## Testing a condition

Three ways, from cheapest to most realistic.

| Way | How | What it proves |
| --- | --- | --- |
| **A Check policy block** | A flow with `policy.check`, a `policy` (name or inline) and the `record` and `input` you choose. It follows `allowed` or `denied` | The condition's logic for a context you control |
| **A real request** | Call the endpoint with a publishable key and a user token for each caller you care about | The whole path, including the plan, SQL and status codes |
| **A direct evaluation** | In a Python test, call the engine's `evaluate` with a context | Fast unit tests of many cases |

Test **both sides**: the caller who should pass, and the ones who should not, including a signed-out caller, a stranger, a caller with a missing claim, and a record with `null` in each column the condition reads. Never test with a secret key, which passes before the condition is read. See [Testing and debugging](/policies/debugging).

## Grammar summary

```text
condition  := true | false | group | comparison | check | shorthand

group      := {"all": [condition, ...]}
            | {"any": [condition, ...]}
            | {"not": condition}

comparison := {OP: [operand, operand]}
OP         := eq | ne | gt | gte | lt | lte | in | not_in
            | contains | starts_with | ends_with | matches

check      := {"exists": operand} | {"truthy": operand} | {"empty": operand}

shorthand  := {"authenticated": bool}
            | {"role": string | [string]}
            | {"permission": string | [string]}
            | {"owner": column}
            | {"service": bool}
            | {"kind": string}
            | {"scope": string}
            | {"aal": string}

operand    := "$path" | "$$text" | literal
path       := name ("." (name | index))*
literal    := string | number | boolean | null | [literal, ...]
```

An object has exactly one key. Anything else is a validation error.


## Condition bugs, by symptom

Most condition problems are one of a handful of mistakes. Matching the symptom to the cause is faster than rereading the whole condition.

| Symptom | Likely cause | Check |
| --- | --- | --- |
| A policy that should refuse lets everyone through | A path that resolves to nothing compared with another nothing | Print the context for a request and look for the key. `$auth.org_id` is `$auth.org` |
| A policy that should allow refuses everyone | A comparison between a number and a text with a decimal, or a `$now` comparison, or a left side that is `null` | Compare types: `5` and `5.0` are different, and a date is not text |
| It works for users and fails for a signed-out caller, or the reverse | A missing `{"authenticated": true}` | See [the overview](/policies/overview#a-plain-eq-on-an-owner-column-fails-open) |
| An `in` that never matches | The right side is a **string**, not a list | `{"in": ["$x", "abc"]}` compares against the characters `a`, `b`, `c` |
| A role check that never matches | Case. Roles are compared exactly | `Admin` is not `admin` |
| A permission list that requires all | `permission` with a list needs **every** permission | Use `any` of single permissions for "one of" |
| A role list that requires none | `role` with an empty list is false | An empty list matches nobody |
| A list shows too few rows | A residual per-row check after the page was fetched | See [pushdown](/policies/pushdown#what-a-residual-does-to-pages) |
| A save is refused with `expected [left, right]` | A comparison with one or three operands | Two operands exactly |
| A save is refused with `unknown operator` | A typo, or an operator from another language (`neq`, `and`, `or`) | The names are `ne`, `all`, `any` |
| `matches` finds too much | It is a **search**, not a full match | Anchor with `^` and `$` |
| `contains` is case sensitive | Yes, always | Lower-case in the data, or use `matches` with `(?i)` |

The operator names are a frequent trip: documents written for other systems use `neq`, `and` and `or`. Pawabase's are `ne`, `all` and `any`.

## A worked design: nested conditions

A document service has these rules: a document is readable by its owner, by anyone in the owner's organisation if it is marked `shared`, by an administrator of that organisation, and by anyone if it is `public`. Nobody who is banned may read anything.

Written as one condition it nests three deep:

```json
{
  "all": [
    { "not": { "role": "banned" } },
    { "any": [
      { "eq": ["$record.visibility", "public"] },
      { "owner": "owner_id" },
      { "all": [
        { "exists": "$auth.org" },
        { "eq": ["$record.org_id", "$auth.org"] },
        { "any": [
          { "eq": ["$record.visibility", "shared"] },
          { "in": ["$auth.org_role", ["owner", "admin"]] }
        ] }
      ] }
    ] }
  ]
}
```

It is correct, and it is hard to review. A **list** of references means every one of them must pass, so the seam to split at is the outer `all`: the ban check and the visibility rule are separate ideas joined by `and`. The `or` of three branches stays together, because a list cannot express `or`.

| Stored policy | Condition |
| --- | --- |
| `not_banned` | `{"not": {"role": "banned"}}` |
| `readable_document` | The `any` of the three branches: public, owner, or in the owner's organisation with the visibility rules |

and the resource's `list` and `get` take both as a list:

```json
["not_banned", "readable_document"]
```

Each policy now has a name that says what it allows, `not_banned` can be reused on other resources, and a change to the ban rule touches one definition. The branches inside `readable_document` can be split further only if you are willing to repeat the `all` around them, since `or` cannot be expressed across a list. See [References](/policies/references#lists).

## Questions that come up

<AccordionGroup>
  <Accordion title="Can a condition read a database value that is not on the record?">
    No. A condition sees only the context. For a lookup, use a [Python policy](/policies/python-policies), or copy the value onto the record.
  </Accordion>
  <Accordion title="Can I use arithmetic or string functions?">
    No. There are no functions. Compare to a stored value, or compute it in a flow before the write.
  </Accordion>
  <Accordion title="Why does my regex save and then fail?">
    A pattern from a path is compiled when it is evaluated, not when you save. Only a literal pattern is checked at save time.
  </Accordion>
  <Accordion title="How do I express 'at least two of these three'?">
    With `any` of three `all` pairs. There is no counting operator.
  </Accordion>
  <Accordion title="Is the authenticated shorthand with false the same as signed out?">
    Yes. `{"authenticated": false}` expands to a comparison of `$auth.authenticated` with `false`, which is true for a signed-out caller. It is rarely what you want, since it admits only anonymous callers.
  </Accordion>
  <Accordion title="Does the order of keys in an object matter?">
    No, an object has one key. The order of items in `all` and `any` is evaluation order.
  </Accordion>
  <Accordion title="Can I put a comment in a condition?">
    No. Use the policy's description.
  </Accordion>
</AccordionGroup>

## What to remember

- **Five forms: constants, groups, comparisons, checks, shorthands.** One key per object.
- **`all` of nothing is true. `any` of nothing is false.**
- **`$` starts a path. `$$` is a literal dollar.** Everything else is a literal.
- **A missing path is empty, not an error.** Two empties are equal.
- **Saving checks shape, not meaning.** A shorthand's argument and a path-built regex are not checked.
- **Studio's builder keeps what it does not understand** and suggests two paths that do not exist.
- **Put identity before the record,** and let the planner split the rest.
