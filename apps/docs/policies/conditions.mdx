A policy's **condition** is a small expression language written in JSON. It has no variables, no loops and no functions. That's a feature: every condition can be read by a person, rendered by Studio as a form, validated before saving, and partially evaluated so it can be turned into SQL.

This page defines the whole language. If you only read one reference page about policies, read this one.

## The five forms

Every condition is exactly one of these:

| Form | Shape | Example |
| --- | --- | --- |
| **Boolean** | `true` or `false` | `true` |
| **Group** | `{"all": [...]}`, `{"any": [...]}`, `{"not": ...}` | `{"any": [c1, c2]}` |
| **Comparison** | `{"<operator>": [left, right]}` | `{"eq": ["$record.owner_id", "$auth.user_id"]}` |
| **Check** | `{"exists" \| "truthy" \| "empty": operand}` | `{"exists": "$input.email"}` |
| **Shorthand** | `{"<shorthand>": argument}` | `{"role": "admin"}` |

Two rules keep the grammar unambiguous:

1. **An object has exactly one key.** `{"role": "admin", "authenticated": true}` is invalid. To combine conditions, wrap them in a group.
2. **Comparisons take exactly two operands.** `{"eq": ["$a", "$b", "$c"]}` is invalid.

Both are checked when a policy is saved, so a malformed condition never reaches production.

## Booleans

`true` and `false` are complete conditions. They're how the built-ins `public` (`true`) and `deny` (`false`) are defined, and they're the result of empty groups (see below).

```json
{ "name": "anyone", "condition": true }
```

<Warning>
A policy that is literally `true` makes an operation public to anonymous callers with a publishable key. Prefer the built-in `public` so the intent is obvious when someone reads the resource.
</Warning>

## Groups

Groups combine conditions.

### `all`: every condition must pass

```json
{ "all": [
  { "authenticated": true },
  { "role": "teacher" },
  { "eq": ["$record.published", true] }
] }
```

### `any`: at least one condition must pass

```json
{ "any": [
  { "role": "admin" },
  { "owner": "author_id" }
] }
```

### `not`: invert one condition

```json
{ "not": { "eq": ["$record.status", "archived"] } }
```

`not` takes a **single** condition, not a list. To say "none of these", wrap an `any`:

```json
{ "not": { "any": [
  { "eq": ["$record.status", "archived"] },
  { "eq": ["$record.status", "deleted"] }
] } }
```

Studio's rule builder calls this **None of**.

### Empty groups

| Group | Value | Why |
| --- | --- | --- |
| `{"all": []}` | `true` | Nothing failed |
| `{"any": []}` | `false` | Nothing passed |

This matters when you build conditions programmatically: an `any` you forgot to fill denies everyone, which is the safe failure.

### Nesting and short-circuiting

Groups nest to any depth. Evaluation **short-circuits**: `all` stops at the first `false`, `any` at the first `true`. Put cheap, decisive checks first. Role checks are usually the most decisive, because they're decided without looking at the record:

```json
{ "any": [
  { "role": ["admin", "principal"] },
  { "all": [ { "authenticated": true }, { "eq": ["$record.class_id", "$auth.claims.app.class_id"] } ] }
] }
```

For an admin, the first branch decides everything and the record is never consulted. That also lets list requests skip filtering entirely. See [pushdown](/policies/pushdown).

## Operands: paths and literals

Operands are the values a comparison or check works on.

### Paths

An operand that is a string **starting with `$`** is a path into the [evaluation context](/policies/context):

| Path | Resolves to |
| --- | --- |
| `$auth.user_id` | The caller's user id |
| `$auth.roles` | The caller's roles (a list) |
| `$auth.claims.app.department_id` | A custom claim in the token |
| `$credential.is_service` | Whether a secret key or operator is calling |
| `$record.owner_id` | A field of the record |
| `$record.address.city` | A nested field |
| `$input.amount` | A field of the submitted body |
| `$request.params.id` | A path parameter |
| `$request.query.dry_run` | A query parameter |
| `$object.segments.0` | The first segment of a storage key |
| `$now` | The current UTC time |

Paths use dots. A numeric segment indexes a list: `$auth.roles.0` is the first role, `$object.segments.1` the second key segment.

**Missing paths resolve to `null`.** `$record.nonexistent` doesn't raise; it's `null`, and comparisons treat it accordingly (see [operators](/policies/operators#null-handling)). Because `$auth.user_id` is `null` for anonymous callers, a comparison with it never accidentally matches a record whose `owner_id` is also missing, as long as you also require `authenticated` (which the `owner` shorthand does for you).

### Literals

Anything that isn't a `$`-string is a literal:

```json
{ "eq": ["$record.status", "published"] }        // string
{ "gte": ["$record.score", 50] }                  // number
{ "eq": ["$record.flagged", false] }              // boolean
{ "eq": ["$record.deleted_at", null] }            // null
{ "in": ["$record.status", ["draft", "review"]] } // list
```

To use a string that **begins with a dollar sign** as a literal, double the dollar: `"$$9.99"` is the literal `"$9.99"`.

### Either side can be a path

Comparisons don't care which side is the path:

```json
{ "eq": ["$record.owner_id", "$auth.user_id"] }  // path vs path
{ "eq": ["admin", "$auth.claims.app.level"] }        // literal vs path
```

Both work the same way, including for [pushdown](/policies/pushdown).

### Id normalisation

Ids arrive as integers from databases and as strings from tokens. Equality normalises integers to strings, so `42 == "42"` is **true** in `eq`, `ne`, `in` and `contains`. Ownership checks never fail just because of a type difference. Booleans and `null` are not normalised: `true != "true"`.

## Comparisons

```json
{ "<operator>": [left, right] }
```

The twelve operators are `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `not_in`, `contains`, `starts_with`, `ends_with` and `matches`. Their exact semantics, null handling and examples are in the [operators reference](/policies/operators). In summary:

| You want | Use |
| --- | --- |
| Equality | `eq`, `ne` |
| Ranges | `gt`, `gte`, `lt`, `lte` |
| One of a set | `in`, `not_in` |
| A list containing a value, or a string containing a substring | `contains` |
| Prefixes / suffixes | `starts_with`, `ends_with` |
| A pattern | `matches` (regular expression) |

## Checks

Checks test a single operand:

| Check | True when | Example |
| --- | --- | --- |
| `exists` | the value is not `null` | `{"exists": "$input.email"}` |
| `truthy` | the value is truthy | `{"truthy": "$record.published"}` |
| `empty` | the value is falsy: `null`, `false`, `0`, `""`, `[]`, `{}` | `{"empty": "$record.tags"}` |

`exists` is especially useful with `$input` on updates, to detect whether a field is being changed:

```json
{ "any": [
  { "role": "admin" },
  { "not": { "exists": "$input.salary" } }
] }
```

"Anyone who passes the rest of the policy may update, but only admins may touch `salary`."

## Shorthands

Shorthands are single-key conditions for the rules everyone writes:

```json
{ "authenticated": true }
{ "role": "admin" }                    // or a list: any of the roles
{ "permission": "reports.publish" }    // or a list: all of the permissions
{ "owner": "author_id" }               // signed in and record.author_id == auth.user_id
{ "service": true }                    // secret key or operator
{ "kind": "user" }
{ "scope": "reports:export" }
{ "aal": "aal2" }                      // signed in with a second factor
```

Each expands to ordinary comparisons before evaluation, so they combine freely with everything else. [Shorthands reference →](/policies/shorthands)

## Evaluation, step by step

Take this condition and a guardian reading a report card:

```json
{ "any": [
  { "role": ["admin", "principal", "teacher"] },
  { "all": [
    { "eq": ["$record.published", true] },
    { "contains": ["$record.guardian_user_ids", "$auth.user_id"] }
  ] }
] }
```

| Step | Expression | Value |
| --- | --- | --- |
| 1 | `role` expands to `any(contains($auth.roles, "admin"), …)` | the guardian has `["guardian"]` → **false** |
| 2 | `any` continues to the next branch | |
| 3 | `eq($record.published, true)` | the card is published → **true** |
| 4 | `contains($record.guardian_user_ids, "8")` | `["8"]` contains `"8"` → **true** |
| 5 | `all` of steps 3 and 4 | **true** |
| 6 | `any` of step 1 and step 5 | **true** → allowed |

## Writing conditions people can read

<AccordionGroup>
  <Accordion title="Name groups of actors, then compose">
    Instead of repeating `{"role": ["admin", "principal", "teacher", "bursar", "librarian"]}` in ten conditions, define a `staff` policy. Inline conditions can't reference named policies, but entry points can take a **list** of references (`["staff", "mfa"]`), and you can keep the role lists identical by generating them from one place in your definitions script.
  </Accordion>
  <Accordion title="Put the role check first">
    Role checks are decided without the record. Leading with them makes the condition cheaper and lets list requests skip filtering entirely for staff.
  </Accordion>
  <Accordion title="Prefer eq for ownership and tenancy">
    `eq` on a record field is the only comparison that becomes SQL. Structure list rules around it.
  </Accordion>
  <Accordion title="Avoid negations of negations">
    `not(not(x))` is legal and confusing. Rephrase with the positive form or `ne`.
  </Accordion>
  <Accordion title="Describe every policy">
    The `description` shows in Studio and in pickers. Write it in the language of the business: *Staff always; the student and guardians once the report is published.*
  </Accordion>
</AccordionGroup>

## Validation errors you might see

Conditions are checked when a policy (or any definition carrying a condition) is saved. The message names **where** in the condition the problem is, as a path starting at `condition`:

| Message | Cause | Fix |
| --- | --- | --- |
| `condition: a condition is true, false, or an object with one key` | An object with two keys, a string, a number | Wrap multiple conditions in `all`/`any` |
| `condition.any: expected a list of conditions` | `{"any": {...}}` instead of `{"any": [...]}` | Use a list |
| `condition.all[1].eq: expected [left, right]` | A comparison with one or three operands | Exactly two operands |
| `condition.matches: invalid pattern: …` | A regular expression that doesn't compile | Fix the regex; escape backslashes in JSON |
| `condition: unknown operator 'equals'` | A misspelled operator or shorthand | See [operators](/policies/operators) and [shorthands](/policies/shorthands) |

Paths like `condition.all[1].eq` point at the second item of the top-level `all`, so you can find the problem even in large conditions.

## From requirements to conditions

The hardest part of writing policies is translating a sentence from a product spec into a condition. Here are twelve real requirements and their conditions, from simple to subtle.

<AccordionGroup>
  <Accordion title="1. &quot;Only signed-in users.&quot;">
    ```json
    { "authenticated": true }
    ```
    Or reference the built-in `authenticated`.
  </Accordion>
  <Accordion title="2. &quot;Only the person who created it.&quot;">
    ```json
    { "owner": "created_by" }
    ```
    Set `created_by` as the resource's **owner field** so the server fills it; otherwise a client could claim someone else's id on create.
  </Accordion>
  <Accordion title="3. &quot;Admins, or the owner.&quot;">
    ```json
    { "any": [ { "role": "admin" }, { "owner": "owner_id" } ] }
    ```
  </Accordion>
  <Accordion title="4. &quot;Members of the same organization.&quot;">
    ```json
    { "eq": ["$record.org_id", "$auth.org"] }
    ```
    `$auth.org` is the active organization in the caller's token. This condition pushes down into SQL.
  </Accordion>
  <Accordion title="5. &quot;Published items for everyone; drafts only for editors.&quot;">
    ```json
    { "any": [ { "eq": ["$record.status", "published"] }, { "role": "editor" } ] }
    ```
  </Accordion>
  <Accordion title="6. &quot;Guardians can see their children's records.&quot;">
    ```json
    { "contains": ["$record.guardian_user_ids", "$auth.user_id"] }
    ```
    Requires a denormalised list of guardian user ids on the record. See [recipes](/policies/recipes#families-and-dependants) for alternatives.
  </Accordion>
  <Accordion title="7. &quot;Authors can edit their drafts but can't publish them.&quot;">
    ```json
    { "all": [
      { "owner": "author_id" },
      { "eq": ["$record.status", "draft"] },
      { "not": { "eq": ["$input.status", "published"] } }
    ] }
    ```
    `$record` is the row before the update; `$input` is the change being requested.
  </Accordion>
  <Accordion title="8. &quot;Nobody may reassign ownership, except admins.&quot;">
    ```json
    { "any": [ { "role": "admin" }, { "not": { "exists": "$input.owner_id" } } ] }
    ```
    Combine this with the rest of your update rule in an `all`.
  </Accordion>
  <Accordion title="9. &quot;Bursars can approve up to 500,000; above that, the principal.&quot;">
    ```json
    { "any": [
      { "role": "principal" },
      { "all": [ { "role": "bursar" }, { "lte": ["$input.amount", 500000] } ] }
    ] }
    ```
  </Accordion>
  <Accordion title="10. &quot;Sensitive actions need 2FA.&quot;">
    ```json
    { "all": [ { "role": "bursar" }, { "aal": "aal2" } ] }
    ```
  </Accordion>
  <Accordion title="11. &quot;Our reporting service may read, with a scoped key.&quot;">
    ```json
    { "any": [ { "role": "admin" }, { "all": [ { "service": true }, { "scope": "reports:read" } ] } ] }
    ```
    Secret keys bypass policies entirely, so this pattern matters for **publishable** keys with scopes, or as a `policy.check` inside flows.
  </Accordion>
  <Accordion title="12. &quot;Announcements reach the audience they were written for.&quot;">
    ```json
    { "any": [
      { "role": ["admin", "principal", "teacher"] },
      { "all": [
        { "authenticated": true },
        { "eq": ["$record.published", true] },
        { "any": [ { "eq": ["$record.audience", "all"] }, { "contains": ["$auth.roles", "$record.audience"] } ] }
      ] }
    ] }
    ```
  </Accordion>
</AccordionGroup>

## Testing a condition

<Steps>
  <Step title="Test with real requests">
    Create one user per role you care about, sign each in, and call the endpoint. The response body names the refusing policy (`policy 'report_access' refused`), so you can tell which rule said no.
  </Step>
  <Step title="Compare with a secret key">
    The same request with a secret key bypasses policies. If the secret key sees the row and the user doesn't, the policy is responsible; if neither sees it, the row doesn't exist or a filter excludes it.
  </Step>
  <Step title="Try it inside a flow">
    A test flow with a `policy.check` block lets you pass any `record` and `input` and see `allowed` or `denied` in the run trace, without touching real data. [Debugging →](/policies/debugging)
  </Step>
  <Step title="Automate it">
    Put the role-by-role expectations in a script (like the school tutorial's 33 checks) and run it after every policy change.
  </Step>
</Steps>

## Grammar summary

```text
condition   := true | false | group | comparison | check | shorthand
group       := {"all": [condition*]} | {"any": [condition*]} | {"not": condition}
comparison  := {op: [operand, operand]}
op          := eq | ne | gt | gte | lt | lte | in | not_in | contains
             | starts_with | ends_with | matches
check       := {"exists" | "truthy" | "empty": operand}
shorthand   := {"authenticated": bool} | {"role": str | [str]} | {"permission": str | [str]}
             | {"owner": str | true} | {"service": bool} | {"kind": str}
             | {"scope": str} | {"aal": str}
operand     := "$path" | "$$literal" | string | number | boolean | null | [operand*]
path        := segment ("." segment)*        e.g. $auth.roles.0, $record.address.city
```
