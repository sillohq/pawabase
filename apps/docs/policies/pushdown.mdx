## The problem a list creates

A policy answers one question about one record: may this caller touch it? A list asks that question about **every row of a table**, and returns one page of the ones that pass. There are two ways to do that, and only one of them is correct.

| Approach | How | What goes wrong |
| --- | --- | --- |
| **Filter afterwards** | Read a page of rows, drop the ones the caller may not see | Pages come back **short** (a page of twenty with five allowed rows returns five), the **total** is unknown, an unlucky page is **empty** while later pages are full, and rows are fetched that the caller never sees |
| **Filter in the database** | Add the policy to the `WHERE` clause, so the database returns only allowed rows | Nothing. Pages are full, `total` is exact, and the database does the work |

Pawabase does the second whenever it can, and the first only for what it cannot express in SQL. Understanding which is which is the whole of this page, because the difference shows up in your product: a list that **stays in SQL** behaves like an ordinary query, and a list with a **residual** behaves differently in ways that matter to a client.

Everything below was run. The plans come from the engine, and the pages and totals from a running API.

## How a request is planned

For a list, the engine does not call the policy once. It runs a **plan** in three steps:

| Step | What happens | Result |
| --- | --- | --- |
| **1. Partial evaluation** | Everything in the condition that does **not** depend on the row is decided now, using what is known about the caller and the request | A condition that is entirely decided becomes `true` (allow, no filter) or `false` (refuse before any query) |
| **2. Pushdown** | What remains is split into equalities between **one record column and a known value**, and everything else | The equalities become SQL `WHERE` filters |
| **3. Residual** | Whatever is left after pushdown is kept as a condition to check **per row** | Rows failing it are removed after the query |

A condition with nothing left over is decided entirely before the query. One with only equalities is pure SQL. One with anything else has a residual.

### What counts as "known"

During planning the engine knows the caller (`$auth`, `$credential`), the request (`$request`), and the environment. It does **not** know the row (`$record`) or the submitted body (`$input`), which is not read until later. A comparison is **decidable now** when neither side mentions `$record` or `$input`, and it is **deferred** when either does.

So these are decided at plan time, with no row in sight:

| Condition | Plan |
| --- | --- |
| `{"role": "admin"}` for an admin | allow, no filter |
| `{"role": "staff"}` for someone else | **refuse before any query** |
| `{"authenticated": true}` for a signed-out caller | refuse |
| `{"eq": ["$auth.org", "acme"]}` | decided from the caller |

and these are deferred, because they need the row:

| Condition | Deferred part |
| --- | --- |
| `{"eq": ["$record.owner_id", "$auth.user_id"]}` | The comparison, with the caller's id substituted in |
| `{"gt": ["$record.n", 3]}` | The whole comparison |
| `{"eq": ["$record.user_id", "$input.user_id"]}` | The comparison, with `$input` left for the full check |

### What becomes SQL

Only **equalities** between a **single record column** and a **known value** are pushed down, and only when they are combined with `all`. The engine splits a condition into its `all` parts and takes each part that is an `eq` between `$record.<column>` and something known:

```json
{ "all": [
  { "eq": ["$record.user_id", "$auth.user_id"] },
  { "eq": ["$record.status", "open"] },
  { "gt": ["$record.n", 3] }
] }
```

becomes the filters `user_id = '7'` and `status = 'open'` (the caller's id was substituted), with the residual `{"gt": ["$record.n", 3]}`. Plans, as the engine produced them, for a signed-in caller with id `7` and the role `admin`:

| Policy | Filters (SQL) | Residual (per row) |
| --- | --- | --- |
| `public` | none | none |
| `authenticated` | none | none |
| `owner:user_id` | `user_id = '7'` | none |
| `{"eq": ["$record.org_id", "$auth.org"]}` | `org_id = 'acme'` | none |
| `{"eq": ["$auth.org", "$record.org_id"]}` (sides swapped) | `org_id = 'acme'` | none |
| `all` of owner `eq` and `{"eq": ["$record.status", "open"]}` | `user_id = '7'`, `status = 'open'` | none |
| `all` of owner `eq` and `{"gt": ["$record.n", 3]}` | `user_id = '7'` | `{"gt": ["$record.n", 3]}` |
| `["authenticated", "own_rows"]` | `user_id = '7'` | none |
| `any` of owner `eq` and `{"role": "admin"}` (as an admin) | none | none (decided: allow all) |
| `any` of owner `eq` and `{"role": "staff"}` (not staff) | `user_id = '7'` | none |
| `any` of owner `eq` and `{"eq": ["$record.public", true]}` | none | the whole `any` |
| `{"not": {"eq": ["$record.status", "draft"]}}` | none | the whole `not` |
| `{"in": ["$record.status", ["a", "b"]]}` | none | the whole `in` |
| `{"eq": ["$record.a", "$record.b"]}` | none | the whole comparison (two columns) |
| `{"eq": ["$record.address.city", "Lagos"]}` | none | the whole comparison (a nested path) |
| `{"role": "staff"}` (not staff) | | **refused before any query** |

Three observations carry most of the weight:

- **A known caller branch of an `any` collapses.** `any` of "I am the owner" and "I am an admin" costs nothing for an admin (the second branch is true, so the whole thing is) and becomes the owner filter for everyone else (the second branch is false and drops out). `any` of **two record conditions** cannot be reduced and stays a residual.
- **Only `eq` is pushed.** `in`, `ne`, `gt`, `contains`, `starts_with` and the rest are per-row. See [Operators](/policies/operators#operators-and-sql).
- **A nested path is not pushed.** `$record.address.city` is a path into a JSON column, and only a plain column name becomes a filter.

If the same column appears in two equalities, only the first is pushed. This was run: with `eq a $auth.user_id` and `eq a "other"`, the plan pushed `a = '7'` and kept `a = 'other'` as the residual, which can never be true, so such a policy returns nothing.

### Anonymous callers

For a signed-out caller, `$auth.user_id` is empty, so `{"eq": ["$record.user_id", "$auth.user_id"]}` plans to the filter `user_id = NULL`. That matches **no row**, so a list is empty, not refused. The single-record operations behave differently, because they evaluate the comparison against one record. See [the overview](/policies/overview#a-plain-eq-on-an-owner-column-fails-open).

## What a residual does to pages

When a policy has a residual, the query runs **without** it. The database returns one page of rows (those matching the pushed filters, sorted and paged as the caller asked), and **then** each row is checked in Python and the failures are dropped. The page is whatever survives.

This was run on a table of thirty rows, every third one `published`, with three policies and `per_page=5`:

| | Pushed: `status = 'published'` | Residual: published **or** mine | Residual: `status` is not `draft` |
| --- | --- | --- | --- |
| Page 1 | ids 3, 6, 9, 12, 15 (**5 rows**) | id 3 (**1 row**) | id 3 (**1 row**) |
| Page 2 | 18, 21, 24, 27, 30 (5 rows) | 6, 9 (**2 rows**) | 6, 9 (2 rows) |
| Page 3 | none | 12, 15 (2 rows) | 12, 15 (2 rows) |
| Page 4 | none | 18 (1 row) | 18 (1 row) |
| `total` | **10** | **`null`** | **`null`** |

Both effects are visible:

- **Pages are short and uneven.** Page 1 of the residual list holds one row, because the first five raw rows contained one published row. A client that asks for five and receives one cannot tell whether that is the end of the list.
- **`total` is `null`.** The database's count includes rows the caller may not see, so reporting it would be wrong, and it cannot be recomputed without reading everything. The exact policy reports an exact `total`, the residual one reports nothing.

The practical consequences for clients and screens:

| Symptom | Cause |
| --- | --- |
| A page of 20 shows 3 items | A residual removed the rest after the page was read |
| An empty page, then a full one | The raw rows of the first page were all disallowed |
| "Page 1 of ?" | `total` is `null` |
| `sort=-id&per_page=3` returns one row | The newest raw rows were drafts and were dropped |
| Counting rows by paging to the end | Unreliable: the end is not marked |

Pagination by `page` and `per_page` still **advances** through the table, and every allowed row appears exactly once across pages, but nothing tells the client when to stop. A client that stops at the first short page stops too early. See [Sorting and pagination](/data/sorting-pagination#paging-with-a-per-row-policy).

<Note>
The same residual check is why a Python policy always has a residual: nothing in a function can be pushed into SQL, so a list under a Python policy is checked row by row and reports `total: null`. See [Python policies](/policies/python-policies).
</Note>

## A `select` can walk around a residual

A residual is evaluated on the rows the query returned. If the request used `?select=` to return only some columns, **the rows the residual sees contain only those columns**. A condition that reads a column the caller did not select reads nothing, and nothing compares in the way you did not intend.

This was run, on the same table (every third row `published`, the rest `draft`) with an anonymous caller:

| Request | Policy | Rows returned |
| --- | --- | --- |
| `GET /rest/v1/pushed?select=title&per_page=5` | Pushed: `status = 'published'` | ids 3, 6, 9, 12, 15, only published rows. `total` 10 |
| `GET /rest/v1/residual_ne?select=title,status&per_page=5` | Residual: `status` is not `draft` | id 3 only. Correct |
| **`GET /rest/v1/residual_ne?select=title&per_page=5`** | Residual: `status` is not `draft` | **ids 1, 2, 3, 4, 5, the drafts** |
| **`GET /rest/v1/residual_any?select=title&per_page=5`** | Residual: published **or** mine | **ids 1, 2, 3, 4, 5, the drafts** |

With the policy column in the selection, the residual worked. With `select=title` it did not: the row had no `status`, the comparison `status <> 'draft'` was true for a missing value, and the `any` branch that compared the owner to a signed-out caller compared two empty values. **Every draft was returned to an anonymous caller.**

<Warning>
**A residual list policy can be bypassed with `?select=`** by choosing columns that leave out the ones the policy reads. Pushed (SQL) policies are not affected, because their filter is part of the query. Do not rely on a policy that has a residual to protect a list. Keep access rules to **equalities that can be pushed down**, or enforce the rule where the caller cannot change the columns.
</Warning>

The fix is in how you write the policy, because the engine does not add the policy's columns to the selection for you:

| Approach | How |
| --- | --- |
| **Make the rule pushable** | Express it as `all` of equalities on columns and known values, so it becomes a SQL filter. Safe regardless of `select` |
| **Split the resource** | Put the protected data in a resource whose policy is a pushable equality, and expose the open part separately |
| **Use a route** | A flow that runs the query itself decides what is returned. See [Custom routes](/data/custom-routes) |
| **Do not expose the list** | Disable `list` and serve a route, or serve only `get` by id |

For a single record (`get`) the policy runs on the whole row it loaded, so this particular bypass is a list problem. Test your own `get` with `select` as well, since the behavior of a residual on a partial row is the behavior to distrust.

## Your filters narrow, never widen

The caller's `filter[...]` parameters are added to the policy's, with `AND`:

| Request | Result |
| --- | --- |
| `GET /rest/v1/pushed?filter[title]=eq.t3` | One row: the policy's `status = 'published'` and `title = 't3'` |
| `GET /rest/v1/pushed?filter[status]=eq.draft` | **Zero rows, `total` 0**: `status = 'published'` and `status = 'draft'` cannot both hold |
| `GET /rest/v1/pushed?sort=-id&per_page=3` | ids 30, 27, 24, `total` 10 |

A filter can only remove rows from what the policy already allows. It cannot see past it, **except** by reading the values of hidden columns through the result, which is a different concern: see [Filters can read what responses hide](/data/filtering#filters-can-read-what-responses-hide).

For a residual list the same holds, and `sort=-id&per_page=3` returned only id 30: the three newest raw rows were 30, 29 and 28, and only 30 was published.

## Designing for pushdown

The goal is a list whose policy is **all equalities between a column and a caller-known value**. Here is how to get there from the rules people actually have.

| The rule | As written | Stays in SQL? | A pushable design |
| --- | --- | --- | --- |
| My rows | `owner:user_id` | **Yes** | Already pushable |
| My organisation's rows | `{"eq": ["$record.org_id", "$auth.org"]}` | **Yes** | Already pushable |
| Published rows | `{"eq": ["$record.status", "published"]}` | **Yes** | Already pushable |
| My rows in my org | `all` of two equalities | **Yes** | Already pushable |
| Published **or** mine | `any` of two record conditions | **No** | Two lists (below), or a flag column |
| Anything but drafts | `{"ne": ["$record.status", "draft"]}` | No | A column that is `true` for the visible rows, compared with `eq` |
| One of several statuses | `{"in": ["$record.status", [...]]}` | No | A flag, or one resource per audience |
| Created after a date | `gt` on a date | No | A flag maintained by a schedule |
| Rows of any of my teams | `contains` on a list | No | A route that queries |
| Admin sees everything, others their own | `any` of a role and an owner `eq` | **Yes** | Already pushable: the role decides at plan time |

### Replace a negative with a positive

`ne` and `not` cannot be pushed. Most "everything except" rules can be turned into an "equals" by adding a column:

| Instead of | Add | Policy |
| --- | --- | --- |
| `status != 'draft'` | `visible` (boolean), set when a record is published | `{"eq": ["$record.visible", true]}` |
| `status in ('published', 'featured')` | `public` (boolean) | `{"eq": ["$record.public", true]}` |
| `deleted_at is empty` | `deleted` (boolean, default false) | `{"eq": ["$record.deleted", false]}` |

A flag costs a little to keep in step. A flow on the resource's events, or the API's own validation, can set it. In exchange the list is exact, indexed and bypass-proof.

### Two lists for "published or mine"

A single list cannot page "published **or** mine" correctly, because the `or` is across two record conditions. Serve it as **two** lists, each pushable, and let the client combine them:

| List | Policy | Query |
| --- | --- | --- |
| Published | `{"eq": ["$record.status", "published"]}` | `GET /rest/v1/posts` |
| Mine | `owner:author_id` | `GET /rest/v1/my_posts`, a second resource over the same table, or a route |

or a **route** whose flow runs one SQL query with the `or` in it and returns a page. The route's own policy then decides who may call it, and the SQL decides the rows.

### Index what you push

Every pushed equality is a `WHERE` on a column. A table with a million rows and a policy on `org_id` is fast when `org_id` is indexed and a scan when it is not. Mark the policy's columns **indexed** (the field's JSON, `"indexed": true`) and migrate. See [Migrations](/data/migrations#indexes) and [Filtering](/data/filtering#filters-and-indexes).

### Pin the value that makes it push

The pushed value must be **known at plan time**. A value from `$auth` or a literal is. A value from `$input` or another record column is not. If you find yourself writing `{"eq": ["$record.org_id", "$input.org_id"]}` for a list, there is nothing to push: lists have no input. For `create` and `update` that condition is right and is evaluated on the full check.

## Operations other than list

The plan is for `list`. The other operations evaluate the policy **once, against one record**, with the full context, and nothing is pushed:

| Operation | Evaluation |
| --- | --- |
| `list` | Planned. Filters in SQL, residual per row |
| `get` | The plan runs first (a policy that refuses everyone, or only fixes filters, applies at once), then the loaded row is checked against any residual |
| `create` | The full condition, with `$record` and `$input` both the new data |
| `update` | The full condition, with `$record` the existing row and `$input` the patch |
| `delete` | The full condition, with `$record` the existing row |
| `?expand=` | Each related row is checked against the related resource's read policy, one row at a time |

The planner's filters also apply to `get`: a single-record request for a row outside the pushed filters is a `404`, as it would be for a missing row. That is how `owner:user_id` hides someone else's record even though the check is "per record".

A related note on `expand`: the related rows are fetched for the whole page, then **each** is checked in Python, so a policy on a related resource always behaves like a residual, and a row the caller may not see comes back as `null`. See [Relations](/data/relations).

## Seeing what the plan did

You can tell which kind of list you have from the response alone:

| You see | Meaning |
| --- | --- |
| `"total": 10` (a number) | The whole policy ran in SQL |
| `"total": null` | A residual or a Python policy ran per row |
| A short page followed by a fuller one | A residual |
| `403` or `401` for a list with no query | The plan refused (a caller-only condition was false) |

In **Observability**, a request's trace records the policy that produced the plan in its notes, which tells you which definition to open. It does not show the filters. To see them, read the policy and apply the table in [how a request is planned](#how-a-request-is-planned).

## Cost, in one table

| Part of the policy | Cost per list request |
| --- | --- |
| Decided at plan time | None |
| A pushed equality | A `WHERE` clause. Free with an index, a scan without |
| A residual per row | Python on every row of the fetched page, **and** the rows are fetched even when most are dropped |
| A Python policy | A function call per row, plus whatever the function does |
| A residual on a related resource (`expand`) | A check per related row, per page |

A residual does not make a request wrong, it makes it **wasteful and unpredictable**: a page of 20 fetches 20 raw rows whether 20 or 0 are allowed. For a table that is mostly allowed, a residual is cheap. For one that is mostly forbidden, it fetches a lot and returns little.

## Questions that come up

<AccordionGroup>
  <Accordion title="Why is `total` null?">
    Because part of the list policy was checked per row after the query. The database's count would include rows the caller may not see.
  </Accordion>
  <Accordion title="Why does my page of 20 show 3 items?">
    A residual removed the rest after the page was read. Make the policy pushable, or fetch more pages.
  </Accordion>
  <Accordion title="Can I get an exact total with a residual?">
    Not from the list. Count with a route that runs the query, or restructure the rule as equalities.
  </Accordion>
  <Accordion title="Is an `any` ever pushed down?">
    Yes, when all but one branch is decided at plan time. `any` of an owner check and a role check is the owner filter for non-admins and unrestricted for admins. `any` of two record conditions is a residual.
  </Accordion>
  <Accordion title="Does a Python policy push down?">
    No. Every list under a Python policy is a residual, with `total` null.
  </Accordion>
  <Accordion title="Do stored policies and inline conditions plan the same?">
    Yes. The plan sees only the condition, whatever it was called.
  </Accordion>
  <Accordion title="Can I add a database index for a policy?">
    Yes, and you should. Index every column a pushed equality uses.
  </Accordion>
</AccordionGroup>

## What to remember

- **A list is planned: caller-only parts are decided first, equalities become SQL, the rest is a per-row residual.**
- **Only `eq` between one column and a known value is pushed, and only inside `all`.**
- **A residual makes `total` null and pages short.** The end of the list is not marked.
- **A residual can be bypassed with `?select=`.** Keep access rules pushable.
- **A caller's filters only narrow.**
- **Replace negatives and `any` with a flag column and an `eq`.**
- **Index the columns you push.**
- **Anything caller-only is free.** Put roles and plans where they decide before the query.
