## Two kinds of bug

Access bugs come in two shapes. **Someone is refused who should get in**, which is annoying and noisy: a user reports it. And **someone gets in who should not**, which is quiet: nobody reports it, and it is found by an audit or an incident. The techniques are the same, but the second kind needs to be hunted, because no error points at it.

This page gives a method for both. It was written from running the failures: a wrong path, a deleted policy, a residual list, a policy that fails open. The outputs quoted are what came back.

## Start with the response

The status and the body tell you **which layer** decided. Before you open a policy, work out whether a policy decided at all.

| Status | Body | Layer | Meaning |
| --- | --- | --- | --- |
| `401` | `{"error": "missing_api_key", "message": "Send a valid project API key in the apikey header."}` | Gateway | No key |
| `401` | `{"error": "invalid_api_key", ...}` | Gateway | An unknown, revoked or wrong-environment key |
| `403` | `{"error": "origin_not_allowed", "message": "<origin> may not use this key."}` | Gateway | A browser origin not in the project's CORS list, with a publishable key |
| `403` | `{"error": "ip_not_allowed" \| "route_not_allowed", "message": "This API key is not allowed for this request."}` | Gateway | The key's **Allowed IP ranges** or **Allowed routes** |
| `429` | `{"error": "rate_limit_exceeded", "retry_after": 20}` | Gateway or resource | Too many requests |
| `422` | A list of `{type, loc, msg, input}` | Validation | The body is invalid. **No policy ran** |
| `403` | `This API key lacks the 'resource:write' scope` | API gate | The key's scopes |
| `401` | `Authentication required` | Policy or gate | Signed out, and a check refused |
| `403` | `policy 'org_admin' refused` | **Policy** | The named policy said no |
| `404` | `Not found` | Policy or data | A missing record, **or** a read policy hiding it |
| `404` | `policy 'own' refused` | **Policy** | A signed-out `DELETE` (a known oddity) |
| `404` or `405` | The router's own text | Router | The route or operation does not exist (`405` for a method on a path that serves another) |
| `500` | `Internal Server Error` | **A policy that cannot be resolved or that raised** | A deleted or renamed policy, a Python policy that raised, an unvalidated reference |

Two rows are the ones to learn. The `422` means **no policy ran**, so a validation error says nothing about access. And the plain `500` on a read, for a signed-in user but not for a secret key, is the signature of a **missing policy**: the reference was valid when saved and its target is gone.

### Read the message, not only the status

A refusal carries the **policy's name**: `policy 'authenticated+role:editor' refused`. The name is whatever the reference resolved to:

| Reference | Name in the message |
| --- | --- |
| `own_rows` | `own_rows` |
| `role:admin` | `role:admin` |
| An inline condition | `inline` |
| `["authenticated", "own_rows"]` | `authenticated+own_rows` |
| No policy (the default) | `authenticated` |

So the first question is **"is that the policy I expected on this operation?"** A refusal naming `authenticated` on an operation you thought had `own_rows` means the operation has no policy and is using the default. A refusal naming `inline` means you attached a condition and will have to look at the attachment, not the Policies page.

A message and a status can disagree. The signed-out `DELETE` above is a `404` whose body says `policy '...' refused`. Believe the message.

## Find the request

Every response carries an **`x-request-id`** header. Quote it when you report a problem, and use it to find the request:

1. Open **Observability** in Studio.
2. Paste the id into **Exact request id**, or search the path in **Search path**, and narrow with the status filter (**2xx success**, **4xx client error**, **5xx server error**).
3. The list shows **When**, **Method**, **Path**, **Status**, **Duration**, **Caller** and **Request id**.

The **Caller** column is the user's id, or the key's role when no user was signed in (`anon` for a publishable key). It answers "who did the server think this was?" without any more work, and it is often the whole answer: the caller was `anon` when you thought you were signed in, because the token was not sent or had expired.

Click the row to open the **Request trace**. The HTTP request block shows the method and path, the status, the duration, the **Caller** and **IP**, and a JSON block with the user agent and the request's **notes**. For a resource request the notes include:

```json
{ "api_version": "v1", "policy": "own_rows" }
```

`policy` is the name of the policy that **produced the plan** for the request, recorded even when the request was refused. A refused anonymous `GET` still shows `own_rows`. Writes also list the events they published (`"events": ["m.created"]`). So the trace answers **which policy was in play**, and you can open it. It does **not** say why the condition was false, or what values it compared. For that you need the next two sections.

## See the caller the engine sees

Most "I am refused" bugs are a caller who is not who you think, so check that before you read the condition. A small flow shows the context the engine gets for any token. Create a flow whose HTTP trigger has **no path** and the policy `public`, and make it return the caller:

```json
{
  "nodes": [
    { "id": "t", "data": { "block": "trigger.http", "config": { "policy": "public" } } },
    { "id": "r", "data": { "block": "response.return", "config": {
        "status": 200,
        "body": { "auth": "{{ auth }}", "credential": "{{ credential }}", "project": "{{ project }}", "env": "{{ env }}" }
    } } }
  ],
  "edges": [{ "id": "e1", "source": "t", "target": "r" }]
}
```

Call it at `POST /flows/v1/whoami` with the token you are debugging. This was run, and it shows what a policy would read:

```json
{
  "auth": {
    "authenticated": true, "kind": "user", "user_id": "a1", "email": null,
    "roles": ["editor"], "permissions": [],
    "org": "acme-co", "org_role": "member", "aal": "aal1", "session_id": "s",
    "claims": { "sub": "a1", "prj": "acme", "env": "development", "typ": "access", "aal": "aal1" }
  },
  "credential": { "role": "anon", "is_service": false, "scopes": [], "key_id": "k-1" },
  "project": "acme",
  "env": "development"
}
```

For a signed-out caller the same flow returns `authenticated: false`, `kind: "anonymous"`, empty `roles`, and `claims: {}`. For a **secret key** it returns an anonymous `auth` and a `credential` with `role: "service"` and `is_service: true`: the key is not a person, and it bypasses policies.

What to read in the answer:

| You see | Meaning |
| --- | --- |
| `authenticated: false` for a token you sent | The token was not sent, not valid for this environment, or expired. Tokens last minutes |
| `roles` missing a role you granted | The token was issued **before** the grant. Sign in again |
| `org: null` | The token has no organisation. A tenant policy will refuse it |
| `credential.scopes` is `[]` | An unrestricted key. `{"scope": ...}` policies are **false** for it |
| `credential.is_service: true` | A secret key. No policy will refuse this caller |
| `aal: "aal1"` | The caller has not passed a second factor, so `mfa` refuses |

Delete the flow when you are done: it is a way for any caller to read their own claims, which is harmless, and it is also an endpoint you do not need.

## Evaluating a condition with `policy.check`

The Check policy block (`policy.check`) evaluates a **policy name or an inline condition** against a context, and follows `allowed` or `denied`. It is the way to test a condition without touching a resource. The block takes:

| Config | Meaning |
| --- | --- |
| `policy` | A stored, Python or built-in name, or an inline condition |
| `record` | The value to use as `$record` |
| `input` | The value to use as `$input` |

and uses the flow run's own `auth` and `credential`. A tester flow:

```json
{
  "nodes": [
    { "id": "t", "data": { "block": "trigger.http", "config": { "policy": "public" } } },
    { "id": "c", "data": { "block": "policy.check", "config": {
        "policy": "own_rows",
        "record": "{{ input.record }}",
        "input": "{{ input.input }}"
    } } },
    { "id": "ok", "data": { "block": "response.return", "config": { "status": 200, "body": { "decision": "allowed" } } } },
    { "id": "no", "data": { "block": "response.return", "config": { "status": 403, "body": { "decision": "denied" } } } }
  ],
  "edges": [
    { "id": "e1", "source": "t", "target": "c" },
    { "id": "e2", "source": "c", "target": "ok", "sourceHandle": "allowed" },
    { "id": "e3", "source": "c", "target": "no", "sourceHandle": "denied" }
  ]
}
```

Called with `{"record": {"owner_id": "a1"}}` as the owner and as a stranger, it answers `allowed` or `denied`. This was run on the condition `{"gte": ["$input.total", 100]}`: a body of `{"total": 500}` followed `allowed` and `{"total": 5}` followed `denied`.

Three limits to keep in mind:

- **Do not call it with a secret key.** The engine's first step passes service credentials, so the block answers `allowed` for every policy. Use a user's token, and check `credential.is_service` is false (see above).
- **It answers allowed or denied, not why.** To find which clause failed, evaluate the clauses one at a time: replace the policy with each child condition and call again.
- **It is a check, not a plan.** It does not show the SQL filters a list would get. For that, read [how a request is planned](/policies/pushdown#how-a-request-is-planned).

This is also how to test a Python policy by name inside Studio, with a context you build.

## Test every role, not one

A policy is tested by the callers it should **refuse** at least as much as by the ones it should allow. Write the matrix once, as a script, and rerun it after every change to a policy. Each cell is one request:

```bash
BASE="https://api.example.com/rest/v1/tasks"
KEY="pk_live_..."           # publishable key

declare -A TOKENS=(
  [anon]=""
  [owner]="$OWNER_TOKEN"
  [stranger]="$STRANGER_TOKEN"
  [editor]="$EDITOR_TOKEN"
  [admin]="$ADMIN_TOKEN"
)

for who in anon owner stranger editor admin; do
  auth=()
  [ -n "${TOKENS[$who]}" ] && auth=(-H "Authorization: Bearer ${TOKENS[$who]}")
  for op in "GET $BASE" "GET $BASE/$ROW" "PATCH $BASE/$ROW" "DELETE $BASE/$ROW"; do
    set -- $op
    code=$(curl -s -o /dev/null -w '%{http_code}' -X "$1" "$2" \
      -H "apikey: $KEY" "${auth[@]}" \
      -H 'Content-Type: application/json' -d '{"title":"x"}')
    printf '%-9s %-6s %s\n' "$who" "$1" "$code"
  done
done
```

Compare the output to a table you wrote **before** running it:

| Caller | List | Get own row | Get another's row | Patch another's row | Delete another's row |
| --- | --- | --- | --- | --- | --- |
| anon | `401` | `401` | `401` | `401` | `404` (the oddity) |
| owner | `200`, own rows | `200` | `404` | `404` | `404` |
| stranger | `200`, own rows | `404` | `404` | `404` | `404` |
| admin | `200`, all | `200` | `200` | `200` | `204` |

Three habits make this catch real bugs:

- **Include a row whose owner column is empty.** Plain `eq` on an owner column fails open for it, and only that row exposes it. See [a plain eq fails open](/policies/overview#a-plain-eq-on-an-owner-column-fails-open).
- **Include a caller with the wrong tenant**, and try to `PATCH` a row **into** that tenant, not only to read it.
- **Include a read-only key** for the write cells. `DELETE` skips the scope check, so a key you thought was read-only may still delete (see [the delete gap](/policies/enforcement-points)).

Test with a **publishable key and user tokens**. A secret key passes every cell, so a matrix run with one proves nothing.

## Symptom, cause, fix

| Symptom | Likely cause | Check | Fix |
| --- | --- | --- | --- |
| Everyone but secret keys gets `500` on one resource | A policy it references was deleted or renamed | Request trace notes name a policy that is not on the Policies page | Recreate the name, or reattach the operation. See [deleting and renaming](/policies/references#deleting-and-renaming) |
| A list is empty for everyone, `get` works | A path in the condition does not exist (`$auth.org_id`), so it compares to `null` | Run the `whoami` flow and compare the path with the real one | Use the real path: `$auth.org` |
| A list is **short** or `total` is `null` | A residual condition is filtered after the page was read | Open the Policies page and look for a condition that is not `all` of `eq` between a column and a value | Redesign for pushdown. See [pushdown](/policies/pushdown) |
| `?select=` returns rows the plain list hides | A residual plus `select` | Compare with and without `select` | See [a select can walk around a residual](/policies/pushdown#a-select-can-walk-around-a-residual) |
| Anonymous callers read or change rows with no owner | A plain `eq` on a nullable column | Add a row with a null owner and request it as anon | Use `owner:<column>` |
| A policy refuses everything after a deploy | A stored policy shares a name with a built-in and replaced it | Compare the Policies page names with `authenticated`, `owner`, `mfa` | See [a stored policy can replace a built-in](/policies/overview#a-stored-policy-can-replace-a-built-in-one) |
| An expiry check refuses everything | `$now` was compared with text | `{"lt": ["$now", "2026-01-01"]}` is always false | Store a timestamp and compare as in [time](/policies/operators#time) |
| `{"scope": "..."}` refuses a key that works elsewhere | The key has no scopes, which counts as unrestricted and matches nothing here | `credential.scopes` is `[]` in the whoami flow | Give the key the scope, or check `role` instead |
| A `mfa` policy refuses a user who enrolled | The session is at `aal1` | `auth.aal` in the whoami flow | Complete the second factor to reach `aal2` |
| A role was granted but the user is still refused | The token predates the grant | `auth.roles` in the whoami flow | Sign in again |
| A condition that looks right is false | Number against text, or `5` against `5.0` | See [operators](/policies/operators) | Compare the same type |
| A `not exists` guard lets a request through | The caller sent `null`, and `exists` is false for `null` | Send `null` for the field | See [exists is false for null](/policies/overview#exists-is-false-for-null-so-not-exists-allows-nulling) |
| A user changes a row's tenant | The update policy checks only the existing record | `PATCH` the tenant field | Check the incoming `$input` too |
| A subscription's condition never matches | Path `$event.data` or the default `exists` | Look at the delivered event | Use `$event.payload` |

## Three worked scenarios

### The typo that fails open

A tenant policy was written as:

```json
{ "eq": ["$record.org_id", "$auth.org_id"] }
```

`$auth.org_id` does not exist (the path is `$auth.org`), so the right side is always `null`. What happened when run:

| Request | Result |
| --- | --- |
| Signed in, list | `200`, empty, `total: 0` |
| Signed in, get a row of the user's own tenant | `404` |
| Anyone, including **anon**, get a row with no `org_id` | **`200`** |

The first two look like a plain bug, and a developer fixes the policy to "see the data". The third is the real problem: `null` equals `null`, so every row without a tenant is public. It was found only by requesting an orphan row as a stranger.

How to find it: run the `whoami` flow and copy the **path from its output**, never from memory or from the rule builder's suggestions (which offered `$auth.org_id`). How to prevent it: a matrix with a row that has no tenant.

### The short list

A list that returns 7 rows with `limit=20` and `"total": null`. Nothing was refused and nothing logged.

The policy has a condition the planner could not turn into SQL, so it read a page and **dropped the rows that failed** afterwards. Each page is short by a different amount and the total cannot be known. The page can even be empty while later pages are not.

Check: open the policy and look for anything beyond `all` of `eq` between a column and a known value: an `any`, a `not`, an `in`, a comparison on `$input`, a Python policy. Fix it by moving the part that selects rows into a plain `eq` and keeping the rest as a single-record check. [Designing for pushdown](/policies/pushdown) has the patterns.

### Refused only after promotion

A resource works in development. After promotion every non-service request returns `500`, and the Overview lists no problem.

The cause is the missing policy: a promotion carries the kinds you ask for, and the resource was promoted without the policy it references (or the policy was renamed in development). The request trace notes name the policy, and the Policies page of the target environment does not have it.

Fix: promote the policies with the resources (`"include"` lists the kinds), or create the missing policy. To prevent it, put **policies first** in the promotion list. See [environments and promotion](/operate/environments-and-promotion).

## Debugging checklist

1. Which layer answered? Gateway codes, `422` and router `404`/`405` are not policy decisions.
2. Take the `x-request-id` and open the request in Observability. Does the **Caller** match who you meant?
3. Read the `policy` name in the notes. Is it the one you expected for this operation?
4. Run the `whoami` flow with the same token. Does the context hold the values the condition reads?
5. Evaluate the condition, or each of its parts, with a `policy.check` flow and a hand-built record.
6. Run the role matrix, including an empty-owner row and a wrong-tenant caller.
7. Confirm you were not testing with a secret key.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Is there a way to see why a condition was false?">
    Not directly. Observability shows which policy ran, not its evaluation. Test the parts one at a time with a `policy.check` flow, and use the `whoami` flow to see the values being compared.
  </Accordion>
  <Accordion title="My secret key can do everything, so is the policy even on?">
    Secret keys bypass policies by design, so that tells you nothing. Test with a publishable key and a user token.
  </Accordion>
  <Accordion title="Why does a refused delete say 404?">
    Deletes are handled outside the gate that returns `401` and `403`, so a refusal can come back as a `404` carrying the policy message. Read the message, and treat the status as unreliable for `DELETE`.
  </Accordion>
  <Accordion title="Should I leave the whoami flow in production?">
    No. It only shows a caller their own claims, but an endpoint that does nothing for the product is a surface you do not need. Remove it when you finish.
  </Accordion>
</AccordionGroup>

## What to remember

- The status and message say which layer decided. `422` means no policy ran.
- A plain `500` for users but not for a secret key is a missing policy.
- The `x-request-id` header leads to the request trace, which shows the policy name and the caller, not the reason.
- A `whoami` flow shows the exact context a policy reads. Copy paths from it.
- A `policy.check` flow evaluates a condition against a record you supply. It must not be called with a secret key.
- Test refusals as much as allowances, with an empty-owner row, a wrong-tenant caller and a read-only key, and never with a secret key.
