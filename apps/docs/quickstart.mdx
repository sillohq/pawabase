In this quickstart you will build the backend for a small task application. Users will be able to sign in, create tasks, and read only authenticated data through Pawabase's public API.

You will use Studio to configure the backend and `curl` to act like an application. The same public endpoints work from a web app, mobile app, or server.

```text
Studio configuration
      ↓
project + environment + resource + policy
      ↓
public gateway
      ↓
sign in → create task → list tasks
```

<Note>
This guide deliberately keeps authorization simple: every signed-in user can see every task. The [first project tutorial](/tutorial/first-project) adds server-controlled ownership so each user sees only their own records.
</Note>

## Before you begin

You need:

- a running Pawabase installation;
- the Studio URL and an operator account;
- the public gateway URL;
- `curl` or another HTTP client.

For a local installation, follow [Run Pawabase locally](/installation/local-development). The default URLs are:

```text
Studio:  http://localhost:8090
Gateway: http://localhost:8080
```

## 1. Create an organization

Sign in to Studio. If this is your first sign-in, Studio asks you to create an organization.

An organization is the team workspace that owns projects. Enter a name, choose a URL name, and create it. You become the organization owner and can invite teammates later.

## 2. Create a project

From the organization page, choose **New project** and select **A blank project**.

Enter:

| Field | Value | Why it matters |
| --- | --- | --- |
| Name | `Tasks demo` | The name shown in Studio |
| Reference | `tasks-demo` | Stable identifier used by the project and its keys |
| Description | `Backend for a private task app` | Helps teammates understand the project |
| Environments | `development`, `staging`, `production` | Isolated copies of configuration and data |

Choose **Create project**. Studio displays the publishable and secret key for every environment once.

Save the `development` publishable key. You do not need the secret key for this guide.

<Warning>
A publishable key may be used by a browser or mobile application because policies still apply. A secret key bypasses policies and belongs only in trusted server-side code. Never put a secret key in a client bundle.
</Warning>

If you close the dialog without saving a key, open **Operate → API keys** and create a replacement. Existing key values cannot be revealed again.

## 3. Create the `tasks` resource

Open the `development` environment, then go to **Build → Resources** and choose **New resource**.

### Details

Configure:

| Field | Value |
| --- | --- |
| Name | `tasks` |
| Primary key | `id` |
| ID type | Auto-increment |
| Description | `Tasks created by application users` |

Pawabase serves this resource under `/rest/v1/tasks`. It adds the primary key and, when timestamps remain enabled, `created_at` and `updated_at`.

### Fields

Add these fields:

| Name | Type | Required | Default | Notes |
| --- | --- | --- | --- | --- |
| `title` | Short text | Yes | — | What the user needs to do |
| `completed` | Boolean | No | `false` | Completion state |
| `due_date` | Date | No | — | Optional due date |

### Access

Enable all five operations and choose **Signed-in users** for each:

| Operation | Method | Endpoint |
| --- | --- | --- |
| List | `GET` | `/rest/v1/tasks` |
| Get | `GET` | `/rest/v1/tasks/{id}` |
| Create | `POST` | `/rest/v1/tasks` |
| Update | `PATCH` | `/rest/v1/tasks/{id}` |
| Delete | `DELETE` | `/rest/v1/tasks/{id}` |

Leave **Emit events** and **Timestamps** enabled. Save with **Create resource**.

Creating the resource definition does not create or alter its database table. Reopen the resource and choose **Create / migrate table**. Run this action again after schema changes that need to be applied to the data store.

<Warning>
Do not select a public policy merely to make a request succeed. Public means a caller with the environment's publishable key can use the operation without signing in.
</Warning>

## 4. Configure sign-up and sessions

Go to **Services → Users & auth → Configuration**.

For this development environment:

1. Turn on **Sign-up enabled**.
2. Leave **Require email verification** off for the quickstart.
3. Under **Passwords**, note the configured policy and minimum length.
4. Leave the access-token and refresh-token lifetimes at their defaults.
5. Save.

In production, require email verification when ownership of the address matters, configure the site and redirect URLs, and configure mail before enabling an email-based method.

## 5. Set your client values

In a terminal, define the public gateway and the development publishable key:

```bash
export PAWABASE_URL="http://localhost:8080"
export PAWABASE_KEY="your-development-publishable-key"
```

Check what authentication features the environment exposes:

```bash
curl "$PAWABASE_URL/auth/v1/settings" \
  -H "apikey: $PAWABASE_KEY"
```

This is a public application endpoint. The response tells a client whether sign-up, email verification, magic links, MFA, or configured social providers are available.

## 6. Create an application user

Register through the public application boundary:

```bash
curl -i -X POST "$PAWABASE_URL/auth/v1/signup" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "ada@example.com",
    "password": "correct-horse-1",
    "name": "Ada"
  }'
```

With verification disabled, a successful response has status `201` and includes the user, access token, refresh token, and session information. With verification required, the response contains no active session until the user follows the verification link.

You can also create a development or support user in **Users & auth → Users → New user**, but application registration should normally use `/auth/v1/signup`.

## 7. Sign in

Sign in with the password grant:

```bash
curl -X POST "$PAWABASE_URL/auth/v1/token" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "grant_type": "password",
    "email": "ada@example.com",
    "password": "correct-horse-1"
  }'
```

Copy `access_token` from the response:

```bash
export PAWABASE_TOKEN="your-access-token"
```

The two credentials have different jobs:

| Credential | Header | Meaning |
| --- | --- | --- |
| Publishable key | `apikey: ...` | Selects the Pawabase project environment |
| Access token | `Authorization: Bearer ...` | Identifies the signed-in user and their authorization context |

An access token expires. A real client stores the refresh token securely and exchanges it for a new token pair; see [Tokens and sessions](/auth/tokens-and-sessions).

## 8. Create a task

```bash
curl -i -X POST "$PAWABASE_URL/rest/v1/tasks" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $PAWABASE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Connect the task app to Pawabase",
    "completed": false,
    "due_date": "2026-10-15"
  }'
```

Pawabase selects the environment from the API key, authenticates the bearer token, validates the request against the resource fields, evaluates the create policy, writes the record, and emits `tasks.created` because **Emit events** is enabled.

If the body omits `title`, the request fails validation. If the bearer token is missing, the signed-in policy rejects the request.

## 9. List and update tasks

List the newest tasks first:

```bash
curl "$PAWABASE_URL/rest/v1/tasks?sort=-created_at&per_page=20" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $PAWABASE_TOKEN"
```

Update task `1`:

```bash
curl -i -X PATCH "$PAWABASE_URL/rest/v1/tasks/1" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $PAWABASE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"completed": true}'
```

Delete it:

```bash
curl -i -X DELETE "$PAWABASE_URL/rest/v1/tasks/1" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $PAWABASE_TOKEN"
```

A successful delete returns `204 No Content`.

## 10. Make the same call from JavaScript

Only place the publishable key in browser configuration:

```js
const pawabaseUrl = "http://localhost:8080";
const publishableKey = "your-development-publishable-key";

export async function createTask(accessToken, input) {
  const response = await fetch(`${pawabaseUrl}/rest/v1/tasks`, {
    method: "POST",
    headers: {
      apikey: publishableKey,
      Authorization: `Bearer ${accessToken}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify(input),
  });

  const body = response.status === 204 ? null : await response.json();
  if (!response.ok) {
    throw new Error(body?.detail?.message ?? body?.detail ?? `Request failed (${response.status})`);
  }
  return body;
}
```

For a browser application, add its exact origin under **Operate → Settings → CORS**. CORS is enforced by browsers; it is not a replacement for authentication or policies.

## Verify in Studio

Use Studio to inspect what happened:

- **Build → Database** to inspect the stored row;
- **Services → Users & auth → Users** to inspect the account and sessions;
- **Services → Users & auth → Sign-in activity** to inspect sign-in attempts;
- **Operate → Events & runs** to find the resource event;
- **Operate → Observability** to view request and error activity;
- **Build → API Explorer** to make another public API request interactively.

Studio is the control plane for configuring and operating the environment. Your application should continue to call the public gateway, not Studio's management requests.

## Troubleshooting

| Result | Meaning | Fix |
| --- | --- | --- |
| `401` before sign-in | Missing or invalid `apikey` | Use the publishable key from the same environment. |
| `401` on `/rest/v1/tasks` | Missing, expired, or wrong-environment access token | Sign in again with the same environment key. |
| `403` | The operation exists, but its policy denied the caller | Confirm the operation uses **Signed-in users** and send the bearer token. |
| `404` for `/rest/v1/tasks` | The resource or operation is not served | Check the resource name and enable the operation. |
| Table-not-found or migration error | Definition exists but its table is not ready | Choose **Create / migrate table** on the resource. |
| `422` or validation response | The request body does not match the fields | Check required fields, types, and date format. |
| Browser CORS failure | The browser origin is not allowed | Add the exact origin under **Operate → Settings**. |
| Empty results with another key | You reached another environment | Align URL, key, token, and selected Studio environment. |

## What you built

You now have:

```text
Tasks demo project
└── development environment
    ├── password sign-up and sessions
    ├── tasks resource and database table
    ├── authenticated CRUD endpoints
    ├── resource events
    └── publishable application credential
```

This is already more than a database with an API attached: the same environment can add per-record authorization, file uploads, realtime updates, event-triggered flows, queued work, webhooks, schedules, and custom business routes without moving those concerns into the client.

Continue to [Your first real project](/tutorial/first-project) to add ownership, relations, a flow, and realtime behavior. Read [REST conventions](/clients/rest-conventions) when integrating a real client.
