In this quickstart you will create a project, model a `tasks` resource, add authentication, protect records, and make application-facing requests. You will finish with a backend that has a real data model and a clear security boundary—not just an empty project.

<Callout>
Pawabase is configured in Studio. The commands in this guide are only for starting the local platform and calling the public application API. If you are using Pawabase Cloud or an existing deployment, start at **Create a project**.
</Callout>

## Before you begin

For a local installation, complete [Docker installation](/installation/docker) or [local development](/installation/local-development). You need:

- a running Pawabase deployment;
- access to Studio;
- a web browser;
- `curl`, or another HTTP client, for the final application request.

In the local setup, Studio is normally at `http://localhost:8090` and the application gateway is normally at `http://localhost:8080`.

## 1. Create a project

Open Studio and choose **New project**.

Enter:

| Field | Example | Meaning |
| --- | --- | --- |
| Project name | `Tasks demo` | The human-readable project name. |
| Project reference | `tasks-demo` | The stable identifier used in environment URLs and client configuration. |
| Environments | `development` | The first isolated environment for building. |

Choose **Create**. Studio opens the new environment's overview. Keep this environment for development; production should have its own credentials and data.

## 2. Create a resource

In Studio, open **Build → Resources → New resource**.

Create a resource named `tasks`. A resource represents application data and its public operations. Configure these fields:

| Field | Type | Required | Default |
| --- | --- | --- | --- |
| `title` | Short text | Yes | — |
| `completed` | Boolean | No | `false` |
| `due_date` | Date | No | — |

Save the resource and migrate it when Studio asks. The resource editor now shows the operations that can be exposed: list, get, create, update, and delete.

<Note>
Creating a resource does not automatically make it public. Each operation has its own enabled state and access policy. Treat that separation as a safety feature.
</Note>

## 3. Add authentication

Open **Services → Users & auth → Settings** and confirm that email/password sign-in is enabled for development. Then open **Users → Create user** and create a development user, for example `you@example.com`.

For a real application, users should register and sign in through the public authentication interface. Creating a user in Studio is convenient for development and support; it is not a replacement for application sign-up.

## 4. Protect the resource

Return to **Build → Resources → tasks → Operations**.

For development, use the built-in **Authenticated** policy on list, get, create, update, and delete. Enable each operation and save.

The policy means that a caller must have a valid signed-in user session. It does not yet separate one user's tasks from another user's tasks. Add that distinction in the next tutorial with an owner field and an owner policy.

<Warning>
Do not choose a public policy for personal data just to make the first request work. If a resource contains user, financial, operational, or private business data, start with the narrowest policy that matches the product requirement.
</Warning>

## 5. Sign in from the application boundary

The exact authentication request and token shape are documented in [tokens and sessions](/auth/tokens-and-sessions). A minimal development request looks like this:

```bash
curl -X POST "http://localhost:8080/auth/v1/token?grant_type=password" \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"your-development-password"}'
```

Copy the returned access token. In a browser or mobile app, use the JavaScript, React, Python, or mobile client guidance rather than storing a long-lived secret in the client.

## 6. Create and read a task

Use the environment's publishable key from **Overview → Connection details**. A publishable key identifies the environment; the access token identifies the signed-in user.

```bash
export PAWABASE_URL="http://localhost:8080"
export PAWABASE_KEY="your-development-publishable-key"
export PAWABASE_TOKEN="your-access-token"

curl -X POST "$PAWABASE_URL/rest/v1/tasks" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $PAWABASE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Read the Pawabase flow guide","completed":false}'

curl "$PAWABASE_URL/rest/v1/tasks" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $PAWABASE_TOKEN"
```

The request is evaluated in this order: the gateway identifies the environment, authentication validates the token, the resource validates the body, the operation policy authorizes the action, and the database stores or returns the record.

## 7. Understand the failure paths

These responses are useful signals, not random errors:

| Situation | Typical result | What to check |
| --- | --- | --- |
| Missing or invalid publishable key | Authentication or key error | Copy the key for the correct environment. |
| Missing or expired access token | `401` | Sign in again or refresh the session. |
| Operation is disabled | Route or operation error | Enable that operation in Studio. |
| Policy rejects the caller | `403` or a filtered result | Review the operation's policy and caller context. |
| Invalid field or type | Validation error | Compare the request body with the resource fields. |
| Wrong environment URL | Missing resource or unexpected data | Check the project reference and environment name. |

Use [client errors](/clients/errors) and [troubleshooting](/reference/troubleshooting) when you need the full error shape.
