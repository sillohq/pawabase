Supabase and Pawabase both offer open-source backend platforms with auth, database, and realtime capabilities. They share some surface-level similarities — both provide PostgreSQL-based databases, authentication, and realtime subscriptions — but diverge significantly in how backend logic is authored and executed.

Supabase uses Edge Functions (TypeScript/Deno) triggered by database events. Pawabase uses flows (visual graphs) and Python functions triggered by 8 different event types. This guide walks through migrating a Supabase project to Pawabase.

## Key architectural differences

Before starting, understand the fundamental differences that affect how you port your logic:

| Aspect | Supabase | Pawabase |
| --- | --- | --- |
| **Database engine** | PostgreSQL | SQLite (dev) / PostgreSQL (production) |
| **ORM** | `supabase-py` (limited) | Full ORM with `Record` class |
| **Row-Level Security** | Postgres RLS policies | Pawabase policies (unified engine) |
| **Functions** | Edge Functions (Deno/TypeScript) | Flows (visual) + Python functions |
| **Trigger model** | Database events via Postgres triggers | 8 trigger types with unified engine |
| **Deployment** | `supabase functions deploy` | Save definitions — no deploy |
| **Realtime** | Postgres `LISTEN/NOTIFY` via WebSocket | Angula WebSocket server |
| **Versioning** | Per-function versioning | Per-environment versioning |
| **Promotion** | Manual (separate projects per env) | Built-in promotion between envs |

## Authentication migration

Supabase Auth and Pawabase's Akountz both handle email/password, social login, MFA, and session management. The token formats differ, but user data can be migrated cleanly.

### Step 1: Export Supabase users

Use the Supabase Admin API or PostgreSQL client to export users:

```sql
SELECT id, email, email_confirmed_at, raw_user_meta_data, created_at, last_sign_in_at
FROM auth.users
WHERE aud = 'authenticated';
```

Or use the Supabase Python client:

```python
from supabase import create_client
supabase = create_client(SUPABASE_URL, SUPABASE_SERVICE_KEY)
users = supabase.auth.admin.list_users().data
```

### Step 2: Create Pawabase accounts

Each Supabase user maps to a Pawabase user through Akountz. The migration process creates accounts with the same email addresses and sets passwords from the existing auth data.

For users who signed in via OAuth, create OAuth links in Pawabase matching their provider:

| Supabase provider | Pawabase provider | Notes |
| --- | --- | --- |
| Google | Google OAuth | Direct mapping |
| GitHub | GitHub OAuth | Direct mapping |
| Apple | Generic OAuth/OIDC | Configure Apple in Pawabase |
| Facebook | Generic OAuth/OIDC | Configure Facebook in Pawabase |
| Email/Password | Email/Password | Direct mapping |
| Phone | Not yet supported | ❌ Coming soon |

### Step 3: Migrate organizations and teams

Supabase organizations map to Pawabase roles and permissions. Each Supabase org becomes a set of roles in Pawabase's RBAC system:

```python
# Create organization-level roles
await rbac.define_role(
    project, env, "org_member",
    description="Member of the organization",
    permissions=["read:org", "update:profile"],
)
await rbac.define_role(
    project, env, "org_admin",
    description="Organization administrator",
    permissions=["*"],
)
```

### Step 4: Verify token compatibility

Supabase issues JWT tokens with specific claims. Pawabase issues its own tokens with RBAC claims. The client application needs to switch from the Supabase JS client to Pawabase's auth SDK.

| Supabase | Pawabase |
| --- | --- |
| `supabase.auth.signInWithPassword()` | `PawabaseAuth.signIn({ email, password })` |
| `supabase.auth.signUp()` | `PawabaseAuth.signUp({ email, password })` |
| `supabase.auth.signOut()` | `PawabaseAuth.signOut()` |
| `session.access_token` | `PawabaseAuth.getToken()` |
| `supabase.auth.getUser()` | `PawabaseAuth.getUser()` |
| Custom claims via `security_policy` | RBAC roles via `defineRole` |

## Database migration

Supabase uses PostgreSQL with Postgres RLS policies. Pawabase uses the same Postgres engine in production, but the data model is defined as resources rather than raw tables.

### Step 1: Define resources from existing tables

Each Supabase table becomes a Pawabase resource. In Studio, create a resource for each table and map the columns to fields:

| Supabase | Pawabase |
| --- | --- |
| Table | Resource |
| Column | Field (with type) |
| `jsonb` column | `object` or `list` field |
| Foreign key | Relation field |
| `CHECK` constraint | Validation rule in field definition |
| `UNIQUE` constraint | Unique validation |
| Index | Query optimization (automatic) |

### Step 2: Migrate data

Use the Pawabase API to bulk-insert existing PostgreSQL data into the new resource definitions:

```python
from app.platform import Platform
from app.config import ApiSettings

platform = Platform(ApiSettings())

# Migrate each table's data
for table_name in ["profiles", "projects", "tasks"]:
    # Read from existing Supabase database
    rows = await fetch_from_supabase(table_name)
    for row in rows:
        await platform.dispatch(
            CreateResourceJob,
            project="my-project",
            env="development",
            resource=table_name,
            data=row,
        )
```

### Step 3: Convert RLS policies to Pawabase policies

Supabase's Row-Level Security policies are the most complex part to migrate. Each RLS policy becomes a Pawabase policy evaluated by the unified policy engine.

**Supabase RLS:**
```sql
CREATE POLICY "Users can view own profile" ON profiles
  FOR SELECT USING (auth.uid() = user_id);
```

**Pawabase policy:**
```json
{
  "name": "users-can-view-own-profile",
  "condition": "{{ auth.user_id == record.user_id }}",
  "description": "Users can view their own profile",
  "enforcement_point": "resource.read"
}
```

The Pawabase policy engine evaluates conditions at every enforcement point — not just database reads, but also routes, channels, and flows. This is more powerful than Supabase's RLS, which only applies to database operations.

### Converting common RLS patterns

| Supabase RLS | Pawabase policy |
| --- | --- |
| `auth.uid() = user_id` | `{{ auth.user_id == record.user_id }}` |
| `auth.role() = 'admin'` | `{{ auth.role == 'admin' }}` |
| `exists (select 1 from org_members where ...)` | `{{ auth.user_id in record.member_ids }}` |
| `record.org_id = auth.jwt() ->> 'org_id'` | `{{ record.org_id == auth.claims.org_id }}` |
| `pg_has_role(...)` | `{{ auth.permissions contains 'org:admin' }}` |

## Edge functions migration

Supabase Edge Functions (Deno/TypeScript) map to Pawabase flows and Python functions. The conversion requires rewriting TypeScript to Python, but the logic maps cleanly.

### Trigger mapping

| Supabase trigger | Pawabase equivalent | Migration approach |
| --- | --- | --- |
| `db-functions` (table insert/update/delete) | `trigger.resource` in a flow | Create a flow with resource trigger |
| `edge-functions` (HTTP endpoint) | Extension route or `queue.function` | Create a custom route or function |
| `edge-functions` (scheduled) | `trigger.schedule` in a flow | Create a flow with cron/interval |
| `rpc` calls | `function.call` or inline function | Convert to a Pawabase function |
| `storage` events | `trigger.resource` on storage bucket | Create a flow with resource trigger |

### Example: converting an Edge Function

**Supabase (TypeScript):**
```typescript
Deno.serve(async (req) => {
  const { email } = await req.json();
  const user = await supabase.auth.getUser();
  const { data: profile } = await supabase.from('profiles').select().eq('id', user.id).single();
  return new Response(JSON.stringify({ profile }), { status: 200 });
});
```

**Pawabase Python function:**
```python
from pawabase import function

@function("get-profile")
def get_profile(ctx, email: str) -> dict:
    profile = await ctx.runtime.resource_get(
        "profiles", filter={"email": email}
    )
    return {"profile": profile}
```

**Pawabase flow equivalent:**
```json
{
  "id": "get-profile",
  "nodes": [
    {"id": "start", "data": {"block": "trigger.http", "config": {"method": "POST", "path": "/get-profile"}}},
    {"id": "lookup", "data": {"block": "resource.get", "config": {"resource": "profiles", "filter": "{{ body.email }}"}}},
    {"id": "return", "data": {"block": "control.return", "config": {"value": "{{ steps.lookup.output }}"}}}
  ]
}
```

### Handling Supabase storage triggers

Supabase storage triggers (activated on file upload) map to Pawabase resource events on the storage bucket:

```json
{
  "id": "process-upload",
  "nodes": [
    {
      "id": "start",
      "data": {
        "block": "trigger.resource",
        "config": { "resource": "storage", "operations": ["created"] }
      }
    },
    {
      "id": "process",
      "data": { "block": "function.call", "config": { "function": "process-image" }}
    }
  ]
}
```

## Realtime migration

Supabase uses Postgres `LISTEN/NOTIFY` for realtime subscriptions. Pawabase uses Angula, a dedicated WebSocket server with separate channel management, presence, and history.

### Step 1: Map Supabase channels to Pawabase channels

Supabase realtime channels are tied to specific tables. Pawabase channels are named rooms with independent subscribe/publish policies.

| Supabase | Pawabase |
| --- | --- |
| `realtime.channel("table_name")` | `pawabase.realtime.channel("channel-name")` |
| `channel.subscribe()` | `channel.subscribe()` |
| `channel.on("postgres_changes", ...)` | Event filter in channel policy |
| Broadcast | `publish` on the channel |
| Presence | Built-in presence with history |

### Step 2: Convert subscription filters

```typescript
// Supabase
const channel = supabase.channel("orders")
  .on("postgres_changes", 
    { event: "UPDATE", schema: "public", table: "orders" },
    (payload) => { ... }
  )
  .subscribe();
```

```javascript
// Pawabase
const channel = pawabase.realtime.channel("orders-updates");
channel.on("order.updated", (event) => {
  // event contains the full event envelope
});
```

### Step 3: Set up channel policies

Supabase's `REALT_TIME` and row-level security on realtime subscriptions map to Pawabase channel policies:

```json
{
  "channel": "orders-updates",
  "subscribe": "{{ auth.user_id in record.member_ids }}",
  "publish": "{{ auth.role == 'admin' || auth.user_id == record.created_by }}"
}
```

## Policy engine migration

Supabase's Postgres RLS policies and Pawabase's unified policy engine serve the same purpose but work differently. Pawabase's policies are evaluated at every enforcement point, not just database access.

### Key differences

| Supabase RLS | Pawabase policies |
| --- | --- |
| Evaluated at query time only | Evaluated at all enforcement points |
| SQL expressions | Expression language with template syntax |
| Per-table policies | Named policies with enforcement point |
| `auth.uid()`, `auth.role()` | `auth.user_id`, `auth.role`, `auth.claims` |
| Manual per-policy management | Centralized policy management in Studio |
| Applied to Postgres tables | Applied to resources, routes, channels, flows |

### Policy expression comparison

| Supabase | Pawabase |
| --- | --- |
| `auth.uid()` | `{{ auth.user_id }}` |
| `auth.role()` | `{{ auth.role }}` |
| `auth.email()` | `{{ auth.email }}` |
| `auth.jwt()->>'org_id'` | `{{ auth.claims.org_id }}` |
| `exists (...)` | `{{ auth.user_id in query(...) }}` |
| `pg_has_role(...)` | `{{ auth.permissions contains 'perm' }}` |

## Complete migration checklist

  <Accordion title="Pre-migration">
    - [ ] Audit all Supabase features (auth, tables, edge functions, storage, realtime, RLS)
    - [ ] Create a migration plan per subsystem
    - [ ] Set up a Pawabase staging environment
    - [ ] Export all PostgreSQL data and auth users
    - [ ] Define resource schemas in Studio
  </Accordion>
  <Accordion title="Auth migration">
    - [ ] Export Supabase users via Admin API
    - [ ] Create Pawabase accounts and map OAuth providers
    - [ ] Migrate organizations and team roles to RBAC
    - [ ] Update client auth SDK
    - [ ] Verify MFA and email verification
  </Accordion>
  <Accordion title="Database migration">
    - [ ] Create resources from existing tables
    - [ ] Migrate data using the migration utility
    - [ ] Convert all RLS policies to Pawabase policies
    - [ ] Define relations between resources
    - [ ] Test queries and validation rules
  </Accordion>
  <Accordion title="Functions migration">
    - [ ] Convert Edge Functions to flows and Python functions
    - [ ] Map trigger types (database events, HTTP, scheduled)
    - [ ] Test each converted function
    - [ ] Set up error handling and retry policies
  </Accordion>
  <Accordion title="Storage migration">
    - [ ] Configure object storage backend
    - [ ] Migrate files from Supabase Storage
    - [ ] Update client-side storage calls
    - [ ] Verify signed URLs and access policies
  </Accordion>
  <Accordion title="Realtime migration">
    - [ ] Define channels in Pawabase Studio
    - [ ] Map Supabase realtime subscriptions to channels
    - [ ] Convert RLS realtime policies to channel policies
    - [ ] Test realtime updates from the client
  </Accordion>
  <Accordion title="Promotion setup">
    - [ ] Use Pawabase's built-in promotion to copy definitions between environments
    - [ ] No need to manually create separate Supabase-like projects per environment
    - [ ] Verify that promotion preserves resource schemas and policies
  </Accordion>
</AccordionGroup>

## Next steps

After migrating, take advantage of Pawabase-specific features that Supabase doesn't offer:

- **Visual flows** — Convert remaining hardcoded logic to visual flows in Studio
- **Per-environment promotion** — Promote definitions between environments without manual exports
- **Built-in run history** — Every flow execution is recorded with full step traces
- **Unified policy engine** — Apply policies consistently across resources, routes, and channels
