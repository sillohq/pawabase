A **project** is the backend for one product or operational system. An **environment** is an isolated instance of that backend, with its own data and runtime settings.

The usual progression is:

```text
development → staging → production
```

You can use different environment names when your release process needs them, but the principle stays the same: build safely in one environment, validate in another, and expose production only when the behavior and access rules are understood.

## What belongs to a project

A project groups the definitions and services that make up one backend:

- resources and database behavior;
- authentication and organizations;
- policies and roles;
- flows, events, queues, and schedules;
- storage buckets and realtime channels;
- routes, functions, mail, and webhooks.

Keep separate products in separate projects. A project is not a user account, a database table, or a production deployment by itself.

## What belongs to an environment

Each environment has its own:

- application data and resource tables;
- users, sessions, and organization memberships;
- publishable and secret keys;
- encrypted secrets and external integration settings;
- storage objects and realtime activity;
- logs, jobs, flow runs, and webhook deliveries.

This isolation lets the same backend design use safe development credentials and test data without touching production.

## Create a project in Studio

1. Open Studio and choose **New project**.
2. Enter a human-readable name and a stable project reference.
3. Create a development environment.
4. Open the environment overview and copy its connection details.
5. Configure the backend in that environment before creating staging or production.

Choose a reference that will remain stable in URLs and application configuration. Avoid including a temporary customer, branch, or developer name in a project reference.

## Configure environments differently

The definitions can be consistent across environments while operational settings differ:

| Setting | Development | Production |
| --- | --- | --- |
| Database | Disposable or local data | Backed up, monitored data store |
| Authentication | Test users and relaxed verification | Real verification and recovery settings |
| Webhooks | Mock or disabled destinations | Verified production destinations |
| Secrets | Development provider keys | Production provider keys |
| API keys | Short-lived or local-use keys | Scoped, rotated keys |
| Realtime | Small test audience | Capacity and channel rules reviewed |

Do not copy production credentials into development just because the definitions are the same.

## Promote changes

Use Studio's environment promotion workflow when a set of definitions is ready to move forward. Review the promotion before confirming it.

Promote definitions such as:

- resources and field validation;
- policies and transformers;
- flows, routes, schemas, and functions;
- subscriptions, schedules, templates, and webhook configuration.

Keep environment-specific data and credentials separate. After promotion:

1. migrate any resource changes in the target environment;
2. set target-specific secrets and provider credentials;
3. review webhook URLs and enabled state;
4. check API keys and application configuration;
5. run a smoke check with a target-environment user;
6. inspect the environment overview for definition problems.

## Data migration considerations

Changing a resource definition can affect existing records and clients. Before promotion, decide:

- whether a new required field needs a default or a backfill;
- whether a renamed field needs a compatibility period;
- whether a policy will hide records from existing users;
- whether a response change breaks an older application version;
- whether a large migration needs a maintenance window.

Read [Migrations](/data/migrations) before changing production data structures.

## Environment-specific application configuration

Your application should select its Pawabase URL and publishable key by environment. Keep those values in the application's environment configuration, not in source code that is shared blindly across deployments.

```text
development app → development URL + development publishable key
staging app     → staging URL + staging publishable key
production app  → production URL + production publishable key
```

The user session must also belong to the environment being called. A token from development is not a production credential.

## Deleting an environment

Deleting an environment is a destructive operational action. It can remove that environment's data, users, storage objects, jobs, and configuration. Confirm the project and environment, export anything you need for audit or recovery, and check that no deployed application still points to it.

## Blueprints and promotion

For a repeatable starting point or a new project based on an existing design, use a blueprint through Studio. For moving a change between environments in the same product, use promotion. In both cases, treat production data, keys, sessions, and secrets as environment-specific unless the workflow explicitly says otherwise.

## Troubleshooting isolation problems

| Symptom | Likely cause |
| --- | --- |
| The application sees no records | It is calling a different environment. |
| A token is rejected after switching environments | The token belongs to the previous environment. |
| A webhook works in staging but not production | The target URL or secret is environment-specific. |
| A promoted resource exists but requests fail | The target resource was not migrated or its policy was not promoted as expected. |
| A key works locally but not after deployment | The deployed application has the wrong environment key. |

Keep the environment name visible in deployment logs and application diagnostics. It is one of the fastest ways to find configuration drift.
