## Projects

A **project** is one application backend: a school system, a marketplace, a SaaS. It has a human name and a **reference** (`ref`): lower-case, stable, used in URLs, keys and project code paths (`code/<ref>/`).

```bash
# Platform API
POST /platform/v1/projects
{ "name": "School Management System", "ref": "school",
  "environments": ["development", "staging", "production"] }
```

The first environment listed is the default. Every environment gets a publishable and a secret key, returned **once** in the response.

## Environments

An **environment** is a fully isolated instance of the project. Everything the platform stores is keyed by `(project, environment)`:

<CardGroup cols={2}>
  <Card title="Isolated per environment" icon="lock">
    Definitions and their version · API keys · secrets · the token signing key · resource data (its own `database_url`) · storage (its own driver/bucket) · mail settings · auth settings and users · queues and event history · realtime rooms
  </Card>
  <Card title="Shared by the project" icon="share-2">
    The name, reference and description · project code under `code/<ref>/` (functions, policies, transformers, routes), loaded for every environment
  </Card>
</CardGroup>

<Note>
Users are per environment. A user who signs up in `development` doesn't exist in `production`, and a `development` token is rejected by `production` because the signing keys differ (`HMAC(master, "<project>:<env>")`).
</Note>

## Infrastructure per environment

Each environment points at its own infrastructure under **Settings → Infrastructure**:

```json
{
  "database_url": "postgres://app:secret://DB_PASSWORD@db.internal:5432/school",
  "storage": { "driver": "s3", "bucket": "school-prod", "region": "eu-west-1",
               "access_key": "secret://S3_KEY", "secret_key": "secret://S3_SECRET" },
  "mail": { "host": "smtp.postmarkapp.com", "port": 587, "username": "secret://SMTP_USER",
            "password": "secret://SMTP_PASS", "from": "School <no-reply@school.example>" }
}
```

Values written as `secret://NAME` are resolved from the environment's encrypted [secrets](/operate/secrets) at the moment they're used and are never returned by the API. Full reference: [environment settings](/reference/environment-settings).

## A typical setup

| Environment | Database | Keys used by | Purpose |
| --- | --- | --- | --- |
| `development` | SQLite default or a local Postgres | Your laptop | Designing resources, flows, policies |
| `staging` | A copy-sized Postgres | CI, QA, preview deploys | Promotion target, integration tests |
| `production` | Your production Postgres, S3, SMTP | Your real apps | Live traffic |

Design in development, [promote](/operate/environments-and-promotion) definitions to staging, verify, promote to production. Data, keys and secrets never move.

## Versions

Every definition change bumps the environment's **version**. The compiled app, cached configuration in other services and the OpenAPI document all key off it, so a change is live on the next request without restarts. The overview page shows the current version (`definitions version 486`).

## Creating more environments

```bash
POST /platform/v1/projects/school/envs
{ "name": "preview-42", "copy_from": "staging" }
```

`copy_from` copies definitions only. Use short-lived environments for pull-request previews and delete them when done: `DELETE /platform/v1/projects/school/envs/preview-42`.
