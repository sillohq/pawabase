A **project** is the backend for one product or operational system, and it lives in an [organization](/concepts/organizations): the team that owns it and controls who can work on it. An **environment** is an isolated instance of that backend, with its own data and runtime settings.

The usual progression is:

```text
development → staging → production
```

You can use different environment names when your release process needs them, but the principle stays the same: build safely in one environment, validate in another, and expose production only when the behavior and access rules are understood.

## What belongs to a project

A project groups the definitions and services that make up one backend:

- resources and database behavior;
- authentication and organizations;
- policies and roles;
- flows, events, queues, and schedules;
- storage buckets and realtime channels;
- routes, functions, mail, and webhooks.

Keep separate products in separate projects. A project is not a user account, a database table, or a production deployment by itself.

### How to decide project boundaries

The test that scales well: would these two things ever need genuinely different resources, policies, or flows because they serve different purposes, not just different customers? A B2B admin console and the customer-facing app it manages, for the same product, usually belong in the *same* project — they share the same resources (orders, customers) even if they expose different operations and policies on them. Two unrelated products run by the same company — a delivery app and an unrelated internal HR tool — belong in *separate* projects, because sharing a project buys you nothing (their resources, policies, and flows have nothing in common) and costs you real risk (an operator with access to one now has a path to touching the other).

A common mistake in the other direction is creating a new project per customer for what is actually one multi-tenant product. If every customer of your SaaS product gets a new Pawabase project, you've multiplied your operational surface by your customer count — every policy, flow, and schema change now needs to be made N times, once per project. The correct shape for a multi-tenant product is almost always one project, with tenancy modeled as an `organization_id` (or similar) field on your resources and enforced by policy, not one project per tenant. Reach for a project boundary per customer only when customers need genuinely isolated infrastructure — a strict compliance or data-residency requirement, for instance — not merely for organizational tidiness.

## What belongs to an environment

Each environment has its own:

- application data and resource tables;
- users, sessions, and organization memberships;
- publishable and secret keys;
- encrypted secrets and external integration settings;
- storage objects and realtime activity;
- logs, jobs, flow runs, and webhook deliveries.

This isolation lets the same backend design use safe development credentials and test data without touching production.

### How many environments do you actually need

Three (`development`, `staging`, `production`) is the common default, and it maps cleanly onto the usual promotion path. Some teams need more:

- a **per-feature or per-branch environment**, created temporarily for a large change and torn down afterward, useful when several developers need to work on conflicting schema changes simultaneously without blocking each other in a shared `development`;
- a **demo environment**, separate from both `staging` and `production`, seeded with realistic-looking but fake data specifically for prospect or customer demos, so a live sales demo never risks showing (or accidentally modifying) real customer data;
- a **load-testing environment**, isolated from `staging` so synthetic load doesn't interfere with ordinary pre-release validation.

Fewer teams need more than four or five environments in total; beyond that, the operational overhead of keeping each one's secrets, integrations, and promoted definitions current tends to outweigh the isolation benefit. If you find yourself creating environments faster than you can keep them meaningfully current, that's usually a sign to consolidate rather than a sign you need better tooling for more of them.

## Create a project in Studio

1. Open Studio and choose **New project**.
2. Enter a human-readable name and a stable project reference.
3. Create a development environment.
4. Open the environment overview and copy its connection details.
5. Configure the backend in that environment before creating staging or production.

Choose a reference that will remain stable in URLs and application configuration. Avoid including a temporary customer, branch, or developer name in a project reference.

### What "stable" means in practice

A project reference embedded in a URL or a client's configuration is expensive to change later — every deployed client, every stored webhook destination URL pointing back at your infrastructure, and every piece of documentation your own team has written all assume it doesn't move. Treat choosing it with the same weight you'd give choosing a production domain name: pick something that describes the product, not the moment you created it (`acme-checkout`, not `acme-checkout-oct-rewrite` or `jamies-test-project`).

## Configure environments differently

The definitions can be consistent across environments while operational settings differ:

| Setting | Development | Production |
| --- | --- | --- |
| Database | Disposable or local data | Backed up, monitored data store |
| Authentication | Test users and relaxed verification | Real verification and recovery settings |
| Webhooks | Mock or disabled destinations | Verified production destinations |
| Secrets | Development provider keys | Production provider keys |
| API keys | Short-lived or local-use keys | Scoped, rotated keys |
| Realtime | Small test audience | Capacity and channel rules reviewed |

Do not copy production credentials into development just because the definitions are the same.

### What should stay identical across environments, and what genuinely differs

It's worth stating both directions explicitly, because teams sometimes over-correct into thinking "environments are isolated" means "environments can drift in design." The **definitions** — resource fields, policies, flow logic, schemas, transformers — should be as close to identical as your release process allows; divergence here is exactly the thing that causes "it worked in staging" surprises. The **operational configuration** — credentials, external integration targets, data volume, verification strictness — is expected and correct to differ. If you notice a *policy* or a *flow's business logic* differing between staging and production (beyond a deliberate, tracked feature flag), that's drift worth investigating; if you notice *credentials* differing, that's simply environments working as designed.

## Promote changes

Use Studio's environment promotion workflow when a set of definitions is ready to move forward. Review the promotion before confirming it.

Promote definitions such as:

- resources and field validation;
- policies and transformers;
- flows, routes, schemas, and functions;
- subscriptions, schedules, templates, and webhook configuration.

Keep environment-specific data and credentials separate. After promotion:

1. migrate any resource changes in the target environment;
2. set target-specific secrets and provider credentials;
3. review webhook URLs and enabled state;
4. check API keys and application configuration;
5. run a smoke check with a target-environment user;
6. inspect the environment overview for definition problems.

### What promotion does not do, explicitly

It's worth being precise about the boundary, since assuming promotion does more than it does is a recurring source of production incidents. Promotion does **not**: create or update secrets in the target environment (you configure those separately, deliberately, because a development provider key should never silently become live in production); enable a webhook destination that was disabled in the target (destinations are environment-specific for exactly this reason); migrate data (a new required field on a resource needs an explicit migration step in the target, because the target's existing records don't automatically gain a value for it); or carry over users, sessions, or organization memberships (those are entirely environment-local). Promotion moves the *shape* of your backend forward; it deliberately never moves the *substance* running inside it.

### A promotion checklist for a non-trivial change

For anything beyond a trivial fix, walk through this before confirming a promotion:

- Does this change add a required field to a resource with existing records in the target environment? If so, plan the backfill or default before promoting, not after.
- Does this change rename or remove anything another definition depends on? Confirm nothing in the target environment still references the old name (a promotion succeeding does not guarantee every previously-existing reference in the target was updated consistently, if the target has any environment-specific customizations).
- Does this change alter a policy in a way that could hide records from users who could previously see them, or expose records that were previously hidden? Test with a representative user of each affected role before promoting, not after a customer reports it.
- Does this change depend on a secret, provider credential, or webhook destination that doesn't yet exist in the target? Configure it as part of the same promotion window, not as a follow-up you might forget.
- Does this change affect a response shape an already-deployed client depends on? If older client versions are still in the field (a mobile app update not everyone has installed, for instance), consider whether the change is backward compatible before promoting to production.

## Data migration considerations

Changing a resource definition can affect existing records and clients. Before promotion, decide:

- whether a new required field needs a default or a backfill;
- whether a renamed field needs a compatibility period;
- whether a policy will hide records from existing users;
- whether a response change breaks an older application version;
- whether a large migration needs a maintenance window.

Read [Migrations](/data/migrations) before changing production data structures.

## Environment-specific application configuration

Your application should select its Pawabase URL and publishable key by environment. Keep those values in the application's environment configuration, not in source code that is shared blindly across deployments.

```text
development app → development URL + development publishable key
staging app     → staging URL + staging publishable key
production app  → production URL + production publishable key
```

The user session must also belong to the environment being called. A token from development is not a production credential.

### Handling this across common deployment shapes

For a **web application**, this usually means build-time or runtime environment variables that differ per deployment target, injected by your hosting platform's own environment configuration — never a single hardcoded URL and key checked into source alongside application code meant to run everywhere.

For a **mobile application**, this is more delicate: an app store build typically ships with a single, fixed configuration, which is exactly why a separate build variant (or a build-time flag) per environment matters — you cannot change a shipped mobile binary's embedded key after the fact the way you can redeploy a web app's environment variables. Confirm which environment a mobile build variant points to as part of your release checklist, not by inspecting behavior after release.

For **server-to-server integrations**, treat the environment selection the same as any other secret-adjacent configuration: store it alongside the secret key it's paired with, and never let a single script or worker be silently pointable at more than one environment by an accidental default.

## Deleting an environment

Deleting an environment is a destructive operational action. It can remove that environment's data, users, storage objects, jobs, and configuration. Confirm the project and environment, export anything you need for audit or recovery, and check that no deployed application still points to it.

### Before you delete

- Confirm, out loud or in writing, the exact project and environment name — not "the one we don't use anymore," but the literal name shown in Studio.
- Check whether any deployed client, scheduled job, or external integration (a partner's webhook configuration, a third-party OAuth redirect registered against this environment's URL) still references it.
- Export anything with retention or compliance value — audit trails, financial records, anything you might need months later and cannot reconstruct.
- If the environment was ever production, or ever held real customer data, treat the deletion with the same procedural weight you'd give deleting a production database, regardless of what Studio currently calls it.

## Blueprints and promotion

For a repeatable starting point or a new project based on an existing design, use a blueprint through Studio. For moving a change between environments in the same product, use promotion. In both cases, treat production data, keys, sessions, and secrets as environment-specific unless the workflow explicitly says otherwise.

A blueprint is most useful when you're standardizing how your team starts new projects — a common auth setup, a standard set of operational resources (audit logs, feature flags) every new product should have — rather than as a way to keep two already-running projects in sync. Once a project exists and is evolving, promotion between its own environments is the right tool; re-applying a blueprint is not a substitute for it.

## Troubleshooting isolation problems

| Symptom | Likely cause |
| --- | --- |
| The application sees no records | It is calling a different environment. |
| A token is rejected after switching environments | The token belongs to the previous environment. |
| A webhook works in staging but not production | The target URL or secret is environment-specific. |
| A promoted resource exists but requests fail | The target resource was not migrated or its policy was not promoted as expected. |
| A key works locally but not after deployment | The deployed application has the wrong environment key. |
| A field that's required in production doesn't reject an old client's request in staging | The environments have drifted — staging wasn't kept current with the same promoted definitions as production, or vice versa. |
| A realtime channel that worked in development shows no messages in production | Channel rules or realtime capacity settings weren't reviewed as part of promotion, since those are frequently intended to differ. |

Keep the environment name visible in deployment logs and application diagnostics. It is one of the fastest ways to find configuration drift.
