An **organization** is the top level of a Pawabase installation. It is a team of operators (the people who sign in to Studio) and the projects they build. Nothing exists outside one: after setup, the first thing you do is create an organization, and every project you create afterwards belongs to it.

```text
installation
└── organization        people, roles, invitations, audit log
    └── project         one backend
        └── environment development · staging · production
```

<Note>
  This is the **platform's** organization, for the people running Pawabase. It is not the same thing as the [end-user organizations](/auth/organizations) inside a project's authentication service, which group *your application's* users. The two never mix: platform organizations hold operators and projects; project organizations hold your customers.
</Note>

## First run

1. Start Pawabase and sign in to Studio with the operator from `PAWABASE_ADMIN_EMAIL` / `PAWABASE_ADMIN_PASSWORD`.
2. Studio asks you to **create your organization** (a name, and a URL name used in links). Every page redirects here until you have one.
3. You become its **owner**. Invite your team, then create projects.

If you are upgrading an installation that already has projects, the first organization created adopts all of them, so nothing is orphaned.

You can belong to several organizations and switch between them from the sidebar. Studio opens the one you used last.

## Roles

A member has one role in the organization, and it applies to every project in it. A role includes everything the roles before it can do.

| Role | Can |
|---|---|
| **Viewer** | Read every project in the organization: definitions, data, logs. Change nothing. |
| **Developer** | Create projects and change anything inside them: definitions, flows, keys, secrets, data, releases. |
| **Admin** | Also delete projects, manage members and invitations, and rename the organization. |
| **Owner** | Also delete the organization and grant or remove ownership. |

Rules that keep an organization manageable:

- Only owners grant, change or remove ownership, or invite another owner.
- An organization always keeps at least one owner.
- Anyone can leave an organization, unless they are its only owner.
- An organization can only be deleted when it has no projects.

## Team management

Open **Team** in the sidebar. Everyone sees the member list; owners and admins can also change roles, remove members and invite people.

### Invitations

Choose **Invite someone**, enter an email and a role. Studio shows an invitation link **once**; send it to the invitee.

- The link works for one person only: the address it was sent to, and expires after 7 days.
- Only a hash of the token is stored, so a lost link cannot be recovered. Revoke the invitation and send a new one.
- Inviting an address again replaces the earlier open invitation.
- The invitee opens the link. If they have no operator account they choose a password and are signed in; if they do, they sign in and accept. Either way they join with the role you chose.

Pawabase does not send the email itself; the link is yours to deliver.

## Who can see what

Access is enforced by the API on every management call, not only in Studio's screens:

- A project is visible only to members of its organization. To anyone else it does not exist (`404`), which also stops probing for project names.
- Reading needs at least *viewer*; changing needs *developer*; deleting a project needs *admin*.
- The audit log Studio shows is the organization's: changes to its projects and to its team.
- Studio's own shortcuts to realtime, identities and the API Explorer check membership before forwarding.

Service credentials (secret keys, other Pawabase services, automation with no operator behind it) are not tied to an organization. If they create a project without naming one, it goes into an organization called `default`.

## The API

All routes live under `/platform/v1` and take the same operator or service credentials as the rest of the management plane.

| Method and path | Purpose | Needs |
|---|---|---|
| `GET /orgs` | Organizations you belong to, with your role | member |
| `POST /orgs` | Create one; you become owner | operator |
| `GET /orgs/{slug}` | One organization | viewer |
| `PATCH /orgs/{slug}` | Rename | admin |
| `DELETE /orgs/{slug}` | Delete (must have no projects) | owner |
| `GET /orgs/{slug}/members` | Members | viewer |
| `PUT /orgs/{slug}/members/{user_id}` | Change a role | admin |
| `DELETE /orgs/{slug}/members/{user_id}` | Remove a member, or leave | admin, or self |
| `POST /orgs/{slug}/invitations` | Invite (returns the token once) | admin |
| `GET /orgs/{slug}/invitations` | Open invitations | admin |
| `DELETE /orgs/{slug}/invitations/{id}` | Revoke | admin |
| `GET /invitations/{token}` | What an invitation offers | token |
| `POST /invitations/{token}/accept` | Join as the signed-in operator | matching email |

Creating a project now takes the organization:

```http
POST /platform/v1/projects
{ "ref": "shop", "name": "Shop", "org": "acme" }
```

`org` is required for operators. `GET /projects` and `GET /audit` accept `?org=<slug>` and otherwise return everything the caller's organizations own.
