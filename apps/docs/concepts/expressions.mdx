Pawabase uses two complementary expression styles: **`$`-prefixed paths** for resolving values from runtime context, and `{{ }}` template strings for interpolating those values into strings. You encounter both in flow conditions, variable sets, policy configurations, webhook mappings, and event subscriptions.

This page is the single source of truth for how those expressions work. If you have read only the mental model page and need to write your first `$input.event.payload.name`, read this first.

## The two syntaxes, at a glance

| Syntax | Used for | Example |
| --- | --- | --- |
| `$`-prefixed path | Resolving a value from context in a condition or config field | `$input.event.payload.name` |
| `{{ }}` template string | Interpolating a resolved value into a larger string | `Hi {{ input.event.payload.name }}` |

The key difference: a `$`-path returns the **resolved value** (a string, number, object, etc.). A `{{ }}` template returns a **string** with the value interpolated in. You can use `{{ }}` *inside* a `$`-path expression to build dynamic lookups, and you can use `$`-paths inside `{{ }}` templates.

## Where expressions are accepted

Expressions appear in every place where you need to reference runtime data rather than a literal value:

- **Flow conditions** — the `condition` field of a `control.if` or `control.switch` block
- **Flow variables** — the `values` field of a `control.set` block
- **Policy conditions** — the condition objects in resource operations, routes, and hooks
- **Webhook mappings** — field mappings in outbound webhook configurations
- **Event subscriptions** — filter conditions and payload templates
- **Flow block configs** — any config field that accepts a `$`-path or `{{ }}` string

If you see a field in Studio that says "accepts expressions" or shows a `$` placeholder icon, it supports both syntaxes.

## The `$` path syntax

A `$`-path walks through the runtime context tree. The engine resolves it at evaluation time and returns the value found at that location.

### Root variables

Every expression starts from one of these root variables:

| Root | Available in | What it contains |
| --- | --- | --- |
| `$input` | All flows and events | The trigger payload — the event body, HTTP request body, schedule payload, or whatever the trigger received. |
| `$auth` | Policy conditions, flow conditions with auth context | The resolved caller identity: `user_id`, `roles`, `org`, `org_role`, `aal`, `claims`, etc. |
| `$step.<node_id>` | Flow conditions after the referenced step has run | The output dictionary of a previous step in the same flow run. |
| `$vars` | Flow conditions and `control.set` targets | The current contents of the flow's variable store. |
| `$event` | Event handlers and subscriptions | The full event envelope: `name`, `payload`, `source`, `timestamp`, `correlation_id`. |
| `$record` | Policy conditions on resource operations | The record being created, updated, or deleted (varies by operation). |
| `$request` | Route handlers and hooks | The incoming HTTP request: `method`, `path`, `headers`, `query`, `body`. |
| `$env` | Any expression context | Environment variables configured for the project/environment. |

### Walking nested properties

Dot notation resolves nested keys:

```text
$input.event.payload.shipping_address.city
```

If any intermediate key is missing, the resolution stops and returns `null` — it does not throw an error. This means you can chain long paths safely:

```text
$input.event.payload.user.profile.preferences.theme
```

If `user` is missing, the whole expression resolves to `null`, not an error.

### Indexing into arrays

Use bracket notation to access array elements by index:

```text
$input.items[0].name
```

You can also use `$`-paths inside bracket notation to build dynamic lookups:

```text
$input.items[$vars.index]
```

### Missing properties and null handling

When a path resolves to a missing key, the engine returns `null`. This is the same as if the key existed with a `null` value. You can test for this explicitly:

```json
{ "eq": ["$input.event.payload.user_id", null] }
```

### Accessing step outputs

Every block in a flow produces output. You can reference the output of any previous step using `$step.<node_id>`:

```text
$step.validate_output.error
```

The `node_id` is the **block ID** you assigned in the flow editor — not a display name, not a line number. It's the lowercase, hyphen-separated identifier you set when you created the block.

<Note>
If you reference a step that hasn't run yet (e.g., it's in a branch that wasn't taken), `$step.<node_id>` resolves to `null`. This is how conditional flows work — later steps see the data only if earlier steps ran.
</Note>

## The `{{ }}` template syntax

Template strings interpolate resolved values into text. The expression inside `{{ }}` follows the same path rules as `$`-paths, but the result is always rendered as a string.

### Basic interpolation

```text
"Dear {{ input.event.payload.user.email }}, your order {{ input.event.payload.order.id }} is confirmed."
```

### Formatting numbers and dates

Inside `{{ }}`, you can apply format specifiers by adding a `|` after the path:

```text
"Total: {{ input.total | currency }}"
"Created: {{ input.created_at | date-short }}"
```

Supported formats: `currency`, `date-short`, `date-full`, `number`, `percent`. If the resolved value can't be formatted (e.g., `null`), the interpolation renders as an empty string.

### Combining literal and dynamic text

Everything inside `{{ }}` is an expression; everything outside is literal text. You can mix freely:

```text
"User {{ auth.user_id }} placed {{ input.order.count }} orders on {{ input.order.date | date-full }}."
```

### Escaping braces

To output a literal `{{` or `}}`, use triple braces:

```text
"JSON template: {{{{ key }}: {{ value }}}}"
```

This renders as: `{"key": "value"}`

## Condition operators

Conditions are JSON objects that evaluate to `true` or `false`. They appear in `control.if`, policy conditions, and webhook filters. The operators all use the same syntax:

```json
{ "operator": [first_operand, second_operand] }
```

### Truthiness

```json
{ "truthy": "$input.event.payload.name" }
```

Resolves the `$`-path and considers the result truthy or falsy using these rules:

| Value | Truthy? |
| --- | --- |
| Non-empty string (`"hello"`) | True |
| Empty string (`""`) | False |
| Non-zero number (`42`, `-1.5`) | True |
| Zero (`0`) | False |
| `true` | True |
| `false` | False |
| Non-empty array (`[1, 2]`) | True |
| Empty array (`[]`) | False |
| Non-null object (`{ "a": 1 }`) | True |
| `null` / missing key | False |

### Equality and comparison

```json
{ "eq": ["$input.status", "paid"] }
{ "neq": ["$auth.org", null] }
{ "gt": ["$input.amount", 100] }
{ "lt": ["$input.amount", 0] }
{ "gte": ["$input.quantity", 1] }
{ "lte": ["$input.retry_count", 3] }
```

Comparisons follow standard JavaScript-like coercion rules for the operand types. `eq` and `neq` compare values of any type. `gt`, `lt`, `gte`, `lte` require both operands to be numbers; comparing a string to a number is always `false`.

### Membership

```json
{ "in": ["$input.role", ["admin", "editor"]] }
```

The `in` operator checks whether the first operand equals any element in the second operand (which must be an array).

### Logical combinators

```json
{
  "all": [
    { "truthy": "$input.user_id" },
    { "eq": ["$auth.aal", "aal2"] }
  ]
}
```

- `all` — every sub-condition must be `true`
- `any` — at least one sub-condition must be `true`
- `not` — negates a single sub-condition

### Combining `$`-paths and literals

In a two-operand operator, the first operand is typically a `$`-path (resolving to a value), and the second operand is typically a literal:

```json
{ "eq": ["$input.status", "paid"] }
```

But either operand can be a `$`-path or a literal. To compare two runtime values:

```json
{ "eq": ["$input.source_account", "$auth.user_id"] }
```

## Variables in flow state

The `control.set` block writes to the flow's variable store. Each variable is a key-value pair, and subsequent steps can reference them with `$vars.<key>`.

### Setting variables

```json
{
  "id": "set_discount",
  "data": {
    "block": "control.set",
    "config": {
      "values": {
        "discount_rate": "$input.campaign.discount",
        "max_discount": 1000
      }
    }
  }
}
```

After this step runs, `$vars.discount_rate` resolves to the value of `$input.campaign.discount`, and `$vars.max_discount` is `1000`.

### Variable lifetimes

Variables persist for the entire flow run. They survive across branches and loop iterations. If a branch doesn't run, variables set in that branch won't exist — `$vars.<key>` will resolve to `null`.

### Nested variable access

You can access nested properties of a variable just like any other `$`-path:

```text
$vars.campaign.discount_rate
```

## Expression evaluation context

Expressions are evaluated in the context of the running flow, event handler, or policy check. The available root variables depend on what you're configuring:

### In flow conditions

- `$input` — the trigger payload
- `$step.<id>` — outputs of previous steps
- `$vars` — flow variables
- `$auth` — the caller's identity (if the trigger has auth context)
- `$env` — environment variables

### In policy conditions

- `$auth` — the caller's identity and claims
- `$record` — the record being created/updated/deleted
- `$input` — the input data for the operation
- `$env` — environment variables

### In webhook mappings

- `$input` — the event payload that triggered the webhook
- `$event` — the full event envelope
- `$env` — environment variables

## Debugging expressions

When a condition evaluates differently than you expected, the fastest way to debug is through Studio's execution inspector:

1. In Studio, open the flow run you want to debug.
2. Click into the step whose condition you're checking.
3. The **State inspector** panel shows the resolved value of every `$`-path in scope at that point in the run.
4. If a path shows `null` where you expected a value, trace back through the steps to find where the data was lost or transformed.

<Note>
Expressions are evaluated **lazily** — a `$`-path that's never referenced in a condition or mapping is never resolved. This means a missing step won't cause an error unless something actually tries to read it.
</Note>

### Common expression mistakes

**Referencing a step before it runs.** If a `control.if` condition references `$step.some_block`, but `some_block` comes later in the flow, the path resolves to `null` and the condition evaluates to `false`. Always place the step that produces the data before the step that consumes it.

**Using template syntax where a value is expected.** A condition expects an expression like `$input.status`, not `"{{ input.status }}"`. Writing `"{{ input.status }}"` creates a string like `"paid"`, not a comparison. Use the `$`-path directly in the condition.

**Forgetting `$auth` requires an authenticated caller.** If the trigger or context doesn't have auth, `$auth.user_id` resolves to `null`. Anonymous-accessible resources have `$auth` set to `{}` — all `$auth.*` paths return `null`.

## Environment variables in expressions

Environment variables are available via `$env`:

```text
$env.PAWABASE_REDIS_URL
```

Variable names are case-sensitive. If the variable isn't set, the expression resolves to `null`. This is useful for environment-specific configuration without hardcoding values in definitions.

<Note>
Not all environment variables are exposed. Only variables prefixed with `PAWABASE_` or `PWP_` are available in expressions, to prevent accidentally leaking secrets.
</Note>
