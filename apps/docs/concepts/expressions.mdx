Several Studio fields can use a value from the current request or flow run instead of a fixed literal. An **expression** is evaluated when the operation runs, not when you save the configuration. This page is a complete reference: the two expression forms, every available root, every filter, every condition operator, and — because these are the details that actually cause production bugs — exactly what happens when a path is missing, when types don't match, and when a step never ran.

<Callout>
You will see expression-capable fields in flow blocks, route responses, notifications, webhook mappings, transformers, and policy conditions. A field that does not indicate expression support treats what you enter as a literal value — typing `$input.body.email` into a plain text field stores that literal string, not a lookup.
</Callout>

## Why Pawabase has expressions at all

Studio configuration is data, not code (see [Definitions as data](/concepts/definitions-as-data)). A resource, policy, or flow is a JSON document Pawabase validates and compiles. That document has to be able to say "use whatever the caller sent as the order's `customer_id`" without becoming a general-purpose programming language — because a programming language embedded in configuration would defeat the entire point of configuration being inspectable, diffable, and safe to store in Studio.

Expressions are the answer: a small, closed vocabulary for reading a value out of the current request or flow-run state, and an equally small vocabulary for reshaping that value into text. There is no loop, no user-defined function, and no arbitrary computation inside an expression — if a flow genuinely needs a loop, it uses the `control.foreach` block; if it needs arithmetic, it uses `math.calculate`; if it needs real code, it uses a registered function. Expressions only ever *read* and *format*.

## The two forms

### A path for a value

Use a `$` path when the field needs the value itself — a condition operand, or a config field documented as accepting a raw path:

```text
$input.event.payload.customer_id
```

A `$` path resolves to whatever is at that location in the current state: a string, a number, a boolean, `null`, an object, or an array. It is never coerced to text. This matters most in conditions (`$input.body.total` compared numerically with `gt`) and in fields that are meant to carry a whole object or array forward (see [Whole-value templates](#whole-value-templates-preserve-type) below, which is the template equivalent).

### A template for text

Use `{{ }}` when you are building text:

```text
Order {{ input.event.payload.order_number }} is ready
```

Inside `{{ }}` you write the path **without** the leading `$` — the braces themselves signal that this is a template lookup. A common mistake is writing `{{ $input.body.email }}`; the leading `$` there is not part of the syntax and will resolve as if you were looking up a field literally named `$input`, which does not exist, and the whole lookup will silently return a missing value.

### Whole-value templates preserve type

If the **entire field** is one template — nothing before or after the `{{ }}` — Pawabase returns the value itself rather than converting it to text:

```text
{{ input.items }}
```

This can pass an array straight through to a field that expects an array, such as `transform.batch`'s `value` or `resource.create`'s `data`. The moment the template is mixed with other text —

```text
Items: {{ input.items }}
```

— the result is always a string, and a non-scalar value embedded this way is serialized as JSON text (an array becomes `["a","b"]` inside the sentence, not a native array). This is exactly how the templating engine works internally: a string that is *entirely* one `{{ }}` expression evaluates the expression and returns its native value; anything else runs every `{{ }}` occurrence through substitution and concatenates the results as text, converting objects and arrays to JSON along the way and rendering a missing value as an empty string.

<Warning>
Because a partially-templated field always produces text, do not try to build an array or object by concatenating templates inside one string field (`"[{{ a }}, {{ b }}]"`). Use `transform.template` to build structured JSON from parts, or pass a single whole-value template.
</Warning>

## Available roots

The available roots depend on where the field runs — a policy condition and a flow condition do not see the same state.

| Root | Use it for | Example | Available in |
| --- | --- | --- | --- |
| `input` | The data received by the trigger | `input.body.email` | Flow steps and conditions |
| `auth` | The current caller's identity | `auth.user_id`, `auth.roles` | Flows, policies |
| `credential` | The API key or service credential making the call | `credential.is_service`, `credential.scopes` | Policies, and flow steps with caller context |
| `record` | The record being read or changed | `record.owner_id` | Policies, `policy.check`, resource-triggered flows |
| `request` | Details of the underlying HTTP request | `request.method` | Policies |
| `steps` | Output from a previous flow step | `steps.load_customer.output.id` | Flows |
| `vars` | Values set earlier with a Set variables step | `vars.retry_count` | Flows |
| `item` | The current item inside a For each step | `item.id` | Flow steps inside a `control.foreach` branch |
| `index` | The current For each position | `index` | Flow steps inside a `control.foreach` branch |
| `error` | Error information in an error branch | `error.message` | Flow steps wired to an `error` branch |
| `project` | The current project reference | `project` | Flows, policies |
| `env` | The current environment name | `env` | Flows, policies |
| `now` | The current UTC timestamp | `now` | Anywhere a path is resolved — it is a reserved path segment, not a value under any root |

In a **policy condition**, the useful roots are usually `auth`, `record`, `input`, `request`, and `credential` — a policy is deciding whether one caller may touch one record, so its state is narrower and more stable than a flow run's. In a **flow condition**, use the flow roots (`input`, `steps`, `vars`, `item`, `index`, `error`, `auth`, `project`, `env`) — a flow run accumulates state as it executes, so later steps see more than earlier ones.

### `auth` versus `credential`

These are commonly confused. `auth` describes the **signed-in user**, if any — their id, roles, permissions, authentication assurance level. `credential` describes the **API key or service identity** making the call — whether it's a service credential (which bypasses policies entirely), and what scopes it carries. A request can have a `credential` (a valid publishable key) with no meaningful `auth` (no signed-in user, i.e. an anonymous caller), and a service-to-service call can have a `credential` with no `auth` at all. When a policy needs to distinguish "any signed-in customer" from "our own trusted backend," it is usually combining a check on `credential.is_service` (via the `service` shorthand) with a check on `auth`.

## Trigger input

The shape of `input` is determined entirely by the trigger, and it differs meaningfully between trigger types:

- an HTTP trigger has `input.body` (the parsed request body), `input.params` (path parameters), and `input.query` (query string parameters);
- an event trigger has the event envelope under `input.event`, typically `input.event.payload` for the event's data and `input.event.name` for the event name itself;
- a resource-change trigger has the changed record and the operation that produced it, so you might see `input.record` and `input.operation`;
- a scheduled trigger receives whatever payload the schedule was configured to send, which may be empty;
- a queued run (`trigger.job`, dispatched by `queue.flow`) receives exactly the `input` object that `queue.flow` was configured to pass;
- a manual run receives whatever input the operator supplied when starting it from Studio or the platform API.

For an event trigger such as `order.created`, a condition can inspect:

```text
$input.event.payload.status
```

For a custom route, a response or data step can use:

```text
{{ input.body.customer_id }}
```

<Tip>
Open the flow run's trigger input in Studio when you are unsure about the actual shape, rather than guessing the path from the trigger's name or the event's name. Event payload shapes in particular are whatever the emitting side put there — `event.emit`'s `payload` field, or the default payload Pawabase builds for a resource-change event — and are not standardized across every event in your backend.
</Tip>

## Previous step output

Every completed flow step has an output, addressed by `steps`, the step's id, and `output`:

```text
$steps.find_customer.output.id
```

```text
HTTP trigger
   ↓
Find customer
   ↓
Condition: $steps.find_customer.output.total
   ↙                         ↘
Create order                Return not found
```

### If a step didn't run

If a step is inside a branch that did not execute — the `false` side of an `if` that took `true`, the untaken cases of a `switch`, an `each` branch of a `foreach` that never iterated because the list was empty — its output does not exist for the rest of the run. Referencing `steps.<that id>.output` resolves to a missing value rather than raising an error at that point; the failure, if any, shows up later, wherever a downstream field actually requires a value and gets none. Guard the reference with an `exists` or `truthy` condition before you rely on it, and be explicit about the difference between "this step ran and returned nothing useful" and "this step never ran."

### Referencing a step across a retry or timeout boundary

Inside a `control.retry` or `control.timeout` block's `attempt` branch, the step ids inside that branch behave like any other step — `steps.<id>.output` after the retry block reflects the attempt that actually finished (successfully, for `retry`; within budget, for `timeout`). If every attempt of a `control.retry` fails, the block's own error propagates and steps inside the `attempt` branch are treated as not having produced usable output.

## Variables

Use Studio's **Set variables** step (`control.set`) to keep a value for the rest of the flow run:

```text
Variable: retry_count
Value: 0
```

Later fields can reference it:

```text
$vars.retry_count
```

Variables belong to exactly one flow run. They are not database records, they are not shared with another concurrent request or job, and they do not persist between runs — a counter you want to survive across runs belongs in a resource or the cache (`cache.get`/`cache.set`), not in `vars`. Setting the same variable name twice in one run simply overwrites it for every step after the second `Set variables`.

## Nested values and arrays

Use dot-separated paths for nested objects and numeric path segments for arrays:

```text
$input.body.shipping_address.city
$input.body.items.0.sku
```

Internally, path resolution walks each dot-separated segment: if the current value is an object, it looks up the segment as a key; if it's a list and the segment is a number, it indexes into it; otherwise it treats the segment as an attribute lookup. The moment any segment can't be resolved — a missing key, an out-of-range index, a segment applied to something that isn't an object or list — the whole lookup resolves to a missing value (`null` in a template, absent for `exists`/`truthy` checks) rather than raising a path error partway through. This is deliberate: a flow that conditionally receives an `items` array of varying length should not crash just because `items.5` doesn't exist this time.

The practical consequence is that a typo in a path (`input.boddy.email`) is indistinguishable, at evaluation time, from a legitimately absent field. Nothing tells you "this path doesn't exist in the schema" — you only see a missing value downstream. When a template renders unexpectedly empty, treat a typo as at least as likely as absent data, and check the step's actual output in Studio rather than re-reading the expression for a while.

### Arrays of objects

A common shape is an array of objects, such as line items on an order:

```text
$input.body.items.0.sku
$input.body.items.0.quantity
```

There is no wildcard or "for every item, extract this field" path syntax — that transformation is what `control.foreach` (to act on each item) or `transform.pick`/`transform.map` (to reshape every item in a list at once) are for. A plain path only ever reaches one specific index.

## Template filters

Pawabase supports these filters in `{{ }}` templates, applied with `|`:

| Filter | Example | Result |
| --- | --- | --- |
| `default` | `{{ input.body.name \| default: "Guest" }}` | Uses the fallback when the value is missing (`null`) or an empty string. A value of `0` or `false` is **not** replaced — only `null`/missing and `""` trigger the default. |
| `upper` / `lower` | `{{ input.body.code \| upper }}` | Changes text case. Applied via `str(value).upper()`, so a non-string value is stringified first rather than raising an error. |
| `json` | `{{ input.body.metadata \| json }}` | Serializes a value as JSON text — the standard way to embed a whole object or array inside a larger text field. |
| `length` | `{{ input.body.items \| length }}` | Returns the length of a list, string, or object; a missing value returns `0` rather than erroring. |
| `int` / `float` | `{{ input.body.amount \| int }}` | Converts a value when conversion is possible. A missing value or empty string converts to `null`, not `0` — check for this before doing arithmetic on it. A genuinely non-numeric string (`"abc"`) will raise an error at evaluation time, which surfaces as a failed step. |
| `str` | `{{ input.body.enabled \| str }}` | Converts to text; a missing value becomes an empty string rather than the text `"None"` or `"null"`. |
| `bool` | `{{ input.body.enabled \| bool }}` | Converts using ordinary truthiness — see [Missing values and truthiness](#missing-values-and-truthiness) below, since the same rule applies here as in conditions. |
| `first` / `last` | `{{ input.body.items \| first }}` | Selects the first or last item of a list. An empty or missing list resolves to a missing value, not an error. |
| `keys` | `{{ input.body.metadata \| keys }}` | Returns the object's keys as a list; a non-object value returns an empty list rather than erroring. |

Filters can be chained with `|`, evaluated left to right: `{{ input.body.code | default: "n/a" | upper }}` first substitutes a default if the code is missing, then upper-cases whatever survives. The argument after `:` on a filter like `default` is parsed as JSON when possible (so `default: 0` supplies the number `0`, not the string `"0"`) and falls back to a plain string otherwise (`default: "Guest"`).

Use the filter result only where the next field accepts that type — remember that any template mixed with surrounding text always produces a string, filters included, so `{{ input.body.total | int }}` embedded in a sentence still renders as text even though the filter itself performed a numeric conversion.

## Conditions

In Studio's condition editor, and in any raw condition field (`control.if`'s and `control.while`'s `condition`, `transform.filter`'s `condition`, `policy.check`'s `policy`, and every resource operation's policy), you choose an operator and supply operands. A condition is always a single-key object naming the operator; combinators nest other conditions as their value.

<Warning>
Fields documented as "raw" (`control.if`, `control.while`, `transform.filter`) are **not** pre-rendered as `{{ }}` templates before the block runs — you write the condition directly as a `$`-path structure, not wrapped in `{{ }}`. Writing `{{ $input.status = paid }}` into a condition field is a common mistake; write `{"eq": ["$input.status", "paid"]}` (or the equivalent Studio condition-builder UI) instead.
</Warning>

### Combinators

- **all** — every child condition must be true (logical AND).
- **any** — at least one child condition must be true (logical OR).
- **not** — negates a single child condition.

```json
{ "all": [
  { "eq": ["$input.status", "paid"] },
  { "gt": ["$input.total", 100] }
] }
```

### Comparisons

**eq**, **ne**, **gt**, **gte**, **lt**, **lte** compare two operands. Numeric comparisons (`gt`, `gte`, `lt`, `lte`) treat a missing operand (`null`) as always failing — a `gt` where either side is missing evaluates to `false`, not an error, so a genuinely absent `total` will make a `gt` condition on it fail closed rather than throw.

`eq` and `ne` normalize ids before comparing: a numeric id from the database and the same id arriving as a string from a token or URL parameter are treated as equal. This exists specifically so that `{"eq": ["$record.owner_id", "$auth.user_id"]}` (the shape behind the built-in `owner` policy) works regardless of which side happens to be a database integer and which happens to be a string claim.

### Membership and text

**in**, **not_in** check list membership (with the same id normalization as `eq`); **contains** checks either list membership or a substring, depending on whether the left operand is a list or a string; **starts_with** and **ends_with** are string prefix/suffix checks; **matches** applies a regular expression, checked with `re.search` (a *search* for the pattern, not a required full match) against the string form of the left operand.

```text
Truthy: $input.body.email
Exists: $steps.find_customer.output.id
Equals: $input.body.status = paid
Matches: $input.body.reference matches ^ORD-
```

A `matches` pattern with a syntax error is rejected when you save the condition, not silently ignored at run time — Studio validates the regex against Python's `re` engine before storing the policy or flow.

### Presence checks

**exists** is true when the resolved value is not `null` — this includes `0`, `false`, and empty string/list/object, all of which "exist" even though they are falsy. **truthy** applies ordinary truthiness (see below). **empty** is the negation of truthy.

Use `exists` when you specifically need to distinguish "present but empty" from "absent"; use `truthy` when an empty value should be treated the same as a missing one, which is the more common case for optional business data.

### Shorthands

Policy and flow conditions can also use the built-in access shorthands, each of which expands to an ordinary combination of the operators above:

| Shorthand | Expands to (conceptually) | Typical use |
| --- | --- | --- |
| `authenticated` | Caller has a valid session | Gate on any signed-in user |
| `role` | Caller's roles include the named role(s) | `{"role": "admin"}`, or `{"role": ["admin", "support"]}` for any-of |
| `permission` | Caller's permissions include the named permission(s), or the wildcard `*` | `{"permission": "orders.refund"}` |
| `owner` | Caller is authenticated **and** the named record field equals the caller's user id | `{"owner": "author_id"}` (defaults to `owner_id` if given as `true`) |
| `service` | The credential is a service credential (secret key or operator), not an ordinary user session | `{"service": true}` |
| `kind` | The caller's auth kind equals the given value | Distinguishing session types where your backend has more than one |
| `scope` | The API key's scopes include the given scope | `{"scope": "resource:write"}` |
| `aal` | The caller's authentication assurance level equals the given value | `{"aal": "aal2"}` for MFA-gated operations |

These read most naturally in a resource policy or in `policy.check`'s `policy` field, where `record` and `credential` are always in context. Inside a plain flow `control.if`, they still work — but only once whatever they depend on (`record`, `credential`) is actually present in that run's state; a `control.if` early in a flow, before any resource block has populated `record`, cannot meaningfully evaluate `{"owner": "author_id"}`.

<Note>
Service credentials (a secret key, an operator, or an internal service call) bypass ordinary policy evaluation entirely rather than being checked against the condition — this is why your own trusted server, and flow steps like `resource.create` that run with service rights, don't need to satisfy the same policy a public caller would.
</Note>

## Missing values and truthiness

`truthy` (and the `bool` filter) apply this rule: missing values, `null`, `false`, `0`, empty strings, empty lists, and empty objects are **false**. Non-empty strings, non-zero numbers, `true`, non-empty lists, and non-empty objects are **true**.

This means `truthy` cannot distinguish a `total` of `0` from a `total` that was never set — both are false. When missing and explicitly-zero (or explicitly-`null`) mean different things for your business rule — a discount of `0` is a valid discount, but a missing discount might mean "not yet calculated" — validate the input up front (`validate.schema`) or test with `exists` instead of `truthy`, and don't let the ambiguity travel deeper into the flow before you resolve it.

## Where expressions are actually used

Expressions are not confined to one Studio screen. The same `$path`/`{{ }}` syntax and the same condition language appear in:

- **flow blocks** — nearly every config field on a data or platform block accepts a template, and `control.if`, `control.while`, and `transform.filter` accept raw conditions;
- **resource operation policies** — the condition deciding whether an operation may run, evaluated with `auth`, `record`, `input`, `request`, and `credential` in scope;
- **`policy.check`** inside a flow — the same condition language, evaluated explicitly against a `record` and `input` you supply, useful when a flow needs to make an authorization decision mid-run rather than only at the trigger;
- **response and transformer configuration** — shaping what a caller receives;
- **webhook payload mapping** — building the JSON body sent to an external system from flow state;
- **mail templates** — building subject lines and body content from trigger and step data.

Learning the syntax once means it transfers directly to every one of these surfaces; there is no separate expression language for policies versus flows versus mail.

## Debug an expression

1. Open the flow run in Studio and inspect the trigger input and the output of the step immediately before the expression that isn't behaving.
2. Compare the path segment by segment with the visible object — a missing value almost always means either a typo in the path or a step that didn't run, not a bug in the expression engine.
3. Check whether the step you're referencing is on a branch that actually executed this run.
4. Check whether the field expects a raw value (`$path`, for a condition) or rendered text (`{{ }}`), and that you haven't mixed the two syntaxes.
5. If a filter is involved, check its documented behavior on a missing value above — several filters (`default`, `length`, `first`/`last`, `keys`) deliberately return a safe fallback rather than erroring, which can mask an upstream problem if you assumed it would fail loudly.
6. Add a temporary `log.write` step with the expression's value, run the flow again, and remove the log afterward if it could expose sensitive data such as a token or a customer's personal information.

The most common mistakes, in order of frequency: writing `step` instead of `steps`; reading event data from `input.body` instead of `input.event.payload`; wrapping a raw condition field in `{{ }}`; referencing a step that is on a branch that didn't run; and confusing `truthy` with `exists` when a business value of `0` or an empty string is meaningful.
