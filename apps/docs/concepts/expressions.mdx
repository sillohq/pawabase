Several Studio fields can use a value from the current request or flow run instead of a fixed literal. An expression is evaluated when the operation runs.

You will see expression-capable fields in flow blocks, route responses, notifications, webhook mappings, and other configuration screens. A field that does not indicate expression support treats what you enter as a literal value.

## The two forms

### A path for a value

Use a `$` path when the field needs the value itself, such as a condition or a variable:

```text
$input.event.payload.customer_id
```

### A template for text

Use `{{ }}` when you are building text:

```text
Order {{ input.event.payload.order_number }} is ready
```

If the entire field is one template, Pawabase preserves the value's type. For example, `{{ input.items }}` can pass an array to a later step. When a template is mixed with other text, the result is text.

## Available roots

The available roots depend on where the field runs.

| Root | Use it for | Example |
| --- | --- | --- |
| `input` | The data received by the trigger | `input.body.email` |
| `auth` | The current caller context | `auth.user_id` |
| `steps` | Output from a previous flow step | `steps.load_customer.output.id` |
| `vars` | Values set earlier with a Set variables step | `vars.retry_count` |
| `item` | The current item inside a For each step | `item.id` |
| `index` | The current For each position | `index` |
| `error` | Error information in an error branch | `error.message` |
| `project` | The current project reference | `project` |
| `env` | The current environment name | `env` |

In a policy condition, the useful roots are usually `auth`, `record`, `input`, `request`, and `credential`. In a flow condition, use the flow roots above.

## Trigger input

The shape of `input` is determined by the trigger:

- an HTTP trigger usually has `input.body`, `input.params`, and `input.query`;
- an event trigger has the event envelope under `input.event`;
- a scheduled or queued run receives the payload supplied when it was started.

For an event trigger such as `order.created`, a condition can inspect:

```text
$input.event.payload.status
```

For a custom route, a response or data step can use:

```text
{{ input.body.customer_id }}
```

Open the flow run input in Studio when you are unsure about the actual shape. Do not guess the path from the event name alone.

## Previous step output

Every completed flow step has an output. Reference it with `steps`, the step's ID, and `output`:

```text
$steps.find_customer.output.id
```

Example:

```text
HTTP trigger
   ↓
Find customer
   ↓
Condition: $steps.find_customer.output.total
   ↙                         ↘
Create order                Return not found
```

If a step is in a branch that did not run, its output is missing. Guard the reference with an existence or truthiness condition before using it.

## Variables

Use Studio's **Set variables** step to keep a value for the rest of the flow run:

```text
Variable: retry_count
Value: 0
```

Later fields can reference:

```text
$vars.retry_count
```

Variables belong to one flow run. They are not database records and are not shared with another request or job.

## Nested values and arrays

Use dot-separated paths for nested objects and numeric path segments for arrays:

```text
$input.body.shipping_address.city
$input.body.items.0.sku
```

If a property is missing, the lookup resolves to a missing value rather than raising a path error. A later operation can still fail if it requires a non-null value, so use a condition or a default before passing optional data to a required field.

## Template filters

Pawabase supports these filters in `{{ }}` templates:

| Filter | Example | Result |
| --- | --- | --- |
| `default` | `{{ input.body.name \| default: "Guest" }}` | Uses the fallback for a missing or empty value. |
| `upper` / `lower` | `{{ input.body.code \| upper }}` | Changes text case. |
| `json` | `{{ input.body.metadata \| json }}` | Serializes a value as JSON text. |
| `length` | `{{ input.body.items \| length }}` | Returns the length of a list or value. |
| `int` / `float` | `{{ input.body.amount \| int }}` | Converts a value when conversion is possible. |
| `str` / `bool` | `{{ input.body.enabled \| bool }}` | Converts the value to text or boolean. |
| `first` / `last` | `{{ input.body.items \| first }}` | Selects the first or last item. |
| `keys` | `{{ input.body.metadata \| keys }}` | Returns object keys. |

Use the filter result only where the next field accepts that type. A template embedded in a sentence is always text.

## Conditions

In Studio's condition editor, choose the operator and enter expressions or literal values for its operands. The supported operators are:

- **all**, **any**, and **not** for combining conditions;
- **truthy**, **exists**, and **empty** for presence and value checks;
- **eq**, **ne**, **gt**, **gte**, **lt**, and **lte** for comparisons;
- **in**, **not_in**, **contains**, **starts_with**, **ends_with**, and **matches** for membership and text checks.

Useful condition values include:

```text
Truthy: $input.body.email
Exists: $steps.find_customer.output.id
Equals: $input.body.status = paid
Matches: $input.body.reference matches ^ORD-
```

Policy conditions can also use the built-in access shorthands **authenticated**, **role**, **permission**, **owner**, **service**, **kind**, **scope**, and **aal**. Configure those in the policy editor; see [Policies](/policies/overview).

## Missing values and truthiness

`truthy` uses the value resolved by the path. Missing values, `null`, `false`, `0`, empty strings, empty lists, and empty objects are false. Non-empty strings, non-zero numbers, `true`, non-empty lists, and non-empty objects are true.

When missing and explicitly `null` are equivalent for your business rule, test with `exists` or `truthy`. When they mean different things, validate the input before the flow reaches the ambiguous step.

## Debug an expression

1. Open the flow run in Studio.
2. Inspect the trigger input and the output of the step immediately before the expression.
3. Compare the path segment by segment with the visible object.
4. Check whether the step is on a branch that actually ran.
5. Check whether the field expects a value or rendered text.
6. Add a temporary log step with the expression, run the flow again, and remove the log if it could expose sensitive data.

The most common mistakes are using `step` instead of `steps`, reading event data from `input.body`, referencing a step that did not run, and putting a template into a condition field that expects a path.
