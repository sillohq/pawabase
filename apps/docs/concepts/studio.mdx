Pawabase Studio is the control center for your project. It is where you design the backend that your application consumes: data resources, access policies, flows, authentication, storage, realtime, integrations, and operational settings.

<Callout>
Studio is a product interface, not a source-code editor. Configure features using the fields, builders, and editors Studio provides. The internal representation saved by Pawabase is not something your application needs to construct.
</Callout>

## Start with the environment selector

Before changing anything, confirm the project and environment shown in Studio. A change made in `development` is not a change made in `production`.

The environment determines:

- which database and storage are used;
- which users and organizations exist;
- which API keys and secrets are valid;
- which integrations receive events;
- which application traffic you are inspecting.

Make it a habit to say the environment name out loud before a destructive or operational action.

## What you configure in Studio

### Build

Use the build areas to define the backend:

| Area | Use it to… |
| --- | --- |
| Resources | Define application data, fields, relations, operations, and migrations. |
| Schemas | Reuse validated input shapes for routes and flows. |
| Policies | Define who may read, create, update, or delete data. |
| Transformers | Shape responses for a particular consumer. |
| Routes | Expose a business operation handled by a flow or supported extension. |
| Database | Inspect the environment's data and use supported database tools. |

### Automate

Use the automation areas to connect behavior:

| Area | Use it to… |
| --- | --- |
| Flows | Build multi-step processes with triggers, conditions, data operations, and side effects. |
| Events | Connect a business event to downstream behavior. |
| Queues and jobs | Move work out of a request and inspect retries or failures. |
| Schedules | Run a flow or event on a cron or interval. |
| Webhooks | Send or receive signed events with external systems. |
| Mail | Define reusable email content and delivery behavior. |

### Services

Use the service areas to configure what applications use directly:

- **Users and auth** for accounts, roles, organizations, sessions, and auth settings;
- **Storage** for buckets, object access, and file lifecycle;
- **Realtime** for channels, subscriptions, presence, and history.

### Operate

Use the operations areas to understand the running system:

- request and application logs;
- flow runs and execution traces;
- queue depth and failed jobs;
- event and webhook deliveries;
- API keys and encrypted secrets;
- environment configuration and promotion.

## A reliable Studio workflow

For any feature, follow the same loop:

<Steps>
  <Step title="Frame the product behavior">
    Write down who performs the action, what data changes, what must happen immediately, and what may happen later.
  </Step>
  <Step title="Configure the smallest backend surface">
    Create only the resource, policy, flow, route, or integration needed for the behavior. Keep the first version easy to inspect.
  </Step>
  <Step title="Check the generated application surface">
    Use the environment's API documentation and connection details to see how your application will call the backend.
  </Step>
  <Step title="Run a realistic request">
    Test as each relevant actor: anonymous, signed-in customer, staff member, organization member, or administrator.
  </Step>
  <Step title="Inspect the result and the failure path">
    Check the returned data, policy result, flow trace, event, job, notification, or webhook delivery as appropriate.
  </Step>
  <Step title="Promote deliberately">
    Move definitions to the next environment only after the behavior and permissions are understood. Keep production data and credentials separate.
  </Step>
</Steps>

## Use the generated API documentation

Open the environment's **API docs** from Studio to inspect the public application-facing operations generated for that environment. This is the right place to confirm:

- the route and HTTP method;
- required and optional fields;
- response shape and relations;
- authentication requirements;
- available query parameters;
- example requests for the selected environment.

Do not use Studio's own management requests as an application integration. Your application should use the public gateway endpoints and client guidance documented under [Clients](/clients/overview).

## Safe changes

Some Studio actions have lasting effects:

- migrating or changing a resource field;
- enabling a public operation;
- changing a policy;
- rotating or revoking a key;
- changing a webhook destination;
- deleting data or a definition;
- changing production settings.

Before saving, check the environment, read the impact shown by Studio, and consider whether existing records and clients still satisfy the new validation or policy. Use a development or staging environment for schema and workflow changes first.

## When a feature does not behave as expected

Start at the boundary where the behavior should occur:

| Symptom | First place to inspect |
| --- | --- |
| The application cannot sign in | Auth settings, credentials, and token/session response. |
| A request returns `401` | Session, token expiry, or environment key. |
| A request returns `403` | Operation policy and caller context. |
| A field is rejected | Resource fields, schema, and request body. |
| A flow does not start | Trigger, event name, enabled state, and event history. |
| A flow starts but stops | Execution trace and the failed step's error. |
| A job remains pending | Queue depth, worker status, schedule, or retry state. |
| A webhook is missing | Event subscription, destination status, signature, and delivery attempts. |
| A live update is missing | Authentication, channel rule, subscription, and realtime connection. |

See [Troubleshooting](/reference/troubleshooting) for the diagnostic sequence and [Observability](/operate/observability) for the operational views.

## What Studio is not

Studio is not:

- your end user's application;
- a replacement for your application client or server;
- a public API credential;
- a reason to expose management access to untrusted users;
- a place to edit Pawabase's internal implementation.

Configure the backend in Studio, then integrate your product through the public interfaces described in the client, auth, data, storage, realtime, events, and webhooks documentation.
