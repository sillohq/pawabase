Pawabase Studio is the control center for your project. It is where you design the backend that your application consumes: data resources, access policies, flows, authentication, storage, realtime, integrations, and operational settings.

<Callout>
Studio is a product interface, not a source-code editor. Configure features using the fields, builders, and editors Studio provides. The internal representation saved by Pawabase is not something your application needs to construct, and you will never need to write or read it directly to use Pawabase well.
</Callout>

## What Studio is, in one sentence

Studio is where you turn a description of product behavior — "customers can view their own orders," "a new signup gets a welcome email," "only staff can issue refunds" — into a running backend, and where you go afterward to see what that backend actually did. Everything else on this page is detail underneath that one sentence.

## Start with the environment selector

The sidebar's top switcher shows your [organization](/concepts/organizations); its **Team** page manages members, roles and invitations, and everything you see is limited to the organizations you belong to.

Before changing anything, confirm the project and environment shown in Studio. A change made in `development` is not a change made in `production`.

The environment determines:

- which database and storage are used;
- which users and organizations exist;
- which API keys and secrets are valid;
- which integrations receive events;
- which application traffic you are inspecting.

Make it a habit to say the environment name out loud before a destructive or operational action. This sounds excessive until the first time you delete a resource field in what you believed was `staging` and discover it was `production` — at which point it becomes a habit you keep permanently.

### Why Studio makes you pick an environment explicitly, every time

It would be technically possible for Studio to remember your last environment across sessions and never ask again. Pawabase deliberately keeps the environment selection visible and prominent instead, because the cost of a wrong assumption here — editing production policy thinking you're in staging — is disproportionately higher than the minor friction of confirming it. Every destructive action in Studio (deleting data, rotating a key, disabling an operation) is scoped to the environment you're currently in, with no cross-environment undo.

## What you configure in Studio

### Build

Use the build areas to define the backend:

| Area | Use it to… |
| --- | --- |
| Resources | Define application data, fields, relations, operations, and migrations. |
| Schemas | Reuse validated input shapes for routes and flows. |
| Policies | Define who may read, create, update, or delete data. |
| Transformers | Shape responses for a particular consumer. |
| Routes | Expose a business operation handled by a flow or supported extension. |
| Database | Inspect the environment's data and use supported database tools. |

**When to use each area, concretely.** Reach for **Resources** first, always — it's the foundation almost everything else refers to. Reach for **Schemas** when the same input shape (say, a shipping address) is validated in more than one place — a resource field set and a custom route's input — and you don't want to define it twice. Reach for **Policies** as soon as a resource holds anything other than fully public data; the default posture should be "narrow, then widen deliberately," not the reverse. Reach for **Transformers** when different consumers of the same resource need different shapes of the same data — an internal admin view that shows every field versus a public API that omits internal notes. Reach for **Routes** only when a business operation doesn't map to a single resource's CRUD lifecycle — checkout, a report export, a multi-step signup.

### Automate

Use the automation areas to connect behavior:

| Area | Use it to… |
| --- | --- |
| Flows | Build multi-step processes with triggers, conditions, data operations, and side effects. |
| Events | Connect a business event to downstream behavior. |
| Queues and jobs | Move work out of a request and inspect retries or failures. |
| Schedules | Run a flow or event on a cron or interval. |
| Webhooks | Send or receive signed events with external systems. |
| Mail | Define reusable email content and delivery behavior. |

**When to use each area, concretely.** Build a **Flow** whenever a business operation needs more than one step, a branch, or a side effect beyond a plain database write. Use **Events** when more than one independent piece of behavior should react to the same underlying change, so you're not hard-wiring every consumer into the producer. Check **Queues and jobs** whenever you suspect something is slower or less reliable than it should be — it's the single fastest way to see whether a backlog is building up. Use **Schedules** for calendar-driven work that isn't triggered by any specific event. Use **Webhooks** to talk to systems Pawabase doesn't otherwise integrate with directly. Use **Mail** to centralize transactional email content so it isn't duplicated across several flows.

### Services

Use the service areas to configure what applications use directly:

- **Users and auth** for accounts, roles, organizations, sessions, and auth settings;
- **Storage** for buckets, object access, and file lifecycle;
- **Realtime** for channels, subscriptions, presence, and history.

These three are grouped separately from Build and Automate because they are capabilities your application talks to *directly*, over their own public endpoints, rather than capabilities that only exist inside resources and flows. A mobile app calls the auth endpoints, uploads to storage, and opens a realtime connection on its own — it does not go through a resource or a flow to do any of those three things, even though a flow can also call them server-side (`storage.put`, `realtime.publish`, `auth.lookup`).

### Operate

Use the operations areas to understand the running system:

- request and application logs;
- flow runs and execution traces;
- queue depth and failed jobs;
- event and webhook deliveries;
- API keys and encrypted secrets;
- environment configuration and promotion.

This is the area you should expect to spend real time in once your backend is handling real traffic — not because something is necessarily broken, but because "is the fulfillment flow keeping up with order volume" and "did that customer's webhook actually get delivered" are ordinary, routine questions that Operate is built to answer without you needing to reconstruct the answer from raw data.

## A reliable Studio workflow

For any feature, follow the same loop:

<Steps>
  <Step title="Frame the product behavior">
    Write down who performs the action, what data changes, what must happen immediately, and what may happen later. Doing this in plain language before opening any Studio screen is what keeps you from accidentally building the wrong shape — a resource operation when you needed a flow, or a public policy when you needed an owner check.
  </Step>
  <Step title="Configure the smallest backend surface">
    Create only the resource, policy, flow, route, or integration needed for the behavior. Keep the first version easy to inspect. Resist the urge to add fields, operations, or branches "while you're in there" for a use case that doesn't exist yet — every additional surface is one more thing that can be misconfigured.
  </Step>
  <Step title="Check the generated application surface">
    Use the environment's API documentation and connection details to see how your application will call the backend. This step catches a surprising number of mistakes on its own — an operation you thought was enabled but wasn't, a field with a type you didn't expect, a route path that doesn't match what your client code expects.
  </Step>
  <Step title="Run a realistic request">
    Test as each relevant actor: anonymous, signed-in customer, staff member, organization member, or administrator. Testing only as yourself, an operator with elevated access, is the most common reason a policy bug reaches production undetected — your own operator session may bypass the exact restriction you meant to test.
  </Step>
  <Step title="Inspect the result and the failure path">
    Check the returned data, policy result, flow trace, event, job, notification, or webhook delivery as appropriate. Deliberately trigger the failure path too — an invalid input, a denied policy, an external call you can simulate failing — rather than only confirming the happy path works.
  </Step>
  <Step title="Promote deliberately">
    Move definitions to the next environment only after the behavior and permissions are understood. Keep production data and credentials separate.
  </Step>
</Steps>

## Use the generated API documentation

Open the environment's **API docs** from Studio to inspect the public application-facing operations generated for that environment. This is the right place to confirm:

- the route and HTTP method;
- required and optional fields;
- response shape and relations;
- authentication requirements;
- available query parameters;
- example requests for the selected environment.

Do not use Studio's own management requests as an application integration. Your application should use the public gateway endpoints and client guidance documented under [Clients](/clients/overview).

<Tip>
When a client integration behaves unexpectedly, compare what your code is actually sending against the generated API documentation for that exact environment before assuming the bug is in Pawabase's handling of the request. A stale assumption about a field name or a required parameter — often left over from an earlier version of the resource — is a more common cause than it might seem.
</Tip>

## Safe changes

Some Studio actions have lasting effects:

- migrating or changing a resource field;
- enabling a public operation;
- changing a policy;
- rotating or revoking a key;
- changing a webhook destination;
- deleting data or a definition;
- changing production settings.

Before saving, check the environment, read the impact shown by Studio, and consider whether existing records and clients still satisfy the new validation or policy. Use a development or staging environment for schema and workflow changes first.

### A checklist for a risky change

Before making one of the changes above in production, it's worth explicitly answering:

- **Who is affected?** Existing records that don't satisfy a new required field, existing sessions relying on a role you're about to rename, existing clients calling an operation you're about to disable.
- **Can it be reversed?** Rotating a key can be reversed by issuing a new one and updating your application, but revoking one without a replacement ready is not reversible without a period of broken integration. Deleting data is generally not reversible at all outside of your own backup strategy.
- **Does anything downstream depend on the current shape?** A flow reading a field you're about to rename, a webhook mapping built around a response shape you're about to change, a transformer built on a field you're about to remove.
- **Is there a safer sequence?** Often a two-step change (add the new field, backfill, migrate consumers, then remove the old field) is safer than a single destructive edit, even though it takes longer.

## When a feature does not behave as expected

Start at the boundary where the behavior should occur:

| Symptom | First place to inspect |
| --- | --- |
| The application cannot sign in | Auth settings, credentials, and token/session response. |
| A request returns `401` | Session, token expiry, or environment key. |
| A request returns `403` | Operation policy and caller context. |
| A field is rejected | Resource fields, schema, and request body. |
| A flow does not start | Trigger, event name, enabled state, and event history. |
| A flow starts but stops | Execution trace and the failed step's error. |
| A job remains pending | Queue depth, worker status, schedule, or retry state. |
| A webhook is missing | Event subscription, destination status, signature, and delivery attempts. |
| A live update is missing | Authentication, channel rule, subscription, and realtime connection. |
| A promoted feature works in staging but not production | Target-environment secrets, webhook destinations, and API keys — promotion moves definitions, never environment-specific configuration. |
| A change "didn't take effect" | Whether the environment finished recompiling after the save, and whether you're looking at the environment you actually edited. |

See [Troubleshooting](/reference/troubleshooting) for the diagnostic sequence and [Observability](/operate/observability) for the operational views.

## Studio access and operator accounts

Studio access is itself a permission surface worth designing deliberately, not an afterthought. Give each person configuring or operating the backend their own operator account rather than a shared login, so that an audit trail of configuration changes is meaningful. Grant the narrowest role a person's job actually requires — a support team member who needs to look up a customer's order does not need the ability to change policies or rotate keys, and a contractor working on one integration does not need access to every environment in the project.

See [Credentials](/concepts/credentials) for how Studio sessions relate to every other credential type in Pawabase, and treat a Studio operator account with at least the same care you'd give a production database password — because, functionally, that's close to what it is.

## What Studio is not

Studio is not:

- your end user's application;
- a replacement for your application client or server;
- a public API credential;
- a reason to expose management access to untrusted users;
- a place to edit Pawabase's internal implementation.

Configure the backend in Studio, then integrate your product through the public interfaces described in the client, auth, data, storage, realtime, events, and webhooks documentation.

## Studio's relationship to the rest of the platform

It's worth being explicit about the boundary Studio sits on, since it's easy to blur once you're used to it. Studio is where a human designs and inspects a backend. The gateway, authentication, data, storage, realtime, and flow-execution capabilities described in [Architecture](/concepts/architecture) are what actually serve your application's traffic, minute to minute, whether or not anyone has Studio open. Closing your Studio tab does not pause your backend; it only stops you from watching or changing it. Conversely, nothing your application does at runtime writes back into Studio's configuration — a flow can write application data, but it cannot redefine another flow or change a policy. Configuration flows one direction, from Studio into the running environment; application traffic never flows back into configuration. Keeping that one-way relationship in mind is usually enough to resolve confusion about "can my flow modify another flow" (no) or "does Studio need to be running for my API to work" (no).
