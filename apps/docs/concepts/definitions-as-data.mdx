Pawabase lets you design a backend from named building blocks. Studio stores and validates those choices so the same environment can expose data, authentication, automation, storage, realtime, and integrations consistently.

You do not need to edit the representation that Studio stores. Think in terms of the product behavior you are configuring.

<Callout>
The title of this page — "definitions as data" — describes a design property, not a feature you interact with directly: every resource, policy, flow, schema, and transformer you configure in Studio is stored as structured, validated configuration rather than as generated source code. You never need to read or write that structure yourself; this page explains what that property buys you and how the pieces reference each other, so that Studio's behavior (validation errors, promotion, cross-feature references) makes sense rather than feeling arbitrary.
</Callout>

## Why this matters even though you never touch it directly

If Pawabase generated a fresh block of source code every time you edited a resource in Studio, two things would follow that materially hurt you as a customer. First, promoting a change between environments would mean diffing and merging generated code, which is exactly the kind of task Pawabase exists to spare you from. Second, validating a change before it goes live — "does this policy reference a field that still exists," "does this flow reference a resource operation that's actually enabled" — would require re-parsing and re-analyzing code rather than simply checking a stored document's internal consistency, which is slower and less reliable.

Because every definition is data, Studio can validate a single change in isolation, check its references against every other definition in the same environment, version the whole set as a unit, and move a coherent bundle of definitions from one environment to another with a predictable, reviewable diff. None of this requires you to know what the stored data looks like — it only requires you to know that Studio's validation and promotion behavior is trustworthy because of it.

## The pieces you will use

| You need to… | Configure… |
| --- | --- |
| Store and query durable application data | A resource with fields, operations, relations, and validation |
| Decide who may perform an operation | A policy attached to the operation |
| Accept a structured request | A schema used by a route or flow |
| Shape what a client receives | A transformer |
| Coordinate several steps | A flow |
| Run work after something happens | An event and a subscription |
| Run work later or outside the request | A queue, job, or schedule |
| Store files | A storage bucket and its access rules |
| Send or receive external events | An outbound webhook or inbound hook |
| Send reusable email | A mail template |
| Deliver live updates | A realtime channel or resource-change subscription |

### How these pieces actually reference each other

It's worth being explicit about the reference graph, because understanding it is what makes Studio's validation messages make sense. A resource operation references a policy by name. A flow references resources (through resource blocks), schemas (through validation blocks), and other flows only indirectly (through `queue.flow`, which dispatches rather than calls). A subscription references both an event name and a consumer — a flow, function, webhook, or channel. A bucket references a policy the same way a resource operation does. None of these references are structural nesting — a policy is not "inside" the resource that uses it, it's a separately named definition that several resources, routes, and buckets can all point to by name. This is exactly why renaming a policy without updating its references breaks every place that pointed to the old name, and why Studio checks references at compile time rather than only when each definition is individually saved.

## A typical product operation

Suppose a customer places an order:

```text
Resource or custom route
        ↓
Authentication + policy
        ↓
Validate and save the order
        ↓
Order-created event
   ┌────┼─────────────┐
   ↓    ↓             ↓
Flow  Realtime      Webhook
   ↓
Queue payment or fulfillment work
```

Each piece has a distinct responsibility. Keep the initial request short and observable; move slow, retryable, or externally dependent work into the appropriate asynchronous feature.

## Names and references

When Studio asks you to select a resource, policy, schema, flow, event, bucket, or template, it is connecting two backend features by name. Choose stable names that describe business intent:

- `orders` for the data;
- `customer_order_access` for the policy;
- `checkout_input` for the request shape;
- `fulfill_order` for the workflow;
- `order.created` for the event.

Avoid renaming a definition casually after other definitions depend on it. Before changing a name, search the environment's references and update dependents in the same change.

### A naming convention that scales

As a backend grows past a handful of resources, an ad hoc naming approach (`policy1`, `check_stuff`, `flow_final_v2`) becomes a real cost — not stylistically, but functionally, because names are how you and your team navigate cross-references in Studio's search. A convention worth adopting from the start:

- **Resources**: plural nouns describing the data — `orders`, `customers`, `return_requests`.
- **Policies**: `<resource>_<operation-intent>_access` or a short description of the rule — `orders_owner_access`, `admin_only`, `mfa_required`.
- **Schemas**: `<purpose>_input` or `<purpose>_shape` — `checkout_input`, `shipping_address_shape`.
- **Flows**: verb-first, describing the action — `fulfill_order`, `send_trial_reminder`, `process_refund`.
- **Events**: `<resource>.<past-tense-verb>` — `order.created`, `subscription.cancelled`, `payout.failed`.

This isn't a Pawabase requirement — Studio doesn't enforce a naming scheme — but consistency here pays for itself the first time someone other than the original author has to trace what `flow_final_v2` actually does.

## Validation and problems

Studio validates individual settings when you save them and checks cross-feature references when the environment is compiled. A missing policy, invalid flow connection, unavailable handler, or conflicting route should appear as a configuration problem before application traffic depends on it.

When Studio reports a problem:

1. Open the problem from the environment overview.
2. Read which definition and reference failed.
3. Open the referenced feature and correct the name, field, connection, or setting.
4. Save and wait for the environment to recompile.
5. Re-run the application request that exposed the problem.

### The difference between a save-time error and a compile-time problem

These are two different checkpoints, and knowing which one you're looking at changes what you should check. A **save-time error** means the definition you're actively editing is internally invalid — a policy condition with a malformed operator, a resource field with a type Studio doesn't recognize, a flow block missing a required config field. You cannot save past this; fix it in the editor you're already in.

A **compile-time problem** means the definition saved successfully on its own, but doesn't fit with the rest of the environment — it references a policy that was since deleted, a resource field that was renamed, or a flow that points at a disabled operation. This is the more common source of confusion, because it can surface on a definition you didn't just edit: deleting a policy that three resources still reference will produce compile-time problems on those three resources, not on the deletion itself. Before deleting or renaming anything, search for what currently references it.

## Moving a backend between environments

Use environment promotion for a controlled move from development to staging or production. Definitions can move as a unit, while production data, credentials, sessions, and secrets remain environment-specific.

Before promoting:

- confirm policies with a test user for each role;
- migrate resource changes in the target environment;
- configure target-specific secrets and integrations;
- verify webhook destinations and realtime rules;
- check the target environment's API documentation.

See [Environments and promotion](/operate/environments-and-promotion) for the operational workflow.

## When to choose which piece

Use a resource when the main job is storing and querying records. Use a flow when the job is coordinating steps. Use an event when multiple independent consumers should react to a change. Use a queue when the work can outlive the request or needs retry isolation. Use a function or extension only when the product behavior genuinely needs code that the available Studio capabilities cannot express.

This separation keeps your backend understandable: data has a home, access has a policy, orchestration has a flow, and operational work has a visible job or event.

### A decision checklist for a new piece of behavior

When you're not sure which piece a new requirement belongs in, work through these questions in order:

1. **Is this primarily about storing or retrieving data?** → a resource, possibly with a relation to an existing one.
2. **Is this primarily about deciding who may do something already defined?** → a policy, attached to the relevant operation, bucket, or channel rule.
3. **Does it require more than one step, a branch, an external call, or a wait?** → a flow.
4. **Should more than one independent thing happen in response to the same change, without those things knowing about each other?** → an event with subscriptions.
5. **Can the work tolerate happening seconds, minutes, or hours later?** → a queue/job or a schedule, rather than inline in a flow triggered by the request.
6. **Does it need to notify or be notified by a system outside Pawabase?** → an outbound webhook or inbound hook.
7. **Does none of the above genuinely fit, because the behavior requires arbitrary logic the built-in blocks can't express?** → a function, used as narrowly as possible, in the specific step that needs it — not as a wrapper around an entire feature that could otherwise be built from resources, policies, and flows.

Reaching for a function too early is the most common way a Pawabase backend ends up harder to reason about than it needs to be: every piece of behavior expressed as a function is a piece Studio can no longer validate, promote as data, or show you the execution trace of in the same way it shows you a flow's. Reserve functions for the genuine minority of cases — a specialized calculation, a library integration with no HTTP equivalent — rather than as a default escape hatch.

## Worked example: a complete feature traced through every piece

To see the pieces work together, consider building "customers can leave a review on a delivered order, and a flagged review goes to moderation before publishing."

- **Resource**: `reviews` (order id, customer id, rating, text, status: `pending`/`published`/`flagged`/`rejected`).
- **Policy**: create requires the caller to be the customer on the referenced, delivered order (an owner-style check, verified via a flow if the resource policy language can't directly join through the order's delivery status); read of `published` reviews is public; read of any status is staff-only.
- **Schema**: a `review_input` schema validates rating range and text length before a review is even attempted, shared between the resource's create operation and a moderation-panel custom route if one exists.
- **Flow**: a resource-change trigger on `reviews` creation runs a moderation flow — checks the text against a simple content rule, and either sets `status` to `published` directly or leaves it `pending` for a human moderator.
- **Event**: `review.published` fires when a review's status changes to `published`.
- **Subscriptions**: one subscription sends a realtime update to the product page showing the new review; another queues a "thanks for your review" email.
- **Transformer**: the public review list response omits the customer's id and email, showing only a display name.

Every one of those seven bullet points is a separately named definition, referencing the others by name, independently validated by Studio, and independently visible in the environment's operational views once it's running. That decomposition — not any single clever piece of configuration — is what "definitions as data" is actually giving you as a customer.
