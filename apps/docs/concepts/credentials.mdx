Pawabase credentials answer two different questions:

1. **Which project environment is being addressed?**
2. **What kind of caller is making the request?**

Keep those questions separate. A key can identify an environment, while a user session identifies the person using your application. Nearly every confusing credential problem in Pawabase — a request that mysteriously returns no data, a `401` after what looked like a successful sign-in, a webhook that never arrives — comes from conflating these two questions, so this page treats them as genuinely distinct throughout.

## Credential types

| Credential | Used by | Safe in browser or mobile code? | Answers |
| --- | --- | --- | --- |
| Publishable key | Your web, mobile, or public client application | Yes, when paired with policies and intended for that environment | Which environment |
| User access token | A signed-in user session | Yes, as managed by the client session flow | Who is calling |
| Secret key | Your trusted server or private integration | No | Which environment, with elevated trust |
| Studio session | A human operator using Studio | No; do not share or automate from client code | Who is configuring the backend |
| Provider or webhook secret | Pawabase and an external integration | No | That a delivery is genuine |

## Publishable keys

A publishable key identifies an environment for application requests. It is designed to be present in a browser or mobile app, but it is not an authorization replacement.

Use it with:

- enabled resource operations;
- explicit policies;
- a user access token when the operation requires sign-in;
- a channel or storage rule where the application uses realtime or files.

Never assume that hiding a publishable key protects data. Anyone can inspect a client bundle or browser request; the policy is the security boundary.

### Why the publishable key exists at all, if it grants no authorization

If a publishable key is not itself a security boundary, it's fair to ask why it's required on every request rather than Pawabase simply trusting whatever origin a request arrives from. The answer is that the key's job is narrower and more mechanical than authorization: it tells the gateway *which environment's* data, policies, and configuration apply to this request, before authentication or policy evaluation can even begin. Without it, a single public origin would have no way to know whether an anonymous request was meant for `development` or `production` — the key is what makes environment isolation possible for callers who haven't signed in yet, which is most callers, most of the time (a storefront's product catalog, for instance, is read by anonymous shoppers all day).

### What happens when a publishable key is wrong, missing, or mismatched

- **Missing entirely.** The request is rejected before it reaches any resource or route — there's no environment context to evaluate anything against.
- **Well-formed but for the wrong environment.** The request succeeds at the transport level but operates against a different environment's data than you intended — this is the classic "why is my staging app showing production... or empty... data" bug, and it is a configuration mistake in your client, not a platform failure.
- **Revoked or rotated without updating the client.** The request is rejected the same way a missing key is; existing deployed clients using the old key start failing immediately, which is why key rotation needs a coordinated rollout (see [Rotation and incident response](#rotation-and-incident-response) below).

## User sessions

After a user signs in, the application receives a session containing an access token and usually a refresh token. The access token is sent with requests that need the user's identity.

Your client should:

- keep session handling in the supported client integration;
- refresh or re-authenticate when the access token expires;
- clear the session on sign-out;
- avoid logging tokens;
- never send a user's token to an unrelated service.

Read [Tokens and sessions](/auth/tokens-and-sessions) for the full session lifecycle.

### The relationship between the publishable key and the access token

These two credentials answer different questions and are sent together, not as alternatives. The publishable key says "this request is for environment X"; the access token says "and the caller is user Y within that environment." A request with a valid publishable key but no access token is anonymous within that environment — some operations (a public product catalog) allow that; others (viewing a customer's own orders) require the access token as well. A request with an access token but the wrong environment's publishable key will fail, because the token itself is scoped to the environment it was issued in — an access token from `development` does not identify a user in `production`, even if, coincidentally, a user with the same email exists in both.

### Multiple concurrent sessions

A user can be signed in from more than one device or browser at once — a customer on their phone and their laptop, for instance. Each session has its own access and refresh token pair. Signing out on one device should not necessarily invalidate the others unless your product specifically wants a "sign out everywhere" behavior, which is a deliberate choice to configure rather than an automatic side effect of any one sign-out request. Design your application's expectations around this: don't assume a customer only ever has one active session.

## Secret keys

A secret key is for a trusted backend or private worker. It has elevated access and must remain server-side.

Store it in a deployment secret manager or environment variable. Do not put it in:

- browser JavaScript;
- mobile application assets;
- public repositories;
- screenshots or support tickets;
- client-visible logs;
- URLs or query parameters.

If a secret key is exposed, revoke it immediately, issue a replacement, and review the audit and request history for its environment.

### What "elevated access" actually means in practice

A secret key is treated as a service credential: operations that would otherwise be checked against a policy proceed without that check, because the assumption is that whatever is holding the secret key is your own trusted code, not an arbitrary end user. This is what lets a background worker read and write records across your whole resource model without needing a policy carve-out for every internal operation — and it's exactly why the key must never reach a context outside your own trusted infrastructure. A secret key in the wrong hands does not just leak data a policy would otherwise protect; it bypasses those policies entirely for as long as it remains valid.

### When you might need more than one secret key

A single secret key per environment is enough for most backends, but consider separate secret keys per integration once you have more than one server-side system talking to Pawabase — a nightly reporting job, a support tool, and a payment-reconciliation worker, for example. Separate keys mean you can revoke or rotate one integration's access without disrupting the others, and — where Studio offers scoped keys — restrict each to only the operations that integration actually needs (see [API key scopes](#api-key-scopes) below).

## API key scopes

When Studio offers scopes for a key, grant only the capabilities that integration needs. A reporting worker may need read access; it should not receive write access to every resource.

Use separate keys for separate systems so you can rotate or revoke one integration without breaking the others. Name keys by purpose and environment, such as `staging-reporting` or `production-warehouse-sync`.

### A worked example: three integrations, three keys

A mid-sized e-commerce backend might reasonably have:

- `production-storefront` — a publishable key, used by the public website and mobile app, relying entirely on resource and route policies for protection.
- `production-warehouse-sync` — a secret key scoped to read orders and write fulfillment status, used by a third-party warehouse management system polling for new orders.
- `production-analytics-export` — a secret key scoped to read-only access across several resources, used by a nightly job that exports data to a data warehouse.

If the analytics export credential ever leaks — checked into a public repository by mistake, say — you revoke exactly that key. The storefront and warehouse integrations are unaffected, and the blast radius of the incident is limited to read access on the resources that key was scoped to, not full read/write access to the entire backend.

## Studio credentials

Studio access is for people who configure and operate the backend. Protect operator accounts with strong passwords, MFA, least-privilege roles, and individual accounts rather than shared credentials.

Do not use Studio's management session or management interface as the credential for an end-user application. Configure the backend in Studio, then use the public environment interfaces from your application.

### Why a shared operator login is a real risk, not just a hygiene nitpick

A shared Studio login means every configuration change — a policy edit, a key rotation, a resource deletion — is attributed to "whoever was logged in," which in practice means it's attributed to no one. When something goes wrong in production and the question is "who changed the checkout policy last week," a shared login has already destroyed the answer. Individual operator accounts, even on a small team, cost almost nothing to set up and are the only thing that makes an audit trail meaningful after the fact.

## Webhook and provider secrets

External systems may sign requests sent to Pawabase or receive signed requests from Pawabase. Store the relevant secret in the environment's secrets area and rotate it according to the provider's procedure.

For inbound requests, verify the signature before trusting the payload. For outbound requests, give the receiver the verification details it needs and keep the signing secret private.

See [Inbound webhooks](/webhooks/inbound), [Outbound webhooks](/webhooks/outbound), and [Webhook signatures](/webhooks/signatures).

### Why signature verification is not optional, even on HTTPS

TLS proves the request came over an encrypted connection to the right host; it says nothing about who initiated it. Any client that knows your inbound webhook URL can send it a request over HTTPS. Signature verification is the actual proof that the payload originated from the provider you configured it for — skipping it because "the URL is hard to guess" or "it's already on HTTPS" leaves the endpoint open to a forged payload from anyone who finds or guesses the URL, which is a materially weaker guarantee than a provider assumes you're relying on.

## Environment separation

Credentials are environment-specific:

```text
development key + development user token → development
staging key + staging user token         → staging
production key + production user token   → production
```

Do not reuse a development secret, user token, provider credential, or webhook secret in production.

### Why environment-specific credentials, specifically

Beyond the general principle of isolation, there's a concrete failure mode this prevents: a development secret key, likely handled more casually (shared in chat for debugging, pasted into a scratch script, left in a less-protected `.env` file) than a production one, cannot do any damage to production data even if it leaks, because it simply doesn't resolve to the production environment at all. Environment-specific credentials turn "a development secret leaked" from a production incident into a development-only cleanup.

## Rotation and incident response

When a credential may have leaked:

1. identify its environment and purpose;
2. revoke or disable it in Studio;
3. issue a replacement with the smallest required scope;
4. update the server or provider configuration;
5. review request, audit, flow, and webhook history;
6. remove the leaked value from logs, repositories, and build artifacts;
7. document the incident and the new rotation owner.

### Rotating a publishable key without downtime

Because a publishable key is embedded in already-deployed clients, revoking it immediately breaks every client still using the old value. Where the exposure isn't itself actively being exploited, a safer sequence is: issue the new key, deploy it to your client (a new app build, or a config change for a web app), confirm traffic has shifted to the new key by checking request logs, and only then revoke the old one. Where the key is being actively abused, accept the downtime and revoke immediately — a brief outage for legitimate clients is preferable to continued abuse.

### Rotating a secret key

Because a secret key is only ever used by your own server-side code, rotation is more contained: update the environment variable or secret manager entry your server reads from, redeploy or restart the affected service, confirm it's using the new key, then revoke the old one. There is no client rollout to coordinate.

## Common mistakes

- using a secret key from a browser because the first request is easier;
- sending a publishable key without policies and assuming it is private;
- using a development token against staging or production;
- sharing one secret across several unrelated integrations;
- putting a webhook secret in a request body for debugging;
- logging the `Authorization` header;
- forgetting that a realtime connection needs its own authenticated session and channel permission;
- assuming TLS alone verifies a webhook's sender (see [above](#why-signature-verification-is-not-optional-even-on-https));
- revoking a leaked publishable key before a replacement is deployed to every client that needs it, causing a self-inflicted outage;
- reusing the same operator login across a team, destroying the audit trail for configuration changes.

## A troubleshooting order of operations

When a request fails, work through these questions in order rather than guessing at the cause:

1. **Which credential was actually sent?** Log or inspect the request the client made — not what you believe your code sends, but what left the wire.
2. **Which environment does that credential belong to?** A key that resolves perfectly well, just not to the environment you expected, produces confusing-looking but entirely correct behavior.
3. **Does the operation require a user session, and if so, is one present and unexpired?** This separates an authentication failure from a policy failure.
4. **If a session is present, does the caller's identity satisfy the operation's policy?** This is where you move from "who is calling" to "may they do this."
5. **If none of the above explain it, check the integration-specific configuration** — a scope on the key, a webhook secret mismatch, a channel rule that doesn't match the channel name being used.

Following this order reliably separates credential and environment problems (steps 1–2) from authentication problems (step 3) from authorization problems (steps 4–5) — three categories that produce superficially similar symptoms (a failed or empty-seeming request) but require completely different fixes.
