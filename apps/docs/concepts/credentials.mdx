Pawabase credentials answer two different questions:

1. **Which project environment is being addressed?**
2. **What kind of caller is making the request?**

Keep those questions separate. A key can identify an environment, while a user session identifies the person using your application.

## Credential types

| Credential | Used by | Safe in browser or mobile code? |
| --- | --- | --- |
| Publishable key | Your web, mobile, or public client application | Yes, when paired with policies and intended for that environment |
| User access token | A signed-in user session | Yes, as managed by the client session flow |
| Secret key | Your trusted server or private integration | No |
| Studio session | A human operator using Studio | No; do not share or automate from client code |
| Provider or webhook secret | Pawabase and an external integration | No |

## Publishable keys

A publishable key identifies an environment for application requests. It is designed to be present in a browser or mobile app, but it is not an authorization replacement.

Use it with:

- enabled resource operations;
- explicit policies;
- a user access token when the operation requires sign-in;
- a channel or storage rule where the application uses realtime or files.

Never assume that hiding a publishable key protects data. Anyone can inspect a client bundle or browser request; the policy is the security boundary.

## User sessions

After a user signs in, the application receives a session containing an access token and usually a refresh token. The access token is sent with requests that need the user's identity.

Your client should:

- keep session handling in the supported client integration;
- refresh or re-authenticate when the access token expires;
- clear the session on sign-out;
- avoid logging tokens;
- never send a user's token to an unrelated service.

Read [Tokens and sessions](/auth/tokens-and-sessions) for the full session lifecycle.

## Secret keys

A secret key is for a trusted backend or private worker. It has elevated access and must remain server-side.

Store it in a deployment secret manager or environment variable. Do not put it in:

- browser JavaScript;
- mobile application assets;
- public repositories;
- screenshots or support tickets;
- client-visible logs;
- URLs or query parameters.

If a secret key is exposed, revoke it immediately, issue a replacement, and review the audit and request history for its environment.

## API key scopes

When Studio offers scopes for a key, grant only the capabilities that integration needs. A reporting worker may need read access; it should not receive write access to every resource.

Use separate keys for separate systems so you can rotate or revoke one integration without breaking the others. Name keys by purpose and environment, such as `staging-reporting` or `production-warehouse-sync`.

## Studio credentials

Studio access is for people who configure and operate the backend. Protect operator accounts with strong passwords, MFA, least-privilege roles, and individual accounts rather than shared credentials.

Do not use Studio's management session or management interface as the credential for an end-user application. Configure the backend in Studio, then use the public environment interfaces from your application.

## Webhook and provider secrets

External systems may sign requests sent to Pawabase or receive signed requests from Pawabase. Store the relevant secret in the environment's secrets area and rotate it according to the provider's procedure.

For inbound requests, verify the signature before trusting the payload. For outbound requests, give the receiver the verification details it needs and keep the signing secret private.

See [Inbound webhooks](/webhooks/inbound), [Outbound webhooks](/webhooks/outbound), and [Webhook signatures](/webhooks/signatures).

## Environment separation

Credentials are environment-specific:

```text
development key + development user token → development
staging key + staging user token         → staging
production key + production user token   → production
```

Do not reuse a development secret, user token, provider credential, or webhook secret in production.

## Rotation and incident response

When a credential may have leaked:

1. identify its environment and purpose;
2. revoke or disable it in Studio;
3. issue a replacement with the smallest required scope;
4. update the server or provider configuration;
5. review request, audit, flow, and webhook history;
6. remove the leaked value from logs, repositories, and build artifacts;
7. document the incident and the new rotation owner.

## Common mistakes

- using a secret key from a browser because the first request is easier;
- sending a publishable key without policies and assuming it is private;
- using a development token against staging or production;
- sharing one secret across several unrelated integrations;
- putting a webhook secret in a request body for debugging;
- logging the `Authorization` header;
- forgetting that a realtime connection needs its own authenticated session and channel permission.

When a request fails, first identify which credential was used, which environment it targets, and whether the operation requires a user session. Then inspect the policy or integration configuration.
