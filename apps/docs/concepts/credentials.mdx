Two questions are answered separately on every request:

1. **Which project environment, with which privileges?** Answered by the **API key**.
2. **Which person?** Answered by the **user access token**, if any.

## API keys

| Role | Prefix | Where it lives | What policies see |
| --- | --- | --- | --- |
| **Publishable** | `pb_pk_…` | Browsers, mobile apps, anything public | `credential.role = "publishable"`, `is_service = false`: every policy applies |
| **Secret** | `pb_sk_…` | Servers, CI, scripts you control | `credential.role = "secret"`, `is_service = true`: **policies are bypassed** |

Send the key as the `apikey` header (or `x-api-key`). For browser navigations and WebSockets, which can't set headers, `?apikey=` works too; the gateway strips it before forwarding.

<Warning>
A secret key is equivalent to root access to that environment's data. Never ship it in a client, commit it or log it. If one leaks, [revoke it](/operate/api-keys) and create another.
</Warning>

### Scopes

A key can be limited to **scopes**. An empty list means "everything the role allows".

| Scope | Allows |
| --- | --- |
| `resource:read` | Resource `list` and `get` |
| `resource:write` | Resource `create`, `update`, `delete` |
| `routes:invoke` | Custom routes |
| `resource:*`, `*` | Families and everything |

A key without the needed scope gets `403 This API key lacks the 'resource:write' scope` before any policy runs. Policies can also check scopes: `{"scope": "reports:export"}` passes when the key carries it.

### Origins

For publishable keys, the gateway enforces the environment's allowed origins (`cors_origins` in environment settings), so a key copied into another website fails its CORS preflight. See [rate limits and CORS](/operate/rate-limits-and-cors).

## User access tokens

Issued by `POST /auth/v1/token`, sent as `Authorization: Bearer <token>`:

- short-lived (default **15 minutes**, `access_ttl`), refreshed with a rotating refresh token (default **30 days**, `refresh_ttl`);
- signed with a key derived for that project environment only;
- carry the user id, email, roles, permissions, active organization, session id and **AAL** (`aal1`, or `aal2` after MFA).

Every service validates them statelessly. What a policy sees:

```json
{
  "authenticated": true, "kind": "user", "user_id": "8", "email": "chioma@example.com",
  "roles": ["guardian"], "permissions": ["family.read"], "org": null,
  "aal": "aal1", "session_id": "5491…", "claims": { "...": "..." }
}
```

## Combinations

| `apikey` | `Authorization` | Who is calling | Typical use |
| --- | --- | --- | --- |
| publishable | none | Anonymous visitor | Public catalogue, sign-up, sign-in |
| publishable | user token | A signed-in person | Every app screen |
| secret | none | Your server, as the service | Admin jobs, imports, back-office |
| secret | user token | Your server acting *for* a user | Server-side rendering with the user's identity; policies still bypassed |

## Operators

People using Studio are **operators**: Akountz users of the reserved `_platform` project, signed in with a browser session (Secure cookie behind HTTPS). Operators reach services through Studio's bridge with service tokens and act with service rights. The first operator comes from `PAWABASE_ADMIN_EMAIL` / `PAWABASE_ADMIN_PASSWORD`.
