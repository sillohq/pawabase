When an application calls Pawabase, the request crosses a small number of product boundaries. Understanding them makes errors easier to diagnose and helps you decide which behavior belongs in a resource, route, flow, event, or job.

## The request path

```text
Application
   ↓
Environment gateway
   ↓
Authentication
   ↓
Route or resource operation
   ↓
Validation
   ↓
Policy
   ↓
Database or flow step
   ↓
Response
```

If the request creates or changes a resource, additional work may begin after the response:

```text
Saved change
   ↓
Event
   ├── flow or function
   ├── queue/job
   ├── outbound webhook
   └── realtime update
```

That downstream work is intentionally separate from the request that caused it. A slow email provider or warehouse webhook should not make a successful database write appear to fail.

## 1. The environment and key

Your application sends a request to one project environment and includes its public application key. The key identifies the environment and establishes which public application surface is being used.

Keep environment keys separate. A development key should never be embedded in a production build, and a secret key should never be sent to a browser or mobile application.

See [Credentials](/concepts/credentials) for key types and [Client errors](/clients/errors) for key failures.

## 2. Authentication

If the endpoint requires a user, the application includes the user's access token. Pawabase validates the session for the selected environment and makes the caller's identity available to the operation and its policy.

The important distinction is:

- no session may be valid for a public operation;
- a valid session identifies a caller;
- an expired or invalid session is an authentication failure.

Do not try to encode authorization decisions in the client. The backend must evaluate them for every request.

## 3. Routing and validation

Pawabase matches the request to either a generated resource operation or a custom route. It then validates the input against the fields or schema you configured in Studio.

Validation answers whether the request has the right shape:

- required values are present;
- values have the expected type;
- strings, numbers, patterns, and allowed values are within their limits;
- nested input matches the configured schema.

A validation failure happens before your business operation runs. Fix the request body or the Studio definition; do not use a policy to compensate for malformed input.

## 4. Policy evaluation

After the request has the right shape, Pawabase evaluates the operation's policy. The policy can use caller context, the record being read or changed, and—in operations that accept input—the submitted values.

For a list operation, a record-level policy may restrict the database query so the result and total reflect only rows the caller can see. For a single record, an inaccessible record may look like a not-found result to avoid revealing its existence.

See [Policies](/policies/overview) and [Policy context](/policies/context) for the values available to a policy.

## 5. The operation runs

For a resource operation, Pawabase reads or writes the record and returns the configured response shape. For a custom route, Pawabase starts the configured flow or supported function and returns its response.

At this point, the request should contain the smallest synchronous work needed to produce a reliable response. If the operation needs several external calls, long waits, or repeated attempts, hand that work to a flow, job, or event consumer.

## 6. What happens after a write

When resource events are enabled, a successful create, update, or delete can produce an event. Consumers may then:

- run a flow;
- invoke a function;
- enqueue work;
- send an outbound webhook;
- publish to realtime.

Consumers have their own logs and failure state. A downstream failure does not undo a database write automatically. If the business needs compensation, model that explicitly—for example, a refund flow, a retryable payment state, or an operator review.

## A worked example: order checkout

```text
POST /rest/v1/orders
   ↓
Environment key identifies the project/environment
   ↓
Customer access token identifies the shopper
   ↓
Order fields validate
   ↓
Checkout policy checks customer and account state
   ↓
Order is saved
   ↓
order.created is recorded
   ├── customer receives a realtime update
   ├── fulfillment flow is queued
   └── warehouse webhook is scheduled
```

If validation fails, no order exists. If the policy fails, the caller cannot create it. If the warehouse is unavailable after the order is saved, inspect the webhook delivery and retry or compensate without pretending the order never happened.

## Troubleshooting by boundary

| Symptom | Boundary to inspect |
| --- | --- |
| Key or environment error | Project reference, environment, and publishable key. |
| `401` | Access token, expiry, refresh behavior, and auth settings. |
| `403` | Operation policy, roles, organization, and record ownership. |
| Validation response | Resource fields, schema, and request body. |
| Route not found | Operation enabled state, route path, and environment. |
| Original request succeeds but follow-up work fails | Event history, flow run, queue/job, webhook delivery, or mail log. |
| Client misses a live change | Realtime authentication, channel rule, subscription, and connection state. |

Use [Observability](/operate/observability) to follow the request and its downstream work without relying on guesswork.
