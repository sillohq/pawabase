Pawabase presents one application-facing backend even though several platform capabilities work together behind it. Your application does not need to know which internal process handles a request. It connects to the environment gateway, and Pawabase routes the request to the configured data, auth, storage, realtime, or automation capability.

## The product-level architecture

```text
Web, mobile, or server application
                 │
                 ▼
        Environment gateway
        ┌────────┼────────┐
        ▼        ▼        ▼
      Auth     Data     Storage
        │        │        │
        └────┬───┴───┬────┘
             ▼       ▼
          Flows   Realtime
             │       │
       Events/jobs   Live clients
             │
       External systems
```

The gateway gives your application one stable origin. The environment then applies authentication, validation, policies, and configuration before the request reaches your data or workflow.

## The main boundaries

### Application boundary

Your application owns the user experience and client-side state. It should use a publishable key, user sessions, and the public application interfaces documented under [Clients](/clients/overview).

Never place a secret key, operator credential, or deployment secret in browser code or a mobile bundle.

### Environment boundary

Each project environment has its own data, users, keys, secrets, integrations, and runtime configuration. Development traffic cannot safely be assumed to behave like production traffic because the environments are isolated by design.

### Data boundary

Resources expose validated operations over application data. Policies protect those operations. Storage buckets protect files. Realtime channel rules protect live delivery.

These surfaces can share the same authentication context, but each surface still needs an explicit access decision.

### Automation boundary

Flows, events, queues, schedules, and webhooks handle work that should not be embedded in every client request. They make long-running or retryable behavior visible in Studio.

## Synchronous and asynchronous work

Use the request path for work that must be complete before the application can respond:

```text
Authenticate → validate → authorize → save → respond
```

Use asynchronous capabilities when work can continue after the response:

```text
Save → emit event → queue flow → call provider → retry or record failure
```

This separation protects response times and gives operators a place to inspect failures. It also means a successful write does not automatically mean every downstream consumer succeeded.

## Data and external systems

Pawabase can connect your application data to external services through HTTP steps, functions, inbound hooks, and outbound webhooks. Treat those services as unreliable dependencies:

- validate their response before changing durable state;
- use timeouts and retries where appropriate;
- make repeated delivery safe with idempotency;
- store enough status to explain a partial failure;
- keep credentials in environment secrets.

For webhook delivery, see [Outbound webhooks](/webhooks/outbound) and [Webhook signatures](/webhooks/signatures).

## Self-hosted deployments

When you self-host Pawabase, you operate the deployment infrastructure: the gateway, Studio, database connection, object storage, mail provider, cache, and workers. The customer-facing product model remains the same.

Before production, configure TLS, backups, secret handling, worker capacity, and monitoring. Start with [Self-hosting requirements](/self-hosting/requirements) and the [production checklist](/self-hosting/production-checklist).

## What this architecture means for design

When planning a feature, draw the path from the application to the final side effect:

```text
User action
  ↓
Public route or resource operation
  ↓
Authentication + policy
  ↓
Database change
  ↓
Event / flow / job
  ↓
External system or realtime client
```

For every arrow, decide what data is passed, who may cross the boundary, what failure looks like, and where the outcome is observed. That is the architecture you need to document and operate; the internal service topology is an implementation detail.
