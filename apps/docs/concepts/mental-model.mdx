Pawabase becomes easier to use when you separate five questions:

1. **What data does the product own?**
2. **Who can access it?**
3. **What should happen when something changes?**
4. **How does the application receive or initiate that behavior?**
5. **How will the team observe and operate it?**

Studio gives you a place to answer each question. An environment is the isolated backend where those choices run. This page walks through each question in depth, with the reasoning behind Pawabase's design and concrete business scenarios, before pointing you to the dedicated page for each capability.

<Callout>
Read this page once, fully, before your first real project. Almost every confusing moment in Pawabase — "why did my request return an empty list," "why didn't my webhook fire," "why does staging behave differently than production" — traces back to conflating two of these five questions. Keeping them separate in your head is the single highest-leverage thing you can do before you start building.
</Callout>

## Why separate these five questions at all

It would be possible to build a backend platform that just gives you a database and lets you write arbitrary server code for everything else. Many teams start there. The problem that shows up within a few months is that "arbitrary server code" has no shape: an authorization check ends up inline in a route handler, a retry loop ends up hand-rolled inside a request, and six months later nobody can answer "what happens when an order is created?" without reading every file in the codebase.

Pawabase's design bet is that most backend behavior decomposes into a small number of recurring shapes — store validated data, decide who may touch it, react to a change, deliver an update, do slow work later — and that naming those shapes explicitly (resource, policy, flow, event, realtime channel) makes a backend something a team can reason about without reading implementation code. The five questions above are exactly those shapes. When you're not sure where a piece of behavior belongs, ask which of the five questions it's actually answering; that usually tells you which Pawabase capability to reach for.

## Project and environment

A **project** is the product boundary. It groups the backend definition, credentials, and environments for one application or system. If you're building two genuinely separate products — a customer-facing marketplace and an unrelated internal admin tool for a different business unit — they belong in two projects, not two environments of one project, because environments assume a shared design that only differs in operational maturity, not a shared design that differs in actual purpose.

An **environment** is an isolated runtime of that project. Development, staging, and production can have the same design but different data, users, keys, secrets, integrations, and operational settings. Two environments of the same project should, most of the time, have the *same resources, the same policies, and the same flows* — what differs is the data inside them and the credentials that unlock them.

Use environments to protect production while you build. Promote definitions deliberately; do not treat a development environment as a mirror of production data — seeding development with real customer records, even for convenience, creates a second place that data can leak from and a second thing to keep compliant.

See [Projects and environments](/concepts/projects-and-environments) for promotion and environment-specific configuration in depth.

### A concrete scenario: subscription billing across environments

Imagine you're building a subscription product. In `development`, your billing provider is in test mode, so charges never touch a real card and webhooks come from the provider's test event stream. In `staging`, you use a separate test-mode provider account so a demo to a customer doesn't collide with your own development traffic. In `production`, real charges happen against real cards, and a failed webhook delivery is an incident, not a shrug. The **resource** (`subscriptions`), the **policy** (only the owning customer or a billing admin may view a subscription), and the **flow** (renew, retry a failed charge, downgrade after cancellation) are identical text in all three environments. Only the provider credentials, webhook destination URLs, and the data itself differ. That is exactly what environments are for.

## Data: resources are the application boundary

A **resource** represents a kind of application data such as `customers`, `orders`, or `messages`. In Studio you choose its fields, validation, relations, response shaping, and operations.

For each enabled operation, Pawabase can expose a public application API. The operation's policy decides whether a request may use it.

```text
Application request
       ↓
   Resource operation
       ↓
 validation + policy
       ↓
   stored record
```

Resources are a good fit for durable business data — the things your product needs to remember correctly, indefinitely, and query efficiently. They are not a substitute for every workflow: when a request needs branching, waiting, retries, external calls, or multiple writes, use a flow instead of trying to cram that logic into a resource's validation or response shaping.

### When a resource is the wrong tool

A few recurring situations where reaching for a resource operation directly will fight you:

- **Multi-record consistency.** Creating an order and decrementing inventory in the same operation is not "create one record" — it's a transaction spanning two resources, which belongs in a flow (using `db.transaction` or two coordinated `resource.*` blocks) or a custom route, not a single resource's create operation.
- **Conditional side effects.** "Create the order, and if the customer is new, also send a welcome email and create a loyalty account" is a sequence with a branch — a flow, triggered by the resource's create operation via a resource-change trigger, not logic bolted onto the resource itself.
- **External validation.** "Check that this promo code is still valid with our promotions provider before allowing the order" requires an HTTP call mid-request, which a resource's field validation cannot do; use a flow behind a custom route instead.
- **Derived or computed responses that vary by caller.** A resource's transformer can reshape a response, but if the shape genuinely depends on complex, caller-specific business logic beyond field selection, a flow-backed custom route gives you more room.

## Access: authentication and policies answer different questions

**Authentication** answers "who is calling?" A signed-in session can identify a user, their roles, and — where applicable — their organization context.

**Authorization** answers "may this caller perform this operation on this record?" Policies apply that context to resources, custom routes, storage, realtime channels, and other protected surfaces.

Keep the distinction visible while designing:

```text
No valid session         → authentication fails
Valid session, wrong row → policy fails
Valid session, allowed row → operation runs
```

Start with a narrow policy. Expand access deliberately for public catalog data, internal operations, or organization-wide records.

### Common access patterns, by business shape

| Product shape | Typical policy pattern |
| --- | --- |
| Personal data (a user's own notes, orders, or messages) | `owner` policy on the field that stores the creating user's id |
| Team or company workspace | Organization membership check combined with a role (`{"all": [{"role": "member"}, {"eq": ["$record.org_id", "$auth.org_id"]}]}`) |
| Public catalog (products, articles) | `public` for read operations, an admin role for write operations |
| Marketplace listing owned by a seller, visible to buyers | `owner` for write operations, `public` (or an authenticated-buyer policy) for read |
| Internal operational data (refunds, payouts) | `permission`-based policy naming a specific capability, not just a broad role |
| Data only your own backend should touch | `service` policy, or no public operation enabled at all |

Read [Authentication](/auth/overview) and [Policies](/policies/overview) together; neither is a complete security design by itself. A perfectly configured authentication flow with a `public` policy on sensitive data is not secure, and a tightly scoped policy behind broken authentication is equally not secure.

## Behavior: flows coordinate work

A **flow** is a configurable backend process. It starts from a trigger, reads input, executes steps, branches, and returns or records a result.

```text
Trigger → input → validate → read/write data → branch → side effect → result
```

Use flows for behavior that has more than one meaningful step:

- validate an order before creating it;
- send a welcome email after sign-up;
- retry an external request;
- wait for a scheduled time;
- create a record, emit an event, and notify another system.

The flow editor is where you configure this process. The [Flow overview](/flows/overview) explains the execution model before the block reference.

### A worked example: marketplace payout

A marketplace pays sellers weekly. The behavior:

```text
Schedule (weekly)
   ↓
List orders delivered since last payout, per seller
   ↓
For each seller
   ├── Calculate payout total (minus platform fee)
   ├── Call payment provider to transfer funds
   │      ├── success → create payout record, emit payout.completed
   │      └── failure → create payout record marked failed, emit payout.failed
   └── (loop continues to next seller)
   ↓
Done
```

This is unambiguously a flow: it has a schedule trigger, a loop over a list, a branch on an external call's outcome, and two different downstream events depending on which branch was taken. No single resource operation could express this, and hand-writing it as ad hoc server code would hide the branch and retry behavior from anyone who didn't read the code.

## Events, queues, and schedules

These features separate a change from the work it causes.

- An **event** describes something that happened, such as `order.created`.
- A **subscription** connects an event to a flow, function, webhook, or realtime destination.
- A **queue or job** moves work out of the request path so it can run asynchronously and be retried.
- A **schedule** starts work at a time or interval.

For example:

```text
Create order
   ↓
order.created event
   ├── realtime update for the customer
   ├── queued fulfillment flow
   └── outbound webhook for the warehouse
```

The original request can finish while the downstream work continues. That makes failure and retry behavior explicit instead of hiding it inside a long request.

### Why events, and not just calling the flow directly

You could, in principle, have the order-creation flow directly call the fulfillment flow, directly publish to realtime, and directly send the webhook, all inline. The reason Pawabase separates this into "emit an event, let subscriptions react" is that it decouples the number and identity of consumers from the thing producing the event. Six months after launch, when you add a loyalty-points flow that also needs to react to `order.created`, you add a new subscription — you do not go back and edit the order-creation flow to remember one more downstream call. The producer never needs to know who's listening.

### Choosing between a flow, a queue, and a schedule

- Use a **flow triggered directly** (HTTP or resource-change trigger) when the work must be visibly tied to one specific request and should mostly finish before you consider the operation "done," even if some of its own steps are async.
- Use an **event and subscription** when more than one independent piece of behavior should react to the same change, or when the producer shouldn't need to know its consumers.
- Use a **queue/job** (`queue.flow`, `queue.function`) when the work can tolerate a delay, needs its own retry policy independent of the request, or would otherwise make the request slow.
- Use a **schedule** when the work isn't triggered by any single event at all, but by the calendar — nightly reconciliation, weekly payouts, a reminder three days before a trial ends.

## Storage and realtime

**Storage** is for objects — images, documents, exports, and other files. A bucket defines what can be stored and who can read or write it. A file policy should usually be related to the record or organization that owns the file — a customer's uploaded receipt should be readable by that customer and relevant staff, not by every authenticated user.

**Realtime** is for delivering changes to connected applications. A channel is not automatically public: authentication and channel rules determine who may subscribe, publish, or receive presence and history.

Use the database as the durable source of truth. Use realtime to tell an application that something changed; the application can then update its view or fetch the authoritative record. Do not use a realtime message as the only record of a state change — if a client is disconnected when the message is published, it will never see it unless it separately reconciles with the database (or uses channel history, where retained).

### A concrete scenario: live order status for a delivery app

A customer places an order and watches its status update live: preparing, out for delivery, delivered. The resource (`orders`) is the source of truth. A resource-change trigger fires a flow whenever the order's status field changes; that flow publishes to a realtime channel scoped to that customer (`orders:customer:<id>`), whose channel rule only allows that customer's own session to subscribe. If the customer's app was closed when the status changed, it fetches the current `orders` record on reopen rather than relying on having received every intermediate realtime message — the realtime channel is a convenience notification, not the record of truth.

## Application integration

Your application normally uses:

- authentication endpoints or an SDK for sessions;
- resource APIs for data;
- flow or custom routes for business operations;
- storage APIs for files;
- realtime connections for live changes.

Studio configures these surfaces. It is not the application runtime and its management interface is not the public API for your users.

See [Client integration](/clients/overview) for application code and [REST conventions](/clients/rest-conventions) for the public request model.

## Operations: build for the day after launch

Production behavior includes invalid input, expired sessions, denied policies, duplicate events, failed external calls, timeouts, retries, and partial completion. Pawabase exposes operational views for requests, flow runs, jobs, events, webhooks, and mail so you can inspect what happened.

Design each important workflow with:

- an idempotency strategy for retries;
- explicit failure and timeout paths;
- an observable business state;
- a safe permission boundary;
- a way to replay or compensate when an external dependency fails.

### Why this matters more than it seems to at first

Everything up to this point in the mental model is about building the happy path. The uncomfortable truth about backend systems is that the happy path is rarely where a team spends its time in production — the payment provider times out, a webhook is delivered twice, a worker crashes mid-job, a customer's session expires exactly between two requests they expected to be atomic. A backend that has no visible state for "this is retrying" or "this failed and needs a human" forces an engineer to reconstruct what happened from database timestamps and guesswork at 2am. A backend where every job, flow run, and webhook delivery has a visible, inspectable outcome turns that same incident into a five-minute lookup.

This is also why Pawabase treats synchronous and asynchronous work so differently (see [Architecture](/concepts/architecture)): the request path is kept short and simple specifically so that everything genuinely uncertain — the stuff that fails, retries, and needs investigation — happens somewhere with its own observable lifecycle, rather than being buried inside a request that either fully succeeded or, from the caller's point of view, just vanished.

The [production operations](/operate/observability) and [jobs and failures](/operate/jobs-and-failures) guides show how to use those signals.

## A complete request, end to end

Consider a customer submitting an order:

```text
Application
   ↓ request with session
Gateway
   ↓ identify environment and authenticate
Resource or route
   ↓ validate input and evaluate policy
Database write
   ↓ emit order.created
Queue / flow
   ↓ charge, fulfill, or call a warehouse
Realtime + webhook
   ↓ update the application and notify the partner
Operations
   ↓ inspect failures, retries, and the final state
```

At each boundary, ask what data is available, who is allowed to continue, what happens if the next dependency fails, and where the result can be observed. If you can answer those four questions for every arrow in that diagram, you understand the feature well enough to build it in Pawabase; if you can't, that's usually a sign the feature needs one more resource field, one more policy clause, or one more flow branch before you start.

## A second worked example: customer onboarding with a trial

To see all five questions answered together, consider a SaaS product's signup flow:

1. **Data** — a `accounts` resource (organization-level: plan, trial end date) and a `memberships` resource (which users belong to which account, and with what role).
2. **Access** — a new user can create an `accounts` record and becomes its owner automatically (an owner field set server-side); only members of an account, checked via `memberships`, may read or modify it afterward.
3. **Behavior** — an `account.created` event triggers a flow that starts a 14-day trial (setting `trial_end`), sends a welcome email, and schedules a reminder three days before the trial ends.
4. **Application integration** — the signup form calls the public sign-up endpoint, then creates the `accounts` record using the new user's session; the dashboard reads `accounts` and `memberships` to show plan and trial status.
5. **Operations** — the scheduled reminder flow and the trial-expiry flow both have visible run history, so if a customer complains "I never got a trial reminder," support can check whether the flow ran and what it did, rather than guessing.

Every piece of that description maps directly onto a named Pawabase capability. That mapping — from a plain description of product behavior to resource/policy/flow/event/schedule — is the mental model this page is trying to build. Once it's automatic, most of the rest of Pawabase's documentation is filling in field-level detail on capabilities you already know how to choose between.
