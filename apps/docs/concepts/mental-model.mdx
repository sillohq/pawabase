Pawabase becomes easier to use when you separate five questions:

1. **What data does the product own?**
2. **Who can access it?**
3. **What should happen when something changes?**
4. **How does the application receive or initiate that behavior?**
5. **How will the team observe and operate it?**

Studio gives you a place to answer each question. An environment is the isolated backend where those choices run.

## Project and environment

A **project** is the product boundary. It groups the backend definition, credentials, and environments for one application or system.

An **environment** is an isolated runtime of that project. Development, staging, and production can have the same design but different data, users, keys, secrets, integrations, and operational settings.

Use environments to protect production while you build. Promote definitions deliberately; do not treat a development environment as a mirror of production data.

See [Projects and environments](/concepts/projects-and-environments) for promotion and environment-specific configuration.

## Data: resources are the application boundary

A **resource** represents a kind of application data such as `customers`, `orders`, or `messages`. In Studio you choose its fields, validation, relations, response shaping, and operations.

For each enabled operation, Pawabase can expose a public application API. The operation's policy decides whether a request may use it.

```text
Application request
       ↓
   Resource operation
       ↓
 validation + policy
       ↓
   stored record
```

Resources are a good fit for durable business data. They are not a substitute for every workflow: when a request needs branching, waiting, retries, external calls, or multiple writes, use a flow.

## Access: authentication and policies answer different questions

**Authentication** answers “who is calling?” A signed-in session can identify a user, their roles, and—where applicable—their organization context.

**Authorization** answers “may this caller perform this operation on this record?” Policies apply that context to resources, custom routes, storage, realtime channels, and other protected surfaces.

Keep the distinction visible while designing:

```text
No valid session         → authentication fails
Valid session, wrong row → policy fails
Valid session, allowed row → operation runs
```

Start with a narrow policy. Expand access deliberately for public catalog data, internal operations, or organization-wide records.

Read [Authentication](/auth/overview) and [Policies](/policies/overview) together; neither is a complete security design by itself.

## Behavior: flows coordinate work

A **flow** is a configurable backend process. It starts from a trigger, reads input, executes steps, branches, and returns or records a result.

```text
Trigger → input → validate → read/write data → branch → side effect → result
```

Use flows for behavior that has more than one meaningful step:

- validate an order before creating it;
- send a welcome email after sign-up;
- retry an external request;
- wait for a scheduled time;
- create a record, emit an event, and notify another system.

The flow editor is where you configure this process. The [Flow overview](/flows/overview) explains the execution model before the block reference.

## Events, queues, and schedules

These features separate a change from the work it causes.

- An **event** describes something that happened, such as `order.created`.
- A **subscription** connects an event to a flow, function, webhook, or realtime destination.
- A **queue or job** moves work out of the request path so it can run asynchronously and be retried.
- A **schedule** starts work at a time or interval.

For example:

```text
Create order
   ↓
order.created event
   ├── realtime update for the customer
   ├── queued fulfillment flow
   └── outbound webhook for the warehouse
```

The original request can finish while the downstream work continues. That makes failure and retry behavior explicit instead of hiding it inside a long request.

## Storage and realtime

**Storage** is for objects—images, documents, exports, and other files. A bucket defines what can be stored and who can read or write it. A file policy should usually be related to the record or organization that owns the file.

**Realtime** is for delivering changes to connected applications. A channel is not automatically public: authentication and channel rules determine who may subscribe, publish, or receive presence and history.

Use the database as the durable source of truth. Use realtime to tell an application that something changed; the application can then update its view or fetch the authoritative record.

## Application integration

Your application normally uses:

- authentication endpoints or an SDK for sessions;
- resource APIs for data;
- flow or custom routes for business operations;
- storage APIs for files;
- realtime connections for live changes.

Studio configures these surfaces. It is not the application runtime and its management interface is not the public API for your users.

See [Client integration](/clients/overview) for application code and [REST conventions](/clients/rest-conventions) for the public request model.

## Operations: build for the day after launch

Production behavior includes invalid input, expired sessions, denied policies, duplicate events, failed external calls, timeouts, retries, and partial completion. Pawabase exposes operational views for requests, flow runs, jobs, events, webhooks, and mail so you can inspect what happened.

Design each important workflow with:

- an idempotency strategy for retries;
- explicit failure and timeout paths;
- an observable business state;
- a safe permission boundary;
- a way to replay or compensate when an external dependency fails.

The [production operations](/operate/observability) and [jobs and failures](/operate/jobs-and-failures) guides show how to use those signals.

## A complete request, end to end

Consider a customer submitting an order:

```text
Application
   ↓ request with session
Gateway
   ↓ identify environment and authenticate
Resource or route
   ↓ validate input and evaluate policy
Database write
   ↓ emit order.created
Queue / flow
   ↓ charge, fulfill, or call a warehouse
Realtime + webhook
   ↓ update the application and notify the partner
Operations
   ↓ inspect failures, retries, and the final state
```

At each boundary, ask what data is available, who is allowed to continue, what happens if the next dependency fails, and where the result can be observed.
