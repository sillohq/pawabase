icon: "code"
---

Nearly every block configuration value in Pawabase can contain a **template** — a `{{ }}` expression that gets resolved against the run's current state before the block executes. This is how flows read data from earlier steps, reference the caller's identity, and build dynamic values without any code.

```json
{
  "id": "reply",
  "data": {
    "block": "response.return",
    "config": {
      "status": 200,
      "body": {
        "order": "{{ steps.load.output }}",
        "requested_by": "{{ auth.user_id }}",
        "total": "{{ steps.calculate.output }}"
      }
    }
  }
}
```

The engine renders every template in a block's `config` before calling `block.run()`, so the block receives plain values — no template strings left to evaluate.

<Note>
Templates are resolved **depth-first**: the engine recursively walks the config object and renders every string value that contains `{{ }}`. An object like `{"name": "{{ steps.user.output.name }}"}` has its `name` field rendered to the actual value. A string that doesn't contain `{{ }}` is passed through unchanged.
</Note>

## What templates can reference

Templates resolve against the run's `state` dictionary, which is built fresh for every execution:

```python
self.state: dict[str, Any] = {
    "input": input,          # the trigger payload
    "auth": dict(auth or {}), # the caller's policy context
    "project": project,
    "env": env,
    "vars": {},              # set with control.set
    "steps": {},             # each finished block's output
    "run": {"id": self.id, "flow": name},
}
```

The following variables are always available inside `{{ }}`:

| Variable | Source | Example |
| --- | --- | --- |
| `input` | The trigger payload | `{{ input.params.id }}` |
| `auth` | The caller's policy context | `{{ auth.user_id }}`, `{{ auth.authenticated }}` |
| `vars` | Values set with `control.set` | `{{ vars.greeting }}` |
| `steps.<node_id>.output` | A previous block's output | `{{ steps.load.output.id }}` |
| `item` and `index` | Inside a `control.foreach` body | `{{ item.name }}`, `{{ index }}` |
| `error` | Inside an error branch | `{{ error.message }}` |

<Warning>
Missing paths resolve to `None`. If a template references `{{ steps.missing.output.field }}` and `steps.missing` doesn't exist in state, or `steps.missing.output` doesn't have a `field`, the template resolves to `None` rather than raising an error. This silent behavior is a common source of bugs — always verify that earlier steps actually ran and produced the shape you expect before referencing their output.
</Warning>

## Syntax

Templates use double curly braces. Inside them you write a Python-style expression against the run state:

```
{{ input.params.id }}
{{ steps.load.output.total }}
{{ vars.greeting }}
{{ auth.user_id }}
{{ item.name }}
{{ steps.result.output | int }}
{{ steps.result.output | round(2) }}
```

The expression after `{{` and before `}}` is evaluated with the run state as context. Most expressions are simple attribute/index access chains. Filters (described below) can be applied with a pipe `|`.

## Filters

Filters transform a value in the template output without needing a separate block step:

| Filter | Effect | Example |
| --- | --- | --- |
| `\| int` | Convert to integer | `{{ steps.avg.output \| int }}` |
| `\| float` | Convert to float | `{{ steps.count.output \| float }}` |
| `\| round(n)` | Round to n decimal places | `{{ steps.price.output \| round(2) }}` |
| `\| json` | Serialize as JSON string | `{{ steps.data.output \| json }}` |
| `\| default("x")` | Fallback if value is None | `{{ steps.user.output.name \| default("Anonymous") }}` |

### `default` filter

```json
{
  "id": "greeting",
  "data": {
    "block": "control.set",
    "config": {
      "values": {
        "name": "{{ input.body.name | default('Valued Customer') }}"
      }
    }
  }
}
```

When `input.body.name` is missing or `None`, the filter substitutes `"Valued Customer"` instead — useful for fallback display text in mail templates and response bodies.

### `json` filter

```json
{
  "id": "encode",
  "data": {
    "block": "json.stringify",
    "config": { "value": "{{ steps.payload.output | json }}" }
  }
}
```

The `json` filter serializes any value to a JSON string, equivalent to calling `json.dumps()` — useful when a block expects a string but you need to pass an object.

## Template examples in practice

### Building a response from multiple steps

```json
{
  "id": "reply",
  "data": {
    "block": "response.return",
    "config": {
      "status": 200,
      "body": {
        "order_id": "{{ steps.load.output.id }}",
        "customer": "{{ steps.load.output.customer_name }}",
        "total": "{{ steps.calculate.output }}",
        "currency": "{{ steps.load.output.currency }}",
        "paid_at": "{{ time.now.output }}"
      }
    }
  }
}
```

### Nested objects and arrays

Templates can build nested structures inline:

```json
{
  "id": "envelope",
  "data": {
    "block": "transform.template",
    "config": {
      "template": {
        "order_id": "{{ steps.order.output.id }}",
        "customer": {
          "email": "{{ steps.order.output.email }}",
          "name": "{{ steps.customer.output.name }}"
        },
        "lines": "{{ steps.items.output }}",
        "placed_at": "{{ steps.now.output }}"
      }
    }
  }
}
```

### Inside mail templates

Mail templates receive `data` values that are themselves templates resolved at render time:

```json
{
  "id": "send",
  "data": {
    "block": "mail.send",
    "config": {
      "to": "{{ input.event.payload.email }}",
      "template": "welcome",
      "data": {
        "greeting": "{{ vars.greeting }}",
        "name": "{{ input.event.payload.name | default('there') }}",
        "order_total": "{{ steps.order.output.total | int }}"
      }
    }
  }
}
```

## raw_config: blocks that skip pre-rendering

Most blocks have `raw_config = False`, meaning the engine renders all templates in their `config` before `run()` is called. Some blocks set `raw_config = True` to receive the **unrendered** config, because they need to decide *what* to render and when.

**Blocks with `raw_config = True`:**
- `control.if` — needs the raw condition object to evaluate it
- `control.foreach` — needs to see the iterable expression before rendering
- `control.switch` — needs to inspect the condition structure
- `transform.template` — renders its own templates internally

This matters because without `raw_config`, a `control.if` would have its condition object rendered into strings before the block could read it — losing the structure needed to evaluate a condition.

```python
class If(Block):
    raw_config = True  # the engine does NOT pre-render our config

    async def run(self, config, run):
        condition = config["condition"]  # still a dict like {"truthy": "$input.event.payload.name"}
        ...
```

## Common mistakes

<AccordionGroup>
  <Accordion title="Referencing a step that hasn't run yet">
    If a flow has a branch where some paths skip a step, `{{ steps.missing.output }}` resolves to `None` rather than raising an error. Use `control.if` with `{{ steps.node.output is not None }}` to guard references, or ensure every path through the flow reaches the step you're referencing.
  </Accordion>
  <Accordion title="Forgetting that math.calculate returns floats">
    `{{ steps.divide.output }}` on `divide([10, 3])` renders as `3.3333333333333335`. Use `{{ steps.divide.output | round(2) }}` or `{{ steps.divide.output | int }}` to control precision.
  </Accordion>
  <Accordion title="Using templates in db.query sql instead of params">
    `"sql": "SELECT * FROM orders WHERE id = {{ input.params.id }}"` reopens SQL injection — templates render before the block runs, so that's string concatenation. Keep the placeholder in `sql` and pass values through `params`.
  </Accordion>
  <Accordion title="Assuming templates can reference future steps">
    Templates resolve against `state`, which only contains steps that have already executed. A step cannot read the output of a step that comes later in the graph. If you need data from two places, structure the flow so the shared data comes from a single earlier step.
  </Accordion>
  <Accordion title="Putting a secret's literal value in a template">
    Anything in a `config` value is stored as part of the flow definition. If a template resolves to a secret value (e.g. `{{ vars.api_key }}` where `api_key` came from `secret.get`), that value *is* visible in the trace. `secret.get` only protects the secret from appearing in its own trace entry — it doesn't stop you from leaking it two nodes later.
  </Accordion>
</AccordionGroup>
