The platform ships with a rich set of built-in blocks, but any developer on a team can write their own. A custom block is a Python class that implements the `Block` protocol — a `run(config, run)` method that returns a `BlockResult`. Once registered in the `Registry`, it becomes available in every flow's JSON definition just like the built-ins.

## The Block protocol

Every block implements these two methods:

```python
class Block:
    async def run(self, config: Mapping[str, Any], run: FlowRun) -> BlockResult:
        """Execute the block. Return a BlockResult."""
        raise NotImplementedError

    def validate(self, config: Mapping[str, Any]) -> list[str]:
        """Return a list of problem strings. Empty means valid."""
        return []
```

| Attribute / Method | Description |
| --- | --- |
| `key` | The block's identifier string (e.g., `"my_custom_block"`) |
| `trigger` | `True` if this block can serve as a flow entry point |
| `handles` | The output handles the block declares (`["next"]`, `["next", "error", "missing"]`, or `["*"]`) |
| `raw_config` | `True` if the block needs the unrendered config (control blocks need this for conditions) |
| `run(config, run)` | Execute the block, return `BlockResult` |
| `validate(config)` | Validate the config before saving |

## BlockResult

Every `run()` returns a `BlockResult`:

```python
@dataclass
class BlockResult:
    output: Any = None      # The result — available as {{ steps.<node>.output }}
    handle: str = "next"    # Which edge to follow ("next", "error", "missing", etc.)
    stop: bool = False      # If True, the walk stops immediately
```

```python
# A block that always follows "next" and returns a value
return BlockResult(output={"status": "ok"}, handle="next")

# A block that stops the walk (like response.return)
return BlockResult(output={"status": 200}, handle="next", stop=True)

# A block that signals an error (like error.raise)
return BlockResult(output=None, handle="error")
```

## Minimal custom block example

Here's a complete custom block that computes a greeting and returns it:

```python
from pawabase_kit.flows.blocks import Block, BlockResult
from typing import Any, Mapping

class Greet(Block):
    key = "my.greet"
    handles = ["next"]
    trigger = False
    raw_config = False

    async def run(self, config: Mapping[str, Any], run: FlowRun) -> BlockResult:
        name = config.get("name", "world")
        rendered_name = run.render(name) if isinstance(name, str) and "{{" in name else name
        return BlockResult(output=f"Hello, {rendered_name}!")

    def validate(self, config: Mapping[str, Any]) -> list[str]:
        problems = []
        if "name" not in config:
            problems.append("name is required")
        return problems
```

Register it:

```python
from pawabase_kit.flows.registry import Registry

registry = Registry()
registry.register(Greet)
```

The block is now available in any flow's JSON definition:

```json
{ "id": "greet", "data": { "block": "my.greet", "config": { "name": "{{ input.event.payload.name }}" } } }
```

## The `run` method in detail

The `run` method receives two arguments:

1. **`config`** — the node's `data.config` dictionary, with all templates already rendered into their final values (unless the block opts into `raw_config`). You can call `config.get("field")` to access any config key.
2. **`run`** — the `FlowRun` instance, which gives you access to:
   - `run.state` — the full run state dictionary
   - `run.render(value)` — render templates in a value against the current state
   - `run.targets(node_id, handle)` — resolve edges from a node
   - `run.run_branch(node_id, handle, extra)` — walk a sub-graph
   - `run.entry_node()` — the trigger node id
   - `run.current_node` — the node currently being executed

```python
async def run(self, config: Mapping[str, Any], run: FlowRun) -> BlockResult:
    # Read a config value
    resource_name = config["resource"]
    record_id = config["id"]

    # Read from state directly
    store = run.state["auth"]["org"]

    # Render a template expression
    rendered = run.render(config["query"])

    # Call another block's method through the runtime
    result = await run.resource_list(resource_name, filters={"store_id": store})

    return BlockResult(output=result)
```

## The `validate` method

`validate` is called before the flow is saved. It returns a list of problem strings — empty when the config is valid. This catches errors at save time rather than at runtime.

```python
def validate(self, config: Mapping[str, Any]) -> list[str]:
    problems = []
    if "api_key" not in config:
        problems.append("api_key is required")
    if config.get("timeout") and not isinstance(config["timeout"], int):
        problems.append("timeout must be an integer")
    return problems
```

## Registry — registering blocks

The `Registry` is the central catalog of all blocks. It maps block keys to block classes and provides lookup by key:

```python
class Registry:
    def __init__(self):
        self._blocks: dict[str, type] = {}

    def register(self, block_class: type) -> None:
        """Register a block class by its `key` attribute."""
        self._blocks[block_class.key] = block_class

    def get(self, key: str) -> type | None:
        """Return the block class for a key, or None."""
        return self._blocks.get(key)

    def __contains__(self, key: str) -> bool:
        return key in self._blocks
```

The platform initializes the registry with all built-in blocks at startup. To add custom blocks, call `registry.register(MyBlock)` after the registry is created — either in a plugin, an import hook, or at the environment's bootstrap configuration.

<Tip>
Custom blocks are **per-environment**. Register a block in one environment and it's only available in that environment's flows. This lets you experiment with custom blocks without affecting production.
</Tip>

## Writing a block that handles errors

Some blocks need to signal failure so the flow can take an `error` edge:

```python
class Fail(Block):
    key = "my.fail"
    handles = ["next", "error"]
    trigger = False

    async def run(self, config: Mapping[str, Any], run: FlowRun) -> BlockResult:
        should_fail = config.get("should_fail", False)
        if should_fail:
            return BlockResult(output=None, handle="error")
        return BlockResult(output={"ok": True})
```

Inside the error branch, blocks can read `{{ error.message }}`, `{{ error.type }}`, and `{{ error.node }}`.

## Writing a block that stops the walk

`response.return` stops the walk because it sets `stop=True` on its `BlockResult`. Any block can do this:

```python
class Return(Block):
    key = "my.return"
    handles = ["next"]
    trigger = True

    async def run(self, config: Mapping[str, Any], run: FlowRun) -> BlockResult:
        body = config.get("body")
        return BlockResult(output=body, handle="next", stop=True)
```

When `stop=True`, the engine halts immediately — even if there are more reachable nodes. This is how `response.return` and `control.stop` work.

## Writing a block with custom handles

Most blocks declare `["next"]`. Some declare multiple handles:

```python
class ResourceGet(Block):
    key = "my.resource.get"
    handles = ["next", "missing"]  # "next" on success, "missing" if not found
```

Inside the flow definition, edges specify which handle they follow:

```json
{ "id": "load", "data": { "block": "my.resource.get", "config": { "id": "{{ input.params.id }}" } } },
{ "id": "not_found", "data": { "block": "error.raise", "config": { "status": 404 } } }
```

```json
{ "edges": [
  { "source": "load", "target": "not_found", "sourceHandle": "missing" },
  { "source": "load", "target": "process" }
]}
```

A block with `handles = ["*"]` declares that it accepts any handle — used by control blocks that can follow any edge.

## Writing a trigger block

A trigger block is a block with `trigger = True`. It must have `handles = ["next"]` (only one outgoing edge — the flow walks from there):

```python
class MyTrigger(Block):
    key = "my.trigger"
    handles = ["next"]
    trigger = True
    raw_config = True  # conditions need the unrendered config

    async def run(self, config: Mapping[str, Any], run: FlowRun) -> BlockResult:
        # Trigger blocks don't return a value to steps — they start the walk
        return BlockResult(output=None, handle="next")
```

A flow must have at least one trigger block. If a flow's nodes contain no block with `trigger = True`, validation fails with `"a flow needs a trigger block"`.

## The `raw_config` flag

Control blocks (`control.if`, `control.switch`, `control.foreach`) set `raw_config = True` because their condition objects contain template-like expressions that need to be evaluated as conditions, not rendered as strings. When `raw_config` is `True`, the engine passes the raw config dictionary to `block.run()` without rendering templates inside it.

```python
class ControlIf(Block):
    key = "control.if"
    handles = ["*"]
    trigger = False
    raw_config = True

    async def run(self, config: Mapping[str, Any], run: FlowRun) -> BlockResult:
        condition = config["condition"]  # raw condition object, not rendered
        # evaluate the condition against run.state
        result = run.eval_condition(condition)
        return BlockResult(output=result, handle="true" if result else "false")
```

## Writing a block that reads resources

The simplest way to interact with resources from a custom block is through the `FlowRun`'s runtime methods:

```python
class MyResourceGet(Block):
    key = "my.resource.get"
    handles = ["next", "missing"]

    async def run(self, config: Mapping[str, Any], run: FlowRun) -> BlockResult:
        resource = config["resource"]
        record_id = config["id"]
        try:
            result = await run.resource_get(resource, record_id)
            return BlockResult(output=result, handle="next")
        except NotFoundError:
            return BlockResult(output=None, handle="missing")
```

For writes, use `run.resource_create`, `run.resource_update`, and `run.resource_delete`. For queries, use `run.db_query`. For events, use `run.event_emit`. The runtime exposes every platform block's operation as an async method on `FlowRun`.

## Complete example: custom block package

A typical custom block lives in a Python module, is registered at startup, and is used in flow definitions:

```python
# myapp/flows/blocks.py
from pawabase_kit.flows.blocks import Block, BlockResult
from typing import Any, Mapping

class Greet(Block):
    key = "my.greet"
    handles = ["next"]

    async def run(self, config: Mapping[str, Any], run: FlowRun) -> BlockResult:
        name = config.get("name", "world")
        return BlockResult(output=f"Hello, {name}!")

    def validate(self, config: Mapping[str, Any]) -> list[str]:
        return [] if "name" in config else ["name is required"]
```

```python
# myapp/bootstrap.py
from pawabase_kit.flows.registry import registry
from myapp.flows.blocks import Greet

registry.register(Greet)
```

```json
{
  "name": "greet_flow",
  "definition": {
    "nodes": [
      { "id": "start", "data": { "block": "trigger.manual", "config": {} } },
      { "id": "greet", "data": { "block": "my.greet", "config": { "name": "{{ input.name }}" } } }
    ],
    "edges": [
      { "source": "start", "target": "greet" }
    ]
  }
}
```

## Debugging custom blocks

<AccordionGroup>
  <Accordion title="Block not found in the registry">
    Check that `registry.register(MyBlock)` ran before the flow saved. Custom blocks are registered per-environment — verify the registration runs in the correct environment's bootstrap.
  </Accordion>
  <Accordion title="validate returns errors but the flow still runs">
    Validation errors prevent saving, not running. If you're running a flow programmatically without going through the validate path, errors in `validate` won't catch anything. Add runtime checks in `run` instead.
  </Accordion>
  <Accordion title="BlockResult.handle doesn't match any edge">
    The walk will raise — an edge pointing at a missing handle fails validation. Ensure every declared handle has a corresponding edge in the flow definition.
  </Accordion>
  <Accordion title="run.render raises unexpectedly">
    `run.render` renders templates against the current state. If a template references `{{ steps.<id>.output }}` for a node that hasn't run yet, it resolves as `undefined`. Use `run.eval_condition` for condition objects that need more control.
  </Accordion>
</AccordionGroup>
