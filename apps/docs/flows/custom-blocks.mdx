Pawabase ships roughly fifty built-in blocks covering triggers, control, data, resources, and platform capabilities. For the logic that falls outside that vocabulary — a custom payment integration, a proprietary data transformation, a third-party SDK wrapper — you can define your own blocks. Custom blocks appear in Studio's palette alongside built-in blocks and run with the same `Runtime` protocol.

## How blocks work

Every block is a class extending `Block` from `pawabase_kit.flows.registry`:

```python
class Block:
    key: ClassVar[str] = ""        # Unique identifier, e.g. "stripe.charge"
    title: ClassVar[str] = ""      # Display name
    category: ClassVar[str] = "general"  # Palette tab
    description: ClassVar[str] = ""      # Short description
    config: ClassVar[list[dict]] = []    # Config fields for Studio's form
    handles: ClassVar[list[str]] = ["next"]  # Output handles
    raw_config: ClassVar[bool] = False     # Don't pre-render templates
    trigger: ClassVar[bool] = False        # Starts a run

    async def run(self, config, run) -> BlockResult: ...
```

The `config` list declares the block's configuration fields in the schema format used by `pawabase_kit.schemas`. Each field spec has a `name`, `type`, whether it's `required`, and optionally a `widget` hint for Studio. Studio reads `config` to render a form — no block-specific frontend code needed.

`BlockResult` is what `run()` returns:

```python
@dataclass
class BlockResult:
    output: Any = None    # Stored as steps.<node id>.output
    handle: str = "next"  # Which outgoing edges to follow
    stop: bool = False    # End the run after this block
```

## Creating a custom block

Here's a complete custom block that calls the Stripe API to create a charge:

```python
# my_package/blocks.py
from __future__ import annotations
import os
import httpx
from pawabase_kit.flows.registry import Block, BlockResult

class CreateCharge(Block):
    key = "stripe.charge"
    title = "Create charge"
    category = "integrations"
    description = "Charge a card through Stripe"

    config = [
        {"name": "amount", "type": "integer", "required": True, "minimum": 50},
        {"name": "currency", "type": "string", "default": "usd"},
        {"name": "token", "type": "string", "required": True},
    ]

    async def run(self, config, run):
        amount = int(config["amount"])
        currency = config["currency"]
        token = config["token"]
        api_key = await run.runtime.secret("STRIPE_SECRET_KEY")

        async with httpx.AsyncClient() as client:
            response = await client.post(
                "https://api.stripe.com/v1/charges",
                auth=(api_key, ""),
                json={"amount": amount, "currency": currency, "source": token},
            )
            data = response.json()

        if response.status_code >= 400:
            return BlockResult(
                output=None, handle="failed",
            )

        return BlockResult(
            output={"charge_id": data["id"], "amount": amount},
            handle="next",
        )
```

Notice a few things:
- The block uses `run.runtime.secret()` to load the Stripe secret key — it never imports or accesses the secret directly
- It returns `BlockResult(handle="failed")` when the API returns an error — this means an `error` edge drawn from the block in Studio will follow `failed`
- The block calls the external API directly through `httpx` because the `Runtime` protocol doesn't have a Stripe-specific method — for integrations not covered by built-in blocks, this is the pattern

## Registering custom blocks

Blocks are discovered through the `pawabase.blocks` entry point group. In your package's `pyproject.toml`:

```toml
[project.entry-points."pawabase.blocks"]
stripe = "my_package.blocks:register"
```

The `register` function adds your blocks to the `BlockRegistry`:

```python
# my_package/blocks.py
from pawabase_kit.flows.registry import BlockRegistry

def register(registry: BlockRegistry) -> None:
    registry.add(CreateCharge)
    registry.add(RefundCharge)
    registry.add(ConnectAccount)
```

`default_registry()` in `pawabase_kit.flows.registry` loads built-in blocks plus all `pawabase.blocks` entry points on first use. Entry points whose value starts with `pawabase_kit.flows.blocks` are skipped (built-ins are registered separately).

## Block categories and Studio

The `category` class attribute determines which tab in Studio's visual editor palette the block appears in. Built-in categories include `triggers`, `control`, `data`, `resources`, `auth`, `cache`, `events`, `jobs`, `realtime`, `storage`, `mail`, `integrations`, `code`, `observability`, and `responses`. When you add a custom block, pick a category that makes sense — new categories are fine too, and they'll appear as new tabs in Studio.

Studio reads each block's `config` list to render a form. Each field spec supports these properties:

| Property | Type | Description |
| --- | --- | --- |
| `name` | `string` | The config key |
| `type` | `string` | `string`, `integer`, `number`, `boolean`, `json`, `url`, `text`, `code` |
| `required` | `boolean` | Whether the field is required |
| `default` | any | Default value |
| `minimum` / `maximum` | `number` | For `integer`/`number` types |
| `enum` | `array` | Allowed values |
| `widget` | `string` | Hint for Studio's form renderer |
| `description` | `string` | Help text shown in the form |

## The Runtime protocol and custom blocks

Custom blocks have the same access to `run.runtime` as built-in blocks. The `Runtime` protocol defines every platform capability:

```python
class Runtime(Protocol):
    # data
    async def resource_list(self, resource, *, filters=None, sort=None, limit=50, offset=0) -> dict: ...
    async def resource_get(self, resource, record_id) -> dict | None: ...
    async def resource_create(self, resource, data) -> dict: ...
    # cache
    async def cache_get(self, key) -> Any: ...
    async def cache_set(self, key, value, ttl=None, tags=None) -> None: ...
    # events, queues, realtime
    async def emit(self, name, payload) -> str: ...
    async def dispatch_flow(self, flow, input, *, delay=0, queue=None) -> str: ...
    async def publish(self, channel, event, payload) -> dict: ...
    # storage, mail, outbound
    async def storage_put(self, bucket, key, content, content_type="") -> dict: ...
    async def send_mail(self, to, subject, *, text=None, html=None, template=None, data=None) -> dict: ...
    async def http_request(self, method, url, *, headers=None, json=None, params=None, timeout=30, retries=0) -> dict: ...
    # platform
    async def secret(self, name) -> str | None: ...
    async def call_function(self, name, input) -> Any: ...
    async def identity_user(self, user_id) -> dict | None: ...
    async def check_policy(self, ref, context) -> bool: ...
    async def log(self, level, message, data=None) -> None: ...
    async def metric(self, name, value=1.0, tags=None) -> None: ...
```

A runtime that doesn't provide some capability fails gracefully — `BaseRuntime.__getattr__` returns an async function that raises `NotAvailable(f"{name} is not available in this runtime")`. Your custom block should handle this or assume the host provides the capabilities it needs.

## Testing custom blocks

Because blocks use `Runtime` rather than importing services directly, you can test them with a fake runtime:

```python
from unittest.mock import AsyncMock
from pawabase_kit.flows.runtime import BaseRuntime
from my_package.blocks import CreateCharge

class FakeRuntime(BaseRuntime):
    async def secret(self, name):
        return "sk_test_fake"

block = CreateCharge()
result = await block.run(
    {"amount": 1000, "currency": "usd", "token": "tok_test_123"},
    run=FakeRuntime()  # or a minimal mock
)
assert result.handle == "next"
```

In the platform's own test suite, the real `ApiRuntime` is used for integration tests, and a fake `Runtime` for unit tests — the same pattern applies to your custom blocks.

## Limitations

Custom blocks are subject to the same constraints as built-in blocks:

- **Timeout**: The flow's `timeout` applies to all blocks, including custom ones
- **Steps**: The 10,000 step limit applies
- **`db.query` is read-only**: Custom blocks cannot bypass `is_read_only` enforcement — that's enforced in `ApiRuntime.db_query`, not in the block itself
- **`raw_config`**: If your block needs to see unrendered templates (like `control.if` and `control.foreach`), set `raw_config = True`
- **Entry point loading**: Custom blocks are loaded at registry initialization. Errors during entry point loading are logged but don't crash the process — `default_registry()` catches exceptions from each entry point individually

<Note>
Custom blocks can be added to the `pawabase.blocks` entry point group from any installed package. The `pawabase_kit.flows.registry.default_registry()` function loads them on first access. If you're building a package that adds blocks, test that `default_registry()` can load them cleanly.
</Note>

## Common mistakes

<AccordionGroup>
  <Accordion title="Hardcoding secrets in the block's config">
    Anything typed directly into `config` is stored as part of the flow definition. Load secrets via `run.runtime.secret()` and reference them at runtime.
  </Accordion>
  <Accordion title="Forgetting that the block must have a unique key">
    `registry.add()` raises `ValueError` if a block with the same `key` already exists. Ensure your block's `key` is unique — prefix it with your package name like `mypackage.action_name`.
  </Accordion>
  <Accordion title="Not handling errors in run()">
    If `run()` raises an exception and there's no `error` edge drawn from the block, the run fails. Return `BlockResult(handle="error")` for expected failures, or let exceptions propagate for unexpected ones.
  </Accordion>
  <Accordion title="Using run.state directly instead of templates">
    Blocks should receive their configuration as rendered values (templates already resolved). Access `run.state` only when you need to read state that wasn't part of the config — rare, but sometimes necessary for cross-run lookups.
  </Accordion>
</AccordionGroup>
