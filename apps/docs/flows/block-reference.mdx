This page is the index. It lists **every block** Pawabase registers — all 64 of them — with a correct, complete summary table per category: the config fields a Studio user fills in, the branches a block can take, and a one-line description.

For triggers and control blocks, and for the five resource blocks and the thirty-two platform blocks, the deep explanation — worked examples, gotchas, common mistakes — lives on a dedicated page, linked from each section below. This page does not repeat that depth; it exists so you can find the right block and its exact field names without leaving the page, and then click through when you need the full story.

<Note>
Four data blocks — `transform.filter`, `transform.sort`, `transform.group`, `transform.batch` — aren't yet covered on [Data blocks](/flows/data-blocks), so this page documents them in full below rather than only summarizing them.
</Note>

## How to read the tables

Every block has:

- **Key** — what you select in Studio's block picker, and what appears in a flow's stored definition (`resource.get`, `control.if`, and so on).
- **Config** — the fields Studio renders a form for. Any field can hold a literal value or a `{{ }}` expression (see [Templates](/flows/templates)); a few blocks (marked below) leave their config unrendered and evaluate it themselves as a condition.
- **Branches** — the named outcomes a block can produce. Most blocks have a single `next` branch, meaning there's exactly one way forward. A block with more than one branch (`true`/`false`, `next`/`missing`, `hit`/`miss`, …) lets you wire different Steps to different outcomes. Any block, regardless of its declared branches, can also have an `error` branch wired to it — see [Errors and retries](/flows/errors-and-retries).

## Triggers — how a Flow starts

Every Trigger hands the payload that started the run straight through as its output — none of them transform data, they only declare *when* a run begins. What the host puts into that payload (`input`) is documented per-trigger on [Triggers](/flows/triggers).

| Key | Title | Branches | Config | Starts on |
| --- | --- | --- | --- | --- |
| `trigger.http` | HTTP request | `next` | `method`, `path`, `policy` | An inbound request to a route this Flow is bound to |
| `trigger.event` | Event | `next` | `event` | A matching platform event being published |
| `trigger.schedule` | Schedule | `next` | `cron`, `every` | A cron expression or a fixed interval |
| `trigger.resource` | Resource change | `next` | `resource`, `operations` | A create/update/delete on a resource |
| `trigger.webhook` | Inbound webhook | `next` | `hook` | A verified inbound webhook delivery |
| `trigger.realtime` | Realtime message | `next` | `channel` | A client publishing to a realtime channel |
| `trigger.job` | Background job | `next` | `queue` | This Flow being dispatched as a job (by `queue.flow`) |
| `trigger.manual` | Manual run | `next` | — | A run started from Studio or the platform API |

Every Flow needs at least one Trigger; a Flow with none fails validation. Full field descriptions, the exact shape of `input` for each Trigger, and how to choose between them: [Triggers](/flows/triggers).

## Control blocks — branching, looping, timing

Eleven blocks, all under the `control` category. They never touch your database or call an outside service — they decide which path a run takes, how many times a branch repeats, and when the run pauses, retries, or stops.

| Key | Title | Branches | Config | What it does |
| --- | --- | --- | --- | --- |
| `control.if` | If | `true`, `false` | `condition` (raw) | Follows one of two branches depending on a condition |
| `control.switch` | Switch | one per entry in `cases`, plus `default` | `value`, `cases` | Follows the branch named by `value`, or `default` |
| `control.foreach` | For each | `each`, `done` | `items`, `concurrency` | Runs the `each` branch once per item, then `done` |
| `control.while` | While | `body`, `done` | `condition` (raw), `max_iterations` | Runs the `body` branch while a condition holds, then `done` |
| `control.set` | Set variables | `next` | `values` | Writes `vars.<name>` for later Steps |
| `control.merge` | Merge objects | `next` | `objects` | Merges a list of objects into one (later keys win) |
| `control.noop` | Do nothing | `next` | — | Continues without changing state or doing work |
| `control.delay` | Delay | `next` | `seconds` | Pauses the run, up to 300 seconds |
| `control.stop` | Stop | *(none)* | — | Ends the run immediately, with no further branches |
| `control.retry` | Retry | `attempt`, `next` | `attempts`, `base_delay` | Runs the `attempt` branch with backoff until it succeeds |
| `control.timeout` | Timeout | `attempt`, `next`, `timeout` | `seconds` | Runs the `attempt` branch with a deadline |

<Warning>
`control.if`, `control.while`, and `transform.filter` (in Data blocks below) all set `raw_config`: their `condition` field is **not** pre-rendered as a `{{ }}` template before the block runs. Instead it's evaluated directly as a condition object, using `$path` operands — see [Condition syntax](#condition-syntax) below. Don't wrap a `condition` value in `{{ }}`; write the `$` form instead.
</Warning>

Full explanations, worked examples, and common mistakes for every one of these eleven: [Control flow](/flows/control-flow).

### Condition syntax

`control.if`, `control.while`, `transform.filter`, and `policy.check` all consume the same condition language — a JSON object with exactly one key naming the operator. An operand starting with `$` is a path into the current state (`$input.status`, `$auth.user_id`, `$record.owner_id`); anything else is a literal.

| Kind | Operators |
| --- | --- |
| Combinators | `all` (every child true), `any` (one child true), `not` (negate) |
| Comparison | `eq`, `ne`, `gt`, `gte`, `lt`, `lte` |
| Collection & string | `in`, `not_in`, `contains`, `starts_with`, `ends_with`, `matches` (regex) |
| Presence | `exists` (not `null`), `truthy` (not falsy), `empty` (falsy) |
| Shorthands | `authenticated`, `role`, `permission`, `owner`, `service`, `kind`, `scope`, `aal` |

```json
{ "all": [{ "eq": ["$input.status", "paid"] }, { "gt": ["$input.total", 100] }] }
```

The shorthands expand to a combination of the operators above — `{"role": "admin"}` means "the caller's `roles` include `admin`," `{"owner": "user_id"}` means "the caller is authenticated and `record.user_id` equals `auth.user_id`." They read most naturally in a resource [policy](/policies/overview) or in `policy.check`'s `policy` field, where `record` and `credential` are always in context; inside a plain `control.if` they still work, but only once whatever they reference (`record`, `credential`) is actually present in the run's state.

## Data blocks — transform, validate, compute

Nineteen blocks, all under the `data` category, plus `db.query` and `db.transaction` (registered under `resources`, documented here because they're commonly reached for alongside these). Every one of them is a pure step: given its config and the run's current state, it produces an output and moves on to `next`.

| Key | Title | Branches | Config | What it does |
| --- | --- | --- | --- | --- |
| `transform.map` | Transform | `next` | `value`, `transformer` | Applies a [transformer](/data/transformers) to a value |
| `transform.template` | Template | `next` | `template` (raw) | Builds a JSON value from a template |
| `transform.pick` | Pick fields | `next` | `value`, `fields` | Keeps only the named keys of an object (or list of objects) |
| `transform.rename` | Rename fields | `next` | `value`, `fields` | Renames top-level object fields |
| `transform.filter` | Filter list | `next` | `value`, `condition` (raw) | Keeps list items matching a condition |
| `transform.sort` | Sort list | `next` | `value`, `field`, `descending` | Sorts a list by a field or dotted path |
| `transform.group` | Group list | `next` | `value`, `field` | Groups a list into an object keyed by a field |
| `transform.unique` | Remove duplicates | `next` | `value`, `field` | Keeps the first item for each distinct value |
| `transform.batch` | Batch list | `next` | `value`, `size` | Splits a list into bounded batches |
| `transform.flatten` | Flatten list | `next` | `value`, `depth` | Flattens nested lists |
| `transform.slice` | Slice list | `next` | `value`, `offset`, `limit` | Selects a window of a list |
| `validate.schema` | Validate | `next`, `invalid` | `value`, `fields`, `on_invalid` | Validates a value against field definitions |
| `json.parse` | Parse JSON | `next` | `text` | Parses a JSON string |
| `json.stringify` | Stringify JSON | `next` | `value`, `indent` | Serializes a value to a JSON string |
| `math.calculate` | Calculate | `next` | `operation`, `values`, `digits` | Arithmetic on a list of numbers |
| `transform.summarize` | Summarize list | `next` | `value`, `operation`, `field`, `group_by`, `ignore_null` | Counts, aggregates, or groups a list |
| `util.id` | Generate id | `next` | `kind`, `length` | A UUID4 or a random URL-safe token |
| `crypto.hash` | Hash | `next` | `text`, `algorithm`, `secret` | SHA-256, SHA-512, or HMAC-SHA256 |
| `time.now` | Current time | `next` | `offset_seconds`, `format` | The current UTC time, optionally shifted |
| `db.query` | SQL query | `next` | `sql`, `params` | A parameterized, read-only SQL statement |
| `db.transaction` | Transaction | `next` | `operations` | Several resource writes, applied atomically |

Full explanations and worked examples for `transform.map` through `db.transaction`: [Data blocks](/flows/data-blocks). The four blocks below aren't on that page yet, so they're documented in full here.

### `transform.filter` — Filter list

Keeps the items of a list that match a condition, evaluated once per item with `item` and `index` added to the state the condition sees.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `value` | `json` | yes | The list to filter (a template is rendered first) |
| `condition` | `json` | yes | A condition object (raw — not pre-rendered); use `$item` and `$index` to inspect each element |

**Output:** the list of matching items, in their original order.

```json
{
  "id": "high_value",
  "data": {
    "block": "transform.filter",
    "config": {
      "value": "{{ steps.orders.output }}",
      "condition": { "gt": ["$item.total", 100] }
    }
  }
}
```

### `transform.sort` — Sort list

Sorts a list by a field name or a dotted path into each item.

| Config | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `value` | `json` | yes | — | The list to sort |
| `field` | `string` | yes | — | A field name, or dotted path (e.g. `customer.name`) |
| `descending` | `boolean` | no | `false` | Reverse the order |

**Output:** a new, sorted list. Items missing the field sort first (ascending) or last (descending); if values aren't comparable, they're sorted as strings instead.

```json
{
  "id": "by_total",
  "data": {
    "block": "transform.sort",
    "config": { "value": "{{ steps.orders.output }}", "field": "total", "descending": true }
  }
}
```

### `transform.group` — Group list

Groups a list into an object keyed by a field name or dotted path.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `value` | `json` | yes | The list to group |
| `field` | `string` | yes | A field name, or dotted path, whose (stringified) value becomes the group key |

**Output:** an object whose keys are the distinct field values and whose values are lists of the matching items.

```json
{
  "id": "by_status",
  "data": {
    "block": "transform.group",
    "config": { "value": "{{ steps.orders.output }}", "field": "status" }
  }
}
```

### `transform.batch` — Batch list

Splits a list into consecutive, bounded-size chunks — useful for feeding a `control.foreach` that dispatches one job per batch instead of one per item.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `value` | `json` | yes | The list to split |
| `size` | `integer` | yes | Items per batch, 1–1000 |

**Output:** a list of lists, each with up to `size` items (the last one may be shorter).

```json
{
  "id": "chunks",
  "data": {
    "block": "transform.batch",
    "config": { "value": "{{ steps.recipients.output }}", "size": 100 }
  }
}
```

## Resource blocks — read and write your records

Five blocks, under the `resources` category, that go through the same store a generated `/rest/v1/<resource>` route uses.

| Key | Title | Branches | Config |
| --- | --- | --- | --- |
| `resource.list` | List records | `next` | `resource`, `filters`, `sort`, `limit`, `offset` |
| `resource.get` | Get record | `next`, `missing` | `resource`, `id` |
| `resource.create` | Create record | `next` | `resource`, `data` |
| `resource.update` | Update record | `next`, `missing` | `resource`, `id`, `data` |
| `resource.delete` | Delete record | `next` | `resource`, `id` |

Resource blocks run with **service rights** — they don't re-evaluate the resource's own policies, regardless of who triggered the run. Full explanations, the `filters`-is-equality-only caveat, and worked examples: [Resource blocks](/flows/resource-blocks).

Thirty-three blocks under nine categories, each a thin call into the host runtime. Full explanations for every one: [Platform blocks](/flows/platform-blocks).

| `cache.set` | Cache set | `next` | `key`, `value`, `ttl`, `tags` |
| `cache.delete` | Cache delete | `next` | `key` |
| `cache.invalidate` | Cache invalidate tags | `next` | `tags` |

### Events, jobs, and realtime

| Key | Title | Branches | Config | What it runs |
| --- | --- | --- | --- | --- |
| `event.emit` | Emit event | `next` | `event`, `payload` | Publishes a platform event |
| `flow.call` | Call flow | `next` | `flow`, `input` | Runs another Flow inline and returns its result |
| `queue.flow` | Queue flow | `next` | `flow`, `input`, `delay`, `queue` | Runs **another Flow** as a background Job |
| `queue.function` | Queue function | `next` | `function`, `input`, `delay`, `queue` | Runs a Python Function as a background Job |
| `realtime.publish` | Publish to channel | `next` | `channel`, `event`, `payload` | Publishes a message to a realtime channel |

<Warning>
`flow.call`, `queue.flow`, and `function.call` are easy to confuse. `flow.call` invokes a **Flow** inline and waits for its result. `queue.flow` dispatches a **different Flow** to run later, as a Job, and returns only `{"job_id": ...}`. `function.call` (under Outbound and code, below) calls a Python **Function** inline and continues with its return value.
</Warning>

### Outbound and code

| Key | Title | Branches | Config | What it runs |
| --- | --- | --- | --- | --- |
| `http.request` | HTTP request | `next`, `failed` | `method`, `url`, `headers`, `params`, `body`, `timeout`, `retries` | An external HTTP call |
| `webhook.send` | Send webhook | `next` | `event`, `payload` | Delivers to every outbound webhook subscribed to the event |
| `secret.get` | Read secret | `next` | `name`, `as` | Loads a secret into `vars` |
| `function.call` | Call function | `next` | `function`, `input` | A Python **Function**, inline, in the current run |

### Observability

| Key | Title | Branches | Config |
| --- | --- | --- | --- |
| `log.write` | Log | `next` | `level`, `message`, `data`, `category`, `code`, `tags` |
| `metric.increment` | Metric | `next` | `name`, `value`, `tags` |

### Responses and errors

| Key | Title | Branches | Config |
| --- | --- | --- | --- |
| `response.return` | Respond | *(none)* | `status`, `body`, `headers` |
| `error.raise` | Fail | *(none)* | `status`, `message`, `code` |

Both of these end the run — `response.return` answers the triggering HTTP request (or is simply discarded on a non-HTTP Flow) and stops; `error.raise` always fails the run with the given status and message, even if an `error` branch is wired to it.
