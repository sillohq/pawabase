A flow is a graph of **blocks**. [Triggers](/flows/triggers) start a run, [control blocks](/flows/control-flow) decide which path it takes, [resource and platform blocks](/flows/resource-blocks) talk to your database and the rest of the platform — and **data blocks** do the work in between: turning one value into another, checking it against field definitions, computing a number, or reading the current time.

This page covers every block registered under the `data` category in `pawabase_kit.flows.blocks.data`, plus two blocks that read and write the database directly — `db.query` and `db.transaction` — because most flow authors reach for them right alongside `math.calculate` and `time.now`. In the block catalogue itself these two are filed under the `resources` category next to [`resource.get`/`resource.list`/…](/flows/resource-blocks), and [`flows/block-reference`](/flows/block-reference) groups them there; this page groups them here because that's how you'll actually use them.

<Note>
Every block on this page is a pure step: given its configuration and the run's current [state](/flows/state), it produces an output and moves on. None of them branch except `validate.schema`, and none of them end the run. If you're looking for `if`/`switch`/`for each`, see [Control flow](/flows/control-flow); if you're looking for `resource.create` or `http.request`, see [Resource blocks](/flows/resource-blocks) and [Platform blocks](/flows/platform-blocks).
</Note>

## Quick reference

| Key | Title | Category | Handles | What it does |
| --- | --- | --- | --- | --- |
| `transform.map` | Transform | `data` | `next` | Applies a [transformer](/data/transformers) |
| `transform.template` | Template | `data` | `next` | Builds a value from a [template](/flows/templates) |
| `transform.pick` | Pick fields | `data` | `next` | Keeps only some keys |
| `transform.rename` | Rename fields | `data` | `next` | Renames fields on objects |
| `transform.unique` | Remove duplicates | `data` | `next` | Keeps the first occurrence of each item or field value |
| `transform.flatten` | Flatten list | `data` | `next` | Flattens nested lists |
| `transform.slice` | Slice list | `data` | `next` | Selects a page or range of list items |
| `validate.schema` | Validate | `data` | `next`, `invalid` | Validates against field definitions |
| `json.parse` | Parse JSON | `data` | `next` | Parses a JSON string |
| `json.stringify` | Stringify JSON | `data` | `next` | Serialises a value as JSON |
| `math.calculate` | Calculate | `data` | `next` | Arithmetic on a list of numbers |
| `transform.summarize` | Summarize list | `data` | `next` | Aggregates a list, optionally by group |
| `util.id` | Generate id | `data` | `next` | UUID4 or random token |
| `crypto.hash` | Hash | `data` | `next` | SHA-256, SHA-512, HMAC-SHA256 |
| `time.now` | Current time | `data` | `next` | UTC time in iso/date/unix |
| `db.query` | SQL query | `resources` | `next` | Read-only SQL statement |
| `db.transaction` | Transaction | `resources` | `next` | Several resource writes, atomically |

<Tip>
Every block's `output` is available to later blocks as `steps.<node id>.output`. That's true for these blocks exactly as it is for resource and platform blocks — a `math.calculate` node named `total` exposes its number as `{{ steps.total.output }}` just like a `resource.get` node exposes its record. See [State](/flows/state) for the full picture.
</Tip>

## `transform.map` — Transform

Applies a [transformer](/data/transformers) to a value: the same mechanism resources use to shape their API responses, available inside a flow on any value at any point.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `value` | `json` | yes | The value to transform |
| `transformer` | `json` | yes | A transformer definition (inline) or the name of a stored transformer |

**Output:** the transformed value.

```json
{
  "id": "shape",
  "data": {
    "block": "transform.map",
    "config": {
      "value": "{{ steps.order.output }}",
      "transformer": "order_public"
    }
  }
}
```

An inline transformer works the same way:

```json
{
  "id": "shape",
  "data": {
    "block": "transform.map",
    "config": {
      "value": "{{ steps.order.output }}",
      "transformer": { "fields": ["id", "number", "status", "total_minor", "currency"] }
    }
  }
}
```

## `transform.template` — Template

Builds a JSON value — a string, an object, or a list, at any depth — from a [template](/flows/templates). Unlike most blocks, `transform.template` sets `raw_config = True`: its `template` configuration is **not** pre-rendered by the engine before the block runs. The block renders it itself with `pawabase_kit.templating.render`.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `template` | `json` | yes | Any JSON value; strings inside it are rendered as templates |

**Output:** the rendered value.

```json
{
  "id": "envelope",
  "data": {
    "block": "transform.template",
    "config": {
      "template": {
        "order_id": "{{ steps.order.output.id }}",
        "customer": { "email": "{{ steps.order.output.email }}", "name": "{{ steps.customer.output.name }}" },
        "lines": "{{ steps.items.output }}",
        "placed_at": "{{ steps.now.output }}"
      }
    }
  }
}
```

<Tip>
In practice you rarely need `transform.template` as its own node: almost every block's `config` values are templates already. Reach for a dedicated `transform.template` node when you want to build a value once and reuse it — for example, an outgoing event payload referenced from both an `event.emit` node and a `log.write` node.
</Tip>

## `transform.pick` — Pick fields

Keeps only the named keys of an object, or of every object in a list.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `value` | `json` | yes | An object, or a list of objects |
| `fields` | `array` of `string` | yes | The keys to keep |

**Output:** an object with only those keys (missing keys are simply absent, not `null`), or a list of such objects when `value` is a list.

```json
{
  "id": "public_view",
  "data": {
    "block": "transform.pick",
    "config": {
      "value": "{{ steps.customer.output }}",
      "fields": ["id", "name", "email"]
    }
  }
}
```

Given `{"id": 9, "name": "Ada", "email": "ada@example.com", "password_hash": "…", "notes": "VIP"}`, the output is `{"id": 9, "name": "Ada", "email": "ada@example.com"}` — `password_hash` and `notes` are dropped.

<Warning>
`transform.pick` is a shaping convenience for what a flow **returns** or forwards on — it is not an access control mechanism. It runs after the data has already been read from the database with full, service-level rights. If a caller should not be able to read a field at all, the answer is a [policy](/policies/overview) or a transformer's `read_only`/`write_only` fields on the resource itself.
</Warning>

## List and object transforms

These blocks are common cleanup steps after `resource.list`, an HTTP request, or parsed JSON. All preserve item order.

| Block | Config | Result |
| --- | --- | --- |
| `transform.rename` | `value`, `fields` | Renames top-level object fields. `fields` is an object such as `{"first_name":"given_name"}`. Works on one object or every object in a list. |
| `transform.unique` | `value`, optional `field` | Removes duplicates, keeping the first item. Set `field` to a dotted path such as `customer.email` to deduplicate records by that value. |
| `transform.flatten` | `value`, `depth` | Flattens nested lists one or more levels; `depth` defaults to `1`. |
| `transform.slice` | `value`, `offset`, optional `limit` | Returns a window of a list, useful for pagination and limits. |

```json
[
  {
    "id": "unique_customers",
    "data": {
      "block": "transform.unique",
      "config": { "value": "{{ steps.orders.output.data }}", "field": "customer.email" }
    }
  },
  {
    "id": "first_page",
    "data": {
      "block": "transform.slice",
      "config": { "value": "{{ steps.unique_customers.output }}", "offset": 0, "limit": 20 }
    }
  }
]
```

## `validate.schema` — Validate

Validates a value against a list of [field definitions](/data/transformers) — the same shape resources, functions and custom routes use. This is the one data block that branches.

| Config | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `value` | `json` | yes | — | The value to validate |
| `fields` | `json` | yes | — | A list of field definitions |
| `on_invalid` | `string` (`fail` \| `branch`) | no | `fail` | What to do when validation fails |

**Handles:** `next` (valid), `invalid` (only reachable when `on_invalid` is `branch`).

**Output:** on success, the *cleaned* value — defaults applied, types coerced, unknown keys dropped. On the `invalid` branch, `{"errors": [...]}` with the same shape as the `422` body a resource operation would return.

By default a failed validation **fails the run** with a `422` and the field errors as `details` — useful right after a `trigger.http` node:

```json
{
  "id": "check",
  "data": {
    "block": "validate.schema",
    "config": {
      "value": "{{ input.body }}",
      "fields": [
        { "name": "email", "type": "email", "required": true },
        { "name": "quantity", "type": "integer", "required": true, "minimum": 1, "maximum": 99 }
      ]
    }
  }
}
```

Set `on_invalid` to `branch` when the flow should handle a bad payload itself:

```json
{
  "id": "check",
  "data": {
    "block": "validate.schema",
    "config": {
      "value": "{{ input.body }}",
      "fields": [{ "name": "email", "type": "email", "required": true }],
      "on_invalid": "branch"
    }
  }
}
```

```json
{
  "id": "reply_invalid",
  "data": {
    "block": "response.return",
    "config": { "status": 422, "body": { "ok": false, "errors": "{{ steps.check.output.errors }}" } }
  }
}
```

<Note>
Most of the time you don't need `validate.schema` at all: a `trigger.http` node bound to a route already validates the body, and every `resource.create`/`resource.update` block validates `data`. Reach for `validate.schema` when a flow accepts a shape that isn't already described anywhere — the body of a [webhook trigger](/flows/triggers#trigger-webhook), or a nested object inside a larger payload.
</Note>

## `json.parse` — Parse JSON

Parses a JSON-encoded string. Useful for a webhook body a provider sent as a string field, or for text read back with `storage.read`.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `text` | `string` | yes | The JSON text to parse |

**Output:** the parsed value. Invalid JSON fails the run with a `400` and code `bad_json`:

```
FlowError("invalid JSON: Expecting value: line 1 column 1 (char 0)", status=400, code="bad_json")
```

## `json.stringify` — Stringify JSON

The inverse: serialises any value to JSON text.

| Config | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `value` | `json` | yes | — | The value to serialise |
| `indent` | `integer` | no | — | Pretty-print with this many spaces |

**Output:** a JSON string. Non-JSON-native Python values are serialised with `default=str`.

```json
{
  "id": "encode",
  "data": {
    "block": "json.stringify",
    "config": { "value": "{{ steps.payload.output }}", "indent": 2 }
  }
}
```

Common pairing: build a value, hash it, and store the string form for an audit trail —

```json
[
  { "id": "encode", "data": { "block": "json.stringify", "config": { "value": "{{ steps.order.output }}" } } },
  { "id": "sign", "data": { "block": "crypto.hash", "config": { "text": "{{ steps.encode.output }}", "algorithm": "hmac-sha256", "secret": "WEBHOOK_SIGNING_KEY" } } }
]
```

## `math.calculate` — Calculate

Arithmetic on a list of numbers. Every commerce, billing, and inventory flow in this platform leans on it.

| Config | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `operation` | `string` (enum) | yes | — | `add` \| `subtract` \| `multiply` \| `divide` \| `round` \| `min` \| `max` \| `sum` \| `average` |
| `values` | `json` | yes | — | A list of numbers |
| `digits` | `integer` | no | `2` | Decimal places, used only by `round` |

**Output:** a number. Every value in `values` is coerced with Python's `float()` first.

### Operations

| Operation | Behaviour |
| --- | --- |
| `add` / `sum` | The sum of every value in the list |
| `subtract` | The first value minus the sum of the rest — `subtract([10, 3, 2])` → `5` |
| `multiply` | The product of every value in the list |
| `divide` | The first value divided by each following value — `divide([100, 2, 5])` → `10` |
| `round` | Rounds `values[0]` to `digits` decimal places |
| `min` / `max` | The smallest / largest value in the list |
| `sum` | Alias for `add` |
| `average` | The mean of the list; `0.0` for an empty list |

### The float output gotcha

`math.calculate` always coerces its inputs to `float`, does the arithmetic in floating point, and only afterwards checks whether the **result** is a whole number:

```python
if isinstance(result, float) and result.is_integer():
    result = int(result)
```

That means `add([2, 3])` outputs the **integer** `5`, not `5.0`. But `divide([10, 4])` outputs the **float** `2.5`, and `divide([10, 3])` outputs `3.3333333333333335`. Two consequences to design around:

<Warning>
1. **Templates render floats with their full precision.** `"{{ steps.avg.output }}"` on `3.3333333333333335` writes exactly that unless you round it first.
2. **A field expecting an integer needs an explicit cast.** The blueprint examples consistently write `"{{ steps.total.output | int }}"` when a `math.calculate` output feeds a `resource.update` field typed `integer`.
</Warning>

### Worked examples

Summing a cart's line totals:

```json
[
  {
    "id": "sum_qty",
    "data": {
      "block": "math.calculate",
      "config": {
        "operation": "add",
        "values": ["{{ steps.line.output.data.0.quantity }}", "{{ input.body.quantity }}"],
        "digits": 0
      }
    }
  },
  {
    "id": "available",
    "data": {
      "block": "math.calculate",
      "config": {
        "operation": "subtract",
        "values": ["{{ steps.variant.output.stock }}", "{{ steps.variant.output.reserved }}"],
        "digits": 0
      }
    }
  }
]
```

Computing a platform fee in minor units:

```json
[
  {
    "id": "fee_raw",
    "data": {
      "block": "math.calculate",
      "config": {
        "operation": "multiply",
        "values": ["{{ steps.payment.output.amount_minor }}", "{{ steps.store.output.data.0.platform_fee_bps }}"],
        "digits": 0
      }
    }
  },
  {
    "id": "platform_fee",
    "data": {
      "block": "math.calculate",
      "config": {
        "operation": "divide",
        "values": ["{{ steps.fee_raw.output }}", 10000],
        "digits": 0
      }
    }
  }
]
```

`platform_fee_bps` is basis points (1/100 of a percent), so multiplying the amount by the bps and dividing by `10000` gives the fee in the same minor unit.

Rounding a rating average to one decimal:

```json
[
  {
    "id": "stats",
    "data": {
      "block": "db.query",
      "config": {
        "sql": "SELECT COALESCE(AVG(rating), 0) AS avg, COUNT(*) AS n FROM reviews WHERE product_id = ? AND status = 'approved'",
        "params": ["{{ steps.review.output.product_id }}"]
      }
    }
  },
  {
    "id": "round",
    "data": {
      "block": "math.calculate",
      "config": { "operation": "round", "values": ["{{ steps.stats.output.0.avg }}"], "digits": 1 }
    }
  }
]
```

Negating a value to write an offsetting ledger entry (there's no `negate` operation — `multiply` by `-1` is the idiom):

```json
{
  "id": "neg",
  "data": {
    "block": "math.calculate",
    "config": { "operation": "multiply", "values": ["{{ item.quantity }}", -1], "digits": 0 }
  }
}
```

Flooring a value at zero so released stock never goes negative (there's no `clamp` operation — `max` against `0` does it):

```json
[
  {
    "id": "less",
    "data": {
      "block": "math.calculate",
      "config": { "operation": "subtract", "values": ["{{ item.reserved }}", "{{ item.quantity }}"], "digits": 0 }
    }
  },
  {
    "id": "floor",
    "data": {
      "block": "math.calculate",
      "config": { "operation": "max", "values": ["{{ steps.less.output }}", 0], "digits": 0 }
    }
  }
]
```

## `transform.summarize` — Summarize list

Summarizes records already in the flow, with an operation selected in Studio. It is the no-code alternative to a simple SQL `COUNT`/`SUM`/`GROUP BY` when the list is already available from a resource, HTTP request, or earlier step.

| Config | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `value` | `json` | yes | — | The list to summarize |
| `operation` | `string` (enum) | yes | — | `count`, `count_distinct`, `sum`, `average`, `min`, `max`, `median`, `mode`, `first`, `last`, `collect`, or `distinct` |
| `field` | `string` | no | — | Field or dotted path to read from each item; omit to summarize the items themselves |
| `group_by` | `string` | no | — | Field or dotted path to group by before summarizing |
| `ignore_null` | `boolean` | no | `true` | Ignore `null` values for field-based operations |

Numeric operations (`sum`, `average`, `min`, `max`, `median`, `mode`) coerce values with `float()` and fail with `not_a_number` if a non-numeric value remains. Empty numeric input returns `null`. `count` counts rows when `field` is omitted; with a field, it counts non-null values by default.

```json
{
  "id": "sales_by_team",
  "data": {
    "block": "transform.summarize",
    "config": {
      "value": "{{ steps.orders.output.data }}",
      "operation": "sum",
      "field": "total_minor",
      "group_by": "team"
    }
  }
}
```

For `[ {"team":"blue","total_minor":1200}, {"team":"blue","total_minor":800}, {"team":"red","total_minor":500} ]`, the output is `{"blue": 2000, "red": 500}`. Without `group_by`, the same block returns one value; for example, `operation: "count_distinct", field: "customer_id"` returns the number of unique customers.

Use `collect` to extract a field as a list, or `distinct` to extract its unique values while preserving their first-seen order. For joins, filters against data not already in the run, window functions, or database-scale aggregation, use [`db.query`](#dbquery--sql-query) instead.

## `util.id` — Generate id

Produces a UUID4 or a random URL-safe token.

| Config | Type | Default | Description |
| --- | --- | --- | --- |
| `kind` | `string` (`uuid` \| `token`) | `uuid` | Which kind of id to generate |
| `length` | `integer` | `32` | Token length; only used when `kind` is `token` |

**Output:** a string. `uuid` produces a standard `uuid.uuid4()` string like `"a1b2c3d4-…"`; `token` produces a random URL-safe token via Sillo's `random_token` helper.

```json
{
  "id": "recovery_token",
  "data": {
    "block": "util.id",
    "config": { "kind": "token", "length": 32 }
  }
}
```

## `crypto.hash` — Hash

Hashes text, or signs it with an HMAC when you need the receiving side to prove they hold a shared secret.

| Config | Type | Default | Description |
| --- | --- | --- | --- |
| `text` | `string` | required | The text to hash |
| `algorithm` | `string` (`sha256` \| `sha512` \| `hmac-sha256`) | `sha256` | Which algorithm |
| `secret` | `string` | — | The name of a stored secret, required for `hmac-sha256` |

**Output:** the hex digest string.

Plain hashing — deriving a stable cache key from a large input:

```json
{
  "id": "cache_key",
  "data": {
    "block": "crypto.hash",
    "config": { "text": "{{ steps.query.output | json }}", "algorithm": "sha256" }
  }
}
```

Signing an outbound payload with HMAC:

```json
{
  "id": "sign",
  "data": {
    "block": "crypto.hash",
    "config": {
      "text": "{{ steps.encode.output }}",
      "algorithm": "hmac-sha256",
      "secret": "PARTNER_SIGNING_KEY"
    }
  }
}
```

<Warning>
`secret` is a **name**, resolved server-side through the runtime's `secret()` capability. If the named secret doesn't exist, the block fails the run with `HMAC needs an existing secret` / code `missing_secret`. The secret's *value* is never written to `text`, the trace, or the run's logs — only the digest is.
</Warning>

## `time.now` — Current time

The current UTC time, optionally shifted, in one of three formats. Nearly every flow that writes a timestamp field starts with a `time.now` node.

| Config | Type | Default | Description |
| --- | --- | --- | --- |
| `offset_seconds` | `integer` | `0` | Shift the moment by this many seconds |
| `format` | `string` (`iso` \| `date` \| `unix`) | `iso` | `iso`: `2026-09-28T08:00:00+00:00` · `date`: `2026-09-28` · `unix`: seconds since epoch |

**Output:** a string (`iso`, `date`) or an integer (`unix`).

<Note>
`time.now` always works in **UTC**. If a flow needs to reason in a store's local time, convert on the way out with a template filter or compute the offset explicitly. Storing everything in UTC and converting for display is the pattern used throughout this platform.
</Note>

### The three formats

```json
{ "id": "now_iso", "data": { "block": "time.now", "config": {} } }
```
→ `"2026-09-28T08:00:00.123456+00:00"` — the default, for a `datetime` field.

```json
{ "id": "today", "data": { "block": "time.now", "config": { "format": "date" } } }
```
→ `"2026-09-28"` — a bare date, for a `date`-typed field.

```json
{ "id": "epoch", "data": { "block": "time.now", "config": { "format": "unix" } } }
```
→ `1790668800` — an integer, useful as a cache-busting value.

### Shifting with `offset_seconds`

A cutoff an hour in the past, to find carts that have gone quiet:

```json
{ "id": "cutoff", "data": { "block": "time.now", "config": { "offset_seconds": -3600 } } }
```

Yesterday's date, for a nightly rollup that must always summarise the *previous* day:

```json
{ "id": "day", "data": { "block": "time.now", "config": { "format": "date", "offset_seconds": -86400 } } }
```

A future expiry stamped onto a record:

```json
{ "id": "expires", "data": { "block": "time.now", "config": { "offset_seconds": 86400 } } }
```

<Tip>
`offset_seconds` only shifts the *value returned by this node* — it does not delay the run. To pause a running flow, use [`control.delay`](/flows/control-flow#control-delay). For anything longer, dispatch a delayed job with [`queue.flow`](/flows/platform-blocks#queue-flow).
</Tip>

## `db.query` — SQL query

Runs a single, parameterised, **read-only** SQL statement against the project's database and returns the rows. It's the escape hatch for anything a `resource.list` filter can't express: joins, aggregates, `GROUP BY`, subqueries, window functions.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `sql` | `text` (code widget) | yes | A `SELECT`/`WITH`/`EXPLAIN`/`PRAGMA`/`SHOW` statement with `?` or `$1`/`$2` placeholders |
| `params` | `json` | no | A list of parameter values, positional |

**Output:** a list of row objects.

### Enforcement: read-only, one statement, with a timeout

The API's `ApiRuntime.db_query` runs every statement through `is_read_only(sql)` before it ever reaches the database:

```python
async def db_query(self, sql, params=None):
    if not is_read_only(sql):
        raise FlowError(
            "db.query only runs single read-only statements; use resource blocks "
            "or a transaction to write",
            status=400,
            code="write_refused",
        )
    source = await self.state.source()
    return await asyncio.wait_for(
        source.fetch(sql, list(params or [])), timeout=self.platform.settings.query_timeout
    )
```

`is_read_only` is deliberately conservative:

- the statement must be a **single** statement — a literal `;` anywhere refuses the whole thing;
- it must **start** with `select`, `with`, `explain`, `pragma`, or `show` (case-insensitive);
- even a statement that starts with one of those keywords is scanned for the words ` insert `, ` update `, ` delete `, ` drop `, ` alter `, ` create `, ` truncate `, ` grant `, and ` attach ` appearing anywhere in it — this catches a `WITH` CTE that tries to smuggle a write.

A refused statement fails the run with a `400` and code `write_refused` — before any SQL is sent to the database at all.

The statement also runs under a hard **timeout**, `platform.settings.query_timeout` (`15.0` seconds by default), via `asyncio.wait_for`. A query that runs long is cancelled and the run fails rather than hanging a worker indefinitely.

<Warning>
`db.query` genuinely cannot write. There is no configuration flag to relax this — the enforcement happens in the runtime, not in the block. If you need to write, use [`resource.create`/`update`/`delete`](/flows/resource-blocks) or [`db.transaction`](#db-transaction).
</Warning>

### Placeholders and params

`params` is always a **list**, matched positionally to `?`/`$1…` placeholders in `sql` — never a named/keyword substitution, and never string interpolation:

```json
{
  "id": "totals",
  "data": {
    "block": "db.query",
    "config": {
      "sql": "SELECT COALESCE(SUM(quantity * unit_price_minor), 0) AS subtotal, COALESCE(SUM(quantity), 0) AS items FROM cart_items WHERE cart_id = ?",
      "params": ["{{ vars.cart.id }}"]
    }
  }
}
```

<Warning>
Because `params` are true bind parameters passed straight to the database driver, they are automatically safe against SQL injection. **Never** build `sql` itself with a template that inserts a caller-controlled value. Always leave the value as a `?`/`$1` placeholder and pass it through `params` instead.
</Warning>

## `db.transaction` — Transaction

Applies several **resource writes** atomically: either every operation lands, or none does.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `operations` | `json` | yes | A non-empty list of operations, each `\{"op": "create"|"update"|"delete", "resource": "&lt;name&gt;", "id": &lt;id&gt;, "data": \{…\}` |

**Output:** a list of results, one per operation, in the same order.

### How it's enforced

```python
async def db_transaction(self, operations):
    source = await self.state.source()
    results, effects = [], []
    async with source.transaction() as client:
        for operation in operations:
            op = operation.get("op")
            store = await self.state.store(operation["resource"])
            if op == "create":
                record = await store.create(operation.get("data") or {}, client=client)
                effects.append((operation["resource"], "created", record))
            elif op == "update":
                record = await store.update(operation["id"], operation.get("data") or {}, client=client)
                if record is None:
                    raise FlowError(f"{operation['resource']} {operation['id']} not found", status=404, code="not_found")
                effects.append((operation["resource"], "updated", record))
            elif op == "delete":
                record = await store.delete(operation["id"], client=client)
            else:
                raise FlowError(f"unknown transaction operation {op!r}", code="bad_config")
            results.append(record)
    for resource, change, record in effects:
        await after_write(...)  # only once committed
    return results
```

Two things that make `db.transaction` behave differently from a sequence of `resource.create`/`resource.update` nodes:

1. **Every operation shares one database transaction.** All the writes run on the same connection inside `source.transaction()`. If any operation raises, the whole block fails and **every** write in the list is rolled back.
2. **Effects fire only after the commit.** The `resource.*` events, cache invalidation and realtime notifications are queued during the loop but only actually run **after** the transaction commits successfully. A rolled-back transaction never emits a stray event.

An `update` or `delete` targeting a record that doesn't exist fails the whole transaction with a `404` (`not_found`).

### Worked example: order placement with a stock reservation

```json
{
  "id": "place_order",
  "data": {
    "block": "db.transaction",
    "config": {
      "operations": [
        {
          "op": "create",
          "resource": "orders",
          "data": {
            "store_id": "{{ vars.cart.store_id }}",
            "customer_id": "{{ vars.customer.id }}",
            "total_minor": "{{ steps.totals.output.0.total | int }}",
            "currency": "{{ vars.cart.currency }}",
            "status": "pending",
            "payment_status": "pending"
          }
        },
        {
          "op": "update",
          "resource": "carts",
          "id": "{{ vars.cart.id }}",
          "data": { "status": "converted" }
        }
      ]
    }
  }
}
```

<Note>
`db.transaction`'s `operations` only cover `create`/`update`/`delete` on **resources** — it can't run an arbitrary write statement. If a write genuinely needs raw SQL, that's outside what flows currently expose. See [Custom blocks](/flows/custom-blocks) for what is and isn't extensible.
</Note>

Because `db.transaction`'s operations are resource writes, each one still runs resource-level field validation exactly as `resource.create`/`resource.update` would — a validation failure on the second operation rolls back the first just like any other failure inside the transaction.

<Tip>
For the very common "read, compute, then write several rows together" shape, put your `db.query`/`math.calculate` steps **before** the `db.transaction` node and feed their outputs into its `operations` templates. `db.transaction`'s own operations are plain JSON, not a sub-flow, so you can't branch or loop *inside* it — build the full `operations` list with a `control.foreach`/`control.set` pair beforehand if the number of writes is dynamic.
</Tip>

## Common mistakes

<AccordionGroup>
  <Accordion title="Writing a caller-controlled value into db.query's sql instead of params">
    `"sql": "SELECT * FROM orders WHERE id = {{ input.params.id }}"` reopens SQL injection. Always keep the placeholder in `sql` and pass the value through `params`.
  </Accordion>
  <Accordion title="Expecting db.query to write">
    `is_read_only` refuses anything that isn't a `select`/`with`/`explain` statement. There's no override. Use `resource.create`/`update`/`delete` or `db.transaction`.
  </Accordion>
  <Accordion title="Forgetting math.calculate returns a float unless the whole result happens to be an integer">
    `divide`, `average`, and any `multiply`/`subtract` chain that doesn't land on a whole number will produce a float with full precision. Cast with `| int` or chain a `round` step.
  </Accordion>
  <Accordion title="Treating db.query's output as a single row">
    `db.query` always returns a **list**, even for `SELECT COUNT(*)`. Read a scalar as `steps.<node>.output.0.<column>`, not `steps.<node>.output.<column>`.
  </Accordion>
  <Accordion title="Assuming db.transaction's writes are visible to db.query mid-transaction">
    `db.query` and `db.transaction` use separate connections/transactions. A `db.query` step that runs after a `db.transaction` step sees its committed results.
  </Accordion>
  <Accordion title="Relying on time.now's format to imply a timezone conversion">
    `time.now` is always UTC, regardless of `format`. If a flow needs "9am store time," compute the offset explicitly with `offset_seconds`.
  </Accordion>
</AccordionGroup>

## FAQ

<AccordionGroup>
  <Accordion title="Can db.query call stored procedures or functions?">
    Only ones invoked from inside an allowed statement — `SELECT my_func(...)`, say — and only if none of the forbidden words in `is_read_only` appear in the function's name or the surrounding SQL text.
  </Accordion>
  <Accordion title="Does db.transaction retry on conflict?">
    No. If the underlying database raises, the block fails the run like any other error — wrap it in [`control.retry`](/flows/control-flow#control-retry) if the operation is safe to retry, or design the writes so conflicts can't occur.
  </Accordion>
  <Accordion title="Is transform.map the same engine resources use for their response shape?">
    Yes — `transform.map` calls `pawabase_kit.transformers.apply_transformer`, the identical function a resource operation runs on its way out.
  </Accordion>
  <Accordion title="Why is there no dedicated 'negate' or 'clamp' math operation?">
    `math.calculate`'s operation set is deliberately small. `multiply` by `-1` covers negation; `max`/`min` against a literal covers clamping. Both idioms are used throughout this platform's own blueprint flows.
  </Accordion>
</AccordionGroup>
