A flow is a graph of **blocks**. [Triggers](/flows/triggers) start a run, [control blocks](/flows/control-flow) decide which path it takes, [resource and platform blocks](/flows/resource-blocks) talk to your database and the rest of the platform — and **data blocks** do the work in between: turning one value into another, checking it against field definitions, computing a number, or reading the current time.

This page covers every block registered under the `data` category in `pawabase_kit.flows.blocks.data`, plus two blocks that read and write the database directly — `db.query` and `db.transaction` — because most flow authors reach for them right alongside `math.calculate` and `time.now`. In the block catalogue itself these two are filed under the `resources` category next to [`resource.get`/`resource.list`/…](/flows/resource-blocks), and [`flows/block-reference`](/flows/block-reference) groups them there; this page groups them here because that's how you'll actually use them.

<Note>
Every block on this page is a pure step: given its configuration and the run's current [state](/flows/state), it produces an output and moves on. None of them branch except `validate.schema`, and none of them end the run. If you're looking for `if`/`switch`/`for each`, see [Control flow](/flows/control-flow); if you're looking for `resource.create` or `http.request`, see [Resource blocks](/flows/resource-blocks) and [Platform blocks](/flows/platform-blocks).
</Note>

## Quick reference

| Key | Title | Category | Handles | What it does |
| --- | --- | --- | --- | --- |
| `transform.map` | Transform | `data` | `next` | Applies a [transformer](/data/transformers) — inline, stored, or Python — to a value |
| `transform.template` | Template | `data` | `next` | Builds a value from a [template](/flows/templates) (strings, objects or lists) |
| `transform.pick` | Pick fields | `data` | `next` | Keeps only some keys of an object or list of objects |
| `validate.schema` | Validate | `data` | `next`, `invalid` | Validates a value against field definitions |
| `json.parse` | Parse JSON | `data` | `next` | Parses a JSON string into a value |
| `json.stringify` | Stringify JSON | `data` | `next` | Serialises a value as JSON text |
| `math.calculate` | Calculate | `data` | `next` | Arithmetic on a list of numbers |
| `util.id` | Generate id | `data` | `next` | A UUID4 or a random URL-safe token |
| `crypto.hash` | Hash | `data` | `next` | SHA-256, SHA-512, or an HMAC-SHA256 signature |
| `time.now` | Current time | `data` | `next` | The current UTC time, optionally shifted |
| `db.query` | SQL query | `resources` | `next` | A single read-only SQL statement |
| `db.transaction` | Transaction | `resources` | `next` | Several resource writes, applied atomically |

<Tip>
Every block's `output` is available to later blocks as `steps.<node id>.output`. That's true for these blocks exactly as it is for resource and platform blocks — a `math.calculate` node named `total` exposes its number as `{{ steps.total.output }}` just like a `resource.get` node exposes its record. See [State](/flows/state) for the full picture of what a running flow can see.
</Tip>

## transform.map — Transform

Applies a [transformer](/data/transformers) to a value: the same mechanism resources use to shape their API responses, available inside a flow on any value at any point.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `value` | `json` | yes | The value to transform |
| `transformer` | `json` | yes | A transformer definition (inline) or the name of a stored transformer |

**Output:** the transformed value.

Reach for `transform.map` when you already have a transformer defined for a resource and want a flow step to produce exactly the same shape — for example, a flow that emails a customer a receipt built from the same `order_public` transformer the storefront API uses, so the two never drift apart.

```json
{
  "id": "shape",
  "data": {
    "block": "transform.map",
    "config": {
      "value": "{{ steps.order.output }}",
      "transformer": "order_public"
    }
  }
}
```

An inline transformer works the same way:

```json
{
  "id": "shape",
  "data": {
    "block": "transform.map",
    "config": {
      "value": "{{ steps.order.output }}",
      "transformer": {
        "fields": ["id", "number", "status", "total_minor", "currency"]
      }
    }
  }
}
```

## transform.template — Template

Builds a JSON value — a string, an object, or a list, at any depth — from a [template](/flows/templates). Unlike most blocks, `transform.template` sets `raw_config = True`: its `template` configuration is **not** pre-rendered by the engine before the block runs. The block renders it itself with `pawabase_kit.templating.render`, which is what lets a single field hold an entire nested object of templates rather than one string.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `template` | `json` | yes | Any JSON value; strings inside it are rendered as templates |

**Output:** the rendered value.

```json
{
  "id": "envelope",
  "data": {
    "block": "transform.template",
    "config": {
      "template": {
        "order_id": "{{ steps.order.output.id }}",
        "customer": {
          "email": "{{ steps.order.output.email }}",
          "name": "{{ steps.customer.output.name }}"
        },
        "lines": "{{ steps.items.output }}",
        "placed_at": "{{ steps.now.output }}"
      }
    }
  }
}
```

<Tip>
In practice you rarely need `transform.template` as its own node: almost every block's `config` values are templates already (see [Templates](/flows/templates)), so a `resource.create` node's `data` object can hold exactly this same nested shape directly. Reach for a dedicated `transform.template` node when you want to build a value once and reuse it — for example, an outgoing event payload referenced from both an `event.emit` node and a `log.write` node.
</Tip>

## transform.pick — Pick fields

Keeps only the named keys of an object, or of every object in a list.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `value` | `json` | yes | An object, or a list of objects |
| `fields` | `array` of `string` | yes | The keys to keep |

**Output:** an object with only those keys (missing keys are simply absent, not `null`), or a list of such objects when `value` is a list.

```json
{
  "id": "public_view",
  "data": {
    "block": "transform.pick",
    "config": {
      "value": "{{ steps.customer.output }}",
      "fields": ["id", "name", "email"]
    }
  }
}
```

Given `{"id": 9, "name": "Ada", "email": "ada@example.com", "password_hash": "…", "notes": "VIP"}`, the output is `{"id": 9, "name": "Ada", "email": "ada@example.com"}` — `password_hash` and `notes` are dropped. Run it on a list (say, `steps.customers.output.data`) and every element is picked the same way:

```json
{
  "id": "public_list",
  "data": {
    "block": "transform.pick",
    "config": {
      "value": "{{ steps.customers.output.data }}",
      "fields": ["id", "name"]
    }
  }
}
```

<Warning>
`transform.pick` is a shaping convenience for what a flow **returns** or forwards on — it is not an access control mechanism. It runs after the data has already been read from the database with full, service-level rights. If a caller should not be able to read a field at all, the answer is a [policy](/policies/overview) or a transformer's `read_only`/`write_only` fields on the resource itself, evaluated before the row leaves the database layer — the same point made in [Policies → Common mistakes](/policies/overview#common-mistakes).
</Warning>

## validate.schema — Validate

Validates a value against a list of [field definitions](/data/transformers) — the same shape resources, functions and custom routes use. This is the one data block that branches.

| Config | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `value` | `json` | yes | — | The value to validate |
| `fields` | `json` | yes | — | A list of field definitions |
| `on_invalid` | `string` (`fail` \| `branch`) | no | `fail` | What to do when validation fails |

**Handles:** `next` (valid), `invalid` (only reachable when `on_invalid` is `branch`).

**Output:** on success, the *cleaned* value — defaults applied, types coerced, unknown keys dropped, exactly as `pawabase_kit.schemas.validate_payload` returns it for a resource create. On the `invalid` branch, `{"errors": [...]}` with the same shape as the `422` body a resource operation would return.

By default a failed validation **fails the run** with a `422` and the field errors as `details` — useful right after a `trigger.http` node, mirroring what a generated resource route already does for you automatically:

```json
{
  "id": "check",
  "data": {
    "block": "validate.schema",
    "config": {
      "value": "{{ input.body }}",
      "fields": [
        { "name": "email", "type": "email", "required": true },
        { "name": "quantity", "type": "integer", "required": true, "minimum": 1, "maximum": 99 }
      ]
    }
  }
}
```

Set `on_invalid` to `branch` when the flow should handle a bad payload itself instead of a bare `422` — for example, to log it, or to reply with a custom body:

```json
{
  "id": "check",
  "data": {
    "block": "validate.schema",
    "config": {
      "value": "{{ input.body }}",
      "fields": [{ "name": "email", "type": "email", "required": true }],
      "on_invalid": "branch"
    }
  }
}
```

```json
{
  "id": "reply_invalid",
  "data": {
    "block": "response.return",
    "config": {
      "status": 422,
      "body": { "ok": false, "errors": "{{ steps.check.output.errors }}" }
    }
  }
}
```
Edge from `check` to `reply_invalid` on the `invalid` handle.

<Note>
Most of the time you don't need `validate.schema` at all: a `trigger.http` node bound to a route already validates the body against the route's `input_fields`/`input_schema` before the flow even starts, and every `resource.create`/`resource.update` block validates `data` against the resource's own field definitions. Reach for `validate.schema` when a flow accepts a shape that isn't already described anywhere — the body of a [webhook trigger](/flows/triggers#trigger-webhook), or a nested object inside a larger payload.
</Note>

## json.parse — Parse JSON

Parses a JSON-encoded string. Useful for a webhook body a provider sent as a string field, or for text read back with `storage.read`.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `text` | `string` | yes | The JSON text to parse |

**Output:** the parsed value (object, array, string, number, boolean, or `null`).

```json
{
  "id": "decode",
  "data": {
    "block": "json.parse",
    "config": { "text": "{{ steps.read_config.output }}" }
  }
}
```

Invalid JSON fails the run with a `400` and code `bad_json`:

```
FlowError("invalid JSON: Expecting value: line 1 column 1 (char 0)", status=400, code="bad_json")
```

## json.stringify — Stringify JSON

The inverse: serialises any value to JSON text.

| Config | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `value` | `json` | yes | — | The value to serialise |
| `indent` | `integer` | no | — | Pretty-print with this many spaces of indent; omit for compact output |

**Output:** a JSON string. Non-JSON-native Python values (like `datetime`s that have already been resolved from templates) are serialised with `default=str`, so they never raise — they just become their string form.

```json
{
  "id": "encode",
  "data": {
    "block": "json.stringify",
    "config": { "value": "{{ steps.payload.output }}", "indent": 2 }
  }
}
```

Common pairing: build a value, hash it, and store the string form for an audit trail —

```json
[
  { "id": "encode", "data": { "block": "json.stringify", "config": { "value": "{{ steps.order.output }}" } } },
  { "id": "sign", "data": { "block": "crypto.hash", "config": { "text": "{{ steps.encode.output }}", "algorithm": "hmac-sha256", "secret": "WEBHOOK_SIGNING_KEY" } } }
]
```

## math.calculate — Calculate

Arithmetic on a list of numbers. Every commerce, billing, and inventory flow in this platform leans on it, because `db.query` results and resource fields arrive as plain values, not already summed or rounded.

| Config | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `operation` | `string` (enum) | yes | — | `add` \| `subtract` \| `multiply` \| `divide` \| `round` \| `min` \| `max` \| `sum` \| `average` |
| `values` | `json` | yes | — | A list of numbers (a single value is wrapped in a list for you) |
| `digits` | `integer` | no | `2` | Decimal places, used only by `round` |

**Output:** a number. Every value in `values` is coerced with Python's `float()` first — a non-numeric value (an empty string, `null`, a word) fails the run with `calculate needs numbers` / code `not_a_number`.

### Operations

| Operation | Behaviour |
| --- | --- |
| `add` / `sum` | The sum of every value in the list |
| `subtract` | The first value minus the sum of the rest — `subtract([10, 3, 2])` → `5` |
| `multiply` | The product of every value in the list |
| `divide` | The first value divided by each following value in turn — `divide([100, 2, 5])` → `10`. Any zero divisor after the first value fails the run with `division by zero` / code `division_by_zero` |
| `round` | Rounds `values[0]` to `digits` decimal places (only the first value is used) |
| `min` / `max` | The smallest / largest value in the list |
| `sum` | Alias for `add` |
| `average` | The mean of the list; `0.0` for an empty list |

### The float output gotcha

`math.calculate` always coerces its inputs to `float`, does the arithmetic in floating point, and only afterwards checks whether the **result** is a whole number:

```python
if isinstance(result, float) and result.is_integer():
    result = int(result)
```

That means `add([2, 3])` outputs the **integer** `5`, not `5.0` — convenient when the result feeds straight into an `integer` field on `resource.update`. But `divide([10, 4])` outputs the **float** `2.5`, and something like `divide([10, 3])` outputs `3.3333333333333335`, not neatly rounded. Two consequences to design around:

<Warning>
1. **Templates render floats with their full precision.** `"{{ steps.avg.output }}"` on `3.3333333333333335` writes exactly that into a string field or a JSON body unless you round it first (chain a `round` step, or apply `| round(2)` — see [Templates](/flows/templates#filters) for the filter list).
2. **A field expecting an integer needs an explicit cast.** The blueprint examples in this codebase consistently write `"{{ steps.total.output | int }}"` when a `math.calculate` output feeds a `resource.update` or `resource.create` field typed `integer` or `number` with no decimals — because the block itself only drops the `.0` when the *whole result* happens to be a whole number, not when your business logic implies it should be. A subtraction of reserved stock that goes through several `add`/`subtract` steps in minor-unit money math should always be capped with `| int` (or a trailing `round` node) before it's written back.
</Warning>

### Worked examples

Summing a cart's line totals and reserving the right amount of stock — adapted directly from the commerce blueprint's `cart_add` flow:

```json
[
  {
    "id": "sum_qty",
    "data": {
      "block": "math.calculate",
      "config": {
        "operation": "add",
        "values": ["{{ steps.line.output.data.0.quantity }}", "{{ input.body.quantity }}"],
        "digits": 0
      }
    }
  },
  {
    "id": "qty_existing",
    "data": {
      "block": "control.set",
      "config": { "values": { "qty": "{{ steps.sum_qty.output | int }}" } }
    }
  },
  {
    "id": "available",
    "data": {
      "block": "math.calculate",
      "config": {
        "operation": "subtract",
        "values": ["{{ steps.variant.output.stock }}", "{{ steps.variant.output.reserved }}"],
        "digits": 0
      }
    }
  }
]
```

Computing a platform fee in minor units (multiply then divide, both capped and cast):

```json
[
  {
    "id": "fee_raw",
    "data": {
      "block": "math.calculate",
      "config": {
        "operation": "multiply",
        "values": ["{{ steps.payment.output.amount_minor }}", "{{ steps.store.output.data.0.platform_fee_bps }}"],
        "digits": 0
      }
    }
  },
  {
    "id": "platform_fee",
    "data": {
      "block": "math.calculate",
      "config": {
        "operation": "divide",
        "values": ["{{ steps.fee_raw.output }}", 10000],
        "digits": 0
      }
    }
  }
]
```
`platform_fee_bps` is basis points (1/100 of a percent), so multiplying the amount by the bps and dividing by `10000` gives the fee in the same minor unit as the payment.

Rounding a rating average to one decimal before saving it:

```json
[
  {
    "id": "stats",
    "data": {
      "block": "db.query",
      "config": {
        "sql": "SELECT COALESCE(AVG(rating), 0) AS avg, COUNT(*) AS n FROM reviews WHERE product_id = ? AND status = 'approved'",
        "params": ["{{ steps.review.output.product_id }}"]
      }
    }
  },
  {
    "id": "round",
    "data": {
      "block": "math.calculate",
      "config": { "operation": "round", "values": ["{{ steps.stats.output.0.avg }}"], "digits": 1 }
    }
  },
  {
    "id": "save",
    "data": {
      "block": "resource.update",
      "config": {
        "resource": "products",
        "id": "{{ steps.review.output.product_id }}",
        "data": { "rating_avg": "{{ steps.round.output }}", "rating_count": "{{ steps.stats.output.0.n | int }}" }
      }
    }
  }
]
```

Averaging an order total for a daily rollup:

```json
{
  "id": "avg",
  "data": {
    "block": "math.calculate",
    "config": {
      "operation": "divide",
      "values": ["{{ item.gross }}", "{{ item.orders }}"],
      "digits": 0
    }
  }
}
```

Negating a value to write an offsetting ledger entry (there's no `negate` operation — `multiply` by `-1` is the idiom used throughout the platform's own flows):

```json
{
  "id": "neg",
  "data": {
    "block": "math.calculate",
    "config": { "operation": "multiply", "values": ["{{ item.quantity }}", -1], "digits": 0 }
  }
}
```

Flooring a value at zero so released stock never goes negative (there's no `clamp` operation either — `max` against a literal `0` does it):

```json
[
  {
    "id": "less",
    "data": {
      "block": "math.calculate",
      "config": { "operation": "subtract", "values": ["{{ item.reserved }}", "{{ item.quantity }}"], "digits": 0 }
    }
  },
  {
    "id": "floor",
    "data": {
      "block": "math.calculate",
      "config": { "operation": "max", "values": ["{{ steps.less.output }}", 0], "digits": 0 }
    }
  }
]
```

## util.id — Generate id

Produces a UUID4 or a random URL-safe token, for anything that needs an identifier that isn't the resource's own primary key — an idempotency key, a recovery token, a correlation id passed to an external system.

| Config | Type | Default | Description |
| --- | --- | --- | --- |
| `kind` | `string` (`uuid` \| `token`) | `uuid` | Which kind of id to generate |
| `length` | `integer` | `32` | Token length in characters; only used when `kind` is `token` |

**Output:** a string. `uuid` produces a standard `uuid.uuid4()` string like `"a1b2c3d4-…"`; `token` produces a random URL-safe token of the requested length via Sillo's `random_token` helper (imported lazily, inside the block, so a runtime that doesn't need it never pays for the import).

```json
{
  "id": "recovery_token",
  "data": {
    "block": "util.id",
    "config": { "kind": "token", "length": 32 }
  }
}
```

Straight from the abandoned-cart recovery flow: generate a token, stamp it on a new record, and email a link that embeds it —

```json
[
  { "id": "token", "data": { "block": "util.id", "config": { "kind": "token", "length": 32 } } },
  { "id": "now", "data": { "block": "time.now", "config": {} } },
  {
    "id": "record",
    "data": {
      "block": "resource.create",
      "config": {
        "resource": "abandoned_carts",
        "data": {
          "store_id": "{{ item.store_id }}",
          "cart_id": "{{ item.id }}",
          "email": "{{ item.email }}",
          "recovery_status": "emailed",
          "recovery_token": "{{ steps.token.output }}",
          "notified_at": "{{ steps.now.output }}"
        }
      }
    }
  },
  {
    "id": "mail",
    "data": {
      "block": "mail.send",
      "config": {
        "to": "{{ item.email }}",
        "template": "cart_recovery",
        "data": { "token": "{{ steps.token.output }}" }
      }
    }
  }
]
```

The recipient then follows `https://shop.example.com/recover/{{ token }}`, and a `trigger.http` flow looks the record up by `recovery_token` with a `resource.list` filter — see [Recipes → Abandoned cart recovery](/flows/recipes#abandoned-cart-recovery) for the full round trip.

## crypto.hash — Hash

Hashes text, or signs it with an HMAC when you need the receiving side to prove they hold a shared secret.

| Config | Type | Default | Description |
| --- | --- | --- | --- |
| `text` | `string` | required | The text to hash |
| `algorithm` | `string` (`sha256` \| `sha512` \| `hmac-sha256`) | `sha256` | Which algorithm |
| `secret` | `string` | — | The name of a stored [secret](/operate/secrets), required for `hmac-sha256` |

**Output:** the hex digest string.

Plain hashing — for example, deriving a stable, non-reversible cache key from a large input:

```json
{
  "id": "cache_key",
  "data": {
    "block": "crypto.hash",
    "config": { "text": "{{ steps.query.output | json }}", "algorithm": "sha256" }
  }
}
```

Signing an outbound payload with HMAC so a receiver can verify it came from you (the same technique Pawabase's own outbound webhooks use, described in [Events → Webhooks](/webhooks/outbound)):

```json
{
  "id": "sign",
  "data": {
    "block": "crypto.hash",
    "config": {
      "text": "{{ steps.encode.output }}",
      "algorithm": "hmac-sha256",
      "secret": "PARTNER_SIGNING_KEY"
    }
  }
}
```

<Warning>
`secret` is a **name**, resolved server-side through the runtime's `secret()` capability — the same one `secret.get` uses (see [Platform blocks](/flows/platform-blocks#secret-get)). If the named secret doesn't exist in this environment, the block fails the run with `HMAC needs an existing secret` / code `missing_secret` rather than silently hashing with an empty key. The secret's *value* is never written to `text`, the trace, or the run's logs — only the digest is.
</Warning>

## time.now — Current time

The current UTC time, optionally shifted, in one of three formats. Nearly every flow that writes a timestamp field, computes a cutoff, or names a day for a rollup starts with a `time.now` node.

| Config | Type | Default | Description |
| --- | --- | --- | --- |
| `offset_seconds` | `integer` | `0` | Shift the moment by this many seconds (negative moves into the past) |
| `format` | `string` (`iso` \| `date` \| `unix`) | `iso` | `iso`: `2026-09-28T08:00:00+00:00` · `date`: `2026-09-28` · `unix`: seconds since epoch |

**Output:** a string (`iso`, `date`) or an integer (`unix`).

<Note>
`time.now` always works in **UTC**. There is no timezone configuration on the block itself — if a flow needs to reason in a store's or a user's local time, convert on the way out with a template filter or compute the offset explicitly (see [Templates → Filters](/flows/templates#filters)). Storing everything in UTC and converting for display is the pattern used throughout this platform's own resources and blueprints.
</Note>

### The three formats

```json
{ "id": "now_iso", "data": { "block": "time.now", "config": {} } }
```
→ `"2026-09-28T08:00:00.123456+00:00"` — the default, and what you want for a `datetime` field on `resource.update`/`resource.create`.

```json
{ "id": "today", "data": { "block": "time.now", "config": { "format": "date" } } }
```
→ `"2026-09-28"` — a bare date, for a `date`-typed field or for grouping ("yesterday's rollup").

```json
{ "id": "epoch", "data": { "block": "time.now", "config": { "format": "unix" } } }
```
→ `1790668800` — an integer, useful as a cache-busting value or a signature timestamp component.

### Shifting with `offset_seconds`

A cutoff an hour in the past, to find carts that have gone quiet:

```json
{
  "id": "cutoff",
  "data": { "block": "time.now", "config": { "offset_seconds": -3600 } }
}
```
```json
{
  "id": "idle",
  "data": {
    "block": "db.query",
    "config": {
      "sql": "SELECT id, email FROM carts WHERE status = 'open' AND last_activity_at < ? LIMIT 200",
      "params": ["{{ steps.cutoff.output }}"]
    }
  }
}
```

Yesterday's date, for a nightly rollup that must be idempotent and always summarise the *previous* day regardless of what time the job actually fires:

```json
{
  "id": "day",
  "data": { "block": "time.now", "config": { "format": "date", "offset_seconds": -86400 } }
}
```

A future expiry stamped onto a record, used later by a scheduled sweep:

```json
{
  "id": "expires",
  "data": { "block": "time.now", "config": { "offset_seconds": 86400 } }
}
```

<Tip>
`offset_seconds` only shifts the *value returned by this node* — it does not delay the run. To pause a running flow, use [`control.delay`](/flows/control-flow#control-delay) (capped at 300 seconds); for anything longer, dispatch a delayed job with [`queue.flow`](/flows/platform-blocks#queue-flow) or [`queue.function`](/flows/platform-blocks#queue-function) and its own `delay`.
</Tip>

## db.query — SQL query

Runs a single, parameterised, **read-only** SQL statement against the project's database and returns the rows. It's the escape hatch for anything a `resource.list` filter can't express: joins, aggregates, `GROUP BY`, subqueries, window functions — the blueprint examples in this codebase reach for it constantly for cart totals, discount pricing, shipping rates, and rollups.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `sql` | `text` (code widget) | yes | A `SELECT`/`WITH`/`EXPLAIN`/`PRAGMA`/`SHOW` statement, with `?` (SQLite/MySQL style) or `$1`, `$2`, … (Postgres style) placeholders |
| `params` | `json` | no | A list of parameter values, positional, matching the placeholders in `sql` |

**Output:** a list of row objects (`[{"col": value, …}, …]`), in the shape your database driver returns them — column names as keys.

### Enforcement: read-only, one statement, with a timeout

The API's `ApiRuntime.db_query` runs every statement through `is_read_only(sql)` before it ever reaches the database:

```python
async def db_query(self, sql, params=None):
    if not is_read_only(sql):
        raise FlowError(
            "db.query only runs single read-only statements; use resource blocks "
            "or a transaction to write",
            status=400,
            code="write_refused",
        )
    source = await self.state.source()
    return await asyncio.wait_for(
        source.fetch(sql, list(params or [])), timeout=self.platform.settings.query_timeout
    )
```

`is_read_only` is deliberately conservative:

- the statement must be a **single** statement — a literal `;` anywhere in it (other than a single trailing one) refuses the whole thing, so stacked statements can never sneak a write in behind a `SELECT`;
- it must **start** with `select`, `with`, `explain`, `pragma`, or `show` (case-insensitive) — anything else (`insert`, `update`, `delete`, `merge`, a bare table name) is refused outright;
- even a statement that starts with one of those keywords is scanned for the words ` insert `, ` update `, ` delete `, ` drop `, ` alter `, ` create `, ` truncate `, ` grant `, and ` attach ` appearing anywhere in it (padded with spaces so word boundaries match) — this catches a `WITH` CTE that tries to smuggle a write, or a `SELECT` that references a function with a dangerous name.

A refused statement fails the run with a `400` and code `write_refused` — before any SQL is sent to the database at all.

The statement also runs under a hard **timeout**, `platform.settings.query_timeout` (`15.0` seconds by default), via `asyncio.wait_for`. A query that runs long is cancelled and the run fails rather than hanging a worker indefinitely.

<Warning>
`db.query` genuinely cannot write. There is no configuration flag to relax this — the enforcement happens in the runtime, not in the block, so it applies identically no matter how the flow was authored. If you need to write, use [`resource.create`/`update`/`delete`](/flows/resource-blocks) for a single resource, or [`db.transaction`](#db-transaction) below for several writes that must land together. This is also why `db.query` never emits `resource.*` events or runs `after_write` hooks — reads have nothing to announce.
</Warning>

### Placeholders and params

`params` is always a **list**, matched positionally to `?`/`$1…` placeholders in `sql` — never a named/keyword substitution, and never string interpolation. Build the list with templates exactly like any other block config:

```json
{
  "id": "totals",
  "data": {
    "block": "db.query",
    "config": {
      "sql": "SELECT COALESCE(SUM(quantity * unit_price_minor), 0) AS subtotal, COALESCE(SUM(quantity), 0) AS items FROM cart_items WHERE cart_id = ?",
      "params": ["{{ vars.cart.id }}"]
    }
  }
}
```

<Warning>
Because `params` are true bind parameters passed straight to the database driver, they are automatically safe against SQL injection — the value is never spliced into the `sql` string. **Never** build `sql` itself with a template that inserts a caller-controlled value (`"SELECT * FROM orders WHERE id = {{ input.params.id }}"`) — that reintroduces exactly the injection risk parameters exist to prevent. Always leave the value as a `?`/`$1` placeholder and pass it through `params` instead.
</Warning>

### Worked examples

A join with computed columns, from the commerce blueprint's cart lines query:

```json
{
  "id": "lines",
  "data": {
    "block": "db.query",
    "config": {
      "sql": "SELECT ci.id, ci.variant_id, ci.quantity, ci.quantity * ci.unit_price_minor AS line_total_minor, p.title, v.stock, v.reserved FROM cart_items ci JOIN product_variants v ON v.id = ci.variant_id JOIN products p ON p.id = ci.product_id WHERE ci.cart_id = ? ORDER BY ci.id",
      "params": ["{{ vars.cart.id }}"]
    }
  }
}
```

An aggregate `GROUP BY … HAVING` for a payout run:

```json
{
  "id": "balances",
  "data": {
    "block": "db.query",
    "config": {
      "sql": "SELECT store_id, currency, SUM(amount_minor) AS balance FROM ledger_entries GROUP BY store_id, currency HAVING SUM(amount_minor) > 0",
      "params": []
    }
  }
}
```

A conditional-pricing lookup with a nested `CASE`, three placeholders reused across the statement:

```json
{
  "id": "price",
  "data": {
    "block": "db.query",
    "config": {
      "sql": "SELECT COALESCE((SELECT CASE WHEN d.kind = 'percentage' THEN CAST(? AS INTEGER) * d.value / 10000 ELSE d.value END FROM discounts d WHERE d.id = ? AND d.is_active = ?), 0) AS amount",
      "params": ["{{ steps.totals.output.0.subtotal }}", "{{ steps.code.output.data.0.id }}", true]
    }
  }
}
```

A scalar result read back through the first row: `db.query` always returns a **list**, even for a single aggregate row, so a scalar is `steps.<node>.output.0.<column>`:

```json
{
  "id": "reply",
  "data": {
    "block": "response.return",
    "config": { "body": { "count": "{{ steps.stats.output.0.n | int }}" } }
  }
}
```

<Tip>
Because `is_read_only` allows `EXPLAIN` and `PRAGMA`/`SHOW`, `db.query` also works for lightweight introspection during development — `EXPLAIN QUERY PLAN SELECT …` to sanity-check an index is being used. It's not a substitute for [Studio's database inspector](/data/database-console), which is where you'd normally reach for that.
</Tip>

## db.transaction — Transaction

Applies several **resource writes** atomically: either every operation lands, or none does. Use it whenever a flow must keep two or more resources consistent with each other and a partial write would leave bad data behind — for example, creating an order together with its ledger entries, or moving stock between two variants.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `operations` | `json` | yes | A non-empty list of operations, each `{"op": "create"|"update"|"delete", "resource": "<name>", "id": <id, for update/delete>, "data": {…}, for create/update}` |

**Output:** a list of results, one per operation, in the same order — the created/updated record for `create`/`update`, or the delete's return value for `delete`.

### How it's enforced

```python
async def db_transaction(self, operations):
    source = await self.state.source()
    results, effects = [], []
    async with source.transaction() as client:
        for operation in operations:
            op = operation.get("op")
            store = await self.state.store(operation["resource"])
            if op == "create":
                record = await store.create(operation.get("data") or {}, client=client)
                effects.append((operation["resource"], "created", record))
            elif op == "update":
                record = await store.update(operation["id"], operation.get("data") or {}, client=client)
                if record is None:
                    raise FlowError(f"{operation['resource']} {operation['id']} not found", status=404, code="not_found")
                effects.append((operation["resource"], "updated", record))
            elif op == "delete":
                record = await store.delete(operation["id"], client=client)
            else:
                raise FlowError(f"unknown transaction operation {op!r}", code="bad_config")
            results.append(record)
    for resource, change, record in effects:  # only once committed
        await after_write(...)  # resource.<change> events, cache invalidation, realtime
    return results
```

Two things that make `db.transaction` behave differently from a sequence of `resource.create`/`resource.update` nodes:

<Steps>
  <Step title="Every operation shares one database transaction">
    All the writes run on the same connection inside `source.transaction()`. If any operation raises — a missing `update`/`delete` target, a constraint violation, a validation error — the whole block fails and **every** write in the list is rolled back, including ones that had already succeeded earlier in the list.
  </Step>
  <Step title="Effects fire only after the commit">
    The `resource.*` events, cache invalidation and realtime notifications that normally follow a write (see `after_write` in [the mental model](/concepts/mental-model)) are queued during the loop but only actually run **after** the transaction commits successfully — the comment in the runtime is explicit: `# only once committed`. A rolled-back transaction never emits a stray `orders.created` event for a row that no longer exists.
  </Step>
</Steps>

An `update` or `delete` targeting a record that doesn't exist fails the whole transaction with a `404` (`not_found`) — there's no "skip missing" mode; if you need to tolerate a missing target, check for it first with a `resource.get` and a `control.if` before building the operations list.

### Worked example: order placement with a stock reservation

A simplified version of the pattern the commerce blueprint uses when placing an order — the order row, its first line item, and a movement ledger entry, or nothing at all if any of them fails:

```json
{
  "id": "place_order",
  "data": {
    "block": "db.transaction",
    "config": {
      "operations": [
        {
          "op": "create",
          "resource": "orders",
          "data": {
            "store_id": "{{ vars.cart.store_id }}",
            "customer_id": "{{ vars.customer.id }}",
            "total_minor": "{{ steps.totals.output.0.total | int }}",
            "currency": "{{ vars.cart.currency }}",
            "status": "pending",
            "payment_status": "pending"
          }
        },
        {
          "op": "update",
          "resource": "carts",
          "id": "{{ vars.cart.id }}",
          "data": { "status": "converted" }
        }
      ]
    }
  }
}
```

<Note>
`db.transaction`'s `operations` only cover `create`/`update`/`delete` on **resources** — it can't run an arbitrary write statement the way `db.query` runs an arbitrary read. If a write genuinely needs raw SQL (a bulk `UPDATE … WHERE …` across many rows, say), that's outside what flows currently expose; do it in a migration, a Python [function](/code/overview) with direct database access, or ask for it in a future release. See [Custom blocks](/flows/custom-blocks) for the wider picture on what is and isn't extensible today.
</Note>

Because `db.transaction`'s operations are resource writes, each one still runs resource-level field validation (required fields, types, `min`/`max`, uniqueness) exactly as `resource.create`/`resource.update` would — a validation failure on the second operation rolls back the first just like any other failure inside the transaction.

<Tip>
For the very common "read, compute, then write several rows together" shape, put your `db.query`/`math.calculate` steps **before** the `db.transaction` node and feed their outputs into its `operations` templates, as in the example above (`steps.totals.output.0.total`). `db.transaction`'s own operations are plain JSON, not a sub-flow, so you can't branch or loop *inside* it — build the full `operations` list with a `control.foreach`/`control.set` pair beforehand if the number of writes is dynamic (see [Control flow → For each](/flows/control-flow#control-foreach)), then pass the finished list in.
</Tip>

## Common mistakes

<AccordionGroup>
  <Accordion title="Writing a caller-controlled value into db.query's sql instead of params">
    `"sql": "SELECT * FROM orders WHERE id = {{ input.params.id }}"` reopens SQL injection — templates render before the block runs, so that's string concatenation, not a bind parameter. Always keep the placeholder in `sql` (`WHERE id = ?`) and pass the value through `params`.
  </Accordion>
  <Accordion title="Expecting db.query to write">
    `is_read_only` refuses anything that isn't a `select`/`with`/`explain`/`pragma`/`show` statement, or that contains a write keyword anywhere. There's no override. Use `resource.create`/`update`/`delete` or `db.transaction`.
  </Accordion>
  <Accordion title="Forgetting math.calculate returns a float unless the whole result happens to be an integer">
    `divide`, `average`, and any `multiply`/`subtract` chain that doesn't land on a whole number will produce a float with full precision. Cast with `| int` (when the value is conceptually an integer, e.g. minor-unit money or a stock count) or chain a `round` step before writing the value to a field or a response body.
  </Accordion>
  <Accordion title="Treating db.query's output as a single row">
    `db.query` always returns a **list**, even for `SELECT COUNT(*)`. Read a scalar as `steps.<node>.output.0.<column>`, not `steps.<node>.output.<column>`.
  </Accordion>
  <Accordion title="Assuming db.transaction's writes are visible to db.query mid-transaction">
    `db.query` and `db.transaction` use separate connections/transactions (`db.query` never opens a transaction at all — it's a single autocommit read). A `db.query` step that runs after a `db.transaction` step sees its committed results; nothing running concurrently, or before the transaction commits, does.
  </Accordion>
  <Accordion title="Relying on time.now's format to imply a timezone conversion">
    `time.now` is always UTC, regardless of `format`. If a flow needs "9am store time," compute the offset explicitly with `offset_seconds` (from a store's stored UTC-offset field) rather than expecting the block to know about timezones.
  </Accordion>
</AccordionGroup>

## FAQ

<AccordionGroup>
  <Accordion title="Can db.query call stored procedures or functions?">
    Only ones invoked from inside an allowed statement — `SELECT my_func(...)`, say — and only if none of the forbidden words in `is_read_only` appear in the function's name or the surrounding SQL text. There's no separate "call procedure" block.
  </Accordion>
  <Accordion title="Does db.transaction retry on conflict?">
    No. If the underlying database raises (a serialization failure under concurrent writes, a constraint violation), the block fails the run like any other error — wrap it in [`control.retry`](/flows/control-flow#control-retry) if the operation is safe to retry, or design the writes so conflicts can't occur (e.g. a single `UPDATE … SET balance = balance + ?` rather than read-then-write).
  </Accordion>
  <Accordion title="Is transform.map the same engine resources use for their response shape?">
    Yes — `transform.map` calls `pawabase_kit.transformers.apply_transformer`, the identical function a resource operation runs on its way out. A transformer named for use on a resource works unchanged inside a flow. See [Transformers](/data/transformers).
  </Accordion>
  <Accordion title="Why is there no dedicated 'negate' or 'clamp' math operation?">
    `math.calculate`'s operation set is deliberately small. `multiply` by `-1` covers negation; `max`/`min` against a literal covers clamping at one bound. Both idioms are used throughout this platform's own blueprint flows rather than adding more operations to the block.
  </Accordion>
</AccordionGroup>
