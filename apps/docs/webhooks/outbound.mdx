**Outbound webhooks** deliver platform events to external endpoints via HTTP POST. When a subscribed event fires — whether from a resource write, a flow, or an explicit `event.emit` — Pawabase sends a POST request to each configured webhook endpoint with the event payload.

Unlike the internal event bus (which triggers flows and realtime), outbound webhooks send data **outside** your Pawabase backend — to partner APIs, external services, or webhook receivers like n8n or Zapier.

<CardGroup cols={2}>
  <Card title="Automatic" icon="clock">Subscribed to an event — fires on every matching resource write.</Card>
  <Card title="Manual" icon="hand-pointer">Use the `webhook.send` block in a flow to trigger delivery on demand.</Card>
</CardGroup>

## How outbound webhooks flow

```text
Event published (resource.write, flow, manual)
       ↓
Pawabase matches the event name to subscribed webhooks
       ↓
POST with signed payload to each endpoint URL
       ↓
Endpoint returns 2xx → delivery succeeds
Endpoint returns 5xx or times out → retry with backoff
After max retries → marked as failed
       ↓
Every delivery recorded in Studio's delivery log
```

## Creating an outbound webhook in Studio

1. Go to **Automate → Webhooks → Outbound**.
2. Click **New webhook**.

| Field | What it controls | Example |
| --- | --- | --- |
| **Name** | Identifier for this webhook in Studio | `partner-notifications` |
| **Events** | Which event names trigger this webhook | `orders.created`, `orders.*` for all order events |
| **URL** | The HTTPS endpoint that receives the POST | `https://partner.example.com/webhooks/order` |
| **Signing secret** | Secret used to sign the payload | Select an existing secret, or create a new one |
| **Custom headers** | Additional HTTP headers to include | `X-Custom-Header: value` |
| **Retry policy** | How many attempts and what backoff | Up to 5 attempts with exponential backoff |

<Note>
The URL must be an HTTPS endpoint. HTTP URLs are accepted only in development environments for testing purposes.
</Note>

### Subscribing to events

The **Events** field accepts:
- A specific event: `orders.created`
- All events for a resource: `orders.*`
- A wildcard for all events: `*`
- Multiple events: add each one separately

### Event payload format

When a webhook fires, the endpoint receives a JSON body:

```json
{
  "id": "evt_abc123",
  "event": "orders.created",
  "project": "acme",
  "env": "production",
  "data": {
    "id": "ord_001",
    "total": 2999,
    "status": "pending",
    "customer_id": "cust_123"
  },
  "sent_at": 1727520000
}
```

| Field | Description |
| --- | --- |
| `id` | Unique event identifier |
| `event` | The event name |
| `project` / `env` | Which project and environment emitted the event |
| `data` | The event payload (the record, or whatever was emitted) |
| `sent_at` | Unix timestamp of when the delivery was queued |

### Signature header

Every delivery includes a `Pawabase-Signature` header containing the HMAC-SHA256 signature of the payload. The endpoint should verify this signature to confirm the request came from Pawabase and wasn't tampered with.

See [Signatures](/webhooks/signatures) for verification code examples in every major language.

## Retry policy

If the endpoint returns a non-2xx status code or doesn't respond within 30 seconds, the delivery is retried:

| Attempt | Delay before retry |
| --- | --- |
| 1 | Immediate (first attempt) |
| 2 | 1 minute |
| 3 | 2 minutes |
| 4 | 4 minutes |
| 5 | 8 minutes |

After 5 failed attempts, the delivery is marked as **failed** and no more retries are scheduled. You can see the full delivery history and error messages in Studio.

<Warning>
The endpoint must respond within **30 seconds**. Anything slower is killed and counts as a failed attempt. Keep your endpoint fast — if you need to do long-running work, acknowledge immediately and process in the background.
</Warning>

## Manual delivery from flows

You can trigger webhook delivery on demand from a flow using the **`webhook.send`** block:

1. Add a **Platform → Webhook send** block to your flow.
2. Configure:
   - **Event** — the event name (e.g., `order.exported`)
   - **Payload** — optional JSON data (can use `{{ }}` expressions)

The block returns the number of endpoint deliveries that were queued:

```json
{ "deliveries": 3 }
```

<Info>
`webhook.send` triggers delivery to all outbound webhooks subscribed to the given event — regardless of whether a resource change triggered it. It's the manual equivalent of an event fire.
</Info>

## Delivery tracking in Studio

Every webhook delivery is recorded in Studio under **Automate → Webhooks → Deliveries**.

| Column | What it shows |
| --- | --- |
| **Status** | `delivered`, `failed`, or `pending` |
| **Event** | The event name that triggered the delivery |
| **URL** | The destination endpoint |
| **Attempts** | How many times the endpoint was contacted |
| **Duration** | How long the delivery took |
| **Response** | The HTTP status code and trimmed response body |
| **Error** | Error message if the delivery failed |

You can filter by:
- Webhook name
- Event name
- Status (delivered / failed / pending)
- Time range
- Error text

### Failed deliveries

Failed deliveries appear in the **Failed deliveries** tab. Each shows:
- The exact error (connection refused, timeout, 500, 403, etc.)
- All retry attempts and their error messages
- The full request payload and response (if any)

## Security

| Concern | How Pawabase handles it |
| --- | --- |
| **Signature** | Every delivery is signed with HMAC-SHA256 using the webhook's secret; the signature is in the `Pawabase-Signature` header |
| **Secret storage** | Signing secrets are encrypted at rest |
| **URL safety** | Private/loopback IP addresses are rejected (except in development) |
| **Timeout** | Each delivery times out after 30 seconds |
| **Retry caps** | Maximum 5 retries prevent infinite delivery loops |

### Best practices

<AccordionGroup>
  <Accordion title="Verify signatures on your endpoint">
    Always verify the `Pawabase-Signature` header before processing a webhook. Never trust a webhook request without signature verification. See [Signatures](/webhooks/signatures).
  </Accordion>
  <Accordion title="Respond 200 quickly">
    Your endpoint should return `200 OK` as fast as possible. Slow responses or non-2xx status codes trigger retries, which may cause duplicate deliveries.
  </Accordion>
  <Accordion title="Make endpoints idempotent">
    Webhook deliveries may be retried. Check the event `id` on every request and deduplicate — if you've already processed `evt_abc123`, return 200 and don't process again.
  </Accordion>
  <Accordion title="Monitor delivery status">
    Check Studio's delivery log daily. Failed deliveries indicate issues with the external endpoint that need attention.
  </Accordion>
</AccordionGroup>

## Common patterns

### Fan-out to multiple partners

A single event can trigger deliveries to multiple webhook endpoints:

```text
order.paid
   ├── POST to partner-a.com/webhook
   ├── POST to analytics.com/events
   └── POST to fulfillment.com/orders
```

Each delivery is independent — a failure in one doesn't affect the others.

### Event-driven integration

```text
Resource write
   → Event emitted
      → Flow processes (validation, enrichment)
      → event.emit (internal bus)
         → webhook.send (external delivery)
            → POST to external API
```

## Common mistakes

<AccordionGroup>
  <Accordion title="Not verifying signatures">
    Without HMAC verification, an attacker could forge webhook requests and trigger unauthorized actions on your endpoint.
  </Accordion>
  <Accordion title="Returning non-200 too slowly">
    Slow responses cause retries and potential duplicate processing. Acknowledge immediately, do work in the background.
  </Accordion>
  <Accordion title="Not handling duplicates">
    Retries mean the same event may be delivered multiple times. Use the event `id` to deduplicate.
  </Accordion>
  <Accordion title="Using HTTP instead of HTTPS">
    Production webhooks require HTTPS. Using HTTP in production sends data unencrypted over the network.
  </Accordion>
</AccordionGroup>

## Debugging checklist

When webhooks aren't delivering:

1. **Check the event name** — Go to **Automate → Webhooks → Outbound** and verify the event name matches what's being published.
2. **Check the URL** — Verify it's reachable from the internet (use a tool like webhook.site for testing).
3. **Check delivery logs** — Look at **Deliveries** for error messages.
4. **Verify signatures** — If verification fails on the endpoint, check that the signing secret matches.
5. **Check network** — The Pawabase worker must be able to reach the endpoint. Firewalls and VPNs can block this.

For more debugging guidance, see [Troubleshooting](/reference/troubleshooting).
