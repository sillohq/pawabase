**Inbound webhooks** let external services (GitHub, Stripe, Slack, etc.) send events into your Pawabase project. When an external service makes an HTTP POST to your webhook endpoint, Pawbase verifies the signature, records the event, and routes it to the matching flow trigger.

  <Card title="Receive" icon="inbox">Unique webhook URLs for each external integration.</Card>
  <Card title="Verify" icon="shield-check">HMAC signature validation with replay protection.</Card>
  <Card title="Route" icon="flow">Automatic dispatch to flows with matching triggers.</Card>

## How inbound webhooks work

```text
External service (GitHub, Stripe, …)
       ↓
HTTP POST to /hooks/v1/<slug>
       ↓
Signature verification (HMAC-SHA256)
       ↓
Event recorded in Studio's delivery log
       ↓
Flow with matching trigger.webhook runs
       ↓
202 Accepted
```

The entire process is asynchronous — the webhook endpoint responds `202 Accepted` immediately, and the flow runs in the background as a queued job. If the flow fails, it's retried according to the webhook's retry policy.

## Creating an inbound webhook in Studio

1. Go to **Automate → Webhooks → Inbound**.
2. Click **New inbound webhook**.

| Field | What it controls | Example |
| --- | --- | --- |
| **Slug** | The URL path segment | `stripe` → URL: `https://api.yourapp.com/hooks/v1/stripe` |
| **Name** | Human-readable label shown in Studio | `Stripe events` |
| **Secret** | Signing secret for HMAC verification | Select or create a secret |
| **Event pattern** | Which event names to match | `stripe.*` or leave empty for all |
| **Enabled** | Whether the webhook accepts requests | Toggle on/off in Studio |

<Note>
The slug becomes part of the public URL. Use a name that identifies the external service, not the action (e.g., `stripe` rather than `payment-success`).
</Note>

## The webhook URL

Every inbound webhook is served at:

```
https://<your-domain>/hooks/v1/<slug>
```

The gateway doesn't require a project API key for this path — the webhook's HMAC signature authenticates the request instead. This means external services can send webhooks without knowing your API keys.

Configure the URL in your external service's webhook settings:

```
https://api.yourapp.com/hooks/v1/github
https://api.yourapp.com/hooks/v1/stripe
https://api.yourapp.com/hooks/v1/slack
```

## Signature verification

Every inbound webhook request includes a signature header for verification. Pawabase supports two formats:

1. **Pawbase format:** `Pawabase-Signature: t=<timestamp>,v1=<hex_hmac>`
2. **Plain HMAC:** `X-Hub-Signature-256: sha256=<hex_hmac>` (for GitHub, Shopify)

See [Signatures](/webhooks/signatures) for verification code examples in every language.

<Note>
The timestamp tolerance is 300 seconds (5 minutes). Requests older than 5 minutes are rejected to prevent replay attacks.
</Note>

## Routing to flows

When a webhook is received, Pawabase looks for flows that have a **Webhook trigger** matching the webhook's slug. The trigger's `hook` field must match the slug exactly.

**Example:** A flow with a Webhook trigger configured for `github` will receive every request sent to `/hooks/v1/github`.

In the flow editor:
1. Add a **Trigger → Webhook** block.
2. Set the **Hook** field to the slug you configured (e.g., `github`).
3. Connect the trigger to your processing steps.

The flow receives the webhook's raw POST body as `$input`. From a GitHub webhook, for example:
- `$input.action` → `"opened"`
- `$input.issue.title` → `"Bug report"`
- `$input.repository.full_name` → `"acme/project"`

## Event emissions

You can also configure an inbound webhook to **emit a platform event** in addition to (or instead of) triggering a flow. This lets the webhook payload fan out to subscriptions, realtime channels, and other event consumers.

The event name follows the pattern `<slug>:<action>` where `<action>` is extracted from the webhook's configuration.

## Delivery records

Every inbound webhook request is recorded in Studio under **Automate → Webhooks → Inbound → Deliveries**. Each record shows:

| Field | What it means |
| --- | --- |
| **Status** | `delivered` (verified and processed), `failed` (signature rejected), `error` (processing error) |
| **Event** | The event name (for GitHub: the `action` field, e.g., `issue.opened`) |
| **Timestamp** | When the request arrived |
| **Response** | The HTTP status code returned |
| **Error** | Error message if verification or processing failed |
| **Duration** | How long processing took |

## Configuring retry behavior

When a flow triggered by a webhook fails, the failure is retried:

| Attempt | Delay | Behavior |
| --- | --- | --- |
| 1 | Immediate | First attempt |
| 2 | 5 minutes | Retry after 5 minutes |
| 3 | 15 minutes | Retry after 15 minutes |
| 4 | 1 hour | Retry after 1 hour |
| 5 | 6 hours | Final retry |

After 5 failed attempts, the delivery is marked as `failed` and the job is dead-lettered. You can inspect the full error trace in Studio's delivery log and retry it manually.

## Common webhook examples

### GitHub webhook

Configure GitHub to send to `https://api.yourapp.com/hooks/v1/github`. The payload looks like:

```json
{
  "action": "opened",
  "issue": {
    "number": 42,
    "title": "Bug report",
    "body": "The login button doesn't work",
    "state": "open",
    "user": { "login": "ada" }
  },
  "repository": { "full_name": "acme/project" }
}
```

In a flow triggered by this webhook, access the fields:
- `$input.action` → `"opened"`
- `$input.issue.title` → `"Bug report"`
- `$input.issue.number` → `42`

### Stripe webhook

Configure Stripe to send to `https://api.yourapp.com/hooks/v1/stripe`. The payload:

```json
{
  "id": "evt_123",
  "type": "payment_intent.succeeded",
  "data": {
    "object": {
      "id": "pi_123",
      "amount": 2999,
      "currency": "usd",
      "status": "succeeded"
    }
  },
  "livemode": true
}
```

In your flow:
- `$input.type` → `"payment_intent.succeeded"`
- `$input.data.object.amount` → `2999`

### Slack webhook

Configure Slack to send to `https://api.yourapp.com/hooks/v1/slack`. The payload includes the full event body from Slack's API.

## Error responses

| Scenario | Response | What to fix |
| --- | --- | --- |
| Invalid signature | `403 Forbidden` | Check that the signing secret matches the one in Studio |
| Timestamp too old | `403 Forbidden` | The external service's clock may be skewed, or the request was delayed |
| No matching flow | `202 Accepted` | The webhook was verified, but no flow has a matching trigger. Add a flow with a Webhook trigger matching the slug. |
| Flow fails | `202 Accepted` | The error is logged in the delivery record. Check the flow's execution trace in Studio. |

## Security considerations

- **Never disable signature verification** — without it, any request can trigger your flows.
- **Use HTTPS URLs** — webhook payloads can contain sensitive data.
- **Rotate secrets regularly** — update the signing secret in Studio when you rotate secrets.
- **Limit event patterns** — only accept the event types you actually need, reducing the attack surface.
