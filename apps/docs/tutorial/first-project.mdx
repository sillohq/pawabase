The quickstart exposed a public table. Real apps need **private data**, **relations**, **automation** and **live updates**. In this tutorial you build *Notebook*: users own notebooks, notebooks have notes, a welcome email goes out on sign-up, and open tabs see new notes instantly.

<Info>You'll use Studio for every step. Each step links to the page that explains the concept in depth.</Info>

## 1. Create the project

Create a project named **Notebook** (reference `notebook`). Copy the `development` publishable key.

## 2. Model the data

Create two resources in **Resources → New resource**.

<Tabs>
  <Tab title="notebooks">
    | Field | Type | Options |
    | --- | --- | --- |
    | `title` | Text (short) | required, max 120 |
    | `color` | Text (short) | allowed values: `lavender`, `peach`, `mint` |
    | `owner_id` | Text (short) | |

    **Behaviour → Owner field:** `owner_id`. Pawabase fills it with the caller's user id on every create, so clients can't forge ownership.
  </Tab>
  <Tab title="notes">
    | Field | Type | Options |
    | --- | --- | --- |
    | `notebook_id` | Integer | required |
    | `body` | Text (long) | required |
    | `owner_id` | Text (short) | |

    **Owner field:** `owner_id`. **Relations:** `notebook`, *belongs to* `notebooks` via `notebook_id`. **Behaviour:** turn on **Broadcast changes**.
  </Tab>
</Tabs>

Click **Create / migrate table** for both. [Defining resources →](/data/defining-resources)

## 3. Make it private

For both resources set every operation's policy to **Record owner (owner_id)** except **Create**, which stays **Signed-in users**.

The built-in `owner` policy is `{"owner": "owner_id"}`: signed in, and `record.owner_id` equals `auth.user_id`. On lists, Pawabase doesn't fetch everything and filter; it adds `WHERE owner_id = '<you>'` to the SQL, so pages and totals are exact. [How pushdown works →](/policies/pushdown)

Try it with two users:

```bash
# as Ada
curl -X POST localhost:8080/rest/v1/notebooks -H "apikey: $PK" -H "Authorization: Bearer $ADA" \
  -H "content-type: application/json" -d '{"title": "Ideas"}'
# as Bob: Ada's notebook simply isn't there
curl localhost:8080/rest/v1/notebooks -H "apikey: $PK" -H "Authorization: Bearer $BOB"
# {"data": [], "total": 0, ...}
```

## 4. Read with relations

```bash
curl "localhost:8080/rest/v1/notes?expand=notebook&sort=-created_at&per_page=10" \
  -H "apikey: $PK" -H "Authorization: Bearer $ADA"
```

Each note now carries its `notebook` object. `expand` accepts a comma-separated list of relation names. [Relations →](/data/relations)

## 5. Send a welcome email with a flow

1. **Mail templates → New**: name `welcome`, subject `Welcome to Notebook`, HTML `<p>Hi {{ email }}, happy writing!</p>`.
2. **Flows → New flow**, drag in:
   - **Event** trigger with event `user.created`
   - **Send mail** with *To* `{{ input.event.payload.email }}`, *Template* `welcome`, *Data* `{{ input.event.payload }}`
3. Connect them and **Save**.

Sign up a new user: the flow runs on the worker, and **Events & runs** shows the event, the flow run and its step-by-step trace. Until SMTP is configured, mail is logged as *suppressed* under **Events & runs → Mail**. [Flows →](/flows/overview)

## 6. Go live on the page

Because `notes` broadcasts changes, every create, update and delete is published on the channel `resource:notes`. In the browser:

```js
const ws = new WebSocket(`ws://localhost:8080/realtime/v1/socket?apikey=${PK}&token=${accessToken}`);
ws.onopen = () => ws.send(JSON.stringify({ type: "subscribe", channel: "resource:notes", ref: "1" }));
ws.onmessage = (e) => console.log(JSON.parse(e.data));
```

Create a note in another tab and watch it arrive. [Realtime →](/realtime/overview)

<Warning>
Channel access is a policy too. By default channels need a signed-in user; add a [channel rule](/realtime/channel-rules) so that people only receive changes they're allowed to read.
</Warning>

## 7. Promote to staging

**Project → Promote…**, from `development` to `staging`, all kinds. Definitions (resources, policies, flows, templates…) are copied; data, keys and secrets never are. Migrate the tables in staging and point your staging app at its own key. [Environments →](/operate/environments-and-promotion)
