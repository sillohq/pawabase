The quickstart proved that a client can authenticate and use a resource. This tutorial builds a more realistic backend: **Notebook**, a notes product in which every record belongs to a user, notes belong to notebooks, a flow reacts to sign-up, and connected clients receive note changes.

```text
User signs up
   └── user.created → welcome flow → mail

User creates a notebook
   └── owner_id set by Pawabase
       └── user creates notes
           ├── ownership policy protects each operation
           └── notes.created → realtime resource channel
```

You will configure everything through Studio and call only public application APIs from the client examples.

## Before you begin

Complete the [Quickstart](/quickstart) or be comfortable creating a project, resource, table, and application user. You need:

- access to Studio;
- the public gateway URL;
- a development publishable key;
- two test users for verifying isolation.

Use synthetic data. Do not test authorization with production accounts or records.

## 1. Create the project

In Studio, choose **New project → A blank project**.

| Field | Value |
| --- | --- |
| Name | `Notebook` |
| Reference | `notebook` |
| Description | `Private notebooks and notes` |
| Environments | `development`, `staging`, `production` |

Create the project and save the development publishable key. Work in `development` throughout this tutorial.

Set shell variables for later requests:

```bash
export PAWABASE_URL="http://localhost:8080"
export PAWABASE_KEY="your-development-publishable-key"
```

## 2. Configure authentication

Open **Services → Users & auth → Configuration**.

1. Enable sign-up.
2. Leave email verification off while testing locally.
3. Keep the basic password policy with a sensible minimum length.
4. Save.

Register two users through the public API:

```bash
curl -X POST "$PAWABASE_URL/auth/v1/signup" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email":"ada@example.com","password":"correct-horse-1","name":"Ada"}'

curl -X POST "$PAWABASE_URL/auth/v1/signup" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email":"grace@example.com","password":"correct-horse-2","name":"Grace"}'
```

Sign in each user and save their access tokens as `ADA_TOKEN` and `GRACE_TOKEN`:

```bash
curl -X POST "$PAWABASE_URL/auth/v1/token" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"grant_type":"password","email":"ada@example.com","password":"correct-horse-1"}'
```

Repeat with Grace's credentials.

## 3. Create the `notebooks` resource

Go to **Build → Resources → New resource**.

Use the name `notebooks`, an auto-incrementing `id`, and timestamps. Add:

| Field | Type | Required | Configuration |
| --- | --- | --- | --- |
| `title` | Short text | Yes | Maximum length `120` |
| `color` | Short text | No | Allowed values `lavender`, `peach`, `mint` |
| `owner_id` | Short text | No | No client default |

Under **Access**:

- enable **Create** with **Signed-in users**;
- enable **List**, **Get**, **Update**, and **Delete** with **Record owner (owner_id)**.

Under **Behaviour**, choose `owner_id` as the **Owner field**. Keep events and timestamps enabled.

Create the resource, reopen it, and choose **Create / migrate table**.

### Why create and read use different policies

There is no record owner until a record exists, so create checks only that the caller is signed in. Pawabase then fills `owner_id` from the authenticated user's identity. The client cannot choose another owner.

For existing rows, the owner policy compares the record's `owner_id` with the caller. On list operations, ownership is applied to the query so pagination and totals describe only visible rows.

<Warning>
Do not accept `owner_id` from a form and trust it as authorization. Configure **Owner field** so ownership is established at the backend boundary.
</Warning>

## 4. Create the `notes` resource

Create another resource named `notes` with an auto-incrementing `id`, timestamps, and these fields:

| Field | Type | Required | Configuration |
| --- | --- | --- | --- |
| `notebook_id` | Integer | Yes | References a notebook id |
| `body` | Long text | Yes | The note content |
| `owner_id` | Short text | No | Filled by Pawabase |

Configure access exactly as for `notebooks`: signed-in create, and record-owner list/get/update/delete.

Under **Relations**, add:

| Setting | Value |
| --- | --- |
| Name | `notebook` |
| Kind | Belongs to |
| Resource | `notebooks` |
| Foreign key here | `notebook_id` |

Under **Behaviour**:

- choose `owner_id` as the owner field;
- enable **Broadcast changes**;
- leave **Emit events** and **Timestamps** enabled.

Create the resource and run **Create / migrate table**.

<Note>
The relation makes expansion possible; it does not replace authorization. The policies on both resources still decide which records a caller can read.
</Note>

## 5. Verify ownership

Create a notebook as Ada. Do not send `owner_id`:

```bash
curl -X POST "$PAWABASE_URL/rest/v1/notebooks" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $ADA_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Product ideas","color":"lavender"}'
```

The response includes Ada's server-assigned `owner_id`. Save the returned notebook id:

```bash
export NOTEBOOK_ID="1"
```

Create a note:

```bash
curl -X POST "$PAWABASE_URL/rest/v1/notes" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $ADA_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"notebook_id\":$NOTEBOOK_ID,\"body\":\"Design the onboarding checklist\"}"
```

List as Ada:

```bash
curl "$PAWABASE_URL/rest/v1/notebooks?sort=-created_at" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $ADA_TOKEN"
```

Then list as Grace:

```bash
curl "$PAWABASE_URL/rest/v1/notebooks?sort=-created_at" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $GRACE_TOKEN"
```

Grace should receive an empty page, not Ada's notebook. Depending on the operation and whether a record can safely be disclosed, a disallowed single-record request may appear as `403` or `404`; client code should not use that difference to infer whether another user's private record exists.

## 6. Read a note with its notebook

Request notes with the named relation:

```bash
curl "$PAWABASE_URL/rest/v1/notes?expand=notebook&sort=-created_at&per_page=10" \
  -H "apikey: $PAWABASE_KEY" \
  -H "Authorization: Bearer $ADA_TOKEN"
```

Each visible note can include its expanded `notebook`. Expansion is useful for screens that need note and notebook details together, but avoid expanding data a client does not need. See [Relations](/data/relations) for supported relation shapes and limits.

## 7. Create a welcome mail template

Open **Automate → Mail templates → New mail template** and configure:

| Field | Value |
| --- | --- |
| Name | `welcome` |
| Subject | `Welcome to Notebook` |
| HTML | `<p>Hi {{ email }}, your notebook is ready.</p>` |
| Plain text | `Hi {{ email }}, your notebook is ready.` |

Save the template. Template placeholders are filled with the data passed by the sending block; a missing value should be caught in testing before the flow is enabled for production.

SMTP is deployment infrastructure in the current Studio. It is not configured on the mail-template screen or through a customer-facing API. Ask the Pawabase operator to configure it for the installation. Without an SMTP host, Pawabase suppresses delivery but records what would have been sent, which is useful for local testing.

## 8. Build the welcome flow

Open **Automate → Flows → New flow** and name it `welcome_new_user`.

In the flow editor:

1. Add an **Event** trigger.
2. Set the event name to `user.created`.
3. Add a **Send mail** block.
4. Set **To** to `{{ input.event.payload.email }}`.
5. Choose the `welcome` template.
6. Pass `{{ input.event.payload }}` as the template data.
7. Connect the trigger's success output to the mail block.
8. Save and enable the flow.

Create another test user. Open **Operate → Events & runs** and verify:

- a `user.created` event was recorded;
- the event matched the flow trigger;
- the flow run started;
- the mail block either completed or shows a useful delivery error.

Build against the event payload shown in Studio, not an assumed field. If you later want to address the user by name, add a lookup step and pass the lookup output into the template explicitly.

## 9. Subscribe to note changes

Because **Broadcast changes** is enabled, note writes publish resource-change messages to the `resource:notes` channel.

In a browser application, connect with the publishable key and current user's access token:

```js
const url = new URL("ws://localhost:8080/realtime/v1/socket");
url.searchParams.set("apikey", publishableKey);
url.searchParams.set("token", accessToken);

const socket = new WebSocket(url);

socket.addEventListener("open", () => {
  socket.send(JSON.stringify({
    type: "subscribe",
    channel: "resource:notes",
    ref: "notes-feed",
  }));
});

socket.addEventListener("message", ({ data }) => {
  const message = JSON.parse(data);
  console.log(message);
});
```

Create or update a note in another tab and inspect the message. Treat the database as the source of truth: after reconnecting, fetch the current records rather than assuming the client received every message while it was offline.

### Protect the channel

Resource policies and realtime channel rules protect different boundaries. The owner policy protects REST operations; it does not automatically design a per-user broadcast channel.

Open **Operate → Settings → Realtime** and review the default policy and channel rules before production. A shared `resource:notes` channel is unsuitable if its payload could reveal one user's records to another subscriber. Prefer a channel naming and publication design that can be authorized for one user or organization, and test with both Ada and Grace.

Read [Resource change broadcasts](/realtime/resource-changes) and [Channel rules](/realtime/channel-rules) before shipping this part.

## 10. Inspect the complete operation

You can now trace one action across the product:

```text
POST /rest/v1/notes
    ↓ publishable key selects development
    ↓ access token identifies Ada
    ↓ notes.create policy allows signed-in user
    ↓ owner_id is set to Ada by the backend
    ↓ fields are validated and the row is written
    ↓ notes.created is emitted
    ↓ resource change is published to realtime
    ↓ Studio records request, event, and downstream run data
```

Use these Studio areas during development:

| Question | Studio area |
| --- | --- |
| What data was stored? | **Build → Database** |
| Which operations and policies are active? | **Build → Resources → notes** |
| Who signed in? | **Services → Users & auth → Sign-in activity** |
| Did the event happen? | **Operate → Events & runs** |
| Which step failed? | The flow run's step trace |
| Is work queued or stuck? | **Operate → Jobs & queues** |
| Are requests failing broadly? | **Operate → Observability** |

## 11. Prepare staging

Do not point a staging application at development simply because its API works.

Promote definitions from the project page:

1. Choose **Promote…**.
2. Select `development` as the source and `staging` as the target.
3. Select the definition kinds needed by Notebook.
4. Promote.
5. Open the staging environment and run **Create / migrate table** for each resource.
6. Configure staging-specific mail, secrets, redirect URLs, CORS origins, and realtime rules.
7. Create staging test users.
8. Give the staging application only the staging publishable key.
9. Repeat the ownership and flow tests.

Promotion copies selected definitions. It does not copy resource data, users, sessions, keys, secrets, or infrastructure credentials.

## Production review

Before real users rely on Notebook:

- require and test email verification if email ownership matters;
- verify password, refresh-token, and session lifetimes;
- ensure `owner_id` is indexed and populated for every protected record;
- test list, get, update, and delete as both owner and non-owner;
- decide how deleting a notebook affects its notes;
- make flow side effects safe to retry;
- configure mail and inspect failed delivery behavior;
- authorize realtime channels independently from REST resources;
- restrict browser origins;
- keep secret keys on trusted servers only;
- back up data and test restoration;
- promote through staging rather than editing production first.

## What you learned

You built a backend system, not just two tables:

- authentication establishes user identity;
- owner fields establish record ownership at the server boundary;
- policies enforce access on every resource operation;
- relations connect application data;
- events decouple a change from downstream work;
- flows run business behavior visibly;
- mail integrates with an external delivery system;
- realtime informs connected clients;
- environments separate development, staging, and production.
